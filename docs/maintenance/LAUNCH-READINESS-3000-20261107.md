## 3000 / 10 万应如何拆开验证

- **长期积累**：若 10 万个联盟守卫均被加载且仍保持路由登记，按文档每 10 秒续期一次估算，约 1 万次键续期/秒，尚未算联盟等其他实体。这是条件估算，不是实测吞吐；Redis pipeline 会合并往返，但不会消除键处理、内存与冷启动成本。必须测加载增长、重启预加载、RSS 与续期成本，决定分片/卸载/归档是否必要。
- **物理房间**：如果 3000 在线同时进入 20 人物理房间，就是 150 个并发房间；不是用“8 房间短测通过”即可推算一台机器能承载。人数/房间只是示例假设，实际 tick、刚体/约束数和热点不同，容量须实测。
- **视野**：地图均匀分布与活动期间集中同一格/区域是两个负载。须固定 MaxVisible、NPC 数、更新频率、跨格率、场景数量；记录视野裁剪后的业务可接受性。
- **带宽**：测每客户端实际下行（全量、增量、重连峰值均计），总量约为 3000 × 单客户端速率，再计协议与服务间复制；没有实际样本前不报固定网卡配置。
- **跨服资产**：请求率、参与实体数、热点 key 和积压恢复速度决定 Saga/Remote 压力；注册人数不是 TPS。

建议验收顺序：业务闭环与目标配置 → 300/1000/3000 在线分档 → 实际目标硬件上的稳定窗口和长稳 → 保持业务负载注入故障与恢复 → 小流量开放。档位是建议，不是已经跑过；观察预算至少包括 p99/max 延迟、物理 tick 丢拍、内存/原生堆斜率、WAL/投影/消息积压、Redis 续期、拒绝/断线与恢复耗时。延迟和 RPO/RTO 阈值由产品/运维按业务承诺确定，资产防重及守恒必须精确核对。

## 部署拓扑先选定

生成的 k8s 服务默认单副本、固定 SID，例如 game 为 1000。不能直接把 replicas 改成多个而保留相同 SID，也不能让新旧 writer 并行使用同一 WAL。一个逻辑服可包含多个 game/cell/room/alliance SID；先落实玩家静态归属、房间/格路由、同 SID 故障重启和单实例锁，再谈实例数量。Remote owner 死亡不等于框架自动选新 SID 接管，现行恢复路线依赖原 SID 重启或受控迁移。

如果采用**独立 Gate + Lockstep 大快照**，现行已知边界是 Game 准入不等于 Gate 写出，慢链路可断开循环。嵌入 TCP 的 Linux 夹具修复不覆盖该架构；需选择已有写出保证的链路或补齐 Gate 写出回执并验收。普通 EntitySync 不应与 Lockstep 的这项缺口混为一谈。

备份需覆盖所用权威数据：Mongo 与未投影 WAL 的一致恢复、Saga JetStream 权威日志/快照及必要 Redis 业务数据。明确可丢的缓存与不可丢的权威状态；不把运行中的目录复制当成一致快照。部署工具有回滚脚本，不代表任意格式变更都能安全回滚。

## 实际工程发布检查

在首发业务工程执行（使用固定 core/CLI 版本）：

```bash
make ci
make release-check
# 实际挂载的生产文件逐服务检查，不仅检查开发配置
roost config check --service game --file /path/to/config.game.prod.yaml --production
```

各服务配置检查后，还需用项目支持的配置入口对整套生产配置做跨服务一致性校验（SID、NATS 前缀、Redis namespace、Mongo 库、票据签名等）；`--all` 默认检查 manifest 声明的文件，不自动证明仓库外 Secret 正确。`project doctor` 是工程门禁，不替代目标部署、外部连接和业务恢复。

本轮未修改运行时、未部署或启动压测。此前批准的基准文件保持不变。实际生产配置与硬件尚未提供，暂不指定机器台数，不签发上线容量结论。建议首个实施切片是联盟迟到成功业务闭环与 UGC 物理/Level/Unity 联合验收；同时建立可复跑的 10 万数据／3000 在线场景规格。

本轮额外检查：在本机正式生成的 v1.42.2 game-demo 上补齐 `--skip-deps` 后的依赖，再运行 `project doctor`，退出 0，无 FAIL/WARN，生成物最新、全部包与测试可编译。见 [doctor 输出](evidence/launch-readiness-20261107/doctor.log)。此前首次 doctor 因局部测试只解析部分依赖、go.sum 缺项失败，`go mod tidy` 后通过，不记为框架缺陷。这是样板工程证据，不是用户生产工程验收。
