# v1.54.0 开房联机功能审查

被测版本为发布标签 v1.54.0（`9b7db7bf7`）。从 v1.53.0 到该标签共变更 672 个文件。本轮重点审查房间席位、房主交接、客户端快照与 WebSocket 写期限，并运行账号、配置导出和模块配置的定向测试。收尾核对 main `8940ca73c`，下述三处逻辑均保留，TS 客户端同文件的后续变更集中于 leave 的返回值。

## RV-20261118-02 · P2 · TS 房主的旧快照覆盖新任期状态

玩家 A 在 epoch 0 当房主时发起一次异步取快照。快照尚未返回，A 把房间交给 B，B 又交还给 A。A 已在 epoch 2 推出最新状态。这时旧请求返回，SDK 只检查当前是否有连接且自己是否为房主，按当前计数给旧数据分配了更大的序号。relay 接受它并记录为 epoch 2 的最新快照。现场定位见 [TS pushSnapshot](https://github.com/tjbdwanghaibo/roost-core/blob/v1.54.0/client/ts/src/client.ts#L665) 和 [relay storeSnapshot](https://github.com/tjbdwanghaibo/roost-core/blob/v1.54.0/service/relay/room.go#L435)。

两个 Node 客户端通过 WebSocket 连接同版本实际 Go lobby 与 relay，房间目录使用内存。A 等满最小快照间隔后放行旧请求，再正常离开。三轮中 B 都收到序号 `8589934594` 的 `epoch-zero-state`，预期为此前成功发布的 `epoch-two-state`。另用 SDK 的测试连接控制回调，任期不变时三轮均发出一帧，跨任期时三轮也都错误发出一帧。慢取快照与异步压缩都会经过同一处发送前判断。

建议在取状态前绑定连接与房主任期，在异步操作结束、分配序号前校验两者。回归应同时断言过期请求没有占用序号、没有发送或保存快照，并验证下一任房主恢复的实际内容。

## RV-20261118-03 · P2 · 已开局房间遇到报告乱序，主动离开的玩家仍可回座

成员 A 已经上线，房间进入 started。A 经 relay 主动离开，relay 发出 seq 2 的 left，再发出只有房主在线的 seq 3 心跳。若大厅先处理心跳，全房水位先到 3。它把 A 视为普通掉线，保留 Connected。迟到的 left 未进入清理分支，下一次正常心跳仍保留离线席位。A 再 join 得到成功，新人本应收到 ErrRoomStarted。报告发布允许不同 goroutine 并发，这是实现支持的交付顺序。见 [报告接口](https://github.com/tjbdwanghaibo/roost-core/blob/v1.54.0/service/relay/report.go) 和 [大厅合并报告](https://github.com/tjbdwanghaibo/roost-core/blob/v1.54.0/service/lobby/events.go#L126)。

内存目录调用实际建房、加入、开局、报告和再加入入口，三轮乱序均留下离线席位，三轮同序对照均正确拒绝再加入。建议按成员记录最近连接或离席的代次，使其他事件推进房间水位时仍能收敛该成员的离席事实。同时保留已有的「旧 left 晚于同一成员真实重连」用例，避免反向清掉新席位。

## RV-20261118-04 · P3 · Linux WebSocket 写期限回归被对端读超时干扰

原测试让 TCP 接收缓冲为 4 KiB 的客户端在 5 秒内完整读取 4 MiB，失败时服务端报 broken pipe，并将原因指向旧写期限。对照保留发送量、对端停读时间和新的一分钟写期限，撤掉旧写期限后仍连续两次失败。两次客户端都只读到 253942 字节便报 context deadline exceeded。仅恢复默认接收缓冲，两轮都收到完整消息。证据定位到测试条件，生产旧写期限故障没有由此复现。见 [测试夹具](https://github.com/tjbdwanghaibo/roost-core/blob/v1.54.0/infra/network/wsconn/wsconn_test.go#L156)。

建议将「新写操作已阻塞」设为可观测的同步条件，再让接收端排空数据。保留旧期限到期、刷新期限后仍能继续使用连接的断言，失败时同时打印对端读结果。
