## 已采用：按实体类型区分同步频率（2026-11-09）

状态：**用户已确认采用，待 main 实施。** 以下为实施契约，不再是候选建议；具体 API 名称与内部数据结构由 main 实施时确定。

Player/Monster 使用 on_change；TerrainChunk 的常规脏增量每 1 秒合并一次，干净块不发送。这里的 chunk 指持久地形实体，不是物理房间实时运动对象；物理状态不能一起降到 1Hz。

### 当前代码并未直接支持同 Manager 混用

[ManagerConfig](https://github.com/tjbdwanghaibo/roost-core/blob/f0ff1727/framework/sync/entitysync/manager.go#L25) 的 Mode、Interval、OnChangeBatchWindow 是 Manager 级；[NamespaceLimits](https://github.com/tjbdwanghaibo/roost-core/blob/f0ff1727/framework/sync/entitysync/namespaces.go#L19) 只区分对象容量和快照预算，尚无按类型频率。将现有 Manager.Interval 直接改成 1 秒或设置全局合批窗口，不能实现用户要求的隔离。

采用在同一 Manager 内增加独立的 subject 调度策略，按实体类型映射；现有 namespace 可作为 terrain 的配置匹配键，但不同类型共用 namespace 时应允许类型级规则，不能把 namespace 等同于实体类型。容量配置与调度配置保持不同职责。不为此随意拆成两个 Manager，避免改变会话、epoch 和引用表的归属。

### 已采用的行为契约

- 未显式配置的类型保持现有行为；Player/Monster 沿用 on_change 的事务确认与解锁后发送契约。on_change 是状态合并，不保证每个 setter 都发一帧。
- TerrainChunk 仅常规增量按 1 秒到期调度：从干净变脏时设定本批次到期时间为当前单调时间 + 1 秒，后续修改合入该批次且不续期；未到期保持脏集合；其他类型触发 Flush 不应顺带提前清掉它。连续编辑不得不断后移到期时间，避免永远发不出。
- 周期类型不应仍在每次提交走昂贵的 on_change 内容冻结，只在安全的捕获时机取状态；同时保留 CommitLSN 持久确认门槛、版本连续性、失败重试和每订阅者恢复契约。不能仅在最终发送时加时间判断。
- 首次入场全量、重连/断档恢复、权限变更和 remove 不受常规 1 秒增量节流拖延，但继续受既有快照/发送预算。普通显式 Flush 遵守到期；Drain/Stop 绕过此延迟，按现有交付与退出契约处理剩余已确认状态，不绕过持久确认、发送预算或错误处理，也不把强制处理等同于客户端必达。
- 到期后的捕获/确认必须区分新旧脏代际，不能把捕获期间的新修改一起清除；不能让一个新订阅者的即时全量推进其他观察者的基线、丢掉他们待发的增量。
- 调度只登记脏 subject，避免空闲块每秒全扫描编码；可采用到期队列或时间轮，具体结构由实施方选择。按首次变脏时间分散到期，避免统一整秒集中处理；同拍大批变脏仍需服从既有发送预算。
- 地形服务端权威碰撞/移动使用最新已提交地形；1 秒是向客户端下发的节奏，不是延迟服务端生效。编辑者预览与其他玩家地面更新正常运行下约增加 0～1 秒合并等待，另计队列/网络/重试时间；不承诺故障或过载下的硬延迟上界；P3/P6 接入时必须验证站立、挖脚下、跨边界与纠偏体验。

### 收益与限制

重复改同一批点可合并为最终状态，减少事务后捕获、编码、帧头和扇出次数。但每秒持续编辑不同点时，必要数据仍要发送，不保证下行按频率等比下降。地形变化树有 4096 节点预算，延长积累窗口可能触发整树回退全量，抵消节省；需要记录全量回退率、每秒编码次数、字节数、脏积压及发送延迟。周期同步不能替代编辑限流或容量验收。

### 实施验收清单

1. 同一会话混合三类对象：Player/Monster 及时发送；以可控单调时钟验证：首次变脏后 999ms 不发常规增量，1000ms 到期后在下一次可用调度中合并发送；干净地形不发送。
2. 连续地形编辑不会无限延迟；其他类型的高频唤醒不破坏地形 1 秒节奏。
3. 首次进入、重连、断档、remove、持久确认尚未完成、发送失败和 Drain/Stop 都保留正确生命周期。
4. 多观察者中途加入、离开与重新订阅，不丢老观察者的变化；捕获并发新编辑不丢脏数据。
5. 小范围重复刷和不同点分散刷分别验证节点预算/整树回退，报告 CPU、字节量与延迟的取舍；功能验证与压测分开，后续按用户安排执行。
