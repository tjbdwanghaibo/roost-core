## 交接文档点名的几条

**机器人负载 100 / 200 人同秒起跑不通过（第 28 条）**
- 现有证据：2026-10-22 成功 24 / 100、30 / 200；2026-11-14 在忙的机器上重测是 96 / 100、72 / 200，爬坡反而更差。两次都标着“尚未确认”。
- 上次停在：推断是 demo 场景的共享热点加同秒突发，以及前一轮的 saga 积压被下一轮继承。两条推断都没有对照实验。
- 下一步：条目自己写了——空闲机器上，每轮用全新环境（`mirror-local clean/up` 并重新部署）重跑。
- 本机能不能做：能，但必须是空闲的机器。本轮的机器一直有别的会话在跑（负载 4～13），现在跑出来的数字不能用。
- 条目里“证据在本轮 scratchpad 的 122/”指向的是临时目录，不在仓库里，**可能已经没有了**，没有核对。

**登录潮里 account CreateRole 超时（第 38 条）**
- 现有证据：只在 chat 抢写风暴下复现过（2 轮中 1 轮），无风暴的 21 轮都没有。Redis 变慢的推测已经排除。
- 上次停在：account 的 Redis 连接池、NATS 排队、整机 CPU 三个方向没有排除；条目写“要给 account 加 RPC 处理时长与连接池等待的指标再复现”。
- 难点：条目最后一句写“风暴条件已由 chat 写排队与公告合并去掉”，也就是**当初能复现它的条件现在已经不存在了**。
- 要维护者定：是先加指标（要改代码），还是接受“触发条件已消除，记为未归因”。

**Remote 128 / 256 并发约 3s 的全体超时簇（第 8 条）**
- 现有证据：历史 8 轮在高负载、高 swap 下有 20 簇；2026-11-14 的 M-19 在负载 3～5 下没有复现。
- 条目自己的结论：本机没复现只说明该窗口没复现，要在安静的目标硬件上各跑至少 8 轮，并保留停顿时的栈、fsync 与 outbox 指标、主从慢日志。
- 本机能不能做：不能代替目标硬件。本机能做的只有再跑一次，意义不大。

**换服的两条（Q4、期限只记录）**：见 B 类，做法已定，等放行。

**CellWorld 业务适配进模块**：维护者说先不做，不展开。
