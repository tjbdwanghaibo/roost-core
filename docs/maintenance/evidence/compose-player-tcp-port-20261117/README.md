# 生产 compose 不发布玩家 TCP 7000：来由排查（交接 A2，2026-11-17）

对应 [KNOWN-LIMITS 二“大厅 lobby 与转发 relay：遗留”](../../KNOWN-LIMITS.md#大厅-lobby-与转发-relay遗留) 里“生产 compose 不发布玩家 TCP 7000，尚未确认”一条，以及 [deploy 组证据](../lobby-relay-deploy-20261117/README.md) “拿不准”第 3 条。

只读排查，没有改代码。源码行号按 main 的 `742ccafc`（到 `7db0c1ca` 为止，这里引用的文件没有变化）。

## 结论

**是遗漏，不是有意为之。** 生产 compose 引入时（`032dcedf`，2026-08-30）就没有给任何服务写 `ports`，之后也没有人补。按下面“查法”列出的范围，没有找到“compose 由外部负载均衡发布端口”这样的约定（这是“没找到”，不是“证明了不存在”）；而生成工程自己的文档写的是相反的话（模板会声明 7000）。

**实测确认了后果**：按生成的 compose 原样起容器，程序在容器里监听着 7000，但在容器的宿主机上连不到它；加上 `ports` 之后就能连到（第 6 节）。

修复还没做（要等协调者推送之后），修法见“修法”一节，其中有两点要维护者定。

### 2. 现在生成的结果互相矛盾

用工作区的生成器实际生成一个带玩家 TCP 的工程（`roost project new planet -module example.com/planet -mods configdata,mongo,nats,dataengine,nest -template game-demo`），看生成的文件：

| 文件 | 7000 |

| `deploy/docker/docker-compose.prod.yaml` | 整个文件 `ports:` 出现 0 次 |
| `deploy/docker/README.md` | `docker run` 示例有 `-p 9100:9100`、`-p 7000:7000`，并写“Player TCP 已声明，因此示例同时发布 7000；若生产配置修改 player_access.tcp.addr，端口映射、LB 和防火墙必须同步修改” |
| `deploy/k8s/base/game.yaml`、`network-policy.yaml` | `containerPort: 7000`、Service `player-tcp` 7000、NetworkPolicy 放行 7000 |
| `configs/service/config.game.prod.example.yaml` | `player_access.tcp.addr: 0.0.0.0:7000` |
| `docs/PLAYER_ACCESS_TCP.zh-CN.md` | “Docker/Kubernetes 模板会为拥有 player TCP 的 Service 声明 7000”（源：`codegen/internal/roost/render_workflow_docs.go`；`codegen/docs/PLAYER_ACCESS_TCP.zh-CN.md` 有同一句） |

也就是说：文档承诺 Docker 模板声明 7000，docker run 示例和 k8s 都做到了，只有生产 compose 没做到。

说明：这次生成是在 `9dcd5a2f` 加 portal 组当时未提交的改动上跑的；`render_deploy.go`、`render_cicd.go`、`lobby_relay.go` 在 `742ccafc` 里没有变化（`git diff --stat 9dcd5a2f 742ccafc -- <这三个文件>` 为空）。生成过程最后一步 `go mod tidy` 因为沙箱不许写 Go 编译缓存而失败，部署文件在那之前已经写出，不影响这里看的内容。

### 3. 使用者没有不改生成物就能补上端口的办法

- `docker-compose.prod.yaml` 文件头是 `# Code generated by roost-codegen. DO NOT EDIT.`，`roost project sync` 会重写它，doctor 的 `checkCICDTemplates` 也检查它在不在。
- `deploy/docker/deploy.sh` 与 `rollback.sh` 写死 `docker compose --env-file … -f deploy/docker/docker-compose.prod.yaml`，没有第二个 `-f`，也没有 override 文件的入口。
- compose 没有声明 `networks`，用的是项目缺省的 bridge 网络。不发布端口时，宿主机以外的负载均衡连不到容器的 7000；要连只能另起一个接进这个网络的代理容器，这一点没有任何文档提过。

所以按 README 的步骤 `sh deploy/docker/deploy.sh` 部署出来的 game（或 Gate），玩家从宿主机外面连不上。

### 4. 为什么一直没被发现

- 容器的就绪探测在容器里面跑（`/app/healthprobe http://127.0.0.1:9100/readyz`），`deploy.sh` 用 `up --wait`，不经过发布的端口，缺端口时照样显示部署成功。
- `make compose-check` / 生成工程的 `deploy/docker/compose_check_test.go` 只核对 read_only、user、cap_drop、tmpfs、停机宽限期、healthcheck 和卷，不看端口。
- 仓内没有用生产 compose 起服务再让玩家或机器人连进来的脚本（`grep -rn 'docker-compose.prod' scripts/ wiring/scripts` 没有结果），真实进程的验收都走 `deploy/dev/run.sh` 或直接起二进制。

### 5. 目前的不一致

声明了 websocket 的工程里，Gate（或嵌入 TCP 的玩家服务）在生产 compose 里发布了 7080，却没有发布同一个服务的 7000。`codegen/internal/roost/player_websocket_test.go` 的 `TestPlayerWebSocketPortIsDeployed` 断言 compose 里恰好只有 7080 这一段 `ports`，等于把“不发布 7000”也钉住了；修的时候这条断言要按新行为改写（不是放宽）。

### 6. 实测：按生成的 compose 原样起容器，宿主机上连不到 7000（2026-11-17）

环境：macOS 上用 Colima 0.10.3 起一个 Linux 虚拟机（aarch64，2 核 2G，containerd 运行时），客户端是虚拟机里的 nerdctl compose v2.3.1，没有用 docker。虚拟机就是容器的宿主机，相当于生产上的那台 Linux 机器。

被测文件：第 2 节生成的 `deploy/docker/docker-compose.prod.yaml`，测试中没有改它。测完后用 `7db0c1ca` 的生成器把同一个工程重新生成了一遍，这个文件逐字节相同。

做法：另加一个覆盖文件，只把 `game` 服务的启动程序换成 busybox 的 httpd，让它在容器内 7000 端口应答一个固定标记，并关掉健康检查；覆盖文件里不写任何端口。镜像用 `docker.io/library/busybox:1.36.1`，只启动 `game` 一个服务。用替身程序是因为真实的游戏镜像要在容器里编译并下载依赖，这次没有做。

| | 用到的 compose 文件 | 发布的端口（`nerdctl port`） | 容器内访问 `127.0.0.1:7000` | 宿主机（虚拟机）上访问 `127.0.0.1:7000` |
| --- | --- | --- | --- | --- |
| 基线 | 生成的那一份 + 换程序的覆盖文件 | 空 | 拿到标记 | 连接被拒绝（curl 退出码 7）；宿主机上没有进程监听 7000 |
| 对照 | 再加一个覆盖文件：`ports` 写 `7000:7000` 和 `17000:7000` | 7000 → 0.0.0.0:7000，7000 → 0.0.0.0:17000 | 没有重测 | 拿到标记 |

对照组里从 Mac 上访问 `127.0.0.1:17000` 也拿到了标记。Mac 自己的 7000 端口当时被本机另一个开发用的 gate 进程占着，所以 Mac 一侧用 17000 来测，主测点放在虚拟机上。

说明了什么：程序在容器里监听着 7000；按生成的 compose 原样部署，宿主机上没有任何端口通到它；加上 `ports` 之后同样的访问就通了。对照组同时证明这个测法能测出“已发布”，基线的“连不上”不是环境本身不通造成的。

测完后容器、卷、这次建的虚拟机都已删除。

## 尚未确认

- **ops 9100 在 compose 里也没有发布**，而 docker run 示例有 `-p 9100:9100`。这一条更像是有意的（探测在容器内，运维面不该直接对外），但同样没有文字依据，抓指标（`/metrics`）的采集器从宿主机外也够不到。本次没有判断它，留给维护者。
- 实测用的是替身程序，不是真实的游戏镜像：没有构建生成工程的镜像，也没有让真实客户端握手。修的时候应当用真实镜像补一次。
- 实测的客户端是 nerdctl compose，不是 `deploy.sh` 里写的 `docker compose`。“不写 `ports` 就不发布”是 compose 的通用行为，两者应当一致，但 docker 那一边没有实跑。
- 只起了 `game` 一个服务，没有起整套（其余 10 个服务和它们依赖的 Mongo、NATS 等）。

## 修法（等推送之后做）

1. `codegen/internal/roost/lobby_relay.go` 的 `composeClientSettings`：`playerTCPEnabled(m) && servicePlayerListener(m, service)` 时，在 `ports` 里先写 `"7000:7000"`，再写原来的 `serviceClientPorts`。条件和 k8s 的容器端口、NetworkPolicy 用的是同一组函数：有独立 Gate 时只有 Gate 发布，嵌入 TCP 时是拥有玩家接入的那个服务。生产 compose 每个服务只有一个实例（`container_name` 固定），宿主机端口不会互撞。
2. 先红后绿：先写用例——嵌入 TCP 与独立 Gate 两种工程的 compose 里监听服务有 `"7000:7000"`、别的服务没有；没有玩家接入的工程 `ports` 仍为空——看它变红，再改。变异：撤掉那一行，用例变红。`TestPlayerWebSocketPortIsDeployed` 的 compose 断言改成“同一段 `ports` 里有 7000 和 7080”。
3. 逐字节对比：没有玩家接入的工程不变；有玩家 TCP 的工程只有 `docker-compose.prod.yaml` 多出 `ports` 两行（这是预期的变化，CHANGELOG 要写明）。
4. 文档：生成的 docker README 把“示例同时发布 7000”改成“示例与生产 compose 都发布 7000”；`docs/framework/GATEWAY.md` §6 部署模板一句；`codegen/docs/PROJECT_GENERATOR.zh-CN.md` 的部署表。
5. 验证：`GOWORK=off go test -race ./codegen/internal/roost/`、`go vet`；生成一个带玩家 TCP 的工程跑 `make compose-check`；有 docker 的机器上 `compose up` 后从宿主机连 7000 握手一次。

## 要维护者定的点

1. 是否按遗漏处理、照上面的修法补上 7000。
2. 发布的写法：`"7000:7000"` 会绑在宿主机的全部地址上，和 deploy 组给 lobby、relay、7080 的写法一致。如果生产上约定前面一定有负载均衡，可以考虑改成只绑内网地址（例如经 `.env.production` 里的变量），那样四类客户端端口应该一起改。
3. ops 9100 要不要在 compose 里发布（或写明不发布、指标怎么抓）。
