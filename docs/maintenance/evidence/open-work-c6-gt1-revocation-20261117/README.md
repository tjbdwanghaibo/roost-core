# 方案：游戏账号 token（gt1）的吊销（交接 C6，2026-11-17）

状态：**方案，未实施**。要不要做由维护者定；这份文档只把判断依据摆出来。源码行号按 main 的 `742ccafc`。

## 现状

- 格式：`gt1.<过期秒>.<游戏>.<账号>.<签名>`，无状态的签名，不落库（`service/account/game_token.go:17-30`）。里面没有 token 自己的编号，也没有“第几代”的字段。
- 有效期按游戏配置（`account.games.<game>.token_ttl`，`service/account/account_rpc.go:124`）。
- 校验（`service/account/game_token.go:141-163`）：验签和过期 → 游戏还在配置里 → **重读一次账号**，被封的当场拒绝。
- 谁在校验：lobby 的每个接口都校验一次（`service/lobby/rooms.go:61`，经 `wiring/lobby/lobby_mod.go:175-181` 调 account）。
- 谁在签发：portal 的 `POST /portal/game-token`。
- 已登记：“不落库、不能单张吊销，有效期内可重复使用（封号对 gt1 当场生效）”（`docs/maintenance/KNOWN-LIMITS.md:499`）。

所以现在让一张 gt1 失效的办法只有两个：等它过期，或者封号。

## 先分清需求

“吊销”可能指三种不同的事，需要的机制不一样：

| 场景 | 需要什么 | 现在能不能做到 |
| --- | --- | --- |
| 运营要把一个人赶下线 | 让这个账号的所有 token 失效 | 能，封号 |
| 玩家改了密码，或怀疑 token 泄露，要让旧的全部失效，但账号要能继续用 | 让这个账号**在此之前签发的**所有 token 失效 | 不能 |
| 玩家在这台设备上登出，别的设备不受影响 | 让**这一张** token 失效 | 不能 |

还有一个范围问题：**gt1 只在调用 lobby 接口时校验。** 已经拿到的 relay 令牌、已经连上 relay 的连接，不会因为 gt1 失效而断开。吊销 gt1 能阻止的是“之后再建房、加入、重连”，不是“把人从正在进行的房间里踢出去”。后者要另外通知 lobby 和 relay，是更大的一件事。（relay 令牌的有效期与验权流程我没有在这份方案里重新核对。）

## 选项

| | 做法 | 存储与开销 | 能覆盖的场景 |
| --- | --- | --- | --- |
| 1 | 不做。文档写明：靠较短的有效期加封号 | 无 | 第一种 |
| 2 | 账号上加一个“token 代数”，token 里带上签发时的代数；改密码、登出全部设备时代数加一；校验时比较 | 账号记录多一个数字。校验本来就要重读账号，**没有额外的读** | 第一、二种 |
| 3 | token 里带一个随机编号；吊销时把编号写进一张带过期时间的表（过期时间等于 token 剩余的有效期）；校验时多查一次 | 每次校验多一次读；要定这张表放在哪、多个 account 实例之间怎么保持一致、查不到表时是放行还是拒绝 | 三种都能 |

选项 2 与 3 可以都做，也可以只做 2。

## 判断依据

- 如果有效期配得短（例如几分钟到十几分钟），第二、三种场景的风险窗口本来就小，选项 1 可能就够了。**现在各游戏实际配的有效期是多少，要先看一下。**
- 选项 2 很便宜：不加存储、不加读、不引入新的故障方式。它解决不了“只登出这一台设备”。
- 选项 3 是唯一能做到单张吊销的，但每次 lobby 调用都多一次读，而且多了一个“吊销表不可用”的故障方式要处理。
- token 格式要变（加字段）。线上未部署，不需要兼容旧 token；但 gt1 的注释里写明它和另外两种凭证靠“前缀和段数都不同”来互相区分（`game_token.go:19`），加段之后要确认仍然不会和别的凭证混淆，版本前缀建议改成 `gt2`。

## 影响面（选 2 或 3 时）

- `service/account`：token 的签发与校验、账号记录（选 2）、吊销表（选 3）、新增的吊销接口。
- 调用吊销的入口：portal 是否要加“登出”接口；`accountctl` 是否要加一个运维命令。
- `modules/account_auth`、`modules/portal`、`modules/login`：这三个模块最近刚拆过，调用点要按当前源码重新核对，我没有读。
- lobby：接口不变（它只拿校验结果）。
- 文档：方案 §4.1.1、KNOWN-LIMITS 那一条、portal 的接口说明。

## 测试（先红后绿）

- 选 2：签发 → 代数加一 → 旧 token 校验被拒，新签发的通过（现在旧 token 仍然通过，先红）。封号的行为不变。
- 选 3：吊销一张 → 这一张被拒，同一账号的另一张仍然通过；吊销记录在 token 过期后自动消失；吊销表不可用时按定好的方式处理。
- 都要有：改了 token 里的代数或编号，签名对不上（防篡改）。
- 变异：校验时不比较代数 / 不查表 → 对应用例变红。

## 需要维护者定的点

1. 做不做。先确认：真实的需求是上面三种场景里的哪几种。
2. 各游戏的 gt1 有效期打算配多长（这决定选项 1 够不够）。
3. 选 3 的话：吊销表放在哪；查不到时放行还是拒绝。
4. 吊销之后，要不要同时把人从正在进行的房间里断开（另一项工作）。
