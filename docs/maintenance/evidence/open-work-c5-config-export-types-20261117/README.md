# 方案：配置导出的类型范围，三个小项（交接 C5，2026-11-17）

状态：**方案，未实施**。三项互不依赖。源码行号按 main 的 `742ccafc`。

三项都已经在 KNOWN-LIMITS 里如实登记（`docs/maintenance/KNOWN-LIMITS.md:540、542、543`）。按证据看，它们的性质不一样：

| 项 | 性质 | 依据 |
| --- | --- | --- |
| (a) 具名类型不支持 | 范围限制 | 生成器明确拒绝并报错，文档写明了替代办法 |
| (b) 浮点规范写法两端不同 | 两端不一致，是缺陷，影响面小 | 同一个值两端算出的比较键不同 |
| (c) 运行时转换的行号 | 报错信息不准，是小缺陷 | 同一张表，生成步骤报文件行号，运行时报序号 |

## (a) 具名类型

### 现状

- 生成器只看字段的 Go 类型表达式（一段文本），不解析类型。可建索引的类型是一张固定的表：string、bool 和各种整数（`codegen/internal/tablegen/side.go:136-141`，注释写明“生成器不知道具名类型的底层类型”）。
- 导出给 C# 时同样按类型表达式查表，查不到就报错（`codegen/internal/roost/client_config_csharp.go:90-92`）。
- 现在的替代办法：给字段写 parser（客户端拿到原文字符串），或者标成只给服务端。

### 选项

| | 做法 | 代价 |
| --- | --- | --- |
| 1（推荐） | 生成器在读 schema 的包时，顺便收集“底层是内建标量的具名类型”（`type Kind int32` 这一种），导出和索引都按底层类型处理。C# 一侧生成底层类型（`int`），不生成枚举 | 要在 schema 扫描里加一步类型声明收集；别的包里定义的具名类型仍然不支持（要说清楚） |
| 2 | 选项 1 再加：具名类型有一组常量时，C# 生成同名的 `enum` | 客户端代码更好读；但常量的收集、命名冲突、未列出的值怎么处理都要定，工作量明显更大 |
| 3 | 不做 | 维持现状 |

### 测试

- 先红：schema 里加一个 `type Kind int32` 的字段，现在导出报错。
- 索引：具名整数字段上建索引，Go 与 C# 两端按同一个键查到同一行。
- 别的包的具名类型、底层是结构体的具名类型：仍然报错，报错文字说明原因。
- 变异：把“按底层类型处理”改成“按字符串处理”→ 两端一致性用例变红。

## (b) 浮点规范写法

### 现状

- 用途：unique 与 enum 规则比较值时，先把值变成一个规范字符串。
- C#：整数值且绝对值小于 2^53 的写成整数，其余用 `"R"` 格式（`codegen/internal/roost/client_config_csharp_runtime.go:602-608`），所以极大值是 `1E+21`。
- Go：`rules.Canonical`（`framework/configdata/rules/rules.go`），注释写的是“数字取规范十进制（1、1.0、1e0 相同）”。KNOWN-LIMITS 写的是 Go 用 `'g'`，极大值是 `1e+21`。**Go 侧处理数字的那一段我没有逐行读。**
- 影响：只在浮点列上用 unique 或 enum、并且值极大或极小时，两端的比较键不同；报错文字也不同。

### 选项

| | 做法 | 代价 |
| --- | --- | --- |
| 1（推荐） | 把规范写法写成一条明确的规则，配一份两端共用的样例表（值 → 规范字符串，几十条，覆盖整数、小数、极大、极小、负零），Go 与 C# 都用它测试。然后改 C# 去对齐 Go | 只改 C# 的运行时模板和测试；已经生成的 C# 代码要重新生成 |
| 2 | 只把 C# 的大写 `E` 换成小写 | 改动最小；但两端的规则没有被逐条对照过，可能还有别的不同（例如什么时候切换成指数写法、指数的位数），只改大小写不保证一致 |
| 3 | 不允许在浮点列上用 unique / enum | 最干净；但会让已有的 schema 报错，要确认没有人在用 |

推荐 1：问题的根源是“两端各写各的，没有共同的对照”，样例表能一次查清还有没有别的差异。

**要确认的一点**：规范字符串有没有进入数据版本号或清单的哈希。如果有，改 C# 的写法会让哈希变化；我没有查到它被用在哈希里，但没有逐个调用点核对，实施前要查。

### 测试

- 先红：样例表里 `1e21` 这一条，C# 现在给出 `1E+21`。
- 两端各自对整张样例表逐条比较。
- 变异：C# 改回 `"R"` → 变红。

## (c) 运行时转换的行号

### 现状

- 生成步骤读 CSV 时，把每条记录在文件里的行号记了下来（`codegen/internal/tablegen/main.go:698-712`，用的是 `reader.FieldPos`），报错用这个行号（`:757`）。
- 生成出来的运行时转换函数同样跳过 `#` 开头的行，但报错用的是记录的序号加一（`:1074`），所以文件里有注释行时，报的行号比实际小。
- kv 表的转换报的是文件行号（KNOWN-LIMITS 的说明）。

### 修法

只有一种合理的做法：运行时转换也用 `reader.FieldPos` 记下行号，报错时用它。改的是生成模板，已经生成的代码要重新生成。

### 测试

- 先红：一张前面有两行注释的表，第三条记录有错，现在报的行号比文件里的小 2。
- 多行的带引号字段（一条记录占几行）：报的是这条记录开始的那一行。
- 变异：改回序号 → 变红。
