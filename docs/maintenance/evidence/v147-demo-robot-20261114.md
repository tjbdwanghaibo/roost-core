# M-12 game-demo Robot 入口准备与功能证据

基线 `ee5ad2a4`，分支 `tmp/v147-demo-capacity`。本批只建立可重复入口并执行 2 人功能冒烟；100/200 人 × burst/ramp20/ramp10 六档尚未运行，等待统一空闲窗口。没有修改 demo 生产逻辑、正式场景或现有登录脚本，也没有据此关闭 M-12 的容量与“前轮 Saga 积压继承”调查。

## 入口与口径

[`scripts/perf/demo-robot.sh`](../../../scripts/perf/demo-robot.sh) 每次要求新绝对输出目录，在其中自起新私有 mirror HOME、全新 CLI game-demo 工程和 etcd；复用 `demo-drill/lib.sh` 配置/启动/清理。生成 TCP 单 IP 限额从 128 设为 512，11 服务全部就绪且 game 1000 注册后才开始。`GOMAXPROCS=0 GOWORK=off GOFLAGS='-p=2 -mod=mod'`，本机实际运行时 gomaxprocs 为 10。

生成工程里的 `TestDemoRobotCapacity` 只调用正式 `bin/loadtest`：pool、duration 0、seed 1、bus 登录、完整 demo 场景；burst 一次启动 count 人，爬坡按交接 `-ramp-step 20|10 -ramp-interval 1s`。要求所有 count 个场景成功，零 launch_failed/drop/cancel/failure，保留正式 CLI 的 error_rate=0、drop_rate=0、整场景 p95=16s 门槛。count 和延迟对应完整场景，不能报作消息 TPS 或单请求延迟。

原始 Robot JSON/日志、服务与依赖日志、生成源码配置压缩包、源码/工具链与宿主信息、前后游戏指标均保存；失败也执行本次资源清理并返回非零。单次 loadtest 最长 5 分钟，Go 夹具最长 6 分钟。使用说明和六档参数见 [夹具 README](../../../scripts/testdata/demo-robot/README.md)，入口已加入真实依赖登记。

## 实际验证

2026-11-14，macOS arm64 / Go 1.27.3 / 10 逻辑 CPU / 32 GiB。功能测试时并非独占宿主，起跑 load averages 5.57/4.59/5.21、swap used 5003.25 MiB；这些数据只记录运行条件。

```sh
DEMO_ROBOT_OUT=/private/tmp/v147-demo-robot-smoke3 \
DEMO_ROBOT_MIRROR_OFFSET=36600 bash scripts/perf/demo-robot.sh
```

结果 exit 0；工程 `dmr954463`，应用端口平移 31000，etcd 35479，私有 mirror offset 36600。`TestDemoRobotCapacity` 恰好 1 PASS、零 SKIP；scheduled/started/success 各 2，failure/canceled/launch_failed/drop 各 0。保留的整场景 p95 5.464776041s 仅用于核对原 16s 功能门槛，不作为容量或延迟基线。当前入口没有实际跑 100 或 200 人。

服务日志记录 16 个 Saga 分区启动重放，每个 sagas/messages/pending_inputs/last_event 都为 0；本档确实从空分区起跑。这不说明历史非隔离运行有没有继承积压，也不说明负载运行途中没有等待。

日志分析的 gift/alliance saga still、unknown/waiting、Nest sync timeout、WorldStats、RecordEnter 和 Player+World AddExp 子类均为 0。Retry 中间状态不是逐次打印，这些是已打印日志次数，不是所有 Saga 状态/剩余积压/受影响玩家数。初版正则曾把 16 条 `pending_inputs:0` 误算为等待；用实际原始日志发现后补词边界，重跑报告器得到 0，并将 16 条空分区事实独立保留。原始误分类结果仍在 `summary-before-classifier-fix.json` / `diagnostic-matches-before-classifier-fix.json`，没有删除样本。

正式 `RunSnapshot` 只有聚合 stats 与 run 级 error，没有逐 Robot 错误明细；汇总原样提取 `stop_reason` / `final_error` 并列出最终错误命中的类别，本档为 completed、无最终错误。Saga 相关数量只声明日志出现次数，不补造事务数。报告解析修改直接在保留的原始输出上复算，没有重跑 11 服务。

`cleanup.log` 记录私有依赖全部停止、`no residual processes`、私有根目录移除；应用工程工作目录也已删除，原源码/配置保留在 `project-source.tgz`。本机原始目录是 `/private/tmp/v147-demo-robot-smoke3`，不随仓提交，可用入口重新生成。

## 报告守卫的离线负向证据

2026-11-14 在独立临时目录重放上面的真实 2 人 `robot.json`，复用同一轮已编译的 `capacity.test`；先从 `project-source.tgz` 读取 `internal/demorobotcapacity/capacity_test.go`，确认与入库夹具逐字节相同。夹具和正式业务都没有改动。只把隔离目录里的 `bin/loadtest` 换为临时 Python 输出器：读取保留报告，按本案修改 stats，写入夹具传来的 `-report` 路径，然后 `sys.exit(0)`。不执行原 loadtest、不启动服务、不连接依赖；这只验证报告守卫，**不是另一轮网络验收或容量测试**。

四次都保留 `state=finished`、count/scheduled/started=2，子命令返回 0；其他报告字段沿用真实成功报告，故意不让 CLI 退出码或 state 替夹具发现变异：

| 离线重放 | stats.success | stats.failure | 子命令退出码 | 原夹具退出码 |
| --- | ---: | ---: | ---: | ---: |
| 原报告（前置对照） | 2 | 0 | 0 | 0，PASS |
| 1 人失败（另改 failure_rate=0.5） | 1 | 1 | 0 | 1，FAIL |
| 成功数不足，未报失败 | 1 | 0 | 0 | 1，FAIL |
| 恢复原报告（后置对照） | 2 | 0 | 0 | 0，PASS |

两个负向样本都明确输出：

