# 换服恢复审查：旧清理任务与当前归属

**状态：已修复（2026-11-19）。** 修复提交 `ff11333c`（经 `e0b78cae` 合入 main），提交说明逐项对应本文各条发现；现行行为见 CHANGELOG v1.58.0“换服、邮件与活动修复”。以下为评审时的原文。

审查基线：`main@a4ff59d9`。A、B 表示两个游戏服；account 的绑定是玩家归属的权威。以下为三个独立发现，优先级是评审建议，不是线上事故评级。本轮未改实现。

## P1 · 玩家已经换回 A，启动时排队的旧清理仍会要求删除 A 的档

**条件。** A→B 已提交，A 在清理本地副本前退出。A 重启扫描时，account 仍答“在 B”（代数 4）。扫描与清理分开执行；在两者之间，B→A 已提交（代数 5），A 中的文档现在是权威档，而不再是待删旧档。

**证据。** [扫描入队、出队](../../modules/rehome/files/game/modules/rehome/rehome_recover.go.tmpl#L123)保存了扫描时的 `Move`；第 195–203 行只检查本地迁出表是否已有记录，不复核绑定。[落定逻辑](../../modules/rehome/files/game/modules/rehome/rehome_driver.go.tmpl#L530)立屏障，把 A 的当前文档向快照里的 B 做不覆盖复制；复制成功后，第 555 行要求删除 A 的文档。删除所依据的是这次补搬读到的版本，并不是扫描时旧档的版本。

**验证。** 原模板驱动器、真实 `LocalResidency`、替身 account 和文档接口。先给扫描返回 B/4，再将权威状态改为 A/5，本地迁出表为空。观察到 `关闭 A 的会话 → 交出实体 → Copy(A→B, overwrite=false) → Drop(A)`，中间没有再次查询绑定。若 B 已清掉回迁后的源副本，补搬可以成功，A 的当前档面临被删的风险；若 B 有不同版本，补搬报冲突，不会走到删源。**已验证的是错误的删除请求，不是生产 Mongo 丢档，也不是两个库都没了。**

**验收边界。** 旧恢复任务不能对已回到 A 的玩家关连接或清档。除“扫描后、出队前换回”，还应覆盖“复核后、删除前换回”；只在出队时多读一次绑定不能排除后一个窗口。确实仍在 B 且副本一致时，A 的旧档仍应能回收。

## P2 · 换回准入与补建写屏障交错，准入成功但释放句柄丢失

**证据。** [LocalResidency](../../modules/rehome/files/game/modules/rehome/rehome_residency.go.tmpl#L400) 先把记录公开为已迁走（第 440 行），解锁后才交出实体（第 452 行）并把释放函数写回原记录（第 457 行）。此时[换回准入](../../modules/rehome/files/game/modules/rehome/rehome_binding.go.tmpl#L90)可以按新绑定调用 `Settle(Kept)`。如果释放函数尚未写入，第 410–420 行仍会删除该记录；随后完成交出的协程写进的是已经摘除的旧记录。

**验证。** 用通道暂停外部交出，再按 A/5 的绑定执行普通 `Admit`，最后放行交出。实际结果：`Admit=nil`、迁出表无记录、屏障仍为 held。交出与释放用可观测的替身；[生产屏障的语义](../../framework/dataengine/engine/entity_handoff.go#L55)是显式释放或进程退出前拒绝写。没有实测真实客户端报错或线上阻塞时长。

**验收边界。** 准入返回成功时，不应再有只属于上一代迁出的屏障遗留或稍后生效；交出失败、晚完成、准入重试都不应弄丢释放责任。这一项和第一项不同：即使没有删除文档也可能发生。

## P2 · 复制事务根本没有开启，中止清理却能删除已有的不同副本

**证据。** [复制引擎](../../framework/dataengine/engine/entity_copy.go#L159)比较 `_version`、`_last_tx` 和 `_deleted` 才认定文档相同。但只要目标事务调用报错且不是副本冲突，第 182–188 行就把源文档列为可能已写。第 218 行的删除条件只有 `_id` 和 `_version`。[驱动器](../../modules/rehome/files/game/modules/rehome/rehome_driver.go.tmpl#L426)在复制重试仍失败、account 确认留在源服后，用这份清单删目标副本。

**验证。** 真实复制与清理实现、内存 Mongo。在目标库预放相同 ID、相同版本 3，但事务标识和内容不同的文档。注入 `StartSession` 失败，确保未执行写目标的事务；复制仍返回 `Outcome=unknown`。恢复会话后执行中止路径使用的 `DropEntityCopy`，实测 `dropped=1`，原有目标文档查不到。这里测的是引擎的“复制失败清单 → 删除”，不是完整多次重试端到端测试。正常中止时权威档仍在源服，**不能据此推断玩家主档已丢失**。

**验收边界。** 可确定未发写的失败不能授权删目标；真正提交结果未知时，也不能仅凭相同版本号误删另一事务留下的内容。提交实际成功而应答丢失时，重试仍应认出已经复制的同一份文档。

## 验证范围

Go overlay 从独立工作树运行，未在 `main` 运行测试。三个新断言均在上述条件下失败；现有“崩溃后清理旧档”“正在迁回时跳过清理”“提交成功但应答丢失后重做”对照均通过。未运行真实双服、Redis 或 Mongo 集群，也未做线上事故归因。
