## 两项新增 P2

**RV-20261119-03　不同长工程名生成了相同的 Mongo 库名。** 取两个合法工程名，前 40 字节一致，后缀分别为 east 和 west。两个版本的正式 CLI 均成功生成两个工程。旧版的 `dataengine.databases.main` 保留不同后缀；新版把工程名截到 40 字节作为 `mongo.database_prefix`，两份配置均映射 main 到 game。把各自配置交给本版 Mongo 包，两个工程得到同一个业务库，同服号 1000 时也得到同一分服库。若按默认配置共用一个 Mongo，两个工程的持久化数据会落到同名数据库。短名 atlas_a、atlas_b 产生不同库名。此次验证到句柄名称，没有对共享数据库执行读写。验收应比较两个合法长名实际生成的库名和分服库名，或验证 CLI 在生成前明确提示并拒绝冲突风险。[生成器截断](https://github.com/tjbdwanghaibo/roost-core/blob/1397ee400daea6bd8b2a3776d5cab6734ec50488/codegen/internal/roost/add_entity.go#L613) · [生成配置与库名对照](evidence/main-review-20261119-02/comparison.log)

**RV-20261119-04　组成员等候期间已由另一来源订阅，仍收不到优先级更高的房间视图。** 每实体上限为 1，成员 1 先占位，成员 2 等候。成员 1 离组，移除帧已交付；下一次政策阶段前，另一来源给成员 2 订阅同一实体的 public 视图。Manager 已为该会话分配名额，允许第二个来源合并订阅；GroupView 却只查整个实体剩余名额，为 0 时直接跳过。成员 2 的组成员关系有效，连续五次 Flush 后仍只收到 public，组来源始终未持有订阅。将 room 明确设为更高优先级，基线同一时序三轮均收到 room，新版三轮均收到 public；把上限改为 2，两版均收到 room。保持名额占满时，成员会漏掉 room 视图才提供的组内状态。验收应同时保证已有会话可以合并来源、满员时尚无订阅的其他会话继续等候。[GroupView 等候判断](https://github.com/tjbdwanghaibo/roost-core/blob/1397ee400daea6bd8b2a3776d5cab6734ec50488/framework/sync/entitysync/policy/group_view.go#L426) · [Manager 合并既有来源](https://github.com/tjbdwanghaibo/roost-core/blob/1397ee400daea6bd8b2a3776d5cab6734ec50488/framework/sync/entitysync/subscriptions.go#L413) · [基线](evidence/main-review-20261119-02/nov19-group.log) · [本轮](evidence/main-review-20261119-02/r2src-group.log)
