## RV-20261120-03 · P2 · 独立 Gate 有第二条已认证连接时，关闭进图连接会留下旧视野

同一玩家有两条不同 SessionID 的连接，只有 A 执行了 Join 和 Ready。关闭 A，B 保持已认证，但一直没有进图。在正式场景连接回调收到 A 的关闭事件后，运行生产清理循环 2.2 秒，再执行一次 Flush。三轮均得到下表结果。帧数取自按玩家 ID 发送的场景传输记录器。[探针](evidence/main-review-20261120-02/gate_close_test.go.txt) · [三轮输出](evidence/main-review-20261120-02/gate-final.log)

| 部署与时序 | 场景剩余成员 | Manager 中的会话 | 发出的同步帧 |
| --- | ---: | --- | ---: |
| 独立 Gate，B 仍在线 | 1 | 仍为 Ready | 1 |
| 独立 Gate，最后一条连接关闭 | 0 | 已关闭 | 0 |
| 嵌入 TCP，B 仍在线 | 0 | 已关闭 | 0 |

Gate 发出的关闭事件已经携带 A 的物理连接号。场景接收时，只有嵌入 TCP 按该连接号清理；Gate 分支看到玩家还有任意活连接就返回。每秒的补查也跳过 Gate。于是已断开的接收方继续占场景成员与同步会话，仍可产生按玩家发送的帧。这与分区 Base 在重连宽限期保留化身是两件独立的事。实测覆盖生成工程的场景、Manager、Nest 和关闭回调；Gate 绑定表、连接表和帧传输使用测试替身，未测客户端实际收包。[关闭事件来源](https://github.com/tjbdwanghaibo/roost-core/blob/108ff00b8b19737d880c023ddd9435b4a92ccdb3/infra/network/gateway/ingress_forward.go#L150) · [关闭回调](https://github.com/tjbdwanghaibo/roost-core/blob/108ff00b8b19737d880c023ddd9435b4a92ccdb3/demo/internal/service/game/scene.go.tmpl#L409) · [定期补查](https://github.com/tjbdwanghaibo/roost-core/blob/108ff00b8b19737d880c023ddd9435b4a92ccdb3/demo/internal/service/game/partition_session_scene.go.tmpl#L410)

验收应覆盖两个顺序。A 是当前接收方时，A 断开就释放它的视野，B 正式进图前不再为旧成员出帧；若 B 已完成接替，迟到的 A 关闭事件应保留 B 的视野和会话。
