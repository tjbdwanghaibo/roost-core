# 方案：大厅服（lobby）与 relay 服——房主做 host 的开房间场景；account 同时支持多个服务（2026-11-16）

**状态**：**已定，实施中**（维护者 2026-11-17：v1.53.0 发版后实施）。第 6 节是维护者的全部决定（2026-11-16、11-17），第 7 节的 A～H 都已答复。历次补充：account 加游戏账号 token、支持多个游戏（§4.1）；换 host（§4.6）；Web 端房主，包括 relay 的 WebSocket 接入、逻辑只跑在客户端（§4.7）；房间通道与游戏通道（§4.4）；Gate 加 WebSocket 接入层（§4.7.1）。

## 1. 场景与目标

**场景**：简单的开房间联机游戏。服务器不做玩法校验，**房主的客户端就是 host**，负责全部玩法逻辑；服务器只负责三件事：
- 让玩家找到房间；
- 把玩家连到同一个转发点；
- 把消息在成员和房主之间转发。

**目标**：
1. **大厅服**：短连接（HTTP）。负责建房、列房、加入房间、离开房间。一个大厅服同时服务多个游戏（客户端），按 `game` 区分。
2. **relay 服**：长连接，TCP 与 WebSocket 两种接入（WebSocket 给浏览器用，维护者 2026-11-17 要求）。只转发、不做任何逻辑、不做帧同步；玩法逻辑必须跑在房主客户端。成员发的消息只转给房主；房主发的消息按目标转给某个成员或全体成员。
3. **account 可配置同时支持多个服务、多个游戏**：同一套账号登录后，可以进大厅、进 relay，也可以进传统的 game 区服（已有工程不受影响）。
4. **account 新增"游戏账号 token"能力**：在现有登录与票据之上**额外**加一种按游戏签发的账号 token，大厅凭它识别"哪个账号、玩哪个游戏"；一套 account 同时服务多个游戏。现有的账号票据、进服票据、角色会话令牌都不变。
5. **换 host**（维护者 2026-11-17 要求）：房主主动转交，或房主断线后由 relay 选出新的房主，房间继续。relay 仍然不解析载荷，玩法状态的交接由房主客户端完成，relay 只转存不透明的快照（§4.6）。

**不做**：
- game 服务。这个场景下不需要，大厅承担房间逻辑（问题 6）。
- 帧同步、状态校验、反作弊、断线托管。
- relay 实例迁移：房间固定在建房时选中的 relay 实例上，relay 进程崩溃时房间丢失，换 host 救不回来。
- 由服务器保证换 host 后玩法状态正确：快照的内容、版本与合法性由游戏自己负责。

## 3. 总体结构

```
客户端 ──HTTP──▶ account/portal：登录，拿账号票据 at1
客户端 ──HTTP──▶ account/portal：凭 at1 + game 换游戏账号 token gt1（新增）
客户端 ──HTTP──▶ lobby：凭 gt1 建房 / 列房 / 加入
                   └─ 返回 relay 地址 + 短期 relay 令牌
客户端 ──TCP / WebSocket──▶ relay：凭令牌接入房间
                   成员 → relay → 房主
                   房主 → relay → 某个成员 / 全体成员
relay ──NATS───▶ lobby：房间心跳、成员进出、换 host、房间关闭
```

- lobby 是无状态的 HTTP 服务，可以多开实例；房间目录放在 Redis 里，带 TTL。
- relay 可以多开实例，经 etcd 服务发现；房间只活在被分配到的那个 relay 实例的内存里。
- 账号票据和游戏账号 token 都只由 account 签发和校验（沿用 2026-11-12 定的登录架构）。relay 令牌由 lobby 签发，因为它是房间的凭证，不是账号的凭证（问题 3）。

## 4. 设计

### 4.1 account：同时支持多个服务、多个游戏

#### 4.1.1 新增能力：游戏账号 token（维护者 2026-11-17 要求）

在现有能力之上**另加**，不改已有的三种票据和登录流程。

- **是什么**：一张带游戏名的短期账号凭证，回答"这是哪个账号、要玩哪个游戏"。不带区服、不带角色：开房间场景没有区服和角色。
- **格式**：`gt1.<过期秒>.<游戏>.<账号>.<签名>`，与现有票据同一把会话密钥、独立的域前缀 `roost.account.game-token\n`。和 at1、et1 互相不能冒充，长度上限同为 `MaxTicketBytes`。
- **配置**：`account.games` 列出这套 account 服务的游戏；不在列表里的游戏不签发。
  ```yaml
  account:
    games:
      - {name: party,  token_ttl: 2h}   # 开房间类游戏 A
      - {name: brawl,  token_ttl: 2h}   # 开房间类游戏 B
  ```
- **怎么拿**（两条路，都只是新增）：
  - 已登录的客户端：portal 新增 `POST /game-token`，参数 `{game}`，请求头带账号票据 `at1`，答 `{token, expires_at_unix}`；
  - 一步到位：登录接口新增可选参数 `game`，登录成功时在原有答复里多带一张 `gt1`。
- **account 新增 RPC**：
  - `IssueGameToken(ctx, accountTicket, game) (GameToken, error)`：校验 at1、检查账号状态与 `game` 在 `account.games` 里，再签发；
  - `ValidateGameToken(ctx, token, game) (Account, error)`：验签、看过期、核对 token 里的游戏等于 `game`，再读一次账号状态，被封的当场拒绝。错误码与 `ValidateAccountTicket` 同一套（`ErrSessionInvalid` / `ErrIdentityDenied`）。
- **谁用**：lobby。每个 lobby 配置自己服务的游戏列表 `lobby.games`，收到请求时调用 `ValidateGameToken(token, 请求里的 game)`；拿别的游戏的 token 来，当场拒绝。lobby 不持有密钥，也不自己验签。
- **多个游戏共用一套账号**：账号是全局的，同一个人在各个游戏里是同一个账号号；封号仍是全局的（按游戏封号以后需要再加，不在本期）。token 里带了游戏名，大厅和 relay 的房间都按游戏隔开。
- **为什么不直接用 at1**：at1 不带游戏，一个游戏的客户端拿它可以去另一个游戏的大厅。gt1 把游戏写进签名，lobby 只认自己的游戏；寿命也可以按游戏单独配置。

#### 4.1.2 多个服务

- **新增配置 `account.services`**：列出接受本账号体系的服务及其类型：
  ```yaml
  account:
    services:
      - {name: lobby, kind: lobby}   # 无区服，凭账号票据进入
      - {name: relay, kind: relay}   # 无区服，凭 lobby 签的房间令牌进入
      - {name: slg,   kind: game}    # 传统区服（可选；没有就不写）
  ```
- **区服号**：所有 `kind: game` 的服务共用一个全局号段（问题 1），区服表每一行加 `service` 字段，现有的 256 上限放宽。这个场景下不涉及区服。
- **portal**：登录后返回的清单按服务列出（大厅地址、各游戏的区服），`/servers?service=` 按服务筛选。
- **lobby 校验身份**：凭游戏账号 token，经 account 的 `ValidateGameToken` RPC（与 Gate 校验进服票据同一种方式），见 §4.1.1。
- **兼容**：线上未部署，不兼容旧配置。没有写 `account.services` 的工程，按现在的单一 game 服务处理。

### 4.2 lobby（大厅服）

- **定位**：框架服务 `service/lobby` + `wiring/lobby`，进 `frameworkCatalog`。生成工程用 `roost add lobby` 加一个 lobby 服务（`framework: lobby` 托管），不写业务代码就能用。
- **接口**（HTTP + JSON，全部要带游戏账号 token `Authorization: Bearer gt1...`；请求里的 `game` 必须与 token 里的游戏一致）：

  | 接口 | 作用 |
  |---|---|
  | `POST /rooms` | 建房，调用者是房主。参数：`game`、`mode`、`max_members`、`name`、可选 `password`、可选自定义属性（不超过 1KB、不解析）。lobby 选一个 relay 实例（etcd 发现，选房间数最少的），在 Redis 写入房间记录，签发房主令牌 |
  | `GET /rooms?game=&mode=` | 列出可加入的房间：未满、未开始、未过期 |
  | `POST /rooms/{id}/join` | 加入：检查密码、人数，签发成员令牌 |
  | `POST /rooms/{id}/leave` | 离开（也可以直接断开 relay 连接） |
  | `POST /rooms/{id}/state` | 只有房主能调：改成"已开始 / 可加入"，或改自定义属性 |

  返回统一是 `{room, relay_addr, token, expires_at}`。
- **房间记录**：存在 Redis：`<prefix>:room:<id>`，以及按 `game/mode` 的索引。TTL 由 relay 的心跳续期；relay 不再心跳（崩溃或房间关闭），房间自动过期。
- **不做玩法校验**：lobby 只看人数、密码、房主身份。
- **多个游戏共用**：`game` 和 `mode` 只是房间的标签。lobby 可以按配置限定允许的 `game` 列表、每个游戏的最大人数，不做别的区分。

### 4.3 relay 令牌

- **格式**：`rt1.<exp>.<relay实例>.<房间号>.<账号>.<角色 host|member>.<签名>`。签名是 HMAC，密钥由 lobby 和 relay 共同配置（`relay.token_key_env`）。relay 先本地验签，不回调 account。
- **每次连接都向 lobby 验权**（维护者 2026-11-17）：验签通过后，relay 经 NATS 请求 lobby，lobby 按 Redis 里的房间记录核对：房间还在、房间分在这个 relay 上、账号是房间成员且没被踢。lobby 拒绝或在时限内没有应答，relay 都拒绝这条连接（失败即关闭）。所以 lobby 不可用时，新连接和重连都进不来，已连上的不受影响。
- **有效期**：短，缺省 30s，只用于建立连接；连上以后与令牌无关。断线重连要重新向 lobby 要令牌（`join` 对已在房间里的人是幂等的）。
- **一次性**：同一账号在同一房间里只保留最新的一条连接，新连接接入时踢掉旧连接，所以令牌被重放也只能顶掉自己。

### 4.4 relay（转发服）

- **定位**：框架服务 `service/relay` + `wiring/relay`，进 `frameworkCatalog`（问题 4）。不写业务、不解析载荷。
- **连接**：TCP 或 WebSocket（§4.7.1），两种接入用同一套 `client/wire` 帧格式。连接后的第一帧是令牌，验证通过即加入房间；房主的连接到达时房间才算建成，不然房间在令牌有效期之后作废。
- **转发规则**：
  - 成员发的数据帧：relay 加上成员槽位号，**只转给房主**（问题 4）。
  - 房主发的数据帧：带目标（某个成员槽位，或 0 表示全体成员），relay 原样转出。
  - 控制帧（relay 自己生成，发给房主）：成员加入、离开，以及成员的槽位号和账号。房主可以发"踢出某个槽位"的控制帧。
  - **被踢的记录在 lobby**（维护者 2026-11-17）：relay 断开被踢的连接，把“踢出”报给 lobby；lobby 把这个账号记进房间的被踢名单（随房间记录一起过期），从成员里移除。之后这个账号 `join` 被拒，手里没过期的令牌也用不了，因为 relay 每次连接都向 lobby 验权（§4.3）。relay 本地也记一份，只用来挡住“踢出”报到 lobby 之前的那一小段时间。
  - **两种通道，用帧头区分**（维护者 2026-11-17 定 D）：
    - **游戏通道**：游戏内的操作。成员发的只转给房主；房主发的按目标转给某个成员或全体成员。上面三条说的都是这个通道。
    - **房间通道**：聊天、表情、语音这类不需要房主处理的消息。relay 直接转发，目标是全体或某个槽位（私聊）；房主也是收件人。
    - 通道和目标放在帧头里。relay 只读帧头，不解析载荷，仍然“只转发、不做逻辑”。帧头的具体编码实施时定，要和 `client/wire` 现有的类型位兼容。
    - 房间通道单独限额：每连接每秒帧数和字节数，语音占用的带宽不能挤掉游戏通道。
    - 房主可以用控制帧禁言某个槽位的房间通道，做法和踢人一样。
    - 语音走 TCP / WebSocket 时，丢一个包会卡住后面的包，延迟会抖；这一点接受，以后需要再加 UDP 通道。
- **限额**（配置，缺省值实施时定）：
  - 单帧大小上限；
  - 每连接每秒帧数上限；
  - 发送队列上限：超限的连接被断开，不阻塞别人；
  - 空闲超时；
  - 房间最大人数，以 lobby 给的为准，放在令牌里。
- **房间结束**：
  - 房主断开或离开时，按 §4.6 换 host。只有在找不到新房主时才关房，比如没有成员了，或候选都没回应。
  - 所有成员都走了、房主还在：房间保留，直到房主离开或空闲超时。
  - 原来的做法（2026-11-16 稿）：房主一断开就关房，断开全部成员。
- **向 lobby 报告**：每个房间定时经 NATS 发心跳（续 Redis 里房间记录的 TTL，带当前人数）；成员进出、房间关闭时立即发一条。relay 崩溃时房间丢失，Redis 记录随 TTL 过期，客户端看到连接断开。
- **伸缩**：房间固定在建房时选中的 relay 实例上，不迁移。relay 实例通过 etcd 广播自己的对外地址（`relay.advertise_addr`）和当前房间数。

### 4.6 换 host（房主迁移，维护者 2026-11-17 要求）

**原来的做法**（2026-11-16 稿）：不做迁移，房主断开就关房、断开全部成员（原问题 A 推荐“立即关闭”）。下面是加上的流程。

#### 4.6.1 三种触发

| 触发 | 谁发起 | 宽限期 | 状态从哪来 |
|---|---|---|---|
| 主动转交 | 房主发控制帧 `transfer{slot}` | 不等 | 旧房主在同一帧里带上交接数据（不透明字节），relay 原样交给新房主 |
| 房主离开 | 房主发 `leave`，或调 lobby 的 `leave` | 不等 | relay 存的最新快照（§4.6.3）；没有快照就是空 |
| 房主断线 | relay 发现房主连接断开（读写出错、心跳超时） | 等 `host_grace`（推荐缺省 5s）：期间同一账号重连回来，仍是房主，不换 | 同上 |

宽限期内：
- 成员发给房主的数据帧照 §4.6.4 第 3 步处理（丢弃并通知）。
- 房主重连时向 lobby 要令牌，`join` 对已在房间里的人是幂等的。relay 认出账号是当前房主，就把新连接接回房主位置，并通知全体成员 `host_resumed`。

#### 4.6.2 选新房主

- **房主可以预先声明候选顺序**：控制帧 `successors{slots}`，随时可以更新。relay 只记住最新的一份，不判断合不合理。
- **选人规则**：按候选顺序，取第一个此刻在线的成员。没有声明，或候选都不在线时，取在线成员里槽位号最小的，也就是最早进房的。
- 选人只看在线与否，不看延迟或玩法状态，relay 里没有玩法逻辑。
- **没人可选就关房**：没有在线成员，或候选依次都没在时限内回应（§4.6.4 第 5 步）。

#### 4.6.3 状态交接：快照由房主生成并压缩，relay 只存不解（维护者 2026-11-17 补充）

relay 里没有玩法状态，生不出快照。“定期同步快照”只能由房主客户端来做，relay 负责存最新一份，换 host 时交出去。

- **主动转交**：交接数据跟着 `transfer` 帧一起来，是最新最全的状态，最可靠。
- **断线或离开**：用 relay 的快照缓存，游戏可选用。

**快照的发送节奏：房主推，relay 设下限**

| 方式 | 做法 | 取舍 |
|---|---|---|
| **房主推（推荐）** | SDK 缺省每隔 `snapshot_interval`（推荐 3s）发一次 `snapshot{seq, bytes}`；游戏在关键时刻（回合结束、关卡切换）也可以手动触发 | 快照取在逻辑一致的时间点，不会拍到“一个操作处理到一半”的状态 |
| relay 拉 | relay 定时发 `snapshot_request`，房主回一份 | 节奏统一，但房主可能正处在不方便拍快照的时刻；relay 也多了一个定时逻辑 |

无论哪种方式，relay 都：
- 限制最小间隔：两份快照之间不少于 `snapshot_min_interval`，推荐 1s，太密的拒收并告诉房主；
- 记录最新快照的 seq 和收到时间。换 host 时一起交给新房主，新房主据此知道快照落后了多少。

**压缩与大小**
- 压缩在房主客户端做，SDK 提供压缩辅助（LZ4 或 zstd，由游戏选）。relay 不压缩、不解压，CPU 留给转发。
- 单份上限 `snapshot_max_bytes` 按压缩后的字节算，推荐缺省 256 KiB，超限拒收并告诉房主。
- relay 每个房间只保留最新一份，按 seq 递增，旧的直接丢。内存上限约为“房间数 × 单份上限”，实施时用它算 relay 实例的内存预算。

**快照里放什么：只放别人没有的状态**
- 房主平时广播给成员的状态（位置、血量、比分），每个成员本来就有。新房主从成员里选出，手里已经有这些。
- 快照要带的是**只有房主知道的东西**：随机数种子、AI 内部状态、隐藏信息（牌堆、未公开的道具），以及最近几步还没广播出去的操作。
- 这样快照通常只有几 KB 到几十 KB，可以发得更频繁，换 host 时丢得更少。这是写给游戏的建议，relay 不检查内容。

**另一种存法：快照广播给全体成员（游戏自选，不是缺省）**
- 做法：房主把快照用目标 0 广播出去，每个成员各存一份；房主只占一次上行，由 relay 扇出。
- 好处：relay 完全不碰状态，任何候选人手里都有快照。
- 坏处：每个成员都多一份下行流量；隐藏信息会发到所有人手里，容易被作弊工具读出来。
- 游戏要这样做，不用 relay 提供任何新功能，自己按目标 0 发就行。

**不用快照的游戏**
- 新房主用自己本地的状态继续。很多“房主即 host”的游戏里，每个客户端本来就有完整状态。
- 或者由游戏决定重开这一局。

relay 只负责：存最新一份、限间隔与大小、换 host 时交出去。快照的内容、版本、能不能用，都由游戏自己判断。

**换 host 会丢多少（断线的情况）**
- 丢失的状态：最后一份快照之后的变化，最多一个 `snapshot_interval`。
- 画面停顿：发现房主断线的时间（relay 心跳超时，推荐 2s）+ 宽限期 `host_grace` + 新房主回 `host_ready` 的时间。
- 按推荐值：最多丢约 3s 的变化，成员看到约 7s 的停顿。节奏快的游戏可以把宽限期调短、快照发得更频繁，代价是网络稍微抖一下就可能换 host。

#### 4.6.4 切换步骤（每个房间在 relay 里单线程执行，步骤之间不会插入别的事件）

1. 房间进入“换 host”状态，`host_epoch` 加 1。
2. 旧房主的连接如果还在（主动转交），角色改为成员，收到 `you_are_member{epoch}`。之后它发的“房主帧”（带目标的下行帧）一律拒收。
3. **迁移期间成员发给房主的数据帧丢弃**，发送者收到 `host_changing{epoch}`。客户端暂停发送，等 `host_changed` 再继续；要不要重发由游戏决定。relay 不缓存这些帧。
4. 新房主收到 `you_are_host{epoch, members（槽位、账号、是否在线）, handoff 或 snapshot}`。
5. 新房主在 `host_ready_timeout`（推荐缺省 10s）内回 `host_ready{epoch}`。
   - 超时或断开：回到第 4 步，按候选顺序换下一个人。
   - 都失败：关房。
6. 收到 `host_ready` 后，relay 向全体成员广播 `host_changed{epoch, slot, account}`，恢复转发。
7. relay 经 NATS 告诉 lobby `room.host_changed{room, host, epoch}`。lobby 按 epoch 做 CAS，只接受更大的 epoch，迟到的消息忽略；然后改写 Redis 房间记录里的房主。之后 `/rooms/{id}/state` 只认新房主。

#### 4.6.5 身份与令牌

- **角色以 relay 的房间状态为准**：令牌里的 `host|member` 只在建房时用一次，第一条 host 连接把房间建起来。房间建好以后，relay 按“账号是不是当前房主”决定角色，不信令牌里的角色字段。
  - 这样旧房主手里还没过期的 host 令牌，在换 host 之后重连只能当成员。
- **lobby 签令牌时按 Redis 里的当前房主填角色**。lobby 和 relay 之间短暂不一致（第 7 步还没到）时，以 relay 为准，上一条已经保证了这一点。
- **旧房主回来是普通成员**。要拿回房主，只能由现任房主主动转交。

#### 4.6.6 不变的边界

- relay 进程崩溃：房间丢失（§4.4“伸缩”），与换 host 无关。
- 换 host 不保证玩法状态连续：主动转交最完整；断线时最多丢失“最后一份快照之后”的变化，丢失窗口和停顿时长的估算见 §4.6.3 末尾；游戏没用快照，就看新房主本地的状态。
- 不做投票、延迟测量选人、多人同时当 host。

### 4.7 Web 端房主（维护者 2026-11-17：relay 要有 WebSocket 接入，逻辑必须跑在客户端；其余按推荐）

浏览器当房主时，连接本身没问题：大家都连 relay。难点在下面三处。维护者定了：relay 加 WebSocket 接入层；玩法逻辑只跑在客户端，不放进服务器；后台限流按推荐处理；刷新页面沿用 §4.6 的换 host 逻辑。

#### 4.7.1 relay 的 WebSocket 接入层

- **共用的 WebSocket 接入层**（维护者 2026-11-17）：用 coder/websocket，把 WebSocket 连接包成 `net.Conn`，交给已有的 TCP 会话处理。relay 和 Gate 共用这一个适配器。
  - **Gate 只做接入层**：握手、票据、连接代号、路由、出站预算都沿用 TCP 那一套，不重做。WebSocket 监听地址和路径加在现有的 TCP 配置里，独立 Gate 和嵌入 TCP 的 game 用的是同一个配置结构，两条路径一起支持。
  - 测试：把 TCP 握手、收发的关键用例改成表驱动，同一组用例在 TCP 和 WebSocket 上各跑一遍，另加一条 Origin 被拒的用例。浏览器的端到端验证放到 Web 端演练里一起做。
- 同一个 relay 进程另开一个 WebSocket 监听，配置项 `relay.ws_listen`，路径固定，例如 `/relay`。
- **帧格式不变**：每条 WebSocket 二进制消息装一帧 `client/wire` 帧。令牌、转发规则、控制帧、限额、换 host 都与 TCP 完全相同。一个房间里 TCP 成员和浏览器成员可以混在一起。
- **心跳**：沿用 relay 自己的心跳帧，不依赖 WebSocket 的 ping，因为浏览器不能主动发 ping 帧。
- **TLS**：生产环境走 wss。证书由前置的负载均衡终结，或由 relay 直接配置；`advertise_addr` 要能区分 tcp 和 wss 两个地址，lobby 返回给客户端时按它要的类型给。
- **浏览器的限制**：
  - 检查 `Origin` 头，允许的游戏页面域名可以配置；
  - 单条消息的大小上限与 TCP 帧上限一致；
  - 发送队列超限的处理与 TCP 相同，断开慢连接，不阻塞别人。
- lobby 的 HTTP 接口加 CORS 配置，允许游戏页面的域名调用。

#### 4.7.2 玩法逻辑跑在客户端，与房间框架解耦

- 房主的玩法规则写成一个纯 TS 模块：只管“输入操作 → 改状态 → 输出要广播的变化 / 快照”，不依赖网络、计时器和任何服务端框架。
- 浏览器房主外壳负责收 relay 转来的成员帧、喂给规则模块、把输出广播出去，并处理换 host 的控制帧。
- **不使用 Colyseus**（维护者 2026-11-17）：Colyseus 的 `Room` 和它自带的大厅都不用。建房、列房、加入由我们自己的大厅服（§4.2 lobby）处理，转发由 relay 处理，玩法规则只在房主客户端的纯 TS 模块里，不写进任何服务端房间框架。
- 服务器侧（lobby、relay）不托管任何玩法逻辑，这一点与 §1“不做 game 服务”一致。

#### 4.7.3 标签页切到后台（按推荐）

浏览器对后台页的计时器会限流：Chrome 隐藏后每秒最多一次，隐藏几分钟后更严；`requestAnimationFrame` 停掉。手机浏览器会冻结整个后台页。

- **规则循环放进 Web Worker**：桌面浏览器对 Worker 里的计时器基本不做后台限流。这不是规范保证的，所以只当作缓解手段。
- **按经过的时间补帧**：每次被唤醒时用 `performance.now()` 算出过了多久，按固定步长补跑若干帧，保证规则结果不受计时器抖动影响。
- **页面隐藏就让出房主**：监听 `visibilitychange`。
  - 桌面端：隐藏超过 `web_hidden_handoff`（推荐 5s）还没回到前台，就用 §4.6 的主动转交 `transfer`，状态随帧交给一个前台在线的成员。
  - 手机端：一隐藏就立刻转交，因为后台页随时会被冻结。
  - 前台成员靠 SDK 上报的“是否前台”标记来认，是一个控制帧，relay 只转给房主，不解析；房主据此维护 `successors` 候选顺序（§4.6.2），把前台成员排在前面。
  - 没有前台成员可转交时，留在原地：桌面端靠 Worker 加补帧撑着；手机端冻结后表现为房主断线，走 §4.6 的断线换 host。

#### 4.7.4 刷新页面（沿用 §4.6 的换 host 逻辑）

- 刷新等于房主断线，走 §4.6.1 的断线流程：
  - 在宽限期 `host_grace` 内用同一账号重连回来，仍是房主；
  - 超时就按 §4.6.2 选出新房主，新房主拿到 relay 存的最新快照（§4.6.3）继续。
- **刷新的房主怎么接着玩**：客户端自己把快照写进 `sessionStorage`，同一标签页刷新后还在；也可以写进 IndexedDB。宽限期内重连成功后，从本地快照恢复。这是 TS SDK 提供的辅助，relay 不参与。
- **不额外加“relay 把快照还给原房主”**：relay 存的快照只在换 host 时交给新房主（§4.6.3），不新增回传路径。本地快照丢了又在宽限期内回来的房主，只能用本地剩下的状态，或者游戏主动转交给成员。
- **主动刷新或关闭页面**：在 `pagehide` 时，如果有前台成员就先发 `transfer` 再走，比断线更平滑。

#### 4.7.5 TS SDK

- lobby 的 HTTP 调用；
- relay 的 WebSocket 连接与帧编解码；
- 换 host 的控制帧与回调：`you_are_host`、`host_changing`、`host_changed`、`host_resumed`；
- 快照：定时推送与压缩；
- Web 端的辅助：Worker 跑规则循环、按经过时间补帧、`visibilitychange` 让出房主、`sessionStorage` 存快照。

### 4.5 生成器与 `roost.yaml`

- `roost add lobby`、`roost add relay`：加托管服务，补 `account.services`、`relay.token_key_env`、Redis 与 etcd 依赖。
- 一个工程可以只有 account + lobby + relay，不要 game：生成器去掉"必须有一个玩家服务"的限制；有 game 的工程不变。
- **doctor 检查**：
  - `account.services` 列全了工程里的 lobby、relay、game；
  - lobby 与 relay 的 `token_key_env` 指向同一个变量；
  - relay 的 `advertise_addr` 不是回环地址（生产配置）。
- catalog 里"九个框架服务"的说法和对应测试要改（`help.go:278`、`framework_services_test.go:404`）。
- **客户端 SDK**：client 下新增 lobby 的 HTTP 调用、relay 连接和换 host 的控制帧处理。提供 C#、Go 和 TypeScript 三份；TypeScript 版供浏览器使用，走 WebSocket（§4.7.4）。数据帧的载荷由游戏自己定。

- **单测**：
  - 游戏账号 token：签发与校验、过期、篡改、拿 at1 / et1 冒充、游戏不在 `account.games`、拿 A 游戏的 token 进 B 游戏的大厅、封号后当场拒绝；

    - 槽位号、踢人、同账号顶号；
    - 被踢的账号：lobby 记进被踢名单，`join` 被拒；拿没过期的旧令牌连 relay 被拒；lobby 拒绝或不应答时 relay 拒绝连接；

    - 换 host：

      - 宽限期过后按候选顺序选人，候选不在线时取最小槽位；

      - 旧房主拿着没过期的 host 令牌重连只能当成员；
      - 快照只留最新一份；超过上限、间隔太短都被拒；换 host 时快照的 seq 与年龄一起交给新房主；
      - lobby 收到乱序的 `host_changed` 只接受更大的 epoch；
      - 没有成员时房主断开就关房。
- **WebSocket 接入**：
  - 单测：帧格式与 TCP 一致，TCP 成员与 WebSocket 成员混在同一房间里双向转发；`Origin` 检查；超大消息与慢连接被断开。

- **生成工程**：account + lobby + relay（不带 game），编译、`generate --check`、doctor 全部 OK。
- **真实进程演练**：
  - 登录 → 换游戏账号 token → 建房 → 3 个成员加入 → 双向转发计数准确；
  - 同一套 account 配两个游戏、两个 lobby（各服务一个游戏）：互相拿对方的 token 都被拒；
  - kill -9 relay：客户端断开，房间记录在 TTL 内消失；
  - 换 host：对局中 kill -9 房主客户端，新房主拿到最新快照，成员继续收发；lobby 列表里的房主随之改变。主动转交演练一次。
  - 两个 lobby 实例、两个 relay 实例，房间分布正确；
