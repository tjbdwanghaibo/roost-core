## 已采用：按实体类型区分同步频率（2026-11-09）

本批框架实现及 [Linux 功能验证](evidence/type-sync-cadence-20261109/README.md) 已完成；[game-demo 接线与 TCP 验证](evidence/demo-sync-cadence-20261109/README.md) 也已完成。

状态：**框架机制和正式 game-demo 接线已实现。** API 与当前实现边界见 [Entity Sync 类型调度契约](../framework/ENTITY_SYNC.md#按实体类型的同步节奏2026-11-09)。下文保留决策目标；“当前代码”小节描述决策时基线，不代表此后实现仍缺失。

Player/Monster 使用 on_change；TerrainChunk 的常规脏增量每 1 秒合并一次，干净块不发送。这里的 chunk 指持久地形实体，不是物理房间实时运动对象；物理状态不能一起降到 1Hz。

### 决策时基线 f0ff1727 未直接支持同 Manager 混用

[ManagerConfig](https://github.com/tjbdwanghaibo/roost-core/blob/f0ff1727/framework/sync/entitysync/manager.go#L25) 的 Mode、Interval、OnChangeBatchWindow 是 Manager 级；[NamespaceLimits](https://github.com/tjbdwanghaibo/roost-core/blob/f0ff1727/framework/sync/entitysync/namespaces.go#L19) 只区分对象容量和快照预算，尚无按类型频率。将现有 Manager.Interval 直接改成 1 秒或设置全局合批窗口，不能实现用户要求的隔离。

采用在同一 Manager 内增加独立的 subject 调度策略，按实体类型映射；现有 namespace 可作为 terrain 的配置匹配键，但不同类型共用 namespace 时应允许类型级规则，不能把 namespace 等同于实体类型。容量配置与调度配置保持不同职责。不为此随意拆成两个 Manager，避免改变会话、epoch 和引用表的归属。

### 已采用的行为契约

- 未显式配置的类型保持现有行为；Player/Monster 沿用 on_change 的事务确认与解锁后发送契约。on_change 是状态合并，不保证每个 setter 都发一帧。
- TerrainChunk 仅常规增量按 1 秒到期调度：从干净变脏时设定本批次到期时间为当前单调时间 + 1 秒，后续修改合入该批次且不续期；未到期保持脏集合；其他类型触发 Flush 不应顺带提前清掉它。连续编辑不得不断后移到期时间，避免永远发不出。
- 周期类型不应仍在每次提交走昂贵的 on_change 内容冻结，只在安全的捕获时机取状态；同时保留 CommitLSN 持久确认门槛、版本连续性、失败重试和每订阅者恢复契约。不能仅在最终发送时加时间判断。
- 首次入场全量、重连/断档恢复、权限变更和 remove 不受常规 1 秒增量节流拖延，但继续受既有快照/发送预算。普通显式 Flush 遵守到期；Drain/Stop 绕过此延迟，按现有交付与退出契约处理剩余已确认状态，不绕过持久确认、发送预算或错误处理，也不把强制处理等同于客户端必达。
- 到期后的捕获/确认必须区分新旧脏代际，不能把捕获期间的新修改一起清除；不能让一个新订阅者的即时全量推进其他观察者的基线、丢掉他们待发的增量。
- 调度只登记脏 subject，避免空闲块每秒全扫描编码；可采用到期队列或时间轮，具体结构由实施方选择。按首次变脏时间分散到期，避免统一整秒集中处理；同拍大批变脏仍需服从既有发送预算。
- 地形服务端权威碰撞/移动使用最新已提交地形；1 秒是向客户端下发的节奏，不是延迟服务端生效。编辑者预览与其他玩家地面更新正常运行下约增加 0～1 秒合并等待，另计队列/网络/重试时间；不承诺故障或过载下的硬延迟上界；P3/P6 接入时必须验证站立、挖脚下、跨边界与纠偏体验。

### 收益与限制

重复改同一批点可合并为最终状态，减少事务后捕获、编码、帧头和扇出次数。但每秒持续编辑不同点时，必要数据仍要发送，不保证下行按频率等比下降。地形变化树有 4096 节点预算，延长积累窗口可能触发整树回退全量，抵消节省；需要记录全量回退率、每秒编码次数、字节数、脏积压及发送延迟。周期同步不能替代编辑限流或容量验收。

## 已采用：客户端圆滑岸线与跨块边界（2026-11-09）

状态：**用户已确认加入方案，待 main 实施。** 纳入 P2 客户端网格与 P4 水域规则；本节明确数据与表现契约，不要求服务器同步渲染网格，不代表完整 Unity 渲染器已经实现。沿用 2.5D 高度场及规则水位，不新增流体模拟或体素地形。

### 权威边界与岸线生成

1. 服务端提供高度采样、材质、基础资源版本、块版本及水位配置。客户端和服务端复用同一坐标、单位、双线性高度插值及舍入约定；水域按该高度查询与水位比较确定。水位配置发生变化时也必须触发相关水面/岸线失效，不能只监听地形块版本。
2. 客户端用 Marching Squares 从四角高度提取水位等高线，不按整格水/陆标签拼阶梯边缘。每条跨水位的边用 `t = (w - h0) / (h1 - h0)` 求交点，位置取两端位置的线性插值；运算采用世界采样坐标，避免块内浮点原点差异。
3. 水域判定沿用严格低于水位；端点等于水位、整边等于水位、四角交错高低的鞍点格均需统一处理。不得对等高边直接除以零；对恰好落在顶点的交点统一去重和归属，退化线段不生成面积。歧义格采用基于双线性插值的 asymptotic decider，临界相等时使用固定一致的连通规则，避免相邻块产生不同拓扑。
4. 岸线附近按曲率或屏幕误差自适应细分，从同一高度函数重新采样，逼近其水位等高线。粗格 Marching Squares 的直线段只是近似，不宣称与双线性等高线处处精确重合。细分深度与误差阈值由客户端实现时明确，必须有上限。
5. 不用任意样条平滑后的轮廓替换权威水陆判定。湿润带、泡沫、法线与材质渐变可增强圆滑观感，但不改变游泳、移动、建筑放置等服务端判断。权威高度的整数舍入与渲染浮点近似可能有微小误差，实施时记录误差界并验证；不能用视觉细分声称提升原始采样分辨率。
6. 1 米采样不能恢复未采到的细沟、细岸或洞穴。保持现行采样精度；若玩法需要更细结构，另行评估数据、同步、持久化和两端算法兼容成本，不在表现层隐式增加权威细节。

### chunk 接缝与数据就绪

- 所有块使用同一世界采样格、边界采样归属规则、交点算法与水位。网格生成读取右/上等必要相邻块的采样；法线生成读取其算法所需的额外邻域，不假定只读当前块就够。
- 修改边界采样时，标脏所有依赖它的地面、水面、岸线和法线区域；范围包含相邻块与角点依赖块。水域连接关系可能跨块，不以单块独立闭合多边形的方式人为封住块边。
- 相邻块的基础包可读不等于其编辑覆盖已经确认。依赖数据未 ready 时保留待重建状态；首次加载可暂缓显示对应区域或显示加载占位，已有网格可暂留旧视觉，但必须标记过期，不能把它当作新的权威预测数据。邻块到达、重连或重新入视野时重建依赖区域。
- 不同 LOD 的公共边采用一致的边界顶点或显式缝合方案，细分不得在公共边制造 T 接缝。法线/材质过渡也需跨边一致；具体 Unity LOD 实现由客户端选择。

### 连续共建与 1 秒同步的客户端处理

- 收到权威数据后合并脏采样区域，仅重建受影响的块及必要邻域；地形、水面、岸线异步计算，渲染资源在 Unity 允许的线程更新。连续变化合并待处理任务，限制并发及任务队列，避免每个 setter 启动一次全块重建。
- 重建任务使用不可变输入快照，并记录 BaseRevision、水位配置版本、所有依赖块版本及本地加载代际。发布前核对整组依赖；任何依赖已变化、卸载或重连，则丢弃旧结果并保留最新待重建任务。仅比较当前块 Version 不足以保证边界正确。
- 相邻依赖块采用兼容版本的网格结果一起发布，或在不匹配时暂留上一组一致结果并继续重建，避免新旧边界交叉显示造成瞬时裂缝。不同格独立提交本身仍是最终一致，客户端不能凭网格批量发布制造跨格事务原子性。
- 编辑者可以本地预测预览，预览状态与已确认地形分开；收到权威结果后校正。远端玩家按 1 秒合并策略收到变化，表现层允许渐变，但服务端碰撞/移动仍使用最新已提交地形，不能等待视觉动画结束才生效。
- 这里的周期同步只针对 TerrainChunk 数据；不降低 Player/Monster 或实时物理对象频率。站立在被修改地面、挖脚下、填水域等场景需验证位置纠偏与视觉过渡，不能只验证静态截图。

## 已采用：地图高度存储基准为 −100 米（2026-11-09）

用户确认沿用此前选定的 **HeightBase = −100 米**。代码与资源包使用厘米单位，因此写入 `Meta.HeightBase = -10000`，不是 `-100`。这是本游戏地图资源与 demo 接入采用的基准，不把通用 terrain 库限制为只能使用该值。

- 世界高度计算保持 `HeightBase + rawHeight × 10cm`，高度采样仍为 `uint16`。普通地面若取世界高度 0，对应原始采样值 1000；无需改用有符号采样或修改存储格式。
- 原始值 0 对应世界高度 −100 米；按现行最低原始高度 0 的编辑限制，不能继续挖到此基准以下。实际可编辑上限仍由编辑 Policy 决定，不能与 uint16 的表示上限混为一谈。
- HeightBase 是存储基准，不是水面高度，不要求地图所有地面平坦于世界高度 0。WaterLevel 独立配置；本次没有决定新的水位数值，也没有启用局部池塘水位或灌水机制。
- main 在资源生成/导入、demo 接线及客户端加载说明中采用相同基准，服务端和客户端使用相同版本的地形包。若已有地图包采用其他基准，不得仅改元数据而保留旧采样值，否则整张地图会整体位移；按已有基础资源换版流程处理，并校验编辑覆盖与建筑的换版策略。
- 验收至少覆盖：`raw=0 → -10000cm`、`raw=1000 → 0cm`、`raw=950 → -500cm`，以及服务端/C# 查询一致。水域测试显式提供独立水位配置，不把负高度自动等同于水。

状态：本批已将正式 game-demo 的 terrainpack 默认高度基准设为 −10000 厘米，可显式覆盖；CLI 数值先校验再转 int32，避免溢出回绕。已有资源包不自动重写；两端共用包的格式及通用 terrain 库行为不变。
