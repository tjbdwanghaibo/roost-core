## RV-20261114-01：复制已提交但应答丢失时，中止换服却不清理目标副本（P2）

问题入口：[Driver.carry 第 344–349 行](https://github.com/tjbdwanghaibo/roost-core/blob/603dd1394dcf892a25bfaa142454804a723de554/modules/rehome/files/game/rehome/rehome_driver.go.tmpl#L344)。引入换服搬档的提交为 `0b30a3b58`。

Mongo 事务的原子性只保证文档全有或全无，不保证调用方遇到错误就一定“全无”。驱动的 [WithTransaction 第 107–111 行](https://github.com/tjbdwanghaibo/roost-core/blob/603dd1394dcf892a25bfaa142454804a723de554/infra/storage/mongo/driver/session.go#L107) 已明确返回 `ErrCommitResultUnknown`，表示提交发出、结果未确认。正式 [CopyHandedOffEntity 第 170–171 行](https://github.com/tjbdwanghaibo/roost-core/blob/603dd1394dcf892a25bfaa142454804a723de554/framework/dataengine/engine/entity_copy.go#L170) 把该错误连同空 EntityCopy 返回。

但是 Driver 对所有 Copy 错误都调用 `abandon`。它确认 account 中止后，通过没有复制清单的 `finish` 解开源服屏障并清除意图，从不重查或清理这次可能已经落到目标库的副本。第 341–342 行“事务里，失败……中止即可”的推断不成立。现有 `TestRehomeCopyFailureAbortsTheMove` 只模拟写入前失败，因此没有覆盖此情形。

触发顺序：

1. 玩家从 sid 1000 申请换到 1001，源服完成排空、交出。
2. Copy 在目标库提交成功，但提交应答丢失；调用返回 `ErrCommitResultUnknown` 与 `DeadlineExceeded`。
3. Driver 直接中止 account 换服，释放源服屏障、清理换服意图。
4. account 仍绑定 1000，源服继续服务；1001 的数据库仍留着同一玩家的副本，没有相应清理责任。

三轮 Driver 探针结果相同：

```text
control:           owner=1001 source_tracked=true  target_copy=true copy_calls=1 drop_calls=1
lost_commit_reply: owner=1000 source_tracked=false target_copy=true copy_calls=1 drop_calls=0
```

控制组正常迁服，Drop 删除的是源副本，因此目标副本应保留。实验组仍归源服，却留下目标副本；原错误被视为换服已了结。

补充测试直接运行正式 `Runtime.CopyHandedOffEntity` 和 `PreloadLocalEntities`，只在 `mongotest` 的事务成功后注入丢失应答。它验证了底层实际结果：

```text
copy returned unknown with 0 manifest documents; target document=true; target startup loaded=1
```

该底层测试三轮通过，是状态验证，不是“缺陷已修复”。**开启该 kind 的 startup/resident 预加载时，目标服会载入这个不属于它的副本。** 原则上后台写入也需要正确归属；本轮没有运行两个真实 game 进程，也没有证明已经发生重复发奖或生产数据双写。即便不开预加载，目标旧档遗留和清理责任丢失也已复现。

修复方向：区分确定未提交与提交结果未知；结果未知期间保持迁出保护与持久恢复责任，按同一实体、迁服身份和源文档版本做幂等对账，取得可清理的复制清单后再决定继续改绑或中止清理。不能仅改错误日志，不能把超时视为回滚完成，也不能在没有核实当前 account 绑定时盲目覆盖目标库。覆盖复制前失败、提交生效后应答丢失、未知期间重启、对账后中止、已改绑目标已写入等分支。

这不是现有 Q4 的重复报告：Q4 是 account 已改绑后源库删除前崩溃；这里 account 已明确中止且不需要进程崩溃，遗留的是目标库副本。
