## RV-20261117-01（P2）：邮箱已满时，离开钩子未确认旧服广播合并完成

引入提交：`9003dd283109ac96392bee395a0e7eb5adb2ab9b`。定位：[`mailboxPullBroadcastsOnLeave` 第 43–47 行](https://github.com/tjbdwanghaibo/roost-core/blob/44241b956fd0bb118c1ded7535425524b8ffa10d/modules/mailbox/with/rehome/game/controllers/mailbox_rehome.go.tmpl#L43)。

新增联动的契约是：换服离开前按旧范围合并广播，合并失败中止换服；到新服再切换画像。实现却只判断 `mail.Summary` 是否返回错误。Mail 原有的正常背压语义是：邮箱全满时停止合并、保留水位、只记 `mailbox_full` 指标，仍返回成功。

- [`mergeBroadcasts`](https://github.com/tjbdwanghaibo/roost-core/blob/44241b956fd0bb118c1ded7535425524b8ffa10d/service/mail/broadcast.go#L323) 遇到满邮箱时，把水位停在未合并邮件之前。
- [`refreshMailbox`](https://github.com/tjbdwanghaibo/roost-core/blob/44241b956fd0bb118c1ded7535425524b8ffa10d/service/mail/service.go#L1198) 接收新画像后，按新范围继续扫描；`stopped` 只上报指标，没有成为 `Summary` 的错误或完成状态。

确定性复现（实际安装的联动钩子 + 真实 mail 服务，存储为内存替身）：

1. 玩家在服 3 拉过广播画像；用正式 Send 填满 200 封未读邮件。
2. 分别向服 3、服 4 发一封广播，均在离开服 3 之前。
3. 调离开钩子，返回 `nil`，但水位仍为 0，服 3 那封尚未入箱。
4. 按服 4 画像拉取；旧服那封不匹配，被跳过。腾一个空位再 Summary，服 4 在换服前发的那封反而被合并，水位升至 2。

结果：旧服应得邮件缺失，新服不应得的历史邮件出现；恢复空位也无法补回旧服邮件。只填 199 封的对照组会在离开时正确合并旧服邮件并推进水位，后续归属正确。该问题不依赖 RPC 超时、并发或 Redis 特性；本轮没有声称已执行完整跨服搬档或邮件附件领取。

建议：为换服提供带固定截止水位、旧范围和完成状态的合并屏障；未合并完就阻止切换画像，或持久保留旧范围的待合并义务。不要直接把普通 `Summary` 的成功解释为“追平”，也不要为了换服改变所有普通 List / Summary 的满箱语义。

## RV-20261117-02（P2）：C# 错误码未避开生成器自身成员和类名

引入提交：`102ef3322`。定位：[`GenerateCSharp` 第 22–38 行](https://github.com/tjbdwanghaibo/roost-core/blob/44241b956fd0bb118c1ded7535425524b8ffa10d/codegen/internal/errcode/csharp.go#L22)。

`idents` 从空表开始，只防止不同业务名称转换成相同 PascalCase。生成器随后无条件声明 `ErrorCodes` 类和 `Name(int)`、`Message(int)` 方法，未把这些符号纳入冲突检查。

| 合法 errcode 名称 | 生成的常量 | netstandard2.1 编译结果 |
| --- | --- | --- |
| `profile_name` | `ProfileName` | 通过（对照） |
| `name` | `Name` | CS0102，与生成的 Name 方法重名 |
| `message` | `Message` | CS0102，与生成的 Message 方法重名 |
| `error_codes` | `ErrorCodes` | CS0542，成员名与所属类相同 |

探针先把 `errcode.Define(190001, "…", "review")` 写成实际 Go 源文件，经正式 `Definitions` 扫描与 `GenerateCSharp` 导出，所有输入均被接受；再由 .NET SDK 编译输出。不是检查字符串猜测，也不使用假 protoc：ErrorCodes.cs 本来就由 Go 生成，不依赖 protoc。

影响是声明 client_export 的工程可以生成看似有效的客户端产物，客户端仓库编译才失败。建议为错误常量使用独立前缀 / 容器，或至少在生成阶段明确拒绝与自身保留符号冲突的名称并给出定位；补真实 C# 编译回归，覆盖上述名称和普通名称对照。

## RV-20261118-01（P3）：room 断线重试夹具在触发调用后才注入失败

定位：[`TestRoomPresenceRetriesAFailedDisconnectAndGivesUp` 第 168–175 行](https://github.com/tjbdwanghaibo/roost-core/blob/44241b956fd0bb118c1ded7535425524b8ffa10d/modules/room/files/game/modules/room/room_presence_test.go.tmpl#L168)。该顺序在 v1.52.0 `d1a6ab2a7` 已存在，不是 v1.53.0 新引入的生产缺陷。

夹具先 `Track` 一条已经断开的连接，再往 `w.fail` 放三次模拟错误。Track 会立即唤醒后台断线；后台如果先运行，替身看到错误队列为空就返回成功，Presence 正确撤掉登记。随后注入的错误不会再被消费，测试却继续期待重试，2 秒后失败。

本轮自走棋首次矩阵恰好触发它：玩法场景全部通过，但模块校验 room 只有 33/34，错误为 `no disconnect, want {roomID:2 playerID:102 epoch:1}`。验证记录：

- 原测试随后单独 30 轮通过，说明不是每次都会失败；不能据此否定首次失败。
- 新时序探针只让允许发生的“首次调用先成功”确定发生，不改运行时：迟注入分支三轮失败，先注入对照三轮通过。
- 仅在临时工程将三次失败放到 Track 之前，保持其余断言、期限、runtime 原样，原测试 30 轮通过；完成后恢复临时文件。

建议把错误先放入队列再触发 Track，或显式用屏障确认每次注入已就绪。不要增大等待期限掩盖测试时序。此项说明夹具需要修正，不重开上轮已修的 room 提交登记问题。
