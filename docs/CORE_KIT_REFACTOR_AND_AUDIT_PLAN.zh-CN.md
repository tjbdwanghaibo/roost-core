## 2. 与历史流程的冲突处理

| 历史做法 | 本次执行规则 |
| --- | --- |
| Core 是契约、Kit 是基础设施实现 | 本次架构目标更新为 Core 包含契约和基础实现，Kit 做装配 |
| U 单元禁止重构、公开 API 变更 | 保持不变；迁移及必要 API 调整使用独立 M 批次 |
| 一个包、一个缺陷类 | U 单元继续遵守；跨包问题先登记协调事项，再拆 U 单元；确实无法拆分需先明确例外范围 |
| 依赖链等同发布顺序 | 用实际包依赖图决定迁移和构建顺序；不假定五仓形成严格线性链 |
| 每轮发版、main 直推 | 本次以 dev go.work 联调，不自动提交、推送、打 tag 或发布 |
| 固定其他 Agent 的提交署名 | 不沿用；不得伪造作者或共同作者 |
| gap map 变异后编译失败也计红 | 编译失败不证明行为覆盖，单列 invalid；只有目标行为断言失败才计有效证据 |
| 按历史机器绝对路径执行脚本 | 从当前机器路径和脚本参数解析，禁止照抄历史绝对路径 |

历史文件正文不重写，保持可追溯性；本文定义本轮执行规则。

## 3. 架构边界与非目标

### 3.1 Core

- Nest、Remote Entity、事务、恢复、WAL、持久化、同步等核心实现。
- 通用算法、执行器、网络和存储客户端能力。
- 组件自身的资源管理、启动、关闭、健康状态和指标采集。
- 使用明确 Options/Config/依赖接口，不从业务 YAML、环境或全局 Registry 偷取依赖。
- 不依赖 Kit、Skill、Service 或业务项目；测试依赖也必须满足这一点。

### 3.2 Kit

- 读取项目配置、转换成 Core 配置并调用 Core 校验。
- 从 Registry 获取依赖、创建 Core 组件、注册 capability。
- 接入 app 生命周期、健康检查和运维入口。
- 不重复实现事务、锁、状态机、重试和恢复算法。

Core 可以依赖通用第三方驱动；不为保持“纯接口层”把实现重新塞回 Kit。已有 Core 同名包先检查循环依赖，必要时使用实现子包，不能机械合并。

### 3.3 其他组成

- Service 保留通用游戏服务；Skill 保留技能和战斗能力，不把业务语义下沉 Core。
- Codegen 是生成期工具，不应成为 Core 运行依赖；生成物使用 Core 实现与 Kit 装配。
- Core 内部管理资源，Kit 通过有限生命周期接口调用；不大量导出内部字段。

### 3.4 本轮不做

- 不引入旧包转发、兼容别名、两套并存实现。
- 不改 WAL、Mongo 持久化格式、Redis key、wire schema、错误语义来掩盖迁移问题。
- 不新增完整 minigame；使用临时生成工程及现有消费工程验收。
- 不取消已有发布安全门禁；发布流程本轮不作为开发主路径。
- 不保证“全仓无 Bug”；交付明确审查范围、证据及未验证项。

## 4. 两条执行轨道

### 4.1 U：缺陷收敛轨道

继续使用 ledger 第 1 节协议与 C1–C8：

| 类别 | 检查重点 |
| --- | --- |
| C1 | 锁内网络/存储调用、锁顺序、deadline 是否到达 IO |
| C2 | 空断言、宽容替身、skip、守卫是否真正被测试 |
| C3 | 重试回调外累加、重复副作用、重放状态未清空 |
| C4 | import、capability、Mod 名、配置、指标与模板字面量漂移 |
| C5 | 错误丢弃、失败不可见、错误未到达调用方 |
| C6 | 常量指标、未执行的后台维护、无效统计 |
| C7 | 锁/引用/订阅/连接释放、退出链与清理责任 |
| C8 | 快慢、单批、本地远端、首次重试路径不一致 |

每单元一个包一个类别，扫描包含“看过无问题”；最多三个发现，超出拆单。已确认缺陷先红测试、修复、回退修复确认再次红、恢复后绿，补 CHANGELOG 与现有 TROUBLESHOOTING 的 T 记录。

纯 C2 补测可先绿，再做承诺变异确认能抓住行为破坏；标记“补覆盖，无生产修复”，不得凑造 Bug。无法合法复现的观察写 B 待办，不因假设未来类型变化直接改当前公开 API。

### 4.2 M：迁移轨道

每批一个完整能力，步骤固定：

1. 清单：实现/装配/测试/模板/消费方及现有 U/T 证据。
2. 明确接口、依赖方向、不变量和回退范围。
3. 迁移前运行行为测试；如发现 Bug，暂停相关移动，拆 U 修复。
4. 只移动实现和必要接线，不同时优化算法或改变行为。
5. 更新消费者、生成器、文档、CI、集成脚本和 gap map 包路径。
6. 运行批次门禁，记录五仓提交集合和证据。
7. 更新本文批次状态及 ledger 的当前位置关联。

每批包含的跨仓变更作为一个工作区一致性单元。允许批次内部临时未编译，但不得把这种状态交接为“已完成”。

## 7. 证据和测试门禁

### 7.1 每批需要的证据

1. 基线与迁移后的模块提交集合、go.work 和工具链信息。
2. 对应 U/T/B 编号、保留及新增测试清单。
3. 实际命令、退出码、日志路径、integration skip 数及原因。
4. 架构依赖检查、生成物编译与真实启动结果。
5. 尚未验证的环境或场景；缺失必要证据时状态写阻塞，不写完成。

包内基本命令（在实际模块目录执行，目标包按批次填写）：

```bash
go env GOWORK GOVERSION
go list -m
go vet ./...
go test -count=1 ./...
go build ./...
# 在支持 race 的工具链/平台执行
go test -race -count=1 ./<target-package>
# 仅检查 integration 标签编译/静态问题，不等于运行真实集成
go vet -tags integration ./...
```

外部依赖测试按现有脚本和环境变量执行，缺依赖产生的 skip 不算通过。Windows 不支持的脚本在 Linux/WSL 或专用测试环境运行并记录；不自动改全局 Go 工具链或用户环境。

### 7.2 承诺回退安全

- 只在隔离工作树/临时副本操作，不能与另一个 Agent 在同一目录编辑。
- 每次变异只改一条目标规则，保存精确 diff，结束确认恢复。
- 有效红：编译成功且测试因目标承诺被破坏而失败；panic/hang 需要核对是否就是目标安全/退出承诺。
- 编译失败、工具不存在、依赖下载失败、超时原因未知均为无效证据，不计覆盖。
- CRC/摘要夹具应重算无关校验，使目标规则成为唯一拒绝原因。
- 不能使用 git clean/reset 等方式清理共享工作树；隔离目录也只清理由本轮创建的资源。
- gap map 只是有限采样，不等价覆盖率；记录采样上限、跳过、invalid、冗余、不可达以及人工判读。

### 7.3 故障矩阵复用

复用 Kit 当前 `scripts/integration/dataengine-env.sh` 与 toxiproxy 套件，先读脚本再执行 up/status/test/down，迁移后调整目标包列表。

必须保持四类不变量的场景证据：成功不早于规定提交点；不确定时拒绝继续危险写入；旧 fence 不能复活删除数据；已接纳工作按契约完成或显式报告终态。

- NATS：latency/reset/半开，确认重连仍经代理，不旁路 discovered server。
- Redis：丢回复/延迟，确认生产构造器启用 deadline 所需设置，不只在夹具里启用。
- Mongo：真实副本集并发 fence、删除回归、primary 故障；成员发现可能绕过代理，不声称已完成网络级 toxic。
- 每项“恰好一次”仅限所测业务效果与幂等范围，不扩大为传输层的无限保证。

### 7.4 CI 与发布边界

如查询已有 CI，按工作流名及目标 SHA 匹配，不能使用“最近一条运行”代表 CI。历史 Skill 名为 production-gates，执行时核对实际配置。nightly-gapmap 的结果是审计输入，不代替阻塞门禁。

本轮不自动推送或发版。若之后授权提交，验证成功才提交，使用精确文件清单，不用 git add -A 把他人改动混入。发布另行安排，不照抄历史版本号。

## 10. 回退与停止规则

- 一个 M 批次涉及 Core/Kit/Codegen/消费者的修改整体回退，不能仅还原 Core 留下指向新包的消费者。
