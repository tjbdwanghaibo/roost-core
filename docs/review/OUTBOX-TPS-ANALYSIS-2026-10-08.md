# 本轮 Remote 约60 TPS的源码与样本分析

## 结论和置信边界

本轮唯一发布者实现把原来能随独立投影并行的发布，集中成一次全局串行扫描。这是已确认的结构变化，也是目前最强的吞吐瓶颈候选。“唯一入口/重试所有者”是正确的职责收敛，但不需要把互不关联事务的网络I/O全部串行化。

目前只有4分钟部分样本和源码，没有阶段耗时/CPU profile。不能声称已测定Mongo标记、Redis或网络各占多少，也不能声称增加并发后一定达到某个TPS。原始负载因维护者需要机器而中断，详见 [保留记录](OUTBOX-PARTIAL-LOAD-2026-10-08.md)。没有为本分析重启任何依赖或压测。

## 样本能排到哪一层

基线55f2cc20，输入80 TPS，最后240.000981秒完成14423笔、错误4520、调度丢弃0。第60秒后至240秒完成速率60.253 TPS；写额度持续253～256/256，慢池队列长度均为0，WAL未确认2～8。最后98条成功慢请求告警耗时4087～4186ms，中位4130ms；这里只统计日志中的成功慢请求，不能当作全部请求p50/p99。

`256 / 60.1 ≈ 4.26s`：在途额度与成功请求时长吻合，说明额度被长时间占用，完成/释放速率限制了准入。该近似只解释队列形态，不是精确阶段计时。不是“只有60个worker”，也不是10000实体本身只容许60次事务；本次1024慢worker已有大量空余。

WAL积压小且没有记录到投影失败，说明按当前已准入约60 TPS，WAL→Applied仍跟得上；不能据此证明权威库在更高输入下永远没有瓶颈。`Transactions`包含已结束tracker，不能用其累计增长当作outbox积压。

日志中未出现 `sync timeout`、`context deadline exceeded` 或 `republishing persisted commits failed`。请求错误与写额度拒绝计数近似吻合（分次采样差1），不是这次已经确认大量快照同步超时。

## 结构变化

旧基线88fc852c：`ApplyRemoteCommits` 在持久提交后直接逐条发布自己的快照、写published标记。独立Entity的投影允许并行，所以不同事务可以并行走后半段。另有finalizer/outbox补发，所有者重复是此前必须解决的问题。

负载基线55f2cc20：

1. 投影只做到持久Applied并唤醒outbox。
2. `RecoverOutbox` 在整个扫描期间持有 `outboxSerial`，每页逐事务调用 `publishAppliedRemoteTransaction`。
3. 一个事务内，逐Entity、逐DAO快照调用 `cache.Publish`（L2 CAS后更新L1）、按兴趣广播，再执行 `MarkRemoteCommitPublished` 的Mongo UpdateOne。
4. 只有标记成功才把tracker推进Committed；strict的 `remoteWriteBatch.Commit` 等这个结论。
5. `remoteWriteBatch.Close` 释放远端资源后才归还写额度；异常移交finalizer也保留额度直到收尾。

所以，本次独立事务的发布确认不再利用8个投影worker的并行，而是所有事务排到同一条I/O链。约60 TPS对应每个完成约16.6ms的有效串行成本（含扫描等开销的摊销），不是一个实测Mongo RTT。

负载使用普通NATS总线，并显式建立兴趣与快照接收。`SnapshotPush=false`是此装配的能力标志，不能推断没有广播，也不能解释成每包等待JetStream ACK。具体哪个外部调用耗时最大仍需计时。

## 已实施的改进与待性能验证

保留唯一扫描/重试协调者和持久outbox事实源，在其内部增加有界的独立事务并行；投影和finalizer仍不能自行发布。并发配置独立于Nest慢worker与写额度，小规模起步，不直接设1024。

- 调度单位是完整事务。多个Entity有交集时保序，不能仅按第一个Entity哈希；事务内全部快照发布成功才写Committed。
- 同一事务只有一个在途发布拥有者；启动恢复、显式恢复、后台循环继续共用准入与停止屏障。
- 失败事务保留Applied与重试责任，失败页不阻塞无关后续页；不得清理坏记录或把失败标成Committed来维持吞吐。
- 增加扫描、快照发布、标记、等待确认和释放阶段的低基数计时，避免把总延迟都归给某个外部服务。
- 先用可控制的阻塞发布者证明两个不相交事务能并行、重叠事务不乱序、停止等待在途发布；再跑同配置短对照和新的1h长稳。

不通过提早归还额度、把strict回复提前到Applied、降低持久等级或放宽零错误条件提速。单纯把写额度从256加大，只会在瓶颈不变时允许更长的等待；增加慢worker也不会并行化这个扫描循环。

上述并发方案已实施为RR-20261008-47：默认8、上限64，事务全部Entity建立依赖；确定性反例已红转绿。新增扫描、快照、标记、确认等待与释放计时，发布事务另有histogram。功能验证和性能验收分开：尚未重跑任何压测，不能宣称TPS恢复。
