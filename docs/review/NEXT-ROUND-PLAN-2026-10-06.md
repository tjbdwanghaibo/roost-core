## 1. 业务时间只许前进（逻辑偏移不得回调）

**维护者原话**：“acivity 需要走业务时间吧，不能走系统时间。之前很多问题的时间可以往回调，现在加上强限制时间不能往回调，这样 mail 的问题也不存在了，之前一些特殊写的逻辑也不需要了，可以查一查。”

- **规则**：业务时钟（`clock.Business`，真实时间 + `time.logic_offset`）在部署的整个生命期内单调不减。偏移运行期已不可改（D-L3）；新增“跨重启也不得回调”的强约束。
- **做法（待方案细化）**：
  1. 持久化业务时间高水位（每个部署一份，建议放共享 Redis 或 global 服务，App 启动时读取）；启动时若 `真实时间 + 新偏移 < 高水位 − 容差` 则拒绝启动并点名。运行中周期性推进高水位。
  2. 生产仍强制偏移为 0；测试环境要“回到过去”只能清库重建，文档写明。
- **随之简化（逐个核对后删除只为“偏移回调”存在的特殊逻辑）**：
  - activity 协调器：派发退避 `NextAttemptAtUnix` 与进度凭证 `ExpiresAtUnix` 改回业务时钟，删除 `Config.SystemNow`（撤销 `5a3c4a60` 第 1 项的系统钟拆分）。
  - mail：信封 TTL 的 `StorageGrace` 只为回调兜底则去掉或缩为固定小余量；领取租约 `SystemNow` 若只为回调而拆则合并回业务钟（租约若依赖 Redis 服务端 TTL 则保留系统钟——逐项判定）。
  - chat / account / match（D-L3 第八轮）中仅为回调而做的拆分同样核对。
  - D-L3 方案文档 §5 / §9、USER_GUIDE、T-270 中关于“往回调”的说明改为“禁止回调”。
- **保留系统钟的不变**：租约 / 锁、超时、重试退避中依赖服务端 TTL 或跨进程墙钟比较的部分、存储 TTL、Ack、日志 / 指标 / WAL。
- **验收**：启动时偏移回调被拒（红→绿）；删除的拆分逐条有用例证明行为在“单调业务时间”下不变；偏移为 0 时生产行为不变。
- **状态**：已实施（`3e77beb9`，分支 `monotime`），已随 v1.22.0 发布。高水位放在单实例锁的协调存储（共享 Redis，键 `<singleton.key_prefix>:business_time`），容差 1 分钟，运行中每 10s 推进，只在非生产检查；activity 派发退避 / 进度凭证、mail 领取租约合并回业务钟，`mail.RedisConfig.StorageGrace` 删除（宽限固定 24h）；chat 保留期、account token / 运维时间保留系统钟。[方案与实施记录](../feature/BUSINESS-TIME-MONOTONIC-2026-10-06.md)

## 2. configdata 大小写敏感

**维护者原话**：“configdata 需要大小写敏感。”

- **规则**：配置 JSON 的键必须与声明的字段名逐字一致（大小写敏感）；出现只差大小写的键（如 `Level` 对 `level`）或大小写变体，加载 / 热更直接拒绝并点名表、行、键。不再依赖 encoding/json 的大小写不敏感匹配。
- **做法**：参照 skill NC-150 的 `requireExactFieldNames`，在 configdata 解码后按字段的精确 json 名核对原始键；`configdata/rules.Lookup` 改为精确匹配，删除 `5a3c4a60` 第 5 项为大小写变体做的“按原文最后一个”选择逻辑。tablegen / cfggen 生成期检查用同一规则。
- **验收**：`{"Level":1}`、`{"level":1,"Level":2}` 在加载与 reload 时被拒（红→绿）；精确键照常；业务手写代码不增加。
- **状态**：已实施（`c474a6ef`），已随 v1.22.0 发布。[方案与验证](../feature/CONFIGDATA-CASE-SENSITIVE-KEYS-2026-10-06.md)。

## 3. Mirror 第 6 步的本机替代

**维护者原话**：“mirror 的第 6 项看下能否在本机用别的方式替代。”

第 6 步原要求 Linux 真实环境做故障与性能。本机（macOS）可替代的部分：

- **故障**：用本 agent 私有起的依赖进程（不碰共享环境）——3 节点 NATS JetStream（强杀 / SIGSTOP 静默断线 / 自建 toxiproxy 分区与延迟）、Redis 单机 + 3 主 3 从 Cluster（切主）、Mongo 3 节点副本集（stepDown 触发选举）；两进程（owner + 只读服务）跑 remoteflow 样例，覆盖强杀重启、重投、静默断线、owner 切换与 outbox 补发。
- **性能**：同机前后对照（基准 + 两进程样例的读延迟、推送延迟、回源次数、订阅扇出），给出相对数字；macOS 与 Linux 绝对值不可比，只作趋势与回归门。
- **不可替代、仍需外部**：Linux 内核网络行为、跨主机真实分区、长时间容量。列入外部验证清单。
- **状态**：**本机替代已实施（`4ca757aa` 修复、`b15e70c8` 用例与记录，分支 `mirror6`）**。`scripts/mirror-local.sh` 自起私有进程（NATS 三节点、Mongo 副本集、Redis 单机 + 副本与 3 主 3 从 Cluster、toxiproxy），生成工程两进程跑 7 类故障，`-race` 全部通过、0 违例；同机对照 v1.20.2 的读延迟 / 回源次数 / 推送扇出无显著差别（L1 命中 p50 +41ns）。发现并修复 RR-20261006-01（删除 Remote 实体时确认报身份不符、删除不发布，只读方读到已删除实体）；已随 v1.22.0 发布。外部验证（Linux 内核网络、跨主机分区、长时间容量）见[记录](../feature/MIRROR-STEP-6-LOCAL-2026-10-06.md) §5，已汇总进 [外部验证清单](EXTERNAL-VERIFICATION-2026-10-06.md)。
