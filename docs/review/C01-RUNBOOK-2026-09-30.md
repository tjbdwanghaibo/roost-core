## 1.1 宿主机前提（第 3 次教训）

第 3 次的两次停顿都是宿主机换页：`fseventsd` 常驻 100% CPU、RSS 17 GB，swap 用了 9.9 / 11 GB。第 4 次（宿主机已重启）仍有一次 10 s 停顿：三个 mongod 没有 WiredTiger 缓存上限，各自涨到约 3.1 GB，swap 从 0 涨到 2.7 GB；环境脚本已加 `ROOST_IT_MONGO_CACHE_GB`（缺省 1），启动前用 `ps -eo rss,command | grep mongod` 确认每个节点带 `--wiredTigerCacheSizeGB`。启动前检查 `sysctl vm.swapusage`（used 应远小于 total）、`ps -o rss,pcpu -p $(pgrep -x fseventsd)`；不正常就先让维护者重启 `fseventsd` / 机器，否则错误判据必然失败，且 harness 不会做全量核验。

## 2. 前提

- **独占本机约 25 小时**。
  - 期间不要跑其他 Remote 验收、故障矩阵、race 大套件、索引重建或 benchmark。
  - `scripts/perf/remote.sh` 用 `$ROOST_DATAENGINE_IT_ROOT/remote-acceptance.lock` 互斥；这个锁已存在时直接退出，不要手动删锁，先查清是谁持有。
- **只用新环境 `~/.roost-it/roost-dataengine-it`**，端口偏移 1000：Mongo 28117-28119，NATS 15222-15224，Redis 17379，toxiproxy 19474。
  - 旧的 `/tmp/roost-dataengine-it` 仍被另一会话的 demo 使用，而且 mongo-3 的数据文件已被 macOS 清掉。不要启动、停止或重置它，也不要对它跑脚本。
  - 同一个 shell 里不要先后 source 两个 env 文件。
- **env 文件含凭据**：只能 `source`，不输出、不提交；`set +x` 后再 source。
- **不写共享库**：不写 `game` / `saga` / `remote_entity` 库和 `ROOST_*` 流。脚本自己的库名是 `roost_remote_generated_<pid>_<ts>`，属于隔离的。
- 机器不会完全安静：CorpLink 常驻占约 1 核。结果要注明“单机 macOS、有背景负载”。

## 3. 运行

先检查环境：

```bash
cd /Users/whb/roost/roost-core && git log --oneline -1 && git merge-base --is-ancestor 42804572 HEAD && echo fix-included
```

```bash
export PATH=/opt/homebrew/bin:$PATH && cd /Users/whb/roost/roost-core && ROOST_IT_HOME=$HOME/.roost-it ROOST_IT_PORT_OFFSET=1000 bash kit/scripts/integration/dataengine-env.sh status
```

环境没起来时用同样的两个变量执行 `up`（约 1 分钟）。

启动脚本，比如放在 scratchpad 里的 `run-c01.sh`。label 里带上提交号；每次运行都用新 label，不要覆盖旧目录。

```bash
#!/usr/bin/env bash
set -uo pipefail
export PATH=/opt/homebrew/bin:$PATH
set +x
source /Users/whb/.roost-it/roost-dataengine-it/env.sh
cd /Users/whb/roost/roost-core
head=$(git rev-parse --short HEAD)
echo "C01 start $(date -u +%FT%TZ) head=$head"
ROOST_REMOTE_LABEL=c01-soak-24h-80-w256-$head ROOST_REMOTE_DURATION=24h ROOST_REMOTE_TIMEOUT=25h \
  ROOST_REMOTE_RATE=80 ROOST_REMOTE_SESSIONS=1000 ROOST_REMOTE_ENTITIES=10000 \
  ROOST_REMOTE_WORKERS=8 ROOST_REMOTE_FAST_QUEUE=4096 \
  ROOST_REMOTE_IO_WORKERS=1024 ROOST_REMOTE_SLOW_QUEUE=16 \
  ROOST_REMOTE_WRITE_LIMIT=256 ROOST_REMOTE_WAL_LIMIT=512 \
  ROOST_REMOTE_PROJECTION_WORKERS=8 \
  ROOST_REMOTE_HEAP_PROFILE_MINUTES=60,360,720,1080,1380 \
  bash scripts/perf/remote.sh
echo "c01-exit=$? $(date -u +%FT%TZ)"
```

后台启动，防止休眠，并与当前终端脱离：

```bash
nohup caffeinate -i bash <scratchpad>/run-c01.sh > <scratchpad>/c01.out 2>&1 &
```

参数说明：

- **`ROOST_REMOTE_WRITE_LIMIT=256`**：默认 128 个许可只能扛约 1.6 秒 Mongo 停顿，而同机三节点副本集在长跑中会停顿 1.2～2.0 秒。
  - 定容规则是 `max_concurrent_writes ≥ 目标 TPS × 可容忍依赖停顿 + 基线在途（约 15）`，见 [kit/README](../../kit/README.md) 和 [REVIEW-2026-09-29-b30](REVIEW-2026-09-29-b30.md)。
  - 框架默认值仍是 128，这里只改压测参数。
- **`ROOST_REMOTE_HEAP_PROFILE_MINUTES`**：在第 60、360、720、1080、1380 分钟以及结束时，先 GC 再写 `result.json.heap-<N>m.pprof` 和 `result.json.heap-end.pprof`。
  - 每次采样会多一次强制 GC，只用于内存调查。
  - 这一轮的延迟数字要注明“开启了 heap 采样”。

## 4. 运行中怎么看

- 进度：`tail -1 artifacts/perf/remote/<label>/result.json.jsonl`，每 10 秒一条。关注 `errors`、`dropped`、`heap_bytes`、`goroutines`、`projection.ProjectionFailures`、`projection.WALUnacked`、`remote.Transactions`。
- 不要用普通 `tail` 看 `run.log.gz`，运行中它是不完整的 gzip。
- 用 Bash 工具轮询时不要超过 10 分钟一次阻塞；更适合只在结束时检查一次 `c01.out` 里的 `c01-exit=`。

## 5. 通过标准

以下全部满足才算通过：

1. 跑满 24 小时，`c01-exit=0`，结果目录出现 `result.json.verified`（Mongo / NATS / outbox 全量核验通过）。
2. `errors` = 0、`dropped` = 0、`ProjectionFailures` = 0、`FatalProjectionConflicts` = 0。
   - 如果出现写许可拒绝，不判为回归，但**判未通过**。记录每小时的拒绝数和 `WALUnacked` 峰值，对照 B30 的停顿结论，由维护者决定是否提高许可数重跑。
3. **堆没有单调增长**：
   - 用 JSONL 算出每小时 `heap_bytes` 的最低值，列成 24 行表；后半程基线不应持续抬升。
   - 用 `go tool pprof -sample_index=inuse_space -top -diff_base result.json.heap-60m.pprof result.json.heap-1380m.pprof` 看增量；增量不能集中在某一个结构上。
   - 第 1 次运行时，RR-20260930-03 的 `AtomicLocalStore` order 切片就是这样被定位出来的。
4. goroutine 数平稳；`remote.Transactions`（保留的事务 tracker 数，上限 `TransactionTrackLimit` 默认 65536，见 `remoteentity/assembly.go`）始终 < 65536，饱和后应在上限下持平；`remote.Wrappers` 恒定为 10000。
5. 延迟：给出 p50 / p95 / p99 / max 作为记录，C01 不设延迟门槛。

## 8. 中止与清理

- **中止**：对启动的那个进程组发 SIGTERM，例如 `pkill -TERM -f run-c01.sh` 加上它的 `go test` 子进程。`remote.sh` 的 EXIT trap 会删掉 `remote-acceptance.lock`；确认锁目录已不存在。
- **清理残留**：中止后，本次运行的库 `roost_remote_generated_<pid>_<ts>` 和同名前缀的 Redis 键会留下。库名从 `mongosh ... listDatabases` 里找：

```bash
export PATH=/opt/homebrew/bin:$PATH; set +x; source /Users/whb/.roost-it/roost-dataengine-it/env.sh; P=<残留库名>; mongosh --quiet "$ROOST_DATAENGINE_IT_MONGO_URI" --eval "db.getSiblingDB('$P').dropDatabase().ok"; redis-cli -u "redis://$ROOST_DATAENGINE_IT_REDIS_ADDR" --scan --pattern "$P:*" | xargs -n 500 redis-cli -u "redis://$ROOST_DATAENGINE_IT_REDIS_ADDR" unlink >/dev/null; redis-cli -u "redis://$ROOST_DATAENGINE_IT_REDIS_ADDR" dbsize
```

  - 只删 `roost_remote_generated_*` 开头的库，其他库一律不动。
  - 清理完用 `dataengine-env.sh status`（带新环境的两个变量）确认环境健康。
- 中止的目录保留，在 REMAINING §7 标记为“中止，不作为验收”。
