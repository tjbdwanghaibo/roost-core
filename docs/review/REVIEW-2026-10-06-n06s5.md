## 1. 租约接管与晚到 Apply

所有权链：`Engine.coordinatorLoop` → `MongoStore.ClaimDue`（`saga/mongo_store.go:213`；按 `version` 与 `lease_until <= now` 条件 `$set lease_owner/lease_until`、`$inc lease_token`，:225）
→ `processClaimed`（`saga/engine.go:712`）→ `MongoStore.Apply`，过滤条件 `applyFilter`（`mongo_store.go:548`）：`_id + version`，带 `ExpectedLease` 时再加 `lease_owner + lease_token`。
领取不改 `version`、只增 `lease_token`，所以 B 领取之后 A 的 Apply 在 token 上失配；B 已 Apply 之后在 version 上失配。`Complete`、`Resume`、`Compensate` 不带租约，只按 version fence——
它们与持租约的协调器写同一文档，谁先写谁赢，另一方 `ErrConflict` 后重读。A 的租约过期但没人接管时，A 的 Apply 仍成功（token 未变），这是预期：没有别人基于它做过决定。
Apply 的副作用（outbox、回执、tombstone）都在同一 Mongo 事务里，A 失败不留半截。

用例：`saga/coordinator_takeover_review_test.go` `TestCoordinatorLeaseTakeoverFencesTheLateApply`（mongotest）与 `saga/cross_process_real_integration_test.go`
`TestRealMongoCoordinatorLeaseTakeover`（真实副本集，走完整 ClaimDue）：B 已领取未 Apply、B 已 Apply、A 的超时判定与 completion 交错三种顺序，A 都 `ErrConflict`，
记录只有一次派发、outbox 只有 B 的命令、已接收的 completion 不被旧超时覆盖。**负对照**：把 `applyFilter` 的租约条件去掉，第一种顺序变红
（`A's late dispatch after B took the lease = <nil>, want ErrConflict`），说明用例确实依赖 token fence。

## 2. 截止 / 补偿 / Resume 与晚到结果

逐个出口核对“离开当前步骤时关闭哪个操作”：

| 出口 | 当前步骤在等结果（Waiting） | 当前步骤在退避（Attempt > 0） | 结论 |
| --- | --- | --- | --- |
| 超时判定（`retryOrCompensate`） | `closedOperation`：同一步骤继续重试不关闭；用尽进入补偿 / Failed / ManualRequired 时关闭 | 不经过 | 正确 |
| saga 截止 | 关闭 | U-0280 补了 `Attempt > 0` | 正确 |
| 人工 `Compensate` | 拒绝（in flight） | U-0280 补了 `Attempt > 0` | 正确 |
| **定义缺失** | 关闭 `OperationKey` | **不关闭**（`OperationKey` 已清空） | **NC-250** |
| 步骤下标越界（`invalid saga step`） | 不经过（Waiting 分支在前） | 步骤从未派发 | 不适用 |
| `Complete` 以失败关闭 | 按 U-0280 复核记“放弃” | — | 正确 |
| `Resume` | 只从 Failed / ManualRequired 出发，操作已关闭 | — | 正确 |

**NC-250**：[问题](../bug/RR-20261005-NC-250.md) · [修复](../bugfix/RR-20261005-NC-250.md)。修法是三个出口共用 `abandonedOperation`（`saga/engine.go:975`），不是第四份手写判断。
修后再核对与 B1 的组合：fence 后修好定义 `Resume`——没有完成步骤时新一生派发前到达的旧成功按 B1 接收（tombstone 升级为带结果），派发后由收件箱回放（原生）或业务幂等（Mongo 步骤）；
有完成步骤时进入补偿，旧成功按放弃后迟到告警一次。

其余交错（无缺陷，与 U-0280 / B1 用例重叠的不再重写）：补偿方向 ManualRequired 上的 `Compensate` 换代（B1 E4）；Resume 之后旧一生的拒绝 / 成功（B1 E1 / E3）；
截止发生在退避中（U-0280）；截止发生在补偿方向（截止只约束正向，`processClaimed` 的截止分支要求 `PhaseForward`）。

## 3. 多个 completion / 旧 attempt（B1 之后还剩什么）

- 同一 CommandID、摘要不同：`MongoStore.Apply` 与 `CompletionHistory` 返回 `ErrIdentityConflict`，两个结果消费者都不把它当终态，nak 到 `MaxDeliver`。
  只在生产方出错时出现（收件箱回放原样携带回执）；不改。
- 同一生较早尝试晚到的**失败**在协调器等较晚尝试时被接收，可能消耗最后一次重试并放弃一个仍在执行的尝试——B1 第 2 节明确接收、U-0280 复核 1 以告警兜底，
  是契约第 4 条列出的告警来源之一。只接收“正在等的那次尝试”的失败能去掉这个来源，但改协调器状态机，交维护者（O-S5-7）。
- 旧一生：B1 已对齐收件箱，未发现残余。

## 4. TTL 之后的重投（判断：不加协调器告警）

TTL 之后协调器手里既无回执也无 tombstone，分不清“已计入结果的重复”与“放弃后生效的成功”，在 `completeNotWaiting` 上加计数只能把两者一起计，
而且是 B1 方向判断明确反对的协调器特例。正确的约束是让 TTL 之后的重投不可能发生：

- saga 流（普通结果、Mongo 步骤与收件箱回放的结果）：`kit/saga/mod.go:129` 启动时要求 `saga.completion_receipt_ttl > saga.stream_max_age`，消息在 TTL 前就从流里消失。成立。
- 效果流（原生步骤的 completion effect，`ROOST_EFFECTS`）：保留期是 `dataengine.effects.max_age`（DataEngine Mod，默认 168h），与 `saga.completion_receipt_ttl`（默认 720h）
  **没有跨 Mod 校验**。违反时迟到的结果 `ErrNotWaiting` → Term，只有通用的 `nats.jetstream.terminal.total{reason="permanent"}` 与 ERROR 日志。默认值安全，登记观察 O-S5-2。

## 5. outbox 发布

- 发布失败：`NackOutbox`（`mongo_store.go:393`）按 owner + token 条件写退避；超过 `PublishBackoffMax` 的重试由下次领取继续。
- 发布成功、Ack 结果未知：`AckOutbox`（:383）失败只计数，租约过期后另一个发布器领取同一条（`CommandID` 不变，即 JetStream MsgID）：去重窗口内被 broker 去重，
  窗口外由步骤收件箱按 CommandID 去重。
- 并发 supersede：派发新尝试的 Apply 在事务里按 `IdempotencyKey` 删旧命令再插入（:311），不看旧命令的租约；持有旧命令的发布器之后 Ack / Nack 都是 `ErrConflict`，不会写回。
  已发出的旧命令到达步骤侧时要么过了截止（U-0281 ack 不执行），要么那次尝试已有结论（收件箱回放），不重复执行。
- 批量时间预算：`NewEngine`（`engine.go:169` 起）要求 `(LeaseDuration-StoreTimeout)/Batch` 覆盖每条的 Store / Publish 超时，既有 `TestEngineRejectsPublisherBatchWhichCanOutliveLease`。

用例：`TestOutboxSupersedeAndUnknownAckOnMongoStore`（未知 Ack 后重新领取到同一 CommandID、旧发布器 Ack 冲突；持有旧命令时派发新尝试，Ack / Nack 冲突、outbox 只剩新命令）。
观察 O-S5-5（Nack 退避从领取时刻算）。

## 6. 真实 broker + Mongo 跨进程恢复

`TestRealSagaCrossProcessKillRecovers`（`-tags integration`）：父用例在隔离 NATS JetStream（文件存储流 `REVN06S5_<pid>_<ns>`）与 Mongo 副本集（库 `roost_revn06s5_<pid>_<ns>`）上
起两个子进程（同一测试二进制），每个是完整的 `Assembly`（三个持久消费者 + 协调 / 发布循环）加两个 Mongo 步骤消费者，共用同一组 durable；启动 60 个两步 saga，
完成 1/4 时 SIGKILL coordinator-a，只留 coordinator-b。步骤 handler 在事务里按 IdempotencyKey 与 CommandID 各 `$inc` 一个计数，先写后随机等 0～300ms（被杀时有在途事务）。

三次实跑（[real-run.txt](../bugfix/evidence/NC-250/real-run.txt)，第 3 次在 NC-250 修复后）：

| 次 | 恢复时间 | 结果 |
| --- | --- | --- |
| 1（handler 先等后写，MaxAttempts 8） | 4.1s | 60/60 完成，120 个操作各一份业务写，120 次提交；清理时 dropDatabase 超时（被杀进程遗留 2 个事务） |
| 2（先写后等，MaxAttempts 30） | 1m7.8s | 60/60；121 次提交（1 个操作被两次尝试提交）；B 日志 33 次 WriteConflict |
| 3（修复后） | 1m26.7s | 60/60；121 次提交，被重复提交的操作两次都由 coordinator-b 执行（尝试 6、7）；44 次 WriteConflict |

每次都核对：全部 `Completed`、`completed_steps == 2`、outbox 为空、没有残留协调器租约、每个 CommandID 的业务事务至多提交一次。

发现：
- **被杀进程的 Mongo 事务在服务端保持打开、持锁到 `transactionLifetimeLimitSeconds`（默认 60s）**（第 1 次 `$currentOp` 看到 2 个 `inactive transaction`，open 46s）。
  幸存进程对同一文档的事务写一直 `WriteConflict`，步骤尝试反复失败，直到锁被回收；恢复时间因此约 60s 起。默认步骤预算（5s × 5 次 + 退避 ≈ 27s）短于它，
  受影响的操作会用尽重试进入补偿（**推算，未实跑**）。登记 O-S5-3，SAGA.md 运维要点补一句。
- Mongo 步骤跨尝试重复提交（第 2、3 次各 1 个操作）：较早尝试在 WriteConflict 重试里拖到截止才提交，协调器已派发下一次尝试，后者也执行。
  契约第 5 条允许（Mongo 步骤按 IdempotencyKey 业务幂等），用例的业务写按操作幂等所以只有一份效果。这是方向判断里“Mongo 步骤纳入收件箱契约”的实证。

## 方向判断

近 10 天 saga 协调器 / 收件箱的修复链：U-0280（A + B + C'，`054fdd66`）→ U-0280 复核两处（`23b97942`、`877bb66c`）→ B1 四处（`3fabe34d`）→ 本轮 NC-250。
都落在同一个不变量“每个操作实例的结果恰好被计入一次，不被计入的有人知道”上；NC-250 是其中“放弃关闭”子规则第三次在不同出口漏写（U-0280 补了截止与人工 Compensate 两个出口）。
按 B1 的方向判断，这次落在“迟到成功只告警”上，所以先判断再修：修法没有加状态、没有加告警种类，而是把三个出口合成一个判断，属于减少分叉；不涉及状态机、公开语义或 Mongo 步骤契约，未交回。

但信号已经够明确，建议维护者定方向（不在本轮实施）：

1. **把“离开当前步骤”收成一个转移**（低代价）：截止、人工 Compensate、定义缺失、重试用尽目前各自拼 `After` 与 `CloseOperation`，NC-250 只合并了后者。
   做成一个 `abandonStep(record, reason, status)` 后，新出口不可能漏写 tombstone。纯重构，按 roost-coding 方案流程即可。
2. **Mongo 步骤纳入同一收件箱契约**（B1 已提，本轮有实证）：真实跨进程恢复里 Mongo 步骤两次被相邻尝试提交，靠业务按 key 幂等兜住；同时它的提交点不受命令截止约束，
   正是 O-S5-7 / 契约第 4 条“放弃后迟到成功”的主要来源。代价：Mongo 步骤事务里要写操作守卫与封顶租约（每次多一次守卫 upsert），handler 契约从“业务按 key 幂等”变为框架保证，
   已生成工程的 Mongo 步骤要迁移。
3. **只接收正在等的那次尝试的失败**（O-S5-7）：去掉“较早尝试晚到的失败让协调器在最后一次尝试执行中放弃”这一告警来源；改协调器接收规则。
4. 方向 C（只补偿迟到生效的那一步）仍未做；若 2、3 落地，告警来源只剩“effect 发布延迟”与时钟偏差，C 的必要性下降。
