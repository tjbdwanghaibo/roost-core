## 观察与设计建议（未登记 RR）

1. **O1 servicemetrics 在生产里没有落点（接 N06 观察 1）。** 生成工程所有服务 `Metrics()` 返回 nil，Sink 全部空操作；Depth / Refused / Conflict 只在测试 Recorder 里存在。另外两点会影响将来的适配器：Depth 名字里带标识（`"queue."+queue.Key()`，`service/match/queue_store.go:254`；`"board."+board.ID`，`kit/service/rank/redis_store.go:291`），直接当指标名会让指标名无界，适配器要拆成“固定名 + 标签”并考虑看板删除后的归零；`session.swept`（`service/session/service.go:828`）上报的是一次扫描的条数，按 gauge 语义是“最近一次扫了几条”，更像计数器。是否提供默认 Reporter 仍是功能决定。
2. **O2 per-run 序列没有生命周期。** loadtest 默认给 `robot.runner.*` 加 `run` 标签，长期运行的控制面每次运行新增序列、永不删除；NC-161 修复后序列触顶会让门禁明确失败而不是假绿，但控制面在约一千次运行后就不可用了。建议 metrics 增加按标签删除序列的入口，运行结束、评估完毕后删掉本次运行的序列。
3. **O3 metrics 没有删除序列的入口。** 动态标签的 gauge（`nest.dispatch.*{dispatcher}`、`bus_rpc_pending{method}`、`robot.loadtest.active{profile}`）在对象消失后停在最后值；Nest 属核心线，只记录。`bus_rpc_consumer_delivery{method}` 记的是“最近一条消息的投递次数”，method 来自请求，受 2048 上限约束。
4. **O4 Prometheus 文本格式余项。** 不输出 `# TYPE`；标签值用 `strconv.Quote`，非 ASCII 可打印字符原样保留没问题，但制表符 / 非法 UTF-8 会变成 Go 的 `\t` / `\x..`，不在 exposition 格式的转义集合（`\\ \" \n`）里。当前标签都是代码常量或数字 ID，未在真实抓取器上复现，不登记。
5. **O5 N04 观察 3 的归属。** failurelog 的重复追加由 NC-160 关闭；`DistLock.Acquire` 的 `SetNX` 重放与 RedisMod 默认 `MaxRetries` 仍待维护者按命令幂等性统一决定。
6. **O6 日志磁盘 / 失败预算。** 轮转打开新分片失败（EMFILE、ENOSPC、权限）时该行直接丢弃，即使当前文件仍可写，且每行重试一次 MkdirAll+Open；`io.MultiWriter` 在第一个写失败处停止（stdout 出错时文件也不写）；没有任何日志写失败计数。建议：打开失败时继续写旧文件并限频重试，增加 `log.write_errors_total`。
7. **O7 app.run 的最终错误不进文件（交给 N01）。** NC-165 让 Close 之后的行有去处，但 `app.run` 只把最终错误返回给 main，文件 sink 里没有“为什么退出”。建议 `app.run` 在 `flog.Close()` 之前把返回的错误写一行；`app/app.go` 属 singleton 另一线，本轮不改。
8. **O8 robot 会话余项。** `Session.call` 的写不受 ctx 约束（TCP 发送缓冲满时 Call 超过自己的超时，直到会话关闭）；超时后迟到的应答（seq 非 0、已无 pending）会按推送分发给同 msg id 的 WaitPush / handler，而不是丢弃。共享 msg id 的协议里可能把旧应答当成推送；未在真实网关上复现。
9. **O9 runner 余项。** Stage 先缩后扩会复用刚停止机器人的序号与 PlayerID，旧机器人可能仍在收尾；`Run` 在设置 Duration 时第一个 `WithCancel` 的 cancel 被覆盖（父 ctx 结束前不释放）；`Stats` 注释的 `Started == Success+Failure+Canceled` 对 looping 不成立（后者按场景次数计）。
10. **O10 Coalescer.Close 不等最后一次 flush。** `Close` 关闭 done 后立即返回，worker 异步 drain；`Context.Close` 随后关闭会话，最后一批确认可能发在已关闭的会话上。仓内无使用方。
11. **O11 runner 的 Duration 到期记为 completed。** 真实网关 `-duration 1s` 那次 `stop_reason=completed`：runner 自己的 Duration 到期不经 manager ctx，`stopReasonFromContext` 看不到。修后由阈值判失败，但停止原因仍不准确。

## 方向判断

- **“结果未知当成没执行”第三次出现在 Redis 脚本降级上**：cache RefHMap（NC-21，10-04）→ 驱动重放（NC-100，10-05）→ failurelog 降级（本轮 NC-160）。三处是同一个根因：在某个调用点把传输错误解释为“没执行”，然后补做一次。这与 N04 方向判断的结论一致（第三方驱动默认语义与“结果未知交给调用方”契约不一致），不是 failurelog 的实现细节。建议维护者按 N04 ①把“哪些错误可以当作确定没执行”写成 `redis/driver` 的单一判定（例如只认 NOSCRIPT 等服务端明确拒绝），仓内凡是“脚本失败 → 换一条路再写”的地方都只用它；本轮逐个看过仓内非测试的 `Eval` 调用点（versionstore、redis/cas、rank、remoteentity marker / versioned lock / snapshot L2、cache RefHMap），错误分支都原样返回，修后已无“脚本失败 → 换一条路再写”的路径。
- **gauge 生命周期**：NC-164 与 O2 / O3 都源于 metrics 只增不删。目前逐处补“写 0”，若后续再出现同类问题，建议给 Registry 加按标签删除，由对象的拥有者在销毁时删除序列。
- robot 本轮的四条缺陷（NC-161～163 与历史 RR-20260914-09）分散在不同层，没有同一不变量反复被打破的信号。
