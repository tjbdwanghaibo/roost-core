## 观察（不登记 RR）

- **O1 ownerroute 不提供完成回执**：`BusTransport.Send` 不看 ctx（底层是非阻塞 Publish，当前无实际阻塞）；接收端失败只记日志。业务需要确认时要走既有幂等命令 / 回执链（赠礼就是这样用的）。
- **O2 赠礼转交**：`runHandoff` 在 `AdmitBound` 里先刷新驻留记录、之后才校验命令与截止时间，非法 / 过期的转交也算一次“使用”，只影响闲置卸载的时机。转交消息与 JetStream 命令同一信任域，接收端不另验来源。属 `wt-u0280` 范围，未改。
- **O3 兴趣无主动撤销**：`ReleaseRemoteSnapshotInterest` 没有正式调用方，Assembly.Stop 也不撤销；owner 侧租约到期即失效，最多多推 TTL（默认 30s）的消息。
- **O4 兴趣容量是全集群合计**：兴趣主题广播，每个节点为全集群所有 consumer×key 存 lease（上限 `snapshot_interest_subs` 262144），不只自己拥有的 key；超限时续租在 owner 处被拒（只记日志），consumer 不知道，推送停止，陈旧度退回 L1 TTL。50 个服各读 1 万个不同 key 即超限。容量 / HA 设计问题，交维护者。
- **O5 JetStream 重放历史**（真实 JetStream 探针，见证据）：同步总线每个 sid 一个 durable、`DeliverAll`；新 sid（扩容）或落后游标（停机期间）会把 30 分钟保留期内的快照与兴趣消息重放进 L1 / L2。发布受兴趣门控，最后一条被发布的版本可能比实际最新版本旧；L2 那时已过期（键 5 分钟无提交）的话，重放会把旧版本写进 L2，L1 冷的节点 Cached 读到它直到 L2 TTL。NC-130 修好后，L2 仍有新版本时节点会改取 L2；L2 已过期的情形仍在，属 [Mirror 方案](PLAN-REMOTE-POLICY-MIRROR.md)“首载 / 重连补洞”的范围（缓存复制主题更适合 `DeliverNew`，但同一总线也服务需要历史的主题，要按主题定投递策略）。
- **O6 Cached 没有成文的最大陈旧时间**：实际上限是 L1 TTL（30s）、L2 TTL（5min）与上面重放的组合；Mirror 方案要求的 MaxStaleness 仍未实施。

- **实现**：仍未实施。代码里没有独立只读 reader / snapshot client（`ReadRemoteSnapshot` 仍是带写 backend 的 Manager 方法），没有订阅确认 / 首载缓冲、没有 MaxStaleness；本轮补的 L2 墓碑只对应方案“有界墓碑”一项里的共享层水位，不等于方案第 4 步完成。

## 方向判断

快照缓存的删除 / 版本水位近期反复出问题：RR-20260913-01（U-0187）→ 第七轮两处残余（在途回填越过墓碑、冷 L1 删除清新 L2）→ RR-20260913-05/06（L2 冲突 / 回填）→ RR-20260913-08 与 10-05 残余（过期出口）→ NC-35/36（权威回填身份 / 最终版本）→ 本轮 NC-130 与跨节点 L2 残余。共同点是同一条“L1 + 共享 L2 + 本机墓碑 + 广播复制 + 权威加载”的组合，每次补一个入口或一层判定，状态在增加（墓碑旁表、Superseded 钩子、FatalRemoteError 分类、预查 L2、L2 墓碑）。这符合“同一不变量第二次被打破、修复在增加状态”的信号。

判断：根因不在单个实现细节，而在于“谁是版本水位的权威”没有单一答案——L1、L2、本机墓碑各自持有一部分。建议维护者在 Mirror 方案第 2～4 步落地前决定：(a) 把水位收敛到共享层（L2 记录版本与删除墓碑、L1 只是它的有界副本，冷节点永远先问 L2），本轮的 L2 墓碑是这个方向的第一步，代价是 L2 不可用时只能退回 TTL 内的本机判断；或 (b) 按方案改为订阅代际 + 首载缓冲，L1 只接受当前代际内经过准入的消息，代价是需要可确认的订阅（普通 NATS 不满足，要么换 JetStream 要么只交付按需读取）。两条路都应同时把 Cached 的最大陈旧时间写成配置与契约（O6），不再靠 TTL 的组合隐含。
