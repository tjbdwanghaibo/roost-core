## 结论

- **没有需要维护者接受的新退化。** 10 对（修复提交 vs 父提交）的 17 组微基准 + E / F 两组端到端全部跑完，每组每侧 n=10，benchstat 比较。
- **已如实记录的代价**（都在各自记录里）：
  - RR-25：三条请求路径 +0.7%～2.3%（26～87 ns/请求，准入冷判定），分配不变；RR-47 随后把冷判定做成 −84% 的 `IsLoaded`。
  - RR-74：可回滚事务每笔 +1 alloc / 约 +80 B（嵌套独立事务的快照边界簿记），时间不变。
  - RR-30 §5：`ReserveDiscard` +16 B/op（屏障簿记），时间不变。
  - RR-16（合并提交 `985d5ba`，含 RR-03～24 全部）：async 投影准入每笔 +5 allocs，writers_1 吞吐 +1.7%，p99 +7%～14%（writers 1 / 8）；WAL 直接追加与回放 + Ack 不变。
  - RR-28-11：`broadcast_pipelined` 微基准 −27% ops/s（修后等于 strict，即文档承诺的语义）；端到端 80 TPS × 10 min：WAL fsync +22%，请求延迟、错误、核验无退化。
- **收益（与原记录同向）**：RR-47 冷判定 −84%；RR-48 memory handler 内 Create −2.4%、−2 allocs；RR-10 复核 `ReserveDiscard` −9%；RR-04 字节预算恢复 −62% 时间 / −93% 捕获（端到端捕获 −84%、分配 −47%）。
- **不可对照 / 丢弃项**：见 §丢弃与不可对照。

## 机器与方法

- Apple M5（10 核、32 GiB，darwin/arm64），Go 1.27.0；**单机 macOS、有背景负载**：常驻 `fseventsd` 约 1 核（本机 `ps` 显示 ~105% CPU、37% 内存）、CorpLink、Claude / Termius 桌面；
  各组开始时 load average 1 分钟值 2.5～6.5（端到端期间 3.7～8.6，含被测进程本身），全部记录在 `results/loads.txt`，各记录里按组写明。基准运行期间没有并行跑别的测试、编译或索引。
- 每个提交 `git worktree add --detach <scratch>/b29/wt-<sha>`；父提交缺基准文件的，把修复提交里的 `_bench_test.go` 复制过去（见 §移植）；两侧 `GOWORK=off go test -c`（非 race）
  得到 `bin/<组>-<side>.test`。
- 运行：`nohup caffeinate -i bash run-all.sh`（detached），每对基准 **交替**（父侧 → 修复侧 为一轮）10 轮，每侧 n=10：
  `-test.run '^$' -test.bench '<正则>' -test.benchmem -test.count=1 -test.timeout 0`，默认 benchtime；例外（两侧相同）：`BenchmarkProjectorAdmissionMatrix` `-test.benchtime=1000x`、
  `BenchmarkProjectorWALReplayAckMatrix` `-test.benchtime=10x`——默认 benchtime 的爬坡序列让计时之外的尾部 `Flush`（逐条 ack + fsync）与每次迭代的 WAL 开/写/关把单次运行拖到 5～8 分钟以上
  （预跑里父侧 `40804f2` 的 `pipelined/writers_32` 尾部 Flush 8 分钟未结束，goroutine 转储留在 `results-smoke/C1-parent.txt`；固定 2000x 两侧各 14.7 s）。
- 比较：`/Users/whb/go/bin/benchstat 父.txt 修.txt`；输出先经 `mkstat.py` 清洗（只保留 `Benchmark` 行；E 组父侧 1 行被 Nest 的 `WARN` 日志截断，名称行与数值行合并后仍 n=10）。
  各记录里的 benchstat 原文截取 sec/op 与关键指标，保留 n、Δ、p。
- 端到端（E、F）：`source ~/.roost-it/roost-dataengine-it/env.sh`（隔离环境，brew 二进制），在对应 worktree 里跑脚本，**结果目录先复制到主检出 `artifacts/perf/` 再删 worktree**；
  没有碰 `/tmp/roost-dataengine-it`，没有 down / reset / fault。E 组两侧 worktree 都复制了主检出 `c5cfb7c2` 的 `kit/scripts/integration/{dataengine-env.sh,lib/*.sh}`

## 丢弃与不可对照

- **A：`BenchmarkAdmissionColdProbe` 对 RR-25（`28ff15a` → `a31d0ff`）不可对照**——它调用的 `declaredTargetsNeedSlowPreparation` 是 RR-25 引入的，父侧没有这条路径；
  移植版在父侧删掉该基准，只比较三条请求路径。ColdProbe 的数字在 RR-47 对。
- **D 的归因**：`985d5ba` 是 RR-03～24 的合并修复提交，D 组差异包含同批全部修复，无法分离出 RR-16 单条；记录里写明。
- **C 预跑的异常**：默认 benchtime 下父侧 `40804f2` 的 `pipelined/writers_32` 尾部 Flush 8 分钟未完成（修复侧同预跑 8.5 分钟跑完整矩阵；固定 2000x 两侧各 14.7 s），
  改用固定迭代数后两侧正常；没有进一步调查，goroutine 转储保留。预跑（`results-smoke/`、`results-smoke2/`）只用于校时，不计入结论。
- **F 字节预算 204800**：两侧都没有在 7.5 s 测量窗口内追平（5% dirty 的 AOI 变化持续产生冷创建，预算全程受压），所以 `recovery_admission_caught_up_ms` 为 0；
  补跑 1 MiB 预算（`run-extra.sh`）得到追平时间。两档都保留。
- **端到端的 50 ms 门禁**：三侧 sync 脚本都因零星 > 50 ms 事件 exit 1（0.00%～0.12%），报告保留；E 组 remote 两侧都 `Verified`。
- **E 的脚本移植**：两侧 worktree 复制了 HEAD 的 `kit/scripts/integration/{dataengine-env.sh,lib/*.sh}`（见方法）；`remote.sh` 两侧相同未动。
- 没有跑：A 组端到端 `nest-msg.sh`、B 组 `nest.sh`、C 组 `dataengine.sh`（任务只要求微基准 + E / F 端到端；B29 行里这三项是“入口”而非完成判据）。
- 所有 `benchstat` 都在 n=10 下给出 p 值；B/op 在带后台 goroutine 的基准（AdmissionMatrix、BroadcastPipelinedCommit、WALAppend）里方差 ±20%～50%，只在 allocs/op 同时变化时才作结论。
