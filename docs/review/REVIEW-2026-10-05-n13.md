## 4. 观察（不改行为）

- **O1** `Bucket.Get` 未命中时无论 `buildIF` 都升级为写锁（`bucket.go:89-92`）。EntityManager 用 `buildIF=false`，每次查不存在的 id 都串行化整桶；没有性能证据，不立 RR。它也是 NC-180 里“回调只读一个不存在的 id 也自锁”的原因。
- **O2** `LockManager` 的 `MutexFactory` 在桶写锁内执行；注释说可替换为“分布式锁”，那样的工厂若做 I/O 会挡住同桶所有 `GetLock`。默认工厂只分配内存。
- **O3** `BucketHolder.RangeCursor` 是无同步的导出字段，`RangeWithCursor*` 并发调用会数据竞争；零调用方（README §16 仍把它写成巡检惯用法）。
- **O4** `TopologicalSortCache`：同层节点顺序由 map 决定、每进程不同；`GetCompDependencies` 返回内部切片、`RegisterCompDependency` 保存调用方的变参切片，双方都能改到对方。`manager/order.go` 已因这两点不用它。
- **O5** `ObjectPool` 同一对象 `Put` 两次，freeList 里出现两份，之后两次 `Get` 拿到同一对象。与 `sync.Pool` 的误用后果同类，文档已声明单调用栈使用，零调用方。
- **O6** `ShardedSafeMap.Read` 在分片读锁内调用回调，回调里写同一分片会自锁；README 只写了 `Compute`。零调用方。
- **O7** 生成 DAO 的 `RangeX` 对三种 map 的“回调里改 map”语义各不相同且没有文档：Small / Sharded 遍历快照（回调里删掉的未到达键仍会交出），Fast 活遍历（NC-182）。同一个 tag 选项 `map=fast` 因此改变业务遍历的结果。
- **O8** `SafeFunc` 只记录 `recover()` 的值，不记栈，也没有指标；nest / worker 的业务 panic 只剩一行日志。改为记栈是可观测性改进，未改。
- **O9** TaskPool：`Shutdown` 之后再 `Start` 会起读已关闭 channel 的 worker 并把 `IsRunning` 置真，之后 Submit 全部报 worker closed；`totalTasks` 在入队成功后才加，统计瞬间可能 completed > total。零调用方。
- **O10** `Parallel*` 把回调 panic 吞成日志，`*Collect` 对应位置留零值，调用方无法区分。零调用方。
- **O11** 根 README §16 把 `KeyMap` / `ObjectPool` / `BucketHolder` 写成 `misc.*`，实际在 `container`；随本轮文档改正。

## 5. 方向判断

本单元此前没有修复链，不属于“同一处反复出问题”。但本轮六条里有四条（NC-180、181、182、185）是同一类问题：**遍历回调里改容器**在每个容器里各有一套语义，而且没有一个写进文档——BucketHolder 持锁调回调、FastMap 活遍历且会重排、KeyMap 交换删除、Small / Sharded 复制快照、`EntityManager.RangeGroupEntities` 先取切片。调用方（生成 DAO 的 `RangeX`、`ManagerAccess.Range`）把它们包成同一个名字交给业务。修复按各自最小改动收敛到“不卡死、不交出不存在的键、不漏键、false 立即停止”，没有增加状态。建议维护者：

1. 把这条写成仓库级契约（README §16 与 `safemap` 包注释）：凡框架交给业务的 `Range`，回调里可以读写同一容器，返回 false 立即停止；是否看到回调里新增的键不作承诺。以后新增容器按这一条审。
2. 零调用方的 API 决定去留：`container.TopologicalSortCache` / `KeyMap` / `ObjectPool` / `BucketHolder` 的游标遍历、`goroutine.TaskPool` / `Parallel*` / `SafeFunc*` 变体、`safemap` 的便捷构造器与 `Compute` / `Read` / `LoadOrStore` / `Snapshot`。保留就按公开 API 维护（本轮已修三条）；移除是破坏性 API 变化，需要发版说明。
