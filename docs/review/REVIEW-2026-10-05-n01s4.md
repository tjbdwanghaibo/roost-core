## 观察（不立 RR）

- **O1 停机期间才发生的 RuntimeFailure 不进 `run` 的返回值**：`select` 已经因信号醒来之后，失锁（或 DataEngine / Remote fatal）只经 `OnFail` 围栏、写 Error 日志，`Done` 没有人再读，`run` 返回 nil，进程退出码 0（探针 B）。安全动作都已发生（围栏、不 Release），只影响退出码与进程管理器的判定；对所有 RuntimeFailure 来源都一样，不是单实例锁引入的。候选：`run` 结尾并入 `runtimeFailure.Err()`。
- **O2 Unknown 让 `/readyz` 503**：`checkHealth` 把窗口内的 Unknown 报 Degraded，`health.Snapshot` 对任何非 OK 都置 `OK=false`。一次续期失败到下一次成功（≤ `renew_interval`）之间就绪探针失败；生成的 k8s readinessProbe `failureThreshold: 3` 能吸收。方案 §5 只写“不触发存活探针重启”，没说就绪是否应受影响，留给维护者定是否把 Degraded 视为就绪。
- **O3 `Dispatcher.OnInit` 清掉 dispatcher 一层的围栏**（见上表候选排除）：manager 一层兜住，当前无可观察后果；若将来有入口绕过 `FenceError` 直接投 dispatcher，会在“Fence 早于 Start”时漏围栏。属于 K1 Nest，另一线的范围，不改。
- **O4 活着的 game 服超过 64**：协调器 `MaxExpectedGames = 64`，候选 ≤ 200 但同时活着的超过 64 时每个窗口被拒；启动时无法判定。需要维护者决定一个活动组的上限。
- **O5 旧 lease 键无 TTL**：升级后不自动清理，每个 game sid 一条永久残留（体积小）。CHANGELOG 已写可以删除，未给命令；运维可按 `SCAN MATCH <global.key_prefix>:lease:*` + `UNLINK` 清理。
- **O6 `AbortMigration` 对非迁移态的空操作计 Accepted**：`CompleteMigration` 同样情形计 Replayed，两者口径不一致，只影响指标（`service.go:179-208`）。
- **O7 启动失败清理里 `Service.Shutdown` 若不遵守 ctx 会让 `run` 永久阻塞**：`app/app.go:340-344` 同步调用，只给了 5s 的 ctx、没有像正常停机那样的外层超时；阻塞期间续期一直在跑、锁一直持有，接替进程每次等满 `startup_wait` 失败。前提是服务的 Shutdown 本身不遵守 ctx，属于既有行为，单实例锁让后果从“这个进程挂住”变成“这个 sid 起不来”。
- **O8 SIGTERM 落在“拿锁后、`exitSignals` 注册前”**（DataEngine 重放可长达 `dataengine.startup_timeout`）：默认处置直接终止，不 Release，下次启动等一个 TTL；方案 §3.4 已列为现状延续。
- **O9 两处配置边界**：`singleton.enabled: on` / `yes` 这类 YAML 字符串经 viper `GetBool` 读成 false，单实例锁静默关闭（通用的 viper 行为，非本模块特有）；`ttl` 不是整毫秒时 Redis TTL 向下取整（最多差 1ms），对 15s / 5s guard 的配置无实际影响。
