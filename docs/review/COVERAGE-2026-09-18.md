## 可确认的源码审查台账与行为覆盖

初始台账只人工核准最近一轮的 **10 个局部源码入口文件**（Core 7、Codegen 3）。每条包含范围、运行报告和审查 SHA；当前 Git blob 对比对应审查基线未变。它只是本次建立台账的种子，不是历史 49 轮仅审过十个文件；Kit 为 0 也只表示尚未回填，不代表没审过 Kit。其余自动引用均等待人工归类。

`FILES.csv` 的 `whole_file_complete`、`behavior_complete` 暂为 unknown，未把局部阅读升级为整文件完成。虽然脚本提供种子占分母的数值供核算，也不应拿它作为框架 review 完成百分比。

当前没有全框架的函数/分支/风险场景固定分母，不能可信计算行为 review 覆盖率。最近一轮确实执行了 14 个新行为叶子（11 过、3 失败）和三组消费编译（1 过、2 失败）；执行到失败断言依然是审查覆盖，不能把通过率当覆盖率。测试代码行覆盖需另行运行带 instrumentation 的测试取得，且测试执行过某行也不等于审查过其业务语义。本任务未为凑覆盖率重跑旧 bug 验收。

## 后续怎样得到真正可用的进度

每次 review 都应记录：仓库路径、精确源码 SHA、已读函数/范围、确认的不变量、测试场景与结果、环境限制，以及未读/未验证部分。历史引用需要逐条回填确认，不能自动全量认定已读。

建议持续维护四个相互独立的指标：

1. **文档路径触达率**：本次已能复算，适合发现记录盲区。
2. **已核准局部源码覆盖**：台账确认有实际阅读证据的文件/总文件，并区分当前源码未变、已变待复核；不称整文件完成。
3. **整文件阅读完成率**：只有明确检查完全部生产源码且有对应版本证据才计入；当前历史台账不足，显示未知而非 0%。
4. **风险场景执行覆盖率**：先为模块固定场景矩阵（正常、边界、并发、重试、崩溃、恢复、关闭、真实后端），再统计已执行/适用场景；失败属于已执行，问题修复状态单列。

从本轮起已有明确分母和格式，可以逐轮回填，逐步把“有文档”转换成“有核准证据”，而不是事后给所有文件贴一个已审标签。此前 [跨轮进度](PROGRESS.md) 的模块描述仍有效，不被本次自动匹配结果覆盖。
