## 观察与设计建议（未登记 RR）

1. **默认没有任何指标落点。** 生成的 game-demo 对所有服务 `Metrics() servicemetrics.Reporter { return nil }`（`codegen/internal/roost/framework_services.go:393`、`demo/internal/service/*/collaborators.go.tmpl`），仓内也没有把 `Reporter` 接到 `metrics` 包的适配器；代码注释称为“唯一痕迹”的计数（如 activity `dispatch.exhausted`）在默认部署里不存在。建议 kit 提供一个基于 `metrics` 的低基数 Reporter 并由生成工程默认接上——是功能决定，不在本轮做。
2. **CAS 冲突率口径不统一。** kit/service/README 第 6 条要求每个服务有冲突率；实际只有 chat 对 `versionstore.ErrConflict` 计数，其他服务只在 insert-only 碰撞处报 `Conflict`，account / activity 一处都没有。框架级口径问题，建议在 versionstore 层统一计数而不是逐服务补。
3. **activity `markReservationApplied` 无预约身份。** 一次 apply 在参与者 CAS 之后、mark 之前停顿超过 `ReservationTTL`，且客户端在过期后**复用同一请求 ID** 发新请求时，旧操作会把新预约标成 applied。前提是客户端跨视界复用 ID，设计已声明视界外的同 ID 等同新请求；记为身份隔离的设计余项，不登记。
4. `RetireDelivered` 对“键不在该窗口的 Delivering”也返回 true（NC-51 的放大器之一）；`create_role.plan_released` 在两个换名请求并发释放同一死计划时多计一次。（10-06 B9 已修，见 [NC-51 复核补修](../bugfix/RR-20261005-NC-51.md#复核后的补修2026-10-06维护者决定-b9)、[NC-50 复核补修](../bugfix/RR-20261005-NC-50.md#复核后的补修2026-10-06维护者决定-b9)。）
5. chat 单频道单键：NC-52 修后伪冲突消失，但热点频道写仍串行在一个键上，容量未测。

## 方向判断

- **activity 窗口恢复入口**：RR-20260914-02 → RR-20261001-09 → 其残余（10-05 第 27 轮）→ NC-42 → 本轮 NC-51，同一个不变量（“窗口里存的条目先验证再行动”）第四次在相邻循环被打破；每次都是在一个读取窗口条目的位置补判断。本轮已把判断收成一个 `windowKeyProblem`，Keys 与 Opening 共用；仍建议下一步把“读取存储窗口条目”收敛为一个入口（返回已验证条目 + 坏条目清单），Delivering 列表与 `RetireDelivered` 也走它，并补一个 owner-only 的窗口坏条目修复入口，而不是在第五个循环再补。当前证据不支持换掉窗口设计本身。
- **account 建角状态机**：RR-20260929-19 → RR-20261001-06 → 本轮残余，修复每次只覆盖一个请求形状（同名 / 换名），信号是“同一个已判定事实只在部分入口生效”。本轮把 `createRole` 改为显式分支并让换名复用同名的判死证明；建议后续把它写成一张“slot 状态 × 名字条目状态 → 动作”的表，与 Admin 的拒绝条件同源，避免第三种入口（如未来的改名）再漏。
- **versionstore**：NC-52 是新类别（重试循环取值时机），没有反复信号；但它影响所有 Redis 服务，之前多轮“真实 Redis 才红”的偶发冲突值得按此复核。
