# U-0199 漏审复盘

来源是用户复审发现，[作者原记录](../bugfix/U-0199-submit-input-validation-order.md)保留，不计为 review agent 新发现。复盘基于修前 `2c89f3d`、修后 `2c5469e` 及此前实际测试，不能用后见之明宣称当时已覆盖。

## 为什么漏掉

此前 RR-08 验证了身份表容量，临时 TestReviewAcceptedIdentityBound 先 Advance 4096 次，再提交 1..4096 的旧帧，只断言 accepted 长度不超过窗口。它验证“已有资源有界”，没有验证“拒绝请求不产生资源副作用”。即使分配了 129 个槽，也会满足原断言。

对 U-0197 的复核集中在去重和固定环是否解决原问题，没有重新追踪客户端帧号到 slot 索引的完整校验顺序。旧代码在未来帧窗口检查前调用 slot，且先将 uint32 转 int 再取模。忽略前者漏掉非法请求的惰性分配，忽略后者漏掉 32 位负下标。这是审查方法和输入样本选择不足，不应归因于作者改动太多或工具没有报警。

测试运行于 64 位环境，race 检测的是竞争，不检查 32 位整数转换；小帧号、正常回环和原 bug 回归均不能证明极端输入安全。图谱当时旧代也不构成免责理由：该表达式在已经阅读的当前源码内。

“六个文件已读”是阅读进度，不能替代输入边界审查。此前虽保留整体未收敛说明，但没有把这项具体缺口列出，给出的完成度信号仍过于乐观。

## 本次补证

独立临时测试使用 2^31、4e9、MaxUint32 三个未来帧：均须 ErrFrameTooEarly，且 accepted[1] 无分配。对修前 sequencer.go 的 overlay 三个断言均失败（129 槽，0.601s）；修后同测试通过。作者新增测试、已有重传/乱序/覆盖相关测试也通过（专项 1.606s）。没有将仅交叉编译描述为 32 位运行验证；本轮未执行 32 位 panic 场景。

## 后续执行要求

1. 修复改变容器或索引时，重新追踪“外部值→校验→转换→索引/分配→状态提交”，不只复跑原 bug。
2. 每个拒绝分支同时考虑返回值与副作用：容器增长、游标、计数、配额、回调是否改变；区分必要指标和业务状态。
3. 整数用 0、边界±1、MaxInt32、2^31、MaxUint32 检查，区分实际目标架构与源码可移植性。未跑的平台明确记录。
4. 分别维护源码阅读、输入拒绝路径、失败恢复、资源边界与平台证据；不以测试数量判定完成。

未关闭边界：FrameID 回绕时 next+window 与单调性证明的适用域；SubmitInput 的 nil 返回无法区分实际保存、重复或输给已存在输入。后者是作者明确未实施的 API 语义扩展，不擅自改实现，也不另报重复 bug。
