## K1 新增审查范围

### 实体加载

图谱从 `ManagerAccess.loadEntityShared` 向内读源码、向外追到 Get/guard/Nest/remoteentity。ManagerAccess 与 EntityRepository 各有一层 per-fullID singleflight，正常返回时都先保存结果、移除 flight、关闭 done；取消的 waiter 只退出等待。

新增失败面是执行者 panic：两个实现都把清理写在被调用函数之后，没有 defer，因而 flight 永久悬挂。独立临时测试确认 ManagerAccess 层 panic 后同一实体的第二次 load 不再进入 loader。登记 RR-20260919-08。

相邻但未单列的问题包括：首个 caller 的 context 是共享 load 的执行 context，leader 取消会影响所有 waiter；Runtime Shutdown 先撤销 loader 再关闭 projector/outbox，但没有等待已经准入的 repository flight。后者可能让旧 generation 的 load 在关闭期间继续发布进共享 manager。当前有“services 先停”的装配假设，本轮没有完成跨 runtime/真实 store 复现，保留为 K1/K2 交接观察，不写成已确认 RR。

### Nest single/broadcast

single 与 broadcast 都把 Getter 的 `(nil,nil)` 当成实体，生产 ManagerAccess 恰好允许这个返回。single 产生外层 recovery 的 runtime 错误；broadcast 的 nil panic 发生在逐实体 recovery 之前，会终止后续 id。multi/multiGroup 已有 nil 对照。登记 RR-20260919-09。

worker 串行路径继续读取了 `safeHandle`、release defer、Close/TryCast 配对和队列排空；Core 四包 race 通过。本轮没有在该有界范围发现新的 worker 确认问题，但尚未完成真实高负载关闭、leader context 与 runtime handoff，因此 K1 仍是“已验证部分场景”。

## 新 activity feature 的跨层审查

Kit 的 activity 聚合、持久 Delivering 索引、dispatch CAS/token/ACK/Reopen 原语已经形成清晰状态机。缺口在“谁实际把 payload 交给 game”：Server sweep 调 `AttemptDispatch` 会消耗预算，但调用链没有传输；游戏生成物独立轮询两个时间推导 key，无法枚举旧义务。该组合登记 RR-20260919-10。

现有工具足以收敛，不需要另造消息系统：沿用 activity Store/CAS、Delivering 索引、servicerpc 生成器和 token ACK，增加按 game 的有界 owed 索引，让 game 真正领取 payload 时才消耗 attempt。完整方案见[实现学习](IMPLEMENTATION-ENTITY-LOAD-AND-ACTIVITY-HANDOFF.md)。
