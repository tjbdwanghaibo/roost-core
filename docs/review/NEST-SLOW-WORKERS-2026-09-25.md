# Nest 慢池并发与队列实测（2026-09-25）

后续实施：[资源预算与会话恢复](../feature/REFACTOR-2026-09-25-resource-budgets-and-session-recovery.md)。以下表格保留原配置（Remote 写预算 4096）历史数据；新 DefaultConfig 的写预算为 128，复跑时必须记录有效预算，不能直接当作相同配置。

已完成10轮正式生成业务链路测试，全部基于 RR-08/09 修复后的同一套 Go 源。本机当前 strict Remote 负载下，**慢池128 worker / 整池等待16是通过100 TPS短测的候选**；不支持把慢 worker 一律扩大到1024。没有改变全局默认并发、Go业务源码、事务持久化语义或5秒超时。

每轮持续输入120秒，每轮14400笔；所有组 fixture dropped=0，但以下均存在请求错误，没有一轮完成零错误全量验收。p99仅统计成功请求，不能漏看错误列。

| 慢 worker / 等待位 | 成功 TPS | 成功 / 错误 | p99 ms | WAL 未确认采样最大 / 测量结束 |
| --- | ---: | --- | ---: | --- |
| 64 / 64 | 105.14 | 12709 / 1691 | 1321 | 64 / 0 |
| 64 / 64（复跑） | 106.40 | 12873 / 1527 | 1366 | 64 / 0 |
| 64 / 16 | 119.03 | 14329 / 71 | 714 | 64 / 0 |
| 64 / 16（复跑） | 117.74 | 14175 / 225 | 777 | 64 / 0 |
| 128 / 16 | 107.01 | 12936 / 1464 | 1427 | 128 / 0 |
| 256 / 16 | 107.08 | 13024 / 1376 | 2647 | 256 / 0 |
| 1024 / 16 | 10.14 | 1267 / 13133 | 4549 | 3912 / 3066 |
| 1024 / 64 | 10.95 | 1369 / 13031 | 4935 | 3578 / 3059 |

64/64和64/16各跑两次：本轮小队列两次均有较高成功吞吐和较低p99，说明在这套负载下短队列值得采用；但它们都没有通过120 TPS验收，不能把117.74～119.03 TPS当零错误能力。顺序测试和本机环境仍会有波动，两次复跑不构成统计显著性或通用最优配置证明。

128→256的成功吞吐几乎不变，p99从1427ms升到2647ms。1024/16和1024/64都出现严重超时退化，队列长度采样始终为0；问题并不是这16或64个等待位不够。

## 100 TPS通过负载验证

每轮持续输入120秒，每轮12000笔，fixture dropped=0。

| 慢 worker / 等待位 | 成功 TPS | 成功 / 错误 | p99 ms | 验收 |
| --- | ---: | --- | ---: | --- |
| 64 / 16 | 99.08 | 11930 / 70 | 909 | 有拒绝，未执行最终全量校验 |
| 128 / 16 | 99.44 | 12000 / 0 | 1340 | 全量通过，积压清零 |

128/16组退出0，`.verified` 确认全量 Mongo/NATS 快照、rollback/outbox 检查通过；测量结束 WAL、队列及 Remote 在途事务归零。64/16组错误样本均为队列满；采样队列最大只有10并不矛盾，10秒一次的采样会漏掉瞬时满队列。

选择128/16是为了给当前Remote等待提供适量余量；不能声称它比64/16延迟更低。此前64/64的100 TPS历史通过结果仍保留，但没有用历史结果替代本轮通过验收。当前配置可写为：

```go
nest.NestOptionWithWorkerPools(
    nest.WorkerPoolConfig{Workers: 8, QueueCap: 4096},
    nest.WorkerPoolConfig{Workers: 128, QueueCap: 16},
)
```

这是同机短测的候选配置，不是全框架统一默认值。没有重复30分钟/24小时长稳或完整集群故障矩阵；没有确定精确TPS上限。

## 为什么1024反而更差

1024/16最早记录的错误样本为5000ms的 `nest: sync timeout`，当时WAL未确认592笔；该组前32个错误样本均为同步超时，但不能据此穷尽全部13133个错误类型。1024/64的前32个样本同样为同步超时。

1024/16外部准入后排队平均约0.013ms，内部快延续排队平均约0.01ms，Remote确认阶段平均约4722ms；WAL未确认采样最大3912、测量结束3066。1024/64也达到3578/3059。额外并发把等待移进了后置确认链路，Nest队列短并不能证明端到端延迟小。

成功回复TPS与实际投影进度必须分开：1024/16测量期间投影完成约90.7笔/秒，成功回复却只有10.14 TPS。很多事务在调用者超时后继续推进，不能把超时当作未写入。该组进程goroutine采样最大13407（包括负载会话、Nest、租约与后续处理等全部协程），不是慢worker变成了13407个。

源码已核对：`remoteWriteBatch.Commit` 在strict确认等待失败时标记indeterminate，`Close` 转交 `deferRemoteClose`，避免把已持久准入的不确定事务当作回滚成功。因此Nest请求结束后Remote在途数可以继续存在，甚至超过慢worker数；Remote还有独立finalizer准入预算，当前默认4096。本轮没有通过延长超时或改变确认语义掩盖过载。

需要继续扩大总体慢I/O并发时，应区分通用慢池执行资源与Remote后端在途预算；这属于后续优化方向，本轮仅完成验证，没有引入新的限流实现。

## 环境、负载与计量口径

Apple M5、Go1.27.0、GOMAXPROCS=4，本机隔离Mongo三节点、NATS三节点、Redis。固定快池8/4096，Remote投影并发8；1000业务会话、10000 Entity，每事务2 Entity×2 DAO、strict。不是1000人一个room模型，也不是客户端AOI广播或纯Nest消息吞吐测试。

每档新建隔离业务数据库，5000笔事务预热全部实体后计时，预热不计入TPS。固定输入速率独立于完成速度；不同档顺序执行。顺序为64/64、1024/16、128/16、256/16、64/16、1024/64（120 TPS），然后64/64复跑（120）、64/16与128/16（100），最后64/16复跑（120）。

成功TPS分母包含输入结束后的请求返回等待；p99从计划发送时刻算起，包含调用侧排队，但仅统计成功请求。WAL、队列、在途事务、堆内存、goroutine每10秒采样，表中最大值不代表瞬时峰值。失败组的“测量结束”在全部Request返回时，可能早于后台事务收尾；没有把它称作进程退出后的最终持久状态。

每个会话同步等待一笔Request，1000会话限制调用侧并行度；1024worker并不必然同时繁忙。超时转交后台后，Remote在途数可以继续累积。零错误、零丢弃、子进程退出0且全量检查通过才算通过档；有错误时测试刻意跳过最终精确状态校验，因为超时事务可能继续提交。

## 复跑入口

```bash
source /tmp/roost-dataengine-it/env.sh
GOCACHE=/tmp/roost-nest-go-cache \
ROOST_REMOTE_WORKER_LABEL=workers-unique-label \
ROOST_REMOTE_WORKER_CASES='64:64:120 1024:16:120 128:16:120 256:16:120 64:16:120 1024:64:120' \
ROOST_REMOTE_DURATION=120s bash scripts/perf/remote-workers.sh
```

每项为 `慢worker:等待位:输入TPS`。单独验证通过配置可设 `ROOST_REMOTE_WORKER_CASES='128:16:100'`；每次使用新label。脚本保留独立env、result、JSONL、压缩日志和退出码。业务过载失败后继续比较，环境/预热失败且无result则停止；整个矩阵非零退出表示至少一档失败，不能只看是否跑完。需要正常访问本机进程和隔离端口。
