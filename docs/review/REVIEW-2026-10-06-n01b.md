## 3. Health 策略

现行映射（当前源码）：

| 端点 | 判定 | k8s（生成的 Deployment / StatefulSet） | shell 部署 |
| --- | --- | --- | --- |
| `/healthz` | 无条件 200（进程的 HTTP 在就答） | startupProbe（`failureThreshold` 按 `startup_wait + 30s` 计算 × 2s）、livenessProbe（10s × 3） | — |
| `/readyz` | Ops 就绪位（service.started 置 true、service.stopping 置 false）**且**每个 checker 为 OK；Degraded 与 Fail 一样让整体 `ok=false`、回 503（`health.Snapshot`：非 OK 即失败，README 写明“degraded 在聚合层等同失败”） | readinessProbe（5s × 3，timeout 2s） | `healthcheck.sh` 等 readiness |

Degraded 的四个来源：单实例锁续期结果未知（≤ `renew_interval` 的窗口）、entitysync 主体 / 会话 ≥ 80% 容量、remoteentity 写许可用满、DataEngine 投影积压告警（`app/singleton.go:558-572`、`sync/entitysync/manager.go:1018-1036`、`kit/remoteentity/remote_entity_mod.go:259-276`、`kit/dataengine/mod.go:446-468`）。Fail 来源是“不能再安全工作”的状态（fenced、Projector / Outbox 不健康、容量用尽、关闭、失锁、未持有）。

判断：**现状与文档一致，不是缺陷**，但 Degraded = 摘流量对单副本服务的代价可能大于收益（单副本的 Service 没有别的 endpoint 可切；entitysync 在 80% 边界上没有滞回，会随负载来回翻转；积压告警期间仍能正常服务）。是否让 Degraded 保持就绪（200，`dependencies` 里照样报 degraded）属于运维语义，登记为 [DECISIONS-PENDING D1](DECISIONS-PENDING-2026-10-05.md)，本轮不改行为。n01s4 O2（续期 Unknown → 503）由生成的 readinessProbe `failureThreshold: 3`（15s）吸收，并入 D1。

状态切换与探针配合的其他核对：就绪位在 service.stopping 置 false 早于 Service.Shutdown，停机期间 `/readyz` 立即 503；Ops 是共享 Mod、在服务专属 Mod 之后停，停机全程 `/healthz` 可答，liveness 不会在宽限期内误杀。观察 O-H1。

## 观察（不立 RR）

- **O-P1 `bearerToken` 接受不带 scheme 的 Authorization**：`Authorization: <token>` 也能通过（`bearerToken` 无前缀时原样返回）。仍需要知道 token，不构成绕过；若要严格按 RFC 7235 只认 `Bearer`，属行为收紧，留给维护者。
- **O-P2 admin 审计身份是客户端自报**：只有一个共享 token，`Command.Operator` / `Source` 来自请求体，审计记录里的操作者不可信。需要按操作者区分时应在鉴权代理侧做，或改为多 token；属设计边界。
- **O-H1 checker 没有单独期限**：`/readyz` 用请求 ctx 串行跑全部 checker（Redis 自带 2s，DataEngine 的 `RefreshBacklog` 走 Mongo）；k8s 探针 2s 超时断开连接会取消 ctx，配合 ctx 的 checker 随之返回。不配合 ctx 的 checker 每次探针留下一个卡住的 handler，Ops 停机会等它们（按三步停机保留依赖，方向安全，但停机会因此“不完整”）。建议将来给 Snapshot 一个短期限并对卡住的 checker 报 Fail，不在本轮改。
- **O-G1 `ManagerGroup` 无生产调用方**：与 C3 / C8“零调用方 API 保留”同类，注释已写明无预算语义；去留由维护者决定，不另登记。

## 方向判断（roost-coding“反复出问题要上报方向判断”）

**App 停机收尾（`app/app.go` `run`）**：近两轮在同一函数上的修复链——NC-193（`d6550a16`，启动失败清理的 Shutdown 不受预算 / 不保留依赖）、本轮 NC-231（停机阶段 hook 不受预算）、NC-232（停机期失败不进返回值）；更早有 RR-20260926-42 / 51（Mod 停机预算分配）与单实例锁的 `singletonReleasable` 逐点置位。信号：**同一不变量（停机路径上的每个回调都在预算内等、超时保留依赖）第二次在 run 里被打破**（NC-193 之后是 NC-231），而且两次都是“run 里另一处同步调用”。判断：根因是**实现结构**而非前提——run 把启动、Serve、停机、收尾写成一条 400 多行的直线，每个回调点各自决定同步 / 异步、是否保留依赖、是否置位可释放，新增一个点就可能漏一项。本轮修复没有新增状态（`failureReturned` 只是“是否已报告”的布尔），hook 派发复用与 Service.Shutdown 相同的“goroutine + 在 ctx 内等”。建议（与 n01s4 的建议一致，可在下个大版本做）：把 run 的停机收尾收拢成一个“已启动对象栈（Service、服务专属 Mod、共享 Mod、停机 hook）+ 统一的 `stopWithin(ctx, step)` + 是否停完”的结构，单实例锁的可释放判定只看这个栈是否停完，而不是在每个返回点置位；代价是一次中等规模的重构与 `singleton_test.go` / `startup_cleanup_promises_test.go` 全量回归，收益是新回调点不可能绕过预算。当前不需要改变方向。

**kit Mod 停止入口**：NC-233 与 NC-173 残余（etcd `Close` 不幂等）同形——“第三方客户端 Close 不幂等、Mod 按 Close 结果决定是否交出资源”。其余 kit Mod 是否还有同形，本轮未逐一核对（范围外），建议 A3 骨架之外再加一条轻量约定：不等待在途工作的 Close 类停止，第一次调用后无论结果都交出资源、错误只报告一次。
