## 观察（不登记 RR）

1. `RedisStore.Update` 最后一次 CAS 失败后仍退避（最大窗口 64ms）并多一次 GET 才返回 `ErrConflict`；该 GET 出错时返回的是传输错误而不是 `ErrConflict`。纯耗时 / 分类细节，无承诺被打破。
2. `versionstore.RetryBackoff` 不看 ctx，取消后仍睡满一次退避（≤64ms）。有界。
3. go-redis 自动重试对非脚本写命令同样生效：`failurelog` 的 `RPush`（N12）在回复丢失时可能重复追加；driver `DistLock.Acquire` 的 `SetNX` 被重放会把已持有误判为未取得（DistLock 已无生产消费者，`kit/mods/name.go:16`）。NC-100 只关闭脚本重放；是否把 RedisMod 默认 `MaxRetries` 也改为不重试，需要按命令幂等性统一定，留给维护者。
4. 驱动 `DistLock.Release/Extend` 仍用 `rdb.Eval`（包内测试替身只覆写 `Eval`），无生产消费者，本轮未改。
5. `RefHMap.Patch` 对已过期 / 不存在的记录返回 `ErrRefHMapUnsupported`（“requires an existing root”）。不创建是 NC-18 的定案；把“缺记录”归为 Unsupported 让调用方难以区分编程错误与正常过期，建议后续给独立哨兵。
6. 既有 `redis/driver/lock_toxic_integration_test.go` 与 `remoteentity/process_lock_integration_test.go` 等调用 toxiproxy `/reset`，会清掉同一 toxiproxy 上所有代理的毒（包括别的会话的）；本轮新回归改为自建随机端口代理、只删自己的毒。并行使用隔离环境时这两类旧用例应串行跑。
7. `mongo/driver` 的 session 现在自己实现重试循环（与驱动 v2.6.0 便捷 API 规则相同）；升级驱动时要对照驱动 `Session.WithTransaction` 的规则变化（记在 `session.go` 注释与 NC-101 bugfix 记录）。

## 方向判断

versionstore 的同一个 `Update` 循环一天内第二次出缺陷（NC-52 退避后用旧值 → NC-100 驱动重放把自己的写当成别人的写），N04 近期的 Redis 修复链还有 RR-20261004-01（取锁丢回复）、RR-20261004-03（Patch TTL）、NC-13～20（RefHMap）；Mongo 侧 RR-20260926-34（标签丢失导致重跑到超时）与本轮 NC-101。共同根因不是实现细节，而是**第三方驱动的默认重试 / 超时语义与框架“结果未知交给调用方”的契约不一致**：go-redis 默认重放（App 单实例锁已单独关闭）、ContextTimeoutEnabled 曾缺失、Mongo 便捷 API 用 background ctx 提交。每次都是在某个调用点发现后单点修补。

建议（按代价从低到高）：①在 `redis/driver`、`mongo/driver` 两个适配层各写一张“驱动行为契约表”（哪些命令会被驱动重放、哪些 ctx 被驱动替换、默认超时），新增调用点对照它，而不是在业务层各自补；②RedisMod 的 `MaxRetries` 默认改为不重放写命令（需要按命令列幂等性，影响面是全部 Redis 使用者，需维护者定）；③versionstore 的信封里带一次性写令牌，回复丢失后可像 versioned lock 那样“认领自己的写”，把未知结果变成确定结果——改持久格式，需要迁移方案。本轮只做了①中与缺陷直接相关的两处（脚本不重放、提交受窗口约束），没有改默认配置或持久格式。
