## 3. 观察与设计建议（不登记 RR）

- **O1** `codegen/scripts/source-head-check.sh:40-43`：full 场景 `(... roost add ...) || true` 吞掉 add 失败；与 `framework-compat.yml` source-head lane 的 add 序列（component / dao / handler / protocol / endpoint / rpc / sync）已漂移，“本地镜像”名不副实。本机 full 当前全部 add 成功，没有现行触发，建议去掉 `|| true` 并把序列与 workflow 收敛到一处。
- **O2** `scripts/pretag.sh:87`：`go mod tidy` 直接改工作树，未整洁时失败后留下改过的 go.mod / go.sum（提示里要求提交，属有意为之）；`grep '^(--- FAIL|FAIL|panic:)'` 对编译失败只打印 `FAIL pkg [build failed]`，编译错误本身要看保留的完整日志。
- **O3** `scripts/test-remote-matrix.sh:10,12`：label 非法或输出目录已存在时 `exit 2` 不打印原因（remote.sh 会打印）。
- **O4** 验收锁是“目录存在即持有”，进程被 SIGKILL 后残留需人工确认删除（C01-RUNBOOK 已写）；NC-203 修复后残留锁也会挡住 fault / reset，这是预期的保守方向。
- **O5** `kit/dataengine/toxic_integration_test.go:43-44,71`：与 NC-208 同根因，但 kit/dataengine 属 DataEngine 核心边界，本线不改，留给核心线（见 NC-208“未修部分”）。
- **O6** glsvet 仍用已弃用的 `parser.ParseDir`（不看构建约束，平台变体文件会被合在一起解析）；当前门禁没有因此误报，改为 `go/packages` 是独立改造。

## 4. 方向判断

本单元第一次审，没有“同一处修了又坏”的链。但九条里有六条（NC-201、202、203、207、208 以及 N03 的 1s 事故、N04 观察 6）是同一个前提问题：**隔离环境被当成单人独占资源设计**（固定代理名、全局 `/reset`、只有部分入口看的验收锁、按变量准入的整包运行），而实际上多个 agent / 会话会同时用它。继续逐个入口补“检查锁 / 只删自己的毒”能堵住已知路径，但新入口照样会漏。建议维护者在两种方向里定一个：(a) 承认独占——所有会改环境的入口（含 `go test -tags integration` 的故障用例）都必须持有同一把锁，按入口在根包加门禁；(b) 承认共享——故障用例一律自建代理 / 自起进程（versionstore、mongo/driver、remoteentity 已是这样），共享 toxiproxy 只保留给环境脚本自己，`heal` 不再全局 reset。本轮修复按 (b) 的做法收敛用例、按 (a) 的做法给脚本入口加锁检查，两者不冲突；未选定之前不扩大到核心包。
