# Roost 核心功能分类与审查优先级

2026-09-18，按用户要求先分类，后续优先核心功能。此文是风险分类和审查路线，不是新增功能验收，不增加 review 轮数或 RR，不修改实现。用户声明未修复时仍跳过旧 bug 验收，沿核心主链未查范围继续。

基于当前三仓目录清单、README 能力定位和已有审查记录。Core 当前 80426ad，Kit 55f3a35，Codegen 2e09c16。MCP D-whb_s ready，但仍是旧索引；本次 architecture packages 输出主要是外部依赖，不能据此认定完整内部架构，分类以当前文件清单和明确职责为依据。README 的版本及部分旧归属说明不作现行实现证明。

## 一、按功能分八个运行时域

“核心功能”不等于“所有放在 core 仓库里的文件同等优先”。下面是审查分组，不是要求重构目录。共享包会跨域使用，最终文件统计仍需去重。

| 编号 | 功能域 | 要解决的问题 | 主要入口/包 | 审查重点 |
| --- | --- | --- | --- | --- |
| K1 | 实体与事务执行 | 业务对象如何加载、串行修改、回滚、删除 | entity、nest、lock、worker；关联 event、DAO 生成 | 同实体串行、多实体锁序、作用域、内存回滚、删除、超时/停机后的请求结算 |
| K2 | 数据提交与恢复 | 已承诺成功的数据如何不丢、不重复、可恢复 | dataengine、dataengine/engine、nestwal、versionstore；相关持久化 driver | dirty→mutation→WAL→commit→projection、pipelined 水位、不确定提交、重放、checkpoint、schema 升级 |
| K3 | 跨服实体与所有权 | 多进程下谁有权写、迁移后谁是权威 | remoteentity、entity 的 remote 路径、ownerroute、mirror；关联 cache/Redis/etcd | owner/fence/epoch、旧 owner 拒写、锁租约、迁移交接、镜像更新、墓碑与防复活 |
| K4 | 实时同步与房间 | 客户端/其他服务如何得到正确且可恢复的状态 | entitysync、statesync、room、syncstream、syncbus、lockstep、nettransport | 状态与帧同步分别建矩阵；订阅/基线/ACK/LOD、分片、丢包与重传、追帧、慢连接、关闭与业务恢复 |
| K5 | 请求接入与消息通信 | 请求身份是否可信、消息是否送达正确对象 | gateway、bus、servicerpc、security、webroute、httpserver；相关 NATS/协议适配 | 身份绑定、鉴权、重放、参数/资源上限、可靠投递与去重、超时/取消、错误语义；GM 管理面属于此域 |
| K6 | 通用业务与跨域流程 | 邮件、匹配、副本流程、发奖等如何一致 | service/mail、match、session，saga；Kit 尚存 account/chat/global/activity/platform/rank/directory | 奖励幂等、领取与补偿、稳定业务 ID、队列隔离、状态迁移、过期回收、跨存储原子性与 RPC 边界 |
| K7 | 技能、战斗与行为 | 游戏规则如何调度、打断、结算并同步 | skill 及 combat/combatcomponent/skillcompose/skillsync、spatial、actionflow、ai；关联 configdata/timer/clock | 技能生命周期、取消/中断、效果归属、伤害/资源结算、状态组合、定时器、配置热更一致性、玩法同步 |
| K8 | 服务运行与运维安全 | 服务怎样启动、失败、停止、恢复及被观测 | app、manager、lifecycle、health、admin、metrics、log、failurelog、featureflag、hotcode；关联 goroutine | 依赖顺序、部分启动回滚、准入关闭、排空与资源释放、fail-stop、管理命令权限、配置门禁和告警 |

基础容器、safemap、index、misc、HTTP 客户端等作为上述域的依赖审查，不为了提高文件比例先机械扫工具。若某个基础原语处于锁、身份或持久化关键路径，则随关键链优先检查。

## 二、Kit / Codegen 是横向必查项

每个功能域都按同一条消费链检查：

**Codegen 输出与业务调用 → Kit 配置/装配 → Core 实际行为 → 存储或传输 → 故障后恢复。**

这不是每条运行链都必须经过生成器或 Kit；手工接入仍有效。意思是声称支持的接入方式都应有对应证据，不能只测 Core 单包。K1/K2 对应 entity/DAO/Nest 生成器，K4 对应同步配置/packer/transport 装配，K5/K6 对应 protocol/servicerpc 与服务模板，K7 对应配置/属性等生成契约。

Core 负责核心语义，Kit 负责配置、连接、装配和接入便利，Codegen 负责与当前公共 API 一致的生成物。归属与审查优先级不同：Kit 中尚未下沉的核心领域逻辑仍必须优先审，不能因仓库名称略过；Codegen 导致核心功能无法构建也属于核心接入问题。

生成器文字测试、Core 包测试、真实生成消费测试、真实后端故障验证分别记录，不能互相代替。

## 三、风险顺序

以下“第一/第二/第三梯队”是 review 优先级，不是 bug 的 P0/P1 严重度。

| 梯队 | 范围 | 排序原因 |
| --- | --- | --- |
| 第一：数据与权威安全 | K1、K2、K3；K5 的身份/权限；K6 的资产发放/补偿；K8 的准入关闭与 fail-stop | 出错可能导致错写、丢数据、重复资产、越权或不可恢复历史 |
| 第二：实时与玩法核心 | K4；K7；K6 的匹配/会话等状态流程 | 直接影响对战正确性、玩家状态与核心玩法；既有深审区补缺，薄弱区扩大范围 |
| 第三：外围完备性 | K5/K8 其余接入与运维能力、展示/示例、非关键便利工具 | 在核心契约稳定后扩展；若发现安全或全局阻塞风险，立即提升 |

K7 体量观察（当前按用户要求暂缓，不触发优先审查）：当前清单中 skill 子树 179 个主要源码文件，占 Core 526 个的约 34%。历史报告主要集中少数入口，不能由调度测试推导伤害、效果组合和同步都已验证。该数是体量而非风险权重，目标是暴露盲区，不是让大包自动压倒关键小包。

## 四、后续 review 的执行顺序（按用户最新要求）

**当前先集中完成 K1 → K2 → K3 的有界审查与整理，K7 技能/战斗暂缓。** 此顺序优先于上节的一般风险分类。前三类尚有未查内容时，不因全仓覆盖率低转去独立技能、GM、邮件等专题；其他域只在这三类的实际依赖和对外承诺边界需要时跟进。

1. **K1 实体与事务执行**：加载/释放 → guard/串行调度 → 多实体锁序 → mutation/回滚 → 删除、超时及关闭结算；关联 entity/DAO/Nest 生成消费者与 Kit 装配。
2. **K2 数据提交与恢复**：dirty/mutation → WAL admission/commit → projection/checkpoint → reply/outbox/sync 的持久化顺序，检查不确定提交、恢复重放和 schema 升级。与 K1 共享的链只核查一次并互引。
3. **K3 跨服实体与所有权**：owner/fence/epoch → 租约与旧 owner 拒写 → 迁移/镜像 → tombstone/防复活 → 故障恢复，包含实际装配及相关缓存/存储边界。

进入每域先复用有 SHA 的历史证据、列未审入口与场景矩阵，随后持续推进未完成范围，不反复从头读。用户未修复时跳过旧 bug 验收，不因已知问题等待修改而停下新内容审查。

每域分别报告源码整理、场景执行和问题修复状态。已声明范围的机制、资源所有权、验证结果、复现/实施交接与剩余风险归档后，才能称该范围整理完成；受限场景不算通过，仍有缺口不称整域全完成。三域阶段性整理完成后再恢复其他功能域轮转，K7 在用户调整前继续暂缓。

本机 `roost-review` skill 已同步这套分类、顺序与完成标准；个人 skill 位于仓库外，不复制进 Core。

## 五、以后按功能域看进度

各域同时记录以下状态，不用单一全仓文件百分比决定投入：

| 维度 | 可计入的证据 | 不可替代它的证据 |
| --- | --- | --- |
| 源码阅读 | 指定 SHA、具体文件/函数/范围，区分部分阅读和整文件完成 | 仅有路径引用、包测试通过 |
| 接入闭环 | 真实生成或手工消费者，核对 Kit 配置到 Core 的实际调用 | 模板 golden 或某层单测 |
| 失败/并发 | 明确场景分母及实际执行结果；失败也算已执行 | 测试通过率、问题修复数量 |
| 恢复/生产边界 | 真实后端、进程重启、故障模型、部署平台和限制 | fake 后端或一次微基准 |

下一步应为每个域建立适用场景清单，再给域内覆盖率；尚未回填的历史证据标未知。共享文件只在总文件分母计一次，但同一文件在不同业务链的不变量可分别验证。不得把八域平均值或任意权重包装成总体完成率。
