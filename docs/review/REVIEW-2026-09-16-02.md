## 设计及性能评价

实现已有清晰的能力分层：普通 NATS 的成功返回不代表持久化；JetStream 使用同步发布确认，但确认只覆盖 broker 接收，不覆盖业务 Apply。SyncBus 包装主动吞掉 handler 错误，底层 driver 的 NAK 机制不能自动为这个包装提供业务重试。接入应明确需要实时通知还是可恢复状态流，复用已有 syncstream History/ACK/恢复机制时仍须满足其未收敛约束，不能把包装类型替换视为完整恢复方案。

命名空间应贯穿 subject、stream、consumer 与去重身份。现有 topic/SID 的稳定散列有助于重启复用消费者，但 Prefix 变化被遗漏；修复需要考虑 Stream 配置所有权和旧游标迁移。

发布路径先复制 Data，再 JSON 编码；接收驱动复制 Data，随后 JSON 解码。该所有权策略减少调用方别名问题，但有复制与编码开销。同步确认还把网络往返纳入发布延迟。本轮未做吞吐、分配或尾延迟 benchmark，不给出性能退化结论；后续应在真实消息大小、分片数与慢消费者负载下测量，再考虑批处理和减少复制。
