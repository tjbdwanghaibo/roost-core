# Roost 三仓架构评估与第一轮问题复核（2026-09-09）

## 结论

Roost 已经具备可靠性导向的游戏后端框架内核：事务提交的不确定性、实体隔离、停机依赖顺序、持久化与状态分发的先后关系，都有具体实现和测试。Core 提供实现，Kit 负责接入，Codegen 管理消费者工程，这个方向成立。当前最值得投入的工作，是把这些机制贯通为一个外部开发者能够重复接入、排障和升级的完整游戏业务闭环。

这是一轮重点路径的源码与行为评估，不是全仓审计或生产认证。没有依据给出并发人数、TPS 或成熟度分数，也不能从包测试通过推导出真实集群故障下的数据安全。本轮确认第一轮三个 P2 在最新提交仍存在，新增一个接入文档问题。未修改框架源码、测试、模板或正式依赖。

## 架构判断：哪些能力有实证

| 领域 | 已核对的机制与源码入口 | 判断及边界 |
| --- | --- | --- |
| Core/Kit 分工 | Core `dataengine/engine/assembly.go` 的 typed Config/Dependencies 与 Assemble/Start/Shutdown；Kit `dataengine/mod.go` 将配置和能力解析后交给 Assembly | 实现归属符合三仓目标。Core 可以承载必要的基础设施实现，不必退回“只有接口”的空壳；关键是契约与具体驱动的依赖方向 |
| 生命周期 | Core `app/app.go:285` 起收敛 Serve/Shutdown，再逆序停止 mods；`stopModsReverseWithContext:411` 在停止未完成时保留依赖 | 不只是调用 Stop 列表，而是在退出超时与依赖仍被使用之间做了明确取舍。超时不能等同于完成清理，进程级处置仍需部署策略 |
| 事务 | `nest/transaction.go:74` 起明确 durable commit 与 indeterminate 契约；`rollback.go:496` 的 durableCommit；`nest_dispatch.go:831` 的 invokeHandlerTransaction | 能区分可回滚拒绝与结果不确定，后者触发 Fence。对玩家资产这类数据，比只暴露一个通用 error 更有价值；不能据此承诺跨系统任意操作 exactly-once |
| 并发与背压 | `worker/pool.go:148` TryDispatch 有明确队列满错误；`nest_dispatch.go:866` 起核对多实体加锁/释放 | 并发正确性有显式协议。业务仍须定义多实体原子边界；不能把实体串行化误当成所有跨实体操作自动安全 |
| 持久化与客户端可见性 | `entitysync/subscription.go` SetDurableWatermark / FlushSubject：超过 durable LSN 时跳过分发并保留 dirty | 同步路径考虑了 pipelined commit 下“内存已变、磁盘未确认”的间隙。实际安全性仍取决于装配正确安装 watermark 和恢复链路，本轮未全链路故障注入 |
| 实时通信 | `nettransport/channel.go:147` 起有会话、可靠队列、字节预算、发送超时边界；可靠与 latest-only 通道独立工作 | 已有针对积压与慢接收端的机制。这证明设计存在，不证明特定人数或时延目标达成 |
| 帧序列 | `lockstep/sequencer.go:102` 起限制成员、输入大小和未来窗口；Advance 按 PlayerID 排序 | 提供输入排序基础。确定性模拟、客户端兼容、反作弊和完整回放验收不能由序列器单独保证，本轮未深审技能/战斗系统 |
| 工程接入 | Codegen `project.go:53` 起在 staging 生成后 rename；`cli.go:117` 强制 module，依赖失败给恢复命令；doctor 检查生成一致性和编译 | Codegen 已承担消费者工程管理。基础文件提交、可选 game template、依赖解析有不同阶段，不能概括成所有步骤整体原子；doctor 也不等于真实依赖健康或业务成功 |
| 边界守卫 | Core `dependency_boundary_test.go` 限制上层依赖/驱动污染；Kit `assembly_boundary_test.go` 检查非测试代码 Raw 调用 | 架构规则有可执行约束，本轮相关测试通过。AST/导入检查是守卫，不是全部运行时资源所有权的证明 |

一个值得保留的调用链是：

```text
Nest dispatch
  → invokeHandlerTransaction
  → invokeWithTransaction / durableCommit
  → durable accepted 或 rejected / indeterminate
  → indeterminate 时 Fence

EntitySync FlushSubject
  → 比较 subject LastCommitLSN 与 durable watermark
  → 未持久化则保留 dirty，后续重试
```

前半段回答“业务能否把操作当成成功”，后半段回答“哪个版本能被传播”。两者必须一起维护，未来优化流水线或锁持有时间时尤其如此。

## 仍需收敛的设计与产品问题

**1. 发布接入体验与内核成熟度不一致。** 当前 Quickstart 固定 Codegen v1.7.0，而当前 release manifest 为 Core v1.15.0 / Kit v1.14.0 / Codegen v1.15.1；示例缺少当前 CLI 必需的 module。文档中心还展示五仓版本顺序。详情见新增 RR-20260909-01。第一次接入失败会让使用者无法接触已经做好的可靠性机制，应当作为框架质量问题处理。

**2. Core 的通用机制与业务部署策略仍有交织。** `app/config_validation.go:66` 起按 `game`、`instance`、`account` 等具体服务名检查 Redis、player、save_load 配置。安全默认值有价值；但通用 Core 如果绑定一种业务命名和持久化组合，会让不同接入方式承担额外耦合。这是架构观察，未确认运行时 bug。建议后续评估可注册的服务配置 validator/profile：通用机制留 Core，标准游戏接入策略由 Kit/模板选择。不要为“分层整齐”删除现有生产保护。

**3. 通用框架的适用范围需要由样板业务证明。** 在没有进一步产品偏好的情况下，我建议先以长生命周期玩家数据、请求重试和断线恢复为首个参考闭环；这是基于本轮已验证能力的路线建议，不是对所有游戏类型的排名。房间状态同步和确定性帧同步应分别有独立示例及验收契约，避免把一套模型的成功推及另一套。

**4. 现有测试投资值得保留，但仍需检查遗漏的并发交错。** 默认包测试全绿与三个外部最小复现同时成立。下一阶段优先补本轮三个触发条件，沿相同不变量检查邻近调用路径，比反复扩大测试数量更有针对性。历史账本的完成项不在本轮未经证据重新打开，也不能用历史通过代替当前运行。

## 下一步：用可验收成果推进框架

按依赖顺序推进，而非按包数量推进；以下是后续建议，本轮未执行修改。

1. **先闭合当前证据。** 修复三条已复现问题并保留独立回归测试；统一 Quickstart、release manifest 与三仓目录说明。验收：三个失败断言变绿，干净消费者按文档即可生成，pure-tag 无 replace 编译通过。
2. **做一个“参考游戏业务”闭环。** 例如登录 → 加载玩家 → 带请求号的资源变更 → 持久确认 → 回复 → 断线重连。至少覆盖并发同请求、超时后重试、提交前崩溃、提交后回复前崩溃。验收关注无重复奖励、成功结果可恢复、版本不倒退；不是只看接口返回 200。根据业务再选多实体操作或 Saga，避免所有简单操作都被迫套跨服协议。
3. **在 Linux 上补运行证据。** 复用仓库已有测试/故障设施，以真实 Redis/Mongo/JetStream/etcd 检查上述业务闭环及恢复。先核对历史账本已有成果，再补当前提交缺口。本轮没有启动真实基础设施，也没有断言现有仓库完全缺少这些测试。
4. **把接入和升级也当成公共 API。** 文档命令、生成文件归属、重复 sync、旧项目升级和 release 组合形成同一消费者验收。区分 source-head 开发门禁与正式 tag 门禁；对需要人工迁移的符号明确给出诊断与迁移清单。
5. **再确定容量目标。** 选真实业务模型、玩家规模、消息大小、持久化等级与可接受延迟，记录队列积压、拒绝率、提交时延、恢复耗时，再决定优化锁、WAL 或网络。没有该负载定义时，不承诺吞吐目标，也不以性能为由提前增加第二套机制。

下轮从本报告三仓 SHA 做增量。高价值入口：新 Assembly 的部分启动失败/Shutdown 超时与资源所有权；durable watermark 实际装配；Session 的账本冲突清理；Codegen 消费者升级。未深审的 remote ownership、技能战斗、全部通用服务及真实基础设施恢复留待后续有界轮转。

长期执行继续使用已安装的 `roost-review` skill；本轮的源码隔离、图谱补证和文档产出均沿用该流程。未创建自动调度，未提交或推送。
