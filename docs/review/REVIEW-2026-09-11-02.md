## 实际验证

Windows amd64，AMD Ryzen 7 5800H，Go 1.27.0；临时 go.work 指向上述三仓，测试以 overlay 注入，不修改源码、go.mod 或仓库工作区文件。命令及完整测试见[复现附录](../bug/REPRO-2026-09-11-02.md)。

| 验证 | 结果 |
| --- | --- |
| remoteentity/nest 相关已有 finalizer、AsyncCompletion、Pipelined、Delayed、Dispatcher 测试，race | 两包通过，1.675s / 1.662s；只是选定测试 |
| Remote：Stop 后晚到 Close，race | 失败；64 个预先取得的 batch 中 29 个 entries/slot 留在无人消费队列 |
| Nest：已注册 handler 的延迟 Request，race | 失败；Shutdown 成功后未完成回复，取消才退出，包耗时 0.711s |
| Nest BenchmarkCommitLockHold，20x | Strict 5.595ms 锁等待；Pipelined 0.04260ms；总耗时分别约 5.593 / 5.495ms/op |
| Remote tracker 满容量 track+complete，100x | 64/1024/8192/65536 条时分别 1.488/33.988/215.458/5491.790μs/op，均 224B、2 allocs/op |

基准不带 race，单次本机采样。Nest 使用模拟 5ms 提交延迟，不能代表真实 WAL；Remote 使用内存替身，不代表端到端 Redis/数据库吞吐。性能观察不另登记成功能 bug。

## 结论与后续

[RR-20260911-03/04](../bug/REVIEW-2026-09-11-02.md) 分别是 Remote 所有权交接缺口与 Nest 请求终态遗漏。优先处理这两个生命周期不变量，再优化 tracker 的满容量扫描。

设计上，Remote 将不确定提交留给有界 finalizer，Nest 将持锁修改与持久化确认分阶段处理，方向适合强调实体一致性的游戏服务。它们的适用条件、热点串行化和完成顺序边界见[实现学习](IMPLEMENTATION-REMOTE-NEST-LIFECYCLE-AND-PERFORMANCE.md)。

本轮未验证真实 Redis/数据库故障、Linux 压测、应用装配全局停止顺序、内部重排请求停机以及异主实体共享次实体的完成顺序。下轮优先读取本轮 bugfix 并复跑附录；没有修复则转上述未覆盖入口，不重复正常路径。[跨轮进度](PROGRESS.md) 已追加本轮证据。
