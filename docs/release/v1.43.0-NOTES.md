# v1.43.0：可编辑地形大世界，实体同步增量压缩与业务同步视图

本版是可编辑地形这一大轮的收口：玩家改地形、水与建筑、Ghost 副本、跨格移动、分区场景的编辑与建筑、客户端岸线与重建调度，以及顺带做的实体同步线格式压缩、业务层同步视图与服务端 codec 校验。逐条变更、决策出处与证据见 [CHANGELOG](../../CHANGELOG.md) v1.43.0 段，总览见 [TERRAIN-STATUS](../maintenance/TERRAIN-STATUS.md)，设计与日志见 [FEATURE-2026-11-08-editable-terrain](../maintenance/FEATURE-2026-11-08-editable-terrain.md)。

**线格式、存储与协议均不兼容旧版。** 线上尚未部署（维护者 2026-10-06 起的口径），本版不做旧进程 / 旧数据兼容。

## 主要内容

- **实体同步的增量只带变化本身**：帧协议 2（uvarint、`RF` 魔数、Tick 差值、只在创建时带 archetype）、subject 信封 v3（增量只带 flags / 基线版本 / 版本差 / mask，身份继承同一 ObjectRef 的全量）、有状态的 `entitysync.Decoder`（逐帧原子，拒绝缺口 / 代际 / 换引用 / 无基线 / 版本链断裂）、DAO 增量不带 entity_id。一步移动 140B → 30B；128 个对象全在动每观察者约 18.6KB/s（本机实测与估算一致）。
- **服务端 codec 校验**：增量的 codec 与会话基线不同时改发全量，不再发出接收端会错解的增量；指标 `entitysync_codec_resyncs_total`。
- **业务层同步视图**：主视野给 `near`、队伍给 `team`，别的玩家不再收到 exp / gold / items / 属性；Interest 带 `ViewSets`，缺视图拒绝启动。128 名玩家进入视野合计 13.9KB → 9.8KB。
- **可编辑地形**（gameplay/terrain + gameplay/cellworld + game-demo + C# 客户端）：
  - 编辑按（玩家 ID, 编辑序号）判重（D18）、按改动点限流（D16）；
  - 水位区域与建筑（地形包 v2）；建筑是普通同步实体（配置 ID + 参数），跟随场景主视野；
  - Ghost 副本（cellworld wire v8，零头按千分位整数结转）与跨格移动按地形判定；
  - 开地形的普通场景按游戏尺度：视野 32m、单进程 2048m 地图、同步 128 个对象；
  - 分区场景：整份落在一个格里的笔刷 / 建筑转发给写它的格，**跨两个地图进程的笔刷与建筑占地直接拒绝**（`terrain_cross_cell` 100070、`building_cross_cell` 100069）；
  - 确认来源：地形视野里每块都下发 TerrainChunk 对象，没改过的块是 Version 0 就绪标记；
  - C# 客户端岸线（L − 0.5 等高线）与重建调度（算法层）。
- **entitysync 冻结**：on_change 冻结内容不再因“已有冻结 / 交付在途”升成全量。

## 升级步骤

1. core 与生成器同时升级到 v1.43.0（新生成物实际要求 core 至少 v1.43.0；生成器缺省就取最新版。生成器清单里的最低版本在本版 tag 推上去后的下一笔提交才抬到 v1.43.0，见 CHANGELOG），重新生成工程；服务端、Go / C# / C++ 客户端、机器人与 loadtest 一起换（线格式不兼容）。
2. **先停旧进程再起新进程**；清空 `buildings`、`terrain_chunks` 与地形编辑账本集合（未上线，不迁移，旧 schema 记录会被拒）。
3. 客户端：
   - 按（命名空间, 视图键, 编码, schema）注册解码器的（C# `EntityViews.RegisterDao`、C++ `register_dao`），为 player / monster / building 各注册 `near` 与 `team`；
   - 把 Version 0 的 TerrainChunk 当“没改过、可确认”，接 `TerrainChunkSync`；
   - 处理新码 `terrain_pending`（100068，同一序号重发）、`terrain_cross_cell`（100070，把笔刷挪进一个格里）、`building_cross_cell`（100069）；
   - 建筑按新协议发 `ConfigID` / `Params`。
4. 逐条的升级要求见 CHANGELOG 各条的“升级要求”。

## 验证与性能边界

发版前在 main 上跑过：

- 全仓 build / vet / test，framework/sync、framework/entity、gameplay/cellworld、生成 game-demo 的 `-race`；
- 生成 game-demo 全测（36 个包）、`codegen/...`、Sync 双模式脚本、C# 两组测试；
- 私有真实依赖（Mongo / Redis / NATS）上的 demo 集成用例 10 项、开地形的分区多进程演练 6 步、普通无缝演练 14 步加机器人压测。

本机性能验收（macOS 单机，swap 偏高，延迟只看量级；[证据](../maintenance/evidence/perf-terrain-acceptance-20261110/README.md)）：

| 项 | 估算 | 实测 |
| --- | --- | --- |
| 一步移动 | 30B | 30B |
| 一名玩家进入视野 | 85B | 85B |
| 128 名玩家进入视野合计 | 9787B | 9787B |
| 128 个对象全在动，每观察者 | 18.6KB/s | 18.6KB/s |

同步业务负载（`scripts/perf/sync-business.sh`，200 tick @ 20Hz，单样本）：64 人全脏 tick_work p99 13.1ms，128 人全脏 13.3ms，128 人 10% 脏 12.4ms，三档都没有错过 tick。64 人进视野比估算多 10B 已确认是多分了一帧的帧头，内容相同。

普通无缝演练最后一步的机器人阈值按 5 进程拓扑放宽为 p95 40s（saga 步骤被非属主进程拒收重投，约多出 22s；不是性能退化，产品侧加速未做）。

**未覆盖**（验收后置）：Unity / IL2CPP / 真机、跨机、单格数千玩家（T09）、长稳、真实 Mongo 的 WAL 崩溃演练、C++ protobuf 客户端测试（本机无 protoc）。建筑状态 / 归属 / 换版挖填检查等细节按维护者决定暂缓。发布不等于部署。
