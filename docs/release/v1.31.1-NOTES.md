## 1. 建议升级的原因与各项变化

### <a id="f1"></a>F1 JetStream 日志 `DurableAckFloors` 不再信消费者副本报的待投递数（正确性修复，本版的主要原因）

**影响谁**：所有使用 Saga JetStream 协调器的部署（v1.31.0 起的唯一 saga 实现），开了冷副本（`saga.cold_copy.enabled`）的影响更大。

**原来的问题**：saga 分区清理按每个持久消费者的 ack floor 删日志。ConsumerInfo 由消费者 leader 回答，它可能在流的任一副本上，`NumPending` 按那台本机的流副本计数。副本追赶时它对流 leader 已有的命令报“没有待投递”，旧实现据此把 floor 抬到流末，清理可能删掉一条还没被步骤消费者看到的命令（只能等协调器超时重发）；**冷副本 durable 丢的是还没投影的终态，冷副本会永远缺这一条**。另外，4s 内没回答的消费者只出现在服务端列表的 `missing` 里，nats.go v1.53.1 的列表不看它、翻页错位：这个 durable 可能根本不在 floor 里（不守卫），或一直翻页到超时；R1 冷副本所在节点离线时它以零状态出现、被当成已经追上。私有三节点 SIGSTOP 实测复现了这两种情况。

**现在**：先读流末，再自己翻 `$JS.API.CONSUMER.LIST`（带 `missing`），每个 durable 用消费者 Raft 状态里的 `AckFloor.Stream = a` 向流 leader 要“过滤匹配、序号大于 a 的第一条”（`MSG.GET next_by_subj`）：有（序号 n）则 floor = max(a, n−1)，没有则 floor = max(a, 流末)。没回答的消费者 floor 记 0，这一轮不清理。空闲的过滤 durable 照旧不挡清理。

**行为变化（升级必读）**：承载 R1 冷副本 durable 的节点停机或长时间不回答时，这条流的分区清理会停住，超过 `saga.purge_stall_alarm` 后由 `saga.log.purge_blocked_seconds{consumer="…-cold-copy"}` 点名告警，流继续增长（原来会按流末清理、丢掉还没投影的终态）。维护者选 A：框架不自动删除；确认节点短期回不来时，运维删除这个 durable（`nats consumer rm <stream> <stream>_G<g>-cold-copy`），投影器 5s 内在活着的节点上重建，从流里还在的事件重投。处置写在 [SAGA.md](../framework/SAGA.md)“冷副本”的运维条。步骤 durable 跟随流 R3，只在选主的几秒内不回答，不受影响。接口与配置不变。

**代价**：每次清理对每个 durable 的每个过滤多一次流 leader 的 `MSG.GET`（带消息正文，受 `max_payload_bytes` 约束），开销**没有测量**。

### <a id="p1"></a>P1 物理房间 Go 分配削减，第一轮（约 −61%）

macOS ARM64 同机交替 3 轮：机关 8 房间 81.57 → 31.15 MB/s、520k → 191k allocs/s；普通 8 房间 70.04 → 27.38 MB/s、451k → 173k allocs/s。复制载荷逐帧字节不变（新增金样 `TestPlanFramesStayByteIdentical`、`TestRoomReplicationPipelineStaysByteIdentical`）。做法：抓取校验改查已提交帧的共享索引，删除每帧状态副本；`chunksync.Cursor` 组帧一次精确分配；`Commit` 换下的基线 map 与临时变化表留给下一次 plan；成员视野 / 视图账本 ACK 后双缓冲；房间级 Poll 临时对象表复用；`physx.World.Step` 交换缓冲复用；量化快照载荷共用一块数组；输入命令一次预留。

**新增 API（附加，原接口语义不变）**：`SpatialFrame.VisibleInto`、`ReplicationFrame.PlanInto`、`AppendMotionCommands`。**注意**：`chunksync.Cursor` 不能按值复制后分别使用（以前也不应这样用，现在会共用被复用的 map）。多房间负载测试输出新增 `MallocsPerSecond` / `AllocKBPerFrame` / `AllocsPerFrame`。详见 [PHYSICS-ROOM-SERVICE §Go 分配 profile 与削减](../framework/PHYSICS-ROOM-SERVICE.md#go-分配-profile-与削减2026-10-29macos-arm64)。

### <a id="p2"></a>P2 物理房间第二轮削减、`Commit` 契约与 macOS ARM64 长稳

- **第二轮**：`ReplicationFrame` 每帧状态索引由 map 改为按 ID 有序切片，新增 `ReplicationScene.AdoptFrame`（输入已有序时只读引用、不复制，从不修改调用方切片），房间提交路径用它；`SpatialFrame` 的位置 / Block 两张 map 改为切片，可见对象输出次序不变（`TestSpatialVisibilityKeepsBlockOrder` 锁住）。同机交替 3 轮：机关 8 房间 30.90 → **23.46 MB/s**，普通 27.29 → 19.87 MB/s，两份字节金样不变。
- **契约补写（升级必读）**：`service/physicsroom.Commit` 返回后**不得再修改 `Frame.States`**（房间把这块切片直接用作本帧共享的只读视图索引），需要保留的实现自行复制。框架自带的 `EntityHost` 经 `StateDAO.Accept` 本来就复制，不受影响；只有自己实现 `Commit` 且返回后改写切片的业务需要改。
- **长稳**：新增显式启用的 `TestPhysicsRoomSoak`（`ROOST_PHYSICS_SOAK_MINUTES`，缺省跳过）。机关 8 房间 × 20 客户端连续 20 分钟：footprint、Go 映射、goroutine、PhysX 原生堆（malloc 已分配约 **9.6 MiB / 8 房间**，个数持平）稳定窗口斜率都在 0 附近，**没有发现无界增长**；物理 / 交付频率稳定。详见 [PHYSICS-ROOM-SERVICE §长稳、RSS 与原生内存](../framework/PHYSICS-ROOM-SERVICE.md#长稳rss-与原生内存2026-10-29macos-arm64)。
- **没做的一项**：`StateDAO.Accept` 的状态副本（约 3MB/s）。去掉它要让 Nest undo 保护的权威状态与网络侧索引共用切片，一处违约就会静默改坏权威状态，判断为高风险，不做。

### <a id="k1"></a>K1 effect 暂存顺序选项 B 关闭（只改文档）

维护者 2026-10-29“按推荐”。B（按实体有序）的收益来源是“原生步骤记录全部带 effect、彼此串行”；saga 切到 JetStream 协调器后，原生步骤的结论由步骤消费者直接发到分区，记录里不再带 effect，B 不再推进，保持 A 的 WAL 顺序。见 [投影器并行 §9](https://github.com/tjbdwanghaibo/roost-core/blob/132ed79f689df01dc8df0ea3a44e9a768ee126d9/docs/maintenance/FEATURE-2026-10-27-projector-entity-parallel.md#9-维护者决定2026-10-28)。

**更正（维护者 2026-11-05）**：这一决定已被取代。新的高频 effect 来源出现了——联盟服务的入会 / 退出记录都带“成员变化”effect，全局顺序让一个 alliance 进程的全部成员变化排成一条投影通道（[alliance-join-20261105](../performance/benchmarks/alliance-join-20261105/README.md)）。维护者改为**缺省按实体有序**（B）：带 effect 的记录只靠实体 / 回执 / effect ID / 事务键串行；全局 WAL 顺序保留为缺省关闭的可选项 `dataengine.projection.effect_order: wal`（打开后与这里描述的 A 逐字相同）。仓内 effect 消费者与 outbox 路径的逐个核对见 [impl/03 effect 顺序范围](../framework/impl/03-dataengine.md#effect-顺序范围)。

1. `go get github.com/tjbdwanghaibo/roost-core@v1.31.1`。**无数据迁移**，配置、wire / 存储格式与协议版本都不变，不要求“先停旧再起新”；替换完成之前，仍在跑 v1.31.0 的协调器照旧用旧判定清理它负责的分区，所以要尽快替换全部 saga 协调器进程。新旧进程混跑没有专门测试。

## 3. 已知边界与没有验证的项（全文见 [KNOWN-LIMITS](../maintenance/KNOWN-LIMITS.md)）

- **F1 依赖“回答的是当前流 leader”**：网络分区里被罢免、还没察觉的旧流 leader 可能短暂按旧状态回答（nats-server 的读没有 read-index / 租约），floor 可能越过它没见到的命令。不在威胁模型内（崩溃重启的短暂重叠），**没有防护**。
- **F1 的 `MSG.GET` 开销没有测量**：每次清理每个 durable 的每个过滤一次，带消息正文。
- **F1 只在 macOS 私有三节点上验证**（单测 + 真实三节点 SIGSTOP 用例）；Linux、跨机没有跑。
- **物理房间 Linux 没有测**：Linux 的分配复测、RSS 与长稳都没做（本机 Docker 未运行）；也没测小时级、房间反复创建销毁、真实 Gate / NATS / TCP 链路下的内存。长稳中交付频率后 8 分钟比前 8 分钟低 0.9%，原因**尚未确认**；RSS 每分钟 +0.035MB 推断为干净页换入，未逐区域核对。
- **Saga 云 Mongo 只有三档单样本**（c128、c128@strict64、c64）；c128 追平 40～46s 超过 30s 门槛；原型余额 false **尚未确认**。正式实现的 Linux、跨机压测没有跑。
- 本版没有重跑重档性能与故障矩阵；故障矩阵的证据来自 `5c85223c`（Remote 链路与本版逐字相同），见[验收篇](v1.31.1-VALIDATION.md)。
