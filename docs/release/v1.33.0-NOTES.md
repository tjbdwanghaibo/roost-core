# v1.33.0：配置多文件叠加、连接凭据从环境变量读、新建实体本身落库与缺失 DAO 补空（功能版本）

日期 2026-10-30。范围：v1.32.0 之后的 main（`eb7ac19c` R5、`9d2728cd` 发版流程、`540f87b8` R15、`6d3038ae` R11）。变更原文以 [CHANGELOG `[v1.33.0]`](../../CHANGELOG.md) 为准；本版起按[发布文档分级](README.md)只写这一篇。

起因仍是下游 ai-game-blackbox-server 从 cube 迁到 roost-core：它的部署配置依赖多文件叠加与 `*_env` 凭据，端到端冒烟又发现了多 DAO 实体新建后重启加载不出来的框架缺陷；维护者据此定下“新建实体本身就落库”“缺文档的 DAO 补空”两条规则。

## 0. 维护者决定一览（2026-10-30）

| 决定 | 条目 |
| --- | --- |
| 配置叠加由 roost App 原生支持（R5 方案 A），下游配置结构与部署不改 | [N1](#n1) |
| 连接地址与凭据的 `*_env` 进 roost（R11），不让业务写转换胶水；`x` 与 `x_env` 同时写时变量优先（对齐 cube，下游 EKS 配置依赖这种写法） | [N2](#n2) |
| 新建实体写齐全部 DAO 在框架里修（R15），不靠业务记得 MarkPersist；**新建实体本身就落库**（没改持久字段也写）；**冷加载时缺文档的 DAO 按初值补上**（上线后给已有 kind 新增 DAO 是常态），不再判损坏 | [F1](#f1) |
| 发版改为一条命令、当前版本单一来源、发版文档分级 | [P1](#p1) |

## 1. 升级

1. `go get github.com/tjbdwanghaibo/roost-core@v1.33.0`。生成物要求的最低 core 不变（仍是 v1.32.0）：本版没有被生成代码调用的新 API，重新生成不是必须的。
2. **所有用 DataEngine 且实体有多个持久 DAO 的工程都应升级**（[F1](#f1)）。v1.33.0 之前新建、库里只有半个聚合（部分 DAO 没有文档）的存量实体，升级后**由框架自动补空**：冷加载时缺的 DAO 按初值补上，这个实体的下一笔持久提交把它写出；不再需要迁移工具补齐缺失的 DAO 文档。每次补空打 WARN 并计 `dataengine.aggregate.dao_filled.total{kind,collection}`，升级后存量实体第一次加载各一次是正常的。行为变化，升级前核对：①Nest 之外的 `Create` / `GetOrCreate`（生成的登录建号、服务 Init 的 `EnsureWorld`）现在为持久实体补一笔 strict 事务、提交后才返回，多一次 WAL 等待，业务 worker 上调用直接报 `fctx.ErrBlockingInBusinessWorker`；之后的修改是第二笔提交（DAO 版本比以前多 1，断言 `_version` 的测试要调整）。②memory 快路径 handler（rollback=none、durability=memory）里新建持久实体现在返回 `nest.ErrMemoryTransactionPersistentWrite` 并撤销新建，改声明持久策略。③DataEngine 启动后，在没有事务的 Guard 作用域上直接 `CreateInScope` 持久 kind 返回 `entity.ErrPersistentCreateOutsideTransaction`，改用 `Create`。
3. 配置里用了 `*_env` 的部署：确认对应环境变量在进程环境里有值，否则 Init 拒绝启动（[N2](#n2)）。之前这些键被静默忽略，进程会用配置里的缺省地址启动。
4. 入口配置写了 `config.includes` 的部署：之前 roost 静默忽略它，现在会真正叠加；`config.includes` 的值必须是路径列表（[N1](#n1)）。

## 2. 新增

### <a id="n1"></a>N1 App 配置多文件叠加 `config.includes`（R5）

入口配置写 `config: {includes: [a.yaml, b.yaml]}` 时，App 启动、`--check-config`、doctor、`roost config check` 与 `LoadDatabaseMapFile` 读到的都是同一份叠加结果，规则只在 `internal/configfile` 实现一次。语义与 cube 对齐：路径相对入口文件所在目录；按列出顺序叠加，入口自己的键最后叠加；map 深合并，标量与列表整体替换；只支持一层（不会有循环）；include 缺失或格式错误时点名文件与入口。与 cube 的两处差异：`config.includes` 不留在最终配置里；单个字符串不按空白拆开而是拒绝。新增 `app.LoadConfigFile(path)` 给部署工具用。下游 31 个配置文件与其 `configlayer.LoadFile` 逐叶子键对照一致。规则表见[设计篇 07 §1.1](../framework/guide/07-config.md)。

依赖边界：`internal/configfile` 是生成器与运行时共用的第三个例外（与 `configschema`、`configdata/rules` 并列），只依赖标准库加 viper / yaml.v3，根包门禁检查它不 import 本模块任何包。

### <a id="n2"></a>N2 连接地址与凭据从环境变量读（R11）

| Mod | `_env` 键 | 新增的普通键 |
| --- | --- | --- |
| mongo | `uri_env`、`username_env`、`password_env` | `username`、`password`、`auth_source` |
| redis | `addr_env`、`username_env`、`password_env` | `username` |
| etcd | `endpoints_env`（逗号分隔）、`username_env`、`password_env` | — |
| nats | `url_env`、`username_env`、`password_env` | `username`、`password` |

规则只在 `wiring/mods` 的 `EnvValues` 实现一次：`_env` 写了变量名且变量有值时取代配置值；变量未设置或为空时 Init 拒绝，同一 Mod 的缺失一次报全，错误点名键与变量名、不带任何值；`--check-config` / doctor 只校验变量名形状，不要求变量已设置。账号规则：用户名与口令成对（redis 写了用户名就要口令）；mongo / nats 单独写了用户名时 URI 不能再带 userinfo。顺带修了 NATS 连接失败错误与连接日志原样带出含口令 URL 的泄漏。真实鉴权实例（mongod `--auth`、redis ACL、nats user/pass、etcd auth）入口脚本 `wiring/scripts/integration/auth-credentials.sh`。详见[设计篇 13 §2.1](../framework/guide/13-wiring.md)。

未覆盖：`redis.cluster_addrs` 没有 `_env`；NATS token / nkey / creds 文件；etcd TLS；`cmd/mongocheck` 只读一个连接串变量（账号要拼进连接串）。

## 3. 修复

### <a id="f1"></a>F1 新建实体本身就落库并写齐每个 DAO；冷加载把缺的 DAO 补空（R15）

**现象**：DataEngine 只为事务里登记过变化的 DAO 写文档；新建实体时没被写过的 DAO 没有文档，重启后冷加载报 `entity aggregate is incomplete or corrupt: live=… missing=…`，实体再也加载不出来。下游端到端冒烟中新玩家重启一次即复现。影响 v1.12.2～v1.32.0 的多 DAO 实体。另外，新建后没有任何持久修改的实体根本不落库，重启后像从未创建过。

**维护者 2026-10-30 的两条决定**：

1. **缺文档的 DAO 补空**：“服务器上线后逻辑会不断增加，可能会新增 DAO”——冷加载时至少一个 DAO 有活文档、其余缺失（没有墓碑），缺的 DAO 按初值补上，不再判损坏。
2. **新建实体本身就要落库**：“没有改持久化字段也需要落地”——创建它的持久事务提交时为它写齐每个 DAO，与本事务改没改字段无关。

**修法**：Nest 只有一条规则——事务第一次登记某个实体的 DAO 时，把它版本 0（还没有持久文档）的 DAO 一并以整文档登记。`BuildEntity` 在新建与冷加载时都把实体的全部 DAO 绑成一个聚合交给各 DAO 的 tracker。版本 0 的 DAO 有两种来源：新建实体的每个 DAO（Nest 捕获新实体时登记，没改字段也写）；冷加载时补上的 DAO（读路径不写库，随这个实体的下一笔持久提交写出）。全部 DAO 都有文档后这条检查只剩一次原子读。

- 由谁提交：Nest handler 内（含 handler 里的 detached / isolated 事务）由该事务捕获，回滚则不落库、撤销发布；Nest 之外的 `Create` / `GetOrCreate` 由 DataEngine 启动时注册的新建准入门补一笔 strict 事务，提交被接受后才返回；memory 快路径 handler 新建持久实体被拒绝（没有提交点）；有 RollbackTx 的 memory 事务照现有规则在提交点整条拒绝。
- 冷加载分类：全部缺失是从未创建；没有活文档、只有墓碑是删过档（删档之后才加的 DAO 没有墓碑，**不会让删过档的实体复活**）；活文档与墓碑混在一起仍是损坏；Remote 托管实体部分缺失时还查 Remote 元数据墓碑，删过档的不补。
- 可观测性：每次补空一条 WARN（kind、实体 ID、集合名，不带业务数据）与计数 `dataengine.aggregate.dao_filled.total{kind,collection}`。新增 DAO 之后每个存量实体第一次加载各一次是正常的；别的时候非零说明丢写、误删或投影缺口，要人核对——补空放宽的正是原先“只缺一部分就拒绝”这道信号，所以改由告警承担。

- Remote：整文档登记的掩码最高位为 1，Remote 事务记录（`_remote_entity_transactions`）改为按位另存掩码（`mutation_masks`）；修前每个新建 Remote 实体的第一笔写在投影时报 `overflows int64` 并卡住投影（main 上的 R15 首版即如此，未发版）。

**升级影响**：半个聚合的存量实体现在会被自动补空，不再需要迁移工具补齐缺失的 DAO 文档（下游从 cube 迁移的工具可以去掉这一步）。Nest 之外的新建多一次 WAL 等待、不能在业务 worker 上调；memory 快路径不能新建持久实体；详见[升级第 2 条](#1-升级)。

**边界**：handler 之外的 `RunDetachedTransaction` 里新建，新建那笔事务独立提交，外层随后回滚不撤销新实体；Remote 托管 kind 在 Nest 之外新建不经准入门（Remote 持久写只能走消息声明的批次），照旧在第一笔 Remote 批次提交时写齐；没有 DataEngine 的进程事务外新建只在内存。实现与取舍见 [impl 03 §2 第 12 条](../framework/impl/03-dataengine.md#2-必须保持的契约)，限制见 [KNOWN-LIMITS](../maintenance/KNOWN-LIMITS.md)。

## 4. 流程

### <a id="p1"></a>P1 发版改为一条命令

`scripts/release.sh vX.Y.Z [--min-core] [--dry-run]`：前置检查 → 改 `release:`、归档 CHANGELOG、功能版追加 upgrade-compat 矩阵 → 提交 → pretag → 推 main 并核对 → tag 并核对 → 用 tag 生成 game-demo build / vet。文档里不再写死当前版本；补丁版只靠 CHANGELOG，功能版一篇 NOTES。本版是这条命令的第一次真实发版。见[维护手册 §5](../maintenance/README.md) 与[发布文档](README.md)。
