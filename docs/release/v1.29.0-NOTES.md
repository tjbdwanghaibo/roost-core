# v1.29.0：web 运维可配置与错误码响应、配置跨服务检查与端口块、卡牌 RPG 接入

发布状态：**发布准备完成，待维护者推送 tag**——发布准备在分支 `release/v1.29.0` 完成（基线 main `89ac2eda`，之后只有版本号 / 最低 core 与发布文档两类提交），tag 由维护者推送后回填。日期 2026-10-19，维护者 2026-10-19 批准本次发版。范围：`v1.28.0`（`1c2bce7f`）之后到本版 release 提交。验收见[验收篇](v1.29.0-VALIDATION.md)，实现与文件索引见[实现篇](v1.29.0-IMPLEMENTATION.md)（同一套条目编号）。变更原文以 [CHANGELOG `[v1.29.0]`](../../CHANGELOG.md) 为准，本篇只做归类与升级指引。

本版是**次版本，含行为变化**，改动集中在生成器（`codegen`）与业务 HTTP 接入层（`wiring/web`、`infra/network/webroute`、`infra/network/httpserver`）；Nest 调度、DataEngine、Sync 三块的运行时逻辑本版**没有改动**（`framework/`、各 wiring Mod 只在配置声明上加了 `shared` / `follows` / `unique` / `listen` 等 struct tag，供生成器的跨服务检查读取）。线上尚未部署（维护者 2026-10-06 起的规则）：不做旧工程兼容，旧工程按 §1 处理。**生成物要求的最低 core 由 v1.28.0 升到 v1.29.0**：当前生成器写出的 `roost.yaml` 带 `services.<name>.port_block`（[B1](#b1)），生成的 Makefile 按钉住的 core 运行 `go run .../codegen/cmd/roost@<版本>`；钉 v1.28.0 时 `make id-check` 报 `field port_block not found in type roost.ServiceSpec`（minimal 与 game-demo 两种工程都复现，见[验收篇](v1.29.0-VALIDATION.md) V1），`make sync` / `generate` / `doctor` 同样失败。生成的 Go 代码本身仍能对 v1.28.0 编译（同一次复现里 `go build ./...` 通过），升最低版本是为了生成器版本与 `roost.yaml` 格式一致。

## 1. 升级清单（按操作顺序）

1. **钉 core v1.29.0，补端口块号**：`roost project sync`（或 `roost project upgrade`）给 `roost.yaml` 里每个服务分配 `port_block` 并写回（[B1](#b1)）。不跑这一步时其余命令加载 `roost.yaml` 即报错，并给出下一个空闲块号。
2. **核对开发配置的端口**：`roost config check --all`（或 `roost project doctor` 的 `config-across-services`）。
   - 退出码 4、点名 `etcd.advertise_addr`：多个服务共用同一地址（例如旧工程都写 `127.0.0.1:9000`），按提示改成 `127.0.0.1:<9000 + 块号>`（[B2](#b2)）。
   - WARN（`cross_service.warnings`，不影响退出码）：开发配置的 `ops.addr` / `etcd.advertise_addr` 端口与块号派生值不一致——多见于曾经 `add service` 让端口错位的旧工程，改配置或改块号二选一。
   - `deploy/dev/second-game.sh` 派生的第二个 game 改用 ops `9200+N`、advertise `8900+N`（game-demo 由 9110 / 9010 变为 9200 / 8900），按端口写死的本地脚本核对。
3. **改判断**（编译器不会指出）：
   - `roost config check` 的退出码改为区分结论（[B3](#b3)），按“非 0 即失败”判断的脚本不受影响；按 1 判断，或依赖“工程编译不过时以 0 结束”的脚本要改。
   - 业务 HTTP 路由的默认错误响应改为 `{"ok":false,"code":…,"reason":…}`，没有错误码的错误回 500 且不带原文（[B4](#b4)）；读 `error` 字段的客户端改读 `code` / `reason`。
4. **重新生成**：`roost generate`。以前被静默跳过的“标了 `//roost:nest` 却找不到锁目标”的函数现在让 generate 失败（[B5](#b5)），按报错补 `target=<实体>` / `targets=<a>,<b>` 或改参数类型名。
5. 已装 web Mod 的工程可在配置里写新的 `web.*` 五个键（不写取缺省，[F1](#f1)）；`web.read_header_timeout` 不得大于 `web.read_timeout`。
6. 执行 build / vet / test、`roost project doctor`、`roost config check --all` 后启动新版本。

## 2. 行为变化

### <a id="b1"></a>B1 `roost.yaml` 新增必填的 `services.<name>.port_block`，按服务端口只从块号派生

**原因**：修前按服务区分的开发端口按服务名排序现算，`add service field` 让新服务排到最前、拿走 game 的 9100，run.sh 里 game / gate 后移到 9101 / 9102，与它们配置里的端口不一致。维护者 2026-10-19 决定改为记录块号。

**变化**：块号 0～99、各服务不同、一经分配不再改变。新建工程按“业务服务在前、托管框架服务在后、各自按名字排序”分配 0、1、2……（game-demo 的端口逐字节不变）；之后新增的服务取当前最大块号 + 1，删除不回收。全部按服务端口只从块号派生：ops `9100+N`、`etcd.advertise_addr` `9000+N`、`second-game.sh` 的 ops `9200+N` 与 advertise `8900+N`（修前是“第一个 + 10”，第 11 个服务起会撞端口）。`config check --all` 与 doctor 在开发配置端口与派生值不一致时给 WARN。

**升级**：不做旧工程兼容、不从已有配置推断块号（项目未上线）。没有 `port_block` 的 `roost.yaml` 加载即报错，`roost project sync` / `project upgrade` 自动分配（本地复现的 upgrade-compat lane 中 v1.25.0 / v1.27.0 / v1.28.0 工程升级后均写入 `port_block: 0`，见验收篇 V9）。

### <a id="b2"></a>B2 各服务的 `etcd.advertise_addr` 互不相同

**原因**：修前生成器给每个带 etcd 的服务都写 `127.0.0.1:9000`，同机起多个服务时服务注册的地址相同。维护者 2026-10-19 决定各服务不同。

**变化**：开发配置写 `127.0.0.1:9000+N`（N 为 [B1](#b1) 的块号；game-demo 的 game / activity / match 为 9000 / 9002 / 9006）；生产示例保持 `CHANGE_ME:9000`。配置声明新增 `unique` 规则（`configschema.Key.Unique`，tag `unique:"<组名>"`），当前标在 `etcd.advertise_addr` 上：开发配置集里各服务取值必须两两不同，违反时 `config check --all` 退出码 4、doctor `config-across-services` 失败。

**升级**：已有工程的配置不改写；多服务共用一个地址的旧工程按 §1 第 2 步改端口。

### <a id="b3"></a>B3 `roost config check` 的退出码与输出

**变化**：退出码 **0** 全部通过、**1** 命令没跑成（参数、`roost.yaml`）、**2** 键错误、**3** 跨 Mod 规则错误、**4** 跨服务不一致、**5** 检查没跑全（工程编译不过、跨 Mod 没查，或文件名认不出服务），同时出现取最小非零码。修前工程编译不过时以 0 结束（只打印 “NOT checked”），现在是 5；修前任何失败都是 1。键错误的输出改为 `config invalid: <file>` 加逐条列表；结论行 `config is valid` / `config ok` / `config keys are valid (cross-mod rules not checked)` 保留。新增的 `--keys-only` / `--json` 见 [F2](#f2)。

### <a id="b4"></a>B4 wiring/web：默认错误响应接 errcode，Engine 在 `Mod.Init` 建

**原因**：修前任何错误都回 400 `{"ok":false,"error":"<err.Error()>"}`，内部错误原文直接交给客户端（维护者 2026-10-19 批准的 web P1 四项之一）。

**变化**：`webroute.DefaultErrorMapper` 改用 `errcode.ClientError`——带码的错误回 **400** `{"ok":false,"code":<码>,"reason":"<message>"}`（被包装的原因不进响应体）；没有码 / `CodeInternal` 的错误回 **500** `{"ok":false,"code":1,"reason":"server error"}`，原文只进服务端 Error 日志 `webroute: route failed with a server error`（带 `request_id`）。传输层错误（JSON 解码 400、请求体超限 413、panic 500）的响应体不变；业务仍可用 `WriteResultWithMapper` 覆盖；生成的路由代码不变。web Engine 改为在 `Mod.Init` 按配置建，Init 之前调用 `Register` 报错（生成工程在服务 Init 里注册路由，不受影响）。

### <a id="b5"></a>B5 Nest 生成器：`//roost:nest` 找不到锁目标时报错

**原因**：标了 `//roost:nest` 的函数既没写 `target` / `targets`、参数类型名也不含 `Entity` 时，修前 `roost generate` 静默跳过、退出 0，还把此前生成的 Sender 当孤儿删除，业务只在编译时看到 `undefined: Register…NestHandlers`（卡牌 RPG 接入时遇到）。维护者确认改为报错合理。

**变化**：generate 失败并报 `nest: handler <名>: //roost:nest found no entity parameter: …`，给出两种写法。

## 4. 性能

本版没有改动 Nest / DataEngine / Sync 运行时逻辑，**没有**重跑重档压测；web Mod 新增的路由指标中间件只作用于业务 HTTP 路由（每请求一次计数与直方图观测）。KNOWN-LIMITS 里的重档数字仍来自 v1.26.0 / v1.27.0 发布后的复测。

## 5. 测试修复、不在本版与已知限制

- <a id="t1"></a>测试修复（不改产品行为，无 CHANGELOG 条目）：故障矩阵 `mongo-wal-recovery` 格（`TestRealDataEngineRemotePublicationAndWALRecovery`）的偶发失败已查明是测试时序——WAL 投影只保证 Remote 提交持久（Applied），快照发布由 outbox 补发协程异步完成，用例在投影返回后不等发布就停机与查 outbox。用例拆成“发布完成后停机”与“停机打断在途发布”两个子测试，测试包装不再把调用方上下文已取消的 `context.Canceled` 记成失败（`988b9e14`；KNOWN-LIMITS“v1.28.0 发版时发现的两处问题”第 2 项改为已修复）。本次矩阵结果见验收篇 V4。
- 业务 HTTP 路由与配置检查的边界（跨服务检查只比较开发配置集与生产示例里能确定的值、端口块 WARN 不影响退出码等）见 [KNOWN-LIMITS](../maintenance/KNOWN-LIMITS.md#业务-http-路由与配置检查的范围2026-10-19维护者批准的-web-p1-四项)；卡牌 RPG 夹具的范围（教学夹具，不承诺生产容量、完整 Skill Host、客户端协议与跨服玩法）见 KNOWN-LIMITS“卡牌 RPG 接入验收的范围”。
