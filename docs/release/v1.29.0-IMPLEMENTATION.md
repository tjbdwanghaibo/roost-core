## <a id="t1"></a>T1 `mongo-wal-recovery` 偶发失败的测试修复

| 项 | 内容 |
| --- | --- |
| 提交 | `988b9e14`（只改测试与 KNOWN-LIMITS，产品行为不变，无 CHANGELOG 条目） |
| 根因 | WAL 投影只保证 Remote 提交随 Mongo 事务持久（outbox `State:2` 即 Applied），快照发布由 Manager 的 outbox 补发协程异步完成（`ApplyRemoteCommits` 记 Applied 并唤醒补发后就返回，契约“nil 不代表已经发布”）。用例第二段在投影返回后不等发布就 `StopFinalizer`：在途 L2 `Eval` 被取消时测试包装记成失败（`context canceled`）；发布被截断后，新 Manager 重放只唤醒补发、不等发布，紧接着查 outbox 读到 Applied |
| 位置 | `wiring/dataengine/remote_integration_test.go`（`runRemotePublicationAndWALRecovery` 拆成 `published` / `stop-interrupts-publication` 两个子测试；一次性 Eval 钩子把停机钉在发布在途；重放后 `FlushRemoteTransaction` 等结论再查 outbox） |
| 证据（来自该提交说明） | 修前顺序 3/3 红；修前测试单格 50 次失败 2 次，修后 55 次 0 次，21 格矩阵 21/21。本次发布准备在 rebase 后的提交上另跑一次完整矩阵，见验收篇 V4 |
| review 检查点 | 测试包装只放过“调用方自己的上下文已取消”的 `context.Canceled`，其余 Redis 错误（含超时）仍记失败；产品侧同版本同内容重写由 L2 CAS 接受，没有改 |
