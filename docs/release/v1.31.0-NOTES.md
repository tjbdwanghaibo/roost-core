## 3. 新能力与行为（按主题）

### 心跳与移动

#### <a id="h1"></a>H1 按实体的心跳 `gameplay/heartbeat` + `wiring/heartbeat`（D20 P1）

**为什么**：分析 D19 多视野“Nest 模式失守”时维护者指出压测里的移动由一个全局循环驱动、不像真实游戏；移动应在实体自己的心跳里做，心跳天然打散；以后跑在 Nest 快池上的业务周期逻辑都以心跳为底层。框架原来没有可直接用的按实体心跳（entitytimer 是持久期限，不是周期推进）。

**做了什么**：按实体的非持久周期 Nest 消息。10 个固定档位（50ms～60s），按档分环、10ms 一格、1 个驱动 goroutine、相位 = hash(实体 ID)；回调在实体自己的 worker、实体锁与事务内执行；每个登记至多一拍在途，在途或快池满就跳拍（计数 + 限频 Warn），不累积不补发、不追帧；`Elapsed` 上限 `max(1s, 档位)`；事务内启停提交后生效、回滚作废；卸载窗口用实例核对 + 令牌；卡住兜底 10s 起翻倍、80s 封顶；同一实体多个登记不合并。Remote 托管实体只在 `LocalOwned` 执行；共享模式下 `Register` / `Start` 返回 `ErrHeartbeatRemoteShared`，运行中进入共享的由下一拍停掉，回到独占不自动恢复。`Reg.Close` 撤销登记（换场景重建用），驱动发现实例已移除时撤销整个宿主。持久级别按登记选（缺省 async）。

**决定**：见 §0（10-21 ①～⑮、P1 后 ①～④）。

**边界**：Remote 托管实体每拍一次 Remote 写准入；`Strict` 级别每拍在实体 worker 上等落盘；装 Mod 多 3s 停机保底（KNOWN-LIMITS“实体心跳”）。

#### <a id="h2"></a>H2 Nest 批量心跳作业与投递缺省（D20 选项 C）

**为什么**：单目标 `Dispatch`（X）在 50 万拍/秒时约 3～4 核，大头是逐条消息的 Nest 固定开销与 worker 停放唤醒；ssr 式批量（Y）便宜但绕过目标实体的事务与 Sync 捕获，不能用；方案 D（批量入队、逐个执行）只省 10～12%，不合入。

**做了什么**：`NestMgr.DispatchTryBatch`：一个作业带一批单目标投递，每个目标在自己的 Guard 作用域与事务里执行，与普通作业交替取；同 ID 有在途的目标当场转单目标作业排在冲突消息之后（不跳拍）；只读已加载实体；Remote 托管目标不接受（仍单目标）；每个目标重新冻结业务时间（`fctx.Context.Refreeze`）。对全部 Nest 消息无条件生效的两项：两张按 goroutine 登记的表改分片表（`goroutine.LocalMap`）、worker 结束一项后同一次持锁取下一项。心跳 `heartbeat.delivery: batch | dispatch`，**缺省 `batch`**（10-22 决定 B），批 64、组 4（8 → 4）、时间片 100µs（200µs → 100µs，按下文补测）。

**代价（维护者接受）**：同时段进程 CPU 比单目标少约 42%～73%，同一快池上普通业务消息 p99 约 0.08 → 0.19ms。只实现 `nest.Client` 的客户端包装在缺省下 `Bind` 报错，要显式设 `DeliveryDispatch`。批内目标不逐条记 `nest.dispatch.*` 与慢派发 trace，按批记 `nest.dispatch.try_batch.*`。

**审查修复（RV-20261022-01，P1）**：Fence 的契约是“已经开始的 handler 收尾，还没开始的目标不执行业务、交回 `ErrNestFenced`”。修前批量作业只在准备一组时读一次 fence，一组执行期间同组前一个目标 fence 了引擎（handler 主动 `Fence`，或提交结果未知），同组后续 handler 照常执行、没有交回；心跳缺省走批量作业，这是缺省路径。现在“每个 handler 开始前必须检查的事项”（fence、取消）收在一个入口 `NestMgr.checkHandlerStart`，普通派发、广播的每个目标、批量作业的每个目标共用（审查建议 1）；广播有同样的问题，一并改。同组先取锁失败、收尾时才转单目标的目标，在 fence 之后也直接交回 `ErrNestFenced`。实体有效性（只读已加载、`Touch`、取锁拒绝已摘除实例、锁组核对）依赖取到的实体，仍由各路径逐目标做，契约写在同一处注释里。每个目标多一次原子读，微基准同机交替 10 轮无可见差异（实现篇 [H2](v1.31.0-IMPLEMENTATION.md#h2)）。**升级**：无 API、存储、协议变化。

**待补测（今晚）**：“时间片 100µs + 组 4”等组合的同时段对照，合并组更好再改缺省；Linux 未复测（[压测清单 §1](../performance/V1310-PRERELEASE-20261022.md#1-选项-c-参数补测)）。**2026-10-22 晚已补测**（[NEST-BATCH-HEARTBEAT §3G](../performance/NEST-BATCH-HEARTBEAT-20261021.md#3g-2026-10-22-晚参数补测结果v1310-发版前压测第-1-项)）：同时段 3 轮，组 4 / 100µs 的业务 p99 最低（0.104ms，现缺省组 4 / 200µs 0.149ms，单目标 X 0.095ms），进程 CPU 与缺省相同（1.52 对 1.48 核，X 3.00 核）；**维护者 2026-10-22 决定 A：缺省改为组 4 / 100µs，已实施**（`ee01221e`，实现篇 [H2](v1.31.0-IMPLEMENTATION.md#h2)）。Linux 仍未复测。

#### <a id="h3"></a>H3 移动与动作 `gameplay/movement` + `actionflow.BeatRunner`（D20 P2）

`MapBasic`（场景、位置、朝向，状态存业务 DAO，AOI 经 `Space` 接口：进场景 `Enter`、移动 `QueueMove` 走提交门、离开 `Leave`，进出在提交之后）与被动组件 `Move`（`MoveTo` / `Follow`、`Advance(token, elapsed)`、亚格累积、地形 0.5 格采样）。`MoveTo` / `Follow` 是动作，由实体的 `BeatRunner` 驱动：每个组的当前动作挂这个组的心跳 `"actionflow/<组>"`，周期取动作的 `TickInterval`，空闲停。**决定**：移动参考 ssr 由 action 驱动；所有控制实体行为的逻辑都走 action；runner 不随事务回滚，由业务把动作接口放在 handler 最后一步。位置 nopersist，落库由业务选（离开场景 / 周期）。

#### <a id="h4"></a>H4 技能与 Buff 的推进与驱动（D20 P5 + 驱动接口）

`gameplay/skill` 定义驱动接口 `Driver{Wake() error; Sleep()}`（电平式通知）与推进器 `Stepper`（忙时逐 tick 推进、推进到空闲点就停、输入跳到输入的 tick、追帧上限 `MaxCatchUp` 外一次跳过并计数、时刻倒退不动），`TickClock` 换算业务时间与 tick；`skill` 不依赖 Nest / heartbeat / timedomain / fctx（根包守卫）。`combatcomponent.DriveBuffs` 是与驱动无关的 buff 推进；心跳驱动是薄包装 `NewRuntimeBeat` / `AttachBeat`（只有这两个文件 import heartbeat）。`CloseBuffDriver` / `RuntimeBeat.Close` 撤销。同一输入序列（每个输入落在同一 tick）在任何心跳抖动下逐 tick 相同。**决定（10-21）**：心跳只是驱动方式之一、skill 只用接口；P5 四项按推荐（放 `combatcomponent`、Buff 固定粒度、超过追帧上限一次跳过、`TickBuffs` 保留导出）。

#### <a id="h5"></a>H5 Remote 共享模式切换：真实 Manager 验证与两处恢复修复

经真实 `remoteentity.Manager`（进程内权威替身与真实 Redis + Mongo + NATS 两套，`dispatch` / `batch` 两种投递）验证独占 → 共享 → 独占、共享模式下迁移、卸载重载：每登记停掉计数、共享期间零推进、不自动恢复、迁移无双推进。修两处：`BeatRunner.Sync()` 同时重新挂上任务心跳；`ai.Controller.SetStrategy(当前策略)` 只重新对齐 AI 心跳。**维护者 10-21 晚**：Remote 托管实体理论上不应挂移动与心跳组件，`MapBasic.Sync` 不加，“禁止挂载”另行设计（[DESIGN-TODO 待决定](../maintenance/DESIGN-TODO.md#待维护者决定不急)）。

### Sync 与 AOI

#### <a id="s1"></a>S1 观察者是玩家、视野按观察者配置（D14）

**为什么**：维护者 review `AOI.evaluatePair` 时指出 observer 名义上是实体 ID、实际上只有玩家；视野半径不该只有全局一个。观察者按玩家 ID 编号（= 会话 ID），自排除比玩家自身实体；`AOIConfig.LODs` / `MinViewRadius` / `MaxLeaveRadius` / `ViewRadiusStep`；`SetObserverView` 直接生效（层级必须已配置、视野夹取量化、限速、同值不重评）；只看不被看的 `Watch` / `MoveView` / `Unwatch`；删除 `InterestConfig.Session`（多对一互相退订的隐患随之消失）。game-demo 新增 `scene_view`。

#### <a id="s2"></a>S2 视野（View）模型（D19）

视野是 int64 逻辑 ID（0 保留给主视野），空间视野（视点 + 视野 + 可选跟随实体）与关系视野（显式实体集合 + 一个同步层级），玩家与视野多对多；任一挂接视野持有就保持订阅；同一目标被多个层级看见时包含关系取数据多的、否则取并集（`entity.UnionSyncProfiles`）；`MaxVisible` 按视野计；上限 `MaxViewsPerPlayer` / `MaxPlayersPerView` / `MaxPlayerBlocks`。三项实施后小决定（10-21，按推荐保留）：跨政策同一 pair 仍按优先级取一个视图、块预算新增 `MaxPlayerBlocks`、关系视野不排除挂接玩家自己的实体。

#### <a id="s3"></a>S3 多视野下 AOI 批次只评估移动过的目标

16 个额外空间视野时 Nest 模式改值→客户端 P99 350～376ms、帧数 38%（夜间补测）。根因一：每个目标移动让旧、新块上的全部观察者完整重评；改为只评估移动过的目标，结果与完整重评逐项相同。根因二（排队事实一次性挤进 Flush）由 [S4](#s4) 的应用模式解决。

#### <a id="s4"></a>S4 Interest 单写者与两种应用模式

**为什么**：近两周 Interest 连续出问题（Leave→Enter / Hide→Show 旧移动拖回新视野、16 视野 Nest 失守、ApplySync 每周期一批、直接 API 在业务 worker 上等 AOI 批次 15～46ms），根因是三个写入口（直接调用、视野登记表、排队事实）之间没有全序（方向判断见[单写者方案 §1](https://github.com/tjbdwanghaibo/roost-core/blob/132ed79f689df01dc8df0ea3a44e9a768ee126d9/docs/maintenance/REFACTOR-2026-10-21-interest-single-writer.md#1-为什么重构方向判断)）。

**做了什么**：全部写入口只在登记侧短锁内校验、改登记事实并追加一条有序日志，不做 AOI 计算；应用方按日志顺序执行，目标代际号作废被撤除 / 再放置越过的未确认事实。**两种应用模式**（维护者 10-21）：`ApplySync`（缺省，在 Flush 政策阶段执行，提交后下一次 Flush 可见，每玩家视野 ≤ 9，含关系视野）与 `ApplyAsync`（每个 Interest 一个应用线程，Flush 只结算，多约一个同步周期）。**ApplySync 预算**（10-22 决定 A）：一次政策阶段的执行 + 结算不超过同步周期的一半，按单位估计、预计超出就停、至少前进一个单位。**纯前缀切开**（10-22 决定 A）：一步只在日志的前缀边界停——就绪事实不被越过、命令不被越过、提交不切开，部分就绪的提交整笔等；`BatchSize` / 预算只决定停在哪个边界。实施后修了异步模式“已执行未结算的命令不计入 Drain”。新增 `InterestConfig.OnRefusal`；`Apply()` 只给测试 / 工具 / 离线驱动，不在快池上调。

**行为变化**：直接调用的效果在下一次结算可见；未确认的移动被同一目标之后的 `Hide` 越过时整条作废；`Hide` → `Show` 同一周期多一次全量；重负载下 ApplySync 的 AOI 变化晚一两个周期可见；一步可能比 `BatchSize` 多出交错进来的条目（上界是这一步取到的日志快照）。

**审查修复（RV-20261022-03）**：Drain 超时诊断（`drainStalls`）曾在释放登记侧锁之后再读事实计数，与只持登记侧锁的 `QueueMove` 并发写入竞争（`-race` 报告；只是诊断读，未发现影响 AOI 位置或订阅）。现在诊断在登记侧锁内取一次快照，之后只用快照；按审查建议 3，应用方一步拆成取日志、执行并记账、放回三段，结算与 Drain 跨锁都只传值。对外行为、锁序、切点与预算规则不变（[实现篇 S4](v1.31.0-IMPLEMENTATION.md#s4)、[单写者方案 §11.3 第 16 条](https://github.com/tjbdwanghaibo/roost-core/blob/132ed79f689df01dc8df0ea3a44e9a768ee126d9/docs/maintenance/REFACTOR-2026-10-21-interest-single-writer.md#113-执行器批次与结算这一层剩下的约束以及钉住它们的用例2026-10-22)）。

**待补测（今晚）**：ApplySync 预算计入结算的 16 / 0 / 8 视野前后对照（[压测清单 §2](../performance/V1310-PRERELEASE-20261022.md#2-interest-applysync-预算16--0--8-视野)）；纯前缀切开每步多一遍线性预扫描，开销没有测。**2026-10-22 晚已补测**（[INTEREST-SINGLE-WRITER §7.1](../performance/INTEREST-SINGLE-WRITER-20261022.md#71-结果2026-10-22-晚v1310-发版前压测第-2-项)）：16 视野诊断构建政策阶段每 tick P95 35～40 → 27～28ms、Flush 次数满额，延迟不变差；0 / 8 视野不退化（8 视野纯前缀切开前后 3 轮单变量对照无差异）。预扫描的单独开销仍没有微基准。

#### <a id="s5"></a>S5 同步会话因编码失败被丢时断开该玩家

**维护者 2026-10-22 原意**：编码失败就关闭连接，最简单高效。**10-17 对自身视图编码失败定的 B（不关连接、靠 `stranded_players` 告警）作废。** Manager 交给 `SessionLost` 的原因带分类（`entitysync.SessionLoss`：`push_refused` / `object_limit` / `too_large` / `encode_failed`）；不是推送拒收时 `wiring/selfsync.DisconnectLostPlayer` 断开该玩家全部连接（自身视图经 `EntitySyncSetup` 自动接上，game-demo 场景调用同一个函数），计 `player.sync.session_lost_disconnect.total{reason}`、打限频 Warn。会话 ID 就是玩家 ID 的 Manager 丢掉会话后不留下“连接活、同步会话死”的连接。**接受的代价**：玩家被踢一次；原因持续时（挤回超员人堆、实体始终超帧上限）反复重连，框架不做防风暴，根治在业务侧（`MaxVisible`、实体大小）。

#### <a id="s6"></a>S6 一个 Player 一个 Manager、自身视图帧上限取接入层上限

同一 `SubjectSyncState` 只能登记在一个 Manager（`ErrSubjectRegisteredElsewhere`）；`wiring/selfsync` 一帧上限取接入层上限（嵌入 TCP `player_access.tcp.max_payload_bytes`，独立 Gate 经 `LimitFrameBytes`），单个实体超限在 Manager 内编码失败（随后按 [S5](#s5) 断开）。

#### <a id="s7"></a>S7 会话 Hold 后撤到一个订阅都不剩，Ready 后补发空 Full

学习分支审查第 8 条：修前接收端一直留着已撤权对象。现在交付过帧的会话收到一个不含对象的 Full（新 epoch）。剩余：每次 Hold → Ready 都按全量重发仍在的对象，“暂停不重置”原语（方案 B）待决定。

#### <a id="s8"></a>S8 嵌入 TCP 出站全进程驻留预算、关闭事件顺序

全部连接共用驻留预算 `player_access.tcp.outbound.resident_bytes`（缺省 256 MiB），放不下的一帧当场被拒（`gateway.ErrResidentBudgetExhausted`），不关连接；Sync 当整轮重试，Lockstep 实时帧按丢包。会话关闭事件改在写协程退出、驻留预算归还之后发布。

### 优化项（维护者 2026-10-22）

来源：学习分支 `learn/main-review-20261021` KNOWN-LIMITS“main 近期提交审查”第 11 条与维护者 2026-10-22 补充“MMO / SLG 的移动频率一般是 2～5Hz”。**维护者 2026-10-22：“如果这些优化项不复杂的话，可以直接做了”**。登记与状态见 [DESIGN-TODO“优化项（下一阶段）”](../maintenance/DESIGN-TODO.md#优化项下一阶段)；“附近没有玩家观察时 AI 停止”另行实施，不在本节。

#### <a id="o1"></a>O1 缺省移动频率 5Hz

**变化**：`movement.DefaultMovePeriod` 100ms → 200ms。不给 `Period` 的 `MoveTo` / `Follow` 改为每 200ms 一拍：每秒心跳消息减半，每拍走 `速度 × Elapsed`（位移翻倍），走完一段的时间不变；观察者看到的位置每 200ms 更新一次。game-demo 的玩家移动与怪物巡逻用缺省，随之 5Hz（注释、WALKTHROUGH 已改）。生成器的示例动作 `ExampleAction` 不是移动、仍 100ms 档；`actionflow.DefaultBeatPeriod` / `DefaultMissionPeriod` 不变。guide 档位建议改为“移动 200ms”。**为什么**：维护者 2026-10-22“MMO / SLG 的移动频率一般是 2～5Hz”，10Hz 让大规模 NPC 的心跳消息多一倍。**升级**：要 10Hz（动作游戏、近战贴身）就在参数里显式给 `Period: 100 * time.Millisecond`。**压测口径**：sync-aoi `-move-period` 缺省跟 `DefaultMovePeriod`；与 2026-10-22 之前的心跳模式结果对照时显式加 `-move-period=100ms`（[HB-DRIVEN-LOAD §4](../performance/HB-DRIVEN-LOAD-20261021.md#4-待补测2026-10-21-因宿主资源占用推迟)、[压测清单 §7](../performance/V1310-PRERELEASE-20261022.md#7-可选移动-200ms5hz口径缺省已改历史口径显式-100ms)）。

#### <a id="o2"></a>O2 定身期间计划步骤的时限不计时

**变化**：步骤动作所在组被冻结（`Freeze`，含 `state.Gate` 施加的定身）期间，`MissionStep.Timeout` 暂停，解冻后按剩余时长继续，多次冻结累加；按 Behavior 的时钟（`fctx.Now`，挂了时间域时是域时间）。`FreezeCancel`（打断）照旧：动作以取消结束，这一步不重试、走 `OnFail`。新增可选接口 `actionflow.FrozenTimer`（`Behavior.FrozenFor(kind, now)`），自己实现 `ActionList` 而不实现它的照常计时。**为什么**：修前时限在定身期间照样走，定身长于时限时护送 / 巡逻类任务直接以过期失败。**升级**：无存储 / 协议变化。

#### <a id="o3"></a>O3 每个 Interest 的空间视野总数上限 `MaxSpatialViews`

**变化**：`InterestConfig.MaxSpatialViews` 限制一个 Interest 经 `DefineSpatialView` 定义的空间视野总数（挂没挂接都算，不含玩家主视野与关系视野），零值取 `DefaultMaxSpatialViews` = 8192，负数拒绝构造；超出时 `DefineSpatialView` 返回 `ErrSpatialViewLimit`、什么都不定义，并计 `entitysync_interest_view_limit_rejected_total{reason="spatial_views"}`；`RemoveView` 归还名额。**为什么**：每个空间视野都是 AOI 观察者，定义了没挂接的（忘了 `RemoveView` 的眼位、单位视野）也参与每次移动的计算，`MaxViewsPerPlayer` 只数挂接、管不到它们。**缺省 8192 的依据**：D19“两种应用模式”实测（M5、1000 玩家、每视野可见约 50、50ms 周期）里 1000 玩家各 8 个空间视野（8000 个）时 ApplySync 的 Flush 约半个周期，即阈值 8 取的位置；16000 个时贴着周期。**边界**：只在登记侧计数，执行器的切点与预算不变；ApplyAsync 的政策阶段耗时预算没有做；缺省来自一台机器、一种密度。**升级**：定义超过 8192 个空间视野的业务（RTS 一类）显式调大。

#### <a id="o4"></a>O4 行为与移动的文档边界

guide/10-time §4B 新增“逐拍移动适合谁”：SLG 行军按“起点 + 速度 + 出发时刻”按需算位置、到达用 entitytimer，只有大地图 AOI 需要服务端位置时加 1～2Hz 心跳；心跳的 `Elapsed` 是可变步长（随驱动迟到、掉拍变化），确定性玩法（MOBA、格斗、RTS 帧同步）走 Lockstep。§4C：控制等级、韧性、递减由业务在施加 Buff 之前决定，框架不提供。guide/04-sync 应用模式表改正 MOBA 一行：状态同步 MOBA 的阵营视野是每个友方单位一个空间视野挂给全阵营，挂接数几十个，选 ApplyAsync（或等以后的“一个视野多个视点”），帧同步 MOBA 走 Lockstep；`policy.ApplyMode` 注释同步。

#### <a id="r2"></a>R2 心跳按投递代际结算：旧重投、旧交回不再消费下一拍（RV-20261022-02）

**变化**：每次投递分配一个代际（每个登记从 1 递增），凭据（登记 + 代际）作为这一拍 Nest 消息的参数；卡住兜底的重投沿用原代际。执行侧先认领自己那一代、返回时结算；准入被拒与批量作业交回也只结算自己那一代。认领或结算不上的消息（这一代已执行、被拒或交回，或正在执行）按 `heartbeat.dropped_total{reason="duplicate"}` 丢弃：不执行回调，不动下一拍的在途。登记状态、投递代际、重试次数、正在执行四件事分开表达，同包按职责分出 `delivery.go`（投递层与投递身份）、`observe.go`（计数、指标与 Warn），`driver.go` 只留调度与生命周期。

**为什么**：审查确定了一个交错：驱动投出原拍 → 超过兜底阈值重投 → 原拍执行 → 驱动投出下一拍 → 队列里的旧重投执行。修前所有拍都只带同一个 `*Reg`、执行侧只看一个在途布尔值，旧重投多执行一次回调并清掉下一拍的在途（`stale retry executed: calls=2 new beat inflight=false; want 1,true`），下一拍到达后被当成 `duplicate`；停止后重启时旧重投还会冒充重启后的第一拍（`First`）；批量方式下旧重投晚到的交回会清掉下一拍、甚至正在执行这一拍的在途，驱动随即多投一拍，违反“每个登记至多一拍在途”。审查建议 2 原文：“登记状态、投递代际、重试次数和正在执行状态含义不同；单一 inflight 不能表达全部。先明确状态转换和归还所有权，再整理调度、投递、观测职责到同包文件。”方向判断：“优先修正这些状态和检查边界，不继续增加时间阈值或重试分支”，本修复没有改阈值、翻倍规则与重试次数。

**兼容与升级**：公开 API 不变，没有存储 / 协议变化。三处可观察变化：① `dropped{reason="duplicate"}` 的含义从“同一次投递的另一份已执行”扩为“这一代已结算或正在执行”（含旧交回），不新增标签；② 心跳消息的参数从 `*heartbeat.Reg` 改为包内凭据，慢派发 trace 的参数样本显示为 `&heartbeat.beat{registration:"…", entity:…, generation:…}`（仓库里没有从消息参数取 `*Reg` 的代码）；③ 每拍多一次 32 字节分配（凭据不能复用：队列里晚到的旧消息仍持有它），微基准 `BenchmarkDriverDispatch`（驱动侧，假客户端在驱动 goroutine 上直接执行 handler）同机交替 10 轮：`allocs/op` 2 → 3、`B/op` 64 → 96；进程 CPU / 拍 dispatch 方式中位数 +26%～+45%（p<0.05），batch（缺省）方式无显著差异；机器有后台负载，单轮波动 ±30% 以上，各组最小值多出约 30～50ns / 拍。按 H2 的实测单目标 Nest 消息每拍约 6～8µs CPU，这几十纳秒约占 1% 以内（估算，没有在真实 Nest 下对照），原始数据在 [benchmarks/heartbeat-delivery-generation-20261022](../performance/benchmarks/heartbeat-delivery-generation-20261022/benchstat.txt)。维护者 2026-10-22 决定按方案 A 保留：“投递凭据按当前实现，每拍分配一个，简单方便”，不做凭据回收复用。

**边界**：同一代的重投被交回或被拒、而原拍还在队列里时，先到的结算者赢：这一代按跳拍结算，原拍之后到达按 `duplicate` 丢弃（与修前相同，修复只保证不会结算到别的代）。Nest 侧不需要配合：批量作业交回的凭据原样带回即可。RV-20261022-01 修复后，组内 Fence 之后尚未开始的目标以 `ErrNestFenced` 交回：交回的是这一代时按 `rejected` 跳拍结算，是已结算那一代的迟到交回时只计 `duplicate`（`TestAStaleHandBackDoesNotSettleAnotherBeat/fenced_hand-back`）。

#### <a id="r5"></a>R5 朝向作为 MapBasic 的 DAO 数据：只转向也落库，修改随事务回滚（审查建议 5）

**变化**：`movement.MapBasic.SetFacing` 与 `SetPos` 走同一机制：本事务第一次改组件状态时登记回滚（`guard`）、标“变过”（dirty）、写 `Fields`（DAO 字段，生成的 setter 登记逆操作，回滚恢复朝向值）、提交后发布。于是 `Save`、`SaveOnLeave`、`SaveEvery`（心跳 `"map.save"`）在只改朝向时也调 `MapConfig.Save`，回调的 `facing` 参数是当前朝向；回滚的转向既不留下新值，也不留下“变过”。朝向不入 AOI 队列（AOI 不关心朝向）；同步与持久化规则同位置：DAO 字段 `nopersist,sync`，不每拍落库，跟随周期落库与离开场景时的保存。game-demo：`PlayerDao` 新增持久 `saved_facing`，保存回调写它，`MapComponent.EnterScene` 进场景后恢复保存的朝向；怪物是 `noPersist` 实体、没有保存回调，朝向本来就是 `nopersist,sync` 的 DAO 字段，不变。

**为什么**：提交审查可读性与设计建议 5 指出单独 `SetFacing` 后 `Save` 不调用保存回调（dirty 与 Save 只覆盖位置和场景），建议二选一：“若需要，dirty 应包含朝向并支持事务回滚；否则文档明确朝向仅随位置保存”。**维护者 2026-10-22 决定：“朝向（facing）作为 DAO 中的数据”**，即前一种。

**兼容与升级**：公开 API 不变（`MapConfig.Save` 本来就带 `facing` 参数）。可观察变化：只转向的实体在下一次周期落库 / 离开场景时会调一次保存回调（修前不调）。game-demo 存储多一个持久键 `saved_facing`：旧文档读作 0（朝 +X），没有提高 `schema=`（加字段，BSON 解码给零值，与本版 `saved_*` 同样处理）；已生成的工程重新生成 `db/` 与 `map_component.go` 即可。

### Nest：异步完成按 handler、同实体按提交序

#### <a id="n1"></a>N1 Nest 异步完成按 handler 生效（维护者 2026-10-29，不兼容）

**变化**：`nest.NestOptionWithPipelinedAsyncCompletion(workers, queueCap, handlers ...string)` 只让点名的 pipelined handler 走完成泵；名单为空 = 不建完成泵，没有“全部”通配。名单在引擎构造 / 实例注册 / 包级回退查找时解析成每个 handler 的标志，派发热路径不按名字查表。没被点名的 pipelined handler 保持 Phase 1（派发 worker 等票据、AfterCommit 在派发 goroutine 上、回复之前），有完成泵时仍在同实体完成链上占位，同实体异步完成与 Phase 1 事务的 AfterCommit 与回复保持 LSN 序。**删除配置 `nest.pipelined.async`**：生产装配的名单就是本进程声明 pipelined 的原生步骤（[J8](#j8)）。

**为什么**：原来的引擎级开关会让业务自己声明 pipelined 的 handler 悄悄得到异步完成（AfterCommit 改到完成池 goroutine 上、看不到请求上下文）；维护者要求只给真正需要的原生步骤。

**升级**：手写装配改传名单；配置删 `nest.pipelined.async`（doctor 按未声明的键报 FAIL）。

#### <a id="n2"></a>N2 同实体上每笔事务对外可见的效果按提交序（维护者 2026-10-29 决定 A）

**变化**：之前异步完成事务（原生步骤）放锁后，同实体上紧接着提交的 strict / async / memory 事务可以先回复、先跑 AfterCommit，async 的回复还可能把原生步骤尚未持久的状态带出进程。现在完成泵按实体 ID 分片计数在途的异步完成；普通事务仍持声明实体锁时读计数，为 0 走快路径（一次原子读，不加锁、不分配），否则在这些实体的完成链上占位，Guard 放锁之后、AfterCommit 与回复之前等前驱完成（不持锁等待，等待只指向更早的节点，不会死锁）。多实体按全部声明实体检查；批量作业（心跳）遇到有在途异步完成的目标转成单目标作业，不在 worker 上等。没有完成泵的引擎行为不变。

**代价（维护者接受）**：实体上有在途原生步骤时，该实体的普通请求最多多等一次组提交（一个 fsync），期间占一个 short 池 worker；其他实体不受影响。快路径开销：`BenchmarkNestHotPathCompletionPump` / `BenchmarkNestHotPath` allocs 与 B/op 不变、sec/op geomean −0.36%（噪声内）；saga 端到端 c128 pipelined 1011 / 996 saga/s，与上一轮 1022～1053 在噪声内（[证据](../performance/benchmarks/nest-completion-order-all-20261029/README.md)）。契约见 [NEST_PIPELINED_COMMIT §11](../framework/NEST_PIPELINED_COMMIT.md#11-phase-2-实现异步完成)。

**不覆盖**：没有 Guard 作用域的直调（`RunIsolatedTransaction` / `RunDetachedTransaction`）、handler 内 Cast 动态取得的实体；异步完成事务自己只在主实体上占位。

#### <a id="h6"></a>H6 心跳不再支持 pipelined（维护者 2026-10-29，不兼容）

`gameplay/heartbeat` 删除 `heartbeat.beat.pipelined` handler，`Register` 带 `WithDurability(nest.DurabilityPipelined)`（或任何不认识的级别）返回 `heartbeat.ErrUnsupportedDurability`；支持 memory / async / strict。仓库内没有生产调用方。Nest 本身仍允许其他 handler 声明 pipelined（维护者选择按 handler 自由）。

### DataEngine

#### <a id="d5"></a>D5 投影器按实体分片并行投影（维护者 2026-10-27 方案 A）

**变化**：一轮回放的记录按冲突键（文档 `_id`、回执身份、effect ID、事务 ID）分成互不相干的组，分给至多 `dataengine.projection.workers`（1～64，缺省 8，1 = 串行）条通道同时投影，通道内照常合批；有交集的记录保持 WAL 顺序，checkpoint 只确认连续成功前缀，前缀之后已投影的记录靠事务标记幂等重放。**effect 暂存顺序不变**（维护者 10-28 选 A：带 effect 的记录之间仍按 WAL 顺序，选项 B“按实体有序”暂不采用）。配置 `dataengine.projection.remote_workers` 改名 `workers`（旧键不再读）。

**数字**（单机短测，只给量级，[报告](../performance/PROJECTOR-ENTITY-PARALLEL-20261027.md)）：普通记录本机 6815 → 24717 条/s、云 Mongo 431 → 1653 条/s（w8）；带回执记录随通道数近线性；带 effect 的记录不变。设计：[FEATURE-2026-10-27-projector-entity-parallel](https://github.com/tjbdwanghaibo/roost-core/blob/132ed79f689df01dc8df0ea3a44e9a768ee126d9/docs/maintenance/FEATURE-2026-10-27-projector-entity-parallel.md)。

#### <a id="d6"></a>D6 删除 lease fence 机制（saga 第 5 批，L-A）

第 4 批之后没有生产路径再写 lease fence 回执（原生步骤回执在实体里），整套机制删除（见 [B1](#b1)）；strict / async / pipelined、投影冲突 fail-stop、Remote 的行为不变。**升级**：旧 WAL 里带 fence 回执的记录会被当普通回执投影，升级前用旧版本排空 WAL；告警基线第 8 条（`dataengine.fence.*`）作废。

#### <a id="d7"></a>D7 `dataengine.startup_timeout` 缺省 60s、启动排空有界重试

遗留 Mongo 事务最晚 1.5 × `transactionLifetimeLimitSeconds`（部署要求 20s → 30s）才回收，30s 期限没有余量；维护者 2026-10-29“按推荐”调到 60s。启动排空（`drainAtStartup`）在调用方期限内退避重试（`dataengine.startup_drain_retry_total`），直接装配、没给期限时上限 2 分钟。生成器打开单实例锁的服务 install.sh / rollback.sh 的 `HEALTH_ATTEMPTS` 与 compose `start_period` 各加 30s。

### Redis

#### <a id="i1"></a>I1 删除只被测试使用的 Redis API（测试审计跟进，维护者“按推荐”）

`IScript`、分布式锁（`IDistLock` 一组与 driver 的 `DistLockFactory` / `AutoExtendLock`）、WAITAOF 脚本接口（`EvalDurable` / `EvalBatchDurable`、`DurableEvaler` 等）在 Redis 权威删除后没有生产调用方，连同只测它们的用例删除。`EvalReplicated`（WAIT，L2 墓碑在用）与 `IVersionedLock` 不变。需要时从 Git 历史取回（`git show 1a439973:infra/storage/redis/driver/client.go`）。

#### <a id="i2"></a>I2 Redis Cluster 重定向预算耗尽后安全重试（10-23）

MOVED / ASK 纳入既有有界的“确定未执行”重试；执行后丢响应仍不重放，WAIT 不变；永久重定向仍有总预算（[证据](../performance/benchmarks/redis-redirect-20261023/README.md)）。历史八次实际路由未恢复。

### <a id="x1"></a>X1 Redis 权威路线的尝试与放弃（从未发版）

2026-10-26～27 按 [Redis 权威设计 v2](https://github.com/tjbdwanghaibo/roost-core/blob/132ed79f689df01dc8df0ea3a44e9a768ee126d9/docs/maintenance/DESIGN-2026-10-26-redis-authority-v2.md) 在 main 上实施了 2a（协调器存储迁到单主 AOF always 的权威 Redis，Lua + 同连接 WAITAOF 一次往返提交，`6709eb90`）与 2b（Store Service 把权威 Redis 的 saga 日志投影进 Mongo 冷副本，`a3edef04`）。结果（[报告](../performance/SAGA-REDIS-AUTHORITY-2AB-20261027.md)）：协调器每笔 Mongo 操作降到 0，但权威 Redis 与 Mongo 同盘时每次写的 `F_FULLFSYNC` 让吞吐低于旧实现（Mongo 步骤饱和约 0.4～0.5 倍、原生约 0.8 倍），未达 2a 门槛。维护者 2026-10-28 放弃该路线；2c 未合入，本地 tag `archive/redis-authority-2c` 归档；2a / 2b 的代码在 saga 第 4 批（`c776dbe6`）删除。CHANGELOG 里保留了它的条目（标为“已被第 4 批取代”），**v1.31.0 用户不需要做任何与它相关的升级**，除非部署过那段 main。

## <a id="limits"></a>4. 已知边界（摘要，全文见 [KNOWN-LIMITS](../maintenance/KNOWN-LIMITS.md)）

- 心跳批量投递：同时段业务 p99 0.095（单目标）→ 0.104ms（缺省组 4 / 100µs；组 4 / 200µs 0.149ms）；Linux 全部未复测。
- 心跳驱动与投递有正式对比（2026-10-22 晚）；移动、行为、技能 / Buff 本身没有正式性能测量，3000 实体只做了功能冒烟。
- game-demo 100 / 200 人同秒起跑的 loadtest 不通过（共享热点：World / 场景实体、公会目录、gift saga），`object limit exceeded` 已为 0（[压测清单 §3](../performance/V1310-PRERELEASE-20261022.md#3-game-demo-loadtest-100--200-人)）。
- Interest：重负载下 ApplySync 可见性滞后；一步的交错超出量没有数值测量；命令日志不计入 `MaxQueuedFacts`。
- 编码失败断开不做防风暴；Hold → Ready 每次全量重发。
- Lockstep 独立 Gate 慢链路上大快照被断开循环；快照不续传。
- Remote 托管实体挂心跳 / 移动组件的问题只记录方向，没有禁止。
- `MaxSpatialViews` 缺省来自一台机器、一种密度的实测，ApplyAsync 没有政策阶段耗时预算；移动缺省 5Hz 下位置每 200ms 更新一次（[O1](#o1)、[O3](#o3)）。
- game-demo 一个进程一张地图；玩家位置靠 10 秒周期落库。
- **Saga**：分区归属静态（协调器进程停了它的分区就停，没有自动接管）；同一个 sid 只能有一种服务类型装 saga Mod（部署规则，没有启动期检查）；业务键唯一性只在运行期间 + 终态保留期（1h）内成立，冷副本不参与；冷副本 durable 挡分区清理，Mongo 不可写或关了冷副本没删 durable 时清理停住、流满 fail-stop；清理守卫的 floor 在消费者 leader 落后时可能清掉还没投递的命令（只影响活性，**尚未确认**会不会发生）；参与方长停机后过期命令积压（实测 60s 停机约 5000 条，1～3s 排空）。
- **Nest**：实体上有在途原生步骤时，该实体的普通请求最多多等一次组提交、占一个 short 池 worker（[N2](#n2)）；异步完成下的 AfterCommit 在完成池 goroutine 上，没有请求上下文、不持实体锁。
- **投影器并行**：带 effect 的记录之间仍串行（saga 原生步骤负载不受益）；通道静态分配，一个慢调用拖住所在通道与本窗口的确认（[D5](#d5)）。
- 物理房间：Unity 编辑器交互、WAN、多房间容量与长稳未验；LevelComponent 没有真实 Mongo / WAL 多进程崩溃恢复验证（[U1](#u1)、[U2](#u2)）。
