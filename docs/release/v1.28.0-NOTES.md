## 2. 破坏性变化

### <a id="b1"></a>B1 match：队列键加 hash tag，新增跨分区原子成局 `CommitAcross`

**原因**：放宽匹配时一局票来自同一逻辑队列的几个分区，没有原子成局办法，分别 Commit 任何一边失败都留下半局（维护者 2026-10-19 批准）。

**变化**：`Queue.Key()` 由 `<Mode>:<GroupSize>:<Partition>` 改为 `{<Mode>:<GroupSize>}:<Partition>`，Redis 键 `<prefix>:queue:{<Mode>:<GroupSize>}:<Partition>`；同一逻辑队列的分区同槽，代价是一个逻辑队列的全部分区落在同一 Cluster 节点。`key_prefix` 第一对花括号为空时 `NewRedisStore` 拒绝。`Store` / `Matchmaker` 接口新增 `CommitAcross(ctx, TicketRefs)`。

**升级**：旧键不迁移——停旧匹配服务、清空 `<key_prefix>:queue:*`、再起新版本，新旧进程不能共用一个 Redis 前缀。`match.sweep_queues` 写法不变。

### <a id="b2"></a>B2 Sync 慢消费者：推送在活着的连接上被拒即断开连接

**原因**：“推送被拒 → 只关同步会话 → 连接还活着 → 政策层自己重开”这条路径出过 5 次缺陷（RR-20260926-55 `12d4f7ca`、RR-20260927-19 `879b9094`、D6 初版 `fc0a8315`、`00d35150`，以及第 9 次重开后自身视图永久消失）。根因是慢消费者规则在 Manager 与传输两层不一致。维护者 2026-10-17 批准“A + A'”：规则只放在传输一处。

**变化**：新增 `wiring/selfsync.PushPlayerFrame`（自身视图与 game-demo 场景共用）——可靠队列满、绑定失效、帧超限等拒收会关闭该玩家**全部**连接；接入层未就绪 / 已关闭、或每条连接都因进程驻留预算耗尽而拒收时整轮重试、不断开（新哨兵 `nettransport.ErrResidentBudgetExhausted`，仍满足 `ErrReliableBackpressure`）。`policy.SelfView` 删除重开机制；Manager 的线协议 epoch 改为本 Manager 内单调递增（客户端不能假设首帧 epoch 为 1）。Game Ingress 在激活回调执行期间已可按玩家推送。

**升级**：独立 Gate 下，自身视图推送被 Game Ingress 可靠队列背压拒收时客户端会看到连接被服务端关闭（此前保留连接、同连接重开），按普通断线重连。新指标 `entitysync.self_view.stranded_players`（正常为 0）与 `player.sync.push_refused.total{outcome}`。

### <a id="b3"></a>B3 嵌入 TCP：推送改为每连接有界出站队列

**原因**：修前 `TCPRuntime.Push*` 持写锁同步写 socket，一个停读客户端让每次场景 Flush / Lockstep Tick 卡满 `write_timeout`（默认 5s）。

**变化**：每连接一条队列和唯一写协程按序写出推送、回包与心跳 ACK；`Push*` 与业务可见的 `Session.Reply` **只入队**，返回 nil 表示已准入、不表示已写出。“排队 + 写协程在途”超过 1024 帧或 `max(2 MiB, 2 × (max_payload_bytes + 16))` 字节、或一帧在 `write_timeout` 内写不出，关闭该连接（指标 `player_tcp_outbound_overflow_total`），与独立 Gate 一致。帧数上限保持 1024（维护者 2026-10-16 决定）。每连接 goroutine 由 1 变 2。

**升级**：依赖“Push 返回即已写出”的业务代码需改为显式确认（Lockstep 追帧用 [B4](#b4) 的等写出通道）。

### <a id="b4"></a>B4 `lockstep.NewTCPSender` 签名：实时与追帧两个 push

**原因**：B3 之后追帧每 Tick 一页灌进出站队列，慢链路上几 MiB 历史就把连接推过上限被关闭。维护者 2026-10-16 决定方向 A。

**变化**：第 4、5 个参数分别是实时帧 push（生产接 `PushLockstepSession`，只准入）与追帧 push（生产接新增的 `TCPRuntime.PushLockstepSessionWritten`，入队并等写出），都不能为 nil；超过 `CatchupSendTimeout` 的页撤回并计入 `CatchupMaxFailures`。等写出只在 Match 的 `launchSend` goroutine 上。

**升级**：自定义接线改调用。独立 Gate 路径与 game-demo 的 `battleSender` 追帧仍只准入（见 KNOWN-LIMITS）。

### <a id="b5"></a>B5 `entitysync.Manager.RegisterPolicy` 改收 `PolicyHooks`

**变化**（D3，维护者 2026-10-15 决定 A）：`RegisterPolicy(apply, pending...)` → `RegisterPolicy(entitysync.PolicyHooks{Apply, Pending, Stalls})`，`Stalls` 可选。`Manager.Drain` 超时 / 取消时返回 `*DrainStalledError`（`errors.Is` ctx 错误不变），列出前 8 项卡住条目；新指标 `entitysync_drain_timeout_total`、`entitysync_drain_remaining_entries`。Drain 行为不变。

### <a id="b6"></a>B6 Lockstep 历史默认保留 3600 帧，越界追帧明确失败

**变化**（D1，维护者 2026-10-15 决定方案 C）：`MatchConfig.HistoryRetainFrames` 缺省按 `DefaultHistoryRetainFrames` = 3600 帧裁剪（`RetainFullHistory` = -1 关闭，正值须 ≥ 64）。越界追帧立即返回 `*CatchupUnservableError` 并经可靠通道下发 C9 v1 追帧失败通知；Go `FrameAssembler`、`robot.LockstepBot`、C# `LockstepAssembler` / `LockstepClient` 终止，不自动重同步。修复了起点 0 绕过越界检查的问题。

**升级**：需要整局回放的宿主自行持久化或配置 `RetainFullHistory`；旧客户端会把 C9 当坏包终止，客户端与服务端须同版本。

### <a id="b7"></a>B7 Timer：Tick 期间对不存在的定时器改期 / 取消返回 false

**变化**（维护者 2026-10-17 决定）：`Scheduler.ChangeTimer` / `RemoveTimer` 在 Tick 期间（含回调与重入 Tick）对已不存在的 ID 返回 false（原先 true），与 Tick 外一致；操作本身仍无效果。随 Scheduler 重构（节点显式状态替代按 ID 推迟的闭包，维护者 2026-10-17 批准）钩子的**中间序列**也有变化：同一 Tick 内多次改期只在收尾发一次 upsert，收尾按节点首次入队顺序回调，取消等待放回的节点时立即发删除。公开 API 与持久字段不变。

**升级**：依赖 Tick 内恒为 true 的业务改判断；按钩子中间序列推进持久状态的宿主核对[重构方案](../maintenance/REFACTOR-2026-10-17-timer-scheduler.md)。

### <a id="b8"></a>B8 errcode 框架段与删档语义

**变化**：`infra/base/errcode` 划出框架段 1–999：`CodeEntityNotFound = 2`（D7 方案 C：从未创建的实体，Nest 在声明目标的加载结果处包装，客户端收到 `code=2 entity not found`）、`CodeEntityDeleted = 3`（D10，维护者 2026-10-17 决定 B，范围只守 GetOrCreate）。删过档是独立哨兵 `entity.ErrAuthorityEntityDeleted` / `engine.ErrEntityAggregateDeleted`，**不再满足** `ErrAuthorityEntityNotFound`；生成 lifecycle 的 `GetOrCreate` 因此不会重建删过档的 ID，返回 3。Remote 托管实体经元数据墓碑判定。`roost.yaml ids.errcode` 下界 ≤ 999 时 manifest 校验失败。

**约束**：直接 `Create` 不受保护，必须用 id-gen 发的新 ID。**升级**：客户端收到 3 不要重试或自动重登，提示角色已删除；已生成的 lifecycle 归业务不改写（不重新生成也安全，只是码为 `CodeInternal`）；修复前写进 WAL 的重建记录按 §1 清理。

### <a id="b9"></a>B9 DAO 持久键规则、持久文档结构体与旧字段不加载

**原因**：新用户试用第七轮第 1 项（改 Go 字段名静默丢老数据）；维护者 2026-10-19 决定 D13：定义里的 `bson` 名就是持久键，改字段告警、不拒绝。同日维护者改变旧键处理的决定——原话“旧字段就不 load 了，给一个业务层的约束或者通知就可以了”——main 上 `322a7c40` 实现过的“整文档写回保留旧键 + 显式清理入口”在发版前撤销，没有随版本发出。

**变化**：DAO 定义字段的 `bson:"x"` 就是持久键，没写时是 Go 字段名的 snake_case；键须字母开头、只含字母数字下划线、不以 `_` 开头、类型内不重复，`bson` 选项只认 `omitempty`，其余与 `bson:"-"` 生成期报错。生成的 `gen_<x>_dao.go` 新增 `<dao>PersistDoc` / `<dao>StoredKeys` / `<dao>RollbackDoc`，整文档写入由 `bson.M` 改为结构体编码。`roost generate` 以上一次生成物为基线，持久键消失 / 新增 / 类型变化各打一条 `WARN`；加载时库里有、结构体没有的键按 DAO + 键每进程打一次 WARN（`dataengine: stored document has a key the DAO does not declare; it is no longer read`，计数 `dataengine.dao.unknown_stored_key.total{dao}`），照常加载但**不读入**这个键：DAO 内存里没有它，下一次整文档写回（含 Remote data 信封替换）就把它从文档里删掉；单字段补丁不碰它，它留在库里但不再被读取。

**业务层约束**（[SCHEMA-MIGRATION §1](../framework/SCHEMA-MIGRATION.md)）：改名 / 删字段前，要么保留原 `bson` 名，要么先离线迁移再提升 `schema=`；否则旧数据不再加载、写回即丢失。框架只通知（两处 WARN 与计数），不替业务保留旧值。

**升级**：`bson` 名与 snake_case 相同的字段（模板与示例都是）存储键不变；写了不同 `bson` 名的字段，键变成该名字（生成期 WARN，原 snake_case 键下的旧值不再加载，启动前先迁移）；嵌套字段上的 `omitempty` 现在生效（demo `TimerNode.Payload` 为空时不再写出）。

### <a id="b10"></a>B10 生成器：共享资源名按工程名派生及其他新工程默认值

**变化**（新用户试用第四轮第 1 项与 D8 / D9）：新工程的 `nats.prefix`、`syncbus.prefix`、`dataengine.database`、`dataengine.effects.subject_prefix` / `stream`、saga 库 / 主题 / 流、`remote_entity.mongo.database`、`etcd.service_prefix` 与 DAO 骨架的 `db=` 都按工程名派生（工程 planet → `planet`、`planet.sync`、`PLANET_EFFECTS`、`planet_saga`、`planet_remote`、`/planet/services/` 等）；Mod 的运行期缺省值不变。新工程服务包名小写（`package game`）。`roost add access` / `add rpc` 带入的 Mod 补配置段，带 DataEngine 的服务打开单实例锁（**之后启动需要 Redis**）。

**升级**：已有工程配置与 DAO 定义归业务、不改写；之后 `add mod` 追加的段会写新值，与已有段不一致时要么改回旧值，要么把所有服务改成新值并清空旧库、删旧流（`ROOST_EFFECTS`、`ROOST_SAGA`、`ROOST_SYNC` 等）后重启。新生成的 game-demo 换了 DAO 库名，旧 `game` 库数据不迁移。

### <a id="b11"></a>B11 Saga / DataEngine effect

- **效果流只配一处**：`saga.start_effect_stream` / `start_effect_prefix` 去掉缺省值，不写时取 `dataengine.effects`；同进程注册了 DataEngine 且显式写了不同值时，启动前、`--check-config` 与 doctor 都拒绝。完成回执保留期与效果流保留期的比较也搬进跨 Mod 配置检查。
- **原生步骤消费者**：等回执 → 结算 → ack 移出 durable 的串行回调（新 `StepConsumerConfig.ReceiptWaiters`）；同 durable 上同一实体的后一条命令在前一条未投影时撞实体屏障（`ErrFencedEntityPending`，交还租约、退避 nak 重投），不再排队。
- **生成器**：`definition.go` 不再生成 `Subscribe<Step>` / `Subscribe<Step>Compensation`（已有文件归业务、不改写）。
- **删除导出 API**：`kitdataengine.EffectStreamRetention`。
- **game-demo 集合与阶段名**：`_game_gift_step_inbox` → `_game-gift_step_inbox`，`_game_effect_inbox` → `_effect_inbox_game-level-up-mail`（新集合没有旧回执，旧 durable 未 ack 的 effect 会再处理一次，mail 按 RequestID 去重）；转交信封退款阶段名 `refund` → `debit-undo`。

### <a id="b12"></a>B12 game-demo 与指标

- 场景指标 `scene_session_reopen_failed_total` → `scene_session_open_failed_total`（只计 Join 打开会话的放弃）。按旧名查询的面板 / 告警改名。
- `configdata.reload.total` 新增 `result="unchanged"`，原 `ok` 只计内容有变化的成功；`gm.config.reload` 删除，改用框架自带的 `configdata.reload` / `rollback` / `status`（经 ops `/admin/execute`）。
- 副本排行改为按赛季的通关数快照（`UpdateMax`），升级时清空 `clears` 榜；活动贡献只在奖励首次付款时提交。
- 赠礼 saga id 改为 `gift-<发送方>-<完整会话 SHA-256>-<帧序号>`；跨升级重发的同一帧不会被认成同一请求。
- `RecordExp` 返回 error；`handlerClaimDungeon` 多一个 `season` 参数；`gift.NativeStep` 删除。
- World 定时器恢复手写、直接调用 core 的 entitytimer 驱动（维护者 2026-10-18 原话：game-demo 是手写的参考实现，不迁到生成器产物上；生成器只生成框架内容，不能生成 demo）；game 服务不装 `wiring/entitytimer` Mod，缺省 Mod 集 `shutdown.total_timeout` 117s。

### <a id="b13"></a>B13 生成器的新拒绝与输出文本

- 实体 `remote=managed` 而带 Nest 的服务全都没有 `remote_entity` Mod 时，`roost generate` 与 doctor 拒绝并给出 `roost add mod remote_entity -service <svc>`；运行时报新的 `entity.ErrNoRemoteRuntime`（`errors.Is ErrRemoteWriteCapabilityDisabled` 不变）。
- `roost config check` 键检查通过后经编译出的进程跑 `--check-config`（会编译一次工程）；编译不过时结果行为 `config keys are valid (cross-mod rules not checked)` / `config keys ok (cross-mod rules not checked)`，按文本匹配 `config is valid` 的脚本注意。
- `roost add saga -steps` 保留书写顺序、重复步骤名报错；`project new -services` 同样保序。用旧版本生成过多步 Saga 的工程核对 `saga/<name>/definition.go` 的步骤顺序。

## 4. 重要修复（不改 API 的行为修正）

- **Timer / entitytimer**：回调内显式改期不被返回值丢掉或被重入 Tick 提前触发；回调内创建时固定期限与 payload 快照；持久化钩子重入 Tick 时钩子视图与 ID 种子正确；收尾钩子 panic 不重放；entitytimer 回调内的组件操作共享当前 Tick、读得到自己刚写的节点。
- **AOICluster**：同档移动也重选最近的容量内目标（只在跨过容量边界时重排）。
- **Saga**：命令身份摘要按 UTC 比较，经 bus 转交的原生步骤不再与消费者互相 `ErrIdentityConflict`。
- **Nest 生成器**：Sender 的局部名称避让业务参数、`handlerName` 常量与全部预声明标识符。
- **生成器 / game-demo**：表模板真的写进工程；handler 引用自身包类型时报错；领奖账本按执行时间判窗口、清理晚一个宽限；经验 / 背包写前校验范围；公会名规则一处；活动结算榜 `ZADD GT` 单调；服务进程运行期失败不再打印 Usage；`roost config check` 查出拼错的键。

## 5. 性能

- DataEngine：带回执 / effect 的特殊记录与普通记录合并 checkpoint（维护者 2026-10-18 选 A；缺省间隔保持 20 ms，2026-10-19 决定），投影器约 15 → 20 条/s；投影暂存 effect 后唤醒 outbox，“暂存 → 发布”P50 71 → 13 ms。[SAGA-CHECKPOINT](../performance/SAGA-CHECKPOINT-20261018.md)、[SAGA-OPT](../performance/SAGA-OPT-20261018.md)。
- Saga 原生步骤单进程容量（已决定按 A 文档化）：正向约 8/s、全补偿约 5/s 以内 P50 在 1 秒内；量大按 sid 分片多进程、加 `WithAdmit`。
- nestwal 记录编码去反射，codec7 逐字节不变，编码矩阵 24 组显著变快；WAL 追加由 fsync 主导、无退化。[PERF-ROUND-20261015 §2](../performance/PERF-ROUND-20261015.md)。
- Scheduler 重构：按返回值重排 −14.5%，回调显式改期 −18%～−20%。
- 本版**没有**重跑 30 分钟重档压测；运行时热路径（嵌入 TCP 出站、Sync 推送、DataEngine checkpoint）有变化，是否补测由维护者决定（见[验收篇](v1.28.0-VALIDATION.md)）。
