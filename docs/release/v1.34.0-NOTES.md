日期 2026-10-31。范围：v1.33.2 之后的 main（`4e537c0f` 弹性成局；`a7795bc3`～`5c904029` 组同步入口与观察者冲突修复；`e68a6d6e` 审查登记合入）。变更原文以 [CHANGELOG `[v1.34.0]`](../../CHANGELOG.md) 为准。

两项新能力都来自第十个玩法纵切“实时派对房间”暴露的框架缺口（[PARTY-ROOM-INTEGRATION](../framework/PARTY-ROOM-INTEGRATION.md) §8）。**生成物要求的最低 core 升到 v1.34.0**：声明了 `access.player.sync_groups` 的工程，生成的装配调用本版新增的 `selfsync.Groups`。

## 1. 升级

1. `go get github.com/tjbdwanghaibo/roost-core@v1.34.0`，用 v1.34.0 的生成器重新生成。`roost.yaml` 的 `versions.core` 写了低于 v1.34.0 的明确版本时 manifest 校验会拒绝。
2. **匹配服务先升级**：弹性队列的 `MinSize` / `FillAfterSeconds` 只有新版本服务端认识，旧服务端会忽略它们、把弹性队列当固定队列处理。固定人数队列（`MinSize` 为 0）的行为、键名、线格式与存储格式字节都不变。
3. **自建 Entity Sync 观察者的工程**：如果业务经 `NestOptionWithEntitySync` 给了自己的 Manager，同时又用了带 Entity Sync 的 Nest Mod（例如开了 self_sync），现在 `Provide` 返回 `ErrEntitySyncObserverConflict`。之前业务的 Manager 被静默覆盖、收不到提交，改法是把政策装到 Mod 的 Manager 上（`EntitySyncSetup.Attach`，或本版的 `selfsync.Groups`）。

## 2. 新增

### <a id="n1"></a>N1 匹配：弹性人数成局

`service/match` 的 `Queue` 新增 `MinSize` 与 `FillAfterSeconds`（整秒）。凑满 `GroupSize` 立即成局；凑不满时，组里最早一张票按业务时钟等满 `FillAfterSeconds` 后，`MinSize..GroupSize-1` 人也可以成局。规则只在 `Queue.FormableSize` 实现；存储在提交成局的同一次比较并设置里按存储时钟再校验一次，过早返回 `ErrGroupNotReady`（550110）、状态不变。“同一票集合并发只成一局”“同 requestID 幂等”不变，内存与 Redis 存储执行同一段判定。弹性规则是队列身份的一部分（键形如 `{party:2-8@20s}:eu`），`match.sweep_queues` 同一写法。详见 [guide/09 §4](../framework/guide/09-services.md) 与方案页 [FEATURE-2026-10-31-match-flexible-grouping](https://github.com/tjbdwanghaibo/roost-core/blob/132ed79f689df01dc8df0ea3a44e9a768ee126d9/docs/maintenance/FEATURE-2026-10-31-match-flexible-grouping.md)。

**未提供**：已开局房间的存储原生补位。维护者选了业务层写法——房间把空位当一张“房间票”排进补位队列，超员由进房 handler 拒绝；写法随派对房间手册更新。Redis Cluster 上的弹性用例与经 RPC 的端到端未跑。

### <a id="n2"></a>N2 房间 / 组同步的正式入口

新增 `policy.GroupView` 与 `wiring/selfsync.Groups`：按组（例如房间成员）推送某类实体的同步视图，与 self_sync 共用同一个 Manager、同一条玩家连接、同一个推送消息号，客户端按 `Namespace` + `Profile.Key` 区分（如 `player/self` 与 `party_room/room`）。成员关系是事实：`Join` / `Leave` / `Disband` 在 Nest 事务里调用时提交后才生效、回滚不生效；断线重连、顶号、组实体卸载后重载都由框架重新订阅并全量重发。生成器新增 `access.player.sync_groups: [<entity>]`（要求开 self_sync），在实体包创建一次业务文件 `sync_group.go`，只生成装配与声明，不生成成员规则。详见 [ENTITY_SYNC](../framework/ENTITY_SYNC.md) 与方案页 [FEATURE-2026-10-31-room-sync-groups](https://github.com/tjbdwanghaibo/roost-core/blob/132ed79f689df01dc8df0ea3a44e9a768ee126d9/docs/maintenance/FEATURE-2026-10-31-room-sync-groups.md)。

**未验证**：独立 Gate 部署下的组同步、慢消费者断开在组同步上的效果、房间数与成员数的容量。

## 3. 修复

### <a id="f1"></a>F1 带 Entity Sync 的 Nest Mod 不再静默丢掉业务的第二个观察者

Nest 只有一个 `EntitySync` 观察者位置。`wiring/nest.NewModWithEntitySync` 的 `Provide` 把自己的 Manager 追加在业务选项之后，业务给的观察者被覆盖，periodic 模式下毫无报错。现在返回 `ErrEntitySyncObserverConflict`（回归 `TestEntitySyncModRefusesASecondEntitySyncObserver`）。
