# v1.46.0：生成工程只带用到的服务，组合 skill 可以直接装进自己的项目

本版的重点有两项：

- 生成工程不再一次托管九个框架服务，而是装模块时用到哪个才声明哪个。
- 组合 skill（roost-genre）有了独立的入口：在自己的项目里放一份入口文件，运行时从 GitHub 取指定的发布版。生成的工程也带上这份入口，之后的需求自动走 skill。

逐条变更、决策出处与证据见 [CHANGELOG](../../CHANGELOG.md) v1.46.0 段，组合流程见 [compose](../agent-skills/roost-genre/references/compose.md)。

**不兼容旧版。** 线上尚未部署（维护者 2026-10-06 起的口径）。本版的改动只对新生成的工程生效，已生成的工程不迁移。

## 主要内容

- **`-template game` 缺省只有业务服务 game**：带 Nest、Player 与 World，不托管任何框架服务，`uses` 为空。
  - **新参数 `roost project new -framework all | <名字,名字>`**：一开始就托管全部九个，或指定几个。写进了 `roost help project` 与 `roost help services`。
  - **装模块时自动补上用到的托管服务**：模块 `needs.uses` 与 `runtime.framework` 用到、工程里还没有的托管服务，`roost module add` 在同一个安装事务里完成以下几件事，安装失败时与 `roost.yaml` 一起撤销：
    - 声明这个服务，并把它加进业务服务的 `uses`；
    - 给业务服务的配置补上需要的段；
    - 生成新服务的配置、部署与协作者文件；
    - 分配端口块。
  - **`module plan` 先列出会新增的托管服务**：文本输出 `framework service <名字>: will declare`，JSON 字段 `framework_services`。同名的已经是业务服务时报错。
  - **配方**：casual 只带 account、mail；turn-pvp 只带 account、match、rank。
  - **game-demo**：仍托管全部九个，生成物与上一版相比只有一段说明文字不同。
  - **`project doctor`**：新的 `-template game` 工程退出 0，不再有四项 collaborators FAIL。
- **portal 的安装提示**：不再写死 `127.0.0.1:8081`。account 的端口块按托管服务声明的先后分配，看 `services.account.port_block`。
- **组合 skill 的入口 `claude-skill/roost-genre/`**（仓库根目录）：
  - 复制进自己项目的 `.claude/skills/` 即可使用。
  - 运行时 `go mod download` 指定版本的 roost-core，读其中的 skill 正文，再 `go install` 同版本的 CLI，不需要本地检出。
  - 每次使用先检查入口文件与 roost-core 发布版有没有更新；更新入口或升级 core 都先问用户。
  - 安装说明见 `claude-skill/README.md`。
- **组合 skill 正文**：
  - **第 0D 步，实时战斗先分档**：
    - 回合 / 异步、MMO 级服务器权威实时战斗、帧同步对战都支持；
    - 动作 / 射击级不支持，大规模同屏状态同步暂缓，都作为冲突提出；
    - 写明 `combat` 模块只是双人 PvP，多人战斗与打怪按 MMORPG 参考手写。
  - **第 5A 步，生成的工程带接手说明**：工程根目录放 `AGENTS.md`（骨架在正文里）、只有一行 `@AGENTS.md` 的 `CLAUDE.md`，以及入口 skill 的副本。之后在这个工程里提的需求先走 skill。
  - **§4D 多个实体共用一份逻辑**：做共用组件，照 activity 模块的宿主接口写法。状态各存在各自实体的 DAO 里，每个实体只写薄接线。
  - **§4E 进程内的全局逻辑**：
    - 能重建、不进事务的缓存、索引、注册表用 manager；
    - 要和玩家修改一起提交回滚的全服状态挂在 World 上，不另建单例实体；
    - 写明启动顺序：manager 先启动，World 在 `Service.Init` 里建出，实体没有启动顺序。

## 升级步骤

1. core 与生成器同时升级到 v1.46.0，重新生成工程。生成器清单里的最低 core 版本，在本版 tag 推上去之后的下一笔提交才抬到 v1.46.0。
2. 新的 `-template game` 工程如果手写代码要直接调某个托管服务（没有对应的模块），建工程时加 `-framework <名字>`。已有工程按 `roost help services` 手动声明。
3. 依赖“`-template game` 一定有 chat / rank / mail”的脚本或文档，改成装对应的模块，或者加 `-framework`。
4. 用组合 skill 的项目，按 `claude-skill/README.md` 放入口文件；skill 正文不要复制进项目。

## 验证

发版前在本机（macOS）跑过：

- 全仓 `go test -count=1 -timeout 60m ./...`。改动后的提交上，`codegen/internal/roost` 里有两条失败：
  - 一条依赖旧缺省，改用 `-framework all` 后单独通过；
  - 另一条是 game-demo 主视野超限场景，当时同机并行着模块门禁与 17 个纵切脚本。单独重跑通过，在 demo 工程里 `-count=5` 也通过，根因未定位，已作为“尚未确认”写进 KNOWN-LIMITS。
  - 发版脚本的 pretag 会再跑一遍全仓。
- `scripts/test-modules-generated.sh`：新 `-template game` 工程上 doctor 期望 0 个 FAIL，并核对 chat / mail / rank / account 由安装声明。
- 新生成的 game-demo：build / vet / `roost id check` / `roost generate --check`、`go test ./...` 62 个包、`roost module verify` 40 条模块。
- `scripts/test-mmorpg-scenes.sh` 与 16 个 `test-*-generated.sh`、`codegen/scripts/source-head-check.sh full`。
- 手工核对：
  - 新 `-template game` 工程只有 game，doctor 退出 0；
  - `module add portal enter profile naming checkin task leaderboard mailbox chat` 自动声明 account / chat / mail / rank，`module verify` 全部通过，`project sync` 无漂移。
- 先红后绿：改动前的检出上，三条新行为测试全红（模板声明十个服务；`-framework` 未定义；装 leaderboard 被拒，提示手改 `roost.yaml`）。安装器另做了三处变异自检。
- 文档锚点无断链。
