## 1. 升级

1. `go get github.com/tjbdwanghaibo/roost-core@v1.32.0`，用 v1.32.0 的生成器重新生成（`make generate` 或 `roost generate`）。`roost.yaml` 里 `versions.core` 写了低于 v1.32.0 的明确版本时，manifest 校验会拒绝，改成 `v1.32.0` 或 `latest`。
2. **重新生成 DAO 报错时**按 [B1](#b1) 改定义：报错形如 `parse definitions: dao PlayerDao field Deep (map[int32]map[int32]int64): the map's values are maps …; use []byte, a slice of a basic type, a basic type, or a pointer to a nested struct (*T, []*T, map[K]*T); …`。改形状就是改存储形状：已有数据要按 [schema 变更操作手册](../framework/SCHEMA-MIGRATION.md) 处理（线上未部署，不做兼容）。仓内全部 DAO 定义与下游迁移工程的定义都不受影响（[验收 V4](v1.32.0-VALIDATION.md#v4)）。
3. 其余新能力都是新增：不写新标记的路由生成物逐字不变；`[]byte` 字段只多出 `Get<Field>All()`；map 切片值的副本修复不改签名。业务代码不需要改。

## 2. 行为收紧

### <a id="b1"></a>B1 DAO 引用形状生成期拒绝（行为收紧：这些形状重新生成时报错）

**原来的问题**：生成的取值方法只给 `[]byte` 的 `Get<Field>All()` 与 map 的 `[]<基本类型>` 值收发副本（[R1](#r1)、[F1](#f1)）。其余引用形状照常生成、不复制：`Get` / `Range` 交出 DAO 内部的值，`Set` / `Add` 原样存下调用方的值。调用方改它就绕过 setter 改了 DAO——没有脏标记、不进 WAL 与同步、回滚覆盖不到，内存与已提交记录 / 持久文档从此不一致。`*int64` 这类字段的 `Get` 交出内部指针，`Set` 比较的是指针而不是值。

**维护者决定 A（2026-10-30）**：在解析阶段拒绝，规则声明一次、不增加生成代码。选项 B（逐形状生成深拷贝）代价是模板分支与每次读的分配随嵌套层数增长；C（只在文档里写“不要修改”）没有强制点。

**现在被拒的形状**（DAO 与嵌套 struct 相同）：

| 被拒形状 | 例 | 改法举例 |
| --- | --- | --- |
| map 的值是 map | `map[K]map[K2]V` | 合成复合键的 `map[K]V`，或 `map[K]*T`（`T` 里放内层 map） |
| map 的值是指向非嵌套类型的指针 | `map[K]*int64` | `map[K]int64` |
| map 的值是元素仍为引用的 slice | `map[K][][]byte`、`map[K][]*T` | `map[K][]byte`（整段编码）或 `map[K]*T` |
| slice 字段的元素是引用 | `[][]byte`、`[]map[K]V`、`[]*int64` | `[]byte`、`[]<基本类型>` 或 `[]*T` |
| 基本类型 / 非嵌套类型的指针字段 | `*int64`、`*Rank`（`type Rank int64`） | `int64` |

**仍然允许**：基本类型；嵌套 struct 与嵌套类型指针（`*T`、`[]*T`、`map[K]*T`，改动经嵌套类型自己的 setter 标脏）；`[]byte`、`[]<基本类型>`；`map[K]<基本类型>`、`map[K][]<基本类型>`（收发副本）。`roost add saga -native` 加的 `SagaReceipts map[string][]byte` 属于允许形状。

**剩余限制**（写在 [KNOWN-LIMITS](../maintenance/KNOWN-LIMITS.md#生成器配置与工具)）：判定按定义里写出的语法，底层是 slice / map 的命名类型（`type Tags []string` 再写 `map[K]Tags`）认不出；非指针嵌套 struct 值（`T`、`[]T`、`map[K]T`）不在这条规则范围；`//roost:redisdao` 整值读写、没有字段 setter，不查。

## 3. 新能力与修复

### <a id="r1"></a>R1 DAO：字节切片字段的整体读取 `Get<Field>All()`

下游把整段 JSON 存在 `ResultJSON` / `RequestJSON` 这类 `[]byte` 字段里，原来只有按下标的 `Get<Field>(idx)` 与 `Range<Field>`，无法整段 `json.Unmarshal`。现在 `[]byte` / `[]uint8` 字段（DAO 与嵌套 struct）多一个 `Get<Field>All() []byte`，与整体写入 `Set<Field>All`（嵌套 struct 里是 `Set<Field>`）对称；返回**副本**，改返回值不改 DAO，空值读 nil。已发布的 slice 方法不变；持久文档、提交记录、同步载荷里仍是 BSON binary（子类型 0），存储与 sync 格式不变，cube 迁移数据照常读。用法见[命令与标记参考 §4](../../codegen/docs/CODEGEN_REFERENCE.zh-CN.md#生成物与读写约定)。

### <a id="r2"></a>R2 webroute：`headers=`、`compress=gzip`、`RawRequest.Query`、`errors=`、`status=`

对齐下游 cube fork 的能力，让迁移工程**用新标记保持旧客户端契约**（不用手写路由）：

- **`headers=Header-Name:Field,...`**（只用于 `body=json`）：JSON 解码之后生成 `request.Field = r.Header.Get("Header-Name")`。头名生成期规范化、不区分大小写；请求头优先于 JSON 体的同名字段，头缺失为空串，多值取第一个；字段须是 string，类型不对在生成文件的赋值行编译失败；坏写法（缺冒号、非法头名、重复、`body=raw`）生成期拒绝。
- **`compress=gzip`**：成功响应按 `Accept-Encoding` 协商（`gzip` / `x-gzip` 看自身 `q`，未列出看 `*`，`q=0` 拒绝），编码后不少于 1 KiB（`webroute.CompressMinBytes`）才压缩；不接受 gzip 的客户端照常拿明文；错误响应不压缩；全部带 `Vary: Accept-Encoding`。
- **`RawRequest.Query`**：`body=raw` 路由拿到查询参数的独立副本（`url.Values`，同名多值保留）。
- **`errors=<mapper>`**：错误响应改用路由包里声明的 `webroute.ErrorMapper`（迁移工程自带的 StatusError 映射），只认本包标识符，别的包的映射在路由包里写一行 `var x = pkg.Mapper` 引用。
- **`status=<2xx>|response`**：固定成功状态，或由响应的 `HTTPSuccessStatus() int` 决定（只认 200～299，否则 200；只在没有错误时调用）——例如排队中回 202。

不写新选项的路由生成物逐字不变、行为不变（响应类型即使有 `HTTPSuccessStatus` 方法，不写 `status=response` 也不看）。语法与语义见[命令与标记参考 §11](../../codegen/docs/CODEGEN_REFERENCE.zh-CN.md#11-webroute)。

### <a id="f1"></a>F1 DAO：map 的切片值收发副本（修复）

map 值是元素为基本类型的切片（`map[K][]byte` 等）时，修前生成的 `Get<Field>(key)` / `Range<Field>` 原样交出内部切片、`Set<Field>(key, val)` 原样存下调用方的切片，调用方改它就绕过脏标记改了 DAO（与 [B1](#b1) 同一类问题）。`roost add saga -native` 生成的回执字段 `SagaReceipts map[string][]byte` 就是这种形状（框架经 `saga.StepReceipts` 只读；业务直接调用生成的 `GetSagaReceipts` / `RangeSagaReceipts` 时不受保护）。现在 DAO 与嵌套 struct 的这类值 `Get` / `Range` 交副本、`Set` 存副本，nil 与空切片的区别保留；签名、存储与 sync 格式不变，重新生成即可。代价是每次读 / 遍历一个值多一次分配。

### <a id="k1"></a>K1 KNOWN-LIMITS 观察登记：嵌套类型 nil map 往返后 `null → {}`

修 F1 时观察到：嵌套 struct 的 map 字段为 nil 时持久化存成 `null`，读回后再存一次变成 `{}`。语义上都是空 map、读取结果相同；影响限于文档形状不稳定（一次往返多一次无实际变化的写、按 `null` 查询的外部脚本查不到）。DAO 顶层 map 是否同样如此、是否有别的读者依赖 `null` 尚未核对，标“尚未确认是否需要处理”，代码未改。

### <a id="v1"></a>V1 版本号与生成物最低 core

- 生成物最低 core 从 v1.31.0 升到 **v1.32.0**：`//roost:web` 写了 `compress=gzip`（含与 `errors=` 同用）或 `status=response` 的路由调用只在 v1.32.0 才有的 `webroute.WriteCompressedResult` / `WriteCompressedResultWithMapper` / `SuccessStatus`（经 `httpserver.JSONCompressed`），钉 v1.31.x 时编译失败。生成的 `go.mod`、`roost.yaml` 版本下限校验与 help 文本都读同一个下限；`framework-compat` 的 minimum lane 同步。
- `upgrade-compat` 的 previous-project 矩阵加 v1.31.2（上一版，生成器与 v1.31.0 相同）。
