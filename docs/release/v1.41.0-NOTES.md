# v1.41.0：联盟服务、effect 持久性与 Remote 发布归属

本版是 v1.40.1 之后的功能版。逐条变更、决策出处与前后数字见 [CHANGELOG](../../CHANGELOG.md) 的 v1.41.0 段；这里只列升级要做的事、会感觉到的行为变化和验证边界。

## 行为变化

**Remote 实体**

- outbox 发布归属：事务记录带写者 sid（`writer_sid`）。本进程写的提交立即发布，别的进程写的提交在写入后超过 `remote_entity.outbox_takeover_grace` 才代发。该项零值与下限都取 `finalize_projection_timeout`，缺省 30 s，小于下限时 Init 报错。写者崩溃后，它留下的提交要晚一个宽限期才被发布；同 sid 重启的进程会立即发布。宽限期按写者时钟比较，所以**各进程要用 NTP / chrony 校时，偏差在 1 s 以内**（[REMOTE_ENTITY“outbox 发布归属”](../framework/REMOTE_ENTITY.md#outbox-发布归属)）。
- outbox 后台发布循环：一页里只剩慢发布时，转到后台继续，不再挡住之后的全部提交。快照 publish 分片改为按整个实体 ID 打散，同一 kind 不再挤在一把锁上（[outbox 发布并发](../framework/REMOTE_ENTITY.md#outbox-发布并发)）。
- `//roost:entity remote=managed snapshots=none`：没有读方的托管 kind 不写、也不发布快照。`//roost:mirror` 指向这种 kind 时，生成阶段拒绝。

**Nest / DataEngine**

- effect 新增两个维度：持久性 `reliable`（缺省）/ `best_effort`，消费顺序 `entity`（缺省）/ `none`。
  - `best_effort` 不写 WAL、outbox 和 inbox，在持久点之后经 core NATS 发出。
  - 带 best_effort effect 的 async 事务会升为 strict。提交器不支持时返回 `nest.ErrBestEffortPublisherRequired`。
- effect 消费者在一个进程内按实体并发（`dataengine.effect_consumer.workers`，缺省 16）：同一 Key 仍按到达顺序，不同实体之间的先后不再保持。
- 带 effect 的记录缺省按实体有序投影；全局 WAL 顺序改为可选，配置 `dataengine.projection.effect_order: wal`。
- 并发缺省值调整：

  | 配置 | 新缺省 |
  | --- | --- |
  | `nest.io.workers`（写 0 时） | max(256, 4×短池) |
  | `dataengine.projection.workers` | 32 |
  | `remote_entity.outbox_publish_workers` | 32 |
  | `dataengine.outbox.workers` | 8 |

  配置里写了旧值的（例如 `workers: 2`）照旧按旧值运行。

**客户端运行库**

- C# 与 C++ 的鉴权首包带连接代号。跨 Gate 放弃握手后，旧 Bind 迟到完成，不再断开新连接。
- C# 票据上限由 8192 改为 8182 字节。
- 同一会话的两次握手只要有一次没带代号（旧 DLL、旧插件、自建客户端），仍按后完成者胜出。

**game-demo**

- 公会迁到 alliance 服务。
- 联盟逻辑全部不用 effect：
  - 成员通知由服务层直接发；
  - 预约期限放在进程内，丢了由下一个请求自愈；
  - 跨实例宣战改为持久的待确认标记加直接确认。
- `AllianceShard` 已删除。`PlayerDao.GuildID` 改为持久，登录时副本为 0 会查询一次守卫。

## 升级步骤

1. core 与生成器同时升级到 v1.41.0，然后重新生成工程，审查 diff 和 WARN。
2. 改 Interest 代码：`InterestConfig.BandLayer` 的签名改为 `func(level, band int) entity.SyncProfile`，`DefaultBandProfile(band)` 改为 `DefaultBandProfile(level, band)`。原来只看档的映射，加一个忽略的参数即可，不保留旧签名。
3. Remote 存储不用清库。旧的 `_remote_entity_transactions` 记录没有 `writer_sid`，按写者未知处理，立即发布，与修前相同。宽限期如需调整，配置 `remote_entity.outbox_takeover_grace`，不能小于 `finalize_projection_timeout`。
4. 用 effect 的业务：已有 effect 文件再加消费者时，要求存在 `Delivery<Topic>` 常量（`roost add effect -delivery -order` 会生成）。要用 best_effort，提交器必须实现 `BestEffortEffectPublisher`。
5. 基于 game-demo 的工程（未部署，不做迁移）：
   - 先停旧进程再起新进程；
   - JetStream durable `alliance-member-changed`、`alliance-reservation-due`、`alliance-war-declared` 和 `alliance_shard` 集合不再使用，可以删除；
   - 旧数据里在途的跨实例宣战不会补发确认，清空后再起服。
6. Unity 工程重新执行 `scripts/client/build-unity.py` 打包，新插件和 DLL 才会带上连接代号。自建接入服务如果直接把首包载荷当票据用，要先拆信封（Go `wire.DecodeAuth`，C# `AuthPayload.Decode`）。

## 验证与性能边界

发版前，在 main 上跑了以下验证：

- 全仓 build / vet / test，以及 nest、dataengine、remoteentity、entity、client、gateway 等包的 `-race`；
- 真实隔离 Mongo / NATS / Redis 下的 DataEngine 与 Remote 集成测试，含 outbox 代发的真实进程演练；
- game-demo、Remote 生成工程，联盟真实进程端到端 7 条（含进程被杀后接管、缩容，以及离线入会后登录的机器人场景）；
- 13 类玩法生成工程、Sync 双模式，C# / C++ 客户端测试（含跨 Gate 的 C# 端到端）。

本机同机前后对照（macOS 单机三成员副本集，机器高负载，数字只看方向）：

- 两实例 64 并发跨实例 `Join`：18～41 → 155～168 次/秒，失败与写门超时降到 0。
- 单实例 128 并发 `Join`：约 400 次/秒，被 Mongo 封顶，**没有达到 1000 次/秒的目标**。

仍未处理的项，详见 [KNOWN-LIMITS](../maintenance/KNOWN-LIMITS.md)：

- 单实例高并发下偶发的“全体同时约 3 s 超时”：发布侧的两处原因已修，剩下的停顿在 I/O 侧（Mongo 多数派写、WAL fsync、checkpoint 落盘），尚未处理。
- Remote 托管实体上的只读 handler 也会取写许可，每次多一次 Mongo 写。
- 写者崩溃后，要等别的进程再写一次才会触发接管。
- C++ 没有跨 Gate 端到端；Unity Editor / Player 与 Unreal 未实跑。

以上不代表 Linux、跨机、生产 Mongo 或长稳下的表现。发布不等于部署；维护者的最终压测在发版之后进行。
