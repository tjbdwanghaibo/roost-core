# 第一次认识和使用 Roost

这份文档适合第一次接触 Roost 的开发者。你不需要先理解分布式事务、WAL 或所有 Go 类型。先知道一条游戏请求如何完成，再按需要阅读模块文档。

这里的“入门”不替代 Go 语言基础：至少需要能阅读结构体、接口、函数、错误返回和 goroutine。运行时基线是 **v1.24.0**，**v1.24.1** 主要整理文档。正式支持范围是 macOS 和 Linux。

## 1. Roost 帮你解决什么

假设你的游戏有一个玩家，拥有 100 金币。玩家购买一件价格为 20 的道具，服务器需要做三件事：确认这次修改不会和其他请求冲突；把 80 金币和新道具可靠地保存；让客户端看到新背包。

Roost 把这三件事分别交给三个核心模块：

| 模块 | 用普通话解释 | 在购买道具中的作用 |
| --- | --- | --- |
| Nest | 安排哪些业务可以执行，并保护正在修改的对象 | 避免购买和其他请求同时乱改同一个玩家 |
| DataEngine | 保存修改，处理进程重启后的恢复 | 保存金币和背包这一次修改 |
| Sync | 把允许公开的状态变化发送给接收者 | 告诉客户端金币变成 80，并更新背包 |

这是理解框架的起点。业务仍由你编写：价格是否正确、道具是否可以买、背包满了怎么办，都不是框架自动决定的。

## 2. 先认识几个名字

| 名词 | 含义 | 容易误解的地方 |
| --- | --- | --- |
| Entity（实体） | 一个需要被管理的游戏对象，例如玩家或公会 | 不表示所有游戏数据都必须是实体 |
| Component（组件） | 组织实体某一部分行为，例如背包操作 | 需要事务回滚的数据应放在 DAO，而非另存一份组件字段 |
| DAO（数据对象） | 表达需要保存的数据，生成代码帮助记录修改 | 不应绕过生成的 setter 随意修改持久字段 |
| handler（处理函数） | 处理一条消息的业务函数 | 不要在快池 handler 内等待数据库或另一个同步请求 |
| 事务 | 把一次业务修改作为一个整体处理 | 不自动包含任意 HTTP 请求或外部系统副作用 |
| 回滚 | 失败时撤销本次事务负责的修改 | 只有选定策略和回滚范围内的状态会恢复 |
| WAL（预写日志） | 先记录修改，之后再写入数据库，便于恢复 | 日志确认不等于数据库或客户端已经更新 |
| fsync | 请求操作系统把相关文件数据同步到存储设备 | 具体耐久性仍依赖设备和部署环境 |
| 投影 | 把已记录的修改应用到 Mongo 等正式存储 | 此处不是图形学中的相机投影 |
| 幂等 | 同一业务请求重复到达时，不重复产生效果 | 一般依赖稳定请求 ID 和业务设计，不能只靠传输层 |
| 结果未知 | 请求可能已经生效，但当前没有拿到确定答复 | 不能直接再扣一次金币 |
| fence | 拦住后续不安全写入，等待恢复或处理 | 不是普通业务“条件不满足”错误 |
| Mod | 把一个能力接入进程的装配模块 | 例如建立数据库连接、注册接口、负责关闭 |
| Registry | 当前 App 中可用能力的登记表 | 不是另一个进程的全局变量 |
| profile | 某类接收者允许看到的数据视图 | 不是“把整个服务端对象发给客户端” |
| Host | 技能运行器访问游戏世界的接口，例如查目标、扣资源 | 示例Host不等于你的生产世界实现 |
| outbox | 与业务结果一起持久记录的待发送消息 | 写进outbox不表示接收者已经处理 |
| TTL | 一份记录或缓存允许保留的时间 | 刷新、续期及清理时机还要看具体模块 |
| TPS | 每秒完成的事务数 | 与每秒普通消息数不是同一种指标 |
| P99 | 一组样本中约99%的延迟不超过的值 | 不表示最大延迟，也不代表剩余1%合格 |
| HA / 长稳 | 故障切换能力 / 长时间持续运行验证 | 单机测试不能代替跨机器故障验收 |
| epoch / 基线 | 一轮状态同步的身份 / 增量应用的起点 | 断线或缺包后不能在错误基线上继续叠加 |

遇到不认识的词，先回到这张表。实现文档中的类型名主要用于找到源码，不需要一开始全部记住。

## 3. 购买请求怎样走完

1. **收到请求。** 接入层确认连接身份并解码请求。玩家身份来自认证结果，不能直接相信请求体中的玩家编号。
2. **交给 Nest。** 通过正式生成的调用入口，把请求交给负责调度的模块。
3. **执行游戏规则。** handler 在受保护的实体上检查金币和背包，再通过 DAO 修改数据。
4. **按约定保存。** 框架根据持久策略记录修改。明确失败和“结果未知”是两种情况，处理方式不同。
5. **回复并同步。** 达到对应确认边界后，向调用方回复；Sync 按可见范围发送状态。回复、数据库落库和客户端应用不一定在同一时刻完成。

这是流程说明，不是可直接复制的代码。真实工程的 DAO、handler 参数和生成命令由业务定义决定，接入时使用项目生成器提供的结构。

### “购买成功”到底保证了什么

使用 `strict` 持久策略时，成功说明对应 WAL 已完成所需同步，**不表示 Mongo 已投影完成，也不表示客户端已收到**。如果后续操作必须读到数据库中的新值，应使用明确的投影等待能力。不要用一个固定的 `sleep` 来猜测保存是否完成。

如果请求超时，不能立刻换一个请求 ID 再购买一次：第一次可能已经成功。业务要保留请求身份，并按相应服务的查询/幂等协议确认。

## 4. 先跑一个不需要数据库的示例

以下命令用于 macOS/Linux。安装 Git 和 Go 1.27.x，确认 `go version` 的输出符合要求。首次执行可能需要下载 Go 依赖。

```sh
git clone --branch v1.24.1 https://github.com/tjbdwanghaibo/roost-core.git
cd roost-core/examples/configgen
GOWORK=off go run .
```

这个示例演示配置表的加载、类型化读取和热更，不需要预先启动 Mongo、Redis 或 NATS。它把示例数据复制到临时目录，不会覆盖仓库原始数据。正常运行会先打印wolf，故意提交一次错误引用并拒绝它，最后成功更新为dire wolf，然后退出。因此中间出现一次“config reload failed”警告是示例在验证错误保护，不表示整个示例失败。你应看到类似结果：

```text
monster#1=wolf ...
dangling ref rejected: ...
current snapshot still version=1
reloaded: monster#1=dire wolf version=3 ...
```

如果出现找不到 Go 命令，先检查 Go 安装；如果是下载失败，检查网络和模块源；如果找不到配置文件，检查当前目录是否为 `examples/configgen`。不要为了让示例运行而删除数据库或修改框架业务逻辑。

源码入口：[configgen 示例](../examples/configgen/main.go)。另一个不依赖外部服务器的游戏示例是 [技能火球](../skill/examples/fireball/main.go)。

## 5. 准备建立自己的游戏工程

先阅读 [Codegen 的设计与使用](framework/guide/12-codegen.md)，再按 [项目生成器手册](../codegen/docs/PROJECT_GENERATOR.zh-CN.md) 创建工程。建议先完成一条最小链路：连接认证 → 一个只读请求 → 一个受事务保护的修改 → 客户端看到状态。

`game-demo` 是完整工程模板；运行其中的服务需要按模板配置外部资源。不要把上一节“不需要数据库的单个示例”理解为整个游戏服都没有资源依赖。

生成工程后，优先修改手写业务定义，再重新生成。带有 `Code generated` 标记的文件通常不是业务修改入口。版本号要固定并记录，避免同一项目的开发机悄悄使用不同生成器。

## 7. 阅读实现文档的方法

先看“必须保持的契约”和流程说明，带着一个具体问题再展开源码或测试目录。例如想知道持久字段写入为什么被拒绝，就查 DataEngine/Nest 对应的实现入口，而不是从所有测试文件的第一行开始读。

源码表回答“在哪里”，测试表回答“有哪些现成回归入口”。是否已运行、在哪个平台运行、还有哪些限制，则看 [本版验收记录](release/v1.24.1-IMPLEMENTATION.md) 和 [已知边界](maintenance/KNOWN-LIMITS.md)。不能把一张很长的表理解成全部能力已验证。
