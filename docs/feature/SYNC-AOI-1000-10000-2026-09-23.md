# 1000 玩家 / 10000 实体 / 每人约 50 可见的 AOI 验证

后续 A～E 优化的同模型 A/B 与真实异步队列结果见[实施记录第 10 节](REFACTOR-2026-09-23-sync-next-steps.md#10-实施与验收记录)。下文保留优化前的需求和负载基线。

用户明确的目标：1000 名玩家，场景共 10000 个实体，通过 Interest/AOI 决定可见性，每人约 50 个可见实体，延迟要求 50ms。这里将 10000 理解为包括 1000 个玩家在内的总数，其余 9000 个为只被观察的实体。

用户进一步明确：40Hz 过高，采用 20Hz 或按实体变化发送，实体变化频率应更低。本轮据此以 **20Hz、每 tick 1% / 5% 变化**复测，工具默认改为 1%；这两个变化比例是测试假设，尚非真实业务采样。初次 10% 与全活跃结果保留作压力对照，40Hz 仅保留历史记录，不作为推荐配置。50ms 暂按最大延迟严格检查，同时记录 p50/p95/p99 和超标数量。

## 20Hz 与按变化发送的关系

当前实现已经结合了两者：`Register` 安装脏状态通知，实体变化进入 pending 集合；`Flush` 只处理待同步实体，pending 为空直接返回。稳定订阅的实体不脏就不生成 update；新订阅快照、离开视野 remove、失败重试仍需发送。调用方必须通过同步状态的 `MarkDirty` 或相应业务入口标记变化，框架不会自动比较任意内存字段。

`Manager.Start` 使用定时器调用 Flush，配置 Interval=50ms 即 20Hz；没有变化时不会发空帧，也不重新打包。它目前**不会在 MarkDirty 时立即发送**。负载工具同样按 50ms 合并 Flush；本轮不改变生产调度机制。

在当前均匀轮转模型中，1% 表示每 tick 100 个实体变化，全场 2000 次/秒，单实体平均约 5 秒一次；5% 表示每 tick 500 个，全场 10000 次/秒，单实体平均约 1 秒一次。每次变化同时移动并触发 AOI 评估，尚未拆分低频属性与高频移动。

## 模型与边界

- **一个全局实体集合、真实 Interest**：1000 个观察者走 Enter/Move，9000 个主体走 Show/MoveShown，Apply 生成订阅变更。没有 Group、Room、全量广播，也没有手工为每人塞 50 条 Manager.Subscribe。
- 地图使用间距 30 的空间分布，进入/离开半径 150/180，BlockSize=150。AOI MaxVisible=49，加 self 关系最多 50 个；边缘密度较低，报告实际分布。容量仍使用框架默认 MaxObjects=100。
- 活跃实体按互质步长遍历，分散在地图上，玩家与其他实体都能移动；位置往返运动产生真实进入/离开和引用回收。客户端逐帧验证 ObjectRef、会话时钟和主体版本链，最终集合与 Interest.Visible+self 完整比较。
- **两个独立进程**：服务端维护 10000 个 SubjectSyncState、Interest、打包和 TCP 写入；客户端进程维护 1000 条连接、解码和校验。各进程 GOMAXPROCS=4，分别记录分配与 GC；仍在同一台机器上争用 CPU、内核和网络栈，尚非分机生产容量测试。
- 这是按目标规模建模的 **Sync/AOI 模块负载**。组件用 BSON 表示位置、生命值和时间标记，附加 64 字节代表性字段，当前组件编码约 181 字节。尚未获得真实业务 schema，不以它代表所有游戏字段。
- 不经过 Nest、持久化提交、认证或生产接入层；TCP 外层为测试信封，内层为真实 Sync 帧。没有绕过 Sync 的内容捕获、编码或 Interest 订阅。服务端按计划调用 Flush，未使用 Manager.Start 定时循环。

## 50ms 的测量方式

每 tick 的更新分为 10 批，均匀分布在两次 Flush 之间；不会在 Flush 前才把所有状态改掉。

- `state_change_to_client_ms`：实际改变组件状态 → 客户端完成 BSON 解码和字段校验，包含等待下一次 Flush。
- `planned_event_to_client_ms`：输入计划发生时刻 → 客户端完成校验，额外包含服务端积压造成的处理迟到。绝对计划不丢 tick，不用延迟执行的输入掩盖过载。
- `scheduled_flush_to_client_ms`：计划 Flush 时刻 → 客户端完成一帧校验，帮助分离等待周期和交付开销。
- `server_active_work_ms`：状态变更、AOI 移动/Apply 和 Flush 的主动工作耗时，不计主动等待；`flush_start_lag_ms` 单独记录 Flush 迟到。
- 只将本 tick 实际改变的主体纳入变更延迟。进入视野时收到的旧状态快照不冒充新变更；所有帧、快照、remove 仍然做完整性校验。

20Hz 的周期就是 50ms，因此刚错过上一 tick 的变更，仅等待就接近 50ms，还未计入编码和传输。这个频率不能天然保证所有端到端延迟小于 50ms。

## 运行

```bash
# 默认：1000 / 10000 / 50可见，20Hz、1%变化，200 tick，三轮。
./scripts/perf/sync-aoi.sh

# 显式参数，结果目录不允许覆盖。
ROOST_PERF_LABEL=aoi-target ROOST_PERF_COUNT=3 ./scripts/perf/sync-aoi.sh \
  -players=1000 -entities=10000 -visible=50 -hz=20 -dirty=1 -ticks=200

# 保持 20Hz，增加到每 tick 5% 变化。
ROOST_PERF_LABEL=aoi-active ROOST_PERF_COUNT=3 ./scripts/perf/sync-aoi.sh \
  -hz=20 -dirty=5 -ticks=200

# 使用真实 AsyncTransport 队列和工作协程；客户端仍为独立 TCP 进程。
ROOST_PERF_LABEL=aoi-async ROOST_PERF_COUNT=3 ./scripts/perf/sync-aoi.sh \
  -async -hz=20 -dirty=1 -ticks=200

# 全活跃压力上界；应先短测，积压不会被丢弃。
ROOST_PERF_LABEL=aoi-busy ROOST_PERF_COUNT=3 ./scripts/perf/sync-aoi.sh \
  -hz=20 -dirty=100 -ticks=40
```

结果保存在 `artifacts/perf/sync/<label>/`，包括二进制、环境/工作树信息和每轮日志；每轮 `config.json`、`server.json`、`client.json` 分别保存模型、服务端和客户端数据。任何丢会话、收发数量不符、版本/字段/可见集合错误，以及任一延迟超过 50ms，都会非零退出，保留所有失败结果。

客户端与服务端使用同机时钟；以后移到不同机器时，需要单独处理时钟同步/单向延迟误差。1000 连接需要足够的文件描述符，本机 soft limit 为 1048575；没有修改系统限制。

## 实测

### 按最新要求补测的低变化率

保持同样的 1000 玩家、10000 实体、Interest/AOI 和 TCP 校验，两档分别串行重复三轮，每轮 200 tick（计划 10 秒），不与 profile 或测试并发运行。以下分位数范围仍按每轮分别计算：

| 每 tick 变化比例 | 主动工作 p95 | Flush p95 | 实际变更延迟 p95 | 实际变更超过 50ms 的比例 | Sync 字节/秒 | 服务端分配/秒 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1% | 15.09–15.92ms | 8.32–9.13ms | 48.57–48.89ms | 1.56%–2.29% | 3.54 MB | 51.15–51.16 MB |
| 5% | 22.97–29.51ms | 10.82–14.79ms | 48.02–48.49ms | 1.06%–2.58% | 17.76 MB | 215.55–215.77 MB |

1% 每轮 108139 个变更交付样本，最终平均可见 49.586、总订阅 49586，create/remove 为 19738/19294；5% 每轮 554727 个样本，平均可见 49.647、总订阅 49647，create/remove 为 135307/134925。六轮收发帧/字节、版本链、字段和最终可见集合校验全部通过，会话均为 1000、丢失为 0。

负载下降后，1% 的所有主动工作 tick 都在 50ms 内，5% 的三轮分别有 1/0/0 个主动工作 tick 超过 50ms。**处理开销已有明显余量，但端到端 50ms 最大延迟仍未通过**，p99 也仍略超目标；不能用单 tick 工作耗时替代端到端延迟。计划输入超期比例分别为 14.30%–16.37% 和 16.66%–18.30%，保留绝对时间轴上的等待与迟到。

下一步方向是保持 20Hz 合并脏数据，并确认实际延迟分位数；若必须严格小于 50ms，则单独设计变化触发的发送调度，给编码和传输留出预算。变化触发应合并同一实体的连续修改，避免每次字段修改立即写网；同时明确是否允许短时发送超过 20Hz。若连续变化下仍硬限制每次发送至少间隔 50ms，就依然没有严格 50ms 端到端保证。本轮没有实现事件触发调度，也未把调度建议写成已完成的优化。

### 历史压力对照

20Hz/10% 每轮约 109 万个变更交付样本，1.95%～3.07% 的实际变更延迟超过 50ms；40Hz/5% 每轮约 111 万个样本，实际变更超标率为 0%、0.153%、0.448%。分位数按每一轮分别计算，不混成总体分位数。

历史 40Hz 的常见交付延迟满足 **p99 < 50ms**，但这不等于满足用户尚未指定分位数的“50ms 延迟”要求；按最大值严格门禁不能宣布达标，且用户已明确不采用该频率。计划输入延迟揭示了执行迟到和积压，不能只展示实际变更后的短延迟。

100% dirty 的 40 tick 本来只应占 2 秒，实际三轮都接近 9 秒，实际变更超标率约 93%，属于持续过载。没有丢 tick 或减轻工作量来维持表面的 20Hz。

### AOI 与完整性

- 所有档位最终每玩家平均可见 **49.59～49.73** 个，最大 50；总订阅约 **49586～49732**，并非 1000×10000 广播。
- 20Hz/10% 每轮实际发生 247242 次 create、247036 次 remove；40Hz/5% 为 273570 次 create、273103 次 remove（以各轮 JSON 为准）。确实走了移动和进出视野，非静态订阅压测。
- 所有正式样本的会话、收发帧/字节、对象引用、主体版本、BSON 字段及最终 AOI 集合校验通过，无会话丢失。性能门禁失败与数据正确性失败分开记录。
- 40Hz 和 20Hz 的总变更速率相同，但位置轨迹按 tick 推进，AOI 进出次数不同；这是两种候选配置的实测，不能称为严格等工作量的频率 A/B。

默认 MaxObjects=100 足以容纳这里每人约 50 个对象。之前“128 人集中场景超过 100 对象”的结果不代表本目标只能支持 100 人。

### 服务端开销与 profile

20Hz/10% 的服务器主动工作 p95 为 **40.91～51.77ms**，其中 Flush p95 **17.01～19.00ms**；40Hz/5% 主动工作 p95 **24.47～27.28ms**，Flush p95 **12.13～13.33ms**。40Hz 每周期只有 25ms，已经缺少稳定余量。

20Hz/10% 的 Sync 帧约 **33.4～34.0 MB/s**，服务端累计分配约 **370～376 MB/s**；40Hz/5% 约 **35.6 MB/s**、**438～439 MB/s**。这些是 Sync 字节和服务端分配速率，分别不含外层协议/TCP/IP，不等于 RSS。服务端结束时 HeapAlloc 约 63～94 MB，也不是进程 RSS。

单独对 20Hz/10% 采集服务端 profile，结果不计入正式时延表：

- CPU 累计样本：Manager.Flush 约 27.1%；AOI.MoveSubject / evaluatePair 约 19.7%；AOI.evictFarther 约 16.5%；传输 Push 约 16.3%；后台 GC 标记约 19.2%。这些是重叠的调用栈累计比例，不能相加。
- 分配 flat：AOI.observersAt 约 15.1%、evaluateObserver 14.0%、Manager.Flush 11.5%、maps.clone 10.9%、sortedVisible 10.0%、frame.Encode 10.0%。alloc_space 包括该进程的初始化与预热，不能当作测量阶段每秒分配。
- 这里 `MaxVisible=49` 会触发最近对象的容量淘汰，profile 中出现 evictFarther 是该模型的重要条件。真实业务若按自然密度维持约 50，而不设置同样的硬上限，应另设对应的半径/密度档位比较，不能直接照搬本结果。

下一步优先审查 AOI 可见集合评估/排序的分配，以及 Flush/会话 map 克隆；先给出保持可见性、版本和失败语义的改动方案，再做同配置 A/B。还应在独占 Linux 服务端与分机负载端复测，以分离开发机调度和内核竞争。没有证据把所有尖峰归因于某个函数，也不通过反复挑选绿色样本宣称容量达标。

## 工具验收与后续输入

客户端拒绝错误版本、错误字段与错误最终可见集合的回归测试、`go test -race ./scripts/perf/sync-aoi`、`go vet ./scripts/perf/sync-aoi` 已通过。初次 50 玩家/1000 实体烟测也完成数据校验；其 20Hz 的 >50ms 延迟按设计被门禁拒绝，没有把它当作工具错误放宽阈值。

补充 Manager 回归断言：初始快照和一次 delta 成功后，在内容与订阅不变时连续 Flush 20 次，要求零打包、零发送。`go test -race ./sync/entitysync ./scripts/perf/sync-aoi` 用于验证该行为和工具；源码证据为 `manager.go` 的 Register/run 与 `flush.go` 的 pending/dirty 分支。

仍需业务确定：50ms 是最大值还是 p95/p99、输入排队是否包含在预算内、实际变化比例及不同字段的频率、真实同步字段大小、移动速度与可见关系变化量、目标服务器规格。当前按 20Hz 合并脏数据验证；真实接入协议、慢消费者、网络 RTT 和数据库等待不在本轮验证范围内。
