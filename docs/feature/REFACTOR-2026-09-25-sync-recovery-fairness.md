# Sync 新入场与恢复的公平调度

日期：2026-09-25。基线 main `8ce21a5`。用户授权实施；不为通过门禁增加负载特判。

## 当前问题

恢复与新入场都进入 kindSnapshot，预算只按 session/subject ID 轮转。集中恢复期间正常
新可见请求的首次可见诊断 p99 约 1.61 秒。已有对象 Full 刷新虽不扣创建额度，但恢复与
更新仍共享串行 Flush；尚无证据支持新增 worker 或并行 Flush。
Flush 的 policy 失败分支增加计数却不写 LastError，丢失错误证据。其他错误也缺少阶段上下文。

## 结构和契约

保留 sync/entitysync 的包结构；不移动公开符号。subscriptions.go 在 Hold 时标记恢复来源，
新增订阅为普通入场；subject.go 保存这一小段订阅状态；snapshot_budget.go 统一两阶段额度
计划和准入；flush.go 保留捕获、编码、传输、采纳顺序。不要在 AOI 或测试 ID 上增加特殊判断。

主链保持：setter 标脏 → Guard 锁内冻结 → 提交确认 → Sync 串行 Flush → Transport。
不跳过冻结，不拼接不透明 delta，不更改帧协议、50ms 兜底和原延迟门禁。

## 实施

1. Flush 错误统一记账并保留 policy/prepare/admission/reserve/commit 上下文；一次失败的
   Flush 只记一次，保留 errors.Is。确定性测试覆盖 policy 失败及部分准入取消后的重试。
   正式负载先复现历史 FlushFailures，不能把计数直接猜成停机取消。
2. kindSnapshot 冷请求携带是否来自 Hold 的恢复标记。Profile 变更不把旧恢复伪装成新入场；
   最后来源退订后重新订阅是新意图；Hold 会重新分类，成功交付后清理标记，revision/lifetime
   防止在途结算覆盖新意图。
3. 两类候选等额轮转、各类内部继续 session/subject 轮转，共享原有全局对象、字节及每会话
   总额度；某类为空时另一类使用剩余配额，单对象额度跨窗口交替，避免任一类饥饿。
   数量预选限制捕获工作；字节准入沿用同一顺序，避免编码阶段重新按 session ID 推翻选择。
   将分散在每会话内的预算扣减收敛为一次批次计划，不新增独立线程池或一组配置档位。
4. 回归覆盖类间/会话间公平、空闲借用、单额度、字节独占进度、held/Profile/重开/RetryLater，
   相同总预算对比首次可见与恢复时长，保留原变化延迟门禁。不能仅凭总 p99 宣称设计有效。

## 验收与边界

相关 race、静态检查、正式生成工程和原 1000/10000/50、20Hz、1%/5% 正常/恢复负载。
如果公平调度没有改善新入场等待，撤回无收益部分并记录证据，不通过放大总预算解释收益。
两类共享同一 CPU/网络容量；新入场持续超出获得的容量时仍会排队。这一设计不承诺冷对象
全部在 50ms 内到达。对已有对象 Full 突发和 Flush CPU 时间片保持观测，没有 profile 证据
前不引入新的全局调度框架。

## 当前结论与未结项

公平调度与错误留存已实施、功能验证通过；总体性能验收未全部通过，未提交/push、未部署。
保留实现是因为新入场等待与取消数有实测改善，同时明确接受不了的恢复延迟仍须继续处理：

1. 集中恢复期间的冷创建不保证 50ms；此次更公平但恢复更慢。下一步应围绕恢复容量和分批
   恢复策略判断，不能靠增加特判、跳过旧快照统计、修改门禁或另开无证据 worker 宣称解决。
2. 正常状态变化和集中恢复中的已有基线更新需与首次可见分别报告；现有严格总门禁保持不变。
3. 历史 FlushFailures 尚未复现，不能声称根因已修复。本轮修复确保以后失败有阶段和原因。
4. 本轮为短测，未执行生产网络、30 分钟长稳或 24 小时验收。
