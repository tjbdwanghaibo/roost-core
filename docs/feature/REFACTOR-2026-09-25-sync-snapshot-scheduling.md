## 当前证据与优先级

### P1：先让超时样本可解释

[上一批实测](REFACTOR-2026-09-25-resource-budgets-and-session-recovery.md)采用 1000 玩家、10000 实体、平均约 50 可见、20Hz、on_change、1000 会话集中 Hold/Ready。1% 变化样本中实际变化到客户端 p99 为 10.14ms，max 为 48.639ms；5% 为 12.933ms / 915.231ms，458667 样本中 3 个超过 50ms。5% 档不能认定严格 50ms 达标。

当前 `ManagerCounters` 有阶段累计耗时，但不足以串联某个超时实体的冻结、提交确认、预算等待、编码、传输与客户端接收。结束时队列归零也不能证明过程中没有等待。现有客户端按更新步骤和帧操作筛选变更延迟样本，不能仅凭聚合数值判断极值来自恢复、正常更新还是其他阶段。

建议使用有容量上限、默认关闭的诊断记录，关联 subject、会话 lifetime、版本、Full 原因与阶段时间。客户端记录超标样本，服务端保留短时环形记录以便关联；不能仅在服务端慢操作结束时采样，否则会漏掉传输和客户端延迟。避免将实体 ID 放入常驻指标标签。

分开报告正常增量延迟、新可见实体基线到达时间、恢复全部到齐时间，同时保留原有总样本门禁和超标记录。不能通过删除恢复样本来宣称旧门禁通过。

### P1：快照预算耗尽后停止重复构建候选

`sync/entitysync/snapshot_budget.go:planSnapshotCaptures` 先遍历待处理 subject 的订阅、构建候选 map 并排序会话，之后才扣除 on_change 窗口已用额度。全局对象额度已耗尽时仍会完成这轮构建。`flush.go:Flush` 对未选中的快照订阅再次 `markPending`；后续变化唤醒会继续带入相同等待项。当前正常 live 更新不受快照额度限制，但与这部分扫描共享 Flush 执行时间。

已有 5% 产物 `artifacts/perf/sync/session-recovery-20260925-onchange-dirty5/sample-1/server.json` 中，Manager 生命周期累计 FlushCalls=8404、EmptyFlushes=774、SnapshotsDeferred=12446270。计数包含启动、测量和排空，SnapshotsDeferred 是反复延后的次数，不是独立实体数或队列长度。这些证据支持优化重复工作，但未证明其占用多少 CPU，更不能据此归因 915ms。

分两步实施：

1. 在构建快照候选前计算本窗口剩余额度，全局对象额度为零时快速返回明确的“本轮不选快照”结果；不能返回当前表示“不限选择”的 nil。遍历中的停止条件也按剩余额度计算。仍处理 live、remove、生命周期清理及脏状态结算。
2. 若基准证明仍有显著重复扫描，将仅等待快照预算的需求放入下一窗口的等待集合，按 subject 去重；dirty、remove、订阅变更等立即工作独立唤醒。窗口到期重新准入，保留会话公平轮转与字节预算。等待记录携带生命周期/订阅代际，Close、重开、profile 切换、退订、退休及重试均须失效或迁移，避免旧请求复活。

第二步改变内部调度时机，不是单纯整理代码。不能让“尚欠快照”遮住同一实体的 live 更新，也不能为缩短队列而丢弃可靠更新。

### P2：减少 Guard 路径的 Profile 需求重复整理

`mode.go:CaptureSync` 每次调用 `profilesLocked(nil)`，遍历该 subject 的订阅并构建两组去重 Profile；Flush 又按本轮选中的快照计算需求。`entity/sync_frozen.go:FreezeSyncViews` 随后规范化并冻结内容。订阅通常较稳定时，可以评估按订阅需求变化维护缓存，减少每次业务完成时的遍历与临时分配。

优先只缓存不依赖本轮预算的需求；被选快照集合仍需正确过滤。订阅来源、最终 Profile、kindSnapshot/kindLive/kindLeaving 的变化和移除都必须使缓存失效。先比较常见 1–2 个 Profile 与较多 Profile 两类负载，收益小则保留简单遍历，避免增加难维护的状态。

CaptureSync 当前也为等待快照的 Profile 冻结内容，但不能直接因本窗口未选中就跳过捕获。冻结发生在 Entity 锁内，之后读取可变业务数据需要重新满足锁契约。已有内容未交付时使用最新 Full 替代不透明 delta，是一致性策略；应观察 Resync Full 比例和打包耗时，不能任意拼接 delta 或移动到无锁路径。

### P2：明确恢复预算的业务目标，再调整参数

约 50000 条订阅、每 50ms 最多 1000 个快照对象，静态情况下完整恢复就需要约 50 个窗口，量级约 2.5 秒；实际还受字节额度、会话公平性、变化及传输影响。Hold/Ready 调用耗时不等于恢复完成时间。

先补“剩余快照需求、最老等待年龄、恢复到齐耗时”，再比较预算档位对增量长尾、CPU、带宽和恢复时间的影响。已有全局对象/字节及每会话预算继续复用，本轮不新增默认策略。是否引入动态预算或时间片，留待阶段追踪和固定额度对比后决定。

## 目标结构与契约

不新增包、不迁移公开符号，当前与目标目录相同，仅在现有职责处改进：

```text
sync/entitysync/
  snapshot_budget.go   快照候选、额度与等待调度
  flush.go             捕获、编码、交付及结算主流程
  subject.go           订阅及 Profile 需求
```

符号映射为原位置保留。依赖方向仍为业务 Guard → Entity 捕获接口 → EntitySync 调度 → Transport；诊断不能反向调用业务或在慢池取得 Entity local 锁。

保持 setter 仅标脏、Guard 解锁前冻结、提交确认后交付、20Hz 兜底、periodic 默认、on_change 可选。保持版本/基线、会话 lifetime、可靠交付和完整 EntitySync 包边界，不改客户端协议或持久化格式。不为本轮引入并行 Flush、更多 worker 池或网关协议。

## 实施顺序、验收与回退

1. 先补有限诊断和等待指标；验证关闭时无明显额外分配、开启时有固定内存上限，且不改变帧内容。记录现有 5% 超标样本各阶段，未成功复现时明确保留未定位状态。
2. 实施预算耗尽快速路径。确定性测试覆盖同窗口多次唤醒不超预算、live/remove 继续推进、下窗口恢复、部分交付失败与重试；运行相关 race。用大批待快照订阅的重复唤醒基准比较扫描次数、CPU 和分配。
3. 依据第二步收益决定是否引入独立等待集合；补生命周期失效、订阅公平性、关停、Close/同 ID 重开和预算为零时的兼容回归。独立等待集合应能单独回退，不牵动捕获与协议层。
4. Profile 缓存作为独立批次，先建立多来源/profile 变化基准，再修改并验证缓存失效及客户端字段完整性。收益不足则回退缓存，不增加新配置长期维护两个实现。
5. 同机顺序运行 1000/10000/50、20Hz、1%/5% 的正常与集中恢复场景，多次重复；保持相同 payload、预算、网络路径，报告全部超标、版本一致性、最终队列和 CPU/分配。针对后续恢复预算调整单独给出参数对比，不能与算法收益混算。

初始评估阶段只做审查，没有新增已确认的正确性 bug，也未运行新测试或宣称性能收益。已有性能是单机回环 TCP 证据，仍不替代真实网络及长稳验收。

## 实施记录（2026-09-25）

已在 main 工作树实现，不新增包、不改协议：

- 新增可选 `ManagerConfig.Trace` 和固定容量 `SyncTrace`，默认 nil。记录冻结、提交就绪/等待、准备、订阅快照请求、预算等待、选择、编码和准入；传输装配可追加发送事件。容量限制为 1..1048576 条，Drain 返回独立副本及覆盖数；诊断关闭不记录时间戳或事件。实体/会话标识仅进入诊断文件，不进入指标标签。
- 快照对象预算耗尽时返回空选择；候选循环按剩余额度停止。仅等待预算的 subject 独立登记，下一窗口才重新调度；变化、订阅变化和 remove 保持即时调度。等待集合仅记录重查请求与 subject 身份，不缓存旧订阅意图；生命周期变化后使用当前订阅，退休与关闭清理等待。Drain 和 Stats 的 Pending 包含预算等待，避免提前报告排空。
- `profilesLocked` 缓存不依赖本轮预算的需求，订阅/profile/kind 变化使其失效；已发布切片不可改写，Guard 解锁后可安全使用。预算选择只过滤快照需求，不取消锁内冻结或拼接不透明 delta。
- `Stats` 新增 PendingSnapshots（含 held 的待基线订阅）、WaitingSnapshotSubjects（按 subject 去重的预算等待）、OldestSnapshotWait（该 subject 连续预算等待年龄）。仍是诊断遍历，不是每业务事件调用的计数接口，也不是事务一致快照。
- AOI 客户端保留原延迟门禁，分别报告 delta/full 变更延迟和最多 256 个超标样本（每连接最多 16 个，记录省略数）。增加恢复等待采样与服务端快照准入追平时间；后者按 tick 采样，不能当客户端全部恢复时间。`-trace-capacity` 启用逐批 JSONL 诊断，`python3 scripts/perf/sync-trace.py <sample目录>` 离线关联最差样本。

## 继续实施：现有对象全量刷新与冷恢复分开调度

当前证据：404ms 样本是 `ObjectUpdate + Full`，目标会话仍持有引用。现有 `kindSnapshot`
同时表示冷基线和现有对象的视图替换，数量预选与字节准入都按它限流，导致已经可见的
对象也等待冷恢复队列。新一批将恢复预算限定为需要新建客户端对象的快照，现有对象全量
替换按更新交付。它仍需完整快照，不降级为 delta，不跳过授权视图或提交确认。

结构不变，修改 `snapshot_budget.go` 的候选与准入，`flush.go` 的当前会话捕获选择；
不新增包或公开配置。判断以本批不可变 session 引用表为准，不以历史 baseVersion 或
subscription kind 猜测。Hold/Ready 新 epoch 引用表为空，仍受预算；Close/重开和部分交付
沿用既有身份及重试规则。该调整会允许现有对象全量更新超出新对象恢复额度，实际帧硬上限、
冻结内存和可靠传输背压继续有效，不能把恢复额度当全体更新的总带宽限制。

先构造额度用尽后的视图切换回归，分别覆盖对象/字节/每会话预算，确认修前失败；再实现，
验证新对象仍限流、现有对象引用保持、缩小 profile 后字段替换、Hold/重开及 RetryLater。
最后用相同 1000/10000/50、20Hz、1%/5%、1000 对象/窗口的集中恢复负载复测，不改变原门禁。

## 本轮最终收尾方案

在现有目录完成两个独立部分，再验收、提交并 push：

1. 补充客户端创建接收记录，配合有界服务端诊断的冷基线请求、取消和会话重置事件，
   离线统计请求到客户端首次可见、恢复初始集合到齐/取消耗时。明确区分真正收到与因离开
   可见范围取消；记录缺失或环形覆盖时标记统计不完整。只在诊断运行启用这些记录，正式
   延迟基准保持关闭，原有样本与严格门禁不变。
2. 在 `SnapshotBudget` 增加可选 Interval：on_change 的冷创建额度可用更短窗口平滑释放，
   零值沿用 Manager.Interval，periodic 仍按 Flush。生产循环在启用此预算时使用两者较小
   的检查间隔；配额不累积，窗口保持时间基准以免晚醒漂移。默认配置与线协议不变。
   固定容量对比 1000/10 每 50ms 与 200/2 每 10ms，不把增加吞吐配额冒充调度收益。
3. 覆盖窗口轮转、无积攒额度、默认兼容及诊断重置/取消/缺失场景；运行 race、静态检查、
   正式生成工程和无诊断正常/集中恢复负载。动态自适应预算仍不引入，本轮提供可解释的
   固定窗口选择；严格门禁失败如实保留，不以修改统计口径消除超标。
