# 问题快速定位

按**你看到的症状**索引。每行四列：最可能的原因、看哪里、怎么处理。找不到症状时先看 [OBSERVABILITY.md](../OBSERVABILITY.md) 的指标清单，再到 [USER_GUIDE.md](USER_GUIDE.md) 第 12 章。

这份文档与 bug 收敛绑定：每个[工作单元](history/ledger.md)必须为它加一行（编号 `T-xx`，单元日志里回填）。所以它随收敛增长，不是一次写完就过期的文件。"看哪里"引用的指标名、错误值、命令都必须真实存在——文档漂移检查会核对。

| 编号 | 症状（你看到的） | 最可能的原因 | 看哪里 | 怎么处理 |
| --- | --- | --- | --- | --- |
| T-01 | 进程启动后立刻熔断退出，日志有 `ErrCommitIndeterminate` | 上次 fsync 结果不确定，框架按不变量②（结果不确定时 fence，不猜）主动 fail-stop，避免内存回滚制造与 WAL 冲突的第二条历史 | 启动日志里的 WAL replay 记录；`OBSERVABILITY.md` "调度与事务"节的 fence / pipelined verdict 指标 | 让新进程完成 WAL replay 判定权威结果。**不要**手动删 WAL、不要改内存状态后重启；如果 fail-stop 反复发生，查磁盘（写满、只读、fsync 延迟） |
| T-02 | Remote Entity 写被拒，错误含 fence / marker epoch / route epoch 不匹配 | 旧 owner 的延迟写，或租约过期后恢复的进程仍持有旧 fence；存储端按 (marker, route, version) 三元 CAS 拒绝 | `OBSERVABILITY.md` "跨服实体"节的 remote write gate 指标；ownership marker 当前值 | 这是正确行为。从当前 owner 重新发起操作，不要绕过重试；如果是刚迁移完 ownership 的实体，等路由 epoch 传播 |
| T-03 | `roost generate` 报 `unknown kit mod "xxx"` | `roost.yaml` 用了当前 codegen 版本 catalog 不含的名字，通常是升级后名字变了 | `roost.yaml` 的 `mods` / `shared_mods`；`roost version` | `roost project upgrade`；旧名（`sync`、`replication-*`、`checkpoint`）会在加载时归一化并打弃用告警，其余名字按 codegen README 的生成器总览改 |
| T-04 | Mongo Mod 启动预检失败，提示部署无逻辑会话 / 需要 replica set | 接的是单机 `mongod`；kit 的 mongo Mod 写关注硬编码 majority + journal，事务需要副本集 | kit `mongo` 配置段；`require_replica_set` 开关 | 用 replica set（`make dev-up` 起的就是）；生产环境按 `DEPLOYMENT.md` 部署副本集或分片集 |
| T-05 | `nats.reliable.enabled: true` 后 Provide 阶段报找不到 redis capability | 装配顺序：可靠 Bus 的 inbox 去重依赖 redis Mod，redis 必须在 nats 之前注册 | bootstrap 里 `app.Use(...)` 的 Mod 顺序 | 把 redis Mod 移到 nats 之前；codegen 生成的 bootstrap 已按 catalog 依赖排序，手写装配时对照 kit README §3.3 |
| T-06 | entity 数量只增不减（statslog `entity.total` 单调上升） | `Destroy` 未被调用，或持久删除的 admission 被延迟 / 拒绝 | statslog 记录里的 `entity.by_category`；nest 的 delayed admission 指标；`EntityManager.CountByCategory` | 按 category 定位到实体类型，检查其销毁路径是否走了 `EntityManager.Destroy`；查 delete admitter 的拒绝原因 |
| T-07 | goroutine 数持续增长，但 nest / bus 队列指标平稳 | 业务侧泄漏：框架 goroutine 都经 `goroutine` / `worker` 包产生并有上界，增长在框架之外 | statslog `runtime.goroutines`；运行时观察交付后看 `roost_goroutines{owner}` 的残差；pprof goroutine profile | 抓 goroutine profile，按业务包分组看阻塞点；常见是 handler 里 `go func()` 等一个永远不来的 channel |
| T-08 | kit CI 的基准步骤失败：`no Go files in .../sync` 或 `directory not found`，而 `go test ./...` 绿 | 工作流里的包路径字面量没有跟着包改名（v1.10.0 `sync` → `room`） | `.github/workflows/ci.yml` 里所有 `./pkg` 参数；kit 根测试 `TestCIWorkflowPackagePathsExist` 的输出 | 改成新包名；该测试会在普通 `go test` 里报出不存在的路径，改名时先跑它 |
| T-09 | codegen release 工作流的 `framework verify` 一直通过，但生成工程实际用的是更新的 core / kit | `ci/framework-release.yaml` 落后于已发布 tag；门禁校验的是清单里的旧组合，不是你以为的当前组合 | `ci/framework-release.yaml` 的 `framework` 段 vs 五仓 `git describe --tags` | 每次按 core → kit → skill → service → codegen 发布后更新清单；缺 `service` 字段的清单自 codegen 下一版起直接不通过校验 |
| T-10 | kit 集成套件里**第一个**测试失败：`start data engine mod: dataengine mod: ensure effect stream: context deadline exceeded`，后面的测试都过 | NATS 三节点刚起来，JetStream 元集群还没选出 leader，建流请求一直等；`dataengine.startup_timeout` 默认 30s 先到期。只打第一个夹具，因为等它超时时 leader 已经选出来了 | `scripts/integration/dataengine-env.sh status` 每行末尾的 `meta_leader=`；任一监控端口的 `/jsz` 里 `.meta_cluster.leader` | 环境脚本自 U-0003 起把 meta leader 纳入就绪判定。手工搭的环境要等 `/jsz .meta_cluster.leader` 非空再启动进程；生产里如果 NATS 集群整体重启，Data Engine 的 startup_timeout 要覆盖元选举时间 |
| T-11 | 排行榜提交在高并发下偶发返回 `CodeInternal` / "server error"，但 Redis 正常、日志里是 `submit lost 8 compare-and-swaps` | 同一 owner 的 CAS 重试耗尽是业务层面的冲突，不是服务故障；rank v1.4.0 及之前把它当无码错误返回，信封只能填 `CodeInternal` | `rank` 的 `conflict:submit` 指标计数；错误链里是否有 `rank.ErrConflict`（旧名 `ErrConflictSentinel`） | 升级到含 U-0004 的 rank：客户端收到 `CodeConflict 540108` 后按业务重试或提示；服务端不要把它计入故障告警 |
| T-12 | 客户端更新角色 profile 收到 `CodeConflict 560113`，重试仍然失败 | profile 超过 `MaxProfileBytes`（4096）；account v1.4.0 及之前把这种大小违规错报成"冲突"，客户端按冲突语义重试自然永远失败 | 错误 reason 里是否有 `profile is N bytes, limit 4096` | 升级到含 U-0005 的 account 后该失败改报 `CodeRangeInvalid 560112`；客户端对 560112 不要重试，裁剪 profile |
| T-13 | 全服广播邮件发送接口返回成功，但没有任何玩家收到；重发同一个 request id 仍返回成功 | 第一次 fanout 失败后账本已记下这次发送，mail v1.4.0 及之前的回放路径不再投递 | `refused:send:delivery_failed` 是否在首次发送时出现过；账本记录 `delivered_at_unix` 是否为 0（含 U-0006 的版本） | 升级到含 U-0006 的 mail：回放会补投递。旧版本只能换一个 request id 重发，并接受可能的重复 |
| T-14 | 客户端翻邮箱列表时中途提前结束，`Summary` 的未读数却比列过的多 | 上一页最后一封邮件在翻页间隙被删除，旧游标按 id 定位失败，直接返回空页无游标 | 游标格式：含 `|` 的是位置游标（U-0006 起），纯 id 是旧格式 | 升级 mail；客户端对空页且无游标的结果不要缓存为"已读完"，重新从头列一次 |
| T-15 | 玩家反馈"发出去的聊天消息没出现"，服务端却记录了成功；偶发、多人同频道时更多 | 两个客户端在同一频道用了相同的幂等键（客户端本地计数器、短随机串），chat v1.4.0 及之前把后来者当回放，返回前者的消息并报成功 | `refused:publish.<kind>:key_reused` 计数（含 U-0007 的版本）；客户端幂等键的生成方式 | 升级到含 U-0007 的 chat：撞键返回 `CodeConflict 580111`，客户端换键重发。根治是客户端用全局唯一键（UUID 或 roleID 前缀） |
| T-16 | 匹配队列"卡住"：`Candidates` 返回同一张票两次，`Commit` 报 `ticket appears twice`，直到有新玩家入队才恢复 | 只在内存后端（测试、单进程演示、`examples/`）出现：match v1.4.0 及之前的 Mutate 回调就地修改存储值后又放弃保存，`Waiting` 尾部被复制。Redis 后端每次重新解码，不受影响 | 是否在用 `versionstore.NewMemoryStore`；`Candidates` 结果里是否有重复 id | 升级到含 U-0008 的 match。生产环境用 Redis 后端本就不受影响；如果生产也看到重复票，那是别的问题 |
| T-17 | JetStream 上的状态流 / 副本同步偶发少一条：发布方进程刚重启，或 delete 紧跟同版本 upsert，消费者没收到；`nats` 端无报错 | 消息没有独立投递身份时，JetStream 以 `(topic,key,version,sid,part)` 元组去重：重启后重发的同序号帧、同 key 同 version 的 upsert 与 delete 都会被当成重复而丢弃 | 发布出的 `SyncMsg.MessageID` 是否为空；JetStream stream 的 `duplicates` 窗口内是否有同名 MsgId | 升级到含 U-0009 的 core/kit：三条发布路径都经 `syncbus.DeliveryIDs` 生成身份。自写发布者要填 `MessageID`，不要依赖元组回退 |
| T-18 | kit CI 的 `integration` job 在环境脚本一开始就失败：`require_commands` / `command not found: mongod …`，或 `mkdir: cannot create directory '/private': Permission denied`、`failed to initialize build cache at /private/tmp/…` | 前者：runner 上安装步骤没装齐，或 MongoDB apt 源对当前 ubuntu 代号（`lsb_release -cs`）没有发行；后者：脚本里残留 macOS 专属的 `/private/tmp` 路径（U-0010 已把根目录改为 `$(cd /tmp && pwd -P)` 派生，新加路径要沿用） | job 里两步安装的输出；`grep -rn /private scripts/` | 版本对照本地 `mongod --version` / `nats-server --version` 调整；路径一律从 `ROOST_IT_CANONICAL_ROOT` 派生，不要再写字面量 |
| T-19 | Remote Entity 的每一次共享（marked）操作都被 `ErrRemoteFenced: shared lock did not allocate fence` 拒绝，但 Redis 正常、无 ownership 变更 | 装配了一个不实现 `redis.IFencedVersionedLock` 的锁工厂（自写或旧版本），锁拿不到 fence；U-0011 之前这在运行时逐次暴露 | `RemoteEntityMod.Provide` 的返回（含 U-0011 的版本会在这里就停）；日志 `remote_entity: refusing to create wrappers` | 用 kit 自带的 `versionedLockFactory`，或让自写工厂返回带 `Fence() uint64` 的锁。不要绕过：fence 是 Remote commit 三元 CAS 的一维 |
