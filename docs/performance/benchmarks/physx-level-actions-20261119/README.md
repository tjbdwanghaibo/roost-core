# 物理房间带关卡流程的成本与长稳（2026-11-19，macOS ARM64）

结论见 [PHYSICS-ROOM-SERVICE §流程的成本](../../../framework/PHYSICS-ROOM-SERVICE.md#流程的成本2026-11-19macos-arm64)；功能与逐批证据见 [physx-level-actions 证据](../../../maintenance/evidence/physx-level-actions-20261119/README.md)。

环境：Apple M5（10 核），macOS 26.5.2（25F84），Go 1.27.3，GOMAXPROCS=10，PhysX 4.1.2 arm64。负载：`wiring/physicsroom` 的 `TestMultiRoomReplicationLoad` 与 `TestPhysicsRoomSoak`，真实 Room / PhysX / EntityHost / Nest，每房 20 个逻辑客户端按 Relay 节奏（响应后等 50ms）提交输入并 Poll，不含 Gate / NATS / TCP。Linux 未测。

三个对象：

| 标签 | 代码 | 场景 |
| --- | --- | --- |
| 改前 / base | main `ba158535`（方案写的对照点；物理房间相关目录与分支基线 `2d15a1e5` 逐字相同），原生库用同一份 PhysX 静态库与该提交的 `bridge.cpp` 链出（ABI 2） | 机关场景（每房 83 个非静态刚体） |
| 流程关 / off | 分支 `feat/physx-level-actions` 的 `c2187122`（批 5a 之后），ABI 3 | 同上，房间不带流程 |
| 流程开 / on、flow | 同上 | 同上，再挂上流程：20 个玩家刚体、铺满围场的 32 个区域、东西两侧最外一列共 8 个区域进入即重生并让公开变量 `falls` 加一（每次重生给全房间推一次流程视图），其余区域只产生进入 / 离开事实 |

**测量期间这台机器同时被别的会话占用**：1 分钟负载在 7～32 之间，开跑前 swap 已用 12.3～12.5GB / 13GB（各 `*-pre.txt`）。所以 Step p99、提交 p99、物理均频的个别低值有调度噪声；交替轮次能抵掉一部分，长稳三次是先后跑的，抵不掉。下面每个结论都注明了它受不受这个影响。

## 交替 3 轮（`TestMultiRoomReplicationLoad`，1 秒预热 + 5 秒采集）

`rounds.sh` 每轮依次跑改前、流程关、流程开，各 1 / 4 / 8 房间；原始输出 `rounds.txt`，`summ.py` 汇总成 [rounds-summary.md](rounds-summary.md)（括号里是三轮原始值，前面是中位数）。8 房间一档：

| 量 | 改前 | 流程关 | 流程开 | 关 相对 改前 | 开 相对 关 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 物理均频 Hz | 49.82 | 50.00 | 50.00 | +0.4% | −0.0% |
| 交付 Hz / 客户端 | 19.79 | 19.76 | 19.80 | −0.1% | +0.2% |
| 提交 p50 ms | — | 0.025 | 0.038 | — | +52%（+0.013ms） |
| 提交 p99 ms | 0.352 | 0.232 | 0.326 | 噪声内 | 噪声内 |
| Go 分配 MB/s | 23.63 | 23.70 | 28.72 | +0.3% | +21.2% |
| 分配次数 / 交付帧 | 53.5 | 53.7 | 68.7 | +0.3% | +28.0% |
| 载荷 KB/s / 客户端 | 5.99 | 5.99 | 6.96 | −0.1% | +16.2% |
| 事实 / s（8 房间合计） | — | 0 | 300 | | |
| 重生 / 客户端 / s | — | 0 | 0.259 | | |

- **流程开相对流程关，物理均频下降不超过 1%**（方案的判定）：1 / 4 / 8 房间的中位数差是 −0.4% / 0% / 0%。1 房间那一档的 50.20 是 5 秒窗口里多数出一拍，不是频率真的高。
- **不带流程的房间没有回退**：Go 分配 +0.1%～+0.5%，分配次数每帧 +0.0%～+0.3%，载荷 −2.0%～+0.1%（1 房间那一档流程关有一轮交付频率偏低，中位数被带低），都在轮次之间的波动以内。
- **带流程的成本**：Go 分配 +21%～+22%，分配次数每帧 +28%～+29%，每客户端下行载荷 +16%～+18.5%。载荷多出来的是传送后的强制刷新（每次传送每个接收方两次：带标记的一帧、清标记的一帧）；这个负载下每个客户端约每 3.8 秒重生一次，比方案写的“约每 5 秒”重。提交 p50 多 0.003～0.013ms。
- 提交 p99 与 Step p99 三轮之间差到几倍（比如改前 8 房间的 Step p99 是 3.5 / 2.8 / 9.9ms），不能用来比较三者。

提交 p50、事实数、重生次数是这次给夹具加的字段，改前的二进制没有。

## 8 分钟长稳（`TestPhysicsRoomSoak`，8 房间 × 20 客户端）

三次先后运行，每次带进程外采样（`physicsroom-soak-20261029` 的 `run.sh` / `sample.py`：footprint 每 30 秒、vmmap 每 150 秒），预热取 120 秒，汇总用同目录的 `summ.py`。

| 量（稳定窗口） | 改前 | 流程关 | 流程开 |
| --- | ---: | ---: | ---: |
| goroutine | 206，全程不变 | 206 | 206 |
| 估算原生内存 MB（footprint − Go dirty），均值 / 斜率每分钟 | 13.90 / +0.009 | 13.84 / +0.007 | 13.85 / +0.003 |
| malloc 已分配 MB（vmmap，3 个点），首 → 末 | 9.617 → 9.625 | 9.615 → 9.635 | 9.615 → 9.652 |
| malloc 分配个数，首 → 末 | 6489 → 6492 | 6487 → 6496 | 6497 → 6509 |
| footprint MB，均值 / 斜率每分钟 | 41.88 / +0.17 | 43.82 / +0.16 | 43.52 / +0.12 |
| Go heap in-use MB，均值 / 斜率每分钟 | 12.92 / +0.20 | 13.12 / −0.04 | 13.20 / −0.08 |
| RSS MB（ps），均值 / 斜率每分钟 | 53.69 / −0.38 | 55.01 / +0.07 | 52.58 / +0.17 |
| 分配速率 MB/s | 23.27 | 23.13 | 27.45 |
| 物理均频 Hz，均值 / 最低窗口 | 49.24 / 45.37 | 49.35 / 44.64 | 48.86 / 44.42 |
| 提交 p50 ms（中位窗口） | — | 0.043 | 0.076 |
| 提交 p99 ms（中位窗口 / 最大窗口） | 0.36 / 2.35 | 0.40 / 2.37 | 0.95 / 5.69 |
| 1 分钟负载（测试自己读到的） | 6.7～30.2 | 11.0～26.2 | 14.5～32.2 |
| 每房间累计重生 | — | — | 约 1630 次 |

- **没有新的无界增长**（不受机器负载影响）：goroutine 三次都是 206；估算原生内存三次都在 13.8～13.9MB、斜率每分钟不到 0.01MB；malloc 已分配与个数首末差在 0.04MB、12 个以内（各只有 3 个 vmmap 点，流程开那次多出的 12 个分配不足以判断是不是趋势）；Go heap in-use 没有上升趋势。footprint 每分钟 +0.12～+0.17MB 三次相近，来自 Go 映射的 dirty 页（改前也有），不是流程带来的。
- **带流程的房间在重生累计超过 1024 次之后继续运行**：这是批 5a 修的问题，修前同一负载约 330 秒停房（`ledger-before-go.tsv`、`ledger-before-tail.txt`），提交 p50 从 0.115ms 涨到 2.6ms；修后 8 分钟里提交 p50 在 0.056～0.093ms 之间，没有随时间的趋势。
- **物理均频、Step / 提交 p99 不能在三次之间比较**：三次不是同时跑的，负载不同（流程开那次最重）。三次的均频都低于空闲机器上应有的 49.9Hz 以上（2026-10-29 同夹具 20 分钟是 49.85Hz）；流程对频率的影响以上面的交替轮次为准。
