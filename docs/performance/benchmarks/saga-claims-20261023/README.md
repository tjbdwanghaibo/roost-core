失败试验保留，不能以终态数量冒充业务成功。诊断开销不用于精确前后性能百分比。原子认领消除先查候选再竞争同一条记录时的空领；消费并发同时改善 Mongo 步骤和完成结果处理。两项单独使用都未通过此档，默认消费仍为串行，业务启用并发必须保证 handler 并发安全。

`claim-red.txt` / `claim-green.txt`（实际文件名见目录）保存确定性回归：两个可认领记录、两个 worker，旧实现一方得到空列表；新实现分别认领不同记录。微基准只衡量内存替身开销，不代表 Mongo 吞吐。

复跑：加载隔离环境后执行 `ROOST_SAGA_PERF_MODE=forward ROOST_SAGA_PERF_RATE=30 ROOST_SAGA_PERF_DURATION=10m ROOST_SAGA_PERF_WORKERS=2 ROOST_PERF_LABEL=<唯一名称> bash scripts/perf/saga.sh`。`ROOST_SAGA_PERF_HOPS=1` 仅用于诊断；Mongo 命令统计包含清理，不将 dropDatabase 算作业务成本。

## 10 分钟正常测量（关闭 hop 诊断）

`fix-20261023-forward30-10m.forward.json`：18,000/18,000 正向成功，29.987 TPS，P50 408.65ms、P99 576.28ms（服务端 P99 548.00ms）、最大 775.49ms；错误终态 / ManualRequired / 发布失败 / 存储失败均 0。36,000 份步骤效果与 18,000 份业务文档核验通过，结束时 outbox 和租约均 0。十个分钟段各 1800 笔，无持续累积。消费 worker=2，步骤订阅=1；这不是默认串行模式的容量声明。

## 微基准的代价

前后各十轮交替测量见 benchstat.txt。mongotest 的 100 条候选、一次领 3 条场景由 98.43µs/op 升至 221.69µs/op（+125%），分配由 99.73KiB 升至 198.66KiB。替身每次原子领取重新扫描排序，没有 Mongo 索引；这是实际记录的替身开销退化，不能删掉或宣传为全路径加速。真实 Mongo 的收益是消除候选竞争空领，并与有界消费并发结合通过 30/s；索引选择和更大队列容量仍须按部署数据规模验证。
