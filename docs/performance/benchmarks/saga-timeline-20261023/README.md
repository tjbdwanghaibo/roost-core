# Saga 单笔时间线诊断（2026-10-23）

基线 `05f202c6`，只补诊断打点与分析工具，不改 worker、轮询、事务、重试或持久化行为。采用现有 hoptrace.Mark，按 SagaID / CommandID 关联，单进程单调时钟；事件和关联标记各最多100万项，溢出明确报丢弃，不能静默输出“完整覆盖”。生产不安装 Recorder，身份不会进入常驻指标；诊断模式在订阅入口额外解码身份以分开到达和拿到worker。

## 参数与样本

30/s × 1分钟、两个 Mongo 正向步骤、单步骤订阅、MongoWorkers=2、结果Workers=2；其余沿用此前夹具（协调 / 发布各4、batch3/1、poll100ms、GOMAXPROCS4、隔离三副本依赖）。1800/1800成功、错误终态0、实际效果核验通过。压测端 P50 416.9ms、P99 549.5ms；服务端 P99 520.41ms。时间线完整覆盖1800笔，未丢事件、未发现重复时间点，分析结果的服务端P99与夹具一致。

这是带Mongo监视器和事件记录的单次诊断，不用来宣称比此前10分钟576ms改善。宿主供电模式不作为恒定条件；不是跨机容量验收。此前第一轮粗分诊断也全成功（1800笔，服务端P99约489.6ms），但没有订阅入口时间点，不用于本表。

## 时间主要花在哪

下表是**每笔完整交易、两个步骤合计的均值**，不是单步骤，也不是各跳P99相加。整笔均值396.78ms、P50 391.97ms、P99 520.41ms。

| 分组 | 每笔平均 | 约占比 | 解释 |
|---|---:|---:|---|
| 持久状态与回执处理 | 157.83ms | 39.8% | 启动16.94 + 两次派发提交36.59 + 步骤预留34.40 + 业务返回后的fence/回执/提交34.50 + 结果推进35.40；不是全部纯fsync时间 |
| 命令与结果交付 | 137.90ms | 34.8% | 发布开始到订阅回调：命令65.72、结果72.18；包括序列化、JetStream复制/确认、传输、客户端缓冲及先前回调造成的排队 |
| 协调与outbox等待/认领 | 83.75ms | 21.1% | 启动或上一步完成到派发54.21，派发提交到开始发布29.54；包含Mongo认领耗时与调度等待，不是纯轮询sleep |
| 当前回调内等待消费槽 | 15.59ms | 3.9% | 命令10.61、结果4.98；结果还含少量解码/进入Complete开销。不覆盖前一回调堵塞导致当前回调尚未开始的等待 |
| 业务写入 | 1.65ms | 0.4% | 两个步骤handler里的Mongo业务写；不包含事务最终commit |

关键推断：业务函数不是主要耗时；消费槽的直接等待也不是最大项。可靠提交是基础成本，另外存在交付和认领等待，应该优先拆清这两处，而不是盲目增加worker。

嵌套测量：单命令PubAck平均15.81ms、单结果PubAck平均15.48ms。发布返回后到订阅回调的有符号均值分别约17.05 / 20.61ms；消费者可早于发布者收到PubAck，命令有6次这种重叠，不能把负值裁成“丢数据”。这些PubAck时间已经包含在交付分组里，不重复相加。尚未拆分客户端缓冲、订阅串行回调阻塞、broker复制与内核传输各占多少，因此**不能把137.90ms称为网络RTT，也不能直接归因于NATS服务端慢**。

## P99对应的具体交易

`summary.json` 的 P99Transaction 为 perf-75，两个步骤总计520.41ms：持久处理170.15ms、交付166.81ms、协调/outbox128.39ms、消费槽53.69ms、业务1.33ms，其余约0.04ms。这是一笔真实完整时间线，而不是把不同交易各阶段P99相加。

最慢1%样本（19笔，包含分位边界）平均命令交付121.96ms、结果交付90.97ms、协调认领62.70ms、outbox等待46.31ms；相对全体均值，尾部增加较多的是交付与等待。具体数值和每阶段分布见 summary.json。

跨worker交接可能重叠：Mongo状态写入在前一客户端收到commit确认前就被另一个worker看见。分析器仅允许协调交接 / outbox交接出现这类重叠，单列负的 handoff_overlap 抵消重复计时；同goroutine区间逆序则拒绝分析。每笔各段加重叠扣除必须精确等于整笔时长。只支持完整成功、无重试重复事件的正向样本；缺失、重复、丢事件、错误终态都会拒绝，不能把异常样本静默筛掉。

## 接下来值得做什么

1. 先分开订阅前的客户端排队、前一回调等待槽、broker交付：保留消息身份和客户端收包时刻；使用隔离NATS的监控与时间线关联，避免只测网络ping。
2. 测协调认领中的Mongo命令耗时与空领唤醒等待；已有kick，不直接把PollInterval从100ms调小来掩盖空查成本。
3. 在相同可靠性下评估有界发布流水；PubAck/outbox确认可能影响下一条命令，不能提前删outbox。实际跨服交易的原生Entity步骤要另测，不能套Mongo步骤的1.65ms业务成本。

## 复跑与验证

加载私有环境后：`ROOST_SAGA_PERF_MODE=forward ROOST_SAGA_PERF_RATE=30 ROOST_SAGA_PERF_DURATION=1m ROOST_SAGA_PERF_WORKERS=2 ROOST_SAGA_PERF_HOPS=1 ROOST_PERF_LABEL=<唯一名> bash scripts/perf/saga.sh`。然后 `python3 scripts/perf/saga-timeline.py artifacts/perf/saga/<唯一名>/forward.json --output <summary.json>`。

原始 timeline 位于主工作树 `artifacts/perf/saga/timeline-20261023-forward30-slots/forward.json.timeline.json`，报告保留小型摘要；原始文件与第一轮样本均已复制保存。诊断关闭时MongoCommandInboxHandle前后各10次交替、每次100笔，114.7µs/op对114.7µs/op，无显著差异（p=0.739），分配无显著差异；该微基准只覆盖Mongo步骤入口，不代表全链路开销为零。见before/after/benchstat.txt。

验证：Saga包race、integration标签下记录器 / 消费worker的race测试、Saga integration vet、根包门禁均通过。分析器用合成时间线核对精确总和、跨worker重叠抵消，并确认缺失 / 重复 / 丢事件拒绝；真实1800笔逐笔总和检查通过。CBM图谱仍为10-14旧代际，本轮按覆盖提示读当前源码补证。
