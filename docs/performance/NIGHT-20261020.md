## 10. 第 10 项：Lockstep 纯追帧页在限速链路上

功能演练，不是性能基线。夹具由 2026-10-20 快照演练的嵌入 TCP 夹具改成只追帧：不配快照来源（Recovery 缺省为追帧），先无连接地切 3000 帧（窗口 3600 之内），客户端从第 1 帧请求追帧，之后 30Hz Tick。8 席、每席每帧 50 B 输入（实测每帧约 420 B），`RedundancyDepth` 1（TCP 可靠，便于按字节核算），其余（`CatchupBatchFrames` 32、`CatchupSendTimeout` 2s、`write_timeout` 5s）取缺省。共享隔离环境的 toxiproxy 新建 `lsnight-catchup-*` 代理，只在下行加 `bandwidth` toxic（1 KB = 1000 B），用例结束删除；演练前后代理列表都是 `nats-1～3, redis`。夹具原样存为 [catchup_drill_test.go.txt](benchmarks/night-20261020/catchup_drill_test.go.txt)。

- 不覆盖：独立 Gate（只准入）下的纯追帧页、真实移动网络与跨机、冗余深度 3 下的实时广播放大。

## 11. 第 11 项：匹配队列容量与 Redis Cluster 故障切换

## 13. 第 13 项：Player 跨机演练

按 [PLAYER-MIGRATION §2](../framework/PLAYER-MIGRATION.md#2-步骤)，同一套环境上同机两个 game 进程 A / B：同 sid 1000，B 只改 ops（9200）、玩家 TCP（7100）、`etcd.advertise_addr`（9010），并显式写空 WAL 目录 `data/walB/dataengine/1000`；A 用缺省目录。写入负载是 ops GM `gm.player.add_item` 循环（玩家 2001 / 2002 × 物品 1001 / 1002 轮流加 1，每 50ms 一次，记录每次确认的数量），“路由切换”是改循环的目标端口。脚本与原始记录在 [drill-player/](benchmarks/night-20261020/drill-player/)。

**正常迁移**：

1. A 就绪，写入循环指向 A。4 秒后启动 B：B 日志 `singleton: waiting for the current holder to release or expire`（持有者为 A 的 PID），`/readyz` 不通，没有创建 `data/walB`。
2. account 把 sid 1000 标为 maintenance。
3. SIGTERM A（循环不停）：A 在 04:19:50.978 记 `singleton: released`，之后请求得到 1 次 `nest: stopped` 与连接拒绝。
4. `wal-drained` A：`drained: true`（checkpoint 与最后一条记录同为 segment 1 offset 16118）。记录玩家快照。
5. B 在 04:19:53.890 记 `singleton: acquired`（A 释放后约 2.9 秒，B 的重试间隔），随后就绪；`players -compare` 未变。
6. 写入切到 B 约 6 秒，停 B，`wal-drained` B 通过。

**异常退出与回退**：

1. B 在原 WAL 目录重启、写入中 `kill -9`：这次投影跟得上，`wal-drained` 仍为 `drained: true`。在原 WAL 目录重启 B：等旧锁过期，15 秒后就绪（`singleton.ttl` 15s）；正常停机、`wal-drained` 通过后迁回 A（A 的旧 WAL 已全部确认），写入继续。
2. **未排空**：写入中对三个私有 mongod 发 SIGSTOP 让投影停住 2 秒，期间 `kill -9` A，再 SIGCONT。`wal-drained` A：`drained: false`（checkpoint segment 1 offset 24672、最后一条记录 offset 29222，退出码 1）。此时 Mongo 中两名玩家的 `_version` 为 143，而已确认给业务的写入对应 155——**若此刻在新机器用空 WAL 接管，每人 12 次、共 24 次已确认的写入会丢失**。在原 WAL 目录重启 A 后正常停机，`wal-drained` 通过，Mongo `_version` 155。

**核对**（`writes-summary.txt`）：共确认 302 次（A 156、B 146）。四个（玩家, 物品）键的确认数量在全程（含 A→B、B 崩溃重启、B→A、A 崩溃重启）都严格逐次加 1、没有跳号或重复；最终 Mongo 数量（1001: 79、1002: 76，两名玩家相同）等于各键最后一次确认；`_version` 增量（4 → 155，151）等于每名玩家的确认次数（75 + 76）。A 与 B 从未同时持有锁。

结论：与 2026-10-15 演练一致，v1.30 候选上成立。边界同手册：同机两进程，没有跨机网络、卷迁移与 DNS / 负载均衡切换；写入经 ops GM 而不是玩家 TCP，客户端重连路径未演练。

## 16. 能证明什么 / 不能证明什么 / 是否阻塞发版

**能证明**（本机、本次参数）：

- v1.30 候选在嵌入 TCP（场景 Sync 与 self_sync）、独立 Gate、Block AOI 4 并行度三种重档 15 分钟下计数、终值、可见集合与门槛全部通过；嵌入 TCP 出站预算缺省 256 MiB 在这个推送量下不被触及（拒绝 / 关闭计数全 0）。
- 同机交替两轮下，HEAD 的 Sync 提交→客户端 P99 比 v1.27.0 稳定高 0.6～1.1ms；10-19 观察到的长尾差异今晚不出现。
- 原生步骤 saga 在正向 8/s、全补偿 5/s 下 15 分钟全部正确；Mongo 步骤路径在正向 30/s、全补偿 15/s 饱和且饱和时 outbox / lease / 存储无残留与失败。
- WAL 与 Mongo 不同盘时 checkpoint 与 WAL 追加的 fsync 成本基本消失。
- Remote 80TPS、Lockstep 纯追帧限速、schema 迁移、Player 跨机迁移（含崩溃与未排空）在 v1.30 候选上与历史结论一致；匹配队列在 Cluster 主节点切换下没有部分生效。

**不能证明**：

- 跨机、Linux 实机、独占服务器上的结果；所有项每档只有 1～2 个样本（第 3 项 A-B-A-B 每边 2 个，§9.1 Remote 同机对照每边 1 个）。
- Sync P99 增加的具体代码来源（没有单变量对照）；夜间 Remote P99 偏高时共享 Mongo 主节点变慢的原因（§9.1 只把差异对应到 Mongo 慢操作）、16 视野 Nest 失守的原因；原生步骤 P99 尖峰的 Mongo 侧原因（只有逐跳最大值同时升高的推断）。
- 嵌入 TCP 出站预算在停读客户端或更高推送量下是否够用（每连接队列峰值与驻留字节没有 Gauge）；self_sync 整轮重试放大（本负载下没有被触发）。
- 匹配队列在 Cluster 下的容量、跨机 Redis 往返、异步复制丢写。
- 第 14 项（生成工程 strict 复测）未跑（维护者未批准）。

**是否阻塞发版：否。** 理由：

- 没有任何一项出现正确性问题（终值、计数、恰好一次、迁移检查点、多键原子性都通过）；所有失败都是容量饱和或夹具 / 命令自身的结构性门槛（sync-aoi periodic 模式、Saga 30 / 15 档）。
- 发现的退化与边界（Sync P99 +0.6～1.1ms、Remote P99 偏高、D19 16 视野 Nest 模式失守、原生步骤 P99 指引数字不准、匹配队列保留期状态上限）都在已发布能力的门槛之内或属于新能力的压力配置，已登记为尚未确认 / 能力表结论，交维护者决定是否在发版前处理：
  1. **D19 多视野**：是否在发版文档里写明“每玩家额外空间视野 4 个以内已测、16 个时 Nest 模式失守”，或先定位原因（A：只写边界，推荐；B：发版前定位，代价是推迟发版）。
  2. **原生步骤容量指引**：guide/06 §5、`add_saga.go` 的 `sagaCapacitySummary`、`roost help saga` 里的“P99 0.8 / 1.2 s”改为 15 分钟样本的“P99 可到 3.6～3.9 s，P50 < 1 s”（生成器文本，属代码改动，本轮未改）。
  3. **匹配队列**：guide/09 §4 是否补“单分区每秒成局人数 × 保留期 ≤ 约 4500 人”的建议。
  4. **Remote P99**：维护者 2026-10-21 批准后已做同机对照（[§9.1](#91-同机-a-b-a-b2026-10-21)，各 1 次）：v1.27.0 / HEAD p99 同为 263ms，倾向环境条件、不是代码退化，不阻塞发版。
