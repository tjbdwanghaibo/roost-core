源码基线 `6c36e0df`，包含最近的 Nest 三池/Await、Sync/AOI/Relation 与 Lockstep 改动；本轮补 codegen 配置快照与调度基准夹具修复。环境为 macOS/arm64、Apple M5、Go 1.27.0，`GOWORK=off GOMAXPROCS=0`，实际并行度 10。测量串行运行，不并跑 race、编译其他项目或索引重建；无法保证宿主不存在其他应用负载。

## 重档混合负载

沿用 [Gate/AOI 复跑入口](GATE-AOI.md)：1000 玩家、10000 Entity，每玩家 10 条消息/s，所有 Entity 挂 10Hz heartbeat，5% 修改率，on_change 即时处理、20Hz 兜底、合批窗口 0；AOI 上限 49 加自己。短 worker 8、I/O worker 8、短等待容量 65536、I/O 等待容量 64，输入窗口 15 分钟。Gate/Game/客户端在同一进程，通过真实 TCP 与本轮自建的本机独立 NATS 通信。

本场景不声明长业务 Kind，不调用 Await、Remote 或 Saga，不作为这些路径的容量验收；非零合批窗口也未纳入本轮端到端性能测量。

### 同参数诊断复跑：确认慢任务抓栈放大超时

`diagnostic-heavy-15m-20261012` 于18:06:50建立连接，18:19:16再次出现通道过期，约12分25秒失败。短池仍8/65536，I/O池8/64，长池8/4096（本负载未使用），`GOMAXPROCS=0`实际10。没有调大超时、队列或减少负载。临时夹具增加Go flight recorder、每秒runtime/Nest和独立NATS监控采样；它们有观测开销，本轮用于定位，不与无诊断样本作吞吐收益对照。捕获后停止负载和本轮私有NATS，未得到最终15分钟统计。

**已确认的故障放大路径是Nest慢任务诊断中的全进程抓栈。** [trace.go](../../framework/nest/trace.go) 的watch在200ms触发，经过5秒进程级限频后，`captureSlowDispatchStack`调用`runtime.Stack(buf, true)`。限频控制次数，256KiB控制输出上限，两者均不限制单次暂停耗时。本次调用记录明确的`stop-the-world (all goroutines stack trace)`，不是推测自事后堆栈。

| 首错现场 | 测量结果 |
| --- | ---: |
| 慢任务诊断触发时已耗时 | 241.197ms |
| 全进程抓栈STW区间（含停住各P） | 330.160ms |
| 最后一个其他P转Idle到STW结束 | 303.832ms |
| Game→Gate发送开始时context剩余预算 | 249.977ms |
| 该发送调用返回超时的总耗时 | 571.923ms |
| 首个错误发送载荷 | 337字节 |
| 独立采样定时器延迟 | 458.611ms |
| 跨首错的相邻采样GC暂停增量 | 1.167ms |
| 18:19:16的outbound失败日志数量 | 52条 |

轨迹中G4123在`inboxClient.RequestContext`的select等待回信/取消；随后Nest的G1559918抓取全进程栈，覆盖该发送的到期时间。STW结束后，context取消唤醒G4123，约8.3μs便重新运行，最终返回超时。因此这条发送不是在可运行队列里单独等了572ms，也不是一个337字节包正常传输需要572ms。Nettransport按原准入年龄过期，GameIngress关闭旧绑定，随后出现stale binding及重试。关闭绑定符合当前可靠通道契约；把期限调大无法解决诊断暂停本身。

GC的PauseTotal不包含这类抓栈STW，不能由GC暂停短推导“没有全局暂停”。该暂停来自正式Nest诊断，调用栈与本轮首错后才执行的flight recorder保存、pprof抓栈不同，后者不能倒因解释首错。采样前后快队列没有持续上涨、没有准入拒绝；NATS秒级监控未报告slow consumer，首错邻近pending为0。这些证据不支持先增加Nest worker或认定NATS已达容量上限，秒级采样也不能排除更短暂的竞争。

**尚未唯一定位的是触发慢诊断的最初延迟。** 抓栈前轨迹已有约91.46ms、98.97ms的事件空档，以及44.12ms的NATS写syscall区间；事件空档本身不能区分宿主抢占、运行时调度或未产生轨迹事件的执行。缺少OS线程调度证据，不能声称已证明机器休眠、NATS锁竞争或新增提交回归，也不能承诺去掉自动抓栈后15分钟必过。

下一步应先取消慢请求热路径自动全进程抓栈，保留handler/实体身份、阶段、耗时、队列和限频日志；全局栈改为显式诊断操作。不要简单在timer goroutine内改成`runtime.Stack(..., false)`并称为handler栈，那只会抓到诊断回调自身。之后同参数复验，并针对残留初始延迟补宿主调度观测。诊断样本采集时未修改行为；后续修复及复验见下节。

## 合批测试提交边界修复的证据

`TestOnChangeBatchWindowBurstComparison` 原先直接调用 MarkDirty 后再 CaptureSync，没有正式提交门：MarkDirty 通知让 Manager 进入 Flush，可能在 CaptureSync 冻结之前消费脏数据，触发 `subject sync state has no pending dirty data`。这是测试夹具问题，不是合批窗口的生产缺陷；用 Go overlay 恢复 HEAD 的 manager.go 后重复 1000 轮仍可复现（[基线失败](benchmarks/review-20261012/batch-window-baseline-failure.txt)）。修复后 BurstComparison 与 PreservesDelivery 走正式提交边界（规则见[维护手册 §7](../maintenance/README.md#编写行为测试的边界)），原 0/5/10ms 窗口分别 20/4/2 帧、版本链、最终 payload 和冻结预算释放断言全部保留；两条交付测试重复 1000 轮通过、全部 on_change 测试 race 重复 100 轮通过，EntitySync/Policy、Nest 和 Wiring/Nest 整包通过：[重复回归](benchmarks/review-20261012/batch-window-fix-repeat.txt)、[race 回归](benchmarks/review-20261012/batch-window-fix-race.txt)、[整包回归](benchmarks/review-20261012/batch-window-fix-packages.txt)。只修改测试夹具与文档，没有修改运行时、放宽断言或重跑性能负载。
