# Saga 原生步骤性能优化（2026-10-18）

维护者 2026-10-18 批准“按推荐处理”：先逐跳打点，再做第一档两项（投影后唤醒 DataEngine outbox；去掉冗余读），然后做第二档第 3 项（等回执移出 durable 的串行回调）；第二档第 4 项（同 durable 按实体并发）与第三、四档本轮不做。夹具与基线沿用 [Saga D12 前后对照](SAGA-D12-20261018.md) 的夹具 B。样本、编排脚本与修前失败原文：[benchmarks/saga-opt-20261018](benchmarks/saga-opt-20261018/)。

## 1. 结论

- **延迟**：持续档（正向 5/s、全补偿 3/s，各 3 分钟 × 2 轮）协调器记录的完成耗时（Server）P50 正向 440 / 399 → 278 / 314 ms，全补偿 597 / 610 → 352 / 424 ms（基线 → 三项后，两轮）；压测端 P50 正向 498 / 444 → 326 / 354 ms。主要来自第一档 1：DataEngine outbox 的“暂存 → 发布”从 P50 71 ms（100 ms ticker）降到 13 ms，每笔正向 saga 少约 115 ms。第二档第 3 项在持续档几乎不改端到端延迟（它不在单笔关键路径上），把步骤消费者回调占用 durable 的时间从 P50 70 ms 降到 29 ms。
- **吞吐上限**：**没有实质提升到正向 10/s**——四个阶段在正向 10/s、全补偿 10/s、正向 20/s 都饱和崩溃。三项之后的变化是“崩溃点后移、过载时先排队后崩溃”：正向 7/s、8/s 基线（与只加打点）已有 186～281 笔终态不对，三项之后 0 笔不对、全部恰好一次，但延迟升到秒级（正向 8/s P50 5.4 s、P99 7.3 s）；全补偿 5/s 基线 43 笔不对，三项之后 0 笔不对（P50 6.8 s）。
- **新的第一瓶颈是 DataEngine 投影器**：带回执 / effect 的记录逐条处理，每条一次投影事务（P50 13～16 ms）加一次 checkpoint（WAL ack，负载下 P50 50～55 ms），单进程约 14～20 条/s；正向每笔 2 条、全补偿每笔 3 条。第二档第 3 项让步骤消费者不再限流，过载时积压从 durable 移到了投影器（投影积压峰值 5～10 → 36～81）。这正是被列为第三档的“投影器合批带回执 / effect 的记录”。
- **逐跳分解**（§3）：一笔两步正向 saga ≈ 8 次事务提交 + 9 次 findAndModify + 约 8 次事务外 majority 写（delete / update）≈ 25 次需要多数派确认的 Mongo 往返（P50 10～15 ms），另有约 30 次快读（P50 < 1 ms）；4 次 PubAck（P50 5～8 ms）；2 次 WAL strict fsync（P50 12 ms）；投影器 2 次 checkpoint fsync（不在单笔关键路径，但串行限制投影吞吐）。

## 2. 测什么

夹具 B：`wiring/saga` `TestRealNativeStepsPerformance`，正式 Mongo / NATS / DataEngine / Nest / saga Mod，两步原生步骤（debit、credit，补偿 refund），步骤体经 Nest Client 请求 handler、在事务里 `step.Complete`；`Steps` 写法（steps 变体）。配置取生产缺省（saga / outbox 轮询 100 ms、步骤超时 5 s、最多 5 次尝试、退避 100 ms..5 s），saga 流与效果流三副本；64 对账户轮转（热点档 1 对）；`GOMAXPROCS=4`。延迟口径同 D12 报告：P50～Max 从计划启动时刻到轮询（50 ms）读到持久终态；Server 是记录的 `updated_at − created_at`。每次运行逐账户核对每个操作实例恰好生效一次。

读法：

- 每步约 140～175 ms，主要是一串需要多数派确认的 Mongo 往返：协调器领取（find + findAndModify）、派发事务、saga outbox 认领（find + findAndModify）、Reserve 事务、投影事务、DataEngine outbox 认领、Complete 事务——每个 P50 10～17 ms。
- 修前最大的一跳是 DataEngine outbox 的“暂存 → 发布”（占 30%）：OutboxWorker 只按 100 ms ticker 轮询；修后 13 ms（只剩认领本身）。
- 第二档第 3 项不改单笔关键路径：等回执（P50 约 40 ms）本来就在 completion 发布之后；它改变的是 durable 的占用（回调 P50 70 → 29 ms）。
- Apply 少读的那一次 tombstone 是事务内的 find（P50 < 1 ms），每笔省 2～3 次快读，端到端看不出。
- checkpoint 的 P50 在 s1 是 26 ms、s2 / s3 是 40 ms（正向 5/s）：outbox 被唤醒后它的 Ack / 认领写与 checkpoint 的 fsync 同时落在同一块盘上的可能性变大。checkpoint 不在单笔关键路径，但决定投影器的吞吐（见 §5）。**原因尚未确认**（只有相关性，没有做隔离实验）。

| s3-compensate10-sat | 7.16 | 977 | 3539/4243 | 4885/4941 | 22/63 | 508/4645 | 16 | 55/87 | 81 | 930 | 1253 |

读法：

- base / s2 在全补偿 5/s 先在**步骤消费者**上排队（投递 + 排队 P95 4.9 s ≈ 命令截止，步骤体在截止后被取消 45～117 次），投影器跟得上（投影等待 P95 0.2 s）；s3 消费者不再排队（P95 26 ms），积压移到**投影器**（投影等待 P50 2 s、积压 54），但截止前都投影完了、没有重试放大，所以 0 笔不对。
- 投影器每条带回执 / effect 的记录 ≈ 投影事务 16 ms + checkpoint 50～55 ms（负载下），约 14～20 条/s；正向 7～8/s（14～16 条/s）、全补偿 5/s（15 条/s）正好落在这里。正向 10/s 以上投影等待超过命令截止，记录在投影时因租约过期被整笔跳过（日志里大量 “evicted an entity whose lease-fenced step was skipped”），协调器按超时重试，重试放大到崩溃——四个阶段相同。
- 过载时协调器的“到期 → 领取”也到秒级（ClaimDue P50 46～52 ms，4 个 worker 抢同一批候选），是放大后的连带结果，不是第一瓶颈（全补偿 5/s 时 s3 仍是 34 ms）。
- 第二档第 3 项在过载时的代价：同一 durable 上同一实体的前后命令不再排队，撞实体屏障交还租约（s3 全补偿 10/s 1253 次，持续档 0 次）。

## 6. 热点实体与打点开销

- 热点档（1 对账户，正向 5/s，1 分钟）：s2 Server P50 357 ms / P99 540 ms，s3 369 / 581 ms，两者都 0 次屏障挡回、核对通过——相邻两笔对同一账户间隔 200 ms，前一条早已投影完。同一 durable 上同一实体的命令间隔短于投影时间（几十毫秒）时才会撞屏障，这个档位没有覆盖；`TestRealStepsRunNativeStepsUnderTheRealNestScheduler` 的第 1 个场景（两笔并发扣同一账户）实测撞了 1 次、交还租约后同一尝试生效。
- 打点开销：s1 关闭打点的正向 5/s Server P50 368 ms / P99 666 ms，打开打点的两轮 460 / 552、378 / 624 ms——差异在轮间波动内，没有可测的代价。

## 7. 判断与建议

- 本轮三项做完后单进程原生步骤的容量（延迟 1 秒内）约为正向 5/s、全补偿 4/s；正向 7～8/s、全补偿 5/s 能全部正确完成但延迟秒级；正向 10/s、全补偿 10/s 起崩溃。崩溃前的“排队但不放大”区间是第二档第 3 项带来的。
- **不建议现在做第二档第 4 项（同 durable 按实体并发）**：s3 的步骤消费者已不是瓶颈（过载前回调 P50 17～35 ms），并发只会更快地把记录送进已经饱和的投影器，并增加实体屏障冲突。
- **再提高吞吐要动投影器**（第三档）：checkpoint 占每条特殊记录的大头（负载下 50～55 ms）。候选：①特殊记录投影后的 checkpoint 按 `CheckpointInterval` 合并（投影事务有持久事务标记，重放幂等；要论证 lease fence 与回执在重放时的判定不变）；②合批带回执 / effect 的记录（改投影契约，代价最高）；③checkpoint 的 fsync 与 Mongo 日志分盘（部署层面）。都属于 DataEngine 三大块之一的契约，需维护者决定。
- 结果处理的共享 durable（nest-result）不是瓶颈：持续档 Complete P50 15 ms、投递 + 排队 P50 10 ms；过载时它跟随上游，本轮未改。

## 8. 未验证与限制

- 单进程、单机、共享隔离环境；宿主长期后台负载（swap 已用 6.7 GB）。饱和与上限档各只有 1 个样本、2 分钟，崩溃过程有混沌成分（s2 正向 8/s 比 base 更差），只作定性比较。
- checkpoint 在 s2 / s3 变慢的原因尚未确认（§3）。
- 热点实体“间隔短于投影时间”的档位没有压测（§6）。
- 多进程、跨机、Linux 未测。
