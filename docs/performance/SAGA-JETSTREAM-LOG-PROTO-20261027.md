# Saga 协调器以 JetStream 为权威日志：原型压测（2026-10-27）

设计与语义实测见 [PROPOSAL-2026-10-27-saga-jetstream-log](../maintenance/PROPOSAL-2026-10-27-saga-jetstream-log.md)。
样本（每档一行 JSON、运行日志、语义与变异原始输出、2c 同机样本摘要）在
[benchmarks/saga-jetstream-log-proto-20261027](benchmarks/saga-jetstream-log-proto-20261027/)；完整原始结果在本机
`artifacts/perf/saga-jslog-proto-20261027/`（不随仓）。

**这是压缩矩阵**（维护者 2026-10-27 要求总时长 ≤ 30 分钟）：每档 30s、稳态窗口 [5s, 30s)，单样本为主（正向 P=4 两个样本）。
结论只给量级与趋势；与 main / 2a2b / 2c 的数字**口径不同**（§1），不算倍数。

## 0. 结论

1. **正确性**：全部 28 档的逐账户余额核对、终态复读（新实例从日志重放后逐笔比对版本与状态）都通过，没有非期望终态，
   发布结果未知 0 次（压测里没有注入故障；故障注入在正确性用例里做，见设计稿 §10）。
2. **量级**：同一进程（GOMAXPROCS=4）里协调器 + 参与方（真实 Nest + nestwal strict）+ 发起方，私有 R3 集群：
   两步正向 c1 约 80～90 TPS、端到端 P50 约 11ms；c128 约 2500～2900 TPS、P50 约 45～50ms，**c128 仍未饱和**（TPS 随并发继续上升，没测更高档）。
   补偿（三步）c128 约 1900～2000 TPS。
3. **每步的持久化次数**：协调器关键路径上 0 次本地 fsync、0 次 Mongo / Redis；每步 JetStream 消息 3 条（正向）/ 2.67 条（补偿），
   随并发上升协调器把一轮的事件合成原子批量（c128 每次发布 8～9 条事件），每步发布调用从 3.0 降到约 1.5～1.7。
   参与方 WAL fsync 每步从 c1 的 1.0 次降到 c128 的约 0.04 次（组提交）。
4. **分区与流**：P=1 / 4 / 16 在 c128 都是 2500～2900 TPS，分区数不是本机的瓶颈；P=1 时每次发布携带 33 条事件（批量更满）。
   16 分区分到 4 条流与单流在本机没有可分辨差异（三节点同机，leader 分散没有收益可测；它的价值在选主停顿与跨机吞吐，未验证）。
5. **pipelined** 与 strict 在本机 c16 / c128 同量级（600 / 2750 vs 590～740 / 2500～2900 TPS）。
6. **重放**：从完整日志接管约 30 万条消息/s（合成日志 1 万条 23ms、5 万条 116ms；压测后的真实日志 47 万条 1.1～2.0s）；
   开快照（每 2000 条事件、终态保留 2s）后接管只读快照之后的尾巴（c64 档：7074 条、33ms），吞吐同量级（1602 TPS）。
7. **与现状对比（只看量级）**：同机同日的 2c 样本里原生步骤正向 c1 P50 约 260～330ms、饱和约 7～9 TPS（main、2a2b、2c 三者同量级）；
   原型 c1 P50 约 11ms、c128 未饱和于约 2500 TPS。差距的大头来自口径（原型不跑 Mongo、去掉了步骤侧的 DataEngine 投影与收件箱、
   参与方结果在 WAL 落盘后直接发出），不是同一工作量下的倍数，见 §1、§4。

## 1. 口径与省掉的段（逐项）

| 项 | 原型 | main / 2a2b / 2c 的 Saga 压测（`saga-scan.sh`） | 对数字的影响 |
| --- | --- | --- | --- |
| Mongo | **不运行**：协调器不写 Mongo，参与方不投影 | 三节点副本集同机同盘：协调器（main）/ 步骤收件箱 / DataEngine 投影都写 | 原型没有 Mongo 的往返，也没有 Mongo journal 与 NATS / Redis 抢同一块盘（2a2b 报告 §3 证实这一项在本机很重） |

## 3. 解释

- **c1 的 11ms** 是两步各一次“协调器发事件（PubAck）→ 参与方取到命令 → Nest 事务 + WAL F_FULLFSYNC → 发结果（PubAck）→ 协调器取到结果”，
  再加启动一次、终态一次。每步只有一次本地 fsync（参与方），协调器没有。
- **吞吐随并发上升、c128 未饱和**：协调器每个分区同时只有一次发布在途，但一轮把排队的输入合成一个原子批量，并发越高批越满（P=1 时一次 33 条）；
  参与方 WAL 组提交同样摊薄 fsync。瓶颈没有出现在 JetStream 或协调器循环上；更高并发与 CPU 采样没测。
- **P=1 与 P=16 同量级**：一个分区一次一批已经够用，分区多反而批更空（P=16 每次 2.6 条）。分区数的意义在多实例分摊与故障域，不在单机吞吐。
- **补偿比正向少约 25%**：多一步（补偿）和一次拒绝。

# 第二轮：投影打开（2026-10-27 晚，维护者决定 1A / 2A / 3A 之后）

样本在 [benchmarks/saga-jetstream-log-proto-20261027/round2-projection](benchmarks/saga-jetstream-log-proto-20261027/round2-projection/)；
完整原始结果在本机 `artifacts/perf/saga-jslog-proto-20261027/round2-projection/`（不随仓）。仍是**压缩矩阵**：每档 30s、稳态 [5s, 30s)，
P=4、缺省 4 条流（G=4），正向投影打开两个样本、其余各一个样本。只给量级与趋势。

## R0. 结论

1. **投影门槛按新口径全部达标或只在一档贴线**：未投影的积压折算成 saga 笔数，峰值为在途笔数的 0.98～2.06 倍（只有 `proj-forward-s1` c64 是 2.06，
   同档第二个样本 1.22；c1 两个样本恰好 2.00）；停止加压后两边 44～88ms 归零（门槛 30s）；冷副本与观察到的终态、Mongo 账户与参与方内存全部 0 差异；
   余额逐账户核对、新实例重放复读全部通过。
2. **投影打开后吞吐与延迟明显变差**：正向 c1 P50 约 11ms → 约 45ms、c128 约 2660 → 600～810 TPS；补偿 c128 约 1710 → 634 TPS。
3. **退化不是投影进了关键路径，是同盘的 I/O 互相拖慢**（正式口径：Mongo 三节点、私有 NATS 三节点、参与方 WAL 在同一块盘上）。诊断列显示投影打开后：
   参与方一次 Nest 调用（含 strict WAL F_FULLFSYNC）4.5～8ms → 10～21ms，参与方发结果到 PubAck 0.3～2.8ms → 3～17ms，协调器发布到 PubAck 0.2～4ms → 4～16ms。
   这三段都不读写 Mongo；它们变慢只能来自 Mongo journal 刷盘与 NATS / WAL 争用同一块盘（与 [JetStream 独立与 Mongo 混合对照](benchmarks/jetstream-isolation-20261023/README.md)
   当时“同机 Mongo 持久负载让 JetStream 交付从约 1.4ms 升到约 43ms”是同一现象）。定位短测里（c16、8s、单样本）只开冷副本投影比只开参与方投影拖得更多
   （约 93～151 vs 219 TPS），冷副本投影消费者改 R1 内存、批等待 50ms 后有改善但仍是主要来源。
4. **与 2c 同机对照（只看量级）**：2c 的原生步骤正向 c1 P50 272ms、c128 5.7 TPS（过载，10 笔非期望终态）；Mongo 步骤 w16 c1 P50 198ms、c128 131 TPS。
   原型投影打开时正向 c1 P50 约 45ms、c128 600～810 TPS。口径差异见 R3，不算倍数。
5. **方向**：设计在“投影打开、同盘”的正式口径下仍满足正确性与投影门槛，量级仍高于现状；但同盘时 Mongo 的写放大会直接拖慢协调与步骤关键路径。
   生产部署应让 Mongo 与 NATS / 参与方 WAL 分盘或分机（与“Mongo 不在关键路径上”的前提一致），本机无法验证，需 Linux 跨机复测（维护者已定有机器再做）。

## T0. 结论

1. **本机正式口径（参与方投影开、冷副本关、Mongo 与 NATS 同盘）**：正向 c1 约 31 TPS / P50 30ms，c128 约 1650～1790 TPS / P50 约 70ms；补偿 c128 约 1120 TPS。
   介于“全关”（c128 约 2660）与第二轮“全开”（约 600～810）之间。余额、复读、Mongo 账户与内存逐账户全部通过；停止加压后 40～100ms 追平。
   **积压门槛（按笔 ≤ 2 × 在途）有 6 档超出**：正向 s1 c1 2.50、c64 5.96、c128 2.13，s2 c64 2.19，补偿 c1 8.67、c16 3.96（其余 1.35～2.00）。
   都是 500ms 采样到的短时峰值（追平只要 40～100ms），来自现行 DataEngine 投影器的调度节奏，不是持续落后；按规定如实判为未达标，没有改投影器。
2. **云 Mongo（本轮 ping P50 7.8ms，不是 10-26 的约 60ms）**：只把参与方投影的库换成云库后，**关键路径回到“全关”的量级**（c1 82.6 TPS / P50 11.1ms，
   c128 约 1960～2690 TPS）——本机同盘的 I/O 争用没有了，关键路径本来就不碰 Mongo。
3. **云上参与方投影器跟不上**：负载期投影速率约 540～590 条/s，追平期约 440～505 条/s（≈ 250～290 笔两步 saga/s），与并发无关；
   c16 起积压持续增长（停止加压时 c16 1.26 万条、c64 7.19 万条、c128 4.1 万～14.4 万条），按笔折算是在途的 395～560 倍。c16 追平 28.7s、c128 重跑追平 290s，
   c64 在 120s 上限内没追平（剩 1.1 万条）。投影器每次 Mongo 调用平均承载约 50 条记录（每条 0.02 次调用），所以上限不在往返次数，
   在每批的耗时（约 10 次调用/s，单次约 100ms，含多数派写与提交）。按规定没有为达标改投影器，可选改法见 T4。
4. **追平后核对**：c1、c16、c128（重跑）Mongo 账户与参与方内存逐账户一致；c64 没追平，未核对。
5. **尚未确认**：云上第一次 c128 的余额核对报 false（同一档的冷 Mongo 账户与内存逐账户 0 差异、复读一致、非期望终态 0）。当时的核对用 5s 读超时、
   不区分“读超时”与“余额不符”，无法判断是哪一种；加了区分并把读超时放宽到 30s 后重跑同档全部通过（读错误 0、不符 0、投影失败 0、Nest 错误 0）。
   同一档还有一处对不上的数：停止加压时的积压 4.1 万条低于负载期采样到的峰值 11.1 万条（负载期投影速率只有约 560 条/s，积压不应在加压时下降）。
   两处原因都尚未确认，不当作已排除；后续要在同条件下复现并保留投影器与 WAL 的逐秒计数。
6. **与现行的对照（只看量级，同一网络条件）**：同时段云库（RTT 约 8ms）上，main 原生正向 c4 / c16 约 5.3 / 5.2 TPS、P50 755 / 3040ms，Mongo 步骤 w16 c128 67 TPS；
   2c 同三档 5.3 / 5.2 TPS、P50 743 / 2994ms，76 TPS。原型关键路径 c16 468 TPS / P50 33ms；但它的参与方持久化（投影）持续吞吐上限约 250～290 笔/s，
   高于现行的饱和点，低于原型自己的关键路径吞吐。

1. **云 Mongo（本轮 ping P50 64.26ms，单文档更新 c1 P50 68ms；只把参与方投影的库换成云库）**：
   - **准入开**：积压有界——峰值 c64 2844 笔、c128 3053 笔（高水位 2500，超调 14～22%），停止加压后 2.8s / 3.5s 追平；
     **有效持续吞吐（只计接纳并完成的）c64 690 笔/s、c128 735 笔/s**，就是投影器的速率（负载期 1365～1452 条/s ÷ 2）；准入关闭时间占 55% / 72%。
     c16 输入低于投影速率，准入从不关闭（456 笔/s）。
   - **准入关**：c64 / c128 关键路径照跑 1643 / 2815 笔/s，但积压无界增长——峰值 6.0 万 / 12.9 万条，停止加压后 53s / 107s 才追平（这段时间 Mongo 落后于内存）。
   - **原型在云上（RTT 约 64ms、8 通道、单参与方）可承诺的持续吞吐约 690～735 笔/s（两步正向）**，由参与方投影器决定；超过的部分在发起方快速失败（`ErrBackpressure`）。
2. **本机隔离 Mongo（同机同盘）**：投影器（8 通道）跟得上关键路径，积压峰值 20～190 笔，准入开 / 关两组都从不关闭准入、结果同量级：正向 c16 / c64 / c128 约 179 / 608～633 / 1147～1210 笔/s，
   补偿 c64 407 笔/s。**本机可承诺的持续吞吐由关键路径决定，本轮约 1150～1210 笔/s（c128）**；比第三轮同口径（约 1650～1790）低，按宿主负载处理（开跑前 loadavg 4.9～7.8），单样本，未归因。
3. **核对**：全部 13 档余额、复读、Mongo 账户逐账户一致；非期望终态 0（在途的都到了终态）；被拒的 saga 是终态 `Rejected`、没有任何步骤，余额核对只按完成的推算、全部相符（被拒的无副作用）。
4. **推荐参数**见设计稿 §12a（依据：高水位 = 投影器持续速率 × 允许的追平时间 ÷ 每笔记录数）。
