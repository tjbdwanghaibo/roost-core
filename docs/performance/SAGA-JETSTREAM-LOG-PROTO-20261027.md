# Saga 协调器以 JetStream 为权威日志：原型压测（2026-10-27）

设计与语义实测见 [PROPOSAL-2026-10-27-saga-jetstream-log](../maintenance/PROPOSAL-2026-10-27-saga-jetstream-log.md)。
样本（每档一行 JSON、运行日志、语义与变异原始输出、2c 同机样本摘要）在
[benchmarks/saga-jetstream-log-proto-20261027](benchmarks/saga-jetstream-log-proto-20261027/)；完整原始结果在本机
`artifacts/perf/saga-jslog-proto-20261027/`（不随仓）。

**这是压缩矩阵**（维护者 2026-10-27 要求总时长 ≤ 30 分钟）：每档 30s、稳态窗口 [5s, 30s)，单样本为主（正向 P=4 两个样本）。
结论只给量级与趋势；与 main / 2a2b / 2c 的数字**口径不同**（§1），不算倍数。

## 0. 结论

1. **正确性**：全部 28 档的逐账户余额核对、终态复读（新实例从日志重放后逐笔比对版本与状态）都通过，没有非期望终态，
   发布结果未知 0 次（压测里没有注入故障；故障注入在正确性用例里做，见设计稿 §10）。
2. **量级**：同一进程（GOMAXPROCS=4）里协调器 + 参与方（真实 Nest + nestwal strict）+ 发起方，私有 R3 集群：
   两步正向 c1 约 80～90 TPS、端到端 P50 约 11ms；c128 约 2500～2900 TPS、P50 约 45～50ms，**c128 仍未饱和**（TPS 随并发继续上升，没测更高档）。
   补偿（三步）c128 约 1900～2000 TPS。
3. **每步的持久化次数**：协调器关键路径上 0 次本地 fsync、0 次 Mongo / Redis；每步 JetStream 消息 3 条（正向）/ 2.67 条（补偿），
   随并发上升协调器把一轮的事件合成原子批量（c128 每次发布 8～9 条事件），每步发布调用从 3.0 降到约 1.5～1.7。
   参与方 WAL fsync 每步从 c1 的 1.0 次降到 c128 的约 0.04 次（组提交）。
4. **分区与流**：P=1 / 4 / 16 在 c128 都是 2500～2900 TPS，分区数不是本机的瓶颈；P=1 时每次发布携带 33 条事件（批量更满）。
   16 分区分到 4 条流与单流在本机没有可分辨差异（三节点同机，leader 分散没有收益可测；它的价值在选主停顿与跨机吞吐，未验证）。
5. **pipelined** 与 strict 在本机 c16 / c128 同量级（600 / 2750 vs 590～740 / 2500～2900 TPS）。
6. **重放**：从完整日志接管约 30 万条消息/s（合成日志 1 万条 23ms、5 万条 116ms；压测后的真实日志 47 万条 1.1～2.0s）；
   开快照（每 2000 条事件、终态保留 2s）后接管只读快照之后的尾巴（c64 档：7074 条、33ms），吞吐同量级（1602 TPS）。
7. **与现状对比（只看量级）**：同机同日的 2c 样本里原生步骤正向 c1 P50 约 260～330ms、饱和约 7～9 TPS（main、2a2b、2c 三者同量级）；
   原型 c1 P50 约 11ms、c128 未饱和于约 2500 TPS。差距的大头来自口径（原型不跑 Mongo、去掉了步骤侧的 DataEngine 投影与收件箱、
   参与方结果在 WAL 落盘后直接发出），不是同一工作量下的倍数，见 §1、§4。

## 1. 口径与省掉的段（逐项）

| 项 | 原型 | main / 2a2b / 2c 的 Saga 压测（`saga-scan.sh`） | 对数字的影响 |
| --- | --- | --- | --- |
| Mongo | **不运行**：协调器不写 Mongo，参与方不投影 | 三节点副本集同机同盘：协调器（main）/ 步骤收件箱 / DataEngine 投影都写 | 原型没有 Mongo 的往返，也没有 Mongo journal 与 NATS / Redis 抢同一块盘（2a2b 报告 §3 证实这一项在本机很重） |
| 协调器存储 | JetStream 事件（PubAck，服务端不逐条 fsync，前提 1） | main：Mongo 事务；2a2b / 2c：Redis 脚本 + `appendfsync always`（macOS F_FULLFSYNC） | 原型关键路径没有本地 fsync |
| 步骤侧（原生步骤） | 参与方实体里的回执 + 实体锁；结果在 WAL 落盘后直接发 | `_dataengine_step_operations` Reserve 事务、lease fence、实体屏障、DataEngine 投影后经 outbox 发 completion | 现行原生步骤的上限就是步骤侧投影器（约 10 TPS，SAGA-CLOUD-MONGO §4.2）；原型把它移出关键路径。生产里投影仍要做，只是异步（单 mutation 快路），其持续吞吐本轮**没有测** |
| 参与方实体 | 手写 DAO（补丁 `bal` / `r.<opKey>`），不经代码生成；WAL 从不 ack | 生成的 Entity / DAO，投影后 checkpoint | 原型少了 checkpoint 写与投影事务 |
| NATS | 私有三节点（2.14.5，R3，文件存储），数据在 scratchpad（同一 APFS 卷） | `~/.roost-it` 隔离三节点 | 同类部署；原型的流只有本测试一个使用者 |
| 观察方式 | 发起方用 JetStream 有序消费者读终态事件（推送，无轮询）；服务端延迟 = 终态事件 `updated_at − created_at`（协调器时钟，ms） | 夹具约 50ms 轮询读终态；服务端口径各自定义 | 原型的观察延迟更小 |
| 时长 | 每档 30s，稳态 [5s, 30s)，单样本为主 | 每档 60s，稳态 [10s, 60s)，两样本 | 原型样本更短、噪声更大 |
| 未实现的功能 | Resume / 代际、人工补偿、定义版本、业务键查询、指标、按 sid 路由、App fail-stop 接线 | 全部 | 省掉的是功能，不是每步的持久化 |
| 机器 | 本机 macOS，GOMAXPROCS=4，loadavg 开跑前 5.9～7.6（本机基础负载），交流电 | 同机，同日更早 | — |

## 3. 解释

- **c1 的 11ms** 是两步各一次“协调器发事件（PubAck）→ 参与方取到命令 → Nest 事务 + WAL F_FULLFSYNC → 发结果（PubAck）→ 协调器取到结果”，
  再加启动一次、终态一次。每步只有一次本地 fsync（参与方），协调器没有。
- **吞吐随并发上升、c128 未饱和**：协调器每个分区同时只有一次发布在途，但一轮把排队的输入合成一个原子批量，并发越高批越满（P=1 时一次 33 条）；
  参与方 WAL 组提交同样摊薄 fsync。瓶颈没有出现在 JetStream 或协调器循环上；更高并发与 CPU 采样没测。
- **P=1 与 P=16 同量级**：一个分区一次一批已经够用，分区多反而批更空（P=16 每次 2.6 条）。分区数的意义在多实例分摊与故障域，不在单机吞吐。
- **补偿比正向少约 25%**：多一步（补偿）和一次拒绝。

## 4. 与现状的对照（只看量级）

同机同日 2c agent 的样本（`2c-summary.txt`，口径见 2a2b 报告 §1；`base0` = main，`ab` = 2a2b，`new` = 2c，`newram` = 2c 的权威 Redis AOF 放内存盘的诊断）：

| 场景 | main / 2a2b / 2c（共享盘） | 2c 内存盘诊断 | 原型 |
| --- | --- | --- | --- |
| 原生步骤正向 c1 | P50 约 260～330ms，约 3～3.8 TPS | P50 212ms | P50 约 11ms，约 80～90 TPS |
| 原生步骤正向饱和 | 约 7～9 TPS（c32～c64） | 约 13 TPS | c128 约 2500～2900 TPS，未饱和 |
| 原生步骤补偿饱和 | 约 5～6 TPS | 约 7 TPS | c128 约 1900～2000 TPS，未饱和 |
| Mongo 步骤正向 w16 饱和 | main 约 43～46，2a2b 约 20～22，2c 约 125～140（P50 25s 以上） | 约 275 | （无对应场景） |

这张表说明的是“现状的上限在哪一段、原型把那一段拿掉之后剩下的是什么量级”，不是同一工作量的倍数：
现状原生步骤的上限在步骤侧的 DataEngine 投影（逐条 Mongo 事务），原型不跑 Mongo、把投影移出关键路径，同时不承担 Mongo 的盘竞争。
要得到可比的倍数，需要在同一环境里给原型补上异步 Mongo 投影（设计稿 §12）并让它在压测期间运行，量它的持续吞吐与积压。

## 5. 正确性用例与变异（摘要，详见设计稿 §10）

- `-race` 全套通过（语义、端到端、kill -9）：`race-run.txt`。
- 变异 `SAGAJS_MUTATE=nofence`（发布不带期望序号）：`TestFenceRejectsStaleWriter` 失败，`command s2:f:0:1 dispatched 2 times`、`saga s2 versions [1 2 3 1 2 3]`（`mutate-nofence.txt`）。
- 变异 `SAGAJS_MUTATE=noreceipt`（参与方不查回执）：`TestEndToEndDuplicateCommandsAndResults` 失败，`balances do not match the terminal states (sum 64000002, want 64000000)`（`mutate-noreceipt.txt`）。
- 原型自身缺陷：时间轮第一版把“当前 tick 内未到期”的条目推迟一整圈，`TestEndToEndLateSuccessReopensAndCompensates` 8 次红 3 次
  （`late-0 v3 completed f1 a1`：截止没触发，迟到的成功被当成正常成功）；修正后 8/8 绿，并在 `TestWheelDeliversDueEntriesOnce` 加了断言
  （该断言是修正后补的，没有在旧代码上单独证明变红）。
