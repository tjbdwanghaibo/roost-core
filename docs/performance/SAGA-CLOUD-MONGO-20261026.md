# Saga 并发吞吐：云 Mongo 与本机 Mongo 对照（2026-10-26）

Saga 性能改造的第 0 步，只做测量，不改产品代码。维护者要求用云 Mongo 重测，并且统计并发吞吐，不能只看单线程（原话：“云 db 可能有延时，最好统计并发的吞吐量，单线程不准确”）。本轮在同一台机器上，用同一套闭环并发扫描分别压本机 Mongo 和云 Mongo，回答三个问题：换成独立的 Mongo 后饱和 TPS 是多少；饱和时时间花在哪个阶段；Redis 权威方案能消掉哪几段、收益上限是多少。

样本放在 [benchmarks/saga-cloud-mongo-20261026](benchmarks/saga-cloud-mongo-20261026/)。往返次数的源码审计见 [Redis 权威方案审查 §6](https://github.com/tjbdwanghaibo/roost-core/blob/132ed79f689df01dc8df0ea3a44e9a768ee126d9/docs/maintenance/PROPOSAL-2026-10-26-redis-authority-review.md#6-往返次数审计)（`5b6b846d`）；本报告逐项核对了那张表。

## 0. 结论

1. **换成云 Mongo 后吞吐没有提高，反而降了 6～15 倍。** 本轮测量时，本机到云 Mongo 的往返约 58～61ms（ping P50 57.6ms）。下午那份未提交短测记的是 7～16ms，两次测的不是同一条网络条件。

   | 场景（闭环饱和点） | 本机 Mongo（同机，RTT 0.06ms） | 云 Mongo（RTT 约 60ms） |
   | --- | ---: | ---: |
   | 原生步骤正向 | 约 10 TPS（c32） | 0.88 TPS（c4），c16 起出现 Failed |
   | 原生步骤全补偿 | 约 6 TPS（c16～c64） | 0.62 TPS（c4），c16 起出现 Failed |
   | Mongo 步骤正向，消费 worker 2（历史口径） | 约 40～45 TPS（c16～c128） | 2.08 TPS（c16），c32 起出现补偿 / Failed |
   | Mongo 步骤正向，消费 worker 16 | 约 43 TPS（c32～c128） | 6.72 TPS（c128），无错误 |

2. **两边的瓶颈都不在 Mongo 服务端，而在框架里的串行工作池：每个池的吞吐 ≈ worker 数 ÷（每项串行往返数 × RTT + 服务端耗时）。**
   - 云 Mongo 的服务端写均值只有 1～5ms。单文档事务在 128 并发下仍能线性扩到 790 次/s，没有饱和。
   - 本机 Mongo 单文档事务在 128 并发下有 6888 次/s。Saga 压满时，本机 Mongo 每秒只提交约 350 个事务。
   - **原生步骤卡在 DataEngine 投影器。** 投影器对带回执 / effect 的记录逐条处理，一笔交易两条。本机约 100ms/笔（投影事务 17ms × 2，加 checkpoint 约 57ms），上限约 10 TPS；云上投影事务约 530ms/条（实测约 9 次往返），上限约 0.94 TPS。原生步骤没有可调的并发参数。
   - **Mongo 步骤卡在当前配置下最先排满的那个池。** 本机 worker 2 时卡在步骤消费者，worker 16 时卡在发布器（4 个 worker 串行“领取 → PubAck → 删除”）。云上 worker 2 时卡在结果消费者（completion apply 约 480ms，8 次往返），worker 16 时卡在协调器（4 个 worker 串行“领取 + 派发事务”）。
3. **Redis 方案的收益上限取决于 Redis 放在哪里。** 按实测各阶段占比推算（§6）：
   - **延迟**：并发 1 时，可被 Redis 替换的段占关键路径的比例，本机 58%（原生）/ 45%（Mongo 步骤），云上 88% / 59%。
   - **吞吐**：只有当被替换的段正好是饱和的那个池时，Redis 才能抬高上限。原生步骤的上限是投影器；方案把投影移出关键路径，但 Store Service 的投影吞吐如果仍是逐条串行，持续吞吐的上限不会变，积压只会转到 Redis 里。
   - **与“不换存储先减往返”的对照**：Redis 也和 Mongo 一样隔着 60ms 时，每个协调事务从 4～8 次往返降到 1～2 次。这部分收益和方案审查 §6.4 列的“先减往返”（O1～O5）重叠约 2/3（往返数按源码估算）。
4. **领取查询有确定的内存排序问题**（协调方追加的核对，§5）：
   - 两条领取查询现行索引都是阻塞 SORT，要检查全部到期文档。
   - 云上积压 1 万条时，单次领取约 419ms（saga）/ 648ms（outbox），服务端执行 724 / 584ms。
   - 加上带 `_id` 的索引，或者排序去掉 `_id`，就变成 SORT_MERGE / 直接走索引，只检查 1 条文档，单次领取降到约 1 个 RTT。
   - 本轮扫描的积压不超过并发数（≤128），所以在饱和点附近，claim 的占比**不算明显偏高**。
5. **过载时的正确性**：
   - 过载档的 Failed 全部是超时类：命令在队列里过了截止，或 Mongo 的客户端超时 / 提交结果未知。没有写冲突。
   - 两个过载档各有 1 个账户少了 1：本机原生正向 c128 和云上原生全补偿 c16。日志显示的是同一种形状：迟到成功触发重开补偿，之后 5 次补偿命令都在执行前过了截止。按设计这会进入 ManualRequired，但夹具只记了第一次读到的终态（Failed），最终状态**尚未确认**。
   - 云上原生 c32 / c64 / c128 的“核对未通过”没有不符账户。原因是夹具的总 context 在排空阶段到期，核对查询本身没能执行，属于核对未完成，不能算作数据错误。

**是否发版：否。** 本轮只交付诊断夹具、脚本和报告，下一步由维护者决定（§7）。

## 1. 环境与口径

- **代码**：基线 main `ce49b3c3`。测量期间 Saga / DataEngine 源码与 `5b6b846d` 相同（之间只有物理房间、Nest 批量时间片和文档的改动）。夹具改动见 §8。
- **机器**：macOS / arm64，10 逻辑 CPU，交流电源。机器长期有桌面与 MDM 后台负载（sysmond 持续约 90% 单核）。每档开跑前用门控等 1 分钟 loadavg 低于 6，实际开跑时 2.8～5.9，每档前后的 load 见各 `runs.tsv`。测试进程 GOMAXPROCS=4，与 Saga 历史口径一致；Linux 未测。
- **本机 Mongo**：`~/.roost-it` 长期隔离副本集，8.0.32，3 节点，同机同盘。
- **云 Mongo**：维护者提供的云副本集，8.2.3-r1，`hello` 显示 2 个数据节点，自动连到 primary。连接串不带 `replicaSet=`，驱动自动发现拓扑。夹具的副本集要求用 `hello.setName` 判定（`infra/storage/mongo/driver/client.go:112`），不依赖 URI 参数，所以没有做任何处理。主机名、账号和连接串没有进入日志、样本或本文：测试输出经过脱敏过滤后才落盘，提交前用脚本核对，命中 0。
- **NATS**：本机隔离 JetStream 三节点，测试流 Replicas=3，两边相同。
- **持久口径**：生产默认，即 majority + j:true、事务、租约、幂等，没有放宽。
- **闭环并发**：N 个发起者各自“启动一笔 → 等到持久终态 → 启动下一笔”，持续 60 秒，然后停止发起并排空在途。
  - **稳态成功 TPS**：只计 `[10s, 60s)` 窗口内到达期望终态的笔数 ÷ 50 秒，排除爬升和排空阶段。
  - **服务端延迟**：Mongo 步骤夹具取“调用 StartSaga → 终态 Apply 提交返回”（同进程单调时钟）；原生夹具取 `updated_at − created_at`（Mongo 毫秒精度）。
  - 每档一个样本。
- **场景**：
  - **原生步骤**：真实 Nest + DataEngine，两步 debit / credit，账户对数 256，避免并发度之外叠加同账户屏障；全补偿时 credit 被业务拒绝，再补偿 debit。
  - **Mongo 步骤**：两步 reserve / ship，每个订阅 MongoWorkers=2（历史口径），另跑 16 作对照。协调器、发布器各 4 个 worker，CoordinatorBatch=3。
- **逐笔追踪**：所有档都开了 hoptrace。
  - Mongo 步骤用 `saga-timeline.py` 重建每笔的关键路径，各段之和精确等于整笔时长。出现重试 / 重复事件的过载档无法这样拆，改看逐跳累计。
  - 原生步骤用逐跳累计（每笔两步合计），各跳之间有交叠，加总会比实际延迟高约 10～30%，所以只用来看占比。
  - 关掉追踪对照：本机原生正向 c32 关闭 9.04 TPS、开启 9.96 TPS，单样本，看不出追踪拖慢了吞吐。
- **Mongo 侧指标**：每档前后各取一次 `serverStatus`：opLatencies 的写均值、事务提交数、WiredTiger 日志同步。云库的计数覆盖整个实例，可能包含其他使用者的流量；云主机的 CPU、磁盘和复制监控拿不到。

## 4. 阶段拆分：饱和时时间花在哪

### 4.1 Mongo 步骤（逐笔时间线，各段之和等于整笔时长，单位 ms / 笔）

| 段 | 本机 c1 | 本机 w2 c32 重跑（饱和） | 本机 w16 c128（饱和） | 云 c1 | 云 w16 c128（饱和） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 协调 Mongo 事务（启动 + 两次派发 + 两次完成推进） | 64 | 86 | 91 | 1497 | 1652 |
| 协调等待 + 认领 | 25 | 95 | 192 | 210 | **16173** |
| 步骤 Mongo 事务（预留 + 业务 + 回执提交） | 65 | 68 | 69 | 1096 | 1106 |
| outbox 排队（等发布器） | 23 | 68 | **2454** | 62 | 87 |
| NATS 命令 / 结果交付（含消费者排队） | 22 | **356** | 98 | 7 | 7 |
| 消费槽 | 0.2 | 53 | 0.1 | 0.3 | 0.2 |
| **整笔 P50** | 198 | 720 | 2959 | 2851 | 20534 |

每个饱和点由哪个池决定：

- **本机 w2**：命令卡在步骤消费者（每个订阅 2 个 worker）前面，表现为 command_transport / 消费槽的排队。
- **本机 w16**：卡在发布器。outbox 排队约 2.5s，发布器 4 个 worker 每条串行 ClaimOutbox、PubAck、AckOutbox。
- **云 w2**：卡在结果消费者。complete.apply 每次约 425ms，2 个 worker 每秒约处理 4 个完成，约等于 2 笔交易，与实测 2.08 吻合。
- **云 w16**：卡在协调器。4 个 worker 每批串行 ClaimDue 加最多 3 次派发事务（每次约 250ms）。

## 5. 领取查询的索引与排序

协调方追加的核对：`9dd9806a` 把领取改成逐条执行 FindOneAndUpdate，排序是 `{next_run_at:1,_id:1}` / `{next_attempt_at:1,_id:1}`，但 `_id` 不在索引里。

**方法**：工具是 `scripts/perf/saga-claim-explain`，查询形状照抄 `framework/saga/mongo_store.go:227-230,377-380`，索引照抄 `:82-94`，对 findAndModify 做 `explain("executionStats")`。

- **积压构造**：backlog 条到期文档，三种非终态轮流；另加同样多的已终态文档（saga）或已被领取的文档（outbox）作为历史。
- **实测领取**：每档另外真实执行 200 次领取，被领取的文档不再到期。

| 查询 | 索引 / 排序 | 积压 | 本机：SORT / 检查文档 / 执行 ms / 领取均值 ms | 云：SORT / 检查文档 / 执行 ms / 领取均值 ms |
| --- | --- | ---: | --- | --- |
| ClaimDue | 现行 | 1000 | **SORT** / 1000 / 4 / 10.9 | **SORT** / 1000 / 73 / 99.3 |
| ClaimDue | 现行 | 10000 | **SORT** / 10000 / 14 / 13.2 | **SORT** / 10000 / **724** / **418.9** |
| ClaimDue | 加 `{status:1,next_run_at:1,_id:1}` | 10000 | SORT_MERGE / 1 / 0 / 10.0 | SORT_MERGE / 1 / 3 / 68.4 |
| ClaimDue | 排序去掉 `_id` | 10000 | SORT_MERGE / 1 / 0 / 9.8 | SORT_MERGE / 1 / 3 / 67.9 |
| ClaimOutbox | 现行 | 1000 | **SORT** / 1000 / 4 / 11.6 | **SORT** / 1000 / 58 / 118.4 |
| ClaimOutbox | 现行 | 10000 | **SORT** / 10000 / 7 / 16.8 | **SORT** / 10000 / **584** / **648.4** |
| ClaimOutbox | 加 `{next_attempt_at:1,_id:1}` | 10000 | 无 SORT / 1 / 0 / 10.7 | 无 SORT / 1 / 2 / 71.2 |
| ClaimOutbox | 排序去掉 `_id` | 10000 | 无 SORT / 1 / 0 / 10.2 | 无 SORT / 1 / 1 / 68.1 |

1000 积压下两种候选写法同样是 1 文档、0～4ms，完整数据见 `claim-explain-{local,cloud}.json`。

- **结论：怀疑成立。** 现行写法每次领取都要对全部到期文档做阻塞内存排序（outbox 还会扫到已被领取的索引项，keys 为积压的 2 倍）。
  - 本机服务端只多十几毫秒，不明显。
  - 云上积压 1 万条时，单次领取约 0.42s / 0.65s。按 CoordinatorBatch=3 逐条领，一次 ClaimDue 约 1.3s。积压越多，排空越慢。
  - 两种候选写法都让服务端执行降到 0～3ms，只检查 1 个文档，领取耗时只剩 1 个 RTT。
- **与本轮扫描的关系**：扫描中的积压不超过并发数（≤128），claim 的服务端代价很小。
  - 云 w16 c128 饱和时，协调器 worker 每笔忙约 148ms 在领取（0.67 次 × 220ms），约 500ms 在两次派发事务，领取约占 23%，主要是往返，不是排序。
  - 本机饱和点的 claim 每次约 39～41ms（批量 3 的逐条往返）。
  - 所以饱和点附近 **claim 占比不算明显偏高**。内存排序是“积压之后恢复”场景里的问题：停机或 Mongo 抖动之后积压上万条，正好是需要快速排空的时候。
- **建议（只出建议，不改代码）**：
  - 推荐 A：保留排序，新增 `{status:1,next_run_at:1,_id:1}` 与 `{next_attempt_at:1,_id:1}`，并评估能否替换现有 `claim_due` 索引。`lease_until` 改在 FETCH 阶段过滤，被领取但还没处理完的文档数受 worker × batch 限制，影响很小。
  - B：排序去掉 `_id`。同一毫秒到期的记录之间顺序不再稳定。按现有规则，正确性不依赖这个顺序，但需要契约复核。
  - 改索引前要先确认已有部署的索引迁移策略（`IndexMigrationPolicy`）。

## 6. Redis 权威方案的收益推算

**口径**：只用本轮实测的段占比和往返数。“可替换段”按设计稿划定：

- 原生步骤：协调事务、唤醒 / 认领、步骤预留、投影排队与投影事务（方案 §1 / §4 / §6）；
- Mongo 步骤：只算协调部分，业务事务按方案 §6 不迁移。

| 场景 | 可替换段占关键路径（c1） | Redis 与 Game 同地域 | Redis 与 Mongo 同样隔 60ms |
| --- | --- | --- | --- |
| 原生步骤，本机 | 58%（约 190ms / 320ms） | 可替换段（约 185ms）换成约 11 次 Redis 提交 × 约 4ms（本机 AOF always 单脚本 P50 4.0ms，§6.1）≈ 44ms → c1 延迟最多降约 40% | — |
| 原生步骤，云 | 88%（约 3.8s / 4.4s） | 剩下“outbox + NATS + 本地 WAL + 冷加载”约 0.54s，加约 11 次同地域 Redis 提交，约 0.6s，**约 5～6 倍** | 每次提交 1～2 次往返 × 约 11 次 ≈ 0.7～1.3s，加上不可替换段约 0.54s，c1 约 1.2～1.9s，**约 1.8～2.8 倍** |
| Mongo 步骤，本机 | 45%（约 90ms / 200ms） | c1 最多从 198 降到约 130ms（约 5 次 Redis 提交 × 4ms 补回） | — |
| Mongo 步骤，云 | 59%（约 1.7s / 2.9s） | 降到约 1.2s（业务事务的 1.1s 仍在） | 协调约 7 次操作 × 1～2 次往返 ≈ 0.4～0.8s，加上业务事务，约 1.6～2.0s |

**吞吐上限只看饱和的那个池有没有被替换**：

- **原生步骤**：投影器是上限，本机约 10 TPS，云上约 0.94 TPS。方案让交易不再等投影，但 Store Service 要以同样的速率持续投影。投影仍是逐条事务的话，**持续吞吐的上限不变**，积压会在 Redis 里累积，最后触发背压。真正抬高上限需要 Store Service 分区并发或合批，或者审查 §6.4 的 O4（投影事务从 9 次往返合并到约 4 次，投影吞吐约翻倍）。去掉投影之后，下一个上限是步骤 durable 的串行回调：本机约 43ms/步、云上约 365ms/步。
- **Mongo 步骤**：
  - 云上 w16 卡在协调器，w2 卡在结果消费者，这两段都可以替换。协调器每条从约 6 次往返（领取 + 派发事务）降到约 2 次，池的上限约 ×3（6.7 → 约 20 TPS）；再往上会碰到步骤消费者（每步约 9 次往返，约 550ms，w16 约 29 步/s）。
  - 但同样的上限，**加 worker 也能线性抬高**：w2 → w16 已经实测 ×3.2。这一层是配置能解决的问题，不是存储能解决的问题。
  - 本机 w16 卡在发布器（outbox 领取 + PubAck + 删除），换 Redis 后每条省约 2 次本机往返，量级约 20ms。

### 6.1 本机 Redis 持久提交的代价（对照）

私有 redis-server 8.10.1，`appendonly yes`、`appendfsync always`，单节点，没有副本确认，与 Mongo majority **不是同一持久等级**。用一个 Lua 脚本做 HSET + XADD：

| 并发 | 次/s | P50 / P99 ms |
| ---: | ---: | --- |
| 1 | 242 | 4.0 / 7.8 |
| 16 | 1916 | 8.1 / 13.0 |
| 64 | 7424 | 8.8 / 13.6 |

同盘 Mongo 单文档事务是 10.7 / 17.0ms（c1）。本机上每次持久提交只省约 60%，因为两边都要等本地 fsync。Redis 要加副本确认（`WAITAOF 1 1`）的话，还要再加一次副本往返。同地域、带副本的 `WAITAOF` 对照没有测（§7）。

**综合判断**：在这条 60ms 的链路上，任何方案的收益都首先来自“减少串行往返”和“同地域部署”。Redis 能拿到的往返收益约有 2/3 与“先减往返”（O1～O5）重叠（往返数按源码估算）。吞吐上限则要靠投影器并发 / 合批和协调器 / 消费者的池大小。所以本轮数据支持方案审查的排序：先测同地域，再做第 1.5 步（先减往返），然后再判断第 2～4 步是否值得做。

## 7. 未完成项与限制

- **同地域对照没测**：本机 Mongo 是同机同盘，不等于“同地域独立 Mongo”。同地域时 RTT 约 1ms、存储独立，延迟形状会介于两者之间。需要在云上同地域放一台压测机。
- **云上网络条件只有本轮一个时段**：本轮 ping 约 58～61ms，下午短测是 7～16ms，原因没有查（可能是链路或代理路径不同）。所有云上数字都只对 60ms 这个条件成立。没有拿到 `_ALT` 备选库，也没有测它。

- **门禁**：main 在 `ce49b3c3` 时根包门禁有两项已知失败（`cmd/physics-viewer` 分层），本轮没有修。rebase 到 `5b6b846d`（含 `a5cae602` 删除 cmd/physics-viewer）后重跑：`GOWORK=off go test -count=1 .` 通过。同时通过的还有：
