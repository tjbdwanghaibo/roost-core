# Saga D12 前后对照（2026-10-18）

DESIGN-TODO D12 方向 A（`framework/saga.NativeStep`、`wiring/saga.Steps`、`wiring/dataengine.SubscribeEffects`）的性能验证项。基线 `79d15114`（D12 之前）对 `63b63fa8`（D12 合入），同机、同参数、同环境，交替运行，测量期间机器上没有本轮启动的其他测试或构建（测试二进制事先编好，编排脚本只执行二进制）。样本与编排脚本：[benchmarks/saga-d12-20261018](benchmarks/saga-d12-20261018/)。

环境：Apple M5（10 核）、32GB、go1.27.0；共享隔离环境（Mongo 副本集 28117–28119、NATS 三节点 15222–15224）；开测时 load average 5～6、swap 已用 6.7GB/8GB（宿主长期后台负载）。

## 3. 原生步骤的单进程容量（新发现，不是 D12 引入）

glue 与 steps 在同一处饱和，限制在两者共用的路径上：

1. **一个 durable 在一个进程里逐条处理**：nats.go `Consume` 的回调在核心订阅的单个 goroutine 里串行调用（`jetstream/pull.go` `internalHandler`），`SubscribeDataEngineStep` 一条命令占住消费者的时间 = Reserve（Mongo 事务）+ Nest 提交（strict WAL）+ 等回执投影（`waitReplay` 25ms 轮询）。实测正向满载时 Nest 请求 P50 约 19ms，相邻两条 debit 的步骤体间隔 P50 约 54～69ms，单个 durable 约 14～18 条/s。
2. **投影器单条处理带回执 / effect 的记录**：原生步骤的记录都带 lease fence 回执与 completion effect，`isLocalBatchRecord` 为 false，每条前后各一次 checkpoint、不合批（`framework/dataengine/engine/projector_replay.go`）。全补偿每笔三条这样的记录（debit、被拒的 credit、refund），所以全补偿比正向更早饱和。
3. 过载时命令在队列里等过截止 → 协调器按步骤超时发下一次尝试 → 队列更长（重试放大）。

同一 durable 的逐条处理还意味着：投影停顿时，一条在等自己回执的命令会挡住这个 durable 上后面的全部命令，直到它的截止（真实 Nest 用例 `TestRealStepsRunNativeStepsUnderTheRealNestScheduler` 的 stall 场景复现过）。这些是容量与可用性性质，不影响恰好一次（上面的饱和核对与集成用例都通过）。登记见 [KNOWN-LIMITS](../maintenance/KNOWN-LIMITS.md)“Saga 原生步骤容量（单进程）”，是否改进由维护者决定。
