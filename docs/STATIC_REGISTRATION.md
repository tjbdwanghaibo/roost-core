# 静态注册的统一方案

面向的问题：一个 roost 项目的**静态注册面**（实体、组件、配置表、协议、nest
handler、路由）目前一半由 codegen 生成、一半靠手写聚合，而调用点又落在业务自己
造的一个 mod 里。本文给出统一方案、它为什么不是一个新 mod，以及分步落地路径。

## 现状：一半生成，一半手写

| 注册类 | 叶子函数 | 聚合器 | 调用点 |
| --- | --- | --- | --- |
| nest handler | 生成 | **生成** `game/bootstrap/nest.go` | 生成的 bootstrap |
| entity | 生成 `RegisterEntity()` | **手写**（业务仓里 15 个包手工列举） | 手写的业务 mod |
| component | **手写**，且命名不统一 | **手写**（40+ 个包手工列举） | 同上 |
| config table | 生成 `RegisterGeneratedConfigData()` | 手写包一层 + 自己的 `sync.Once` | 生成的 bootstrap（部分） |
| protocol | 生成 | **手写** | 手写的业务 mod |
| webroute | 生成 `RegisterRoutes()` | — | 手写 |

`nest.go` 那一行是决定性的：**这条路 codegen 已经走通了**——扫描项目、生成 import
列表、生成有序调用、内容未变则不重写（`internal/nest/bootstrap.go`）。其余几类只是
没做。后果有三个：

1. 每次 `roost add entity` / 加组件都要手改一个聚合文件，而这正是 codegen 该消除的；
2. 聚合器里每类一个 `sync.Once`，外面再套一个总 Once，全靠手维护；
3. 业务仓需要造一个 mod，唯一职责是"有个地方调这些注册"。

## 三层分离

判据只有一个：**这段代码需不需要 `app.Registry`。**

### 层 A — 纯静态注册：生成的 `RegisterAll()`，在 `app.New()` 之前调用

不需要 Registry、不做 I/O、必须在任何 mod 之前完成的注册，全部收进
`internal/registry/generated.go`（DO NOT EDIT），由 `roost generate` 生成，
在生成的 `bootstrap.New()` 顶部调用一次。

**为什么不是 mod。** 静态注册必须在**任何** mod 的 `Init` 之前完成。一个 entity
builder 如果在某个 mod 的 `Start` 里注册，那么另一个在 `Provide` 里解析实体的 mod
就已经晚了。放在 `app.New()` 之前，这个排序问题**根本不存在**——用构造消除，而不是
再引一个 mod 用 `DependsOn` 去管理它。少一个活动部件，且不可能配错。

### 层 B — 需要 Registry 的业务接线：`app.IManager`，进 `manager` mod

"建一个 runtime 注册到某个 capability"、"注册需要查表的 admin 命令"这类工作要
`app.Registry`，是真正的运行时接线。`app.IManager` 的 `Start(r *app.Registry)`
正是这个形状，还免费得到依赖序启动、逆序停止、启动失败回滚。

层 A 落地后，业务仓那个"为了有地方调注册"而存在的 mod 就没有理由了：它降级成一个
`IManager`。

### 层 C — 资源型：保持 `app.Mod`

`dataengine`、`mongo`、`nats`、`nest`、`room`、`remote_entity` 不动。

**`dataengine` 不能隐式启动，也不该由生成的 DAO/entity 代码启动。** 它不是注册，
是资源拥有者：`Provide` 里要查 `ModMongo`（活连接）、`ModNatsJetStream`（活连接）、
可选的 `ModRemoteEntity` + `ModRemoteEntityAtomicStore`、以及 `ModHealth`（注册健康
检查）；`Init` 读 `dataengine.*` 配置（WAL 目录、段大小、投影批量、outbox 租约）；
`Start` 打开 WAL 文件并起投影与 outbox worker；`WithEntityAccess` 是注入的对象而非
全局单例；停止要有界并 flush。生成的注册代码跑在进程启动最早期，那时 Mongo/NATS
还不存在——要让它隐式启动就得改成懒连接，那会毁掉框架赖以立足的 fail-fast 启动：
配置门禁、mod 依赖序、健康注册全部失效，"启动就绪即可服务"退化成"第一次写才知道
数据库连不上"。

## 机制：`//roost:register`

component 的叶子函数是手写的，且命名不统一——`RegisterComponent()`、
`RegisterScheduler()`、`RegisterBasicMissions()`、`RegisterBattleAction()`……
codegen 无法按约定推导。因此不按类型推导，而是**让注册函数自己声明**：

```go
//roost:register phase=component
func RegisterComponent() { ... }

//roost:register phase=component order=-10
func RegisterScheduler() { ... }
```

- 标记打在**无参数**的函数上，返回值必须为空或单个 `error`。
- `phase=` 决定阶段，取值是固定枚举（见下），未知值直接报错并列出合法值。
- `order=` 可选，用于阶段内的手工排序（默认 0）；同 order 时按 import 路径 + 函数名
  排序，因此**输出是确定的**，不随 map 顺序变化。
- 生成的 entity wire 代码自带 `//roost:register phase=entity`，所以 entity 走同一条
  路径，没有专门的分支。

一个机制覆盖全部类别，新增一类不需要改 codegen——标记一个函数即可。

### 阶段顺序

`pre` → `kind` → `config` → `component` → `entity` → `protocol` → `nest` → `route` → `post`

顺序是语义的，不是风格：

- `kind` 必须早于 `entity`：builder 注册时要解析 kind→category；
- `config` 必须早于任何读配置表的注册；
- `pre` / `post` 给业务留出"必须最先/最后"的位置，因此不需要另外一个 custom 钩子
  文件——业务函数和生成函数用同一个标记，出现在同一份清单里。

### 生成物形态

```go
// Code generated by roost-codegen. DO NOT EDIT.
package registry

var (
	registerOnce sync.Once
	registerErr  error
)

// RegisterAll runs every static registration in this project, once.
func RegisterAll() error {
	registerOnce.Do(func() { registerErr = registerAll() })
	return registerErr
}
```

`sync.Once` 收在一处，业务不再声明。返回 error 而不是 panic：注册失败是配置/编号
冲突这类可诊断错误，应当由 `bootstrap.New()` 一路返回给 `main`。

## 迁移风险

**比看起来低，而且原因是可验证的**：每个生成的叶子函数都自带自己的 `sync.Once`
（`registerEntityOnce.Do(...)`）。因此一个项目同时留着旧手写聚合器和新生成聚合器
时，只会注册一次而不是两次。这点关键，因为 `entity.RegisterEntityBuilder` 对同
kind 重复注册是**直接 panic** 的——但它只被叶子调用，而叶子是幂等的。

**必须处理的一处**：生成新聚合器时，若检测到旧的手写聚合器仍在，应当**报明确的
迁移提示**，而不是默默生成一个与旧路径并存的文件。理由是维护性而非正确性：两个
聚合器都在，下次加实体的人不知道该改哪个。

## 哪些注册属于层 A：按签名判定

层归属不能靠直觉，要看函数签名——它诚实地说明了这段代码需要什么：

| 注册类 | 生成的签名 | 层 |
| --- | --- | --- |
| entity | `RegisterEntity()` | A |
| component | `RegisterComponent()`（业务手写，命名不统一） | A |
| config | `RegisterGeneratedConfigData(r *configdata.Registry) error` | A（经无参包装） |
| nest handler | `RegisterNestHandlers()` | A |
| protocol | `RegisterPlayerProtocols(*player_agent.ProtocolRegistry, *app.Registry) error` | **B** |
| webroute | `RegisterRoutes(webroute.Registerer, *Service) error` | **B** |

protocol 要 `*app.Registry`，route 要活的 `Service` 实例——**两者都不能在 `app.New()`
之前运行**，因此不属于层 A。它们今天已经在正确的位置：protocol 走一个
`app.IManager`（业务仓的 `player_protocol_mgr`）与生成的 access mod，route 绑在
web service 上。没有东西要搬。

config 的签名带参数，因此生成器额外产出一个带标记的无参包装
`RegisterConfigData()`（内部用默认 registry）；带参的版本保持导出，供测试和自建
registry 的服务使用。

## 落地顺序

每一步都可独立回退。

1. **`//roost:register` 机制 + entity/component/config/nest 四个阶段。**（已完成）
   component 是手工维护最痛的一类（业务仓 50 个包手工列举）。生成物与手写聚合器做过
   **只读比对**，迁移守卫在业务仓上精确识别三个手写聚合器。
2. **层 B 降级**：业务仓那个"为了有地方调注册"而存在的 bootstrap mod 改成
   `app.IManager`，进 `manager` mod。它剩下的工作（建 runtime 注册到 capability、
   注册需要查表的 admin 命令）本来就是 `Start(r *app.Registry)` 的形状。
3. **业务仓迁移**：给每个注册函数打上 `//roost:register phase=<phase>`，删掉
   `game/bootstrap/register.go` 的 `RegisterAll`、`game/entities/register/`、
   `game/components/register/`，跑 `roost generate`。守卫会在删干净之前拒绝生成。

protocol 与 route 不在列——它们已经在正确的层。
