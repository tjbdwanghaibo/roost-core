## 根因（基线 `9bf20e28` 行号）

见问题记录：`handBackOne:716-720` 撤离等超时 → `finishHandBack(…, false)` 租约回到服务，撤离仍在 `evictions` 里（`dropResident:460-464`、`runEviction:475-483`）；
`Admit:895-911` / `refusalLocked:916-936` 不看 `evictions`，于是放行，`Claim:1007` 的 `continuous` 为真、`:1016` 跳过撤离直接确认。

## 决策：`Admit` 在本玩家有撤离进行中时拒绝；不改 `refusalLocked`，不 `abandon`

- `Admit` 在 `refusalLocked` 通过之后、写 `lastUsed` 之前查 `owners.evictions[playerID]`（同一把 `mu`，`dropResident` / `runEviction` 都在这把锁下读写该表），在则返回
  `ErrLeaseNotHeld: player N, the copy is still being dropped`。
- 一处判断覆盖全部出口：后台消费者（`Owns` / `OwnedHere` 先问 `Admitted`，拒绝后 `Owns` 见 Redis 答本进程而本地无放行 → false，不重新认领）、写闸 `AdmitMessage`、
  `Claim` 的 `continuous`（拒绝 → 跨间断 → `dropResident` 加入那次撤离，等不到就不确认）。登录与归还已结束才到的 `Claim` 因此与“等过归还”的 `Claim`（RR-20260921-03）落到同一处理。
- **恢复点就是撤离结束**：`runEviction` 在锁内摘掉 `evictions` 项之后，`Admit` 自然放行——租约一直是本进程的（归还没 Release、刷新循环照常续租），副本已被撤离则下一次访问冷加载
  （RR-20260920-12：“持有租约时丢弃并重新加载永远安全”），撤离失败则副本仍常驻、租约无间断、照常服务。下一轮闲置归还会再选中这个玩家（仍闲置），这次撤离已无东西可等，正常走完投影等待与 Release。
- 不进 `refusalLocked`：它是对**租约**的判断，`abandon`（RR-20261001-07）用它决定“这把租约是否不该再续”。撤离进行中不是租约有间断：若算进去，登录在撤离期间的 `Claim` 等不到（登录预算 2s < 撤离）就会
  `abandon` 一把从未中断的租约，让它 30s 后在 Redis 自然过期——而且跳过了归还本来要做的投影等待（RR-20260926-31）。变异验证：把同一判断放进 `refusalLocked`，回归
  `…/login` 红在 `a login that could not wait for the drop made this process forget a lease it never stopped holding`。

**未采用：**
- 任务提示的“像 RR-20261001-07 一样 `abandon` 本地租约状态直到撤离结束”的字面做法（撤离超时就删 `local`）：租约不再续、在 Redis 自然过期，恢复要等某次 `Claim`；
  后台 `Owns` 在键过期前一直答 false（Redis 说是本 sid、本地无确认），最长 `Lease`（30s）；而且绕过了归还的投影等待——下一个 owner 可能在本进程 WAL 还没落库时冷加载（RR-20260926-31 的问题）。
  RR-07 那边删是因为租约**有过间断**、副本可能已落后；这里租约无间断，没有理由放弃它。
- 新增 `leaseState` 标记位（例如 `draining`），撤离结束时清除：与 RR-20261001-07 记录里否决 (b) 的理由相同——`snapshot` / `confirmLocked` / `Admit` / `handBackIdle` 都要各自绕开，
  且要在 `runEviction` 里回写别的玩家状态；`evictions` 表本来就是“撤离进行中”的唯一事实，直接读它不会与之不一致。
- 让归还的 `handingBack` 一直保持到撤离结束：`Claim` 会在 `enterClaim` 上等整个撤离（登录预算内等不完），刷新循环自己的重新认领也会在 `enterClaim` 上等到它——刷新循环等自己；
  也破坏 RR-20260921-03 “`handBackIdle` 返回前结束它标记的每一个归还”的论证。
- 归还选人时跳过撤离进行中的玩家（省掉每轮一次 `evictWait` 的预算）：是优化不是本缺陷的根因，未做，见未验证项。

## 锁与等待顺序

- 新判断在 `Admit` 已持有的 `owners.mu` 下读 `evictions`，不新增锁、不新增等待；`Admit` 仍然不阻塞（写闸 / 快池可调用的性质不变）。
- 等待只在既有位置：`Claim` 跨间断时 `dropResident` 加入在途撤离，受调用方 ctx / `evictWait` 约束（登录在连接 goroutine、后台 `Owns` 在消费者 goroutine、刷新循环在本回合预算内，见 RR-20261004-10）；
  `runEviction` 只在摘表项时短暂持锁。刷新循环不会等自己：本回合的归还在重新认领之后、同一 goroutine，`enterClaim` 不受影响。

## 未验证项 / 风险

- 只有模板单测（evictor 替身）；没有在真实环境构造“闲置玩家的实体被 > 5s 事务占住、归还放弃、随即登录”的演练。
- 撤离进行中的玩家仍会被每轮闲置归还选中、加入撤离再等一份 `evictWait`（修前就如此）；一个卡住的实体每轮占用 5s 回合预算（RR-20261004-10 之后重新认领与归还共用这份预算）。可选优化：选人时跳过 `evictions` 里的玩家。
- 围栏后台撤离（`fence`）期间该玩家本地已无状态，`Admit` 原本就拒绝；本条不改变。撤离失败结束（`EvictPlayer` 返回错误）后副本仍常驻、可能已离开场景，与修前同一结局（RR-20260920-12 / RR-20260930-23 已记录），未改。
