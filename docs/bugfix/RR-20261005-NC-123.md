# NC-123 修复：补丁点状态整体发布

问题：[RR-20261005-NC-123](../bug/RR-20261005-NC-123.md)。2026-10-05，分支 `revn10`，基线 `197f7bb9`。

## 根因

`hotcode/registry.go:43-45`（基线）当前函数、Meta、代数是三个独立原子值，`Replace` / `Revert` 分三步写、互不排斥，`List` 分三次读。

## 决策

- 合成一个不可变的 `pointState{fn, meta, gen}`，用 `atomic.Pointer` 整体发布；写者（Replace / Revert）在每个补丁点自己的 `writeMu` 下基于上一代生成下一代；`Resolve` / `List` 不取锁，一次 Load 拿到同一次写入的三项。状态从三份减成一份。
- 热路径不变：Nest 每次派发的 `hotcode.Resolve` 仍是一次无锁原子读。
- 未采用：整个 Registry 用 `mu` 写锁串行化 Replace / Revert——读者 `List` 仍会读到撕裂的中间态，而且无关补丁点之间也互相阻塞。

## 文件与行为

- `hotcode/registry.go`：`point` 改为 `writeMu` + `state atomic.Pointer[pointState]`，新增 `publish`；中文注释写明原因与 RR 编号。
- `hotcode/concurrent_patch_promises_test.go`：100000 轮并发 Replace / Revert，每轮检查 Resolve、Patched、Meta 与代数一致。

无格式 / API / wire 变化，`PointInfo` 字段与语义不变（未打补丁的点 Generation 0、Meta 为空）。

## 回归与结果

- 修前：[red](evidence/noncore-bugfix-20261005-n10/red.txt)——5 次普通 + 1 次 race 全部撞出。修后：[green](evidence/noncore-bugfix-20261005-n10/green.txt)——hotcode race×3、`./nest` race（hotcode 唯一生产消费者）、全新生成 game-demo build / vet 与 `game/rewards`、`internal/service/game` 测试通过。
