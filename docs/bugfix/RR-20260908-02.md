# RR-20260908-02：ReadThrough 跟随者取消后不归还等待名额

**仓库 / 位置**：roost-core `cache/read_through.go`，`load` 的跟随者分支（原第 91–105 行）。
**修复单元**：U-0155（C2）。**定位文档**：TROUBLESHOOTING T-51。

## 问题

首个 loader 尚未完成时，后到的请求进入等待并 `call.waiters++`；因取消 / 超时离开时直接返回，
计数不减。`MaxWaitersPerKey` 于是限制的是"本次 load 期间累计进过门的次数"而不是"正在等的
人数"：慢后端叠加短超时重试，健康请求会在首个 load 结束前一直收到 `ErrLoadWaitersExceeded`。
默认上限 256，设为 1 即可最小复现。

## 根因

计数器语义混淆：把"曾经等过"当成了"正在等"。名额只随整个 call 在 load 完成后 `delete(s.calls,
key)` 一起消失。

## 方案选择

只有一种合理修法：取消路径在同一把锁下减回。要注意的边界是 key 相同但 call 已经换代（旧 load
结束、新 load 开始）时不能扣到新 call 上，所以减之前核对 `s.calls[key] == call`。

## 改动

`cache/read_through.go`：`case <-ctx.Done()` 分支加锁，`if s.calls[key] == call { call.waiters-- }`。
累计统计 `Coalesced` 不变——它记的是进过门的次数，和当前等待人数是两个量。

## 证明

`cache/read_through_waiters_promises_test.go`（收自审查附录并加一例）：上限 1、loader 阻塞；第一个
跟随者入场后，第二个被拒（真满额仍拒绝）；第一个取消离开后，新跟随者必须入场；再取消，loader
放行收尾。

修前：`waiter 2 refused: cache: load waiter limit exceeded`。修后 cache 全绿。

## 未做 / 边界

只证明公开 API 场景。等待被 `call.done` 唤醒的正常路径不减计数是对的：call 随后整体删除。
