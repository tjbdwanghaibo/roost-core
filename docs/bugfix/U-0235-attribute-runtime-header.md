# U-0235：attribute 的 runtime.go 缺生成标记，doctor 判成应用自有文件

- 仓库：roost-codegen `internal/roost`
- 缺陷类：C4（生成物所有权标记）
- 来源：实施 §9.2 后复跑 `project doctor` 自查发现，无 RR；**随 codegen v1.15.10 已发出**
- 相关：T-129；测试 `internal/roost/attribute_runtime_promises_test.go`

## 问题

启用 `attribute` feature 的工程，`roost project doctor` 报：

```
FAIL  project-templates    refusing to overwrite non-generated file game/gameplay/attribute/runtime.go
```

doctor 的 project-templates 项因此整项失败（其余 30 项 OK）。`project sync` / `upgrade` 走同一条所有权判断，
所以这个文件也不会被升级回写——它本该是 codegen 受控的。

## 根因

U-0230 新增的 `attributeRuntimeTemplate` 文件头自造了一句 `// Code generated by roost. DO NOT EDIT.`，
而 `canOverwriteGenerated` 认的是 `generatedHeader` 常量（`// Code generated by roost-codegen. DO NOT EDIT.`）。
两句话看起来是一回事，机器不这么看。

为什么没被发现：新增 feature 的验收跑的是编译与运行时门，没有对启用该 feature 的工程跑一次 `project doctor`；
demo 模板不带 `attribute`（B8 是随后一批加的），所以既有的 demo doctor 断言也覆盖不到。

## 方案

- 采用：模板直接拼 `generatedHeader` 常量，不再自己写字符串。
- 没采用：放宽 `canOverwriteGenerated` 去认多种写法。所有权判断应当只认一种标记，放宽等于让"看起来像生成物"的文件也被覆盖。

## 改动

`internal/roost/attribute_runtime.go`：`const attributeRuntimeTemplate = `` + generatedHeader + `` …`。

## 证明

新测试两条：`renderAttributeRuntime` 的输出必须以 `generatedHeader` 开头且 `canOverwriteGenerated` 认它；
用 `-features attribute` 生成一个工程后跑 doctor 的同一条检查（`DiffProject`），必须是 `summary: 0 file(s) would change`。

修前（`git stash` 掉实现）：

```
--- FAIL: TestAttributeRuntimeFileIsMarkedGenerated
    the attribute runtime file does not start with the generated header:
    // Code generated by roost. DO NOT EDIT.
```

修后：两条通过；干净工程 `project doctor` 31 项全 OK（此前 30 OK + 1 FAIL）。

## 未做 / 边界

- 只修了这一个文件的标记。其余 codegen 受控文件都走 `addGo` 的既有路径，没有普查；
  这条测试也只钉住 attribute 这一份——**值得 review 判断是否要一条"所有 owned 文件都带标记"的通用断言**。
- 已发出的 v1.15.10 生成的工程里，这个文件带着旧标记：升级 codegen 后 `project sync` 仍会拒绝覆盖它，
  需要手动删掉那一行（或删文件重新 sync）。处置写进 T-129。
