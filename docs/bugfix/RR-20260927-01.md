## 决策

清单给了两条路：Windows 上也生效的写失败注入（优先），或 Windows 上 `t.Skip`。采用前者——两条用例守护的是 RR-80 的提交 / 回滚承诺，
Windows 正是 `writeAtomic` 有专门分支（“先挪到备份再改名”）的平台，跳过就等于那条分支在 Windows 上没有任何失败路径覆盖。

`readOnlyDir` 改名为 `blockWritesIn`（语义从“目录只读”变为“目录里已有的文件不可替换”）：

- **Windows**：打开目录里每个常规文件并持有到用例结束（`t.Cleanup` 在 `t.TempDir` 之后注册，先于删目录执行）。
  依据：Go 在 Windows 打开文件的共享模式只有 `FILE_SHARE_READ | FILE_SHARE_WRITE`，不带 `FILE_SHARE_DELETE`（Go 1.27.0 `src/syscall/syscall_windows.go:395`）；
  `os.Rename` 是 `MoveFileEx(..., MOVEFILE_REPLACE_EXISTING)`（`src/internal/syscall/windows/syscall_windows.go:357-367`）。替换一个被这样打开的文件需要对它的 DELETE 访问，
  与句柄的共享模式冲突而被拒绝；`writeAtomic`（`codegen/internal/roost/project.go:626` 起）的兜底 `os.Rename(path, backup)` 同样需要挪走这个文件，也被拒绝，于是返回错误。
  读取不受影响（`os.ReadFile` 也只要读共享），`copyProject`、`snapshotProjectInputs`、`verifySyncChangeCurrent` 照常读到原字节，注入点确实落在“提交时写不进去”。
  目录里一个文件都没有时直接 `Fatal`，避免注入悄悄不发生。
- **Unix**：不变，`os.Chmod(dir, 0o555)`（打开的句柄在 Unix 上不妨碍改名，不能用同一办法）；root 仍 `t.Skip`。

两条用例的断言与场景不变，失败文案从 “… is read-only” 改为 “no file in … can be written”。
