# RR-20260910-01:极短 IdleTTL 推导出零扫描周期

**仓库 / 位置**:roost-core `room/room_manager.go`,`NewRoomManager` 的默认值推导。
**修复单元**:U-0163(C2)。**定位文档**:TROUBLESHOOTING T-57。**优先级**:P3。

## 问题

`SweepInterval` 留零时按 `min(IdleTTL/2, 30*time.Second)` 推导。`IdleTTL` 是 `time.Duration`
即整数纳秒,**任何小于 2ns 的有效正值,除以 2 都得 0**,而构造器接受了这个 `IdleTTL`
(它只拒绝 `<= 0`)。`Start` 起的 `run` 随后 `time.NewTicker(0)`,那会 panic 在后台 goroutine 里。

也就是说:一个构造成功、启动也成功、然后把进程带走的配置。

## 根因

派生默认值没有约束。构造器逐项校验了输入,却没有校验自己算出来的东西。

## 方案选择

- **构造阶段拒绝过小的 IdleTTL。** 但 `IdleTTL` 本身是合法的正持续时间,拒绝它是把"我算不出
  一半"说成"你给的值不对"。而且门槛定在哪都是任意的。
- **推导结果取下限(采用)**:`max(min(IdleTTL/2, 30s), time.Nanosecond)`。合法的 TTL 继续被接受,
  只是"一半"在这个量级上无法表示时退化为最小可表示周期。显式给的正 `SweepInterval` 一字不改。

## 改动

`room/room_manager.go`:推导表达式外面套一层 `max(..., time.Nanosecond)`,注释写明整数除法与
`time.NewTicker(0)` 的因果。

## 证明

`room/sweep_interval_promises_test.go`:五个 TTL(1ns、2ns、3ns、1µs、10min)逐个构造,断言构造
成功、派生周期严格为正且不超过 30s 上限,然后真的 `Start` 与 `Close` —— 因为 ticker 是 `Start`
里建的,零周期就在那里 panic。最后断言显式的正 `SweepInterval` 不被改写。

修前红:

```text
--- FAIL: TestDerivedSweepIntervalIsAlwaysPositive/one_nanosecond
    accepted positive IdleTTL 1ns but derived SweepInterval=0s; the sweep ticker would panic
```

修后 `go test ./room -race` 绿。

## 未做 / 边界

- 1ns 的扫描周期在实践中等于"尽可能频繁地扫",CPU 开销由调用方自己承担。这里只保证它是合法的
  ticker 周期,不替调用方判断这个配置是否明智。
- 没有普查其他包里的派生默认值是否有同类问题。审查建议里提到"同时验证派生默认值的约束",
  那是一次独立的扫描单元。
