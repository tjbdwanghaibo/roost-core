# RR-20260913-10:快照 Lua 把 uint64 版本转成浮点,丢失排序精度

**仓库 / 位置**:roost-core `remoteentity/snapshot_l2.go`,CAS 脚本的 `tonumber` 比较。
**修复单元**:U-0177(C8)。**定位文档**:TROUBLESHOOTING T-71。**优先级**:P3。

## 问题

脚本用 `tonumber` 把 marker / route / version 转成 Lua 数值再比较,而 **Lua 的数值是 float64**:
超过 2^53 之后相邻的 uint64 会塌到同一个值。审查在真实 Redis 8.8.0 上实测:

- 先写 9007199254740993,再写同字节的 9007199254740992,**旧值被接受**,wire 里的版本回退。
- 先写 9007199254740992,再写不同字节的 9007199254740993,被当成"同版本内容冲突"**拒绝**。

Go 侧的契约是 uint64,两边的比较域必须一致。

## 根因

跨语言的数值域不一致。Go 的 uint64 在 Lua 里没有对应类型,而 `tonumber` 静默地降到 float64。

## 方案选择

- **限定支持的计数域**(比如只承诺 2^53 以内)。合法 API 没有这个限制,迁移或导入的大值仍会触发,
  而且"静默错"变成"文档说了所以不算错"并不解决问题。
- **精确十进制比较,比较后写回原始字符串(采用)**。脚本自己按十进制字符串比大小:先去前导零,
  再比长度,长度相同再按字典序 —— 对非负十进制串这与数值序等价。存储时逐字写 ARGV,不经过任何
  数值归一化。只有 TTL 还走 `tonumber`,它很小且不与任何东西比较排序。

## 改动

`remoteentity/snapshot_l2.go`:脚本加 `norm` / `cmp` 两个局部函数,三处排序比较改用 `cmp`,
`HSET` 写 `ARGV[i]` 原串。

**替身先被改忠实,再跟着改对。** 原来的 `snapshotRedisFake` 用 `strconv.ParseUint` 精确解析,
所以这个缺陷在单测里根本看不见。先把它改成 `ParseFloat` 去模拟 `tonumber`,红测试才出现;
修好脚本之后,替身再镜像成同样的十进制串比较。这一步值得记下来:**一个比被测实现更"正确"的
替身会把缺陷藏起来**。

## 证明

`remoteentity/snapshot_l2_cas_promises_test.go` 的
`TestL2ComparesVersionsExactlyBeyondFloatPrecision`,用 2^53 与 2^53+1 这对在 float64 下不可区分的
版本,两个子用例正是审查在真实 Redis 上观察到的两种表现:更旧的版本必须被当作陈旧忽略、存储里的
版本不能回退;真正更新的版本不能被误判成同版本冲突。

修前红(替身改忠实之后):

```text
stored version = 9007199254740992, want 9007199254740993; the older write was accepted and the version went backwards
```

修后 remoteentity 含 `-race` 全绿。

## 未做 / 边界

- **没有跑真实 Redis。** 审查明确写了"真实 Lua 必须保留两条边界测试",修复后的脚本要在集成环境
  再验一次;替身再忠实也不是 Redis。
- marker 与 route 同样改成了精确比较,但没有为它们单独写边界用例 —— 它们走的是同一个 `cmp`。
