# RR-20260916-04:Recover 的位置核对识别不出删除 ABA 与同位置替换

**仓库 / 位置**:roost-core `syncstream/syncstream.go`,`observe` / `appendIfUnchanged` / `Recover`,以及
`lifecycle_journal.go` 的 `RotateEpoch` / `DeleteStream` / `DeleteObserver` / `SweepIdle`。
**修复单元**:U-0216(C8)。**定位文档**:TROUBLESHOOTING T-110。关联 U-0214(RR-20260915-09,其原触发仍通过)。

## 问题

U-0214 让 Recover 在调 provider 前记下 epoch / 流是否存在 / latest,提交时核对三者。三者描述的是"当前位置",
位置相同推不出"期间无事发生":

- 流原本不存在;provider 捕获期间有人 Append 新状态又 DeleteStream。提交时仍是"不存在、同 epoch",核对通过,
  旧捕获被当成 seq=2 的 Full 追加。
- 流原本 latest=1;期间 Import 了同 epoch / 同 latest、内容不同的快照。核对通过,旧捕获作为 seq=2 覆盖新内容。

两种交错都在 provider 内按顺序操作即可确定性复现,接收者按更高序号应用后回退到旧内容。

## 根因

C8:判据选了"位置"而不是"变更"。位置是协议层的 Epoch/Sequence,它们本来就允许在替换后回到同一个值
(删后重建、导入同位置快照),所以不能当一致性判据。

## 方案选择

- **把 sequenceFloor 也加进比较。** 不够:同 floor 的 Import 仍可换内容;删除也不动 floor。
- **持 History 锁跑 provider。** 注释明确禁止:provider 可能重入 History。
- **每流代数 + 删除墓碑。** 误拒绝最少,但墓碑要收界,而"不存在的流被重建"恰恰是本 RR 的一种交错,墓碑的生命周期又是一道契约。留作需要时再做。
- **进程内全局修改代数(采用)。** `History.revision uint64`,写锁下每个成功改变流集合 / 链 / ACK / epoch / floor 的操作
  `revision++`;`observe` 只记 revision,`appendIfUnchanged` 只比 revision。全局意味着无关流的并发修改也会让本次捕获
  作废——代价是一次重试,永远不是一次错误提交。代数不持久化、不从快照带入(Import 自己推进一次)。

## 改动

- `syncstream.go`:`History.revision`;`streamObservation{revision}`、`observe()` 不再按 key;`appendIfUnchanged` 只比代数;
  `appendLocked` 成功尾部、`AcknowledgeEpoch` 改动 acked 处、`Import` 切换后各 `revision++`;`Recover` 注释更新。
- `lifecycle_journal.go`:`RotateEpoch` / `DeleteStream` / `DeleteObserver`(有删除时)/ `SweepIdle`(有删除时)各 `revision++`。
- 每处推进都在 journal.Record 成功之后、状态改变的同一把写锁下——失败路径不推进。

## 证明

`syncstream/recover_replacement_promises_test.go` `TestRecoverPromiseRejectsReplacementAtTheSamePosition`,五叶子:
`no_change` / `append_control` 对照,`append_delete_absent` / `same_position_import` / `delete_observer_absent` 三种交错。
修前红:

```

stale capture accepted after same_position_import: err=<nil> committed payload="stale"
stale capture accepted after delete_observer_absent: err=<nil> committed payload="stale"
```

修后 `syncstream`、`skill/skillsync` `-race` 全绿;U-0214 的 `recover_validation_promises_test.go` 五叶子仍过。

## 未做 / 边界

- 只约束 History 自己观察到的变更;宿主业务状态变了却没经 History 的一致性,要 SnapshotProvider 自己的捕获协议。
- 全局代数的误拒绝在高并发多流场景下会放大重试次数;需要时再做每流代数,并先给墓碑定界。
- `ErrRecoverStale` 的宿主重试策略(次数 / 退避)本轮未定义,仍是调用方责任。
- 审查提到的 SweepIdle 交错未单独成叶子(需要可注入时钟),由 `delete_observer_absent` 覆盖同一条删除路径的推进。
