# RR-20261004-12 修复：生成器拿工程根下的路径，`runGenerators` 不再 `os.Chdir` 整个进程

问题：[RR-20261004-12](../bug/RR-20261004-12.md)（来源 [W-2026-10-04-05](../bug/WANTED.md)）。
日期 2026-10-04；实施基线 main `9bf20e28`（v1.19.2 之后）。状态：已修复，本地验证通过，已提交（worktree），未推送、未发版。

## 调查：暂存目录的生命周期

`project sync` / `roost add` → `Add` → `commitManifestSyncResult` → `SyncProject`；`project new -template game-demo` → `NewProject` → `scaffoldDemoTemplate` → 约 40 次 `Add`（每次一个 `SyncProject`）→ 最后在工程里就地 `Generate`。`SyncProject`（`project.go:171-247`）对 `.roost-sync-*` 做的事：

| 步骤 | 文件句柄 / 子进程 | 核对结论 |
| --- | --- | --- |
| `os.MkdirTemp(filepath.Dir(absRoot), ".roost-sync-*")`，`defer os.RemoveAll(stage)` | — | 返回前删除；**错误被丢弃** |
| `copyProject` → `writeAtomic`（`os.CreateTemp` + `Write` / `Sync` / `Close`，`defer os.Remove(tmp)`，`Rename`，跨目录失败走备份回退） | 每个分支都在返回前 `Close` | 无泄漏 |
| `snapshotProjectInputs` / `planStagedProjectCommit` / `planExplicitStagedFiles`（`filepath.WalkDir` + `os.ReadFile`） | 标准库内部关闭 | 无泄漏 |
| `refreshGeneratedShutdownConfigs`、`syncManifest`、`pruneLegacyKubernetesBase` | `os.ReadFile` / `writeAtomic` | 无泄漏 |
| `Generate(stage)` → `runGenerators`：**`os.Chdir(stage)`** → dao / event / errcode / protocol / entity / nest / attribute / tablegen×3 / webroute / servicerpc / registry → `os.Chdir(old)` | 生成器里的 `os.Open` 只有 `tablegen.readCSVRecords`（`defer Close`）与 `errcode.writeCSV`（`defer Close`）；目录读取都走 `os.ReadDir` / `WalkDir` / `go/parser` | 句柄无泄漏；**进程工作目录在窗口内是暂存树** |
| 子进程 | SyncProject 路径上没有任何子进程：`servicerpc.resolveDir` 的 `go list` 只在 `-dir` 形如 import path 时启动（这里是 `./internal/rpc/<name>`）；`gitChanged` 只在 `-changed`；`TidyProjectDependencies` 只在 `GenerateTransactional` / `project deps` | 无 Wait 缺失 |
| `verifyProjectInputs`、`commitSyncChanges` 写真实工程 | `writeAtomic` | 无泄漏 |

结论：被测代码没有遗留的文件句柄和未 `Wait` 的子进程；唯一能让暂存树在 SyncProject 之外仍被占用的进程内路径，是生成器窗口里的进程级 chdir——同进程其他 goroutine 此时不设 `Dir` 启动的子进程把暂存树继承为自己的工作目录。Windows 上进程当前目录的句柄不带删除共享，目录在子进程存活期间删不掉；CI 报错正落在暂存目录本身、错误码是 sharing violation，与此形态一致。

### 探针（macOS，不提交）

1. **全包子进程工作目录**：`go test -c` 出测试二进制，用 PATH 垫片（go / git / docker / kubectl / shellcheck / sh，各记 `$PWD` 与参数后再调真命令）跑整个 `codegen/internal/roost`：59 个子进程，带 Dir 的都在各自工程，不设 Dir 的（`sh` 脚本检查、`kubectl`、`shellcheck`、`docker compose version`）这一次恰好都落在包目录——它们何时撞上别的用例的生成器窗口取决于调度。
2. **并发启动不设 Dir 的子进程**：5 次 `SyncProject` 期间另一 goroutine 连续 `exec.Command("pwd")` 4919 次，72 次输出是 5 个不同的 `.roost-sync-*`。机制在 macOS 上确定存在，只是 macOS 不阻止删除。
3. `lsof +D` 未做：探针 2 已直接给出“哪个进程以暂存树为工作目录”，lsof 在 macOS 上看不到“删不掉”这一 Windows 语义。

## 决策

**去掉进程级 chdir，生成器拿 `root` 下的绝对路径。**

- `generator.Run` 从 `func(io.Writer) error` 改为 `func(root string, w io.Writer) error`；`generatorsFor` 里每个相对参数改为 `under(root, rel)`（`filepath.Join(root, filepath.FromSlash(rel))`）。protocol 原先靠 `-proto` / `-pb` / `-msgid` / `-manifest` 的相对默认值落到 cwd，现在显式传入；`registry.Run(root, …)`、`projectRPCDirs(root, …)`。
- servicerpc 把 `-dir` 原文写进生成文件头注释（“重新生成请运行 …”），孤儿识别也按这行匹配，所以不能传绝对路径。新增 `servicerpc.RunIn(base, args, w)`：相对 `-dir` / `-out` 按 base 解析，`-dir` 形如 import path 时 `go list` 的 `Dir` 退到 base；`Run` = `RunIn("", …)`，CLI 行为不变。roost 调 `RunIn(root, "-dir", "./internal/rpc/<name>")`。
- `runGenerators` 只做 `filepath.Abs(root)`，锁改名 `generatorRuns`，保留串行化：生成器原是一次性命令，没审过并发运行，去掉锁不在本 RR 范围。
- 生成物不变的证据：修前 / 修后两个 `roost` 二进制分别生成 `game-demo`（覆盖 attribute / config / dao / entity / errcode / event / nest / protocol / saga）、`game`、空模板 + `add rpc Guild` + `add entity Hero` + `project sync` + `generate` + `generate -check` 三个工程，`diff -r` 三棵树完全相同。

### 未采用的方案

1. **测试侧给 `docker compose version` 等子进程设 `Dir`**：只能堵住本包测试自己的一处，库调用方的 goroutine、`cli.go` 的 `go env`、`framework_release.go` 的 `go mod download` 照样继承；根因是库把进程级状态借给了一次生成。
2. **`SyncProject` 返回 `os.RemoveAll(stage)` 的错误**：sync 已经提交，删除暂存树失败时报错会把成功的提交说成失败；而且占用者不消失，只是换个地方报告。保留“尽力删除”，消除占用来源。
3. **测试清理对 `RemoveAll` 做有界重试 / 跳过 Windows**：`testing` 本身已对 sharing violation 重试 2 秒；在没排除进程内占用之前加重试是掩盖。
4. **把生成放进子进程跑**：能隔离 cwd，但每次 sync 多一次进程启动和 IPC，生成器错误报告也要重做，代价与收益不成比例。

## 文件与行为

- `codegen/internal/roost/generate.go`：`generatorRuns` 及注释；`generator.Run` 签名；`under`；`generatorsFor` 全部参数取 root 下路径；`runGenerators` 去掉 `Getwd` / `Chdir` / 恢复。
- `codegen/internal/servicerpc/run.go`：新增 `RunIn`，`Run` 委托它。
- `codegen/internal/roost/project_fixture_test.go`：注释里对旧锁的描述改为现状。
- 回归（新增）`codegen/internal/roost/generator_cwd_promises_test.go`：
  - `TestGeneratorsDoNotMoveTheProcessIntoTheTreeTheyGenerate`（确定性）：`runGenerators` 跑一个探针生成器，断言它拿到工程根、`os.Getwd` 不是工程根、不设 Dir 的 `go env GOMOD` 不在工程里。
  - `TestSyncProjectStagesNeverBecomeAChildsWorkingDirectory`（端到端）：3 次 `SyncProject` 期间另一 goroutine 连续 `go env GOMOD`，断言没有一次落在 `.roost-*` 暂存树。修前每次都红（统计性：修前 3 次 sync 有 9 次命中；修后进程不再 chdir，必然为 0）。

## 兼容性

- 生成物逐字节不变（上面三棵树）。
- 生成器的 stdout 提示里有两行从相对路径变成绝对路径：protocol 的 `no protocol structs found in …`、tablegen 的 `table go: …`（其余提示修前就是绝对路径）。暂存运行的输出经 `replayStagedOutput` 把暂存路径换回真实工程路径，不会泄漏 `.roost-*`。
- 新增导出函数 `servicerpc.RunIn`（internal 包）；`servicerpc.Run` 与 `cmd/servicerpc` 行为不变。
- 库调用方：生成期间进程工作目录不再变化；以前依赖“生成器窗口里 cwd 是工程根”的代码不存在于本仓。

## 未验证项 / 风险

- **没有 Windows 环境**：Windows 上“进程当前目录不可删除”是已知语义，但修复后 windows-compatibility 是否不再出现这条失败只能等 CI。CI 两次失败需要占用持续到用例结束后 2 秒以上，而本包并行阶段在 Windows 上唯一不设 Dir 的子进程 `docker compose version` 是短命的——本修复消除的是进程内唯一能让暂存树成为某进程工作目录的路径，不证明它是那两次失败的全部原因。若修后仍以同样文本失败，占用者只能在进程外（Defender 实时扫描 / 索引），那时再考虑测试侧有界重试并写明依据。复现步骤：Windows 上 `go test -count=20 -run 'TestDemoTemplate|TestSyncProjectStagesNeverBecomeAChildsWorkingDirectory' ./codegen/internal/roost/`，失败时用 Sysinternals `handle.exe <暂存目录名>` 看占用进程。
- 观察（未改，另列候选）：`doctor.go:runDoctorGoCommand` 与 `dependencies.go:runDependencyCommand` 用 `exec.CommandContext` 且没设 `WaitDelay`；超时时只杀 `go`，它起的编译 / 链接孙进程可能继续占用 `Dir`（`project deps` 时是 `.roost-deps-*` / `.roost-generate-*` 暂存树），`CombinedOutput` 还可能等孙进程关管道。不在 sync 路径上，未复现。
