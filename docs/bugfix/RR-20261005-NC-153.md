# NC-153 修复：创建者取消的共享加载不决定等待者的结果

[问题](../bug/RR-20261005-NC-153.md) · [本轮](../review/REVIEW-2026-10-05-n09-batch3.md)。已修复、声明场景验证，未发版。

## 根因与决策

plan 层与资产层都是“第一个调用者用自己的 ctx 加载，其他调用者等 ready 后照搬结果”（`skill/presentation_asset_cache.go` 的 `Acquire` / `load`、`acquireAsset`）。创建者的 ctx 一结束，加载以 ctx 错误失败，等待者拿到别人的取消。

修法：条目新增 `abandoned`——加载失败且创建者的 ctx 已结束（plan 层是创建者的 ctx，资产层是 preload 派生的 ctx，含兄弟资产失败触发的 cancel）时置位。等待者醒来看到 `abandoned` 且自己的 ctx 仍有效，就重新进入获取（失败条目已删除，它成为新的创建者，用自己的 ctx 加载）；自己的 ctx 已结束或加载是真实失败时照旧返回错误。`Acquire` 改成循环，`acquireAsset` 拆出 `acquireAssetOnce` 返回是否重试。

未采用：让共享加载使用独立于所有调用者的 context（或所有引用都取消才取消）——要另起 goroutine 和引用计数驱动的取消，改动面大；而重试只在别人的取消发生时多一次加载，失败条目本来就会删除。重试次数以“依次取消的创建者个数”为界。

## 文件与行为

`skill/presentation_asset_cache.go`。成功路径、真实失败、等待者自身取消的行为不变；只有“创建者取消、等待者仍有效”的路径从返回 `context.Canceled` 变为重新加载。

## 回归

`skill/presentation_asset_cache_cancel_promises_test.go`，Loader 由测试闸门控制：

- `TestVisualPlanCacheWaiterSurvivesCreatorCancellation`（plan 层，等待者按 refs == 2 精确同步）修前：
  ```
  presentation_asset_cache_cancel_promises_test.go:128: waiter with a live context returned before reloading: lease=false err=preload "asset-impact": context canceled
  ```
- `TestVisualAssetWaiterSurvivesCreatorCancellation`（两个 plan 共用一个 asset）修前：
  ```
  presentation_asset_cache_cancel_promises_test.go:178: asset waiter returned before reloading: context canceled
  ```
  资产层等待者不改任何可观察状态，测试给它 20ms 的有界窗口进入等待；窗口只影响修前能否复现（晚到的等待者直接成为创建者），修后两种顺序都通过。
- 控制 `TestVisualPlanCacheWaiterSeesRealLoadFailureAndOwnCancellation`：Loader 真实失败时创建者与等待者都拿到该失败、等待者自己取消立即返回 ctx 错误，修前修后都 ok。

修后三条与既有 `TestVisualPlanCache*` 在 `-race -count=5` 下通过；plan 层用例断言释放后 asset 引用归零。
