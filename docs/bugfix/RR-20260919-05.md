# RR-20260919-05：一条读不出来的订单饿死整页（U-0248）

- 仓库：roost-codegen `demo/internal/service/platform`
- 缺陷类：C5（错误处理吞掉正确结果）
- 优先级：P1
- 相关：T-142；测试 `internal/service/platform/pending_index_test.go` 的
  `TestOneUnreadableOrderDoesNotStarveThePage`

## 问题

待发货索引按 score 读一页，然后逐条向服务查订单状态以决定是否退休。任一条查询报错就 `return nil, err`。

页是**按 score 从旧到新**读的，所以一条读不出来的订单永远排在每一批的最前面。整页失败之后，
Server 跳过这一 tick，下一 tick 从同一个成员开始——排在它后面的健康订单**永远**拿不到重试机会。
这和索引自己宣称的"反复失败的那笔挡不住后面的"正好相反。

## 根因

把"这一条判断不了"和"这一页判断不了"当成了同一种失败。写的时候脑子里想的是
"读不出来的订单要保留而不是退休"——这一点是对的，也确实保留了——但保留的方式是让整页失败。

## 方案

- 采用：**按失败的作用域分流**。服务句柄在进页之前解析一次：解析不出来就整页报错（这一页什么都判断不了）。
  逐条的读取失败则记日志、**保留该成员、继续构造其余候选**。
- 保留而不退休仍然成立：它的状态未知，退休掉的是一笔再也没人看的付款；而对已发货订单多试一次是空操作。
- 没采用：让 `PendingOrders` 返回"部分 ids + error"。契约上更完整，但要同时改 kit 的 Server
  （它现在遇到 error 就跳过整个 tick）；部署侧先把自己这半做对，接口层的形状留给 kit。

## 改动

`demo/internal/service/platform/pending_index.go`：`platformService()` 提到循环外；逐条 `Order` 失败
`continue` 并 `slog.Error`；删掉不再需要的 `finished` 辅助函数。

## 证明

修前：`broken`（score 1，读取报错）+ `healthy`（score 2）+ `later`（score 3），整页返回空、err 非 nil。
修后 `TestOneUnreadableOrderDoesNotStarveThePage` 得到 `[healthy later]`，`broken` 仍在集合里；
`TestAnUnreadableOrderIsKept` 改成断言"不报错、条目保留"；新增
`TestAFailureThatIsNotAboutOneOrderIsReported`（服务根本够不着时仍然报错）。

## 未做 / 边界

- 没有覆盖"退休本身失败"（`ZREM` 失败）：那条现在只是下一 tick 再读一次，代价是一次多余的读。
- 坏订单会在每一 tick 被读一次并记一条日志；没有加退避或"连续失败 N 次后告警"的机制。
