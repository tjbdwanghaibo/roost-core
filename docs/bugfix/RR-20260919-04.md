# RR-20260919-04：订单与待办索引不是同一次写（U-0253）

- 仓库：roost-core `redis` / `versionstore`、roost-kit `service/platform`、roost-codegen `demo`
- 缺陷类：C4（两个写构成一个事实）
- 优先级：P1
- 相关：T-147；测试 `roost-core/redis/cas_index_promises_test.go`（真 Redis）、
  `roost-core/versionstore/index_promises_test.go`、`roost-kit/service/platform/pending_index_promises_test.go`（真 Redis）

## 问题

`HandleCallback` 先 `Orders.Create` 把订单持久化，再进 `AttemptDelivery`；而 U-0234 之后的待办索引
是**部署侧**在 deliverer 里补写的。两者之间至少三个窗口：

1. `Create` 成功、进程退出，deliverer 还没跑；
2. `Create` 成功、`ZADD` 失败（订单已经消耗了一次 attempt）；
3. 调用方按"付款已记录"向渠道确认收到，渠道不再重投。

第二种窗口用最新生成工程复现过：订单是持久的 `reserved`、grant 没写、`PendingOrders(128)` 返回空。
后台循环唯一的输入就是那个列表，所以**它无法自行恢复这笔订单**。源码注释把"渠道会重投"当兜底，
但服务契约同时允许调用方在订单已记录时确认接收——两者不能共同构成恢复保证。

## 根因

索引被放在了写不到同一个地方的一侧。部署侧只能在订单写完**之后**写索引，两次写之间的窗口不是实现细节，
是这个位置本身的性质。"记录存在"和"记录在待办集合里"是同一个事实，只有同一次写才能让它们同时为真。

## 方案

- 采用：**把索引放进存储，和值同一个脚本**。
  - core `redis`：`CompareAndSetCommand.Index`（member / score / remove）与一个双 key 脚本——
    compare 通过之后才 `ZADD` / `ZREM`，compare 没通过就一个字节都不动。score 以十进制字符串过去，
    不靠 Lua 解析 Go 的浮点序列化（kit 那两个跨语言缺陷就是这样长期不可见的）。
  - core `versionstore`：`RedisConfig.Index`（key + `Entry(T) (score, include)`）让 `Create` / `Update` /
    `Delete` 自动维护它，`IndexDue(maxScore, limit)` 按分数从低到高读一页。
    `include` 是关键：索引是**待办清单**，不是键空间的副本——值变成终态的那次写就把它退休掉。
  - kit `platform`：`NewRedisOrders` 带上索引（score = `NextAttemptAtUnix`，回落到付款时刻；
    `include = !Terminal()`），返回的 `*RedisOrders` 同时实现 `OrderStore` 与 `PendingOrders`；
    `Mod.Provide` 在部署没给索引时用它，于是**后台重试默认是开的**。
  - codegen demo：删掉部署侧索引，`Pending()` 返回 nil 并写清为什么这才是对的。
- **Redis Cluster**：两个 key 同一个脚本要求同槽。`Mod.Init` 在配了 `redis.cluster_addrs`
  而 `platform.key_prefix` 没有 hash tag 时**拒绝启动**，消息给出改法。单机部署键名不变，没有迁移。
- 没采用：`Pending.Track` 由服务在 Create 之后调用。审查说得对，那只能缩小窗口；
  而且它会让"索引是谁的责任"更含糊。

## 改动

core：`redis/cas.go`（`CompareAndSetIndex` + 双 key 脚本）、`versionstore/redis_store.go`
（`RedisIndex`、三处写入路径、`IndexDue`）、测试替身 `versionstore/fake_redis_test.go` 跟上。
kit：`service/platform/redis_store.go`（`RedisOrders` + `PendingIndexKey` + `pendingIndexEntry`）、
`platform_mod.go`（默认索引 + cluster 守卫）。
codegen：删 `demo/internal/service/platform/pending_index.go` 与它的测试，`Pending()` 返回 nil，
deliverer 不再补写索引，`game/purchase` 去掉 `PendingKey`。

## 证明

对着**真 Redis**（`ROOST_REDIS_TEST_ADDR`）：
`TestIndexIsMaintainedInTheSameWriteIntegration`（建 → 索引里有；compare 失败 → 索引不动；
更新 → 分数移动；终态 → 退休）、`TestIndexScorePrecisionSurvivesLuaIntegration`（unix 秒原样回来）、
kit 的 `TestAStoredOrderIsImmediatelyEnumerableIntegration`（**记录订单就是进索引，没有第二次写**）、
`TestATerminalOrderLeavesTheIndexIntegration`（三种终态）、`TestBackoffMovesAnOrderInTheIndexIntegration`。
替身侧 `versionstore/index_promises_test.go` 四条锁住 store 的逻辑。
`TestAClusterWithoutAHashTagIsRefused` 锁住守卫。

## 未做 / 边界

- **`Delete` 的退休和删除不是同一次写**：删除走"CAS 成 sentinel → `Del`"两步，索引在第一步退休。
  中间崩一次会留下一条没有记录的索引条目；读到它的循环会得到 `ErrOrderInvalid`（订单不存在），
  这是可见且无害的方向，但它不是原子的。
- 索引只有一个维度（下次该看的时刻）。按渠道、按玩家分片要另加索引，`RedisIndex` 目前只支持一个。
- 老部署里已经存在的订单**不在索引里**：索引是从这一版起的写建立的。升级后要么等它们被 callback
  重投带进来，要么跑一次性的回填（遍历 `<prefix>:order:*` 把非终态的 `ZADD` 进去）。
  这一条对已经跑过 v1.14.10 的部署是必须做的，demo 里没有提供脚本。
