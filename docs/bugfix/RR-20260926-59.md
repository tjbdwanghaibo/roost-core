# RR-20260926-59 修复：仅内存卸载后仍有订阅者时，框架从权威重载并 Rebind 全量；重载不了退回 remove

问题：[RR-20260926-59](../bug/RR-20260926-59.md)。日期 2026-09-26。实施基线：本地 main `3e26f91`，在 [RR-20260926-50](RR-20260926-50.md) 修复之上；首版提交 `2cfab75` 与已合入 main 的 RR-54 / RR-55 / RR-57 冲突，
在 main `5ba74df` 上重新应用并统一语义（见 §7），本记录描述统一后的机制。
状态：已修复，本地验证通过，已本地提交，未推送/发布。

## 根因（基线行号）

- RR-30 驱逐（`dataengine/engine/fenced_step.go` `evictStaleEntities`）与 RR-39 拒绝卸载（`remoteentity/local_runtime.go` `unloadRejectedEntities`）共用
  `entity.ManagerAccess.Unload`（`entity/manager_access.go:396-408`）：只 `Destroy(deleteFromDB=false)`，实例的 `SubjectSyncState` 随 ClearBase 关闭，
  entitysync 对关闭的状态不捕获、不发送（`sync/entitysync/flush.go:189`），subject 保持登记、不发 remove。
- 订阅者得到修正只有一条路：有人重新访问实体 → 正式仓储重载 → `OnEntityLoaded` → `Rebind`（`kit/nest/nest_mod.go:156-186`）。没人访问时一直停在
  卸载前最后交付的内容上。
- 这份内容并不一定与权威一致：Durability 1 在 Commit 返回时推测性确认 Sync（`remoteentity/batch.go:459`、`nest/msg.go:108-116`），投影器拒绝前
  订阅者可能已收到被拒绝内容；RR-30 的原生步骤在准入时已按正常路径外发被跳过的效果。RR-39 修复记录“订阅者保留拒绝前、与权威一致的状态”对这两种
  情况都不成立（见[RR-39 复核补修](RR-20260926-39.md#复核补修2026-09-26rr-20260926-59)）。
- 附带：`ManagerAccess.Unload` 返回时，若实例还有在途引用（Touch 计数未归零），ClearBase 推迟，同步状态此刻仍是打开的——`Rebind` 在这段时间里会以
  `ErrSubjectRegistered` 拒绝接新状态。

## 修复（维护者 2026-09-26 批准的约束：主动重载并全量重绑）

约束：卸载后若该 subject 仍有订阅者，框架在慢阶段主动从权威重载该实体并 Rebind 全量；重载失败（权威不存在 / 持续错误，有界重试后）退回向订阅者发
remove；RR-30 与 RR-39 共用；执行位置遵守契约（重载 I/O 在慢阶段，发布 / Rebind 按既有正式路径）；无订阅者不主动重载。

### 1. 触发点：`ManagerAccess.Unload`（两条路径共用）

- 实例一离开 EntityManager（`value.IsRemoved()`，含业务 `OnDestroy` panic、实例已被别处卸载的幂等情形），就在 `Unload` 的 defer 里关闭它卸载前的
  `SubjectSyncState`（不再等在途引用归零），然后调用已接线的重载器 `schedule(id)`。
- `schedule` 在快池（Unload 的调用位置）运行，只做：问 Sync 侧该 subject 是否在等（`SubjectAwaitsReload`），按实体 ID 去重登记，按需启动 worker。
  不做 I/O、不等待、不取实体锁。无订阅者 → 不登记、不重载。

### 2. 重载 worker（快池之外）

新文件 `entity/unload_resync.go`，`ManagerAccess.ConfigureUnloadResync(target, config) (stop, error)`：

- worker 是按需启动的后台 goroutine（最多 `Workers` 个，默认 4；队列空即退出），不在快 worker 上，允许冷加载 I/O 与等待——与 RR-30 驱逐 worker、
  Remote finalizer 同一类执行位置（快池之外、不执行业务、不取 Entity 锁）。
- 一次重载 = `ManagerAccess.Get(ctx)`——与业务冷加载**同一条** RR-54 共享加载（同一个 flight、同样与调用方 ctx 解耦、同样受框架加载上限
  `DefaultEntityLoadTimeout` / `ConfigureLoadTimeout` 与 loader 注销约束，没有另设截止时间）。ctx 带 ManagerAccess 已绑定的本地执行入口
  （`NewEngine` 经 `BindLocalExecutor` 交给 getter 的 `NestMgr.RunLocal`；未绑定即就地执行）：worker 领头时发布走它，worker 离开后共享加载按 RR-54
  改走同一个绑定入口。loader——正式 `EntityRepository` 先 `WaitEntityProjection`（RR-30：等驱逐完成、屏障解除后才读 Mongo），读权威，发布与
  `OnEntityLoaded`（kit 的 `Rebind`）在快池续行里执行。之后 worker 再对新状态调一次 `Rebind`（正式路径下是同一状态的空操作，覆盖不经 EntityRepository 的 loader）。
- 结果判定：
  - subject 不再等（已绑新状态、订阅者都已离开、已退役）→ 完成；
  - `errors.Is(err, entity.ErrAuthorityEntityNotFound)` 或 loader 返回 nil → 权威里没有它，**立即**退回 remove（不重试）；
  - 重载出来的实体没有启用同步 → 订阅者无法被服务，退回 remove；
  - 其他错误、重载后又被卸载 → 按 `RetryMin`→`RetryMax`（默认 100ms→2s，逐次翻倍）重试，共 `Attempts` 次（默认 5），用尽退回 remove。
- 退回 remove = `RetractUnloadedSubject(id)`：只在 subject 仍停在已关闭状态上时退役（检查与退役同在 `subj.mu` 下，已被重新绑定的活 subject 不会被误删），
  语义与 `Unregister` 相同：持有对象的会话收到 `ObjectRemove`，全部发出后 subject 被忘掉（remove-before-create）。退役完成前实体又被加载出来时，
  `Rebind` / `Register` 按 RR-55 的排队机制登记到退役完成之后（见 §3、§7）。
- 去重与再触发：同一实体已在队列里 → 忽略；正在处理 → 标记“结束后再来一轮”（处理期间新实例又被卸载）。
- 有界：等待队列上限 `QueueCapacity`（默认 4096），放不下的卸载**立即**退回 remove（订阅者不会停在错误内容上），计 `Overflow`。
- 停机：`stop(ctx)` 标记停止、清空队列、让 worker 离开在途等待，等 worker 退出（受 ctx 限制）；取消不算失败、不发 remove。在途共享加载本身按
  RR-54 继续到完成或被 loader 注销（DataEngine Runtime 停机）取消，完成后照常发布。
  已停止的接线可被重新 `ConfigureUnloadResync`（Nest Mod 重启）。
- 计数：`ManagerAccess.UnloadResyncStats()`（Scheduled / Reloaded / Retracted / Failures / Overflow）；日志：退回 remove（Info）、重试用尽 / 队列满（Warn）。

### 3. Sync 侧（`sync/entitysync/manager.go`）

`Manager` 实现 `entity.UnloadedSubjectSync`：

- `SubjectAwaitsReload(id)`：已登记、未退役、当前状态已关闭，且有非 leaving 的订阅者。
- `Rebind`（既有）。对 `RetractUnloadedSubject` 退役中的 subject，`Rebind` / `Register` 不再返回 `ErrSubjectRetiring`，而是把新状态作为 RR-55 的
  `successor` 排在退役完成之后登记（最后一个 remove 交付的同一步 `forget` → `Register`），返回 nil；后到的替换先到的（先到者的 done 收到
  `ErrRegistrationCancelled`）。业务 `Unregister` 的退役不变（仍 `ErrSubjectRetiring`，业务走 `RegisterAfterRetirement`）：`Unregister` 清除
  `subject.unloadRetracted`，业务注销意图优先。
- `RetractUnloadedSubject(id)`：见上；与 `Unregister` 共用抽出的 `retireLocked` / `finishRetire`（`Unregister` 行为不变；被取消的排队登记在解锁后
  `finish`，与 RR-55 原实现一致，不在持锁时回调 done）。

### 4. 权威缺失的判别

`entity.ErrAuthorityEntityNotFound`（新）。DataEngine 的 `ErrEntityAggregateNotFound` 改为带 `Is` 方法的错误值：`errors.Is(err, ErrEntityAggregateNotFound)`
照旧成立、错误文本不变，同时满足 `errors.Is(err, entity.ErrAuthorityEntityNotFound)`。自定义 loader 报“权威没有”时包它即可，或返回 `(nil, nil)`。

### 5. kit 接线（`kit/nest/nest_mod.go`）

装配了 entitysync、getter 为 `*entity.ManagerAccess`（生成工程的 `EntityAccess`）时，`Mod.Start` 在 Nest 启动前调用 `ConfigureUnloadResync(entitySync,
默认配置)`（发布入口是 `NewEngine` 已绑定给 getter 的 `NestMgr.RunLocal`，不另传）；`StopWithContext` **先**停重载（worker 离开、不发 remove；等待超时
也继续停 Nest，错误合并返回），再停 Nest、注销 `OnEntityLoaded`、停 Sync。Nest 启动失败时一并回收。

### 6. 并发访问的补丁（`ManagerAccess.loadEntityShared`）

对抗性自查发现：`Get` 查内存未命中之后、拿到 `flightMu` 之前，上一轮加载可能刚发布并撤掉 flight（RR-54 后 flight 仍在发布之后才删除），于是同一实体被读第二次权威、第二次发布撞
`ErrEntityExists`（`-race -count=50` 下复现：`loads=2, want one shared load`）。现在在 `flightMu` 下复查内存，已发布就直接返回。主动重载与业务访问
并发时正是这个窗口；修复对所有冷加载生效，行为只少一次多余读取。统一后复查放在 RR-54 `loadEntityShared` 的“新建 flight”分支里（已有 flight 的照常加入）。复查只在配置了 EntityManager 时进行（首版未判空，`entity` 包全量 race 下 `TestALoaderPanicDoesNotWedgeTheEntity` 以 nil manager 调用，panic 时
`flightMu` 未释放、测试挂起到 10 分钟超时；已改为判空后复查，全量通过）。

### 7. 与 RR-54 / RR-55 / RR-57 的统一（重新应用于 main `5ba74df`）

- **一条加载路径（RR-54）**：首版给重载 worker 传了 `run`（本地执行入口）与 `AttemptTimeout`，等于在共享加载之外又定一套执行器和截止时间。统一后
  `ConfigureUnloadResync` 去掉这两个参数：重载就是 `ManagerAccess.Get`，受同一个 30s 框架上限与 loader 注销取消，发布经 `BindLocalExecutor` 绑定的
  `NestMgr.RunLocal`；worker 停机离开后加载按 RR-54 继续，不会因 worker 离开而截断同 flight 的业务等待方。`flightMu` 内复查并入 RR-54 的新建 flight 分支。
- **一个“退役后登记”入口（RR-55）**：退回 remove 之后若实体又被加载，`Rebind` / `Register` 走 RR-55 的 `successor` 排队（见 §3），业务与 kit 的
  `OnEntityLoaded` 回调都不再遇到 `ErrSubjectRetiring`；RR-35 的 `RetractSyncSubject` 与业务 `Unregister` 语义不变。`retireLocked` 合并了 RR-55 的
  “退役取消排队登记”，并把 done 回调移到解锁之后（合并时发现自动合并把它留在了持锁的 defer 里）。
- **RR-57**：`flush.go` 的死分支已在 main 删除；本修复只在保留下来的 `ErrSubjectSyncClosed` 分支注释里补一句，无逻辑改动。

未采用：在快池里就地重载（快池不得 I/O / 等待）；在 finalizer / 驱逐 worker 上顺带重载（两条路径各写一份，且驱逐 worker 要等重载会拖住屏障解除；
约束要求共用）；经同 ID 链的 Nest 消息重载（没有业务 handler，且冷加载等驱逐、驱逐与消息互等的风险同 RR-30 记录）；卸载时直接对订阅者发 remove
（实体在权威里仍存在，客户端会先看不到、再重新创建，违背 RR-39 统一规则中“仍存在就换代”）；无订阅者也重载（多余读取，约束明确不要）。

## 兼容性

- 行为变化：接了 `ConfigureUnloadResync`（kit 的 `NewModWithEntitySync` 装配自动接）时，仅内存卸载后仍有订阅者的实体会被框架主动重载一次（多一次权威
  读取与一次全量），重载不了时订阅者收到 remove；卸载时实例的同步状态立即关闭。无订阅者时与修复前相同。自建 entitysync 装配需自己调用
  `ConfigureUnloadResync`（与 RR-30 要求自建装配在 `OnEntityLoaded` 里 Rebind 同理）；不调用则维持修复前行为。
- 退回 remove 之后，若实体又被加载：remove 发完前 `Rebind` / `Register` 排队（返回 nil），最后一个 remove 交付时以新状态登记；发完后同 ID 的登记是新
  subject。退役期间的订阅仍返回 `ErrSubjectRetiring`（remove-before-create），订阅关系由政策层（Interest/AOI 等）按自己的规则重新建立。
- `ManagerAccess.Get` 在 flight 窗口里少一次重复加载（见 §6）。
- 新增导出 API：`entity.ErrAuthorityEntityNotFound`、`UnloadedSubjectSync`、`UnloadResyncConfig`、`UnloadResyncStats`、`ManagerAccess.ConfigureUnloadResync`、
  `ManagerAccess.UnloadResyncStats`；`entitysync.Manager.SubjectAwaitsReload`、`RetractUnloadedSubject`。`Rebind` / `Register` 对“卸载后退回 remove”
  的退役中 subject 由返回 `ErrSubjectRetiring` 改为排队登记。`ErrEntityAggregateNotFound` 的动态类型变化
  （`errors.Is` 与文本不变，直接 `==` 比较仍成立）。无配置项、持久格式变化。

## 对抗性自查

- **主动重载与业务并发访问 / 重复登记**：重载与业务访问经 ManagerAccess singleflight（加 §6 复查）共用一次加载，`EntityRepository` 还有自己的 flight 与
  `ErrEntityExists` 兜底；重复卸载触发按实体 ID 去重，处理中再被卸载标“再来一轮”；业务先重载并 Rebind 时 worker 发现 subject 不再等待即结束。回归：
  `TestUnloadResyncSharesTheLoadWithConcurrentAccess`（`-race -count=50`）。
- **重载风暴的有界性**：并发重载 ≤ `Workers`（4），等待 ≤ `QueueCapacity`（4096，按实体去重），超出立即 remove；每实体最多 `Attempts` 次共享加载，每次受框架加载上限
  （默认 30s）约束，外加退避。持续 Mongo 故障下排在后面的实体要等前面的尝试用尽才轮到，订阅者在这段时间里仍看到旧内容——有界但可能是分钟级，已记录为边界。
  回归：`TestUnloadResyncStormIsBounded`。
- **停机时重载取消**：kit 先停重载再停 Nest，worker 立即离开在途等待；共享加载按 RR-54 由 loader 注销（DataEngine 停机）取消，穿透 loader 与
  `WaitEntityProjection`；停机取消不发 remove；停止后的卸载不再登记。回归：`TestUnloadResyncStopCancelsInflightReload`（stop 及时返回、注销 loader 后在途
  加载收到取消）、kit 用例。独立装配若先停 Nest 再停重载，重载的发布会拿到 `ErrNestStopped` 并按失败重试，最后退回
  remove——文档要求先停重载。
- **屏障解除时机**：RR-30 的屏障只由驱逐完成解除（RR-50 后每笔一次），重载经正式仓储先等该实体投影/驱逐结束，读到的是不含被跳过效果的 Mongo 状态；
  重载不参与屏障。RR-50 的 WAL terminal 扫描解除屏障后，重载的投影等待返回 terminal 错误，按失败重试、最终 remove（此时进程已在 fence / 停机）。
- **remove 与 create 顺序**：退回 remove 走 `Unregister` 同一退役路径；remove 发完前同 ID 的 Rebind / Register 排到退役完成之后（RR-55 `successor`），
  退役期间订阅仍被拒绝，最后一个 remove 交付的同一步才以新状态登记；`RetractUnloadedSubject` 与 Rebind 都在 `subj.mu` 下判断“仍是关闭状态”，已接上新状态的 subject 不会被误退役。回归：
  `TestUnloadRetractsWhenAuthorityHasNoEntity`（remove 之后同 ID 重新登记成功）、`sync/entitysync/unloaded_retract_test.go`（退役中 Rebind / Register
  排队、订阅被拒、remove 先交付、之后新订阅得到新状态的 create；业务 Unregister 后仍返回 `ErrSubjectRetiring`）。
- **快慢池边界**：快池里只有 `schedule`（两把短锁：entitysync `subj.mu` 与重载器 `mu`，均不嵌套实体锁、不做 I/O）；冷加载 I/O、投影等待、重试退避都在
  worker 上；实例发布与 `OnEntityLoaded`（Rebind）经 `NestMgr.RunLocal` 在快池续行里执行；worker 自己的 Rebind / Retract 只取 entitysync 锁，不取实体锁、
  不执行业务。回归：kit 用例断言发布在快 worker 上。
