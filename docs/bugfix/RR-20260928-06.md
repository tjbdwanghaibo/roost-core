逐段补上看下一处失败：

```text
+ platform 段：  service game init: game: player owners: game_route.key_prefix is empty; ownership is a shared fact and needs a keyspace
+ game_route 段：service game init: game: activity: activity.key_prefix is empty; the game reads the coordinator's keyspace to keep its own board beside it
+ activity 段（即 RR-34 演练时从开发配置手工补齐的三段）：game healthy、RestartCount=0
```

## 根因

- `codegen/internal/roost/demo.go:201-228`（基线行号）`demoPaymentSecrets`：把 `platform:`（`key_prefix` + `payment_secret`）只追加进 `configs/service/config.<game>.yaml`（`:227-228`）。
- `:263-287` `demoActivityKeys`：把 `game_route:` 与 `activity:`（`key_prefix`、`game_sids`）同样只追加进开发配置（`:281-287`）。
- 生产示例 `config.<game>.prod.example.yaml` 由 `renderServiceConfig(m, service, true)` 按 Mod 目录渲染，Secret 示例 `deploy/k8s/base/secret.<game>.example.yaml` 由 `renderKubernetesSecretExample` 同样按 Mod 目录渲染后嵌进 `stringData.config.yaml`；这三段不属于任何 Mod 的配置，是 demo 的 game 代码自己读的键，两份生产配置都没有。
- demo 读这些键的位置：`demo/game/controllers/player/controller.go.tmpl:206`（`platform.payment_secret`，空即拒绝）、`demo/internal/service/game/playerowner.go.tmpl:324`（`game_route.key_prefix`）、`demo/internal/service/game/activity.go.tmpl:120-126`（`activity.key_prefix`、`activity.game_sids`）、`demo/internal/service/game/purchase_drain.go.tmpl:63`（`mods.KeyPrefix(cfg, "platform")`）。

## 决策

同一段文本（同源）追加进 game 的三份仓内配置：开发配置、生产示例、Secret 示例（新 `appendDemoGameConfig`）。

- **前缀**：三段的 `key_prefix` 和原来一样从所属服务的配置读（`activity` / `platform` 的开发配置；生产示例里它们的前缀与开发配置相同，回归逐项核对），`game_route` 由 activity 的前缀派生。前缀不是密钥，生产与开发一致，否则 game 与 activity / platform 进程会各看各的键空间。
- **密钥不复制**：`platform.payment_secret` 在开发配置里仍是 `dev-platform-payment-secret`，生产示例与 Secret 示例里写 `CHANGE_ME`，与 platform 服务自己的生产示例一致——运维必须把两边填成同一个真值；`CHANGE_ME` 让应用 fail-closed，`config check --production` 也拒绝它。
- **`game_sids`**：生产示例的 `sid` 是 1000，这里同样写 `- 1000`，注释说明部署要列出实际运行的每个 game 的 `--sid`（compose 默认给 game 的 sid 是按服务名排序的 `1000+序号`，本工程为 1003，演练时按此改写）。
- **Secret 示例**：它的 `config.yaml` 是缩进四格的字面块、位于文件末尾，按同样缩进追加。生产文本走 `productionizeConfig`，与整份生产示例的变换一致（这三段里没有地址，结果不变）。
- **幂等**：某份文件已有该顶层键就不动它（手改保留）；文件不存在（例如没有 k8s 部署目标）跳过。

没有采用：把这三段做成某个 Mod 的 `Config` 走 `renderServiceConfig`——它们是 demo 业务代码的键，不是框架 Mod 的配置，放进 Mod 目录会让不用 demo 的工程也生成它们。

## 另外发现（未修，已报主会话）

**k8s Secret 示例还缺 `saga` 与 `player_access` 两段。** 新回归第一版按“Secret 示例与开发配置键集合一致”断言时暴露：game 的 Secret 示例由 `renderKubernetesSecretExample` 按 Mod 目录渲染，而 `saga:` 段（`add saga` 时 `appendModConfigSections` 追加）与 `player_access:` 段（`ensurePlayerTCPConfig`）只写进开发配置与生产示例，Secret 示例没有。实跑：把修后 Secret 示例里的 `config.yaml` 取出、只做同样的地址 / 隔离改写后起 game，`mod saga start: saga: ensure stream: nats: API error: code=500 err_code=10047 description=insufficient storage resources available`（saga 按代码默认值——8 GiB 的 `ROOST_SAGA`——建流，重启 4 次）；`player_access` 缺失则玩家 TCP 接入按默认关闭。这是 RR-06 之外的同形缺口，本条回归只核对 Secret 示例里的三段，没有扩大范围。
（这次探测按默认值连了共享命名空间：saga 的 `EnsureInfrastructure` 对共享 `saga` 库做了一次幂等的集合 / 索引确认，随后对既有的 `ROOST_SAGA` 流的 ensure 被服务端拒绝。核对：`ROOST_SAGA` 仍是 2026-09-22 创建、`max_bytes` 512 MiB、112 条消息、5 个消费者，未被改动；`saga` 库没有写入业务文档——saga 在建流失败处就停了。）
