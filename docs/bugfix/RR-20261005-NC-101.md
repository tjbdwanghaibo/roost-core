# NC-101 修复：事务提交受 transaction_timeout 约束

问题：[RR-20261005-NC-101](../bug/RR-20261005-NC-101.md)。证据：[evidence](evidence/noncore-bugfix-20261005-revn04/)。

## 根因与决策

`mongo/driver/session.go` 把带截止的 ctx 交给 `mongo.Session.WithTransaction`；驱动 v2.6.0 用 `newBackgroundContext(ctx)` 提交、提交重试只受它自己的 120s 计时器约束且只在尝试之间检查，所以网络黑洞时调用方的 `transaction_timeout` 不起作用。

采用：`session.WithTransaction` 自己实现与驱动便捷 API 相同的重试规则——回调返回 TransientTransactionError 时整体重跑（5ms 起、×1.5、封顶 500ms 的全抖动退避，期间看 ctx）；提交返回 UnknownTransactionCommitResult（非 MaxTimeMSExpired）时只重试提交；提交返回 TransientTransactionError 时重跑回调；截止已到时不发提交、abort 后返回 ctx 错误——只是把同一个带 `transaction_timeout` 截止的 ctx 交给 `CommitTransaction`。回调失败后的 abort 用 `context.WithoutCancel` 加 5s 上限（尽力而为，服务端也会按生命周期中止）；提交失败后不 abort（与驱动一致）。`TransactionTimeout <= 0` 时用驱动的 120s。

截止落在提交中途时返回驱动错误（链与标签保留，通常 `errors.Is(err, context.DeadlineExceeded)`）：服务端可能已提交，调用方按结果未知处理。现有调用方（DataEngine 投影 / 加载、Remote committer、saga、effect inbox）都在重试前按持久身份 / 回执裁决，修前它们在同样的“已提交但报错”情形下也拿到错误（downstream 例的 server selection 错误），所以没有新的错误类别，只是时间有界了。

未采用：客户端 CSOT `SetTimeout(TransactionTimeout)`——它作用于该客户端的每一个操作（含长扫描 `StreamFind`），改变面过大。

## 文件与行为

- `mongo/driver/session.go`：自实现重试循环、`commit`、有界 `abort`、`hasErrorLabel`。
- `mongo/config.go`：`TransactionTimeout` 注释改为“端到端约束回调重试与提交；提交发出后的错误可能已提交”。
- 回归：`mongo/driver/transaction_deadline_integration_test.go`（真实副本集，本用例自建随机端口 toxiproxy 代理、directConnection 直连主节点；upstream / downstream 两种黑洞，`transaction_timeout=2s`，返回不晚于 4s、返回错误、已提交时错误可识别为未知结果）。

兼容性：调用方在网络分区下更早拿到错误（≤ `transaction_timeout`，回调失败时另加至多 5s abort），而不是阻塞到网络恢复后成功。无 API / 配置键 / 持久格式变化。

## 未验证 / 风险

分片集群（mongos 上提交失败后 abort 的并发问题正是驱动不 abort 的原因，本实现同样不 abort，但未在 mongos 上实测）；主从切换期间的提交；驱动升级时便捷 API 规则若变化需同步本循环。kit/dataengine 的真实 Mongo 集成套件写 `ROOST_IT_EFFECTS_*` 流并含主节点切换用例，本轮按共同要求没有在共享环境上跑。

## 复审追加（2026-10-05，独立审查 81659082）

**缺口**：修复只限住了 `WithTransaction` 本身。提交因截止失败时驱动不更新事务状态（v2.6.0 `mongo.Session.CommitTransaction` 的 `IsTimeout` 分支直接返回，事务仍是 InProgress、Committing），于是之后的 `EndSession(ctx)` 会先 `AbortTransaction(ctx)`。全部正式调用方（DataEngine 投影 / 批量投影 / 加载、Remote committer、saga store / command consumer / step inbox、effect inbox）都 `defer session.EndSession(ctx)`，投影器传的是常驻 ctx（无截止）：网络黑洞时这次 abort 与修前的提交一样阻塞到网络恢复，`transaction_timeout` 对调用方仍然失效。原回归在 `WithTransaction` 返回后立即恢复网络、`EndSession` 放在 defer 里，测不到这一段。

**修复**：`session.EndSession` 与回调失败后的 abort 相同，用 `context.WithoutCancel(ctx)` 加 `transactionAbortTimeout`（5s）上限；没有进行中的事务时驱动不发命令，正常路径无额外往返。代价：上限内没送达的 abort 留下的服务端事务持锁到 `transactionLifetimeLimitSeconds`（缺省 60s），其间写同一文档的事务得到 WriteConflict 并按 TransientTransactionError 重跑——修前（无界 abort）网络恢复后 abort 才送达，调用方则一直阻塞。副本集上同一 txnNumber 的 commit / abort 由服务端串行裁决，未知结果的含义不变。`session.go` 注释原写“提交失败后不 abort”，改为说明 EndSession 仍会补发 abort。

```text
source ~/.roost-it/roost-dataengine-it/env.sh
GOWORK=off go test -tags integration -count=1 -run TestRealMongoEndSessionAfterCommitTimeoutIsBounded -v ./mongo/driver/
# 修前（81659082 的 session.go）：
#   upstream: WithTransaction=2s EndSession done at 30.01s（看门狗恢复网络的时刻）  FAIL bound 9s
#   downstream: WithTransaction=2s EndSession done at 24.97s                         FAIL bound 9s
# 修后：upstream / downstream 均 EndSession done at 7s（2s 窗口 + 5s abort 上限）     PASS
```

用例自建随机端口 toxiproxy 代理、directConnection 直连主节点；测量后只 `killSessions` 本会话的 lsid（不用 killAllSessions），让清理里的 dropDatabase 不必等 60s 生命周期。

**仍未解决（观察）**：截止导致的错误不一定带 `UnknownTransactionCommitResult` 标签（upstream 三次里一次带、两次不带——驱动对提交的一次内部重试“operation not sent”覆盖了首个带标签的错误），而 `errors.Is(err, context.DeadlineExceeded)` 同样匹配“回调中 / 提交前到期”这类确定未提交的错误。调用方只能把 `WithTransaction` 的任何错误当作结果未知、按持久回执裁决（现有调用方都是这样做的）；需要区分时应由 session 在提交发出后包一个专用哨兵。
