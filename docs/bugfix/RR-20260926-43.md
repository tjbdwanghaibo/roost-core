# RR-20260926-43 修复：versionedLock 异步续期按锁代际（token）绑定

问题：[RR-20260926-43](../bug/RR-20260926-43.md)（探针见 [REPRO-2026-09-26-04 §9](../bug/REPRO-2026-09-26-04.md)）。
日期 2026-09-26；实施基线 main `49f20ee`。状态：已修复、本地验证通过，已提交未推送/未发布。

## 根因

续期登记只有一个布尔 `touchActive`，与锁代际无关：

- 旧续期 goroutine 在 `Touch` 里把 `acquired` 置 false（基线 `remoteentity/versioned_lock.go:344-350`）后，要到 `runAsyncTouch` 的 defer
  （`:439-444`）才清 `touchActive`；
- 持有方见 `!IsAcquired` 跳过 Unlock（`transaction_manager.go` `releaseRemoteEntries`），不等旧 goroutine；
- 下一写者在同一锁对象上 `TryLock` 落在窗口内时，`startAsyncTouchLocked`（`:412-423`）见 `touchActive==true` 直接返回，新代际没有续期，
  TTL 后 Redis 租约过期，本进程写被 fence / Unlock 得到 NotOwned。

另外旧 goroutine 的 `Touch` 每次重新读取 `l.token`，它可能续期已经不属于它的新代际，退出时又把新代际的登记一起清掉——登记与服务对象都不按代际隔离。

## 决策

采用修复约束的第一种方式：**续期 goroutine 按 token 绑定**。

- `touchActive bool` 换成 `touchGeneration string`（当前登记的续期 goroutine 所服务的 token）。
- `startAsyncTouchLocked(token)`（仍在 `TryLock` 的 `l.mu` 临界区内调用）：若登记的是别的代际，**取消**它并立即为新 token 启动续期；
  不在 `l.mu` 下等待旧 goroutine（它的续期要取 `l.mu`，等待会死锁）。
- `runAsyncTouch(ctx, cancel, token, …)` 只调用 `touchLease(token)`：代际已被替换或已失效时直接返回过期并退出；
  退出时只在 `touchGeneration == token` 时清除登记。迟到的 `-1` 回复沿用原有 `l.token == token` 判断，只能把同一代际标记为失效。
- `stopAsyncTouch` 取消当前登记并 `touchWg.Wait()` 等待全部续期 goroutine（含正在退出的旧代际）。
- 公开 `Touch` 取当前 token 后委托 `touchLease`，行为不变。

goroutine 数量：每个锁对象至多一个服务当前代际的 goroutine；被替换的旧 goroutine 已被取消，在当前 Eval 返回（上限一个续期间隔的
evalCtx 超时）后退出，Unlock / Close 等待它们。每次加锁不会累积 goroutine。

未采用：

- “置 `acquired=false` 的同一临界区清 `touchActive`”：旧 goroutine 仍存活时新代际会启动第二个 goroutine，旧 goroutine 的 defer 随后会清掉
  新代际的 `touchCancel`/登记——仍需要代际判断，等于本方案的子集。
- “TryLock 在旧 goroutine 退出后补启动”：需要在 TryLock 外异步等待并补登记，状态更多，且 TryLock 持 `l.mu` 时不能等待。

## 文件与行为

- `remoteentity/versioned_lock.go`：`touchGeneration` 字段与所有权注释；`holdsGeneration`、`touchLease`；`startAsyncTouchLocked(token)`、
  `stopAsyncTouch`、`runAsyncTouch` 按代际实现。锁 token、fence、grant、Unlock/Refresh 逻辑未改。
- 回归 `remoteentity/versioned_lock_touch_generation_test.go`：
  - `TestVersionedLockNewGenerationRenewsWhileOldTouchGoroutineExits`（状态注入必现）：stub 让旧代际的 touch 挂在 Redis 端，
    `Refresh` 观察到旧代际失效（`acquired=false`，旧 goroutine 仍存活），下一写者 `TryLock`；放行旧回复（-1）后断言新代际 500ms 内有续期、
    旧 goroutine 退出后续期持续、Unlock 后不再续期、goroutine 数回到基线；
  - `TestVersionedLockTouchRestartStressNoLostRenewal`（高迭代、无注入）：20000 次“旧代际由续期 goroutine 自己观察到失效 → 持有方跳过 Unlock →
    立即 TryLock”，按 `GOMAXPROCS/2` 个 worker 并行，断言每个新代际 200ms 内得到续期，漏启动 0 次。

## 兼容性

无公开 API / 配置 / 协议变化。行为变化：新代际在旧续期 goroutine 退出前也会立即得到自己的续期；旧 goroutine 不再续期其他代际。

## 对抗性自查

- **锁代际与 fence**：token、fence、grant 仍只由 TryLock 分配；续期 goroutine 只以自己的 token 调用 touch Lua，Lua 按 owner==token 生效，
  新旧代际在 Redis 侧天然隔离。旧 goroutine 被取消前正在进行的 Eval 用的是旧 token，对新代际无影响。
- **迟到回复隔离（RR-20260924-20 类）**：touch 的 `-1`、refresh 的 0、unlock 的回复都在 `l.token == token` 下才改本地状态；`touchLease`
  入口先检查 `holdsGeneration(token)`，被替换的代际不再发出续期。
- **泄漏与死锁**：锁序保持 `l.mu → touchMu`；goroutine 退出路径只取 `touchMu`，`touchLease` 只取 `l.mu`，没有反向嵌套；
  `stopAsyncTouch` 不持 `l.mu`。TryLock 失败不启动 goroutine；旧登记由其 goroutine 在下一次 tick 发现代际不符后自行清除。
- **并发前提**：同一锁对象的 TryLock / Unlock 由 wrapper 写门串行（与基线相同）；`touchWg.Add` 只在 TryLock 内发生。
