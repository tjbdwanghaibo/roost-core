# RR-20261006-62 修复：lockstep 广播预算按发送器声明的载荷上限做满载校验

问题：[RR-20261006-62](../bug/RR-20261006-62.md)（F04-6）。基线 `a7285da6`，分支 `lockstep`，提交 `99a3e99f`。

## 根因

Room 的预算是一个常量（1232），既不是 KCP / QUIC 的载荷上限（1200），也不是 UDP 扣掉 32 字节信封后的载荷；Room 没有途径知道发送器真正接受多大的载荷。

## 修复

- `sync/nettransport`：新增可选接口 `DatagramPayloadLimiter{ MaxDatagramPayload() int }`——发送器在扣掉自己的信封后能接受的最大载荷。`KCPTransport` / `QUICTransport` 返回配置的 `MaxDatagramBytes`；`UDPTransport` 返回 `MaxPacketBytes - UDPEnvelopeOverhead`（新导出常量 32 = 16 字节会话 / 序号头 + 16 字节 GCM 标签，保护器只构造 AES-GCM）；`CompositeTransport` 转发数据报通道的声明。
- `sync/lockstep/room.go` `datagramBudget`：`MaxDatagramBytes` 为 0 时取发送器声明值，发送器没声明时取 `DefaultMaxDatagramBytes`（改为 `nettransport.DefaultMaxDatagram` = 1200）；配置值超过发送器声明值时 `ErrRoomConfigInvalid`；负数拒绝。最坏包估算不变（每座位满载、varint 按 5 字节算），比较对象从“包长”改为“载荷上限”。
- `MaxDatagramBytes` 字段注释改为“载荷上限（发送器信封之后）”。demo `battle.go.tmpl` 注释同步（demo 走玩家 TCP，值随常量变为 1200，2 人 × 8 字节 × depth 3 远在预算内）。

## 兼容性

**行为收紧**：没写 `MaxDatagramBytes` 的房间，预算从 1232 降为发送器声明值（KCP / QUIC / UDP 默认都是 1200）或 1200；最坏包落在 1201..1232 的配置现在 `NewRoom` 即失败（之前满载时整房被拒）。显式写了大于发送器声明值的 `MaxDatagramBytes` 现在被拒。`DefaultMaxDatagramBytes` 数值 1232 → 1200。新增 API：`nettransport.DatagramPayloadLimiter`、`UDPEnvelopeOverhead`、三个传输与 `CompositeTransport` 的 `MaxDatagramPayload`。未部署。
