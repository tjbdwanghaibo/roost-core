# NC-52 修复：RedisStore.Update 退避之后重读再重试

[问题](../bug/RR-20261005-NC-52.md) · [证据](evidence/noncore-bugfix-20261005-revn06/README.md)。已修复、声明场景验证，未发版。

## 决策与实现

`versionstore/redis_store.go` Update：输掉 CAS 后 `backoff` 之后用 `readRaw` 重读当前值（含缺失→found=false），再对新值 mutate。注释改写为原因：退避就是让赢家先写，CAS 带回的是赢家写之前的值。代价是**只在输掉 CAS 之后**多一次 GET；无竞争路径不变，最大尝试次数、退避策略、`ErrConflict` 语义都不变。与 `kit/service/rank/redis_store.go` 的“退避后重读”同形。

未采用：不退避、立即用 CAS 带回的值重试——这正是 `RetryBackoff` 注释反对的“锁步重试一起耗尽预算”；提高 `DefaultMaxAttempts`——把伪冲突变成更长的延迟，不修根因。`fredis.CompareAndSet` 仍返回 Current（其他调用方可能用），不改。

## 验证与边界

`retry_freshness_promises_test.go`（fake Redis，确定性，无 sleep）：竞争者在每个退避窗口写一次——修前 8 次全输 `ErrConflict`，修后第 2 次成功、竞争写不丢；退避期间键被删——修前 mutate 看到 present/present/absent（多浪费一次），修后 present/absent 且以版本 1 重建。`./versionstore` `-race -count=3`；所有依赖它的服务包 `-race` 通过；隔离真实 Redis `-tags integration -p 1` 跑 `./versionstore ./service/... ./kit/service/...` 891 pass / 23 skip（Cluster 等环境门）/ 0 fail，结束后未遗留键。chat 两副本并发 Append + Prune 组合在真实 Redis 修前持续失败、修后 9/9 通过。

未做：同配置吞吐 / p99 前后对照（只有小样本冲突计数，不当容量结论）；Cluster；高延迟网络下多一次 GET 的成本。
