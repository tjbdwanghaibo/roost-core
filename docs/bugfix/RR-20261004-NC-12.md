# RR-20261004-NC-12：watch callback 唯一收尾与可取消等待

2026-10-04，基线 `3560a19b5c2b2fbeb936bf1bb6a9c1fa0be1f956`。**已修复，声明场景验证，尚未发版。** [原问题](../bug/REVIEW-2026-10-04-noncore-08.md#rr-20261004-nc-12) · [运行](../review/REVIEW-2026-10-04-noncore-09.md) · [证据](evidence/noncore-bugfix-20261004-05/README.md)。

## 根因与实现

旧 [watch_callback.go](../../etcd/watch_callback.go) 的 requestClose 在 sync.Once 内同步 watcher.Close，CloseWithContext 尚未进入 select 就阻塞；另一个 caller 也会等相同 Once。run 的 defer 又调用一次底层 Close。

现在 requestClose 只标记显式关闭、取消 context 并发起每 subscription 唯一底层关闭任务。父 context 取消也通过 AfterFunc 发起同一任务，即使 handler 还在执行。run 在 handler 真实返回后等待 watcherDone，两者退出才 close(Done)。多 caller 的取消/期限只结束各自等待；后续 Close 等同一收尾，不派发重复关闭任务。

底层 Close 错误保存，完成后的 Close/CloseWithContext 返回它，Err 合并 terminal cause 和 cleanup cause。handler错误依旧通过 Err 提取，单独 handler错误而清理成功时 Close仍返回nil。父取消与 watcher 通道关闭竞争时保留 context 原因；干净显式关闭 Err仍为nil。

未采用提前完成 Done、忽略 watcher错误或每次重试新 goroutine。没有增加 IWatcher 强制方法；现有第三方实现仍可用，必须最终结束自己的 Close。

## 红绿与兼容

实际第三方 watcher.Close 经门闩确认入场。修前：`returned_before_watcher_release=false err=context canceled`，已取消的 caller 仍卡100ms；修后立即结束等待，底层门闩放行后才能完成 Done。新增八个并发 caller、取消后再次排空、handler和watcher双责任、关闭只执行一次、callback与清理双错误的 errors.Is，以及父取消先开始清理控制通过。

最终共同验证61 test pass事件、59叶子/独立项、0fail/skip，新正式生命周期15项和原overlay8项通过，两个测试包race/三包vet通过；KitEtcd无测试。完整命令与中间编译失败见[证据](evidence/noncore-bugfix-20261004-05/README.md)，不把夹具签名错误算修前行为证据。

公开接口不变；**行为收紧**：过去吞掉的底层关闭错误现在返回给完成等待的 caller，也通过 Err 保留。使用方必须处理失败，不以返回ctx错误代表资源已关闭。非协作 handler/第三方 watcher可让生命周期始终未完成，取消预算不能强制杀死用户代码；保留同一subscription供外部再次等候。callback内不能无期限等自己完成，应使用可取消等待，由外部负责最终排空。本批未验证真实 etcd网络恢复、HA、长稳或吞吐。[使用说明](../USER_GUIDE.md)。
