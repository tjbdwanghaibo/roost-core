# W-2026-09-22-02：Remote 创建 ID 在进程重启后复用

日期：2026-09-24。基线：`967bc69` 加现有工作树。状态：**根因已修复，生成工程与真实 Mongo/WAL 回归通过，未发布；历史冲突 WAL 未改写。** [原始问题](../bug/WANTED.md)。

## 原始证据与更正

找到 09-22 保存的真实 WAL，原目录为 `/private/tmp/claude-502/-Users-whb-roost/af8210cf-03f7-4bcc-ac3e-f021e05e9049/scratchpad/evidence/wal-dataengine-1000/`。只在副本上使用当前 nestwal 解码器读取，未打开原件做写入或 ack。

- segment 文件 631080 字节，SHA256 `a5f1d0e6c95f0e94077866f5fbc7b117f89115ccdda11be96616cccbd7b1cdff`。
- ack-0 SHA256 `ba08ac659144e5e156704610ee82bbfae29d2f8f7b57d19bbdac7b7621914338`；ack-1 SHA256 `f3956a59345550f97d8cb666b0aa23279a03ef57b8b5cfcfd2c47075779bd297`。
- 保留 ack 的副本剩余 70 条记录；另一个仅含原 segment 的副本完整读出 1158 条。
- 旧事务 `944c96f5412e6a6600000000000000f3` 已以 `BaseVersion=0, NextVersion=1` 创建 entity `6935121213685498901`。
- 新化身的首条未确认事务 `80ceb6c8c60c05af00000000000000ba`，handler 为 `handlerFoundGuild`，又以 `0→1` 创建 **同一 entity**。其中还有玩家 DAO 的 guild_id 修改，两次创建的业务内容不同。
- 后续新化身的 `…bf / …c2 / …d1 / …db / …e0 / …e7` 继续重复旧公会 ID，符合进程本地 sequence 重置的连续模式。

根因是生成工程 `HandleFoundGuild → RuntimeIDs().Next()`：`runtimeid.New(sid)` 固定 `static-half | sid<<34`，sequence 每次构造归零。这套分配器的既有测试甚至明确约定“重启复用，只适合临时实体”。Guild 持久化使用它违背了前提。

因此，旧报告“化身 WAL/ack/receipt 起点不齐”的推测不成立。WAL ack 按 segment/offset 排序，与事务前缀无关；两笔创建是不同事务，Mongo 的唯一键冲突是在保护旧公会。不能把没有 receipt 的新创建误判成已投影并跳过。

本机现存 `game/remote_entity` 是另一轮较晚测试的数据（事务前缀 `31d522…`），只作只读核对，没有把它当作原失败时数据库快照。

## 修复

- 生成工程公会创建使用 `game._guild_id_sequence` 的 Mongo 原子 `$inc`；框架 Mongo driver 已使用 primary、majority+journal 和 retryable writes。
- 发号在业务创建前持久化完成，失败不进入 Entity/WAL；允许空号，不回收。计数器与业务数据同库备份恢复，不能单独清空。
- 新公会使用 unique ID 的 dynamic 半区，避开全部历史 runtimeid 的 static 半区；完整 EntityID 包含 kind，不与玩家身份冲突。旧公会 ID 无需迁移，仍可正常寻址。
- 保留 runtimeid 对临时实体的既有契约；没有更改 Remote fence、WAL 格式或“不同事务不得覆盖同一新建实体”的约束。
- Remote 原子投影错误补充 entity ID 和 `base→next`，保留 `%w` 错误链，便于定位以后真实冲突。
- 模板配方增加 `guild_ids.go` 与对应测试，已有生成业务文件不会被 project sync 自动覆盖；已有工程需移植公会发号路径及 Controller 的 Mongo collection 装配。
