# RR-20260914-10:同 tick 投影覆盖使延迟 ACK 绑定错误基线,后续 delta 静默漏对象

**仓库 / 位置**:roost-core `statesync/session.go`(`prepare` / `commitPrepared`),`statesync/replicator.go`(`prepareLatest`)。
**修复单元**:U-0200(C8)。**定位文档**:TROUBLESHOOTING T-94。

## 问题

`sent` 按 tick 建键,`Acknowledge` 只按 tick 确认。同一 tick 可以被重新投影(兴趣变化)再次提交,第二次覆盖
`sent[tick]`。审查的串行序列:tick 1 投影只显示对象 1 → 提交、客户端应用;同 tick 兴趣变化后再投影显示 1、2 →
提交(传输已接受),网络丢弃;第一版的 tick 1 ACK 迟到,绑到已被覆盖的 `sent[1]`(含 1、2);发布内容相同的 tick 2
后,服务端算出零变化的 delta,客户端 `ApplyDelta` 成功却永远只有对象 1。`client objects=1 want=2, delta changes=0 base=1`。

## 根因

基线身份是 (session, tick),而一个 tick 对一个会话可以有多个视图;ACK 携带的信息不足以区分(C8:发送侧
和确认侧对"基线是什么"的判据不同)。`SendLatest` 是先发后 `Commit`,所以只在 Commit 时拒绝也太晚——传输已经
把第二版交出去了。

## 方案选择

- **帧 / ACK / 基线引用都带修订号。** 协议变更,客户端要跟着改;不在一个 RR 的范围内。
- **只保留第一份 `sent`,不管客户端拿到哪版。** 审查已指出不够:客户端可能收到的是后一版。
- **一个 tick 一个视图(采用)。** `prepare` 发现 `sent[targetTick]` 已存在时,把已提交的视图作为本次的
  "当前快照",跳过重新投影——同 tick 的再次发送与第一次字节一致,ACK 无歧义;兴趣变化延到下一 tick 生效
  (审查的"只在下一 tick 改投影"对照本来就正常)。并发准备(两次 prepare 都早于任一 commit)是这条覆盖不到的:
  `commitPrepared` 对"该 tick 已有不同视图"按 `ErrPreparedFrameStale` 拒绝,服务端基线记录保持第一版。这时客户端
  可能持有第二版,但下一帧 delta 从第一版出发:多出来的对象走 `ObjectCreate`(覆盖同 ref),少掉的走 `ObjectRemove`
  (删不存在的是 no-op),组件差异被 set 覆盖,都收敛;真正对不上的落到 `ErrObjectNotFound` → 客户端基线不匹配
  → 主动 resync,是安全方向。

## 改动

`session.go`:`prepare` 的 8 值返回改为 `prepareResult` 结构体,多出 `frozen`;`commitPrepared` 对同 tick 不同视图
返回 stale;新增 `snapshotEqual`(按 ref / TypeID 的无序比较)。`replicator.go`:`prepareLatest` 有 `frozen` 时跳过
投影。老测试 `replicator_test.go` 里直接调 `prepare` 的一处跟着改。

## 证明

`statesync/baseline_identity_promises_test.go`:
- `TestPrepareLatestPromiseFreezesATicksViewAtFirstCommit`(审查的两个子例:下一 tick 对照 / 同 tick 丢第二版);
- `TestCommitPromiseRejectsADifferentViewOfAnAlreadySentTick`(并发准备:不同视图的第二次提交 stale,冻结后再准备
  复用第一版且提交幂等)。

修前红:`client objects=1 want=2, delta changes=0 base=1` / `a different view of an already-sent tick was committed over the first: <nil>`。
修后 statesync 含 `-race` 全绿,core 全仓 `-race` 全绿。

## 未做 / 边界

- 并发准备的第二版若已被传输送达,客户端与服务端基线记录短暂不一致,靠 delta 操作的幂等性 / 客户端 resync 收敛,
  不是精确的修订身份;精确身份需要协议加修订号。
- 兴趣变化在同一 tick 内不再生效,最多延迟一个 tick(发布周期)。
