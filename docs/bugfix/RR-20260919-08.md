# RR-20260919-08：一次 loader panic 让这个实体永远加载不了（U-0254）

- 仓库：roost-core `entity`、`dataengine/engine`
- 缺陷类：C7（拿了东西没有 defer 归还）
- 优先级：P1
- 相关：T-148；测试 `entity/load_flight_promises_test.go`、
  `dataengine/engine/entity_repository_flight_promises_test.go`

## 问题

两层共享加载（`ManagerAccess.loadEntityShared` 与 `EntityRepository.LoadEntity`）都把
"从 map 里删掉这次 flight + `close(done)`" 写在加载调用**之后**，没有 defer。

于是 loader / store / builder / 解码 / `OnInitFinish` 里的任何一次 panic 都会跳过这两步：
map 里留下一个永远不会关闭的 flight。进程还活着（Nest 顶层会 recover handler 的 panic），
但这个 fullID 从此不可用——后来的每个请求都等在那个 channel 上，直到自己的 ctx 超时，
而且**重试永远进不了 loader**，因为它们看到的是"已经有人在加载了"。

一次 panic，一个实体永久下线，没有任何日志说明为什么。

## 根因

"拿了就要还"的那条还没有落成 defer。共享加载天然是"注册 flight → 做事 → 结束 flight"，
中间那一步是任意深的用户代码，所以结束必须无条件。

## 方案

- 采用：**两层都用 defer 收尾**，顺序固定为"写入稳定结果 → 删除 flight → close(done)"。
  panic 时把它变成一个带原因的稳定错误交给 waiter（他们在自己的 goroutine 上，在那里重新 panic
  等于让他们替别人的错误把进程带走），然后**让 leader 继续 panic**——加载失败的调用方不能被告知成功。
- 没采用：只在 Nest 外层 recover。仓库不是只能从 Nest 进来（remote entity、guard scope 都直接调），
  而且 Nest 的 recover 发生在 flight 已经被污染之后。
- 没采用：把 panic 静默转成错误。那会让"加载 panic 了"看起来像"加载失败了"，
  两者的运维含义完全不同。

## 改动

`entity/manager_access.go`、`dataengine/engine/entity_repository.go`：各加一个 `settled` 标志与 defer。

## 证明

修前红（两层各两条）：`the flight survived the panic; every later request for this entity would wait forever`、
`the waiter was released by its own deadline, not by the flight finishing`。
仓库那两条用 `git stash push -- dataengine/engine/entity_repository.go` 单独验过红。
修后：flight 被清掉、重试真的再进 loader（`loader.calls == 2`）、waiter 拿到点名 panic 的错误。

## 未做 / 边界

- **第一个调用方的 ctx 仍然是整次共享加载的执行 ctx**，所以 leader 取消会影响所有 waiter。
  审查把它列为相邻设计风险、没有另立 RR；本轮也没有改——改它要先定"共享加载的生命周期归谁"。
- 没有给"加载 panic"加计数器。它会以错误文本出现在调用方和日志里。
