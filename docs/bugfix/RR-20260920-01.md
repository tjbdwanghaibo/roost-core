# RR-20260920-01：BSON 装不下的那一半散列空间（U-0261，C8）

## 问题

远端提交在投影阶段报

```text
dataengine mongo: remote projection: cannot marshal type bson.M to a BSON Document:
12630717602282170696 overflows int64
```

BSON 没有无符号 64 位整数。snapshot 的 `Checksum uint64` 原样进文档，于是**大约一半的载荷**
（CRC64 高位为 1 的那些）写不进去。更糟的是这条 WAL 记录会在每次启动恢复时以同样的方式再失败一次：
进程从此起不来，只能删 WAL。

第十八批（Guild）就是卡在这里，所以这条修完 Guild 才能合入。

## 根因

C8：同一个值在两处用了不同判据。产生方（CRC64）认为 64 位全域都是合法值——事实如此；
存储方（BSON）只有有符号 64 位。中间没有人负责把这两个域对上。

**W-2026-09-19-01 的推断在这里被更正**：我当时判成"负的 stateVersion 转 uint64"，
审查核实 `remoteentity/batch.go` 与 `RemoteEntityBase.SetEntityVersion` 都会把负版本归零，
那条推断不成立。真正的触发项是 checksum，而它和版本号**不能用同一种修法**。

## 方案选择

按字段语义分开定编码，这是本条的核心判断：

| 字段 | 谁在用它 | 编码 |
| --- | --- | --- |
| `checksum` | 只做相等比较 | 定长 8 字节 binary，**保住全域** |
| `version` / `epoch` / `fence` | Mongo 要按它们比较（快照读 `$gte`、版本 CAS） | 保持数字，**域截到 MaxInt64** |

- 放弃 **checksum 也截断/取低 63 位**：那会让一半的载荷共享校验和空间，等于削弱校验。
- 放弃 **版本也改成 binary**：`$gte` 和 CAS 依赖数值序，改成字节就得同时改查询与迁移。
- 放弃 **只在投影处 recover**：记录那时已经持久化，恢复会一遍遍重放它。

## 改动

- `entity/remote_snapshot_codec.go`：新增 `RemoteChecksum`（底层 `uint64`），自带 BSON 编解码：
  写 8 字节，读兼容 binary 与历史的 int64/int32/double/null。`RemoteSnapshotChecksum` 改为返回它，
  `RemoteSnapshotRecord` / `RemoteSnapshotEnvelope` / `RemoteSnapshot` 的字段随之改名类型。
  这样**每一条持久化路径**（快照文档、事务/outbox 文档里的整个 commit、L2 的 JSON）一次修好。
- `remoteentity/commit_encoding.go`：`validateRemoteCommitEncodable`，在 `validateRemoteCommitBatch`
  里、写任何东西之前拒绝超出 MaxInt64 的计数器；checksum **不在**校验范围内，因为它已经可写。

### 一个踩了两次才看清的坑

第一版方法签名写成 `MarshalBSONValue() (bson.Type, []byte, error)`，编译通过、测试照旧红。
驱动的 `ValueMarshaler` 是 `(byte, []byte, error)`，而 `bson.Type` 是 `type Type byte`——
**定义类型，不是别名**。签名不匹配时接口没被实现，方法被静默忽略，值走默认的 uint64 编码器。
现在注释把这件事写在方法上方。

## 证明

`remoteentity/snapshot_encoding_promises_test.go`：

- `TestASnapshotCommitsWhicheverHalfOfTheHashSpaceItLandsIn`：用循环找出 CRC64 落在 MaxInt64
  两侧的两个**普通**载荷，各提交一次并读回。修前"上半区"红：

  ```text
  a snapshot whose checksum is 16867212788789152291 could not be committed:
  16867212788789152291 overflows int64
  ```

  （"下半区"修前就是绿的——这正好证明了丢的是一半空间，不是全部。）
- `TestACommitWhoseCountersCannotBeEncodedIsRefusedUpFront`：version / marker epoch / route epoch /
  lock fence 各一条。断言的不是"哪一种拒绝"，而是**调用方永远拿不到 `overflows int64`**——
  拿到它就意味着记录已经走到编码器，在持久化路径上就意味着它已经进了 WAL。
- `TestAChecksumStoredAsANumberStillReads`：int64 / int32 / 缺失三种历史形态仍可读。
- `TestAChecksumIsStoredAsEightBytes`：新写出去的确实是 8 字节，避免"兼容旧的"被误读成"还在写旧的"。

fake mongo 用真实 bson 编解码每一个文档（`mongotest.normalizeDoc`），所以这些用例验的是产品代码
写出来的那个文档，不是我对 BSON 的理解。

## 未做 / 边界

- **已经存在的毒丸 WAL 记录没有隔离流程**。本条让新记录不可能成为毒丸，但对一台已经起不来的进程，
  唯一办法仍是删 WAL。审查建议的"报告 transaction/entity/snapshot key 并进入可操作的隔离流程"
  需要先定契约（谁有权跳过一条权威提交、跳过之后状态怎么算），在 dataengine 的恢复路径上，不在本包。
- 版本域从 `uint64` 实际收窄到 `MaxInt64`。这是显式选择：单调计数器到 MaxInt64 已经足够，
  而保住 Mongo 的数值序比保住理论域更值钱。
- **顺带发现**：`safemap.SmallSafeMap` 的 `MarshalBSONValue` 也是 `bson.Type` 签名，同样从未生效，
  它会被编码成**空文档**。DAO 生成物目前自己拼 patch，不走这条路，所以是潜伏的；
  已记入 `docs/bug/WANTED.md` 的 W-2026-09-20-03，没有顺手改。
