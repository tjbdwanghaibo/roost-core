# RR-20260916-01:写入 / 发布结果不确定后继续使用旧内存状态

**仓库 / 位置**:roost-core `syncstream/file_journal.go`,`flushBatch` / `Checkpoint` / `Record`。
**修复单元**:U-0212(C5)。**定位文档**:TROUBLESHOOTING T-106。

## 问题

1. sequence 2 完整写入并 fsync,同步结果却报错:History 回滚内存(latest 仍 1),调用方重试 Append **又成功**写了
   一条 sequence 2——重启时同一 WAL 两条 sequence 2,`ErrInvalidSnapshot`。
2. checkpoint 已发布新 generation,发布同步报错:对象仍记旧 generation,随后 Append 成功却落在旧 WAL;重启选最新
   checkpoint/WAL 对,成功追加的 sequence 2 消失。Linux `durableReplace` 先 Rename 再同步目录,天然存在"文件已发布但
   函数报错"的阶段。

## 根因

所有错误都被当成"没有副作用"(C5)。Write / Sync / 发布这三步一旦开始,失败就是不确定结果;后续继续用落后的内存
状态写,要么重复序号要么丢追加。

## 方案选择

- **原地恢复:按可确认的 WAL 末端重建 History。** 要在写路径里读回文件、重建内存,复杂且审查也提醒"不能仅重置错误位"。
- **fail-stop(采用)。** journal 加 `failure`:Write / Sync / publish 出错即置位,之后 `Record` / `Checkpoint` /
  `flushBatch` 一律返回 `ErrHistoryJournalFailed`(包着原因),直到关闭重开——重开的 Load 从真正落盘的内容恢复
  (半尾由 U-0211 截掉,完整的多余记录按落盘为准)。副作用**之前**的失败(临时文件建不出、下一代 WAL 创建失败)
  仍返回普通错误,可以重试。`publish` 出错时不再删临时文件——它可能已经是 checkpoint。
  为了能测"副作用已完成但调用方收到错误",把 `syncFile` / `publish` 做成 journal 的字段,默认真实实现。

## 改动

`file_journal.go`:`failure` / `syncFile` / `publish` 字段与 `failed()`;`Record` / `flushBatch` / `Checkpoint` 入口拒绝;
三处出错置位。`syncstream.go`:`ErrHistoryJournalFailed`。

## 证明

`syncstream/journal_failstop_promises_test.go`:真 fsync 后报错 → Append 报 failed、重试与 Checkpoint 都被拒、重开后
序号 2 恰好一次;真 rename 后报错 → Checkpoint 报 failed、Append 被拒、重开加载到新 generation;对照:目录只读导致临时文件
建不出(副作用之前)→ 普通错误,恢复权限后重试成功。修前(缝已加、fail-stop 未加时)红:重试 Append 返回 nil。

## 未做 / 边界

- fail-stop 后没有"原地恢复"入口,必须重开 journal;History 对象本身不知道 journal 失败(它的 Append 会持续拿到 failed 错误)。
- 注入是"真做完再报错",不是硬件故障;没有 Linux 断电实验。
