# RR-20260918-10：顶层 DAO 容器里的嵌套值，换掉之后还能以原来的 key 写回

- 单元：U-0238 · 缺陷类 C4（跨层契约不一致）· 等级 P1
- 仓库：roost-codegen `internal/dao`（生成器模板）
- 排障行：T-132 · 与 U-0236 同源（那次修的是嵌套结构内部，这次是顶层 DAO 的容器）

## 问题

`SetEquips(key, new)` 给 new 装上回调，却不对同 key 的 old 调 `SetNotify(nil)`；
回滚的 undo 把 old 放回并调 `d.Init()`，而 `Init()` 只会给**当前**内容重新接线，
不会解除已经被丢弃的 new 的回调。

比 U-0236 严重一档的地方在于**回调捕获了 key**：

```go
val.SetNotify(func() { d.markEquipsKeyDirty(key, val) })
```

于是一个已经离开 map 的值，后续任何修改都会以**它已经不占有的那个 key** 的名义进入持久化补丁——
把游离对象的内容写到当前 key 上。这是数据错误，不是多打一次脏标记。

审查的四个场景（`internal/dao/testdata/runtime/ownership_test.go`）：

| 场景 | 期望提交记录 | 修前 |
| --- | --- | --- |
| 提交替换后改**旧**值 | 0 | **1，且补丁写的是 `equips.1`** |
| 提交替换后改**新**值 | 1 | 1 ✔ |
| 回滚后改**旧**值 | 1 | 1 ✔ |
| 回滚后改**新**值 | 0 | **1** |

## 根因

与 U-0236 完全同源：**"值进入/离开容器"和"通知绑定/解绑"不是同一个操作**。
容器这一侧多了一条：`d.Init()` 被当成 undo 的兜底手段，而它只会绑不会解——
一个"重新给所有人接线"的函数天然修不了"某个人不该再有线"。

## 方案选择

- **（选中）与 U-0236 同一形状：生成 `bind<F>Value` / `unbind<F>Value`（map，按 key）与
  `bind<F>Items` / `unbind<F>Items`（slice）**，不标脏、不登记 undo，因而可在已是 rolledBack 的事务里调用。
  setter、`Del`、raw 装载、`Init`、以及两处 undo 全部改走它们；undo 里的 `d.Init()` 随之删掉——
  精确地解绑当前、恢复、再绑定，比"重绑所有人"既正确又便宜。
- 在 undo 里复用公开 mutator：不行，事务已 rolledBack，会再登记一次 undo。
- 让回调不捕获 key（改成每次从 map 反查自己的 key）：反查要遍历，且同一个值出现在两个 key 时无解。

## 改动

roost-codegen `internal/dao/template_dao.go`：

- map 字段生成 `bind<F>Value(key, val)` / `unbind<F>Value(key)`（后者解绑**当前**在该 key 上的值）；
  `Set` 改为"解绑当前 → 写入 → 绑定新值"，undo 改为"解绑当前 → 放回旧值 → 绑定旧值"，`Del` 同形。
- slice 字段生成 `bind<F>Items` / `unbind<F>Items`，`Add` / `SetAll` 及其 undo 同形。
  slice 的回调不捕获下标，所以症状只是多余的脏标记——但它是同一处模板里的同一个缺陷，一起修。
- `Init` 与 `set<F>RawMap` 改调 helper，于是"谁通知谁"在生成物里只有一处定义。
- fixture `internal/dao/testdata/def/hero.go` 加 `Squad []*EquipInfo`（此前顶层没有嵌套 slice 字段），goldens 重生成。

## 证明

`internal/dao/testdata/runtime/ownership_test.go` 新增 `TestTopLevelMapValueOwnership`（4 叶子）与
`TestTopLevelSliceItemOwnership`（4 叶子），由 dao 运行时门跑（真 core、真 Nest 事务、记录型 committer）。
除记录条数外还解码 `Mutation.Patch.SetBSON`，把"这次提交会写哪些文档路径"打进失败信息。

修前（`sh scripts/dao-golden-runtime.sh`）：

```
--- FAIL: TestTopLevelMapValueOwnership/committed_old_is_detached
    mutating the old value produced 1 commit records, want 0 (it would write [equips.1])
--- FAIL: TestTopLevelMapValueOwnership/rolled_back_new_is_detached
    mutating the new value produced 1 commit records, want 0 (it would write [])
```

第一条就是审查说的数据损坏：**游离的旧值会以 `equips.1` 的名义写回**。修后八个叶子全绿，
codegen `go vet ./... && go test ./... -count=1` 全绿，生成工程 build / test 全绿。

## 未做 / 边界

- **审查要求的 panic、确定性拒绝提交、多次写回滚三类仍未覆盖**：本轮只加了"提交 / 回滚 × 旧值 / 新值"
  这一组，以及 slice 的同组。
- 顶层 Kind 3（嵌套结构字段）的 `Set` 仍是"赋值后绑定"，没有解绑——值类型是就地覆盖，没有旧对象可解绑；
  指针类型有，但顶层没有该形状的 fixture，未改也未测。写在这里，下一轮若登记就一起做。
- 一个值同时出现在两个 key 上仍是未定义行为（`SetNotify` 是单槽，后绑的赢），与 U-0236 的边界一致。
