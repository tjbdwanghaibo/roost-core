# RR-20260916-03:同一总线的同 topic 订阅竞争同一消费者,广播变为分摊

**仓库 / 位置**:roost-core `room/jetstream_syncbus.go`,`Subscribe` / `Stop`。
**修复单元**:U-0209(C8)。**定位文档**:TROUBLESHOOTING T-103。

## 问题

同一 `jetStreamSyncBus` 对同一 topic 注册两个本地 handler:每次 Subscribe 都用相同 topic/SID 生成同一个持久消费者名,
再各自 `Consume`。真实服务端把消息在两个 Consume 实例之间分摊(审查实测 12 条 → 6/6),分片流两边都重组不出 Packet
(51 个分片全部 ACK,0 个 Packet)。普通 NATS 总线用普通 Subscribe,是广播。切到 JetStream 后本地多个同主题同步器漏更新。

## 根因

`ISyncBus.Subscribe` 的契约是广播,而持久 JetStream 消费者是工作队列;适配层把"一次 Subscribe"映射成"一个 Consume",
两种语义在同一个消费者名上撞在一起(C8)。

## 方案选择

- **每次 Subscribe 随机 durable 名。** 避免竞争,但消费者积累、历史重放与游标迁移问题一堆,审查明确不建议。
- **一个 topic 一个底层订阅 + 本地 handler 注册表(采用)。** 第一位订阅者创建消费者,后来者只登记 handler;
  投递时在锁内快照 handler 列表、锁外逐个调用;每个 handler 拿自己的消息副本(与普通总线一致,handler 可能改 msg);
  panic 逐个隔离、错误按既有契约记日志继续;单个退订只删自己,最后一位离开才停底层订阅;Stop 停全部并清表。
  `mu` 贯穿第一次创建,并发的第一批订阅者只创建一个消费者,Stop 也不会和创建交错。消费者身份与重启游标不变。

## 改动

`room/jetstream_syncbus.go`:`subs []*syncSubscription` → `topics map[string]*topicFanout`;`Subscribe` / 退订闭包 / `Stop` 重写;
新增 `invoke`。老测试 `TestJetStreamSyncUnsubscribeRemovesTrackedSubscription` 改看 `topics`。

## 证明

`room/jetstream_fanout_promises_test.go`:同 topic 两个 handler 各收全部消息、只建一个消费者、数据互不影响;退订一个另一个
继续且底层不停;最后一位退订底层停一次、再订阅重建;handler panic 不影响兄弟;8 个并发首订阅只建一个消费者。
修前红:`two local subscribers created 2 durable consumers, want 1 shared` / `concurrent first subscribers created 8 consumers`。
修后 room 含 `-race` 全绿。
