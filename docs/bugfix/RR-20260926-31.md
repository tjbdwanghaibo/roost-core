# RR-20260926-31：闲置交还在驱逐后、释放租约前等待本实体投影

问题：[原始复审](../bug/RR-20260926-31.md)。日期 2026-09-26。实施基线：main `87d9499`。
状态：已修复，适用本地验证通过，已本地提交，未推送/发布。

## 根因

`demo/internal/service/game/playerowner.go.tmpl`（基线）`handBackIdle` 在 `dropResident` 成功（`:506`）后立刻 `Release` Redis 租约（`:511`）。
驱逐只丢掉内存副本；这份副本已经确认的事务可能还在本进程 WAL 里等待投影。另一进程接手时只从 Mongo 读取
（RR-10 的 `WaitEntityProjection` 只跟踪本进程在途记录，`dataengine/engine/entity_projection.go`），于是装载落后版本，
之后两边投影版本冲突 fatal。

## 修复

- `kit/dataengine/mod.go` 新增 `Mod.WaitEntityProjection(ctx, entityID)`，转发 `Runtime.WaitEntityProjection`；
  Mod 未装配、Runtime 未就绪、投影失败、WAL 不健康都返回错误。业务从 `mods.ModDataEngine` 按接口取得，不需要引用 kit 具体类型。
- 模板 `playerowner.go.tmpl`：`projectionBarrier`（按玩家 ID 询问）与适配器 `playerProjections`（`BuildEntityID(playerID, Player)` 后转发引擎）；
  `PlayerOwners.Projections(...)` 与 `Evict` 同样在发布前装配。`handBackIdle` 顺序改为：会话检查 → 驱逐 → **等待本玩家投影** → `Release`。
  等待失败（超时 / 投影失败 / 未装配屏障）时 `cancelHandBack` 恢复准入、保留租约，下一轮刷新重试（驱逐已完成，重试时是空操作）。
- 等待只在刷新循环自己的 goroutine 上发生，不在 Nest 快 worker 上；框架入口在快 worker 上仍按 RR-06 fail-fast。
- 一轮交还共用一个 `projectionWait` 预算（默认与驱逐预算相同 5 秒），数据库卡住时一轮刷新只多等一个预算，不是每个玩家一个。
- `service.go.tmpl` 在 `Evict` 之后装配 `Projections`；取不到 `ModDataEngine` 的屏障能力时 Init 报错（DataEngine 是唯一持久化引擎，缺失即装配错误）。

未采用：把等待放进 `playerEvictor.EvictPlayer`——驱逐还服务于 Claim 跨间隙丢副本与 fence，这两处等待没有意义，且 fence 路径不该被数据库拖慢；
每玩家独立预算——会让一轮刷新在数据库卡住时累加到 8×预算，挤掉其他玩家的续租。

## 兼容与行为变化

生成工程的闲置交还现在可能推迟：投影未完成时租约保留到下一轮（每 10 秒一轮），期间该玩家准入正常恢复。
自定义工程若沿用此模板但不装配 `Projections`，租约永不闲置交还（告警日志），与“不装配 evictor 不交还”同一取向。
kit 新增方法，无破坏性 API 变化。
