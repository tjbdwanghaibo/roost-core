# RR-20261001-06：account 名字被他人 committed 后自动释放 pending slot；补 owner-only `Admin.ResolvePendingCreation`

问题：[docs/bug/RR-20261001-06.md](../bug/RR-20261001-06.md)（来源 [B 线 service 修复独立复审 §4 疑点 1](../review/REVIEW-2026-10-01-bline-audit-service-1.md) → W-2026-10-01-01，维护者 10-01 拍板）。等级 P2。基线 main `c38e0b08`（worktree HEAD `815ac535`）。状态：已修复、已验证（Memory + 隔离真实 Redis），已提交，未推送、未发版。

## 根因（到行，worktree HEAD `815ac535`）

RR-20260929-19 把建角计划持久在 slot 上，Admitted 之后一切错误都"向前恢复"——正确，但留了一条死路：

- `kit/service/account/create_role.go:79-87` `resumeRoleCreation` 的 `Names.Reserve` 拿到 `directory.ErrKeyTaken` 时调 `releaseCreationSlot(ctx, key, slot, false)`；`:180-192` 的 `DeleteIf` 条件是 `PlayerID == 0 && Creation.ID 相同 && (foreignID || !Admitted)`——Admitted 的计划只在 foreign allocator ID（`:145`）时才能删。
- 名字租约 `ClaimTTL`（默认 30s）过期、被另一个账号 Reserve + Commit 之后，这个计划不可能再 Commit 自己的名字（`directory/store.go:160-186` Commit 要求 token 等于当前条目的 token；committed 条目只有 owner 能 `Release`，`:269-296`，本包无人调 Release），也就永远走不到 `:149` 之后的发布。
- 但 slot 留在 pending：同名重试 → `ErrNameTaken`；换名 → `createRole:68-70` `ErrRoleLimit: another name is pending`。该账号在该区服永久建不了角色。包里没有 `admin.go`；platform（`ResolvePendingAttempts`）、activity（`ReconcileProgress`，RR-20261001-05）、session（`ForceRelease`）都有 owner-only 面，account 没有。

## 决策与未采用方案

**采用：(a) owner-only 入口 + (b) 的可判定子情形自动失败，一个修复单元。**

1. **名字被别人 committed → 同名重试顺手释放 slot。** 这是 (b) 里唯一能证明"不会释放一个其实仍可能提交的计划"的子情形，以名字租约状态为准：
   - committed 给别的 owner 是**稳定事实**：Commit 需要 token 匹配当前条目（我们的 token 已不是条目的 token），committed 条目只会被它的 owner `Release`（本包没有调用方），所以这个计划此后既不能 Commit 名字也不能发布角色（发布在 Commit 之后，`create_role.go:149-152`）。即使别人日后 Release 了名字，这个计划的 slot 已经没了，账号会以新计划重建——正是想要的结果。
   - 被别人 **reserved** 不释放：预约会过期，计划仍可能完成（RR-19 的"保留证明"对这一情形仍成立，`TestNameReservedElsewhereKeepsThePendingSlot` 钉住）。
   - 丢失回复留下的未发布角色记录**不删**：它永不可玩（`roleReady` 要 slot 指向它）、永不可恢复（新计划是新的 creation id），而删一条可能是玩家数据的记录是本包不做的自动清理；RR-19 已把孤儿角色留给离线对账。指标 `create_role.plan_released`。
   - Lookup 失败时按旧行为（保留 slot）：不以未知结果释放。
2. **`Admin.ResolvePendingCreation(ctx, accountID, serverID, note) (RoleCreation, error)`，owner-only，不上 bus。** 覆盖自动路径不能证明的情形：名字只被别人 reserved、或名字空闲但玩家要换名（例如 NameRules 后来拒绝了这个名字——`CreateRole` 在 resume 之前就 `ErrNameInvalid`，计划其实不可完成）。
   - **顺序**：读 slot + 名字条目决定（拒绝不写任何东西）→ 把备注写到 **Account**（`admin_note` / `admin_action_at_unix`）→ `DeleteIf`（读到的版本 + `Creation.ID` + `PlayerID == 0`）。备注写在 Account 上是因为 slot 本身要被删掉，Account 是留下来的那条记录；写在删除之前，是为了被围栏挡住的释放（并发重试再次 admit 或发布让版本变了）仍留下这次干预——"有备注没效果"可复核，"有效果没备注"不可。版本围栏意味着任何在读之后改动 slot 的并发 CreateRole 都让释放失败并报 `ErrConflict`（`slot moved after the decision` 子用例）。
   - **拒绝（`ErrNotResolvable`）**：无 slot；已发布（`PlayerID != 0`）；legacy 空 slot（没有 creation 身份，可能挂着已发布的 legacy 角色，释放等于放开"一服一角"）；名字仍被本计划自己 **reserved**（可能有在途尝试，租约 ≤ ClaimTTL 自己会过期，错误文本给出过期时间）；名字已被本计划自己 **committed**（同名 `CreateRole` 就能完成；放弃它要么烧掉要么 Release 一个 committed 名字，而"先删 slot 再 Release"中间失败就是永久烧名、"先 Release 再删"遇到并发发布就是没有名字条目的已发布角色——两种都不做）。
   - 返回被放弃的 `RoleCreation`：`PlayerID` 指向可能存在的未发布角色记录，运维据此留档。

**未采用：**

- 只做 (a) 不做 (b)：committed 这一情形是可以机器判定的，让玩家等运维没有必要。
- (b) 扩大到"租约过期且名字已被占（含 reserved）"：reserved 会过期，这是释放一个仍可能提交的计划，题目要求证明不释放，证不出来。
- 保留 slot 改成"已放弃"标记而不删：`createRole` 要多一条"已放弃 slot 上 CAS 换新计划"的路径（插入专用的 `Create` 走不了），hot path 多一个状态、和既有的 `DeleteIf` 释放两套语义；删除复用 RR-19 已有的身份围栏删除，`createRole` 零改动。
- 备注写在未发布角色记录上：只在角色记录存在时才有地方写，而且 `Role` 是 RPC 线型，不该带运维字段。
- 入口里删除未发布角色记录：见上，不自动删可能是玩家数据的记录；`Config.Roles` 也没有要求支持 `DeleteIf`。
- 让入口接受"名字 committed 给本计划"并 Release：见拒绝条目里的两种失败顺序。

## 未验证项 / 风险

- `TestResolvePendingCreationRefusesWhatItCannotProve` 只在 Memory 跑（它用 `newService`，不走 Redis 变体）；拒绝分支只读 slot / 名字条目，不依赖后端；`slot moved` 子用例靠包装的 `DeleteIf` 把并发重试插在决定与释放之间，Redis 侧 `DeleteIf` 的版本围栏由 `versionstore` 自己的用例覆盖。
- 没有在真实 Redis 上等默认 30s `ClaimTTL`；路径与 1s TTL 相同（`Lookup` 报缺失 → 别人 Reserve 成功）。
- 没有 Cluster 环境，`ResolvePendingCreation` 只用 Account / Slots / Names 三个单 key store。
- 未发布的孤儿角色记录与它占用的 player id 仍留在 `Roles` 里（RR-19 已接受的"合法空洞"），本修复不清理，也没有枚举它们的入口；T-182 给了判别方法。
- `ResolvePendingCreation` 在"备注已写到 Account、DeleteIf 又失败"时留下一条没有效果的备注；这是有意的（见决策），运维重跑会覆盖它。
- 名字只被别人 reserved、玩家又不断重试同名的账号，`ResolvePendingCreation` 会一直拒绝"live reservation"（每次重试续约本计划的预约，直到对方预约过期）；停掉客户端重试或等 ≤ ClaimTTL 即可。

## 复核后的补修（2026-10-05）

问题见 [bug 记录末节](../bug/RR-20261001-06.md#复核后的补修2026-10-05)。基线 `50e9a4e8`，worktree 分支 `revn06`。

- **决策**：换名请求遇到 PlayerID 为 0 的 pending 计划时，用与同名路径**同一个证明**判断它是否已死——`nameCommittedElsewhere(plan.Name, <slotKey>/<plan.ID>)`，即名字已 committed 给别的 owner。已死则 `releaseCreationSlot(planDead=true)`（版本 + 计划身份 + PlayerID==0 围栏的 `DeleteIf`），计 `create_role.plan_released`，然后在同一次调用里按新名字走正常的建计划流程；未死（本计划自己 reserved / committed，或只被别人 reserved）仍答 `ErrRoleLimit`、slot 不动。每次调用至多释放一次：第二轮仍遇到别的名字，说明另一个请求刚建了新计划，它是活的。
- **未采用**：在 `ErrRoleLimit` 里回传旧计划名字让客户端自己同名重试——把服务端可判定的事实推给客户端，且旧客户端拿不到；换名时无条件释放——会放掉仍可能完成的计划（RR-20260929-19 的承诺）。
- **文件与行为**：`kit/service/account/create_role.go`——`createRole` 拆出 `creationSlot`（读或建计划，原逻辑不变）与 `creationOwner`（名字预约 owner，原内联表达式），主流程变成“取计划 → 已发布 / 同名续作 / 换名判死释放”的显式分支；三处补偿统一经 `compensated` 计 `rollback.failed`（[NC-50](RR-20261005-NC-50.md)）。换名路径的新错误：名字目录 `Lookup` 失败或释放失败时返回该存储错误（客户端 `CodeInternal`），不再一律 `ErrRoleLimit`。
- **兼容**：无持久格式 / API / wire 变化；不清理已留下的未发布角色记录。并发两个不同的新名字同时释放同一死计划：一个释放并建新计划，另一个 `DeleteIf` 版本不符（`releaseCreationSlot` 按既有约定视为已处理）后看到新计划答 `ErrRoleLimit`——结果正确，但 `create_role.plan_released` 会多计一次（与同名路径既有口径相同，记为观察）。
- **回归**（`pending_creation_other_name_promises_test.go`）：换名直接释放死计划并建角（旧孤儿不可玩、赢家名字不变、计数 1）；三种仍可完成的计划换名答 `ErrRoleLimit` 且 slot 不动（控制）；释放失败一次 → 报错、slot 保留、`rollback.failed`=1，下一次换名重试释放成功；同名路径释放失败同样计数。修前 3 红 / 1 控制（3 子用例）绿，Memory 与真实 Redis 同文；修后 Memory `-race -count=3` 与真实 Redis（`ROOST_REVIEW3_BACKEND=redis`，前缀 `revn06:account:<纳秒>`，用例结束删除）全绿。[证据](evidence/noncore-bugfix-20261005-revn06/README.md)。
- **未验证**：Cluster；默认 30s ClaimTTL（用 1s）；跨进程同时换名只用同进程并发推演，未实跑。T-182 处置列已追加。
