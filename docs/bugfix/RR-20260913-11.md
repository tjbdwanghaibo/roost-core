# RR-20260913-11:大 epoch 拼成科学计数法并持久化不可读的 marker

**仓库 / 位置**:roost-core `remoteentity/marker.go`,EnterShared / LeaveShared / Transfer 三个脚本。
**修复单元**:U-0178(C8)。**定位文档**:TROUBLESHOOTING T-72。**优先级**:P3。

## 问题

三个脚本都用 `.. ((tonumber(x) or 0) + 1)` 拼新 lease,拼进去的是一个 **Lua 数值**,而 Lua 5.1
(Redis 内嵌的版本)用 `"%.14g"` 渲染数值:10^14 会写成 `1e+14`。审查预置一条合法 lease
`local:1001:100000000000000:1`,执行真实 EnterShared 之后 Redis 里变成 `shared:1001:1e+14:1`,
Go 的 `parseMarkerLease` 只接受十进制 uint64,于是解析失败 —— 而失败发生在 **Redis 已经写下坏
记录之后**。再次 `GetOwnership` 一样失败,这份所有权记录就此不可读。

## 根因

与 [RR-20260913-10](RR-20260913-10.md) 同源:Go 的 uint64 经过 Lua 数值。但表现不同 —— 那边是
比较域丢精度,这边是**输出格式被破坏**,而且破坏的是已经落盘的记录。所以是两个单元。

## 方案选择

- **只在 Go 侧把解析错误报得更清楚。** 没有用:那时共享记录已经被改坏了。
- **脚本自己按十进制递增,并在写之前校验可表示范围(采用)**。`incdec` 逐位加一,进位到头就补一位;
  结果超过 uint64 最大值就返回 nil,调用处据此返回空串 —— 拒绝在写之前,而不是写完再报错。

## 改动

`remoteentity/marker.go`:新增 `ownershipDecimalInc` 常量(一段 Lua 辅助函数),三个脚本通过常量
拼接前置它;`EnterShared` / `LeaveShared` 用 `incdec(currentFence)`,`Transfer` 的 marker 与 route
都用它,任一返回 nil 就整体拒绝。

替身 `markerEvalStub` 同样先被改忠实(用 `%.14g` 模拟 Lua 的数值渲染)再跟着改对,理由与
RR-20260913-10 相同。

## 证明

`remoteentity/marker_epoch_format_promises_test.go`:三个大 epoch(2^46、10^14、2^53+1)各预置一条
合法 lease,执行 EnterShared,断言不报错、新 epoch 正好加一、而且**再读回来仍然可解析**。

修前红:

```text
epoch 100000000000000: enter shared = remote_entity: invalid marker lease "shared:1001:1e+14:1";
the record was rewritten before this failed
```

修后 remoteentity 含 `-race` 全绿。

## 未做 / 边界

- **没有跑真实 Redis。** 同 RR-20260913-10:替身镜像脚本,但集成环境仍需再验。
- 溢出时返回空串,调用方看到的是"CAS 失败"而不是一个专门的"计数用尽"错误。真到 uint64 上限是
  天文数字,本次不为它新增错误类型;但拒绝是明确的,不会写坏记录。
- `ClaimOwnership` 写的是固定的 `:1:1`,不经过递增,未受影响。
