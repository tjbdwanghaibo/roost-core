# RR-20260919-07：没有订单的索引条目仍会占住每一页的槽位（U-0256）

- 仓库：roost-core `versionstore`、roost-kit `service/platform`
- 缺陷类：C5（错误路径不推进状态）
- 优先级：P1
- 相关：T-150；测试 `service/platform/pending_index_promises_test.go` 的
  `TestAnIndexEntryWithNoOrderIsRetiredIntegration`（对真 Redis）

## 问题

RR-20260919-05 把"一条读不出来的订单让整页失败"改成了跳过，U-0253 又把索引搬进了订单存储
（读的时候不再逐条查订单）。剩下的那一半是：一个**没有订单记录**的索引成员——删除的两步之间崩过一次，
或者运维手工删了 key——会被每一页读到、每一次都被 `AttemptDelivery` 以 `ErrOrderInvalid` 拒绝，
然后**继续留在集合里**。它的 score 是老的，所以它永远排在最前；`limit` 有多小，它就占掉多大比例的预算。

## 根因

"这个条目永远不会有结果"是一个可判定的终局，而循环把它当成了一次普通失败：记日志、下一条。
一个不推进状态的错误路径，在一个按分数排序的队列头部，就是永久占位。

## 方案

- 采用：**判定为"没有记录"时退休这个条目**。core `versionstore` 加 `IndexRemove(key)`（只动索引、不动值），
  kit 的 `*RedisOrders` 用它实现 `RetirePending`，Server 的循环在 `ErrOrderInvalid` 分支调用它
  （通过 `PendingRetirer` 可选接口——做不到退休的索引就保留条目，日志是运维的信号）。
- **只在这一种情形退休**：条目指向的订单不存在。退休一个还存在的订单会把真实的待办藏起来，
  所以调用方必须先确定"不存在"，`IndexRemove` 的注释写明了这条。
- 没采用：给坏条目往后推 score。审查提过，但那会把损坏记录藏起来，而且要另配退避与人工入口。

## 改动

core `versionstore/redis_store.go`（`IndexRemove` + `indexRemoveScript`）、
kit `service/platform/redis_store.go`（`RetirePending`、`PendingRetirer`）、`server_run.go`（新分支）。

## 证明

对真 Redis：索引里放一个没有订单的 `ghost`（score 更老）+ 一个真实订单，`PendingOrders(1)` 先给出 ghost
——这正是问题的形状；`RetirePending("ghost")` 之后同样的 `PendingOrders(1)` 给出真实订单。

## 未做 / 边界

- 退休只发生在**循环真的读到它**的时候，所以一个 ghost 至少被读一次。这是刻意的：
  只有在服务说"没有这个订单"之后退休才是安全的。
- `Delete` 的两步（CAS 成 sentinel → `Del`）仍然不是原子的，ghost 的来源没有被消除，只是不再累积代价。
