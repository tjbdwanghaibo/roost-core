# RR-20261006-74 修复：生成的 ClientMod 按 nats.rpc.transport 选择传输

问题：[RR-20261006-74](../bug/RR-20261006-74.md)（F09-R3）。基线 `c78d0c34`（main）。codebase-memory 共享 generation 停在 09-30（比基线旧），按 worktree 当前源码。分支 `remfix`（同批 RR-20261006-68～74，F05-1～F05-7、F09-R2、F09-R3）。
本文末尾“本批验证”是 RR-20261006-68～74 与 F05-6、F05-7 文本修正的共同验证记录。

## 决策

- 维护者给的二选一里选 **ClientMod 读 transport**：生成模板（`codegen/internal/servicerpc/template.go`）的 `ClientMod.Init` 读本进程的 `nats.rpc.transport`（`servicerpc.OptionsFromConfig`），`Provide` 用“配置的传输 + 构造参数”建客户端，构造参数在后、显式给的优先。`nats.rpc.transport` 由 ClientMod 依赖的 NATS Mod 声明，ClientMod 只读不重复声明。
- **未采用**：启动时校验两端一致——客户端进程看不到服务端进程的配置；读本进程配置与“两端写同一个值”的部署方式一致。

## 兼容性

行为变化：配了 `nats.rpc.transport: jetstream` 的调用方进程，生成的 ClientMod 改走 JetStream（之前一律轻量、每次都被截获）。服务端是轻量传输、调用方却配了 jetstream 的部署，调用方现在会走 JetStream 而服务端不订阅——两端仍须写同一个值（文档写明）。
