# RR-20261005-NC-230：OpsMod.Start 同步 bind，端口被占用时启动失败

2026-10-06，基线 `c8ecbabb`。**已修复、声明场景验证，未发版。** [问题](../bug/RR-20261005-NC-230.md) · [本轮](../review/REVIEW-2026-10-06-n01b.md) · [证据](evidence/noncore-bugfix-20261006-n01b/README.md)。

## 根因

`OpsMod.Start` 把 `ListenAndServe`（bind + serve）整个放进 goroutine，bind 的结果没有回到 `Start`。

## 修法

`Start` 里先 `net.Listen("tcp", ops.addr)`，失败返回 `ops: listen on ops.addr <addr>: …`，不登记 server；成功后登记 server 与实际地址，goroutine 里 `server.Serve(listener)`（Shutdown 后返回 `ErrServerClosed`、由 Serve 关闭 listener，Shutdown 早于 Serve 登记 listener 时同样由 Serve 关闭）。日志打印实际监听地址（`ops.addr` 写端口 0 时是系统分配的端口）。

没采用：在 goroutine 里 bind、用 channel 等结果——和直接 `net.Listen` 等价但多一层同步。

## 兼容

- **行为收紧**：端口被占用时进程启动失败（之前带着一条 Error 日志继续跑）。同机多实例必须各配各的 `ops.addr`（生成的 dev-run 已经这样做；k8s 每个 Pod 独立网络命名空间不受影响）。[APP-SINGLETON-LOCK](../feature/APP-SINGLETON-LOCK-2026-10-05.md) §4 的 P2 场景：P1 卡住仍占着 ops 端口时，P2 现在在 ops Start（DataEngine 之前）就失败、停掉已启动的 Mod、释放锁、非零退出，比原来在 `flock` 处失败更早，方向一致。
- `ops.enabled: false` 不变。

- `TestOpsStopContract`：A3 停机契约骨架套 OpsMod（卡住的工作是不配合 ctx 的 admin 命令，`CallerReleases`），绿——NC-04 的修复在新的 Start 下仍成立。
