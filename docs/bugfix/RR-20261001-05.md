## 决策与未采用方案

**采用：三件事，一个修复单元。**

1. **`!found` 的 pending 视为已越过重试地平线，回收。** 依据是 ledger 的既有契约（`types.go` `ProgressReservation` 注释、`redis_store.go:32-36`）：ledger 条目只会因 TTL 消失（仓内对 `Ledger` 只有 Create / Get / Update，无 Delete），TTL = `ReservationTTL` = “最长客户端重试地平线”，过了它 ledger 自己就把重放当新请求。pending 要保护的只是“mark 没写上期间的重放不能二次计入”，条目一消失这层保护在 ledger 侧也已经不存在了，继续留着只剩占名额。
   - 不变量 **ledger 存储 TTL ≥ `ReservationTTL`**：正式装配 `activity_mod.go:115/123` 两处都来自 `m.reservationTTL`（相等）；`kit/service/integration/redis_test.go:863-872` 同样两处 30min。`New` 无法校验——`versionstore.Store` 不暴露 TTL——所以写成 `Config.Ledger` 的接线不变量（注释），没有加 Init 校验。
   - Memory 后端没有 TTL，`!found` 只在测试显式 Delete 时出现；生产只有 Redis 会触发。
   - **迟到重放得到什么**：回收后，同 requestID 的重放若其 ledger 条目已过期，`Ledger.Create` 会成功创建新条目 → 按**新请求**应用一次（`TestExpiredLedgerEntriesFreeOrphanedPendingProofs` 末尾钉住）。这正是 ledger 契约早已声明的“TTL 之后的重放等同新请求”，不是本修复新增的风险；条目还在（TTL 内）的重放仍走原路径（Reserved → 环内 no-op / Applied → 短路）。
   - 指标：回收发生时 `Dropped("apply_progress.proof_expired", n)`。
2. **满窗改报 `ErrProgressBacklog`（新码 `CodeProgressBacklog` 620119），不再是 `versionstore.ErrConflict`。** 修后“满”仍可能发生（TTL 内 32 个 mark 失败未重放），但它是最多持续一个 TTL 的背压，立即重试无益；`CodeConflict` 的语义是“CAS 争用、现在重试”。既有码里 `ErrBacklog`（620107）是 OpenActivity 的活动窗口满，消息文本固定为 `pending activity window is full`，借用会让 ApplyProgress 的调用方去查活动窗口，所以新开一个码。不用 `"%w: %w"` 同时包 `versionstore.ErrConflict`：`Error()` 先 `errors.Is(versionstore.ErrConflict)` 会把它映射回 `CodeConflict`，正好抵消区分的目的。
3. **`Admin.ReconcileProgress(ctx, key, participantID, note)`，owner-only，不上 bus。** 与 platform `ResolvePendingAttempts` 同形（备注必填、记录到被改的记录上），但语义更强：pending 里每个 id 的 participant 写**已经落地**（它就是在那次 CAS 里进 pending 的），缺的只是 ledger mark，所以入口做的是把 `markReservationApplied` 补上再释放证明——是完成 applyProgress 没完成的第二步，不是“断言客户端已停止重试”。补过 mark 之后同 id 重放由 ledger 短路（no-op），不需要任何客户端假设。为什么还要入口：主修法把拒绝从“永久”缩到“≤ 一个 TTL（默认 30 分钟）”，一次 Redis 抖动积满的忙参与者仍要等半小时，运维补 mark 可以立刻结束。ledger 还写不了时 mark 失败 → 返回错误、不动 participant（已写的 mark 幂等，重试接着来）。

**未采用：**

- 给 pending 项记 `AdmittedAtUnix`，只回收 `now - admitted > ReservationTTL` 的项——更保守，但要改 `Participant` 的 JSON 形状（pending 从 `[]string` 变结构体），且 ledger TTL 已经是同一个时钟的权威，重复一遍没有新信息；时钟偏移下反而可能比 ledger 晚回收。
- 只改错误码不回收——参与者仍永久被拒，只是错误更好看。
- 在 applyProgress 热路径里顺手补 Reserved 条目的 mark——每次有 pending 时多 ≤32 次写，热路径成本上升；交给 Admin 入口。
- 用 `ErrBacklog` 复用——见上。
- Init 里校验 ledger TTL——Store 接口不暴露，加接口只为一次校验不值。

## 未验证项 / 风险

- 真实 Redis 用例的“TTL 内满窗仍拒绝”（`too-early`）只在 Memory 侧断言；Redis 侧 3s TTL 下 32 次写 ≈ 60ms，断言放进去也会过，但那是和时钟赛跑，按规范不写。Redis 侧第 2 / 3 条用例同样依赖“3s 内跑完”，超时会红不会假绿。
- 没有在真实 Redis 上等默认 30min TTL；逻辑路径与 3s TTL 相同（`Ledger.Get` 返回 `!found`）。
- 没有 Cluster 环境（本机无 `ROOST_REVIEW_CLUSTER`），`ReconcileProgress` 的 Cluster 变体未跑；它只用 participant / ledger 两个单 key store，不涉及双 key Lua。
- 没有压测：回收不增加读次数（扫描本来就逐条 Get），只多一个分支。
- `ReconcileProgress` 在 ledger 整体丢失（例如 Redis 被 FLUSH）时等价于主修法（条目全 `!found` → 释放），不会伪造 mark；但那种事故下 ledger 侧的重放防护本来就没了，与 RR-20260929-02 记录“缺失 ledger 的旧证明需对账”一致——现在对账入口就是它。
