# RR-20261004-04 修复：ReadThrough 的 loader 回填被准入拒绝时不再让读取失败

问题：[RR-20261004-04](../bug/RR-20261004-04.md)（来源 [REVIEW-2026-10-04-nc-audit-3 §3 D2](../review/REVIEW-2026-10-04-nc-audit-3.md)）。旧缺陷，[NC-15](RR-20261004-NC-15.md) 让 `LocalStore` / RawJSON / Hash 返回 `ErrStaleWrite` 后扩大。
日期 2026-10-04；实施基线 main `91ab67f7`（含 `v1.19.0`），在 RR-20261004-02 提交之后。状态：**已修复，本地验证通过（包回归 race、400 次合并测试、真实 Redis），已提交，未推送、未发版**。

## 根因（基线行号）

- `cache/read_through.go:191-193`（`loadOne` 的 loader 分支，`74e6d971`）：`if err := s.setLocal(ctx, value); err != nil { return zero, false, err }` 不区分准入拒绝与 L1 故障。loader 执行期间同一 key 的更新值已发布进 L1 时，回填被 `ErrStaleWrite` / `ErrConflictingWrite` 拒绝，`Get` 返回 `(zero, false, 拒绝)`——读取因为“写被拒”而失败。同一函数的 L2 回填分支（`:160-174`）早已读回 L1 已准入值，loader 分支没有。
- `cache/read_through.go:186-188`：loader 结果回写 L2，strict 模式下 L2 以 `ErrStaleWrite` 拒绝（loader 执行期间 L2 收到了更新的值）同样让读取失败；NC-15 之后 RawJSON / Hash 也会返回它。
- 影响面：仓库内唯一生产用法 `entity/remote_snapshot.go:238` 的 loader 是 nil，不受影响；受影响的是 `NewReadThroughStore` 带 loader 的公开组合。

图谱：generation 2026-09-30，`cache/read_through.go` metadata_changed，以当前源码补证；`NewReadThroughStore` 的调用方用 `rg` 确认（仅 `entity/remote_snapshot.go`）。

## 决策

- **loader 分支复用 L2 回填分支的规则**（`read_through.go:195-212`）：`setLocal` 成功交付 loader 值；`ErrStaleWrite` / `ErrConflictingWrite` 读回 L1，已准入值存在就交付它；L1 没有值时 stale 是 miss（被更新的删除取代，RR-20260913-01 复核的语义），conflict 返回拒绝（不交付被拒的 loader 值）；其他 L1 错误照旧返回。读回抽成 `localAdmitted`（`:214-224`），L2 回填分支的两处读回改用它，行为逐字不变（读回失败仍视为没有值）。
- **L2 回写的 stale 不让读取失败**（`:186-194`）：`ErrStaleWrite` 是写入准入的结论，与 strict / `IgnoreRemoteError` 无关；loader 结果照常进入 L1 准入，由上面同一条规则决定交付什么。其他 L2 错误仍按 `degradable` 分类（fatal 与 strict 返回，outage 在 ignore 模式下吸收）。
- 合并逻辑（`load` 的 `calls` / `waiters`）未动；修改只在 `loadOne` 返回之前，合并的跟随者拿到的是同一个结果。

### 未采用的方案

1. **L2 回写 stale 后回读 L2 现值并交付 / 回填它**：多一次远端往返和新的错误分支；ReadThrough 的 L1 对其他副本的发布本来就只靠 `LocalTTL` 收敛，这里交付 loader 的权威结果、L1 内容以 TTL 为界，与既有设计一致。
2. **L2 回写 stale 后不写 L1、直接交付 loader 值**：绕过 L1 准入（墓碑 / 冲突检查），可能交付 L1 会拒绝的值；走同一条准入规则更一致。
3. **把 L2 回填分支的 conflict 无值也改成返回拒绝，与 loader 分支完全共用一个函数**：L2 回填分支 conflict 无值时目前交付 L2 值（RR-20260913-06 的既有行为），改它超出本 RR；两分支只共用读回，各自保留对“无值”的处理。
4. **只把 stale 当 miss、不读回 L1**：L1 已经有更新的已准入值时，读取应得到它而不是 miss（会让调用方误以为不存在）。

## 文件与行为

- `cache/read_through.go`：loader 分支的 L2 回写与 L1 回填按上述规则；新增 `localAdmitted`；L2 回填分支只替换读回调用。Get 的 L1 命中路径、合并、Set、Delete 未改。
- 回归 `cache/read_through_loader_fill_promises_test.go` `TestReadThroughLoaderFillRefusalIsNotReadFailure`（loader 内同步发布，不 sleep）：
  - `local_stale` / `atomic_stale`：loader 期间 L1 收到 v2，loader 返回 v1 → 交付 v2、err=nil（LocalStore 与 AtomicLocalStore 两种 L1）；
  - `atomic_conflict`：L1（`Conflict` 钩子）收到同版本不同内容 → 交付 L1 的值；
  - `stale_without_value`：L1 拒绝且没有值 → miss、err=nil；
  - `conflict_without_value`：L1 冲突拒绝且没有值 → 返回 `ErrConflictingWrite`、不交付值（对照，修前修后都过）；
  - `remote_stale`：strict 模式，loader 期间另一副本把 v2 写进 L2，回写 v1 被 L2 以 stale 拒绝 → 读取成功、交付 loader 的 v1。

## 兼容性

- 带 loader 的 `ReadThroughStore.Get`：以前因 L1 准入拒绝或 L2 stale 回写返回错误的读取，现在返回 L1 已准入值、miss 或 loader 值。conflict 且 L1 无值仍返回拒绝。
- `FatalRemoteError` 把 `ErrStaleWrite` 判为 fatal 的配置者：loader 回写 L2 的 stale 现在不再让读取失败（stale 不再经过 `degradable` 分类）。仓库内没有这样的配置（`entity/remote_snapshot.go` 的 fatal 是 `ErrRemoteVersionConflict` / `ErrConflictingWrite`，且 loader 为 nil）。
- `ReadThroughStore.Set` 对 L2 / L1 拒绝的处理不变（写仍报错）。无公开 API、持久格式、配置变化。

## 未验证 / 风险

- `remote_stale` 时 L1 可能写入比 L2 旧的 loader 值，本副本在 `LocalTTL` 内服务它（`LocalTTL=0` 时用 L1 自己的 `DefaultTTL`；两者都为 0 则不过期，直到被覆盖或删除）。这是 ReadThrough L1 既有的跨副本新鲜度边界，不是本修复引入；需要更强保证的调用方应在发布侧失效 L1。
- L2 回填分支 conflict 且 L1 无值时仍交付 L2 值，与 loader 分支不对称（见未采用方案 3），未登记。
- 真实带 loader 的生产消费者在仓库内不存在，仓外组合未穷尽验证。
