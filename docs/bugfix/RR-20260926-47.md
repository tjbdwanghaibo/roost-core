# RR-20260926-47 修复：准入冷目标判定改用不加载的 IsLoaded 查询，不再在发送方调用 Getter

问题：[RR-20260926-47](../bug/RR-20260926-47.md)（探针见 [REPRO-2026-09-26-04 §12](../bug/REPRO-2026-09-26-04.md)）。修的是
[RR-20260926-25](RR-20260926-25.md) 的准入判定。日期 2026-09-26；实施基线 `49f20ee`，建立在同批 RR-35（`ff73e64`）之上。
状态：已修复、本地验证通过，已本地提交，未推送 / 未发布。方向按维护者批准的修复约束：准入探测改用不做加载的查询接口，由
`ManagerAccess` 实现；自定义 Getter 未实现时退回旧行为（不判冷、不自动转慢），不依赖其遵守契约。

## 根因

`nest/slow_load.go` `declaredTargetsNeedSlowPreparation`（基线）对每个声明目标调用
`mgr.getter.Get(admissionProbeContext, …)`，靠 Getter 遵守 `LoadedEntitiesOnly` 返回 `ErrColdLoadInLogic` 来判冷。它由
`Dispatcher.TrySendMsg`（`nest/dispatcher.go`）在调用方 goroutine 上执行：异步发送的业务 goroutine、在 handler 里发送的快 worker，
以及唯一的延迟派发 goroutine（延迟消息到期、锁超时 requeue 都经它，`group_transition.go`）。自定义 Getter 不遵守契约时，
I/O 就发生在这些 goroutine 上，延迟派发被串行化。

## 决策与实现

- `entity/entity.go`：新可选接口 `entity.LoadedChecker{ IsLoaded(id int64) bool }`。语义是“无需加载即可读取”：在内存 → true；
  不在内存且有加载器 → false；没有加载器 → true（慢阶段也读不到，缺失交给派发阶段按不存在处理，与 RR-25 的“未加载且可由 loader
  加载才转慢”一致）。注释写明它在发送方 goroutine 上执行，不得 I/O、等待或 Touch。
- `entity/manager_access.go`：`ManagerAccess.IsLoaded` = 一次分片 map 查找，未命中时再读一次加载器配置；不调 loader、不看 singleflight。
- `nest/nest.go`：`NewEngine` 对配置的 Getter 做一次类型断言，只有实现 `LoadedChecker` 才安装 `dispatcher.coldTargets`；
  热路径不做逐条断言。
- `nest/slow_load.go`：`declaredTargetsNeedSlowPreparation` 改用 `IsLoaded`，删除 `admissionProbeContext`（再无 `Get` 调用）。
  `beforeSlowPreparation` 改为 `NestMgr` 方法，并要求引擎有 `LoadedChecker`：准入不判冷的 Getter 没有“准入时已加载”的前提，
  准入后发现冷目标也不原位转慢，冷目标按 RR-02 原样返回 `ErrColdLoadInLogic`——这是约束里“退回旧行为（不判冷、不自动转慢）”的完整含义。
  实现了 `LoadedChecker` 的 Getter（含 `ManagerAccess`）保留 RR-25 的自动转慢、准入后三个驱逐窗口的原位迁移与同 ID 顺序，代码路径不变。
- `nest/nest_dispatch.go`：五处调用点改为 `mgr.beforeSlowPreparation()`。

未采用：

- 保留 `Get` 探测、仅对 ManagerAccess 走快捷路径：仍依赖未知 Getter 遵守契约，违背约束。
- 对未实现 `LoadedChecker` 的 Getter 保留准入后的原位转慢：它由快阶段 `Get` 的冷错误触发，同样依赖自定义 Getter 遵守契约才成立；
  而且约束明确“不自动转慢”。代价：这类 Getter 的冷目标又需要显式 `SendOptionSlow()`（与 RR-25 之前相同，已写入 USER_GUIDE）。
- 把判定挪到 worker 上执行：准入与同 ID 顺序在 `TrySendMsg` 统一建立，挪走会让“走哪个池”在准入之后才确定，需要重做派发队列。

## 兼容性与新导出 API

- 新导出：`entity.LoadedChecker`、`(*entity.ManagerAccess).IsLoaded`。删除了未导出的 `admissionProbeContext`。
- `ManagerAccess`（kit、生成工程的 `EntityAccess`）行为不变：自动转慢、原位迁移、同 ID 顺序与 RR-25 相同。
- 自定义 Getter：准入不再调用它。未实现 `LoadedChecker` 时冷的声明目标返回 `ErrColdLoadInLogic`（RR-25 之前的行为），需要显式 Slow；
  想要自动转慢就实现 `IsLoaded`。`scripts/perf` 里的包装 Getter 只访问已加载实体，不受影响。
- 快阶段读取仍按 `LoadedEntitiesOnly` 契约；本修复只把准入判定从契约里拿掉。

## 对抗性自查

- **同 ID 顺序与准入**：判定仍在 `TrySendMsg` 调 `queue.admit` 之前、同一处完成，`dispatchIDs` 登记与走哪个池无关；只是判冷函数从
  `Get` 换成 `IsLoaded`，对 ManagerAccess 两者答案一致（在内存 / 有 loader），RR-25 回归全部通过。
- **快阶段约束（RR-02/03/06/25/26）**：新判定只读内存，发送方即使是快 worker 也不会等待；删除 `admissionProbeContext` 后准入不再构造或
  传递 LoadedEntitiesOnly ctx。快阶段读取、Cast、慢准备的 Getter 调用不变。
- **原位迁移的唯一收尾**：`beforeSlowPreparation` 多了一个“引擎有 LoadedChecker”条件，只会让迁移更少发生；迁移本身（`slowReroute`、
  派发队列位置、`pending`）未改。未实现 `LoadedChecker` 时，驱逐窗口回到 RR-25 之前的结果（冷错误 / not found / 锁超时 requeue），
  这些路径是 RR-25 之前的既有收尾。
- **判定与执行之间的竞态**：`IsLoaded` 为 true 之后被驱逐仍由原位迁移兜底（ManagerAccess）；为 false 之后被别处加载，慢准备的 `Get`
  直接命中内存，多一次慢池往返，不影响正确性——与基线 `Get` 探测相同。
- **Sync / 回滚 / CreateInScope**：本修复不涉及提交路径。RR-35 撤销的实体从索引摘除后 `IsLoaded` 按“不在内存 + 有 loader”判冷，
  同 ID 的后续请求走慢准备由 loader 判定是否存在，与实体被驱逐 / 删除时相同。

## 未验证项 / 风险

- 未在 1000 玩家负载下复测 Nest 吞吐与尾延迟；只做了 nest 包同机微基准。
- 自定义 Getter 若实现了 `IsLoaded` 却在其中做 I/O，仍会在发送方阻塞——接口注释写明禁止，框架无法拦截。
- 未实现 `LoadedChecker` 的自定义 Getter 部署会失去 RR-25 的自动转慢（冷目标需显式 Slow）；仓内正式装配都用 ManagerAccess。
