# RR-20260914-06:座位 -1 与旁观者标记碰撞

**仓库 / 位置**:roost-core `lockstep/sequencer.go` `NewSequencer`,`lockstep/room.go` `ownerSpectator`。
**修复单元**:U-0195(C8)。**定位文档**:TROUBLESHOOTING T-89。

## 问题

Room 用 `PlayerID(-1)` 当 `sessionOwners` 里的旁观者哨兵,而 Sequencer 接受 `Players={-1}`:`Attach(-1, 101)` 之后
`AttachSpectator(101)` 仍成功,同一 session 同时在 seats 与 spectators 里;`broadcastOrder` 列两次,`DetachSpectator`
会清掉座位的 ownership / catchup。

## 根因

座位号与接收者种类共用一个值域,哨兵占了合法配置能取到的值(C8:两处对同一个 id 的解释不同)。

## 方案选择

- **显式接收者种类结构代替哨兵。** 更干净,但要改 `sessionOwners` / `broadcastReceiver` 的形状,超出最小改动。
- **座位号必须非负(采用)。** `NewSequencer` 拒绝负值;生产代码没有任何负座位用法(grep 确认),wire 上 player
  以 uint32 编码,负值本来就是绕路。

## 改动

`lockstep/sequencer.go`:`NewSequencer` 对 `player < 0` 返回 `ErrConfigInvalid`。

## 证明

`lockstep/seat_identity_promises_test.go` 的 `TestRoomPromiseNegativeSeatIsRefused`。
修前红:`same session accepted as seat -1 and spectator: <nil>`。修后 lockstep 含 `-race` 全绿。

## 未做 / 边界

- 哨兵仍是 -1,只是配置进不来了;换成显式种类留作后续重构。
