# RR-20260926-10：卸载重载等待实体投影

问题：[原始复审](../bug/RR-20260926-10.md)。日期 2026-09-26。
实施基线：main `381efc9` 加上一轮 RR-03～09 的未提交修复；原报告基线 `aaada47` 保留。
状态：代码已修复，适用本地验证通过，尚未提交/发布。完整证据和限制见[本轮汇总](../review/REVIEW-2026-09-26-release-fixes.md)。

## 修复与依据

Projector 按完整 Entity ID 跟踪在途记录，Repository 冷加载通过 Runtime 等待该实体全部 DAO 投影完成；不等无关实体。成功投影即解除屏障，失败/关闭唤醒等待方，WAL 健康异常拒绝冷读。

涉及：`dataengine/engine/entity_projection.go`、`entity_repository.go`、`runtime.go`、`projector.go`。

## 验证

TestEntityProjectionBarrierTracksAllDAOsAndReleasesOnFailure；TestGeneratedDataEngineReloadWaitsForProjection（真实 Mongo，async/strict/pipelined）。命令、负对照范围与环境见汇总；没有把全部测试绿色当成生产故障已穷尽。

## 兼容与边界

加载可能等待相关投影，须走慢阶段。独立构造的 Repository 若使用自定义 RecoveryGate，需提供 WaitEntityProjection；正式 Runtime 已接入。

## 复核后的补修（2026-09-26）

基线 main `87d9499`（含 RR-29 修复的本地提交）。针对[复核残留](../bug/RR-20260926-10.md#复核残留2026-09-26基线-985d5ba未修复) (1)(2)；(3) 性能未测，见末尾。

### 根因

- 投影 fatal 只对本轮 `records` 调 `completeProjection(err)`（`projector_replay.go:114-118,161-165`），fatal 之后后台循环退出、不再投影任何记录，
  但 fatal 批次之外实体的 `entityProjection` 永远不会被关闭；`WaitEntityProjection`（`entity_projection.go:77-88`）只在等待之后才看 fatal，
  等待中不感知，慢阶段 ctx 常为 Background，于是占住慢 worker 与 load flight 直到 Close。
- 同一处还有一个等待前的缺口：Projector 已关闭后才开始等待的调用方，因 Close 已把待投影项清空，直接走到末尾的
  `errors.Join(p.fatal(), p.wal.Healthy())` 返回 nil，放行冷读——而那条记录并未投影、也不会再被本进程投影。
- pipelined 记录的 WAL 票据失败（写入结果未知）时，Projector 的待投影项无人结束，等待方同样只能等到截止时间。

### 修法

- `isFatalProjection` 在 `fatalOnce` 内先写 `fatalErr`，再 `completeAllTickets(err)`：唤醒**全部**待投影实体等待方与 `CommitSystem` 票据，
  错误就是 fatal 本身（`ErrProjectionConflict` / `ErrTransactionIdentity` / `ErrReceiptIdentity`，可 `errors.Is`）。ReplayPass 里两处“只完成本批次”的循环删除，
  由这一处统一负责。
- `reserve` 在 `heldMu` 下复查 fatal：唤醒扫描也持 `heldMu`，所以扫描之后不会再登记新的等待项（Commit/Enqueue/CommitSystem 在 WAL 前拒绝）。
- `WaitEntityProjection` 等待前、等待后都调 `projectionUsable()`：fatal → fatal 错误；Projector 已关闭 → `ErrRuntimeStopped`；否则 `wal.Healthy()`。
  等待中由上面的唤醒扫描、Close 的 `completeAllTickets` 与 `p.ctx.Done()` 覆盖。
- `signalWhenDurable` 带上事务 ID：票据失败时 `finishEntities(id, ticketErr)`，等待方立即拿到 WAL 错误；之后的等待由 `wal.Healthy()`（terminal）拒绝。
- 未采用：给 WaitEntityProjection 再加一个 fatal channel 的 select 分支——有了“扫描 + reserve 同锁复查”的不变量，所有等待项都会被关闭，多一个分支只是重复；
  把 fatal 改成 cancel `projector.ctx`——会让 fatal 与 Close 混为一谈（`ErrRuntimeStopped` 不可判别出 fatal），也会改变后台循环/外部 Flush 的既有错误语义。

### 兼容性

- `WaitEntityProjection` 行为收紧：fatal 后立即返回 fatal（原先等到截止时间）；Projector 关闭后返回 `ErrRuntimeStopped`（原先可能返回 nil）。
  正式 Runtime 路径先查 `Ready()`，关闭后本就返回 `ErrRecoveryIncomplete`，不受影响；直接用 Projector 作 RecoveryGate 的调用方会看到新的错误。
- fatal 后 `CommitSystem` 票据以 fatal 结束（原先等到 Close 以 `context.Canceled` 结束）；fatal 竞态窗口内的准入在 WAL 前以 fatal 拒绝。
- 无导出 API、持久格式或配置变化。

- 正式 Nest 慢阶段入口（`nest.SendOptionSlow` → Repository 等待）没有新增端到端回归，仍依赖既有 fast-worker 断言与审查探针。
