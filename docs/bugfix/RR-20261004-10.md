## 根因（基线行号）

见问题记录：`renew:528-608` 在 `Refresh` 结果循环里逐个 `interrupt` → `Claim`（`:558-559`），`Claim:1017` 每人等一份 `evictWait`；预算只覆盖 `handBackIdle`（`:607`）。
同一循环里排在后面的 `confirmRenewal`（`:532` → `confirmLocked:806`）从确认时刻起算窗口，越过 `Refresh` 时设的键 TTL。

## 决策

**采用：`renew` 分两段，先记录、后等待；等待的那一段只有一份预算。**

- 第一段只做不等待的事：Held → `confirmRenewal`；Err → 原 Warn；不是我们的 → `interrupt` 并记入 `lost`。于是所有续租确认紧跟 `Refresh`，本地窗口不越过键的 TTL，
  RR-20260921-04 预算推导的前提（“回合之前的续租把每把租约确认到 `Lease`”）重新成立。
- 第二段 `beginPass` 开一份 `refreshPass`（`handBackPassWait` = `handBackPassBudget`，出厂 15s；表时钟记账 + ctx 结束真实等待，与 RR-04 同一套“两把钟一份预算”）：
  先 `retakeLost`（每个丢失租约开始前检查预算），再 `handBackIdle(ctx, pass)`（开头先查预算，用完就不选人，避免标记后立即复位）。
- `retakeOne` 是原 default 分支逐字搬出（`errStaleCopyKept` / Redis 没答复 / 取回 / 围栏四个结局与日志行不变），只是调用新的内部 `claim(ctx, pass.ctx, id)`：
  **Redis 往返用刷新循环的 ctx，撤离等待用回合 ctx**。公开 `Claim(ctx, id)` = `claim(ctx, ctx, id)`，登录 / `Owns` 不变。
  - 撤离等待被预算截断 = 撤离没在时限内完成：`dropResident` 回 ctx 错误 → `errStaleCopyKept` → RR-20261001-07 的 `abandon` + RR-20260930-23 的关连接，与 `evictWait` 到期同一结局。
  - `store.Claim` 不放进预算：SetNX 可能已落地而回复被 ctx 截掉，本进程就持有一个自己不知道的认领（`Refresh` 下一轮会答 Held 并确认一份没扔掉的副本）。它与归还的 `Release` 一样是一次 Redis 往返，留在预算之外，写进常量注释。
- 预算用完时没轮到的丢失租约：已经 `interrupt`（`Admit` 拒绝），副本不动、连接不关，下一轮 `Refresh` 再问——与“Redis 没答复重新认领”（原 `case err != nil`）同一结局。
  日志 `refresh pass out of time; the remaining lost leases are retaken by the next pass remaining=N budget=…`。
- 常量名 `handBackPassBudget` / 字段 `handBackPassWait` 保留（RR-04 的回归与生成工程合并都引用它们），注释改为“续租之后的整个回合：先重新认领、再归还”。

**未采用：**
- 只把重新认领也套上预算、确认仍与它交错：回合时长能界住，但排在后面的确认仍从确认时刻起算窗口，最多越过键 TTL 一整份预算（15s，扣掉 guard 仍有 10s 的双写窗口）。
- `confirmLocked` 改为以 `Refresh` 发出时刻为基准：能修窗口越界，但要把时间戳穿过 `leaseTable.Refresh` 与 `confirmRenewal`，改动面比调整顺序大，回合时长问题仍在。
- 重新认领移到后台 goroutine：与 RR-20260921-04 记录里不移出归还的理由相同（刷新循环自己的 `Claim` 会与归还 / `fence` 并发，RR-20260921-03 的互斥论证要重做；撤离不可取消，后台也要时间界）。

## 锁与等待顺序

- `owners.mu` 仍从不在等待时持有：`beginPass` 只在锁内读 `handBackPassWait`；`retakeLost` / `handBackIdle` 的撤离、投影、Redis 往返都在锁外。
- 刷新循环的 `claim` 在 `enterClaim` 里不会等归还：本回合的归还在重新认领**之后**、同一 goroutine，且 `handBackIdle` 返回前结束它标记的每一个玩家（RR-20260921-03 的论证不变）；
  因此刷新循环不等自己。
- 回合的严格上界：`handBackPassBudget` + 回合内每次重新认领的一次 SetNX 往返 + 每次归还的一次 Release 往返 + 围栏 / 关连接（不等待）。不新增快池等待入口（刷新循环不在 Nest 快 worker 上）。

## 兼容性

- 只改 game-demo 模板，框架 / kit / codegen / 协议 / 配置 / 持久格式不变。**已生成工程须按新模板手工合并** `internal/service/game/playerowner.go` 与 `playerowner_test.go`
  （与 RR-20260921-03 / 04、RR-20261004-11 一起合并，改的是同一段；demo 应用文件 sync 不更新）。
- 行为变化：一次刷新回合（重新认领 + 归还）最多花 15s 等待，之前重新认领无界（N × 5s）；超出的丢失租约 10s 后下一轮再取回，期间 `Admit` 拒绝、连接保持（与 Redis 没答复时相同）。
  一批丢失时，被别的进程接手的那几位会晚一轮（≤ 10s）才被围栏断线——这段时间他们的写入已被 `interrupted` 拒绝。
  重新认领用掉预算时本轮不归还（下一轮再归还）。新增 Warn `refresh pass out of time; the remaining lost leases are retaken by the next pass`。
- 续租确认的时刻提前到所有等待之前：同一回合内被确认的租约本地窗口不再越过键 TTL（收紧）。

## 未验证项 / 风险

- 只有替身上的记账与缩放实跑；没有在真实环境构造“8 把租约同时丢失、每个实体都被长事务占住”的回合。
- 回合的 Redis 往返（`Refresh`、每次重新认领的 SetNX、每次 Release）不在预算内；Redis 本身变慢时回合仍可能变长，这与续租本身同一个依赖，未改。
- 修前就存在、本条未改：`Claim` 的 `confirmClaim` 在撤离等待**之后**以当时的 `now` 起算窗口，而 SetNX 在等待之前就设了键 TTL——跨间断的认领（登录、`Owns`、刷新循环）本地窗口最多越过键一份撤离等待（≤ `evictBudget` 5s，正好被 `AdmissionGuard` 吃掉准入、但在途事务的保护被缩短）。
  建议作为 Wanted 候选（位置 `claim` 的 `confirmClaim`，修法：在 `store.Claim` 之前取时刻、确认用它）。
