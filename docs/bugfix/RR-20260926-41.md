# RR-20260926-41：最后一段零填充尾部按四条件判据截断，其余仍 ErrCorrupt

问题：[RR-20260926-41](../bug/RR-20260926-41.md)（复现见 [REPRO-2026-09-26-04](../bug/REPRO-2026-09-26-04.md) §1 `TestProbeZeroFilledTail`）。日期 2026-09-26。
实施基线：main `49f20ee` + [RR-20260926-33](RR-20260926-33.md) 本地提交 `bca358d`（RR 约束要求 RR-16 / RR-33 已修：checkpoint 不越过已 fsync 的位置，fence 才能作为“未确认”的可信边界）。
状态：已修复，适用本地验证通过，本地提交，未 push / 发布。按 RR 记录中维护者批准的“修复约束”实施。

## 1. 根因（基线 `49f20ee` 的 `nestwal/wal.go`）

- `scanFramesFrom`（`wal.go:1238-1258`）只按长度判撕裂：读到的帧头不足 20 字节（`:1238`）或帧 end 越过文件末尾（`:1255`）算撕裂尾；
  帧头 magic / 版本无效一律 `ErrCorrupt "invalid frame header"`（`:1245`）。于是零尾 5 / 19 字节打开成功、20 / 4096 字节拒绝启动，判据自相矛盾；
  而断电后“文件长度已持久、数据块未写回”的零填充通常是整块（≥4 KiB），恰好落在拒绝一侧。
- `openActive`（`wal.go:1049-1070`）先按扫描结果截断文件（`:1055`），之后才核对 checkpoint（`:1069`）；尾帧越过 fence 时文件已被截断再报错，拒绝打开却改动了现场。

## 2. 方案

`openActive` 的尾部处理抽为 `recoverTail`（同文件，职责单一：决定最后一段可截断的尾部并执行），判据与 [NEST_TRANSACTION_WAL.md §5“尾部截断判据”](../../NEST_TRANSACTION_WAL.md) 一致，四条同时满足才截断：

1. **仅最后一段**：`openActive` 只扫描最后一段；更早的段轮转时已 fsync，`Replay` 以 `allowTornTail=false` 读取，零尾同样 `ErrCorrupt`。
2. **坏点不早于 checkpoint fence**：坏点 = 第一个无法解析的帧起点（`scanFramesEnd` 返回的 lastGood）。fence 是最后一个已确认帧的**结束偏移**，
   所以坏点 ≥ fence 就是“坏区严格位于已确认区之后”；坏点 < fence 时报 `ErrCorrupt`（零填充时附“inside the acknowledged prefix”及 checkpoint 位置）。该检查现在**先于截断**，拒绝时文件原样保留。
3. **坏点形态**：既有的不完整尾帧照旧；新增零填充——`allZeroFrom` 以 64 KiB 缓冲确认自坏点至文件末尾全为 0（即坏帧头所在 4 KiB 块剩余部分及其后所有块全零）。
   帧头有效而 CRC 不符、非零垃圾、零区后又有非零字节（含中间零页后仍有完整帧）都不满足，仍返回原 `ErrCorrupt`。
4. **告警 + 指标**：截断后 `slog.Warn`（reason、段、坏点偏移、字节数、所在块偏移、checkpoint）；`nestwal.recovery.tail_truncated.total` / `.bytes`，标签仅 `reason=torn_frame|zero_fill`（按截掉内容是否全零分类，低基数）。

涉及：`nestwal/wal.go`（`openActive`、新增 `recoverTail` / `checkRecoveredEnd` / `allZeroFrom`）；新增 `nestwal/zero_tail_promises_test.go`；`NEST_TRANSACTION_WAL.md` §5。

### 未采用方案

- 任何 magic 无效都当撕裂截断：会把 CRC 不符的非零数据、中间损坏吞掉，违反“完整 frame CRC 错误拒绝启动、不静默跳过”。
- 只要求坏帧头 20 字节为 0：零页之后若仍有非零字节（中间页丢写回、后续页已写回），其后的内容是否曾被 strict 确认无法判断，按约束必须拒绝。
- 零尾出现在 fence 之前时截断到 fence 或跳过坏区：属于删除已确认记录 / 跳过 WAL，禁止。
- 以“截断长度上限”替代全零判据：长度与是否被确认无关，不能区分撕裂与损坏。

## 3. 兼容性

- 公开 API、配置、WAL / checkpoint 格式不变。
- 行为变化（供 CHANGELOG）：最后一段满足判据的零填充尾部（任意长度）在启动时截断并告警，不再以 `invalid frame header` 拒绝启动；
  新增指标 `nestwal.recovery.tail_truncated.total` / `nestwal.recovery.tail_truncated.bytes`（`reason=torn_frame|zero_fill`），既有的撕裂尾截断也会计数并告警；
  尾部坏点早于 checkpoint 时拒绝启动且不再先截断文件。其余损坏（非零垃圾、CRC 不符、非末段损坏、段缺口）行为不变。
- 启动代价：仅当最后一段有尾部需要处理时多读一次尾部字节（≤ 段大小），不影响运行期 Append / Ack / ticker 路径，未做运行期性能对照。

## 5. 自查（逐条论证不破坏）

- **strict / pipelined 语义**：只改启动恢复，运行期 Append / Enqueue / 票据 / fsync 路径未动。被截断的只可能是坏点之后、fence 之后的内容：
  async 本就不承诺 fsync；strict / pipelined 在 fsync 成功前不会得到成功，已成功但未 ack 的记录只有在介质整块清零时才会被误截（见 6 残余风险）。
- **RR-16 checkpoint 顺序**：未改 Ack；新判据依赖 RR-16 / RR-33 保证的“checkpoint 不越过已 fsync 位置”，坏点 ≥ fence 才截断，截断后 `checkpoint ≤ 恢复末端` 仍成立。
- **group commit 批量**：不涉及写路径。
- **关闭排空（RR-17）**：不涉及 Close / operations；Open 失败路径仍关闭段文件、释放目录锁（`Open` 原有清理）。
- **fatal 传播**：启动失败以 `ErrCorrupt` 从 `Open` 返回，由装配层按原路径失败启动；运行期 terminal / OnFatal / Fence 未动。
- **DurableWatermark 单调**：`durableLSN` 是进程内计数，Open 时从 0 开始，未涉及。
- **不跳过冲突 WAL / 不删已确认记录**：fence 之前任何损坏都拒绝，拒绝前不改文件（修前会先截断）；fence 之后只截“全零”或既有的不完整尾帧，非零损坏仍拒绝。

## 6. 未验证项 / 残余风险

- **残余风险（维护者约束中已列出）**：已 fsync、strict 已向调用方确认但尚未 ack 投影的记录，若介质把它所在块及其后全部内容整块清零，形态与未写回的零尾无法区分，会被当作撕裂截断，
  该记录丢失而不报 `ErrCorrupt`。`reason=zero_fill` 的告警 / 指标是唯一线索，生产应对其告警并核对投影结果。已 ack 的记录不受影响（坏点早于 fence 即拒绝）。
- 零尾以直接追加 / 覆写 0 字节模拟，未在 ext4 `data=writeback`、网络盘或 VM 快照上做物理断电实验；未跑故障矩阵（按任务要求）。
- 截断后未额外 fsync 段文件：若截断后、首次 fsync 前再次断电，零尾可能重现，下一次启动会按同一判据再次截断（幂等）。
