# RR-20260926-32 修复：Remote 批次按显式“持久提交成功”状态决定 Commit / Abort

问题：[RR-20260926-32](../bug/RR-20260926-32.md)（探针见 [REPRO-2026-09-26-03 §6](../bug/REPRO-2026-09-26-03.md)）。
日期 2026-09-26；实施基线 main `87d9499`（本批 RR-26/25/27 提交之上）。状态：已修复、本地验证通过，已提交未推送/未发布。

## 根因

`nest/msg.go:84`（基线）`finishRemoteWriteBatch`：

```go
} else if (dispatchErr != nil && !errors.Is(dispatchErr, ErrAfterCommitFailed)) || !m.remoteFinalized {
	err = batch.Abort(ctx, dispatchErr)
```

“是否已提交”从 `dispatchErr` 的错误类型推断，只有 `ErrAfterCommitFailed` 被视为提交后错误。strict Remote 事务持久提交之后，
`dispatchLoadedEntities` 的 `defer release()`（`nest/nest_dispatch.go:328-330` 基线）→ `entity/entity_guard.go:300-304` `ReleaseEntity`
调用业务注册的 release hook，hook panic 由 `runNestLogic` 的 recover 变成普通 dispatchErr → Abort：远端内存回滚、事务标 Rejected、
`postRemoteCommit`（Sync Confirm）被跳过——RR-13/14 已经修过的症状从另一条错误路径回来。RR-14 的修法只把
`ErrAfterCommitFailed` 加入例外，根因（按错误分类推断提交事实）没有消除。

## 决策

- `Msg` 增加 `remoteCommitted`：`commitDurable` 在 `durableCommit` 返回 nil（WAL/持久准入成功、`acceptPersistence` 完成）后、
  任何 AfterCommit / 释放 / hook 之前设置。这是 Remote 事务唯一的成功提交路径（Remote 批次不走 pipelined；
  `RollbackNone+Memory` 的免事务分支在有 Remote 批次时不进入）。
- `finishRemoteWriteBatch` 改为三分支：`remoteIndeterminate` → 交给状态驱动的收尾（不变）；`remoteCommitted` → `Commit`，成功后照常
  执行 `postRemoteCommit`（与 RR-13/14 一致）；其余 → `Abort`（dispatchErr 为 nil 的异常情况用 `ErrRemoteCommitNotFinalized` 作原因）。
  提交后的错误（release hook panic、AfterCommit 失败、Close 失败）只随回复报告，不改变 Commit/Abort 决策。
- 字段由执行 handler 的快 goroutine 写、慢 worker 在内部续行返回后读；`remoteLogicCall.done` 的 close/receive 建立 happens-before，
  与 `remoteFinalized` 等既有字段同一所有权模型。

未采用：继续扩充错误类型白名单（例如把 `ErrEntityReleaseFailed` 也列为提交后错误）——release hook 的 panic 值是任意类型，
错误链上没有可靠的身份，白名单永远会漏；也就是问题所说的“靠错误类型推断”。

## 文件与行为

- `nest/msg.go`：`remoteCommitted` 字段与注释；`finishRemoteWriteBatch` 只看显式状态。
- `nest/execution.go`：`commitDurable` 持久提交成功后设置 `msg.remoteCommitted`。
- `nest/sync_modes_test.go`：`TestSyncRemoteConfirmationIsSeparateFromLocalCommit` 手工构造“本地已提交”的 Msg，原先靠
  `remoteFinalized + nil 错误` 让收尾推断已提交；按新不变量补上 `remoteCommitted: true`（断言不变）。
- 回归 `nest/remote_release_hook_promises_test.go` `TestRemoteReleaseHookPanicAfterDurableCommitStillCommits`（REPRO §6 探针改写）：
  - 提交后 release hook panic：WAL 有 mutation、`Commit` 被调用、`Abort` 未调用、回复带 hook 错误、本地值保持 11；
  - 提交前业务失败：`Abort` 被调用、`Commit` 未调用、无 WAL mutation、本地回滚到 10。

## 兼容性

已持久提交的 Remote 事务遇到提交后错误时不再被 Abort；调用方仍会收到错误（例如 `release hook failed`），不能据此认为未提交而
重复业务（与 USER_GUIDE “Remote 数据提交成功后 Close/hook 错误仍可能返回给请求”一致）。未提交的失败路径不变。
