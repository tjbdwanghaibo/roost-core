# RR-20261004-07 修复：Bus 停止超出预算后保留 pool 供再次排空，NatsMod 重试最终关闭 Assembly；RPC callback 内 Stop 不再自锁

问题：[RR-20261004-07](../bug/RR-20261004-07.md)（来源 [B 线 NC 复审第二组 §3 D2、§4 S1 / S2 / S4](../review/REVIEW-2026-10-04-nc-audit-2.md)）。
日期 2026-10-04；实施基线 main `c888223f`（含 v1.19.0）。状态：已修复，本地验证通过，已提交（A 线 worktree），未推送、未发版。

## 根因（基线行号）

- `kit/nats/nats_mod.go:161-164`（`3560a19b`，NC-09）：Bus 停止返回任何错误都直接 `return stopErr`，保留 `m.bus` / `m.asm`，前提是“再次停止能继续排空”。
- `bus/bus.go:316-352` `Bus.StopWithContext`：第一次调用就把 `b.pool` 置 nil，把 `stopResources(ctx)` 的结果（含 `pool.StopWithContext(ctx)` 的 ctx 错误）存进 `b.stopErr` 并关闭 `stopDone`；之后每次调用只返回这个缓存错误，不再等 pool。`worker.Pool.StopWithContext` 本身可重复等待（`worker/pool.go:93-96`），但 Bus 已经丢了引用。
  两处合起来：handler 退出后重试仍是 `context deadline exceeded`，Assembly（连接、RPC 回调池）永不关闭；修前（`3560a19b^`）NatsMod 至少会继续 `asm.Close`。
- 同一前提的第二个反例：Bus 退订失败是终态错误（不会再有进展），NatsMod 也把它当“稍后重试”，重试永远拿到同一个退订错误，Assembly 同样永不关闭。
- 复审 S2：`nats/driver/rpc.go:237-239`（NC-09）`RPCClient.Stop()` 改成 `StopWithContext(Background)`，停止已发起时 callback 里的 `Stop()` 去等唯一停止任务，而停止任务在等这个 callback 退出——永久互等；修前 CAS 立即返回。
- 复审 S1：`nats/driver/rpc.go:285` `drainCallbacks` 在 `pending.Range` 之后直接 `callbacks.Wait()`；`finishPending`（第 295-307 行）在 `callbackMu` 内**先** `LoadAndDelete` **再** `callbacks.Add(1)`。reply / timeout 删掉最后一个键、还没 Add 时，Range 跳过它，Wait 在计数 0 时立即返回，`StopWithContext` 报 nil，那次终态 callback 之后才执行（也是 WaitGroup “计数 0 时 Add 与 Wait 并发”的误用）。第 282-284 行注释说 “added under callbackMu before deletion”，与代码顺序相反。

图谱：codebase-memory 项目 `Users-whb-roost-roost-core` generation 2026-09-30，早于 `3560a19b`；`check_index_coverage` 显示 `kit/nats/nats_mod.go`、`nats/driver/{rpc,assembly}.go`、`servicerpc/client.go` 为 `metadata_changed`，`bus/bus.go`、`worker/pool.go`、`nats/driver/client.go` 为 `metadata_match`。结论全部以当前源码为准，没有刷新共享索引。

## 决策

采用复审候选一：**`Bus.StopWithContext` 可重新等待**，与 `worker.Pool` / `RPCClient` 的“唯一停止、可重复等待”对齐。

- 停止分两段。teardown（cancel 运行 ctx、退订、JetStream RPC 收尾）只由第一个调用者做一次，顺序与修前相同（退订 → 有界等 pool → JetStream RPC 收尾，超时也照常收尾 JetStream RPC）。pool 排空可以被多次等待：第一个调用者超时只返回 ctx 错误，`drainPool` 保留；之后的调用先等第一个调用者的 teardown 结束（`teardownDone`），再 `drainPool.StopWithContext(ctx)` 继续等同一次排空；排空完成的那个调用把结果定为终态（`finishStopLocked`：`stopErr = teardownErr`、释放 `drainPool`、关闭 `stopDone`）。之后的调用直接返回终态结果。
- 返回值契约写进 `StopWithContext` 文档：**ctx 错误只表示这个调用者不再等待，排空仍由 Bus 持有；其他错误（退订失败）是终态**。没有新 goroutine，等待都在调用者自己的 goroutine 上，ctx 有界。
- NatsMod 按这个契约分流（`busDrainPending`）：ctx 错误 → 保留 bus / asm 返回，下次停止继续；终态错误 → 合并进返回值，照常关闭 Assembly 并释放引用（修前行为）。
- `Bus.Stop()`：停止已经发起时立即返回，第一次发起时无期限等待（`StopWithContext(Background)`）。原因：可重新等待之后，业务 handler 在一次超预算停止之后调用 `Stop()` 会去等正在等它自己的那次排空——修前它拿到缓存错误立即返回（handler 内调用 Stop 在 `Start` 注释里是预期场景）。需要继续等同一次排空的调用方用 `StopWithContext`。
- S2：`RPCClient.Stop()` 同样在停止已经发起（`stopped`）时立即返回，恢复 NC-09 前的语义；`StopWithContext` 仍是“重复调用等同一任务、ctx 有界”。两处规则一致：`Stop()` 只在第一次发起时等待，`StopWithContext` 才是可重复的有界等待。
- S1：能写确定性红（见回归），一并修：`drainCallbacks` 在 `Wait` 前取一次 `callbackMu` 作屏障。`stopped` 已在锁内置位，之后不会再有新的 pending；任何被 Range 跳过的删除都在这把锁的临界区里，屏障之后它的 Add 一定先于 Wait。注释按真实顺序改写。为了确定性复现，`RPCClient` 加两个未导出的测试缝 `testBeforeDrain`（停止任务 Range 之前）与 `testAfterClaim`（`finishPending` 临界区内删除之后、Add 之前），生产中为 nil，只多一次 nil 判断。
- S4：两个回归给首个阻塞点加有界等待（2s），不改承诺。

### 未采用的方案

1. **复审候选二：NatsMod 只在 Bus 返回非 ctx 错误时继续关闭 asm，ctx 错误也继续硬关闭**：Bus 的 handler 仍在运行时关闭连接，正是 NC-09 想避免的“提前关闭它仍使用的连接”；而且 Bus 侧的粘滞错误仍在，`Bus.StopWithContext` 自己的重试依旧永远失败。
2. **第二次停止硬关闭并报告**：Bus 没有可以“硬关闭”的东西——handler 是业务代码，不可抢占；硬关闭只能是丢掉 pool 引用假装完成，即修前的粘滞行为。
3. **Bus 起一个后台停止任务 goroutine（仿 `RPCClient.drainCallbacks`），调用者只等 done**：要么把 JetStream RPC 收尾挪到“pool 真正排空之后”（超时时不再收尾 JetStream RPC，比修前退化），要么在后台任务里拆出第一段，复杂度不比两段式少；可重复等待的 `worker.Pool` 已经提供了需要的语义。
4. **按 goroutine id 识别“在自身 handler / callback 内的 Stop”**（`goroutine.GoID`）：能让 handler 内的 `StopWithContext(Background)` 也不自锁，但要在每条消息 / 每个 callback 的热路径上登记、注销 goroutine id，为一个罕见的调用方式付全量成本。
5. **S1 只改注释、不加屏障**：审计时判为“理论竞态”；加两个测试缝后它是 10/10 确定性红，屏障只是一次空临界区，留着不修没有理由。

## 兼容性

- **`Bus.StopWithContext`**：超出预算后的再次调用从“立即返回同一个 ctx 错误”变为“继续有界等待同一次排空，排空后返回 nil（或退订错误）”。只缓存非 ctx 的终态结果。签名不变。
- **`Bus.Stop()` / `RPCClient.Stop()`（行为变化）**：停止已经发起后立即返回、不等待排空（`RPCClient` 回到 NC-09 之前的语义；`Bus` 以前会等待正在进行的停止）。第一次调用仍无期限等待排空。需要等待别人发起的那次排空，用 `StopWithContext`。仓内 `Bus.Stop()` 的调用方：`kit/nats` 的回退分支（`*bus.Bus` 不会走到）、demo loadtest 模板退出时、测试；`RPCClient.Stop()` 的生产调用方：无（`Assembly.Close` 用 `StopWithContext`）。
- **NatsMod**：Bus 返回终态错误时不再保留 bus / asm，与 NC-09 之前一致；ctx 错误时保留并可重试（NC-09 承诺，现在成立）。
- 仍然成立的限制：handler / callback 内用无期限 ctx 调 `StopWithContext` 等待自身所在的 Bus / RPCClient，或者在停止尚未发起时在 handler / callback 内第一次调用 `Stop()`，仍会等待自身（NC-09 之前在 pool 路径上同样如此）。App 只调用一次 `stopModSafely`，不会自动重试；App 路径上超预算时 Bus 与连接保留到进程退出，与 NC-09 记录一致。
- 无持久格式、wire、配置变化。
