# RR-20261003-NC-03：保留错误 HTTP 状态与原始原因

2026-10-04，修前 `183b0bddc5b46f6d3b50c5edda2d08da45150a69`。[原问题](../bug/REVIEW-2026-10-03-noncore-01.md#rr-20261003-nc-03p2-错误响应解码失败掩盖-http-状态和原文)。已修复、具名场景验证，未发版。

根因：DoJSON 先按成功类型解码 body，失败即返回，跳过 HTTP 状态分类。现在读取响应后先建立非 2xx 的 StatusError；读取/解码也失败时用 errors.Join 保留两种原因，errors.As 可提取 StatusError 和具体解码错误，errors.Is 可匹配读取失败。部分读取失败时 StatusError.Body 保存已取得字节，defer Close 始终执行。

没有吞掉解码失败；也没有取消已有“兼容错误 JSON 填入 out”的行为。200 坏 JSON 仍直接报原解码错误，正常非 2xx 且成功解码仍返回 StatusError。

正式红：503 文本为 SyntaxError、401 异型 JSON 为 UnmarshalTypeError，两者 `StatusError=false, want true`。修后六个原分类分支通过；补读取失败 200/503 对照和解码原因可提取断言，保留 partial body 并确认 Close。原 header/签名/错误体解码既有测试通过。

兼容性：StatusError 结构不变；部分错误的最外层类型变为 Join error，调用方应使用 errors.As/Is，不依赖直接类型断言或精确错误字符串。没有改重试策略、状态码规则、超时或 body 容量上限，不涉及持久数据迁移。

[完整证据](evidence/noncore-bugfix-20261004-01/README.md)，正式测试 `httpclient/client_boundaries_promises_test.go`。真实代理/网关/TLS 和大型响应未实测；T-185。
