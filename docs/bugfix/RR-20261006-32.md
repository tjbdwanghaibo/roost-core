# RR-20261006-32 修复：停止被拒的衍生物在第一次请求时就转入待停止，回调不再重跑

问题：[RR-20261006-32](../bug/RR-20261006-32.md)。基线 `57c87634`，分支 `skstop`，与停止入口统一（[方案](../feature/REFACTOR-2026-10-06-skill-spawn-stop-unified.md)）同一提交，未发版。
读代码：codebase-memory 共享 generation 停在 09-30，以当前源码为准；`terminateSpawn` 的调用点用 `rg 'terminateSpawn\(' skill/` 穷举（14 处），守卫测试用 `go/ast` 再核。

## 根因

宿主拒绝之后的处理散在入口里：施法里的入口出错后不动记录，靠错误传到 `failCastLocked`（或下一 tick 的 reap）再停一次；`terminateSpawn` 只凭 `Status == running` 判断要不要跑回调，第二次停止看到的仍是 running。

## 修法

不在入口里补“已跑过回调”的标记，而是把失败处理收进唯一的停止函数 `requestSpawnStop`（`skill/runtime_spawn_stop.go`）：`terminateSpawn` 之后仍是 running 就转入 `stop_pending`。之后 `failCastLocked` 的 `stopScopedSpawns` 只选 running、不再重停；reap 只看 running；Runtime 按退避重试时只重发宿主 `StopSpawn`（`terminateSpawn` 对非 running 不跑回调与离开信号）。

| 方案 | 结论 |
| --- | --- |
| ① 统一停止函数，被拒即转待停止（采用） | 维护者“停止入口统一”的决定本身；回调重跑、同一 tick 二次打宿主、`Shutdown` / `RemoveProgram` 不重试同时消失 |
| ② 在 `SpawnInstance` 上加“回调已跑”标记 | 未采用：多一个状态、要进 checkpoint，入口仍各自处理失败，下一个新入口还会漏 |
| ③ `failCastLocked` 不再停衍生物 | 未采用：`failCastLocked` 是施法失败的唯一终态入口（NC-110～112），要停掉还在运行的衍生物 |

## 文件与行为

见方案 §3.2。行为差异：Interrupt / Cancel / goto / 收尾 / 移交被拒时 cancel 回调只跑一次；启动失败、owned 事务提交失败的清理被拒时不跑 cancel 回调（与宿主停得了时一致）；宿主在同一请求里只被打一次，之后在拒绝后第 `SpawnStopRetryBackoff` 个 tick 重试。
