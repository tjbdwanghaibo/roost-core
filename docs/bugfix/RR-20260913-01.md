# RR-20260913-01:Remote 快照删除无版本屏障,旧删除清新值 / 旧值复活

**仓库 / 位置**:roost-core `entity/remote_snapshot.go`(`Delete` / `Publish`),`remoteentity/syncer.go`
(`ApplyReplica` 删除分支),`remoteentity/transaction_manager.go`(提交后的本地失效)。
**修复单元**:U-0187(C8)。**定位文档**:TROUBLESHOOTING T-81。

## 问题

`DeleteRemoteSnapshot` 把提交版本放进 `env.Version` 发出去,接收侧却直接 `cache.Delete(key)`:
不比较版本,也不留水位。同一 key 的 delete 与 upsert 乱序投递时:
1. 发 delete v2、再发 full v3;先到 v3、后到 delete v2 → v3 被清掉(`found=false`);
2. 发 full v1、再发 delete v2;先到 delete、后到 full v1 → 已删的键复活(`found=true version=1`)。

## 根因

upsert 走 `Publish`:分片锁 + 版本 CAS(`Stale`)+ 同版本同值(`Conflict`),是一条有序写入边界;
delete 却是另一条无版本的失效路径。同一个 key 的两种写不在同一个比较与 apply 边界里(C8)。

## 方案选择

- **只在接收侧 Get 版本再 Delete。** 两步无锁,与并发 Publish 交错仍会错;而且解决不了场景 2
  (先到的删除后面什么都没有可比)。
- **给 L1 存一个"已删除"占位值。** 会污染 `Get` / 大小统计 / L2 CAS,且 `ReadThrough` 的 miss 语义要改。
- **版本化删除 + 有期限的墓碑(采用)。** `DeleteAtVersion(ctx, key, version)` 在与 `Publish` 相同的
  publish 分片锁下:L1 里的快照比 version 新 → 删除是过去式,不动;否则删 L1/L2,并在旁表记
  `{version, until}`。`Publish` 拿到分片锁后先查墓碑:`StateVersion <= 墓碑版本` 且未过期 → 丢弃
  (与输掉版本 CAS 同样返回 nil);更新的快照清掉墓碑再写。墓碑寿命 `TombstoneTTL`,默认等于缓存
  `TTL`——比缓存条目自身还晚到的旧快照不在可重放窗口内,不是这条协议要保护的。按时间收界而不是
  按条数(U-0165 的教训),插入时若表已大于 1024 条则顺手清理过期项。
  无版本的 `Delete(key)` 保留为纯失效原语并加注释;两个生产调用点(复制接收、提交后本地失效)都
  改成按版本删除;`env.Version <= 0` 的老发布方消息仍走无版本删除以兼容。

## 改动

`entity/remote_snapshot.go`:`RemoteSnapshotCacheConfig.TombstoneTTL`;`RemoteSnapshotCache` 增
`tombMu` / `tombstones` / `tombstoneTTL`;新增 `DeleteAtVersion`、`rememberTombstone`、`deletedAtOrAfter`;
`Publish` 分片锁下先查墓碑。`remoteentity/syncer.go`:删除分支按 `uint64(env.Version)` 调
`DeleteAtVersion`。`remoteentity/transaction_manager.go`:`commit.Invalidations` 用 `commit.NextVersion`。

## 证明

- `remoteentity/snapshot_delete_order_promises_test.go`(真实 `SnapshotReplicaStore`,只重排投递):
  `TestApplyReplicaPromiseDelayedDeleteKeepsNewerSnapshot`、`TestApplyReplicaPromiseDeleteFencesDelayedOlderSnapshot`
  (含按序 v3 复活的对照)。
- `entity/snapshot_delete_version_promises_test.go`(缓存层):保留更新的、挡住更旧与同版本的、
  更新的快照清墓碑、墓碑到期后不再挡(边界的文档化)。

修前红(把实现 stash 掉后跑复制层测试):`old delete removed v3: found=false version=0 err=<nil>` /
`deleted snapshot resurrected: found=true version=1 err=<nil>`。修后 entity / remoteentity 含 `-race` 全绿。

## 未做 / 边界

- 墓碑是每个进程 L1 旁的本地表,不进 L2;L2 只被删除。另一节点在墓碑过期后收到极晚的旧快照仍会
  复活它——这是 `TombstoneTTL` 划定的协议边界,和缓存 TTL 一致。
- `LoadAuthoritative` 也走 `Publish`,权威返回的版本若不超过墓碑会被丢弃、以 L1 未命中返回;权威在
  删除提交之后不应再返回更旧的版本,若返回说明权威落后于删除,丢弃是对的。
- `cache/mirror.go` 的通用 mirror 删除路径不在本单元(不是 Remote 快照协议)。

## 2026-09-13 复核后的补修(仍归 U-0187)

审查第七轮两条确定性失败,都是"删除水位只在 Publish 里判、L2 删除不看版本"留下的口子:

1. **在途回填越过墓碑**:Get 已从 L2 捕获 v1 尚未回填,`DeleteAtVersion(2)` 走完;回填经
   `ReadThrough.loadOne` → `setLocal` 直接进 L1,不经过 Publish 的墓碑检查。实测 `returned=true cached=true`,
   完全在墓碑有效期内——我原记录"墓碑在 Publish 判定"的边界描述漏掉了这条 L1 写入口。
2. **冷 L1 的旧删除清掉较新的 L2**:L1 空、L2 有 v3,`DeleteAtVersion(2)` 比较不到任何东西,对共享 L2
   无条件 `Del`。实测 L2 `found=false version=0`。

**改动**:
- `cache.StoreConfig.Superseded func(next V) bool`:与 `Stale` / `Conflict` 同一把分片锁下判、键不存在时也判,
  拒绝返回 `ErrStaleWrite`。entity 把墓碑检查接到这个钩子上——publish、loader fill、L2 回填三条 L1 写入口共用
  一条准入(第一版只有 Publish 有)。锁序:分片锁 → `tombMu`,`tombMu` 从不在持有时去拿分片锁。
- `ReadThrough.loadOne` 回填被 L1 以 `ErrStaleWrite` 拒绝时,返回 L1 现值或 miss,不再把刚被拒的值交给调用方。
- `entity.RemoteSnapshotVersionedDeleter` 可选接口;`RemoteSnapshotCache.DeleteAtVersion` 若 L2 实现了它就调
  `l2.DeleteAtVersion`(有界 ctx、故障降级同 ReadThrough.Delete),再删 L1;否则退回无条件删除。
- `remoteSnapshotL2Store.DeleteAtVersion`:新 Lua `remoteSnapshotL2DeleteAtVersion`,与 CAS 共用精确十进制比较
  helper(抽成 `remoteSnapshotL2Lua`),`stored > ARGV[1]` 则返回 0 不删,否则 `DEL`。fake 按脚本文本分支镜像同一规则。
- Publish 里的墓碑早查保留:它挡的是 L2 写(墓碑是本机的,L2 是共享的,不能让一条已删版本的快照写回 L2)。

**证明**:`entity/snapshot_delete_l2_promises_test.go` 的 `TestDeleteFenceCoversInflightL2Refill`、
`TestColdL1DeletePreservesNewerL2`(含 delete v3 照常清 L2 的对照);`remoteentity/snapshot_l2_delete_promises_test.go`
的 `TestRemoteSnapshotL2DeleteAtVersionKeepsNewerSnapshot`(含 2^53+1 vs 2^53 精度用例)。修前红:
`deleted v1 refilled through live tombstone: returned=true cached=true` / `old delete removed newer L2: found=false version=0`。
修后 cache / entity / remoteentity 含 `-race` 全绿。

**边界**:TTL 与 broker 重放窗口的关系仍是"默认等于缓存 TTL"的约定,没有从真实协议推导;L2 上没有墓碑,
另一节点在 L2 被删后写回一个更旧版本仍会成功(它自己的 L1 墓碑挡不住别人)。

## 复核后的补修（2026-10-05，N05 revn05）：共享 L2 墓碑

**已修复、声明场景验证（含真实 Redis 与自起 Redis Cluster），未发版。** [复核](../bug/REVIEW-2026-09-13.md#复核rr-20260913-01-跨节点-l2-删除水位2026-10-05n05-revn05) · [本轮](../review/REVIEW-2026-10-05-n05-revn05.md) · [证据](evidence/noncore-bugfix-20261005-n05/README.md)。上一节“边界”所说的“L2 上没有墓碑，另一节点写回更旧版本仍会成功”被复现为同根因残余（旧值复活），按残余补修，不新编号。

**修法**（`remoteentity/snapshot_l2.go`）：

- `remoteSnapshotL2DeleteAtVersion` 不再只是条件 `DEL`：L2 里的快照不新于删除版本时，键被替换成只含 `deleted_version` 的墓碑，TTL 与 L2 快照相同（`SnapshotL2TTL`，默认 5 分钟）；已有更高的墓碑不降低；L2 没配 TTL 时仍是普通 `DEL`（不留永久墓碑）。
- CAS 脚本先查 `deleted_version`：版本不新于它的写一律返回 0（任何 epoch），Go 侧按 RR-20261005-NC-130 报 `cache.ErrStaleWrite`，`Publish` 不装 L1；更新的写（重建）照常写入并 `HDEL deleted_version`。
- `Get` 读 `data`，墓碑没有 `data`，即 miss。`DeleteAtVersion` 多传一个 TTL 参数；Redis 替身同步镜像两段脚本。
- 墓碑只比版本，与本机墓碑同一规则；Remote 元数据在删除后保留 `_ver`（`mongo_committer.go:420`），重建的版本接着递增（`mongo_authority.go:100-118`），所以重建总是越过墓碑。

**兼容**：L2 键格式增加 `deleted_version` 字段。滚动升级期间旧节点的 CAS 不认它，仍可能像修复前一样在墓碑上写回旧数据；新节点的下一次删除会同时清数据、保留水位（真实 Redis 用例覆盖“两种字段并存”）。旧节点的 `DeleteAtVersion` 对墓碑等同删除。若某个部署的重建会把版本归零（本仓正式链路不会），重建后的快照会被墓碑挡住最多一个 L2 TTL。墓碑数量 = 删除速率 × L2 TTL。

**验证**：修前红 `L2 after the delete at v2: held=true version=1 err=<nil> — the deleted snapshot was written back`（两种跨节点触发）与 `a snapshot at the delete's own version reached L2`；真实 Redis 修前 `write v1 (any epoch) over tombstone 2 = <nil>`。修后 `TestDeleteWatermarkHoldsInL2AgainstAnInflightLoadOnAnotherNode`、`...AgainstALateReplicaOnAnotherNode`、`TestDeleteWatermarkControls`（重建可见、旧删除不降水位、重复删除幂等、删除不清更新的 L2）通过；真实 Redis `TestRealSnapshotL2TombstoneFencesEveryWriter`（PTTL、拒绝 v1/v2、跨节点在途加载、重建清墓碑、混合格式收敛）与更新后的 `TestRealSnapshotL2KeyPrefixOnRedis` 通过；`ROOST_REMOTE_CLUSTER_IT=1` 自起 3 主 3 从的 `TestRealSnapshotL2KeyPrefixOnRedisCluster` 通过；`entity` / `remoteentity` / `cache` / `kit/remoteentity` `-race -count=3` 通过。

**仍是边界**：墓碑过期（L2 TTL）之后才到的旧快照仍能写回——它要晚于删除一个 L2 TTL，JetStream 30 分钟保留期内的重放可以做到这一点（审查 O5），这属于 Mirror 方案的首载 / 重连补洞；不配置 L2 TTL 时没有墓碑。
