# RR-20260927-10 修复：RegisterEntityKindDefs / RegisterEntityKindCategories 整批校验后再写入

问题：[RR-20260927-10](../bug/RR-20260927-10.md)（OPEN-ITEMS C17）。日期 2026-09-27；基线 `d4234c9`；worktree 分支 `fix-r7-ent`。
codebase-memory 图谱停在 09-26，已过期，未使用；以源码为准。

## 根因

`entity/entity_factory.go:115-124`：逐条 `registerEntityKindDefinitionLocked`，每条立即 `Store` + `refreshLockRankLocked`，出错即返回。

## 决策

- 把原 `registerEntityKindDefinitionLocked` 的判定部分原样搬进 `resolveEntityKindDefinition(existing, def)`：只计算合并后的记录（返回 `existing`
  本身表示无变化），不写注册表。所有规则（none 检查、category 不一致、策略“none 可补、部分重复声明忽略、其余冲突”、RR-71 的 builder 生命周期校验）不变。
- 新增 `registerEntityKindDefinitionsLocked(defs)`：第一遍在 `staged` 副本上依次合并，批内同一 kind 的后续定义基于前面合并后的记录判定；任一失败直接返回，
  注册表未动；第二遍按首次出现顺序逐 kind `Store` 并刷新锁档。单条入口 `registerEntityKindDefinitionLocked` 调它（批长度 1，行为与修前相同）。
- `RegisterEntityKindCategories` 与 `RegisterEntityKindDefs` 同形（同一个逐条写入循环），一并改为同一路径（清单只点名后者，这是同一缺陷的另一个入口）。
- 可见性：读者无锁（每 kind 一个 `atomic.Pointer`），第二遍逐 kind 发布，读者可能在发布过程中看到批内前几个 kind 已生效、后几个尚未生效——与修前逐条注册成功时
  的中间态相同，但不会再看到被拒批次的任何部分。没有为整批做一次性原子切换：那需要换注册表的数据结构，读路径（锁序判断在持锁时读它，M-01）会变重，收益只在
  注册期的瞬间。

## 文件与行为

- `entity/entity_factory.go`：`RegisterEntityKindDefs`、`RegisterEntityKindCategories`、`registerEntityKindDefinitionLocked`（转调）、
  新 `registerEntityKindDefinitionsLocked`、`resolveEntityKindDefinition`。
- 回归：`entity/kind_defs_batch_atomic_promises_test.go` `TestRegisterEntityKindDefsLeavesNoHalfBatch`（新 kind 在 category 冲突之前、策略升级在非法定义之前、
  批内同 kind 两条冲突、categories 批次、`Must*` panic 后无半批、合法批次整批生效且锁档正确）；用 `isolateEntityRegistry` 隔离，`-count` 可重复。

## 兼容性

成功路径行为不变；失败时不再留下前半批。依赖“部分成功”的调用方（仓内无）会看到被拒批次完全未生效。无导出 API、配置或生成物变化。
