# NC-81 修复：recover 只在响应开始前改写为 500

[问题](../bug/RR-20261005-NC-81.md) · [证据](evidence/noncore-bugfix-20261005-n02/README.md)。已修复、声明场景验证，未发版。

## 决策与实现

`recoverMiddleware` 用一个记录“响应是否已开始”的 writer 包装下游：最终状态的 `WriteHeader`（1xx 除 101 外不算）、`Write`、`ReadFrom`、`Flush`、成功的 `Hijack` 都标记已开始。panic 处理：

1. `http.ErrAbortHandler` 原样重新 panic，保持标准库“中止、不打印堆栈”语义；
2. 其他 panic 记录日志（新增 `response_started` 字段）；
3. 已开始：以 `http.ErrAbortHandler` 重新 panic，由 net/http 中止连接（HTTP/1 不发终止块，HTTP/2 RST_STREAM），客户端看到传输失败；Hijack 之后不再写任何东西；
4. 未开始：原有 500 JSON。

包装 writer 保留 `http.Flusher`、`io.ReaderFrom`，提供 `Unwrap` 供 `http.ResponseController`（SetWriteDeadline 等）取得原 writer；只有原 writer 支持时才暴露 `http.Hijacker`，类型断言结果与原 writer 一致（websocket 升级可用）。没有为每个可选接口做组合爆炸；`http.Pusher` 不透传（HTTP/2 push 已被主流客户端弃用）。

## 兼容性

响应前 panic 的 500 JSON 不变。改变的两点：响应开始后 panic 不再追加错误体而是中止连接；`panic(http.ErrAbortHandler)` 不再得到 500 JSON。直接用 `httptest.ResponseRecorder` 调 `Engine.ServeHTTP` 并 panic `ErrAbortHandler` 的测试，现在会看到 panic 传播（与直接用 net/http 一致）。原 writer 不是 Flusher 时包装后仍声称 Flusher（Flush 静默无效），与 ResponseController 的行为一致。

## 验证

`httpserver/response_integrity_promises_test.go`：write/write_header/flush 三形状中止、ErrAbortHandler 传播 4 叶子在旧产品红、修后绿；1xx 后 panic 仍 500、Hijack/Flush/ResponseController 透传、Hijack 后 panic 不追加内容为控制。既有 `TestEngineRecoversPanicAsJSON` 等原回归不变。

## 未验证 / 风险

HTTP/2、真实反向代理/网关对中止连接的呈现未验；`http.Pusher` 不再可断言。

## 评估与取舍（2026-10-05 合并前复核）

结论：**包装 writer 是当前最简单的正确做法，保留；补一处 FlushError 透传**。

| 方案 | 能否判断“响应已开始” | 与契约一致 | 改动面 / 维护 | 调用方 |
| --- | --- | --- | --- | --- |
| **N02 包装 writer（保留）** | 能：最终状态 WriteHeader / Write / ReadFrom / Flush / 成功 Hijack 都记录 | 响应前 500 JSON 不变；Hijacker 只在原 writer 支持时暴露 | ~60 行，两个类型 | 拿到的是包装 writer，类型断言结果与原 writer 一致（Pusher 除外） |
| `http.ResponseController` | 不能：只提供 Flush/Hijack/SetRead/WriteDeadline/EnableFullDuplex，没有“是否已写头”的查询；它沿 `Unwrap` 链找能力，反而要求包装 writer 提供 `Unwrap`（N02 已提供） | — | — | — |
| 不包装，panic 一律 `ErrAbortHandler` 中止 | 不需要判断 | **破坏**响应前 panic 回 500 JSON 的既有契约（`TestEngineRecoversPanicAsJSON`） | 最小 | 客户端从 500 变成传输失败 |
| chi `middleware.NewWrapResponseWriter`（已在依赖里） | 部分：记录写头与字节数、透传 Pusher；**不记录 Hijack**，Hijack 后 panic 仍会向已劫持连接写 500；变体按协议版本选（v5.3.0 `NewWrapResponseWriter(w, protoMajor)`），也只有 `Flush()` 没有 `FlushError()` | 1xx 处理与本仓一致 | 复用，但仍要自己补 Hijack 追踪 | 同上 |
| `felixge/httpsnoop` | 能（按接口组合生成包装） | 一致 | 新增依赖 | 同上 |

`http.Pusher`：标准库 HTTP/2 仍实现，但主流浏览器已移除服务器推送，Go 自带 HTTP/2 客户端以 `SETTINGS_ENABLE_PUSH=0` 关闭（`net/http/internal/http2/transport.go`），`Push` 对这些客户端本就返回 `ErrNotSupported`；规范写法 `if p, ok := w.(http.Pusher); ok` 断言失败时自然降级。Engine 是 JSON 接口与管理面，加一个 Pusher 变体（以及 Hijacker+Pusher 组合）收益不抵维护成本，不加。

复核发现的缺口（已修）：包装 writer 只实现 `Flush()`，`http.ResponseController.Flush` 先找 `FlushError()` 再找 `Flusher`，于是命中包装的 `Flush()` 并返回 nil——原 writer 不支持 Flush 时本应得到 `http.ErrNotSupported`，连接写失败的错误也被吞掉，与 N02 记录的“ResponseController 透传”不符。改为实现 `FlushError()`：返回原 writer 的结果；只有 `ErrNotSupported` 时不标记响应已开始（什么都没写出）。`Flush()` 调它并丢弃错误，与 `http.Flusher` 语义相同。

- 红（N02 提交上）：`TestResponseControllerFlushErrorsPassThroughTheTracker/unsupported`：`Flush on a writer without flush support = <nil>, want http.ErrNotSupported`；`/flush_error`：`Flush whose underlying FlushError failed = <nil>, want connection reset`。
- 绿：两叶子通过；NC-81 原 4 叶子与 1xx、Hijack/Flush/ResponseController、Hijack 后 panic 控制不变通过。
