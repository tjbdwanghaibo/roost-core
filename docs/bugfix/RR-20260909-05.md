# RR-20260909-05:Enqueue 重放返回其他 Subject 的 Ticket

**仓库 / 位置**:roost-kit `service/match/queue_store.go`,`Enqueue` 的幂等重放分支。
**修复单元**:U-0164(C8)。**定位文档**:TROUBLESHOOTING T-58。

## 问题

`Requests` 只按 `requestID` 查,命中就直接返回原 Ticket。同一个队列里,player:2 用了 player:1
的 requestID,就会拿到 **player:1 的 Ticket 与 Score**,而且它自己这次入队意图整个消失:既没有
建立自己的请求记录,也没有进队。候选数仍然是 1。

## 根因

读取侧一直在校验归属:`Ticket()` 调 `validateOwnership`,不匹配就 `ErrNotPermitted`,注释还专门
写了"不说谁才是主人,避免把可猜的 id 变成枚举工具"。写入侧的重放分支漏了同一道检查 —— 两条路径
对"这张票是不是你的"用了不同的判据,C8。

## 方案选择

- **按 subject 给请求键加命名空间**(`subject.Key()+"|"+requestID`)。撞键从根上消失,但它会
  **静默放行**一个客户端缺陷:同一队列里两个玩家用同一个业务请求键,本身就说明键的生成有问题。
  而且改键空间要迁移已存的 `Requests`,得定义旧数据兼容策略。
- **忽略命中、照常新建票。** 更糟:requestID 随后指向另一张票,原主人的幂等性被破坏。
- **校验归属后拒绝(采用)**,复用读取侧同一个 `validateOwnership`,同一个 `ErrNotPermitted`,
  同样不透露主人是谁。改动最小,而且把客户端的撞键暴露出来而不是掩盖。

## 改动

`service/match/queue_store.go`:重放分支在返回命中票据之前调 `validateOwnership(ticket, subject)`;
不匹配则计 `refused:enqueue:request_subject_mismatch` 并返回错误。因为在 `Update` 的回调里
`return current, false, err`,状态一个字节都不改。

## 证明

`service/match/enqueue_request_owner_promises_test.go`:同一队列先由 player:1 用 `shared-request`
入队;断言主人自己重试仍然复用原票;断言 player:2 用同一个 requestID 被 `ErrNotPermitted` 拒绝
且拿到空票;断言拒绝之后状态未变(主人的票仍在、候选只有它一张);最后断言 player:2 用自己的
requestID 仍能正常入队。

修前红:

```text
cross-subject replay = ({ID:bd83… Subject:{Kind:player ID:1 Score:100} State:waiting
RequestID:shared-request …}, <nil>), want ErrNotPermitted
```

修后 `go test ./service/match -race` 绿,kit 全仓绿。

## 未做 / 边界

- 键空间不变,所以没有数据迁移。
- 命中一张**已终态**票时仍然按重放返回(`expireLocked` 先跑,过期票会先被处理)。这是既有行为,
  本次没有改动;审查建议里提到的"过期票据"场景属于另一条判据,若要改需要先定清"重放一张已结束
  的票应该答什么"。
