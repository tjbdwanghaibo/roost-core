# RR-20260914-12:单片重组绕过 MaxFrameBytes

**仓库 / 位置**:roost-core `statesync/datagram.go`,`Reassembler.push` 的 `ChunkCount == 1` 快路径。
**修复单元**:U-0202(C8)。**定位文档**:TROUBLESHOOTING T-96。

## 问题

接收端 `MaxFrameBytes=256`。同一份 400 字节载荷:按 `maxDatagram=300` 分两片 → 多片路径累计大小检查 →
`ErrFrameTooLarge`;按 1200 一片 → `ChunkCount==1` 直接返回 `done=true, 400 字节, nil`。两条路径对帧大小的
判据不一致(C8)。P3:需要 `MaxFrameBytes` 小于单片可容纳载荷才触发,且后续 `DecodeFrame` 用同一 Limits 仍会拒绝,
所以是重组 API 的契约不一致,不是越过完整解码链。

## 方案选择

- **单片也进 inflight 表走统一路径。** 为了一个比较把快路径的零分配优势丢掉。
- **快路径上加同一个上限比较(采用)。** `len(payload) > MaxFrameBytes → ErrFrameTooLarge`,与多片的
  `total+len > MaxFrameBytes` 同一判据(恰好等于上限都放行)。

## 改动

`datagram.go`:`push` 的单片分支加一个比较。

## 证明

`statesync/reassembly_limit_promises_test.go` 的 `TestReassemblerPromiseSingleChunkHonoursMaxFrameBytes`:
两片 / 单片都必须 `ErrFrameTooLarge` 且不留 inflight;对照:上限恰好 400 时两种分片都放行。
修前红:`datagram=1200 chunks=1 accepted=true bytes=400 err=<nil>`。修后 statesync 含 `-race` 全绿。

## 未做 / 边界

- 没有动 `DecodeDatagram` 的 `MaxDatagramBytes` 校验;两者分工不变。
