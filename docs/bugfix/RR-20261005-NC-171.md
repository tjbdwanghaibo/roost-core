# NC-171 修复：Nest Mod 卸载后重载的停止句柄保留到 worker 退出，entitysync 排空后才释放

[问题](../bug/RR-20261005-NC-171.md) · [证据](evidence/noncore-bugfix-20261005-stopshape/README.md)。提交 `c99a687d`。已修复、声明场景验证，未发版。

## 决策与实现

只改 kit 装配 `kit/nest/nest_mod.go`，不动 `entity` 的 `unloadResync.stop`（它本身已符合三步）与 Nest 核心：

- `stopUnloadResync`：`stopResync(ctx)` 成功才置 nil；超时保留句柄，重试再等同一批 worker。
- `StopWithContext`：①停卸载后重载、发起 Nest 停机（两者幂等；保留原设计“等 worker 超时也照样发起 Nest 停机”）；②在 ctx 内等两者，任何一个返回错误就返回，句柄与 entitysync 都保留；③两者都排空后才 `entitySync.Stop / Drain / Close`——entitysync 是重载 worker 的 Rebind / Retract 目标。全部完成后置 `stopped`，之后的 Stop 返回 nil（修前成功停完后再调用会得到 `entitysync: manager is closed`）。

Start 失败的清理路径仍用 `context.Background()` 停重载，不变。

## 兼容性

重载 worker 未排空时，Nest 停机仍会被发起，但 entitysync 不再在同一次调用里被关闭；App 一次停机的结果（返回 ctx 错误、判定不完整）不变。配置、API 不变。

## 验证

- `kit/nest/unload_resync_stop_retry_promises_test.go`（经 `unloadResyncConfigurer` 注入受 channel 控制的停止句柄）：修前 3 条断言红，修后绿；`-race -count=10` 通过。
- `GOWORK=off go test -race -count=3 ./kit/nest/`、`go run ./cmd/glsvet ./nest ./entity ./dataengine/engine ./sync/entitysync` 通过。

## 未验证 / 风险

正式 `ManagerAccess` 接线下，取消后 worker 几乎立即退出（见问题记录的触发窗口分析），本修复主要消除“句柄已清空 = 已停”的形状；没有在真实负载下制造 entitysync 锁长时间占用的场景。
