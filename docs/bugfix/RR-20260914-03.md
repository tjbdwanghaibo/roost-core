# RR-20260914-03:派发扫描只看本轮新完成,重试任务失去入口

**仓库 / 位置**:roost-kit `service/global/activity`,`server_run.go` `sweepGroup`、`service.go` 完成后的窗口退出。
**修复单元**:U-0192(C8)。**定位文档**:TROUBLESHOOTING T-86。

## 问题

`sweepGroup` 只对 `AdvanceExpired` **本轮**返回的 `advanced` 调 `DueDispatches` / `AttemptDispatch`;活动完成即从聚合
窗口删除,下一轮不再出现。审查三条实测(两轮 sweep、中间推进时钟超过退避):宽限到期完成的 Attempts=1(期望 2);
最后一个 notify 收齐完成的 0;首次派发 Create 失败、下轮 heal 的 0——全部 pending 且 due=true。显式调
DueDispatches→AttemptDispatch 两次、ACK 排除的对照通过:状态机原语没问题,内置循环找不到它们。

## 根因

首次与重试不对称(C8):派发状态机是持久、跨轮的,而调度入口只认"这一轮刚完成的"。

## 方案选择

- **完成后不从聚合窗口删。** 占 `MaxPendingActivities` 的开活动名额,审查明确反对。
- **新增独立 store 做待派发索引。** 要动 Config / redis_store / mod 装配,是公开配置面的扩展。
- **窗口记录里加独立的 `Delivering` 列表(采用)。** 完成的活动从 Keys 退出时进入 `Window.Delivering`(与 U-0191 的
  `retireFromWindow` 同一个 CAS),不计入开活动名额;`DeliveringActivities(group, limit)` 按 key 排序并在 Service 内
  保存每组游标轮转,长列表不会总是服务前 64 条;sweep 每轮对它们 DueDispatches→AttemptDispatch;`RetireDelivered`
  先 `ensureDispatches` 兜底(dispatch Create 失败后的唯一回路),全部 dispatch 终态(acked / exhausted)或活动已不存在
  才从 Delivering 移除。寿命由 `DispatchMaxAttempts × 退避` 收界,列表自排空。

## 改动

`types.go`:`Window.Delivering`、`delivering()`。`service.go`:`Service.deliveryCursor`;`DeliveringActivities`、
`RetireDelivered`;`settleCompletion` / `AdvanceExpired` 的 heal 经 `retireFromWindow` 进 Delivering。`server_run.go`:
`sweepGroup` 的派发循环改从 `DeliveringActivities` 出发,末尾 `RetireDelivered`;新增计数 `sweep.delivering_read_failed`、
`sweep.retire_failed`。

## 证明

`service/global/activity/dispatch_rediscovery_promises_test.go`:
- `TestSweepRetriesDispatchesAcrossRounds`(grace / notify / heal 三种完成路径,两轮 sweep 后 Attempts=2);
- `TestDeliveringIndexRetiresAtTerminalStates`(全部 ACK 后退出;打满预算 exhausted 后退出)。

修前红:`two due sweeps: attempts=1 want=2 state=pending due=true` / `attempts=0 want=2 …`(三个子用例)。修后 activity 含
`-race` 全绿,kit 全量绿。

## 未做 / 边界

- `sweepGroup` 仍丢弃 `AttemptDispatch` 返回的 payload——投递适配器的责任本轮没定,`Attempts` 不等于已送达(审查的接入观察)。
- `AckDispatch` 不主动退出 Delivering,由下一轮 sweep 的 `RetireDelivered` 收;多一轮几个 Get。
- Delivering 没有硬上限:寿命由尝试预算 × 退避收界;不用条数收界(U-0165 的教训)。
- 管理端 reopen 的活动如何重新进入调度没有一起做。
