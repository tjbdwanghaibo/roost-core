# RR-20261004-13 修复：roost 跑的 go 命令按进程树取消，`Wait` 有界

问题：[RR-20261004-13](../bug/RR-20261004-13.md)（来源 [W-2026-10-04-06](../bug/WANTED.md)）。
日期 2026-10-04；实施基线 main `28b161e3`（v1.19.2 之后）。状态：已修复，本地验证通过，已提交（worktree），未推送、未发版。

真 go 探针（macOS，不提交）：临时 GOCACHE 下 `go build -a std`，4 秒时 `kill -9` go，0.5 秒后 `ps` 仍见 `compile -o …` 进程，ppid 已是 1——被杀的 go 确实留下孙进程。

仓内其他子进程调用（`rg -n 'exec\.Command' codegen`，非测试）：`servicerpc/run.go:243` `go list`、`roost/generate.go:510` `git status`、`roost/render_deploy.go:625` `docker compose config`、`roost/framework_release.go:162` `go mod download`、`roost/cli.go:588` `go env`——都是 `exec.Command`，没有 context、不会被取消，因此没有“取消后残留孙进程 / Wait 被拖住”这一隐患（它们无界等待是另一个问题，不在本 RR）；仓内 `exec.CommandContext` 只有本 RR 的两处。

## 决策

新增 `runCommandTree(ctx, dir, env, stdout, stderr, binary, args...)`（`codegen/internal/roost/command_tree.go`），两个调用点都换成它：

- `WaitDelay = 5s`：即使有进程逃出整树击杀（自建会话 / 进程组）还握着管道，`Wait` 也在 ctx 结束后 5 秒内返回。
- **Unix**（`command_tree_unix.go`）：`SysProcAttr.Setpgid = true`，`Cancel` 里 `kill(-pid, SIGKILL)`，组已不存在（ESRCH）时返回 `os.ErrProcessDone`。go 起的 compile / link / git 继承进程组，即使 go 已先退出也一并杀掉。
- **Ctrl-C**：独立进程组把 go 移出终端前台组，Ctrl-C 不再直达 go。为不改变“一次 Ctrl-C 结束 roost”的既有行为，命令运行期间 `signal.Notify` 接住 SIGINT / SIGTERM / SIGHUP（启动时已被忽略的，如 `nohup`，保持忽略），收到后取消 ctx 杀树、等 `Wait`，`signal.Stop` 恢复默认动作后把同一信号发给自己：roost 照旧死于该信号，只是不再留下 go 子树。
- **Windows**（`command_tree_windows.go`）：不新建进程组（控制台 Ctrl-C 本来就到达 go 及其子进程），`Cancel` 里 `taskkill /T /F /PID <go>`——它按父 pid 找子进程，必须在 go 还活着时跑，失败再退回 `Process.Kill()`。
- 其他平台（`command_tree_other.go`）：只有 `WaitDelay` 上限。
- 为测试注入替身，两个函数各抽出带 binary 参数的未导出内层：`runDoctorCommand`、`runDependencyBinary`（生产路径固定传 `"go"`）。

### 未采用的方案

1. **只设 `WaitDelay`**：能让调用按时返回，但孙进程照旧活着占用暂存目录（Windows 上删不掉），只修了一半。
2. **Windows job object**（`CREATE_SUSPENDED` 启动后 `AssignProcessToJobObject` 再恢复，`KILL_ON_JOB_CLOSE`）：比 `taskkill /T` 更彻底（父进程先死也能杀到孙进程），但 `exec.Cmd` 不支持挂起启动，要自己调 `CreateProcess` 或引入 `x/sys/windows` 线程恢复，代码量与风险不成比例；`taskkill` 在 go 仍活着时（超时取消的常态）足够。
3. **Ctrl-C 转为“取消并返回错误”**（不重发信号）：`project deps` 会因此走回滚、删暂存目录，看起来更好；但 `doctor` 会接着跑下一项检查，用户要按三次 Ctrl-C，且行为与修前不同。选择保持“死于信号”的既有语义。
4. **不建进程组，靠遍历子进程（`pgrep -P` / `/proc`）**：不可移植，且 go 先退出后孙进程已过继给 init，按父 pid 找不到。

## 文件与行为

- 新增 `codegen/internal/roost/command_tree.go`、`command_tree_unix.go`、`command_tree_windows.go`、`command_tree_other.go`。
- `codegen/internal/roost/doctor.go`：`runDoctorGoCommand` → `runDoctorCommand("go", …)`，输出改为 `bytes.Buffer` 经 `runCommandTree`（同一 writer 时 exec 串行写入，与 `CombinedOutput` 等价）。
- `codegen/internal/roost/dependencies.go`：`runDependencyCommand` → `runDependencyBinary("go", …)` 经 `runCommandTree`；去掉 `os/exec` 导入。错误文本不变。
- 回归（新增，`//go:build unix`）`codegen/internal/roost/go_command_tree_promises_test.go`，替身 `go` 是 sh 脚本：起 `sleep 30 &`（继承 stdout / stderr 与工作目录）、记下其 pid、`wait`：
  - `TestDoctorGoCommandTimeoutReturnsAndLeavesNoGrandchild`：3 秒时限，断言 ctx 结束后 10 秒内返回、结果是 “timed out after 3s”、孙进程 2 秒内消失。
  - `TestDependencyCommandCancelWithBufferedOutputReturnsAndLeavesNoGrandchild`（generate 路径）：取消后有界返回、错误非 nil、孙进程消失；再用新 context 跑一个立即成功的替身返回 nil，暂存目录可删（“取消后重试并最终可接管”）。
  - `TestDependencyCommandCancelWithFileOutputLeavesNoGrandchild`（CLI 路径，`*os.File` 输出）：孙进程消失。
  - `TestDependencyCommandInterruptKillsTheGoTreeAndStillKillsRoost`：重新执行测试二进制扮演 roost（自成进程组，代替终端前台组），向该组发 SIGINT，断言 roost 死于 SIGINT（行为同前）且 go 子树消失。这一条守的是新设计的副作用（Ctrl-C），不是原缺陷的红。

## 兼容性

- 退出与错误文本不变；超时 / 取消后的返回从“等孙进程结束”变为 ctx 结束后立即（最多 5 秒）。
- Unix 上 go 在独立进程组里运行：它若要读终端（例如用户显式设 `GIT_TERMINAL_PROMPT=1` 让 git 交互询问凭据）会收到 SIGTTIN 而停住，直到超时被杀。go 默认设 `GIT_TERMINAL_PROMPT=0`，SSH 口令提示走 askpass / agent 时不受影响；需要交互认证的私有模块应先配置凭据助手或 `GOPRIVATE` + `.netrc`。
- 无 API、生成物、持久格式变化。

## 未验证项 / 风险

- **Windows 未实跑**：`taskkill /T /F` 路径只做了 `GOOS=windows go vet` 编译检查；回归测试是 `unix` 构建标签（sh 替身、`syscall.Kill`），Windows CI 不覆盖。复现入口：Windows 上 `roost doctor` 对一个大工程设短时限，超时后 `tasklist /FI "IMAGENAME eq compile.exe"` 应为空、暂存目录可删。
- 若 go 在超时前已退出、只剩孙进程，Windows 的 `taskkill /T` 按父 pid 找不到它们（Unix 进程组不受此限）；此时只有 `WaitDelay` 保证调用按时返回。
- 真 go 修后探针没有做修前负对照（只确认了修前 `kill -9` go 会留下 compile 孙进程，用的是 shell 探针而非同一匹配逻辑）；承诺本身由替身用例的红绿证明。

## 补修（2026-10-05）：满载偶发红与重发信号的竞态

现象：`TestDoctorGoCommandTimeoutReturnsAndLeavesNoGrandchild` 只在满载时红（全量 `go test ./...`、`-race ./...`、v1.20.0 pretag），文本 `fake go never recorded its grandchild`；同文件 `TestDependencyCommandInterruptKillsTheGoTreeAndStillKillsRoost` 也偶发红。

根因：

1. **测试拿真实 3s 计时器和替身的 exec 赛跑**（测试缺陷）。doctor 用例只能靠 `runDoctorCommand` 的超时取消，满载时 sh 替身起 `sleep &`、再 `mv` 写 pid 文件要几秒，3s 到点时孙进程还没报告，用例什么也没证明就判失败。其余用例 `waitStarted` 写死 5s 上限（中断用例要重新 exec 一份 `-race` 测试二进制），孙进程消失写死 2s（被杀的孙进程托管给 launchd 后在回收前是僵尸，`kill(pid,0)` 仍成功），孙进程只活 30s（满载下可能自然退出、漏报泄漏）。
2. **`runCommandTree` 重发信号后立即返回**（实现缺陷，fix）。接住 SIGINT 杀树后 `self.Signal(sig)` 只是 `kill(getpid())`：多线程进程里信号可能被别的线程接走，`kill` 返回时默认动作还没生效，调用方先跑了下去——`project deps` 会回滚、打印错误、以自己的退出码结束，而不是“和以前一样死于信号”。满载下才看得见：测试子进程打印 `runDependencyBinary returned instead of dying of the signal`，`exit status 3`。

改法：

- `doctor.go`：`runDoctorCommand` 拆出 `runDoctorCommandUntil(ctx, …, timeout, …)`，超时语义不变（`ctx` 以 `DeadlineExceeded` 结束时报 `timed out after <timeout>`）。
- `command_tree.go`：重发信号后等 `reraisedSignalGrace`（10s）让默认动作生效；只有进程里别处也接了这个信号时才会等满并返回错误。
- 测试：doctor 用例用测试可控的期限上下文，等替身报告孙进程 pid 之后才让期限到达，再断言 10s 内返回、报 `timed out after 3s`、孙进程不在；另加 `TestDoctorGoCommandTimeoutIsItsOwnDeadline` 用真实 1s 计时器钉住 `runDoctorCommand` 自己的超时接线。`waitStarted` 在被测调用 / 子进程先结束时立刻失败，否则只有 2 分钟兜底；孙进程消失兜底 30s 且僵尸算已消失；孙进程寿命 600s。承诺（上下文结束后 10s 内返回、无孙进程残留、Ctrl-C 后 roost 死于 SIGINT）不变。

压力复现（10 核 macOS；20 个 `yes > /dev/null` + 两个循环 `go test -race ./codegen/internal/...`；`-race` 测试二进制；SIGINT 恢复默认）：

| --- | --- | --- | --- |
