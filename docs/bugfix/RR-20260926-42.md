# RR-20260926-42 修复：Mod 可声明停机预算，App 在 `shutdown.total_timeout` 内优先分配；dataengine 声明 `shutdown_timeout`

问题：[RR-20260926-42](../bug/RR-20260926-42.md)（探针见 [REPRO-2026-09-26-04 §8](../bug/REPRO-2026-09-26-04.md)）。
日期 2026-09-26；实施基线 main `49f20ee` + RR-20260926-34 提交 `35060cc`。状态：已修复、本地验证通过，已本地提交，未推送/未发布。

## 根因

`kit/dataengine/mod.go`（基线）只有兼容 `Stop()` 读取 `dataengine.shutdown_timeout`；App 停机只走 `StopWithContext`，截止时间来自
`app/app.go` `modStopContext` 的 `剩余 / (i+1)`，与该配置无关。总 30s 时 5 / 7 / 10 个 Mod 的 dataengine 只拿到 7.5s / 6s / 4.29s。
另外服务专属 Mod 与共享 Mod 分两段停止、共用同一个总时限，前一段的均分只看本段 Mod 数，最后一个服务专属 Mod 可以拿走全部剩余时间。

## 决策（按维护者批准的修复约束：总时限内优先分配给声明预算的 Mod）

- 新增可选接口 `app.ModStopBudgetProvider { StopBudget() time.Duration }`（<=0 视为未声明）。
- `modStopContext` 每停一个 Mod 重新规划（前面的 Mod 提前结束省下的时间自然留给后面）：
  - 需求 = 声明预算之和 + 本段未声明 Mod 数 × `defaultModStopTimeout`（5s，原本就是无截止时间时的单 Mod 预算）。
  - 需求 ≤ 剩余：声明的 Mod 恰好拿到声明值；未声明的 Mod 均分其余（每个不少于 5s）。
  - 需求 > 剩余（“不足”）：全部需求按 `剩余 / 需求` 同比缩放，声明的 Mod 被缩减时记 Warn `mod stop budget scaled down`（带
    declared / granted / remaining）。声明预算之和因此不超过总时长。
  - 没有任何 Mod 声明时，结果与原先 `剩余 / 剩余 Mod 数` 完全相同（两种分支都可推出）。
  - 无总截止时间的兼容路径（启动失败回滚的 `stopModsReverse`）：声明的 Mod 用声明值，其余 5s。
- 服务专属一段改用 `stopModsReverseBefore(ctx, serviceMods, sharedMods, …)`：之后才停的共享 Mod 只贡献**声明预算**参与规划；
  共享 Mod 中未声明的不参与这一段的均分（与原先相同，避免改变未声明配置下服务专属 Mod 的时长）。
- `kit/dataengine.Mod.StopBudget()` 返回 `dataengine.shutdown_timeout`（默认 30s，未 Init 为 0）。
- 超时语义不变：某个 Mod 超过截止时间仍返回 `DeadlineExceeded`，App 停止后续关闭、保留其余 Mod 资源（`stopIncomplete` 分支未改）。

**超出约束字面的一处取舍（请维护者确认）**：约束写“不足时按声明比例缩放，其余 Mod 均分剩余”。若把声明预算缩放到恰好占满总时长，
生成配置的默认值（`total_timeout: 30s`、`dataengine.shutdown_timeout: 30s`）会让排在 dataengine 之前停止的 nest / saga 拿到零截止
时间，立即超时并中断整条关闭链（dataengine 与之后的 Mod 都不再停止）。因此“不足”的判定把每个未声明 Mod 计 5s 基准需求，一起按比例
缩放：默认配置下 dataengine 在 5 / 7 / 10 个 Mod 时得到约 20s / 18s / 15s（修前 7.5s / 6s / 4.29s），nest 约 3s，并告警。
生成配置的数值未改，只补注释说明应满足 `total_timeout ≥ dataengine.shutdown_timeout + 5s × 其他 Mod 数`；是否上调生成默认的
`total_timeout`（会连带部署 `terminationGracePeriodSeconds`，见 docs/DEPLOYMENT.md）留给维护者决定。

未采用：每个 Mod 只看自己的声明值、不看总时限——违反“总和不超过总时长”；把 dataengine 从均分中排除但不缩放——总时长不足时仍会越界。

## 兼容性

- 新导出 API：`app.ModStopBudgetProvider`、`(*kit/dataengine.Mod).StopBudget`。未实现接口的 Mod 行为不变。
- 行为变化：装配了 dataengine 的服务，排在 dataengine 之前停止的 Mod（nest、saga 等）截止时间变短（让出 dataengine 的预留），
  dataengine 之后停止的基础设施 Mod 拿到 dataengine 提前结束后剩下的时间（与原先一样动态复用）。默认生成配置下停机会记一条
  `mod stop budget scaled down` 告警，属预期提示。
- 服务专属 Mod 的时长现在会扣除之后共享 Mod 声明的预算；没有声明时不变。
- 生成配置只多了注释，YAML 语义不变；已生成工程无需迁移。

## 对抗性自查

- **停机顺序**：逆序与“服务专属先、共享后”的顺序未变；只改每个 Mod 的截止时间。服务专属一段为之后的共享 Mod 保留声明预算，
  共享一段在剩余时间内照常规划。
- **超时保留所有权**：`stopIncomplete` 分支未改：任何 Mod 超时即中断后续关闭，保留依赖资源；Service.Shutdown 超时时仍不停 Mod。
  缩放规则保证未声明 Mod 不会拿到零截止时间（零会立即超时并中断整条链），这是选择 5s 基准的原因。
- **无声明时等价**：两种分支都推出 `剩余 / 本段剩余 Mod 数`，既有 `app` 测试（含 `TestAppUsesConfiguredShutdownTimeout`、
  `TestStopModsReversePreservesDependenciesAfterTimeout`）全绿。
- **兼容 Stop()**：`kit/dataengine.Mod.Stop()` 仍用 `shutdown_timeout`；启动失败回滚路径现在也给 dataengine 声明值（原为 5s）。
- **并发**：规划在停止循环的单 goroutine 内完成，只读 Mod 的声明值；`-race -count=20` 通过。
