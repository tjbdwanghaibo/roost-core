## 根因（基线 `8d06d80` 源码，行号为修前）

撤销发布分两段，两段之间新实体的锁已经交还，而 `removing` 标记还在：

1. `entity/manager_factory.go:130-143` `revokeCreated`（事务回滚 / 拒绝时由 `RollbackTx` 调用，Guard 仍持锁）：锁内摘索引、
   `m.removing[id] = struct{}{}`（:138）、`SetRemoved`。
2. Guard 释放：`entity/entity_guard.go:169` `releaseEntities` 先解锁全部实体（`doReleaseEntity` 的 `mu.Unlock`，:490），
   然后 `:177` `runPostRelease`。撤销登记的 post-release（`manager_factory.go:154-166`）这时才跑 `DestroyAll` / `OnDestroy` / `ClearBase`、
   `LockManager.ReleaseLock(id)`，最后 `delete(m.removing, id)`（:160）。
3. 这段时间里另一个 handler 新建同 ID：`build` 从 LockManager 拿到同一把（已空闲的）锁，`lockCreated` 的 try-lock 成功，
   `TryAdd` 在 `entity/entity_manager.go:113-114` 撞上 `removing`，返回 `ErrEntityRemoved: <id> is being removed`；
   `CreateInScope` 在 `manager_factory.go:84-89` 原样返回。`ErrEntityRemoved` 不在 `isRequeueableDispatchError` 的类别里，
   `nest/nest_dispatch.go:102` 之后不重排，它成为最终回复。

RR-48 交叉创建回归的失败形状：H1 建 X、H2 建 Y，H1 新建 Y 冲突 → 整条回滚、撤销 X → Guard 解锁 X；H2 此时新建 X，try-lock 成功，
`TryAdd` 撞上 H1 尚未收尾的 `removing[X]` → H2 以 `ErrEntityRemoved` 结束（H2 自己的回滚也撤销了 Y，H1 重排后建成两者）。
`Destroy`（`entity_manager.go:261-273`）同样是“锁内置 removing → 解锁 → 收尾回调 → 清 removing”，窗口形状相同。

## 决策

采用约束的第二种：Nest handler 内新建撞上 `removing`，与 RR-48 的新建锁冲突同样处理。

- **为什么不是“撤销在释放锁之前完成移除”**：要让窗口不可观测，`removing` 的整个生命周期（销毁回调、`ClearBase`、`ReleaseLock`、清标记）都得
  挪进 Guard 持锁期间，也就是在快 worker 上、handler 仍持有全部声明 / Cast / 新建实体锁时运行业务 `OnDestroy`。RR-35 有意让它与
  `Destroy` 同序放到锁释放之后，原因是销毁回调可能按锁序去协调其他实体；锁内运行会让回调在已持有更高锁组时取锁，破坏 RR-48 建立的
  全序（并且 pipelined / strict 拒绝路径上的撤销也要一起改）。单独把 `removing` 提前清掉也不行：旧实例的收尾回调会与同 ID 新实例并存。
  而 `removing` 标记本身就是“持有者尚未交还这个 ID”的信号，窗口在持有者 goroutine 上紧接着锁释放结束，属于暂时状态。
- **为什么按锁冲突处理成立**：窗口由另一个持有者（撤销方或 Destroy 方）在自己的 goroutine 上收尾，与“锁被其他持有者占用”同类，
  并且同样不能在快 worker 上等待。可回滚事务整条回滚后 5ms 重排时收尾早已完成；不能回滚的 handler 按 RR-64 返回冲突哨兵、不重排，
  冲突前的修改不会被重复执行。对 `Destroy` 收尾窗口一并生效：`TryAdd` 的 `ErrEntityRemoved` 不区分两者，两者都是暂时状态，
  只处理撤销而让销毁窗口继续返回 `ErrEntityRemoved`，业务在 handler 里仍会拿到同样无法区分的失败。
- **不在快 worker 上等待**：只是把一个错误换成另一个错误，没有新增等待入口。

## 兼容性与迁移

- **行为收紧**：Nest handler 内（生成 Lifecycle 的 `Create` / `GetOrCreate` 创建分支、`ManagerAccess.Create`、`CreateInScope`）新建时，同 ID 的
  上一个实例正在撤销 / 销毁收尾：此前返回 `entity.ErrEntityRemoved`（最终错误、不重排）；现在返回 `nest.ErrCreatedEntityLockConflict`——
  可回滚事务同时带 `ErrLockTimeout`，框架整条回滚后自动重新准入；不能回滚的 handler 不带 `ErrLockTimeout`、不重排。
  handler 内按 `errors.Is(err, entity.ErrEntityRemoved)` 判断这一窗口的业务代码需改看 `ErrCreatedEntityLockConflict`。
- handler 内的生成 `GetOrCreate` 不再对这一窗口做 RR-57 的立即重试（错误不再是 `ErrEntityRemoved`），改由框架回滚重排（可回滚）或返回冲突（不能回滚）；
  Nest 之外调用（capturer 为 nil）不变，仍返回 `ErrEntityRemoved`、GetOrCreate 仍有界重试。
- 无新导出 API、无哨兵新增、无配置 / 持久格式变化。

## 对抗性自查

- **已做的修改不重复生效**：可回滚事务的冲突发生在准入之前，`createLockBusy` 让它即使被业务吞掉也整条回滚后才重排；不能回滚的 handler
  在消息上记冲突（`markCreateLockConflictWithoutRollback`），`requeueAllowed` 为假，只回复一次（memory 子用例断言执行 1 次、值只加一次）。
- **锁不泄漏、不在未加锁时发布**：锁在改写错误之前按原逻辑归还（`lockedNow` 时 `ReleaseEntity`），新实例未发布。
- **RR-57 不回退**：Nest 之外 capturer 为 nil，分支不命中，`TestLifecycleGetOrCreateRetriesWhileRevokeFinishes` 通过。
- **快池不阻塞**：只多一次 `errors.Is` 与冲突路径上的错误构造。
- **同一 Guard 自己的撤销**：handler 内嵌套独立事务新建 X 后回滚（撤销的 post-release 挂在同一 Guard 上，要等整个 handler 释放才跑），
  外层随后再新建 X 也会命中该分支：可回滚时整条回滚重排（新 Guard 上收尾已完成），不能回滚时返回冲突。此前返回 `ErrEntityRemoved`。
  这一形状未单独写回归。
