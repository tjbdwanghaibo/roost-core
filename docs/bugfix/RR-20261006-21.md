# RR-20261006-21 修复：失败启动删 cast 前删掉它已停进程的记录；有进程停不下来时保留 cast

问题：[RR-20261006-21](../bug/RR-20261006-21.md)（SKILL-1 第三条补测）。基线 `37338490`，分支 `sktest2`，未发版。与 [RR-20261006-23](RR-20261006-23.md) 同一处根因（已停进程的记录从不删除），两条共用新的两个 helper，分开登记是因为触发与后果不同。
读代码：codebase-memory 共享 generation 停在 09-30（`failCastLocked` 等 10 月新符号不在图里），以当前源码为准直接阅读；`runtime.processes` 的删除点用 `rg 'delete\(runtime.processes'` 穷举（只有 `startEntityProcess` 的三条失败分支）。

## 根因

`startLocked`（基线 `skill/runtime.go:440-447`）删 cast、还 ID 之前只撤了排程任务（NC-110），没处理进程记录；`stopProcess` 停进程只改状态、entity 进程清掉 `Program`。旧记录挂在被复用的 ID 下，`Checkpoint` 找不到它的程序。

## 方案取舍

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| ① 删 cast 前删它名下的记录，有运行中的进程就保留 cast（采用） | `castHasRunningProcessLocked` 为假时 `forgetCastProcessesLocked` 再删 cast、还 ID；为真（宿主 `StopProcess` 失败，进程仍在宿主侧运行）时 cast 留作 failed、不还 ID，Start 返回 `(cast.id, 原错误)`，与已提交后失败一致 | 采用。运行中的记录始终挂在一个存在的 cast 名下；正常路径仍是“等于没有施法”，ID 照旧复用 |
| ② 失败启动永不复用 ID | 不再 `nextCastID--` | 未采用：改变 NC-110 已定的“未提交失败等于没有施法”，调用方看到的 ID 序列跳号 |
| ③ 停进程时就删记录 | `stopProcess` 里删 | 未采用：已提交的 cast、状态同步与表现停止事件都还要读停止后的记录；记录随 cast 一起回收是 RR-23 的做法 |

宿主停不下进程时，进程仍在宿主侧运行，这是宿主故障的直接后果；修复保证 Runtime 状态自洽（记录有归属、checkpoint 可恢复），之后由该 cast 的保留 / 回收规则处理，不再让下一个 cast 接走。

## 兼容性

API 与 checkpoint 格式不变。行为差异：正常失败启动之后不再残留进程记录（state mutation 不再出现属于被删 cast 的进程）；宿主停不下进程的失败启动现在返回非零 cast ID 并保留 failed cast（之前返回 0、记录被下一个 cast 接走）。

## 未验证 / 风险

宿主停不下进程时，进程在宿主侧仍运行，Runtime 不会自动重试停止（与已提交后失败的 `failCastLocked` 忽略停止错误一致）；`Shutdown` / `RemoveProgram` 仍会再停一次。

## 后续：Runtime 负责重试停止（维护者 2026-10-06）

上面“未验证 / 风险”里的“Runtime 不会自动重试停止”改为由 Runtime 负责到底。维护者原话：“如果是技能本身的问题是不是技能自己处理比较好”（B 选项）。不新编号；实施中另发现的两处缺陷登记为 [RR-20261006-30](RR-20261006-30.md)、[RR-20261006-31](RR-20261006-31.md)，同一提交修复。分支 `skretry`，基线 `90c92caf`，未发版。读代码：codebase-memory 共享 generation 停在 09-30，以当前源码为准；停止入口与 `ProcessRunning` 判断点用 `rg` 穷举。

### 设计

| 项 | 做法 |
| --- | --- |
| 记录 | 不新建状态表。`failCastLocked` 停完之后，本 cast 名下仍在运行（宿主拒绝停止）、未移交的进程标成新的 `ProcessStatus` `stop_pending`（`deferUnstoppedProcessesLocked`），记录仍是 `runtime.processes` 里那一条。`stop_pending` 与 running 一样钉住 cast（`castHasRunningProcessLocked` 改用 `liveOnHost`），所以 `startLocked` 照 RR-21 保留 failed cast、不还 ID。进程不再步进、不派发信号、不跑回调（这些路径都只认 running） |
| 重试 | `advanceHost` 推进到一个 tick 后调 `retryProcessStopsLocked`：按 ID 顺序重试到期的待停止进程，复用 `stopProcess`。第一次在 `ProcessStopRetryBackoff`（默认 4）tick 之后，之后每失败一次翻倍，最多 64 倍。成功后进程进入 `cancelled`、发 `process_stop` 表现，随即 `pruneCompletedCastsLocked`，cast 与记录按 RR-23 的规则回收。重试失败不让 `Advance` 返回错误（错误已在第一次停止时返回过） |
| 上限与告警 | 失败的重试到 `ProcessStopRetryLimit`（默认 10，约 1276 tick，20Hz 下约 64 秒）后不再自动重试：计 `skill.process.stop_retry_exhausted.total`、写一条 Warn 日志（进程 / cast / owner / lifecycle 实体 / 次数 / 错误），记录保留；`RetentionStats` 新增 `StopPendingProcesses` / `StopRetryExhaustedProcesses`。`Shutdown` / `RemoveProgram` 仍会再停一次（它们的选择条件改为 `liveOnHost`） |
| 内存 | 待停止条目最多 `MaxStopPendingProcesses`（默认 256）。新增条目会超限时先丢最早（ID 最小）的已告警条目，没有就丢最早仍在重试的：删记录（state mutation 发 `process_remove`，cast 不再被钉住、按 `CompletedCastLimit` 回收）、计 `skill.process.stop_pending_dropped.total`、写 Error 日志，Runtime 从此不再负责停它。被钉住的 cast 因此最多多出 `MaxStopPendingProcesses` 个 |
| 容量 | 待停止的 entity 进程仍在宿主侧，照样占 `MaxOwnedProcesses*` 容量 |
| checkpoint | 格式只扩展、版本 2 → 3：进程记录加 `stop_retry_attempts` / `stop_retry_tick` / `stop_retry_exhausted`（只在 stop_pending 时出现），payload 加三项选项（恢复用 checkpoint 里的值，重试时刻与原 Runtime 一致）。恢复校验：只有 stop_pending 带重试字段、次数不超过上限、到上限才算 exhausted、条数不超过上限、不在 owned 表里。版本 2 得到 `ErrCheckpointUnsupported`（线上未部署，不兼容） |
| 宿主 | `Host` 接口注释写明 `StopProcess` 必须幂等；`MemoryHost` 本来幂等（`TestMemoryHostStopProcessIsIdempotent`），测试替身都委托给它 |
| 同步 | 见下 |

### 客户端看到什么

skillsync 只转发 Runtime 的 state mutation 与 presentation，不对进程状态做特判（`rg` 核对 `skill/skillsync` 无 `ProcessRunning` / 状态判断）。

- state mutation：进入待停止是一条 `process_upsert`（`status: stop_pending`；失败启动时进程在同一笔里创建，所以只有这一条，没有先 running 的）；停掉后 `process_upsert`（`status: cancelled`）；cast 回收时 `process_remove`。重试次数与时刻不在 `ProcessStateSnapshot` 里，重试不产生 mutation。被丢弃的条目直接 `process_remove`。
- presentation：进入待停止时多一条 `process_update`（`ProcessStatus: stop_pending`，带视觉的进程才有），停掉时 `process_stop`。待停止期间 `PresentationSnapshot` 的 reset 仍带着这个进程（宿主侧还在），状态 `stop_pending`、`PrimaryTarget` 按 RR-22 的规则；停掉后不再带。
- `OwnedProcesses` 只列 Runtime 仍在推进的移交进程；待停止的看 `StateSnapshot().Processes` 或 `RetentionStats()`。

### 未采用

| 方案 | 原因 |
| --- | --- |
| 单独一张“待撤除”表 | 维护者要求复用 RR-21 / RR-23 的记录生命周期；两份状态要各自同步、各自进 checkpoint |
| 每个 tick 重试 | 维护者要求退避，宿主故障期间不能被每 tick 打一次 |
| 到上限后删除记录 | 维护者要求保留记录让运维看到；删除只在超过内存上限时发生，且告警 |
| 进入待停止时也写日志 | 错误已返回调用方，日志只在到上限和被丢弃时写，避免宿主故障期间刷屏 |

### 兼容性

- 新 `ProcessStatus` 值 `stop_pending` 会出现在 `ProcessStateSnapshot.Status`、state mutation、`PresentationEvent.ProcessStatus` 与 `ActivePresentation.ProcessStatus`；按状态值分支的客户端 / 渲染器要认它（含义：Runtime 还在负责停，世界里仍在）。
- `RuntimeOptions` 新增三项、`RuntimeRetentionStats` 新增两个字段，零值取默认。
- checkpoint 版本 3，版本 2 不再恢复。
- 行为：宿主停不下的进程之后会被再次 `StopProcess`（宿主必须幂等）；tick 驱动的停止失败不再冻住 Runtime（RR-31）。

无外部依赖，未在真实宿主上演练。重试与丢弃按进程表全量扫描（O(进程数)），只在有待停止条目或进入待停止时发生。`process` 这个名字维护者另有整体改名任务（Spawn），本次沿用现有名字。
