# RR-20260914-04:已入帧输入的迟到重传再次入帧

**仓库 / 位置**:roost-core `lockstep/sequencer.go`,`SubmitInput` / `Advance`。
**修复单元**:U-0193(C8)。**定位文档**:TROUBLESHOOTING T-87。

## 问题

`SubmitInput` 对原帧号小于 `next` 的输入先改成 `next`,只在目标帧的 pending map 里去重;`Advance` 切帧后删掉
map,没有保存原始 `(player, frame)` 的处理身份。已进帧 1 的输入重传后又进帧 2;首次迟到折进帧 2 的重传后又进
帧 3。一次性开火 / 技能会被纳入两帧(所有客户端可能一致地收到,不必然分歧,但执行了两次)。

## 根因

首次到达与重传走同一条"折入下一帧"的路径,身份只活到目标帧被切(C8)。

## 方案选择

- **只存每玩家最大已见帧号。** 乱序到达的未来帧(先 3 后 2)会被误丢,审查明确指出。
- **拒绝所有 `frame < next` 的输入。** 丢掉"首次迟到折入下一帧"的乐观帧锁策略。
- **每玩家有界的已接受身份表(采用)。** `accepted[player][original] = target`,`SubmitInput` 先查身份:命中即
  返回当初折入的帧号、不改任何状态;未命中按原逻辑折入 / 去重 / 覆盖占位,并且**所有被接受的结果**(包括输给
  同帧已有输入的)都记身份——否则它的重传还会折到更后面。`Advance` 按 `ReplayHorizon`(= MaxSubmitWindow = 64 帧)
  修剪,内存 players × 64。超过期限的重传与首次到达不可区分,按首次折入,期限写进常量注释。

## 改动

`lockstep/sequencer.go`:`ReplayHorizon`;`Sequencer.accepted`;`SubmitInput` 身份先查、`remember`;`Advance` 修剪。

## 证明

`lockstep/input_replay_promises_test.go`:按时 / 首次迟到两种重传都不再入帧且返回原目标帧;乱序未来帧(先 3 后 2)
两者都入各自的帧;显式输入仍覆盖迟到占位、之后迟到输入的重传不再入帧。

修前红:`replay reported frame 2, the original was folded into 1`(断言顺序调整后即审查的
`same original input executed in frames 1 and 2` / `frames 2 and 3`)。修后 lockstep 含 `-race` 全绿。

## 未做 / 边界

- 期限之外(> 64 帧)的重传仍会折入;没有确认水位协议,客户端也没有收到"已接受到哪一帧"的回执。
- 记录型替身,不涉及真实传输。
