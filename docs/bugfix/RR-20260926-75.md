# RR-20260926-75 修复：带 Remote 批次的消息里嵌套独立事务直接拒绝，不替外层 finalize、不提交外层批次

问题：[RR-20260926-75](../bug/RR-20260926-75.md)（探针 [REPRO-2026-09-26-07](../bug/REPRO-2026-09-26-07.md) §1 探针 3b）。
日期 2026-09-27；实施基线本地 main `62fdbe6`，建立在同批 [RR-20260926-73](RR-20260926-73.md)、[RR-20260926-74](RR-20260926-74.md) 之上。
状态：已修复、本地验证通过，已本地提交，未推送 / 未发布。方向按维护者 2026-09-27 批准的修复约束（拒绝，不引入嵌套独立批次）。
codebase-memory 图谱对 `nest/` 已过期（generation 09-26 08:36），结论来自当前源码。

## 根因（基线源码核对）

`invokeWithTransaction`（`nest/execution.go`）与 `commitDurable` 判断 Remote 分支用的是“当前派发消息有没有批次”（`msg.RemoteWriteBatch != nil`，
`:181`、`:239`、`:245`、`:259`、`:267`），而不是“这是不是消息自己的事务”（RR-49 的 `owner` / `tx.dispatch`）。handler 内的
`RunIsolatedTransaction` 因此：

1. `:181` 调 `msg.finalizeRemoteWriteBatch(tx)`：批次 `FinalizeLocked` 收到嵌套事务的 outcome，`nest/msg.go:68` 置 `remoteFinalized`，外层随后
   自己的 finalize 在 `nest/msg.go:41` 被跳过；
2. `:259-263` 嵌套事务持久提交后置 `msg.remoteCommitted = true`，外层失败时 `finishRemoteWriteBatch` 仍按已提交走 `batch.Commit`，
   `replyAfterCommit` 为真，回复被包 `ErrAfterCommitFailed`，而外层自己的提交数为 0；
3. 嵌套事务被拒绝时 `:245-246` 还会 Abort 外层的批次。

## 决策与实现

- `invokeWithTransaction` 入口先取 `msg := currentNestDispatchMsg()`（原先在函数中段取，现提前，不增加查找次数）：
  `msg != nil && msg.txInFlight && msg.RemoteWriteBatch != nil` 即“消息自己的事务正在执行、这是嵌套事务、消息带 Remote 批次”，直接返回
  `fmt.Errorf("%w: nested %q in message %q", ErrNestedTransactionInRemoteMessage, …)`。此时还没有建 SyncMutation、没有建 RollbackTx、
  没有调用 `call`，批次与 `remoteFinalized` / `remoteCommitted` / `remoteIndeterminate` 都不被触碰。
- 嵌套事务的 `call` 不执行，所以它的内存修改也不存在，不需要回滚；RR-65 的 `nestedTxCommitted` 不置位，外层照常按自己的结果处理
  （本身是 RollbackNone 时按 RR-73 不重排）。
- “嵌套事务会触及 Remote 实体、而消息没有批次”由既有检查覆盖：嵌套 strict 事务捕获 remote-managed 实体时 `CaptureEntities` 返回
  `ErrDurableRemoteWriteUnsupported`（`nest/rollback.go`，捕获发生在写任何持久记录之前），本修复不改它。
- `RunDetachedTransaction` 在已有 RollbackTx（Remote 消息总有）时直接复用外层事务，不是嵌套事务，不受影响。

未采用：引入嵌套独立批次（维护者明确不做）；让嵌套事务跳过 Remote 分支继续提交本地部分——同一消息里本地与 Remote 的原子性会被拆开，
约束要求拒绝。

## 兼容性与迁移

- **行为收紧**：带 Remote 批次的消息里调用 `RunIsolatedTransaction`，此前会提交并污染外层批次，现在返回 `ErrNestedTransactionInRemoteMessage`、
  什么都不做。仓内没有这种调用（审计核对）；仓外业务需把写入并入消息自己的事务。
- 新导出：`nest.ErrNestedTransactionInRemoteMessage`。无删除 / 改签名，无配置、持久格式变化。
- 性能：只在已有的 `currentNestDispatchMsg()` 结果上多两次字段读取。

## 对抗性自查

- **批次只随外层事务**：拒绝发生在任何 Remote 分支之前；回归覆盖外层成功（外层 finalize、Commit）与失败（Abort）两侧。
- **不误拒消息自己的事务**：条件要求 `txInFlight`，消息自己的事务进入时它为 false（随后才由 owner 置位）；既有 Remote 用例全部通过。
- **不影响无批次消息**：条件要求 `RemoteWriteBatch != nil`；RR-65 / RR-74 的本地嵌套用例通过。
- **快池不阻塞**：无新增等待。

## 未验证项 / 风险

- 外层事务返回之后（`txInFlight` 已复位）、Remote 批次收尾之前在同一消息里调用 `RunIsolatedTransaction`（例如业务 release hook 里）不属于本约束的“嵌套”，
  本修复未覆盖；该时点 Remote 批次尚未收尾，这种调用会被当成消息自己的事务处理——仓内没有此用法，未构造回归，交主会话判断是否登记。
- 使用替身批次，未在真实 remoteentity + Mongo 环境验证。
