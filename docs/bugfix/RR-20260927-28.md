# RR-20260927-28：`RetractSyncSubject` 在 `subj.mu` 内比对状态，按实例撤回

问题：[RR-20260927-28](../bug/RR-20260927-28.md)（OPEN-ITEMS B41）。日期 2026-09-27。基线 `7b56060` + cherry-pick `ed32ba3`（RR-20260927-22，本分支 `85e4779`），分支 `fix-r7-b12`。
状态：已修复，本地验证通过，本地提交，未推送 / 发布。codebase-memory 图谱过期（09-26），以当前源码为准。

## 决策（按清单推荐）

- `Unregister(id)` 的主体移到 `unregister(id, only)`；`Unregister` 传 `nil`，行为与 RR-22 完全相同（按 ID 注销当前登记，取锁后确认表项、不一致就重查）。
- `only` 非 nil 时，在取 `subj.mu`、`m.mu` 读锁下确认表项**之后**比对 `subj.state != only`：不是就解锁返回，什么也不做。比对与退役在同一把 `subj.mu` 下，
  中间没有窗口；`rebind` 换状态要取 `subj.mu`，forget 摘表要取 `m.mu` 写锁，都不可能插进来。
- `RetractSyncSubject(state)` 去掉锁外的 `subj.state` 比对（它也是与 `rebind` 并发的数据竞争），只做 `m.subject(id) == nil` 的快速返回，然后 `unregister(id, state)`。
- 形状二（旧登记忘掉后新状态重新登记为新 subject）：重查到的新 subject 状态不是 `state`，同样不动。同一个状态对象在退役后被排队重新登记（`RegisterAfterRetirement` / forget
  的排队登记）时 `subj.state == state`，照旧撤回——那仍是这次要撤回的状态。
- 测试缝 `retractLookedUp` 放在“取到 subject 之后、比对并注销之前”，生产中恒为 nil。

锁序 `subj.mu → m.mu`（读）与 RR-22 的 `Unregister` 相同；无新等待，调用方（`entity/manager_factory.go` `revokeCreated`，Nest 快 worker 上持实体锁）不受影响。
