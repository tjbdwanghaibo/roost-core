# RR-20260927-25：不可比较的自定义 `lock.Mutex` 值类型在 `holding` 比较时 panic

问题：[RR-20260927-25](../bug/RR-20260927-25.md)（OPEN-ITEMS B06 → 12 追加）。日期 2026-09-27。基线 `7b56060`，分支 `fix-r7-b12`。
状态：已修复，本地验证通过，本地提交，未推送 / 发布。codebase-memory 图谱过期（09-26），调用点以当前源码与 `git grep` 为准。

## 根因（基线行号）

`entity/entity_guard.go:315` `holding`：`current == ent || current.GetMutex() == ent.GetMutex()`。两个 `lock.Mutex` 接口值动态类型相同且该类型
不可比较（含 func / slice / map 字段的值类型，值接收者）时，`==` 在运行期 panic。同 ID 两个实例各持一份这种锁（RR-67 的“Destroy 后同 ID 重建”形状，
或自定义 builder 为同 ID 构建多个实例）时，`RequireEntity` / `TryRequireEntity` / `GuardedEntity` / 锁序判断 `mayLockEntity` 都会 panic。
全仓非测试代码里接口间 `GetMutex() ==` 只有这一处（其余都是与 `nil` 比较，不会 panic）。

## 决策

主记录给了两种处理：先判可比较、不可比较按“不是同一把锁”；或按实体实例身份比较。选前者：

- 按实例身份比较会丢掉 RR-67 明确保留的语义——“同 ID、同一把锁的另一实例（Destroy 之前重复构建）算已持有”
  （`TestGuardTreatsInstanceSharingTheHeldMutexAsHeld`）；这对框架的 `*lock.ReentrantMutex` 正确且需要，不能为自定义类型回退。
- 新增 `sameMutex(a, b lock.Mutex)`：动态类型是 `*lock.ReentrantMutex`（框架 `NewEntityBase`、`LockManager` 缺省工厂、`EntityCreateParam` 缺省都用它）
  时只做类型断言与指针比较，不经反射；其余类型才 `reflect.TypeOf` 判断两边动态类型相同且 `Comparable()` 再 `==`。两边都为 nil 时保持原来的“相同”。
- 不可比较的值无法判定是否同一把锁，按“不是同一把锁”：新实例自己加锁，旧实例连同它的锁转入 `superseded`，Guard 释放时一并解锁——与 RR-67 对换锁实例的处理一致。
  代价写进注释：这种值类型若内部共用同一把**不可重入**锁，第二次加锁会自锁；自定义 Mutex 应当用指针或可比较的值实现。

热路径开销：`holding` 只在 eMap 已有同 ID 且不是同一实例时才比较锁（重入命中走 `current == ent`），比较本身对框架锁只多一次类型断言。
同机对照（`BenchmarkZZHoldingSharedMutex`，同 ID 共用锁的另一实例重入 `RequireEntity`，临时用例未提交，`-count=5`）：
修前 7.12～7.90 ns/op，修后 6.90～7.70 ns/op，均 0 B/op、0 allocs/op，差异在噪声内。

实体接口值本身的 `current == ent` 未改：实体实现都是指针（`Base()` 返回可变的 `*EntityBase`），值类型实体不在本条范围，见未验证项。

## 未验证项 / 风险

- 不可比较的自定义 Mutex 若多个实例内部共用同一把不可重入锁，同一 Guard 对第二个实例加锁会自锁（框架无法判定是否同一把锁）；已在 `sameMutex` 注释写明。
- `holding` 里实体接口值的 `current == ent` 仍是直接比较：值类型且不可比较的实体实现同样会 panic；仓内与生成物中的实体都是指针，未构造回归。
