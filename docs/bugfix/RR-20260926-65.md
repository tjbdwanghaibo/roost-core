# RR-20260926-65 修复：handler 内嵌套独立事务已提交后，外层消息不再自动重排，回复带可判别错误

问题：[RR-20260926-65](../bug/RR-20260926-65.md)（探针 [REPRO-2026-09-26-06](../bug/REPRO-2026-09-26-06.md) §1 P-C）。
日期 2026-09-27；实施基线本地 main `2373e21`，建立在同批 [RR-20260926-64](RR-20260926-64.md) 之上。
状态：已修复、本地验证通过，已本地提交，未推送 / 未发布。方向按维护者 2026-09-27 批准的修复约束（与 RR-64 同规则）：消息执行期间任一
嵌套独立事务已持久提交，则该消息不再自动重排（按“已越过提交点”处理，回复带可判别错误）。

## 根因（基线源码核对）

- `nest/execution.go` `invokeWithTransaction`：RR-49 用 `txInFlight` 让 handler 内嵌套的 `RunIsolatedTransaction` 不认领消息（有意：
  它的提交不是消息自己的提交，不能给外层置 `txAdmitted` / `txCommitted`，否则外层失败会被误报为已提交）。于是嵌套事务在
  `commitDurable` 里持久提交后，消息上没有任何记录。
- `nest/nest_dispatch.go`：外层随后以锁超时类错误失败（RR-48 强制并入的新建实体冲突、嵌套派发 try-lock 失败、业务错误）时，
  `transactionPastCommitPoint` 为假，`requeueTransientDispatch` 克隆重排，handler 从头执行，独立事务再提交一次。
- 仓内唯一生产调用 `dataengine/engine/entity_delete.go` `admitLocalEntityDelete`：没有 RollbackTx（memory handler）时本地删除走
  独立事务提交删除准入。

## 决策与实现

判据与 RR-49 同一来源：`Msg.transactionPastCommitPoint` 多一个事实 `nestedTxCommitted`，重排入口（`Msg.requeueAllowed`，RR-64 引入）不变。

- `commitDurable`：事务**不认领消息**（`tx.dispatch == nil`）且当前在派发中（`currentNestDispatchMsg()` 非 nil）时——
  - `durableCommit` 成功且 `tx.accepted`（committer 确实接受了非空记录）→ `msg.markNestedTransactionCommitted()`；
    记录为空时没有任何内容持久化，不算越过提交点（保持“独立事务什么都没写时外层照常可重排”）；
  - 结果未知（`ErrCommitIndeterminate`）同样置位：WAL 里可能已有它。
  - 被明确拒绝不置位：没有持久化，外层可以照旧重排（保持性回归覆盖）。
- `dispatchNest`：`nestedTxCommitted` 且回复有错误、不是 `ErrAfterCommitFailed`（消息自己的事务已提交时那个哨兵已说明“已提交”）
  时包新哨兵 `nest.ErrNestedTransactionCommitted`（`%w` 保留原因链）。它**不**是 `ErrAfterCommitFailed`：消息自己的事务确实没有提交
  （回滚或失败），只有独立事务提交了。
- 只有 `RunIsolatedTransaction` 这类“不认领消息的嵌套事务”受影响；`RunDetachedTransaction` 在已有 RollbackTx 时直接复用它，不产生
  嵌套事务；在 memory handler 内（无 RollbackTx）会新建事务，同样被记录。

未采用：让嵌套事务认领外层消息（会把外层的失败误报为已提交，违背 RR-49 / RR-53 的“嵌套事务不认领”）；只在重排函数里判断错误类型
（嵌套事务提交与外层错误类型无关）。

- `nest/execution.go`：`commitDurable` 记录嵌套事务提交 / 结果未知。

- `nest/nest_dispatch.go`：回复包 `ErrNestedTransactionCommitted`。

## 兼容性 / 行为变化

- handler 内 `RunIsolatedTransaction` 已持久提交（或结果未知）后外层失败：此前可能被重排、独立事务重复提交；现在只执行一次，
  回复满足 `errors.Is(err, nest.ErrNestedTransactionCommitted)`，原因（如 `ErrLockTimeout`）仍可 `errors.Is`，不带 `ErrAfterCommitFailed`。
- 外层普通业务错误的回复同样多了这个前缀（`nest: a nested isolated transaction committed before the message failed: …`）；按文本匹配的
  调用方需改用 `errors.Is`。
- 独立事务被拒绝或没有写任何内容时，外层行为不变。
- 新导出：`nest.ErrNestedTransactionCommitted`。无删除 / 改签名，无配置、持久格式变化。

## 对抗性自查

- **已提交内容不被重复执行（含嵌套、memory、pipelined）**：嵌套独立事务的提交在 `commitDurable` 返回前置位，早于外层 handler 继续执行、
  外层回滚与 `dispatchNest` 的重排判断；三种外层路径（strict / memory / pipelined）都经 `dispatchNest` 同一判断，回归逐一覆盖。
  结果未知的嵌套事务同样不重排。外层 pipelined 事务自己已被 WAL 接纳的情形仍由 RR-49 的 `txAdmitted` 覆盖。
- **不过度抑制**：独立事务被拒绝 / 记录为空时不置位，外层锁超时照旧重排（`TestIsolatedRejectedThenOuterLockTimeoutStillRequeues`）；
  RR-48 的可回滚冲突重排（外层没有独立事务）不受影响。
- **RR-48 死锁不回来 / RR-35 提交边界**：没有改取锁、捕获、撤销发布与准入顺序，只多一个布尔事实与回复包装。
- **错误语义**：`ErrNestedTransactionCommitted` = 外层未提交、独立事务已提交（勿当作未执行重试）；`ErrAfterCommitFailed` 仍只表示消息
  自己的事务已提交（外层已提交时不再叠加新哨兵）；可重排的未提交失败（没有嵌套提交）两者都不带。
- **嵌套不认领**：`txInFlight` / `tx.dispatch` 规则未改，嵌套事务仍不置 `txAdmitted` / `txCommitted`，外层失败不会被误报为已提交。

## 未验证项 / 风险

- 推断（源码阅读，未构造回归）：外层是 RollbackState 时，外层回滚按事务开始时的快照恢复 DAO，可能覆盖独立事务已持久提交的内存修改
  （内存与持久分叉）——修前即有、与重排无关，本次未改，另行评估。
- 嵌套独立事务结果未知时框架不 fence（fence 只在消息自己的事务经 `invokeHandlerTransaction` 返回 `ErrCommitIndeterminate` 时触发；
  `admitLocalEntityDelete` 自己调用 `runtime.fail`）——修前即有，未改。
- 在带 Remote 批次的消息里调用 `RunIsolatedTransaction` 时，嵌套事务会走外层批次的 `finalizeRemoteWriteBatch` / `remoteCommitted` 分支
  （`invokeWithTransaction` / `commitDurable` 按 `msg.RemoteWriteBatch` 判断，而不是按“是否本消息自己的事务”）——仓内无此调用，修前即有，
  未改、未构造回归，交主会话分流。
