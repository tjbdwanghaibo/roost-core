# RR-20260926-69 修复：forget 在删表前、m.mu 内清除旧 subject 的通知器，且只忘掉调用方看到的那个 subject

问题：[RR-20260926-69](../bug/RR-20260926-69.md)（复现 [REPRO-2026-09-26-06 §5](../bug/REPRO-2026-09-26-06.md#5-rr-69forget-清除重新登记-subject-的脏通知器)）。日期 2026-09-27。
实施基线：`2373e21`（RR-64～72 登记之后）。状态：已修复，本地验证通过，已本地提交，未推送/发布。

## 根因（基线行号）

`sync/entitysync/manager.go` `forget`：`:523` 在 `m.mu` 内把 subject 从表里删掉、放开锁，`:540` 才对旧 subject 的状态 `SetDirtyNotifier(nil)` /
`DiscardFrozenSync`。两步之间 `RegisterAfterRetirement(state)`（`:385` `Register` → 表里没有该 ID → 新 subject + `installDirtyNotifier`）装上的是**新**
subject 的通知器，随后被 forget 清掉：登记返回 `queued=false err=nil`，之后 `MarkDirty` 不进 pending，观察者再也收不到变化。同一状态对象重新登记
（RR-55 快速重连）正是这个形态。附带：forget 按 ID 查表，两条收尾路径（Flush 的 retiring 清理与 CloseSession 的“最后一个订阅者离开”）各看到一次
“可以忘掉”时，迟到的一次会把之后同 ID 新登记的 subject 删掉。

## 修复（维护者 2026-09-27 批准的约束：通知器清除在删表前或 m.mu 内完成）

- `forget(subj *subject)`：先在 `subj.mu` 下读状态（退役中的 subject 不再换状态：`rebind` 对它只排队或拒绝），再在 `m.mu` 内核对表里仍是**同一个**
  subject，在删表之前清除通知器并丢弃冻结内容，然后删表。表里已是另一个 subject 时什么都不做。之后的 successor 登记、snapshot 等待清理不变。
- 锁序 `m.mu → 状态锁`：`SetDirtyNotifier(nil)` 不回调（只在通知器非 nil 时触发）；`DiscardFrozenSync` 只调用冻结内容的 `release`，即 `reserveFrozen`
  返回的原子计数归还；状态锁内没有任何路径取 Manager 的锁（脏通知在状态锁外调用）。不在 `m.mu` 下取 `subj.mu`（既有锁序是 `subj.mu → m.mu`）。
- 调用方传 subject 指针：`finishRetire(subj, …)`、Flush 的退役清理、`dropSession` 的 defer、`unsubscribe`。
- `unsubscribe` 里 `defer m.forget(...)` 注册在 `defer subj.mu.Unlock()` 之后，按后进先出会在持锁时运行（forget 要取 `subj.mu`，会自锁）。该分支当前不可达
  （退役时 `retireLocked` 清空了全部来源，退订在来源检查处就返回 `ErrSubscriptionNotFound`），顺手改为解锁之后再 forget，不改变行为。
- 测试缝：`Manager.forgetUnlinked`（未导出，生产恒为 nil），在 subject 离表、放开 `m.mu` 之后调用，用来让登记确定性地落在窗口里。

未采用：“比对后再清”（需要给 `SubjectSyncState` 增加带身份的 compare-and-clear API，跨包改动更大，且冻结内容也要同样比对）；forget 完成前不走直接
Register（RegisterAfterRetirement 需要另一套“收尾中”状态，而删表前清除已使窗口不存在）。

- `sync/entitysync/manager.go`：`forget`、`finishRetire`、`Unregister` / `RetractUnloadedSubject` 调用、测试缝字段。
- `sync/entitysync/flush.go`、`subscriptions.go`：调用方传 subject；`unsubscribe` 的 forget 移到解锁后。

## 兼容性

## 对抗性自查

- **锁序**：新增的嵌套只有 `m.mu → 状态锁`；状态锁是叶子（其内只有原子计数与冻结内容释放）。`subj.mu` 只在 `m.mu` 之外取，保持既有 `subj.mu → m.mu`。
- **订阅者视图**：forget 只在最后一个 remove 交付（或最后一个订阅者会话关闭）后运行，remove-before-create 不变；新 subject 的订阅照旧从全量开始。
  冻结内容在删表前丢弃：删表之后 `CaptureSync` 的收尾检查（`mode.go` `m.subject(id) != subj` 时丢弃）仍会清掉旧 subject 迟到的冻结。
- **与 RR-55 / RR-59**：排队的 successor 仍在 forget 标记 `forgotten` 时取走；`RegisterAfterRetirement` 在离表后直接登记、在离表前排队，两种都不再丢通知器。
- **goroutine**：无新增。
