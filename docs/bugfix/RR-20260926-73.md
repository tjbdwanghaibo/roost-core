## 根因（基线源码核对）

- `nest/cast.go:168-171`：`guard.RequireEntity(e)` 在取得锁后发现实体已清理 / 摘除（`entity/entity_guard.go` `RequireEntity`：
  `ent.IsClear() || ent.IsRemoved()`）时返回 false，Cast 一律返回 `ErrLockTimeout`——目标已不在被伪装成暂时性锁冲突。
- `nest/nest_dispatch.go:101`：`msg.requeueAllowed(err)` 为真就交给 `requeueTransientDispatch` / `requeuePendingEntityGroupTransition`。
- `nest/msg.go:227-232` `requeueAllowed` 只排除“越过提交点”（RR-49 / 65）与“不能回滚的 handler 内新建实体冲突”（RR-64）。memory 快路径
  （`nest/execution.go:129`）与带 Remote 批次的 RollbackNone 事务在 handler 失败时不撤销任何修改，但 handler 返回任意锁超时 / 组迁移类错误
  （Cast 的上述伪装、嵌套派发 try-lock、业务自己传回的错误）仍被整条重排，handler 从头再执行，失败前的修改重复生效。

## 决策与实现

- **不重排的判据**：`Msg.noRollbackHandlerStarted`（`nest/msg.go`），在 `invokeWithTransaction` 里业务调用之前置位——memory 快路径在
  `invokeMemoryHandler` 之前，RollbackTx 路径在 `tx.policy == RollbackNone`（带 Remote 批次的 memory handler）时于 `callTransactionHandler`
  之前（`nest/execution.go`）。只由本条消息自己的事务置位（`owner`，嵌套事务的 `owner` 为 nil，nil 接收者无操作）。外层消息是
  RollbackNone、handler 内的嵌套独立事务可回滚时，外层已置位，同样不重排——即约束里的“本事务 / 外层消息事务为 RollbackNone”。
  `requeueAllowed` 增加 `!m.noRollbackHandlerStarted`。取锁、组锁、组迁移待定检查、冷目标改道等都发生在 `invokeWithTransaction` 之前，
  不置位，照常重排（“准入阶段失败照常重排”）。
- **回复哨兵**：`dispatchNest` 在不重排分支里，对 `noRollbackHandlerStarted`、未越过提交点且属于可重排类别（`isRequeueableDispatchError`：
  `ErrLockTimeout` / `ErrEntityLockGroupChanged` / `ErrEntityGroupTransitionPending`）的错误包 `ErrNonRollbackNotRequeued`（`%w` 保留原因）。
  已越过提交点的由 `ErrAfterCommitFailed` / `ErrNestedTransactionCommitted` 说明，不叠加。RR-64 的冲突哨兵补齐逻辑保留不变。
- **Cast**：`RequireEntity` 失败且 `e.IsRemoved() || e.IsClear()` 时返回 `fmt.Errorf("%w: id=%d was removed while waiting for its lock", ErrEntityNotFound, id)`；
  其余失败（无效 ID / 无锁对象）仍是 `ErrLockTimeout`。可回滚事务收到它照常整条回滚；`ErrEntityNotFound` 本就不在重排类别里。

### 哨兵选择：并列新哨兵 `ErrNonRollbackNotRequeued`，不复用 `ErrCreatedEntityLockConflict`

- `ErrCreatedEntityLockConflict` 的含义是具体原因“handler 内新建实体的锁按锁序不能等待”，它的 godoc 与 USER_GUIDE 还约定了可回滚形态
  （同时带 `ErrLockTimeout` = 已回滚、已重排、次数耗尽）。拿它标 Cast 目标失效、嵌套派发锁超时、组迁移，会让
  `errors.Is(err, ErrCreatedEntityLockConflict)` 不再能识别新建实体冲突，也会让可回滚形态的读法出现歧义。
- 新哨兵表达的是与原因正交的事实“handler 不能回滚、框架没有重排”，原因（`ErrLockTimeout` 等）照旧在链上，与 RR-65
  `ErrNestedTransactionCommitted` 的形状一致。RR-64 的回复形状（只带 `ErrCreatedEntityLockConflict`、不带 `ErrLockTimeout`）不变：它的错误本就
  不属于可重排类别，不会再补新哨兵；业务把冲突换成锁超时回复时两个哨兵都带。
- 与 RR-64 不同，这里不能去掉 `ErrLockTimeout`：它是业务返回的原因，框架只能包装、不能改写链。判别规则因此写成“带
  `ErrNonRollbackNotRequeued` 时 `ErrLockTimeout` 不表示未执行”（USER_GUIDE、godoc；RR-77 的判别表统一收口）。

未采用：让不能回滚的 handler 失败后自动撤销（memory 快路径没有快照，约束也未要求）；只改 Cast 的错误而不改重排判据（嵌套派发 try-lock、
业务自行返回的锁超时仍会重排，约束要求“任何锁超时 / 组迁移类暂时性错误”）。

## 兼容性与迁移

- **行为收紧**：memory handler（及带 Remote 批次的 memory handler）开始执行后返回 `ErrLockTimeout` / `ErrEntityLockGroupChanged` /
  `ErrEntityGroupTransitionPending` 时，此前被自动重排（最多 400 次），现在只执行一次，回复 `ErrNonRollbackNotRequeued`（原因仍可 `errors.Is`）；
  Remote 批次随失败 Abort。依赖“memory handler 返回锁超时就自动重试”的业务需要自行重试，先确认 handler 幂等。
- **Cast 错误变化**：等锁期间目标被 Destroy / 仅内存卸载，此前 `ErrLockTimeout`（并被重排），现在 `ErrEntityNotFound`（不重排）。
  按 `errors.Is(err, nest.ErrLockTimeout)` 判断“目标不在”的调用方需改看 `ErrEntityNotFound`。
- 可回滚事务（state / undo）的锁超时重排、RR-48 的新建冲突回滚重排、RR-49/65 的提交点判断、准入阶段的重排都不变。
- 新导出：`nest.ErrNonRollbackNotRequeued`。无删除 / 改签名，无配置、持久格式变化。

## 对抗性自查

- **已做的修改不重复生效**：不能回滚的 handler 一旦进入业务调用，dispatchNest 的两个重排函数都不再对这条消息生效，消息只回复一次；
  memory 快路径失败不 `Admit`，SyncMutation 按未准入丢弃；Remote 批次随失败 Abort（回归断言）。
- **准入阶段照常重排**：置位点在业务调用之前的最后一步；`invokeWithTransaction` 之前的取锁 / 组锁 / 组迁移检查失败不置位（既有 3 个用例）。
  RollbackTx 路径在置位之前只有 `CaptureEntities`，policy none 时它只登记参与者，不产生可重排错误。
- **可回滚事务语义不回退**：`noRollbackHandlerStarted` 只在 policy none 时置位；RR-48 冲突回滚重排、undo 锁超时重排均通过。
- **快池不阻塞**：只增加布尔字段读写与错误路径上的一次 `IsRemoved` 读取；没有新增等待。
- **同 ID 顺序**：不重排的消息直接回复并释放派发位置，与其他失败回复相同。

## 未验证项 / 风险

- 生产上 DataEngine 驱逐 / RR-39 卸载与 Cast 等锁的竞态只用受控 mutex 复现，未在真实 WAL + Mongo 环境构造。
- 性能：只增加一个布尔字段的写与读，未单独跑基准。
- 附带发现（范围外，未改）：RR-48 的 `TestHandlerCreateCrossOrderResolvesWithoutDeadlock` 在基线 `62fdbe6` 上即偶发失败
