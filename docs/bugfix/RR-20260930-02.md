# RR-20260930-02 · protocol 旧产物退役与上层提交修复

原问题与修前 CLI 证据见 [Codegen 第一轮问题](../bug/REVIEW-2026-09-30-codegen-01.md)。实施基线 Core `f6566d4e0a9026484d66d78f53036bbd9bc5f3fc`；本轮修复后状态：**原触发已修复，声明场景已验证；未发布**。

`codegen/internal/protocol/run.go` 在定义集合为空时，现在退役可识别的 proto、PB、msgid、JSON manifest、bind、robot 与 handler 文件；若配置了 player bootstrap，则先验证模块与空 bootstrap 内容，再退役旧输出，最后写入不引用旧 handler 的 bootstrap。定义仍非空时，也会按当前 handler 域集合清理消失的域。`retire.go` 只删除自身 Go 生成头、带 `roost:source=go_def` 的默认 proto、符合旧生成 manifest 结构的 JSON，以及指定目录下带生成头的 `protocol_gen.go`；无法识别的手写文件保留。

仅修 CLI 不足以让 `roost generate` 真正提交删除：原暂存规划和 `--check` 漏看没有 `Code generated` 注释的 `protocol.proto` / manifest。现通过同一 `IsGeneratedArtifact` 识别规则，让 `codegen/internal/roost/generate.go` 的快照、`project.go` 的暂存差异/删除都纳入这两项默认产物。修前新增 `TestRunRetiresOutputsWhenLastDefinitionIsRemoved` 失败：旧 `protocol.proto` 仍存在；修后 CLI、带 bootstrap、单域 handler 退役、手写文件保护、失败前置验证、`SyncProject` 实际提交和 `generate --check` 漂移门均通过。

兼容边界：删除最后定义会让旧消息 ID、类型及 manifest 消失，旧客户端或手写 import 必须按业务版本窗口处理；本修复不替用户迁移线上协议。默认 `roost` 规划识别默认 proto/manifest 路径；直接 CLI 自定义输出路径由 generator 自身清理，但不自动扩展上层项目规划。原始字节/标记被人工改成无法确认归属时保守保留。直接 CLI 的多文件删除不是跨文件原子操作；`roost` 同步有暂存与逐文件回滚保护，强杀/磁盘故障仍未验。
