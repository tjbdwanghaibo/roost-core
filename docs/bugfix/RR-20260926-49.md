# RR-20260926-49 修复：越过提交点的事务一律不重新准入；提交回调 panic 以 %w 保留原因链

问题：[RR-20260926-49](../bug/RR-20260926-49.md)（替身探针见 [REPRO-2026-09-26-05 §2](../bug/REPRO-2026-09-26-05.md)）。
日期 2026-09-26；实施基线本地 main `3e26f91`，建立在同批 [RR-20260926-48](RR-20260926-48.md)（`49f99e0`）之上。
状态：已修复、本地验证通过，已本地提交，未推送 / 未发布。方向按维护者批准的修复约束：已持久提交（Msg 显式已提交状态或错误带
`ErrAfterCommitFailed`）的事务一律不重新准入；提交回调 panic 用 `%w` 保留错误链。

## 根因（基线源码核对）

- `nest/nest_dispatch.go` `dispatchNest` 回复前依次调用 `requeuePendingEntityGroupTransition`、`requeueTransientDispatch`
  （`nest/group_transition.go`），后者只看错误链里有没有 `ErrLockTimeout` / `ErrEntityLockGroupChanged`，不看事务是否已经提交。
  已提交事务的收尾错误（Remote 批次 Close、release hook、AfterCommit 回调）只要链上带锁超时，就会以克隆消息重新准入，
  handler 再执行一次——已提交的业务被重复执行。
- 纯本地事务没有任何“已提交”的显式状态：RR-46 的 `remoteConfirmed` 只在 Remote 批次确认后置位。
- `nest/rollback.go` `runCommitCallback` 把 panic 值以 `%v` 格式化，原因的 `errors.Is` 链丢失（也因此让 §2 之外的提交回调错误
  “碰巧”不触发重排）。

## 决策与实现

- `Msg` 新增 `txInFlight`、`txAdmitted`（`nest/msg.go`）。`invokeWithTransaction` 进入时若消息没有在途事务，就认定当前事务是
  这条消息**自己的**事务（handler 内嵌套的 `RunIsolatedTransaction` 看到 `txInFlight` 而不认领），`RollbackTx.dispatch` 指向消息。
- 越过提交点即 `markTransactionAdmitted`：
  - strict / memory 持久化的事务路径：`commitDurable` 中 `durableCommit` 成功之后（本地提交点）；
  - pipelined：`Enqueue` 返回 ticket 之后（记录已进入 WAL，无论随后准入是否成功、ticket 是否结果未知）；
  - memory 快路径：handler 成功、`SyncMutation.Admit()` 之后。
- `Msg.transactionPastCommitPoint(err)`：`txAdmitted`、`remoteCommitted`（Remote 本地已持久提交）、`remoteIndeterminate`，或错误链带
  `ErrAfterCommitFailed` / `ErrCommitIndeterminate`。为真时 `dispatchNest` 不调用两个重排函数，原样回复错误。
  “结果不确定”也不重排：WAL 里可能已有这条事务，且实例已被 fence。
- `runCommitCallback`：panic 值是 `error` 时 `fmt.Errorf("%w: %w", ErrAfterCommitFailed, cause)`，否则保持 `%v`。

未采用：只在 `requeueTransientDispatch` 里判断 `ErrAfterCommitFailed`——纯本地提交后的 release hook 错误目前不带该哨兵
（[RR-20260926-53](RR-20260926-53.md) 另修），且约束要求 Msg 的显式状态；把标志放在 `commitDurable` 的 `msg` 参数上——那是
`currentNestDispatchMsg()`，嵌套独立事务提交时会误标外层消息。

## 文件与行为

- `nest/msg.go`：`txInFlight` / `txAdmitted`、`markTransactionAdmitted`、`transactionPastCommitPoint`。
- `nest/execution.go`：认领自身事务，三处提交点置位。
- `nest/rollback.go`：`RollbackTx.dispatch`；`runCommitCallback` 的 `%w`。
- `nest/nest_dispatch.go`：重排前检查提交点。
- 回归 `nest/committed_requeue_promises_test.go`。

## 兼容性

- 行为变化：已越过提交点的事务，回复错误链里即使有 `ErrLockTimeout` / `ErrEntityLockGroupChanged` / `ErrEntityGroupTransitionPending`，
  也直接回复调用方，不再自动重排（此前会把已提交业务再执行，最多 400 次）。未提交的锁超时（含 RR-48 的创建锁冲突）照旧重排。
- 提交回调 panic 的错误现在还满足 `errors.Is(err, <panic 的 error 值>)`，错误文本不变。
- handler 内 `RunIsolatedTransaction` 已持久提交、外层事务随后以锁超时失败时，外层仍会重排（未改变；见未验证项）。

- 保持性：RR-48 的 `TestHandlerCreateThenHigherGroupCastDoesNotFormCycle` 等依赖未提交锁超时照旧重排，全部通过。

## 对抗性自查

- **回滚后重排不重复执行已提交内容**：重排的唯一入口（`dispatchNest` 末尾两个函数）现在先问提交点；提交点在持久提交 / WAL 接纳 /
  memory 准入之后立即置位，早于释放锁、release hook、AfterCommit 与回复，所以这些阶段的任何错误都不会让消息重排。未提交的失败
  （RR-48 冲突、handler 报错、提交被明确拒绝）照旧可以重排。
- **RR-35 提交边界 / 撤销发布**：未改；撤销只发生在未越过提交点的回滚路径。
- **同 ID 顺序与内部续行准入资格**：不重排的消息直接回复，释放它在派发队列上的位置，与其他失败回复相同；续行通道未改。
- **快池不阻塞**：只增加布尔字段读写。
- **嵌套事务**：`txInFlight` 保证 handler 内嵌套的 `RunIsolatedTransaction` 不认领外层消息；broadcast 每个目标的事务依次认领、释放。

## 未验证项 / 风险

- handler 内 `RunIsolatedTransaction` 已持久提交、外层事务随后以锁超时失败时仍会重排，独立事务会再执行一次；本次约束只覆盖消息自身
  的事务，未改。
- 真实 remoteentity Close、快池续行目前仍不产生锁超时类错误（登记时的判断），回归使用替身批次与业务 release hook。
