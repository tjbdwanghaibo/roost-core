## 根因（基线行号）

RR-70 的记录生命周期是“撤销时写入 `retracted` → 新 subject 登记时 `releaseRetracted`（`sync/entitysync/policy_queue.go:130`，由
`manager.go:281` 调用）移入 `resubmits` → 下一次 Flush 政策阶段 `deliverResubmits`（`:148`）取出交付”。第二次撤销发生在登记之后、交付之前时：

1. `recordRetractedLocked`（`:108`）只遍历当时的 `subj.subscribers`。政策还没重说，里面没有政策来源的订阅（只有让 `SubjectAwaitsReload` 为真的
   非政策订阅者），一条也不记；已在 `resubmits` 里的记录不动。
2. 下一次 Flush 交付这些记录，subject 已退役或已被忘掉：`Group.resubmit`（`policy/group.go:84`）、`Direct.resubmit`（`policy/direct.go:77`）的
   Subscribe 得到 `ErrSubjectNotRegistered` / `ErrSubjectRetiring`，记 Warn 后放弃——记录已被取出，第三次登记时 `retracted` 为空，这对订阅永久丢失。
   Interest 把被拒绝的 pair 放进重试表，下一次 `Apply` 重说，所以能恢复。
3. 同类窗口还有两处：`releaseRetracted` 在 `register` 放开 `m.mu` 之后执行、不检查 subject 状态，登记与交还之间 subject 被再次撤销时记录照样进队列；
   `deliverResubmits` 取出队列后、政策的 Subscribe 落下之前 subject 被撤销，取出的记录同样丢失。

## 修复（按 RR 主记录的修复约束）

`sync/entitysync/policy_queue.go`、`manager.go`：

- **再次撤销时移回**：`recordRetractedLocked`（在 `subj.mu` 内、退役清空来源之前）除当前订阅外，把 `resubmits` 里同 ID 的排队项**移回**撤销表；
  `deliverResubmits` 取出、回调尚未返回的项放在新增的 `Manager.delivering`（仍计入 `resubmitEntries`），撤销时**复制**回撤销表——政策的 Subscribe
  可能落在本次退役之后而被拒绝，也可能已落下（那样它就在当前订阅里，去重后只一条）。
- **上界**：新增 `addRetractedLocked` 合并时按（来源, 会话）去重，同一 subject 下每对只留一条；条数仍不超过政策持有、尚未释放的 pair。来源自己释放
  （`dropRetracted`）与业务注销（`dropRetractedSubject`）同时从 `delivering` 删除，释放过的 pair 不会经复制复活。
- **交付时 subject 未登记**：`releaseRetracted` 改收 `*subject`，在该 subject 的 `subj.mu` 内确认未退役再移动；已退役（被再次撤销：记录已并入撤销表，
  留给下一次登记；被业务注销：记录已清除）则不交还。撤销与注销也在 `subj.mu` 内处理记录，所以进入 `resubmits` 的记录在被取出之前 subject 一直是活的，
  交付时 subject 未登记只可能发生在取出之后，由上面的 `delivering` 复制覆盖。没有在 `deliverResubmits` 里再按 subject 查表：那需要在叶子锁
  `resubmitMu` 内取 `m.mu`，且查到“不在表里”时分不清是撤销（应保留）还是业务注销（应丢弃）。
- **锁序不变**：新增的只有 `subj.mu → resubmitMu`（RR-70 已有的方向），`resubmitMu` 仍是叶子；回调仍只在 Flush 政策阶段、不持 Manager 锁时执行，
  政策锁 → Manager 锁的顺序不变；Register 路径不回调政策（`releaseRetracted` 只移动记录并 `WakeSync`）。`Group.AddSubject` 持 `g.mu` 调 Register 时
  `releaseRetracted` 取的是新 subject 的 `subj.mu`，与既有 `g.mu → subj.mu` 同向。

政策侧（`policy/group.go`、`direct.go`、`interest.go`）不改：它们的 resubmit 本来就按自己的当前判定重新订阅，问题只在 Manager 把记录交给了缺席的 subject。

未采用：政策在 Subscribe 被拒绝（`ErrSubjectNotRegistered` / `ErrSubjectRetiring`）时自己保留、等下一次交还——政策不知道何时会有下一次登记，只能靠
Manager 再交还一次，而 Manager 此时已没有记录；让 Group / Direct 也建重试表——实体永不回来时每次 Apply 都被拒绝，RR-70 已因同一理由否决。

## 文件与行为

- `sync/entitysync/policy_queue.go`：`recordRetractedLocked` 移回 / 复制，`addRetractedLocked` 去重，`releaseRetracted(*subject)` 在 `subj.mu` 内检查，
  `deliverResubmits` 维护 `delivering`，`dropRetracted` / `dropRetractedSubject` / `clearRetracted` 同步清理 `delivering`；生命周期注释。
- `sync/entitysync/manager.go`：`delivering` 字段；`register` 把新 subject 指针交给 `releaseRetracted`。
- 文档：`sync/README.md`、`docs/USER_GUIDE.md` 各补一句。
- 回归：

## 兼容性

- 无导出 API、配置、协议或持久格式变化。
- 行为变化：RR-70 的重新提交在交付前（或交付中）遇到再次撤销时不再丢失，下一次登记后交还；同一 pair 不会被交还两次（此前可能两条）。
  自建政策的 resubmit 回调可能对同一 pair 在两次登记后各收到一次——与 RR-70 的“按政策当前判定重说”一致，重复 Subscribe 同来源同视图是空操作。

## 未验证项 / 风险

- “登记与 `releaseRetracted` 之间被撤销”的窗口没有确定性回归（`register` 在放开 `m.mu` 与交还之间没有测试缝）；由 `subj.mu` 内检查的构造保证，
  并由交付中被撤销的回归覆盖相邻的取出后窗口。
- 实体被撤销后永不重新登记、政策一直持有 pair 时记录一直保留（RR-70 既有边界，条数与政策持有的 pair 同量级，本修复去重后不会更多）。
- 会话关闭不清理撤销记录（RR-70 审计疑点，未改）；同 ID 重开会话后重新登记，政策仍按自己的判定重说——Direct 的绑定表随会话关闭清理见 RR-79。
- 正式生成工程里没有构造“两次卸载撤销”的端到端场景；以 entitysync / policy 包内真实 Manager 与三种政策验证。
