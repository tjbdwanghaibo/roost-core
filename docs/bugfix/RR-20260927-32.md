## 决策

### 第 1 项：在 `rejectCommit` 统一包

- `rejectCommit` 开头：原因还不带 `ErrCommitRejected` 时 `errors.Join(ErrCommitRejected, cause)`，再回滚。它的三个调用点（Remote 定稿拒绝、`commitDurable`、`commitPipelined`
  的非“结果未知”分支）都在写任何持久记录之前：`durableCommit` / `pipelinedEnqueue` 里越过 committer 之后唯一的失败来源是 `acceptPersistence`，它恒返回
  `ErrCommitIndeterminate`，走 abandon 分支，到不了这里。committer 已包的不重复包。
- 放在 nest 而不是 remoteentity：`FinalizeLocked` 是 `entity.RemoteWriteBatch` 接口方法，自定义 Remote 实现同样会在这里拒绝；在 Nest 的唯一拒绝出口包一次覆盖全部实现。
- 嵌套 `RunIsolatedTransaction` 的拒绝（包括第 9 行 `ErrNestedTransactionRollbackConflict`）同样带上它；判别表“第一个命中的行”仍是第 9 行，不变。
- 未包的：handler 执行之前的准入 / 配置失败（`ErrPipelinedCommitterRequired`、`ErrPipelinedNotAllowed`、声明目标捕获失败、`ErrNestedTransactionInRemoteMessage` 等，
  handler 未执行或事务未开始，不是“提交被拒”），handler 自己返回的错误。

**调用方核对**（只增加一个 `errors.Is` 命中，确认没有调用方据此换分支）：

- `git grep ErrCommitRejected`：生产代码只有定义与三处包装；`dataengine/lease_fence.go:23`、`SAGA.md:91` 是注释 / 文档（“`ErrFencedEntityPending` 同时带它”，仍成立）。
  测试里全是正向断言（`nest` 5 处、`codegen/.../fenced_step_test.go:224`、`saga/fenced_entity_promises_test.go:33`、`remoteentity/reply_sentinel_table_test.go`）。
- 其余哨兵的分支：`errors.Join` 保留原因链上全部 `errors.Is` / `errors.As`。nest 内据错误分支的地方（`invokeHandlerTransaction` 的 `ErrCommitIndeterminate` → Fence、
  `requeueAllowed` / `isRequeueableDispatchError`、`transactionPastCommitPoint`、`dispatchNest` 的 `ErrAfterCommitFailed` / `ErrNestedTransactionCommitted` 包装）都用
  `errors.Is`，结果不变；拒绝链上不会出现 `ErrCommitIndeterminate`（它先被分流）。
- 按身份 / 文本比较：`git grep -nE '(err|Err)[A-Za-z]* (==|!=) (nest\.|corenest\.)?Err'`（非测试）只命中 `skill/` 自己的技能错误；`errors.Unwrap(` 非测试无命中；
  `strings.Contains(err.Error()…)` 非测试命中在 codegen 生成模板（直接调 `BuildRemoteCommitLocked`，不经 Nest）与 robot action，不涉及 Nest 回复。
- 回复文本多了一行 `nest: transaction commit rejected` 前缀（`errors.Join` 的换行格式，与 committer 拒绝一致）；`./nest ./kit/... ./remoteentity ./dataengine/... ./saga/... ./skill/...`
  全部测试通过，无按文本断言的用例受影响。

### 第 2 项：RR-06 在 RollbackNone 下按实际行为写（不改成真正回滚）

二选一选“按实际行为写”。理由（RR-64 / 73 的 memory 语义）：RollbackNone 的 handler 不登记快照，框架从设计上就不撤销它的内存修改，失败时不重排、由业务按幂等性决定是否重试
（第 5、6 行）。要让 fence 拒绝“真正回滚”，只能给 RollbackNone 事务补快照——这等于把它变成 state / undo 事务，违背 memory handler 的定位，也只对这一种拒绝生效
（同一 handler 的 Remote 定稿拒绝、committer 拒绝同样不撤销）。所以统一写成：可回滚事务已回滚；不能回滚的 handler 内存修改不撤销，按第 5 行的语义处理。
回归 `fenced/memory_remote_with_effect` 与 `finalize_refused/memory_remote` 钉住“值仍是 77、committer 0 次、Remote 批次 Abort”。

### 第 3 项：判别表第 1 行补一句

实跑核对后写两种形态：外层有要持久的记录时，它在交给 committer 之前被拒，回复是第 4 行 `ErrNestedTransactionCommitted` + `ErrNestFenced` + `ErrCommitRejected`
（RR-06 回归 `TestOuterCommitAfterNestedAcceptFailureIsRefusedBeforeWAL` 已补断言 `ErrCommitRejected`）；外层没有要持久的记录（含 memory handler）时**回复是成功**，只能从之后的请求
得到 `ErrNestFenced`（探针：state/strict 外层不写持久内容、嵌套写别的 DAO 且 committer 返回 `ErrCommitIndeterminate` → `reply=ok err=<nil> fence=true`；memory 外层同样）。
后一种形态清单没有提到，按实际行为写进第 1 行。

## 兜底行：反例（未加）

清单写法是“不命中以上任何一行：未提交”。反例：**带 Remote 批次的 strict 消息，本地 WAL 已持久提交后 Remote 被明确拒绝**，回复不命中 1～12 行任何一行，但本地部分已提交
（RR-20260926-58：同一事务里已持久提交的本地实体照常生效）。`finishRemoteWriteBatch` 的 `m.remoteCommitted` 分支 `batch.Commit` 返回 `entity.ErrRemoteRejected`，
`remoteConfirmed` 不置位，所以不带 `ErrAfterCommitFailed`（RR-46 有意排除拒绝），也不带 `ErrCommitRejected`（不经 `rejectCommit`）。

探针（`remoteentity`，真实 Nest + 正式 Remote Manager，`newReloadFixture` + `boundedConfirmManager`：strict、本地 committer 立即持久、等待开始前让存储 `reject` 并触发
`ApplyRemoteCommits`；未提交，保留在 scratchpad `r8b13-probes/zz_probe_postcommit_reject_test.go`）：

```text
PROBE reply=<nil> err=nest: finish remote write batch: remote entity: write rejected before commit: remote entity: state version conflict first-row=0 sentinels=[]
```

所以“其余：未提交”对这类回复是错的；按 preamble “推荐有反例就停下说明”，兜底行没有加。可选方向（需要主会话 / 维护者定）：

- (a) 给“本地已提交、Remote 被明确拒绝”的回复加一个哨兵（新增导出错误，属 API 增加），兜底行就能写“未提交”；
- (b) 兜底行按实际写成“消息自己的事务未提交，**例外**：带 Remote 批次的消息在本地提交之后 Remote 被明确拒绝，本地部分已提交（回复只带 `entity.ErrRemoteRejected` 等 Remote 错误，
  与准备阶段的 Remote 拒绝无法用哨兵区分）”——只改文档，但这一行无法按 `errors.Is` 判定。
