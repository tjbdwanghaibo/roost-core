# RR-20261001-09：activity sweep 回收无 Intent 的 legacy Opening；坏 Intent 跳过并记一次日志，不再让整组 `AdvanceExpired` 每 tick 失败

问题：[docs/bug/RR-20261001-09.md](../bug/RR-20261001-09.md)（来源 [B 线 service 修复复审 §4.4](../review/REVIEW-2026-10-01-bline-audit-service-2.md)，W-2026-10-01-04 维护者拍板）。等级 P3。基线 main `c38e0b08`（含 RR-20261001-05 的 `551d1e36`）。状态：已修复、已验证（Memory + 隔离真实 Redis），已提交，未推送、未发版。

## 根因（到行，main `c38e0b08`）

`kit/service/global/activity/service.go:799`（`AdvanceExpired` 的 Opening 循环）：`if entry.Intent == nil || nowUnix-entry.AdmittedAtUnix < openingGraceUnix { continue }`——没有 Intent 的条目无条件跳过，而 `types.go:863` `Window.pending()` 把 `Opening` 全部计入 `MaxPendingActivities`，所以升级前已孤儿化的 legacy 条目永久占名额；旧版（`4b0837d7` 之前）在 `OpeningGrace` 后把它 `dropOpening`。同一循环 `:802-807`：Intent 的 Key 不符 / 非 Pending / `validateExpectedGames` 失败时 `return nil, err`，`:808-811` `Activities.Create` 失败也 `return nil, err`——都发生在 due 活动的 `completeExpired`、`ensureDispatches`、`retireFromWindow` 之前，所以该 group 其他到期活动一个都推进不了；`server_run.go` 的 `sweepGroup` 只记 `sweep.advance_failed` 并等下一 tick，下一 tick 卡在同一条上。`ScanAfter` 轮转只在 `pending() > MaxPendingActivities` 的超容量窗口里发生（`:739`），正常窗口没有任何“绕过去”的机制。RR-20260914-02 残余（`4b0837d7`，SERVICE-BUGFIX-2026-09-29-05）引入。

## 决策与未采用方案

三类“帮不了”的 Opening 条目各自处理，哪一类都不再挡住同组其他活动：

1. **无 Intent（legacy）→ 过 `OpeningGrace` 且活动不存在则回收名额。** 理由：这种条目只能由计划字段出现之前的 build 写入，而 09-29 记录已定升级契约“全部 owner 升级并排空旧调用后再启用新流程；不支持混合旧 owner 写 Window”——写它的 opener 已排空，不会再有人确认它，sweep 也没有任何计划可以代为执行；留着只剩占名额。回收沿用旧规则（`AdmittedAtUnix + OpeningGrace`）和 U-0191 的世代守卫：`retireFromWindow` 的 CAS 里**只删 CAS 时仍然没有 Intent 的那一段**——快照与 CAS 之间若有同 key `OpenActivity` 补上了计划（`admitToWindow` 对 legacy 条目就是这么做的），名额归它，回收什么都不做。活动已存在（`exists`）的 legacy 条目与之前一样走 confirm，不受影响。grace 内不回收（同 key Open 仍能补计划）。
2. **Intent 畸形（Key 不符 / 非 Pending / expected 集合非法）→ 跳过、每 tick 计 `sweep.opening_intent_malformed`、日志只在状态变化时打一次，名额保留，不回收也不改写。** 为什么不回收：`OpenActivity` 写计划前做过同样校验，所以畸形只能是本包之外改了存储（数据损坏 / 外部写）；原 opener 自己那次 `Activities.Create`（用的是它当时拿到的计划）仍可能迟到落库，名额一旦给出去，这条记录就成了“有活动、无窗口条目、永远没人 sweep”——正是 RR-20260914-02 堵住的洞。为什么不自动改写 / 不自动删：那是“自动删坏记录”，本 skill 明令不许；坏数据的处置属于运维（修 JSON 或删条目），修好后下一 tick 按正常计划创建并确认（回归钉住）。为什么只记一次：每 20s 一条 Warn 会淹没日志，而状态变化（出现 / 修好 / 被删）才是运维要看的；状态放 `Service.malformedOpening`（`Server` 是生成代码不能加字段），不进 Window 记录（避免每 tick 一次写）。有界扫描之外的 key 不动（没看到 ≠ 看到它好了）：清除条件是“这一 tick 扫到它且不再畸形”或“它已不在 Opening 里”。
3. **Intent 完好但 `Activities.Create` 持续失败 → 错误照旧上报，但在同组其余工作做完之后。** `TestSweepRetainsAndRecoversAnUnknownOpeningAfterGrace` 的契约（Create 结果未知、名额保留、错误上报、后端恢复后完成）不变；变的只是其他 due 活动不再陪它一起停。`sweepGroup` 收到错误仍计 `sweep.advance_failed` 并跳过本 tick 的派发半段——与之前一致。

`Activities.Get` 失败仍立刻返回（后端整体不可用，不是单条问题）。

**未采用：**

- 把畸形条目也回收——见上，会重开 RR-20260914-02 的洞。
- 给坏条目加 `Admin` 入口或在 Window 里打标记——P3，先给运维可见性（指标 + 一次性日志 + T 行）；Window 标记要每 tick 写一次或改持久格式，入口留给需要时再加。
- 同 key `OpenActivity` 用新计划覆盖畸形 Intent——改了“重试拿回已存计划”的不变量，而且现状下 `admitToWindow` 会把畸形计划原样交给 Create（见未验证项），不在本 RR 里碰。
- 让 Create 失败也“跳过不报”——会把后端故障藏进指标里（U-0120 反对的形态）。

## 兼容性

- **持久格式**：`Window` JSON 不变；没有新字段、无迁移。回收只删 `opening` 数组里的条目。
- **Go API**：公开签名不变；`retireFromWindow` 是包内私有。错误：`AdvanceExpired` 对畸形 Intent 不再返回错误——没有仓内调用方依赖它（`sweepGroup` 只记数打日志）。
- **行为收紧**：无。放宽的是“legacy 永久占名额”和“单条坏数据整组停”。CAS / 版本比较未改；`Store.Update` 回调先 `clone()`。
- **升级前提**（沿用 09-29 记录）：legacy 回收的安全性依赖“旧 owner 已排空”——若有旧 build 的 opener 仍在写 Window，它的迟到 Create 会在回收后遇到 `confirmWindow` 的 `ErrConflict`，活动记录存在但无窗口条目。这不是新风险（09-29 记录已声明不支持混跑），只是回收让它从“占名额”变成“无索引”；混跑本来就不被支持。
- 不上 bus、不加配置项；`OpeningGrace` 多了一个含义：legacy 条目的回收期限（与旧版相同）。

## 未验证项 / 风险

- 畸形 Intent 的修复路径只验证了“运维原地修好 JSON”；**没有**给 `admitToWindow` 加畸形校验——现状下同 key `OpenActivity` 会把存储里的畸形计划原样交给 `Activities.Create`（Key 不符时写出 Key 字段与存储 key 不一致的记录）。这是 RR-20260914-02 修法的既有路径，不在本 RR 范围；T-182 的处置写的是“修 / 删条目”，不是“再 Open 一次”。要不要在 `admitToWindow` 拒绝畸形存量计划，可作为 Wanted 候选。
- `malformedOpening` 只在本进程内存里，重启后同一条坏数据会再 Warn 一次（可接受：重启本身是状态变化）。
- 超容量窗口（`pending() > 256`）的轮转下，坏条目不在本批时既不计数也不清除，日志语义是“扫到它时”；未对 257+ 条目的窗口单独加回归。
- 没有 Redis Cluster 环境，`TestBugfix7Activity*Cluster*` 本轮未跑（与 RR-05 一致）。
