# RR-20260919-10：activity 的结果交付没有闭环（U-0257）

- 仓库：roost-core `versionstore`、roost-kit `service/global/activity`、roost-codegen `demo`
- 缺陷类：C4（两半各自成立，合起来不成立）
- 优先级：P1
- 相关：T-151；测试 `service/global/activity/owed_dispatch_promises_test.go`

## 问题

两半都缺，合起来是"奖励义务持久存在、却谁也交付不了"。

**服务端**：`Server.run` 的 sweep 从持久的 Delivering 索引找到 due dispatch，然后调 `AttemptDispatch`。
那个方法只是 CAS 增加 `Attempts`、设置下一次退避、把 payload 返回——而这一侧**没有任何传输**
（`trace_path` 的生产入向只有 `sweepGroup → run → Serve`）。于是 payload 被丢掉，尝试次数被花掉；
默认五次之后 dispatch 进 `DispatchExhausted`，游戏服一次都没收到。

**游戏端**：demo 的 runner 每次只构造"上一窗口"和"当前窗口"两个 activity id 去 `LookupDispatch`。
离线超过一个窗口，旧的 pending dispatch 就再也不会被查询——而 kit 的枚举能力（`DueDispatches`）
按 activity 组织，也没有经 RPC 暴露给游戏服。

## 根因

"谁交付"这个问题没有答案，两边都以为是对方。sweep 的名字（Attempt**Dispatch**）听起来像交付，
实际只是"领取一次尝试"；游戏那边没有"问问我被欠了什么"的入口，只能拿本地时钟去猜。

## 方案

- 采用：**拉取式闭环**，四处改动：
  1. **按 (组, 游戏服) 的 owed 索引**，与 dispatch 同一次 Redis 写（core 的 `RedisIndex.KeyOf`，
     本轮为此新增）。score 是下次值得取的时刻；终态（acked / exhausted）那一次写就退休条目。
  2. **`OwedDispatches(groupID, gameSID, limit)` 上 RPC**：游戏按批排空自己的欠单，不需要知道 activity id，
     也不需要假设自己离开了多久。路由按 group，与其它 activity 调用一致。
  3. **`AttemptDispatch` 从"服务自用"移到 RPC 上**：取走 payload 的人是游戏，所以尝试次数由它来花。
     这样"预算"度量的是**真的发生过的交付**，而不是一个循环空转的次数。它带调用方自己的 gameSID，
     与 `NotifyPhase` 同一个信任模型。
  4. **sweep 收回到本分**：推进过期、补建缺失 dispatch、退休终态、报指标；对等待超过 10 分钟的结果
     按 tick 报 `dispatch.stale`——没人来取的结果是运维要看见的事实。
- 没采用：服务端主动推送（bus / webhook）。那要求服务知道每个游戏服的可达地址与在线状态，
  正是 `global` 的租约在管的事；拉取让"我什么时候能处理"由游戏自己决定。
- 没采用：让 sweep 继续 attempt 但不算次数。那等于留着一个什么也不做的调用，下一个人还会以为它在交付。

## 改动

core `versionstore/redis_store.go`（`RedisIndex.KeyOf`、`IndexDueIn` / `IndexRemoveIn`）；
kit `service/global/activity`：`redis_store.go`（`RedisDispatches` + owed 索引 + `OwedDispatchKey`）、
`types.go`（`ParseDispatchKey`、`ErrUnsupported`）、`service.go`（`OwedDispatchIndex`、`Service.OwedDispatches`）、
`activity_rpc.go` + 重新生成的传输、`server_run.go`（sweep 不再 attempt，改报 stale）；
codegen demo `internal/service/game/activity.go`（按 owed 排空，不再猜两个窗口）。

## 证明

`TestAGameFindsWhatItIsOwedWithoutGuessingActivityIDs`：三个窗口在游戏离线期间完成，
它回来后一次拿到三条欠单，ack 掉一条剩两条。
`TestTheSweepDoesNotConsumeDeliveryAttempts`：修前红——五轮 sweep 之后 dispatch 是 `exhausted`、
`attempts=3`，游戏一次都没收到；修后仍是 `pending`、`attempts=0`，游戏回来第一次取是 attempt 1。
编码旧契约的两条测试（U-0192 的跨轮重发现、终态退休）改成断言新的不变量而不是删掉。
实跑（10 进程）：开窗 → 贡献 → `gm.activity.close` → phase reported → **4 秒内 settled paid=2**，
owed 索引在 ack 之后为空。

## 未做 / 边界

- **没有指标面板**：新增的 `dispatch.stale` 计数与既有的 attempt / exhausted 计数没有配 Grafana 图；
  审查建议的"游标滞后"也没有度量（当前实现没有游标，每次从最老一条开始读一批）。
- **并发 runner**：两个同 sid 的进程会互相抢 attempt。`global` 的租约正是防这件事的，
  但代码里没有强制"只有持租约者才能取"——那需要把 incarnation 带进 RPC，本轮没做。
- 老部署的既有 dispatch **不在 owed 索引里**（索引从这一版的写开始建立）。升级后要么等它们被下一次
  状态变更带进来，要么跑一次性回填（遍历 `<prefix>:disp:*`，把 pending 的 `ZADD` 进对应的 owed 集合）。
