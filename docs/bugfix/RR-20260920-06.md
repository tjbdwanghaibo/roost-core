# RR-20260920-06：被房间拒绝的 subscribe 永不重试（U-0267）

- 等级：P1
- 仓库 / 位置：roost-codegen `demo/game/scene/runtime/interest.go.tmpl`、`demo/game/scene/scene.go.tmpl`、
  `demo/internal/service/game/scene.go.tmpl`
- 审查记录：[REVIEW-2026-09-20-02](../bug/REVIEW-2026-09-20-02.md) · 复现附录 [REPRO-2026-09-20-02](../bug/REPRO-2026-09-20-02.md)
- 缺陷类：C5（静默吞错）

## 问题

兴趣系统产出订阅变更 → `Scene.applyChanges` 调 `room.Subscribe` → 协调器可能**拒绝**
（`ErrDurabilityDeferred`、`ErrRoomSubjectRetiring`、两个容量上限、下游传输错误）。
拒绝只写一条 `slog.Warn` 就被丢掉，那个观察者从此永久收不到那个 subject 的状态。

## 根因

三行代码合起来，任何一行单看都是对的：

```go
// interest.go：产出变更之前就乐观置位
if !hold.subscribed {
    hold.subscribed = true
    return scene.SubscriptionChange{…, Subscribe: true}, true
}
return s.rebandLocked(key, hold)

// interest.go：重发只在 band 变化时发生
if band == hold.band || !hold.subscribed {
    return scene.SubscriptionChange{}, false
}

// scene.go：失败只记日志
slog.Warn("scene: subscribe", …)
```

`applyChanges` 上方的注释写着 "the pair stays claimed in the interest system, so the next tick that
touches it tries again"——**这句话是假的**，两个站着不动、同在 band 0 的玩家永远不会 reband。

还有第四件事，是本轮实现时才看清的：`Tick` 只把 source 的事件折进聚合，**没有事件就没有变更**。
所以"把 `hold.subscribed` 清掉等下一 tick 自己重来"也不成立——没有任何东西会再提起这个 pair。
重试必须是兴趣系统里一份显式的待办。

## 方案选择

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 成功才置位（`SubscribeConfirmed`） | 语义最强，但要求调用方汇报**每一次成功**，happy path 多一次加锁 | 未采用 |
| 只清 `hold.subscribed` | 一行改动，但 `Tick` 不产生无事件的变更，清了也没人再提 | 不成立 |
| 乐观置位 + 失败回报 + 重试队列 | 只在失败路径上多做事，happy path 逐字不变 | **采用** |

`SubscribeFailed(observer, subject)` 清掉乐观标记并把 pair 排进 `retry`；`Tick` 在排空 source 之后
排空这条队列。队列的上界落在写入口：只为 `held` 里存在、且尚未排队的 pair 追加
（"held 的 pair 一定是 subscribed，除非它正在排队"，于是这个判据就是精确的去重），
每次排空整体取走，因此任一时刻至多 `len(held)` 条。

容量类拒绝**不**终止重试。审查建议过"容量类拒绝不进入无限重试"，这里没有照做：
把容量拒绝的 pair 丢掉，得到的正是本条要修的缺陷——一个应该存在的订阅不存在、而且没有人会再问。
房间满是暂态，有人离开就有位置。真正要避免的是**刷屏**，所以 `SubscriptionChange` 多了一个
`Retry` 标记：首次拒绝 `Warn`，重复拒绝降到 `Debug`。重试频率本身受 tick 约束，而 demo 的 tick 是
事件驱动的（Join / Moved / Leave / Show / Hide / SetTeam）。

## 改动

- `demo/game/scene/scene.go.tmpl`：`Interest` 接口加 `SubscribeFailed`；`SubscriptionChange` 加 `Retry`。
- `demo/game/scene/runtime/interest.go.tmpl`：`retry` 队列、`SubscribeFailed`、`drainRetriesLocked`，
  `Tick` 末尾排空，`Stop` 清空；乐观置位那一处补上"为什么乐观"的注释。
- `demo/internal/service/game/scene.go.tmpl`：`applyChanges` 取一次 `Interest`，失败时回报；
  按 `Retry` 分两级日志；把那句不成立的注释换成事实。

## 未做 / 边界

- **空场景不重试**：demo 没有场景级定时 tick，重试搭的是下一次场景事件的便车。任何人移动都会排空
  队列（`Moved` 每次移动都 Tick），但一个完全静止的场景不会。要做成时间驱动需要给场景加一条
  tick 循环，那是另一个单元。
- **不区分可重试与终局**：见上，故意的。若将来 `room` 给出"这个 pair 永远不行"的错误（而不是容量），
  再在 `applyChanges` 里分流。
- **只改了 demo 模板**：`room` / `entitysync` 侧的拒绝语义没有动。框架侧的契约是"拒绝要可判别"，
  这一条已经成立（`ErrDurabilityDeferred` 等都是命名错误）。
- 审查提出的"16 个观察者同场景时没有 pair 停在已标记未订阅"没有做成自动化用例：它需要一次 16 机器人
  实跑，本轮用确定性的"组队先于进场"覆盖了同一条因果。
