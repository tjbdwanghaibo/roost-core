## 复核后的补修（2026-09-26）

对应[复核残留](../bug/RR-20260926-05.md#复核后的补修2026-09-26)。基线 main `87d9499` + RR-04 补修 `2b770f6`；状态：已修复、已验证，本地提交，未 push。

### 根因

Push 按会话 ID 顺序（`87d9499` `flush.go:258-265`），`commitSnapshotAttempts` 按计划顺序给每个已尝试会话推进游标（`snapshot_budget.go:338`）。游标轮转后两者不一致，RetryLater 中断时游标会停在“ID 更小但计划更靠后”的已尝试会话上，越过计划内未尝试的会话。

### 方案（两处同时改）

- **Push 顺序跟随计划**：`snapshotPlan.admissionOrder` 让本批有冷创建计费的会话按计划中首次出现的顺序先 Push，其余会话仍按 ID 顺序（`flush.go` 在 `scheduleSnapshots` 之后取用）。单类别时，被 RetryLater/取消打断后实际尝试的会话恰好是计划前缀，计费与游标一致。
- **游标只推进到按计划顺序的实际尝试前缀**：`commitSnapshotAttempts` 遇到仍然有效却未被尝试的会话就停止推进游标和下一类别，其后已尝试的会话照常计费（“一旦尝试即消费本批冷额度”的既有规则不变），但不越过前面的未尝试者。已失效的会话（编码失败被关闭、Close、Hold 替换）不再参与轮转，可以越过。这一条覆盖同一会话同时有新入场与恢复请求、Push 顺序无法与两个类别都一致的情况。

取舍：跨类别时排在未尝试者之后、已经尝试过的会话已被计费，但下一次计划仍可能先轮到它一次（重复一个轮次的机会），换取“不越过未尝试者”；不做逐帧退款。

涉及文件：`sync/entitysync/snapshot_budget.go`、`flush.go`；回归：`snapshot_attempt_test.go`。无公开 API、协议或持久格式变化；Push 在会话间的顺序由“全按 ID”变为“冷创建计费会话按计划顺序在前”，各会话内部帧序和交付语义不变。

### 回归

- `TestSnapshotRetryWithRotatedCursorDoesNotSkipUnattempted`：游标从中间开始、轮转越过末尾。on_change（MaxObjects=3，游标 2，计划 3→4→1，会话 3 RetryLater）与 periodic（MaxObjects=2，游标 3，计划 4→1，会话 1 RetryLater）；断言 on_change 下计费会话与实际尝试会话相同，且第二次 Flush 后会话 4 已持有对象。修后输出 `attempted=[3] windowSessions=map[3:1] cursor=[3 0]`、`second flush delivered=[1 4]`；periodic `attempted=[4 1]`、`delivered=[2 3 4]`。
- `TestSnapshotCursorStopsBeforeUnattemptedAcrossClasses`：恢复 s2 → 新入场 s1 → 新入场 s2，s2 RetryLater；断言 Push 顺序为计划顺序、新入场游标不越过 s1。修后 `attempted=[2] windowSessions=map[2:2] cursor=[0 2]`，同窗口第二次 Flush 交付 s1。
- 修前红、负对照见问题记录；既有 `TestSnapshotRetryOnlyChargesAttemptedSessions`、`TestSnapshotBudgetDoesNotChargeUnattemptedSessions`、`TestSnapshotAttemptBudgetPreservesSuccessfulFramePrefix`、`recovery_fairness_test.go`、`snapshot_requests_test.go` 保持通过。

## 后续验证（2026-09-27）

来源：[OPEN-ITEMS B37](../review/OPEN-ITEMS-2026-09-27.md)（上文“持续 RetryLater 时会话间公平性只按本条规则推理”）。基线 main `d4234c9`，分支 `fix-r7-sync`。
图谱说明：codebase-memory 图谱已过期（09-26），结论来自源码与实跑。结论：**无缺陷，收为回归。**

`sync/entitysync/snapshot_retry_progress_test.go` `TestEverySessionIsDeliveredUnderPersistentRetryLater`：6 个会话各有一个冷创建，`MaxObjects=2`，
传输在**每个窗口**只接下第一帧、之后回 `ErrRetryLater`，最低 ID 的会话每个窗口还新增一个小的冷对象与其余会话竞争；periodic（每次 Flush 一个窗口）
与 on_change（窗口起点前移一个 Interval 确定性轮转，不 sleep）各跑一遍，断言每个会话在 24 个窗口（会话数 × 4）内收到自己的冷创建。实测两种模式
都在第 7 个窗口前全部交付（首次交付窗口 `map[1:1 2:2 3:5 4:3 5:7 6:4]`，6 个窗口以 RetryLater 结束）。

负对照：临时去掉 `snapshot_budget.go:400` 的游标推进（`m.snapshotCursor[candidate.class] = candidate.sessionID`），两种模式都红：

```text

    snapshot_retry_progress_test.go:88: sessions [2 3 4 5 6] never received their cold create within 24 windows of persistent RetryLater (delivered=map[1:1])
```
