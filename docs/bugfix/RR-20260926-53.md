# RR-20260926-53 修复：纯本地事务提交后的释放 / 回调错误同样带 ErrAfterCommitFailed

问题：[RR-20260926-53](../bug/RR-20260926-53.md)（探针见 [REPRO-2026-09-26-05 §2b](../bug/REPRO-2026-09-26-05.md)）。
日期 2026-09-26；实施基线本地 main `3e26f91`，建立在同批 [RR-48](RR-20260926-48.md)（`49f99e0`）、[RR-49](RR-20260926-49.md)（`c162b93`）之上。
状态：已修复、本地验证通过，已本地提交，未推送 / 未发布。方向按维护者批准的修复约束：本地持久提交成功后发生的释放 / 回调错误同样包
`ErrAfterCommitFailed`（保留原因链）；未提交路径不带；与 RR-49 一起保证已提交事务不被重排。

## 根因

RR-46 只在 Remote 批次确认后置 `Msg.remoteConfirmed`，`dispatchNest` 只凭它包哨兵。纯本地事务（strict、memory、pipelined）没有对应状态：
strict 持久提交后 release hook panic 经 `runNestLogic` recover 成普通错误，回复 `release hook failed`，调用方无法区分“已提交但收尾失败”
与“未提交”。pipelined 由完成池回复的路径（`nest/pipelined_completion.go` `complete`）把释放错误原样回复，同样没有哨兵。

## 决策与实现

- `Msg.txCommitted`（`nest/msg.go`）：本条消息自己的事务已确定提交。置位点与 RR-49 的提交点相同，只是 pipelined 要等 ticket 持久
  （或记录为空）才置位；ticket 结果未知只有 `txAdmitted`（不重排），没有 `txCommitted`（不带哨兵）：
  - strict / memory 持久化的事务路径：`commitDurable` 持久提交成功后；
  - memory 快路径：handler 成功、`Admit` 后（内存提交就是这个模式的提交点，与 AfterCommit 回调 panic 已带同一哨兵一致）；
  - pipelined 无完成池（inline）：ticket 成功后、`tx.commit(true)` 前。
- `Msg.replyAfterCommit()`：带 Remote 批次的消息（`remoteCommitted`）仍只看 `remoteConfirmed`——本地已提交而 Remote 确认未知 / 被拒绝
  不是“已提交”（RR-46 / RR-37）；其余看 `txCommitted`。`dispatchNest` 改用它决定是否 `fmt.Errorf("%w: %w", ErrAfterCommitFailed, err)`。
- 完成池回复（queued / 队列饱和降级）：ticket 成功后 `tx.commit(true)` 与释放错误合并得到的错误，没有哨兵时同样用 `%w` 包上。
  ticket 失败（结果未知）分支不变。

## 兼容性

- 行为变化：纯本地事务提交后 release hook panic、pipelined 释放失败（`ErrEntityReleaseFailed`）、预加载引用释放失败等回复，现在满足
  `errors.Is(err, nest.ErrAfterCommitFailed)`，错误文本多前缀 `nest: transaction committed but after-commit work failed: `；原因链不变。
  memory 快路径 handler 成功后的 release hook 失败同样带哨兵。
- 未提交路径（handler 报错、panic、提交被明确拒绝、pipelined Enqueue 拒绝）与结果未知（strict `ErrCommitIndeterminate`、pipelined ticket
  失败、Remote 确认未知）不带哨兵。
- 按错误文本匹配的调用方需要改为 `errors.Is`。

## 对抗性自查

- **已提交 / 未提交的判定来自显式状态**：哨兵只由 `txCommitted` / `remoteConfirmed` 决定，不从错误类型推断；未提交路径从不置位。
- **与 RR-49 的关系**：带哨兵的错误本身也在 `transactionPastCommitPoint` 里，所以即使别的路径遗漏了显式状态，已声明提交的回复也不会重排。
- **嵌套事务**：`txCommitted` 只由消息自己的事务（RR-49 的 `txInFlight` 认领）置位，handler 内 `RunIsolatedTransaction` 提交后外层失败
  不会带哨兵。
- **快池不阻塞 / 同 ID 顺序 / RR-35**：只改回复错误的包装，不改执行、排队与撤销路径。
