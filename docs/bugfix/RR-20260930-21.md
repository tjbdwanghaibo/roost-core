# RR-20260930-21 修复：释放 Redis 锁失败后进入"持有状态未知"，下一次 TryLock 以 Redis 为准

问题：[RR-20260930-21](../bug/RR-20260930-21.md)（B27 第 2 批端到端暴露，[RR-20260926-46 后续验证](RR-20260926-46.md#后续验证2026-09-30b27-第-2-批)）。
日期 2026-09-30；实施基线 main `4d9018e1`。状态：已修复，本地验证通过，已提交，未推送、未发版。

## 根因（基线行号）

- `remoteentity/versioned_lock.go:236-282` `UnlockWithRetry`：只有 Redis 答复 0（不再持有）或 1/2（已释放）才改本地状态；Redis 错误用尽重试后返回 `lastErr`、ctx 到期返回 `ctx.Err()`，两条路径都留着 `acquired=true`、`token` 不变。
- `:108-110` `TryLock`：`if l.acquired { return "versioned lock already acquired" }`——只看本地状态，不问 Redis；这个错误不是 `ErrVersionedLockNotAcquired`，`Lock`（`:185-187`）当作不可重试错误立即返回。
- `remoteentity/batch.go:165-167` `beginWrite`：`w.rMu.Lock(ctx)` 失败即拒绝这次写（`remote_entity: shared lock <id>: …`）；锁对象随 wrapper 常驻（`manager.go:189` 每个实体一把），进程内没有第二把锁可用。
- 能清 `acquired` 的只有 `touchLease` / `Refresh` 看到 Redis 答复 -1 / 0（`:355-405`）；`UnlockWithRetry` 一开始就 `stopAsyncTouch()`，写之间也没有人 Touch。于是 Redis 恢复、TTL 过期之后，本进程对该实体的每次写都被本地状态拒绝，只能重启。

## 决策

释放失败不能伪造"已释放"：Redis 上 owner 可能仍是我们（没人续期，直到 TTL）、可能已过期、也可能已被别人取得。本地只能进入**持有状态未知**，让下一次 `TryLock` 以 Redis 为准：

- `UnlockWithRetry` 的三条"没有明确答复"出口（循环前 ctx 到期、退避等待中 ctx 到期、重试用尽）都调 `releaseOutcomeUnknown(token)`：只对仍是当前代际的 token 生效（Touch / Refresh 已看到失效的代际不再改），`acquired=false`，token 存到 `releaseUnknownToken`。此时 `IsAcquired` / `writeGrant` / `Touch` / `Refresh` / `Close` 都按未持有处理；续期 goroutine 已由 `stopAsyncTouch` 停掉并等待退出，不会再有人为这个 token 续期。
- `TryLock` 把 `releaseUnknownToken` 作为 `ARGV[3]` 交给 `versionedTryLockLua`：`owner == false or (ARGV[3] ~= "" and owner == ARGV[3])` 都视为可取得——在同一条脚本里换成新 token、`INCR` 分配新 fence、`PEXPIRE` 新租期，是**新的一代**而不是延续旧代；owner 是别人照旧 `{0,0,0}` → `ErrVersionedLockNotAcquired` → `Lock` 的既有退避重试（"别人持有"路径）。脚本回复解析成功后清空 `releaseUnknownToken`（Redis 已给出明确答复：要么被本次取得替换，要么已不是 owner）；Redis 错误时保留，下次再问。
- authority 模式（正式 kit 装配）下 `GrantWrite` 与之前一样对新 token 做一次 FindAndModify（`$inc _grant_fence`、`$set _grant_token`），fence / version 来自 Mongo 许可；Redis-only 兼容模式下 fence 来自 Redis 计数器递增。两种模式都满足"一次取得一枚 fence"。
- 代际隔离沿用 RR-20260924-20 / RR-20260926-43：新代际是新 token，`startAsyncTouchLocked(newToken)` 为它登记续期；旧代际的迟到回复（公开 `Touch` 在释放失败前发出、重新取得后才回 -1）只匹配 `l.token == oldToken`，改不了新代际。

### 未采用的方案

1. **`TryLock` 每次都问 Redis、忽略本地 `acquired`**：本地 `acquired` 是真正的双重加锁保护——同一锁对象在持有中再次 `TryLock` 是编程错误，应立即失败；去 Redis 只会得到 owner 是自己的 `{0,0,0}`（误报"别人持有"）或被当作重新取得而换代，持有中的写会拿到不一致的 fence。
2. **释放失败后直接视为已释放**（`acquired=false`、忘掉 token）：伪造了 Redis 上并不存在的事实，之后没有任何东西再去核对。下一次 `TryLock` 拿新 token 争锁，owner 仍是自己的旧 token 时得到 `NotAcquired`，只能等 TTL 到期（`LockTTL` 内实体不可写，本进程自己的租约却拿不回）；`Lock` 的默认重试预算（5 × 100ms 退避 ≈ 3.1s）通常等不到 TTL，写就失败。
3. **释放失败后由 `Close` 或下一次 `TryLock` 先补一次 unlock 再取锁**：多一次往返；且 unlock 脚本会写版本缓存，而本地 `version` 是提交前的值（失败的那次释放没更新它），补写会把旧版本写进 Redis 缓存。一条脚本原子判定 owner 更简单，也不碰版本字段。
4. **owner 仍是旧 token 时沿用同一 token / 同一 fence 延续旧代际**：fence 是"一次取得一枚"的不变量，续期登记与迟到回复隔离都按 token；复用会让 RR-20260924-20 / 43 的隔离失效。
5. **重新取得时顺带把失败释放想写的 version 写进 Redis 缓存**：不采用，让 unlock 脚本保持唯一的版本缓存写入者。代价：Redis-only 兼容模式下重新取得后 `Version()` 是提交前的值，wrapper 会多做一次从后端的重载（`batch.go` 的版本比较照常，不放宽）；authority 模式 version 来自 Mongo 许可，不受影响。

## 兼容性

- `redis.IVersionedLock` / `IFencedVersionedLock` 接口、配置、键布局（`lock:<key>:<id>`、`…:fence`）不变；TryLock 脚本多一个 `ARGV[3]`，KEYS 不变，Redis Cluster 槽位不受影响。仓内只有本包调用该脚本；仓外若有模拟这段 Lua 的替身需接受第三个参数（空串 = 无重新取得）。
- 行为变化（收紧到与 Redis 一致）：
  - 释放没有明确答复后 `IsAcquired()` 立即为 false（此前为 true，直到 Touch / Refresh 看到失效或永远）；`Touch` / `Refresh` 回 `ErrVersionedLockExpired`。
  - 此状态下 `Close()` 不再尝试释放（此前会以旧 token 再 unlock 一次，成功时把提交前的本地 `version` 写进 Redis 缓存）；租约由 TTL 到期或被下一次 `TryLock` 重新取得。
  - `releaseRemoteEntries` 的 `ErrRemoteReleaseIncomplete`、`remote_entity.release_failure_total` 与 `FatalError` / kit `OnFatal` 记录不变——那次释放确实没交还资源；本修复只保证之后的写以 Redis 为准，不掩盖那次失败。
- 无数据迁移；Redis 上遗留的旧 token 租约按原 TTL 到期。

## 对抗性自查

- **fence / 版本**：新代际的 fence 仍只由 TryLock 分配（authority 模式来自 Mongo `GrantWrite`，兼容模式来自 Redis 计数器），旧代际的 fence 不复用；`batch.go` 的版本比较与 `SetEntityVersion` 的回退拒绝未改。
- **迟到回复**：`releaseOutcomeUnknown` 只改 `l.token == token` 的代际；重新取得后 `l.token` 是新 token，旧代际的 unlock / touch / refresh 回复都匹配不上。
- **续期 goroutine**：`UnlockWithRetry` 先 `stopAsyncTouch()`（取消 + `touchWg.Wait()`），进入未知状态时登记已清空；新代际由 `startAsyncTouchLocked(newToken)` 登记，按 RR-43 代际规则。
- **锁序**：`releaseOutcomeUnknown` 只取 `l.mu`；`TryLock` 读写 `releaseUnknownToken` 都在 `l.mu` 临界区内（与基线相同，同一锁对象的 TryLock / Unlock 由 wrapper 写门串行）。
- **重新取得脚本执行了但回复丢失**：Redis owner 已是新 token，本地丢掉它、`releaseUnknownToken` 仍是旧 token（匹配不上）——退化为等 TTL 到期后再取，不会拿到不属于自己的锁。
