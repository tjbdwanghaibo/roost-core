# RR-20260915-01:满容量对象 / 组件替换因先创建后删除被误拒

**仓库 / 位置**:roost-core `statesync/delta.go`,`ApplyDelta` 与 `applyComponentDeltas` 的逐步上限检查。
**修复单元**:U-0204(C8)。**定位文档**:TROUBLESHOOTING T-98。

## 问题

`MaxObjects=1`,旧快照只有 ID=2,新快照只有 ID=1,双方经 `NewSnapshot` 校验都合法。`BuildDelta` 按标识有序合并,
先 `Create(1)` 再 `Remove(2)`;`EncodeFrame` / `DecodeFrame` 都接受。`ApplyDelta` 在第一步暂存两个对象时立即
`ErrObjectLimit`,没有机会执行删除。组件层同理(`MaxComponentsPerObject=1`,TypeID 2 → 1,先 Set 后 Remove →
`ErrComponentLimit`)。把 ID 改成 3(先删后加)就成功——替换能否应用取决于标识排序。

## 根因

三个阶段对"上限"的不变量不一致(C8):`NewSnapshot` 校验**最终集合**;diff 有序合并、编码允许增删操作数大于
最终存量(解码侧上限是 `2×MaxObjects` / `2×MaxComponentsPerObject`);`ApplyDelta` 却在**每一步**用最终存量上限
检查暂存 map。

## 方案选择

- **diff 规范"删除先行"。** 改变帧内操作顺序的含义;审查也提醒对外部输入的重复键 / 冲突操作,无条件重排会改语义。
  而且只修发送侧,老发送方生成的帧在新接收方仍会被拒。
- **取消过程中的检查。** 暂存 map 对进程内直接构造(未经 `DecodeFrame`)的敌意帧就失去了上界。
- **过程用 2× 上限、最终集合用上限(采用)。** 一个最终集合合法的帧,暂存 map 至多 = base(≤ Max)+ 本帧 creates
  (≤ Max,因为同 Ref 在一帧内不能既 create 又 remove——`validateDeltaFrame` 拒绝重复 delta),即 ≤ 2×Max,
  与解码侧允许的每帧操作数上限同一因子。循环里保留 `> 2×Max` 的过程上界,循环后再对最终集合按 `> Max` 拒绝。
  对象层与组件层同形,一起改。

## 改动

`delta.go`:`ApplyDelta` 循环内改为 `len(objects) > MaxObjects*2`,循环后加 `len(objects) > MaxObjects`;
`applyComponentDeltas` 同形。函数注释写明"上限约束结果,不约束每一步"。

## 证明

`statesync/replacement_capacity_promises_test.go`:
- `TestApplyDeltaPromiseFullCapacityReplacementIsOrderIndependent`:审查的六个叶子(对象 2→1 / 2→3、组件 2→1 / 2→3、
  schema 变更、同 Ref archetype 变更),经完整 BuildDelta → Encode → Decode → ApplyDelta 回环并 `DeepEqual` 目标快照;
- `TestApplyDeltaPromiseFinalSetStillBounded`:最终集合超限的对象 / 组件帧仍分别以 `ErrObjectLimit` / `ErrComponentLimit` 拒绝。

修前红:`valid before/after snapshots rejected: replication: object limit exceeded operations=[{Create 1} {Remove 2}]` /
`… component limit exceeded …`。修后 statesync 含 `-race` 全绿,core 全仓 `-race` 全绿。

## 未做 / 边界

- 过程上界 2× 是按"最终集合合法"推出来的;一个最终集合本就超限的帧可能在过程中就被 2× 上界拒绝,
  也可能到循环后才被拒,两者返回同一个错误,调用方不可区分——这是可接受的。
- 没有改 `BuildDelta` 的操作顺序;发送侧生成的帧形状不变。
