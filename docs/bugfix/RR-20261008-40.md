# RR-20261008-40 修复记录

问题：[KCP E2E 停机先取消网络，误报在途机器人发送失败](../bug/RR-20261008-40.md)。基线d30c3f02；仅修复测试夹具与验收条件，不改生产代码，不移动v1.23.1。

## 根因与处置

finishE2EBot 先停止机器人接收循环、等待所有者交回统计，再取消网络 context；不按 errors.Is(context.Canceled) 过滤错误。

保留原 KCP 丢帧、补洞、desync、帧预算和业务错误断言。新增3个受控子场景：在途输出完成后退出、普通业务发送失败、业务主动返回context.Canceled；后两者仍原样报错。修前只重现主动停机误报，控制场景未被放宽。

## 方向判断

这次并非生产逻辑重复失效，而是验收方混淆了发起停止与依赖可释放的先后；沿用框架既有停止、排空、释放的顺序，不让机器人吞取消错误。

## 红绿和限制

修前原文见问题记录。目标场景macOS `go test -race ./remoteentity ./sync/lockstep -run <3个相关用例> -count=30`通过；相邻4包race三轮通过。完整macOS/Linux结果统一回填[本轮收口](../review/FOLLOWUP-MAC-LINUX-2026-10-08.md)。这不把一次旧日志的所有潜在根因都推定为相同原因；当前声明契约须在明确时间/停机边界下通过，不靠平台性能偶然性。
