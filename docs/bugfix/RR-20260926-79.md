# RR-20260926-79 修复：会话关闭 / 业务注销时通知政策，Direct 的绑定表随之收缩

问题：[RR-20260926-79](../bug/RR-20260926-79.md)（复现 [REPRO-2026-09-26-07 §2](../bug/REPRO-2026-09-26-07.md#2-rr-78rr-79政策重新提交的两处残留syncentitysyncpolicy-包)）。
日期 2026-09-27。实施基线：本地 main `62fdbe6` + RR-78（`bc611f7`）。状态：已修复，本地验证通过，已本地提交，未推送/发布。
前序：[RR-20260926-70 修复](RR-20260926-70.md)（引入 `Direct.bound`）。

图谱说明：codebase-memory 对 `sync/entitysync` 的 generation 为 09-26 08:36，已过期；以下行号与结论全部来自 `62fdbe6` 源码。

## 根因（基线行号）

RR-70 为了在 RR-59 撤销后按调用方当前绑定重新提交，给 `Direct` 加了绑定表：`Bind` 写入（`sync/entitysync/policy/direct.go:53`），只有 `Unbind`
删除（`:62`）。Manager 在另外两处丢掉订阅：`dropSession`（`subscriptions.go:186`，`CloseSession` 与传输拒绝帧后的 `loseSession` 共用，`:212`
逐条 `removeSubscriptionLocked`）与 `Unregister`（`manager.go:438`，`:446` `retireLocked` 清空来源、改为 leaving）。两处都不告诉政策，`Direct.bound`
随历史绑定数单调增长（审计探针：`manager live subscriptions=0, Direct.bound entries=1000`）。

修复中另确认一个后果：会话关闭时实体恰好处于 RR-59 撤销后的缺席期，Manager 的撤销记录与 Direct 的绑定都还在；同 ID 会话重开、实体重新登记后，
`Direct.resubmit`（`:72`）按旧绑定把订阅重新提交到新连接上（临时探针：`bound=1 reopened session 7 holds 8=true`）。审计时“未发现过期绑定被错误
恢复”，是因为探针没有覆盖“撤销期间关闭会话”。

## 修复（按 RR 主记录的修复约束）

### Manager：在既有的丢弃点记下释放，政策阶段通知（`policy_queue.go`、`subscriptions.go`、`manager.go`）

- 新导出 `SubscriptionSourceHooks{Resubmit, Released}`、`Manager.NewSubscriptionSourceWithHooks`、`ReleasedSubscription{Session, Subject}`；
  `NewSubscriptionSourceWithResubmit` 不变。`SubscriptionSource` 增加未导出 `released`。
- **通知点**：`dropSession` 在逐条移除订阅的同一把 `subj.mu` 内，`Unregister` 在 `retireLocked` 清空来源之前，把订阅里带 `Released` 的来源记为
  （来源, 会话, subject）；RR-59 撤销后尚待重新提交的记录（撤销表、待交付、交付中）没有订阅可遍历，按会话（`dropSession`）或 subject（`Unregister`，
  随 `dropRetractedSubject` 一起）另行查找。`RetractUnloadedSubject` 不产生通知（那些订阅走 Resubmit）。
- **交付**：排进 `Manager.releases`（与 RR-70 记录共用叶子锁 `resubmitMu`，`releaseEntries` 原子计数让政策阶段在没有通知时不加锁）并 `WakeSync`；
  下一次 Flush 的政策阶段、`deliverResubmits` 之前按来源分批调用 `Released`。先释放后重新提交：会话关闭时仍排队的重新提交，政策先删掉绑定，交还
  时就不会说回去。`policiesPending` 计入待交付通知，`Drain` 等它们交付；`Manager.Close` 清空。
- **为什么不在调用方路径上回调**：`Unregister` 会在 Nest 快 worker 上、持实体锁时被调用（`RetractSyncSubject`），也可能在政策持锁时被调用；
  RR-70 已因同一理由把重新提交放到政策阶段。**为什么不起 goroutine**：约束要求，也不需要——政策阶段每个 Flush 周期都运行。
- **Holds**：新导出 `SubscriptionSource.Holds(session, subject)`，报告本来源此刻是否让该会话（当前这一次打开）订阅着该 subject（subject 已登记、
  未退役、来源在订阅里）；撤销后待重新提交的不算。通知是异步的，之间调用方可能已在重开的会话 / 重新登记的实体上重新订阅，政策删除簿记前据此确认。
- **RR-70 的记录不变**：会话关闭时 Manager 不删除撤销记录（审计已接受的边界，Interest 的恢复语义依赖它），只把其中属于该会话的 pair 通知政策，
  由政策决定是否释放。

### Direct（`policy/direct.go`）

- 改用 `NewSubscriptionSourceWithHooks`，新增 `released`：在 `d.mu` 内，对仍在绑定表里、且 `Holds` 为假的 pair 删除绑定，并 `Unsubscribe`
  （此时本来源已不持有订阅，只让 Manager 释放为这对 pair 保留的撤销记录，`ErrSubjectNotRegistered` / `ErrSubscriptionNotFound` 忽略）。
  `Holds` 与 `Bind` / `resubmit` 都在 `d.mu` 内，本来源的订阅只在 `d.mu` 下变化，判定与删除之间不会插入新的绑定。
- 上界：一次政策阶段之后，绑定表 = 本来源持有活订阅的 pair + RR-59 撤销后、会话仍开着、等待重载的 pair，即“活跃绑定数”。

Group、Interest 不接 `Released`：Group 的成员 / 实体集合由调用方 `Leave` / `RemoveSubject` 管理，Interest 由 `Leave` / `SessionLost → Resubscribe`
管理，行为不变。

未采用：会话关闭时 Manager 直接删除 RR-70 撤销记录（改变 RR-70 对 Interest 的恢复语义，约束要求不变）；同步回调（调用方路径持锁问题同上）；
去掉 `Direct.bound`、把视图存进 Manager 的撤销记录（改 RR-70 的交还格式，且仍需会话关闭时的清理）；通知只带会话 / subject、由 Direct 扫全表
（会把通知途中重开会话后重新 Bind 的绑定误删，仍需 `Holds`）。

## 兼容性

- 新增导出：`entitysync.SubscriptionSourceHooks`、`entitysync.ReleasedSubscription`、`Manager.NewSubscriptionSourceWithHooks`、`SubscriptionSource.Holds`。
  既有 API 不变；无配置、协议、持久格式变化。
- 行为变化（收紧）：`policy.Direct` 的绑定在会话关闭（含传输失败）或业务 `Unregister` 该实体后，于下一次 Flush 删除；此后 RR-59 撤销的恢复不再作用于
  它。此前会话关闭时实体恰好缺席的绑定会在实体重新登记后重新提交到同 ID 重开的连接上，现在不会——重开的连接需要观看就重新 `Bind`（与会话关闭时
  实体在场的情形一致：Manager 丢掉订阅，Direct 从来不替新连接恢复）。直接用 `Manager.Subscribe`、普通来源、Group、Interest 的行为不变。
- 开销：`dropSession` / `Unregister` 对每条订阅多一次来源遍历（本来就在 `subj.mu` 内处理），只有带 `Released` 的来源才分配；RR-70 记录存在时
  `dropSession` 额外扫描一次记录（记录只在 RR-59 撤销后存在）。

## 未验证项 / 风险

- 通知是异步的：会话关闭 / 注销到下一次政策阶段之间，绑定表暂时多出这些 pair；Manager 停止（未 Close）后不再 Flush 时通知排队不交付，`Close` 清空。
- RR-70 的交还本身不带会话 lifetime：会话关闭与同 ID 重开恰好夹在政策阶段取出重新提交与 Direct 的 Subscribe 之间时，仍可能提交到新连接
  （微秒级窗口，RR-70 既有；本修复消除了确定性的“撤销期间关闭会话”路径）。Interest / Group 的同类情形不在本 RR 范围，行为未改。
- `Manager.Close` 不通知政策（Manager 已不可用）。
- Direct 目前不在生产代码使用；正式生成工程无端到端场景，以 policy / entitysync 包内真实 Manager 验证。
