# RR-20260914-11:ForceFull 被请求之前发送的帧的 ACK 取消

**仓库 / 位置**:roost-core `statesync/session.go`,`Acknowledge` 与 `handleControl` 的 ACK 分支。
**修复单元**:U-0201(C8)。**定位文档**:TROUBLESHOOTING T-95。

## 问题

发布 tick 1、准备并提交;ACK 尚未到达时调用 `ForceFull`;随后 tick 1 的 ACK 经 `Acknowledge` 或 `HandleControl`
到达,ackTick 从 0 变 1,并**清掉 `forceFull`**。发布 tick 2 后 `BuildLatest` 返回 delta(kind=2、base=1)而不是
要求的全量:恢复承诺落空。两个入口独立失败;先 ACK 再 ForceFull、以及 Resync 后旧 ACK 被序号拒绝的对照正常。

## 根因

ACK 的水位推进与恢复意图耦合在一处(C8:两个 ACK 入口对"恢复是否完成"用了错误的判据)。恢复意图真正的
释放点其实已经有了——`commitPrepared` 里"属于当前 generation 的全量帧提交成功"时 `forceFull = false`,而且
`ForceFull` 会 `generation++`,所以更早准备的帧根本提交不进去。ACK 路径上的那句 `forceFull = false` 是多余且错误的。

## 方案选择

- **ForceFull 时记下 lastSent,ACK 只在 tick 大于它时才清标志。** 多一个字段,而且仍然让 ACK 参与恢复判定。
- **删掉 ACK 路径上的清除(采用)。** 释放点唯一化为全量帧的提交;ACK 只推进水位。会话创建时 `forceFull=true`,
  第一帧全量提交即清;`prepare` 因基线被淘汰而置位的 `forceFull`,也由随后的全量提交清。没有任何路径需要 ACK 来清。

## 改动

`session.go`:`Acknowledge` 与 `handleControl` 的 ACK 分支各删一行 `s.forceFull = false`,注释写明释放点。

## 证明

`statesync/recovery_intent_promises_test.go` 的 `TestForceFullPromiseSurvivesAcksOfEarlierSends`:审查的四个子例
(先 ACK 再 Force 对照 / 原始 ACK 后到 / 线上 ACK 后到 / Resync 后旧 ACK 被拒),每个子例末尾再断言全量帧提交并
ACK 之后下一帧回到 `delta base=2`——释放点没有跟着消失。

修前红:`ForceFull lost: kind=2 base=1`(raw / wire 两个子例)。修后 statesync 含 `-race` 全绿;包内没有任何旧测试
依赖 ACK 清标志。
