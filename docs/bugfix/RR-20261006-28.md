# RR-20261006-28 修复：生产校验接受 redis.cluster_addrs；accountctl 与 dev run.sh 能连 Redis Cluster

问题：[RR-20261006-28](../bug/RR-20261006-28.md)。基线 main `0db819b0`，未发版。来源：[真实进程演练](REAL-PROCESS-DRILLS-2026-10-06.md)第 ⑥ 项。

## 根因

三处各自只认 `redis.addr`：`app.validateProductionServiceConfig`（`app/config_validation.go`）、生成的 `cmd/accountctl`（只有单机客户端）、生成的 `deploy/dev/run.sh` 的 `register_game_server`（只 awk `addr`）。框架其余部分在 NC-190 已经统一按 `redis.cluster_addrs` 判断 Cluster，这三处没有跟上。

## 改动

| 位置 | 改动 |
| --- | --- |
| `app/config_validation.go` | 生产校验改为 `redis.addr` 或 `redis.cluster_addrs` 至少一个非空，错误文本 `config: production <type> requires redis.addr or redis.cluster_addrs`。`cluster_addrs` 的解析从 `kit/mods` 移到 `app.RedisClusterAddrs`（逗号串或 YAML 列表、去空白、丢空项，行为不变），`kit/mods.RedisClusterAddrs` 转调它——校验与 Redis Mod 用同一份解析，空串、只有逗号、空列表都算没配 |
| `demo/cmd/accountctl/main.go.tmpl` | 新参数 `-redis-cluster addr,addr,...`（`redis.cluster_addrs`），给了就用 Cluster 客户端（`fredis.Config.ClusterAddrs`），`-redis` / `-redis-db` 忽略；`openService` 改收一份 `*fredis.Config` |
| `codegen/internal/roost/render_dev_run.go` | `register_game_server` 从 `config.account.yaml` 的 `redis:` 块读 `cluster_addrs`（逗号串或 YAML 列表，去引号与空白），有值就 `accountctl -redis-cluster <seeds>`，否则照旧 `-redis / -redis-db` |

未采用：
- 在 `app` 里 import `kit/mods`——层次反了（kit 依赖 core）；反过来让 kit 转调 app 的解析，一处定义。
- accountctl 用 `-redis` 接受逗号串自动判断 Cluster——单个地址的 Cluster 种子与单机无法区分，显式参数更清楚。

## 兼容

- 生产校验放宽：只配 `cluster_addrs` 的配置现在能启动；两者都没有时照旧报错（文本多了 `or redis.cluster_addrs`，`TestValidateServiceConfigRejectsProductionServicesWithoutRedis` 的子串断言不变）。
- `kit/mods.RedisClusterAddrs` 签名与行为不变；`app` 多一个导出函数 `RedisClusterAddrs`。
- 生成形状：`cmd/accountctl/main.go` 与 `deploy/dev/run.sh` 变化，已有工程重新生成或手工合并；单机配置的行为不变（`TestDevRun*` 原有用例通过）。

## 验证（`GOWORK=off`）

- 修前红见问题记录；修后 `go test -race -count=3 ./app/ ./kit/mods/ ./kit/redis/` 与 `go test ./codegen/...` 通过（含 `TestDevRunRegistersTheGameServerOnTheAccountServicesRedisCluster` 两种写法）。

## 更正（2026-10-07，以冻结点 `5e72ca4d` 源码为准）

上面“改动”表第一行和“兼容”写的是修复当时（`0db819b0`）的位置。A4①（`d1226825`，每个 Mod 声明自己的配置）之后，这些已经不成立：

- **检查不在 `app` 里了。** `app.validateProductionServiceConfig` 已删除，`app/config_validation.go` 里不再有 Redis 的生产检查。现在的检查是 `kit/redis/redis_mod.go` 第 63-68 行的 `(*Config).ValidateConfig(production bool)`：生产环境下 `redis.addr` 为空且 `redis.cluster_addrs` 没有任何地址时报错。它是 `redis.*` 声明的检查，有两处会执行：App 在任何 Mod Init 之前按本服务全部 Mod 的声明做检查（`--check-config` 也走这条路），以及 Redis Mod / 单实例锁 `SingletonStore` 读配置时。因此约束对象是“读 Redis 配置的进程”，不再按服务类型区分。
- **`app.RedisClusterAddrs` 与 `kit/mods.RedisClusterAddrs` 都已删除**（CHANGELOG A4① 条目有记）。`redis.cluster_addrs` 改由 `kitredis.ClusterConfig` 声明为 `[]string`，逗号串和 YAML 列表的解析、去空白、丢空项由声明解析统一处理。服务 Mod 匿名嵌入同一个 `ClusterConfig`，`mods.ValidateClusterKeyPrefix` 也按它判断是否为 Cluster。
- **错误文本不再带服务类型。** 原来是 `config: production <type> requires redis.addr or redis.cluster_addrs`，现在是 `config: production requires redis.addr or redis.cluster_addrs`。实际报出时外面还包一层：经 App 启动检查 / `app.CheckConfig` 报出时是 `mod redis: config: production requires redis.addr or redis.cluster_addrs`；直接调 Redis Mod `Init` 时是 `redis mod: config: production requires redis.addr or redis.cluster_addrs`（2026-10-07 在 `5e72ca4d` 上用临时用例实测，用例未提交）。
- **对应的 app 测试已删除**，包括 `TestValidateServiceConfigRejectsProductionServicesWithoutRedis` 和 `app/production_redis_cluster_promises_test.go`。现在由以下测试守住这条约束：`kit/redis/config_types_promises_test.go` 的 `TestProductionRedisNeedsAnAddrOrClusterSeeds`（addr、逗号串、YAML 列表三种写法通过；没写、空 addr、只有逗号、空列表、全是空白项五种写法拒绝），以及 `kit/config_schema_promises_test.go` 的 `TestProductionDoesNotRequireSwitchesNothingReads`（经 `app.CheckConfig` 检查）。
- accountctl 的 `-redis-cluster` 和 dev `run.sh` 读 `cluster_addrs` 两项，在 `5e72ca4d` 上仍和上文一致，不需要更正。
