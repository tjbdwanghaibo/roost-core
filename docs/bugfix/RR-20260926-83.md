## 根因（指到行，基线 `9009268`）

kind 注册表（`entity/entity_factory.go:50-53` `kindEntries`）、派生锁档（`entity/category_order.go:77` `lockRankByKind`）、category 集合
（`category_order.go:73` `taxonomy`）和 delta 注册表（`entity/remote_snapshot_codec.go:21` `remoteSnapshotDecoders`）都是进程级的，
`go test -count=N` 在同一进程里把整包跑 N 轮；包的 `init()`（`entity_factory_test.go:39-83`，kind 3 / 252 / 253）与各用例的 `sync.Once`
（`kind_policy_builder_promises_test.go:20-22`，kind 211～214）只在第一轮注册。

1. **主因：两处收尾清空全局表。**
   - `remote_view_test.go:9` `t.Cleanup(ResetEntityRegistryForTest)` 在第一轮中途清空每个 kind 槽。第二轮 `init` 与 `sync.Once` 不会再跑：
     `entity_factory_test.go` 的 6 个用例、`guards_promises_test.go:20`、`kind_policy_builder_promises_test.go:41` 找不到 kind / builder，
     `:66` 对 `GetEntityBuilderParam(...)` 返回的 nil 取 `.Lifetime` 空指针 panic，整包中止（后面的用例第二轮根本没跑）。
   - `category_lock_order_promises_test.go:14`、`lock_order_no_hook_promises_test.go:12` 的 `t.Cleanup(resetEntityCategoriesForTest)` 把**所有** kind 的
     锁档清零；而重复注册相同定义在 `entity_factory.go:187-188` 直接返回、不重算锁档，这些 kind 第二轮起落到 `GetEntityGroup` 的旧路径（`entity_guard.go:23-30`）。
2. **被整表清空掩盖的问题**（去掉清空后才会红，下文“修前（中间态）”有原文）：
   - kind 撞号：`kind_registration_promises_test.go:28` `aboveField = 231`（category 4）与 `snapshot_load_waiters_promises_test.go:19` 的 231（category 1）。
     第一轮按文件顺序中间恰好隔着 remote_view 的清空才没有冲突。
   - “未链接 kind”取了已注册的值：`lock_order_no_hook_promises_test.go:50` 用 kind 200 构造“本进程不认识的 kind”，但 `remote_snapshot_test.go:142` 注册了 200。
   - 假定 kind 从未注册的用例：`kind_registration_promises_test.go:36`（kind 201，“被拒的注册没有留下登记”）、`kind_registry_promises_test.go:124`
     （kind 154 的 `RegisterEntityBuilder` 第二轮 `duplicate entity builder` panic）。
   - delta schema：`remote_snapshot_test.go:20` 每轮 `RegisterRemoteSnapshotDelta(44001, …)`，第二轮 `ErrRemoteSnapshotDecoderDuplicate`。

## 决策、文件与行为

- **统一夹具** `entity/registry_fixture_test.go` `isolateEntityRegistry(t)`：进入时在 `categoryMu → registryMu`（同 `RegisterEntityCategories` 的顺序）下记下
  每个 kind 的不可变记录指针、锁档与 category 集合指针，`t.Cleanup` 原样放回。只撤销本用例的登记，不动 `init` / `sync.Once` 留给别人的登记；
  记录是不可变的，保存指针即完整快照。包内没有 `t.Parallel` 用例，恢复不会覆盖并发用例的注册（夹具注释写明只用于非并行用例）。
  同文件 `forgetRemoteSnapshotDeltaOnCleanup(t, schema)` 撤销一次 delta 登记。两者都是测试文件内的未导出函数。
- 使用夹具的用例：`remote_view_test.go`（替换 `ResetEntityRegistryForTest`）、`category_lock_order_promises_test.go`、`lock_order_no_hook_promises_test.go`
  （替换 `resetEntityCategoriesForTest` 收尾；前者开头的 `resetEntityCategoriesForTest()` 保留，用例需要从“未声明 category”开始）、
  `kind_registration_promises_test.go` 的 `TestRegisterEntityKindCategoryRefusesEachInvalidPair`、`kind_registry_promises_test.go` 的 `TestKindRegistryKeepsItsRegistrationRules`。
- 换 kind：`aboveField` 231 → 239；“未链接 kind” 200 → 250。两个值在 `entity` 包测试里无人注册（`grep -rnw` 核对；250 只作为 `ComponentType` 出现）。
  撞号换号、夹具兜底两者并用：换号让冲突在单跑 / `-run` 过滤 / 乱序下也不出现，夹具让“需要未注册前提”的用例每轮成立。
- `remote_snapshot_test.go` `TestRemoteSnapshotCacheAppliesDeltaAndRejectsGap`：注册 delta 后 `forgetRemoteSnapshotDeltaOnCleanup`。
- `entity_factory_test.go`：仅 `gofmt`（基线上 `:193-194` 未格式化，`gofmt -l entity` 非空），无语义变化。
- 未采用：
  - 只删 `remote_view_test.go` 的清空、其余靠换号：`TestRegisterEntityKindCategoryRefusesEachInvalidPair` 与 `TestKindRegistryKeepsItsRegistrationRules` 断言的正是
    “首次注册”的行为，换号不能让第二轮重新“首次”；再给它们加 `sync.Once` 会让第二轮什么都不验证。
  - 修改或删除导出的 `ResetEntityRegistryForTest`：属生产文件与导出 API，约束不允许；它现在在仓内没有调用方，保留原样。
  - 改 `resetEntityCategoriesForTest` 让它重算锁档：夹具已经覆盖“收尾恢复”，这个函数只剩“开头清掉 category 声明”一个用途，保持不动。
- 无生产代码、配置、导出 API 变化。
