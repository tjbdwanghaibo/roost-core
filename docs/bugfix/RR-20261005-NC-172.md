# NC-172 修复：JetStream 同步总线自带投递准入与在途计数，停止在 ctx 内等在途 handler

[问题](../bug/RR-20261005-NC-172.md) · [证据](evidence/noncore-bugfix-20261005-stopshape/README.md)。提交 `c99a687d`。已修复、声明场景验证（含真实 NATS），未发版。

## 决策与实现

沿用 NC-90 在 Bus 上已定的做法（JetStream 回调自己的准入 / 在途门，并入停止），不另造机制。`sync/syncbus/driver/jetstream.go`：

- 每个 topic 的 consume 回调入口先 `beginDelivery`；停止开始后到达的投递返回 `errJetStreamSyncStopping`（非永久错误，driver NAK 交还 broker，由下一个消费同一 durable 的实例处理），不调用本地 handler。
- 新增 `StopWithContext(ctx)`：①关闭准入、停掉全部订阅（幂等）；②在 ctx 内等在途回调归零，超时返回 ctx 错误，重试再等；③返回 nil 后调用方才能释放总线与 NATS 连接。`Stop()` 改为无期限包装。
- 停止开始后 `Subscribe` 返回错误：否则新建的消费者每条投递都会被准入拒绝、NAK 到 MaxDeliver 被 Term。

`kit/syncbus/mod.go` 无需修改：总线实现 `StopWithContext` 后 Mod 走带 ctx 的分支，出错时已保留 `m.bus`；App 因此判定停机不完整、不停 NatsMod。

未采用：在单个订阅者的退订函数里等待（`ISyncBus.Subscribe` 返回 `func()`，没有 ctx，不能有界等待）。逐个订阅者的排空由订阅者自己负责（NC-174 的 replicator）。

## 兼容性

`Stop()` 现在会等到在途 handler 返回；handler 内部同步停自己的总线会等待自身（与 Bus pool handler 的既有限制相同）。停止后的投递从“交给 handler”变成 NAK 重投。API 只增加 `StopWithContext`。

## 验证

- 包内：`TestJetStreamSyncBusStopWaitsForAnInFlightHandler` 修前红（`Stop returned while a handler was still running on the subscription`），修后绿；`TestJetStreamSyncBusStopWithContextIsBoundedAndRetryable`（新 API）与 `TestSyncModStopTimeoutKeepsTheBusForRetry` 绿；`-race -count=10` 通过。
- 真实 nats-server（测试自起私有进程，不用共享环境）：`GOWORK=off go test -tags integration -count=1 -run TestRealJetStreamSyncBusStopDrainsAnInFlightHandler ./kit/syncbus/`。修前驱动 `err=<nil> bus_retained=false nats_closed=true`、`ack_pending=1 ack_floor=0`；修后 `err=context deadline exceeded bus_retained=true nats_closed=false`、重试 `err=<nil>`、`ack_pending=0 ack_floor=1`。

## 未验证 / 风险

nats.go 订阅缓冲里尚未回调的消息仍在 AckWait 后重投（与 NC-90 相同，不是本条承诺）；集群节点故障下的停止未验。
