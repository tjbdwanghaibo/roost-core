# RR-20260930-11 修复：`TestReadThroughStoreCoalescesMisses` 先把 8 个 goroutine 钉到合并点再放行加载器

问题：[RR-20260930-11](../bug/RR-20260930-11.md)（RR-20260930-03 验证时发现，[REMAINING-2026-09-28](../review/REMAINING-2026-09-28.md) §7）。日期 2026-09-30。基线 `153cac3d`，worktree `.claude/worktrees/agent-a3e8428d32b11619a`，分支 `worktree-agent-a3e8428d32b11619a`。
状态：**已修复**（本地提交，未推送 / 未发版）。codebase-memory 图谱 generation 09-26，落后于基线，本轮以当前源码与实跑为准。

## 根因

见问题记录。要点：`cache/read_through.go` 里领头者先写 L1（`:190`）再删合并项（`:138`），没有“已加载未写入”窗口；`loads=2` 来自一个在 `:88` 看到过期 miss、到 `:97` 取锁时首个加载已结束的 goroutine，它与首个加载不重叠，再加载一次不违反“并发 miss 合并”（`:54-55`）的承诺。测试（`cache/atomic_local_test.go:90-92`）只等到 `loads > 0` 就 `close(start)`，没有把其余 7 个 goroutine 钉到登记为等待者之后。

## 决策

只改测试，实现不动。

- 放行前的屏障改为轮询 `store.Stats()`，直到 `Loads == 1 && Coalesced == 7`；`Coalesced` 在 `s.mu` 下与 `waiters++` 一起递增（`read_through.go:104-105`），读到 7 即 7 个跟随者都已挂在 `call.done` 上，加载器又被 `start` 挡着，所以条件必然到达、且到达后再放行不可能出现第二次加载。轮询用 `runtime.Gosched()`（同包 `TestReadThroughReturnsACanceledWaitersSlot` 的 `awaitCoalesced` 写法），5s 上界，超时先 `close(start)`、`wg.Wait()` 收回 goroutine 再 `t.Fatalf`。
- 断言落在承诺上：加载器计数 `loads == 1`，且 `Stats()` 为 `Loads == 1 && Coalesced == 7`（原来只断言 `Coalesced != 0`）。
- 没有新增 sleep，原来的 `time.Sleep(time.Millisecond)` 轮询也去掉了。

**未采用：**

- 给 `load` 加“取到 `s.mu`、发现没有在飞的加载后再查一次 L1”的双重检查。它能消除这条过期 miss 的重复加载，但要在全局 `s.mu` 下多做一次 L1 查询（每个领头者路径），而收益只是省掉一次结果相同的加载：加载器是权威源，重复加载写回同版本同值，`Set` 不报错，调用方拿到的值不变。承诺本身没有被违反，不为测试稳定性改产品代码。
- 给 store 加只在测试里用的钩子（如“等待者登记完成”回调）：`Stats().Coalesced` 已经暴露了同一信息，并且同包已有测试这样用，钩子没有必要。
- 把 `MaxWaitersPerKey` 或 goroutine 数改小以降低概率：不解决问题。
