# RR-20260918-03：嵌套 child 的通知归属在替换与回滚之后没有跟着走

- 单元：U-0236 · 缺陷类 C4（跨层契约不一致）· 等级 P2
- 仓库：roost-codegen `internal/dao`（生成器模板，改的是所有工程的生成物）
- 排障行：T-130

## 问题

嵌套结构里再嵌套的 child（`map[K]*Child`、`[]*Child`、`*Child`）靠一个 callback 把自己的变更
往上报给父结构，父结构再往上报给 DAO，最后才进持久化补丁。审查第二轮把"什么时候该报、什么时候
不该报"逐格列了出来（[REVIEW-2026-09-18-02](../bug/REVIEW-2026-09-18-02.md)）：

| 字段形状 | 正常替换后旧 child | 正常替换后新 child | 回滚后恢复的旧 child | 回滚后丢弃的新 child |
| --- | --- | --- | --- | --- |
| `map[int32]*GemInfo` | 不通知 ✔ | 通知 ✔ | **该通知，实际 0 次** | **不该通知，实际 1 次** |
| `[]*Child` | 不通知 ✔ | 通知 ✔ | **该通知，实际 0 次** | **不该通知，实际 1 次** |
| `*Child` | **不该通知，实际 1 次** | 通知 ✔ | 通知 ✔（因为从来没解绑过） | **不该通知，实际 1 次** |

不是"多打一次 / 少打一次脏标记"而已：回滚之后对恢复出来的那个 child 做的**真实**修改会整条漏出
持久化链——下一次事务提交时父 DAO 认为无事发生，committer 一条记录都收不到。

## 根因

`internal/dao/template_nested.go` 里，"谁通知谁"是写在两个地方的裸 `SetNotify` 调用：

- setter 的 Kind 1 / Kind 2 分支：替换前遍历旧值 `SetNotify(nil)`，写入后遍历新值 `SetNotify(s.Mark)`；
- setter 的 Kind 3 分支（`*Child`）：**只有**写入后 `SetNotify(s.Mark)`，没有解绑旧值——三个分支本来就不一致；
- undo 闭包：`func() error { s.<field> = old; return nil }`，只把字段值设回去。

callback 不是字段值的一部分。Nest 的 `RollbackUndo` 逆序执行已登记的闭包、`RollbackUndo` 的 DAO
capture 只恢复 tracker，都不会去遍历嵌套结构修回调。于是回滚把**身份**恢复了、**运行时关系**没恢复。

`*Child` 分支漏解绑是同一个根因的另一面：归属是零散写在各分支里的，不是一处定义。

## 方案选择

- **（选中）把归属做成生成的内部方法。** 每个带嵌套 child 的字段生成 `bind<Field>`（把当前字段里
  的 child 绑到 `s.Mark`）与 `unbind<Field>`（解绑当前字段里的 child）。两个方法**不标脏、不登记 undo**
  ——这正是它们能在 undo 闭包里调用的原因（那时事务已是 rolledBack，公开 setter 会再登记一次 undo 并失败，
  审查报告点名了这一点）。所有改变"字段里装着什么"的路径都变成同一个三步：解绑要丢掉的 → 换值 → 绑定留下的。
  于是"哪些 child 通知这个结构"恒等于"字段里装着哪些 child"，三个分支自动一致。
- 在 undo 闭包里复用公开 setter：不行，见上。
- 让 Nest 在回滚时自己遍历嵌套修回调：Nest 不认识生成结构的形状，且会把一条框架规则绑死在 codegen 的
  输出形状上。
- 全量序列化后重建：能把引用语义盖过去，但丢掉 child 的对象身份（调用方手里的 `*Child` 会变成孤儿），
  审查也明确不接受这条。

## 改动

roost-codegen（生成器，一次改动作用于所有工程的下一次 `make generate`）：

- `internal/dao/template_helpers.go`：`fieldCarriesChildHook`（哪些字段需要接线）与
  `fieldDetachesOldChildren`（哪些字段的旧内容会作为独立对象活下来、因而需要解绑）。值类型的嵌套字段
  是就地覆盖，没有"旧对象"可解绑，所以只绑不解。
- `internal/dao/gen.go`：两个判据以 `hasHook` / `hasDetach` 进 nested 模板的 funcMap。
- `internal/dao/template_nested.go`：生成 `bind<Field>` / `unbind<Field>`；setter、`set<Field>RawMap`
  （从存储装载）、`setBSONDoc`（BSON 恢复）、undo 闭包四条路径一律改调这两个方法。
  顺带修掉同一处的两条不一致：`*Child` 的 setter 现在解绑旧值；值类型嵌套字段的 setter 现在绑定
  （此前只有 `setBSONDoc` 绑，`Set<Field>` 赋值是一次结构体拷贝、把 hook 一起覆盖成 nil，替换过的
  子结构后续修改再也到不了父对象）。
- `internal/dao/testdata/def/hero.go`：`EquipInfo` 补 `Runes []*GemInfo`、`Core *GemInfo`、`Shape Position`
  ——此前 fixture 只有 map 一种 child 形状，另外两种分支没有任何生成物被锁住。goldens 随之重生成。
- `scripts/dao-golden-runtime.sh`：改成把 `testdata/runtime/` 下所有 `*_test.go` 拷进一次性模块，
  不再只拷 `roundtrip_test.go`。

## 证明

`internal/dao/testdata/runtime/ownership_test.go`（`//go:build daoruntime`，由 dao 运行时门跑）：
`TestNestedChildNotificationOwnership`（3 形状 × 4 模式 = 12 叶子）、
`TestRestoredChildStillReachesTheCommitRecord`（2 叶子，真 `HeroDao` → `EquipInfo` → `GemInfo`，
断言回滚之后对恢复出来的 child 的修改仍然产出 1 条 commit 记录）、
`TestReplacedNestedValueStillNotifies`（值类型字段）。

修前（`sh scripts/dao-golden-runtime.sh`，roost-core v1.15.7）：

```
--- FAIL: TestNestedChildNotificationOwnership/map/rollback_old      parent notifications = 0, want 1
--- FAIL: TestNestedChildNotificationOwnership/map/rollback_new      parent notifications = 1, want 0
--- FAIL: TestNestedChildNotificationOwnership/slice/rollback_old    parent notifications = 0, want 1
--- FAIL: TestNestedChildNotificationOwnership/slice/rollback_new    parent notifications = 1, want 0
```

与审查独立复现的 7 条行为失败逐条对上（`pointer/rollback_old` 当时是"碰巧绿"——旧值从来没被解绑过）。
值类型那条单独验过红：把生成物里 `SetShape` 的 `s.bindShape()` 去掉，运行时门报
`parent notifications = 0, want 1`。

修后：运行时门全绿；codegen `go vet ./... && go test ./... -count=1` 全绿（含 golden 文本比对）。

## 未做 / 边界

- **只覆盖嵌套结构自己的字段。** 顶层 DAO 的 `Init` / 容器 setter / 删除，以及 BSON 就地恢复与顶层
  替换的交接，审查明确说本轮没有判为全覆盖，这里也没有动——它们是下一步的一致性检查入口。
- **同一个 child 挂到两个父对象**仍是未定义行为：`SetNotify` 是单槽，后绑的赢。本轮 12 个场景都不共享 child。
- 没有验 panic / 确定性拒绝提交 / 一次事务里多次替换后回滚 / 并发入口持实体锁这些失败模式；
  审查列的验收清单里这几项留给下一轮。
- `bind`/`unbind` 是按字段名生成的未导出方法（`bindGems`），与既有的 `set<Field>RawMap` 同一命名族；
  两个只在大小写上不同的字段名会撞，和既有生成物同风险，未额外防。
