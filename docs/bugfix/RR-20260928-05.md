## 实证（修前）

不调用 systemctl、不写任何系统目录。做法：

- 生成的 `deploy/shell/install.sh` 拷进演练目录（脚本按自己的位置求 `ROOT`，所以演练目录里同时放 `healthcheck.sh`、`configs/data` 与生产配置）；`APP_ROOT` / `STATE_ROOT` / `LOG_ROOT` 本来就可用环境变量覆盖，指向 scratchpad 里的临时根；`UNIT_PATH` 是写死的 `/etc/systemd/system/...`，只在演练副本里临时改成 `${UNIT_PATH:-...}`（**未提交**，生成器不变）。
- PATH 前置替身：`id -u` 报 0，`getent` / `useradd` 空操作，`install` 去掉 `-o/-g`（不是 root 不能 chown），`mv -Tf` 用 rename（BSD mv 没有 `-T`），`systemctl` 记录调用，`restart` 时按 unit 的 `WorkingDirectory=` 与 `ExecStart=` 真的起进程（`cd` 到工作目录后 `exec`），起之前把 `$APP_ROOT` 与 release 目录去掉写权限，近似 root 属主 + `ProtectSystem=strict`；`stop` 结束进程。
- 进程是 game-demo 的 game（darwin 本机编译，生成 DAO 库名改为 `zz16_game`），配置由生成的生产示例改写：只换连接地址为本地隔离环境（Mongo `27117` directConnection、NATS `14222`、Redis `16379` db 15、私有 etcd `23796`）与 `zz16` 隔离前缀，WAL 目录改为安装器要求的 `$STATE_ROOT/wal`（install.sh 自带校验），补上 RR-20260928-06 缺的三段。

基线 install.sh（`sh deploy/shell/install.sh game 1003 v1 config.game.yaml`）：


推断成立：release 里只有二进制与配置，工作目录 `$APP_ROOT` 下也没有 `configs/data`，config_data 启动即失败；首次安装走“readiness 失败 → 停服”分支。RR-20260928-04 的 install.sh 同样失败在这一行（只多了 `$APP_ROOT/log` 链接，统计文件已在 `LOG_ROOT` 创建）。

## 根因

- `codegen/internal/roost/render_deploy.go:130-132`（基线行号）：release 只装 `$BINARY` 与 `config.yaml`。
- `:149` unit `WorkingDirectory=$APP_ROOT`；`config_data.dir` 生成值是相对的 `configs/data`（`catalog.go` `defaultConfigDataDir`），`kit/configdata` 按工作目录解析为 `$APP_ROOT/configs/data`，没有任何步骤创建它。
- 与 RR-20260927-34 同形：那条修了镜像 / compose / k8s，shell 部署不在当时范围内。

## 决策：数据进 release，工作目录改为 `$APP_ROOT/current`

与 RR-34 的镜像布局一致：镜像里 `WORKDIR /app` 同时装着二进制与 `configs/data`；这里 release 目录同时装着二进制、`config.yaml` 与 `configs/data`，unit 的工作目录就是这个 release。

- **为什么数据进 release，而不是装到 `$APP_ROOT/configs/data`**：数据表由 `make generate` 从 `configs/table` 产出，表结构由二进制里的生成代码注册，必须与二进制同版本（RR-34 的理由）。放在 release 里，不可变、按版本号区分，`rollback.sh` 切 `current` 时数据跟着回退；放在 `$APP_ROOT` 下会被每次安装覆盖，回退后旧二进制读新数据。
- **为什么 `WorkingDirectory=$APP_ROOT/current`，而不是在 `$APP_ROOT` 放一个 `configs -> current/configs` 链接**：systemd 在进程启动时 `chdir` 并解析链接，进程的工作目录钉在它自己的 release 上。install.sh 与 rollback.sh 都是“先切 `current`、再 restart”；用链接的话，切换到重启之间旧进程的 configdata Reload 会读到新版本的数据。工作目录方案下切换只在重启后生效。
- **缺数据时在创建 release 之前拒绝**：`CONFIG_DATA=${CONFIG_DATA:-"$ROOT/configs/data"}`（与 `BINARY` 一样可覆盖），用 configdata 的服务要求其中有 `_manifest.json`，否则 `exit 2` 并提示 `make generate`。放在 `install -d ... "$RELEASE_ROOT"` 之前，否则会留下一个空 release，下一次安装被“release already exists and is immutable”挡住。
- **只给用 configdata 的服务装**：和 WAL 校验一样按服务名 `case`；不用 configdata 的服务 release 里没有 `configs/`。数据文件 root 所有、`go-w`（进程只读）。
- **RR-20260928-04 的统计目录链接随之移动**：工作目录变成 release 后，`log -> $LOG_ROOT` 放在每个 release 里（`ln -sfn "$LOG_ROOT" "$RELEASE_ROOT/log"`）；`$APP_ROOT/log` 不再生成。

没有采用：`SHA256SUMS` 覆盖数据文件——现在只覆盖二进制与 `config.yaml`，未改（数据文件较多，列入校验要改 sha256sum 的调用方式，与本问题无关）；给 `ExecStart` 写绝对的 `--config_data.dir`——配置由应用所有，改部署物即可。

## 兼容性

- install.sh 是 codegen 受控文件，`roost project sync` 即更新；service 配置不变。
- **行为变化**：unit 的工作目录从 `$APP_ROOT` 变为 `$APP_ROOT/current`。生成配置里按工作目录解析的相对路径只有 `config_data.dir`、`stats_log.dir` 与 `log.dir`（生产示例 `file: false`）；WAL 在生产示例里是绝对路径。手工在配置里写了其他相对路径、并依赖它落在 `$APP_ROOT` 下的部署要改成绝对路径。
- 旧 release（本版之前安装的）没有 `configs/data` 与 `log` 链接。新 unit 下 `rollback.sh` 回退到它们时，用 configdata 的服务仍会在 config_data 启动失败（与修前相同），统计文件写不进去（启动 WARN）；回退目标应是用新 install.sh 安装过的版本。
- 新的可选环境变量 `CONFIG_DATA`（缺省 `$ROOT/configs/data`）。
- **install.sh 失败时的自动回滚**（2026-09-28 补写，[RR-20260928-08](RR-20260928-08.md)，第七轮审计疑点；源码推断，未在临时根实跑）：install.sh 在切换 `current` 之前就重写了 unit
  （`WorkingDirectory=$APP_ROOT/current`），随后 `daemon-reload`；新版本 readiness 失败时只把 `current` 切回上一个 release 再 `restart`，**unit 不回退**。
  上一个 release 若是本版之前安装的（没有 `configs/data`、没有 `log` 链接），旧二进制在新 unit 下按 release 目录解析 `configs/data`：用 configdata 的服务启动失败，
  install.sh 打印 `rollback also failed readiness; manual recovery required` 并以 1 退出，实例停在失败状态（systemd 按 `Restart=on-failure` 反复重启）。
  与修前的差别：修前 unit 的工作目录是 `$APP_ROOT`，运维若为绕过本问题手工在 `$APP_ROOT/configs/data` 放过数据表，旧 release 修前能跑，在这次自动回滚里不能——这是新增的失败形态；
  没放过的，旧 release 修前本来就起不来（与修前相同）。不用 configdata 的服务回滚后照常启动，只少统计文件链接（启动 WARN）。
  建议：第一次用新 install.sh 升级用 configdata 的服务之前，先用新 install.sh 以新版本名重装一次当前在跑的版本，让“上一个 release”带上 `configs/data`；
  或备好手工恢复——把数据表拷进上一个 release 的 `configs/data`（与它的二进制同版本）后 `systemctl restart`。`rollback.sh` 的同一限制见上一条。

## 未验证项 / 风险

- 没有真 systemd：`WorkingDirectory` 跟随链接、`ProtectSystem=strict` / `ReadWritePaths` 的挂载语义只用替身近似（替身按 unit 文本 `cd` 后起进程，只读用去掉写权限代替）；`useradd`、`install -o/-g` 的属主、GNU `mv -T` 由替身代替。
- 没有在 Linux 上跑（macOS 演练；install.sh 的 GNU 选项由替身吸收）。

## 后续（2026-09-28，RR-20260928-10）

上文兼容性一节“install.sh 失败时的自动回滚”与 `rollback.sh` 回退到本版之前 release 的限制，已在临时根演练中实证（`rollback also failed readiness` / `rollback target failed readiness`），并由 [RR-20260928-10](RR-20260928-10.md) 修复：每个 release 的 unit 记在 `$APP_ROOT/units/<version>.service`，覆盖前先把正在用的那份记给当前 release，自动回滚与 `rollback.sh` 连同 unit 一起回退。用修后脚本第一次升级本版之前安装的实例时，旧 unit 记给当时的 `current`，回退到它即回到旧 unit（`WorkingDirectory=$APP_ROOT`），与升级前相同；上文“先以新版本名重装一次当前版本”的变通不再必需。更早、当时不是 `current` 的 release 没有 unit 记录，仍是上文所说的限制。
