# RR-20260914-02:OpenActivity 与 sweep 交错丢失活动窗口索引

**仓库 / 位置**:roost-kit `service/global/activity`,`OpenActivity` / `admitToWindow` / `AdvanceExpired` / `pruneWindow`。
**修复单元**:U-0191(C8)。**定位文档**:TROUBLESHOOTING T-85。

## 问题

`OpenActivity` 先把 key 放进窗口、再 `Activities.Create`。sweep 对"窗口里有 key、活动记录不存在"的判据是
"死条目,删掉"。交错:admit → sweep 读到 key、Get 不存在、prune → Create 成功 → 首个 notify 进入 collecting →
宽限期过了,窗口里没有它,没人再看它:`status=collecting window=[]`。玩家一直等跨服聚合结果。

## 根因

窗口条目没有生命周期:sweep 分不清"还没建"和"已经没了"(C8:开活动与清理对同一个条目用了不同的判据)。
单 key CAS 保证窗口自己一致,保证不了窗口与活动记录的跨 key 生命周期。

## 方案选择

- **先 Create 再 admit。** 进程死在两步之间,活动永远不进窗口——这正是原顺序要避免的。
- **Create 后再 admit 一次。** 审查指出不够:sweep 可能早已收集了 prune 候选、在二次 add 之后才执行删除。
- **窗口条目分 opening / 确认两段(采用)。** `Window.Opening []OpeningEntry{Key, AdmittedAtUnix}`,`Keys` 只放
  Create 之后确认过的。`admitToWindow` 进 Opening;Create 返回后(无论 created 与否)`confirmWindow` 在一个 CAS 里
  从 Opening 挪进 Keys——**无条件保证 key 在 Keys 里**,哪怕 sweep 已经回收了 opening 条目。sweep 对 Keys:活动
  缺失 → 真的没了,照旧 prune;对 Opening:活动存在 → 代为确认并按普通条目分类,活动缺失 → 只有超过
  `OpeningGrace`(新配置,默认 1 分钟)才回收,且回收 CAS 只删"仍在 Opening 里"的条目(确认已经把它挪走的话,
  回收观察到的那一代不复存在,什么也不做)。容量按 `len(Keys)+len(Opening)` 计。`PendingActivities` 返回两者。
  Redis 记录 JSON `omitempty`,老记录只有 `keys`,按确认条目处理,零迁移。

## 改动

`types.go`:`Window.Opening` / `OpeningEntry`、`openingIndex` / `pending`、clone 深拷贝。`service.go`:`Config.OpeningGrace`
(`DefaultOpeningGrace`);`admitToWindow` 进 Opening;`OpenActivity` 后 `confirmWindow`;`AdvanceExpired` 扫 Opening;
`pruneWindow` 改为 `retireFromWindow(prune, delivering, dropOpening)`(delivering 属 U-0192)。

## 证明

`service/global/activity/open_window_lifecycle_promises_test.go`:
- `TestOpenSweepInterleaveKeepsTheActivityInTheWindow`:Create 之前插入一次真实 sweep,活动仍按宽限期完成;
- `TestSweepHealsAnOpeningEntryWhoseActivityExists`:Create 与确认之间进程退出,sweep 代为认领并完成;
- `TestSweepReclaimsAnAbandonedOpeningEntryAfterGrace`:Create 一直失败,宽限内不回收、过后回收名额。

修前红:`open succeeded but expired activity stranded: status=collecting window=[]`。修后 activity 含 `-race` 全绿,kit 全量绿。

## 未做 / 边界

- 开活动进程在 admit 与 Create 之间停顿超过 `OpeningGrace` 且 sweep 已回收、随后 Create 成功:confirm 仍把 key 加进
  Keys,但此时容量可能超过 `MaxPendingActivities` 一个——扫描按 MaxPendingActivities 截断,尾部条目要等前面的退出。
- 没有多 key 原子操作,不涉及 Redis Cluster slot 约束;仍是单 key CAS + 生命周期。
- MemoryStore 复现;未跑真实 Redis。
