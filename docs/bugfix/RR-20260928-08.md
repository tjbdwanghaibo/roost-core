# RR-20260928-08 修复：等待投影器结论的 Remote `Commit` 失败一律带 `ErrRemotePersistenceIndeterminate`，只有明确拒绝不带

问题：[RR-20260928-08](../bug/RR-20260928-08.md)（第七轮审计 [N1、N2 与疑点](../review/REVIEW-2026-09-28-audit7.md)）。日期 2026-09-28；基线 `7ead224`；worktree 分支 `fix-r10-b18`。
codebase-memory 图谱停在 09-26，已过期，未使用；以当前源码与实跑为准。

## 根因

- `remoteentity/batch.go` `(*remoteWriteBatch).Commit`（基线 `:497-499` 等待，`:503` 归类）：strict 的 Remote 部分由 WAL 投影器写权威，`Commit` 只调
  `waitRemoteTransaction` 等 tracker 结论；等待失败时 `:503` 对 strict **任何**错误都置 `b.indeterminate`、交给 finalizer（之后回源按已提交收尾），
  但错误本身原样返回。`waitRemoteTransaction` → `trackedRemoteTransaction` → `newRemoteTransactionLocked`（`transaction_tracking.go:50-61`）在
  已关闭的 tracker 被容量淘汰、剩余名额被 pending 占满时返回裸 `entity.ErrRemoteOverloaded`。
- `nest/msg.go:96-98` 按 RR-20260928-03 的判据“本地已提交后 Commit 出错且不带 `ErrRemotePersistenceIndeterminate` = Remote 明确拒绝”置
  `remotePartRejected`，回复加 `ErrRemotePartRejected`（判别表第 4 行）。批次自己按“结果未知”处理的错误，回复却说“Remote 没写入”——两处判定不一致。
- 附带（N2、疑点）：`remoteentity/reply_sentinel_table_test.go` 的 `replySentinels` 停在 RR-03 改号之前（第 14 行记为兜底，
  `ErrNestCanceled` / `ErrNestTimeout` 记为 0，第 8 行“冲突 + 锁超时”会被算成第 7 行）；判别表第 14 行只点 `Nest.Request`；
  `nest/nest_dispatch.go:96-99` 在消息自己的本地事务已提交时仍用 `ErrNestedTransactionCommitted` 的文本“…committed before the message failed”包外层；
  RR-20260928-05 的兼容性没写 install.sh 失败时的自动回滚。

## 先弄清拒绝的范围：两条路径上的全部错误来源

按当前源码逐项列出 `Commit` 在本地事务已提交之后（nest 只在 `m.remoteCommitted` 分支调用一次）可能返回的错误。行号为修后。

### Durability 0（memory handler 带 Remote 批次）：`Commit` 直接调 `ApplyRemoteCommits` 写权威（`batch.go:497`，`transaction_manager.go:633-705`）

| 来源 | 错误 | 类别 | 说明 |
| --- | --- | --- | --- |
| `backend == nil`（`:645`） | `ErrRemoteWriteCapabilityDisabled` | 明确拒绝（没写） | 装配错误；写前返回 |
| 事务 ID 为零 / 空批 / 事务不一致（`:648-656`） | `ErrRemoteRejected` | 明确拒绝（没写） | 定稿后不可达，写前 |
| `commit.Validate()`（`:658`） | `ErrRemoteRejected` / `ErrRemoteVersionConflict` / `ErrRemoteFenced`（缺 ownership epoch） | 明确拒绝（没写） | 写前校验 |
| `validateRemoteCommitEncodable`（`:661`） | 编码错误 | 明确拒绝（没写） | 写前 |
| `trackRemoteTransaction`（`:667`） | `ErrRemoteOverloaded` | 过载，**没写** | tracker 在 `FinalizeLocked` 登记、Commit 前一直 pending（pending 不淘汰），实际不可达；即使发生也在写之前 |
| 后端 `CommitRemote(Batch)` 返回 fenced / 版本冲突 / rejected（`:679`） | 原错误（`ErrRemoteFenced` / `ErrRemoteVersionConflict` / `ErrRemoteRejected`） | **明确拒绝** | 权威 CAS 拒绝；tracker 记 Rejected |
| 后端其他错误（`:683-685`） | `ErrRemotePersistenceIndeterminate` + 原错误 | 结果未知 | 可能已写入 |
| 回执数不符 / `afterRemoteCommit` / `MarkRemoteCommitPublished` 失败（`:689-701`） | 带 `ErrRemotePersistenceIndeterminate` | 结果未知 | 已写入、发布未完成 |
| 另：`batch.go:513` 拒绝后本地回滚的 `RunLocal` 错误、`:519` 隔离错误 | 与上面 join | 附加 | 不改变类别 |

结论：Durability 0 下 fenced / conflict **算明确拒绝**；不带未知哨兵的错误全部发生在写前或是权威拒绝，“不带 = 没写入”成立。**本条不改这条路径。**

### strict（以及带 Remote 批次、随 strict 路径提交的 pipelined，`outcome.Durability` 为 2 / 3）：`Commit` 只等结论（`batch.go:500-505`）

| 来源 | 修前错误 | 类别 | 修后 |
| --- | --- | --- | --- |
| tracker 终态 Rejected（`transaction_tracking.go:190`）：投影器写权威得到 fenced / 版本冲突 / rejected（`transaction_manager.go:679`）、过期租约跳过（`dataengine/engine/mongo_projection.go:151` `RejectRemoteTransaction`）、回源 `CommitStatus` 得到持久 Rejected | `ErrRemoteRejected: <cause>`（fenced / 冲突只在文本里，不可 `errors.Is`） | **明确拒绝** | 不变（第 4 行） |
| tracker 终态 Indeterminate（`:192`）：投影器发布报告未知 | 带 `ErrRemotePersistenceIndeterminate` | 结果未知 | 不变（第 2 行） |
| 等待截止（`:180-182`，RR-20260927-24） | `ErrRemoteCommitTimeout` + `ErrRemotePersistenceIndeterminate` + ctx 错误 | 结果未知 | 不变（第 2 行） |
| **tracker 被容量淘汰后重新登记失败**（`:60`，本条 N1） | 裸 `ErrRemoteOverloaded` | 过载 / 未登记，**不说明没写** | 加 `ErrRemotePersistenceIndeterminate`（第 2 行） |
| tracker 被淘汰、重新登记成功（容量未满） | 新 tracker 为 Admitted，等到截止 | 结果未知 | 同截止（第 2 行） |
| `remoteStatusError` default（`:195`） | `ErrRemoteCommitNotFinalized` | 未定终态 | 不可达（关闭的 tracker 只有终态或 Indeterminate）；若出现加未知哨兵 |
| `trackedRemoteTransaction` 的 `m.remote == nil` / 事务 ID 为零（`:42`） | `ErrRemoteRejected` | 按明确拒绝 | 不可达（定稿后 ID 非零、Manager 已构造）；保持原样 |
| 重复调用 `Commit`（`b.committed`，`batch.go:472-485`）的 `RemoteCommitStatus` 查询失败 | 原错误 | 查询失败，不是拒绝 | 加未知哨兵（nest 只调用一次，仅为契约一致） |

另：`Commit` 开头的 `ErrRemoteCommitNotFinalized`（批次为 nil / 未定稿 / 已 Abort / 已 Close，`batch.go:465`、`:470`）是调用顺序错误，nest 不经过（`FinalizeLocked` 在本地提交前完成，
Abort / Close 只在 `finishRemoteWriteBatch` 的其他分支或之后），不属于“本地已提交后 Commit 的结论”，未改；`fctx.AssertBlockingAllowed` 在快 worker 上 panic，不是错误返回。

结论：strict 下 conflict / fenced **算明确拒绝**，但它们只以 `ErrRemoteRejected`（Rejected 终态）的形态出现；除此之外的一切等待失败都不说明 Remote 没写入。

## 决策

- **判据改在 remoteentity 源头**：新增 `waitedCommitError`（`batch.go:532-545`），等待分支（`:504`）与重复调用分支（`:479`）的错误，
  不是 `ErrRemoteRejected`、也还没带 `ErrRemotePersistenceIndeterminate` 的，`errors.Join(ErrRemotePersistenceIndeterminate, err)`；原因链保留
  （回归断言 `ErrRemoteOverloaded` 仍可 `errors.Is`），写法与 `ApplyRemoteCommits` 的未知分支一致。这样错误的类别与 `:508` 的收尾处理一致：
  strict 批次本来就按结果未知交给 finalizer，现在回复也说“结果未知”。nest 的判据（`msg.go:100`）不变，自定义 Remote 实现按 USER_GUIDE / entity 契约同样要求。
- **范围按“等待分支”而不是 `Durability == 2`**：带 Remote 批次的 pipelined handler 在 nest 里留在 strict 提交路径（`nest/execution.go:185-187`），`outcome.Durability=3`
  走同一个等待分支。修前它的过载错误同样被标第 4 行，而且 `:508` 的 `== 2` 不认它，批次不接手收尾（探针 `deferTook=0`）；修后过载带未知哨兵，`:508` 的第二个条件认它，
  由 finalizer 收尾（探针 `deferTook=1`）。回归包含这一形态。
- **B19 并存外层文案**：消息自己的本地事务已提交（`msg.remoteCommitted`，Remote 未确认——结果未知或被拒绝）而嵌套独立事务也已提交时，外层用未导出的
  `errNestedTransactionAlsoCommitted`（`nest/nest.go`），文本“nest: a nested isolated transaction also committed”，`Is` 只对 `ErrNestedTransactionCommitted` 为真。
  `errors.Is` 语义不变；判别表“先命中的行”不变（第 2 / 4 行在第 5 行之前）。唯一受影响的是按文本匹配的调用方——USER_GUIDE 一直要求不匹配文本，
  仓内（含 kit、codegen 模板与生成物）没有按这段文本或按 `==` / `errors.Unwrap` 比较它的代码（`rg` 核对），跨进程也不传这段文本（`Nest.Request*` 是进程内调用），
  所以改代码而不是只改文档。行 2 并存（Remote 结果未知 + 嵌套已提交）同样适用，一并改。
- **`replySentinels`**：按判别表 1～14 行列出判据，第 7 / 8 行按是否带 `ErrLockTimeout` 区分（新增 `with` / `without`），第 13 行列 `entity.ErrEntityRemoved`（来源由用例保证），
  第 14 行 `ErrNestCanceled` / `ErrNestTimeout`；不命中任何一行时 `firstTableRow` 返回兜底第 15 行（`err == nil` 返回 0）。`context.DeadlineExceeded` 仅打印（row 0）。
- 未采用：在 nest 侧改判据（例如只把 `ErrRemoteRejected` 当拒绝）——Durability 0 的权威拒绝是 `ErrRemoteVersionConflict` / `ErrRemoteFenced` 等，不带 `ErrRemoteRejected`，
  nest 侧无法区分 Durability，且修复约束要求在 remoteentity 源头补。

## 兼容性

- strict / pipelined 带 Remote 批次的消息：原先被误报为第 4 行的“没等到结论”类回复，现在带 `entity.ErrRemotePersistenceIndeterminate`、落在第 2 行，不再带
  `ErrRemotePartRejected`；文本多了 `remote entity persistence outcome is indeterminate` 一行。明确拒绝（`ErrRemoteRejected`）与 Durability 0 的回复不变。
- pipelined + Remote 的等待失败（非拒绝）现在交给 finalizer 收尾（与 strict 相同），提交后回调在拿到结论后执行一次；之前不接手，Sync 门保持冻结、AfterCommit 不执行。
- B19 / 行 2 并存形态回复的外层文本由 `nest: a nested isolated transaction committed before the message failed: …` 变为 `nest: a nested isolated transaction also committed: …`；
  `errors.Is(err, nest.ErrNestedTransactionCommitted)` 照常成立。
- 自定义 Remote 实现：没等到结论的失败必须带 `ErrRemotePersistenceIndeterminate`（契约早已如此，现在写进 entity godoc 与 USER_GUIDE）。
