# RR-20260914-08:去重身份表在两次 Tick 之间没有窗口上限

**仓库 / 位置**:roost-core `lockstep/sequencer.go`,`SubmitInput` / `remember` / `Advance`(U-0193 引入)。
**修复单元**:U-0197(C8)。**定位文档**:TROUBLESHOOTING T-91。

## 问题

U-0193 为"重传幂等"加了 `accepted[player][original]`,但 `SubmitInput` 对**所有**过去的原帧号都记身份,
只有 `Advance` 才按 `ReplayHorizon` 清理。两次 Tick 之间提交大量不同的旧帧号:pending 仍只有一帧,
`accepted` 却随旧帧号数量线性增长,而且下一次 `Advance` 还要遍历这些条目去删。审查实测:4096 次 Advance 后
单个座位连续提交原帧号 1..4096,得到 `accepted=4096 bounded_window=129 pending_frames=1`——上限由比赛历史长度
和本次处理的消息数决定,不由声明的 replay 窗口决定。

## 根因

准入路径与回收路径对"哪些身份值得留"用了不同的判据(C8):准入无条件记,回收才按期限筛。这是我上一轮
自己的修复留下的资源边界——加了"逐项列举"的结构却没在写入口收界。

## 方案选择

- **只提高清理频率(比如每次 SubmitInput 也扫一遍)。** 审查明确反对:那是把无界准入的代价挪到更热的路径。
- **拒绝超期限的首次迟到输入。** 会改掉 U-0193 已声明、审查已复核的边界行为(超期限输入仍按首次折入),
  超出本 RR 的范围。
- **固定容量环 + 准入期限判据(采用)。** 每个座位一个 `replayWindowSize = ReplayHorizon + MaxSubmitWindow + 1`
  = 129 槽的环,按 `original % replayWindowSize` 定位。任一时刻的合法原帧号区间是 `[next-ReplayHorizon, next+window]`,
  恰好 129 个值,两两之差小于环长,所以**期限内的原帧号不可能撞槽**。超期限的原帧号既不查也不记:不查是因为
  那个槽里的旧条目本就不可信,不记是因为写进去会让客户端用一个很旧的帧号挤掉一个仍然有效的身份(去重绕过)。
  于是准入即有界,`Advance` 的清理遍历整段删除——陈旧条目由"期限判据 + 被后来的同槽 id 覆盖"自然退休。

## 改动

`lockstep/sequencer.go`:`replayWindowSize` / `replaySlot`;`Sequencer.accepted` 由 `map[PlayerID]map[FrameID]FrameID`
改为 `map[PlayerID][]replaySlot`(按座位首次提交时惰性分配);新增 `replayFloor` / `slot`,`remember` 带
`inHorizon` 参数并对超期限直接返回;`SubmitInput` 查表前先算 `remembered`;`Advance` 删掉清理遍历。

## 证明

`lockstep/replay_window_promises_test.go`:
- `TestSubmitInputPromiseIdentityMemoryIsBoundedBetweenTicks`:4096 次 Advance 后灌入原帧号 1..4096,单座位身份
  结构不得超过 129,且洪水之后期限内的重传仍然幂等;
- `TestSubmitInputPromiseOutOfHorizonSubmissionDoesNotEvictAnIdentity`:150 与 21 落在同一槽,超期限的 21 不得挤掉
  期限内 150 的身份(环结构特有的风险,map 实现下修前修后都过);
- `TestSubmitInputPromiseOutOfHorizonReplayStillFolds`:把"超期限重传仍会折入"这条现在承载内存上界的边界钉住。

修前红:`one seat before the next tick: accepted=4096 bounded_window=129 pending_frames=1`。修后 lockstep 含 `-race`
全绿,core 全仓 `-race` 全绿。

顺带的性能变化(同机 before/after,`BenchmarkRoomTickTenPlayers -benchtime=2000x -count=3`,Apple Silicon):
修前 12739 / 8459 / 7001 ns/op,修后 3237 / 2965 / 2605 ns/op——每 tick 遍历所有座位所有身份的清理原本是主要开销。
只是本机快照,不推算生产吞吐。

## 未做 / 边界

- 超过 `ReplayHorizon`(64 帧)的重传仍会再次折入并被执行两次;这与 U-0193 一致,且现在是内存上界的组成部分
  (不记 = 不增长)。要让它也幂等需要确认水位协议,不在本轮。
- 环按座位惰性分配 129 槽 × 12 字节 ≈ 1.5KB;256 座位的房间约 396KB,只在这些座位真的提交过输入时才付。
- 记录型替身,没有真实传输或压测;审查也未做 OOM / 延迟压测。
