# RR-20260913-02:旧兴趣释放取消新订阅

**仓库 / 位置**:roost-core `remoteentity/interest.go`、`transaction_manager.go`,
`entity/remote_protocol.go`。**修复单元**:U-0184(C8)。**定位文档**:TROUBLESHOOTING T-78。

## 问题

真实 `Renew → Release → Renew` 生成三条消息;接收侧先收到新的 renewal,再收到迟到的旧 release,
当前兴趣被删掉。此后 `syncer` 的兴趣过滤静默跳过本该发送的快照更新,而本地仍认为兴趣有效、读时
续租还会合并请求。发布端按时间戳发,接收端按 key/SID 无条件删,两端对"哪次操作更新"没有共同判据。

## 根因

订阅没有代际。`ExpiresAt` 不能顶替:合法 release 的发布时刻通常**早于**它撤销的 lease 到期时刻,
按它比较会把每次合法 release 都判成旧的。

## 方案选择

- **用 ExpiresAt 当版本。** 上面说了为什么不行。
- **接收端记录"最近一次 release 的时间"并拒绝更早的 renew。** 只能防一个方向,而且仍依赖时钟。
- **发布端给每条消息一个只增的 Generation(采用)**。注册表按 (key, SID) 记 `{expiresAt, generation}`:
  renew 的代际落后于记录则忽略(不让 lease 倒退);release 只在代际不落后于记录时生效。计数器
  从 `UnixNano` 播种 —— 进程重启复用 SID 时,新计数从任何旧进程可能发出的值之上开始,不会出现
  "在途的旧 release 代际高于所有新 renew"。

## 改动

- `entity/remote_protocol.go`:`RemoteSnapshotInterest.Generation uint64`,随 JSON 自然进 wire。
- `remoteentity/interest.go`:`interestLease{expiresAt, generation}` 代替裸 int64;`renew` 忽略落后代际;
  `release(key, sid, generation)` 只删代际不落后的;`interested` / `pruneExpiredLocked` 改读字段。
- `remoteentity/transaction_manager.go`:`remoteState.interestGeneration atomic.Uint64`,
  `nextInterestGeneration()` 首次调用从时钟播种,Renew / Release 各盖一次;本进程自己回滚或清理
  本地兴趣时用当前已发出的最大代际,那两处没有重排问题。
- `InterestReplicaStore.ApplyReplica` 把 wire 里的代际传给 `release`。

## 证明

`remoteentity/interest_generation_promises_test.go` 两条:注册表层 —— renew(10)、renew(12)、迟到的
release(11) 之后仍 interested;release(13) 才取消;落后的 renew 不改动 lease。Manager 层 —— 三条
消息代际严格递增;新建一个 Manager(模拟重启复用 SID)发出的代际高于旧的。

修前红:`an older release canceled the newer renewal`。修后 remoteentity 含 `-race` 全绿。

## 未做 / 边界

- 旧版本发出的消息 `Generation` 为 0:它们的 release 只能取消同样为 0 的 lease,取消不了新版本的
  renewal —— 混合部署期间偏向"保留兴趣",安全方向。
- 代际是每个 Manager 一个计数器,不是每个 key 一个;这足够,因为比较只在同一个 (key, SID) 内进行。
- 审查提到的 Interest payload 与信封的绑定校验(类比 RR-20260913-03)没有一起做。
