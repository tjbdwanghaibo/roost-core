# RR-20260917-06：attribute feature 没有提供可使用的运行时契约（U-0230）

- 仓库：roost-core（新增 `attribute` 包）+ roost-codegen（`internal/attribute`、脚手架）
- 缺陷类：C4（feature 交付不完整）
- 优先级：P2；来源 Wanted-03 转入
- 相关：T-124；测试 `roost-core/attribute/container_promises_test.go`、`roost-codegen/scripts/attribute-runtime.sh`

## 问题

`roost add attribute` + 一个 profile 声明，生成的代码引用 `AttrID`、`AttrValue`、`AttributeMeta`、
`AttributeProfile`、`Snapshot`、`Container`、`Selector` 七个类型，三仓都不提供；脚手架只产出 `package attribute`。
空 feature 自身能编译，真写 profile 之后整包编译不过（`undefined: AttrID` …）。参考文档写的是"所在包需提供"，
但没有任何可直接实现/导入的权威契约——整条 feature 没有使用方。

## 根因

生成器是这套设计的一半，另一半从来没有落地。而且生成器给 `Snapshot` 与 `Container` **生成方法**
（`func (s Snapshot) X()` / `func (c *Container) X(...)`），所以另一半即便存在于 core，也不能用 type alias 引进来——
Go 不允许给外包类型定义方法。这是"只加别名"这条捷径走不通的原因，也是它长期没人补的原因。

## 方案

- 采用：**框架半进 core，生成半改成包级函数**。
  - 新增 `roost-core/attribute`：`AttrID` / `AttrValue` / `Meta` / `Profile`（生成物实现的接口）/
    `Selector` / `Snapshot`（Profile 是副本）/ `Container`（按层存放，Install / Live / Snapshot / Apply / Dirty / ClearDirty / Remove / Layers）。
  - 生成器不再给 `Snapshot` / `Container` 挂方法，改生成 `<Name>Of(Snapshot)`、`<Name>In(*Container, Selector)`、
    `<Name>Live(*Container, Selector)` 三个包级函数。于是工程侧的那七个名字可以全是 **alias**。
  - 脚手架为启用 `attribute` feature 的工程写 codegen 受控的 `game/gameplay/attribute/runtime.go`：把 core 的类型
    以生成物用的名字再导出，外加 `Base` / `Final` / `NewContainer`。
  - `dirtyMask` 约定显式化：profile 结构体必须自带 `dirtyMask uint64`，缺了在**生成期**报错
    （报在声明上，而不是让使用者去读生成文件的编译错误）。
- 没采用：只在工程侧定义七个类型（不进 core）。那样每个工程各写一份容器语义，"快照是副本"这种不变量没人保证。
- 没采用：给 `Snapshot` / `Container` 在工程侧做本地 wrapper 保留方法风格。能work，但每个工程多一层转换类型，
  而包级函数读起来一样好（`CombatIn(container, Base)`）。

## 改动

- roost-core：新增 `attribute/attribute.go`、`attribute/container.go`、`attribute/container_promises_test.go`。
- roost-codegen：`internal/attribute/gen.go`（三个包级访问器）、`internal/attribute/parse.go`（dirtyMask 守卫）、
  `internal/roost/attribute_runtime.go` + `render.go`（脚手架写 runtime.go）、
  `internal/attribute/testdata/runtime/` + `scripts/attribute-runtime.sh`（运行时门，接进 ci.yml，core 未发版时自跳过）、
  `docs/CODEGEN_REFERENCE.zh-CN.md` §11 重写；旧测试 fixture 补 `dirtyMask` 并新增"漏了 dirtyMask"用例。
- game-demo 因此可以真正用上这条 feature（B8）：`game/gameplay/attribute/combat.go` 三个属性、一个派生公式、
  `LevelUp` / `ForLevel`，随工程生成的 `combat_test.go` 断言派生跟随输入、派生属性不可直接写、容器快照是副本。

## 证明

修前（运行时门）：`undefined: AttrID` / `undefined: AttributeMeta` / `undefined: AttributeProfile` …，build failed。

修后：`sh scripts/attribute-runtime.sh` → `ok attributeruntime/combat`（类型化 setter 与 dirty 位、派生公式跟随输入、
元数据按 id 与两个名字可查、导出 / 载入往返保住派生值、容器快照是副本、未知层礼貌回答）；
core `go test ./attribute -race` 全绿；生成的 game-demo `go test ./game/... ./internal/...` 全绿。

## 未做 / 边界

- `Container` 只做"按层存放 + 快照"，**不做层间合成**（把 base 与 buff 叠成 final）。合成规则各游戏不同，
  等有真实需求再定；demo 只用一个 `Base` 层。
- 生成的构造函数名沿用 `New<TypeName>Profile`，所以类型叫 `CombatProfile` 会得到 `NewCombatProfileProfile`；
  本轮没有改命名约定，文档示例改用 `Combat`。
- 属性没有接进持久化与同步（DAO / entitysync）；那是 profile 的宿主决定的，demo 没有把 Combat 存进 Player DAO。
- **发版顺序**：`roost-core/attribute` 必须先发，codegen 的 demo 才能解析依赖；framework-compat 的
  released × demo 暂时排除，等 core v1.15.7。
