# RR-20260919-03：会话关闭的订阅者 panic 会带走整个进程（U-0247）

- 仓库：roost-codegen `internal/roost`（生成的 player TCP 接入层）
- 缺陷类：C3（错误路径无隔离）
- 优先级：P1
- 相关：T-141；测试 `internal/access/player/tcp/server_gen_test.go` 的
  `TestASubscriberPanicIsIsolated` / `TestAPanickingSubscriberDoesNotStopTheDispatcher`（生成物内）

## 问题

U-0243 给接入层加了会话关闭生命周期源：关闭路径只往有界队列投递，独立 goroutine 派发给订阅者。
派发函数复制订阅者列表之后直接 `fn(event)`，**没有逐订阅者 recover**。

那个 goroutine 是这个源自己的。Go 里没人恢复的 panic 终止整个进程——于是 scene 桥或 presence 桥里
一个 nil map，就把"某个玩家断线"变成"所有玩家掉线"。审查直接调用生成物的 `deliverClosed`，
panic 原样逃出。

## 根因

新加的回调边界没有跟上仓库里已有的约定。core 的 bus、Nest、configdata、room、etcd 都是**逐回调隔离**的；
这个源是 U-0243 现写的，隔离那一层漏了。

## 方案

- 采用：**逐订阅者 recover**。`deliverClosed` 改为遍历 `(id, fn)`，每个走 `callClosedSubscriber`：
  `defer recover()`，计 `player_tcp_session_closed_callback_panics_total`，日志带订阅者 id、
  player/session 身份和栈，然后**继续下一个订阅者**。
- 为什么后面的订阅者必须继续跑：它们维护的正是"谁在线"——scene 的成员集、chat 的世界频道收件人集。
  一个 panic 吃掉整批，等于让这些集合停在一个过时状态上，而它们是靠收敛而不是重放来保持正确的。
- 没采用：把订阅者放到各自的 goroutine 上。会让"一个关闭事件的处理顺序"不再确定，而现在的契约是
  "在派发 goroutine 上顺序执行、不要阻塞"；隔离用不着换掉这个契约。

## 改动

`internal/roost/render_player_tcp.go`：`deliverClosed` 带上订阅者 id，新增 `callClosedSubscriber`；
生成文件多 import `runtime/debug`。生成的测试文件加两条。

## 证明

修前（生成工程内直接跑）：

```
panic: subscriber blew up
	.../internal/access/player/tcp.(*Runtime).deliverClosed(...)
FAIL	example.com/rr3/internal/access/player/tcp
```

修后两条通过：一条断言 panic 前后的健康订阅者都执行、且**下一个事件仍然送达所有人**；
一条走真实路径（`publishClosed` → 派发 goroutine → `stopLifecycle` 排空）断言派发器没死。

## 未做 / 边界

- 只隔离 panic，不隔离**阻塞**。一个卡住的订阅者仍然会拖住这条派发链，这在 U-0243 的契约里是明说的
  （"不要在订阅者里阻塞"），队列有界是那一面的保护。
- 计数器新增，没有为它加告警；接进项目的 Prometheus 时应当把它当作"有订阅者在崩"的信号。
