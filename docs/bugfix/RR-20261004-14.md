## 根因（基线 `5d1cb974` 行号）

见问题记录：`confirmLocked:888` 以确认时刻的 `now()` 起算 `Lease`；`claim:1118` 设键之后 `:1126-1145` 的撤离等待、`renew:556` `Refresh` 自身的往返都排在起算点之前。
“另记”：`claim:1119-1121` 认领报错什么都不记，`renew:559` 对 Held 无条件 `confirmRenewal`，清掉 `interrupted`、延长窗口。

## 决策

### 一、窗口从设键那次请求发出的时刻起算（W-2026-10-04-07 本条）

- `confirmLocked(playerID, used, asked)`：`validUntil = asked + Lease`。Redis 在回答那次请求时才设 TTL，键至少活到 `asked + Lease`；本地窗口以它为界，`AdmissionGuard` 从这里往回量。
- `claim`：在 `store.Claim` **之前**取 `asked`，`confirmClaim(playerID, asked)`——跨间断的撤离等待（≤ `evictWait`）不再加到窗口上。
- `renew`：在 `store.Refresh` **之前**取 `asked`，`confirmRenewal(playerID, asked)`——`Refresh` 逐个玩家往返的耗时（Redis 卡顿时可达秒级）不再加到窗口上。
  这是 W 条目之外的同一行根因：RR-20261004-10 把确认挪到等待之前，但仍以 `Refresh` 返回之后的 `now()` 起算；当时记录里“`confirmLocked` 以 `Refresh` 发出时刻为基准”因要把时间戳穿过调用链而未采用，
  本条已经要给 `confirmLocked` 加这个参数，续租只多一个调用点，一并收掉；回归 `renewal` 子测试单独覆盖（变异：只回退续租的起算点 → 只有它红）。
- `lastUsed` 仍取确认时的 `now()`（“最近一次使用”是另一个问题，RR-20260920-11）。

**未采用：**
- 在 `store.Claim` **返回之后**取时刻：仍晚于 Redis 设 TTL 的时刻（差一个往返），方向不保守。
- 确认时从 `now()` 减去 `evictWait`：只对撤离等满的那一种情况恰好正确，撤离提前结束时又把窗口缩得过多；也不覆盖续租。
- 只改认领、续租照旧：同一行根因留一半，`Refresh` 慢时同样越界（见上）。

### 二、认领丢回复不能被下一轮续租“确认”（W 条目“另记”）

能在本单元内低成本关掉，且写出了确定性红（两个路径），一并修：

- `claim`：`store.Claim` 报错且 `!continuous`（跨间断）时调 `markUnansweredClaim`：锁内若该玩家仍有本地状态、且 `refusalLocked` 此刻拒绝（窗口跑完 / 已 `interrupted`），置 `interrupted = true`。
  - 刷新循环的重新认领：状态本来就是 `interrupted`，标记幂等；后台 `Owns` / 登录：窗口跑完的状态从“什么都没记”变成 `interrupted`，`Admit` 继续拒绝。
  - 不标的情况（接受侧）：只因撤离进行中被拒（RR-20261004-11，`refusalLocked` 为 nil），或等过一次放弃的归还后仍可服务（RR-20260921-03）——键从未中断，认领不可能“重建”它；
    没有本地状态（登录路径、本进程从没持有）——不在续租集合里，键自然过期，下一次 `Claim` 照常跨间断撤离（修前即如此）。
- `renew`：`confirmRenewal` 对 `interrupted` 的租约返回 false、不确认；`renew` 把它并入 `lost`，在同一份回合预算内走 `retakeOne` → `claim`：`Admit` 拒绝 → 跨间断 →
  `store.Claim`（键已是自己的则 `CompareAndExpire`）→ `dropResident` → `confirmClaim`；结局与键过期后重新认领完全相同（连接按 RR-20260930-23 关闭，撤离失败按 RR-20261001-07 `abandon`）。
  依据：`interrupted` 只在 Redis 答“不是我们的”时置位，此后键再是我们的只能是本进程的某次认领放回了 token；确认过的认领会清掉 `interrupted`，所以“`interrupted` 且 Held”= 一次没确认的认领（丢回复，或并发进行中）。
  并发进行中的那种（登录正在撤离）：重新认领加入同一次撤离，与修前“刷新循环重新认领”同一处理，不新增等待入口。

**未采用：**
- 认领报错时 `abandon`（删本地状态）：刷新循环路径会失去“下一轮再问 Redis”，玩家连接保持、所有写被拒，直到客户端自己重连；还要补关连接，等于把一次 Redis 抖动变成踢人。
- 认领报错时 `store.Release`（CompareAndDelete 自己的 token）：在刚失败的 Redis 上再加一次写；而且只关掉“丢回复”这一种来源，`renew` 对 Held 无条件确认的口子仍在。
- `renew` 把“窗口已跑完（`validUntil ≤ asked`）的 Held”一律当作间断重新认领：更宽，还能顺带关掉 [RR-20261001-07 记录](RR-20261001-07.md) §未验证项那条“并发续租抢先确认”的窄交错；
  但会把“续租回复全丢、实际都落地了”的长时间 Redis 故障变成所有玩家撤离重载并断线，行为面超出本条；留作后续候选（见未验证项）。
- 租约带世代号（RR-20260920-09 当时未采用）：根治“Refresh 分不出键的来历”，但改持久格式 / 协议，不属于本修复单元。

## 锁与等待顺序

- 不新增锁、不新增等待：`markUnansweredClaim` 与 `confirmRenewal` 的判断都在既有 `owners.mu` 下、不阻塞；取 `asked` 只读表时钟。
- 被改判为“重新认领”的 Held 租约进入 RR-20261004-10 的第二段（`retakeLost`），受同一份 `handBackPassBudget` 约束；刷新循环自己的 `claim` 仍在归还之前、同一 goroutine，不会等自己（RR-20260921-03 论证不变）。
- RR-20260921-04 的预算推导（“回合之前的续租把每把租约确认到 `Lease`”）现在以续租**发出**的时刻为起点，`Refresh` 自身的往返如实计入；它本来就在预算之外（RR-20261004-10 记录 §未验证项），未改。
