# RR-20261005-NC-233：Redis Mod 第一次 Close 之后交出 asm，错误只报告一次

2026-10-06，基线 `c8ecbabb`。**已修复、声明场景验证，未发版。** [问题](../bug/RR-20261005-NC-233.md) · [本轮](../review/REVIEW-2026-10-06-n01b.md) · [证据](evidence/noncore-bugfix-20261006-n01b/README.md)。

## 根因

`RedisMod.StopWithContext` 把“Close 返回 nil”当成“已释放”，只在成功时置空 `m.asm`。go-redis 的 Close 不等在途命令、先置 closed 再关连接，返回错误时连接池同样已经释放。

## 修法

第一次 Stop 先取出并置空 `m.asm` 再 `Close`；Close 的错误包成 “redis mod: close (the connection pool is closed regardless): …” 返回一次，之后的 Stop 返回 nil。用 [A3 停机契约](../feature/REFACTOR-2026-10-05-shared-stop-contract.md)核对：Redis 的 Close 不等待在途工作（在途命令随之失败），骨架的第 1～3 步（超时保留、重试再等）不适用，适用的是第 4 步“已停完再调用返回 nil”，用例只钉这一步，没有套 `stopcontract.Check`。

没采用：在 `redis/driver.Client.Close` 记住第一次结果、之后返回同一个错误（etcd NC-173 残余的做法）——那样重试仍然永远失败，O3 要解决的正是这一点；etcd 的情形里第一次结果是 nil，两者不冲突。

## 兼容

Close 出错之后健康检查从 “ping failed: client is closed” 变为 “client not initialized”，状态同为 Fail（只发生在停机之后）。

## 验证

修前红见问题记录；修后 `TestRedisModStopConvergesAfterACloseError` 通过；`GOWORK=off go test -race -count=3 ./kit/redis/`、`go vet` 通过。未跑 integration（改动不涉及与 Redis 的交互）。
