# RR-20261004-NC-01：逐 Manager 停止 panic 隔离

2026-10-04，修前 `7e0d6ee29a134e75db142fda94ef93332b8e9841`。[原问题](../bug/REVIEW-2026-10-04-noncore-02.md#rr-20261004-nc-01)。已修复、声明场景验证，未发版。

根因在原 manager/engine.go:203–233：started 先转移，stopOne panic 会打断余下清理。现在只在既有 stopOne 增加逐对象 recover，名字在保护范围内读取，panic 为 error 时保留 errors.Is cause；普通 Stop/StopWithContext、启动失败 rollback、最后一个 Start 与 Stop 交错的单对象清理均复用此边界。保留逆序、锁外用户回调与失败 manager 自清理规则。

未采用整个 Mod recover（无法回到内部循环）、重复启动所有对象或无界重试。出错对象是否实际结束仍由其实现负责；本修复承诺继续清理其他对象并上报，不能保证 panic 对象已释放。

正式修前两 Stop 反例与 rollback 反例：`panic=stop boom error=<nil> older_stops=0`；修后同断言均通过，Start cause 保留，older_stops=1。追加 error panic 的 errors.Is 原因与最后一次 startup handover 控制，既有 Manager 停止交错用例/race 全通过。[红绿与复跑](evidence/noncore-bugfix-20261004-02/README.md)。正式回归 manager/engine_lifecycle_promises_test.go，T-187。

公开签名/数据/依赖不变，panic 变为返回 error；Kit ManagerMod.Stop 的既有日志现在能记录异常。完整 App 故障进程、永久阻塞 callback、跨进程资源清理未验证，不扩张为所有生命周期故障均收敛。
