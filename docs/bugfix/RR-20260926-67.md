# RR-20260926-67 修复：Guard 以实例判断是否已持有，handler 内 Destroy 后重建的同 ID 实例取锁并纳入提交边界

问题：[RR-20260926-67](../bug/RR-20260926-67.md)（探针 [REPRO-2026-09-26-06](../bug/REPRO-2026-09-26-06.md) §3 P-D）。
日期 2026-09-27；实施基线本地 main `2373e21`，建立在同批 RR-64（`b4018e7`）、RR-65（`6a2e1aa`）之上。
状态：已修复、本地验证通过，已本地提交，未推送 / 未发布。方向按修复约束：Guard 以实例（而非仅 ID）判断是否已持有；同 ID 新实例在 handler
内按 RR-48 规则取锁并纳入提交边界；Destroy 后同 ID 重建的回滚语义保持。

## 根因（基线源码核对）

- `entity/entity_manager.go` `Destroy`：在实体锁（可重入，handler 的 Guard 已持有一层）内摘索引、标记 removed，返回前
  `LockManager.ReleaseLock(id)`，之后 `GetLock(id)` 给出**新的** mutex。Guard 的 `eMap` 仍以 ID 记着旧实例（其锁仍被持有一层，直到 Guard 释放）。
- `entity/manager_factory.go` `CreateInScope` → `build` 用新 mutex 构造新实例；`lockedNow := !guard.Guarded(id)` 为假，
  `lockCreated` → `mayLock(id)` 按 ID 认为已持有 → `RequireEntity` 见 `eMap[id]` 存在直接返回 true：新实例的锁从未取得就发布，
  handler 随后修改一个其他 goroutine 可以加锁的实体（探针 `sameMutex=false freshLockableByOtherGoroutineMidHandler=true`）。
- 同源：`CheckContainAllLock`、Cast / 派发 / 组锁的“已持有则跳过加锁”（`nest/cast.go`、`nest/nest_dispatch.go`、`nest/group_lock.go`）都按 ID 判断；
  Destroy 后别处重建同 ID、handler 再 Cast 它会拿到未加锁的新实例（新增回归证实）。

## 决策与实现（`entity/entity_guard.go`）

- **“已持有”按实例**：`holding(ent)` —— `eMap[id]` 是同一实例，或同 ID 且共用同一把 mutex 的另一实例（Destroy 之前重复构建，例如
  handler 内对已持有的 X 再 `Create(X)`：同一把锁已持有，不重复加锁，随后 `TryAdd` 得 `ErrEntityExists`，行为不变）都算已持有；
  同 ID 但 mutex 不同的旧实例作为 stale 返回，不代表新实例的锁。
- **取得新锁时保留旧锁的所有权**：`RequireEntity` / `TryRequireEntity` 取得新实例的锁后 `hold`：新实例进 `eMap`，旧实例连同它仍被本 Guard
  持有的锁移入 `superseded`（记下 ID，旧实例可能已被清理、ID 归零）。Guard 释放时先释放 `eMap`、再释放 `superseded`（旧实例仍运行
  release hook，与修前它留在 `eMap` 里时相同）；`ReleaseEntity(id)` 释放当前实例后把被取代的旧实例放回 `eMap`——锁仍被持有，锁序
  判断（`maxLockedGroup`）与 `Guarded` 仍要算上它。`doReleaseEntity` 只在它仍是该 ID 的当前实例时才从 `eMap` 删除。
- **锁序按实例**：`mayLockEntity(ent)` 用于 `CheckContainAllLock` 与 `lockCreated`。同 ID 换了锁的新实例不是已持有，而它的锁组与本 Guard
  持有的旧实例相同，所以不满足锁序：handler 内新建走 RR-48 的 try-lock（新锁无人持有即成功，被占用则按 RR-48 / RR-64 给冲突错误）；
  Cast 返回 `ErrCastDeadlockRisk`；嵌套派发改用 try-lock。`CheckContainAllIDs`（加载前按 ID 预检）不变。
- **跳过加锁的调用点改为按实例**：新导出 `(*EntityGuard).GuardedEntity(ent)`；`CreateInScope` 的 `lockedNow`、`CastMulti`、
  `lockDispatchEntities`、`tryLockDispatchEntities` 改用它。`Guarded(id)` 保留按 ID 的语义，其余调用点（Remote 批次 Abort 判断、Sync 锁内判断、
  Remote 未声明目标预检）问的是“这个 ID 是否在本 Guard 锁内”，不改。
- **提交边界与回滚**：新实例经正常 `CreateInScope` 路径被事务捕获、加入 SyncMutation，回滚 / 拒绝时按 RR-35 撤销发布；旧实例的销毁
  不回滚（`Destroy` 不是事务操作，修前修后相同）。未改 `Destroy`。

未采用：在 `Destroy` 里从 Guard 摘掉旧实例并立即解锁——旧实例的 release hook 会在 handler 中途运行，且 Destroy 不知道调用方是否持有该 Guard；
新实例直接覆盖 `eMap[id]` 而不保留旧锁——旧 mutex 永远不解锁，拿到旧指针在 `RequireEntity` 上等待的 goroutine 会永久阻塞。

- `entity/entity_guard.go`：`superseded` / `heldEntity`、`holding`、`hold`、`mayLockEntity`、`GuardedEntity`、`ReleaseEntity` 恢复旧实例、释放顺序。
- `entity/manager_factory.go`：`lockedNow` 按实例。

## 兼容性 / 行为变化

- handler 内 Destroy 后同 ID 重建：新实例现在持锁到 handler 结束并进入提交边界（此前未加锁发布）。
- handler 内 Destroy 后，别处已重建同 ID、handler 再 Cast 它：返回 `ErrCastDeadlockRisk`（此前返回未加锁的新实例）。
- 新导出 `(*entity.EntityGuard).GuardedEntity`。`Guarded(id)`、`Entities()` 语义不变（`Entities()` 只列当前实例，不列被取代的旧实例）。
- 无配置、持久格式变化；正常路径（没有同 ID 换锁）多一次接口比较，无分配。

## 对抗性自查

- **RR-48 死锁不回来**：会等待的取锁仍只有三类且遵守同一全序（声明目标排序、Cast / Create 向更高锁组）。新增的“同 ID 换锁”情形一律按
  不满足锁序处理（try-lock 或拒绝），不会引入新的等待边；`maxLockedGroup` 仍覆盖被取代的旧锁（同 ID、在 `eMap` 或随 `ReleaseEntity` 放回）。
- **没有锁泄漏 / 双重解锁**：每把取得的锁只在一个位置记账（`eMap` 当前实例或 `superseded`），释放各一次；同 mutex 的重复实例不再加锁，
  也就不会多解一次（`TestGuardTreatsInstanceSharingTheHeldMutexAsHeld`）。`clean()` 清空 `superseded`，Guard 归还池时不残留。
- **RR-35 提交边界**：新实例经原 `CreateInScope` 路径捕获、Include、撤销；`revokeCreated` 的“索引里仍是这个实例”检查未改。
  strict 下新实例进入提交记录，回滚时撤销并不持久（回归覆盖）。
- **已提交内容不被重复执行**：本 RR 不改重排与提交点；新实例取锁失败时走 RR-48 / RR-64 的既有错误路径。
- **快池不阻塞**：同 ID 换锁时只 try-lock（新锁通常无人持有）；未增加等待入口。
- **并发访问者**：拿到旧实例指针、在旧 mutex 上等待的 goroutine 在 Guard 释放 `superseded` 后取得旧锁，看到 removed 退出（`GetLock` 契约）。

## 未验证项 / 风险

- 自定义 `lock.Mutex` 实现若为不可比较的值类型，`holding` 的接口比较会 panic；框架内实现均为指针类型（`ReentrantMutex`、`defaultMutex`），
  `Lock/Unlock` 需要可变状态，值类型实现实际不可用。
- Remote 实体（慢阶段准备 + 远端锁）的 Destroy 后同 ID 重建未单独构造回归。
