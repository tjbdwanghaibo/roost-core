# NC-170 修复：manager Engine 停止按三步，超时保留没停完的 manager 与它的依赖

[问题](../bug/RR-20261005-NC-170.md) · [证据](evidence/noncore-bugfix-20261005-stopshape/README.md)。提交 `c99a687d`。已修复、声明场景验证，未发版。

## 决策与实现

`manager/engine.go` `stopStarted` 改为三步（roost-coding 生命周期复审要点）：

1. 发起：锁内置 `stopping`（幂等），Start 据此中止；`started` 为 nil 时置成非 nil 空切片（保持“生命周期已结束、拒绝 Register”的旧语义）。
2. 等待：取得停止执行权（新增 `stopTurn`，容量 1 的通道；等待者按自己的 ctx 离开）后，逆序取 `started` 末尾的 manager 停止。停完（含普通错误、panic 被隔离成错误）才从 `started` 移除；返回 `context.Canceled` / `DeadlineExceeded` 时立即返回，不在过期 ctx 下继续停依赖。每次停之前先看 ctx。
3. 释放：没停完的 manager 与更早启动的都留在 `started`，新 ctx 重试从它继续；全部停完后 `Stop` 返回 nil。

判定“没停完”与 App 的 `stopIncomplete` 相同（ctx 错误），普通错误照旧算停完、其余 manager 继续停、全部错误 `errors.Join`（`TestEngineStopReportsEveryFailureAndStillStopsTheRest` 保持）。Start 回滚路径仍用 `fctx.BaseContext()` 调同一函数；最后一个 manager 启动期间被 Stop 的路径（RR-20260916-06）仍直接 `stopOne`，不经执行权（那时 `stopping` 已置位，它不在 `started` 里）。

## 兼容性

`Engine.Stop` / `ManagerMod.StopWithContext` 在预算耗尽时不再继续停更早的 manager，而是返回 ctx 错误并保留它们；App 本来就会把 ctx 错误当停机不完整并保留后续 Mod，行为一致。直接重试的调用方现在会等到真实停完。API 不变。

## 未验证 / 风险

不配合 ctx 的 `StopWithContext` 不会被终止，只是如实超时并保留；只实现 `Stop()` 的 manager 没有期限，一旦阻塞仍会拖住执行权（与修前相同）。
