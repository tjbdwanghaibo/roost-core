# NC-91 修复：派发池拒绝的轻量 RPC 立即回失败包，不再进入死信

[问题](../bug/RR-20261005-NC-91.md) · [证据](evidence/noncore-bugfix-20261005-n03/README.md) · [本轮](../review/REVIEW-2026-10-05-noncore-n03.md)。已修复、声明场景验证（含真实 NATS），未发版。

## 根因

基线 `bus/bus.go:761-789` 的 `dispatchTask` 对“派发器不在运行”和“`pool.Dispatch` 失败（队列满 / worker 已关）”两种拒绝只记日志、指标并 `deadLetter`，不区分 RPC 与消息。RPC 调用方因此收不到任何回包；死信条目（`bus/reliable.go:119-136`）不保存 reply / SessionId，重放（`:258-274`）只能把它发成普通模块消息。

## 修法

新增 `refuseTask`：消息照旧写死信；RPC 请求带 reply 时立即回 `encodeRPCFailure`（原因包裹内部的 `errRPCNotAdmitted` 与拒绝原因），不写死信；没有 reply（不应出现）只返回。与“无 handler”“非法请求信封”两条既有拒绝路径一致。

未采用：为“未准入”新增一个对外 errcode——bus 目前没有自己的错误码段，新增码属于线协议变化，需要维护者定码段；本次沿用无 handler 拒绝的 `CodeInternal`（调用方得到 `remote.1: server error`）。

## 兼容与边界

- 调用方原来在过载 / 停机窗口等满超时得到 `request timeout`，现在立即得到远端错误。按“超时即重试”写的调用方，现在需把这个远端错误视为“未执行、可换实例重试”；它与业务返回的普通错误同码，目前无法仅凭错误码区分（见上）。
- 死信里不再出现 RPC 请求；`bus_dispatch_drop_total` 指标照旧计数。
- JetStream RPC 不经过这个池，不受影响。

## 验证

- 修前红（`GOWORK=off go test -count=1 -run TestRefusedRPC ./bus/`）：

  ```
  dispatcher not running: no reply; the caller waits for its whole timeout and sees an unknown outcome
  1 refused RPC requests written to the dead-letter queue, first {MsgID:not-running ... Reason:dispatcher not running ...}
  queue full: no reply; the caller waits for its whole timeout and sees an unknown outcome
  48 refused RPC requests written to the dead-letter queue, first {MsgID:queued-16 ... Reason:dispatch failed: worker: queue full ...}
  ```

- 修后绿：两条用例通过，`TestReliableDispatchDropGoesToDeadLetter`（消息仍进死信）通过；真实 NATS 满队列探针由 `request timeout elapsed=2.00182475s` 变为 `err=remote.1: server error elapsed=293.375µs`。
- `GOWORK=off go test -race -count=3 ./bus/ ./kit/nats/` 通过。
- 未验证：长时间过载下调用方重试策略的整体效果（容量问题，不在本条）。
