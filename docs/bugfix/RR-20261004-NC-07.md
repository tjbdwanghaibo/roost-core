# RR-20261004-NC-07：生成与注册共用 chi 模式校验

2026-10-04，起点 `c4aa1e7d`。[原问题](../bug/REVIEW-2026-10-04-noncore-04.md#rr-20261004-nc-07)已修、声明场景验证，未发版；T-193。

新增 `webroute.ValidatePath(path) error`，在一次性 chi router 上安装空 handler，复用当前依赖的正式语法；解析 panic 转含 path 的 error。既有 `Registrar.Register` 在触达应用 router 前校验，Codegen `parseRoute` 在扫描阶段调用同一入口，因此坏模式尚未写任何产物就失败。保留生成器原基础路径 `invalid path` 错误文本；首次包回归捕获了该文本变化，定向更正并保留原失败证据。

实际 installer 的 panic 也转 error（error 原因用 %w），seen 只在安装成功后写入；锁随 error 释放。普通 chi 坏模式只修改一次性校验 router，不会半改业务 router。自定义 RouteRegistrar 可能先安装再 panic，本框架无法回滚外部对象；遇这种失败应重建 router，不将 error 理解为任意 installer 的原子回滚。注册仍用于启动阶段，不允许与实际请求并发热改 chi router。

正式 runtime 三个非法模式与自定义 installer 失败四项修前红，Codegen 三个坏模式/保持原文件三项红；十个合法参数、正则（含嵌套量词）、通配符控制通过。修后这17项全部通过，[正式日志](evidence/noncore-bugfix-20261004-03/README.md)。

实际构建 `codegen/cmd/webroute` CLI，四个独立业务 module：正常生成、8次 HTTP 控制和2次退役404均通过；三个非法模式现在 generation_exit=1、包含 handler/path、没有新产物。另给三个 module 放入旧生成物，再编译调用正式 Module 注册，均正常返回启动 error、没有 panic（consumer_exit=0）。不是依靠重新生成才能保护旧消费者。

生成形状、已有正常路由与字面 method/path 去重规则不变；不同参数名但匹配形状相同的覆盖仍为契约观察。校验会增加启动阶段 scratch-router 分配，本轮未测吞吐或启动时间；不是请求热路径。没有发版/tag、跨版本发布消费者或生产部署验收。

## 复核后的补修（2026-10-04，A 线发版前）

`49796514` 让 `codegen/internal/webroute/parse.go` import 了 core 运行时包 `roost-core/webroute`（为复用 `ValidatePath`），违反生成器层“不得 import core 层”的边界，根包 `TestCoreDependencyBoundary` 从 10-04 起在 ci（linux-test (1)、windows-compatibility）与 nightly 上红。补修：生成器内 `validateChiPath` 直接调用 chi 的解析器（与运行期 `webroute.ValidatePath` 同一语法，同样 recover chi 的 panic），去掉对 core 包的 import。修前红：`dependency_boundary_test.go:60: codegen/internal/webroute/parse.go (codegen layer): 生成器保持独立于它生成的运行时，不得 import core 层: github.com/tjbdwanghaibo/roost-core/webroute`；修后 `TestCoreDependencyBoundary` PASS，`go test ./codegen/internal/webroute/ ./webroute/` ok。
