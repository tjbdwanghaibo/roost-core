# RR-20260912-01:nestwal Shutdown 等待后台重放锁时忽略截止时间

**仓库 / 位置**:roost-core `nestwal/committer.go`,`Flush`、`replayPass`、`Shutdown`。
**修复单元**:U-0186(C1)。**定位文档**:TROUBLESHOOTING T-80。

## 问题

后台 `run` 循环的 `replayPass` 正在 `ApplyMutations`,持有 `replayMu`;调用方带 20ms 截止时间调
`Shutdown`。`Shutdown` 先 `Flush`,`Flush` 进 `replayPass` 后阻塞在没有 context 的 `replayMu.Lock()`。
applier 正确监听传进来的 context——但那是 committer 自己的 context,只有后面的 `Close` 才会 cancel。
调用方的截止时间管不到这段等锁:审查实测 20ms 到期后再等 50ms 仍不返回,释放 applier 后才退出。
并发的两个 `Flush` 在 `flushMu` 上是同一形状。

## 根因

"等待 Flush / replay 所有权"是一次可能很长的远程等待(下游投影器),却用 `sync.Mutex` 表达——
它没有带 context 的获取。锁内部的远程调用(C1)。

## 方案选择

- **Shutdown 先 Close 再 Flush。** 取消后台 pass 确实能更快拿到锁,但 Flush 的含义就变成"在已取消的
  committer 上排空",而且 `CloseWAL` 时 WAL 已关闭,Flush 的 Sync 会失败;审查也明确不建议靠并发关闭
  绕过锁。
- **把 replayMu 换成 TryLock 加退避轮询。** 能遵守 ctx,但把等待改成了轮询。
- **一格信号量(采用)。** `flushSem` / `replaySem` 是容量 1 的 channel,`acquireSlot(ctx, sem)` 在
  `sem <- struct{}{}` 与 `ctx.Done()` 之间 select。语义与互斥锁完全一致(同一时刻只有一个持有者),
  只是等待可取消。后台 `run` 传的是 `c.ctx`,Close 的 cancel 照样能把它从等待里唤醒。`Shutdown` 不变:
  Flush 超时返回 ctx 错误,接着 Close 触发 cancel(其自身也按 ctx 返回),状态仍可收尾——之后再调一次
  不带截止时间的 Close 会等到后台退出。

## 改动

`nestwal/committer.go`:`flushMu` / `replayMu` → `flushSem` / `replaySem`(构造时 `make(chan struct{}, 1)`);
`Flush` 与 `replayPass` 用 `acquireSlot` 获取、`<-sem` 释放;新增 `acquireSlot`。

## 证明

`nestwal/shutdown_deadline_promises_test.go`:
- `TestCommitterShutdownPromiseHonoursDeadlineWhileReplayBusy`:applier 卡住(同时监听自己的 ctx),
  20ms 的 `Shutdown` 必须在 300ms 内返回 `context.DeadlineExceeded`。
- `TestCommitterFlushPromiseHonoursDeadlineBehindAnotherFlush`:后台循环退避一小时,第一个 Flush
  在 applier 里,第二个带 20ms ctx 的 Flush 必须按时返回。

修前红:`Shutdown stayed blocked behind background replay after its context expired`(第二条同形)。
修后 nestwal 含 `-race` 全绿(第一版测试自己有一处对 `release` 变量的重赋值竞争,已改成 `sync.Once`)。

## 未做 / 边界

- 没有引入"优雅排空 vs 停止重试"两阶段状态机;现有 Shutdown = Flush + Close 的形状保留,只是等待
  可取消。超时返回后后台 pass 仍可能在 applier 里,直到它自己观察到 `c.ctx` 取消。
- `WAL.replayMu`(读端串行化)仍是 `sync.Mutex`:它只包住本地文件读,没有远程调用。
