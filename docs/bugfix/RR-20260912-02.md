# RR-20260912-02:WAL.Sync 成功返回时已准入 ticket 仍未写入

**仓库 / 位置**:roost-core `nestwal/wal.go`,`Sync`、`collectBatch`、`processBatch`。
**修复单元**:U-0185(C8)。**定位文档**:TROUBLESHOOTING T-79。

## 问题

`Enqueue` 成功返回 ticket 后,记录还在 `appendCh` 里,或 writer 正在 `collectBatch` 里等 `BatchDelay`。
此时调 `Sync`:它只检查 ctx / terminal,然后 fsync 当前 active 文件。没写进文件的字节不在这次 fsync
的范围内,于是 Sync 返回 nil 而 ticket 未完成、`DurableLSN` 仍是 0。依赖 "Sync(nil) 等于之前接收的写
全部持久化" 的调用方(`Committer.Flush` 第一步就是它)会提前推进自己的状态。

## 根因

注释写着"Append 已经等物理写入,所以不需要队列屏障"——这在只有同步 `Append` 的时代是对的。
`Enqueue` 引入了"准入即返回、稍后写入"的异步路径,Sync 的契约没有跟着更新:快路径(Append)与
慢路径(Enqueue)对 Sync 的语义不一致(C8)。

## 方案选择

- **轮询 `durableLSN >= 准入边界`。** 只解决等待,不解决"writer 还在等 BatchDelay",默认 500µs 还好,
  但契约不能依赖一个可配置的延迟;而且轮询本身是坏味道。
- **单独的 kick 信号让 collectBatch 提前收批。** 需要另外记住"哪条 LSN 之前算准入",kick 与
  writer 空闲态的竞争还会让 kick 被吞掉或滞留成一次多余的小批次。
- **有序屏障请求(采用)。** Sync 往同一条 `appendCh` 里放一个不带 frame 的 `barrier` 请求。FIFO 保证
  writer 处理到它时,它前面所有已准入的请求都已经写入(或 WAL 已进 terminal);`collectBatch` 见到
  屏障立即收批,不再坐等 BatchDelay;`processBatch` 先写记录再答复屏障,并把终止错误带给它。屏障
  答复后 Sync 再 `syncActive()` fsync。等待遵守 ctx;WAL 已关闭时队列已被 `drainAndClose` 排空,屏障
  空满足直接返回 nil,不会卡在没人接收的 send 上。

## 改动

`nestwal/wal.go`:`appendRequest.barrier`;`Sync` → `awaitWriteBarrier(ctx)` → `syncActive()`;
`awaitWriteBarrier` 在 `enqueueMu` 下取 `nextLSN` 作边界,`durableLSN` 已覆盖且队列为空时跳过往返;
`collectBatch` 见屏障即返回;`processBatch` 拆成"记录部分 `processRecords` 返回终止错误 + 答复屏障"。
容量拒绝(unreserved 的 disk_cap)不是持久化失败,不会传给屏障。

## 证明

`nestwal/sync_barrier_promises_test.go`:
- `TestWALSyncPromiseCoversAdmittedTickets`:`BatchDelay=time.Hour`,Enqueue 一条,500ms ctx 的 Sync
  必须返回 nil 且 ticket 已 Done、`DurableLSN() >= ticket.LSN()`。
- `TestWALSyncPromiseDoesNotBlockAfterClose`:干净 Close 之后 Sync 立即返回 nil(屏障的回归保护)。

修前红:`Sync returned nil before admitted ticket resolved: admitted=1 appended=0 durable_lsn=0 ticket_lsn=1`。
修后 nestwal 含 `-race` 全绿。

## 未做 / 边界

- Sync 的 ctx 取消只放弃等待,不改变任何状态,下一次 Sync 会重做;没有单独测 writer 卡在 fsync
  时的取消路径(需要能卡住的文件替身)。
- 干净 Close 之后 Sync 返回 nil 而不是 `ErrClosed`:Close 已排空并 fsync 了全部队列,契约是满足的;
  这是有意的选择,避免停机顺序里 Flush 晚于 WAL Close 的调用方突然报错。
