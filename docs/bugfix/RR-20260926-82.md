# RR-20260926-82 修复：dataengine/engine 包测试可重复运行（kind 冲突、驱逐队列断言的时序假设）

问题：[RR-20260926-82](../bug/RR-20260926-82.md)。
日期 2026-09-27；实施基线本地 main `8d06d80`，在同批 RR-81 提交之后（未推送）。状态：已修复、本地验证通过，已本地提交，未推送 / 未发布。
方向按修复约束：只改测试，用到全局注册表的用例使用互不冲突的 kind；不改生产注册语义、不新增导出 API。
codebase-memory 图谱对这些文件已过期（generation 09-26 08:36），结论来自当前源码。

## 根因（指到行，基线 `8d06d80`）

1. **kind 冲突（主记录的失败）**：`dataengine/engine/fenced_step_resync_test.go:23` `const fencedResyncKind entity.EntityKind = 243`，
   与 `entity_repository_load_promises_test.go:15` 的 `dataEngineNoBuilderKind = 243` 相同。kind 注册表是进程级的
   （`entity/entity_factory.go` `kindEntries`），两处各自用 `sync.Once` 注册一次：load 用例只登记 243 的类别（`:45`），期望
   `LoadEntity` 报“no builder for entity kind 243”（`:96`）；fenced 用例随后给 243 注册了 builder（`fenced_step_resync_test.go:67`）。
   第一轮按文件顺序 load 用例先跑，通过；同一进程的第二轮 243 已有 builder，加载走到聚合查找，报 `entity aggregate not found`。
2. **修掉 1 后暴露的时序假设**：`fenced_eviction_once_test.go:25-35` `TestSkippedFencedStepIsQueuedForEvictionOnce` 在 5 轮 `ReplayPass` 之后立即断言
   `len(projector.evictQueue) == 0`。第一轮登记的驱逐项由 `startStaleEviction`（`fenced_step.go:119-124`）放进队列并启动 worker，worker 在
   `runEvictions`（`:140-146`）里才取走它；worker goroutine 还没被调度时队列里正是那唯一一项，断言把它误报为“重投多排了 1 次”。
   与全局状态无关，重复运行 / 负载高时偶发（单跑该用例 `-count=200` 两次：一次 FAIL（失败次数未计），一次 0 失败）。

## 决策、文件与行为

- `fenced_step_resync_test.go`：`fencedResyncKind` 改为 248（同包测试已用 71～73、235、236、239～247），注释写明为什么必须与同包其他 kind 不同。
  选择换 kind 而不是撤销注册：注册表没有撤销入口，约束不允许新增导出 API；给测试加未导出的撤销入口要改 `entity` 包，
  而冲突本身只是两个常量撞号，换号即可消除。
- `fenced_eviction_once_test.go`：第一轮 `ReplayPass` 之后先 `awaitChan(recorder.failed)`——驱逐 worker 已取走第一项并进入失败重试（`recorder.fail` 为真），
  之后 4 轮重投若再登记就会留在队列里，断言只数这些多排的项。RR-50 的承诺（重投不再排队）与原断言文本不变；修 RR-50 之前的实现
  每轮重投都会排队，worker 卡在退避里，队列仍非空，负对照照样成立。
- 无生产代码、配置、导出 API 变化。

## 兼容性与迁移

无。只改测试文件。
