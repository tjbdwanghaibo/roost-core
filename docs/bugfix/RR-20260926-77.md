# RR-20260926-77 修复：“是否已提交 / 能否重试”判别表与停机文档如实改写

问题：[RR-20260926-77](../bug/RR-20260926-77.md)。日期 2026-09-27；实施基线本地 main `62fdbe6`，在同批 RR-73～76（新哨兵定型）之后写。
状态：已修复（纯文档 + godoc），已本地提交，未推送 / 未发布。方向按修复约束：只改文档与导出符号的 godoc。

## 根因（基线文档与源码核对）

1. `docs/USER_GUIDE.md`（2026-09-26 Remote 收尾链路一节）的 RR-46 / 53 指引把 `errors.Is(err, nest.ErrAfterCommitFailed)` 当作“是否已提交”的判据。
   RR-65 之后，嵌套独立事务已提交、外层失败时回复是 `ErrNestedTransactionCommitted` 包着外层原因（`nest/nest_dispatch.go` 回复包装处），
   外层原因为锁超时时同时满足 `ErrLockTimeout` 而不带 `ErrAfterCommitFailed`，按旧指引写重试的调用方会重复执行已提交的独立事务。
2. `ErrCreatedEntityLockConflict` 的 godoc 与 USER_GUIDE §4 说“可回滚事务里它与 `ErrLockTimeout` 并存 = 已回滚、已重排、次数耗尽”。
   外层已有嵌套提交时 `transactionPastCommitPoint` 为真，消息不重排，回复同样两者并存（另带 `ErrNestedTransactionCommitted`）。
3. `docs/DEPLOYMENT.md` §8：“调大 `total_timeout` / `dataengine.shutdown_timeout` 后执行 `roost project sync` 即重算宽限期”。
   `codegen/internal/roost/shutdown_budget.go` `serviceShutdownPlan` 按常量 `generatedDataEngineShutdownTimeout`（30s）计 dataengine 的声明预算，
   `configuredShutdownTotal` 只读 `shutdown.total_timeout`；只有 doctor（同文件 `checkShutdownBudgets`）读配置里的 `dataengine.shutdown_timeout`，
   不够时 WARN，且 WARN 末尾 `Set it to` 的建议值仍是按 30s 算的公式值。

## 决策与实现

- USER_GUIDE §4 新增小节“回复错误判别：是否可能已提交、能否重试”：一张 11 行的表，按“自上而下取第一个命中行”判断，规则写明
  “带任一‘可能已提交’哨兵（`ErrCommitIndeterminate`、`entity.ErrRemotePersistenceIndeterminate`、`ErrAfterCommitFailed`、
  `ErrNestedTransactionCommitted`）即不得重试，即使链上同时有 `ErrLockTimeout`”，并把 RR-73 / 64 的“框架没有重排、修改未回滚”两行排在
  `ErrLockTimeout` 之前。约束列出的 `ErrAfterCommitFailed`、`ErrNestedTransactionCommitted`、`ErrCreatedEntityLockConflict`、`ErrLockTimeout`、
  `ErrCommitIndeterminate` 与 RR-73～75 的三个新哨兵都在表中；另加 `entity.ErrRemotePersistenceIndeterminate`（同属“可能已提交”，漏掉会让
  规则不完整）与 `ErrCommitRejected`（最常见的“未提交”回复）。
- 行顺序依据代码里的实际组合：`dispatchNest` 对已越过提交点的消息不补 `ErrNonRollbackNotRequeued`（RR-73），所以第 5 行不会与前 4 行
  同时出现；`ErrCreatedEntityLockConflict` + `ErrLockTimeout` 且带 `ErrNestedTransactionCommitted` 的情形由第 4 行先命中，满足第 2 点。
- 原 RR-46 / 53 那句保留历史链接，补“只看 `ErrAfterCommitFailed` 不够，完整顺序见判别表”；RR-48 那段补例外说明。
- godoc（`nest/nest.go`，只改注释）：`ErrLockTimeout`（新增说明）、`ErrAfterCommitFailed`、`ErrCommitIndeterminate`、`ErrCreatedEntityLockConflict`、
  `ErrNestedTransactionCommitted` 各补“是否可能已提交 / 能否重试”；RR-73～75 新哨兵的 godoc 在各自修复里已写，本次把
  `ErrNonRollbackNotRequeued` 里“可能与 `ErrNestedTransactionCommitted` 同时出现”的错误说法改为与代码一致（越过提交点时不补本哨兵）。
  给 `ErrLockTimeout` 加注释使它前面 6 行变成单独的对齐组，gofmt 重排了这 6 行的空格。
- DEPLOYMENT.md §8 那句改为：调大 `shutdown.total_timeout` 后 sync 重算宽限期；`dataengine.shutdown_timeout` 不参与生成，只调大它不会改变生成值，
  须同时手动把 `total_timeout` 调到不低于“新值 + 3s × 其余 Mod 数 + 5s”再 sync；doctor 按实际配置计算、只 WARN，并说明 WARN 建议值的口径。

## 后续验证（2026-09-27）

来源：[OPEN-ITEMS-2026-09-27](../review/OPEN-ITEMS-2026-09-27.md) B23（判别表第 2 行按 RR-37 记录写入，没有重跑 Remote 用例核对哨兵组合）。基线 `d4234c9`；图谱过期（09-26），以当前源码为准。

- 结论：**判别表与实际不一致，已按任务要求改表（文档修正，代码未改）**。在真实 Nest + 正式 Remote Manager（MongoCommitter 权威、ManagerAccess loader）上跑 RR-37 的四种
  “本地已提交、Remote 结果未知”，回复链上的哨兵组合：

  | 场景 | 回复满足 `errors.Is` 的哨兵 | 原表第一个命中行 |
  | --- | --- | --- |
  | Durability 0，Remote 已写入但回复丢失 | `ErrRemotePersistenceIndeterminate` + `context.DeadlineExceeded` | 2 |
  | Durability 0，从未到达 | `ErrRemotePersistenceIndeterminate` + `context.DeadlineExceeded` | 2 |
  | strict，等待 Remote 确认期间投影器报告未知 | `ErrRemotePersistenceIndeterminate` | 2 |
  | strict，等待 Remote 确认到截止 | `entity.ErrRemoteCommitTimeout` + `context.DeadlineExceeded` | **无**（不带任何“可能已提交”哨兵） |

  strict 截止分支来自 `remoteentity/transaction_tracking.go` `waitRemoteTransaction` 的 `ctx.Done()` 分支（`errors.Join(entity.ErrRemoteCommitTimeout, ctx.Err())`），
  `nest/msg.go` `finishRemoteWriteBatch` 与 `nest/nest_dispatch.go` 只加 `nest: finish remote write batch:` 前缀，不补 `ErrRemotePersistenceIndeterminate`。
  按原表调用方会判成“未提交”，可能重复业务。
- 修改：`docs/USER_GUIDE.md` 判别表第 2 行改为 “`ErrRemotePersistenceIndeterminate`，或 `ErrRemoteCommitTimeout`”并写明两种形态；表下补一段：调用方自己的等待先截止时
  `Request` 返回 `nest.ErrNestCanceled` / `nest.ErrNestTimeout`，只说明没等到回复，持久 handler 按“可能已提交”处理（生产里 strict 的请求截止与 Remote 确认截止常是同一时刻，
  调用方多半先看到这一形态）；§ Remote 段落“strict 远端确认超时……可 `errors.Is(ErrRemotePersistenceIndeterminate)`”一句同步更正。
- 回归：`remoteentity/reply_sentinel_table_test.go`（`TestRemoteUnknownOutcomeRepliesHitDecisionTableRow2`，四个子用例），按表的行序求“第一个命中行”并断言为 2，
  `t.Logf` 打印组合。strict 用例用只截短 Remote 确认等待的 Manager 装饰（其余全是正式 Manager）让确认截止先于调用方截止，回复才能送达。
  命令：`GOWORK=off go test -race -count=50 -run TestRemoteUnknownOutcomeRepliesHitDecisionTableRow2 ./remoteentity/` → `ok`（6.928s）。
- 待主会话决定（未做）：若要让代码兑现 RR-37 兼容性一节“strict 确认超时……仍返回可 `errors.Is(ErrRemotePersistenceIndeterminate)`”的原话，
  可在本地已提交后的 strict 等待截止处把 `ErrRemotePersistenceIndeterminate` 一并 Join 进错误；这是行为变化，本批按“改判别表”处理。
  `nest/nest.go` `ErrLockTimeout` 注释里列举的“可能已提交”哨兵同样没有 `ErrRemoteCommitTimeout`（属 Nest 批次文件，本批未改）。
