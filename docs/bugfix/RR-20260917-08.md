# RR-20260917-08：FinishDungeon 重放及非成功终态仍发奖励（U-0226）

- 仓库：roost-codegen `demo/`（game-demo 模板）
- 缺陷类：C2（幂等 / 状态判定）
- 优先级：P1
- 相关：T-120；测试 `game/dungeon/dungeon_test.go`（随工程生成）+ 机器人场景 `finish_dungeon_replay`

## 问题

`HandleFinishDungeon` 调用 `session.Finish` 成功后，只看**请求里的** `Success` 决定发不发奖励。
于是三条路径都多发：同一 run 重复发 `Success=true`（每次都发）、先失败再发成功（对 failed 发一次）、
run 过期后再发成功（对 expired 发一次）。后两者的响应还同时带着 `State:failed/expired` 和 `ExpGranted:100`。

## 根因

`session.Finish` 是**幂等**的，这正是它该有的语义：终态 run 会走 `releasePending` 并原样返回，不报错、不改结束时间；
超过 deadline 的 run 无论调用方要什么都变成 `expired`（core `service/session/service.go` 的 `finish`）。
模板里的注释却写着"重试会被 `ErrRunTerminal` 拒绝"——这句话从来不成立，代码按它写，所以：

1. 判据取错了对象：该看 `Finish` 返回的 `run.State`，不是请求里的 `Success`；
2. 即便判据对了，两个并发重放都会看到 `succeeded`，所以还需要一个**发奖事务内**的身份。

## 方案

- 采用：**权威状态 + 领取账本**。端点只在 `run.State == StateSucceeded` 时进入发奖；发奖走新的
  `ClaimDungeon` 两实体事务（Player + World），它在同一条 WAL 记录里把 `run.ID` 写进 Player 的
  `DungeonClaims` 账本并只在"是本次事务写进去的"时候发奖。记录与发奖同生共死，`rollback=undo` 一起回滚。
- 账本的界是**时间**，不是条数：重放只能经 `session.Finish` 到达，而 run 超过 `session.run_ttl`（生成配置里 30m）
  就不存在了、`Finish` 直接 `ErrRunMissing`。所以保留期只要明显长于 run_ttl（取 4h），被清掉的条目就不可能再被重放命中。
  清理放在写入口（`ClaimDungeonRun`），不需要清扫器。
- 没采用：端点先查后写。两个并发重放都会查到"未领取"，解决不了并发；崩溃窗口也没解决。
- 没采用：用条数给账本收界。条数不能保证"活到重放不可能为止"（skill 里反复踩过的那一条）。
- 没采用：改 `session.Finish` 让重放报错。它的幂等释放语义是对的，且"完成已持久化、奖励未提交"之后必须还能重试。

## 改动（roost-codegen）

- 新增 `demo/game/dungeon/dungeon.go`：`ClearExp`、`ClaimRetentionSeconds`（含为什么是时间界的论证）、
  `ClaimExpired`、`ClaimResult`；`demo/game/dungeon/dungeon_test.go` 随工程生成的表驱动测试。
- `demo/db/def/player.go`：`DungeonClaims map[string]int64`（`persist,map=fast`，不 sync——是服务端账本不是客户端状态）。
- `demo/game/entities/player/profile_component.go`：`ClaimDungeonRun`（查 → 按时间清理 → 记录）、`DungeonRunClaimed`。
- 新增 handler `demo/game/handler/claim_dungeon.go`（`rollback=undo durability=strict`）与 errcode `dungeon_run`(100010)。
- `demo/game/controllers/player/finish_dungeon.go`：按 `run.State` 判定、经 `MultiSync_ClaimDungeon` 发奖、
  只有 `Claimed` 才填 `ExpGranted/LevelsGained`；把那段不成立的注释换成真实语义。
- 机器人：新增 `finish_dungeon_replay` 动作（断言 `State==succeeded` 且 `ExpGranted==0`），场景在 `finish_dungeon` 之后重放一次。

## 证明

```
started=2 success=0 failure=2
```

`dungeon_claims: {"4cbbbab9045b4532e19addbe4ea276ae": 1789703076}`，等级停在 2（重放没有再升一级）。
`game/dungeon` 的表驱动测试随工程生成，`go test ./...` 会跑到它。

## 未做 / 边界

- `Finish` 与领取仍是两次调用：两者之间崩溃会留下"已结算未发奖"的 run。方向是安全的（可重试拿到奖励），
  但重试目前靠客户端再发一次；生产游戏要有服务端补偿。记录在端点注释里。
- failed / expired 现在不发奖，也没有"部分奖励"的概念——demo 只演示判据与账本。
- 账本按时间清理的前提是 `session.run_ttl` 不被调大到超过 `ClaimRetentionSeconds`；两个常量的关系写进了
  `game/dungeon` 的注释，并由随工程生成的测试断言。
