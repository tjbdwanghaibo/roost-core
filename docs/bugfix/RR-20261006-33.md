# RR-20261006-33 修复：源文档 digest 改为逐字段的规范表示，带上接口值的具体类型与全部字段

问题：[RR-20261006-33](../bug/RR-20261006-33.md)。基线 `443d08f6`，分支 `skpart`，未发版。
读代码：codebase-memory 共享 generation 停在 09-30（`canonical_definition.go` 为 metadata_match），`Definition` 下的接口与 `json:"-"` 字段用 go/types 在当前源码上枚举（临时测试，不提交）。

## 根因

`skill/canonical_definition.go` 用 `json.Marshal(Definition)` 当规范表示。`encoding/json` 编码接口值时只写具体类型的字段、不写类型；`json:"-"` 字段直接跳过。规范表示因此不是文档的单射：判别字段（effect / policy / input schema / shape / filter 的类型）和三个 `json:"-"` 字段（`Cost.Amount`、cast window 的 windup / recovery 表达式）都不在摘要里。

## 修法

规范表示改为按反射逐字段写出整棵 `Definition`（`canonicalEncoder`）：

- 接口值先写具体类型名（`reflect.Type.String()`，如 `skill.AddMemoryEffectDefinition`），再写值——只差类型的同形定义从此不同；
- 结构体写类型名、字段数和每个字段（字段名 + 值），不看 json tag，`json:"-"` 与未导出字段一样写出；
- map 按 key 的规范表示排序（`TestProgramIdentityIgnoresMemoryMapInsertionOrder` 照旧通过）；nil 指针 / 切片 / map / 接口与空值区分；字符串带长度前缀、数值定长，两段不会拼成同一串字节；
- 函数、通道等没有规范形式的类型直接 panic：封闭的 Wire 树里没有它们，出现说明 `Definition` 加了不能进摘要的字段，由全部 fixture 的编译测试暴露。

摘要域（`roost.skill/v2/source-document`）与 `stableDigest` 不变。

| 方案 | 结论 |
| --- | --- |
| ① 反射逐字段、接口写具体类型名（采用） | 一处修完所有接口字段与 `json:"-"` 字段，新加的效果 / 形状 / 字段自动覆盖，不需要维护类型表 |
| ② 给每个 wire 类型写 `MarshalJSON` 带上 `"type"` | 未采用：五十多个类型各写一遍，新加类型漏写就回到同一个缺陷；`json:"-"` 字段仍要逐个处理 |
| ③ 摘要改为对原始 JSON 字节规范化 | 未采用：`Definition` 也由 Go 代码直接构造（skillcompose、测试），没有原始字节；同一文档的空白 / 键顺序差异还要另做规范化 |

Go 类型名与字段名在摘要里：重命名 wire 类型或字段会改变源文档 digest。之前用 json 编码时字段名同样在摘要里（多数字段没有 json tag），性质不变，改名记录里已按“改名的直接后果”处理。

## 文件与行为

- `skill/canonical_definition.go`：`canonicalDefinitionDigest` 改用 `canonicalEncoder`，注释写明规范表示的规则与之前为什么错。
- `skill/canonical_definition_promises_test.go`：十种“只改一处”的定义对（效果类型、消耗数量、windup / recovery 表达式、策略、两组输入、两组形状、过滤器）摘要必须不同且稳定；端到端 `set_memory` → `add_memory` 编译后源文档 digest 必须变化。
- 行为：**全部定义的 `SourceDocumentDigest` 改变**（例：`owned_trap.json` `755f1b5c…` → `ae66782e…`，`simple_damage.json` `93325acd…` → `af49c467…`）。gameplay / presentation digest 不经过它，不变（上面两个 fixture 的 gameplay 仍是 `c2376552…` / `c8648243…`）；checkpoint、Program 查找、skillsync、skillcompose 契约都按 gameplay digest，不受影响。

## 兼容

保存了旧 `SourceDocumentDigest` 做比对的调用方，升级后第一次比对会认为全部源文档变了（一次性），之后恢复正常。框架内无此类调用方。
