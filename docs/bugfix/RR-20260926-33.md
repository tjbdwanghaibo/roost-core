# RR-20260926-33：fsync 失败粘滞——terminal 后 Ack / ticker / Sync 不再刷段、不推进 checkpoint 与 DurableLSN

问题：[RR-20260926-33](../bug/RR-20260926-33.md)（复现见 [REPRO-2026-09-26-04](../bug/REPRO-2026-09-26-04.md) §0 §1 §1b）。日期 2026-09-26。
实施基线：main `49f20ee`。状态：已修复，适用本地验证通过，本地提交，未 push / 发布。按 RR 记录中维护者批准的“修复约束”实施。

## 1. 根因（基线 `49f20ee` 的 `nestwal/wal.go`）

| 位置 | 问题 |
| --- | --- |
| `wal.go:474-511` `Ack` | 不查 `w.terminal()`，只看本次 `syncActive` 返回值；首次 fsync 失败时 `:496` `w.setTerminal(err)` 未包 `ErrCommitIndeterminate`，`failPendingTickets` 把裸 EIO 交给 pipelined 票据，违反 `nest/transaction.go:102-106` 票据契约（`nest/execution.go:45` 只对该错误 Fence）。 |
| `wal.go:1106-1120` `syncActiveLocked` | fsync 失败只返回错误，`unsynced` 保持 true；terminal 另由调用方在释放 `stateMu` 后设置。下一次调用再 fsync，Linux ≥4.13 同一 fd 的错误只报告一次，返回 0 即清 `unsynced` 并 `resolveDurableLocked`。`active == nil` 时不论 `unsynced` 直接返回 nil。 |
| `wal.go:1122-1132` `syncAndCloseActive` | 最后一次 sync 失败后仍把 `active` 置 nil，在途 Ack 走上一行的 `active == nil` 分支得到 nil 并存 checkpoint。 |
| `wal.go:798-801` ticker | terminal 后仍每个 `GroupCommitInterval` 调 `syncActive`，把 `DurableLSN` 推过票据已判不确定的记录。 |

后果与 RR-16 相同：checkpoint 越过从未落盘的页，断电 / 丢写回后 `openActive` 报 `acknowledgement is beyond recovered WAL end` 拒绝启动。

## 2. 方案

1. **正式测试缝**（替代 REPRO §0 的探针全局变量）：`Options.syncFile func(*os.File) error`，段文件 fsync 统一经 `fsyncSegment`（`syncActiveLocked` 与 `rotateLocked` 新段 fsync）；
   `Options.afterAckAdmitted func()` 让测试把在途 Ack 停在 Close 之前。二者未导出、仅包内测试设置，生产路径为 nil，只多一次 nil 判断；放在 Options 而非包变量，测试之间互不串扰。
2. **fsync 失败粘滞**：`syncActiveLocked` 是 Ack、ticker、Sync、批量写、轮转、关闭排空共同的刷段入口：
   - 入口先查 terminal：已 terminal 直接返回 terminal，不 fsync、不清 `unsynced`、不推进 `DurableLSN`；顺带清扫并发登记漏网的票据（见 4）。
   - fsync 失败即在 `stateMu` 内 `setTerminal(ErrCommitIndeterminate ⊕ err)` 再返回。terminal 与“失败”在同一把锁内可见，不再有“调用方释放 `stateMu` 后才设 terminal”的窗口让另一次 fsync 抢先“成功”。
   - `active == nil && unsynced` 返回（并设置）不确定错误；`active == nil && !unsynced`（干净关闭）仍返回 nil。
3. **Ack**：`checkpointMu` 内先查 terminal（拒绝且不写 checkpoint），再做 RR-16 的刷段，最后存 checkpoint；刷段失败的错误已是 `ErrCommitIndeterminate`。
   ticker 分支只调用 `syncActive`，失败处理集中在 `syncActiveLocked`；`Sync`、`processRecords`、`drainAndClose` 改用 `indeterminate(err)`——已归类的错误原样返回，其余包 `ErrCommitIndeterminate`，避免重复包装。
4. **terminal 读免锁**：terminal 只写一次，读发生在每次刷段、Ack、Append、Enqueue 上；由 `terminalMu`+error 改为 `atomic.Pointer[terminalState]`，
   `setTerminal` 以 `CompareAndSwap(nil, …)` 保持“首个错误胜出”（性能原因见 4）。
5. **票据清扫**：`failPendingTickets` 对 LSN ≤ `DurableLSN` 的票据按已落盘解析（nil），其余给 terminal 错误。`DurableLSN` 只在 terminal 之前的成功 fsync 后发布，修复后 terminal 之后不会再动，所以覆盖即证明落盘。
   这是为保持旧行为的正确一面：以前“晚于覆盖它的 fsync 才登记”的票据靠 ticker 下一次 `resolveDurableLocked` 以 nil 解析；ticker 不再在 terminal 后工作，改由清扫按同一判据解析，不让等待方悬挂，也不把已落盘的记录误判为不确定。

涉及：`nestwal/wal.go`；新增 `nestwal/fsync_failure_promises_test.go`；`NEST_TRANSACTION_WAL.md` §7。

### 未采用方案

- 保留 REPRO 的包级可替换函数变量：包内测试若并行或未恢复会互相污染，且形同导出缝（探针的 `ProbeSetFileSync`）；Options 字段按实例生效。
- 只在 Ack 查 terminal、syncActiveLocked 不改：ticker / Sync / 关闭排空仍会“二次成功”推进 `DurableLSN`，且调用方释放 `stateMu` 后才设 terminal 的窗口仍允许 Ack 抢先 fsync 成功。
- fsync 失败后重开 fd 重试：无法证明失败那批页的去向，属于用重试伪造持久确认，违反 roost-coding DataEngine 契约与 NEST_TRANSACTION_WAL §7。
- terminal 后停止 ticker：`syncActiveLocked` 入口已不再刷段，停 ticker 只省一次无锁竞争的 RLock，还要额外处理晚到票据；不值得增加 writerLoop 状态。

## 3. 兼容性

- 公开 API、配置、WAL / checkpoint 格式不变。
- 行为变化（供 CHANGELOG）：WAL terminal 后 `Ack` 返回 terminal 错误（`errors.Is(err, nest.ErrCommitIndeterminate)`），不再写 checkpoint——包括已被 checkpoint 覆盖的重复确认；
  Ack 自身 fsync 失败返回、并交给在途 pipelined 票据的错误现在都是 `ErrCommitIndeterminate`；terminal 后 group-commit ticker 与 `Sync` 不再 fsync、`DurableLSN` 不再前进；
  排空关闭最后一次 sync 失败后在途 Ack 返回错误。干净关闭后的在途 Ack 与 `Sync` 仍返回 nil。
- 投影侧：terminal 后 Projector 的 ack 失败按普通失败记录并退避重试（`dataengine/engine/projector.go` `recordFailure`，非 fatal），已投影的记录由重启回放幂等吸收；进程应已由 `OnFatal` fencing。

## 5. 自查（逐条论证不破坏）

- **strict 语义**：strict 仍在所在批的 group commit fsync 成功后才返回 fence；fsync 失败仍返回 `ErrCommitIndeterminate` 并 terminal，Append 在 terminal 后仍同步拒绝。
  新增的入口 terminal 检查只在另一路径（Ack / Sync / ticker）刚判定 fsync 失败时生效，此时本批如实得到不确定错误，而不是靠第二次 fsync“成功”宣称落盘。成功路径只多一次无竞争的 RLock。
- **pipelined 语义**：`Enqueue` 的全部同步拒绝点未动；票据只以两种方式解析为 nil——成功 fsync 后的 `resolveDurableLocked`，或清扫时 LSN ≤ `DurableLSN`（同样只来自成功 fsync）；
  其余一律 `ErrCommitIndeterminate`，满足 `nest/transaction.go` 票据契约（修前 Ack 路径会交出裸 EIO）。阶段一 `<-ticket.Done()` 不会悬挂：`setTerminal` 清扫、`processRecords` terminal 分支、
  `syncActiveLocked` terminal 分支三处兜底（`TestTerminalSweepResolvesTicketsAlreadyCoveredByDurableLSN` 覆盖第三处，修前该票据永远不完成）。
- **RR-16 checkpoint 顺序**：Ack 仍在 `checkpointMu` 内按“terminal → 已覆盖 → 越界 → 刷段 → 存 checkpoint”执行，刷段先于 `storeCheckpoint` 不变；
  `TestAckSyncsAsyncRecordBeforeCheckpoint`、`TestMultiCheckpointCancellationConfirmsOnlySuccessfulPrefix` `-race -count=20` 通过。
- **group commit 批量**：每批仍最多一次 fsync（`requireSync` 聚合），async 仍由 ticker 周期刷；没有新增 fsync，只在 terminal 后减少了 fsync。性能对照见 4。
- **关闭排空（RR-17）**：`operations` Begin/Stop 与 `drainAndClose` 顺序不变：排空队列 → 最后 sync 并关闭段 → 等在途 Replay/Ack → 交出目录锁。terminal 后最后一步不再 fsync，但仍关闭段文件、
  置 `active=nil`、把 terminal 并入 `closeErr`；干净关闭后在途 Ack 仍成功（守卫测试修前修后都绿），失败关闭后在途 Ack 返回错误。
- **fatal 传播**：`setTerminal` 仍“首个错误胜出”并各只触发一次 `failPendingTickets` 与异步 `OnFatal`；现在 fsync 失败在 `stateMu` 内调用它：terminal 本身是无锁 CAS，随后只取 ticketMu，锁序为既有的“stateMu -> ticketMu”；`OnFatal` 在独立 goroutine 执行，不在锁内进入用户代码。所有 terminal 错误现在都 `errors.Is(ErrCommitIndeterminate)`，
  Nest 对 Append / 票据的该错误照旧 `Fence`（`nest/execution.go:45`），Ack 首次失败的情形也不再漏 Fence。
- **DurableWatermark 单调**：`durableLSN` 只在 `resolveDurableLocked` 内以“小于才写”更新；terminal 后该函数不再被调用，`failPendingTickets` 只读。
  `nestwal.Runtime.DurableWatermark` 即此值，Sync 外发门槛在 terminal 后停在最后一次成功 fsync 处，不会放行未证明落盘的变更。

## 6. 未验证项 / 残余风险

- 注入的是 fsync 返回值与 Linux errseq 语义（失败一次后返回 0），不是物理坏盘、云盘摘挂或 thin 卷 ENOSPC；“丢写回”以截断段文件模拟。
- terminal 后 `Replay` 仍按已写入的 `w.offset` 读，Projector 可能把未证明落盘的记录投影进 Mongo。这与 NEST_TRANSACTION_WAL §7 “结果不确定、由新进程回放判定”一致（strict 调用方已得到不确定错误，async 本就不承诺 fsync），本次未改。
- 未跑故障矩阵（按任务要求）；未在 Linux 上实测。
