# RR-20260915-03:entitysync 订阅快照与直接分发绕过持久化水位

**仓库 / 位置**:roost-core `entitysync/subscription.go`(`Subscribe` / `DistributeBatch` / `FlushSubject`),
`entity/subject_sync.go`(`prepareLocked` / `CaptureSnapshot` / `SubjectSyncUpdate`)。
**修复单元**:U-0206(C8)。**定位文档**:TROUBLESHOOTING T-100。

## 问题

配置 `SetDurableWatermark` 返回 0,`MarkDirty` 后 `SetLastCommitLSN(7)`——最新流水提交尚未持久化。`FlushSubject` 正确
推迟;但新 `Subscribe`、已订阅后的 profile 切换、`Prepare → Distribute` 三个入口都直接向 sink 交付了一批。使用流水
WAL + 水位门槛的宿主里,新进入兴趣集 / profile 变化 / 自定义 room tick 分发会把未落盘的状态送出;之后进程故障,
接收端见过的状态无法从持久日志恢复。

## 根因

门槛只装在 `FlushSubject` 一个入口(C8:三条暴露内容的出口对同一状态的判据不同)。而且它检查的是**可变的**
`LastCommitLSN`,然后放锁再 `Prepare`——检查与捕获之间可以落进新提交(审查特别点了这一条)。

## 方案选择

- **在每个入口前复制 FlushSubject 的检查。** 三处同样的 check-then-capture 窗口。
- **门槛跟着被捕获的内容走(采用)。** `SubjectSyncUpdate` 新增 `CommitLSN`:`prepareLocked` 与 `CaptureSnapshot` 都在
  `withEntityLock` 里,而 nest 的流水提交是"enqueue in-lock、stamp entity LSNs、release locks early"(`nest/rollback.go`)——
  同一把实体锁,所以锁内读到的 `lastCommitLSN` 与捕获的内容严格一致,不存在窗口。协调器只在准入前看
  `update.CommitLSN > watermark()`:
  - `Subscribe`(含 profile 切换):捕获后判,推迟则 `rollbackSubscription` 回到原状态(原有效订阅保留)并返回新的
    可重试错误 `ErrDurabilityDeferred`;
  - `DistributeBatch`:任一 update 推迟则 `abortPreparedBatch(prepared, ErrDurabilityDeferred)`——整批 abort、所有
    prepared 状态保持 dirty、下一 tick 重试;
  - `FlushSubject`:保留原来的廉价前置检查(省一次 Prepare),Distribute 若因水位推迟则按原契约返回 nil。
  新计数 `entitysync_durability_gate_deferred_total{entry}`。
- **让 sink 自己做门槛。** sink 只见 envelope,不知道 WAL 水位;责任在协调器。

## 改动

`entity/subject_sync.go`:`SubjectSyncUpdate.CommitLSN`;`prepareLocked` / `CaptureSnapshot` 锁内读 LSN 并写入每条 update。
`entitysync/subscription.go`:`ErrDurabilityDeferred`;`deferredByDurability`;三个入口如上。

## 证明

`entitysync/durability_gate_promises_test.go`:
- `TestDurabilityGatePromiseCoversEveryDeliveryEntryPoint`:审查的五个叶子(subscribe / profile_change / direct_distribute
  不外发;flush_blocked 不外发;水位=7 的 durable_subscribe 正常外发);
- `TestDurabilityGatePromiseDeferralIsRetryable`:推迟的 profile 切换返回 `ErrDurabilityDeferred` 且原订阅原样保留;推迟的
  新订阅不留 pending;推迟的 Distribute 整批 abort、状态仍 dirty、版本不前进;水位追上后三件事都成功。

修前红:`non-durable LSN=7 watermark=0 escaped via subscribe: batches=1`(profile_change / direct_distribute 同形)。
修后 entity / entitysync 含 `-race` 全绿,core 全仓 `-race` 全绿,kit 构建与 `service/...` 测试通过。

## 未做 / 边界

- 只模拟了 LSN / 水位,没有真实 WAL 崩溃或跨进程故障实验(审查同样未做)。
- `FlushSubject` 的前置检查仍是 check-then-prepare;它现在只是省一次 Prepare 的优化,正确性由 Distribute 上的
  按内容判断保证。
- 宿主若自己管理 `SubjectSyncState` 而不经 EntityBase(`SetLastCommitLSN` 导出给这种用法),要自行保证在实体锁内盖 LSN。
