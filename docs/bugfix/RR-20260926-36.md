# RR-20260926-36：生成传输层每次 Dispatch 有截止、Session 关闭取消在途请求、EnterGame 另给登录预算

问题：[原始记录](../bug/RR-20260926-36.md)（复现 [REPRO-2026-09-26-04 §4](../bug/REPRO-2026-09-26-04.md)）。日期 2026-09-26。
实施基线：main `49f20ee`。状态：已修复，适用本地验证通过，已本地提交，未推送/发布。

## 根因（复核）

生成 TCP 传输 `serveConnection` 把只在 server 停止时取消的 `connectionCtx` 直接交给 `Dispatch`；demo `EnterGame` 用它做
`Claim` + `GetOrCreate`，冷加载经 `ManagerAccess` → `EntityRepository` → `Projector.WaitEntityProjection` 等待投影，而投影器对瞬时失败无限退避。
读循环同步 Dispatch，挂住期间不读 socket、占连接槽与按 IP 计数；`session.Close`（同 SessionID 重连替换、`CloseSessions`）只关 socket，
在途 Dispatch 不知道，重连只会累积挂住的旧 goroutine 与槽位。

## 修复（按维护者批准的约束）

1. **正式生成传输层**（`codegen/internal/roost/render_player_tcp.go` → 生成 `internal/access/player/tcp/server_gen.go`）：
   - 新配置 `player_access.tcp.dispatch_timeout`：每次 Dispatch 在连接 ctx 上 `context.WithTimeout` 派生截止 ctx，返回后立即 cancel。
     键缺省时取同一配置的 `nest.request_timeout`，再缺省 3s；上限 5m。超过预算的请求计 `player_tcp_dispatch_timeout_total`。
   - 连接 ctx 改为 `context.WithCancelCause(server.ctx)`，`session` 持有其 cancel；`session.Close(reason)` 在关 socket 后 `cancel(reason)`，
     在途 Dispatch 随之结束（`context.Cause` 为关闭原因）。读循环、连接槽、按 IP 计数仍由 `serveConnection` 的 defer 各释放一次，释放点未变。
   - 响应仍用连接 ctx 写回（受 `write_timeout` 约束）：handler 在截止时返回的答复是“发生了什么”，不因请求截止被丢弃。
   - 新配置 `player_access.tcp.login_timeout`（缺省 min(2s, dispatch_timeout)，校验 `0 < login ≤ dispatch`）。传输层不使用它，
     经 `Runtime.LoginTimeout()` 发布给登录端点。
   - 读循环仍同步、每连接串行；截止只是一个 `timerCtx`，不为请求起 goroutine。
2. **生成配置**：`renderPlayerTCPConfig` 参考块与 `playerTCPConfigDefaults`（`add transport tcp` / `config enable player-tcp` 补键）加入
   `dispatch_timeout: 3s`、`login_timeout: 2s`；补键时若该服务配置已有 `nest.request_timeout`，`dispatch_timeout` 按它写（`playerTCPDefaultsFor`），
   `login_timeout` 不超过它。game-demo 生成的 `config.game.yaml` / `.prod.example.yaml` 为 `request_timeout: 3s`、`dispatch_timeout: 3s`、`login_timeout: 2s`。
3. **demo EnterGame**（`demo/game/controllers/player/enter_game.go.tmpl`、`controller.go.tmpl`）：`Claim` 与 `GetOrCreate` 运行在
   `loginContext`（dispatch ctx 上再套 `Controller.LoginTimeout()`，经 `access.player.tcp` capability 的 `LoginTimeout()` 读取，取不到时只受 dispatch 截止约束）；
   超出预算（`errors.Is(err, context.DeadlineExceeded)`）由 `loginCutShort` 回新错误码 `login_timeout`（100021，`demo/internal/errors/login_timeout.go.tmpl`），
   记 Warn，不再记成 `CodeInternal`/Error；连接被关闭导致的 `context.Canceled`（同 Session 重登替换）同样回 login_timeout、记 Info（答复实际已无处可去）；
   其他失败的答复与日志与原先相同。之后的 RecordEnter / EnterScene / Join / 结算 / 公告用剩余的 dispatch 预算。
   新模板测试 `demo/game/controllers/player/enter_game_test.go.tmpl` 加入 `codegen/internal/roost/demo.go` 的脚手架列表。
4. **共享加载 flight**：未改。`ManagerAccess.loadEntityShared` / `EntityRepository` 的等待方 ctx 结束只让该等待方离开；本次回归证明了这一点。

未采用：在传输层识别登录消息另给截止（传输层不该知道业务消息）；把登录预算放进 demo 自有配置段（与 dispatch 分离后无法在一处校验 `login ≤ dispatch`）；
每请求 goroutine + 超时强制返回（违背读循环有序与“不引入每请求 goroutine”，且不遵守 ctx 的 handler 仍在后台运行）。

## 兼容性与行为变化

- 生成工程的每个玩家请求现在有总截止（默认 3s）。以前只有 handler 内每次 Nest 调用各自的 `request_timeout`；**顺序做多次长等待的 handler**
  （例如连续两次各接近 3s 的 Nest 调用）现在会在第二次中途被截止，需要调大 `dispatch_timeout`。正常负载下单次调用为毫秒级，无影响。
- 截止只停止等待，不撤销已准入的业务：Nest 请求在截止前已准入的事务照常提交；handler 收到超时错误时结果可能已生效。客户端对非幂等请求
  应带幂等键重试或先查询（demo 的 EnterGame 可重试：GetOrCreate 找到上次可能已创建的实体；RecordEnter 计数与登录公告在重试时可能各多一次，属统计/公告，
  不影响玩家数据）。
- handler 返回错误仍关闭连接（原契约）；需要客户端可读答复的超时应像 EnterGame 一样编码为 errcode。
- 已有工程执行 `roost config enable player-tcp` 或 `add transport tcp` 时补上两个新键；未补键的工程由运行时缺省值（取 `nest.request_timeout`）兜底。
- 新增生成符号：`Config.DispatchTimeout/LoginTimeout`、`Runtime.LoginTimeout()`、`defaultDispatchTimeout/defaultLoginTimeout`；无删除或改名。
  应用代码直接构造 `Config` 调 `NewServer` 而未设两字段时，`NewServer` 补缺省值（3s / min(2s, dispatch)），不拒绝旧写法。

## 交付前对抗性自查

- **超时 ≠ 撤销**：截止只让等待方返回；Nest 请求一旦准入，其事务照常提交/投影，传输层没有任何回滚入口。连接 ctx 被 Session 关闭取消时同理。
  handler 在截止时仍返回的答复照常写回。客户端语义：超时结果未知，非幂等请求需幂等键或先查询；EnterGame 可重试（见“兼容性”）。
- **登录并发（同一玩家多次登录）**：同 SessionID 重登 → `registerSession` 关闭旧 Session → 旧连接在途的 EnterGame 被取消（`Canceled` 记 Info 并回 login_timeout，
  答复写到已关闭连接即丢弃）；不同 SessionID 并发 → 共享同一加载 flight。领头者自己的登录预算到期时 flight 以 `DeadlineExceeded` 结束，
  同 flight 的等待方也得到 login_timeout（它们重试即开始新 flight，回归“the login leads the load”覆盖“超时后不遗留 flight”）；等待方自己超时不影响领头者（回归覆盖）。
  归属 `Claim` 对同进程同玩家幂等。
- **重连 Hold/Ready 与代际**：本 RR 不改 scene；重连的 Hold/Ready/代际一致性见 RR-20260926-40 修复。
- **连接槽 / 按 IP 计数唯一释放**：释放点仍只在 `serveConnection` 的 defer（`<-connectionSlots` 一次、`ipConnections` 减一次）；`session.Close` 只关 socket 并取消 ctx，
  不触碰计数。回归断言槽位与按 IP 计数恰好回到仍打开的连接数（0 或 1），不会少减或多减。
- **不引入每请求 goroutine**：每个请求多一个 `context.WithTimeout`（父为标准 `cancelCtx`，不起 propagate goroutine；计时器到期前不占 goroutine），
  读循环仍同步；handler 不遵守 ctx 时传输层不抢占（明确限制）。
- **快池**：未新增等待入口；登录路径在连接 goroutine 上，不在 Nest 快 worker 上。

## 未验证项

- 没有在真实 Mongo 不可用的集成环境里端到端复现“冷登录挂起 → 超时答复”；回归用真实投影器 + 失败 store 覆盖等待链。
- 不遵守 ctx 的自定义 handler（任意阻塞 RPC）不受截止保护，这是既有契约（SKILL：handler 内阻塞 RPC 不会自动隔离）。
- 其他传输（生成物目前只有 TCP）无此改动。
