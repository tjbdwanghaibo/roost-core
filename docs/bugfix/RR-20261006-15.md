# RR-20261006-15 修复：步骤收件箱按操作只取有影响的 claim，上限与尝试次数、Resume 次数脱钩

问题：[RR-20261006-15](../bug/RR-20261006-15.md)。分支 `fixs`，基线 `b549e4df`，未发版。

代码阅读：codebase-memory 共享 generation 停在 09-30（`saga/step_operation_inbox.go` 未入索引），本轮以当前源码为准，未调用图谱。

## 决策

累积的 claim 绝大部分对判定没有影响：`resolveOtherAttempts` 跳过被接替的（`superseded`）与可重试失败，旧一生的拒绝也不回放。会影响判定的只有
**pending**（在途要等、过期要接替；原生投影已写回执、还没标记的也在这里）、**任何一生的成功**、**本生的拒绝**。让查询只取这些，上限就和尝试次数、Resume 次数无关：

- claim 标记 completed 时（`markCompleted`、Mongo 步骤生效点 `settleOwnClaim`）多写 `outcome`：`success` / `refused` / `retryable`（`claimOutcome`）。
- `operationClaimsFilter`：`{namespace, operation_key, $or: [pending, completed+success, completed 且没有 outcome, completed+refused+本生]}`。
  第 0 代的 `incarnation` 有两种写法（新建 claim 时 `omitempty` 不写，接管自己过期的 claim 时 `$set` 写成 0），两种都匹配。
- 上限常量改名 `maxDecisiveOperationClaims`（仍 4096），只在数据异常时触发；`operationSuccess` 改用同一查询（不读拒绝），超过上限报错而不是截断。

**有界性证明**（写在 `operationClaimsFilter` 注释里）：一次 Reserve 只有在处理完其他尝试后才写自己的 claim（过期的 pending 全部接替，有在途的就不写），守卫文档让同一操作的
Reserve 串行，所以没有结论的 pending 任何时刻至多一份，另加结论已写、尚未被下一次 Reserve 标记的少数几份；一个操作至多生效一次（U-0280），成功至多一份；同一生出现拒绝后，
后来的尝试回放它、不再写 claim，本生拒绝至多一份；没有 outcome 的只来自升级前与混跑中的旧进程，数量有限、随 TTL 消失。结果集是小常数。

未采用：
- **限制 Resume 次数**（例如累计尝试超过 4096 拒绝 Resume）：把运维修好原因后的恢复变成永久拒绝，要等 30 天；而且协调器不知道收件箱里的 claim 数，要在 Record 上新增累计计数。
- **Resume 时清理旧 claim**：claim 是跨尝试去重与“旧一生成功仍回放”的依据，删了会让已生效的步骤再执行。
- **只调大上限或分页扫全部**：仍随 Resume 无界增长，每次 Reserve 在事务里读的文档越来越多。

## 兼容

- **持久格式只增**：claim 多 `outcome` 字段。旧进程不认识它、照旧按全部 claim 计数（混跑期间旧进程的行为与修前相同）；新进程读到没有 `outcome` 的 completed claim 按“可能有影响”读取并解 completion 判断。
- 判定语义不变：被排除的三类 claim 修前也被跳过，只是现在不读出来；`operationSuccess` 修前的截断实际不可达（Reserve 的门让 claim 数最多 4097 = Limit），现在上界不再由 Reserve 保证，所以改为同一查询并在超限时报错。
- 服务端：查询仍走 `by_operation (namespace, operation_key)` 索引，`$or` 的其余条件在取到的文档上过滤；同一操作 claim 很多时服务端检查的文档数随之增加，但只在这种异常累积下出现，返回给客户端与解码的只有小常数份。没有加新索引（不改 `ensureClaimIndexes`）。
  **更正（复核）**：实测服务端检查的文档数随这个操作的全部 claim 线性增长，而且集合里只有少数操作时优化器会改选 `claim_expired` / `uniq_command`；
  已补索引 `by_operation_decision`，见下面“复核后的补修与验证”。
- **滚动升级建议**（复核补充，混跑实测见下）：新旧步骤进程可以混跑，同一操作至多生效一次、新旧进程互相读得懂对方的 claim。旧进程仍按全部 claim 计数：
  一个操作累积超过 4096 份 claim 后，旧进程对它的 Reserve 报 `ErrConflict`（事务中止、什么都不写，消息 nak 后重投，落到新进程就照常执行或回放），
  过期投递也少一次重发成功的机会（`operationSuccess` 截断，同 SAGA.md 混跑说明的那个角落）。新进程不受影响（含旧进程在上限边上留下的 4097 份旧 claim，
  RR-20261006-16）。建议：步骤进程（Mongo 步骤与原生步骤消费者）尽快全部升级，与协调器的升级顺序无关；新索引由新进程启动时的 `EnsureInfrastructure`
  在线建立，claims 集合很大时可在发布前手工建好（`createIndexes`，键 `namespace, operation_key, status, outcome, incarnation`，名 `by_operation_decision`），
  旧进程用不到它也不受影响；`by_operation` 保留给混跑中的旧进程，全部升级后不再被新查询使用。

## 复核后的补修与验证

分支 `rr15v`，基线 `ca029401`，未发版。环境：`scripts/mirror-local.sh up` 起的私有三节点副本集（私有根目录、偏移 24600），用完 `clean`；

### 1. 新旧进程混跑

**做法**：`saga/mongo_step_mixed_version_real_mongo_integration_test.go`。“旧进程”是 `5ca32611^` 的源码加上这一个文件编出的测试二进制，作为子进程按
`ROOST_SAGA_MIXED_ROLE` 执行 `Handle`；“新进程”是当前测试进程。两份 saga 代码不能编进同一个二进制，在测试里手抄一份“旧路径”只是对旧代码的转述，
所以用修前源码真编出来的进程；文件只用两个版本都有的符号，复制过去就能编。运行入口写在文件头，没有 `ROOST_SAGA_MIXED_OLD_BINARY` 时跳过。
业务写在 handler 的 Mongo 事务里按 CommandID 插一份文档，文档数就是生效次数。用例与断言：

| 用例 | 交替 / 并发 | 断言 |
| --- | --- | --- |
| `…AlternatingAttemptsTakeEffectOnce` | 旧可重试失败 → 新 handler 出错交还租约 → 旧读到它、接替并执行 → 新读两份旧 claim 后执行成功 → 两边回放；Resume 后两边回放；旧进程重投新进程执行过的命令 | 旧写的 claim 没有 `outcome`、新写的有；被接替的是新进程那份；生效 1 次 |
| `…RefusalsReplayWithinTheirLife` | 新第 0 代拒绝（不带 incarnation）→ 旧同生回放；旧第 1 代拒绝（不带 outcome）→ 新、旧同生回放；新第 2 代执行成功 → 两边回放 | 拒绝只在同一生回放；生效 1 次 |
| `…InFlightAttemptsAreFencedAcrossVersions` | 旧进程在 handler 里被 SIGKILL：新进程在它租约内 `in_flight`、过期后接替执行，旧重投 `superseded`；新进程停在 handler 里：旧 `in_flight`、过期后接替执行，新随后提交被 fence | 生效 1 次，新进程的迟到提交 `errAttemptFenced` |
| `…ConcurrentAttemptsTakeEffectOnce` | 5 轮，每轮两进程各 4 个尝试同时 Handle 同一操作 | 每轮恰好 1 个执行，其余回放它；生效 1 次 |
| `…AttemptCapOnlyStopsTheOldProcess` | 4100 份带 outcome 的可重试失败 | 旧进程 `ErrConflict` 且 claims 集合不变；新进程执行；旧进程之后仍 `ErrConflict`，新进程回放 |
| `…OldProcessAtTheCapDoesNotStopTheNewProcess` | 旧进程在 4096 份时写下第 4097 份 | 新进程执行（修前红，即 RR-20261006-16） |

结果：前五个在修前（`ca029401`）就通过，第六个红，登记为 [RR-20261006-16](RR-20261006-16.md) 并修复；修后全部通过。原文：
[mixed-run.txt](evidence/RR-20261006-15/mixed-run.txt)。结论：同一操作至多生效一次；新进程读懂旧进程不带 `outcome` 的 claim；旧进程读带 `outcome` 的 claim
不出错（驱动解码忽略未知字段）；4096 上限在混跑下只挡旧进程，旧进程撞上限时事务中止、不写任何东西。原生步骤（`DataEngineStepInbox`）与 Mongo 步骤共用
`stepOperationInbox` 的 Reserve / 判定 / 标记代码，版本差异只在这一份代码里，混跑用例走 Mongo 步骤；原生步骤特有的“回执先于标记”由旧进程补标时留下
不带 `outcome` 的 claim，按旧 claim 读取并单独计数（RR-20261006-16 的余量）。

### 2. 服务端过滤的耗时与执行计划

**测量**：`TestRealMongoOperationClaimsQueryCost`（`saga/step_operation_claims_cost_real_mongo_integration_test.go`，`ROOST_SAGA_CLAIM_COST=1` 时运行）。
单个操作 1000 / 4000 / 10000 份带 `outcome` 的可重试失败（RR-15 的累积形态），另有不带 `outcome` 的 1000 / 4097 份（升级前形态）；同一集合里再放 0 或
50000 份其他操作的 claim。每组 60 次：完整的 reserve 事务（守卫 + 按操作查询 + 写自己的 claim）、`operationSuccess`、单独的查询（修后过滤与修前
“全部 claim、Limit 4097”对照）；explain `executionStats`。

修后（RR-15 提交时的查询，只有 `by_operation`），背景 50000 份：

| 形态 | claims | 计划 | 检查 keys / docs | reserve p50 | operationSuccess p50 | 查询 p50 | 修前查询 p50 |
| --- | ---: | --- | ---: | ---: | ---: | ---: | ---: |
| outcome | 1000 | IXSCAN(by_operation) | 1060 / 1060 | 9.85ms | 1.17ms | 0.86ms | 3.39ms |
| outcome | 4000 | IXSCAN(by_operation) | 4060 / 4060 | 11.95ms | 2.96ms | 3.08ms | 11.47ms |
| outcome | 10000 | IXSCAN(by_operation) | 10060 / 10060 | 15.70ms | 6.35ms | 7.34ms | 11.49ms（截断在 4097） |
| legacy | 1000 | IXSCAN(by_operation) | 1060 / 1060 | 12.50ms | 4.42ms | 3.47ms | 3.35ms |
| legacy | 4097 | IXSCAN(by_operation) | 4157 / 4157 | 23.30ms | 14.64ms | 12.07ms | 11.03ms |

（keys / docs 多出的 60 是测量本身每次写下、标成可重试失败的 claim。）走了索引、没有全表扫描，但服务端检查的文档数等于这个操作的全部 claim，随尝试与
Resume 线性增长——RR-15 不采用“分页扫全部”的理由同样适用于服务端。集合里没有其他操作时，优化器对 10000 份选了 `claim_expired`（status 前缀）的 OR 计划、
对 legacy 选了 `uniq_command`（namespace 前缀），在生产集合里那会扫其他操作的 claim；背景 50000 份时选回 `by_operation`。

**补修**：claims 集合加索引 `by_operation_decision (namespace, operation_key, status, outcome, incarnation)`，`operationClaimsFilter` 的每个 `$or` 分支都是
它前缀上的等值或区间；第 0 代拒绝的两种写法从嵌套 `$or` 拆成两个平级分支（嵌套 `$or` 让优化器给那一支改选 `claim_expired`，explain 实测）。
守卫用例 `TestRealMongoOperationClaimsQueryExaminesOnlyDecisiveClaims`：2000 份累积 claim（可重试失败与被接替）加 pending、两代拒绝，三种查询检查的文档数
不超过返回数加 2。修前红：

```text
reserve, life 2 over 2000 accumulated claims: examined 1336 keys and 1337 documents to return 2 (plan LIMIT<-FETCH<-OR<-[FETCH<-IXSCAN(claim_expired),IXSCAN(claim_expired)]), want only the decisive claims touched
```

（原文 [index-guard-red-before.txt](evidence/RR-20261006-15/index-guard-red-before.txt)。）补修后，背景 50000 份：

| 形态 | claims | 计划 | 检查 keys / docs | reserve p50 | operationSuccess p50 | 查询 p50 |
| --- | ---: | --- | ---: | ---: | ---: | ---: |
| outcome | 1000 | OR(4 × IXSCAN(by_operation_decision)) | 0 / 0 | 8.47ms | 0.41ms | 0.14ms |
| outcome | 4000 | 同上 | 0 / 0 | 9.38ms | 0.46ms | 0.22ms |
| outcome | 10000 | 同上 | 0 / 0 | 9.56ms | 0.35ms | 0.23ms |
| legacy | 1000 | IXSCAN(by_operation) | 1060 / 1060 | 12.63ms | 4.16ms | 3.34ms |
| legacy | 4097 | IXSCAN(by_operation) | 4157 / 4157 | 23.55ms | 14.30ms | 12.11ms |

带 `outcome` 的累积不再影响耗时（reserve p50 约 9.5ms，主要是事务本身；没有背景时三档同样是 0 / 0）。不带 `outcome` 的旧 claim 只能全部读出来解码，
4097 份时 reserve p50 约 24ms，与修前进程读全部 claim 同量级，只出现在升级前卡住的操作上，随 TTL 消失。原文：
[claims-query-cost-before.txt](evidence/RR-20261006-15/claims-query-cost-before.txt)、[claims-query-cost-after.txt](evidence/RR-20261006-15/claims-query-cost-after.txt)。

**写入代价**：多一个索引，每份 claim 的插入与标记多维护一条索引项。`BenchmarkRealMongoCommandInboxHandle`（同机、同一私有副本集，无索引 / 有索引两个
二进制交替各跑 8 次，`-benchtime 500x`）：无索引 18.27ms ± 4%、有索引 18.33ms ± 3%（p=0.442，无显著差异），B/op +0.15%，allocs 不变。原文 [handle-bench-index.txt](evidence/RR-20261006-15/handle-bench-index.txt)。
