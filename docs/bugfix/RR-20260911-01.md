# RR-20260911-01:墓碑计数淘汰早于信封过期,再铸领取 token

**仓库 / 位置**:roost-kit `service/mail/mailbox.go`(`evictSettledClaims`)、
`service/mail/service.go`(`ReserveClaim`、`Deliver`)、`service/mail/types.go`。
**修复单元**:U-0171(C8)。**定位文档**:TROUBLESHOOTING T-65。
**关联**:RR-20260910-02 / U-0165 —— 原单次淘汰的修复有效,本条是墓碑层的另一个触发条件。

## 问题

A 已领取并提交,Entry 被淘汰、留下墓碑。信封还有一周有效期,期间又有 `MaxSettledClaims` 条
更新的已领取邮件被淘汰:A 的墓碑成为最旧项被计数上限挤掉。之后 A 重投,`Deliver` 当作首次
投递,`ReserveClaim` 只确认信封仍有效,于是返回同一个附件和一个**新 token**。

## 根因

我在 U-0165 的记录里写过:"计数上限够用是因为 `ReserveClaim` 本来就拒绝过期信封,墓碑只需活得
比信封长。"**这个论证是错的。** 计数上限保证不了任何时间期限:被挤掉的时刻只取决于后面来了
多少条,与信封还剩多久毫无关系。"过期邮件会被拒绝领取"推不出"未过期邮件是安全的"。

这也是 C8:保留策略按条数判断"哪条该忘",而可领取性按时间判断"哪条还要紧",两条路径对同一个
对象用了不同的判据。

## 方案选择

- **单纯增大 200。** 只能推迟触发,不能消除。审查明确指出了这一点。
- **token 由业务身份稳定派生。** 发奖侧按 token 去重就只付一次,但邮件仍会重新变成未读、重新
  可领,产品语义仍然错;而且 token 从随机凭证变成可推导值。
- **按信封的可领取窗口保留,容量不足时明确拒绝(采用)**。领取身份活到"这封邮件再也领不了"
  为止;真的挤不下时拒绝投递,而不是悄悄忘掉一条身份 —— 这与 `full()` 对"腾不出位置"的处理
  是同一个态度:操作者必须看见,静默丢失才是这个上限要防的事。

## 改动

- `Entry` 增加 `ClaimEnvelopeExpiresAtUnix`,`ReserveClaim` 从信封抄进去(那里本来就持有信封)。
- `evict` 把它一并写进 `SettledClaim.EnvelopeExpiresAtUnix`。
- `evictSettledClaims(nowUnix)` 改为按时间:信封已不可领取才删。
- **旧记录的兼容**:U-0165 写下的墓碑没有窗口字段,无法按时间老化。只有这一类才按计数淘汰,
  最旧先删,且仅当整体超过上限 —— 这既给升级后的邮箱收了界,又保证"知道自己在保护什么"的记录
  永不被提前删掉。
- 新增 `ErrClaimHistoryFull`(码 590115),`Deliver` 在保留后仍超界时拒绝并计
  `refused:deliver:claim_history_full`。用独立错误而不是复用 `ErrMailboxFull`:两个上限失败的
  原因不同,操作动作也不同 —— 前者要玩家去读信,后者说明一个信封生命周期内领取并淘汰的附件
  太多了。

## 证明

`service/mail/settled_claim_retention_promises_test.go` 两条,全走公开 Service:

- `TestSettledClaimsOutliveTheEnvelopeTheyProtect`:建立一条墓碑后,在信封远未过期时反复
  制造新的"已领取并淘汰"。两种结果都算正确 —— 身份被保住,或投递被
  `ErrClaimHistoryFull` 明确拒绝;**绝不能**是悄悄忘掉。最后断言原邮件仍然
  `ErrAlreadyClaimed`,没有铸出第二个 token。
- `TestSettledClaimsAreDroppedOnceTheEnvelopeExpires`:把时钟推过信封截止,再触发一次保留,
  断言墓碑确实被清掉 —— 它不该永远留着。

`claim_identity_promises_test.go` 里 U-0165 那条按计数收界的测试改为
`TestSettledClaimsAgeOutWithTheirEnvelope`:最旧但仍可领取的不删、已过期的删、没有窗口的旧记录
才按计数删,并断言有窗口的记录不会被计数挤掉。

修前红:

```text
reserve … / the settled claim was dropped while its envelope was still claimable
```

修后 mail 含 `-race` 全绿,kit 全仓绿。

## 未做 / 边界

- **`ErrClaimHistoryFull` 是一个新的拒绝路径。** 一个邮箱在单个信封生命周期内领取并淘汰超过
  `MaxSettledClaims` 封附件邮件时,新投递会被拒。这是刻意的取舍:拒绝可见,遗忘不可见。
  真遇到了应该调大上限或缩短信封有效期,而不是把遗忘放回来。
- **升级期的旧墓碑没有窗口**,只能按计数老化。也就是说升级前留下的记录仍带原来的残余风险,
  直到它们被清掉或被新记录取代。
- 没有连接真实资产服务;证明的是不再铸出第二个 token,不是"此前发生过真实重复发放"。
- 过期清理只在投递触发保留时发生。一个再也收不到邮件的邮箱会一直留着它的墓碑,这点与 Entries
  的保留策略一致。
