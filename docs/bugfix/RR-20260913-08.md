# RR-20260913-08:快照的绝对过期时间未参与读取准入

**仓库 / 位置**:roost-core `entity/remote_snapshot.go`,`Get`。
**修复单元**:U-0175(C8)。**定位文档**:TROUBLESHOOTING T-69。

## 问题

`RemoteSnapshotEnvelope` 有 `ExpiresAt` 与 `Expired()`,但构造缓存时只用了固定的容器 TTL,`Get`
从不看这个字段。把 `ExpiresAt` 设成一秒前、TTL 设成一分钟,Cached 读仍然 `found=true`,而返回的
这份 `Expired(now)` 为真 —— 调用方拿到一份自己声明已经过期的业务快照。

## 根因

两个有效期判的不是同一件事:容器 TTL 是"本机还保留多久",信封 `ExpiresAt` 是"这份数据到什么
时候为止还算数"。只用前者做准入,等于让缓存的保留策略去替业务决定数据是否有效。

## 方案选择

- **在写入时拒绝已过期的值。** 不够:发布时还没过期、读取时已经过期,才是常态。
- **以两者中更早的那个控制可用性(采用)**:读到的值若已过自己的截止时刻,就当作未命中。
  Cached 答"没有",Monotonic 按契约回权威 —— 这正是 miss 本来的处理路径,不需要新分支。

## 改动

`entity/remote_snapshot.go`:`Get` 在 `layered.Get` 之后、分派之前判一次 `Expired(time.Now())`,
命中则把结果降级为未命中,注释写明两个有效期各自回答什么。

## 证明

`entity/snapshot_expiry_promises_test.go`:发布一份 `ExpiresAt` 在一秒前、容器 TTL 一分钟的快照,
断言 Cached 读不命中、Monotonic 读回权威且权威只被问了一次;再发布一份不设 `ExpiresAt` 的,
断言它照常命中 —— 没有 `ExpiresAt` 的快照行为一字不变。

修前红:

```text
a cached read served a snapshot that declares itself expired: version=3 expired=true
```

修后 entity 含 `-race` 全绿。

## 未做 / 边界

- 只改了读取准入。发布一份已经过期的值仍然会被写进去(随后读不出来),L2 回填与权威加载的返回值
  也没有在各自入口再判一次 —— 它们最终都要经过 `Get`,所以行为一致,但没有更早拒绝。
- "同版本刷新有效期是否允许"这个产品问题没有回答,审查也把它列为待定。

## 2026-09-13 复核后的补修(仍归 U-0175)

审查第四轮指出:U-0175 只在 `Get` 的 `layered.Get` 命中后判了 `Expired`,而 Linearizable 直接返回
`LoadAuthoritative`,Monotonic miss 走 `loadMonotonic` 也返回它的结果,`LoadAuthoritative` 自己
Publish 后 `local.Get` 直接返回 —— 三条出口都没有过期后置条件。我原记录里"它们最终都要经过
Get,所以行为一致"这句是错的,提前返回路径不经过那道检查。

还有一个交错:L1 里是过期值,权威回来同版本同内容但更新的有效期,Publish 的同版本去重分支不看
过期元数据直接返回 nil,最终仍返回过期值。

**改动**:`LoadAuthoritative` 对权威原始返回值与 Publish 之后的 L1 值各判一次 `Expired`,过期即
miss,且过期的权威结果不进缓存(没有人能读它);`Publish` 的同版本相同内容分支,若新值的
`ExpiresAt` 更晚则继续写入(只是元数据前移),否则才短路返回。

**证明**:`snapshot_expiry_authoritative_promises_test.go` —— Monotonic 与 Linearizable 两种模式下
权威返回已过期快照,公开 `Get` 都不得 `found=true`;以及"L1 过期、权威同版本更新有效期"必须
返回新有效期。修前红:`mode 1 returned an expired authoritative snapshot`。

**边界**:权威持续返回过期值时每次读都是 miss,不会递归 —— miss 不触发再次加载。

## 2026-10-05 复核后的补修（仍归 U-0175）

基线40d89ac6。原补修两处 Expired 复用了 Publish 前的时间；Publish 内的有界 L2 I/O 可以跨过 ExpiresAt，最终检查仍用旧时间，读出一份在返回时已经过期的快照。

采用在最终 L1 返回前使用 `time.Now()` 重新判定。没有把信封截止时间改成容器 TTL，没有删除缓存/水位，没有在过期后递归加载；保留 miss 语义。也没有为测试引入时钟接口或新调度器。

[正式测试](../../entity/snapshot_authoritative_admission_promises_test.go) 的 L2.Set 等待信封自己的250ms截止时间，明确检查写钩子实际触发，Monotonic / Linearizable 两项修前红：`expired during publish was served: found=true expired=true err=<nil>`。修后均返回 found=false/err=nil，随后无绝对期限的新版本5加载成功。[命令、红绿与最终验证](evidence/noncore-bugfix-20261005-14/README.md)。

此前测试只验证调用前已过期与同版本延长有效期，遗漏 I/O 期间跨越期限，不能据它们排除这个残余。[复盘与后置条件清单](../review/IMPLEMENTATION-AUTHORITATIVE-SNAPSHOT-POSTCONDITIONS.md)。已修复（含残余补修，未发版）；只收紧最终读取准入，过期值仍可能按容器 TTL 保留。没有验证系统时钟回拨、真实 Redis HA 或长期容量。
