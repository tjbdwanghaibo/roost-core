# RR-20260911-06:异步 AfterCommit panic 遗漏回复与释放;饱和回退可崩溃

**仓库 / 位置**:roost-core `nest/rollback.go`(`Commit`)、`nest/pipelined_completion.go`
(`complete` 闭包与泵的饱和回退)、`nest/nest.go`。**修复单元**:U-0183(C5)。
**定位文档**:TROUBLESHOOTING T-77。

## 问题

两个表现,一个根因。

**回复与释放丢失**:`Commit` 先把事务标成 committed,再逐个执行回调,没有逐项异常隔离。一个业务
`AfterCommit` 回调 panic,后面的回调全部跳过 —— 包括框架自己追加的 `TransactionReleased` ——
`retChan` 也没有发送。worker 的 `SafeFunc` 只在最外层恢复并打日志:goroutine 活下来了,被跳过的
义务没有。调用方只能等自己的取消或超时,而事务已经持久化。审查实测:
`missing_reply=true release_count=0 durable_lsn=1 value=1`。

**进程崩溃**:completion pool 饱和时 `pump.run` 直接内联调用 `complete`,这个 goroutine 是泵本身,
没有 `SafeFunc` 边界。审查在隔离子进程实测:普通回调正常退出,改成 panic 后子进程 exit 2,
堆栈 `RollbackTx.Commit → prepareCompletion → completionPump.run`。

## 根因

业务回调的异常控制流被当成了框架收尾的一部分:一个 panic 既取消了后续回调,又逃出了没有恢复
边界的 goroutine。持久化事实已经不可回滚,框架的义务(释放通知恰好一次、回复恰好一次)不应
依赖业务代码不出错。

## 方案选择

- **只在饱和回退外面套 recover。** 进程不崩了,但回复与释放照样丢。审查已指出"仅恢复 panic 并
  打日志仍会丢回复/释放"。
- **把 TransactionReleased 从回调列表里拿出来单独执行。** 只救了释放,救不了其他被跳过的业务回调,
  也没有把异常告诉调用方。
- **逐项恢复 + 报告(采用)**:`Commit` 对每个回调各自 recover,任何一个 panic 都记进返回的
  error(新增 `ErrAfterCommitFailed`),但**继续执行后面的回调**;异步完成路径拿到这个错误后,
  回复的是它而不是 handler 的返回值 —— 调用方明确知道"已持久化,但收尾失败",与回滚区分开;
  饱和回退包进 `goroutine.SafeFunc`,和 worker 的边界一致。

## 改动

- `nest/rollback.go`:`Commit()` 返回 `error`;`runCommitCallback` 逐项恢复;两处同步调用方把错误
  交给闭包的命名返回值。走 guard `AppendPostRelease` 的路径不变,guard 的执行器本来就逐项恢复。
- `nest/nest.go`:`ErrAfterCommitFailed`。
- `nest/pipelined_completion.go`:`complete` 按 `Commit` 的错误回复并计
  `async_total{result="completion_failed"}`;饱和回退 `goroutine.SafeFunc(func() { complete(err) })`。

## 证明

`nest/commit_callback_panic_promises_test.go`:三个回调,中间一个 panic —— `Commit` 必须返回
`ErrAfterCommitFailed`,且第一个和第三个都执行过(第三个模拟 `TransactionReleased`);第二次
`Commit` 幂等、不重跑回调。

修前:`tx.Commit()` 无返回值,测试不编译;把签名改成 `error` 后 panic 直接穿出测试。修后 nest
含 `-race` 全绿。

## 未做 / 边界

- 没有复现审查那个"真实 Nest Request + 可控 committer + 饱和 pool"的端到端场景,也没有在子进程里
  验证饱和回退不再退出。逐项恢复是在 `Commit` 这一层证明的,饱和回退的边界是代码改动,靠
  `SafeFunc` 的既有行为保证。
- 同步路径(`durableCommit` 之后的 `Commit`)现在把回调 panic 变成 handler 的返回错误,而不是穿出
  到 worker 的 `SafeFunc`。这是有意的:两条路径对同一种失败给同一种答案。
- 走 `RemoteWriteBatch` 的 `addPostRemoteCommit` 路径把回调交给远端批次,那边的执行器没有在
  这个单元里检查。
