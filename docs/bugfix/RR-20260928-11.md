# RR-20260928-11 修复：回退到 strict 路径的 pipelined 记录经 `WAL.Append` 提交时等 fsync

问题：[RR-20260928-11](../bug/RR-20260928-11.md)（来源：[RR-20260928-09 修复记录“kit 装配下 pipelined + Remote 路径的其他差异”](RR-20260928-09.md)）。日期 2026-09-28；基线 `ead6a9d`；worktree 分支 `fix-r10-b20`。
codebase-memory 图谱停在 09-26，已过期，未使用；以当前源码与实跑为准。状态：已修复，本地提交，未 push / 发布。

## 根因

- pipelined handler 在两条路径上不走 `Enqueue`，回退到 strict 提交：`nest/execution.go:177-188` 只有 `releaseLocks != nil` 且消息不带 Remote 批次时才选
  `PipelinedTransactionCommitter`；broadcast（`nest/nest_dispatch.go:542` 传 `releaseLocks == nil`）与带 Remote 批次的消息落到 `commitDurable`
  → `durableCommit`（`nest/rollback.go:615` `committer.Commit`），记录的 `Durability` 仍是 3（`tx.durability = meta.Durability`）。
- 进入 WAL 的阻塞式入口：kit 装配 `kit/dataengine/mod.go:355` `Mod.Commit` → `dataengine/engine/projector.go:266` `Projector.Commit` → `WAL.Append`；
  另一实现 `nestwal/committer.go:194` `Committer.Commit` → `WAL.Append`。
- 基线 `nestwal/wal.go:331`：`requireSync: record.Durability == corenest.DurabilityStrict`。Durability 3 不在内，写线程 `processBatch`（`:928-969`）
  对这一批不 fsync，`Append` 写完即返回，与 async 相同；fsync 要等组提交 ticker（默认 10ms）或其他 requireSync 的批次。
- 于是 Nest 在 `Append` 返回后释放锁、按 Guard post-release 执行 Sync `Confirm` 与 AfterCommit、回复；带 Remote 批次时锁外开始 Remote 确认，
  第 4 行“本地已提交、Remote 被拒绝”的回复也可能在本地部分 fsync 之前送达。违反 `NEST_PIPELINED_COMMIT.md` §5 “表现等同 Strict（锁内等待 durable）”。

## 决策

`nestwal/wal.go:337`（修后）改为 `requireSync: record.Durability >= corenest.DurabilityStrict`，注释写明原因与编号；`Append` 加文档注释说明各 Durability 的返回时机。

- 取值范围：`Append` 在这一行之前调用 `encodeRecordVersion` → `canonicalizeRecord`（`nestwal/codec.go:61`），`Durability > DurabilityPipelined` 已被拒绝，
  所以 `>= Strict` 恰为 {strict 2, pipelined 3}；memory 0 与 async 1 不变。
- 快路径不受影响：正常 pipelined 记录走 `Enqueue`（`requireSync: true`，票据在 fsync 后完成），不经 `Append`。
- 快池契约：broadcast / Remote 批次上 pipelined 本来就在锁内提交（设计如此），锁内 WAL 准入及 strict 锁内 fsync 属于 roost-coding 的显式豁免；本修复只让它
  与文档写的 strict 语义一致，没有新增等待入口。
- 未采用：在 nest 侧把回退路径的 `tx.durability` 改写成 strict——会改变写进 WAL 的记录（回放、Remote finalizer 与 `outcome.Durability` 都按 3 处理，
  RR-20260928-09 刚按 `>= 2` 对齐），而且缺陷在 WAL 的“阻塞入口要等什么”这一层；只在 kit `Projector.Commit` 改——`nestwal.Committer` 路径仍漏。

## 兼容性

- 公开 API、配置、WAL / checkpoint 格式不变。
- 行为变化（供 CHANGELOG）：pipelined handler 在 broadcast 与带 Remote 批次的消息上，现在与 strict 一样在锁内等本地 WAL fsync 后才释放锁、确认 Sync、执行 AfterCommit 与回复；
  这两条路径的锁持有时间与延迟因此包含一次组提交 fsync（之前实际是 async 语义，进程在组提交间隔内崩溃会丢掉已对外可见的事务）。单目标 / 多目标 dispatcher 路径（`Enqueue`）不变。
- 直接调用 `nestwal.WAL.Append` / `Committer.Commit` / `Projector.Commit` 并传 Durability 3 的自定义代码：返回时机从“写入后”变为“fsync 后”。

它的本地提交与 broadcast 走同一 `Append` 判定，多出的等待是一次组提交 fsync，与 Remote 确认等待（投影器结论）相比处于次要量级，但没有实测数字。
