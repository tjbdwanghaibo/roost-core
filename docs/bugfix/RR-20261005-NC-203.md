# RR-20261005-NC-203 修复：会改动隔离环境的入口在别人持有验收锁时拒绝

日期 2026-10-05。基线 `8597046c`（审查提交 `345488e4`）。状态：已修复、声明场景验证，未发版。问题：[RR-20261005-NC-203](../bug/RR-20261005-NC-203.md)。

## 决策

- `lib/common.sh`：`ROOST_IT_ACCEPTANCE_LOCK=<根>/remote-acceptance.lock`；`require_acceptance_lock_free_or_held`（锁不存在或 `ROOST_REMOTE_ACCEPTANCE_LOCK_HELD` 等于锁路径才放行，否则 2）；`acquire_acceptance_lock`（mkdir 取得、EXIT 释放、导出持锁标记；上层已持有时沿用）。
- `dataengine-env.sh`：`preflight`（up / fault / heal）、`down`、`reset` 先检查锁；`test` 在 `environment_up` 之前取得锁（先建根并记录偏移，避免新根被偏移检查拒绝），整套故障用例运行期间与矩阵 / 长稳互斥。`status` 只读不受限。usage 写明规则。
- `scripts/remote-fault.sh` 注入前检查锁。
- 持锁者 `scripts/test-remote-matrix.sh`、`scripts/perf/remote.sh` 取得锁后导出 `ROOST_REMOTE_ACCEPTANCE_LOCK_HELD`，自己调起的 heal、生成工程调用的 remote-fault.sh 由此放行。

未采用：让 fault / heal 各自去 mkdir 取锁——矩阵调用它们时锁已被矩阵持有，只能靠持锁标记区分“持锁者的子进程”与“别的会话”。没有把锁扩展到 `go test -tags integration` 的故障用例本身（属方向判断里的 (a)，待维护者定）。

## 行为与兼容

锁空闲时所有命令行为不变；持锁期间其他会话的 up / down / reset / fault / heal / test / remote-fault 以 2 拒绝并提示“不要在不清楚持有者时删锁”。nightly CI 的 `test` 在新根上取得并释放锁，之后的 `down` 正常。强杀后残留的锁会挡住这些命令（审查 O4），按 C01-RUNBOOK 确认后手工删。

## 验证

- 红：临时根上放锁，fault / down / remote-fault / reset 都 exit 0，reset 删掉锁和根（[脚本](../review/evidence/noncore-review-20261005-n15/lock_red.sh) · [输出](../review/evidence/noncore-review-20261005-n15/nc203-red.txt)）。
- 绿：四个入口 exit 2（`refuse: … is held by a running Remote acceptance / fault run`），锁仍在，status 照常（[输出](evidence/noncore-bugfix-20261005-n15/nc203-green.txt)）。
- 控制：带持锁标记时 fault / remote-fault / down exit 0；`acquire_acceptance_lock` 空闲时取得、二次取得被拒、进程退出后释放（[脚本](evidence/noncore-bugfix-20261005-n15/lock_control.sh) · [输出](evidence/noncore-bugfix-20261005-n15/nc203-control.txt)）。
- `dataengine_env_test.sh`、根包、shellcheck 通过。

## 未验证

没有在共享隔离环境上实跑修后的矩阵 / heal（会注入故障）；持锁者链路按源码与临时根控制验证。

## 复核后的补修（2026-10-05，维护者决定 A5）

[残余](../bug/RR-20261005-NC-203.md#复核后的补修2026-10-05维护者决定-a5)：全局命令只检查锁、不持有；调用 fault / heal 的 Go 用例与带故障的生成工程验收整段不持锁。上文“未采用：让 fault / heal 各自去 mkdir 取锁”的理由（矩阵调用时锁已被矩阵持有）由持锁标记解决：`acquire_acceptance_lock` 在上层已持有时沿用，不重复取锁。

- `lib/common.sh`：删掉只检查的 `require_acceptance_lock_free_or_held`；`acquire_acceptance_lock` 在根目录不存在时放行（没有可保护的环境），取得后记 `ROOST_IT_ACCEPTANCE_LOCK_OWNED`，EXIT 时由新的 `release_acceptance_lock` 释放（沿用上层的锁时不释放）。
- `dataengine-env.sh`：`preflight`（up / fault / heal）、`down`、`reset` 改为持锁；`up` 先建根、记录偏移再取锁（锁目录在根下面）。usage 改为“除 status 外的命令运行期间持锁”。
- `scripts/remote-fault.sh`：持锁。`scripts/test-remote-generated.sh`：带 `ROOST_REMOTE_FAULT` 时在生成工程之前取锁，EXIT trap 同时删工作目录与释放锁。
- `kit/dataengine/failover_integration_test.go`：`holdAcceptanceLock(t)` 在登记 heal 之前取锁（经 `dataengine-env.sh test` 运行时沿用），别人持有时直接失败、不注入故障，并对子命令设持锁标记；heal 之后释放。
- 守卫：`kit/scripts/integration/dataengine_env_test.sh` 新增一节，用临时根（偏移 31000）加 PATH 垫片（`mongod` / `mongosh` / `nats-server` / `redis-*` / `curl` / `jq` / `nc` / `go`，被调用时记下锁目录在不在后失败退出，不碰任何服务）断言 fault / heal / remote-fault / 带故障的 test-remote-generated 运行期间持锁、退出后释放，别人持锁时 fault / heal / down 以 2 拒绝且不触达服务，持锁者的子进程沿用且不释放；根包 `TestGlobalEnvironmentOperationsHoldTheAcceptanceLock` 扫描调用 `dataengine-env.sh` 的 Go 用例（fault / heal 必须先 `holdAcceptanceLock(t)`）与调起环境命令的 `scripts/*.sh`、`scripts/perf/*.sh`（必须持锁）。

验证：

- 红（基线 `bb3aa647`）：垫片一节四条全部 `lock=free`；根包守卫点名三个 failover 用例与 `scripts/test-remote-generated.sh`（[输出](evidence/a4-config-20261005/a5-red.txt)）。拒绝与持锁者子进程两条在基线上即通过（NC-203 已有的行为）。
- 绿：`bash kit/scripts/integration/dataengine_env_test.sh` 通过；`GOWORK=off go test -count=1 .` 通过；`go vet -tags integration ./kit/dataengine/` 通过。

兼容：锁空闲时命令行为不变，只是运行期间别的会话的全局命令会被拒绝（以前会交错执行）。强杀后残留的锁照旧按 T-252 处置。普通 `-run` 用例（自建代理 / 进程注入故障）不取锁，与这些命令可以并行，这是 A5 的共享模式。

未验证：没有在共享隔离环境上实跑三个 failover 用例与带故障的生成工程验收（它们会停共享节点）；持锁链路按临时根与垫片验证。
