# RR-20261005-NC-203 修复：会改动隔离环境的入口在别人持有验收锁时拒绝

日期 2026-10-05。基线 `8597046c`（审查提交 `345488e4`）。状态：已修复、声明场景验证，未发版。问题：[RR-20261005-NC-203](../bug/RR-20261005-NC-203.md)。

## 决策

- `lib/common.sh`：`ROOST_IT_ACCEPTANCE_LOCK=<根>/remote-acceptance.lock`；`require_acceptance_lock_free_or_held`（锁不存在或 `ROOST_REMOTE_ACCEPTANCE_LOCK_HELD` 等于锁路径才放行，否则 2）；`acquire_acceptance_lock`（mkdir 取得、EXIT 释放、导出持锁标记；上层已持有时沿用）。
- `dataengine-env.sh`：`preflight`（up / fault / heal）、`down`、`reset` 先检查锁；`test` 在 `environment_up` 之前取得锁（先建根并记录偏移，避免新根被偏移检查拒绝），整套故障用例运行期间与矩阵 / 长稳互斥。`status` 只读不受限。usage 写明规则。
- `scripts/remote-fault.sh` 注入前检查锁。
- 持锁者 `scripts/test-remote-matrix.sh`、`scripts/perf/remote.sh` 取得锁后导出 `ROOST_REMOTE_ACCEPTANCE_LOCK_HELD`，自己调起的 heal、生成工程调用的 remote-fault.sh 由此放行。

未采用：让 fault / heal 各自去 mkdir 取锁——矩阵调用它们时锁已被矩阵持有，只能靠持锁标记区分“持锁者的子进程”与“别的会话”。没有把锁扩展到 `go test -tags integration` 的故障用例本身（属方向判断里的 (a)，待维护者定）。

## 行为与兼容

锁空闲时所有命令行为不变；持锁期间其他会话的 up / down / reset / fault / heal / test / remote-fault 以 2 拒绝并提示“不要在不清楚持有者时删锁”。nightly CI 的 `test` 在新根上取得并释放锁，之后的 `down` 正常。强杀后残留的锁会挡住这些命令（审查 O4），按 C01-RUNBOOK 确认后手工删。
