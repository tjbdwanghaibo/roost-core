# NC-224 修复：spawn 进程每一步重新求值的字段不能读施法输入、memory 与局部变量

[问题](../bug/RR-20261005-NC-224.md) · [本轮](../review/REVIEW-2026-10-06-n09-batch5.md)。已修复（方向 A）、声明场景验证，未发版。

## 根因与决策

进程字段按施法作用域做类型检查，却在移交后的进程上下文里逐步求值。两个方向：

- **A（采用）**：编译期拒绝。`skill/compile_owned_entity.go` 的 `validateDetachedProcessFields`：对 spawn 的进程里每一步都会重新求值的字段（area 选择、follow / tracking / carry 目标、path 点、orbit 锚点、parabola 目的地、未绑定进程数值属性的数值字段）中的 `$input.*` / `$memory.*` / `$local.*` 引用报 `INPUT_UNAVAILABLE`，定位到引用本身。numeric track 的值与绑定到属性的数值字段只在启动时用施法求值一次（`initializeProcessNumeric`），不在此限；`$caster` 系列在两个上下文里都是施法者，仍允许。这与回调的既有规则、AI 生成约束（“Entity-scoped processes cannot read expired Cast memory or input”）一致。
- **B（未采用，留给维护者）**：进程启动时把施法输入（以及需要时 memory）冻结进 `ProcessInstance`（这两个字段与 checkpoint 字段已经存在、目前不被填写），`detachedProcessCast` 读冻结值。这样 path 投射物（`points: $input.path`）、落点投掷（`destination: $input.position`）才真正可用；A 下它们只能用 `$caster.position` 等。B 是语义扩展（冻结时机、memory 是否跟随），不在 bugfix 范围。

`ProcessScopeCast` / `ProcessScopePhase` 仍有类型定义、没有创建点；进程字段的“施法作用域”检查看来是那时留下的，B 若实施可一并清理。

## 文件与行为

`skill/compile_owned_entity.go`。上表定义从“下一 tick 起 ErrProgramInvariant”变为启动期编译失败。`motion_test.go` 两个用内部 harness 以施法本身推进的用例改写：path 用例直接驱动 `advanceMotionPath` 的算术，parabola 用例的目的地改为 `$caster.position`；“未初始化的 motion memory 目标”用例改为断言 `INPUT_UNAVAILABLE`（memory 在进程字段里一律不可读，原 `MEMORY_MAYBE_UNINITIALIZED` 已不可达）。

## 兼容性
