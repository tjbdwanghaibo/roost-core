# RR-20260926-48 修复：handler 内新建实体按 Cast 锁序取锁，冲突时整条回滚并重新准入；memory handler 内 Create 持锁到 handler 结束

问题：[RR-20260926-48](../bug/RR-20260926-48.md)（探针见 [REPRO-2026-09-26-05 §1、§1b](../bug/REPRO-2026-09-26-05.md)）。
日期 2026-09-26；实施基线本地 main `3e26f91`（未推送）。状态：已修复、本地验证通过，已本地提交，未推送 / 未发布。
方向按维护者批准的“修复约束”：handler 内新建实体的加锁遵循与 Cast 相同的锁序规则并使用 try-lock；冲突时整条消息回滚后以锁超时类
可重试错误重新准入（复用现有 requeue），不在快 worker 上无界阻塞、不在 handler 执行一半迁移；memory 模式 handler 内 Create 同样在
Guard scope 内持锁至 handler 结束；RR-35 的提交边界与撤销发布语义保持。

## 根因（基线源码核对）

- `entity/manager_factory.go` `CreateInScope` 用 `EntityGuard.RequireEntity`（`entity/entity_guard.go`，`mu.Lock()` 无超时）取新实体的锁，
  不做 Cast 的锁序检查。RR-35 复核补修后，handler 内 `EntityManager.Create`（生成 Lifecycle 的 `Create` / `GetOrCreate` 创建分支）
  沿用 handler 的 Guard，锁持有到事务结束：两个 handler 以相反顺序新建 X、Y，各持一把等另一把，两个快 worker 永久阻塞，Guard 与声明实体
  都不释放。新建 X（与已持有同组）后再 Cast 更高锁组的 Z，而持有 Z 的另一个 handler 新建 X，同样成环。
- Cast（`nest/cast.go`）只在目标锁组高于已持有的全部锁组时等待（`CheckContainAllIDs` / `CheckContainAllLock`，否则 `ErrCastDeadlockRisk`）；
  嵌套派发（`lockDispatchEntities`）在同一判定不满足时改用 try-lock 并返回 `ErrLockTimeout`，由 `requeueTransientDispatch` 重新准入。
  新建实体的锁两条规则都没有走。
- memory 快路径（`nest/execution.go` RollbackNone + DurabilityMemory、无 Remote 批次）不调用 `callTransactionHandler`，Guard 上没有绑定
  `CreatedEntityCapturer`；handler 内 `Create` 于是走自建短作用域，创建后立即解锁，handler 随后修改一个别人可以加锁的实体，
  新实体也不在本次 SyncMutation 里。

## 决策与实现

### 1. 取锁规则（`entity/entity_guard.go` `lockCreated`，`CreateInScope` 调用）

Guard 绑定了 `CreatedEntityCapturer`（即在 Nest handler 内）时：

- 新实体的锁组**高于**本 Guard 已持有的全部锁组（与 Cast 同一判定 `mayLock(id, maxLockedGroup())`）：照旧 `RequireEntity` 等待。
  这与 Cast 的有序等待完全相同——所有会等待的取锁（声明目标按 (锁组, ID) 排序、Cast / Create 只向更高锁组）都遵守同一个全序，
  不会成环，属于 Guard/本地锁豁免；
- 否则（同组或更低组，交叉创建、创建后再 Cast 更高锁组都落在这里）：只 `TryRequireEntity`。被占用时调用 capturer 的新方法
  `CreatedEntityLockBusy(id)`，把它返回的错误交给业务，**不发布、不持锁、不等待**。

Nest 之外（`Create` 自建的短作用域、独立 `WithGuardScope`）保持等待取锁、立即发布的原语义。

`TryRequireEntity` 是新导出的 Guard 方法（不等待取锁，已清理 / 已摘除返回 false）；Nest 的 `tryRequireDispatchEntity` 改为调用它，
去掉同一逻辑的两份实现。

选择“有序时等待、否则 try-lock”而不是一律 try-lock：约束写的是“与 Cast 相同的锁序规则”，一律 try-lock 会让锁序检查失去意义，并把
本来无环的有序等待（例如声明 Account 后新建更高锁组的 Player）也变成回滚重试；选择 try-lock 而不是 Cast 的直接拒绝：同组新建是生成
Lifecycle 最常见的写法（声明目标与新实体同一类别），直接拒绝会让它们全部失败，而冲突只是暂时的。

### 2. 冲突后的整条回滚与重新准入（`nest/rollback.go`、`nest/execution.go`）

- `RollbackTx.CreatedEntityLockBusy` 记录第一次冲突（`tx.createLockBusy`），返回满足 `errors.Is(err, ErrLockTimeout)` 的错误
  （`nest: lock timeout: created entity <id> is locked by another holder and cannot be waited for in lock order`）。
- `invokeWithTransaction` 在 handler 返回后：记录过冲突、事务可回滚（RollbackState / RollbackUndo）而回复错误里没有 `ErrLockTimeout`
  （业务吞掉了错误甚至返回成功）时，把冲突错误并入 `err`。随后走既有失败路径：`tx.Rollback()` 恢复快照 / undo、丢弃持久化记录、
  按 RR-35 撤销本事务里已发布的新实体；`dispatchNest` 的 `requeueTransientDispatch` 见 `ErrLockTimeout` 以克隆消息延迟 5ms 重新准入
  （上限 400 次，用尽后调用方收到锁超时）。冲突发生在准入之前，没有任何内容越过提交点。
- RollbackNone 的事务（以及 memory 快路径）不强制：它们本就不撤销已做的内存修改，强制重做会让这些修改重复生效；冲突错误原样交给业务，
  业务返回它时与 Cast / 嵌套派发的锁超时一样重新准入。

### 3. memory 快路径绑定（`nest/execution.go` `invokeMemoryHandler`、`nest/rollback.go` `memoryHandlerCreates`）

memory 快路径在调用业务期间把无状态的 `memoryHandlerCreates` 绑定到当前 Guard（新导出的无分配方法
`EntityGuard.SwapCreatedEntityCapturer`，`BindCreatedEntityCapturer` 改为基于它）。于是 handler 内 `Create` / `CreateInScope` 沿用 handler
的 Guard：持锁到 handler 结束、按上面的锁序取锁、进入本次 SyncMutation（handler 成功后 Admit + Confirm，锁释放后才可外发）。
它不捕获、不撤销（memory 快路径没有回滚），冲突时返回同一个锁超时错误。

### 4. 发布失败时归还锁（`CreateInScope`）

`TryAdd` 失败（`ErrEntityExists` / `ErrEntityRemoved`）时归还本次取得的锁。原实现把锁连同未发布的实例留在 Guard 上：同一作用域随后按同 ID
重试（RR-57 的 GetOrCreate 有界重试就会这样做）时新实例经 `eMap` 命中直接“已持有”，而 LockManager 可能已换了新 mutex，新实例会在
未加锁的情况下发布。

## 兼容性

- `entity.CreatedEntityCapturer` 增加方法 `CreatedEntityLockBusy(id int64) error`。该接口由 RR-35 新增，尚未发布；仓内实现只有
  `*nest.RollbackTx` 与 memory 快路径的内部类型。新导出 `(*entity.EntityGuard).TryRequireEntity`、`SwapCreatedEntityCapturer`。
- 行为：handler 内新建与已持有同组或更低组的实体时，锁被占用不再等待，而是回滚后重新准入；业务在第一次尝试里看到的
  `access.Create` 错误满足 `errors.Is(err, nest.ErrLockTimeout)`。重新准入的消息排到同 ID 后继之后（与 Cast / 嵌套派发 / 组锁的锁超时
  重排相同）。重排 400 次仍冲突时调用方收到锁超时错误。
- memory handler 内 `Create` 的实体现在持锁到 handler 结束并进入本次 Sync 提交屏障（handler 成功后外发，报错时本次同步内容丢弃，
  与 Cast 实体相同）；此前创建即解锁、立即可同步。memory handler 报错不撤销新实体（RollbackNone 语义不变）。
- 有序等待（新实体锁组更高）与 Nest 之外的调用不变。

## 对抗性自查

- **锁序与 Cast 一致**：新实体只在与 Cast 相同的判定成立（锁组高于已持有的全部锁组）时等待；判定使用的 `eMap` 已包含本 handler
  先前 Cast / 新建的实体，所以“先新建同组 X 再 Cast 更高组 Z”之后再新建同组实体仍只 try-lock。会等待的取锁只剩三类：声明目标按
  (锁组, ID) 排序等待、Cast 向更高锁组等待、Create 向更高锁组等待，三者遵守同一全序；其余一律 try-lock。
- **回滚后重排不重复执行已提交内容**：冲突发生在 handler 内、准入之前；可回滚事务整条 `Rollback`（快照 / undo 恢复、持久记录丢弃、
  新实体撤销发布、SyncMutation 按未准入丢弃），然后才由 `requeueTransientDispatch` 克隆重排，原消息不回复。pipelined 的冲突早于
  `Enqueue`，Remote 批次的冲突早于 `finalizeRemoteWriteBatch`，收尾走 Abort。RollbackNone 不强制重做（见决策 2）。已越过提交点的
  事务不被重排由 [RR-20260926-49](RR-20260926-49.md) 保证。
- **RR-35 提交边界 / 撤销发布**：捕获、Include、`revokeCreated`、准入前补 Include 都未改；新增的只有取锁方式与发布失败时归还锁。
  `TestCreateInScope*`、`TestLifecycleCreate*`、`TestCreateOutsideTransactionUnchanged` 在 `-race -count=20/200` 下通过。
- **同 ID 顺序与内部续行准入资格**：没有改派发队列与续行通道。冲突的消息按既有锁超时语义重新准入，排到同 ID 后继之后（与 Cast /
  嵌套派发相同，不是新增的破坏）；RunLocal、慢阶段续行不经过这条路径。
- **快池不阻塞**：不满足锁序的新建只 try-lock；满足锁序的等待与 Cast 相同，属于 Guard/本地锁豁免（持有者不会反过来等本 handler）。
  memory 快路径新增的绑定只是 Guard 字段交换，无 I/O、无分配。探针 A/B 的无关请求在冲突期间照常完成。

## 未验证项 / 风险

- 对称的交叉创建（两请求完全同时重试）在理论上可能连续冲突直到 400 次上限，调用方收到锁超时；回归中未出现，重排延迟固定 5ms、没有抖动。
- 同一 handler 内先 `Destroy` X 再新建同 ID 的 X：Guard 的 `eMap` 仍记着旧实例，新实例的锁被当作“已持有”，与修前相同，本次未处理。
- RollbackNone 事务 / memory handler 在冲突前已做的内存修改，若业务返回冲突错误并被重新准入，会再执行一次——与 Cast 在 memory handler
  内返回 `ErrLockTimeout` 的既有语义相同。
- 未在真实 WAL + Mongo 的端到端环境里构造交叉创建；回归使用受控 committer。
