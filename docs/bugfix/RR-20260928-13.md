# RR-20260928-13：CRLF 的 k8s Secret 示例与 LF 同样编辑；认不出结构时各命令统一 WARN

问题：[RR-20260928-13](../bug/RR-20260928-13.md)（第八轮独立审计，P4，含审计疑点 D2）。日期 2026-09-28。基线 `3a58811`，分支 `fix-r11-b21`（在 RR-20260928-12 提交之后）。
状态：**已修复**，回归修前红、修后绿，本地提交，未推送 / 发布。codebase-memory 图谱过期（09-26），本轮以当前源码、`rg` 与实跑为准。

## 根因

- `codegen/internal/roost/render_deploy.go:811`（基线）：`editKubernetesSecretExampleConfig` 用 `strings.Count(body, "\n  config.yaml: |\n") != 1` 定位。CRLF 文件里是 `\r\n  config.yaml: |\r\n`，定位失败后直接 `return "", nil`：不改文件，也不提示。`add mod` / `add saga`（经 `render.go:624` `appendModConfigSections`）与 `add transport tcp`（`add.go`）都走这里。
- `codegen/internal/roost/shutdown_budget.go:290`（基线）：`refreshGeneratedShutdownConfigs` 直接拿 `string(raw)` 去匹配。`:227` 摘要行正则里的 `(\d+)\n *# undeclared` 遇到 `\r` 匹配不上，`:296` 的整块比对同样匹配不上。因此 CRLF 的开发配置、生产示例与 Secret 三份文件的 `shutdown:` 块从此不再随 Mod 刷新，这个问题修前就有。
- D2：认不出 Secret 时，各命令处理不一致。`add mod` / `add saga` 静默跳过；`add transport tcp` 在内嵌 config 无法合并时（如 flow 风格的 `player_access`）走 `add.go:161`（基线），整体失败并回滚。

## 修复

- CRLF：新增 `lfText` / `restoreLineEndings`（`render_deploy.go`）。含 `\r\n` 的文件先规范成 LF 再定位、改写，写回时恢复 CRLF。这与仓内既有的 `ensurePlayerTCPConfig`（`player_tcp_config.go`，回归 `TestPlayerTCPConfigPreservesCRLFAndExistingParentMap`）做法相同。`editKubernetesSecretExampleConfig` 与 `refreshGeneratedShutdownConfigs` 都改走这条路径。混用行尾的文件写回后统一为 CRLF，与 `ensurePlayerTCPConfig` 一致。
- 认不出结构时统一处理。两种情况：没有恰好一个 `  config.yaml: |` 块；`edit` 返回错误，即内嵌 config 无法合并。`editKubernetesSecretExampleConfig` 这时向 `warn` 写一行警告，不动 Secret，返回 nil：

  ```text
  WARN: deploy/k8s/base/secret.<svc>.example.yaml: <原因>; left unchanged, apply the same change to its embedded config.yaml by hand (it mirrors configs/service/config.<svc>.prod.example.yaml)
  ```

  读写失败仍返回错误。`AddOptions` 新增 `Warnings io.Writer`，CLI 传入 stderr；值为 nil 时用 `os.Stderr`，保证不会静默。`appendModConfigSections` 多一个 `warn` 参数。

### 为什么统一成“WARN、不失败”，而不是统一成失败

- Secret 示例是非受控的脚手架，`project sync` 不重写它，也没有进程直接读它。部署从它复制出 `secret.<svc>.local.yaml`，或者改用 Vault / External Secrets 注入（DEPLOYMENT §3）。把它改写成生成器认不出的结构，比如 `data:` base64 或 kustomize `secretGenerator`，是合法的定制。如果因此让 `add` 失败，这类工程就再也加不了 Mod，而且没有绕过的办法。
- `add mod` / `add saga` 的既有语义本就不能“失败即回滚”：manifest 在追加配置段之前已经经 `commitManifestSync` 提交（`add.go`，Mod 分支）。在这之后失败只会留下半完成的状态。`add transport tcp` 把 Secret 放进回滚集合是 RR-07 的做法，现在只对读写失败保留：这类失败仍会回滚。
- 真正决定运行时配置的开发配置与生产示例，处理方式不变：`add transport tcp` 合并生产示例失败时，仍然整体失败并回滚。

停机块刷新没有新增 WARN：块被手改后不刷新，是它既有的“认不出就不动”，由 `roost doctor` 的 shutdown 检查报告（RR-20260926-66 / 80）。本修复只让它认得 CRLF。

## 文件与行为

- `codegen/internal/roost/render_deploy.go`：`editKubernetesSecretExampleConfig` 支持 CRLF，新增 `warn` 参数；新增 `lfText`、`restoreLineEndings`。
- `codegen/internal/roost/shutdown_budget.go`：`refreshGeneratedShutdownConfigs` 支持 CRLF。
- `codegen/internal/roost/render.go`：`appendModConfigSections(..., warn)`。
- `codegen/internal/roost/add.go`：新增 `AddOptions.Warnings`；Mod / saga / transport 三个分支都把它传下去。`add transport tcp` 的 Secret 合并失败从“整体失败回滚”改为 WARN。
- `codegen/internal/roost/cli.go`：`runAdd` 传入 stderr。
- `codegen/internal/roost/k8s_secret_crlf_promises_test.go`（新）：
  - `TestCRLFKubernetesSecretExampleGetsTheSameEditsAsLF`：LF 与 CRLF 两个工程执行同样的 `add mod redis` → `add saga` → `add access player` → `add transport tcp`，每步之后 `sync`。忽略行尾后，三份配置要与 LF 工程逐字节相同；CRLF Secret 里不能出现只有 LF 的行；`add mod` 之后 CRLF Secret 要有 `redis:`。
  - `TestUnrecognizedKubernetesSecretExampleIsAVisibleWarningForEveryCommand`：经 CLI 的 `Run` 执行两种情况，都断言命令成功、stderr 有 WARN 并点名 Secret、Secret 里对应内容没被猜着改。一是 `add mod redis`，Secret 的 `config.yaml: |` 被改名；二是 `add transport tcp`，只有 Secret 里的 `player_access` 是 flow 风格，同时断言生产示例照常加上 `tcp:`。
- 使用说明：`docs/DEPLOYMENT.md` §3。

## 兼容性

- 只影响 `roost add` 这几个入口和 `project sync` 的停机块刷新。生成文件不变，LF 工程的行为逐字节不变（上面的回归以 LF 工程为基准）。
- `add transport tcp` 遇到无法合并的 Secret 时，由失败改为成功加 WARN，Secret 保持原样，需要手工同步。脚本里依赖它失败的调用方需要改看 stderr。
