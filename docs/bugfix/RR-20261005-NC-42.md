# NC-42 修复：持久 opening 恢复前校验完整计划

[问题](../bug/RR-20261005-NC-42.md) · [证据](evidence/noncore-bugfix-20261005-17/README.md) · [机制](../review/IMPLEMENTATION-OUTBOX-CLAIM-AND-OPENING-RECOVERY.md)。已修复、声明场景验证，未发版。

## 实现与兼容

admitToWindow 在复用持久 Intent 前调用既有 openingIntentProblem，检查 Key.Validate、所属 group、intent 与 entry 同键、pending 状态及合法 expected 集合。坏计划包裹 ErrConflict，在 Activities.Create 及窗口修改前拒绝，保持原数据供操作员检查。合法持久计划仍优先于新调用的 expected 集合；legacy 缺 Intent 仍能由合法 Open 补计划，无新格式/API/配置或迁移。

共用校验的 sweep 另补 RR-20261001-09 残余：在访问 Activities 之前拒绝非法 opening key 或跨组条目，保留名额并计 malformed，同组正常到期活动继续完成/派发。诊断缓存以实际所属窗口分组，不能用坏记录自报的 GroupID 决定归属；移除条目后清理诊断、日志报恢复。既有有界扫描/未扫描条目保留、legacy grace 回收、Create 结果未知保留责任不变。

这会收紧坏存量的公开 Open 行为：以前可能成功并写出污染活动，现在返回 ErrConflict。修正可信原计划后再试；不能将错误视为允许删活动/WAL。已污染记录需要具名对账，不自动修复。畸形计划不会让正常当前版本首次 Open 产生，故按 P3 记录。

## 红绿与取舍

原 public Open 三种形状均红；sweep 非法 ID、含分隔符 phase、foreign group 三种均红，最后一种还在跨组写后因无窗口 admission 阻塞本组。旧产品 overlay 同样6红，均落在实际副作用或推进承诺上，非编译失败。

最终本文件10叶子通过：3公开拒绝→人工修复→正常重投，3 sweep 跳过→保留坏计划→正常活动完成，2合法持久/legacy 控制，1诊断清理，1 owner-only ReconcileProgress 读后另一 Service 加入新证明的控制（不误清新证明，第二次对账收敛）。未改 admin 实现；该控制是继续 review 的新增证据。

没有新 manager、自动删坏记录或循环重试。没有把所有存储损坏都宣称已覆盖；confirmed Keys 中的异键存量、晚到旧 writer、真实 Redis Cluster/混跑升级仍待专项。采用 Memory/正式 Service 后端契约，真实 Redis 未本轮独立执行；历史 Redis 证据不能冒认当前补修验收。
