## 根因

- 前 20 里的 6.5s 几乎全是一次 game-demo `NewProject`。game-demo 有 470 个文件，每个都经 `writeAtomic`（`codegen/internal/roost/project.go:626`）写临时文件、`Sync()`（`:640`）、改名。darwin 上 `File.Sync` 是 `F_FULLFSYNC`，Windows 上是 `FlushFileBuffers`，后者还要叠加 Defender 对新文件的扫描。用 CLI 实测，本机一次 game-demo 生成墙钟 9.6s，CPU 23%。生成 game-demo 的调用点共 25 处：`newGameDemo` 20 处，`shutdown_budget_test.go` 3 处直接调用，`demo_test.go` 2 处。其中几处在子用例循环里，每个子用例各生成一次；前 1～3 名就是一个用例里生成两到三次。另有约 50 个用例各自生成一个 75 个文件左右的小工程（每个 0.5～1.2s）。
- 这些用例要的只是生成出来的那棵树，大多随后只做 `sync`、`doctor` 或读文件。写盘的 fsync 成本却每个用例都付一遍，而且整包全部串行。
- `writeAtomic` 的 fsync 是生产语义（工程文件崩溃安全），不能为了测试去掉，也不能加测试专用的“跳过 fsync”入口。因此修测试侧的重复，不动生产代码。

## 修复（只改测试）

### 1. 生成工程夹具：同参数只真实生成一次，每个用例拿私有副本

新增 `codegen/internal/roost/project_fixture_test.go`：

- `projectFixtureOptions` 登记四种形状：`game-demo`（`configdata,mongo,nats,dataengine,nest` + `Template: game-demo`）、`saga`（`configdata` + `saga`）、`configdata`、`bare`（只有 Name / Module）。其中 Name 都是 `planet`，Module 都是 `example.com/planet`，与各调用点原来的参数逐字相同。
- `generatedProjectFixture(name)` 用每个形状各自的 `sync.Once`，把工程生成到包级临时目录。之后的调用直接返回这份原件，原件只读，不交给用例改。`TestMain` 在 `m.Run()` 之后删除整个目录，本机核对过跑完不留残余。
- `copyOfNewProject(t, name)` 把原件复制到 `filepath.Join(t.TempDir(), "planet")` 并返回这个路径，与原来 `NewProject(Out: filepath.Join(t.TempDir(), "planet"))` 返回的 root 形状相同。复制时逐个文件、逐个目录保留权限位（根目录是 `MkdirTemp` 的 0700，也照样保留）。遇到普通文件与目录之外的类型直接报错。复制用 `os.WriteFile`，不 fsync，这正是省下的时间。没有复用生产的 `copyProject`（`generate.go:388`），因为它要跳过 `bin` / `log` 等目录、统一写成 0644，而且逐个 fsync。
- `projectFixtureOptionsFor` 深拷贝切片，避免并发的 `NewProject` 共用同一个 `Mods` 切片。

换成副本的调用点：

| 调用点 | 形状 |
|---|---|
| `newGameDemo`（`shutdown_budget_promises_test.go`，约 20 个用例经它取工程），`shutdown_budget_test.go` 三处直接调用（`TestGeneratedShutdownTimeoutFollowsEachServicesMods`、`TestSyncNeverLowersTheGracePeriodBelowTheConfiguredTotal`、`TestDoctorChecksEachServicesShutdownWindow`） | `game-demo` |
| `newSecretTestProject`（`k8s_secret_crlf_promises_test.go`），`TestAddedConfigSectionsReachTheKubernetesSecretExample`，`TestAddModAppendsItsConfigSectionToExistingServiceConfigs` | `saga` |
| `roost_test.go` 8 处、`shutdown_budget_promises_test.go` 5 处、`shutdown_budget_test.go` 1 处、`next_optional_promises_test.go` 2 处，都是只取 root 的 `Mods: configdata` | `configdata` |
| `roost_test.go` 7 处只取 root 的无 Mod 工程 | `bare` |

保持直接调用 `NewProject` 的有三类：用到 `result`（`Created` 等）的用例；专门验证模板生成本身的 `TestDemoTemplateGeneratesABuildableWritePath` 和 `TestDemoTemplateFollowsTheGameServiceName`；参数不在登记表里的用例。因此 `NewProject` 的暂存、改名提交和 Windows 改名重试（`renameProjectStage`）仍被多个用例直接覆盖。

**为什么不改变测试语义**：

- 新增 `TestProjectFixtureCopiesMatchAFreshNewProject`。它对登记表里的每种形状都新鲜跑一次 `NewProject`，再与副本比较，要求路径集合、文件内容、类型和权限位全部相同。换言之，“副本 = NewProject 的结果”是一条每次都实跑的断言，不是假设。生成物一旦开始依赖目标绝对路径、时间或随机量，这条先红。登记表新增形状时，它自动纳入比较。
- 做过变异核对（未提交）：复制时跳过 `.gitignore`、在 go.mod 末尾多写一个换行，这条用例对四种形状都报 `the copy lacks .gitignore` / `go.mod differs`；把目录权限多给 `0o055`，报 `. has mode drwxr-xr-x in the copy, drwx------ when freshly generated`。
- 每个用例的副本都在自己的 `t.TempDir` 里，彼此互不影响，改文件、注入写失败都只作用在自己那份上。断言一行没改。只有 4 处原来复用 `NewProject` 返回的 `err` 变量，改成了 `err :=`。
- 生成失败时，每个取用该形状的用例都以同一个错误 `t.Fatal`，与原来各自 `NewProject` 失败时一样。
- RR-20260927-01 的两条 Windows 写失败注入用例（`TestSyncWritesNothingWhenTheShutdownRefreshCannotBeWritten`、`TestSyncRollsTheShutdownRefreshBackWithTheTemplates`）改取 `configdata` 副本，保持串行，没有 `-short` 或 skip。`blockWritesIn` 在 Windows 上持有的是副本里 `configs/service` 等目录的文件句柄，与原来持有 `NewProject` 写出的文件没有区别。

### 2. 慢用例 `t.Parallel`

给 47 个修前或修后耗时 0.5s 以上的顶层用例加了 `t.Parallel()`，清单见下。入选条件：

- 只读写自己 `t.TempDir` 里的工程，路径全是绝对路径；
- 不用 `t.Setenv` / chdir，不碰包级钩子（`syncProjectBeforeCommit`、`buildVersion`），不改 `os.Stdout` / `os.Stderr`；
- 子进程（doctor 的 `go mod verify` / `go list`、shell 演练的 `sh`）都显式设了 `Dir` 或环境变量。

`Generate` 内部的 `os.Chdir`（`generate.go:318-330`）由 `generatorWorkingDirectory` 串行化。这把锁本来就是为库调用方并发而设的，其余生产路径拿到的都是绝对 root。顶层并行用例要等全部串行用例结束后才一起开跑，所以留在串行的用例与并行用例从不重叠。留在串行的有：用钩子的 `TestSyncRefusesAConfigEditedWhileItRuns`，改 `buildVersion` 的 `framework_release_test.go`，读相对路径 `.` 的 `literal_coupling_test.go`，RR-20260927-01 的两条（保守起见，不让 Windows 句柄注入与别的用例同时跑）。`-race -count=3` 整包通过，是这一点的实跑证据。

并行的用例：`TestProjectFixtureCopiesMatchAFreshNewProject`、`TestCRLFKubernetesSecretExampleGetsTheSameEditsAsLF`、`TestUnrecognizedKubernetesSecretExampleIsAVisibleWarningForEveryCommand`、`TestGameDemoProductionConfigsPassTheGameInitChecks`、`TestDemoTemplateFollowsTheGameServiceName`、`TestDemoTemplateGeneratesABuildableWritePath`、`TestShellReleaseSwitchStopsTheRunningProcessUnderItsOwnUnit`、`TestShellReleaseSwitchRestoresCurrentAndUnitWhenTheUnitCannotBeInstalled`、`TestShellRollbackRejectsDotVersions`、`TestShellRollbackRunsThePreviousReleaseUnderItsOwnUnit`、`TestDoctorJudgesANonPositiveTotalAsTheAppsFallback`、`TestDoctorAdviceFollowsTheConfiguredDataEngineBudget`、`TestDoctorReportsTheAppsFallbackWhenItCannotCoverTheMods`、`TestDoctorNamesTheFileAndKeyOfAnExampleItCannotParse`、`TestSyncNeverLowersTheGracePeriodBelowTheConfiguredTotal`、`TestDoctorChecksEachServicesShutdownWindow`、`TestSyncMovesAnUneditedShutdownBlockWithTheServicesMods`、`TestSyncMovesAnUneditedBlockWrittenBeforeThePlayerTCPBudget`、`TestOneSyncConvergesAfterAServiceLosesAMod`、`TestOneSyncConvergesAfterAServiceGainsAMod`、`TestDoctorWarnsForEachRepositoryConfigThatCannotCoverTheModFloors`、`TestAddedConfigSectionsReachTheKubernetesSecretExample`、`TestAddPlayerTCPTransportIsExplicitAndProductionGuarded`、`TestAddRPCScaffoldsOwnerAndWiresCaller`、`TestAddModAppendsItsConfigSectionToExistingServiceConfigs`、`TestAddRefusesEachInvalidKindParameter`、`TestAddEntityScaffoldsTheOtherCategoryInsteadOfMintingOne`、`TestConfigEnablePlayerTCPRefusesSkeletonThenPreservesConfig`、`TestDoctorFirstBusinessReportsActionableMissingSteps`、`TestDoctorFailsWhenGeneratedProjectDoesNotCompile`、`TestDoctorReportsUnimplementedCollaborators`、`TestGenerateCheckToleratesCRLFCheckouts`、`TestExplicitFirstBusinessWorkflowGeneratesAccessLifecycleAndEndpoint`、`TestProjectNextRejectsEmptyDAOAndComponentSkeleton`、`TestProjectNextReturnsOnlyTheCurrentSafeAction`、`TestBeginnerEntityComponentAndDAOFlowWiresAggregate`、`TestSyncUpgradesLegacyGeneratedMakef
