# NC-150 修复：wire 层字段名逐字匹配

[问题](../bug/RR-20261005-NC-150.md) · [本轮](../review/REVIEW-2026-10-05-n09-batch3.md)。已修复、声明场景验证，未发版。

## 根因与决策

`decodeStrictSingle`（`skill/parse.go`）依赖 `DisallowUnknownFields`，而 `encoding/json` 按大小写不敏感匹配字段；重复键扫描（`parse_duplicate.go`）按字节比较。两套比较规则之间的缝让 `"ID"`、`"Cooldown_Ticks"` 被接受，大小写变体的重复键后者生效。

修法：`decodeStrictSingle` 解码成功后调用新的 `requireExactFieldNames`，按目标类型（reflect）逐层核对对象键必须是字段的规范 JSON 名；以名字为键的 map（memory、persistent_state、attribute_overrides、parameter_bindings）只递归其值、不约束键；自带 `UnmarshalJSON` 的类型（`json.RawMessage`、`SkillPresentation`、`VisualRef`、`RuntimeValue`）跳过，因为它们内部再走 `decodeStrictSingle`。所有 wire 对象都经这一个入口，所以 header 预读用 `json.Unmarshal` 的地方（`wire_flow.go` 等）也被最终的严格解码兜住。

未采用：
- 在重复键扫描里按大小写折叠比较：能挡住重复，挡不住单独出现的 `"Cooldown_Ticks"`；还会误伤 map 里合法的大小写不同的名字（宿主的属性名目录不限制大小写）。
- 改用 `encoding/json/v2`（大小写敏感、默认拒绝重复名）：Go 1.27 里仍需 `GOEXPERIMENT=jsonv2`。

顺带修正两处依赖大小写不敏感匹配的解码目标：`wire_select.go` 的 `status_id` 与 `status_stack_compare` / `status_duration_compare` 过滤器用的是无 tag 的 `struct{ Type, Status string }` / `struct{ Type, Op string … }`，规范的小写键此前只是“碰巧”匹配上；补上 `json` tag 后行为不变。用 AST 扫描确认 wire / value / parse / runtime_value_json 里没有别的无 tag 解码目标。

## 文件与行为

- `skill/parse.go`：`decodeStrictSingle` 末尾调用 `requireExactFieldNames`。
- `skill/parse_duplicate.go`：`requireExactFieldNames` / `structFieldNames`（按类型缓存）。
- `skill/wire_select.go`：两个过滤器解码结构体补 tag。

行为收紧：非规范大小写的键（顶层、嵌套、表达式、presentation、ParseGenerated 的 rejection）现在以 `json: unknown field "X" (field names are case-sensitive)` 失败。规范 JSON 不受影响；`RuntimeValue` 的 JSON（checkpoint / skillsync 记录）由 Go `Marshal` 产生，字段名本来就逐字一致。每个对象多一次 map 解码，只发生在 Parse / checkpoint 恢复。

## 未验证
