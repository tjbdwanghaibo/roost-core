# RR-20260917-03：内存匹配 Store 泄露可变切片，返回值可改写存储

**仓库 / 位置**：roost-core `service/match/queue_store.go`（Enqueue / Cancel / Ticket / Candidates / Commit / Match 的输入与返回）、`types.go`。
**修复单元**：U-0223（C2）。**定位文档**：TROUBLESHOOTING T-117。

## 问题

内存 versionstore 按值存取，`Ticket.Subject.Payload`、`Match.Members`、`Match.TicketIDs` 是浅复制：改 Enqueue 的输入 Payload、
任何返回值里的切片，再读存储就是改过的值（七个场景全部失败）。与序列化后端（Redis）行为不一致；并发改写还是数据竞争。

## 根因

C2：类型化 Store 对外承诺"返回的是对象"，却把内部引用交了出去；泛型 versionstore 无法替 T 决定所有权。

## 方案选择

- 改通用 versionstore 深复制：它不知道 T 的形状，全框架加隐性成本。不采用。
- **采用**：在 match 自己的边界深复制——`Subject.clone`（Payload）、`Ticket.clone`、`Match.clone`（Members 逐个 + TicketIDs）；
  Enqueue 存入 `subject.clone()`，三处 `return result` 改 `result.clone()`，Ticket / Candidates / Match 返回值 clone，Commit 的 members 用 clone。
  `queueState.clone` 保持浅拷 Ticket / Match（内部版本之间不改切片内容，只改结构体字段）。

## 改动

- `types.go`：三个 `clone`；`queue_store.go`：六个边界。
- 测试：`result_ownership_promises_test.go`（六个子用例覆盖输入 Payload、Enqueue / Ticket / Candidates 返回、Commit / Match 返回的 Members 与 TicketIDs）。

## 证明

- 修前：`Commit's returned match aliases the store: {… Members:[{Kind:player ID:999 … Payload:[88 108 100]} …] TicketIDs:[forged …]}`（其余五个子用例同类）。
- 修后：`service/match` `-race` 绿。

## 未做 / 边界

- Redis 后端每次解码新值，本就隔离；P3 按内存实现用途处理。未发版。
