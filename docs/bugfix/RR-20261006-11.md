## 1. RR-20261006-11：表满时的撤销水位

### 根因

`remoteentity/interest.go` `release`（基线 `:229`）：`generation == 0 || (!exists && r.total >= r.maxSubs)` 时只 `removeLocked`。被撤销的条目不存在、表又满时没有地方放水位，于是不留。

### 改动

- `release`：代际 0（旧发布者）照旧只撤销。条目不存在且表满时先 `pruneExpiredLocked`（可能腾出位置，就照常写水位）；仍满则 `fenceOverflowLocked`：在 `overflow[consumerSID]` 记一个 `interestOverflowFence`——代际上限（取最大）、256 位 key 指纹位图（`remoteInterestReplicaKey` 取模）、到期时刻（最后一次 release + `ReleaseFence`，与撤销水位同一个上界：撤销之前发出的续租此时都已过期）。
- `renewIfNeeded`：建新租约之前（原水位判定之后、配额判定之前）查 `overflowFencedLocked`：未到期、续租代际不新于上限、key 落在位图里 → 忽略（`false, nil`，与撤销水位相同，不报错、不触发重投）。
- `pruneExpiredLocked` 顺带清到期的溢出水位；读时遇到到期的也就地删除。

内存：每个 consumer sid 至多一个 48 字节的条目，与 `perConsumer` 同一个量级，不占 `snapshot_interest_subs`。

### 取舍与未采用的方案

- **位图碰撞的代价**：同一窗口（一个兴趣 TTL）里，这个 consumer 另一个 key 的迟到旧续租若指纹碰撞也会被忽略。后果与续租被拒相同：这个 key 暂无推送、读取按陈旧上限回源；consumer 下一次续租（剩余不足一半时，代际一定更新）照常建立。撤销之后发出的续租代际都更新，不受影响。只在表满时出现。
- 未采用“水位不计入总上限”：撤销水位只由 release 产生，数量由 release 速率 × TTL 决定，没有配置上界，等于放开内存上限。
- 未采用“每个 consumer 只记代际上限”：代际是 consumer 全局递增的，会挡住同一窗口里该 consumer 所有 key 的迟到旧续租，误伤面比位图大。
- 未采用“表满时挤掉别的条目给水位腾位置”：挤掉的是别的租约或水位，只是把丢失挪了地方。

### 兼容

wire、配置、指标都不变。行为收紧只发生在表满时：之前会复活的旧续租现在被忽略。表不满时行为与之前相同。

## 2. 同批疑点闭环（不是 RR）

### 2.1 “L1 写入只经 `admitLocked`”字面上不成立 → 结构守卫 + 注释 / 文档更正

逐个核对 `entity/remote_snapshot.go` 里不经 `admitLocked` 的写入点（全部在 key 的 `publishMu` 下，且都经 `setL1Locked` / `l1.Delete`，即 L1 自己的 `Stale` / `Conflict` 准入）：

| 函数 | 写入 | 为什么不经 admitLocked，为什么没有绕过准入 |
| --- | --- | --- |
| `refresh`（`setL1Locked` ×4） | 记下刚从 L2 读到的值；同值改记确认时刻；L2 没有活值时给删除标记改记确认时刻 | 值就是 L2 当前持有的，再 CAS 回 L2 没有意义；锁内与 L1 当前值重新比较（`remoteSnapshotEntryStale`，与 L1 准入同一函数），L1 比 L2 新时走 `admitLocked` 修复分支 |
| `adoptSharedLocked`（`setL1Locked`、`l1.Delete`） | L2 以 stale 拒绝之后记下 L2 的值；L2 已没有活值时删掉不比被拒写入新的 L1 快照 | 本身就是 `admitLocked` 的 stale 分支；不记删除标记的理由见函数注释（不知道墓碑确切版本） |
| `loadForRefresh`（`l1.Delete`） | 权威说不存在：删掉加载开始之前确认的 L1 快照 | 只删不写；L2 本就没有活值（否则不会回源） |
| `Delete`（`l2.Delete`、`l1.Delete`） | 不带版本的失效（旧发布者，复制消息 `DeleteVersion == 0`） | 语义就是“无条件删、不留水位”（函数注释写明）；带版本的删除走 `DeleteAtVersion` → `admitLocked` |

没有发现绕过墓碑或水位校验的路径，所以不是缺陷，没有登记 RR。为挡住以后新增的绕行，加结构守卫 `TestRemoteSnapshotCacheWritesStayInTheListedFunctions`（`entity/remote_snapshot_write_guard_test.go`），按源码 AST 检查：

1. 直接写 L1（`setL1Locked`、`l1` 上除 `Get` / `Stats` 以外的方法）与直接写 L2（`l2` 上除 `Get` 以外的方法）只出现在封闭表 `remoteSnapshotDirectWriters` 列出的函数里，每处带理由；表里的函数不再写入时也报错（表随源码收缩）。
2. 需要分片锁的 helper（`*Locked` 方法与 `writeShared`）只被 `*Locked` 方法或自己取 `publishMu` 的函数调用；直接写的函数同样要么是 `*Locked`，要么自己取锁。

负对照（临时改源码，未提交）：在 `ApplyUpdate` 里加一句 `c.setL1Locked(...)`、去掉 `loadForRefresh` 的取锁，守卫报：

```

remote_snapshot.go:1035: ApplyUpdate writes the snapshot cache directly; route it through admitLocked or list it with a reason
remote_snapshot.go:818: loadForRefresh writes l1.Delete without the publish shard lock
```

注释更正：`RemoteSnapshotCache` 类型注释（新值经 `admitLocked`，其余直接写点只回填 L2 的值或删除，清单由守卫检查）、`admitLocked` / `loadAuthoritative` / `ApplyReplica` 注释、`remoteentity/snapshot_client.go` 类型注释与 `publishCommitted` 注释、`remoteentity/syncer.go` `SnapshotReplicaStore` 注释。文档更正：[B2 §2](../feature/B2-REMOTE-SNAPSHOT-L2-WATERMARK-2026-10-06.md#2-目标不变量) 第 1 条（并更正第 2 条“L2 已无值时记删除标记”——源码只删不记）、DECISIONS-PENDING 第九轮 Mirror 第 4 步行。
