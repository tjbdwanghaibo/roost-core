# RR-20260911-02:Mailbox.clone 未复制新增的 SettledClaims map

**仓库 / 位置**:roost-kit `service/mail/mailbox.go`,`clone`。
**修复单元**:U-0170(C2)。**定位文档**:TROUBLESHOOTING T-64。
**引入来源**:U-0165 加字段时遗漏,不是历史缺陷。

## 问题

`clone` 的第一行是 `out := m`。结构体赋值复制的是 map 的**头**,不是内容:Entries 后面被显式
深拷贝了,U-0165 新增的 `SettledClaims` 没有,于是它继续和存储里的那张 map 共享底层数据。

`Service.Mailbox` 返回的是 clone 的结果。调用方在这个"快照"上
`delete(snapshot.SettledClaims, mailID)`,存储里的领取记录就没了 —— 绕过 `Store.Update` 改到了
权威状态,而且下一次投递会把那封已领取的邮件当成首次投递。

## 根因

`clone` 的形状是"赋值 + 逐个深拷贝可变集合",加字段时必须同时加一段拷贝,而这件事没有任何
机制提醒。这是加字段时的经典遗漏。

## 方案选择

- 让 `Mailbox` 不含可变集合(比如改成切片 + 二分)。不成比例。
- **补上拷贝(采用)**,并在注释里点明 `out := m` 复制的是 map 头而不是内容 —— 下一个加字段的人
  读到的是原因,不是一句"记得拷贝"。

## 改动

`service/mail/mailbox.go`:`clone` 增加 `SettledClaims` 的逐项拷贝。

## 证明

`service/mail/settled_claim_retention_promises_test.go`,
`TestMailboxSnapshotDoesNotShareTheSettledClaims`:正常领取并淘汰出一条墓碑,取
`Service.Mailbox` 的返回值删掉它,再取一次断言存储里还在;并且断言这条记录仍然起作用 ——
重投后 `ReserveClaim` 仍然 `ErrAlreadyClaimed`。

修前红:

```text
mutating the returned mailbox deleted the stored settled claim
```

修后 mail 含 `-race` 全绿。

## 未做 / 边界

- 审查把它定为 P3,因为确认场景是进程内 MemoryStore;Redis 存储每次解码出新对象,不共享。
  没有声称远程玩家可以直接篡改。
- 没有为"所有可变集合都必须在 clone 里拷贝"加静态检查。`Mailbox` 目前只有这两张 map。
