# RR-20260911-04:Nest 停机遗漏延迟同步请求的回复

**仓库 / 位置**:roost-core `nest/dispatcher.go`,`OnDestroyWithContext` 回收延迟队列处。
**修复单元**:U-0172(C5)。**定位文档**:TROUBLESHOOTING T-66。

## 问题

一个已注册 handler 的同步 `Request` 带 `SendOptionWithDelay` 进了延迟队列、还没到期,这时
`Shutdown`。`OnDestroyWithContext` 取走队列后直接 `recycleMsg`,**没有向 `RetChan` 发任何东西**。
Shutdown 返回成功,而调用方还在 `waitResult` 里等自己的 context 或同步超时。

不是永久等待 —— `waitResult` 有超时分支 —— 但一个已经被接受的请求既没有执行结果,也没有明确的
停止错误,错误语义退化成"取消 / 超时",而真正的原因是服务停了。

## 根因

同一件事的两条路径判据不同(C5 的静默吞错,也是 C8 的味道):入场时被拒的路径一直是给答案的
(`ErrNestStopped`),而"已经进了队列、还没到期"这条路径只回收消息、不回答。

## 方案选择

- **让调用方靠超时自己发现。** 就是现状。停机是已知事件,把它报成超时是把可诊断的原因丢掉。
- **在回收前统一回复(采用)**,答案沿用入场路径的 `ErrNestStopped`,语义一致。

关键是**最多回复一次**。这里成立:延迟队列是在 `m.mu` 下整体取走并置空的,而延迟泵从
`m.delayedHeap` 弹出时也在同一把锁下 `delete(m.delayed, dm)`。所以一条消息要么在这份快照里、
要么已被弹出去分派,不可能两边都有。泵在这段代码之前就已经停下并等到 `done`。

## 改动

`nest/dispatcher.go`:回收循环里,`RetChan` 非空就发 `ErrNestStopped` 并把字段置 nil
(`GenSyncMsg` 的通道容量是 1,正好放得下这一个值,发送不会阻塞;置 nil 让"最多一次"显式);
没有等待者的异步消息沿用 `logAsyncDispatchFailure`,与入场路径一致。

## 证明

`nest/delayed_shutdown_promises_test.go` 两条,直接用 `NewDispatcher` + `delaySendMsg`:

- `TestShutdownAnswersDelayedRequestsInsteadOfDroppingThem`:一条延迟一小时的同步消息,
  `OnDestroyWithContext` 之后必须在一秒内从 `RetChan` 收到 `ErrNestStopped`;dispatch 回调里
  放了一个 `t.Error`,所以"其实被分派了"也会被抓住。
- `TestShutdownDropsDelayedFireAndForgetQuietly`:没有等待者的延迟消息不能让停机阻塞或 panic,
  停机后延迟计数归零。

修前红:

```text
the accepted request got no answer at all; the caller is left to its own timeout
```

修后 `go test ./nest -race` 绿,core 全仓绿。
