# RR-20260920-02：普通 delta 不能走会被覆盖的通道（U-0260，C8）

## 问题

链路是闭合的：

```text
RoomBroadcaster.flushStateBatch
  → SubscriptionCoordinator.DistributeBatch
  → RoomEnvelopeSink.AdmitEnvelopes
  → RoomTransportSink.AdmitRoomFrames
  → AsyncTransport.AdmitBatch
```

`RoomTransportSink` 把 snapshot / leave 放可靠通道、把普通 delta 分片成 datagram；
`AsyncTransport.AdmitBatch` 对同一个 stream 执行 `queue.latest[stream] = item.datagrams`，
已有待发帧时直接替换并计 `DatagramFramesDropped`。

问题出在跨层契约上：**frame 2 与 frame 3 都是相对实体 dirty mask 的增量，frame 3 不是 frame 2 的超集。**
frame 2 入队成功之后，`DistributeBatch` 已经提交了这一批、清掉了 dirty、推进了订阅的 content version；
传输层随后把 frame 2 换掉，不会把它的 `pos_x` 合并进 frame 3，也没有 ACK、缺口补发或周期全量。
玩家停止变化之后，那个字段对那个客户端**永久**缺失。

## 根因

C8：同一个状态在两层用了不同判据。房间层认为"交给传输层 = 送到了"，于是提交并清 dirty；
传输层认为"同 stream 只有最新的那帧值得送"，而这个前提只有在帧是**自包含的最新状态**时才成立。
两个判据各自都自洽，合起来丢数据。

## 方案选择

- **采用**：普通 room delta 改走**可靠通道**。队列上限与 slow-consumer 驱逐把背压明确表达出来
  （`ErrReliableBackpressure` → 房间保留 dirty 重试，或按策略驱逐），而不是安静地少发一个字段。
- **采用**：保留 datagram 路径，但收进一个显式开关 `RoomTransportSinkConfig.LatestOnlyDeltas`（默认关）。
  打开它是一个声明：这些帧是自包含的最新状态，或者被下一帧替换不会丢任何东西。删掉整条路径会
  丢掉一套已测试的能力，而那正是将来"自包含帧"模式要用的。
- 放弃 **在传输层合并被覆盖的帧**：传输层看到的是编码后的字节，不知道哪些字段可合并；
  要合并就得把 delta 语义带进传输层。
- 放弃 **靠 ACK / 缺口补发**：`RoomFrame.SessionSequence` 的注释确实说它是为丢失检测准备的，
  但两端都还没有实现，那是另一条更大的路，不该用来给这次的数据丢失兜底。

## 改动

`room/room_transport_sink.go`：lane 选择从 `if reliable` 改成 `if reliable || !s.config.LatestOnlyDeltas`；
新增配置项与说明；类型注释重写。

## 证明

`room/delta_durability_promises_test.go`：

- `TestOrdinaryDeltasGoOnALaneThatDoesNotDropThem`：结构断言（delta 不在 latest-only 通道上）；
- `TestTwoConsecutiveDeltasBothReachTheClient`：**行为断言**——快照 + 两帧 delta 过真正的
  `AsyncTransport`，三份内容都必须到达下游。修前红，且红的正是生产现象：

  ```text
  "pos_x" never reached the client; a committed change was dropped in transport:
  1 reliable, 1 datagram payload(s) reached the client
  ```

- `TestLatestOnlyDeltasRemainsAvailableAsAnExplicitChoice`：开关打开时 datagram 路径仍然可用。

`TestRoomTransportSinkRoutesLifecycleAndState` 编码的是被推翻的旧契约（"delta 必须在 datagram 通道"），
按规矩改成断言新不变量而不是删掉，内容断言原样保留。

实跑（16 客户端）：修前客户端 `deltas>0` 且自己的 `pos_x` / `equipment` 永久缺失；
修后 `deltas=0`（全部走可靠通道），`pos_x` 出现在收到的字段里。

## 未做 / 边界

- **16 客户端场景仍有红，但换了形状**，这不是本条的残余：修后 3/16 失败的客户端
  `own_updates=6~7`（自己的订阅在正常投递）、`other_updates≈100`，可是收到的字段里始终没有
  `pos_x` / `pos_y` / `scene_id`——即**位置那一组改动没有送到这个订阅者，而同一批帧送到了别人**。
  40 秒后仍然缺失。这是一条与本条不同的缺陷，证据与复现记进 `docs/bug/WANTED.md` 的 W-2026-09-20-02。
- 丢失检测 / 缺口补发（`SessionSequence` 的本意）没有做。
- 默认部署的 delta 从 datagram 变成 reliable 是**行为变化**：慢消费者从"静默丢帧"变成明确的背压
  或驱逐。客户端两条通道本来就都要处理，不需要改。
