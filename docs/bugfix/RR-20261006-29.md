# RR-20261006-29 修复：通关遇到还没开的窗口时自己开窗再记

问题：[RR-20261006-29](../bug/RR-20261006-29.md)。基线 main `0db819b0`，未发版。来源：[真实进程演练](REAL-PROCESS-DRILLS-2026-10-06.md)第 ⑥ 项。

## 根因

`ActivityRunner.Contribute`（`demo/internal/service/game/activity.go.tmpl`）按时钟算窗口 id 后直接 `ApplyProgress`，假定窗口已经由 `runActivity` 开好；而循环每 5s 才开一次，边界之后最长 5s 的窗口在协调方不存在。

## 改动

`Contribute` 收到 `CodeMissing` 且 Activity 开关开着时，调与循环同一个 `openWindow`（按 App 锁的 `Live` 算 expected、`OpenActivity`，已开答 `CodeExists` 视为成功），成功后再 `ApplyProgress` 一次；开窗失败时返回原错误并附上开窗的原因。关窗截止时间（World 上的 `ArmActivity`）仍由循环下一轮装上：它对已开的窗口得到 `CodeExists`，照常 arm。开关关着时不开窗，与循环一致（开关挡的是“开新窗口”这个入口）。

两个服务的 game 同时在缺口里通关时都会开同一个窗口：`OpenActivity` 对同一 Key 幂等，第二个得到 `CodeExists`；expected 由各自的 `Live` 查询给出，与循环开窗时相同。

未采用：
- 缩短 `activityLoopInterval`——缺口变小但仍在，并把每个 game 对协调方的请求放大。
- 机器人在缺口里容忍空 `ActivityID`——掩盖了真实玩家的贡献丢失。
- 在 `Contribute` 里调 `openCurrentWindow`（含 `ArmActivity`）——那是对 World 的 Nest 同步调用，从玩家 handler 里发起是嵌套派发；开窗只需要协调方这一半。

## 兼容

- 生成形状：`internal/service/game/activity.go` 与测试变化；已有工程重新生成或手工合并。协调方接口与持久格式不变。
- 行为：缺口里的通关现在计入当前窗口、响应带窗口 id；开窗失败（例如 `Live` 查询失败）时与以前一样只丢这一点并记 Warn。
