# RR-20261005-NC-208 修复：redis/driver 与 kit/nats 的 toxic 用例改用自建代理，不再 /reset

日期 2026-10-05。基线 `8597046c`（审查提交 `345488e4`）。状态：已修复、声明场景验证，未发版。（部分：`kit/dataengine` 未改，见下）问题：[RR-20261005-NC-208](../bug/RR-20261005-NC-208.md)。

## 决策

沿用 versionstore（NC-100）/ mongo/driver（NC-101）已有做法：

- `redis/driver/lock_toxic_integration_test.go`：`toxicRedis` 在环境的 toxiproxy 上自建唯一命名、随机端口的代理（上游 `ROOST_DATAENGINE_IT_REDIS_ADDR`），清理时删除；`addToxic` 只加在自己的代理上；原来的 `/reset` 改为 `heal`（列出并删除自己代理上的毒）。准入从 `REDIS_PROXIED_ADDR` 改为 `TOXIPROXY_URL` + `REDIS_ADDR`，`ROOST_IT_TOXIPROXY=1` 时缺失仍判失败。
- `kit/nats/jetstream_rpc_toxic_integration_test.go`：按 `ROOST_DATAENGINE_IT_NATS_URL` 的每个直连节点各建一个自有代理，bus 用这些代理地址（已设 `ignore_discovered_servers`，不会绕过代理）；半开毒与恢复只作用于自己的代理。
- 用例断言不变。

**未修部分**：`kit/dataengine/toxic_integration_test.go`（三条 `TestToxicNATS*`）同根因，但 kit/dataengine 属 DataEngine 核心边界，本线不改。建议核心线按 kit/nats 的 `newRPCToxiproxy` 改写其 `toxiproxyEnv` / `reset` / `addToxic`（DataEngine fixture 也需要 `ignore_discovered_servers` 或等价设置）。在它改完之前，这三条仍会 `/reset` 共享 toxiproxy，跑时须独占环境。

## 验证

全部在本 agent 自起的 toxiproxy（39474）/ redis（39379）/ nats（39222，JetStream）上，`-run` 精确到用例，结束后关闭进程：

- 红：bystander 代理上的别人的毒在两个用例之后被清空（[脚本](../review/evidence/noncore-review-20261005-n15/toxreset_red.sh) · [输出](../review/evidence/noncore-review-20261005-n15/nc208-red.txt)）。
- 绿：bystander 毒保留，两个包 ok（[输出](evidence/noncore-bugfix-20261005-n15/nc208-green.txt)）。
- `go test -race -tags=integration -count=3`：redis/driver 三条 toxic 用例与 kit/nats 一条各 3 次通过，结束后 toxiproxy 上没有残留代理（[输出](evidence/noncore-bugfix-20261005-n15/nc208-race3.txt)）。
- 两包普通 `go test -race -count=3`、`go vet -tags integration` 通过。

## 补修（kit/dataengine）

日期 2026-10-05。基线 `6c1538be`。状态：已修复、声明场景验证，未发版。上面“未修部分”至此补齐，三条 `TestToxicNATS*` 不再需要独占环境。

**决策**（照 kit/nats 的 `newRPCToxiproxy`）：

- `kit/dataengine/toxic_integration_test.go`：`toxiproxyEnv` 改为按 `ROOST_DATAENGINE_IT_NATS_URL` 的每个直连节点，在 `ROOST_DATAENGINE_IT_TOXIPROXY_URL` 上自建一个唯一命名（`kit-dataengine-toxic-<pid>-<纳秒>-<序号>`）、`listen: 127.0.0.1:0` 的代理，返回经这些代理的 nats:// 列表；`t.Cleanup` 删除代理（毒随代理一起删）。`reset`（`POST /reset`）删掉，用例中途的恢复改为 `heal`（列出并删除自己代理上的毒）；`addToxic` 只加在自己的代理上，不再写死 `nats-1..3`。准入从 `NATS_PROXIED_URL` 改为 `TOXIPROXY_URL` + `NATS_URL`，`ROOST_IT_TOXIPROXY=1` 时缺失仍判失败。
- `kit/dataengine/real_fixture_integration_test.go`：`ignore_discovered_servers` 原来只在 `natsURL == ROOST_DATAENGINE_IT_NATS_PROXIED_URL` 时打开，自建代理的地址不等于它，客户端会从 INFO gossip 学到真实节点端口、绕过故障注入。改为 `natsURL != ROOST_DATAENGINE_IT_NATS_URL`（凡不是直连地址都是代理）。
- 三条用例的断言不变。

**验证**：

- 红 / 绿都在本 agent 自起的 toxiproxy（`127.0.0.1:60951`，用完关闭）上，Mongo / NATS 用共享隔离环境的直连地址（各 fixture 用唯一库名与流名；跑前确认 `remote-acceptance.lock` 不存在）。脚本在该 toxiproxy 上按旧名建好 `nats-1..3`（供修前用例使用），另建别人的代理 `bystander-nc208b` 与毒 `someone-elses-latency`，三条用例逐条 `-run` 精确运行（[脚本](evidence/noncore-bugfix-20261005-n15/toxreset_dataengine.sh)）。
- 修前红（[输出](evidence/noncore-bugfix-20261005-n15/nc208b-red.txt)）：

  ```
  before: bystander toxics=["someone-elses-latency"] proxies=["bystander-nc208b","nats-1","nats-2","nats-3"]
  ok  	github.com/tjbdwanghaibo/roost-core/kit/dataengine	5.839s
  after TestToxicNATSLatencyKeepsTheCommitOnTheDurablePath: bystander toxics=[] …
  after TestToxicNATSConnectionResetDeliversTheEffectExactlyOnce: bystander toxics=[] …
  after TestToxicNATSHalfOpenAckLossIsBoundedAndDeliversExactlyOnce: bystander toxics=[] …
  ```

  每条之后补回的 bystander 毒都被清空；toxiproxy 日志记到 9 次 `POST /reset`（每条 3 次：开头、中途恢复、清理）。
- 修后绿（[输出](evidence/noncore-bugfix-20261005-n15/nc208b-green.txt)）：三条各自 ok，每条之后 `bystander toxics=["someone-elses-latency"]`，代理列表只剩脚本自己建的四个（用例的自建代理已删）；toxiproxy 日志无新的 `/reset`，自建代理上的 `POST …/toxics`、`DELETE …/toxics/{slow,reset,halfopen}`、`DELETE /proxies/<own>` 各 9 / 3+3+3 / 9 次。半开用例仍要求 `PublishFailures >= 1`，证明毒确实作用到了自建代理上。两份输出末行的 jq 报错是脚本删掉 bystander 代理后再查询得到 404 文本，不影响结论。
- 共享隔离环境上 `go test -race -tags=integration -count=3 -run '^TestToxicNATS(…三条…)$' ./kit/dataengine`：9 次全部 PASS，结束后共享 toxiproxy 只剩环境自己的 `nats-1..3`、`redis`，毒数均为 0，没有残留代理（[输出](evidence/noncore-bugfix-20261005-n15/nc208b-race3.txt)）。
- `gofmt -l` 为空；`go vet -tags integration ./kit/dataengine/`、`go test -count=1 ./kit/dataengine/`、根包 `go test -count=1 .`、`go build ./... && go vet ./...` 通过（`GOWORK=off`）。

**其他 `/reset` 入口**：`rg -n '/reset|toxiproxy' --type go -g '*_test.go'` 之后，测试里已没有 `POST /reset`，也没有在共享代理名（`redis`、`nats-1..3`）上加毒的用例；`remoteentity`、`versionstore`、`mongo/driver` 本来就自建代理。仍会 `/reset` 的只有运维入口 `kit/scripts/integration/lib/toxiproxy.sh` 的 `toxiproxy_heal`（`dataengine-env.sh up` / `heal`，矩阵与 `scripts/perf/remote.sh` 的预检经它调用）：那是有意清空整套环境的命令，受 Remote 验收锁约束（NC-203），不属本条。
