# NC-215 修复：两个参考 Host 与 Runtime 都拒绝的取值在编译期拒绝

[问题](../bug/RR-20261005-NC-215.md) · [本轮](../review/REVIEW-2026-10-05-n09-batch4.md)。已修复、声明场景验证，未发版。

## 根因与决策

只收紧“MemoryHost 与 combatcomponent 都拒绝（或 Runtime 自己拒绝）”的取值，Host 之间口径不同的（shield 时长、relation 取值，见本轮 O24 / O25）不动：

- `compile_shape.go` 的 `rejectValuesTheRuntimeDoesNotExecute`：attribute_modifier `duration_ticks <= 0`、add_status `duration_ticks == 0`（负值仍由 NC-152 报）、resource `operation` 不在 set / add / spend / sub、cost / sustain cost 字面量为负；
- `compile_capability.go`：attribute_modifier `operation` 必须是 add / mul_bp 且在该属性 catalog 的 `ModifierOperations` 里（这张表此前没有读取方）；attribute_compare `op` 必须是比较运算（status 比较 filter 已用同一个 `validCompareOperation`）。

都报 `SHAPE_INVALID` 到字段。cost 只查字面量；表达式的符号由运行期 `payCostList` 拒绝（量化证明未覆盖符号，未扩大）。

## 文件与行为

`skill/compile_shape.go`、`skill/compile_capability.go`。这些定义从“编译通过、每次施法失败（或 filter 静默落空）”变为启动期编译失败。NC-152 的控制 `TestCompileAcceptsZeroTicks` 里 add_status 原来用时长 0 当“非负”样例，改为 1（wait 0、repeat 间隔 0 的控制不变），0 的拒绝由新用例钉住。

## 回归

`TestCompileRejectsValuesEveryHostRejects` 七个子用例修前全部 `compiled; diagnostics=[]skill.Diagnostic(nil)`，修后 ok；控制同 NC-214。

## 兼容性

行为收紧，见上。combatcomponent 的 StatusBridge 若将来支持 0 时长（永久状态）或新的 modifier 运算，需要同时放宽这里与 MemoryHost。
