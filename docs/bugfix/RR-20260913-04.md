# RR-20260913-04:快照合并加载取消后泄漏等待名额

**仓库 / 位置**:roost-core `entity/remote_snapshot.go`,`loadMonotonic` 的跟随者分支。
**修复单元**:U-0174(C2)。**定位文档**:TROUBLESHOOTING T-68。

## 问题

跟随者 `call.waiters++` 之后,ctx 取消就直接 return,计数不减。于是 `MaxWaiters` 计的是"本次
load 期间累计进过门的次数"而不是"正在等的人数":慢权威后端叠加超时重试,健康请求会在首个 load
结束前一直收到 `ErrRemoteOverloaded`。默认上限 256 只是推迟触发。

## 根因

计数器语义混淆:把"曾经等过"当成"正在等"。名额只随整个 call 在 load 完成后一起消失。

这与 [RR-20260908-02 / U-0155](RR-20260908-02.md) 是同一个错误,但那处在 `cache.ReadThroughStore`。
entity 这一层**自己又写了一份**合并加载逻辑,所以同一个洞要各修一次 —— 两份实现就是两份债。

## 方案选择

只有一种修法:取消路径在 `loadMu` 下减回。边界与上次一样 —— 同一个 key 可能已经换代(旧 load
结束、新 load 开始),所以减之前核对 `c.loads[callKey] == call`,不能扣到新一代头上。

## 改动

`entity/remote_snapshot.go`:`case <-ctx.Done()` 分支加锁减回,注释写明"计的是正在等的人数"。

## 证明

`entity/snapshot_load_waiters_promises_test.go`:`MaxWaiters: 1`,权威 loader 用屏障挂住;
一个跟随者入场后第二个被拒(真满额仍拒绝);第一个取消离开后断言名额归零、新的跟随者能进;
放行 loader 后两边都拿到值。等待数用锁内轮询观察,不靠 sleep 抢时序。

修前红:

```text
load waiters = 1, want 0
```

修后 entity 含 `-race` 全绿。

## 未做 / 边界

- 只修了 `loadMonotonic`。`WaitForVersion` 的那套等待者计数是另一组结构(`waitMu` / `waiterCount`),
  既有测试覆盖了它的取消路径,本次没有改动。
- 没有把两处合并加载合成一份实现。那是重构,不在这个单元里。
