# RR-20260926-72 修复：卸载退役中的 RegisterAfterRetirement 返回 queued=true 并由 done 恰好报告一次

问题：[RR-20260926-72](../bug/RR-20260926-72.md)（复现 [REPRO-2026-09-26-06 §8](../bug/REPRO-2026-09-26-06.md#8-rr-72卸载退役中-registerafterretirement-返回值)）。日期 2026-09-27。
实施基线：`2373e21` + RR-69 修复 `e5c55fe`。状态：已修复，本地验证通过，已本地提交，未推送/发布。

## 根因（基线行号）

`RegisterAfterRetirement`（`sync/entitysync/manager.go:385`）先调 `Register`；subject 在表里时 `Register` 走 `rebind`，而 `rebind` 对 RR-59 的卸载退役
（`retiring && unloadRetracted`，`:310-318`）直接把 state 排为 successor 并返回 nil——排队项**不带**调用方的 done。`RegisterAfterRetirement` 看到 nil 就
返回 `queued=false err=nil`（“已登记”），而登记实际在 remove 交付之后才发生，done 永不调用。依赖 done 的调用方（demo scene 的 `registeredLater`：
让政策重说退役期间被拒的 pair）因此不触发。

## 修复（维护者 2026-09-27 批准的约束）

- `Register` 与 `RegisterAfterRetirement` 共用内部 `register(state, done) (queued, err)`；`rebind(subj, state, done) (queued, err)`。卸载退役中的分支把 done
  随排队项保存并返回 `queued=true`；`RegisterAfterRetirement` 原样返回 `(queued, err)`，于是它在卸载退役中也返回 `queued=true`，done 由 forget 的登记
  （nil）或取消（`ErrRegistrationCancelled` / `ErrManagerClosed`）恰好报告一次。
- 排队位共用、后到替换先到：业务 `RegisterAfterRetirement` 与 `Rebind` / `Register`（kit 的 `OnEntityLoaded`）谁后到谁留下；被替换的排队项在解锁后
  `finish(ErrRegistrationCancelled)`（只有带 done 的才真正回调）。`Rebind` / `Register`（done 为 nil）遇到**同一状态**已在排队时保留原排队项，不取消业务的
  done；`RegisterAfterRetirement` 带 done 时总是替换（与 RR-55 业务退役中的替换语义一致）。
- forget 登记排队项时把排队项的 done 交给 `register`：若表里已是另一个又在卸载退役中的同 ID subject（极窄窗口），登记再次排队，done 随新排队项走，
  不会提前报告 nil。
- `Rebind` / `Register` 的公开签名与返回值不变（卸载退役中仍返回 nil）。

## 文件

- `sync/entitysync/manager.go`：`Register` / `register`、`Rebind` / `rebind`、`RegisterAfterRetirement`（文档补卸载退役一段）、`forget` 的排队登记。
- 回归 `sync/entitysync/unloaded_retract_test.go`：
  - `TestRegisterAfterRetirementDuringUnloadRetractionIsQueued`（REPRO §8 S1 正式版）：卸载退役中业务登记返回 `queued=true`，remove 交付前 done 未调用、
    交付后恰好一次 nil，登记的是业务的状态，再 Flush 不重复报告。
  - `TestUnloadRetractionQueueLaterReplacesEarlier`：业务排队后 kit Rebind 到来 → 业务 done 立即收到 `ErrRegistrationCancelled`、重载状态在 remove 后登记、
    不重复报告；kit Rebind 排队后业务登记到来 → `queued=true`，remove 后 done 为 nil、登记的是业务状态。

## 兼容性

无导出 API、配置、协议变化。行为变化：卸载退役中的 `RegisterAfterRetirement` 由 `(false, nil)` 改为 `(true, nil)` 并回调 done；demo scene 的 Join 在这种
情况下会记一行 “rejoin waits …” 并在登记完成后 `apply()`——与 RR-55 业务退役中的 Join 同一路径。

## 对抗性自查

- **恰好一次**：done 只存在于一个排队项里；排队项只会被 forget 取走（登记 / 状态已关闭取消 / 再次排队转交）、被替换、被 `Unregister` 取消或被 `Close`
  取消，这些都在 `subj.mu` 下摘下 successor，解锁后 finish，各自互斥。
- **remove-before-create**：排队不改变退役：卸载退役期间订阅仍被拒绝，登记在最后一个 remove 交付的同一步发生。
- **与 RR-55 / RR-59**：业务退役（`Unregister`）仍返回 `ErrSubjectRetiring` 并走 RAR 原有排队；`Unregister` 清除 `unloadRetracted` 并取消排队项（RR-59 规则不变）。
- **锁序 / goroutine**：无新增锁与 goroutine；done 仍在解锁后执行。
