# RR-20260911-05:被拒绝的投递仍修改了 MemoryStore 里的邮箱

**仓库 / 位置**:roost-kit `service/mail/service.go`,五处 `Mailboxes.Update` 回调。
**修复单元**:U-0182(C2)。**定位文档**:TROUBLESHOOTING T-76。**优先级**:P3。
**关联**:U-0171 新增的 `ErrClaimHistoryFull` 拒绝分支让它更明显,但根因早于它。

## 问题

Update 回调拿到的 `Mailbox` 是结构体浅拷贝,`Entries` / `SettledClaims` 两张 map 仍指向存储对象。
`Deliver` 先 insert、再 evict,最后才做容量拒绝:回调返回 `save=false` 加错误,MemoryStore 不保存
新结构体,但 map 上的修改已经发生 —— `Unread` 与 `Version` 维持旧值,条目和墓碑却多了一个。
审查的观测:`inserted=true settled=200->201 version=1202->1202 unread_field=199 actual_unread=200`。

## 根因

Store / Mutate 的可变对象所有权契约没有被遵守:回调应该在私有副本上计算,只在 `save=true` 时把
副本交给存储。`match` 的每个 Update 回调第一行都是 `current = current.clone()`,`mail` 漏了。
这是 U-0170 同一族的问题(那次是读取副本共享 map),这次是写入回调共享 map。

## 方案选择

- **让 MemoryStore.Update 传 clone。** 它是泛型 `Store[K,T]`,不知道 T 里有 map;只能靠约定。
- **回调第一行 clone(采用)**,五个回调统一,和 match 一致。注释写明为什么。

## 改动

`service/mail/service.go`:五处 `Mailboxes.Update` 回调开头加 `current = current.clone()`。

## 证明

`service/mail/atomic_refusal_promises_test.go`:把墓碑推到上限直到出现 `ErrClaimHistoryFull`,
记录存储状态,再发一次必被拒的投递,断言:该邮件不在 Entries 里、Entries 与 SettledClaims 条数
不变、Version 不变、`Unread` 字段与实际未读条目数一致。

修前红:`Unread field 199 disagrees with 200 actual unread entries`。修后 mail 含 `-race` 全绿。

## 未做 / 边界

- 只在 MemoryStore 上确认;Redis 每次解码新对象,没有共享。审查按 P3 记,理由相同。
- 没有给"所有 Update 回调必须先 clone"加静态检查。
