# RR-20260930-19：Remote 标记键可选部署前缀；锁键与键清单写进使用说明

问题：[RR-20260930-19](../bug/RR-20260930-19.md)（REMAINING §3 N25，维护者 2026-09-30 拍板）。日期 2026-09-30。基线 main `4784ef82`。
状态：已修复，本地验证通过（含真 Redis），本地提交，未推送 / 未发版。

## 根因

- `remoteentity/marker.go:96` `markerRedisKey = "remote_entity:marks"`，`NewRedisMarker(redis, key)` 在 key 为空时用它；所有实体的租约都是这一把 hash 的 field，没有前缀形式。
- 正式 `Assemble`（`assemble.go:120`）的所有权存储是 Mongo 权威，不写这把键——它只属于非 authority 兼容装配（仓内只有两条 integration 测试这样装）。
- 锁键 `lock:<LockKey>:<id>`（`versioned_lock.go:53`）的 `LockKey` 已由 `remote_entity.lock_key` 配置（缺省 `e`），Cluster 下 Init 校验 hash tag（RR-20260924-25）；缺口是使用说明没写“共用 Redis 的部署要各配不同值”。

## 决策

### 采用：core 给标记键加同形前缀构造器；锁键只补文档；kit 不加配置项

- `remoteentity.NewRedisMarkerWithKeyPrefix(redis, prefix) (*redisMarker, error)`：prefix 为空时键仍是 `remote_entity:marks`（逐字不变，与 `NewRedisMarker(redis, "")` 互读）；非空时 `<prefix>:remote_entity:marks`。
  与 `NewSnapshotL2StoreWithKeyPrefix` 同形，同一个部署前缀值可同时用于 L2 与标记。`NewRedisMarker(redis, key)` 显式键名形式不变。
- `remoteentity.ValidateMarkerKeyPrefix`：空合法；拒绝首尾 / 内部空白（与 L2 前缀、`mods.KeyPrefix` 同一规则）。**hash tag 允许**——标记只有一把 hash 键，Lua 全是单键操作，
  带 tag 只是把这一把键钉在一个槽，无害（L2 逐实体多键才禁止 tag）；但写了花括号就要求首个 tag 非空且闭合（Redis 对 `e{` / `e{}` 不做 tag 哈希，配置者会以为钉住了槽而没有），
  这正是 kit 对 `remote_entity.lock_key` 的 Cluster 判断（`remote_entity_mod.go:79-84`）与 `mods.ValidateClusterKeyPrefix` 的同一条规则。core 不知道拓扑，所以不像 kit 那样在 Cluster 下*要求* tag；单键也不需要。
- 锁键：不改缺省、不加新配置。`Config.LockKey` 注释与 USER_GUIDE §6 / kit README 写明键格式、缺省不隔离、共用 Redis 要各配不同值、Cluster 下带 tag、改锁身份要整体重启。
- kit：**不加** `remote_entity.marker_key*` 配置项——Mod 的所有权存储是 Mongo 权威，`Assemble` 不构造 Redis 标记，读了也没有消费者；一个不起作用的配置项正是最容易让运维配错的形状。
  kit README remoteentity 一节加“Redis 键与部署隔离”一行，列出 Mod 实际写的两类键及各自的配置项，并说明 marks 为什么没有配置项。

### 未采用

| 方案 | 为什么不用 |
| --- | --- |
| kit `remote_entity.marker_key`（显式键名）或 `remote_entity.marker_key_prefix` → `Config.MarkerKey*` | kit 装配不构造 Redis 标记（所有权存储是 Mongo 权威），配置项没有消费者；`Config` 字段仓内也没有读者。会让运维以为设了就隔离 |
| 一个统一的 `remote_entity.key_prefix` 同时作用于 marks 与 `lock_key` 缺省值 | 与已有的 `snapshot_l2_key_prefix` 形成两个前缀（L2 禁 tag、锁在 Cluster 下必须有 tag，一个值不能同时满足）；还改变锁键的拼装方式，Cluster 校验要改到拼装后的键上；已自定义 `lock_key` 的部署升级后可能换锁身份 |
| 改锁键缺省值加前缀 | 违反“缺省键逐字不变”，且锁身份改变让滚动发布的新旧节点锁住不同身份（RR-20260924-25 明确不自动改写） |
| 把 `lock_key` 加进生成配置样例（`codegen/internal/roost/catalog.go`） | 有用但不是本条范围（不是新配置项）；会动 codegen 生成物与 fixture，另列 |
| 只用现有 `NewRedisMarker(redis, key)`、不加前缀形式 | 功能上已够（key 参数就是显式键名），但与 L2 的 `<prefix>:remote_entity:…` 布局不同形，一个部署前缀值不能同时用于两者；N25 要的是“与 C11 同类” |

- `remoteentity/marker.go`：`NewRedisMarkerWithKeyPrefix`、`ValidateMarkerKeyPrefix`、`markerKeyForPrefix`、`newRedisMarkerForEvalWithKeyPrefix`；`markerRedisKey` 注释写明谁写它。`NewRedisMarker` / `newRedisMarkerForEval` 不变。
- `remoteentity/config.go`：`LockKey` 注释补键格式与隔离要求（无行为变化）。
- `remoteentity/marker_key_prefix_promises_test.go`（新）：`TestRedisMarkerDefaultKeyIsUnchanged`（空前缀时实际写到的键逐字是 `remote_entity:marks`，且与 `NewRedisMarker(redis, "")` 互读）、
  `TestRedisMarkerKeyPrefixIsolatesDeploymentsSharingOneRedis`（A Claim 后 B 看不到、B 能以自己的 sid Claim、A 的租约不变、只碰两把各自前缀下的键）、`TestMarkerKeyPrefixValidation`。
- `remoteentity/marker_key_prefix_integration_test.go`（新，`-tags integration`）：真 Redis 上两个前缀各自一把 hash，直接 `HGET` 核对键名；键 `b19:<pid>:<token>:{a,b}:remote_entity:marks`，结束 `DEL` 自己的键（`IRedis` 没有 `UNLINK`）。
- `docs/USER_GUIDE.md` §6：把“这个前缀只作用于 L2 快照键”一句扩成三类键的清单表（谁写、缺省、隔离方式）与标记前缀规则。
- `kit/README.md` remoteentity 一节：加“Redis 键与部署隔离”一行。
- `docs/bugfix/RR-20260927-17.md` 末尾 `## 后续（2026-09-30）` 指向本条。

## 兼容性

- 缺省不变、需显式配置：`NewRedisMarker` 签名与行为不变；`NewRedisMarkerWithKeyPrefix(redis, "")` 与它互读同一把 `remote_entity:marks`。锁键缺省 `e` 不变。
- 新导出 API：`NewRedisMarkerWithKeyPrefix`、`ValidateMarkerKeyPrefix`（供 CHANGELOG）。kit 配置面不变；生成配置样例不变。
- 设置 / 修改标记前缀等于换一套空的所有权标记：兼容装配的所有节点必须同一个值并整体重启（滚动时新旧节点看不到对方的租约，会各自 Claim 成 owner）。
