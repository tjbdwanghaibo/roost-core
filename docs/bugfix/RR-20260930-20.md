# RR-20260930-20：回滚后 release hook panic 不再吞掉业务错误

问题：[RR-20260930-20](../bug/RR-20260930-20.md)（B27 第 2 批端到端补测暴露，等级 P2）。日期 2026-09-30。基线 main `4d9018e1`。
状态：已修复，本地验证通过（包内回归 + `scripts/test-dataengine-generated.sh` / `scripts/test-remote-generated.sh` 端到端），本地提交，未推送 / 未发版。

## 根因

handler 返回业务错误（事务回滚）→ `dispatchLoadedEntities` 的 `defer release()`（修前 `nest/nest_dispatch.go:404-406`）→ `releaseDispatchEntities` → `Guard.ReleaseEntity` →
`runOnEntityRelease`（`entity/entity_guard.go:62-73`，不 recover）→ hook panic。

两处叠加把业务错误丢掉：

1. `dispatchLoadedEntities` 用 `return mgr.invokeHandlerTransaction(...)` 直接返回，`defer release()` 抛出的 panic 让这次调用的返回值（在途的业务错误）整个作废——不是被覆盖，是根本没有返回；
2. panic 沿 `singleDispatch` / `dispatchMany` 传到 `runNestLogic` 的 recover（修前 `nest/nest_dispatch.go:203-209`），那里无条件 `err = recoveredErr`。即便 err 已有值（例如 handler 返回后收尾阶段 Guard 作用域释放里 panic），也会被覆盖。`dispatchNest` 的 recover（`nest/nest_dispatch.go:50-57`）同形。

RR-20260926-53 承诺的“未提交路径不带 `ErrAfterCommitFailed`、值回滚”本身成立（`Msg.txCommitted` 未置位，undo 已执行），只是回复里只剩 hook 错误 `release hook failed`，调用方按判别表看不出这是“业务拒绝 + 释放失败”。

## 决策与未采用方案

### 采用：release 阶段的 panic 单独 recover，并进在途错误；两处 recover 改覆盖为并入

- `dispatchLoadedEntities` 改为具名返回 `(ret any, err error)`；兜底释放改成 `defer func() { if r := recoverRelease(release); r != nil { err = joinRecoveredError(err, r); slog.Error(...) } }()`。
  `recoverRelease` 只包住这一次 `release()` 调用：业务阶段沿函数体传出的 panic 不在这里 recover（deferred 函数正常返回时在途 panic 继续传播），仍交给 `runNestLogic`，与之前一致。
- `joinRecoveredError(err, r)`：`err == nil` 时结果就是 panic 的错误本身（非 error 的 panic 值用 `errors.New(fmt.Sprint(r))`，与旧代码相同）——已提交路径的回复文本因此逐字不变，再由 `dispatchNest` 按 `replyAfterCommit()` 包 `ErrAfterCommitFailed`（RR-53）；
  `err != nil` 时 `errors.Join(err, recovered)`，`errors.Is` 对业务错误与 hook 原因都成立，回复文本是两行（业务错误在前）。
- `runNestLogic` 与 `dispatchNest` 的 recover 都改为 `err = joinRecoveredError(err, r)`：收尾（Guard 作用域释放、解锁后回调）里的 panic 到这里时 err 已是 handler 的结果，不再覆盖。
- 不吞 panic：并进错误链之外，release 处 `slog.Error("nest entity release panic", "handler", name, "err", err)`。

### 未采用

| 方案 | 为什么不用 |
| --- | --- |
| 在 `entity.runOnEntityRelease` 里 recover 每个 hook，只记日志 | 会让已提交路径失去 hook 失败的错误报告（RR-53 / RR-32 要求回复带原因链），也改变 Guard 的公开行为；Guard 释放不知道“提交与否” |
| 只改 `runNestLogic` 的 recover 为 Join | 不够：panic 从 `dispatchLoadedEntities` 的 defer 抛出时，函数的返回值根本没有交给调用方，到 `runNestLogic` 时 err 仍是 nil |
| 生成模板（persistflow / remoteflow）里特判 | 违反“修在 nest 派发 / Guard 释放的错误合并处”的约束；所有生成工程与手写 handler 都会遇到同一路径 |
| release 阶段的 panic 按“提交与否”分流成两种哨兵 | 提交事实已由 `Msg.txCommitted` / `remoteConfirmed` 在 `dispatchNest` 统一判定（RR-53 / 46），这里再分流是重复判断；并入错误链后现有分流照常工作 |
| 用 `fmt.Errorf("%w: %w", err, hookErr)` 链而不是 `errors.Join` | 两者 `errors.Is` 都成立；Join 不用为两个独立原因编一句话，且与 `dispatchNest` 里 `finishRemoteWriteBatch` / `prepared.release` 错误的并入方式一致 |

## 文件与行为

- `nest/nest_dispatch.go`：
  - `dispatchNest` recover（:50-53）与 `runNestLogic` recover（:199-203）：`err = joinRecoveredError(err, r)`。
  - `dispatchLoadedEntities`（:370）具名返回；兜底释放（:395-408）经 `recoverRelease` 跑，panic 并进 err 并记日志。
  - 新增 `recoverRelease`（:414-419）、`joinRecoveredError`（:421-432）。
- `nest/rolled_back_release_hook_promises_test.go`（新）：`TestRolledBackReleaseHookPanicKeepsBusinessError`，memory / strict / pipelined 三种策略，复用 `newLocalHookFixture`（RR-53 的 harness）注入 panic 的 `OnEntityRelease`；
  断言 hook 已运行、undo 已回滚到 10、committer 无记录、`errors.Is(err, 业务错误)`、`errors.Is(err, hookErr)`、`!errors.Is(err, ErrAfterCommitFailed)`。
- `codegen/internal/entity/testdata/dataengine/after_commit_test.go`、`codegen/internal/entity/testdata/remoteflow/after_commit_test.go`：去掉两处 `t.Skip("RR-20260930-20：…")`，`TestGeneratedDataEngineRolledBackReleaseHookPanicKeepsBusinessError`（async / strict / pipelined）与
  `TestGeneratedRemoteRolledBackReleaseHookPanicKeepsBusinessError`（strict Remote 消息）作为端到端绿。

行为：

| 路径 | 修前回复 | 修后回复 |
| --- | --- | --- |
| handler 业务错误 → 回滚 → release hook panic（memory / strict / pipelined / Remote strict） | 只有 hook 错误 | `errors.Join(业务错误, hook 错误)`；不带 `ErrAfterCommitFailed` |
| handler 成功 → 提交 → release hook panic | `ErrAfterCommitFailed: hook 错误` | 不变（`joinRecoveredError(nil, r)` 就是 hook 错误本身） |
| handler 成功 → Remote 批次确认 → hook panic | `ErrAfterCommitFailed: hook 错误`，批次 Commit | 不变（RR-32 回归钉住） |
| pipelined 准入后提前释放 panic | `ErrEntityReleaseFailed` 链（`releaseAfterAdmission` 自己 recover） | 不变，不经过本次改动的边界 |

## 兼容性

- 回滚路径的回复从“只有 hook 错误”变为“业务错误 + hook 错误”的 Join：`errors.Is` 业务错误现在成立；按错误文本匹配 hook 错误的调用方仍能 `strings.Contains`，但文本前面多了业务错误一行。
- 已提交路径回复文本逐字不变；`ErrAfterCommitFailed` / `ErrRemotePartRejected` / `ErrNestedTransactionCommitted` 的分流逻辑没动。
- 新增一条 `slog.Error("nest entity release panic", ...)` 日志（之前回滚路径的 hook panic 没有任何日志，只在回复里）。
- 无公开 API、持久格式、wire 变化；生成模板不变。
