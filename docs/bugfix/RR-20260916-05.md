# RR-20260916-05:match 的 Grouping 注入参数被保存,却没有执行者

**仓库 / 位置**:roost-kit `service/match/match_mod.go`(`NewMod`、`Mod.grouping`、`Provide`)、`queue_store.go`
(`Config.Grouping` 及其默认值);roost-codegen `internal/roost/framework_services.go`(match 的 `ModArgs` / `Collabs`)。
**修复单元**:U-0217(C2)。**定位文档**:TROUBLESHOOTING T-111。来源:实现侧候选 W-2026-09-16-01,审查确认为 RR。

## 问题

`NewMod(grouping, reporter)` 与 `Config.Grouping` 的注释承诺"哪些候选成组是整个匹配策略,由这里注入",store 里却没有
任何路径读它:Enqueue 只入队、Commit 提交指定票、Sweep 只清过期票,成组完全由调用方 Candidates → Grouping → Commit 驱动。
codegen 因此为每个工程生成 `Grouping() match.Grouping { return nil }` 并注释"replace it with the project's own rules"。
项目实现了自己的策略交给 NewMod,会以为匹配按它的规则进行,实际静默失效。

## 根因

C2:承诺无实现——一个公开参数从构造函数穿到 Config,再没有人读。审查明确:**这不是"Enqueue 必须自动成组"**,
Commit 就是指定票的原子提交接口;是签名说了实现没做的话。

## 方案选择

- **A. 服务端驱动**:Enqueue 末尾在同一次 CAS 里 Group 并提交。把策略塞进可重试的存储回调,重试即重复执行、
  副作用与延迟进入事务窗口,还要另定执行周期 / 并发仲裁 / 超时,不是"补一次调用"能完成的。不采用。
- **B. 删掉无效参数(采用,WANTED 与审查一致)**:`NewMod(reporter)`,`Config` 去掉 `Grouping`;`Grouping` 接口与
  `FirstComeGrouping` / `ScoreWindowGrouping` 保留为调用方工具,注释写清"store 不运行它";codegen 不再生成 `Grouping()`
  collaborator,bootstrap 生成 `svcmatch.NewMod(serviceMatch.Metrics())`。
- **兼容入口(非 nil 报错)**:考虑过,但会让一个已经无效的参数再活一个版本;kit 与 codegen 同版本发布,已有工程
  的 `Grouping()` 函数留在业务文件里无害。**破坏性**:调用 `NewMod` 的两参形式编译不过,改成一参即可。

## 改动

- kit `match_mod.go`:`Mod` 去掉 `grouping`,`NewMod(reporter)`,`Provide` 不再传;头注释改为说明成组由调用方驱动。
- kit `queue_store.go`:删 `Config.Grouping` 与默认值;`grouping.go`:接口注释写明是调用方工具。
- kit `sweep_run_test.go`:`NewMod(nil)`。
- codegen `framework_services.go`:match `ModArgs` 只剩 `Metrics()`,`Collabs` 改为一段说明(指向 game-demo 的 matchmaker);
  `framework_services_test.go` 钉 `svcmatch.NewMod(serviceMatch.Metrics())`;`demo/README.md` 同步。

## 证明

kit `service/match/grouping_contract_promises_test.go` `TestGroupingIsNotAnInjectionPointOfTheStore`(反射断言,
修前修后都能编译)。修前红:`Config.Grouping still exists: the store never executes it, so accepting it is a promise the
store cannot keep`。修后 kit 全套绿、`service/match -race` 绿;codegen 全套绿,game-demo 生成工程含 matchmaker 的用法不变。

## 未做 / 边界

- 审查的 ARCH-01 建议把 `Grouping` 接口与通用实现挪进 core 的匹配领域库——那要连带 `Queue` / `Ticket` 类型一起迁,
  属于 ARCH 批次,本单元不做;先让签名与行为一致。
- 已有工程 `internal/service/match/collaborators.go` 里的 `Grouping()` 是业务所有文件,codegen 不回写,留一个无引用的函数。
