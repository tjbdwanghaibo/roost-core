# RR-20260926-66 修复：生成器按每个服务实际注册的 Mod 计算 `shutdown.total_timeout` 与部署宽限期

问题：[RR-20260926-66](../bug/RR-20260926-66.md)（复现 [REPRO-2026-09-26-06 §2](../bug/REPRO-2026-09-26-06.md)）。前序：[RR-42](RR-20260926-42.md)、[RR-51](RR-20260926-51.md)。
日期 2026-09-27；实施基线 main `2373e21`。状态：已修复、本地验证通过，已本地提交，未推送/未发布。

## 根因

RR-51 把生成配置 `shutdown.total_timeout` 统一写成 60s、部署宽限期统一 65s。App 的停机规划（`app/app.go` `modStopBudget`，RR-51）
给每个未声明预算的 Mod 固定 3s 保底、声明预算的 Mod（dataengine，30s）从其余时间拿声明值。真实 game-demo 的 game 服务注册
23 个 Mod（20 个服务专属 + lock / ops / statslog），需要 30s + 3s × 22 = 96s，60s 连保底都给不起：每次停机
WARN `cannot cover the per-mod floor`，先停的 `accessplayertcp` 约 3s 以下，dataengine 在最坏情况下只剩 3s。反过来，只有 6 个 Mod
的框架服务用不了 60s。单一默认值不可能同时合适；而生成器本来就知道每个服务的 Mod 集合。

## 决策（按维护者 2026-09-27 批准的修复约束）

生成时按该服务实际 Mod 集合计算，每个服务各自计算：

```text
total_timeout = 声明预算之和 + 3s × 未声明 Mod 数 + 5s
宽限期        = total_timeout + 5s
```

- **Mod 集合**：取生成 bootstrap 真正注册的 Mod——共享 `a.Mods(...)` 一段加该服务 `RegisterServer` 的全部 Mod（Kit Mod、托管框架服务的
  owner Mod、使用的框架 ClientMod、项目 rpc 的 owner / client Mod、player access 的两个 Mod）。为此把 `renderBootstrap` 中服务 Mod 列表的
  拼装提取为 `serviceModConstructors`，bootstrap 与预算计算共用同一个列表，不会一处加了 Mod 另一处漏算。
- **声明预算**：生成器装配的 Mod 中只有 kit/dataengine 实现 `app.ModStopBudgetProvider`，声明值为生成配置的 `dataengine.shutdown_timeout`
  （30s，`catalog.go` 改为引用同一常量 `generatedDataEngineShutdownTimeout`）。
- **3s**：与 `app.undeclaredModStopFloor` 相同（`generatedModStopFloor`，注释指向 app 常量）。
- **余量 5s 的理由**：`shutdownCtx` 在 `Service.Shutdown` 之前开始计时，Service.Shutdown 与 Mod 停止共用同一时限，余量给它。
  生成的服务 Shutdown 只关闭进程内循环（托管框架 Server 直接返回），5s 与 REPRO §2 探针设定的 `pre=5s` 同值。Mod 之间不需要额外余量：
  App 每停一个 Mod 都按 `time.Until(deadline)` 重新规划；且服务专属段规划时不为之后的共享段预留保底，先停的 Mod 实际份额高于保底
  （game 服务在 Service.Shutdown 用满 5s 时仍为 (96 − 30)/19 ≈ 3.47s）。回归矩阵表明不加余量也能覆盖“dataengine 之前的 Mod 用满预算”的
  最坏情况（需要 total − Service.Shutdown ≥ 87s）；余量只为 Service.Shutdown 服务，不为放大到“看起来安全”。
- **宽限期 +5s**：App 最迟在 total_timeout 返回，进程还要退出；与 RR-51 起的 `total + 5s` 规则一致。
- **写入位置**（每个服务各自的值）：`configs/service/config.<svc>.yaml` 与 `.prod.example.yaml`、`deploy/k8s/base/secret.<svc>.example.yaml`
  的 `shutdown:` 段（注释写明 Mod 数、声明值、未声明数、余量与结果，以及该服务的宽限期）；k8s `terminationGracePeriodSeconds`；
  compose `stop_grace_period`；systemd `TimeoutStopSec`（`install.sh` 按 `$SERVICE` 选值）；`deploy/dev/run.sh`（`SERVICES` 条目为
  `name:ops端口:宽限秒数`，stop 按条目等待）与 `second-game.sh`（按 game 服务）；k8s README 列出每个服务的 Mod 数、total 与宽限期。
- **配置随 Mod 变化（修复中发现的必要环节）**：服务配置是应用自有、创建时渲染一次，而部署模板每次 sync 按当前 Mod 重写。game-demo 本身
  就是先按 20 个 Mod 写配置、再由脚手架 `add saga` / `add access` 加到 23 个——第一版实现下生成的 game 配置是 92s、k8s 却是 106s
  （见“修前红”第二段）。因此 `SyncProject` 提交后调用 `refreshGeneratedShutdownConfigs`：只有当 `shutdown:` 段与它自己注释里记录的
  那次计划逐字相同（从未手改）时，才改写为当前计划；手改过的段、RR-66 之前生成器写的段一律不动。所有 `add` 命令与 `roost project sync`
  都经过 `SyncProject`。
- **doctor**：`roost project doctor` 新增 `shutdown:<service>` 检查（WARN，不 FAIL，避免升级即让既有 CI 失败）：配置的 total + 5s 超过
  生成的宽限期（平台会在 App 仍在停 Mod 时 SIGKILL），或 total 覆盖不了“声明值（读配置里的 `dataengine.shutdown_timeout`）+ 3s × 未声明数”。

未采用：宽限期取 `max(total + 5s, 65s)`（违反约束“宽限期 = total + 5s”，且掩盖配置与模板的偏差）；在 App 里改规划或提高运行时兜底
（RR-51 已定案，App 缺省 30s 不变——提高它会让未重新生成部署模板的旧工程在停机中途被 SIGKILL）；让 player TCP Mod 声明停机预算
（约束未要求，另起行为变化，见“未验证项”）。

## 兼容性 / 默认值变化

- 新生成工程：每个服务的 total 与宽限期按 Mod 计算（见上表），不再统一 60s / 65s。Mod 少的服务的宽限期会低于 65s。
- **旧工程（未重新生成）行为不变**：App 代码未改；配置、部署模板都是既有文件，不动它们就没有任何变化。
- **旧工程重新 sync**：部署模板（生成、归生成器所有）按新公式重写；配置里 RR-66 之前格式的 `shutdown:` 段不会被改写。
  Mod 多的服务宽限期变大（安全）；Mod 少的服务宽限期变小，若配置仍为 60s，平台可能在 App 停满 60s 之前 SIGKILL——doctor 给出 WARN，
  应把 total 改为生成值（例如框架服务 23s）。
- 生成配置的 `shutdown:` 注释文案变化；YAML 键不变。`add mod` / `add saga` / `add access` 等之后，未手改的段自动随 Mod 数更新。
- 无 app / kit 导出 API 变化；`serviceModConstructors` 抽取后生成的 bootstrap 字节不变（codegen 全量测试通过）。

## 交付前对抗性自查

- **宽限期 > total 且留出 SIGKILL 余量**：所有模板取 `serviceShutdownPlan(...).grace = total + 5s`，同一函数产生 config 与模板的值；
  回归逐文件核对两者对应同一服务。App 最迟在 total 时返回（`shutdownCtx`），此后 5s 用于进程退出。
- **每个 Mod 拿到保底、dataengine 拿到声明值**：app 回归覆盖 dataengine 在 20 个位置、Service.Shutdown 0 / 5s、两种消耗模式；真实时钟入口无 Warn。
  已知边界：若服务专属段的每个 Mod 都用满各自预算，最后一个服务专属 Mod 会拿走剩余时间、共享段不再有保底——这是 RR-42 / RR-51 定案的
  规划（服务专属段不为共享段未声明 Mod 预留），与总时长取值无关，本次不改。
- **计数与 bootstrap 一致**：两者共用 `serviceModConstructors`；回归从生成的 bootstrap 文本独立数 Mod 再按公式核对，不依赖生成器内部计数。
- **不误改用户配置**：刷新只替换与注释所记录计划逐字相同的段（`strings.Count == 1`），手改值、旧格式段不动（回归覆盖）。
- **旧工程**：见“兼容性”；未重新生成时零变化；重新 sync 的风险由 doctor 提示并写入 kit/README 与 DEPLOYMENT。

## 复核补修（2026-09-27）：部署宽限期不低于实际配置的停机总时长

来源：协调者复核 `fb00df8` 时指出的升级路径风险。首版规则“宽限期 = 公式 total + 5s”只看生成器的公式；而服务配置是应用自有的——
RR-66 之前生成的 `shutdown:` 段（统一 60s）、手改的 total、缺 `total_timeout` 键（App 兜底 30s）都不会被 sync 改写，但部署模板每次 sync
都按公式重写。旧工程升级后框架服务的宽限期从 65s 静默降到 28s，配置却仍是 60s：平台会在 App 自己的 60s 窗口停到一半时 SIGKILL。
首版只让 doctor WARN，上线不可接受。

**规则改为**：生成 / sync 写入的部署宽限期 = `max(公式 total, 该服务配置里实际生效的 shutdown.total_timeout) + 5s`，永远不低于配置 total + 5s。

- “实际生效的 total”取仓库里该服务三份配置（`config.<svc>.yaml`、`.prod.example.yaml`、`deploy/k8s/base/secret.<svc>.example.yaml` 内嵌的
  `config.yaml`）中最大的一个，按 App 的读法：缺键或无法解析为时长时取 App 兜底 30s。配置文件还不存在（本次渲染正在创建）时不参与，
  用公式值。仓库外的生产配置读不到，文档写明需同步到这些文件。
- 实现：`Manifest` 增加不序列化的 `configuredShutdown`，`withConfiguredShutdown(root)` 在渲染进既有工程前填入（`planManifestSync`、
  `planStagedProjectCommit`、`diffManifest`）；`serviceShutdownPlan` 的 `grace = max(total, configured) + 5s`。配置段本身的规则不变：
  生成器原样的段随 Mod 更新（比较只看公式字段 `sameFormula`，不含宽限期），手改段与旧格式段不动，宽限期跟随它们。
  Mod 减少时，sync 先按旧的配置值渲染模板、再刷新配置，宽限期暂时偏大（安全方向），下一次 sync 收敛。
- doctor：`shutdown:<service>` 读取磁盘上的部署模板（k8s、compose、install.sh——含 RR-66 之前的单值 `TimeoutStopSec`——、run.sh——含旧的
  `-lt 65`——、game 服务的 second-game.sh），任何一处宽限期 < 配置 total + 5s 为 **FAIL**（未 sync 或手改模板，会被 SIGKILL）；
  total 覆盖不了“声明值 + 3s × 未声明数”维持 WARN。
