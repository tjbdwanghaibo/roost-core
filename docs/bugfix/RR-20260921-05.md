# RR-20260921-05 修复：本仓 `go:generate` 产物与 codegen 运行期守卫接入 CI

[问题记录](../bug/RR-20260921-05.md)。2026-10-04；基线 main `00bffd2a`（v1.19.1 之后）。已修复、本地验证，未发版；
新 CI job 只有推送后在 GitHub 上才算真正验证（见末节）。

## 根因

- `.github/workflows/ci.yml`（修前 `:17-180`）没有任何一步跑 `go generate`；`generate --check` 只在生成工程侧
  （`framework-compat.yml:147`、`demo-publish.yml:55`、`release.yml:114`）。
- `codegen/scripts/*-runtime.sh` 四个守卫（修前 dao / entity-sync `:15-16`，attribute / cfggen `:17-18`）用 `sed` 从
  `source-head-check.sh` 读 `core_pin=` 行；`6d04aea4` 删了那一行 → 读出空串 → exit 2。
  `attribute-runtime.sh:45`（修前）`core_dir="${ROOST_CORE_DIR:-$here/../roost-core}"` 指向三仓时代的兄弟目录。
- 两者同根：没有 workflow 调用，坏了没人发现。

## 改法

1. **`ci.yml` 新 job `generated-code`**（与 `linux-quality` 并列，并行跑）：
   - `go generate ./...` 后 `git status --porcelain`，非空即 `::error::`、打印脏文件列表与 `git diff`、exit 1。
     用 `git status --porcelain` 而不只是 `git diff --exit-code`：新增的 `go:generate` 产物没提交（untracked）也要红。
     不需要额外工具：13 处指令都是 `go run github.com/tjbdwanghaibo/roost-core/codegen/cmd/servicerpc`（本模块内），
     干净树上幂等（实测两次 `go generate ./...` 后 `git status` 为空，servicerpc 对未变的产物输出 `up to date` 且不重写）。
     不需要 `GOFLAGS=-mod=mod`（10-04 核实里带了，实测不带也成功）。
   - 依次 `sh codegen/scripts/{dao-golden,attribute,entity-sync,cfggen-golden}-runtime.sh`，各自一个 step，失败时日志直接定位到哪一个守卫。
2. **pin 的来源：`codegen/scripts/core-pin.sh`（新）**，打印 `codegen/internal/roost/manifest.go` 的 `minimumVersions.Core`
   （`ROOST_CORE_PIN` 仍可覆盖）；四个脚本改为 `core_pin=$(sh "$here/scripts/core-pin.sh")`。理由：
   - `minimumVersions` 的注释就是"the lowest framework this generator's output compiles against"——这正是守卫要证明的承诺：
     生成工程可能解析到这个版本，goldens / 脚手架 runtime / 生成的实体必须在它上面编译并跑通。
     生成器开始依赖更新的 Core API 时守卫会红，提示该升下限（与 `framework-compat.yml` 的 minimum lane 同一口径）。
   - 它总是已发布的 tag（`framework-compat` minimum lane 已经在每次 push 上从 proxy 解析它）。
   - **未采用** `codegen/ci/framework-release.yaml` 的 `release:`：`scripts/pretag.sh:63-77` 要求它在打 tag **之前**就写成要发的版本，
     发版提交推到 main 时那个 tag 还不存在，守卫 `go get roost-core@<release>` 必然失败——每次发版 CI 红一次。
   - **未采用**"脚本改用仓内 replace / go.work 指向工作树"（10-04 §2.4 的建议）：那测的是 source-head（HEAD 对 HEAD），
     `source-head-check.sh` 与 framework-compat source-head lane 已覆盖；守卫原本的意义是"对着钉住的已发布 Core"，且任务要求 pin 来自仓内权威来源。
   - **未采用**在四个脚本里各写一份 awk：取 pin 的逻辑原来就是四份复制，坏在一个共同来源上；集中到一个脚本、一条测试钉住。
   - `codegen/internal/roost/core_pin_script_promises_test.go` 把 `core-pin.sh` 的输出钉到 `minimumVersions.Core`
     （`manifest.go` 写法变了、awk 读不出来时在普通 `go test` 里红，而不是在 CI 守卫里 exit 2），并验证覆盖变量仍生效。Windows 跳过（脚本只在 Linux CI 跑）。
3. **`attribute-runtime.sh` 的 `core_dir`** 缺省改为模块根（`$(cd "$here/.." && pwd)`）。结果：本仓有 `attribute/`，replace 总是生效，
   attribute 一侧对着**工作树**编译（生成器与 attribute runtime 同一提交、同一 tag 发布）；其余三个对着 `minimumVersions.Core`。
   这是按原设计让 replace 重新生效，不是新语义；若以后要让 attribute 也对着下限测，删掉这段 replace 即可（v1.18.0 已带 attribute 包，
   修前 replace 不生效时设 `ROOST_CORE_PIN=v1.18.0` 实跑也是 ok）。
4. **根包 `ci_generated_code_test.go`**（照 `TestCIRedisJob*` 的写法，但用 `gopkg.in/yaml.v3` 解析到 step 粒度）：
   - `TestCIRegeneratesTheCommittedGeneratedCode`：`ci.yml` 必须有一个 step，在**同一个** `run` 里先 `go generate ./...`、
     其后 `git status --porcelain` 或 `git diff --exit-code`；该 step 及其 job 不得带 `if:` 或 `continue-on-error`。
   - `TestEveryCodegenRuntimeGuardRunsInSomeWorkflow`：`codegen/scripts/*-runtime.sh` 的每一个都要被某个 workflow 的无条件 step 调用
     （shell 注释行不算）。以后新增守卫不接 CI 会红。

文件：`.github/workflows/ci.yml`、`codegen/scripts/{core-pin,attribute-runtime,cfggen-golden-runtime,dao-golden-runtime,entity-sync-runtime}.sh`、
`ci_generated_code_test.go`、`codegen/internal/roost/core_pin_script_promises_test.go`。

## 兼容性

无 API / 持久格式 / wire 变化。CI 行为收紧：提交过期或手改的 `*_gen.go`、漏提交新产物、或生成器输出在 `minimumVersions.Core` 上编译 / 测试失败，
`ci` 都会红。升 `minimumVersions.Core` 时守卫自动跟随（无第二处版本号）。守卫需要访问 Go module proxy（下载 pin 的 roost-core 与依赖），
与 `framework-compat` 相同；`go generate` 一步不需要网络之外的东西（模块依赖由 setup-go 缓存 / `go mod download` 提供）。

新 CI 步骤的命令能抓漂移（模拟"过期产物已提交"：改脏后 `git add`，再跑该 step 的命令）：

```text
$ printf '\n// hand edit that nobody regenerated\nvar _ = 0\n' >> service/session/session_rpc_gen.go
$ go build ./service/session/ && go vet ./service/session/   → 通过（修前唯一的闸看不见）
$ git add service/session/session_rpc_gen.go
$ go generate ./...                                           → generated: session_rpc_gen.go
$ git status --porcelain                                      → MM service/session/session_rpc_gen.go（非空 → step exit 1）
$ git diff --exit-code -- service/session/session_rpc_gen.go  → -// hand edit that nobody regenerated / -var _ = 0；exit=1
$ git restore --staged --worktree --source=HEAD service/session/session_rpc_gen.go
```

干净树：`go generate ./...` 约 2s（热缓存），之后 `git status --porcelain` 为空。

## 未验证项 / 风险

- **新 job 只在本地按 step 逐条跑过**；GitHub 上的真实运行（冷缓存耗时、proxy 下载、ubuntu dash）要推送后看 `ci` 的 `generated-code` job。
  预计 3～5 分钟（setup-go ≈30s；`go generate` 冷编译 servicerpc ≈30～60s；四个守卫各自编译生成器 + 下载 roost-core@v1.18.0 与依赖 + 测试，约 30～60s/个），
  与 `linux-test` 分片并行，不拉长 `ci` 的总墙钟。
- 守卫依赖 module proxy 上 `minimumVersions.Core` 的 tag；proxy 故障时该 job 会红（与 framework-compat 同一外部依赖）。
- codebase-memory 未使用：改动对象是 workflow YAML、shell 与测试，`.github/` 不在索引内，以源码与 `rg` / 实跑为准。
