# RR-20260924-09 修复：DataEngine 可取消的操作所有权等待

对应[问题与修前证据](../bug/RR-20260924-09.md)。日期：2026-09-24。状态：已修复并验证，未提交、未发布。

## 决策与改动

在 engine 原包增加私有 `operationGate`，零值可用，由 sync.Once 初始化容量为 1 的通道。等待空槽与 context.Done 竞争；获取前后都检查取消。每个成功获取点用 defer 归还所有权。它只替代三处跨 I/O 等待的 Mutex，不替换短临界区的普通数据锁，不新增包或公开接口。

- [operation_gate.go](../../dataengine/engine/operation_gate.go)：共享这三处相同的取消语义，中文注释说明所有权与资源边界。
- [projector.go](../../dataengine/engine/projector.go)：Flush 和 ReplayPass 以调用方 context 获取各自所有权；ReplayPass 对 nil context 统一为 Background。
- [runtime.go](../../dataengine/engine/runtime.go)：并发 Shutdown 的等待可取消，已有 projectorClosed/outboxClosed 进度仍受同一个门闩保护；未完成时 Assembly 继续保留 Runtime。
- [shutdown_deadline_test.go](../../dataengine/engine/shutdown_deadline_test.go)：五个失败场景回归，以及恢复操作和 WAL 重开后的记录保留验证。

保持 WAL/文档格式、提交策略、单一重放顺序、held 释放屏障、分段 ack 和 Outbox 独立交付契约。取消等待不让当前持有者失去锁，也不创建代替调用者后台继续执行的 goroutine。已取消的 Runtime.Shutdown 在取得所有权之前返回，不改变 readiness 或撤销入口。

## 实际验证

修前：问题文档中的五场景完整复跑均失败。修后：五场景与既有 Assembly 超时重试测试 race 通过（1.907s）。随后补强真实 WAL 重开验证，定向 race 再通过（1.755s）：后台存储响应取消退出，未投影事务重开后仍可枚举；普通等待取消后原持有者继续完成、ack 清空，后续 Flush 仍可执行。

```sh
GOCACHE=/tmp/roost-nest-go-cache GOWORK=off go test -race \
  ./dataengine/... ./nestwal ./nest ./entity ./kit/dataengine ./kit/nest \
  ./sync/entitysync/... ./codegen/internal/dao ./codegen/internal/entity \
  -count=1 -timeout=120s
GOCACHE=/tmp/roost-nest-go-cache GOWORK=off go vet ./dataengine/... ./kit/dataengine
GOCACHE=/tmp/roost-nest-go-cache GOWORK=off go build ./...
```

11 包 race 通过，其中 engine 4.004s、nestwal 4.479s、kit/dataengine 3.020s；vet/build 退出码 0。build 的模块 stat cache 写权限警告不影响结果。gofmt 与 diff 空白检查通过。本轮未宣称性能提升。

## 限制

这里只修复等待内部所有权不响应 context 的问题。已经进入的文件系统调用或忽略 context 的外部 Store 不能被 Go 强制中断；调用者超时也不代表所有后台活动已退出。真实 Mongo 副本集/NATS、跨进程故障和存量坏 WAL 运维恢复未在本次修复中验证。
