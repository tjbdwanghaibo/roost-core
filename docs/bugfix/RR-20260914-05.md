# RR-20260914-05:每 tick 补一帧无法追上帧头

**仓库 / 位置**:roost-core `lockstep/room.go`,`NewRoom` 的 `CatchupBatchFrames` 归一化、`Tick` / `pumpCatchup`。
**修复单元**:U-0194(C8)。**定位文档**:TROUBLESHOOTING T-88。

## 问题

`CatchupBatchFrames=1` 被接受。每 `Tick` 先产一帧再补至多一帧,积压 +1-1=0:落后 5 帧起 20 轮成功发送后仍
`next=21 head=25 reliable_pages=20`,`CatchingUp` 不结束,live datagram 一直被跳过。batch=2 收敛。不是丢帧,是
"追帧完成并切回 live"的契约兑现不了。

## 根因

产帧速度与补帧速度是两条路径,配置校验只看每 tick 上限、没看净速度(C8)。

## 方案选择

- **解耦追帧泵与 Tick。** 改变 Room 的单 goroutine 驱动模型,超出一个 RR 的范围。
- **归一化 1 → 2。** 静默改写配置,调用方以为限速 1 帧。
- **创建时拒绝 1(采用)。** 净补帧速度 = batch-1 帧 / tick,必须为正;`<= 0` 仍选默认 32。错误信息写清原因。

## 改动

`lockstep/room.go`:`NewRoom` 对 `batch == 1` 返回 `ErrRoomConfigInvalid`;`RoomConfig.CatchupBatchFrames` 注释写明。

## 证明

`lockstep/catchup_rate_promises_test.go`:batch=1 必须被拒绝(或收敛),batch=2 落后 5 帧 20 轮内收敛。
修前红:`batch=1 never closes backlog: next=21 head=25 reliable_pages=20`。修后 lockstep 含 `-race` 全绿。

## 未做 / 边界

- batch=2 的净速度是 1 帧/tick,落后 N 帧要 N 个 tick;没有按落后量自适应。
