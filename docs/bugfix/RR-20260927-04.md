# RR-20260927-04 修复：doctor 停机 WARN 按运行时的兜底判定非正时长，建议值按配置里的声明预算计算

问题：[RR-20260927-04](../bug/RR-20260927-04.md)（[OPEN-ITEMS-2026-09-27](../review/OPEN-ITEMS-2026-09-27.md) A08 + A09）。前序：[RR-20260926-77](RR-20260926-77.md)、[RR-20260926-80](RR-20260926-80.md)。

图谱说明：codebase-memory 图谱已过期（generation 09-26），行号与结论来自源码。

## 决策（按清单推荐）

只改 `codegen/internal/roost/shutdown_budget.go` 的 `checkShutdownBudgets` WARN 分支（FAIL 分支、生成公式、`project sync` 都不动，D11）：

- **A08**：读到的 `shutdown.total_timeout` ≤ 0 时按 `appDefaultShutdownTotal`（30s，App 的兜底）判定——与同函数 FAIL 分支所用的 `configTotalTimeout` 同一规则。
  文案保留文件里写的值并注明实际值：`total_timeout 0s (the App uses 30s) cannot cover …`；OK 行同样写 `total_timeout 0s (the App uses 30s)`。
  顺带同类：`dataengine.shutdown_timeout` ≤ 0 按 kit/dataengine 的 30s 兜底判定（`kit/dataengine/mod.go` `duration()`），否则会把“实际 30s 不够”的配置判为 OK。
  非法时长（解析失败）的处理不变（dev FAIL、示例 WARN 只报文件与键）。
- **A09**：每份不足的配置单独算建议值 = 按它自己的 `dataengine.shutdown_timeout` 算出的所需（声明预算之和 + 3s × 未声明数）+ 余量 5s。
  各份相同时文案不变（`… Set it to 131s`）；不同时逐文件给出（`Set it to 101s in <prod>, 116s in <secret>`）。dataengine 为生成值 30s 时建议值与之前的公式值相同，
  RR-66 / RR-80 的既有断言（`Set it to 101s`）不变。

未采用：让 `project sync` 也读 `dataengine.shutdown_timeout`（D11 明确保持）；把建议值取几份配置的最大值统一给出（dataengine 预算不同时对较小的那份过大，且看不出是哪份需要多少）。
