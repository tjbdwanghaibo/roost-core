# NC-180 修复：BucketHolder 遍历先复制桶快照，再在锁外调用回调

[问题](../bug/RR-20261005-NC-180.md) · [证据](evidence/noncore-bugfix-20261005-revn13/README.md) · [本轮](../review/REVIEW-2026-10-05-n13.md)。已修复、声明场景验证，未发版。

## 根因与修法

`container/bucket.go` 的 `Bucket.Range` 在 `RLock` 内调用回调；回调对同一桶的 `Del` / `Add` / 未命中 `Get` 要写锁，自锁。改为：读锁内把本桶条目复制进切片，释放锁后逐个调用 `f`，`f` 返回 false 即停止。`RangeAll` / `RangeWithCursor*` / `RangeByCursor` 都经过它，`EntityManager.Range` / `RangeByCategory` / `CountByCategory` 与 `ManagerAccess.Range` 随之成立；entity / nest 生产代码不改。

语义变化：回调看到的是复制时的快照，期间被并发删除的实体仍可能交给回调。这与 `EntityManager.RangeGroupEntities`（先取切片）、`safemap.ShardedSafeMap.Range` 一致；实体使用方本来就要在拿到实体锁后复核 `IsRemoved`（`lock.LockManager.GetLock` 的约定）。

未采用：
- 只把 `Get` 未命中改为不升级写锁——回调里 `Del` / `Add` 仍自锁，回调读同一桶时有写者排队仍死锁（递归 `RLock`）；
- 在 entity 层先收集再遍历——改核心包、且 `BucketHolder` 的其他遍历入口照旧自锁。

## 兼容

公开签名不变。遍历分配一个按桶大小的切片；正式调用方只有 `kit/statslog` 的周期统计，不在请求路径上。

## 验证

- 修前：`TestBucketRangeCallbackMayChangeTheHolder` 三叶、`TestManagerRangeCallbackMayDestroyAndStopsAtFalse/destroy_inside_Range` 有界等待 2s 失败（[原文](evidence/noncore-bugfix-20261005-revn13/red.txt)）。
- 修后：两条通过；`go test -race -count=3 ./container ./lock ./entity` 通过（container 中 NC-184 / 185 的两条在其修复前预期为红，见各自记录）；全量门禁见[证据](evidence/noncore-bugfix-20261005-revn13/README.md)。
- 未验证：生成 game-demo 真实进程里业务在 `ManagerAccess.Range` 回调中卸载实体（仓内没有这样的调用方）。

## 复审更正（2026-10-05，独立复审 audit180）

上文“实体使用方本来就要在拿到实体锁后复核”不成立于 `EntityManager` 自己：`RangeByCategory` / `CountByCategory` 在回调前无锁读 `GetEntityCategory()`，`kit/statslog` 也直接读分类 / 种类。修复前桶读锁挡住 `Destroy` 的 `Del`，回调期间实体不会被清理；改为锁外回调后，快照里的实体可能已被 `Destroy` 收尾的 `doClear` 把 ID / 分类 / 种类写回零值——回调拿到 `ID()==0` 的实体，statslog 按分类 0 计数，`-race` 下 `CountByCategory` 的读与 `doClear`（`entity/entity_base.go:430`）报数据竞争。

修法（`entity/entity_manager.go` 的 `rangeHeld`）：`Range` / `RangeByCategory` / `CountByCategory` 对快照里的每个实体先 `Touch` 再回调、返回后 `UnTouch`；`Touch` 失败（已摘除）跳过。与 nest 分发持有实体引用同一协议：持有期间 `Destroy` 的 `ClearBase` 不清理，最后一个 `UnTouch` 才清理。回归 `TestManagerRangeNeverHandsOutAClearedEntity` 两叶（到达前已销毁不交出；回调持有期间被并发销毁仍可读），修前两叶红（`id=0 category=0`），修后通过。代价：10 万实体一次 `Range` 约 0.86ms → 4.1ms（Apple M5，两次 CAS / 实体），唯一正式调用方是 statslog 的分钟级统计。

## 复核后的补修（2026-10-06，C7 遍历回调契约测试发现）

`RangeGroupEntities` 改为与 `rangeHeld` 共用 `visitHeld`：先 `Touch` 再回调、返回后 `UnTouch`，Touch 失败跳过。修前红 `TestEntityRangeContract/EntityManager.RangeGroupEntities/delete_inside_the_callback`：`Range handed out key 0 (value 0) that never existed`；修后 `entity` race×3 与 glsvet 通过。Nest 契约论证与验证见 [C7 方案 §4.2](../feature/C7-RANGE-CALLBACK-CONTRACT-2026-10-06.md#42-rangegroupentities-交出已被清零的实体nc-180-残余)。
