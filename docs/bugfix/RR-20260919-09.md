# RR-20260919-09：缺失实体在 single / broadcast 分派处变成 nil 解引用（U-0255）

- 仓库：roost-core `nest`
- 缺陷类：C8（同一状态在两条路径上判据不同）
- 优先级：P2
- 相关：T-149；测试 `nest/missing_entity_promises_test.go`

## 问题

生产的 `ManagerAccess.Get` 在 manager 未命中、且没有 loader（或 loader 合法地返回 nil）时返回
`(nil, nil)`。`singleDispatch` 与 `broadcastDispatch` 只检查 `err` 就调用 `e.Touch()`：

- single：调用方拿到的是顶层 recovery 生成的 runtime nil pointer，而不是 `ErrEntityNotFound`——
  "没有这个实体"和"框架出错了"变成同一个答案；
- broadcast：逐实体的 recovery 在 `Touch` **之后**，所以一个缺失的 id 会逃到整次分派的外层 recovery，
  **排在它后面的实体一个都不再执行**。

## 根因

同一个包里 multi / multiGroup 写的是 `e != nil && e.Touch()`——契约是清楚的，是这两条路径漏了。
现有的 mock getter 对缺失直接返回 error，恰好掩盖了生产契约，所以测试一直是绿的。

## 方案

- 采用：两条路径显式处理 `e == nil`。single 返回 `ErrEntityNotFound`；broadcast 跳过这个 id 并继续。
- 测试用**生产形状的替身**（缺失返回 `(nil, nil)`），这一点和修复同等重要：用现有 mock 写的测试
  永远证明不了这件事。
- 没做（留给契约）：要不要统一要求 `Getter.Get` 对缺失返回 `ErrEntityNotFound`。在统一之前，
  所有消费方都必须容忍 `(nil, nil)`——本轮把两个不容忍的改成容忍。

## 改动

`nest/nest_dispatch.go`：`singleDispatch` 的 `if e == nil || !e.Touch()`，`broadcastDispatch` 的同一条。

## 证明

修前红：single 是 panic（`invalid memory address or nil pointer dereference`）而不是 `ErrEntityNotFound`；
broadcast 把缺失 id 放在第一个时，后面那个存在的实体一次都没跑（`the handler ran 0 times, want once`）。
修后两条通过。

## 未做 / 边界

- `Getter.Get` 的统一契约没有定（见上）。
- multi / multiGroup 本来就对，没有改动。
