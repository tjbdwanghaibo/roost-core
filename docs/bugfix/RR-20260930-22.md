# RR-20260930-22 修复：gift deliver 的收件人检查改读 Player DAO 自己的库与集合

问题：[RR-20260930-22](../bug/RR-20260930-22.md)（B27 第 3 批真实环境端到端暴露，P2）。
日期 2026-10-01；实施基线 main `db4b7009`。状态：已修复，模板回归与生成工程验证通过，已提交，未推送、未发版。

## 根因（基线行号，模板 `demo/internal/service/game/gift_saga.go.tmpl`）

- `:95` `gameDatabase, _, _ := effectSettings(registry)`——`effectSettings`（`level_up_mail.go.tmpl:97`）读的是 `dataengine.database`（缺省 `game`），这个库是 Data Engine 放 WAL 投影 / fence 回执的库；`:129` 把它塞进 `giftSteps.gameDatabase`。
- `:487` `deliver` 用 `steps.mongo.Database(steps.gameDatabase).Collection(giftRecipientCollection)`（`giftRecipientCollection = "player"`，`:69`）`FindOne {_id: entityID}` 判断收件人是否进过游戏。
- Player 文档实际落在 DAO 标记 `//roost:dao coll=player db=game`（`demo/db/def/player.go.tmpl:3`）生成的 `db.PlayerDaoDBName = "game"` / `db.PlayerDaoCollection = "player"` 里，与 `dataengine.database` 无关；两者只在都保持缺省 `game` 时碰巧同库。README 推荐的隔离做法（改 `dataengine.database`）一改，所有进过游戏的收件人都查不到 → `refuse("recipient has never entered the game")` → saga `compensated`。
- 同模板内核对：`:115` 原生 step inbox `saga.NewDataEngineStepInbox(mongoClient, gameDatabase, …)` 用 `dataengine.database` 是**对的**（回执是那个库上的 lease fence，与 Bag 变更同一提交投影），保留。其它 demo 模板里直接拼库名读 DAO 集合的只有 `game/controllers/player/controller.go.tmpl:239`，它已经用 `db.NewGuildDao().DbName()`，无需改。

## 决策

收件人检查改用 DAO 生成的常量 `db.PlayerDaoDBName` / `db.PlayerDaoCollection`（导入 `{{MODULE}}/db`）——库名和集合名从 DAO 标记单点派生，改标记就跟着变，不再从任何运行时配置推断。`giftSteps.gameDatabase` 字段删除（唯一读者就是这处检查）；`startGiftSaga` 里的局部变量改名 `dataEngineDatabase`，只喂原生 inbox，注释写明它只为此用。

### 未采用的方案

1. **用 Player DAO 的读接口 / 加载 Player 实体**：deliver 跑在 saga 消费者里，收件人通常属于另一进程（ownership 表），把别人的 Player 加载进本进程正是 `gift_saga.go.tmpl` 头注释和 RR-20260920-04 要避免的；现状"直接读集合、不加载实体"是对的，只是库名错了。
2. **让 `effectSettings` 返回 DAO 库名**：`effectSettings` 的职责是和 dataengine Mod 发布效果的键一致（effect inbox 确实要用 `dataengine.database`，`activity.go.tmpl:498`、`level_up_mail.go.tmpl:57`），不能偷换。
3. **保留 `gameDatabase` 字段、由 Init 用 `db.PlayerDaoDBName` 填**：多一个可以填错的字段换不来任何东西；常量直接用。
