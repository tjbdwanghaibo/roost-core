# RR-20260914-09:LockstepBot 回调失败后继续处理成功,但丢失批次尾帧

**仓库 / 位置**:roost-core `robot/lockstep.go`,`HandleBroadcast` / `HandleFrames` / `apply`。
**修复单元**:U-0198(C8)。**定位文档**:TROUBLESHOOTING T-92。

## 问题

`HandleBroadcast` / `HandleFrames` 先让 Assembler 一次释放整个连续批次,Assembler 的 `next` 立刻越过整批;
`apply` 中途出错既不保留尚未处理的帧,也不把 Bot 标记为不可继续。重传原包被当成重复丢弃,后续新帧照常
返回成功——模拟却漏了批次尾帧。审查在三个注入点各测一次(同一包带帧 1、2,处理帧 1 时让一个回调只失败一次,
恢复后重传原包再送帧 3):

| 注入点 | 实际模拟成功序列 | Assembler Next |
| --- | --- | --- |
| `Sink.SubmitInput` | [1,3] | 4 |
| `Sink.ReportHash` | [1,3] | 4 |
| `Simulate` | [3] | 4 |

不是第一次错误被吞掉,而是第一次错误**之后**成功返回的处理已经缺了权威帧。

## 根因

接收游标当成了应用游标(C8:两条路径对"处理到哪了"用了同一个判据)。Assembler 记的是"已交给消费者",
Bot 没有记"已应用到模拟";重传补不回来,因为去重边界已经前移。

## 方案选择

- **失败后把 Assembler 退回批次开头。** 审查明确反对:已成功模拟的帧会被重放,产生重复副作用。
- **一律进入 terminal。** 对 `Simulate` 失败是对的,但把一次暂时的发送失败也变成"重建 Bot",
  而发送失败根本不影响模拟状态。
- **按失败点分开(采用)。** 三步 `simulate → input → hash` 各自有不同的恢复规则:
  - **`Simulate` 失败 → terminal。** 无法判断模拟推进了多少,重跑就是双重副作用。置 `terminal`,
    此后每个入口直接返回 `ErrLockstepBotTerminal`,由宿主重建 / 快照恢复。
  - **`SubmitInput` / `ReportHash` 失败 → 保留。** 帧的模拟已经成立,只是出站没出去。保留这一帧、
    这一步,以及**它已经产出的 payload / hash**,下次调用从那一步继续——不重跑 `Simulate`,也不重新
    调用 `Input` / `Hash` 生产者(重发同样的字节;服务端按 U-0193 对 (player, frame) 去重,重发是幂等的)。
    批次里它后面的帧原地排队,顺序不变。
  保留的工作要有上界(U-0197 的教训):`MaxPendingApply`(默认 256)之外进入 terminal——sink 连续几百帧
  不收就不是暂时故障了。上界只在**保留时**检查,所以一次合法的大批次(比如 64 帧的追帧页)照常排干。

  另外:`HandleFrames` 收的是调用方的帧,payload 是调用方的内存(`DecodeBroadcast` 会复制,这条路径不会),
  跨调用保留必须先复制成自己的副本,否则调用方复用缓冲区就改掉了待应用帧。

## 改动

`robot/lockstep.go`:`ErrLockstepBotTerminal`;`applyStep` / `applyCursor`;`LockstepBot.pending` / `cursor` /
`owned` / `maxPending` / `terminal`;`LockstepBotConfig.MaxPendingApply`;`apply` 改成"在遗留工作之上排干 +
分步游标";新增 `retain`(复制未完成帧、检查上界)、`fail`、`cloneFrame`;两个入口先查 terminal;
新增 `Terminal()` / `PendingApply()`。

## 证明

`robot/lockstep_apply_promises_test.go`:
- `TestLockstepBotPromiseTransientSinkFailureKeepsTheBatchTail`(input / hash 两个注入点):恢复后
  `applied==[1,2,3]`,输入与 hash 各三次不重复,`FramesApplied==3`(没有帧被模拟两次);
- `TestLockstepBotPromiseSimulateFailureIsTerminal`:首次错误即 `ErrLockstepBotTerminal`,之后的
  `HandleBroadcast` / `HandleFrames` 全部拒绝,且不再有帧被模拟;
- `TestLockstepBotPromisePendingApplyIsBounded`:sink 永久失败时进入 terminal,不无限增长;
- `TestLockstepBotPromiseRetainedFramesDoNotAliasCallerPayloads`:调用方在失败后改写自己的 payload,
  恢复时模拟看到的仍是原值。

修前红(只用旧 API 的两条):`continued successfully after failure but simulation skipped frames: applied=[1 3] next=4
stats={FramesApplied:2 InputsSubmitted:1 HashesReported:1 …}`(hash 注入点同形)、
`a retained frame aliased the caller's payload: simulate saw [], want [7]`。terminal 与上界两条依赖新 API,
修前只是不编译。修后 robot 含 `-race` 全绿,core 全仓 `-race` 全绿。

## 未做 / 边界

- `apply` 失败时,本次 Ingest 顺带报出的"空洞"错误仍被丢弃(返回 applyErr),要等下一个补不上空洞的包
  才会发起追帧请求。行为与修前一致,没有一起改。
- `Simulate` 的 terminal 契约要求宿主重建 Bot;类本身不做快照 / 恢复。
- `hasher.Fold` 仍在 `Simulate` 之前——因为 Simulate 失败是 terminal,hash 前移不会被后续处理看见。
- 记录型替身,没有真实传输或负载测试。
