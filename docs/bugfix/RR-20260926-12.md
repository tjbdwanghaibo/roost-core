## 复核后的补修（2026-09-26）

### 残留与根因

复核指出两项验收未完成：(a) 未被读取的配置没有任何告警——`kit/syncbus/mod.go`（基线）`configKey` 只对 `sync` 段按键告警，`room` 段静默兼容，
被 `syncbus` 段遮住的旧键、`syncbus` / `room` 段里的未知键（拼写错误）都悄无声息；另外 `transport` 写错（如 `jetsream`）时 `useJetStream` 为假，
进程静默退回普通 NATS，与 RR-12 原始后果相同。(b) 生成工程测试不断言实际 transport，只有 mod 单测。

### 修复

- `kit/syncbus/mod.go`：`configKeys` 列出本 Mod 读取的全部键；`configWarnings` 在 Init 时列出 (1) `room` / `sync` 段里被实际读取的键——告警弃用并给出改名方向；
  (2) 被更高优先级段遮住的旧键——“写了也不生效”；(3) `syncbus` / `room` 段里不认识的键。`sync` 是共享旧命名空间（`sync.entity.*` 归 kit/nest 的 Entity 同步配置），
  那里只看本 Mod 的键，不报未知键。每类每段一条 WARN，替代原来逐键的 `sync` 告警。`transport` 只接受空 / nats / jetstream / js，其他值 Init 返回错误。
- 生成工程测试：新模板 `demo/internal/service/game/syncbus_config_test.go.tmpl`（登记在 `codegen/internal/roost/demo.go` 的 demo 文件表）用工程自己生成的
  `configs/service/config.<game>.yaml` 与 `.prod.example.yaml` 初始化真实 kit `SyncBusMod` 并 `Start`，解析启动日志：`syncbus mod: started` 的 transport 必须等于配置值，
  且不得有任何 WARN/ERROR。framework-compat 的 generated-consumer 在 demo / source-head 等格子里会跑 `go test ./...`，因此每次都覆盖。
- `.github/workflows/framework-compat.yml`：full 场景真实启动 game 与 demo 场景 dev 栈启动后，都 grep 进程日志要求 `"msg":"syncbus mod: started"…"transport":"jetstream"`，
  否则失败并打印 syncbus 日志行（RR-12 最初就是从这条 CI 日志发现的）。

未采用：在 `app.ValidateServiceConfig` 里同步校验 `syncbus.*`——那里只认 `sync.*`，是 core 层的旧校验；本轮把判断放在真正读取配置的 kit Mod 里，避免两处规则漂移。
`app` 的 `sync.*` 校验保持不变。

### 兼容与行为变化

- 旧 `room:` / `sync:` 段仍按原优先级生效，只多出 WARN。
- **行为收紧**：`syncbus.transport`（或旧段 transport）为 nats / jetstream / js 以外的值时进程启动失败，此前是静默使用普通 NATS。
