# NC-60 修复：Snapshot 在读锁内完成复制

[问题](../bug/RR-20261005-NC-60.md) · [证据](evidence/noncore-bugfix-20261005-n07/README.md) · [本轮](../review/REVIEW-2026-10-05-noncore-n07.md)。已修复、声明场景验证，未发版。

## 根因与修法

基线 `attribute/container.go:107-113` 取到 profile 指针后先 `RUnlock`，再在锁外 `CloneProfile`。改为 `RLock` + `defer RUnlock`，复制在读锁内完成；`Apply` / `ClearDirty` 的写锁因此等到复制结束。注释补充：经 `Live` 拿到的 profile 由属主自己的锁串行，不在承诺内。

未采用：在 `Apply` 里复制再替换层（copy-on-write）——会让 `Live` 持有者看到的对象被换掉，改变 `Live` 的语义；本条只需兑现已写明的锁承诺。

## 兼容

公开 API、生成物不变。`CloneProfile` 现在在容器读锁内运行：实现里回调同一容器的写方法会自锁死。生成的 `CloneProfile` 是值拷贝，不回调；手写 profile 极少这样做，写进注释与本记录。多个并发 `Snapshot` 共享读锁，不互相阻塞。

## 验证

- 修前：`TestSnapshotCopiesUnderTheContainerLock` 失败（Apply 在复制中途进入 LoadValues），`-race` 3 处 DATA RACE。
- 修后：`GOWORK=off go test -race -count=3 ./attribute/` 5 用例 ×3 通过；修复后的组合运行见本轮记录的验证节。
- 未验证：第三方 profile 在锁内回调容器的死锁形态未写用例（属于误用，不承诺）。
