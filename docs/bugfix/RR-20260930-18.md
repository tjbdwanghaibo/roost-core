# RR-20260930-18 修复：`Service.Shutdown` 把 App 的停机 ctx 传给 `Scene.Close`

问题：[RR-20260930-18](../bug/RR-20260930-18.md)（REMAINING §3 N31，维护者 2026-09-30 拍板）。日期 2026-09-30。基线 main `4784ef82`，worktree `.claude/worktrees/agent-af9baa8dcead1162b`，分支 `worktree-agent-af9baa8dcead1162b`，在 RR-20260930-16 / 17 与 N30 提交之后。
状态：**已修复**（本地提交，未推送 / 未发版）。codebase-memory 图谱 ready，本轮以当前源码与实跑为准。

## 根因

见问题记录。要点：`demo/internal/service/game/service.go.tmpl` 的 `Shutdown` 忽略 App 给的 ctx，用 `context.Background()` 关场景，停止重载与 manager 排空不受 `shutdown.total_timeout` 约束。

## 决策

- `func (s *Service) Shutdown(ctx context.Context) error`，`s.scene.Close(ctx)`。`Scene.Close` 已经按 ctx 放弃等待（`stopUnloadResync` 的注释：“Its timeout does not keep the manager open”），只是没人给它一个会到期的 ctx。
- `Init` 里 `registry.Register` 失败时的 `scene.Close(context.Background())` 不改：`app.Service.Init(registry)` 没有 ctx，这是启动失败的清理，不受停机预算约束（App 在 Init 失败后按 Mod 逆序停机）。
- 没有采用“Shutdown 自己再套一层超时”：App 已按 `shutdown.total_timeout` 建 ctx，各 Mod 的停机预算由生成器汇总（RR-20260926-66），服务层不该另定一个数。

## 文件与行为

- `demo/internal/service/game/service.go.tmpl`：`Shutdown(ctx)`、`scene.Close(ctx)`，注释写明编号与旧行为。
- `demo/internal/service/game/service_shutdown_test.go.tmpl`（新模板）：`TestShutdownClosesTheSceneUnderTheAppsStopDeadline`——用既有 harness（`newScene(newSceneRecorder(), nil, gamescene.DefaultConfig())` + `Start`）建场景，把 `stopUnloads` 换成记下 ctx 的替身（harness 没有实体运行时，这个字段本来为 nil；`Close` 一定经过它），用 `context.WithTimeout(…, time.Hour)` 调 `(&Service{scene: scene}).Shutdown`，断言替身看到的 ctx 有 Deadline、`Shutdown` 之后 `s.scene == nil`。
- `codegen/internal/roost/demo.go`：scaffold 步骤加一行写这个模板（`TestDemoTemplateStepsAndShippedFilesAgree` 要求每个模板都有写它的步骤）。

## 兼容性

只影响 `-template game-demo` 生成的工程；demo 文件是应用所有（无生成头），已有工程 `project sync` 不改它们，要手工把 `Shutdown` 的两处改过来。行为收紧：停机时限到期后 `Scene.Close` 不再无限等，`errors.Join(resyncErr, manager.Close(ctx))` 的错误进 `slog.Warn("scene did not close cleanly")`，与既有失败处理一致。
