# RR-20260926-35 修复：事务内 CreateInScope 进入提交边界，回滚 / 拒绝时撤销发布；kit 自动接 pipelined 水位

问题：[RR-20260926-35](../bug/RR-20260926-35.md)（探针见 [REPRO-2026-09-26-04 §3、§3b](../bug/REPRO-2026-09-26-04.md)）。
日期 2026-09-26；实施基线 `49f20ee`（v1.17.0 之后的 review 登记提交）。状态：已修复、本地验证通过，已本地提交，未推送 / 未发布。
方向按维护者批准的“修复约束”：事务内 CreateInScope 与动态 Cast 相同（Include + CaptureEntities），回滚 / 拒绝时撤销发布；
kit 在 committer 为 pipelined 时自动接 `DurableLSN` 水位（二选一中选自动接线）；事务外 CreateInScope 行为不变。

## 根因（基线源码核对）

- `entity/manager_factory.go` `CreateInScope`：build → `RequireEntity` → `TryAdd` 即结束，既不加入当前 `SyncMutation`，也没有任何
  事务捕获。对照 `nest/cast.go` `CastMulti` 末尾的 `mutation.Include(lockedNow)` + `tx.CaptureEntities(lockedNow)`。
  于是新实体的 `commitGate` 为空（`SyncCommitReady()==true`），锁一释放 Sync 就能捕获并外发；回滚只恢复参数 / Cast 实体，
  新实体留在 EntityManager 里继续被同步。
- `entity` 包不能引用 `nest`，所以“事务”对 `CreateInScope` 不可见，需要一个由 Nest 安装的钩子。
- `kit/nest/entity_sync.go` `initEntitySync` 直接用业务给的 `ManagerConfig` 建 Manager，不接 `DurableWatermark`；
  唯一的水位入口是 `nestwal.Runtime.DurableWatermark()`，只有 demo scene 手工接。

## 决策与实现

### 1. 事务绑定到 Guard（`entity/entity_guard.go`、`entity/manager_factory.go`、`nest/execution.go`、`nest/rollback.go`）

- 新接口 `entity.CreatedEntityCapturer{ CaptureCreatedEntity(created, revoke func()) error }`，`EntityGuard` 增加字段与
  `BindCreatedEntityCapturer(c) (restore func())`（Guard 归还池时清空）。
- `callTransactionHandler` 在调用业务期间把当前 `RollbackTx` 绑到当前 Guard，退出时恢复先前值——嵌套的
  `RunIsolatedTransaction` 捕获自己的新实体，外层事务不受影响。
- `CreateInScope` 在 `TryAdd` 之后：Guard 绑定了事务 → 先 `CaptureCreatedEntity`（失败则立即撤销发布并返回错误），
  再 `scope.guard.syncMutation.Include(新实体)`。没有绑定（`Create()` 自建的短作用域、Nest 之外的 `WithGuardScope`）→ 原语义不变；
  只有 SyncMutation 没有事务（RollbackNone + memory 的快路径）时只做 Include，与 Cast 一致。
- `RollbackTx.CaptureCreatedEntity`：先 `DeferRollback(revoke)` 再 `CaptureEntities([created])`。回滚函数逆序执行，
  所以新实体 DAO 的快照恢复先跑、撤销最后跑；即使后续捕获部分失败，回滚也会撤销发布。新实体记入 `tx.created`，
  `runAfterAdmission` 在 `Admit` 之前再 `Include` 一次（Include 按状态对象去重）：业务在 CreateInScope 之后才启用同步状态
  （探针写法）时，新状态也进入同一提交屏障。准入 / 回滚 / abandon 都清空该列表。

### 2. 撤销发布（`entity/manager_factory.go` `revokeCreated`）

调用点只有两个：事务 `Rollback()`（handler 报错、panic、提交明确拒绝、pipelined Enqueue 拒绝、Remote finalize 拒绝都经过它），
以及捕获失败。调用时 Guard 仍持有新实体的锁：

1. `addMu` 内确认索引里还是这个实例（业务在同一事务里已 Destroy 则不重复收尾），标记 `removing`、`SetRemoved`、摘除实体与分组索引、
   清空 owner（Guard 释放时不再对它运行 release hook）。拿到指针的并发访问者取锁后看到 removed 即退出——与 `Destroy` 相同的
   `LockManager.ReleaseLock` 契约。
2. 同步：当前 SyncMutation 的 observer 实现新的可选接口 `entity.SyncSubjectRetractor` 时调用 `RetractSyncSubject(state)`，
   `entitysync.Manager` 以 `Unregister` 语义注销该 subject（只认同一个状态对象）：未持有对象的订阅直接移除，已持有的会话先收到
   ObjectRemove，退役完成前同 ID 重新登记返回 `ErrSubjectRetiring`（remove-before-create）。随后关闭实体的同步状态。
3. `AppendPostRelease`：Guard 释放全部锁后按 `Destroy` 的顺序运行 `DestroyAll/OnDestroy(DestroyReasonCommon)`、`ClearBase`、
   `LockManager.ReleaseLock`、清除 `removing`，之后同一 ID 可以重新创建。

不持久：新实体的 DAO 变更（`MarkPersist`）本来就挂在当前事务上，回滚清空 mutations，拒绝时记录未被接受；撤销不做删除准入。
未新增 `DestroyReason` 常量：`DestroyReasonCommon` 的注释写明业务包会给原因值起领域别名，新增数值可能与业务值冲突。

### 3. Sync 侧两处配合（`sync/entitysync/manager.go`、`sync/entitysync/flush.go`、`entity/entity_base.go`）

- `Manager.RetractSyncSubject`（见上）。
- Flush 捕获时，已退役（`subj.retiring`）subject 的状态在准备期间被关闭，`ErrSubjectSyncClosed` 不再计为 Flush 失败、也不重试，
  只发它欠的 ObjectRemove。负对照：临时去掉这一分支，`TestCreateInScopeRevokedWhenStrictCommitRejected` 在 `-race -count=200` 中
  199 次失败：`concurrent flush: sync prepare subject 9965509: entity: subject sync state is closed`。
- `EntityBase.SetSyncState` 安装的实体锁闭包在安装时取定实体 ID。原闭包在锁外读取 `e.id`，与撤销 / 销毁后 `doClear` 清零 id
  构成数据竞争（并发 tick 回归在 `-race` 下报出：`doClear` 写、`SetSyncState.func1 → EntityBase.ID()` 读），同一竞争在
  `Destroy` + 并发 Flush 上也存在。

### 4. kit 自动接水位（`nest/nest.go`、`kit/nest/entity_sync.go`、`kit/nest/nest_mod.go`）

- 新导出 `(*NestMgr).DurableWatermark() func() uint64`：committer 实现 `PipelinedTransactionCommitter` 时返回其 `DurableLSN`，否则 nil。
- `initEntitySync`：`Configure` 之后 `DurableWatermark` 仍为 nil 时装入转发函数 `committerDurableWatermark`（Manager 在 Init 创建，
  committer 在 Provide 才确定）；`Provide` 构造引擎后 `bindDurableWatermark` 原子写入来源。Provide 之前返回 0（带 CommitLSN 的内容
  一律暂缓，此时也不可能有 pipelined 提交）；committer 不支持 pipelined 时返回 `math.MaxUint64`（不设门槛）。业务显式配置优先。
- **选自动接线、不选缺失时拒绝启动**：kit 的 Data Engine committer（`kit/dataengine.Mod`）总是实现 pipelined 接口，
  拒绝启动会让所有没有手工接线的既有部署起不来；同步持久提交不产生 CommitLSN，接上水位对它们不改变行为。

未采用：把新实体只在准入前统一 Include（不在创建时 Include）——与约束“与动态 Cast 相同”不符，且捕获失败时的撤销点更难说明；
在 `entity` 里通过 fctx 读取 Nest 的事务键——跨包依赖私有键，Guard 字段更直接且随 Guard 生命周期清理。

## 兼容性与新导出 API

- 新导出：`entity.CreatedEntityCapturer`、`(*entity.EntityGuard).BindCreatedEntityCapturer`、`entity.SyncSubjectRetractor`、
  `(*entitysync.Manager).RetractSyncSubject`、`(*nest.RollbackTx).CaptureCreatedEntity`、`(*nest.NestMgr).DurableWatermark`。无删除 / 改签名。
- 行为：handler 内 CreateInScope 新建的实体在提交确认前不外发（strict 为提交且全部锁释放后，pipelined 为 ticket 持久后）；
  回滚 / 拒绝后不再留在内存。RollbackState 下新实体 DAO 需要 `RollbackSnapshotter`/`RollbackParticipant`（生成 DAO 满足），
  remote-managed 实体在 durable 事务内创建返回 `ErrDurableRemoteWriteUnsupported`——与 Cast 同一约束，此前创建不检查。
- 撤销调用 `OnDestroy(DestroyReasonCommon)`；只登记在业务自建 Manager 上的 subject 由业务在 `OnDestroy` 里注销（与 `Destroy` 相同）。
- kit：`NewModWithEntitySync` 未显式配置水位时自动接线；demo scene 自建 Manager 且已手工接线，不变。
- 事务外：Nest 之外调用的 `EntityManager.Create`、生成 Lifecycle 的 `Create` / `GetOrCreate`、独立 `WithGuardScope` 不变
  （`TestCreateOutsideTransactionUnchanged`、`TestLifecycleCreateOutsideNestUnchanged`）。**更正**：初版把 handler 内调用的生成
  Lifecycle `Create` 也算作“事务外”，这是错的，见文末“复核补修”。

## 对抗性自查

- **Sync 冻结时机与提交屏障**：新实体进入 SyncMutation 的时间点在锁内（CreateInScope 时，或准入前的补 Include），`Admit` 仍在
  `runAfterAdmission` 末尾、锁释放前执行，`Release` 在全部锁释放后、`Confirm` 在提交协议成功后（pipelined 在完成池 ticket 持久后）。
  屏障链 `commitGate` 与参数 / Cast 实体共用同一个 batch，没有新增唤醒路径；Include 在 `admitted` 之后拒绝，不会改动已冻结内容。
- **提交屏障与 pipelined 不确定结果**：ticket 失败走 `abandon`，不 Confirm、不撤销——新实体与已有实体一样停在屏障后，等待 fence/recovery；
  撤销只发生在明确拒绝与回滚，符合“结果不确定≠未提交”。
- **Cast / 组锁 / 引用唯一收尾**：新实体仍只由当前 Guard 解锁一次；撤销不解锁、不 UnTouch，只摘索引，锁在 Guard 统一释放，
  `ReleaseLock` 与 `removing` 清理放在 post-release（与 Destroy 同序），组索引在锁内移除。pipelined 完成池的所有权转移不受影响：
  撤销只在准入之前的拒绝路径发生，准入之后不会再调用 revoke（`commit`/`abandon` 清空回滚函数）。
- **RR-02/03/06/25/26 快阶段约束**：新增代码在快 worker 上只做内存操作与短互斥（`addMu`、Sync Manager 的 `m.mu`/`subj.mu`），
  没有 I/O、没有等待、没有投递快池再同步等；`WakeSync` 为非阻塞。CreateInScope 本就在 handler 内（快池），执行位置不变。
- **回滚一致性（Tracker / EntitySyncDirty）**：新实体的 DAO 快照（含 Tracker）由 `CaptureEntities` 登记，回滚先恢复再撤销；
  `SyncMutation.Finish(false)` 照常丢弃未准入的脏位并标记 discarded，Interest 事实按 discarded 丢弃；已有实体的回滚路径未改。
- **同 ID 顺序**：没有改动准入与派发队列。撤销后同 ID 的后继请求在取锁后看到 removed（`RequireEntity` 返回 false），
  按 RR-25 的首跑规则可能原位转慢池，由 loader 判断是否存在——与该 ID 被驱逐 / 删除时的既有语义相同。
- **撤销与并发访问**：发布到撤销之间，其他 goroutine 可能 `Get` 到新实体并在 `RequireEntity` 上等锁；撤销后它们取锁即看到
  `IsRemoved()` 退出。仍持有指针的读者（未加锁）只能读到一个已 removed 的实例；`ClearBase` 在引用计数为 0 时才清理，
  否则由最后一次 `UnTouch` 清理。
- **订阅者已持有对象的 remove 语义**：提交屏障覆盖了发布到撤销的全过程，正常情况下不会有会话持有被撤销的对象；若业务在别处让它
  外发过（例如同步状态绕过屏障），`Unregister` 语义保证已持有的会话先收到 ObjectRemove，退役完成前同 ID 无法重新登记。

## 未验证项 / 风险

- 真实 WAL group-commit + 真实 Mongo 下的端到端（pipelined 新建实体、断电恢复）未跑；水位用受控 committer 验证。
- 业务自建 Sync Manager（非 Nest 装配的 observer）登记的 subject 不会被自动撤回，需要业务在 `OnDestroy` 注销。
- `CreateInScope` 捕获失败而 handler 吞掉错误继续提交时，新实体已撤销，但已登记的提交参与者可能仍在提交时准备记录——
  与 Cast 捕获失败后继续提交的风险同类，业务应返回该错误。

## 复核补修（2026-09-26）

### 缺口

初版只让 `CreateInScope(当前作用域)` 进入事务。但业务在 handler 内新建实体的正式入口是生成 Lifecycle 的 `Create`
（`codegen/internal/roost/add_workflow.go` 模板：`lifecycle.access.Create(&entity.EntityCreateParam{IsCreate: true, UniqueID: …})`），
以及 `GetOrCreate` 的创建分支（`Get` 未找到 → `Create`）。它们经 `ManagerAccess.Create` → `EntityManager.Create`，后者用
`WithGuardScope` 自建短作用域、创建后立即解锁，完全绕过事务：handler 内调用就是事务内，初版把它归为“事务外”是错的。
仓内没有 `ManagerAccess.GetOrCreate`；生成的 `GetOrCreate` 只在 `Get` 返回“未找到”时才创建（handler 内冷目标 `Get` 得到
`ErrColdLoadInLogic`，原样返回，不会误创建），创建分支同样走 `Create`。

### 自查补充

- handler 内经 `Create` 新建的实体，锁从“创建后立即释放”变为“随事务的 Guard 释放”，这正是事务语义。代价：并发的另一个 handler
  对同一 ID 做 `Create` 时会在 `RequireEntity` 上等锁（Guard / 本地锁属于快池等待的明确豁免），随后 `TryAdd` 得到 `ErrEntityExists`
  （生成 `GetOrCreate` 把它转为 `Get`），若前一事务恰被撤销、收尾尚未完成则得到 `ErrEntityRemoved`，属短暂失败。只有两个事务在同 ID 创建之外还互相等待对方已持有的实体时才会构成环，与 `CreateInScope` 的既有性质相同。
- remote-managed 实体（demo 的 Guild）若在 durable handler 内经 Lifecycle 创建，现在与 Cast 一样返回 `ErrDurableRemoteWriteUnsupported`；
  demo 的 Guild 创建在 `found_guild` 端点、Nest 之外，随后才经 Sender 做受 fence 的写入，不受影响。
