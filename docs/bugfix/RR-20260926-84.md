# RR-20260926-84 修复：消息自己的事务结束后、收尾阶段调用 RunIsolatedTransaction 不再认领消息

问题：[RR-20260926-84](../bug/RR-20260926-84.md)（探针 [REPRO-2026-09-26-08](../bug/REPRO-2026-09-26-08.md) §1 探针 A / A2）。
日期 2026-09-27；实施基线本地 main `9009268`。状态：已修复、本地验证通过，已本地提交，未推送 / 未发布。方向按主记录的修复约束
（沿用维护者 2026-09-27 对 RR-75 的“拒绝”）。codebase-memory 图谱对 `nest/` 已过期（generation 09-26 08:36），结论来自当前源码。

## 根因（基线源码核对）

- `nest/execution.go:134` 以 `msg != nil && !msg.txInFlight` 判定“这是消息自己的事务”，据此认领消息（`owner = msg`、`tx.dispatch = owner`）；
  RR-75 的拒绝（`:101`）也只在 `msg.txInFlight` 时生效。`txInFlight` 由消息自己的事务 `defer` 复位（`:138`）。
- 消息自己的事务返回之后，这条消息仍在当前派发上下文里：`nest/nest_dispatch.go:394` `dispatchLoadedEntities` 的 `defer release()`
  （Guard post-release 回调）、`:204-205` `runNestLogic` 的 `releaseGuardScope` / `msg.runAfterUnlock()`（解锁后回调，Remote 消息的
  `TransactionReleased` 走这里），而 Remote 批次要到 `:76` `finishRemoteWriteBatch` 才收尾。此时 `RunIsolatedTransaction` 见
  `txInFlight == false`，被当成消息自己的事务：
  1. Remote：`:200-207` 替外层 finalize（外层失败时外层没 finalize，批次 `FinalizeLocked` 收到独立事务），`commitDurable` `:281-286` 置
     `remoteCommitted`，外层失败时 `finishRemoteWriteBatch` 仍 `batch.Commit`，回复包 `ErrAfterCommitFailed`；
  2. 纯本地：`commitDurable` `:273-274` 置 `txAdmitted` / `txCommitted`，外层已回滚的消息回复误带 `ErrAfterCommitFailed`；
  3. 结果未知：`tx.dispatch` 非 nil，`:254` 的嵌套分支（RR-65 标记 + RR-76 fence）走不到，而外层 fence 只在 `invokeHandlerTransaction`
     （`:45-47`）里，独立事务不经过它，引擎不 fence。

## 决策与实现

**判据改为入口，不再看时序。** 原 `invokeWithTransaction` 的函数体改名 `runTransaction(claimsMessage bool, …)`；`invokeWithTransaction`
保留原签名，是消息自己的事务入口（`invokeHandlerTransaction` 与包内测试），传 `true`；`RunIsolatedTransaction` 与新建事务的
`RunDetachedTransaction` 传 `false`。`nested := msg != nil && (msg.txInFlight || !claimsMessage)`：

- `nested && msg.RemoteWriteBatch != nil` → 返回 `ErrNestedTransactionInRemoteMessage`（与 RR-75 同一分支，call 不执行，没有建 SyncMutation /
  RollbackTx，批次、`remoteFinalized` / `remoteCommitted` / `remoteIndeterminate` 都不被触碰）。批次收尾后 `RemoteWriteBatch` 已置 nil，
  之后的调用按纯本地处理。
- 只有 `!nested` 才认领消息（`owner = msg`）。收尾阶段的独立事务 `tx.dispatch == nil`，`commitDurable` 里已有的嵌套分支照常生效：
  持久提交（`tx.accepted`）或结果未知 → `markNestedTransactionCommitted`（RR-65：不重排，自己的事务没提交时回复带
  `ErrNestedTransactionCommitted`）；结果未知 → `msg.fenceEngine(err)`（RR-76，返回业务之前 fence）。不改 `txAdmitted` / `txCommitted`。
- `nested` 在 `txInFlight` 时与旧判据完全相同（handler 内的嵌套，包括 handler 内的嵌套派发），RR-49/65/73～76 的路径不变。

### 纯本地消息：选“按不认领消息的嵌套独立事务处理”，不拒绝

- 消息自己的事务已结束，独立事务不认领消息后，它碰不到消息自己事务的任何提交事实，也没有外层快照可覆盖（`tx.enclosing =
  CurrentRollbackTx()` 此时为 nil；外层回滚已在之前完成，独立事务在其后写入，内存与持久一致），拒绝没有正确性上的必要。
- 回复语义已有现成的正确表达：外层失败 + 独立事务已提交 = RR-65 的“部分已提交”（第 4 行），结果未知 = RR-76 的 fence（第 1 行）；
  外层已提交时独立事务是另一笔独立提交，回复照旧。
- `RunIsolatedTransaction` 的契约就是“开独立的持久事务”，在 Nest 派发之外（`msg == nil`）照常执行；收尾阶段本质上已在消息事务之外，
  拒绝会让同一个 API 在“派发里、事务后”这一窄窗口里无端失败，仓内唯一生产调用 `admitLocalEntityDelete`（`dataengine/engine/entity_delete.go:92`）
  若经收尾回调触发删除也会因此失败。
- Remote 必须拒绝，是因为那时批次还开着：本地提交与 Remote 批次的原子性只能随消息自己的事务（RR-75 的同一理由），不是因为事务已结束。

未采用：新增“消息事务已结束”布尔（`txFinished`）并在收尾阶段拒绝 / 不认领——广播派发（`nest_dispatch.go:524`）同一条消息逐实体多次
经过 `invokeHandlerTransaction`，第二个实体的事务会被误判为收尾阶段；按入口判定没有这个问题，也不依赖复位时机。改
`invokeWithTransaction` 签名——包内 10 处测试直接调用它，保留原签名只多一个转发函数。

## 兼容性与迁移

- **行为收紧（Remote）**：带 Remote 批次的消息在 Guard post-release / 解锁后回调里（或消息自己的事务开始之前）调用 `RunIsolatedTransaction`，
  此前会替外层 finalize / 提交批次，现在返回 `ErrNestedTransactionInRemoteMessage`、什么都不做。仓内没有这种调用。
- **行为变化（纯本地）**：收尾阶段调用 `RunIsolatedTransaction`（或无 RollbackTx 时的 `RunDetachedTransaction`）照常执行，但不再认领消息：
  外层失败时回复由误带 `ErrAfterCommitFailed` 改为 `ErrNestedTransactionCommitted` 包外层原因；结果未知时引擎 fence（此前不 fence）。
- 无新导出、无签名 / 配置 / 持久格式变化。性能：只多一个布尔参数与一次比较。

## 对抗性自查

- **不认领、不碰批次**：拒绝在 `runTransaction` 第一步，早于 SyncMutation / RollbackTx / call；`owner` 只在 `!nested` 时赋值，收尾阶段的独立事务
  不写 `txInFlight` / `txNoRollback` / `txAdmitted` / `txCommitted` / `noRollbackHandlerStarted`。
- **不误伤消息自己的事务**：`invokeHandlerTransaction` 仍传 `true`，首次进入时 `txInFlight` 为假，判据与旧实现相同；广播逐实体多次进入仍各自认领。
- **RR-65 / 76 在窗口内成立**：收尾阶段在 `dispatchNest` 组回复之前（`runNestLogic` 的 defer 早于 `dispatchNest` 的 defer），`nestedTxCommitted` 被
  重排判断与回复包装看到；fence 在独立事务返回之前。
- **快池不阻塞**：无新增等待；fence 与 RR-76 同一入口。

## 复核后的补修

日期 2026-09-27；基线 `3d325be`，分支 `fix-r7-extra`。来源：上节 OPEN-ITEMS B19 的边界（[主记录复核残留](../bug/RR-20260926-84.md)）。只改文档与 godoc，不改行为、不新编号。

- 事实（`3d325be` 源码）：`nest/nest_dispatch.go:592` 调 `IRemoteEntityManager.PrepareRemoteWriteBatch`，`:599` 才 `msg.setRemoteWriteBatch(batch)`；
  `nest/execution.go` `runTransaction` 的拒绝条件是 `nested && msg.RemoteWriteBatch != nil`。所以准备执行期间 `RemoteWriteBatch` 为 nil，调用不被拒，
  走 `nested` 且不认领消息的路径——RR-65 的 `nestedTxCommitted` 标记与 RR-76 的 fence 照常生效，批次尚不存在也就碰不到它（上节探针：
  `isoErr=<nil> ran=true isoCommits=1 reply=ok batchCommits=1 aborted=false`，只覆盖外层成功；外层失败 / 结果未知两种按同一路径的源码推断，未另写回归）。

  非 nest 调用方只有 `dataengine/engine/entity_delete.go:92` 与 skill 的 `RunDetachedTransaction`）。是否收紧仍可由维护者另议。
- 改动：
  - `docs/USER_GUIDE.md` §4 判别表第 10 行：列出批次挂上之后的三处（慢阶段准备、handler 内、收尾阶段），注明准备执行期间不在此列；表后说明加一段写清这一窗口按不认领消息的
    嵌套独立事务处理（已提交按第 4 行、结果未知按第 1 行 fence）以及谁可能进入它。“2026-09-26 Remote 收尾链路”一节 RR-75 那句（“带 Remote 批次的消息里不支持嵌套独立事务”）
