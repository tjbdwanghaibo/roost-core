# RR-20261001-04 · v1 manifest 工程遇手写 JSON 的"migrate it explicitly"没有恢复步骤

来源：[RR-20261001-04](../bug/RR-20261001-04.md)（独立复审 §4-D2、§3 实验）。基线 main `2308e37f`。P3（文档 / 可用性）。

## 根因

`tablegen/main.go:389-400`（`153cac3d`，[RR-20260930-09](RR-20260930-09.md)）：v1 manifest 没有归属记录，目录里当前 meta 未认领的 JSON 一律 `untracked table JSON … from legacy manifest: remove or migrate it explicitly`。设计上是故意的，但"migrate"没有对应命令，RR-09 记录 / CHANGELOG / `codegen/docs/CODEGEN_REFERENCE.zh-CN.md` 都只写了"先在 meta 齐全时跑一次生成升级 manifest"和"已删 meta 的遗留 JSON 由维护者清理"，不覆盖**从未被生成器拥有的手写 JSON**——而手写未登记 JSON 保留正是 v2 明确支持的用法。所有 v1.17.2 生成的工程只要 `configs/data` 有手写 JSON，`generate` / `--check` / `project sync` 都失败，用户没有任何地方能查到怎么办。

## 决策与未采用方案

采用：不改行为，把恢复步骤写进错误文本本身与参考文档 §9.1。错误文本现为 `untracked table JSON <path> from legacy manifest (v1 recorded no ownership): delete it if an earlier generation produced it; if it is hand-maintained, move it out of <dir>, run generate once to upgrade _manifest.json to v2, then move it back (codegen/docs/CODEGEN_REFERENCE.zh-CN.md §9)`，保留 `legacy manifest` 子串（既有回归 `TestConvertCSVToJSONRefusesEditedOrLegacyUnownedRetirement` 以它断言）。

评估过的替代方案"v1 → v2 升级时把未认领 JSON 当手写登记保留而不是报错"没有采用：v1 分不清手写数据和早已删 meta 的旧生成物，一律保留等于让升级那一轮把陈旧生成物永久当作手写数据——正是 RR-09 要消除的"旧 JSON 留存"，只是换到了每个 v1 工程的升级时刻；而失败只发生一次、恢复四步、现在错误里就写着。另外 B 线正在活跃改 `codegen/`，RR-09 的失败设计是他们刚做的决定，不在本 RR 范围内推翻。
