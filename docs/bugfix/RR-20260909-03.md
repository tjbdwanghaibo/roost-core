# RR-20260909-03：Assembly 停机未完成就忘掉 Runtime，重试虚报成功

**仓库 / 位置**：roost-core `dataengine/engine/assembly.go` `Shutdown`、`runtime.go` `Runtime.Shutdown`。
**修复单元**：U-0159（C8）。**定位文档**：TROUBLESHOOTING T-54。

## 问题

`Assembly.Shutdown` 调 `runtime.Shutdown(ctx)` 后不看结果就把 `a.runtime` 置 nil。停机 context 先
到期（outbox worker 还卡在底层 Claim 里）时第一次返回 `context.Canceled`，第二次用新 context 重试看到
runtime 为 nil，立刻返回 nil——而 worker 的 `done` 尚未关闭。kit `dataengine.Mod.StopWithContext`
直接转发到这里，调用方据"成功"释放 Mongo / JetStream 连接就会拔掉活 worker 脚下的资源。

## 根因

"开始停"与"停完了"没有区分：引用的释放和停机的完成绑在了一起。

## 方案选择

- 只改 Assembly：`err != nil` 就保留 runtime。不够——`Runtime.Shutdown` 重入会再 `Flush` 已关闭的
  projector（`wal.Sync` 报错），重试永远失败，runtime 永远释放不了。
- **Assembly 只在成功时释放 + Runtime 记住已停组件（采用）**：`Runtime.Shutdown` 加互斥与
  `projectorClosed` / `outboxClosed` 两位标记，组件的 `Close` 返回 nil 才置位，重试只等未停的。
  projector 的 flush 只在它还没关时尝试一次：关掉之后没有可 flush 的，没来得及可见的记录留在 WAL
  下次启动重放（这本来就是停机注释写明的语义）。
- 显式 stopping / stopped 状态机：多一个公开状态和一组查询方法，本轮不需要。

## 改动

- `assembly.go`：`if err := runtime.Shutdown(ctx); err != nil { return err }` 之后才置 nil；注释改写。
- `runtime.go`：`Shutdown` 展开为 `Flush` + `Close`（与原 `Projector.Shutdown` 等价），加
  `shutdownMu` 与两位完成标记；`unregister*` 的置 nil 也进了互斥。

## 证明

`dataengine/engine/assembly_shutdown_promises_test.go`：真实 `NewOutboxWorker`，存储的 `Claim` 卡住直到
测试放行。已取消 ctx 的第一次 Shutdown 报 `context.Canceled` 且 `Runtime()` 仍是原 runtime；20ms 限时
重试仍报错仍保留；放行 worker 后重试返回 nil、`done` 已关、`Runtime()` 为 nil；再调一次幂等。

修前：`Runtime() = <nil> after an incomplete shutdown, want the still-running runtime`。修后
engine 含 `-race` 全绿，kit `dataengine` 全绿。

## 未做 / 边界

- 只构造了仅含 Outbox 的 Runtime，未跑完整 Mongo / JetStream 的 `Assembly.Start` → 超时停机。
- flush 失败但 close 成功的第一次 Shutdown 会报错一次，第二次返回 nil——这是"已停下"的正确答案，
  flush 的错误不会被吞（第一次已返回）。
