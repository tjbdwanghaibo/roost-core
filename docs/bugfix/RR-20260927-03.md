## 决策

### A03：`register_game_server`

`codegen/internal/roost/render_dev_run.go` 的 `register_game_server` 从 `config.account.yaml` 的 `redis:` 段再读两项，一起传给 `accountctl`：

- `db`：同 `addr` 的 awk 写法（只在 `redis:` 段内，遇到下一个顶层键即停），缺省 `0`；
- `password`：取 `password:` 之后的整行（密码可以含空格），去掉一层成对的双引号或单引号；生成配置的 `password: ""` 得到空串。

调用变为 `accountctl -redis <addr> -redis-password <password> -redis-db <db> -prefix <key_prefix> upsert-server -sid <SID>`。
`-redis-password ""` 与 accountctl 默认值相同，所以总是传、不分支。

### A04：计数键

`demo/internal/service/account/collaborators.go.tmpl`：

- 计数键 = `<account.key_prefix>:player_id`（`playerIDCounterKey(prefix)`，与 account 服务的 `:acct:` / `:role:` / `:srv:` / `:slot:` / `:names` 同一前缀、同一分隔写法）。
  前缀在 `BindRegistry` 里用 `mods.KeyPrefix(registry.Config(), "account")` 读取——与 account Mod `Init` 读的是同一个键、同一套校验；配置缺失时绑定失败并说明原因。
- **兼容读法**：旧键 `roost:demo:player_id` 改名为 `legacyPlayerIDCounterKey`，只读。每个进程第一次分配前（`carryLegacyCounter`，互斥 + 完成标记，失败则下次分配重试）
  `GET` 旧键，有值就 `SETNX <新键> <旧值>`；新键已存在（本部署已升级过，或别的副本刚种下）时 `SETNX` 不生效。之后只在新键上 `INCR`。
  于是升级后发出的第一个 id 是“旧计数 + 1”，升级前发出的 id 不会再发。旧键不写不删。
- 原注释“故意不派生，免得改前缀后计数器归零”改写：账号、角色、服务器登记本来就都在前缀下，改前缀而保留数据时必须整体迁移旧前缀下的键，计数器现在和它们在一起；
  放在前缀外只换来“多部署共用一个计数器、按前缀清理漏掉它”。

未采用：Lua 脚本在一次 `EVAL` 里“新键不存在就从旧键复制再 INCR”（两个键在 Redis Cluster 下通常不在同一 slot，会 `CROSSSLOT`；而每个进程在自己第一次 `INCR` 前先种子已经足够，
同一时刻不会有新版本进程在种子之前计数）；升级时删除 / 改名旧键（写别人的数据，且多份部署共用旧键时删掉会让尚未升级的那份从头数）。

## 兼容性与迁移

- **run.sh**：生成文件，`project sync` 后生效；db 0 且无密码的开发配置行为不变。
- **已部署 demo 的键名会变**：计数器从 `roost:demo:player_id` 变为 `<account.key_prefix>:player_id`（生成配置 `roost:<项目名>:account:player_id`）。
  - 兼容读法自动接续：新键不存在时以旧键的值为起点，不需要手工迁移；旧键保留，所有部署都升级并分配过 id 后可以手工删除。
  - **升级时先停掉全部 account 进程再启动新版本**。新旧版本混跑时，旧进程继续在旧键上 `INCR`，新进程在新键上 `INCR`，两边可能发出同一个 id。
  - 多份部署曾共用旧键：各自升级后都从同一个旧值起步，之后各数各的；不同部署之间 id 重叠是本修复要的隔离，同一部署内不会重复。
  - 改 `account.key_prefix` 而保留 Mongo 数据：要把旧前缀下的全部键（计数器在内）一起迁到新前缀，否则新计数器从 0 起步会撞上已有玩家；这与账号库本身的迁移是同一件事。
- `collaborators.go` 是应用自有文件（demo 只写一次），**已生成的 demo 工程不会被 sync 改写**；要用新行为需按本记录手工改或重新生成。
- 无框架 / kit API 变化。
