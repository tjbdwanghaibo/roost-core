# RR-20260926-64 修复：不能回滚的 handler 内新建实体遇锁冲突时返回可判别错误，不再整条重排

问题：[RR-20260926-64](../bug/RR-20260926-64.md)（探针 [REPRO-2026-09-26-06](../bug/REPRO-2026-09-26-06.md) §1 P-B）。
日期 2026-09-27；实施基线本地 main `2373e21`（未推送）。状态：已修复、本地验证通过，已本地提交，未推送 / 未发布。
方向按维护者 2026-09-27 批准的修复约束：无回滚的 handler 内新建实体遇冲突时，把可 `errors.Is` 的锁冲突错误返回给调用方，消息不自动
重执行；锁序允许时仍有序等待；可回滚事务保持 RR-48 的“整条回滚后重排”。

## 根因（基线源码核对）

- `entity/entity_guard.go` `lockCreated`：handler 内新建实体按锁序不能等待时只 try-lock，被占用时调用 capturer 的 `CreatedEntityLockBusy`。
- `nest/rollback.go` `memoryHandlerCreates.CreatedEntityLockBusy` 与 `RollbackTx.CreatedEntityLockBusy` 都返回
  `createdEntityLockBusy(id)`——包着 `ErrLockTimeout`。
- `nest/execution.go`：RR-48 的“强制并入冲突错误并回滚”只对 `policy != RollbackNone` 生效（有意：none 不撤销修改）；memory 快路径
  根本不走 RollbackTx。
- `nest/nest_dispatch.go`：memory 快路径失败时 `txAdmitted` 未置位，`transactionPastCommitPoint` 为假，`requeueTransientDispatch`
  见 `ErrLockTimeout` 就克隆重排（5ms × 至多 400 次）。每次重排 handler 都从头执行，冲突前已做且不撤销的内存修改重复生效。
- 附带核对：`validateHandlerMeta` 拒绝 `RollbackNone` 与非 memory 持久级别组合（`ErrRollbackUnsupported`），所以不能回滚的本地
  handler 只有 memory 快路径；探针里的 `none_strict` 子用例在注册时即 panic，不是可达配置。`RollbackTx` 的 policy 为 none 只出现在
  带 Remote 批次的 memory handler。

## 决策与实现

- 新哨兵 `nest.ErrCreatedEntityLockConflict`（`nest/nest.go`）：handler 内新建实体的锁按锁序不能等待且被占用。**两种事务都带它**，
  区别在是否同时带 `ErrLockTimeout`：
  - 可回滚（本事务 state / undo，且所属消息自己的事务也可回滚）：`nest: lock timeout: nest: created entity is locked by another holder: entity <id> cannot be waited for in lock order`，
    RR-48 语义不变（回滚后重排）；
  - 不能回滚（memory 快路径，或本事务 / 外层消息事务是 RollbackNone）：不带 `ErrLockTimeout`，文本说明“handler 不能回滚、消息不重排”。
    选择不带 `ErrLockTimeout`：该哨兵在 Nest 里表示“未执行、可重试 / 已自动重排”，而这里冲突前的修改已经生效，不属于那一类。
- `Msg` 新增 `txNoRollback`（认领自身事务时按 `meta.Rollback == RollbackNone` 置位）与 `createLockConflictNoRollback`
  （不能回滚时的冲突在当前派发消息上置位，`markCreateLockConflictWithoutRollback`）。`RollbackTx.CreatedEntityLockBusy` 同时看
  外层消息：嵌套的 `RunIsolatedTransaction` 自己可回滚，但外层 memory 消息不能，重排外层同样会重复外层修改，所以按“不能回滚”给错误。
- `Msg.requeueAllowed(err)` = `!transactionPastCommitPoint(err) && !createLockConflictNoRollback`，`dispatchNest` 用它代替原判断，
  两个重排函数（组迁移待定、暂时性锁错误）都不再对这类消息生效。
- 冲突发生后业务改返回别的可重排错误（例如嵌套派发的 `ErrLockTimeout`）时，回复补上 `ErrCreatedEntityLockConflict`
  （`isRequeueableDispatchError`），调用方仍能判别“框架没有重排、修改未回滚”；与重排无关的普通业务错误原样回复。
- 锁序允许（新实体锁组高于已持有的全部锁组）时的有序等待未改。

未采用：让不能回滚的 handler 也强制失败并重排（约束明确“不重排”）；只改错误类型、不在 Msg 上记状态——业务换错误回复时仍会被重排。

## 兼容性 / 行为变化

- memory handler 内新建实体冲突：此前重排直到成功 / 已存在 / 400 次后锁超时；现在只执行一次，回复 `ErrCreatedEntityLockConflict`
  （不带 `ErrLockTimeout`）。依赖“memory handler 返回冲突就自动重试”的业务需要自己重试（先确认 handler 幂等）。
- 可回滚事务：冲突错误多带 `ErrCreatedEntityLockConflict`，仍满足 `errors.Is(ErrLockTimeout)`、仍整条回滚后重排；错误文本变为
  `nest: lock timeout: nest: created entity is locked by another holder: entity <id> cannot be waited for in lock order`。按文本匹配的调用方需改用 `errors.Is`。
- 新导出：`nest.ErrCreatedEntityLockConflict`。无删除 / 改签名，无配置、持久格式变化。

## 对抗性自查

- **已提交内容不被重复执行**：本次只减少重排——多了一个“不重排”条件，没有新增重排路径。memory 快路径冲突时 handler 返回错误，
  `Admit` 不执行，SyncMutation 按未准入丢弃；消息只回复一次。pipelined / strict 可回滚事务的冲突发生在准入之前，回滚后重排的
  是未越过提交点的消息（RR-49 判据不变）。
- **RR-48 死锁不回来**：`lockCreated` 未改：不满足锁序仍只 try-lock，满足锁序仍有序等待；memory handler 冲突后立即回复，比修前
  （5ms 重排循环）更快释放快 worker。`TestHandlerCreateCrossOrderResolvesWithoutDeadlock` 等在 `-race -count=50` 下通过。
- **RR-35 提交边界**：捕获 / Include / 撤销发布未改；memory handler 冲突时本来就不发布新实体（try-lock 失败在 `TryAdd` 之前）。
- **错误可判别**：可回滚 = `ErrCreatedEntityLockConflict` + `ErrLockTimeout`（未提交、已回滚、框架已重排，调用方看到它意味着 400 次仍冲突）；
  不能回滚 = 只有 `ErrCreatedEntityLockConflict`（未提交、未回滚、未重排）；二者都不带 `ErrAfterCommitFailed`。
- **快池不阻塞**：只增加布尔字段读写与冲突路径上的一次 goroutine 局部查表（`currentNestDispatchMsg`）。
- **嵌套事务**：外层 memory 消息里的 `RunIsolatedTransaction` 冲突时，嵌套事务自己回滚（RR-48 强制并入），外层按不能回滚处理、不重排。

## 未验证项 / 风险

- 带 Remote 批次的 memory handler（`RollbackTx` policy 为 none 的唯一形态）内新建实体冲突未单独构造回归；代码路径与 memory 相同
  （`txNoRollback` 由 meta 决定）。
- memory handler 内其他锁超时来源（嵌套派发 try-lock 失败返回的 `ErrLockTimeout`）在没有新建实体冲突时仍按既有语义重排，
  冲突前的内存修改同样会重复——不在本 RR 约束内，未改。
