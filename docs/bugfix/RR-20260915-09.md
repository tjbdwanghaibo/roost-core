# RR-20260915-09:Recover 将过期捕获提交为更新的 Full

**仓库 / 位置**:roost-core `syncstream/syncstream.go`,`Recover`。
**修复单元**:U-0214(C8)。**定位文档**:TROUBLESHOOTING T-108。

## 问题

Recover 在锁外调 provider(设计如此,避免 provider 反向取锁),返回后直接 Append:provider 捕获期间同流有了新的
Full(new),旧捕获被标成 epoch 7 / sequence 2 提交;若期间先 RotateEpoch(8) 再发新包,旧捕获被标成 epoch 8 / sequence 2。
接收者按更高序号应用 Full 时回退到旧内容。

## 根因

捕获与提交之间没有一致性核对(C8:决定要全量时看到的状态与提交时的状态可以不同)。

## 方案选择

- **持锁调 provider。** 注释明确禁止:provider 可能反向取锁或重入 History。
- **调用前观察、提交时核对(采用)。** `observe(key)` 在 RLock 下记 epoch / 流是否存在 / latest;provider 返回后
  `appendIfUnchanged` 在写锁内核对三者一致才 `appendLocked`,否则不写、返回 `ErrRecoverStale`(可重试)。Append 的主体
  抽成 `appendLocked` 供两处共用。

## 改动

`syncstream.go`:`streamObservation` / `observe` / `appendIfUnchanged` / `appendLocked`;`Recover` 改流程;`ErrRecoverStale`。

## 证明

`syncstream/recover_validation_promises_test.go`:same_stream_append / epoch_rotation → 返回错误且未提交、流仍是新内容;
no_change / provider_error / replay_skips_provider 对照。修前红:`stale capture appended after newer state: epoch=7 seq=2 payload="old"`。

## 未做 / 边界

- 只比较 epoch / 存在性 / latest;删除后立刻重建到同一个 latest 的极端交错要靠 U-0215 的序号地板(重建后的 latest 不会回到原值)。
- 业务若在不经 History 追加的情况下改变状态,框架仍无法察觉,宿主需自行协调(审查同样如此界定)。
