# RR-20260913-07:L2 的同版本比较遗漏 schema 与 codec

**仓库 / 位置**:roost-core `remoteentity/snapshot_l2.go`,CAS 脚本。
**修复单元**:U-0176(C8)。**定位文档**:TROUBLESHOOTING T-70。

## 问题

CAS 比较 marker / route / version / checksum,而 checksum 只覆盖 payload 字节。于是同一个版本、
同样的字节,换一个 schema 就被接受了:同一份字节的**解释方式**被悄悄改掉,跨进程解码契约分叉。
本地的 `RemoteSnapshotCache.Publish` 对同样的输入是拒绝的(它比 Schema / Codec / Checksum),
两层规则不一致 —— 这就是 C8。

## 根因

"同版本必须是同一个值"里的"值"被理解成了"字节",而不是"字节加上怎么读这些字节"。

## 方案选择

只有一种修法:把 schema 与 codec 纳入同版本比较。要选的是**存在哪里** ——

- 塞进 checksum 一起算。会改变 checksum 的定义,而 checksum 在 Go 侧还有别的含义。
- **在 hash 里各存一个字段,比较时一并比(采用)**。与本地缓存的三项比较一一对应,读代码时
  两层规则显然是同一条。

## 改动

`remoteentity/snapshot_l2.go`:脚本读写 `schema` / `codec` 两个字段,同版本分支的冲突条件扩成
checksum、schema、codec 任一不同即冲突;`Set` 多传两个 ARGV。

替身 `snapshotRedisFake` 同步改成一样的规则 —— 审查专门提醒过"不要仅修改替身让测试变绿",所以
这里是脚本先改、替身跟着镜像,而不是反过来。

## 证明

`remoteentity/snapshot_l2_cas_promises_test.go` 的
`TestL2RejectsSameVersionWithADifferentSchemaOrCodec`:同版本同字节改 schema、改 codec 各一例,
都必须 `ErrRemoteVersionConflict`,并断言被拒之后存储里的解释方式没有被改动;另外断言完全相同的
重复发布仍被接受、真正更新的版本可以改 schema。

修前红:

```text
same version with a different schema = <nil>, want ErrRemoteVersionConflict
same version with a different codec = <nil>, want ErrRemoteVersionConflict
```

修后 remoteentity 含 `-race` 全绿。
