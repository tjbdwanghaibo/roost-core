# RR-20260910-03:完成事务的等待者可能因缓存淘汰而崩溃

**仓库 / 位置**:roost-core `remoteentity/transaction_manager.go`,`waitRemoteTransaction`
唤醒后的状态读取。**修复单元**:U-0168(C8)。**定位文档**:TROUBLESHOOTING T-62。

## 问题

`FlushRemoteTransaction` 已经取得 `tracker.done` 并在等待;事务完成、`done` 关闭;等待者重新
取得 `txMu` 之前,另一笔事务的准入因容量压力淘汰了刚完成的记录。等待者唤醒后执行
`m.remote.txs[id].status.Clone()`,条目已被删除,对 nil 指针取字段 —— **nil pointer panic**。

而且这一行在 `txMu` 临界区里,后面的 `Unlock` 不会执行:调用方即使 recover,之后所有事务跟踪
都被这把锁挡死。一次读取失败升级成整个 Manager 停摆。

## 根因

两条路径对同一状态用了不同的判据(C8):完成侧 `completeRemoteTransaction` 刚把 tracker 标成
`closed`,而准入侧 `evictOldestClosedRemoteTransactionLocked` 恰好挑"最旧的**已关闭**"记录 ——
刚完成的那条正是最新的已关闭记录,容量为 1 时它就是唯一候选。等待者被唤醒的原因和它的记录被
淘汰的原因是同一件事。

更根本的是:等待者已经持有 tracker 指针,却又回去查 map。Go 的对象生命周期由引用决定,map
删除只是移出索引,对象还在 —— 重新查表把一个不需要存在的失败模式引进来了。

## 方案选择

- **唤醒后判 nil,返回 Unknown。** 审查已经指出不行:丢掉本应返回的终态,调用方拿到"不知道"
  而实际上事务已经提交,这比崩溃更难查。
- **淘汰时跳过有活动等待者的 tracker。** 要在 tracker 上加等待者计数、在 wait 前后增减;而且
  容量压力下可能找不到可淘汰项,于是准入返回 `ErrRemoteOverloaded` —— 把一个读取问题变成准入
  问题。
- **用已持有的 tracker 指针读(采用)**。改动最小,没有新状态,而且顺带把"panic 在临界区导致
  `txMu` 永久占用"这个次生故障一起消掉。淘汰仍然只影响后续的历史查询,这正是它该影响的范围。

## 改动

`remoteentity/transaction_manager.go`:

- 新增 `trackedRemoteTransaction(id) (*remoteTransactionTracker, error)`,做原来
  `trackRemoteTransaction` 的事并把 tracker 返回;`trackRemoteTransaction` 变成
  `_, err := ...` 的包装,所以其它三处调用方与既有测试一行都不用改。
- `waitRemoteTransaction` 全程用这个 tracker:首次读取不再 `m.remote.txs[id]`(那里也有同一个
  窗口),唤醒后读 `tracker.status.Clone()`。仍然在 `txMu` 下读,因为
  `completeRemoteTransaction` 会写 `tracker.status`。

## 证明

`remoteentity/transaction_wait_eviction_promises_test.go`,
`TestTransactionWaitReturnsTheTerminalStatusAfterEviction`。

关键是把调度窗口固定住:`select` 在阻塞之前会**求值所有 channel 操作数**,所以传进去一个
`Done()` 会阻塞的 context,就能把等待者钉在"已经取得 tracker 与 done、还没观察到任何后续
变化"这一刻。这是审查附录用的手法,收进仓库时改名为 `selectEntryBarrier` 并写清原理。
`Done()` 返回 nil,于是 `ctx.Done()` 是永不就绪的分支,select 由事务自己的 done 决定。

屏障之后走真实路径:`completeRemoteTransaction` 关闭 done,`trackRemoteTransaction(second)` 触发
容量淘汰,再断言 `txs[first]` 确实已被淘汰(否则这条测试什么都证明不了),然后放行等待者。
断言:没有 panic、返回 committed、事务 id 正确;最后再起一个 goroutine 调
`trackRemoteTransaction`,若 `txMu` 因临界区 panic 而未释放,这一步会超时。

修前红:

```text
the waiter panicked instead of answering: runtime error: invalid memory address or nil pointer dereference
```

修后 `go test ./remoteentity -race` 绿,core 全仓绿。

## 未做 / 边界

- 本轮实测的是**容量淘汰**。TTL 清理(`pruneRemoteTransactionsLocked`)有同一个源码窗口,而修法
  是同一处,所以一起修好了;没有为 TTL 路径单独写一条测试。
- `RemoteCommitStatus`(历史查询入口)对已淘汰的事务返回"查不到",这是淘汰应有的语义,没有改。
- 这是生命周期竞态,race detector 不一定报告数据竞争;测试靠屏障固定交错,不靠概率。
