# RR-20260930-14：依赖事务提交明确的合仓迁移结果

状态：已修复，迁移/失败/并发/隔离回归、正式 CLI 依赖解析与生成消费者通过；未发版。[原问题](../bug/REVIEW-2026-09-30-codegen-05.md#rr-20260930-14)，修前基线 `4784ef820cab599e0b1321a96a5843af2ab95e58`。

旧 `dependencies.go` 在解析 helper 中迁移 stage，但外层仅接收 go.mod/go.sum。现在把自动 ConsolidateProject 移到事务外层：保存初始应用输入后，在 stage 迁移；按 `ConsolidateResult.Files` 和必要 manifest 规划 syncChange；**在 resolver 调用前冻结这些迁移字节**。get/tidy 成功后另规划最终模块文件，核对 root 应用输入，再经原有 commitSyncChanges 一起提交/回滚。没有新增事务抽象或放宽原有业务所有权。

不采用“提交 stage 全部 Go 文件”的方案，也不在 resolver 后直接复制迁移名单里的文件：两者都可能接收依赖命令的任意改写。正式成功用例故意在 runner 里覆盖已经迁移的 business.go、roost.yaml 和一个未迁移文件；root 最终只接收 runner 前的正确迁移结果，未迁移文件保持。无 consolidation 的既有“只提交模块文件”回归继续通过。公开 UpdateFrameworkDependencies API 不变，内部解析 helper 现在只处理模块。

## 兼容与恢复边界

普通无旧布局的 deps 仍只更新模块文件；旧布局现在连同明确的 Go import/必要 manifest 迁移一起提交，这正是此前日志承诺但未履行的行为。不会改映射之外的业务符号、生产数据或网络协议。自动迁移前建议保存项目；无法自动映射的 API 按诊断手工修正。先前 RR-14 造成半迁移的工程可在本版源码工具上重跑 deps；旧 import 的布局检测会再次触发 consolidation。先前旧模块重新被 tidy 引入的，也在此次迁移中清除。

迁移、解析和并发检查失败发生在原项目提交前；提交阶段复用原逐文件验证/回滚，进程强杀、磁盘失败或回滚自身失败未在本轮验证，不宣称跨这些故障原子。显式 upgrade --consolidate 的根迁移流程不改，本轮现有 dry-run 等回归通过，未运行所有旧版本升级消费者组合。使用说明更新在 `codegen/docs/CODEGEN_REFERENCE.zh-CN.md`，全轮验证见[第六轮](../review/REVIEW-2026-09-30-codegen-06.md)。
