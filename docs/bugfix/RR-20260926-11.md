### 根因（基线行号）

`remoteentity/transaction_tracking.go:103`，`completeRemoteTransaction` 无条件 `tracker.status = status.Clone()`。已 Committed 的事务被投影器
重放、重放的发布步骤（`ApplyRemoteCommits` 的 `MarkRemoteCommitPublished`，`transaction_manager.go:450-452`）失败时，把终态改写成 Indeterminate；
`done` 已关闭，后到的 `waitRemoteTransaction` / `FlushRemoteAll` / `RemoteCommitStatus` 读到的都是“结果未知”。

### 修复

- 新增 `remoteCommitFinal`（`transaction_tracking.go:134`），写明终态：**Committed**（已持久并发布）与 **Rejected**（持久拒绝或确定未提交）。
  Admitted、Applied、Indeterminate、Unknown 是过程态或未知结论，可以被后续持久结论覆盖；Indeterminate 仍会关闭 `done` 唤醒等待方（行为不变）。
- `completeRemoteTransaction`（`transaction_tracking.go:103`）遇到终态直接返回，不改写；与现有终态矛盾的更新只计数
  `remote_entity_transaction_final_overwrite_ignored_total`，保留先到的持久结论。
- 重放调用本身的返回值不变：发布失败仍返回可重试的 `ErrRemotePersistenceIndeterminate`，投影器照常退避重试并最终发布、ack；
  只是不再污染已经确定的 tracker。Published 状态当前没有写入 tracker 的路径，未纳入终态集合。

### 回归

- `TestCommittedTrackerSurvivesFailedReplayPublication`（`remoteentity/replay_outcome_test.go`）：单元级，Committed 后注入一次重放发布失败，
  等待方、`FlushRemoteAll`、`RemoteCommitStatus` 仍得到 Committed；并验证 Indeterminate → Committed 的升级仍然生效。
- `TestCommittedReplayAfterFinalizerAndNewerFenceAcksWAL`（`remoteentity/replay_publication_e2e_test.go`）：端到端，真实 nestwal WAL（V2）+
  `engine.Projector`/`engine.MongoStore` + mongotest 伪 Mongo，Remote 走正式 `Backend` + `MongoCommitter` 权威。脚本化存储按调用序号让竞态确定：
  tx1（async）首次发布标记失败 → finalizer 回源 Applied、抢先发布并释放 gate → 同实体下一写者 `GrantWrite` 拿到更大 fence → 投影器重放旧回执
  不被新 fence 拒绝、不回退活实体 fence（再注入一次发布失败，此时 tracker 必须仍是 Committed）→ 第三次投影成功 ack → 新写者 tx2 经 WAL 正常提交。
  断言 `WALUnacked=0`、`FatalProjectionConflicts=0`、`ProjectionFailures=2`（恰为两次注入，无无限重试）、权威 `_ver=2`、tx1/tx2 持久 Committed、写额度归零。

## 后续验证（2026-09-27，OPEN-ITEMS B44）

来源：[OPEN-ITEMS-2026-09-27](../review/OPEN-ITEMS-2026-09-27.md) B44（批次 7 观察：上面这条 B08 回归无 race 时约 1/100 超时 `:115 timed out waiting for the suffix publication`，
见 [RR-20260926-51 后续验证（B28 门禁）](RR-20260926-51.md)）。基线 `e0d38f7`，分支 `fix-r8-b14`；图谱过期（09-26），以当前源码为准。

- 结论：**用例问题，框架无缺陷**；已修测试（`test(remoteentity)：OPEN-ITEMS B44 …`）。
- 复现：基线上单进程 `-count=1000`（无 race）与 `-cpu=1` / `-cpu=2` 各 500 次都不失败；8 个进程并行各 `-count=250` 时 3/2000 超时，20 个进程并行各 300 次再现 3 次。
- 根因（插桩副本定位，插桩未提交）：在 `ReplayPass` 里记下每轮读到的记录。失败的每一次都有一轮只读到 tx1（`records=[…83] segments=1 window=1 replayErr=<nil>`）。
  - 一轮回放在 `nestwal.WAL.Replay` 开头就定下本轮读到的 WAL 末尾（`activeLimit`）。后台回放若在 tx2 追加**之前**开始，扫到 tx1 时 tx1 恰好已被释放（负载下扫描慢），
    这一轮就只有 tx1，按串行段投影。
  - 用例的注入存储让前缀 tx1 的第一次发布标记等后缀 tx2 发布成功。tx2 要等下一轮才开始，于是 10s 超时。
  - 投影器的行为是对的：一轮只投影它开始时已在 WAL 里、且已释放的连续前缀，后来的记录由下一轮处理。用例原注释“投影器第一次读到时两条同在一个窗口”没有被保证。
- 修法（只改测试）：两笔都 `prepare`（追加、仍 held）之后、释放之前，同步调用一次 `projector.ReplayPass(ctx)` 并断言它投影 0 条。
  - 回放之间由 `replayGate` 串行，这次调用返回就说明更早开始的回放都已结束（它们都在 held 的 tx1 前停下）。此后每一轮开始时 WAL 末尾都已包含 tx2。
  - tx1 在 WAL 里靠前且最后释放，所以第一轮能投影任何东西的回放必然同时带上 tx1、tx2，进入同一个并行窗口。
  - 这一步不改变断言与计数（`Projected=3`、`ProjectionFailures=1` 不变）。
- 验证：
  - 插桩副本加同样的修法，20 个进程并行各 300 次（6000 次），没有出现只含 tx1 的回放、没有失败。
  - 修后正式用例：单进程 `-count=1000` → `PASS`；20 个进程并行各 300 次 → 全部 `PASS`（基线同样负载下 3 次超时）。
  - `GOWORK=off go test -race -count=50 -run TestParallelWindowReplaysSucceededSuffixUnderNewerFence ./remoteentity/` → `ok`；`GOWORK=off go test -race -count=20 ./remoteentity/` → `ok`（266.4s）；`go vet ./remoteentity/` 与 `gofmt -l` 通过。
