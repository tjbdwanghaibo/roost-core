# RR-20261006-10 修复：驱动与 Mod 的 Close 统一口径；文档相对链接门禁

问题：[RR-20261006-10](../bug/RR-20261006-10.md)（来源 [WANTED W-2026-10-06-02](../bug/WANTED.md)）。基线 `ba13cb05`，未发版。同批顺带：`skill/README.md` 合仓遗留的失效链接与根包文档链接门禁（见末节）。

## 统一后的口径

1. **重复 Close 幂等，返回 nil；第一次的错误只报给第一次调用。**
2. **并发 Close 串行**：后到者等第一个做完再按状态返回（已关闭就是 nil）；会阻塞的 Close（mongo、nats、带 ctx 的 Mod Stop）里，后到者的等待受它**自己的 ctx** 约束，ctx 先结束返回 ctx 错误、对象状态不变、可以再调用。
3. **Close 之后的其他调用返回该驱动的已关闭错误**，可 `errors.Is`：redis `goredis.ErrClosed`、mongo `mongo.ErrClientDisconnected`、etcd `fetcd.ErrClosed`、nats `fnats.ErrClosed`。

考虑过的另一种口径是“粘滞返回第一次的结果”（etcd Client、单实例锁 store 原来的做法）：调用方每次都能看到第一次的失败。没采用：第一次之后已经没有可以重试的资源（go-redis 遇错照样关完连接池，clientv3 第二次 Close 只会得到 `context.Canceled`），粘滞的错误让停机重试永远不收敛，违反三步停机“已停完的对象再调用返回 nil”；第一次的错误已经报给了做关闭的那次调用，日志里有。

**仍是例外、不改的**：nats `Assembly.Close` 第一次排空失败返回的 `ErrClosedUndrained`（RR-20261004-08，有意的终态错误，NatsMod 据此交出连接）照旧报给那一次调用，只是之后的 Close 改为 nil；等 RPC 回调超时返回 ctx 错误、保留所有权（可以再调用）也照旧。etcd 内部的 `campaignSession.Close` 粘滞返回第一次结果、由 `closeError()` 读回，是选举内部状态，不是对外的 Close，不改。`serviceWatcher` / `watcher` / `localMirror` / `mirrorSubscription` 的 Close 本来就幂等返回 nil。

## 改动

| 位置 | 改动 |
| --- | --- |
| `redis/driver/client.go` `Client.Close` | `sync.Once` 只关一次，错误只报给第一次（`Assembly.Close` 转发，同样生效）。单机与 Cluster 一致 |
| `redis/driver/lock.go` | Acquire / Release / Extend 遇到 `goredis.ErrClosed` 直接返回、锁状态不变：命令确定没发出去（`sendOnce` 只在“确定未执行”时重发，最终错误是 ErrClosed 说明每次都没发出），不记成结果未知 |
| `mongo/driver/client.go` `Client.Close` | `operation.Serial` 串行化 + `closed` 标记；断开失败（FLE）不置标记，下次重做断开。新增未导出字段 `disconnect` 只供测试控制断开耗时 |
| `etcd/driver/client.go` | `Close` 只关一次、错误只报给第一次；Close 开始时置 `closed`，Get / GetPrefixSnapshot（GetWithPrefix 经它）/ Put / PutWithLease / Delete / DeleteWithPrefix / Txn / Grant / KeepAlive / Revoke 先查它，返回 `fetcd.ErrClosed`。Watch / WatchPrefix 不需要：关闭后的 watcher 立即结束、`WatchError` 为 `fetcd.ErrWatchClosed`（实测） |
| `nats/driver/assembly.go` `Assembly.Close` | `operation.Serial` 串行化；连接关闭（排空完成或被硬关）后置 `closed`，之后返回 nil |
| `nats/driver/client.go` `Publish` | 连接已关闭 / 正在排空时立即返回，错误同时 `errors.Is` 到 `fnats.ErrClosed` 与 gonats 原错误，不再空等 3 × 20ms |
| `kit/redis/singleton.go` `singletonStore.Close` | 错误只报给第一次，之后 nil |
| `kit/redis/redis_mod.go` | `mu` 保护 `asm`：Stop 持锁串行（go-redis Close 不等在途命令，持锁很短），健康检查经 `assembly()` 读 |
| `kit/mongo/mongo_mod.go` | Stop 用 `operation.Serial` 串行（会阻塞到 ctx），`mu` 保护 `client`，健康检查与 `Client()` 经锁读 |
| `kit/nats/nats_mod.go` | Stop 用 `operation.Serial` 串行，`mu` 保护健康检查读的 `asm`。用户点名的是 Redis / Mongo Mod，NatsMod 同类（同样的数据竞争），一并统一 |
| `internal/operation/serial.go`（新） | `Serial`：零值可用的停止入口串行器，`Lock(ctx)` 等待受调用方 ctx 约束。用 `sync.Mutex` 时后到者的等待不受自己的 ctx 约束，第一个调用者用 Background 等一个不结束的排空时会跟着永远等，在途 RPC 回调里用可取消 ctx 再次停止也会卡在锁上（nats RPC 的重入约定） |
| `kit/redis/stop_retry_promises_test.go` | NC-233 用例原来靠“再调一次驱动 Close 得到 ErrClosed”制造 Close 错误，驱动幂等后改为先关底层 `Raw()` 连接池 |

未采用：mongo 并发 Close 用 `sync.Mutex`（同上，等待不受后到者 ctx 约束）；etcd 把每次调用的 ctx 与客户端 ctx 合并来同时打断“与 Close 并发的在途调用”——每次调用多一次 `WithCancel` + `AfterFunc`，而契约只要求 Close 之后发起的调用快速失败，在途调用仍受调用方 ctx 约束（停机顺序由调用方负责）；DistLock 把全部 `IsDefinitelyNotExecuted` 错误都当“状态不变”——范围超出 Close，池超时等错误下的锁状态语义另议，这里只处理 ErrClosed。

## 兼容

行为变化（CHANGELOG 已写）：

- **单机 redis 重复 Close 不再返回 `ErrClosed`**，返回 nil（与 Cluster 一致）；并发 Close 的后到者不再立刻拿到 `ErrClosed`。依赖“第二次 Close 报错”判断已关闭的调用方改用 `errors.Is(<命令错误>, goredis.ErrClosed)`。仓内唯一依赖它的是 NC-233 用例，已改。
- kit 单实例锁 store（Redis）与 etcd Client：第一次 Close 出错后，再调返回 nil（原来每次返回同一个错误）。
- etcd Client 关闭后的调用立即返回 `fetcd.ErrClosed`（原来阻塞到调用方截止时间）。`Discovery` / 选举经 `Raw()` 直接用 clientv3，不在此列。
- nats `Assembly.Close`：终态错误之后的 Close 返回 nil；`Publish` 关闭后的错误多了 `fnats.ErrClosed`、不再等重试。
- redis 锁：客户端关闭后 Acquire 每次都返回 `goredis.ErrClosed`（原来第二次起是 `ErrDistLockStateUncertain`）。
- mongo / nats / Mod 的并发 Close：后到者现在等第一个做完，最长等到自己的 ctx 结束。App 停机路径每个 Mod 只串行调一次，不受影响。
