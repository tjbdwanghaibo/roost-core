# RR-20260926-85 修复：释放通知带戳，Direct 只删除通知所指那一次生命期里的绑定

问题：[RR-20260926-85](../bug/RR-20260926-85.md)（复现 [REPRO-2026-09-26-08 §2](../bug/REPRO-2026-09-26-08.md#2-rr-85rr-79-释放通知删掉重开后新做随即被撤销的-direct-绑定探针-fsyncentitysyncpolicy-包)）。

## 根因（基线行号）

RR-79 的释放通知是异步的：`dropSession`（`sync/entitysync/subscriptions.go:186`）/ `Unregister`（`manager.go:442`）排下通知，下一次 Flush 的
政策阶段才交给 `Direct.released`。通知只有（会话, subject），不说明它指的是哪一次会话打开、哪一次登记；`Direct` 用
`policy/direct.go:93` 的 `Holds` 当前值判定“通知途中是否已重新绑定”。`Holds`（`subscriptions.go:297`）在 subject 退役时返回假（`:309`），
subject 被忘掉后也返回假（`:304`）。于是同一 Flush 周期内“关闭 → 重开 → 重新 Bind → RR-59 撤销”（或“注销 → 重新登记 → 重新 Bind → 撤销”）之后，
旧通知把新绑定当成已死：`:96` 删除绑定，`:97` `Unsubscribe` 走到 `subscriptions.go:402-405`（subject 已忘掉）或 `:422-423`（退役中、来源已被
`retireLocked` 清空），`dropRetracted` 删掉 RR-70 为新绑定保留的撤销记录；实体重新登记后没有记录可交还，7 再也看不到 8。

## 修复（按 RR 主记录的修复约束）

判定改成比较“这对绑定是何时做的”与“这次释放是何时发生的”，两者读同一个逻辑时钟：

- `sync/entitysync/policy_queue.go`：新导出 `SubscriptionStamp`（`Manager.stampClock` 原子计数的读数，单调、从不相等）；`ReleasedSubscription`
  增加 `Stamp`。`releasedLocked` / `releasedRecordsLocked` / `releasedRecordsOfSession` / `dropRetractedSubject` 把本次释放的戳写进每条通知（活订阅
  与 RR-70 记录两部分同一个戳）。`SubscriptionSourceHooks.Released` 注释改为按戳判定，并写明不要用 `Holds`。
- `sync/entitysync/subscriptions.go`：
  - `dropSession` 在删除会话的同一把 `m.mu` 内取释放戳。这一次打开里的订阅都在 `m.mu` 内确认生命期后取戳，所以都更小；同 ID 重开必须等
    `m.mu` 放开，新生命期里的订阅戳都更大。
  - 新导出 `SubscriptionSource.SubscribeStamped`：与 `Subscribe` 相同，成功时返回在持有 `subj.mu` 与 `m.mu`、生命期 / 退役检查通过之后取得的戳
    （同视图的重复订阅也返回新戳）。`Subscribe` / `Manager.Subscribe` 委托它，行为不变。`Holds` 注释写明它只是当前值。
- `sync/entitysync/manager.go`：`Unregister` 在退役 subject 的同一把 `subj.mu` 内取释放戳。本 subject 上的订阅都在这把锁内取戳；新登记在 forget
  之后才出现，其上的订阅戳都更大。
- `sync/entitysync/policy/direct.go`：绑定表的值改为 `{profile, stamp}`；`Bind` 与重新提交（`resubmit` 的 Subscribe 成功时）用 `SubscribeStamped`
  更新戳；`released` 只删除 `stamp < pair.Stamp` 的绑定，不再调用 `Holds`。

为什么戳早于通知的绑定一定已死、删除时的 `Unsubscribe` 不会误删新东西：本来源的订阅只在 `d.mu` 下经 `Bind` / `resubmit` 产生，成功就刷新戳；
戳早于释放，说明本来源在这次释放之后没有再成功订阅这对 pair，它的订阅属于被释放的那次打开 / 登记（或更早、同样已被释放的），RR-70 记录也只能
来自这些订阅，`Unsubscribe` 清掉的正是这次释放留下的记录。戳晚于释放的绑定是新生命期 / 新登记上做的，无论此刻是活订阅、被撤销的退役 subject、
已忘掉等重载，还是已排队等重新提交，都保留，记录不动。

约束逐条：释放只删除它所指那次生命期的绑定（戳划界）；重开后新做、随后被撤销的绑定与其 RR-70 记录保留（回归两支）；判定不看 `Holds`；
锁序不变（只新增一次原子加，在既有临界区内完成，不取新锁）；通知仍在政策阶段交付，不在调用方路径上回调，不起 goroutine；RR-78 的记录移回 /
复制与 RR-79 的通知点、交付顺序都未改。

未采用：
- 通知携带会话 lifetime 指针 / subject 指针、`Direct` 按相等比较：`Direct` 要在 `Bind` 时原子地拿到生命期与登记两个身份，且重新提交后 subject 身份
  会变，需要同时维护两个维度；单调戳一个维度就同时覆盖会话关闭与业务注销两种释放。
- `Holds` 扩展为“活订阅或本生命期的撤销记录”：要给 RR-70 记录加生命期字段并改 RR-78 的去重键，还会改变 RR-79 回归断言的 `Holds` 语义。
- 新的订阅成功时由 Manager 取消同 pair 排队中的旧通知：`dropSession` 放开 `m.mu` 后才排通知，重开并订阅可能先于排队，仍有窗口；政策阶段已取出、
  等 `d.mu` 的通知也取消不到。
- `Bind` 之后另行查询生命期：与 `Subscribe` 不在同一临界区，关闭重开夹在中间时会记错代际（误删或泄漏）。

## 兼容性与迁移

- 新增导出：`entitysync.SubscriptionStamp`、`SubscriptionSource.SubscribeStamped`、`ReleasedSubscription.Stamp`。
- 源码兼容性：`ReleasedSubscription` 多了一个字段，仓外若用位置式字面量 `ReleasedSubscription{s, id}` 构造需改为带字段名；直接 `==` 比较通知值
  会把戳也比进去。仓内（含 kit、codegen、模板）除上述测试外没有使用者。
- 行为变化（收紧）：`policy.Direct` 收到释放通知时只删除该次会话打开 / 登记内做的绑定。通知途中重新 Bind 的绑定此前在“未被撤销”时已保留（RR-79），
  现在“随后被 RR-59 撤销”时也保留并在实体重新登记后恢复。自建政策若按 RR-79 文档用 `Holds` 判定，同样有本问题，应改用戳。
- `Holds` 行为不变。无配置、协议、持久格式变化。开销：每次订阅成功、每次会话关闭 / 业务注销多一次原子加。
