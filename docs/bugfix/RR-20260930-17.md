## 根因

见问题记录。要点：生成的 CI 与 `make compose-check` 只跑 `docker compose config --quiet`，只校验语法；结构（例如 tmpfs 被拆成四条挂载）没有人断言。

## 决策

- **go test，不是 shell 脚本。** 生成工程本来就有 Go 工具链与 `go test ./...`；解析 `docker compose config --format json` 用 `encoding/json` 即可，不需要 jq、yq，也不需要 `gopkg.in/yaml.v3`（它在生成工程的 go.mod 里只是 indirect，直接 import 会让 CI 的“module files are tidy”步骤红，旧工程 sync 之后还得手工 tidy）。
- **只在 `ROOST_COMPOSE_CHECK` 设置时执行，设置时没有 docker 就是失败。** 没设置时 `t.Skip`：`go test ./...`（quality 作业的 ubuntu / windows 矩阵，以及没有 docker 的开发机）不被挡住；`make compose-check` 与 CI 的 generated-and-deployment 作业设置它，那里 docker 是硬要求，缺 docker 不是 skip 而是 fail，检查不会静默消失。没有用 build tag：tag 会让 `go vet ./...` 与 quality 作业根本不编译这个文件，编译错误要到部署作业才暴露。
- **文件放在 `deploy/docker/`**，与它检查的 compose 同目录，`package docker`（只有测试文件的包，`go build ./...` 不碰它，`go vet` / `go test` 会编译它）。走 `renderProject` 的 `addGo`（gofmt 后写入）、`Owned: true`，`project sync` 对旧工程会新建它、以后随生成器更新（`canOverwriteGenerated` 对 `deploy/docker/` 前缀放行）。
- **断言的字段**（每个 Service）：`read_only`、`user: 65532:65532`、`cap_drop == [ALL]`、`security_opt == [no-new-privileges:true]`（RR-33 记录点名的两个 flow 序列）、tmpfs 恰好一条、以 `/` 开头且等于 `/tmp:rw,noexec,nosuid,size=64m`（RR-33 本体）、`stop_grace_period` 是正的 duration（RR-26-66 的停机预算）、`healthcheck.test` 是 `[CMD /app/healthprobe …]`（deploy.sh 等的 readiness）、恰好一个 `bind` 且目标是 `/etc/roost/config.yaml`、只读、源文件名 `config.<service>.yaml`（RR-33 记录点名的 config 挂载，也是 `TestProductionComposeMountsTheConfigAsAnExplicitBind` 守的“别当成命名卷”）、每个 `volume` 挂载在顶层 `volumes` 里有声明且不是只读（RR-28-04 的 `<app>-<service>-log`、WAL 卷）、目标都是绝对路径且不重复。ROOST_IMAGE / ROOST_CONFIG_ROOT 由测试自己给占位值（`config` 不要求 bind 源存在），不依赖运行环境。
- 没有采用“CI 里 `compose up`”：维护者明确排除；它需要镜像与真实依赖。

## 文件与行为

- `codegen/internal/roost/render_deploy.go`：`composeCheckEnv` 常量、`renderComposeCheckTest`（生成的测试源码，标准库 only）；`renderDockerReadme` 多一段说明 `make compose-check` 现在跑什么、开关是什么。
- `codegen/internal/roost/render.go`：`renderProject` 经 `addGo` 加入 `deploy/docker/compose_check_test.go`；`Makefile` `compose-check` 在 `config --quiet` 之后加 `ROOST_COMPOSE_CHECK=1 go test -count=1 ./deploy/docker/`；CI generated-and-deployment 作业在 “production compose renders” 之后加一步 “production compose resolves to the shape the deployment relies on”（`env: ROOST_COMPOSE_CHECK: "1"`，`go test -count=1 ./deploy/docker/`）。
- `codegen/internal/roost/compose_shape_check_promises_test.go`：
  - `TestGeneratedProjectCarriesAComposeShapeCheckAndRunsItInCI`：plan 里有这个文件、generator-owned、能解析、`package docker`、含开关与 `docker compose config --format json`；CI 在 `config --quiet` 之后带开关跑它；Makefile `compose-check` 跑它。
  - `TestGeneratedComposeShapeCheckCatchesTheTmpfsShapeComposeUpRefuses`：把生成的测试与生成的 compose 放进一个只有 go.mod 的临时模块，带开关 `go test`：生成的 compose 绿；tmpfs 改回 RR-33 的 `[/tmp:rw,noexec,nosuid,size=64m]` 时红且输出含 `tmpfs resolved to 4 mounts`。本机没有 docker 时 skip（说明写在 skip 文本里）。

## 兼容性

- 生成工程多一个受控文件 `deploy/docker/compose_check_test.go`，`project sync` 新建；`Makefile` 与 `.github/workflows/ci.yml` 是受控文件，sync 即更新。go.mod 不变。
- 需要带 compose 插件的 docker（`docker compose config --format json`，Compose v2）。generated-and-deployment 作业本来就要 docker（`docker build`、kubeconform）。
- 生成工程的 CI 在 `deploy/docker/*.go` 上多跑 `go vet` / glsvet（glsvet 默认跳过测试文件）。
