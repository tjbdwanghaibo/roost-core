# RR-20260926-40：scene 的断线处理按 Join 代际复查，旧连接推送失败不再移出已重连玩家

问题：[原始记录](../bug/RR-20260926-40.md)（复现 [REPRO-2026-09-26-04 §7](../bug/REPRO-2026-09-26-04.md)）。日期 2026-09-26。
实施基线：main `49f20ee`（RR-20260926-36 修复提交之上）。状态：已修复，适用本地验证通过，已本地提交，未推送/发布。

## 根因（复核）

生成传输 `pushPlayer` 向玩家的全部连接推送、任一失败整体报错；entitysync 因此关闭该玩家的复制会话并回调 `SessionLost`。
demo `scene.go.tmpl` 的 `sessionLost` → `dropAsync` → `Leave` 不看 `ActiveSessions`，于是重连窗口里旧连接写失败就把已经通过新连接
重新 Join 的玩家移出兴趣集、注销 subject（其他人收到 ObjectRemove）、关闭会话。`watchSessions` 在事件时刻查 `ActiveSessions` 后异步 `Leave`，
执行时不再复查——期间玩家重新登录也会被移出。Join 与异步 Leave 之间也没有串行化，二者可交错。

## 修复（按维护者批准的约束：Leave 带 Join 代际并复查）

`demo/internal/service/game/scene.go.tmpl`：

- 成员表 `members` 由 `map[int64]struct{}` 改为 `map[int64]sceneMember{generation, ready}`；**每次 Join**（首次登录或重连）分配新代际，
  `Ready` 记录该代际的客户端已 scene_ready。
- 新增 `transitions` 互斥，串行 Join / Ready / Leave / 断线处理（settle）；它跨 manager 与 policy 调用持有，二者都不回调 scene
  （`SessionLost` 只登记 settle），不在 Nest 快池内使用。
- 断线路径（`sessionLost` 与 `watchSessions`）改为 `settleLater`：在事件时刻记下当前代际，异步执行 `settle`，在锁内复查：
  - 代际已不是当前（玩家已重新 Join 或已离开）→ 丢弃；
  - 仍有活跃连接 → 不 Leave；若是 manager 丢掉了复制会话（旧连接推送失败），按成员状态重开会话（ready → `OpenSession`，否则 `OpenHeldSession`），
    并调用新的 `policy.Interest.Resubscribe` 让该观察者持有的全部 pair 重说一次——活着的客户端收到新 lifetime 的全量快照；其他人什么都不收到（subject 未注销）；
  - 确实没有活跃连接且代际仍是当前 → Leave（与原先正常离线一致）。
- `Join`：先 `HoldSession`；会话已被 manager 丢掉（`ErrSessionUnknown`）时 `OpenHeldSession` 并 `Resubscribe`，否则重连后的会话在 pair 变化前收不到任何帧
  （代际判定使迟到的 settle 被丢弃，恢复视图的职责因此落在 Join 上）。
- 公开 `Leave(ctx, subjectID)` 保持**无条件**（归属驱逐器 `playerEvictor` 需要）；`sweep` 改为锁内 `sweepLocked`，逻辑不变。
- 测试缝 `Scene.async`（nil 时用独立 goroutine）只用于让测试决定 settle 何时执行。

`sync/entitysync/policy/interest.go`：新增 `(*Interest).Resubscribe(observer int64) int`——把该观察者持有且已说给 manager 的 pair 标为未订阅并放入重试表，
下一次 `Apply` 重说。它是正式政策 API：任何政策使用方在 manager 因传输失败丢掉会话而观察者仍在政策里时都需要它（Interest 的 held 表不知道 manager 丢了订阅）。
其他观察者对该 subject 的 pair 不受影响；仍被 manager 拒绝的 pair 按既有重试机制每次 Apply 再说。

未采用：让生成传输 `pushPlayer` 只要有一个连接成功就报成功（改变全体推送方语义，且失败连接的客户端会错过帧而与服务端流分叉）；
在 Leave 里只查 `ActiveSessions` 不带代际（约束要求代际；且无法表达“事件属于已被替代的登录”）；resync 时 Leave + 重新 Enter（会清掉 team 关系、
让其他人收到 remove 再 create）。

## 兼容性与行为变化

- 生成工程（game-demo）行为：旧连接推送失败而玩家仍有活跃连接时，玩家留在场景，客户端收到一次全量快照（新会话 lifetime，epoch/tick 重新开始，
  与 Close/Open 新入场同一语义）；以前是被移出场景、其他人看到其对象消失。
- `Scene` 的公开方法签名不变；`sceneJoiner` 接口不变。新增的 core API 只有 `policy.Interest.Resubscribe`，无删除/改名。
- 每次断线事件仍最多起一个 goroutine（与原 `dropAsync` 相同），不是每请求。

## 交付前对抗性自查

- **超时 ≠ 撤销**：本修复不涉及事务；scene 只改复制成员表与订阅，Leave 不再被旧连接的推送失败触发，不影响任何已准入事务。
- **登录并发（同一玩家多次登录）**：Join 在 `transitions` 锁内串行，每次 Join 得到新代际；两次并发登录后成员表只保留最后一次 Join 的代际，
  两个连接之一关闭时 `ActiveSessions>0` → 不动作，两者都关闭才 Leave。
- **重连 Hold/Ready 与代际一致性**：会话仍在 → `HoldSession`（沿用 lifetime、epoch+1、订阅回到快照）；会话已被 manager 丢掉 → 新 lifetime + `Resubscribe`。
  `ready` 随代际重置、由 `Ready` 置位；resync 按它选择 held 或 ready 重开，避免在客户端装好解码器前发帧。迟到的 settle 因代际不符被丢弃，不会对新代际的会话做 Hold 重置或重复重订阅。
  manager 侧只采纳当前 session 结构的丢失（`adoptSession`/`dropSession(expected)`），Join 后的 Hold 使旧在途推送的失败不会再触发 SessionLost。
- **连接槽 / 按 IP 计数唯一释放**：本修复不触及传输层计数。
- **不引入每请求 goroutine**：settle 仍是每个断线事件至多一个 goroutine（与原 `dropAsync` 相同），resync 同步执行于该 goroutine；Resubscribe 只遍历该 Interest 的 held 表一次（仅在会话丢失时）。
- **锁序**：`transitions` → `mu`（短）→ manager/policy 内部锁；`sessionLost` 在 manager tick 内只读 `mu` 并登记 settle，不取 `transitions`，无反向锁序。

## 未验证项与已知边界

- 同一 tick 内 Leave 后立刻 Join（subject 仍在 retiring、remove 帧尚未发出）时 `Register` 返回 `ErrSubjectRetiring`，EnterGame 记 Warn“player did not join the replicated scene”。
  这是既有行为（本修复未改变，TCP 传输下正常重连不会触发 Join 内 sweep 移出自己），编写回归时观察到，未另行登记修复。
- 没有真实双连接（旧 socket 写超时）端到端复现；模板测试用 recorder 模拟旧连接写失败。
- resync 重开会话失败（如会话数达上限）时玩家保留成员身份但自身视图要等下次登录恢复（Warn 日志）。
