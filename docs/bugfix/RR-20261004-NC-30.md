# RR-20261004-NC-30 修复：RefHMap 在删除前裁决 registry 快照

[问题与原红](../bug/RR-20261004-NC-30.md)。2026-10-04；基线 main `e7027a65`，已修复、声明场景验证，未发版。

## 实现与决策

`cache/ref_hmap.go:363` registeredKeys 返回清理键和原始 registry 字节，始终把 root 排在 KEYS[1]。全量 Set 的 refHMapWriteScript 在 DEL 前 HGET root.__keys，与 ARGV[3] 比较；新增 refHMapDeleteScript 对 Delete 做同样比较。匹配才执行，变化返回 0，`refHMapWriteResult` 转成可 errors.Is 判断的 `ErrRefHMapRegistryChanged`。Lua/网络错误直接透传，不转成明确未应用；非预期返回值报错，不误报成功。

不复用 `ErrConflictingWrite`：它表示同版本不同值，registry 竞争不具有这个语义。不用分布式锁或无限重试，也不在脚本中访问未声明键；所有清理键仍先作为 KEYS 传入。检测变化后此次脚本没有写，调用者应先读取当前 schema/业务意图，再决定是否重新 Set/Delete。重试可能覆盖新 schema 的合法内容，框架不会代替业务自动决定。

生产实现只改 ref_hmap.go；同包 fake 更新 Lua 参数及 Delete 仿真，新增 [12 条正式回归](../../cache/ref_hmap_schema_promises_test.go)。Codegen 模板和生产核心三大模块未改，正式生成消费者验证错误能穿过 RedisDAO/CachedDAO；remote 拒绝后 L1 保持原数据。

## 兼容与边界

存储格式和已有 public 方法签名保持，新增错误符号。Delete 现在也要求 adapter 实现已有 Eval 能力。过去竞争中返回 nil 的调用现在可能明确失败；初次并发创建、schema 切换或 Patch 新登记路径都可能改变 registry。已有同布局相同 registry 的写依旧 last-writer；Stale 仍建议性比较，不是 CAS，不保护 Delete/重建的业务 lifetime。历史 root 无 registry 时按空字节比较，root 排序兼容非 root-first 的旧登记。

guard 比较的是 registry 字节，键集顺序变化也会保守拒绝。不会自动清理历史孤儿、迁移数据或复原结果未知的操作。跨 hash Get、旁支 TTL、破坏性 schema 变更继续按 [机制边界](../review/IMPLEMENTATION-REFHMAP-LAYOUT-PATCH-AND-REDIS-LIFETIME.md) 使用。
