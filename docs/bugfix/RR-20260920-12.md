# RR-20260920-12：撤离的预算不覆盖它要等的那件事（U-0272）

- 等级：P2
- 仓库 / 位置：roost-codegen `demo/internal/service/game/playerowner.go.tmpl`
- 审查记录：[REVIEW-2026-09-20-04](../bug/REVIEW-2026-09-20-04.md) · 复现附录 [REPRO-2026-09-20-04](../bug/REPRO-2026-09-20-04.md)
- 缺陷类：C8（快慢路径不对称：声明的预算与真实等待不是一回事）

## 问题

`dropResident` 给 `EvictPlayer` 套了 `context.WithTimeout(ctx, evictBudget)`，注释写着"一次撤离最多 5 秒"。
但撤离的终点 `EntityManager.Destroy`（`roost-core/entity/entity_manager.go:189-207`）只在**入口**看一次
`ctx.Err()`，随后 `mu.Lock()` 等实体锁，而那把锁不接受 ctx：

```go
if err := ctx.Err(); err != nil { return err }
if !e.Touch() { return ErrEntityRemoved }
mu := e.GetMutex()
mu.Lock()          // ← 没有 deadline，等到事务结束为止
```

`Claim` 路径是同步的，而 `renew` 会调它，所以一个事务很长的实体可以把**整个刷新轮**钉住；
`Lease=30s`、`RefreshInterval=10s`，阻塞超过 20 秒就开始有别的玩家的租约真的失效——
一个忙实体换来一片失主。

这与当天上午修掉的 RR-20260920-08（`OpTimeout` 在拿到写闸之后才生效）是同一个形状，
而且是本人当天在 demo 侧重新引入的。

## 方案选择

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 让 core 的 `Destroy` 支持可取消的等待 | 最通用，但要改 core 的实体锁语义，属于"要先定契约"的那一类 | 未采用 |
| 把 `Claim` 路径的撤离也改成异步不确认 | "认领成功但尚未安全"这个中间态要有人表达，等于把 U-0268 的判据再拆一层 | 未采用 |
| **撤离跑在自己的 goroutine 上并跑到底，预算只限制"等多久"** | 预算限制的正是它唯一能限制的东西，语义与名字对上 | **采用** |

关键是把"撤离要多久"和"调用方等多久"分开：前者由那个事务决定，谁也管不着；后者是本进程的选择。
超时的调用方**没有**拿到副本已清的事实，所以照旧 fail-closed——`Claim` 不接管，归还保留租约。

配套加了**按玩家去重的单航班**（`evictions` map）：同一个玩家的第二个调用方加入正在进行的那一次，
而不是再起一个。这条同时挡住了异步化引入的新风险——不可能出现"旧撤离还在跑，新认领已经确认"，
因为每条认领路径都要等在同一次撤离上，且只有它成功返回才会确认。

## 改动

- `evictBudget` 的注释改写成它现在的真实含义（调用方等多久，不是撤离多久），并写清为什么撤离本身不带 deadline：
  它的终点不读 ctx，传一个 deadline 只是没人兑现的承诺。
- `dropResident`：查/建单航班 → 必要时起 goroutine → `select` 等 `done` / 预算到期 / 调用方 ctx。
- 新增 `runEviction`：跑完把结果交给所有等待者（`close(done)` + 共享 `err`，不是 buffered send，
  因为等待者可能有多个），并从 map 里摘掉自己。
- `evictWait` 作为字段（默认 `evictBudget`），测试不必为了证明"等待有上界"真花五秒。

## 证明

新测试（生成工程 `internal/service/game/playerowner_test.go`）：

- `TestAClaimWaitsAtMostTheBudgetForABusyEntity`
- `TestASecondDropJoinsTheOneAlreadyRunning`（单航班；实体放开后下一次认领由它服务）
- `TestOneBusyEntityDoesNotHoldUpTheRefreshLoop`（旁观者的租约不受牵连）

变异验证：把 `go owners.runEviction(...)` 改回同步调用，

```text
panic: test timed out after 45s
FAIL	example.com/w06/internal/service/game	45.529s
```

即旧形状下预算完全不起作用，整个测试进程被一个忙实体挂住——正是生产里刷新轮被钉住的那一幕。
修后生成工程 `go test ./... -race` 全绿，codegen 仓 `go vet` + 全量测试全绿。

## 未做 / 边界

- **core 的 `Destroy` 仍然不可取消**。本单元只在 demo 侧把等待变成有界的；真正让撤离可取消要改 core
  的实体锁等待，单列。
- **撤离会晚到**：超时之后那次撤离仍在后台跑。如果期间归还被取消、租约继续服务，晚到的撤离会把一份
  **我们仍然合法拥有**的实体卸载掉。这是安全的（持有租约时丢弃并重新加载永远安全），代价是一次冷加载。
- 单航班的 key 是玩家 id，所以"撤离进行中"期间该玩家的任何认领都会排队等它——这是刻意的，
  也是上面那条"不可能确认到一份还没清掉的副本"的依据。
