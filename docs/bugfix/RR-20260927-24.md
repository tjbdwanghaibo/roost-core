# RR-20260927-24：strict 等 Remote 确认到截止的回复同时带 `ErrRemotePersistenceIndeterminate`

问题：[RR-20260927-24](../bug/RR-20260927-24.md)（OPEN-ITEMS B23 → 11 追加）。日期 2026-09-27。基线 `23c1201`，分支 `fix-r7-rr24`。
状态：已修复，本地验证通过，本地提交，未推送 / 发布。codebase-memory 图谱过期（09-26），调用点核对以当前源码与 `git grep`（全仓，含 kit、demo、codegen 模板）为准。

## 根因（基线行号）

`remoteentity/transaction_tracking.go:178` `waitTrackedRemoteTransaction` 的 `ctx.Done()` 分支返回
`errors.Join(entity.ErrRemoteCommitTimeout, ctx.Err())`，状态 `RemoteCommitUnknown`。等待截止时 tracker 仍在、事务之后可能提交，
语义上就是“结果未知”；其余三种结果未知（Durability 0 回复丢失 / 从未到达、strict 等待中投影器报告未知）都带 `ErrRemotePersistenceIndeterminate`。
RR-37 修复记录“兼容性”一节承诺 strict 确认超时同样可 `errors.Is(ErrRemotePersistenceIndeterminate)`，按这个哨兵判“可能已提交、不得重试”的调用方
在 strict 截止时漏判，可能重复业务。

## 决策（按主记录修复约束）

- 截止分支改为 `errors.Join(entity.ErrRemoteCommitTimeout, entity.ErrRemotePersistenceIndeterminate, ctx.Err())`：只增加 `errors.Is` 命中，
  原有的 `ErrRemoteCommitTimeout` 与 `context.DeadlineExceeded` / `Canceled` 保留，状态与 `Cause` 不变。
- `nest/nest.go` `ErrLockTimeout` godoc 的“可能已提交”哨兵清单补上 `entity.ErrRemoteCommitTimeout`，并写明 strict 截止两者并存、
  自定义 Remote 实现可能只返回前者所以两者都列。
- `docs/USER_GUIDE.md` §4 判别表第 2 行：四种形态都带 `ErrRemotePersistenceIndeterminate`，strict 截止另带 `ErrRemoteCommitTimeout` 与
  `context.DeadlineExceeded`（本修复起；之前只带后者），判断只看前者即可；表下说明与 Remote 收尾段落同步。

## 兼容性

只增加 `errors.Is` 命中，不删除哨兵、不改状态 / Cause / 控制流。按 `ErrRemoteCommitTimeout` 判断的调用方不受影响；按 `ErrRemotePersistenceIndeterminate`
判“可能已提交”的调用方在 strict 截止时从“漏判”变为正确判定。`FlushRemoteTransaction` / `FlushRemoteAll` 截止同样多满足该哨兵。
若仓外调用方曾用“带 `ErrRemotePersistenceIndeterminate` 且不带 `ErrRemoteCommitTimeout`”区分“投影器报告未知”与“等待截止”，这种区分仍可用（前者仍不带 `ErrRemoteCommitTimeout`）。
