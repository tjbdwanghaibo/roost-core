# RR-20261006-66 修复：saga.max_payload_bytes 成为发起方与协调器共用的配置键，EmitStart 在发起事务内按它拒绝

问题：[RR-20261006-66](../bug/RR-20261006-66.md)（F06-S7 跨进程）。基线 `a7285da6`（main）。codebase-memory 共享 generation 停在 09-30（比基线旧），按 worktree 当前源码。
同一笔提交还有 saga 完成判定统一规则（[方案](../feature/SAGA-COMPLETION-RULE-UNIFIED-2026-10-07.md)，维护者选 A）。

## 决策

- **一份声明，两个 Mod 共用**：`kit/mods.SagaPayloadConfig`（`saga.max_payload_bytes`，缺省 65536、`min 1`、`max 4194304`），`kit/saga`（协调器）与 `kit/nest`（发起方：调 `EmitStart` 必在 Nest 事务里，进程必有 Nest）的配置都匿名嵌入。A4 ① 的 `Merge` 要求同一键声明完全相同，共用结构体保证这一点（`TestSagaPayloadLimitIsOneDeclarationSharedWithNest`）。
- **发起方读它**：`kit/nest` `Init` 调 `coresaga.SetStartDataLimit(值)`；`startDataLimit(type)` = min(线上硬上限 4 MiB, 配置值, 本进程协调器为该类型注册的 `MaxPayloadBytes`)。查表与原子读不做 I/O，留在快池。
- **不写进生成的配置段**（去掉 `example`）：没有 saga 的 Nest 工程不该多出 `saga:` 段；改上限时发起方与协调器写同一个值（SAGA.md）。生成的 saga 服务配置因此少了 `saga.max_payload_bytes: 65536` 这一行（值即缺省）。
- **未采用**：① 发起方经 RPC / KV 读协调器的上限（发起事务里不能做 I/O）；② 只在 `kit/saga` 声明、要求每个发起进程都装 saga Mod（协调器的 Mongo / JetStream 依赖会被带进所有发起进程）。
