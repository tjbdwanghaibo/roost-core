# RR-20260926-25 修复：统一准入对冷的声明目标自动走慢阶段预加载

问题：[RR-20260926-25](../bug/RR-20260926-25.md)（探针见 [REPRO-2026-09-26-03 §1](../bug/REPRO-2026-09-26-03.md)）。
日期 2026-09-26；实施基线 main `87d9499`，建立在同批 [RR-26](RR-20260926-26.md) 之上（准入判定依赖“快阶段冷缺失返回错误、不 panic”）。
状态：已修复、本地验证通过，已提交未推送/未发布。方向由维护者选定：Nest 在统一准入时自动分流，业务代码不改。

## 根因

- 快阶段只读已加载实体：`nest/slow_load.go` `loadedGetter` + `entity/manager_access.go`（RR-02）。
- 进入慢池只有显式 `SendOptionSlow()` 与 Remote：`nest/dispatcher.go:253`（基线）
  `m.queue.admit(msg, m.remoteHandler != nil && (msg.Cost || needsRemoteStage(msg)))`，不看目标是否已加载。
- 生成 sender 不暴露 `SendOpt`，唯一入口是 handler 名 `_cost` 后缀（`codegen/internal/nest/parse.go:562-566`）；demo 没有这样的
  handler，仓内非测试代码没有一处调用 `SendOptionSlow`。于是 gift saga 扣减/补偿（`gift_saga.go.tmpl:445/464`、交接 `:323-325`）
  和 GM 发放（`gm.go.tmpl:186/205`）在离线冷玩家上固定得到 `ErrColdLoadInLogic`。

## 决策与实现

### 1. 统一准入判定（`nest/dispatcher.go`、`nest/slow_load.go`、`nest/nest.go`）

`TrySendMsg` 的慢阶段条件增加第三个来源：`NestMgr.declaredTargetsNeedSlowPreparation(msg)`。它对 Single/Multi/MultiGroup 的全部
声明目标调用 `Getter.Get(admissionProbeContext, …)`，`admissionProbeContext` 是共享的 `WithLoadedEntitiesOnly` ctx：按 Getter 契约
未加载且配置了 loader 的目标返回 `ErrColdLoadInLogic`，不做 I/O、不等待加载（RR-26 之后快 worker 上也只返回错误），所以在调用方
goroutine（包括在 handler 里发送的快 worker）上执行是安全的。任一目标冷即 `admit(msg, slow=true)`，之后与显式 Slow 完全同一路径：
慢 worker `prepareSlowEntities` 用原始 Getter 加载并 Touch 声明目标，再经内部快续行回快池执行 handler。同 ID 顺序仍在
`dispatchQueue.admit` 按 `dispatchIDs` 统一登记，与走哪个池无关。所有外部入口（Request/Dispatch/Multi/MultiGroup、延迟消息到期、
锁超时的重新准入、组迁移续行）都经过 `TrySendMsg`（图谱 `trace_path TrySendMsg inbound` 核对）。

不纳入自动判定：Broadcast（尽力扇出，冷目标逐个报告，`TestFastBroadcastReportsColdTargetAndContinues`；为广播批量冷加载会放大 I/O）、
GroupTransition（内部消息，无业务目标）。显式 `SendOptionSlow()` 保留并仍然有效。未声明的动态 Cast 目标不受影响，保持 RR-02 语义。

### 2. 准入判定之后、handler 取 Guard 之前被驱逐（`nest/nest_dispatch.go`、`nest/dispatch_queue.go`、`nest/msg.go`）

准入时已加载 → 走快池；执行前被闲置回收驱逐，有三个窗口，全部在业务执行与 Guard 之前：

| 窗口 | 检测点 | 旧结果 |
| --- | --- | --- |
| 读取之前 | `singleDispatch` / `dispatchMany` 的 `Get/GetMany` 返回 `ErrColdLoadInLogic` | 冷加载错误 |
| 读取之后、引用之前 | `Touch()` 失败（对象已 `SetRemoved`） | `ErrEntityNotFound`（Multi 可选目标被静默当缺失） |
| 引用之后、取锁之前 | `RequireEntity` 拒绝已摘除实体 → `ErrLockTimeout` | 延迟重新准入，排到同 ID 后继之后 |

仅在快池首跑（`msg.prepared == nil`，`beforeSlowPreparation`）时，这三处改写为 `errDeclaredTargetCold`（`%w` 保留原错误）。
`dispatchNest` 的收尾在 `remoteStage == false` 且看到它时：不回复、不重新准入、不记 dispatch 完成，只设置 `msg.slowReroute` 并释放
本次 fctx。派发队列 `work()` 看到该标记后不释放消息引用，调用 `rerouteToSlow`：作业**保持在 `tails/successors` 中的位置和 `pending`
计数**，`running[0]--`，以已准入身份进入慢池就绪队列（不占新的 QueueCap，上界仍是已准入的快池作业数），慢池执行时就是普通的
Slow 路径。所以同 ID 后继继续等它，停机排空也等它；handler 从未开始，迁移的只是“慢准备”这一步，不是“执行一半的 handler”，
快 worker 上也不发生冷加载。慢准备之后的快续行不会再触发迁移（`prepared != nil`），冷目标错误照常返回，不会循环。

未采用：

- **复用 `requeueNestDispatch`（延迟重新准入）**：会排到同 ID 后继之后，违反“内部续行使用既有准入资格、不能重新排到自身之后”。
  负对照：把取锁窗口的改写临时关掉，`between touch and lock` 子测试得到 `same-ID order changed after moving to the slow stage: [second first]`。
- **在快 worker 上检测到冷目标后投递慢任务并同步等待**：快池内阻塞等待，违反 roost-coding 快池契约。
- **生成 sender 正式暴露 Slow / `_cost` 默认化**：业务要知道目标冷热，demo 和既有工程都要改；维护者选择了准入自动分流。
- **给 Getter 增加“是否已加载”新接口**：`LoadedEntitiesOnly` 已是正式契约，复用它不引入新扩展点；代价是违反契约的自定义 Getter
  会在准入 goroutine 上做 I/O（已写入 USER_GUIDE）。

### 3. 注释与文档

`nest/nest.go` `SendOptionSlow` 注释、`entity/entity.go` Getter 注释（准入判定使用只读路径）、`codegen/internal/nest/parse.go` `_cost`
后缀注释（不影响生成输出）、demo `gift_saga.go.tmpl` / `gm.go.tmpl` 调用处注释、`docs/USER_GUIDE.md`“Nest Remote 慢操作并发”
与“回放、快阶段访问与观测”两段。codegen 模板输出未改，不需要重生成 fixture。

## 兼容性与迁移

- 行为放宽：原来对冷目标固定失败的普通请求现在成功，业务代码、生成 sender、配置都不需要改；已有的 `SendOptionSlow` / `_cost` 保持原义。
- 执行位置：冷目标请求的 handler 仍在快池；慢池多承担这类预加载，慢池 `Stats().Queue.Slow.Started` 会增加；准入后被驱逐而迁移的
  请求在快、慢两池各计一次 Started，另有指标 `nest.dispatch.slow_reroute.total{dispatcher}`。
- 准入开销：每条 Single/Multi/MultiGroup 消息对每个声明目标多一次只读 `Getter.Get`（ManagerAccess 为一次分片 map 查找）。
  同机 before/after（见验证）无新增分配。
- 自定义 Getter 必须遵守 `LoadedEntitiesOnly`，否则准入判定会在调用方 goroutine 上执行 I/O。
- 未声明目标（handler 内动态 Cast）语义不变；Broadcast 不变。

## 未验证项

- demo 级端到端（真实进程重启后 gift 补偿、GM AddItem 打到离线玩家）没有跑：game-demo 只做了生成、编译、vet 与单测；
  冷目标 → 慢池加载 → 等待投影 → 快池执行这条链用正式生成 DAO/Entity + 真实 Mongo 的临时测试验证。
- 自定义 Getter 若不遵守 `LoadedEntitiesOnly`，准入判定会在调用方 goroutine 上执行 I/O；框架无法拦截，只写入契约与 USER_GUIDE。
- “引用与取锁之间”窗口以 `IsRemoved` 判定；若 `ErrLockTimeout` 由组锁超时与驱逐同时造成，也会走原位慢准备（handler 仍未开始，行为安全）。
- 没有在 1000 玩家负载下复测 Nest 吞吐与尾延迟；准入多一次只读查找的影响只做了微基准。
