# RR-20260913-05:L2 版本冲突被当成可降级故障吞掉

**仓库 / 位置**:roost-core `entity/remote_snapshot.go`,`Publish`。
**修复单元**:U-0180(C8)。**定位文档**:TROUBLESHOOTING T-74。

## 问题

缓存对 L2 固定 `IgnoreRemoteError: true`,`ReadThrough` 对 `remote.Set` 的一切错误统一降级再写 L1。
L2 已存同 key/epoch/version 的 A,一个 L1 为空的进程 Publish 同版本的 B:L2 正确返回
`ErrRemoteVersionConflict`,却被吞掉,Publish 返回 nil,**L1=B、L2=A** —— 同一个版本在不同进程返回
不同内容,而发布方收到成功。

## 根因

"网络不通时保留 L1 可用"是对的降级策略,但它把**所有**L2 错误都当成可用性故障。版本冲突是
一致性错误,不是网络故障,两类错误走了同一条判据(C8)。

## 方案选择

- **全局关掉 `IgnoreRemoteError`。** 破坏既有降级:L2 一抖,发布全失败。审查也明确不建议。
- **让 `ReadThrough` 认识 `ErrRemoteVersionConflict`。** cache 包是泛型层,不该依赖 entity 的错误。
- **在 entity 的 Publish 里、L1 未命中时先问 L2 一次(采用)**。L1 对这个 key 一无所知时,同版本值
  唯一可能存在的地方就是 L2;读到冲突就返回一致性错误,不落任何写;L2 **读失败**是真正的可用性
  故障,照旧忽略、继续降级。复用本地已有的同版本比较,不动全局开关。代价是冷 L1 发布多一次
  有界的 L2 读。

## 改动

`entity/remote_snapshot.go`:`RemoteSnapshotCache` 保留 `l2` 引用;`Publish` 在 `local.Get` 未命中且
`l2 != nil` 时用 `LoadTimeout` 有界地 `l2.Get`,同 epoch 同版本且内容不同 → `ErrRemoteVersionConflict`;
同版本比较抽成 `remoteSnapshotSameVersionConflict` 供三处共用。

## 证明

`entity/snapshot_l2_conflict_promises_test.go` 的 `TestPublishSurfacesAnL2VersionConflictAndKeepsItOutOfL1`:
L2 替身预置 A(v5),Publish B(v5) 必须 `ErrRemoteVersionConflict` 且 L1 里没有 B;另外断言 L2 纯故障
(`Set` 报连接错误)时 Publish 仍成功、L1 有值 —— 降级能力没有被一起改掉。

修前红:`publishing a conflicting same-version value = <nil>, want ErrRemoteVersionConflict`。
修后 entity 含 `-race` 全绿。

## 未做 / 边界

- L1 **有**旧版本、L2 有同版本不同内容时,走的是 `layered.Set` → L2 CAS 拒绝 → 仍被 ReadThrough
  吞掉。这个交错的 L1 侧由 U-0181 的 `Conflict` 钩子把关;L2 侧的返回值仍被吞。彻底的做法是
  给 ReadThrough 一个"哪些错误不可吞"的分类钩子,那是 cache 包的接口扩展,留待后续。
- 没有跑真实 Redis;审查第三轮已在真实 Redis 上复现过原问题。

## 2026-09-13 复核后的补修(仍归 U-0180)

审查第七轮:B 的 L2 预检查读到 miss 后暂停,另一发布者写入同版本 A;放行 B,`L2.Set` 正确拒绝,
但 `ReadThrough.Set` 在 `IgnoreRemoteError` 下把它吞掉,B 落进 L1、返回 nil。实测 `err=<nil> L1="B" L2="A"`。
第一版记录的"未做"里已经写了这一条——"彻底的做法是给 ReadThrough 一个'哪些错误不可吞'的分类钩子"——
预检查只能提前发现,不是并发正确性屏障;L2 的 CAS 才是原子边界,它的回答必须算数。

**改动**:`cache.ReadThroughOptions.FatalRemoteError func(error) bool`,`Set` 与 loader fill 的 `remote.Set`
出错时先问它,命中则不降级、原样返回;entity 配置为 `ErrRemoteVersionConflict || cache.ErrConflictingWrite`。
网络故障仍按原契约降级到 L1。cache 包仍不认识 entity 的错误——分类由使用方给。

**证明**:`entity/snapshot_delete_l2_promises_test.go` 的 `TestPublishConflictAfterPreflight`(同文件内另断言
L2 纯故障时 Publish 仍成功写 L1)。修前红:`conflict swallowed after preflight: err=<nil> L1="B" L2="A"`。
修后 cache / entity 含 `-race` 全绿。

**边界**:`ReadThrough.Delete` 的远端错误没有分类(删除没有语义冲突);预检查保留,作为冷 L1 的早发现。
