# RR-20260927-21 修复：本 Guard 自己撤销的新建实体，同一 handler 再建同 ID 为确定失败

问题：[RR-20260927-21](../bug/RR-20260927-21.md)（第五轮审计 N1，RR-20260926-81 引入）。日期 2026-09-27；本修复基于 `d4234c9`（批次 4 worktree `fix-r7-ent`，
叠在本批次 RR-20260927-11 之后）。codebase-memory 图谱停在 09-26，已过期，未使用；以源码为准。

## 根因

`entity/manager_factory.go` `CreateInScope`（基线 `:91`）的 RR-81 分支对 `capturer != nil && errors.Is(err, ErrEntityRemoved)` 一律给
`capturer.CreatedEntityLockBusy`——即“别的持有者尚未交还”的暂时冲突。`revokeCreated` 把撤销收尾（`DestroyAll/OnDestroy`、回收 LockManager 条目、
删除 `removing`）挂在**撤销所在 Guard** 的 post-release 上；handler 内嵌套 `RunIsolatedTransaction` 与外层共用同一个 Guard，所以嵌套事务回滚撤销的 X
要等整个 handler 释放才收尾。外层再建 X 撞上的 removing 是自己留下的，在本次执行内不会结束：可回滚事务每次重排都重现（审计探针 401 次），
memory handler 的文案归咎于 another holder。

## 决策

- **判据落在 Guard 上**：`EntityGuard.revokedCreated`（本 Guard 上撤销、收尾尚未执行的新建 ID）。`revokeCreated` 摘除索引、置 removing 之后登记；
  `releaseEntities` 取走 post-release 回调时清空（收尾就在这批回调里），`clean` 也清空（Guard 回池）。只由持有该 Guard 的业务 goroutine 读写
  （与 `createdCapturer` 同一所有权），不加锁。
- **CreateInScope**：TryAdd 返回 `ErrEntityRemoved` 且 `guard.revokedInThisGuard(id)` 时，在 RR-81 分支之前返回
  `%w; entity N was created and then revoked earlier in this handler, …`：保留 `ErrEntityRemoved`，不带 `ErrCreatedEntityLockConflict` / `ErrLockTimeout`，
  `requeueTransientDispatch` 不认它，消息不重排；可回滚事务在业务返回它时照常整条回滚。锁的归还不变（此时新实例与撤销的旧实例共用 LockManager 里的同一把锁，
  Guard 视为已持有，`lockedNow=false`，不需要归还）。
- **别的持有者**（另一个事务的撤销收尾、Nest 之外的 Destroy 收尾）：不在本 Guard 的登记里，保持 RR-81——可回滚整条回滚重排，不能回滚按 RR-64 给冲突哨兵。
  Nest 之外（capturer 为 nil）仍原样返回 `ErrEntityRemoved`，生成 `GetOrCreate` 的 RR-57 有界重试不变。
- 与本批次 RR-20260927-11（同一函数的捕获失败强制事务失败）互不干扰：本分支在发布之前返回，不进入 `CaptureCreatedEntity`；捕获失败在发布之后。

未采用：按 `guard.eMap[id]` 里“已 removed 且锁由本 Guard 持有”的实例推断——handler 内 `Destroy` 也会留下这种实例，而 Destroy 的收尾在返回前已完成，
推断需要额外排除；显式登记更直接。

## 兼容性

行为变化只在“同一 handler 内重建本 handler 刚撤销的 ID”：回复从“锁超时 + 冲突（可回滚时空转到上限）/ 冲突（memory）”变为确定的 `ErrEntityRemoved`，
不再重排。RR-48 / 64 / 81 的其他形状不变。无导出 API / 配置 / 生成物变化。生成器里 `GetOrCreate` 的注释与工作流说明（RR-81 合并时补的那句）描述的是
别的持有者的收尾窗口，仍准确，未改。
