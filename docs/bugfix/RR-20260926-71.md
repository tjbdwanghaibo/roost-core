# RR-20260926-71 修复：冷加载与构建策略按 kind 的实际 Remote 策略判定，全仓同类点一并收口

问题：[RR-20260926-71](../bug/RR-20260926-71.md)（探针 [REPRO-2026-09-26-06](../bug/REPRO-2026-09-26-06.md) §7）。
日期 2026-09-27；实施基线本地 main `2373e21`，建立在同批 RR-64（`b4018e7`、`66aeeb9`）、RR-65（`6a2e1aa`）、RR-67（`bc6c310`）之上。
状态：已修复、本地验证通过，已本地提交，未推送 / 未发布。方向按修复约束：`dataengine/engine/entity_repository.go` 与
`entity/entity_factory.go`（`validateBuiltEntityPolicy` 与默认生命周期）改用 `entity.GetEntityKindRemotePolicy(kind)`，与 RR-60 一致；
全仓核对其余 `builder.RemotePolicy` / `RemotePolicy.RemoteManaged()` 判定点。

## 根因（基线源码核对）

kind 先经 `MustRegisterEntityKindDefs` 声明 managed，手写 builder 再省略 `RemotePolicy`（即 none）注册时，注册表把 builder 的 none 当作
“部分重复声明”接受并忽略（`registerEntityKindDefinitionLocked`），kind 的实际策略仍是 managed，全部 Remote 路径按托管处理；但：

- `dataengine/engine/entity_repository.go` `loadAggregate`：以 `builder.RemotePolicy.RemoteManaged()` 决定是否恢复 Remote 版本信封 →
  信封被丢弃（向量 `{StateVersion:0 …}`、ownership unknown、未进 Recovering），“托管实体无版本信封视为损坏”的检查也被跳过。
- `entity/entity_factory.go` `validateBuiltEntityPolicy`：按 builder 字段判断，kind 为 managed 而实体不实现 `IThreadSafeRemoteEntity` 时构建成功。
- 同源 `normalizeBuilderPolicy`：注册 builder 时按 builder 字段（none）补默认生命周期（persisted / ephemeral）并校验，托管 kind 得到本地默认生命周期；
  `resolveEntityLifetime` 的兜底分支、`EntityBuilderParam.IsRemoteCapable` 同样读 builder 字段。
- 反向注册顺序（builder 先按 none 注册、kind 定义随后声明 managed）：注册表把 none 升级为 managed，但 builder 的生命周期早已按 none 定下，
  修前被静默接受——kind 变成托管而 builder 的生命周期仍是本地默认值。

## 决策与实现

- 上表“改为”各处以 kind 在注册表里的实际策略为准。`normalizeBuilderPolicy` 在 `registryMu` 内读注册表：builder 自带非 none 策略时仍用它
  （与注册表矛盾时随后的 kind 声明报错，行为不变）；省略时取 kind 已声明的策略，于是托管 kind 默认得到 `EntityLifetimeRemoteManaged`、
  mirror 得到 `EntityLifetimeMirrorCache`，显式写了与之矛盾的生命周期会在注册时 panic（与 builder 自带策略时相同的校验）。
- 不改写 builder 的 `RemotePolicy` 字段（保持业务注册的原值），读取方统一问注册表。
- 反向注册顺序：`registerEntityKindDefinitionLocked` 把 none 升级为 managed / mirror 时，若 kind 已有 builder，用新策略校验它的
  `NoPersist` / `Lifetime`，矛盾则返回 `entity kind <k> remote policy <p> declared after its builder: …`（`MustRegisterEntityKindDefs` panic），
  注册表保持 none。选择拒绝而不是事后改 builder 的生命周期：无法区分生命周期是默认补的还是业务显式写的，且 builder 已对无锁读者发布。

## 兼容性 / 行为变化

- 仅影响“kind 定义为 managed / mirror、手写 builder 省略 RemotePolicy”的组合（生成工程的 builder 总是显式写出策略，走不到）：
  - 冷加载按托管恢复 Remote 版本信封并进入 Recovering；没有信封的记录返回 `ErrEntityAggregateCorrupt`（此前按普通实体加载、之后每次写版本冲突，失败关闭）；
  - 实体不实现 `IThreadSafeRemoteEntity` 时构建返回错误；
  - builder 省略生命周期时默认 `remote_managed` / `mirror_cache`；显式写了与 kind 策略矛盾的生命周期时注册 panic。
- builder 先注册、kind 定义后声明托管且生命周期矛盾：`RegisterEntityKindDefs` 返回错误 / `MustRegisterEntityKindDefs` panic（此前静默接受）。
  迁移：先声明 kind 定义再注册 builder，或在 builder 上显式写 `RemotePolicy` 与匹配的 `Lifetime`。
- 无新导出 API、无配置 / 持久格式变化。

## 对抗性自查（四项合并）

- **已提交内容不被重复执行（含嵌套、memory、pipelined）**：重排唯一入口 `dispatchNest` → `Msg.requeueAllowed` =
  `!transactionPastCommitPoint && !createLockConflictNoRollback`；提交点事实（RR-49 `txAdmitted`、RR-65 `nestedTxCommitted`、Remote 标志）都在
  对应持久动作返回后、handler 继续执行或回复之前置位。memory 冲突（RR-64）、嵌套提交（RR-65 strict / memory / pipelined 三种外层）各有回归；
  RR-49 / RR-53 回归在 `-race -count=20` 下通过。本批只增加“不重排”条件，没有新增任何重排路径。
- **RR-48 死锁不回来**：会等待的取锁仍只有“声明目标排序 / Cast、Create 向更高锁组”三类；RR-67 新情形（同 ID 换锁）按不满足锁序只 try-lock
  或拒绝；RR-48 的交叉创建、Create+Cast 成环、同 ID 占满快池回归在 `-race -count=50` 下通过。
- **RR-35 提交边界**：新建实体的捕获 / Include / 撤销发布未改；Destroy 后重建的新实例经同一路径进入提交记录、回滚时撤销（RR-67 回归）；
  `TestCreateInScope*` 在 `-race -count=200` 下通过。RR-71 只改冷加载与构建期判定，不涉及提交边界。
- **调用方拿到的错误可判别**：
  - 未执行、框架已自动重排仍失败：`ErrLockTimeout`（可回滚冲突另带 `ErrCreatedEntityLockConflict`）；
  - 未提交、未回滚、未重排（不能回滚的 handler 冲突）：只有 `ErrCreatedEntityLockConflict`；
  - 自己的事务未提交、嵌套独立事务已提交：`ErrNestedTransactionCommitted`（勿当作未执行重试）；
  - 自己的事务已提交、收尾失败：`ErrAfterCommitFailed`（RR-46 / 53，不变）；结果未知：`ErrCommitIndeterminate`（不变）。
  - Cast 取到未加锁的同 ID 新实例：`ErrCastDeadlockRisk`（RR-67）；冷加载托管实体无信封：`ErrEntityAggregateCorrupt`（RR-71）。
- **快池不阻塞**：本批没有新增等待入口；新增代码在快 worker 上只做布尔 / 接口比较与 goroutine 局部查表。
