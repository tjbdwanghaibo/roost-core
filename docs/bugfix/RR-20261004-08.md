# RR-20261004-08 修复：连接 drain 失败后 `Assembly.Close` 返回可识别的终态 `ErrClosedUndrained`，NatsMod 报告并释放引用

问题：[RR-20261004-08](../bug/RR-20261004-08.md)（来源 [W-2026-10-04-02](../bug/WANTED.md)，即 [RR-20261004-07 修复](RR-20261004-07.md) §未验证项）。
日期 2026-10-04；实施基线 main `a1c1af3e`（v1.19.1 之后）。状态：已修复，本地验证通过，已提交（A 线 worktree），未推送、未发版。

## 根因（基线行号）

- `nats/driver/assembly.go:66-69`：`Client.DrainWithContext` 出错后 `a.Client.Close()` 已硬关闭连接，却原样返回 drain 错误。超预算时它是裸 `context.DeadlineExceeded`，与第 62-63 行“RPC 回调等待超预算、连接仍在、可再次排空”返回的错误无法区分。
- `kit/nats/nats_mod.go:176-179`：`asm.Close` 返回任何错误都 `return err` 并保留 `m.asm`（第 179 行由 `3560a19b` / NC-09 加入），前提是“再次停止能继续排空”。
- `nats/driver/client.go:159-161`：重试时 `c.conn.Drain()` 对已关闭的连接返回 nats.go 的 `ErrConnectionClosed`（v1.53.1 `Conn.Drain` 首个分支），于是每次重试都失败、`m.asm` 永不置空。资源其实早已释放（RPC 已停、连接已关），只是停止流程永不收敛。
- 同一前提的第二个反例：停止前连接已被服务端断开且不再重连（或正在重连），第一次停止就拿到 `ErrConnectionClosed` / `ErrConnectionReconnecting`（后者 nats.go 会顺带 `Close`），同样被保留、同样永不收敛。

图谱：codebase-memory 项目 `Users-whb-roost-roost-core` generation 2026-09-30，早于 `3560a19b` / `e5aea173`；`check_index_coverage` 显示 `kit/nats/nats_mod.go`、`nats/driver/{assembly,rpc}.go` 为 `metadata_changed`，`nats/driver/client.go` 为 `metadata_match`。结论全部以当前源码为准，没有刷新共享索引。

## 决策

采用 W 条目候选一：**`Assembly.Close` 硬关闭后返回可识别的终态**，NatsMod 据此释放引用并报告。

- `nats/driver` 新增 `ErrClosedUndrained`（“nats: connection closed before drain finished”）。`Assembly.Close` 在连接 drain 出错时仍先 `Client.Close()`，然后返回 `fmt.Errorf("%w: %w", ErrClosedUndrained, drainErr)`：`errors.Is(err, ErrClosedUndrained)` 为真，超预算时 `errors.Is(err, context.DeadlineExceeded / Canceled)` 也仍为真，调用方原有的“停止超预算”判断与日志不受影响。
- 所有 drain 错误都归为终态，不只是超预算：`DrainWithContext` 的每条错误路径之后连接都已关闭（Assembly 自己 `Client.Close()`；`ErrConnectionReconnecting` 时 nats.go 先关闭），之后再 Close 不可能排空任何东西。
- NatsMod 新增 `assemblyClosePending(err) = busDrainPending(err) && !errors.Is(err, ErrClosedUndrained)`：只有 RPC 回调等待超预算（Assembly 仍持有连接，NC-09 承诺再次 Close 继续等同一次回调排空）才保留 `m.asm` 返回；其余错误合并进返回值、记 `nats mod: connection closed before drain finished`，然后释放 `m.asm`。第一次停止仍返回错误（含 ctx 错误），之后的停止返回 nil。
- 规则与 RR-20261004-07 对齐：**ctx 错误且资源仍被对象持有 → 保留供再次排空；终态错误 → 报告并释放**。区别在于这里 ctx 错误本身不够用——同一个 ctx 错误既可能来自“仍可等待”的 RPC 回调，也可能来自“已经硬关闭”的连接，所以由 Assembly 给后者加终态标记，而不是让 NatsMod 猜。

### 未采用的方案

1. **候选二：重试时把 `ErrConnectionClosed` 视为排空已结束**（在 `Assembly.Close` 或 NatsMod 里吞掉它）：能让第二次停止返回 nil，但第一次停止仍保留一个已经没有资源的 `m.asm`、仍返回与“可重试”同形的 ctx 错误，调用方无从知道要不要重试；而且把“连接在停止前就被关闭”这种从未排空过的情况也报成成功，掩盖了未排空的事实。终态应在硬关闭发生的地方标记，而不是事后从副作用推断。
2. **改 `Client.DrainWithContext`：已关闭连接返回 nil 或自定义错误**：`Client` 实现 `fnats.IClient.Drain` 的对外语义，`Drain()` 也走这里，对已关闭连接报错是现有行为（`wrapError` 也把 `ErrConnectionClosed` 映射为 `ErrClosed`）；问题只在 Assembly 的“硬关闭后返回值”上，修在那一层影响面最小。
3. **在 NatsMod 里用 `!asm.Connected()` 判断连接已关闭**：`Connected()` 在重连中也为 false，而重连中连接仍可能恢复、仍被 Assembly 持有；判断依据应是 Assembly 自己做过的硬关闭，而不是一次瞬时状态采样，且两步之间存在竞态。
4. **超预算时不硬关闭连接、保留给下次继续 drain**（把连接层也做成“可重新等待”）：nats.go 的 drain 一旦超时只能 `Close`，`Conn.Drain` 第二次调用对 draining 状态只返回 nil、不提供等待句柄；要实现得自己轮询 `IsClosed` 并承担“连接在预算外无限期保持”的代价，与 Assembly 文档里“超时即硬关闭”的既有约定相反。

## 兼容性

- **`Assembly.Close` 的错误值**：连接 drain 失败时从裸 drain 错误变为 `ErrClosedUndrained` 包裹的错误，文本多了 `nats: connection closed before drain finished: ` 前缀。`errors.Is` 对原错误（`context.DeadlineExceeded`、nats.go `ErrConnectionClosed` 等）仍成立；用 `==` 比较原错误的调用方会变。仓内生产调用方只有 NatsMod。对已经成功关闭的 Assembly 再调 `Close` 也会得到这个终态错误（修前是裸 `ErrConnectionClosed`）。
- **NatsMod**：连接 drain 失败（超预算或连接早已关闭）时第一次停止仍返回错误，但不再保留 `m.asm`；之后的停止返回 nil、健康检查报 “client not initialized”（修前一直 “not connected”）。RPC 回调等待超预算时仍保留并可重试（NC-09 / RR-07 承诺不变）。
- 无持久格式、wire、配置变化；新增一个导出变量。

## 未验证项 / 风险

- 真实 NATS 只覆盖“直连订阅 handler 阻塞导致连接 drain 超预算”；“Bus handler 超预算 → 重试 → 连接 drain 超预算”的全链路与“停止前连接已被服务端关闭”只在协议桩上验证。`jetstream_rpc_toxic_integration_test.go` 会 reset toxiproxy，按约束没跑。
- App 路径只调用一次 `stopModSafely`，不重试：修后 App 的单次停止日志从 `drain interrupted` 变为 `connection closed before drain finished`，其余不变。
- `Assembly.Close` 的“RPC 回调超预算后保留”仍只对 NatsMod 这一调用方有重试；本单元没有改动 NatsMod 字段的并发访问方式（健康检查闭包读 `m.asm`），未评估停止与健康检查并发时的可见性。
