# RR-20260927-11 修复：新建实体的事务捕获失败强制整条事务失败

问题：[RR-20260927-11](../bug/RR-20260927-11.md)（OPEN-ITEMS C26）。日期 2026-09-27；基线 `d4234c9`；worktree 分支 `fix-r7-ent`。
codebase-memory 图谱停在 09-26，已过期，未使用；以源码为准。

## 根因

`nest/rollback.go` `CaptureCreatedEntity` 的失败不在事务上留记号；`nest/execution.go:206-216` 只按 handler 返回值与 `createLockBusy` 决定是否回滚。

## 核对：Cast 的既有做法

按任务要求先找 Cast 捕获失败的做法：`nest/cast.go:188-192` 只把 `CaptureEntities` 的错误返回业务，**没有**事务级“必须失败”记号——业务吞掉 Cast
捕获错误同样会继续提交。仓内唯一的“业务吞错也强制失败”机制是同一函数族里的新建锁冲突 `createLockBusy`（RR-20260926-48，`nest/rollback.go`
字段注释、`nest/execution.go:207`）。清单推荐的实质是“标记事务必须失败”，所以照 `createLockBusy` 实现；Cast 捕获失败未改（不在本条范围，已在批次报告里列为同类观察）。

## 决策

- `RollbackTx.createCaptureFailed`：`CaptureCreatedEntity` 里 `CaptureEntities` 失败时记下第一次的错误（之后照旧返回给 `CreateInScope`，由它撤销发布）。
- `invokeWithTransaction`：紧接 `createLockBusy` 的检查，`createCaptureFailed` 非空且 handler 的错误里还没有它时 `errors.Join` 进去，走同一个回滚分支。
  业务自己返回了该错误（`CreateInScope` 包裹后的形式）时 `errors.Is` 已成立，不重复拼接。
- 不区分回滚策略：与 `createLockBusy` 不同，这里不重新准入（捕获错误不是 `ErrLockTimeout`），所以 RollbackNone 事务也不会因此重复执行；
  强制失败只阻止提交。memory 快路径的 `memoryHandlerCreates.CaptureCreatedEntity` 恒返回 nil，不受影响。
- 嵌套 `RunIsolatedTransaction`：捕获者是嵌套事务，记号只让嵌套事务失败，外层照常由业务处理 `RunIsolatedTransaction` 的错误。

## 文件与行为

- `nest/rollback.go`：字段 `createCaptureFailed`；`CaptureCreatedEntity` 失败时记录。
- `nest/execution.go`：handler 结束时并入错误。
- `entity/manager_factory.go`：`CreatedEntityCapturer` 注释补“Nest 事务同时记下，handler 结束时整条回滚”。
- `docs/USER_GUIDE.md` §4：handler 内新建的约束段补一句。
- 回归：`nest/create_capture_failure_promises_test.go` `TestCreateCaptureFailureFailsTheTransactionEvenIfSwallowed`（新 kind 236 的实体
  `CaptureRollback` 恒失败；RollbackState strict handler 改声明实体并 `MarkPersist`，新建失败后吞错返回成功 → 回复 `errors.Is` 捕获错误、不含
  `ErrLockTimeout`、committer 0 次、声明实体值恢复、X 未发布）。

## 兼容性

行为收紧：此前“新建捕获失败 + 业务吞错”的 handler 会提交，现在整条回滚并把捕获错误交给调用方。捕获失败本身（DAO 不可快照、durable 事务内建
remote-managed 实体等）已有文档约束，正常生成工程不会触发。无导出 API / 配置变化。
