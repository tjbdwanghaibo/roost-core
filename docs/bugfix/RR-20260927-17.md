# RR-20260927-17：Remote L2 快照键可选部署前缀

问题：[RR-20260927-17](../bug/RR-20260927-17.md)（OPEN-ITEMS C11）。日期 2026-09-27。基线 `d4234c9`，分支 `fix-r7-de`。
状态：已修复，本地验证通过，本地提交，未推送 / 发布。codebase-memory 图谱过期（09-26），定位以当前源码与 `git grep` 为准。

## 决策

### core

- `remoteentity.Config.SnapshotL2KeyPrefix`（缺省空）。`NewSnapshotL2StoreWithKeyPrefix(redis, ttl, prefix)` 给 store 带上前缀；
  全部 L2 操作（`Get` / `Set` 的 CAS 脚本 / `Delete` / `DeleteAtVersion`）改走 `store.key`：前缀为空时就是原来的 `remoteSnapshotL2Key`（逐字相同），
  非空时是 `<prefix>:remote_entity:snapshot:…`。`NewSnapshotL2Store` 签名与行为不变（外部调用方无需修改）。
- `ValidateSnapshotL2KeyPrefix`：空值合法；拒绝首尾 / 内部空白（与 kit `mods.KeyPrefix` 同一规则），拒绝 `{` `}`——L2 脚本只操作单键，不需要同槽，
  带 Redis Cluster hash tag 会把全部快照键钉在同一个槽。`Assemble` 用它构造 L2，非法值装配失败。

### kit：接哪个“部署前缀”

先核对了 kit 现有的前缀配置：

| 候选 | 实际语义 | 用作 L2 前缀的问题 |
| --- | --- | --- |
| `redis.key_prefix` | **不存在**（`kit/redis` 只读 addr / password / db / pool / cluster_addrs） | — |
| `<service>.key_prefix`（`mods.KeyPrefix`，account / chat / mail …） | 每个 kit 服务自己的 Redis 键前缀，必填、无缺省，理由正是“两个部署共用一个 Redis 会共享状态” | 属于各服务，Remote Mod 没有对应的一项 |
| `nats.prefix` | NATS subject / JetStream 命名空间，未设时 `"roost"`，生成样例显式写 `prefix: roost` | 管的是 NATS 不是 Redis（共用 Redis 与共用 NATS 是两回事）；而且所有生成工程都显式设了它，派生会让它们升级即换键 |
| `remote_entity.lock_key` | Remote 版本锁的键前缀 / 锁身份，缺省 `"e"`；Cluster 下必须带 hash tag（RR-20260924-25） | 已自定义它的部署升级即换键（违背“缺省键不变、无需迁移”）；Cluster 下带 hash tag，派生后全部快照键落同一个槽；锁身份与缓存布局耦合 |

语义最贴切的是 kit 已有的 **`<service>.key_prefix` 约定**（“按部署隔离 Redis 键”），但它是必填、按服务的；为了满足“缺省为空、键不变”，在 Remote Mod 里按同一约定的校验规则
单列 `remote_entity.snapshot_l2_key_prefix`（与 `snapshot_l2_ttl` 同组命名，名字写明只作用于 L2 快照键，不暗示锁键 / 标记键也被加前缀），可选、缺省空。
没有从 `nats.prefix` 或 `lock_key` 自动派生：两者都会让已经配置了它们的现有部署在升级时换键，与“缺省键不变、无需迁移”冲突。
**这是对清单“kit 从部署前缀接线”的一个判断**：kit 里不存在一个能在缺省下保持键不变的部署级 Redis 前缀，所以接线的是新的显式配置项；若维护者更希望从 `lock_key` 派生，
需要接受“已自定义 lock_key 的部署升级后 L2 冷启动一次”以及 Cluster 下剥掉 hash tag 的额外规则。

- `kit/remoteentity/remote_entity_mod.go` `Init`：读 `remote_entity.snapshot_l2_key_prefix`，经 `ValidateSnapshotL2KeyPrefix` 校验（错误点名配置项），写入 `Config.SnapshotL2KeyPrefix`。
- 生成配置样例（`codegen/internal/roost/catalog.go` 的 `remote_entity` 块）：加 `snapshot_l2_key_prefix: ""` 与说明注释（空 = 键不变；共用 Redis 的部署各设不同值，如 `roost:<project>`；同一部署各节点一致；不带 hash tag）。
- `docs/USER_GUIDE.md` §6：键格式、何时要配、缺省兼容、滚动修改前缀的影响（新旧节点互不可见、`Cached` 读可能在 `snapshot_l2_ttl` 内读旧前缀下的旧快照，应整体重启）、校验规则、作用范围。

## 兼容性

- 缺省（不配置或配空串）时 L2 键与旧版本逐字相同，不需要迁移；`NewSnapshotL2Store` 不变。
- 新配置项 `remote_entity.snapshot_l2_key_prefix`、新导出 `Config.SnapshotL2KeyPrefix`、`NewSnapshotL2StoreWithKeyPrefix`、`ValidateSnapshotL2KeyPrefix`（供 CHANGELOG）。
- 新生成工程的 `config.game*.yaml` 多一行 `snapshot_l2_key_prefix: ""`（值为空，行为不变）；已生成工程不改也不受影响。
- 设置 / 修改前缀等于换一套空的 L2（它是缓存，快照会从权威重新发布），应整体重启而不是滚动。
