# RR-20260923-02 修复：逐帧记录交付，部分成功后以全量恢复内容基线

- 问题：[RR-20260923-02](../bug/RR-20260923-02.md)。状态：已修复并验证，未发布。

## 改动与选择

- `session.encode` 返回包内 `encodedFrame{payload, next}`：每帧对应其准入后的会话状态。仅拆出后续帧时追加副本，保留前一帧状态；通常的一帧路径沿用原来的单次会话克隆。
- `Manager.Flush` 每次 Push 成功立即采纳对应状态，并递增真实准入帧数。后续帧失败不撤销前缀。
- 遇到 `ErrRetryLater`，仍 abort 内容捕获、保留 dirty、重新安排本 tick 的 subject；对本轮有帧准入的会话，将受影响且仍订阅的内容改为等待全量快照。离开中的订阅仍保持离开。下一 tick 的全量可以重新建立内容基线，尚未收到任何帧的会话继续原流程。
- `Transport` 注释明确 Push 的单帧准入语义；包注释说明内容版本、订阅意图与交付引用表的区别。

选择全量恢复而不缓存失败 tick 的编码结果：失败之后可能出现新 dirty、换 profile 和退订；缓存并重放旧 payload 会引入另一套跨 tick 所有权。全量是已有协议能力，允许在同一内容版本重建视图，客户端必须按 Full 语义接收，不能把它当成可丢弃的重复 delta。

## 兼容与代价

公开 Go API、Frame/Subject 线格式、持久化水位门槛不变；部分成功后的重试可能多发全量，交换故障恢复的确定性。会话不会仅因 `ErrRetryLater` 被关闭。`FramesAdmitted` 现在也准确计入最终失败 tick 中已成功的帧。

多帧 tick 需要保留每帧的会话状态副本；正常单帧路径不新增逐帧克隆。未做吞吐/分配基准，不宣称性能提升。
