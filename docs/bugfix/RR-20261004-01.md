## 根因（基线行号）

- `remoteentity/versioned_lock.go:120-125` `TryLock`：取锁脚本 Eval 出错（ctx 截止 / 网络错误）直接返回，本次 token 不留存；脚本若已在 Redis 执行，owner 就是一枚本地再也认不出的 token。
- `remoteentity/versioned_lock_lua.go:11`：取得条件只认空闲或 RR-20260930-21 的单个 `releaseUnknownToken`（`versioned_lock.go:45`，只由释放无答复写入）。下一次 `TryLock` 的新 token 只得到 `{0,0,0}` → `ErrVersionedLockNotAcquired`，直到 LockTTL（缺省 24h）。

## 决策

问题的本质和 RR-20260930-21 一样："本锁对象较早的一代没有拿到 Redis 的明确答复"。但"未知"的代际可以不止一个：释放未知（A）→ 取锁执行后丢回复（B）→ 取锁根本没发出（C）……每一个都可能是 Redis 上的 owner（谁的脚本最后执行谁就是），而迟到落地的脚本还可能在本地已经得到明确答复之后才把租约占上。所以不在本地记"哪几个 token 结果未知"，而是让 token 自带先后，由 Lua 判定：

- **token 按锁对象分代**：`newVersionedLock` 生成随机 `tokenPrefix`（`crand.Text()` + `.`，只有这个锁对象会铸造带它的 token），`TryLock` 在 `l.mu` 下 `tokenSeq++`，`token = tokenPrefix + 十进制 tokenSeq`。
- **Lua 判定**：`TryLock` 传 `ARGV[3] = tokenPrefix`、`ARGV[4] = seq`。`owner == false`，或 owner 带同一前缀且序号**小于**本次，进入取得分支（分支内容不变：`INCR` fence、`HSET owner`、`PEXPIRE`，version 字段不动）——同一条脚本里换成新 token、新 fence，是新的一代；owner 是别人、或序号不小于本次，照旧 `{0,0,0}`。
- **为什么"较早的本对象 token"一定可以取回**：Lua 判定只在本地 `acquired=false` 时发生（`TryLock` 先查本地，持有中直接拒绝），此时本锁对象没有任何一代在本地持有；Redis 上带本对象前缀的 owner 只能是结果未知留下的（取锁回复丢失或迟到、释放无答复、放弃未准入许可的清理 `versionedAbandonLua` 失败），取回它不会抢走任何人的租约。别的锁对象（别的进程，或本进程 wrapper 重建后的新锁对象）前缀不同，照常走 NotAcquired。
- **为什么只认"更早"**：迟到落地的旧代取锁脚本带的是更小的序号，遇到已取得的新代际（序号更大）得不到取得分支，挤不掉新代际（RR-20260924-20）；而新代际明确释放之后才落地、占上空闲租约的旧代脚本，下一次 `TryLock` 的序号更大，照样取回。
- **RR-20260930-21 的路径并入这条判定**：`releaseUnknownToken` 字段删除，`releaseOutcomeUnknown` 只清本地 `acquired`（仍只对当前代际生效）；释放未知的那一代同样是"本对象较早的 token"。
- authority 模式（正式 kit 装配）与之前一样，取得后对新 token 做 `GrantWrite`，fence / version 来自 Mongo 许可；Redis-only 兼容模式 fence 来自 Redis 计数器递增。两种模式都是"一次取得一枚 fence"，不放宽 fence 与版本比较。
- 续期按 RR-20260926-43：没拿到答复的那一代从未在本地持有，不登记续期；重新取得的新代际由 `startAsyncTouchLocked(newToken)` 登记。

### 未采用的方案

1. **WANTED 的候选：Eval 出错时把 token 记进 `ARGV[3]`（与 RR-21 共用单个字段）**：单字段只能记一个。覆盖写会在最常见的场景里回退 RR-21——释放未知（owner A）之后 Redis 仍不可达，下一次取锁根本没发出去，A 被这次没执行的 token 覆盖，恢复后取不回 A（`TestVersionedLockUnsentAcquireKeepsUnknownReleaseReclaimable` 守护）；不覆盖又取不回执行了的取锁。"首个 + 最近一个"两个字段仍会漏掉中间那一代（`TestVersionedLockReacquiresAcrossUnknownChain`）。
2. **本地记全部未知 token、作为 `ARGV[3..n]` 交给 Lua**：持续故障时每次写都追加一枚，无界；在得到明确答复时清空，又会漏掉之后才迟到落地的脚本（`TestVersionedLockReacquiresAfterLateAcquireScriptLands`）。
3. **按前缀取回、不比较序号**（本对象任何 token 都可取回）：迟到落地的旧代取锁脚本带着同样的前缀，会把已经取得的新代际挤掉，违反 RR-20260924-20（`TestVersionedLockLateAcquireScriptCannotTakeNewGeneration` 守护）。
4. **在锁 hash 里另存 holder / seq 字段**：滚动升级时旧版本进程取锁不写这两个字段，留下的旧字段会和别人的 owner 配对，误判成"本对象较早一代"而挤掉别人；把身份编进 owner token 本身没有这个问题。
5. **Eval 出错后立即补一次查询或放弃脚本**：同样拿不到答复时还是未知，而且多一次往返；交给下一次 `TryLock` 的同一条脚本原子判定更简单。

## 兼容性

- **token 格式**：从 `crand.Text()`（26 字符 base32）变成 `<26 字符 base32>.<十进制序号>`。token 只作为 Redis owner 与 Mongo 许可 `_grant_token` 的不透明身份，没有代码解析或限制它的格式；随机部分仍是 `crypto/rand`，按锁对象生成。
- **滚动升级**：脚本 KEYS 不变，`ARGV` 由 3 个变 4 个。旧版本进程的脚本只认空闲或它自己的精确 token，不认识也不会动新格式的 owner；新版本只取回带自己随机前缀的 owner，旧版本的 token 不含 `.`、前缀也不可能相同。两版混跑时互相只按"别人持有"处理，与之前一致。
- 行为放宽只在一处：本地未持有时，Redis 上本锁对象更早一代的租约被视为可取回。它不扩大到别的锁对象，也不改 fence / 版本 / 许可的校验。放弃未准入许可的清理（`versionedAbandonLua`）失败留下的 owner 以前要等 TTL，现在下一次 `TryLock` 也会取回。
- 无持久格式、配置或公开 API 变化。

## 对抗性自查

- **fence / 版本**：取得分支未改；每次取得 `INCR` 一枚 fence（authority 模式另由 Mongo 许可发 fence），旧代 fence 不复用；版本缓存只由 unlock 脚本写。
- **迟到回复**：旧代的取锁脚本序号更小，遇不到取得分支；旧代 unlock / touch / refresh 只匹配精确 token，`releaseOutcomeUnknown` 与 Touch / Refresh 的本地清除都只改 `l.token == token` 的代际。
- **锁序**：`tokenSeq` 只在 `TryLock` 的 `l.mu` 临界区内递增与读取；`tokenPrefix` 创建后只读。
- **序号精度**：Lua 5.1 数值是 double，序号在 2^53 以内精确；单个锁对象一次取锁一号，达不到。
- **别的锁对象**：随机前缀 26 字符 base32（130 bit），不会与别的锁对象相同；没有前缀的 owner（旧版本 token、测试里的 `someone-else`）`string.sub` 比较不等。
