# RR-20260926-70 修复：框架退回 remove 撤销的政策订阅，在实体重新登记后交还政策自动重新提交

问题：[RR-20260926-70](../bug/RR-20260926-70.md)（复现 [REPRO-2026-09-26-06 §6](../bug/REPRO-2026-09-26-06.md#6-rr-70兜底-remove-后-interest-不再重新订阅)）。日期 2026-09-27。
实施基线：`2373e21` + RR-69 `e5c55fe` + RR-72 `2fe616f`。状态：已修复，本地验证通过，已本地提交，未推送/发布。

## 根因（基线行号）

RR-59 的兜底 `RetractUnloadedSubject`（`sync/entitysync/manager.go:480`，触发点 `entity/unload_resync.go:169-173` 队列满、`:237` 权威缺失、`:246`
重试用尽）走与 `Unregister` 相同的退役：`retireLocked` 清空每条订阅的来源、持有者收到 ObjectRemove，全部交付后 subject 被忘掉。订阅是政策说的，
框架替政策撤销了它却不告诉政策：`policy/interest.go:423-425` 的 `hold.subscribed` 仍为 true，`Apply` 只对新事件与重试表说话，实体之后重新登记
（业务访问、RR-55 successor、普通 Register）时谁也不再订阅，观察者仍在 AOI 内也永久看不到它，直到这对 pair 自己变化。Group（成员×实体全订）与
Direct（调用方绑定）同理。

## 修复（维护者 2026-09-27 批准：通知政策重新提交订阅）

### Manager（`sync/entitysync/policy_queue.go`、`manager.go`、`subscriptions.go`）

- 新导出 `RetractedSubscription{Session, Subject}` 与 `Manager.NewSubscriptionSourceWithResubmit(resubmit func([]RetractedSubscription))`：与
  `NewSubscriptionSource` 相同，另外登记来源所属政策的重新提交入口。`SubscriptionSource` 增加未导出字段 `resubmit`。
- **撤销时标记**：`RetractUnloadedSubject` 在 `subj.mu` 内、`retireLocked` 清空来源之前，把每条订阅里带 `resubmit` 的来源连同会话记入
  `retracted[subjectID]`（必须在 forget 能发生之前就位：剩余订阅为 0 时 forget 就在同一调用里执行）。默认来源（`Manager.Subscribe`）与普通
  `NewSubscriptionSource` 不记录——无政策时行为不变。
- **重新登记时交还**：同 ID 新 subject 登记（`register` 的新建分支，含 forget 登记排队的 successor、业务 `Register` / `RegisterAfterRetirement`、
  `Group.AddSubject`）后，把记录移入待交付队列并 `WakeSync`。Rebind 到同一 subject（未撤销的正常卸载重载）不涉及记录。
- **交付位置**：下一次 `Flush` 的政策阶段（`applyPolicies` 最前，持有 flushGate、不持有任何 Manager 锁，与 `RegisterPolicy` 处理器同一位置），按来源
  分批调用 `resubmit`。它可以取政策自己的锁并 Subscribe（不得调用 Flush、不得阻塞）；政策订阅在同一次 Flush 的捕获前完成，订阅者在这次 Flush
  收到 create。选这里而不是 `Register` 的调用路径：Register 可能在政策持锁时被调用（`Group.AddSubject` 持 `g.mu`；`Interest.Apply` 持 `in.mu` 的
  Unsubscribe 可能经 forget 登记 successor），在那里回调政策会自锁。`policiesPending` 计入待交付项，`Drain` 等它们交付。
- **记录的释放**：来源自己释放这对 pair（缺席时 `Unsubscribe` 返回 `ErrSubjectNotRegistered`、退役中返回 `ErrSubscriptionNotFound`）时删除对应
  记录与待交付项；业务 `Unregister` 该 ID 时删除该 ID 的全部记录（在 `subj.mu` 内、forget 之前；业务的注销意图优先，与 RR-59 的 `unloadRetracted`
  清除同一口径）；`Manager.Close` 清空。条数不超过撤销时的订阅数，并随政策释放 pair 减少。`resubmitMu` 是叶子锁（可在 `subj.mu` 下取，持有时不取
  其他锁、不回调）；`resubmitEntries` 原子计数让退订 / 登记 / Flush 的热路径在没有记录时不加锁。

### 政策（`sync/entitysync/policy/interest.go`、`group.go`、`direct.go`）

三种政策都改用 `NewSubscriptionSourceWithResubmit`，按自己的判定重新提交：

- **Interest / AOI**：`resubmit` 在 `in.mu` 下找仍在 `held` 里、`subscribed` 的 pair（主体与会话匹配），走既有 `subscribe`：来源视图选择
  （`selectedProfile`）、`ViewSets` 校验、Manager 的优先级与字段白名单照旧；被拒绝的进入重试表，下一次 `Apply` 以 `Retry` 报告并继续重说。
  缺席期间已释放的 pair（观察者走远的 Leave 事件、关系解除、`Hide`）不在 `held` 里，不恢复；已在重试表里的（`subscribed=false`）由重试表处理，不重复。
  不需要调用方 `Apply`（queue 与手动两种模式都在 Flush 的政策阶段完成）。
- **Group**：实体仍在组里、会话仍属于某个成员时以组视图重新订阅；缺席期间 `RemoveSubject` / `Leave` 过的不恢复。拒绝（会话已关闭、容量不足、实体又被
  注销）没有调用方可报告，记 Warn 后放弃。
- **Direct**：新增 `mu` 与当前绑定表（成功的 `Bind` 到 `Unbind` 为止），`Bind` / `Unbind` / `resubmit` 在 `mu` 下串行；按调用方当前绑定的视图重新订阅，
  缺席期间 `Unbind` 过的不恢复；拒绝记 Warn。`Bind` 被拒绝时保留原绑定（与 Manager 拒绝订阅时保留原订阅一致）。

未采用：Manager 按记录自己重新订阅（绕过政策的可见性与视图判定，缺席期间离开 AOI 的观察者也会被恢复）；撤销时就让政策把 pair 放进重试表
（实体若永不回来，每次 Apply 都产生拒绝，`Drain` 因 `queuedPending` 永不结束）；在 `Register` 调用路径上同步回调政策（上述自锁）。

## 对抗性自查（RR-69 / 70 / 72 合并）

- **订阅者视图不重复、不丢、remove-before-create**：交还只发生在同 ID 新 subject 登记之后，而新 subject 只能在 forget（最后一个 remove 交付或最后一个
  订阅者会话关闭）之后出现；退役期间的订阅仍被拒绝。重新提交走正常 Subscribe：同一会话只有一条订阅，同来源同视图重复订阅是空操作，所以政策自己
  已重说过的 pair 不会多一次 create（多来源用例断言恰好一次 create）。Interest 已在重试表里的 pair 不经 resubmit 重复说。RR-69 保证重新登记的
  subject 保留脏通知器，恢复后的变化照常发送。
- **政策判定不被绕过**：Manager 只交还“哪个来源、哪个会话、哪个 subject”，不交还视图、不自己订阅；Interest 用当前 `held` 的来源集合重新选视图并经
  `validateProfile` / Manager 的白名单与优先级；Group 用组视图、Direct 用调用方当前绑定的视图。缺席期间政策已释放的 pair 不恢复（Interest 离开 AOI、
  Group Leave / RemoveSubject、Direct Unbind 均有回归或由绑定表判定）。
- **与 RR-55 排队**：successor 登记（包括 RR-72 带 done 的业务排队）触发交还；业务 `Unregister`（RR-55 的退役）不记录，且清除卸载退役留下的记录。
  RR-72 使 done 在卸载退役中也被调用，demo scene 的 `registeredLater` → `apply()` 与 resubmit 叠加时只是一次幂等的重说。
- **与 RR-59 重载**：正常卸载重载走 `Rebind`，不经撤销，不涉及记录；只有 `RetractUnloadedSubject` 记录。退役中 `Rebind` / `Register` 排队（不变）。
- **与 RR-35 撤销**：`RetractSyncSubject` 语义不变（经 `Unregister`，不记录）；事务内新建后回滚的实体不会被“恢复订阅”。
- **多来源独立撤销**：记录按来源逐条保存、按来源分批交还；一个来源缺席期间释放只删除自己的记录（回归：Direct 解绑、Group 撤销、Interest 撤销互不影响）。
- **锁序**：新增 `m.mu → 状态锁`（RR-69，状态锁为叶子）与 `subj.mu → resubmitMu`（叶子）。resubmit 回调在 Flush 政策阶段、不持有 Manager 锁时执行，
  政策锁 → Manager 锁的既有顺序不变；政策从不在持锁时调用 Flush 或等待 flushGate。`Register` 调用路径上不回调政策（避免 `Group.AddSubject` /
  `Interest.Apply` 持锁时自锁）。`unsubscribe` 的 forget 移到解锁后（原 defer 顺序会在持锁时运行，分支当前不可达）。
- **慢会话失败不拖垮他人**：重新提交被拒绝（某会话已关闭、容量不足）只影响该 pair：Interest 进重试表，Group / Direct 记 Warn；不返回政策错误，
  不会让 `applyPolicies` 失败而中止整次 Flush。
- **goroutine 泄漏**：三笔都不新增 goroutine。记录随政策释放 / 业务注销 / Close 回收。

## 未验证项与边界

- 实体被撤销后、政策重新提交之前（重新登记到下一次 Flush 之间）又被撤销一次：此时新 subject 尚无政策订阅（`SubjectAwaitsReload` 为假，重载器不会
  撤销它，只有非政策来源的订阅者才会触发），若发生，Interest 的重试表会继续重说，Group / Direct 记 Warn 后放弃。没有构造该场景的回归。
- 实体在权威里被删除、永不重新登记，而政策一直持有这对 pair（业务没有 Hide / Leave / RemoveSubject / Unbind）：记录一直保留，条数与政策自己持有的
  pair 同量级。
- 正式生成工程里没有构造“卸载 → 重载失败 → 退回 remove → 重新登记”的端到端场景；以 entitysync / policy 包内真实 Manager 与三种政策验证。
- 未跑故障矩阵（按任务要求）。
