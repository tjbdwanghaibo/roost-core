# RR-20260913-06:L2 回填绕过同版本内容冲突检查

**仓库 / 位置**:roost-core `cache/store.go`、`cache/atomic_local.go`、`cache/read_through.go`,
`entity/remote_snapshot.go`。**修复单元**:U-0181(C8)。**定位文档**:TROUBLESHOOTING T-75。

## 问题

`ReadThrough` 的 L2 命中路径直接 `setLocal(value)`。确定性交错:L1 为空,一次读在 L2 取到 A 后
暂停;另一路 Publish 同版本的 B 成功写进 L1;放行之前那次读 —— 回填把 L1 改回 A,没有任何错误。
并发读取与推送路径对同一个版本形成了不同语义。

## 根因

同版本内容校验只存在于 `Publish` 的外层,而写 L1 的入口不止一个:发布、loader 填充、L2 回填。
只在一个入口加锁不能约束其他入口。Get-then-Set 的 TOCTOU 也说明校验必须与写入在同一把锁下。

## 方案选择

- **回填前 Get 一次比较。** 与写入不原子,正是审查描述的交错。
- **把校验放进本地存储的写入原语(采用)**:`StoreConfig` 新增 `Conflict(old, next) bool` 钩子,
  `AtomicLocalStore.SetWithTTL` 在分片锁下、`Stale` 之后判它,冲突返回新的 `ErrConflictingWrite`。
  于是**所有**写 L1 的路径共用一条规则。回填遇到冲突时不覆盖,把 L1 当前值(本进程已经交出去的
  那份)返回给调用方。

`Stale` 与 `Conflict` 分工明确:前者答"next 是不是更旧",后者答"next 是不是对这个版本撒了谎"。

## 改动

- `cache/store.go`:`StoreConfig.Conflict`,`ErrConflictingWrite`(与 `ErrStaleWrite` 不同,它永不被
  静默吸收:迟到只是迟到,撒谎是错的)。
- `cache/atomic_local.go`:分片锁下判 `Conflict`。
- `cache/read_through.go`:L2 命中回填时若 `setLocal` 返回 `ErrConflictingWrite`,回读 L1 并返回它。
- `entity/remote_snapshot.go`:配置 `Conflict: remoteSnapshotSameVersionConflict`。

## 证明

`entity/snapshot_l2_conflict_promises_test.go` 的 `TestL2BackfillCannotOverwriteAPublishedSameVersionValue`:
L2 替身的 `Get` 带屏障,一次读在取到 A 之后被钉住;此时 Publish 同版本的 B 进 L1;放行后断言 L1
仍是 B。屏障是 channel 控制的确定性交错,不是概率竞态。

修前红:`the L2 backfill overwrote the published same-version value: L1="A"`。
修后 cache 与 entity 含 `-race` 全绿。

## 未做 / 边界

- `Stale` 的回填仍然把**更旧的 L2 值返回给调用方**而 L1 保留新值,这是既有行为,与冲突不同,
  本次没有改。
- `Conflict` 是可选钩子,只有 entity 配置了它;其他使用 cache 包的调用方行为不变。
