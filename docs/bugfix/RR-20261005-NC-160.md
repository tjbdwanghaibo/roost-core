# NC-160 修复：脚本出错原样返回，非原子降级只留给没有 Lua 的适配器

问题：[RR-20261005-NC-160](../bug/RR-20261005-NC-160.md)。2026-10-05，分支 `revn12`，基线 `45d4bc1c`。

## 根因

`failurelog/failurelog.go` 的 `tryAppendWithScript` / `tryDeleteWithScript` / `tryPurgeWithScript`（基线 `:237-305`）把任何 Eval 错误都报成“没走脚本”，调用方随即走 RPUSH / LREM / LLEN+DEL 降级；生产驱动只会在结果未知时报错，降级因此成了第二次执行。

## 决策

- 三个 `tryXxx` 返回 `(handled, err)`：Eval 报错 → 返回包装后的错误（`failurelog: <op> script: %w`，保留 `errors.Is`），**不降级**；Eval 返回 `(nil, nil)`（替身没有 Lua，生产驱动不会这样返回）→ 降级并计 `failurelog_degraded_total`；脚本执行了但返回值不是整数 → 按“已执行、结果未知”报错（`errUnexpectedScriptResult`），同样不降级。
- 与 [NC-21](RR-20261004-NC-21.md)（cache RefHMap 删除降级）、[NC-100](RR-20261005-NC-100.md)（驱动不重放脚本）同一契约：结果未知交给调用方，不猜错误文本是否“肯定没执行”。
- 未采用：按 go-redis 的 `redis.Error`（服务端错误回复）区分“确定没执行”后继续降级——failurelog 不依赖驱动类型；服务端错误回复里也有脚本执行到一半报错的情况。也未采用写令牌认领（改持久格式），与 N04 方向判断③一致，留给维护者。
- 删除“沿用 cache.refhmap.write_degraded_total 约定”的过时注释（那个降级与指标已由 NC-21 删除）。

## 文件与行为

- `failurelog/failurelog.go`：上述三处与 `degraded(op)`、`scriptError`，中文注释写明契约与编号。
- `failurelog/unknown_result_promises_test.go`：append / delete / purge 三个“脚本已执行、回复丢失”反例；没有 Lua 的替身仍走降级的控制。
- `failurelog/unknown_result_integration_test.go`（`-tags integration`）：生产驱动经本地代理连真实 Redis，代理吞掉第一条 EVAL 的回复并断开。
- `kit/scripts/integration/dataengine-env.sh`：故障矩阵的 integration 包列表加入 `./failurelog`（根包 `TestFaultMatrixScriptNamesEveryFullEnvironmentSuite` 要求）。

行为变化：结果未知时 `AppendRaw` / `DeleteRaw` / `Purge` 返回错误（以前降级后多半“成功”）。bus `deadLetter` 记 `bus: write dead letter failed`（错误里带 msg_id），inbox 不标 failed；运维可先 `ListDeadLetters` 核对是否已写入。无 API / 持久格式变化。
