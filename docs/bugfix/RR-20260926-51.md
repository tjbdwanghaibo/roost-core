# RR-20260926-51 修复：停机预算先按声明值分配、未声明 Mod 固定保底不参与缩放；生成默认 `shutdown.total_timeout` 改为 60s，部署宽限期 65s

问题：[RR-20260926-51](../bug/RR-20260926-51.md)（复现 [REPRO-2026-09-26-05 §4](../bug/REPRO-2026-09-26-05.md)）。前序：[RR-20260926-42 修复](RR-20260926-42.md)。
日期 2026-09-26；实施基线 main `3e26f91`。状态：已修复、本地验证通过，已本地提交，未推送/未发布。

## 根因

RR-42 的 `app/app.go` `modStopBudget` 把“声明预算之和 + 未声明 Mod 数 × 5s 基准”当成需求，需求超过剩余时间时**全部**按
`剩余 / 需求` 同比缩放。于是：

- 总时长足以覆盖声明值时仍削减它：总 50s、dataengine 声明 30s、10 个未声明 → 需求 80s，dataengine 只得 25s。
- 声明值偏大时把先停的 Mod 压到接近零：总 30s、dataengine 声明 120s → nest 1.071s（修前均分 6s），nest 超时会中断整条关闭链。
- 生成默认（总 30s、dataengine 30s）每次停机都走缩放分支并告警，nest 约 3s。

## 决策（按维护者 2026-09-26 批准的修复约束实现）

`modStopBudget(remaining, mod, pending, later)` 每停一个 Mod 重新规划（前面的 Mod 提前结束省下的时间留给后面），规则：

1. 保底之和 = 本段未声明 Mod 数 × `undeclaredModStopFloor`（**3s**）；声明预算上限 = 剩余 − 保底之和。
2. 声明值之和 ≤ 上限：声明的 Mod 恰好拿声明值，未声明的 Mod 均分 `剩余 − 声明值之和`（每个 ≥ 3s）。
3. 声明值之和 > 上限：只缩放声明值（按 `上限 / 声明值之和`），未声明的 Mod 恰好拿 3s 保底——保底是固定下限，不参与缩放。声明的 Mod 记 Warn
   `mod stop budget scaled down`（declared / granted / remaining / floor）。
4. 剩余 < 参与规划的 Mod 数 × 3s（连保底都给不起）：所有 Mod（含声明的）均分剩余并记 Warn `cannot cover the per-mod floor`。

参与规划的 Mod = 本段自己及之后的 Mod + 之后另一段（服务专属段之后的共享段）中**声明了预算**的 Mod；另一段未声明的 Mod 仍不参与本段均分（与 RR-42 及其之前相同）。
没有任何声明时三种分支都退化为 `剩余 / 本段剩余 Mod 数`，与旧行为等价（第 4 种情形多一条 Warn，预算值不变）。
无总截止时间的兼容路径不变：声明的 Mod 用声明值，其余 `defaultModStopTimeout`（5s）。

**保底取 3s 的理由**：REPRO §4 反例一要求总 50s 时 dataengine（其后 6 个未声明 Mod）拿满 30s，保底须 ≤ (50−30)/6 ≈ 3.33s；反例二要求 nest ≥ 2s；
3s 与生成配置 `nest.request_timeout` 同值（Nest 排空已准入请求的上限）。保底为代码常量，未新增配置项。

**生成默认值**：`shutdown.total_timeout` 30s → **60s**（`dataengine.shutdown_timeout` 仍 30s）；部署终止宽限期改为 **65s**
（k8s `terminationGracePeriodSeconds`、compose `stop_grace_period`、systemd `TimeoutStopSec`、`deploy/dev/run.sh` 两处 `kill -9` 前的等待）。
App 在配置缺失 `shutdown.total_timeout` 时的运行时兜底仍为 30s——提高它会让未重新生成部署模板（宽限期 45s）的旧工程在停机中途被 SIGKILL。

未采用：沿用 5s 保底（反例一 dataengine 只得 20s，违反“总时长足够时给满声明值”）；把保底做成配置项（约束未要求，另增一个需要与宽限期联动校验的键）。

## 兼容性 / 默认值变化（供 CHANGELOG 与部署说明）

- 行为：装配了声明预算 Mod 的服务，总时长充足时声明的 Mod 拿满声明值（不再被一起缩放）；声明值偏大时先停的 Mod 保有 3s 保底，
  声明的 Mod 拿到“剩余 − 保底”。10 个 Mod 且总 30s 这类旧配置下 dataengine 比 RR-42 少（15s → 12s），比修前均分（4.29s）多。

  改 60s 时须同时把宽限期调到 ≥ 65s（k8s / compose / systemd / dev 脚本）。
- 告警文案变化：`mod stop budget scaled down: shutdown.total_timeout minus the other mods' floors cannot cover every declared budget`；新增
  `mod stop budget: shutdown.total_timeout cannot cover the per-mod floor; splitting the remaining time evenly`，属性键 `default_mod_budget` 改为 `floor`。
- 无新增/删除导出 API；超时语义（`stopIncomplete` 中断后续关闭、保留资源）不变。

## 交付前对抗性自查

- **总时长上限不被突破**：每个 Mod 的截止时间都由 `shutdownCtx` 派生（`context.WithTimeout(parent, budget)` 取两者较早者）；各分支预算都 ≤ 剩余：
  granted 分支声明值 ≤ 上限 ≤ 剩余、未声明份额 = (剩余 − 声明和)/U；scaled 分支声明值缩放后之和 = 上限，未声明拿保底且剩余 ≥ 参与数 × 保底；均分分支 = 剩余/参与数。
- **停机链不被先停 Mod 超时中断**：只要剩余 ≥ 参与数 × 3s，每个未声明 Mod 至少 3s，大声明值只能挤占上限以内的部分（反例二 nest 1.07s → 3s）；
  更小的总时长下均分，不会出现零截止时间。Mod 真需要更久时仍可能超时，这与修前语义相同（`stopIncomplete` 中断后续关闭）。
- **RR-17“超时保留所有权”**：`stopModsReverseBefore` 的 `stopIncomplete` 分支、`Service.Shutdown` 超时不停 Mod、DataEngine `Runtime.stop` 的
  “Close 返回 nil 才标记已关闭、可重试”均未改；本次只改每个 Mod 的截止时长。
- **无声明等价**：`TestUndeclaredStopBudgetsKeepTheEvenSplit` 修前修后均通过；既有 `TestAppUsesConfiguredShutdownTimeout`、`TestStopModsReverse*` 通过。
- **并发**：规划在停止循环的单 goroutine 内完成，只读 Mod 声明值；`-race -count=20` 通过。
