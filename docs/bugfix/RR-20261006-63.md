# RR-20261006-63 修复：追帧页离开房间 goroutine 发送，慢客户端只拖慢自己

问题：[RR-20261006-63](../bug/RR-20261006-63.md)（F04-7）。基线 `a7285da6`，分支 `lockstep`，提交 `99a3e99f`。

## 根因

`Tick` 在房间唯一的 goroutine 上同步等可靠通道的发送，且用调用方的 ctx；KCP 发送窗口满时没有期限就一直阻塞。

## 决策

“加期限”与“改异步”两条里选异步 + 期限：只加期限的话，每个慢客户端每 tick 仍要吃满一次期限，几个慢客户端相加就拖慢全房；房间又跑在单 goroutine（常在 nest 串行 handler 里），不该在 I/O 上等。

## 修复（`sync/lockstep/room.go`）

- 每个追帧会话最多一页在途：`pumpCatchup` 读出页后在自己的 goroutine 里 `SendReliable`，ctx 为 `context.WithoutCancel(tick ctx)` 加 `CatchupSendTimeout`（新字段，缺省 2s）；结果经容量 1 的通道回来，发送方永不阻塞在房间上。
- `Tick` 对本 tick 发起的页最多共等 `CatchupSendWait`（新字段，缺省 5ms，多会话共用一个计时器）；等到的当场结算（行为与之前同步时一致），没等到的留在途中，由之后的 `Tick` 非阻塞收取，`Tick` 不会再等它。
- 结算：成功则游标前进、计 `lockstep.catchup.frames.total`，越过最新帧即结束追帧；失败计次，到 `CatchupMaxFailures` 放弃（错误文本同前）。页在途期间 `StartCatchup` 回退的游标在页成功后保留（记录发起时的游标比较）。
- 收取放在广播之前：上一页成功后剩余的帧都在本 tick 冗余包的窗口内（`next + depth > Latest`）时直接转回直播——否则一页总比等待长的会话会永远落后最新帧一帧、回不到直播。
- `Detach` / 重新 `Attach` / `DetachSpectator` / `Close` 取消该会话的在途页。
- 测试里内存传输用 `CatchupSendWait: time.Minute` 让每页当场结算，原有按 tick 数页的用例不变。

## 兼容性

`RoomConfig` 新增 `CatchupSendTimeout`、`CatchupSendWait` 与常量 `DefaultCatchupSendTimeout` / `DefaultCatchupSendWait`。`ReliableSender` 现在会在房间 goroutine 之外被调用（每会话至多一个并发调用、不同会话可并发）——nettransport 的 KCP / QUIC / AsyncTransport 都是并发安全的；自定义发送器须并发安全。发送 ctx 不再随 `Tick` 的 ctx 取消。未部署。
