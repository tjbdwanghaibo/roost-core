# RR-20261006-41 修复：memory 事务改持久字段时整笔失败回滚，错误点名实体与字段

问题：[RR-20261006-41](../bug/RR-20261006-41.md)（框架文档发现 F02-1 / F03-1 / F02-6）。维护者 2026-10-07 选 A：改实现、强制“memory handler 不能改持久字段”。
基线 `b5c41edc`。codebase-memory 共享 generation 停在 09-30（比基线旧），本修复的定位与结论全部按 worktree 当前源码读取。

## 根因

`nest/rollback.go` `durableCommit` 的 memory 分支（基线 `:586-601`）对“memory 且没有 effect”直接返回 nil，没有核对事务里是否登记了要持久的内容：
DAO 持久字段的 `PersistChange`、`AddMutation` 的本地 mutation、`AddReceipt` 的 receipt 全部随 `commit()` 丢弃。

## 决策

- **在哪里查**：就在这个提交点（`durableCommit` 的 memory 分支，`refuseMemoryPersistentWrite`）。它看的是事务本地的持久登记——`participantOrder`
  （生成 setter 经 `MarkPersist*` 登记的 DAO，即现有的事务内 dirty 标记）、`mutations`、`receipts`——代价是 O(被改实体)，不扫实体全量，不调 `PrepareMutation`。
  没有在 `MarkPersist` 处直接报错：那会让 setter panic（生成 setter 对 `MarkPersist` 错误 panic），handler 中途炸掉、错误不点名；提交点能一次列全。
- **错误**：新哨兵 `nest.ErrMemoryTransactionPersistentWrite`（`nest/nest.go`），文本点名 handler、回滚策略、`collection/id` 与字段，例如
  `handler "x" (rollback=state, durability=memory) would lose memory_write/42088417 fields [value]; declare a durable policy (strict/async/pipelined) or make the fields nopersist`。
  经 `commitDurable` → `rejectCommit` 返回，所以同时满足 `ErrCommitRejected`（判别表第 12 行“写任何持久记录之前被明确拒绝”），按事务的回滚策略撤销内存修改。
- **点名字段**：生成 DAO 新增 `PersistFieldNames(mask) []string`（`codegen/internal/dao/template_dao.go`），nest 以可选接口 `PersistFieldNamer` 读取；
  没实现的参与方按事务里登记的路径（`Set` / `Unset` / `FullFields`）描述，再没有就给位掩码。生成代码不引用 `nest.PersistFieldNamer`，所以用 v1.23.0 的 core
  编译新生成的工程照常通过，`minimumVersions.Core` 不用升。
- **范围**：拒绝的是 memory 分支本会丢掉的一切本地持久内容，不只 DAO 字段——`AddMutation` 的本地 mutation 与 receipt 是同一根因（同一 `return nil`）。
  Remote 批次 finalize 加的 Remote mutation（`Remote != nil`）与批次认领的 DAO 改动（`remoteParticipants`）随批次提交，不算。
- **新建实体**：handler 内 `CreateInScope` / 生成 Lifecycle 新建的实体经 `CaptureCreatedEntity` 进入本事务。新实体的持久化只有一条路：持久 setter 登记，
  首个 mutation 是 Put（`PrepareMutation` 在版本 0 时给全量）。所以同一规则：新建并改了持久字段 → 整笔拒绝，`revoke` 撤销发布；只新建、不改持久字段 →
  照常成功（与修复前相同，新实体只在内存——与 strict 事务新建但不写持久字段时一致）。
- **销毁实体**：`RequestEntityDelete` 把 durability 升为 strict（`nest/rollback.go` `RequestEntityDelete`，与 `Emit` 相同），删除走正常 WAL，到不了 memory 分支，
  不受影响。直接 `MarkPersistDelete`（不经删除意图）不升级，会被本检查拒绝并描述为 `collection/id delete`。
- **rollback=none**：memory 快路径没有 `RollbackTx`，持久 setter 照旧以 `ErrTransactionClosed` panic，**不改、不统一**：快路径是不分配事务的性能路径，
  在那里补一个提交点检查需要先给它分配事务；panic 也已是 fail-fast。带 Remote 批次的 memory handler（`rollback=none` 但有 `RollbackTx`）改**本地**实体的持久字段
  走本检查：回复带本哨兵与 `ErrCommitRejected`、Remote 批次 Abort（Remote 侧的修改随批次回滚、从权威重载），本地内存修改**不撤销**——与 RR-20260927-32、
  RR-20260930-12 对 RollbackNone 的口径一致。fence 检查仍在本检查之前（`TestFencedMemoryRemoteWithoutEffectIsRefused` 仍得到 `ErrNestFenced`）。
- **生成期**：生成器无法知道 handler 会不会调持久 setter，不在生成期拒绝 `rollback=state|undo durability=memory`（它对只改 nopersist 字段的 handler 是合法组合）。
  glsvet 提示（memory handler 里调持久 setter）**未做**：glsvet 不读 `//roost:nest` 的策略，判断“某个 setter 是否持久”要解析生成 DAO 的 tag，跨包跟调用链
  才不漏报，投入与运行期强制的增量不成比例；运行期检查在第一次执行该 handler 时就以点名错误失败，单测即可覆盖。
- **未采用**：① 让 memory 事务把持久改动“顺带”写进 WAL（等于静默升级 durability，违反 handler 声明的提交点语义，维护者选的是 A 而不是改语义）；
  ② 注册期拒绝该组合（误伤只改 nopersist 的合法 handler）；③ 只记日志不失败（仍是静默丢数据）。

## 后续（2026-10-07，分支 `ccfix`）：`skill/combatcomponent` 两个用例被新规则拒绝

**现象**：`c2616106` 合入后，main 上 `skill/combatcomponent` 的 `TestNestUndoWorksThroughRealHandlers`、`TestNestUndoRollbackRestoresCombatStateExactly` 失败：

```text
component_test.go:150: seed: nest: transaction commit rejected
    nest: memory transaction changed persistent fields: handler "combat_seed" (rollback=undo, durability=memory) would lose combat_state/9219033 fields mask=0x7; combat_state/9218009 fields mask=0x1; declare a durable policy (strict/async/pipelined) or make the fields nopersist
component_test.go:238: nest: transaction commit rejected
    nest: memory transaction changed persistent fields: handler "combat_commit" (rollback=undo, durability=memory) would lose combat_state/9220057 fields mask=0x1; declare a durable policy (strict/async/pipelined) or make the fields nopersist
```

**归因**：在 `c2616106^`（`00ef3248`）上这两个用例通过，在 `c2616106` 上失败，确认由本修复引起。

**判断：用例写法不对，组件没有缺陷。** 两个用例手写注册 `nest.HandlerMeta{Rollback: nest.RollbackUndo}`，没写 `Durability`，零值就是 `DurabilityMemory`，而且引擎没有配 committer。
handler 里调用的 `InitCombatant` / `Heal` / `AddShield` / `SetAttributeBase` / `ApplyBuff` 改的是战斗 DAO 的持久字段（`combat_state` 是持久集合，`MarshalPersisted` 落库），
按新规则本来就该拒绝：修复前这两笔“成功”，正是本 RR 说的静默丢失。`combatcomponent` 本身不注册 handler、不选 durability（`component.go` / `adapter.go` / `status_bridge.go` 里没有 `HandlerMeta`）；
生成 handler 的默认值也不是 memory：`codegen/internal/nest/gen.go` `rollbackMeta` 对裸 `//roost:nest` 给 `rollback=state durability=async`，只有显式写 `durability=memory` 才是 memory。

**处置**：两个用例的三个 handler 改为 `Durability: nest.DurabilityStrict`，两个引擎加 `NestOptionWithTransactionCommitter(acceptingCombatCommitter{})`
（durable 事务没有 committer 会返回 `ErrCommitterRequired`；`acceptingCombatCommitter` 是同包 `dao_rollback_promises_test.go` 已有的接受型 committer）。
用例要钉的语义（undo 精确恢复战斗状态与 sync 脏位、提交后保留修改与脏位）不变，只改 durability。改后两个用例通过。

**另记一个易踩点（未改，供维护者判断）**：手写注册时 `HandlerMeta` 零值的 durability 是 memory，而 `//roost:nest` 不写 durability 时生成 async，两边默认值不同。
