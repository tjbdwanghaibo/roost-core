# RR-20261006-05 修复：global `Bind` 重试幂等

问题：[RR-20261006-05](../bug/RR-20261006-05.md)。批次：[收尾第 4 批](CLOSING-BATCH-4-2026-10-06.md)。基线 `8a292a5a`，未发版。

## 改动

`kit/service/global/service.go` `Bind`：`Create` 返回 `!created` 时 `Get` 已存的绑定——

- 找到且 `GlobalGroupID`、`GlobalSID` 与本次请求都一致：返回已存的绑定（其 Epoch / State 以库里为准），`report.Replayed("bind")`，不计冲突；
- 否则 `report.Conflict("bind")` 并返回 `ErrConflict`，错误里带上已存的 group / sid；
- `Get` 出错原样返回（仍是结果未知，调用方可再试）。

决策：按协调者给的口径只比较 group 与 globalSID。已迁移走的绑定 globalSID 已变，原 `Bind` 的迟到重试报冲突（与原语义一致）；迁移中（`RouteMigrating`）而 globalSID 仍是请求值时返回成功——原 `Bind` 确实成功过，返回当前绑定是真实的。没有用“请求 ID 记进值里”的方案：那要改持久格式，A2 ③ 已决定暂不做。

## 兼容

行为放宽：同参数重复 `Bind` 由 `ErrConflict` 改为成功并返回已存绑定（metrics 记 `replayed:bind`）；不同参数仍是 `ErrConflict`。RPC wire 不变。现有用例里“第二次 Bind 被拒”都是换了 globalSID，行为不变。

## 验证（`GOWORK=off`）

- 修前红文本见问题记录；修后 `go test -race -count=3 ./kit/service/global` 通过。新用例同时钉住：换 group、换 globalSID 两种仍报冲突（`conflict:bind` 计 2），库里绑定不变。
- 真实 Redis 用例（`kit/service/integration`，`-tags integration`）本批未跑；其中 `Bind(7, "group-a", 300)` 对已迁移到 200 的绑定仍应被拒，与修后逻辑一致。
