# RR-20260916-06：最后一个 manager 启动期间 Stop，成功启动的对象漏清理

**仓库 / 位置**：roost-core `manager/engine.go`（`Engine.Start` 的循环体、`stopStarted`）；kit `manager.ManagerMod` 转发同一引擎。
**修复单元**：U-0219（C2）。**定位文档**：TROUBLESHOOTING T-113。

## 问题

Start 逐个启动管理器，只在**每轮循环顶部**检查 `stopping`。交错：唯一一个管理器的 Start 已进入并阻塞 → 并发 Stop 置
`stopping=true`、取走此刻为空的 `started` 返回 → 管理器 Start 成功返回 → 引擎把它追加进 `started`，循环结束返回 nil。
Start / Stop 都"成功"结束，管理器 starts=1、stops=0，资源留在运行。后面还有一个管理器时，下一轮顶部的检查恰好补偿，
所以只有最后一个（含唯一一个）暴露。

## 根因

C2：回收依赖"还有下一轮循环"。Stop 取走 `started` 与 Start 追加 `started` 是两次独立的临界区，中间没有人对
"刚启动完但 Stop 已经发生"的对象负责。

## 方案选择

- 持引擎锁调用用户 Start / Stop：用户代码可重入、可阻塞，会把锁变成死锁点。不采用。
- Stop 等待在途启动完成再 drain：改变 Stop 的语义（可能被慢 Start 拖住），也要新的等待原语。不采用。
- **采用**：交接放进同一把状态锁——每个 Start 成功返回后，在 `e.mu` 下判定：`stopping` 已置则**本路径**负责停掉它并返回
  "start aborted by shutdown"（回滚失败一起 Join）；否则追加进 `started`（此后 Stop 负责）。两条路径恰好一方清理，
  循环尾部也覆盖。停单个管理器抽成 `stopOne`，与 drain 共用同一套（优先 `IManagerStopperWithContext`）。

## 改动

- `manager/engine.go`：Start 循环体的追加改为锁下判定 + `stopOne`；`stopStarted` 用 `stopOne`；删掉 `startedCount`。
- 测试：`manager/stop_during_last_start_promises_test.go`（`last` / `has_next` 两个子用例，channel 控制交错，轮询 `stopRequested` 同步 Stop 已生效）。

## 证明

- 修前：`--- FAIL: TestStopDuringTheLastStartStillStopsWhatStarted` / `Start reported success although shutdown was requested before it finished`。
- 修后：`manager` `-race` 全绿（含原 `engine_test.go` 的并发 / 关停用例）。

## 未做 / 边界

- Stop 仍不等待在途启动：它返回时，正在 Start 的管理器由 Start 路径在其完成后立刻停掉；调用方若需要"Stop 返回即全部停止"要自己等 Start 返回。
- kit `ManagerMod` 是包装，随 core 发版继承修复；未发版。
