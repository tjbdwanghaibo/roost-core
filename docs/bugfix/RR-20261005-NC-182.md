# NC-182 修复：FastMap 改已有键不重排，Range 识别表被换掉

[问题](../bug/RR-20261005-NC-182.md) · [证据](evidence/noncore-bugfix-20261005-revn13/README.md) · [本轮](../review/REVIEW-2026-10-05-n13.md)。已修复、声明场景验证，未发版。

## 根因与修法

`safemap/fast.go`：

- **Set**：先 `findSlot`。已有键原地写值；新键落在墓碑、或落在空槽且装载率仍在阈值内，原地插入（`insertAt`）；只有占用新空槽会超阈值时才 `ensureWritable` 扩容 / 重排后再插。之前先 `ensureWritable` 再查键，改已有键也会换掉整张表。“used（已占用 + 墓碑）不超过 75%” 的不变量不变，探测总能遇到空槽结束；常见路径仍只探测一次。
- **Range**：固定开始时的 `keys` / `values` / `states`；每交出一个槽前检查表是否已被换掉（`replaced`：长度或首元素地址不同）。没换就直接交出；换了就把旧数组里还没走到的键改到当前表里 `Get`，查不到（已删除）跳过。旧数组在被换掉后不再被写入，所以 `states[i]` 仍表示“开始时就在、还没走到的键”。
- **Clear**：只丢弃三个数组，不再 `clear` 清零——清零会让正在进行的 Range 读到零值键。

结果：回调里改已有键、插入、删除、Clear 后，每个未被删除的原有键恰好交出一次、带当前值；被删除的未到达键不交出；新增键是否交出不承诺（与 Go map 相同）。

未采用：
- Range 先复制快照（Small / Sharded 的做法）——FastMap 用于外层锁保护的热路径，每次遍历分配；
- 只改 Set 的检查顺序——回调里插入新键仍可能扩容，Clear 仍越界。

## 兼容

公开 API 不变，生成器 / 模板不改。行为变化只在“回调里改 map”时出现。墓碑复用不再顺带触发同容量重排：大量删除后的探测链要等下一次占用空槽超阈值才整理。

## 复审（2026-10-05，独立复审 audit180）

结论：修复成立，不需回退或调整。

- **遍历顺序与持久 / 同步的确定性**：生成 DAO 对 `map=fast` 字段的提交（`marshalCommitState` / 全量 `Marshal`）、回滚快照、增量补丁都不按 FastMap 槽位顺序输出——前两者先经 `RawMap` 拷进 Go map 再 `bson.Marshal`（键序由 Go map / driver `MapKeys` 决定，与 FastMap 无关，修复前后相同），增量补丁按 `MarkPersistSet` / `MarkPersistUnset` 的点路径记录。FastMap 布局变化（改已有键不再重排、墓碑复用不再顺带同容量重排）不改变任何写出的字节集合。
- **Clear 不清零旧数组**：`Clear` 把三个数组置 nil，除正在进行的 `Range` 的局部变量外没有引用，遍历结束即可回收；`Delete` 仍清零被删槽位。没有后续读取能看到旧数组。
- **组合**：golden `VarietyDao` 在 `RangeFastItems` 回调里改已有键、删键、插入到扩容、删空（触发 `FastMap.Clear`）后再插入，提交到真实文件 WAL；重开 WAL 逐条重放到文档，每条之后的解码状态与该笔提交后的内存一致；回调里改完再失败的事务回滚后内存回到原状、不写 WAL。修复前红、修复后通过，`-race -count=50` 通过（[原文与用例源码](evidence/noncore-bugfix-20261005-revn13/audit180.md)）。随机模型探针（2 万个种子，回调里随机 Set / Delete / Clear）未发现违反文档承诺的交出。
