# RR-20261004-02 修复：Layered 的过期 L1 副本不再否决权威值；远端已生效的写不再报 ErrStaleWrite

问题：[RR-20261004-02](../bug/RR-20261004-02.md)（来源 [REVIEW-2026-10-04-nc-audit-3 §3 D1](../review/REVIEW-2026-10-04-nc-audit-3.md)）。引入：[NC-14](RR-20261004-NC-14.md) 与 [NC-15](RR-20261004-NC-15.md) 叠加。
日期 2026-10-04；实施基线 main `91ab67f7`（含 `v1.19.0`）。状态：**已修复，本地验证通过（包回归 race、真实 Redis），已提交，未推送、未发版**。

## 根因（基线行号）

- `cache/layered.go:58-73`（`Get` 回填分支，NC-14 `08d18be9`）：L1 回填返回 `ErrStaleWrite` 时一律读回 L1 并交付。但 Layered 的 L1 副本只在 `localValid`（TTL 窗口）内才算“已准入”；窗口外它只是旧缓存。生成的 DAO 用不过期的 `LocalStore` 作 L1，于是上一个生命周期留下的较高版本（删除后重建、Redis TTL 到期后晚到的写）**永久**否决权威值；`ttl≤0` 本来承诺“绝不从 L1 服务”，同样被否决。
- `cache/layered.go:115-118`（`Set`）：远端写成功、回读 `current` 后，`local.Set(current)` 被 L1 旧副本以 stale 拒绝，错误原样返回——写已经被权威应用，调用方却收到拒绝。
- `cache/local.go:75`（NC-15）让 `LocalStore` 真正返回 `ErrStaleWrite`，把上面两处从“静默”变成可达。
- 可达路径：codegen 生成的带版本字段的 `NewCached*RedisDAO` = `Layered(LocalStore{VersionStale}, RedisRawJSON / RefHMap{VersionStale})`（`codegen/internal/dao/template_redis.go:76-88`、`:174`）。

## 决策

- **回填遇 stale 只在 L1 窗口有效时才交付 L1**（`layered.go:56-70`）：`localValid(key, now)` 为真的副本是这个副本在窗口内写入或回填的值（并发 `Layered.Set` 会续期 expiry），NC-14 的并发 stale 竞态仍走原规则。窗口外：
  1. `local.Delete` 清掉旧副本（失败按普通 L1 故障处理：计 `cache.layered.backfill_failed.total`，交付 L2 值——窗口外的副本不会被 Get 服务）；
  2. `ttl≤0` 不回填，直接交付 L2 值；
  3. 否则再回填一次，结果交给原 NC-14 规则：仍被 stale 拒绝说明是删除之后才落下的新状态——较新删除的墓碑（`Superseded`）或并发 Set 写入的更新值——读回 L1：有值交付、无值 miss。所以 NC-14 的 tombstone 场景（`Delete` 清 expiry 后回填）在新分支上仍得到 miss。
- **`Set` 远端成功后 L1 以 stale 拒绝：删 L1、清 expiry、返回 nil**（`layered.go:132-139`）。下一次 Get 回到权威。没有远端时 L1 就是存储本身，拒绝照常返回。
- 只处理 `ErrStaleWrite`。`ErrConflictingWrite` 保持 NC-14 语义（生成 DAO 的 `LocalStore` 不实现 `Conflict`，不可达；见“未验证 / 风险”）。

### 未采用的方案

1. **窗口外仍读回 L1，但只在 `held` 版本不高于 L2 时交付**：等于在 Layered 里重新实现版本比较，Layered 拿不到版本函数（只有 `StoreConfig.Stale`），而且对“删除后重建”这类版本回退场景仍然判错。
2. **窗口外直接交付 L2 值而不删 L1**：L1 旧副本留着，下一次 `Set` 照样被它拒绝（D1 的第二个现象），而且 `ttl>0` 时永远回填不进去，每次 Get 都打远端。
3. **ttl≤0 时根本不写 L1**：更彻底，但改变“L1 在 ttl≤0 下仍被回填”的现有行为（L1 本身可能被别处读），超出本 RR；保留回填尝试，只在被拒时删。
4. **`Set` 被拒后删 L1 再写 `current`**：多一次 L1 写且可能再次被并发状态拒绝；删掉让下一次 Get 从权威回填更简单，且只多一次远端读。

## 兼容性

- 行为变化只在 L1 以 stale 拒绝的分支：窗口外 Get 交付权威值（以前交付 L1 旧副本），`Set` 在远端成功时不再返回 `ErrStaleWrite`。L1 窗口内、L1 命中、普通 L1 故障、conflict、无远端的 Layered 均不变。
- `Set` 之前返回 `ErrStaleWrite` 的调用方（远端已生效）现在拿到 nil，与权威状态一致；远端自己拒绝（L2 返回 `ErrStaleWrite`）的路径不变，仍返回错误。
- 无公开 API、持久格式、配置变化；生成模板与 golden 未改。

## 未验证 / 风险

- **窗口判定与删除之间的窗口**：`localValid` 判为过期之后、`local.Delete` 之前，若本副本并发 `Set` 写入了更新值并续期，删除会清掉它，随后回填写入较旧的 L2 值并续期，本副本在一个 TTL 内服务较旧值。Layered 没有承诺并发 Get/Set 线性化（NC-14 记录同样声明），偏差以 TTL 为界。
- **conflict 未同等处理**：窗口外的 L1 副本以 `ErrConflictingWrite` 拒绝时仍按 NC-14 读回 L1。生成 DAO 的 `LocalStore` 不实现 `Conflict`，不可达；手工组合 `AtomicLocalStore{Conflict}` 作 Layered L1 时同类问题仍在（同版本不同内容的旧副本否决权威）。未登记，留给 review 判断。
- 复审 §4-7（L2 返回 `ErrStaleWrite` 后 `Layered.Set` 不再回读 L2 刷新 L1）未改，属 TTL 内有界的新鲜度问题。
