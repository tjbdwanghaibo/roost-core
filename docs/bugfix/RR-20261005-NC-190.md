# RR-20261005-NC-190：布尔开关与时长严格读取，`singleton.enabled: on` 与不带单位的时长在启动时报错

2026-10-05，基线 `f6245613`（审查 `efe219c1`）。**已修复、声明场景验证，未发版。** [问题](../bug/RR-20261005-NC-190.md) · [本轮](../review/REVIEW-2026-10-05-n14.md) · [证据](evidence/noncore-bugfix-20261005-n14/README.md)。

## 根因

viper 的 `GetBool` / `GetDuration` / `GetString` 经 `spf13/cast` 宽松转换：失败返回零值不报错，`ToDuration` 给不带单位的数字补 `ns`。`app/singleton.go:116` 的 `GetBool("singleton.enabled")` 把 `on` 读成 false，`validate` 在 `!enabled` 时直接返回；四个时长、`validateDurationIfSet`、`kit/saga/step_budgets.go:111`、`kit/mods.Duration` / `RequiredDuration` 只检查转换后的值；`redis.cluster_addrs` 用 `GetString`，YAML 列表读成空串。

## 修法

- `app/config_values.go` 新增 `ConfigBool` / `ConfigDuration`：设置了却不是合法值时报错并点名键，未设置返回零值。布尔接受 YAML 布尔、`strconv.ParseBool` 认的字符串与整数 0 / 1（宽松读取下本来就正确的写法）；时长接受 `time.ParseDuration` 认的字符串、`time.Duration` 与 0，拒绝不带单位的非零数字和解析不了的值。
- `readSingletonSettings` 改用它们，把读取错误记进 `readErrs`；`validate` 先报读取错误，**不管 enabled 读成了什么**（`on` 不再让校验提前返回）。
- `ValidateServiceConfig` 对 `frameworkBoolKeys`（框架各 Mod 用 `GetBool` 读的 15 个开关）逐个严格检查；`validateDurationIfSet` 改用 `ConfigDuration`。`TestEveryFrameworkBoolSwitchIsCheckedStrictly` 扫描 app 与 kit 源码里的 `GetBool("…")`，新增开关忘了登记时点名失败。
- `kit/mods.Duration` / `RequiredDuration`、`kit/saga` 的步骤预算时长改用 `app.ConfigDuration`。
- `kit/mods.RedisClusterAddrs` 接受逗号串与 YAML 列表、去空白；Redis Mod / 单实例锁连接（`redisConfig`）、`ValidateClusterKeyPrefix`、remoteentity 的 Cluster hash tag 检查都经它判断。

没采用：

- 全局遍历 `cfg.AllKeys()` 按键名猜类型（`*_timeout`、`*_ttl`）——会误伤计数键（探针里 `snapshot_max_waiters`、`etcd.lease_ttl` 是整数）。
- 把 kit 全部约 80 处 `GetDuration` 一起改：超出本轮新装配的范围，且应先定是否引入配置 schema（运行记录方向判断）。

## 兼容

行为收紧：以前被静默读成 false / 纳秒 / 兜底值的写法现在启动失败，错误信息给出键名与正确写法。生成的配置全部写 `true` / `false` 与带单位的时长：生成 game-demo 的 20 份服务配置（开发 + 生产示例）逐份 `ValidateServiceConfig` 通过（临时探针）。`1` / `0`、`"true"`、`True` 仍被接受。`mods.Duration` 对 `0` 仍取兜底值。
