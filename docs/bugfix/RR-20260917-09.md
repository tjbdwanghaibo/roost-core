# RR-20260917-09：battle demo 的启动宽限期没有触发开帧（U-0228）

- 仓库：roost-codegen `demo/internal/service/game/battle.go`
- 缺陷类：C2（状态机 / 定时器语义）
- 优先级：P3
- 相关：T-122；测试 `internal/service/game/battle_test.go`（随工程生成）

## 问题

常量注释约定"等待首次输入、最多宽限 2 秒后开始切帧"。实现里 `started` 只有收到一条 command 才置真，
ticker 在 `!started` 时永远 `continue`；`battleStartGrace` 只参与那个合并的超时计算，没有任何事件会开局。
于是无人输入的房间一帧都不切，最后按超时退出。

## 根因

一个 `deadline := time.NewTimer(battleStartGrace + battleIdleTimeout)` 同时承担了两件互不相干的事：
"什么时候开帧"和"整个房间最长活多久"。前者因此根本没有自己的事件源。

## 方案

- 采用：**两个独立计时器，两件事**。`grace`（`battleStartGrace`）到点把 `started` 置真并记一条日志——
  缺席的座位贡献空帧（乐观帧锁定），迟到的客户端从历史补发追上；`lifetime`（`battleMaxLifetime` =
  宽限 + 帧预算 × 帧间隔 + 收尾 + 余量）是绝对上限，只兜底 ticker / 客户端异常。
- 没采用：改成"必须有输入才开帧"并同步注释。那会让先连上的玩家被没连上的那个拖住，正是宽限期要避免的。
- 顺带（为了能测）：`battleManager.transport` 从 `*accessplayertcp.Runtime` 收成只有 `PushPlayer` 的接口
  `battlePusher`，房间的广播道因此可以在没有监听器的情况下被观察；`battleRoom` 加 `cut atomic.Int64` 计数。

## 改动（roost-codegen）

- `demo/internal/service/game/battle.go`：`battleStartGrace` 独立计时器 + `battleMaxLifetime` 绝对上限
  （替掉 `battleIdleTimeout`），`battlePusher` 接口，`battleRoom.cut` 计数。
- 新增 `demo/internal/service/game/battle_test.go`（随工程生成）：无输入时宽限后必须开帧且每个座位都收到帧；
  房间必须在 `battleMaxLifetime` 内自行结束且切满帧预算。

## 未做 / 边界

- 测试用记录型 `battlePusher`，证明的是开帧状态机与广播扇出，不证明客户端收帧（那由机器人场景覆盖）。
- "迟到的客户端从历史补发追上"这条路径由 lockstep 的 `StartCatchup` 承担，本轮没有为它单独加测试。
- 绝对上限只兜底；正常结束仍然是帧预算走完后进收尾窗口。
