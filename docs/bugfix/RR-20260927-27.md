# RR-20260927-27：非 Nest 领头方持有实体锁时冷加载，loader 发布要锁该实体则永久死锁

问题：[RR-20260927-27](../bug/RR-20260927-27.md)（OPEN-ITEMS B20 相邻形状 → 12 追加）。日期 2026-09-27。基线 `7b56060`，分支 `fix-r7-b12`（在 RR-20260927-25、26 之后）。
状态：已修复，本地验证通过，本地提交，未推送 / 发布。codebase-memory 图谱过期（09-26），以当前源码为准。

## 根因（基线行号）

`entity/manager_access.go:353` `runLocal`：领头方仍在等待、且没有指定执行器（Nest 之外）时，在**加载 goroutine** 上持 `flight.leaderMu` 就地执行 `fn`。
`fn` 是 loader 的发布步骤；它若要锁领头方正持有的 X，就在加载 goroutine 上等 X。领头方在 `loadEntityShared` 的 select（`:292-300`）里等 `flight.done`；
它的 ctx 到期后调 `leaderLeft`（`:374`），而 `leaderLeft` 要先拿 `leaderMu`——被在途发布持有。三方互等，永久死锁，RR-54“每个等待方（含领头方）按自己的 ctx 离开”不成立。
RR-54 之前 LoadEntity 直接在领头方 goroutine 上运行，发布对 X 是可重入加锁，不阻塞。

## 决策：交回领头方 goroutine 执行（恢复修前位置），不采用“让发布失败”

主记录给的两个选项：

1. **发布需要领头方已持有的锁时在领头方 goroutine 上执行**（采用）。
2. 让发布失败返回错误（未采用）。“发布要不要领头方的锁”框架无从预知：发布里的 `RequireEntity` 是阻塞等锁、不看 ctx。要让它失败，只能
   (a) 改 loader 契约为 try-lock——正式 DataEngine 仓库经 `RunLocal → EntityManager.Create` 发布，Create 在 Nest 之外按契约等待取锁，改它影响所有发布；或
   (b) 只把就地执行改成“不持 `leaderMu`”，让领头方能离开。(b) 下领头方确实按 ctx 离开，但加载 goroutine 仍卡在 X 上（不受 30s 框架上限约束，因为等锁不看 ctx），
   flight 一直不结束：领头方持着 X 重试会加入同一个卡住的 flight、每次超时，直到它放掉 X。这把死锁换成了领头方持锁期间的活锁，而且 Y 在此期间对所有调用方不可用。

选项 1 的做法：

- 建 flight 时（在领头方 goroutine 上）判断：领头方**没有指定执行器且当前 GuardScope 持有实体锁**（`currentGoroutineHoldsEntityLocks`）时，flight 带 `leaderSteps`
  （无缓冲）与 `leaderAway`。领头方在等待的 select 里多一个分支：收到交回的本地步骤就在自己的 goroutine 上执行，执行完继续等待。
- `runLocal` 对这种 flight：把 `fn` 发给领头方并等它执行完（加载 goroutine 上等待，不是快 worker）；领头方已离开（`leaderAway` 关闭）时改走领头方离开后的原路径
  （绑定的 `NestMgr.RunLocal`，未绑定时就地执行）。不持 `leaderMu` 等待，`leaderLeft` 不再被发布阻塞。
- 领头方执行步骤期间不看 ctx，所以它按自己的 ctx 离开最多晚一个本地步骤——与 Nest 领头方离开要等快续行结束的既有语义相同，有界于发布本身。
- `fn` 的 panic 在领头方 goroutine 上 recover、带回加载 goroutine 重新抛出，由 `runEntityLoad` 按加载 panic 处理（flight 照常结束、领头方仍看到 panic、之后可重试）。
- **只改这一种领头方**：Nest 慢阶段领头方（有执行器）不变；Nest 之外**不持锁**的领头方保持 RR-54 的“加载 goroutine 上就地执行”（它不持锁，发布无论在哪都等不到它）。
  领头方不会是快 worker（快阶段 Getter 只读已加载实体，冷加载返回 `ErrColdLoadInLogic`），在它的 goroutine 上执行本地步骤不属于快池内等待；
  Nest 慢阶段按契约注入执行器，所以慢 worker 上也不会走到这条路径。

RR-54 的解耦不回退：LoadEntity 的 I/O 仍在加载 goroutine 上、用解耦 ctx；领头方离开不取消加载；等待方各按自己的 ctx 离开。

## 未验证项 / 风险

- 交回领头方执行的发布看到的是领头方 goroutine 的 fctx（请求数据来自领头方，与加载 goroutine 上的快照同源；Base 是领头方的 ctx 而非解耦加载 ctx），
  与 RR-54 之前相同；loader 的发布若读 `fctx.BaseContext()` 做等待，会受领头方截止约束。仓内正式 loader（`dataengine/engine/entity_repository.go`）的发布是
  `EntityManager.Create` + loaded hooks；`git grep fctx.BaseContext()` 的非测试命中都在 bus / kit 模块装配 / manager / nest dispatcher / syncbus，不在 entity 发布路径上（未逐一核对业务自定义 hook）。
- 领头方离开后的发布若仍要锁领头方持有的锁，会等到领头方放锁（加载 goroutine 或绑定的快池入口上的本地锁等待，属 Guard/本地锁豁免），与 RR-54 相同。
- 自定义不可重入 Mutex 下，领头方 goroutine 上的发布对 X 再加锁会自锁——与 RR-54 之前相同。
