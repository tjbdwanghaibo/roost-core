# NC-80 修复：JSON 先编码后写状态

[问题](../bug/RR-20261005-NC-80.md) · [证据](evidence/noncore-bugfix-20261005-n02/README.md)。已修复、声明场景验证，未发版。

## 决策与实现

`httpserver.JSON` 改为 `json.Marshal` → 成功则写原状态码与 `body+"\n"`；失败则记录 `http server: encode response` 日志，改写为 500 与固定体 `{"error":"encode response","ok":false}`。`MarshalJSON` panic 发生在写头之前，由 Engine recover 中间件回 500。成功时字节与原 `json.Encoder` 输出相同（HTML 转义、结尾换行），控制用例逐字节比较。

修在共同出口而不是 Webroute/Ops 各自加校验：图谱显示 15 个调用者都经由它，任何一个调用者单独处理都会留下其余路径。没有引入缓冲池；Marshal 的整段缓冲与原 Encoder 内部缓冲同量级，未做 benchmark，不声称性能变化。

## 兼容性

可编码值输出不变。不可编码值从“原状态码 + 空体”变为“500 + 固定错误体”；原本写 4xx 错误体但错误体本身不可编码的情形也变为 500。依赖空 200 的调用方本来就拿不到数据，不提供兼容开关。生成 Webroute 代码形状不变，无需重新生成。

## 验证

- 正式回归：`httpserver/response_integrity_promises_test.go`（NaN/Inf/channel/MarshalJSON 错误/panic 5 叶子 + 字节形状控制）、`webroute/result_encoding_promises_test.go`（Registrar→Engine→真实 HTTP→httpclient，业务执行 2 次，NaN 得到 StatusError 500）、`kit/ops/response_encoding_promises_test.go`（Init→Provide→Start 真实 listener，命令执行 1 次得到 500）。旧产品（`origin/main` 50e9a4e8）上同一批文件：5+1+1 红，控制绿；修后全绿。
- 正式 CLI 生成消费：`codegen/cmd/webroute` 生成独立 module，修前 `err=<nil> out={WinRate:0}`，修后 `http client: status 500`。
- 本地矩阵见[证据](evidence/noncore-bugfix-20261005-n02/README.md)。

## 未验证 / 风险

真实网关、浏览器与第三方客户端如何呈现 500 未验；业务若想要自定义编码失败响应，需要自己先 Marshal。HTTP/2 未单独跑。

## 评估与取舍（2026-10-05 合并前复核）

维护者要求合并前确认有没有更好的修法。结论：**换成“Encoder + 首次 Write 才写状态”更好，已实施**；上文“`json.Marshal` → 写 `body+"\n"`”与“未做 benchmark，不声称性能变化”两句由本节更正。

关键事实：`json.Encoder.Encode` 在池化 `encodeState` 里完整编码、成功后**一次** `Write`（Go 1.27 标准实现 `encoding/json/stream.go` 与 `GOEXPERIMENT=jsonv2` 的 `v2_stream.go` 均如此），失败时什么都不写。所以修前的空 2xx 来自“先 WriteHeader”，不是 Encoder 流式输出；只要把状态码推迟到第一次 Write，就同时得到先编码后写和原来的零额外复制。

| 方案 | 正确性 | 与契约一致 | 改动面 | 性能（~285KiB 响应，本机 Apple M5，`-count 6`） | 调用方 |
| --- | --- | --- | --- | --- | --- |
| N02：`json.Marshal` + `append('\n')` + Write | 对 | 字节靠“与 Encoder 相同”的约定保持 | 小 | 每次额外分配一份响应体：290KB/op、+1 alloc；330µs（基线 288µs） | 无 |
| **采用：Encoder 写入 `statusOnFirstWrite`** | 对；编码失败时未写任何字节，改回 500 | 字节**就是** Encoder 输出（HTML 转义、换行），无需另行对齐 | 一个 12 行的私有适配器 | 0.5KB/op（与修前基线相同）、+1 alloc（32B 适配器）；276µs | 无 |
| 流式编码遇错中止连接 | encoding/json v1/v2 的 `Encoder` 都不流式，`json/v2.MarshalWrite` 在实验标志下才可用；中止让客户端只看到传输失败，比 500 信息少 | 与 NC-81“已开始才中止”一致，但把本可回 500 的情况也变成中止 | 依赖实验 API | — | 无 |
| 按大小分档（小 Marshal / 大流式） | 同上，“大”没有可用的流式编码器 | 两套行为 | 中 | — | 无 |
| 复用 `bytes.Buffer` 池 + Encoder | 对 | 字节相同 | 新增池 | 仍从 encodeState 复制一次到池缓冲；多一个无界缓存要管大缓冲回收 | 无 |

成功响应逐字节不变：不是协议必需（客户端按 JSON 解析，结尾换行无意义），但采用方案下零成本就能保持，且既有测试、日志对比与文档都按 Encoder 输出写，保持它可以避免无收益的变动。已写出后才返回的错误只能是连接写失败（客户端已不可达），与修前一样忽略，不 panic。

小响应（~60B）三者都在 ~0.5µs，差异在噪声内（±6%）。原文 `bench-json.txt`（三种实现同一二进制、交错运行；benchmark 文件只用于本次对照，未提交）。
