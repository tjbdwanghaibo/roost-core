# RR-20260928-04：stats_log 写失败不再静默；生成的部署物给相对的 stats_log.dir 一个可写位置

问题：[RR-20260928-04](../bug/RR-20260928-04.md)（批次 14 compose 实跑发现）。日期 2026-09-28。基线 `9568140`，分支 `fix-r9-b16`。
状态：已修复，本地验证通过（含本机 docker compose 全部 10 个服务实跑、文件落盘），本地提交，未推送 / 发布。codebase-memory 图谱过期（09-26），本轮以当前源码、`rg` 与实跑为准。

## 根因

两处叠加：

1. **写错误被吞掉。** `kit/statslog/statslog.go:214`（基线行号）周期循环里 `_ = m.FlushOnce()`；`FlushOnce` 在 `:292` `MkdirAll` / `OpenFile` 失败时返回错误，调用方直接丢弃。`Start`（`:195`）不碰文件，所以启动时也不会暴露。没有日志、没有指标。
2. **部署物没有可写位置。** 生成配置 `stats_log.dir: log`（`codegen/internal/roost/catalog.go:33`）是相对路径，按工作目录解析：
   - 镜像运行阶段 `WORKDIR /app`（`render.go:1055`）→ `/app/log`；compose `read_only: true`（`render_cicd.go:451`）、k8s `readOnlyRootFilesystem: true`（`render_deploy.go:595`），而挂载只有 config.yaml、`/tmp` 与 WAL。
   - systemd `WorkingDirectory=$APP_ROOT`（`render_deploy.go:149`）→ `$APP_ROOT/log`；`$APP_ROOT` 属于 root，`ProtectSystem=strict`（`:159`）下只读，`ReadWritePaths=$STATE_ROOT $LOG_ROOT`（`:168`）不含它。

## 决策

### 写失败：告警 + 计数，不 fail-fast

修复约束给了两条路（Warn + 低基数计数，或 Init 时校验可写并 fail-fast），二选一。采用 **Warn + 计数，启动时就探测一次**：

- `Start` 先打开一次文件（`openFile`），目录不可写在启动日志里立刻出现，不用等第一个 interval（默认 1 分钟）。
- 每次打开 / 写入失败计入无标签计数器 `stats_log.write_failures`；开始失败或错误文本变化时 WARN 一次，之后同一错误只计数（interval 调到秒级也不刷屏）；恢复写入时 INFO 一次。
- 不让 `Start` 失败，理由：统计文件是旁路观测——同一份记录每次采集都已发布为 metrics gauge（`runtime.*`、`entity.count*`）与 ops `/statsz`，数据本身并没有丢；而 fail-fast 会让已经部署、但还没合并新部署物的服务（旧 compose / k8s 仍是只读根）升级后直接起不来、按重启策略反复重启，代价远大于缺一份统计文件。探测放在 `Start` 而不是 `Init`：`Init` 阶段不做 I/O 是现有 Mod 的惯例，`Start` 本来就启动写循环。

statslog 的 Start / 周期写不在 Nest 快池上执行（它是自己的 goroutine），不涉及“快池内不得阻塞等待”。

### 可写位置：保持相对的 `log`，由部署物提供

不改生成配置（`stats_log.dir` 仍是相对的 `log`），而是让每种部署物在“工作目录/log”给一个可写位置。理由：service 配置是脚手架，只在建工程时写一次，之后归应用所有、`project sync` 不改；Dockerfile / compose / k8s workload / install.sh 是受控文件，sync 即更新。改部署物，旧工程一次 sync 就修好；改配置，每个已有工程都得手改三份配置（dev、prod 示例、Secret 示例）。开发机上相对路径照旧落在工程根的 `log/`（已在 `.gitignore`）。同一目录也是 `log.dir`（生产示例 `file: false`），将来打开文件日志同样可写。

- **镜像**：构建阶段 `RUN mkdir -p /out/wal /out/log`（原来只有 wal 一行，合成一行），运行阶段 `COPY --chown=65532:65532 --from=build /out/log /app/log`。只读根文件系统下目录本身不够，这一行的作用是：docker 第一次把**空的命名卷**挂到 `/app/log` 时按镜像里该目录初始化卷的内容与属主；没有它，新卷属于 root，65532 进程仍写不进去。
- **compose**：每个启用 stats_log 的服务一个命名卷 `<app>-<service>-log` → `/app/log`（顶层 `volumes:` 同步声明）。选命名卷而不是 tmpfs：统计文件要活过容器重建（实测 `up --force-recreate` 后追加而非重置）。
- **k8s**：`stats-log` emptyDir（`sizeLimit: 1Gi`）挂 `/app/log`。emptyDir 可写（`fsGroup: 65532`），随 Pod 生命周期；game-demo 实测每条记录 0.7–0.9 KiB，默认 1 分钟一条约 1.2 MiB/天，1Gi 留足一年以上；超出会被 kubelet 驱逐，所以说明里写明调小 interval 或要长期保留时改 PVC / 接日志采集。
- **systemd**：install.sh 在创建 `LOG_ROOT` 之后 `ln -sfn "$LOG_ROOT" "$APP_ROOT/log"`。`LOG_ROOT`（`/var/log/roost/<instance>`）属于运行用户、本来就在 `ReadWritePaths`，是实例日志的既定位置；链接不需要放宽 `ProtectSystem`，也不需要给 `$APP_ROOT` 加写权限。

没有采用：`systemd` 的 `LogsDirectory=` / `StateDirectory=`——它们只管理 `/var/log/<name>` 的创建与属主，进程仍在 `WorkingDirectory` 下按相对路径找 `log`，一样要链接或改配置；compose / k8s 给 `working_dir` 换到可写目录——会同时移走 `config_data.dir` 的锚点（RR-20260927-34 的回归守着它）。
