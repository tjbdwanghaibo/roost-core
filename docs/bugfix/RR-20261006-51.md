# RR-20261006-51 修复：施放中的衍生物也逐 tick 推进

问题：[RR-20261006-51](../bug/RR-20261006-51.md)（F08-R R1）。基线 `47abe511`（main，v1.23.0 之后），分支 `skspawn`，提交 `50a0fe88`。codebase-memory 共享 generation 停在 09-30（比基线旧，没有衍生物分区那一轮），定位与结论按 worktree 当前源码读取。
同一批（skspawn）修 RR-20261006-51～55，维护者 2026-10-07 要求先补“施放 → 移交 → 停止”端到端用例、再在用例上修，验证见本篇末尾，其余四篇引用这里。

## 端到端用例

`skill/spawn_lifecycle_e2e_promises_test.go`（新）在 MemoryHost 上跑真实的 `Activate` / `Advance` / `Cancel` / `Interrupt` / `Shutdown` / `Checkpoint` + `RestoreRuntime`：

- 衍生物：area（6 tick、间隔 1、两个成员）、projectile、beam、orbit（4 tick、completion end）；
- 路径：召唤后立即 finish、wait 3 再 finish、同上且施放中 checkpoint 恢复、wait 超过寿命（施放中到期）、施放中 Cancel / Interrupt / Shutdown、移交后 Shutdown（4 × 8 = 32 个子用例）；
- 每个 tick 断言：tick 回调造成的伤害数恰好等于该 tick 应结算的次数（不丢、不重复、停止后为 0）；Host 侧仍 active 的衍生物 = Runtime 仍负责的衍生物（running / stop_pending）；结束时 end / cancel 回调次数；全部伤害事件继承施法的根事件与深度、EventID 互不相同、父事件存在且不是自己；
- 另有：启动步被拒（RR-49）、`once_per_root` / `max_depth` / proc 第 0 号效果（RR-50 / 51）、施放中 area 回调在之后的 tick finish、推进入口的源码守卫。

修前这套用例红出 R1～R4（见各问题记录），没有发现 F08-R / F08-H+ 以外的新缺陷（“观察”一节列了两处顺带看到的现象）。

## 根因

`advanceOwnedSpawns`、`nextOwnedSpawnTick`、两处回收只看已移交分区；施放中分区唯一的推进路径 `spawnStepTask` 没有生产创建点。推进入口按“是否移交”分成两条，施放中那条从来没接上。

## 决策

- **一个推进入口**：`advanceOwnedSpawns` 推进 `spawnSteppedPartitions = {施放中, 已移交}` 的全部运行中衍生物，`nextOwnedSpawnTick`、推进前后的回收（`reapInvalidOwnedSpawns` / `reapOwnedSpawns`）、`terminateOwnedSpawn` 用同一组分区。是否移交只决定停止、表现与 revision 记在谁名下：新 helper `spawnOwnerCast`（施放中 → 所属施法，已移交 → nil），`abandonSpawnLocked` / `retrySpawnStopsLocked` 原来各写一遍的同一规则改用它。
- 每一步都在 `detachedSpawnCast` 上求值（spawn_step 列，与移交后相同，RR-20261005-NC-224 已要求两边都求得出），所以同一个衍生物移交前后的行为完全一致：召唤后 wait 与立即 finish 结算的 tick 序列相同。
- **删 `spawnStepTask` / `executeSpawnStep`**：它是第二条推进路径，只能从 checkpoint 解出来，解出来会让同一个衍生物一个 tick 走两步。checkpoint 里的 `spawn_step` 任务按 `ErrCheckpointCorrupt` 拒绝（与 RR-20261006-03 删 `phase_timeout` 同一做法），任务的 `spawn_id` 字段一起删。
- **守卫**：`TestSpawnStepsHaveOneTickEntry` 读包源码，`stepSpawnMotion` / `stepAreaMembership` 只能由 `startEntitySpawn`（启动步）与 `advanceOwnedSpawns` 调用。与“分区只由 spawnTable 写”“停止只经 requestSpawnStop”两条守卫一起，推进、存放、停止各一个入口。停止仍只经 `requestSpawnStop`（`spawnStopEntries` 登记的调用方不变）。
- **施放中 area 回调在之后的 tick finish**：施放中的衍生物现在会在之后的 tick 跑回调，area 回调的 finish 按既有语义“结束拥有它的施法”（`compile_owned_entity.go` 的 allowAreaFinish）：`finishCastFromAreaCallback` 撤掉当前 phase 的排程任务、推进 phase token、走 `finishCast` 正常收尾（余下的 wait 之后的流程不再执行），area 本身照旧停止、不跑 end / cancel。启动那一步的 finish 仍由 executor 的 summon 分支处理。
- **未采用**：给施放中衍生物排 `spawnStepTask`——两条推进路径要在移交时交接 NextTick，checkpoint 里也要两种状态互相核对，正是分区重构要消除的形状。

## 观察（用例里看到、未改）

- `Shutdown` 停施放中的衍生物不跑 `cancel` 回调（`callbackEvent` 只对已移交的给 `"cancel"`，`skill/spawn_owned.go` `Shutdown`），而 Cancel / Interrupt 停施放中的、`Shutdown` 停已移交的都跑一次。用例对这一格只断言“不超过一次”。是否统一属语义决定，未改。

## 方向判断（反复出问题的模块）

skill 衍生物近两轮的修复链：RR-20261006-21～23（停止失败 / 记录回收）、-31 / -32（tick 回收、重复回调）、-34（循环中途删记录）、RR-20261005-NC-211 / NC-224（移交后 area finish、求值上下文）、两次重构（停止入口统一、分区存放与已放弃分区），本批又是 R1～R4。共同根因是**同一个衍生物按“是否移交”走两套代码**：推进、回收、停止、表现、事件上下文各自按分区分支，每补一处都要在另一套里对齐，漏一处就是一个 RR（R1 就是推进只接了一半）。本批把推进与回收收成一个入口、按分区只区分“记在谁名下”，并用源码守卫钉住推进 / 存放 / 停止各一个入口；端到端用例按“衍生物 × 生命周期路径”的矩阵断言每个 tick，之后新增衍生物 kind 或停止入口时把它加进矩阵即可。建议后续若再改这一块，先看是否还能继续减少“移交前 / 后”的分支（例如 `startEntitySpawn` 的启动步与 `advanceOwnedSpawns` 的一步合并成同一函数），而不是再加状态。
