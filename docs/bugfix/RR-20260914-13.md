# RR-20260914-13:LOD 绝对 tick 采样使错相发送的组件持续保留旧值

**仓库 / 位置**:roost-core `statesync/lod.go`,`refreshDue` 与 `ProjectWithContext` 的保留分支。
**修复单元**:U-0203(C8)。**定位文档**:TROUBLESHOOTING T-97。

## 问题

`refreshDue` 是 `tick%interval == 0`。SnapshotRateHz=20、`LODDecision.MaxRateHz=10` → interval=2。会话只在
tick 1、3、5、7、9 准备并发送:发送间隔早已满足限频,但所有发送都不落在偶数采样点,首次全量之后每个 delta
都继续携带保留的旧值。`client at tick=9 normal=1 want >=8`。ACK 正常也救不回来——ACK 的投影本身就是旧值。

## 根因

采样点用绝对 tick 定义,而发送时机是每个会话自己的(C8:全局相位 vs 会话发送计划)。

## 方案选择

- **按组件上次实际刷新的 tick 计时。** 要给投影加每对象每组件的元数据,审查也提醒 `Previous.Tick` 不是组件的
  刷新 tick、直接相减会不断推迟。
- **所有帧全量。** 掩盖问题。
- **"自上次发送以来是否跨过了采样点"(采用)。** `tick/interval != previousTick/interval`——本次发送与上次
  **已提交**发送不在同一个采样区间就刷新。每个区间至多刷新一次,限频语义不变;与发送相位无关;逐 tick 发送时
  与旧规则逐点等价(`tick%interval==0 ⇔ tick/interval != (tick-1)/interval`),所以 tick 9 仍合法保留 tick 8 的采样值。
  最坏陈旧 < 2 个 interval。`Previous` 来自 `sent[lastSent]`,是上一次**提交**的投影,Abort / 发送失败不会消耗刷新机会
  (审查的另一条顾虑)。不加任何元数据。

## 改动

`lod.go`:`refreshDue(tick, previousTick, …)`,调用点传 `context.Previous.Tick`(该分支已保证 `Previous != nil`)。

## 证明

`statesync/lod_phase_promises_test.go` 的 `TestLODProjectorPromiseRefreshDoesNotDependOnSendPhase`:审查的三个子例
(逐 tick / 奇数 tick / 奇数 tick 每次全量),并对逐 tick 子例额外断言 tick 9 的值恰为 8——限频没有被放宽。
修前红:`client at tick=9 normal=1 want >=8 after multiple rate intervals`。修后 statesync 含 `-race` 全绿。

## 未做 / 边界

- 判据是"跨过采样点",不是"距上次刷新 ≥ interval":两次发送若落在相邻区间的两端(如 tick 3 与 tick 4,
  interval 2)会连续刷新两次;这是采样区间语义本来允许的,不是每 interval 一次的滑动窗口。
- 没有引入每组件的刷新时间元数据。
