# RR-20261006-26 修复：nats 排空被硬关后 Connected() 一直为 false

问题：[RR-20261006-26](../bug/RR-20261006-26.md)。基线 main `37338490`，未发版。来源：[真实进程演练](REAL-PROCESS-DRILLS-2026-10-06.md)第 4 项。

## 根因

nats.go v1.53.1 `drainConnection` 在硬关之后仍把状态翻回 `DRAINING_PUBS` 并空等最长 5s 的 Flush（上游行为，问题记录有逐行说明）；驱动 `Client.Connected()`（`nats/driver/client.go:192`）直接返回 `conn.IsConnected()`，把这段“排空中”报成已连接。

## 改动

`nats/driver/client.go`：

- `Connected()` 在驱动自己的 `closing` 标记置位后一直返回 false（`Close` 置位）。
- `DrainWithContext` 到期硬关改调 `c.Close()`（原来 `c.conn.Close()`，不置标记）。`Assembly.Close` 在排空失败后本来就会再调 `Client.Close()`，这一处让直接用 `DrainWithContext` 的调用方同样正确。

未采用：硬关后等 nats.go 的排空协程结束——它要空等 Flush 超时（5s），停机预算等不起，也看不到它的结束信号；升级 / 修补 nats.go——上游行为，驱动层能完整兜住，不为此改依赖。

## 兼容

只改 `Close` 之后 `Connected()` 的读数（之前最长约 5s 内可能为 true）。之后的调用本来就返回 `fnats.ErrClosed`（nats.go 在 `DRAINING_PUBS` 下返回 `ErrConnectionDraining`，驱动已映射），不变。nats.go 的 `ClosedHandler` 在这种情况下仍会触发两次（驱动日志 `nats: connection closed` 两行），无害，不处理。

## 验证（`GOWORK=off`）

- 修前 `-count=20` 全部红（问题记录）；修后 `go test -tags integration -race -count=30 -run TestRealNatsModUndrainedCloseIsReportedOnce ./kit/nats/` 全绿（真实 NATS，私有环境）。
- `nats/driver` 全包、`kit/nats` `-race -count=3`（含 integration）、根包、`go build ./... && go vet ./...` 通过。
