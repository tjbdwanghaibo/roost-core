# RR-20260919-02：一个 nested 值同时属于两个地方，只有最后一个会落库（U-0252）

- 仓库：roost-codegen `internal/dao`
- 缺陷类：C2（生成物的不变量缺一条）
- 优先级：P1
- 相关：T-146；测试 `internal/dao/testdata/runtime/ownership_test.go` 的
  `TestANestedValueHasOneParentAtATime` 等四条

## 问题

把同一个 `*EquipInfo` 先后放进 `equips.1` 与 `equips.2`，然后改它。内存里两个 key 指向同一个对象、
值当然相等；持久化补丁里只有 `equips.2`。进程重载之后，两个 key 不再相等——**磁盘上的那一份少了一次更新**，
而在那之前没有任何迹象。

跨字段（`equips.1` 与 `Mount`）、跨 DAO（两个 Hero）同理。

## 根因

通知是**单槽**的：`dataengine.DirtyHook` 只有一个 `notify func()`。第二次 `SetNotify` 覆盖第一次，
于是第一处的回调消失。U-0238 的记录把别名写成"未定义边界"，但公开 setter 既没有拒绝它，
也没有任何类型或文档告诉调用方"DAO 图必须是树"。**接受输入之后少写一份**不能继续算未定义行为。

## 方案

- 采用：**唯一父所有权**。一个可变 nested 值同一时刻只属于一个字段 / key / index。
  每个生成的 nested 类型多一个未导出的 `dirtyOwner daoDirtyOwner{holder, field, key}`，
  `bindDirty(owner, notify)` 在已有**不同** owner 时 panic，`unbindDirty(owner)` 只释放自己那一条。
  所有绑定点（DAO 的单指针 / map / slice / 值字段，nested 内部的同四种）都走它们。
- **为什么是 panic**：单槽之下，任何不失败的选择都在某一侧是静默错误——"后绑的赢"让第一处不再落库，
  "先绑的赢"让第二处不落库，静默克隆则改掉了调用方以为的别名语义。仓库里生成的 setter 已经有
  panic 的先例（事务外调用 setter 就是 panic），而"一个值放两处"同样是调用方的编程错误，
  不是运行期可恢复的状况。panic 发生在**写任何东西之前**，所以 recover 的调用方看到的状态没变。
- 没采用：多订阅通知。那等于允许一个对象被多个聚合根共同持久化，回滚顺序、锁序、提交顺序都要重新论证，
  审查也明确不建议作为默认模型。
- 没采用：只扫描当前 map。能通过审查那一条复现，但抓不到跨字段与跨 DAO。

## 改动

`internal/dao/template_helpers.go`（`daoDirtyOwner`、`daoBindDirty`、`daoUnbindDirty`，进每个包一份的
`gen_dao_bson_helpers.go`）、`internal/dao/template_nested.go`（`dirtyOwner` 字段与两个方法，四种绑定点）、
`internal/dao/template_dao.go`（四种绑定点带 owner；map 用 key、slice 用 index、字段用脏位常量）、
`internal/dao/gen.go`（`nestedFieldOrdinal`：nested 没有脏位常量，用定义里的序号做字段身份）。

## 证明

修前红四条（同 map 两 key、同 DAO 另一字段、同 DAO 的 slice、两个 DAO），都是"被接受了"；
修后 panic 且消息点名类型与"one parent"。另外两条锁住不能误伤：
`TestANestedValueCanBeMovedBetweenKeys`（先 `Del` 再 `Set` 是合法的移动，移动后写在新 key 下）、
`TestRebindingTheSameSlotIsAccepted`（`Init` 每次装载都会重绑，同一处重绑不是别名）。
golden 文本门与 `scripts/dao-golden-runtime.sh` 运行时门全绿，game-demo 全量测试与实跑不受影响
（装备那条路径反复把同一批指针放回同一批槽位，owner 相同）。

## 未做 / 边界

- **只覆盖可变的 nested 值**。nested **值**字段（非指针）不会别名，因为它不是同一个对象；
  但 `GetPos()` 返回的是字段地址，把它塞进一个 `map[K]*Position` 仍会被这套机制拦住。
- owner 里的 key 对 map 是 map key、对 slice 是**下标**。所以"把切片元素换个位置"要走
  `unbind → 重排 → bind` 这条既有路径（生成的 `SetXxxAll` 就是这样做的）；手工重排底层切片再改元素，
  会在下一次 bind 时被判为别名。
- panic 的文本是给人看的，没有做成错误码；它出现在开发期的可能性远大于生产期。
