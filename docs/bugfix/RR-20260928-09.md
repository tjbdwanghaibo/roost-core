# RR-20260928-09 修复：带 Remote 批次的 pipelined handler 被明确拒绝时，与 strict 一样交 finalizer 回滚、隔离、卸载并放行 Sync 门

问题：[RR-20260928-09](../bug/RR-20260928-09.md)（来源：[RR-20260928-08 修复记录“范围外发现”](RR-20260928-08.md#范围外发现未修)）。日期 2026-09-28；基线 `f617a95`；worktree 分支 `fix-r10-b19a`。
codebase-memory 图谱停在 09-26，已过期，未使用；以当前源码与实跑为准。

## 根因

- 带 Remote 批次的 pipelined handler 不走 Enqueue（`nest/execution.go:177-188`：`msg.RemoteWriteBatch != nil` 时 `pipelinedCommitter` 留空），经
  `commitDurable` 的 strict 路径提交，`finalizeRemoteWriteBatch`（`nest/msg.go:47`）把 `tx.durability`（3）写进 `outcome.Durability`。
- `remoteentity/batch.go` `(*remoteWriteBatch).Commit`：`:496-505` 按 Durability 分支，2 与 3 同走 `else` 等待投影器结论；但等待失败后的结论处理
  `:508` 只认 `outcome.Durability == 2`（或错误带 `ErrRemotePersistenceIndeterminate`），`:512` 只认 Durability 0。等到的是明确拒绝
  （tracker 终态 Rejected → `entity.ErrRemoteRejected`，不带未知哨兵）时，Durability 3 两个分支都不进：`indeterminate`、`rejected` 都不置位。
- 于是 `DeferUntilDurableOutcome`（`:618-628`）返回 false（nest 计 `nest.remote.post_commit_without_outcome_total`，Sync Confirm / AfterCommit 丢在原地），
  `Close`（`:636`）不交 finalizer、直接释放 gate，也不走 `rejected` 的卸载分支。

**对主记录现象的更正**：主记录写“持有被拒修改的实例不隔离、不卸载”。实跑表明实例**会被隔离**——`Commit` 出错路径无论哪个分支都调
`quarantineEntries`（基线 `:515`）——但**不回滚、不登记重载、不卸载**：下一写者一直得到裸 `ErrRemoteFenced`（不是 RR-62 的可重试
`ErrRemoteEntityReloading`），直到重启都不可写；Sync 门永久冻结；`RollbackRemoteCommit` 不执行。被拒修改没有写出（隔离挡住了），
所以不是数据泄漏，而是可用性与 Sync 冻结。strict 同样情形由 finalizer 回源得到 Rejected 后按 RR-28 / 39 / 58 / 62 收尾。回复本身正确（第 4 行）。

## 决策

- `batch.go:512`（修后行号）改为 `outcome.Durability >= 2`：等待投影器结论的批次（strict 2、带 Remote 批次的 pipelined 3）不论等到什么错误，都置
  `indeterminate`、由 finalizer 按持久结论收尾，与 strict 完全同一条路径：
  - finalizer（`transaction_manager.go:290` `item.durability != 0`，本来就包含 3）等投影器结论；tracker Rejected → `RemoteCommitStatus` 得到 Rejected →
    `settleRejectedRemoteEntries`（经 `Manager.localContext` 在 Nest 快池回滚、隔离、登记重载）→ 释放 gate / 写额度 → 仅内存卸载 → `deliverRemoteOutcome(false)`
    → nest 的闭包 `RejectEntities`，Sync 门放行，AfterCommit 不执行（RR-37 / 58 / 62 不变）。
  - 结果未知（带未知哨兵）本来就走这条路径，不变；成功（`err == nil`）不进这段，不变。
- 回复不变：错误仍原样返回，`ErrRemoteRejected` 不带未知哨兵，nest 照旧标第 4 行（RR-20260928-03 / 08 的判据不动）。
- 不在快 worker 上新增等待：只改一个分支条件，等待仍是既有的 `Commit` 慢阶段等待，收尾由 finalizer 与 `RunLocal` 完成。
- 未采用：让 pipelined 被拒时走 Durability 0 的同步回滚（`:516` 分支）——Durability 3 的本地记录已进 WAL，拒绝是投影器的持久结论，
  应与 strict 一样由 finalizer 收尾（RR-38：有 WAL 的事务由投影器完成）；同步回滚还会绕过 RR-38 的等待与 RR-39 的快池卸载时序。

## kit 装配下 pipelined + Remote 路径的其他差异（核对）

- **nestwal 不 fsync（范围外缺陷，未修）**：strict 路径上的 Durability 3 记录经 `Projector.Commit` / `nestwal.Committer.Commit` → `WAL.Append`，
  `nestwal/wal.go:331` 只对 `DurabilityStrict` 置 `requireSync`，于是 `Append` 在 fsync 之前返回（与 async 相同）；正常的 pipelined 记录走 `Enqueue`
  （`:389` `requireSync: true`）不受影响。探针 `nestwal/zz_probe_pipelined_append_test.go`（`//go:build probe`，保留在 worktree，未提交）：

  ```text
  $ GOWORK=off go test -tags probe -count=1 -run TestZZProbePipelinedAppendSync -v ./nestwal
  PROBE durability=async fsyncBeforeAppendReturned=0 unsyncedAfterAppend=true
  PROBE durability=strict fsyncBeforeAppendReturned=1 unsyncedAfterAppend=false
  PROBE durability=pipelined fsyncBeforeAppendReturned=0 unsyncedAfterAppend=true
  ```

  影响：`DurabilityPipelined` 的契约是“成功（回复、AfterCommit）只在 ticket 持久后对外可见”，`NEST_PIPELINED_COMMIT.md` 写明 broadcast 与 Remote 批次
  “表现等同 Strict（锁内等待 durable）”。broadcast（`nest/nest_dispatch.go:542`，`releaseLocks == nil`）与带 Remote 批次的 pipelined 实际得到 async 语义：
  锁释放、Sync Confirm、AfterCommit / effect 可能在 fsync 之前发生，进程在组提交间隔（默认 10ms）内崩溃会丢掉已对外可见的事务。带 Remote 批次时回复要等投影器结论，
  投影器可能在 fsync 前读到这条记录（`Replay` 读到已写偏移）并写进 Mongo，Remote 已提交的情形因此多由 Mongo 兜住；本地部分在第 4 行（Remote 被拒）回复
  “本地已提交”时可能尚未 fsync。修法候选：`requireSync: record.Durability >= corenest.DurabilityStrict`（`Append` 上的 3 只来自 strict 回退路径）。
  它同时改变 broadcast pipelined 的持久语义（锁内 fsync，与文档一致），属于独立问题，交主会话登记。
- 其余核对无差异：pipelined allowlist 与 `PipelinedTransactionCommitter` 要求在回退 strict 前照常检查（配置一致性，kit `Mod` 实现了 `Enqueue`）；
  `TransactionReleased` 经 `msg.addAfterUnlock` 通知，与 strict 相同；finalizer 等投影器结论（RR-38）、`FinalizeProjectionTimeout`、回源、快池回滚与卸载都按
  `durability != 0` 包含 3；Remote 确认等待在锁外的慢阶段，与 strict 相同。

## 兼容性

- 带 Remote 批次的 pipelined handler，Remote 被明确拒绝时：之前实例一直隔离（裸 `ErrRemoteFenced`，重启前不可写）、Sync 门冻结、`RollbackRemoteCommit` 不执行；
  现在与 strict 相同——finalizer 回滚、隔离、释放、仅内存卸载（业务收到一次 `OnDestroy(DestroyReasonMemoryUnload)`），卸载窗口内下一写者得到可重试的
  `ErrRemoteEntityReloading`，之后从权威重载可写；Sync 门按 RR-58 只丢弃 Remote 实体的内容与事实。回复与原因链不变（第 4 行）。
- 结果未知、成功两种形态行为不变。strict、async、memory 不受影响。
