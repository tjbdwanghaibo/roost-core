# RR-20261006-30 修复：恢复按 prune 的不变量核对完成队列

问题：[RR-20261006-30](../bug/RR-20261006-30.md)。基线 `90c92caf`，分支 `skretry`（与 RR-20261006-21 后续同一提交），未发版。
读代码：codebase-memory 共享 generation 停在 09-30，以当前源码为准；完成队列上限的检查点用 `rg 'CompletedCastLimit' skill/` 穷举（`pruneCompletedCastsLocked` 与恢复末尾的一处）。

## 根因

`pruneCompletedCastsLocked` 的后置条件是“队列不超过上限，或者剩下的全部仍被引用”；恢复检查写成了“队列不超过上限”，比 live Runtime 的不变量更严。

## 方案取舍

| 方案 | 结论 |
| --- | --- |
| ① 恢复用同一不变量：超过上限时，队列里不能有可回收的 cast（`completedCastOrderWithinLimitLocked`，复用 `castEvictableLocked`） | 采用。检查放在任务、policy、进程都恢复之后，引用判据与 live 回收完全同一份代码 |
| ② 恢复时顺手 prune 到上限 | 未采用：恢复只校验、不改状态；被钉住的 cast 本来就回收不了 |
| ③ 停止钉住 cast 的引用 | 未采用：违背 RR-23 的承诺（运行中的进程还在用它的 cast） |

## 文件与行为

| 位置 | 改动 |
| --- | --- |
| `skill/runtime_checkpoint.go` `completedCastOrderWithinLimitLocked`（新）与 `restoreCheckpointPayload` 末尾的上限检查 | 超过上限的部分必须全部仍被引用 |
| `skill/runtime_process_retention_promises_test.go` | `TestHandedOffProcessesBeyondTheCompletedLimitStillRestore` |

## 兼容性

checkpoint 格式不因本条改变（同批的格式版本 3 来自 RR-20261006-21 后续）。放宽：以前判 corrupt 的“被钉住的 cast 多于上限”现在能恢复；队列里仍有可回收 cast 却超过上限的照旧判 corrupt。
