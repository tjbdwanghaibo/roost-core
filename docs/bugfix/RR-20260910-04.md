# RR-20260910-04:Checkpoint 恢复改变完成历史的淘汰顺序

**仓库 / 位置**:roost-core `skill/runtime_checkpoint.go`(payload 构建与恢复)。
**修复单元**:U-0169(C8)。**定位文档**:TROUBLESHOOTING T-63。**优先级**:P3。

## 问题

早创建的慢技能后完成,晚创建的快技能先完成。`CompletedCastLimit=2`,保存/恢复之后再完成第三个
技能触发淘汰:**恢复前后被淘汰的是不同的 cast**,已完成 Cast 的查询记录因此分叉。

## 根因

`completedCastOrder` 是"按完成顺序"的队列,`pruneCompletedCastsLocked` 从队头淘汰。而
Checkpoint 把 casts **按 ID 排序**序列化,Restore 又在遍历这份列表时逐个 append 重建队列 ——
于是"最旧的完成"被替换成"最小的 ID"。两条路径对"谁最旧"的判据不同(C8)。

## 方案选择

- **恢复时按某个已有字段重排**,例如 cast 的完成 tick。快照里没有记录完成时刻,同一 tick 内
  完成的多个 cast 也无法区分先后。
- **定义一个"恢复后一致"的淘汰策略**,例如统一改成按 ID 淘汰。那是产品语义变更:淘汰"最旧
  完成的"是有意的保留策略,改成按 ID 会让低 ID 的历史永远先消失。
- **快照显式保存完成顺序(采用)**。它是运行时已有的状态,没有被序列化只是遗漏;补上之后恢复
  前后按定义一致。

## 改动

`skill/runtime_checkpoint.go`:

- payload 增加 `CompletedCastOrder []CastID`(带 `omitempty`),构建时拷贝一份运行时的切片 ——
  拷贝而不是引用,否则后续运行时活动会改写一个已经取好的快照。
- 恢复逻辑抽成纯函数 `restoreCompletedCastOrder(recorded, completed, casts)`:记录的顺序优先,
  过滤到"确实恢复成终态"的 cast(所以陈旧或被改过的顺序不能复活或重复一个条目);记录里没有
  提到的终态 cast 按 ID 顺序追加。
- 后一条同时是**旧快照的兼容路径**:字段不存在时退化为纯 ID 顺序,也就是它一直以来的行为。

## 证明

`skill/completed_order_checkpoint_promises_test.go` 三组:

- `TestCheckpointCarriesTheCompletionOrderSeparately`:真实运行时激活两个 cast、`Advance` 建立
  宿主状态基线,把完成顺序设成与 ID 顺序相反,断言 payload 带上了这个顺序、`Casts` 仍是 ID 序
  (这正是必须单独带的原因),并断言 payload 持有的是拷贝。
- `TestRestoreCompletedCastOrderPrefersTheRecordedOrder`:对纯函数做表驱动 —— 记录顺序优先、
  字段缺失退化为 ID 顺序、未恢复成终态的 id 被丢弃、顺序漏掉的终态 cast 按 ID 追加、重复 id
  只放一次、没有终态时是空队列。
- `TestRestoredCompletionOrderDecidesWhichCastRetentionEvicts`:用真实的
  `pruneCompletedCastsLocked` 断言后果 —— 带完成顺序时淘汰最旧完成的那个,不带时(旧快照)
  淘汰的是另一个。

回退验证:把序列化与恢复改回原样,`the payload carries completion order [], want [2 1]` 变红,
恢复后 `go test ./skill -race` 绿,core 全仓绿。

## 未做 / 边界

- **没有端到端跑一次 `Checkpoint()` → `RestoreRuntime()` 且完成顺序与 ID 顺序相反。** 原因是
  两道真实校验挡在中间:直接改 cast 状态会让 payload 构建的宿主状态校验拒绝,改 payload 里的
  cast 状态又会让恢复侧的同一道校验拒绝;而按真实推进无法让后创建的 cast 先完成(需要两个
  时长不同的程序与各自有资源的施法者)。因此测试拆成"序列化侧带上顺序"与"恢复侧以记录顺序
  为准"两端,加上真实 pruner 的后果断言。审查附录里的双 Host 端到端测试是更强的验收。
- 影响范围仍限于历史保留与诊断查询。**没有**证明伤害、奖励或随机结果会不同,没有升级为战斗
  确定性故障。
