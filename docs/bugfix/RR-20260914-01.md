# RR-20260914-01:Close 尚未排空时,Sync 把关闭标志当作持久化完成

**仓库 / 位置**:roost-core `nestwal/wal.go`,`awaitWriteBarrier` 的 closed 分支(U-0185 引入)。
**修复单元**:U-0190(C8)。**定位文档**:TROUBLESHOOTING T-84。

## 问题

Enqueue 已返回 ticket;writer 收完这一批、尚未 `processBatch` 时被调度暂停;另一 goroutine 发起 Close,
`closed=true` 但 `doneCh` 未关闭;此时调 Sync。U-0185 的屏障看到 `closed` 直接返回 nil ——
`err=<nil> admitted=1 appended=0 durable=0 ticket=1`,ticket 未完成。对照:同样暂停但不 Close,Sync 正确返回
DeadlineExceeded;等 Close 真正完成再 Sync,成功且 ticket 已完成。只有"关闭进行中"这一段错。

## 根因

关闭是两个事件:`closed` 在 Close 调用时置位,只表示拒绝新准入;`doneCh` 在 writer 排空并 sync 后才关闭。
U-0185 把前者当成了后者——"Close 已排空,屏障空满足"这句推理只对 `doneCh` 成立。自己上一轮的修复留下的口子(C8:
两个状态被一个判断混用)。

## 方案选择

- **closed 时固定等一小段再返回。** 用时间补状态同步,审查明确反对。
- **closed 时直接返回 ErrClosed。** 关闭完成后的 Sync 会从幂等 nil 变成报错,U-0185 有意保留的行为被改掉;
  而且关闭进行中时调用方要的是"等它落盘",不是一个错误。
- **去掉 closed 分支,统一按 doneCh 判(采用)。** 关闭进行中照常把屏障送进队列——`drainAndClose` 会答复队列里
  的每一条;等待时 `doneCh` 关闭才算屏障被构造性满足,此时返回 `w.terminal()`(最终 sync 失败时 drainAndClose 已
  置 terminal,不能读成成功)。发送与等待都受 ctx。完全关闭后:writer 已退,`doneCh` 已关,第一个 select 立即返回
  `terminal()`(干净关闭为 nil)——既有幂等行为保留。

## 改动

`nestwal/wal.go`:`awaitWriteBarrier` 删除 `closed` 早返回,两处 `doneCh` 分支返回 `w.terminal()` 而非 nil;
`Options` 加未导出的 `beforeProcessBatch func()` 测试缝(collectBatch 与 processBatch 之间、writer 不持任何锁的
唯一位置),生产为 nil。

## 证明

`nestwal/sync_closing_promises_test.go`:
- `TestWALSyncPromiseWaitsForDrainWhileClosing`:`open_control` / `closing` 两个子用例,writer 在缝上被钉住,
  30ms 的 Sync 必须返回 DeadlineExceeded 且 ticket 未完成;
- `TestWALSyncPromiseAfterCompletedClose`:Close 完成后 Sync 仍是 nil,ticket 已由 Close 完成。

修前红:`Sync while writer held: closing=true err=<nil> admitted=1 appended=0 durable=0 ticket=1`(open_control 通过)。
修后 nestwal 含 `-race` 全绿。

## 未做 / 边界

- 为了在 writer 不持锁的那一点钉住它,加了一个未导出的测试缝;试过用 `stateMu` / `terminalMu` 钉,但旧 Sync
  自己也要拿这两把锁,红会变成"阻塞"而不是"提前成功",对不上审查的现象。
- 最终 sync 失败后 Sync 返回 terminal 这一支没有单独的注入测试(需要能失败的文件替身);逻辑是一行 `w.terminal()`。
