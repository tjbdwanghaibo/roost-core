# RR-20260927-22 修复：`Unregister` 取锁后确认 subject 仍在表里，旧 subject 已被 forget 时注销当前登记

问题：[RR-20260927-22](../bug/RR-20260927-22.md)（来源 [OPEN-ITEMS-2026-09-27](../review/OPEN-ITEMS-2026-09-27.md) B39）。
日期 2026-09-27；实施基线 `3d325be`（已含批次 2、3、6 的合并），分支 `fix-r7-extra`。状态：已修复、本地验证通过，已本地提交，未合入 main / 未发布。
codebase-memory 图谱已过期（generation 09-26），以下行号与结论来自当前源码与实跑。

## 根因（基线 `3d325be`）

- `sync/entitysync/manager.go:451` `Unregister` 无锁取 `subj`，`:455` 才取 `subj.mu`，之间不确认它仍是表里的那一个。
- `forget`（`:587` 在 `m.mu` 下删表，`:598` 在 `subj.mu` 下才置 `forgotten`）可以在这段窗口里整段完成，或只完成删表那一半；flush 在
  `flush.go:391` 于 `subj.mu` 内判定“退役完成”、放锁后才调 `forget`，所以即便 `Unregister` 先拿到锁，删表也可能在它执行期间发生。
- 删表一放开，同 ID 就能 `Register` 新 subject（`releaseRetracted` 把 RR-70 撤销记录移入 `resubmits`），政策随即以 `SubscribeStamped` 在新登记上订阅。
  `Unregister` 在旧 subject 上取的释放戳比这次订阅戳大，`dropRetractedSubject`（`policy_queue.go:398-413`）又按 ID 删掉新登记名下的记录并发释放通知，
  政策按戳规则删掉新登记上的活订阅：新 subject 仍登记，会话 7 的订阅与待交还记录都没了。

## 决策：按 ID 注销当前登记（主记录修复约束的第二种）

`Unregister` 取 `subj.mu` 后在 `m.mu` 读锁下确认 `m.subjects[id] == subj`；不是（已被 forget 摘表，或 Manager 已 Close）就重新查表，对当前 subject 执行注销，
查不到返回 `ErrSubjectNotRegistered`。读锁一直持有到按 ID 删完撤销记录，之后放开再做 `retireLocked`。

为什么选“注销当前登记”而不是“旧登记已结束、什么都不做”：

- `Unregister(id)` 的调用方按 ID 表达“这个实体不再同步”（demo 的 `leaveLocked` 离场、`RetractSyncSubject` 的回滚撤销）。与它并发出现的新登记来自卸载后重载
  （kit / scene 的 `OnEntityLoaded`、RR-59 排队登记）或业务再次 `Register`。按“空操作”处理，这次注销对调用方返回成功（或“未登记”，demo 两处调用都当作已离开），
  重新登记的那一个却在业务注销之后继续存活并继续发送，业务没有任何信号知道要再注销一次。
- 两种都是某个串行顺序的结果；选择“当前登记”时，线性化点是取锁后确认仍在表里的那一刻，调用方的意图总能落到一个真实存在的登记上。
- 主记录红用例（原文收入）只断言“新登记仍在时不得丢掉它的订阅”，两种方案都能过；本方案另加一条回归钉住选定语义（见下）。

只看 `forgotten` 标记不够：`forget` 先删表、后置标记，`Unregister` 恰好在两者之间拿到锁时标记还是 false（第二条回归覆盖，只加 `forgotten` 检查时仍红）。

锁序：`subj.mu → m.mu` 与 `subscribe`（`subscriptions.go:357-361`）、`retireLocked → sessionHoldsSubject` 相同；`resubmitMu` 是叶子锁，在 `m.mu` 读锁内取不引入新序。
读锁不覆盖 `retireLocked`：它经 `sessionHoldsSubject` 再取 `m.mu` 读锁，RWMutex 读锁重入遇到等待的写者会死锁。
持读锁期间 `forget` 摘不了表，所以同 ID 不会有新登记，按 ID 删掉的撤销 / 待交还记录都属于本次登记；释放戳在同一段里取，新登记上的订阅戳一定更大（RR-85 的前提因此成立）。
通知仍经 `queueReleases` 排到政策阶段，不在调用方路径上回调。重试只在取到的 subject 被摘表时发生，每一轮都意味着一次退役已经完成（或 Manager 已关闭，下一轮查不到即返回），不会空转。

未采用：在 `Unregister` 全程持 `m.mu` 读锁——`retireLocked` 需要重入读锁，改它的锁需求超出本条范围。

## 文件与行为

- `sync/entitysync/manager.go`：`Unregister` 改为“查表 → 取 `subj.mu` → 读锁下确认仍在表里（否则重查）→ 取戳、收集释放、按 ID 删撤销记录 → 放读锁 → 退役”；
  godoc 补一句按 ID 注销当前登记。新增测试缝 `unregisterLookedUp`（取到 subject 之后、取锁之前调用，生产恒为 nil，照主记录原文）。
- `sync/entitysync/unregister_forgotten_test.go`（新）：
  - `TestUnregisterOfAForgottenSubjectDoesNotReleaseTheNextRegistration`：主记录红用例原文。
  - `TestUnregisterBetweenUnlinkAndForgottenRetiresTheCurrentRegistration`：`Unregister` 停在取锁前，flush 发出旧 subject 的 remove 进入 `forget`，
    在 `forgetUnlinked`（已摘表、未置 `forgotten`）窗口里同 ID 重新登记并订阅，再放 `Unregister` 取锁。断言选定语义：当前登记被退役、它上面的政策订阅被释放、
    不留待交还记录。

## 兼容性

- 行为变化只在上述竞态窗口：之前破坏新登记（留着登记、丢掉订阅），现在注销新登记。串行调用的行为不变，返回值集合不变（nil / `ErrSubjectNotRegistered`）。
- `RetractSyncSubject` 走同一个 `Unregister`，本修复未改变它“锁外比对状态再按 ID 注销”的既有窗口（见未验证项）。

## 未验证项 / 风险

- `RetractSyncSubject`（`manager.go` 同文件）在锁外比对 `subj.state == state` 后调 `Unregister(id)`；比对与注销之间若同 ID 被 forget 并以另一个状态重新登记，
  会注销那个新登记。这是修复前就有的窗口（之前 `Unregister` 同样按 ID 重新查表），本修复没有扩大它；调用方在 Nest 持有该实体锁、实体是本事务新建的，
  实际触发需要同 ID 的旧 subject 恰在此刻完成退役。未写回归、未另立条目，交主会话判断是否登记。
- 没有生产负载下的竞态统计；两条回归以测试缝确定性进入窗口。
