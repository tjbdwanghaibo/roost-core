# RR-20260928-03 修复：本地已提交、Remote 部分被明确拒绝的回复带 `nest.ErrRemotePartRejected`

问题：[RR-20260928-03](../bug/RR-20260928-03.md)。日期 2026-09-28；基线 `9568140`；worktree 分支 `fix-r9-b15`（叠在 RR-20260928-01、02 之后）。
codebase-memory 图谱停在 09-26，已过期，未使用；以源码为准。

**范围说明**：哨兵与判别表新行已完成；**维护者要求的末行兜底“不命中以上任何一行：未提交”没有加**——逐一列举落到兜底的回复时找到反例（见下文“兜底行核对”），按任务要求停下报告，由主会话 / 维护者决定。

## 根因

- `nest/msg.go` `finishRemoteWriteBatch` 的 `m.remoteCommitted` 分支（本地事务已提交）里 `batch.Commit` 失败时，只把 Remote 的原因错误返回；
  `nest/nest_dispatch.go:77`（基线）把它 `errors.Join` 成 `nest: finish remote write batch: …`。`replyAfterCommit` 按 RR-46 只在 Remote 也确认时加
  `ErrAfterCommitFailed`，结果未知的 Commit 错误自带 `entity.ErrRemotePersistenceIndeterminate`（第 2 行），而**明确拒绝**的 Commit 错误
  （strict：投影器写权威被拒，tracker 终态 Rejected → `ErrRemoteRejected`；Durability 0：直接写权威被拒，如 `ErrRemoteVersionConflict`）两者都不带，
  判别表一行都不命中。RR-20260926-58 起这种情况只丢弃 Remote 部分、本地部分照常生效，调用方却看不出本地已提交。

## 决策

- 名称沿用 `nest.ErrRemotePartRejected`（维护者建议名；`Part` 对应 RR-58 “只丢弃 Remote 部分”，与第 5 行 `ErrNestedTransactionCommitted` 的“部分已提交”并列）。
- **判据**：本地已提交后 `Commit` 返回错误且**不带** `entity.ErrRemotePersistenceIndeterminate` 即为明确拒绝。依据：`entity.ErrRemotePersistenceIndeterminate` 的契约
  （`entity/remote_manager.go`：后端可能已接受时返回它），以及框架自带 `remoteentity.(*remoteWriteBatch).Commit` 的实际分支——
  Durability 0 的非未知错误全部按拒绝处理（`rollbackRemoteEntries`、`rejected = true`、`markRejectedReloadPending`），其来源是 `ApplyRemoteCommits` 的写前校验
  （`ErrRemoteRejected`、`Validate`、编码、tracker 容量）或后端的 fenced / version conflict / rejected；strict 的 `waitRemoteTransaction` 只有 tracker 终态 Rejected
  （`ErrRemoteRejected`）、Indeterminate、截止（RR-24 起带未知哨兵）三种结论（tracker 在 `FinalizeLocked` 时登记、pending 不淘汰，`remoteStatusError` 的 default 分支不可达）。
  Durability 1 Commit 不返回错误。所以两类互斥、且覆盖全部 Commit 错误。
- **位置与顺序**：事实在 `finishRemoteWriteBatch` 记下（`Msg.remotePartRejected`），包装在 `dispatchNest` 里紧跟 `ErrAfterCommitFailed` 的包装、
  在 `ErrNestedTransactionCommitted` 之前，写法同样是 `fmt.Errorf("%w: %w", 哨兵, err)`，已带时不重复包。与 `ErrAfterCommitFailed`（`remoteConfirmed` 为真）
  互斥；与第 2 行互斥（判据）。只增加 `errors.Is` 命中，原因链不变（回归断言 `ErrRemoteRejected` / `ErrRemoteVersionConflict` 仍可 `errors.Is`）。
  `requeueAllowed` 不受影响（`remoteCommitted` 已使它越过提交点）。
- **判别表位置**：插为第 4 行（第 3 行 `ErrAfterCommitFailed` 之后、原第 4 行 `ErrNestedTransactionCommitted` 之前），让“可能已提交”的行仍是表头连续的前 5 行。
  排在 `ErrNestedTransactionCommitted` 之前，是因为两者可能并存（`PrepareRemoteWriteBatch` 执行期间开的独立事务已提交，B19 窗口）：此时消息自己的事务其实已提交，
  第 5 行“消息自己的事务没提交”的说法不成立，第 4 行更准确。
- 未采用：放在表尾（第 13 行）免去改号——会破坏“前 N 行 = 可能已提交”的规则，且与第 5 行并存时先命中错误的一行。

## 兜底行核对（未加兜底行：发现反例）

任务要求加末行“不命中以上任何一行：未提交”，并逐一列举仍会落到兜底的回复。按回复来源逐类核对（源码 `9568140` + 本修复）：

| 落到兜底的回复 | 来源 | 是否确实未提交 |
| --- | --- | --- |
| `ErrQueueFull`、`ErrNestStopped`（准入 / 停机排空时未执行的排队消息）、`ErrHandlerNotFound`、`ErrInvalidMessage`、`ErrParamMismatch`、`ErrSyncInHandler` / `ErrAsyncInHandler` | `client.go` 准入、`dispatcher.go` 停机排空 | 是：handler 未执行 |
| `ErrNestFenced`（派发入口 / `runNestLogic` 入口的 `FenceError`） | `nest_dispatch.go`、`runNestLogic` | 是：未执行（handler 已执行、提交前被拒的形态带 `ErrCommitRejected`，第 12 行） |
| 慢阶段准备失败（`prepareRemoteSnapshots`、`prepareRemoteWriteBatch` 的所有权 / 冷加载错误、`prepareSlowEntities`）、快续行投递被拒 | `dispatchNest` 前半、`remote_dispatch.go` | 是：handler 未执行，批次 Abort |
| 可回滚事务里业务返回错误 / panic（事务回滚） | `invokeHandlerTransaction` | 是 |
| 不能回滚的 handler（RollbackNone）返回业务错误 / panic | memory 快路径 | 未提交，但失败前的内存修改不撤销（与第 6、12 行同一语义）——兜底行若加，需带这条说明 |
| pipelined ticket 失败 | `pipelined_completion.go` | 不会落到兜底：`CommitTicket.Err` 契约只允许 nil 或 `ErrCommitIndeterminate`（第 1 行） |
| 纯本地提交后收尾失败 / Remote 已确认后收尾失败 / 本地已提交 Remote 未知 / 本地已提交 Remote 被拒 | `dispatchNest` | 不会落到兜底：第 3、2、4 行 |
| **`ErrNestCanceled`（+ `context.Canceled` / `DeadlineExceeded`）——调用方 ctx 在等待回复期间结束** | `client.go` `waitResult` 的 `<-ctx.Done()` | **否：反例**。消息已准入、继续执行，可能随后提交 |
| **`ErrNestTimeout`——同步等待超时（`NestSyncTimeout` 默认 5s，或请求的 `SyncWait`）** | `client.go` `waitResult` 的 `<-timer.C` | **否：反例**。同上 |

反例实跑（探针 `probes-r15/zz_fallback_counterexample_probe_test.go`，`//go:build probe`，未提交；strict + RollbackUndo handler 加一条 mutation，committer 在 gate 上等，
调用方先截止，之后放行 gate）：

```text
$ GOWORK=off go test -tags probe -run TestZZFallbackCounterexampleWaitDeadline -count=1 -v ./nest
PROBE reply=nest: sync canceled
        context deadline exceeded hitsAnyTableRow=false committedAfterReply=1
PROBE reply=nest: sync timeout hitsAnyTableRow=false committedAfterReply=1
```

两条回复都不命中判别表任何一行，而事务随后提交了。USER_GUIDE 表后已有一段说明它们“只说明没等到回复、不说明结果……按‘可能已提交’处理”，与“兜底：未提交”
直接矛盾。另外 `ErrNestCanceled` 同时用于“未执行”（`validateClientDispatch`、派发入口、`runNestLogic` 入口的 ctx 已取消）与“等待截止”，调用方无法用 `errors.Is` 区分。
可选处理（待决定，未实施）：在兜底之前加一行“`nest.ErrNestCanceled` / `nest.ErrNestTimeout`：调用方没等到回复，结果未知、按可能已提交处理”，或把兜底行写成
“不命中以上任何一行、且不是 `ErrNestCanceled` / `ErrNestTimeout`：未提交”，或给等待截止单独一个哨兵。
