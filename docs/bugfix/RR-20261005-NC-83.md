# NC-83 修复：player TCP 停机保留所有权直到真实排空

[问题](../bug/RR-20261005-NC-83.md) · [证据](evidence/noncore-bugfix-20261005-n02/README.md)。已修复（生成器）、声明场景验证，未发版。

## 决策与实现

只改生成器 `codegen/internal/roost/render_player_tcp.go`，生成物形状变化限于下列三个函数与新增测试：

- `Server.Stop`：首个调用关闭 listener/连接；之后的调用不再以 `listener == nil` 判定“已停”，而是同样在自己的 ctx 内等待 accept 循环与连接 goroutine 返回。从未 Start 的 server 仍返回 nil，成功排空后再调用立即返回 nil。
- `Mod.StopWithContext`：`server.Stop` 出错时返回错误并**保留** `mod.server`，lifecycle 也不提前结束；成功后才释放 server，再在同一 ctx 内等会话关闭派发器。
- `Runtime.stopLifecycleContext(ctx)`：关闭停止信号（在 lifecycleMu 下保证只关一次），在 ctx 内等派发器排空；超时返回 `session-close subscribers still running: <ctx err>`，再次调用继续等。原 `stopLifecycle()` 保留为无期限包装，给既有调用方。

沿用 RR-20261004-NC-04（Ops）已定的“取消/超时不等于已排空，错误时保留同一对象供重试”契约，不新造机制；没有终止不配合的回调，也没有增加 goroutine 或重试循环。

## 兼容性

App 一次停机的结果不变（仍按 ctx 返回错误、保留依赖）。直接重试 Stop 的调用方现在会等待到真实排空。已生成工程需要用新版生成器重新生成 `server_gen.go` / `server_gen_test.go`（codegen-owned，`generate --check` 会提示差异）；`auth.go` 等应用文件不受影响。配置、wire 与公开 API 不变。

## 验证

- 生成测试新增 `TestAStopRetryWaitsForAConnectionTheFirstStopCouldNotDrain`、`TestAModStopRetryKeepsTheServerUntilItDrains`、`TestABlockingCloseSubscriberDoesNotHoldStopPastItsContext`：与旧生成器的 `server_gen.go` 组合时 3 红（`retry Stop reported success...`、`server kept = false`、`ignored its context`），新生成物 3 绿。
- game-demo 生成工程（`-template game-demo`，replace 指向本 worktree）：TCP 包 race×3 117 pass；全工程 build/vet/test 通过；`go test ./codegen/...` 通过。
- overlay：真实 TCP 握手下不配合的认证回调占满 `max_handshakes`，第三条连接 201ms（handshake_timeout）被拒、超出 `max_connections` 立即关闭、回调返回后名额全部归还——控制通过。

## 未验证 / 风险

Dispatch handler 不配合 ctx 的同类路径与认证回调共用同一 wait，未单独加用例；真实负载下大量卡死回调的 FD/内存占用、外部网关/客户端重连行为未验。
