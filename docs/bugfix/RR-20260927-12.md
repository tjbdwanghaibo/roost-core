# RR-20260927-12 修复：撤销新建实体使用专门的销毁原因 DestroyReasonCreateRevoked

问题：[RR-20260927-12](../bug/RR-20260927-12.md)（OPEN-ITEMS C27）。日期 2026-09-27；基线 `d4234c9`；worktree 分支 `fix-r7-ent`。
codebase-memory 图谱停在 09-26，已过期，未使用；以源码与 `rg` 为准。

## 决策

- 新增 `entity.DestroyReasonCreateRevoked EntityDestroyReason = 254`，紧挨 `DestroyReasonMemoryUnload`（255）：框架原因从高位往下分配，低位（0 起）留给业务的
  领域别名，回应 bf-35 当时“新增数值可能与业务值冲突”的顾虑。
- `revokeCreated` 的 post-release 改传它；`EntityManager.Destroy`（业务传入的原因）与 `ManagerAccess.Unload`（`DestroyReasonMemoryUnload`）不变。

## 按原因分支的代码核对（`rg DestroyReason` / `OnDestroy(` 全仓，含 `.tmpl`）

| 位置 | 用法 | 是否受影响 |
| --- | --- | --- |
| `entity/entity_manager.go` Destroy、`entity/manager_access.go` Unload | 透传 / 固定 MemoryUnload | 否 |
| `entity/component_base.go`、`entity/entity_base.go`、`skill/combatcomponent/component.go` | `OnDestroy` 空实现 / 转发 | 否 |
| `codegen/internal/entity/gen.go:540` 模板 `generatedOnDestroy`（及 testdata 生成物） | 原样转给 `ComponentManager.DestroyAll(reason)` | 否（不分支） |
| `codegen/internal/roost/add_workflow.go:161` 生成 Lifecycle `Destroy` | 业务传入原因 | 否 |
| `demo/game/entities/scene/entity.go.tmpl` `Scene.OnDestroy` → `runtime.Stop(reason)`；`demo/game/scene/runtime/*.go.tmpl` 各系统 `Stop` | 只转发 / 忽略参数 | 否 |
| `demo/internal/service/game/{playerowner,spawner}.go.tmpl` | 调 `Destroy(…, DestroyReasonCommon, …)` | 否 |

没有任何代码按 `DestroyReasonCommon` 判断“是否业务删除”，所以新值不会落进意外分支；生成器模板与 demo 无需改动、无需重生成。

## 文件与行为

- `entity/entity_kind.go`：新常量与注释。
- `entity/manager_factory.go`：`revokeCreated` 改用新原因，注释同步。
- `docs/USER_GUIDE.md` §4：撤销发布那句改为 `OnDestroy(entity.DestroyReasonCreateRevoked)`。
- 回归：`nest/create_revoke_destroy_reason_promises_test.go` `TestRevokedCreationIsDestroyedWithCreateRevokedReason`（strict handler 新建后失败，
  撤销的销毁回调恰好一次、原因为 `DestroyReasonCreateRevoked`，且不同于 Common / MemoryUnload）。

## 兼容性

新增导出常量，非破坏。行为变化：撤销新建时业务 `OnDestroy` 收到 254 而不是 0；业务若以“原因 == 0”判断业务删除，现在撤销新建不再命中它（这正是本条要的区分），
若以“原因 != MemoryUnload 即业务删除”判断，需要把新原因一并排除。业务自定义原因若恰好用了 254，需要改用低位值。
