# RR-20261004-06 修复：竞选失败 / 取消后由 election 用独立、有截止的 context 撤销 lease

问题：[RR-20261004-06](../bug/RR-20261004-06.md)（来源 [B 线 NC 修复独立复审（第二组）§3 D1](../review/REVIEW-2026-10-04-nc-audit-2.md)）。
日期 2026-10-04；实施基线 main `c888223f`（含 v1.19.0）。状态：**已修复，本地验证通过（含真实 etcd），已提交，未推送、未发版。**

## 根因（基线行号）

`1502f973`（NC-11）之后的 `etcd/driver/election.go`：

- 第 122 / 132 / 138 / 147 / 154 行，Campaign 在 session 建好之后的五个失败分支都是 `cancelSession(); _ = session.Close()`。
- `cancelSession` 取消的是传给 `concurrency.WithContext` 的 `sessionCtx`；SDK `Session.Close`（etcd client v3.7.1 `concurrency/session.go`）是 `Orphan()` 后用 `context.WithTimeout(s.opts.ctx, ttl)` 发 `Revoke`，`s.opts.ctx` 就是这个 `sessionCtx`，于是 Revoke 立即以 `Canceled` 失败。
- 即使删掉显式的 `cancelSession()`，caller 已取消的分支（竞选等待中取消、成功与取消竞争）里 `context.AfterFunc(ctx, cancelSession)` 的桥已经把 `sessionCtx` 取消了，SDK Close 照样发不出 Revoke——只删那一行不够。
- `campaignSession.Close`（第 187–195 行）对正常 Resign 本来就是"先 SDK Close、后 cancel"，所以只有失败路径坏了。

后果：lease 和挂在它上面的候选键 / 领导键留到 TTL（SDK 缺省 60s）。残留的是最低 revision 的领导键时（成功与取消竞争），TTL 内谁都选不上；候补节点周期性超时重试时，每次留下一个孤儿 lease。

## 决策

失败分支统一交给 `election.abandon(ctx, owned, lifetime)`（`election.go:264`）：

1. **同步 Orphan**（`campaignSession.orphan`，`election.go:239`）：停 keepalive、释放 `sessionCtx`，与 `Close` 共用 `closeOnce`——与并发 Resign 的 Close 只有一个生效。不是 SDK session（测试替身）时退回 `Close()`。
2. **Revoke 用 election 自己的 context**：`context.WithTimeout(lifetime, abandonedLeaseRevokeTimeout)`，`lifetime` 是 `cli.Ctx()`（与 NC-11 派生 `sessionCtx` 的是同一个），截止 5s（`election.go:73`）。所以 Revoke 不受 caller 取消影响，关闭 client 会取消它；5s 内没撤成，lease 仍按 TTL 过期（与修前的兜底一样）。
3. **caller 还在等就等它**：`select { <-done; <-ctx.Done() }`。caller 未取消的失败（如 SDK `waitDeletes` 的 "lost watcher"）返回时键已删除，与 `1502f973^` 一致，且上限从 TTL（60s）降到 5s；caller 已取消就立刻返回，NC-11 "按 caller 取消返回"的承诺不变。
4. **election 持有唯一一个 Revoke**：`e.revoking` 记录未结束的那一个；下一次 Campaign 在入场处（`election.go:101`）等它结束（受自己的 ctx 约束），不会排在自己残留的旧键后面，也不会累积后台 goroutine。goroutine 的寿命以 5s 截止和 client 关闭为界。

正常 Resign、成功后 caller 取消保持领导权、setup 取消到达 Grant、loss 观察者与 Close 串行，全部不变。

### 未采用的方案

1. **只删 Close 前的 `cancelSession()`（复审候选修法 1 单独用）**：caller 未取消的分支修好了，但 caller 已取消的分支里 AfterFunc 桥已经取消了 `sessionCtx`，SDK Close 的 Revoke 照样失败；Revoke 上限也仍是 TTL（60s）。负对照见下。
2. **失败时用 `context.WithoutCancel(sessionCtx)` 或 Background 同步 Close**：caller 已取消还要被 TTL 级的 Revoke 拖住，回退 NC-11 的取消承诺。
3. **每次失败丢一个后台 goroutine 不管**：复审明确不接受；没有人能等它，持续失败时无界。
4. **给 `IElection` 加 `Close` / `Stop` 等待 Revoke**：公开接口变化；现有调用方（`etcd/driver/assembly.go` → `kit/etcd` Provide）的停止路径是关闭 client，而 client 关闭已经会取消这个 Revoke，不需要新接口。

- `etcd/driver/election_revoke_promises_test.go`（新）：3 条单元回归——失败分支返回前用活的、有截止的 context 撤销；取消分支立刻返回、election 持有唯一一个 Revoke、下一次 Campaign 等它；关闭 client 结束这个 Revoke。
- `etcd/driver/real_etcd_election_promises_test.go`（新，`//go:build integration`，复用 `startEtcd`，PATH 上没有 etcd 时 skip）：3 条真实 etcd 回归，对应复审触发条件 (a)(b)(d)。`etcd/driver` 原本就有 integration 文件，包集合不变，根包 integration 覆盖门禁仍绿。

## 兼容性

公开签名、lease / fence 格式不变。行为变化：
- 失败的 Campaign（caller 未取消）最多多等 5s 的 Revoke（修前 `1502f973^` 是最多 TTL，v1.19.0 是立即返回但 lease 残留）。
- 上一次失败竞选的 Revoke 未结束时，下一次 Campaign 先等它（≤5s，受 ctx 约束，ctx 到期返回 ctx 错误）。
- 撤销失败不报给 caller（与修前 `_ = session.Close()` 相同）；lease 仍以 TTL 为最终兜底。
无迁移。

## 未验证项 / 风险

- 只跑了单节点 etcd；HA、leader 切换中途、网络分区下 5s Revoke 截止的实际效果没有验证（分区时 lease 仍按 TTL 过期，与修前相同）。
- 5s 截止是固定常量，没有随 session TTL 配置；目前 `createWithEtcd` 不设 `WithTTL`，用 SDK 缺省 60s。
- 没有 benchmark：失败路径多一个短 goroutine，成功路径只多入场处一次 nil 检查。
- 本仓没有 CI job 提供 etcd，真实 etcd 回归只在本机跑；单元回归在默认 `go test` 里守护同一承诺。
