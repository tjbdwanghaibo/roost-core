# RR-20261006-55 修复：被拒的被动候选只告警、事件照常前进；付费之后不再有能失败的派发

问题：[RR-20261006-55](../bug/RR-20261006-55.md)（F08-H+ H1）。基线 `47abe511`，分支 `skspawn`，与 RR-20261006-51～55 同批；验证见 [RR-20261006-51 修复](RR-20261006-51.md)。

## 根因

`dispatchEvent` 把第一个入队失败的候选的错误整个返回；`collectHostEvents` / `drainHostEvents` 在派发成功之后才推进 cursor；`payCostList` 在 `PayCosts` 成功之后才 drain，drain 的错误让未提交的启动被删。

## 决策（错误分类）

| 错误 | 性质 | 处理 |
| --- | --- | --- |
| 候选 Program 不在 Host 能力表里（`ErrHostCapabilityMissing`） | 永久：Host 的表在生命周期内不变，重试同一事件永远失败 | 记 `passive_suppressed`（Result `host_capability`）、计 `skill.passive.dispatch_rejected.total{reason}`、写 Warn，跳过该候选，其余候选照常入队，事件前进 |
| 其他入队错误 | 同一事件重试不会变好 | 同上，Result `rejected` |
| `ErrCastInputInvalid`（不是被动、没有 owner） | 路由的正常过滤 | 原样静默 |
| 根事件表满且都被引用（`ErrRuntimeCapacityExceeded`） | 容量：引用根的施法 / 衍生物结束后表就腾出来；此时还没有候选入队，重试不会重复入队 | **保持原约定**：`collectHostEvents` 留在原处、把错误报给 `Advance` 的调用方，下次重试（既有用例 `TestCollectHostEventsDoesNotAdvanceOrCompactFailedEvent` 原样通过） |

**费用顺序**：`drainHostEvents` 不再返回错误。它跟在已提交的宿主操作（付费、效果、衍生物步进、停止）之后：候选被拒只告警；根事件表满时停在这个事件前、留给 tick 上的 `collectHostEvents`（事件顺序不变）。于是 `payCostList` 在 `PayCosts` 成功之后没有任何能失败的步骤，“付费失败 = 没有付”这一前提成立，不会扣了费又删 cast。被拒的被动 Program 在它自己扣任何费用之前就被拒（`enqueuePassive` 的准入核对），B3 ③ 对两边都成立。`drainHostEvents` 的 8 个调用点去掉了不再可能的错误分支。

未采用：
- 付费之前先派发 / 预检路由——事件由付费产生，派发不了尚未发生的事件。
- 派发失败时退费——要给 Host 加一个可靠的退费操作，失败时又是一层补偿。
- 根事件表满也一律跳过——见“未完成”。

## 未完成 / 待维护者确认

- **根事件表满时 Runtime 仍会停在这个事件上**：引用根的施法要靠排程任务推进才能结束，而排程任务在同一次 `Advance` 里排在事件派发之后，表满且都被引用时只有调用方 `Cancel` / `Interrupt` / `Release` / `RemoveProgram` 能腾出表。是否把它也当成永久拒绝（跳过这个事件的被动路由、告警、前进），与既有用例 `TestCollectHostEventsDoesNotAdvanceOrCompactFailedEvent` 的约定冲突，本批按“原有用例原样通过”保留原约定，留给维护者定。

### 1. 根事件表：配置上界 + 兜底跳过

**上界由哪几个上限组成**（按代码核实，`rootEventReferenceBound` 的注释逐条写了出处）：

| 引用根的东西 | 不同根数上界 | 出处 |
| --- | --- | --- |
| 未结束的施法 | `MaxActiveCasts` | `startLocked` 准入；每条终态路径（`failCastLocked`、Cancel / Interrupt / 收尾 / charge 取消）都经 `markAbilityCastFinished` 减 `activeCastCount` |
| entity 衍生物（施放中 / 已移交 / 待停止） | `MaxOwnedSpawns` | `hasOwnedSpawnCapacityExcluding` 按 `spawnLivePartitions` 计数，待停止的照样占名额 |
| phase / cast 作用域衍生物 | 施放中时与所属施法同根（已算在施法里）；施法结束后只可能留成待停止，≤ `MaxStopPendingSpawns` | `stopScopedSpawns`、`makeRoomForStopPendingLocked` |
| 已停止 / 已放弃记录 | 不引用根 | `rootEventReferencedLocked` 只看 `spawnLivePartitions`；所以 `MaxAbandonedSpawns` 不进上界 |
| 排程任务：未执行的被动激活、`QueueExternalEvent` 的外部事件、能力覆盖到期、已结束施法残留的任务 | **没有配置上界** | `scheduledTaskRootLocked`；`ActivatePassive` / `QueueExternalEvent` / 能力覆盖不限条数 |

**结构性保证**：`validateRootEventLimit` 要求 `RootEventLimit > MaxActiveCasts + MaxOwnedSpawns + MaxStopPendingSpawns`（默认 8192 > 4480）。`NewRuntime` 在默认值补齐之后校验，违反时以 `ErrRuntimeLimitsInvalid` panic（`NewRuntime` 没有错误返回值，改签名要动 240 多个调用点；这是装配期配置错误，与 `regexp.MustCompile` 同类）；`RestoreRuntime` 用 checkpoint 里的上限校验，违反时返回同时 `errors.Is` `ErrCheckpointCorrupt` 与 `ErrRuntimeLimitsInvalid` 的错误。错误信息点出四个选项和当前值。于是施法与衍生物占不满这张表。

**兜底（选 A）**：排程任务钉住的根没有配置上界，表仍可能被它们占满（同一 tick 里大量不同根的事件各自排了被动激活即可）。`dispatchEvent` 遇到 `trackRootEventLocked` 的 `ErrRuntimeCapacityExceeded` 时跳过这个事件的被动路由、计 `skill.root_event.capacity_dropped.total`、写一条 Error（事件 ID、根、上限、表大小），事件照常前进。`dispatchEvent` / `collectHostEvents` 因此不再返回错误，`drainHostEvents` 去掉“停在这个事件前”的分支，外部事件任务的派发也不再失败。`ActivatePassive` 是调用方直接调用，表满时仍把 `ErrRuntimeCapacityExceeded` 返回给调用方。

**改写的既有用例**：`TestCollectHostEventsDoesNotAdvanceOrCompactFailedEvent`（原约定：表满时报错、cursor 不动、事件不压缩，引用结束后原地重试）按新语义改写为 `TestCollectHostEventsSkipsEventWhenEveryRootIsPinned`：合法配置（`RootEventLimit 4 > 1+1+1`）下用 `QueueExternalEvent` 排在之后 tick 的外部事件钉住根 1～4，第 5 个根的宿主事件被跳过、计数 +1、根不进表，cursor 越过它，其后同根 1 的事件照常派发，全部事件被压缩。原用例靠直接塞一个 running cast 加 `RootEventLimit: 1` 构造，这种配置现在构造即被拒。`TestRuntimeRetentionIsBounded` 去掉了没用到的 `RootEventLimit: 2`（同理会被拒）。

先红（红文本在问题记录）：上面的改写用例是在旧签名（`collectHostEvents` 还返回 error）上跑红的，之后签名改成无返回值，断言只把“返回 nil”换成“cursor 前进到 6”，语义不变。

### 2. 施放中的衍生物被 Shutdown 停下也跑一次 cancel 回调

新 helper `spawnCancelCallbackEvent`：entity 衍生物不论施放中还是已移交，提前停止时跑一次 `cancel`，phase / cast 作用域的不跑。`stopScopedSpawns`（Cancel / Interrupt / 施法失败 / goto 经它）与 `Shutdown` 共用它，仍经 `requestSpawnStop` 这一个停止状态机（待停止的不再跑回调，回调只在第一次请求时跑）。`Shutdown` 的 cast 参数仍是 nil（表现用宿主当前 revision），未改。端到端矩阵 `shutdown while casting` 一格由“不超过一次”（`wantCancel: -1`）改为恰好一次，4 种衍生物修前红、修后绿。

未改：`RemoveProgram` 有同样的不对称（只给已移交的传 `"cancel"`，施放中的不跑）。不在本次授权范围内，留给维护者定。

### 1. 排队任务上限，计入根事件表上界

**新选项** `RuntimeOptions.MaxQueuedTasks`（默认 2048）：排程里“排队任务”的条数上限。排队任务 = 未执行的被动激活（`PassiveRouter` 路由的候选、`ActivatePassive`）+ `QueueExternalEvent` 排的外部事件（`isQueuedTask`）。计数 `Runtime.queuedTasks` 在 `scheduleSystem` 入队时加、`executeScheduledTask` 出队时减，checkpoint 恢复时按排程重数。

**上界**：`validateRootEventLimit` 改为要求 `RootEventLimit > MaxActiveCasts + MaxOwnedSpawns + MaxStopPendingSpawns + MaxQueuedTasks`（默认 4096 + 128 + 256 + 2048 = 6528 < 8192），`NewRuntime` / `RestoreRuntime` 同一处校验。

**入口拒绝**（`admitQueuedTaskLocked`，在任何副作用之前）：

| 入口 | 满了时 |
| --- | --- |
| `QueueExternalEvent` | 返回 `ErrQueuedTasksFull`，不排任务。`ErrQueuedTasksFull` 同时 `errors.Is` `ErrRuntimeCapacityExceeded` |
| 事件派发里的被动候选（`enqueuePassive`） | 按“被拒”处理，与 RR-55 同一条路：`passive_suppressed`（Result `queue_full`）、`skill.passive.dispatch_rejected.total{reason="queue_full"}`、Warn 日志；其余候选照常，事件照常前进 |
| `ActivatePassive` | 返回 `ErrQueuedTasksFull`，不记根、不排任务（准入在 `trackRootEventLocked` 之前） |

**其余排程任务为什么不再钉住根**（`queuedTaskRoot` 只认排队任务；之前的 `scheduledTaskRootLocked` 认四类）：

- **能力覆盖到期**：维护者要求“论证不会无界”。按代码核实，覆盖条数**没有**配置上限（每次 `enabled=false` 加一条，只受 `MaximumDurationTicks` 限制存活时长），所以不能靠条数论证；但到期时 `expireAbilityOverlay` 只发一条 `ability_enabled_changed` 运行时事件（`appendRuntimeEvent` + 施法事件日志），不走被动路由、不读写 `rootEventCounts` / `procLedger`。根被淘汰只影响这两张表，覆盖到期与它们无关，钉住根没有保护任何东西。于是改为不钉：覆盖条数再多也不占根事件表。覆盖条数本身（内存）是否要加上限，见“仍未闭合”。
- **已结束施法残留的任务**：Cancel / Interrupt / charge 取消只撤当前 phase token 的任务，旧 token 的任务会留到到期。它们执行时 phase token 不匹配或施法已是终态，`executeScheduledTask` 直接返回（唯一的分支 `beginCastRecovery` 要求 `logicalFinished`，取消类终态不满足；正常收尾到 `CastFinished` 时排程里已没有它的任务），不再在这个根下产生事件。未结束施法的任务与施法同根，已由施法计入 `MaxActiveCasts`，不必另算。
- 弹药回复没有根（与之前相同）。

另：`ActivatePassive` 的根取 `RootEventID`，为 0 时取 `EventID`；之前记进表的是这个根，排进去的任务钉的却是 `RootEventID`（可能是 0）。现在两处都用 `eventRootID`。

**兜底分支保留作防御**：`dispatchEvent` 的跳过逻辑不变，注释改为“合法配置下走不到”。`TestCollectHostEventsSkipsEventWhenEveryRootIsPinned` 改为绕过入口准入、直接往排程里塞 5 个外部事件任务（合法配置 `RootEventLimit 5 > 1+1+1+1`）验证兜底仍然生效；新增 `TestLegalConfigurationNeverReachesTheRootTableFallback` 从 `QueueExternalEvent`、被动路由、`ActivatePassive` 三个入口一起压 40 tick，断言兜底计数不增长、排队数不超过上限。

**checkpoint**：版本 8 → 9，payload 加 `max_queued_tasks`；缺这个字段（0）、或排程里的排队任务多于它，按 corrupt 拒绝。

### 2. `RemoveProgram` 停施放中的衍生物也跑 cancel 回调

`RemoveProgram` 改用 `spawnCancelCallbackEvent`（与 Shutdown / Cancel / Interrupt 共用）：entity 衍生物不论施放中还是已移交都跑一次 `cancel`，phase / cast 作用域的不跑；施放中的仍把所属施法传给 `requestSpawnStop`（已移交的传 nil，与之前一样），待停止的不再跑回调。端到端矩阵新增 `remove program while casting`（修前 4 种衍生物红）与 `remove program after handoff`（修前已绿，锁住已移交路径不回退）两格。

### 3. `NewRuntime` 违反上界保持 panic

不改签名（理由同“后续”：240 多个调用点，装配期配置错误）。panic 信息现在写出全部五个选项及补齐默认值后的当前值，例如 `RootEventLimit (4) must exceed MaxActiveCasts (1) + MaxOwnedSpawns (1) + MaxStopPendingSpawns (1) + MaxQueuedTasks (2048) = 2051`。`TestNewRuntimeRejectsRootEventLimitNotAboveReferencedRootBound` 逐项断言 `Option (value)`，并新增“旧上界下合法、算上默认排队上限后不合法”与“调大 `MaxQueuedTasks`”两例。
