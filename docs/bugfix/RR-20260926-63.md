# RR-20260926-63：RR-43 回归改为事件同步；AcknowledgeRemoteCommit 幂等且并发安全写入契约，测试替身加锁；规范与 Saga 运维说明

问题：[RR-20260926-63](../bug/RR-20260926-63.md)（W-2026-09-26-01 已在 WANTED 分流至此；探针 [REPRO-2026-09-26-05](../bug/REPRO-2026-09-26-05.md) §10）。
日期 2026-09-26。实施基线：main `3e26f91`（本批 RR-58、60、61、62 提交之后）。状态：已修复，本地验证通过，已本地提交，未推送/发布。

## 根因

1. **RR-43 回归窗口**：`remoteentity/versioned_lock_touch_generation_test.go` 的 `TestVersionedLockTouchRestartStressNoLostRenewal` 以“新代际 200ms 内是否出现第一次续期”
   判定漏启动。代码没有真实漏启动路径（新代际在 `TryLock` 的 `l.mu` 临界区内同步登记续期 goroutine），但 race + 负载下 goroutine 第一次 tick 可能晚于 200ms，
   被误判为漏启动（审计 1/50 轮、1,000,000 次中 2 次）。另一条 `TestVersionedLockNewGenerationRenewsWhileOldTouchGoroutineExits` 用 500ms / 1s 的轮询窗口，同类风险。
2. **AcknowledgeRemoteCommit 并发（W-2026-09-26-01 根因）**：RR-38 之后，投影器报告“结果未知”（tracker Indeterminate）时 finalizer 按设计回源 Applied 并自行发布
   （`transaction_manager.go` `publishAppliedRemoteTransaction` → `afterRemoteCommit` → `acknowledgeRemoteCommit`），投影器对同一事务的重试同时走
   `ApplyRemoteCommits` → `afterRemoteCommit` → `acknowledgeRemoteCommit`；两条路径都不持实体锁，并发调用参与者的 `AcknowledgeRemoteCommit`。生产生成实体经
   `dataengine.Tracker.AdvanceVersion`（原子 CAS，版本相等直接成功）是安全的；测试替身 `testRemoteEntity` 直接写 `dirty` 字段，`-race` 报 DATA RACE。
   `IRemoteCommitParticipant` 的契约没有写明“幂等且并发安全”，手写参与者无从得知。
3. **文档**：roost-coding 里“若未来要支持投影时拒绝后的在线恢复，先设计完整内存与 Sync 回滚契约”一句已被 RR-30 / 39 的定案契约取代；SAGA.md 没说明
   屏障期间的重投会消耗 JetStream `MaxDeliver`。

## 决策（修复约束）

1. **RR-43 回归事件同步**（只改测试，不改 `versioned_lock.go`）：
   - 压测：`TryLock` 返回后**同步**检查锁登记的续期代际是否就是新 token（`registeredTouchGeneration`，读 `touchMu` 下的 `touchGeneration`）——这正是 RR-43
     缺陷的判据（修前旧登记挡住新代际）；再等到新代际的第一次续期。等待只受 30s 挂死保护（`touchHangGuard`），不是正确性窗口：负载下续期晚到只会等更久。
   - 状态注入用例：续期计数改为事件等待（stub 每次续期关闭并替换 `renewed` channel，`awaitRenewals(token, n)`），并补断言“旧 goroutine 退出后新代际的登记仍在”、
     “Unlock 后登记为空”。goroutine 回到基线的轮询上限放宽到同一挂死保护。
   - 负对照：把 `startAsyncTouchLocked` 临时改回 RR-43 的缺陷（`touchGeneration != ""` 即不启动），两条用例都确定性变红（见验证），恢复后通过。
2. **契约**：`entity.IRemoteCommitParticipant` 注释写明 `AcknowledgeRemoteCommit` 必须幂等且并发安全、说明并发来源（投影器重试与 finalizer 回源发布、outbox 重放 /
   Committed 对账）、不持实体锁、不能假设与 Build / Rollback / 另一次 Acknowledge 互斥；生成实现如何满足，手写实现与测试替身须自行保证。
   `acknowledgeRemoteCommit` 调用处加同义注释；`REMOTE_ENTITY.md`“WAL 与 outbox”补同一条。
3. **测试替身加锁**：`testDirty` 改为带互斥的 `Dirty()` / `set()` / `SelfClean()`，`testRemoteEntity` 的 Build / Acknowledge / Rollback 与各用例的读写都经它
   （原先直接读写 `.dirty.dirty` 的 40 余处改为方法调用）。`fullDocRemoteEntity` 的 Acknowledge 无状态，本就满足。
4. **并发回归**：`remoteentity/ack_concurrency_test.go` `TestProjectorRetryAndFinalizerAcknowledgeConcurrently`（REPRO §10 探针改写，200 轮）：投影器第一次
   Mongo 事务已提交、发布报告未知 → finalizer 回源发布，同时投影器重试同一事务；`-race` 下无数据竞争，且两条路径都结束后写额度归零、实体确认到本提交的版本。
   REPRO §10 原探针放回包内在修后 `-race` 下也不再报告竞争。
5. **roost-coding**：把 RR-30 那一句改为已定契约（屏障、仅内存卸载经 `NestMgr.RunLocal`、Sync 换代 vs Retract、RR-58 只丢 Remote 实体事实、RR-62 可重试哨兵、
   RR-37 / 61 提交后回调只经快池至多一次、RR-63 ack 契约）；仓库 `docs/agent-skills/roost-coding/SKILL.md` 与本机 `~/.codex/skills/roost-coding/SKILL.md` 同步为同一内容。
   `~/.codex/skills/roost-optimize/SKILL.md` 只引用 roost-coding 与复审要点，无需改动。
6. **SAGA.md**：补“屏障期间重投可能耗尽 JetStream MaxDeliver”的运维说明：Nak 退避与计数、耗尽后适配层 `Term`（`nats.jetstream.terminal.total{reason="max_deliver"}`）、
   只能由 coordinator 的 `Timeout` / `MaxAttempts` 兜底、默认值约 8 天才耗尽、调小时的核算方法与监控项。

## 交付前对抗性自查（本批五项合并后的最终工作树）

1. **RR-37 只执行一次、不回退**：提交后工作只在“本地已持久提交且 Remote Commit 返回错误”时交给批次（`postRemoteCommit` / `remoteSyncMutation` 同时清空，
   Nest 不会再执行）；批次只接受一次；finalizer 只在终态分支、资源释放之后交付，终态分支都 `return`。RR-61 只把“快池拒绝投递 → 就地执行”改为
   “→ 不执行 + 计数”，交付次数从“恰好一次”变为“至多一次”，不存在重复；没有持久结论仍不 Confirm。RR-58 的 `RejectEntities` 只在拒绝结论下调用，
   对本地实体的 Confirm 仅作用于已持久提交的部分。
2. **Rejected 门处理与 RR-28 一致**：被拒绝的 Remote 实例仍“回滚 + 隔离 → 释放 → 卸载”，从不解冻；Sync 拒绝结论仍在卸载成功之后交付（卸载关闭同步状态，
   被拒绝的冻结内容丢弃）；loader 不支持卸载时不交付、整笔门保持冻结（与修前相同）。RR-62 的登记只在隔离成功之后发生、不改变所有权状态。
3. **本地与 Remote 混合事务的 Sync 内容与事实一致**：本地实体——内存保留、冻结内容交付、事实应用；Remote 实体——实例卸载、冻结内容丢弃、事实丢弃、重载后
   Rebind 全量。回归：policy 层 REPRO §7 改写、Nest 跨层混合事务（periodic / on_change）、无 Sync 状态实体的回退路径。
4. **哨兵不破坏既有 `errors.Is(ErrRemoteFenced)`**：`ErrRemoteEntityReloading` 以 `%w` 包裹 `ErrRemoteFenced`，回归逐项断言两者同时成立；仓内按
   `ErrRemoteFenced` 分类的逻辑（`ApplyRemoteCommits` 的拒绝判定）只看提交 / 投影路径，本哨兵只出现在写准入。卸载中重载的错误同时保留 `ErrEntityRemoved`。
5. **快慢池边界**：业务回调与 Sync 放行只经 `NestMgr.RunLocal` 在快池执行，finalizer goroutine 上不再有任何业务回调；延迟回调的快照在慢阶段捕获、
   快阶段应用，慢阶段执行器被屏蔽；RR-62 的登记只取 wrapper 内部互斥，不取 Entity local 锁、不在快池等待；测试替身加锁不影响生产路径。
