# RR-20260926-76 修复：嵌套独立事务提交结果未知时，返回业务之前 fence 引擎

问题：[RR-20260926-76](../bug/RR-20260926-76.md)（探针 [REPRO-2026-09-26-07](../bug/REPRO-2026-09-26-07.md) §1 探针 3a）。
日期 2026-09-27；实施基线本地 main `62fdbe6`，建立在同批 [RR-20260926-73](RR-20260926-73.md)～[75](RR-20260926-75.md) 之上。
状态：已修复、本地验证通过，已本地提交，未推送 / 未发布。方向按修复约束。codebase-memory 图谱对 `nest/` 已过期（generation 09-26 08:36），
结论来自当前源码。

## 根因（基线源码核对）

- `nest/execution.go:44-47` `invokeHandlerTransaction`：只有消息自己的事务（经它进入 `invokeWithTransaction`）返回的错误满足
  `ErrCommitIndeterminate` 时才 `mgr.Fence(err)`。
- `RunIsolatedTransaction`（`:77-87`）/ memory handler 内新建事务的 `RunDetachedTransaction`（`:57-70`）直接调用 `invokeWithTransaction`，
  不经过 `invokeHandlerTransaction`；`commitDurable`（`:232-244`）在结果未知时只 `markNestedTransactionCommitted` 与 `abandon`，然后把错误交给
  业务。业务吞掉它，外层照常提交、回复 ok，引擎不 fence，后续请求照常受理——WAL 里可能已有这条记录，而内存状态已被 abandon。
- 嵌套事务里拿不到 `NestMgr`：`Msg` 只带 getter，没有引擎引用。

## 决策与实现

- `Msg.engine *NestMgr`（`nest/msg.go`，放在结构体末尾单独一组，不打乱既有字段对齐），`dispatchNest` 与 `msg.getter = mgr.getter` 同处设置；
  Remote 消息的快池续行与重排克隆都再经过 `dispatchNest`，`clean()` 清零。
- `Msg.fenceEngine(cause)`：`m.engine.Fence(cause)`，nil 接收者 / 未经 `dispatchNest` 的消息无操作。
- `commitDurable` 结果未知分支里，`tx.dispatch == nil`（不认领消息的嵌套事务）时在 `markNestedTransactionCommitted()` 之后调用
  `msg.fenceEngine(err)`，随后才 `abandon` 并把错误返回业务。入口是同一个 `NestMgr.Fence`，错误是同一个 `err`（链上是 `ErrCommitIndeterminate`），
  `FenceError()` 因此与消息自己的事务结果未知时相同：`errors.Join(ErrNestFenced, err)`。`Fence` 幂等，业务把错误传回后
  `invokeHandlerTransaction` 再 fence 一次不改变结果。
- 消息自己的事务仍由 `invokeHandlerTransaction` fence（未改）；pipelined ticket 结果未知的路径不涉及嵌套事务（独立事务总是 strict）。
- 不在 Nest 派发里（`currentNestDispatchMsg()` 为 nil）的独立事务没有可 fence 的引擎，行为不变；DataEngine 删除路径
  `admitLocalEntityDelete` 仍自行 `runtime.fail`。

未采用：在 `RunIsolatedTransaction` 返回处按错误类型 fence——拿不到引擎，且与 `commitDurable` 里已有的“嵌套事务结果未知”判断重复；
让嵌套事务认领消息以复用 `invokeHandlerTransaction` 的 fence——违背 RR-49 / 65 的“嵌套不认领”。

## 对抗性自查

- **fence 早于返回业务**：`fenceEngine` 在 `commitDurable` 返回之前执行；回归在 handler 内、`RunIsolatedTransaction` 刚返回时读取 `FenceError`。
- **同一入口与错误**：调用的是 `NestMgr.Fence`，参数就是返回给业务的 `err`；与 `invokeHandlerTransaction` 的调用重复时 `Fence` 幂等，
  `FenceError` 保留第一次的原因。
- **RR-65 保持**：`markNestedTransactionCommitted` 仍先于 fence 执行，消息不重排；传回错误时回复带 `ErrNestedTransactionCommitted`。
- **快池不阻塞**：`Fence` 只取 `lifecycleMu` 与 dispatcher 的 `mu` 各一次写入字段，与 `execution.go:46` 在同一快 worker 上的既有调用相同，无 I/O、无等待。

## 未验证项 / 风险

- fence 之后外层 handler 仍会继续执行到结束，其自己的事务仍会交给 committer：真实 WAL 在结果未知后已粘滞为 terminal（`nestwal/wal.go`），
  会拒绝这次提交；使用不具备该语义的自定义 committer 时外层可能仍提交成功。约束只要求“返回业务之前 fence”，未额外拦截外层提交。
- `skill/combatcomponent` 的 `RunDetachedTransaction` 是否在 Nest handler 内调用（影响面）未核实。
- 未在真实 WAL 故障注入环境验证，回归使用受控 committer。

（`nestwal/wal.go` 只在 terminal 时拒绝追加），fence 之后外层 handler 自己的提交仍会被真实 WAL 接受。第四轮审计的探针 C

由 OPEN-ITEMS B03（探针）→ C07（fence 后外层提交在交给 committer 前返回 `ErrNestFenced`）处理，本更正不改变代码。
