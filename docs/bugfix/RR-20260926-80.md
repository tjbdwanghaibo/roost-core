## 根因（基线 `62fdbe6`）

1. `codegen/internal/roost/shutdown_budget.go:375-411`（`checkShutdownBudgets`）：FAIL 分支经 `configuredShutdownTotal` 取三份配置的最大值（正确），
   WARN 分支却只读 `configs/service/config.<svc>.yaml`。按 doctor 提示只把它改成 101s、`.prod.example.yaml` 与 k8s secret 示例仍 60s 时给 OK——
   按示例部署的进程每次停机都 `mod stop budget scaled down`。
2. `shutdown_budget.go:391`、`:413`：OK 行打印 `serviceShutdownPlan(m.withConfiguredShutdown(root)).grace`，即“按当前配置现在会渲染出的”计划值，
   不是磁盘上的模板。两者只在模板已按当前配置 sync 过时才一致。
3. `codegen/internal/roost/project.go:205-225`（`SyncProject`）：模板在 staging 中按 `withConfiguredShutdown(stage)` 渲染——此时配置还是旧值；
   提交之后（`:219`）才在真实工程上 `refreshGeneratedShutdownConfigs`。减少 Mod 时公式 total 变小（101 → 98），模板宽限期取
   `max(98, 旧配置 101) + 5 = 106s`，随后配置被刷新为 98s；下一次 sync 才渲染出 103s（`project diff` 在两次 sync 之间非空）。
   同时这一步在 `verifyProjectInputs` 与 `commitSyncChanges` 之外：刷新写失败时模板已提交、配置未改；并发编辑只被“段不再逐字相同”跳过，没有拒绝。

## 决策（按维护者批准的修复约束）

- **sync：先确定刷新后的配置值再渲染模板**（约束给的两种做法中的前一种）。`SyncProject` 在复制出 staging、`snapshotProjectInputs(stage)` 之后、
  任何渲染之前，对 **staging** 调 `refreshGeneratedShutdownConfigs`；之后 `syncManifest` / `Generate` / `planStagedProjectCommit` 经
  `withConfiguredShutdown(stage)` 读到的就是刷新后的 total，模板一次渲染到位。刷新过的文件用 `planExplicitStagedFiles(absRoot, stage, refreshed...)`
  变成 `syncChange`（`before` = 真实工程当时的字节），`mergeSyncChanges` 并入同一批提交，按路径排序。于是配置改写：
  - 先于 `verifyProjectInputs`：配置本就是应用自有输入（`snapshotProjectInputs` 覆盖），快照取自刷新之前的 staging，等于真实工程；期间有人改了配置即
    “project inputs changed … rerun”，什么都不写；
  - 在 `commitSyncChanges` 里：每个配置写入前 `verifySyncChangeCurrent` 比对 `before`，任何一步失败都连同已写的模板、配置一起 `rollbackSync`。
  - 未采用“提交后再重渲染一次”：要么第二次提交落在第一次的回滚范围之外，要么得把两轮计划合成一轮，复杂度更高且等价。
- **doctor WARN：三份仓内配置逐份判定**。`shutdownConfigTargets` 的三份文件（dev 配置、prod 示例、k8s secret 示例内嵌的 `config.yaml`）各自读
  `shutdown.total_timeout` 与 `dataengine.shutdown_timeout`，各自与“声明值 + 3s × 未声明数”比较；任一份不足即 WARN，Detail 为逐文件的
  `<file>: total_timeout 60s cannot cover 23 Mods (30s declared + 3s x 22 = 96s)`，以 `; ` 相连，后接原有的 `every stop warns … Set it to 101s`。
  dev 配置沿用原有处理（缺失 / YAML 解析失败交给 config 检查、非法时长为 FAIL）；示例文件不存在则跳过，解析失败或非法时长记为指明该文件的 WARN。
- **FAIL 逻辑不变**：仍是“任一磁盘模板宽限期 < 三份配置最大 total + 5s”，文案与判定一字未动。
- **OK / WARN 行的宽限期取磁盘模板**：`deployedGracePeriods`（FAIL 检查已在用的同一读取）的结果；各模板一致时写 `grace period 106s`，
  不一致时逐个列出 `<file> <值>`，没有模板时写明。OK 行的 total 同理（三份一致时一个值，否则逐文件）。
- 宽限期公式 `max(公式值, 配置里实际生效的 total) + 5s` 与 RR-66 复核的安全方向未改（`serviceShutdownPlan`、`withConfiguredShutdown`、
  `configuredShutdownTotal` 未动）；配置段“只改写生成器原样的段”的规则未改。
- 测试缝：`project.go` 增加未导出的 `syncProjectBeforeCommit func()`（生产恒为 nil），在全部计划完成后、`verifyProjectInputs` 之前调用，
  让并发编辑回归按事件顺序注入，而不是靠 sleep 抢窗口。

修法：
- 解析失败单列 `unreadable`，WARN 里只写“文件 + 键 + 解析错误”：`<file>: shutdown.total_timeout: time: invalid duration "soon"`、
  `<file>: dataengine.shutdown_timeout: …`、`<file>: does not parse: yaml: …`（secret 内嵌配置为 `stringData config.yaml does not parse: …`）；
  不带停机告警与建议值。真正的不足照旧是 `<file>: total_timeout 60s cannot cover …; every stop warns and budgets are cut. Set it to 101s`，两类同时存在时先写不足、再写解析失败，末尾照旧是磁盘模板宽限期（RR-80 的 OK / WARN 行约定）。
- `readShutdownSettings` 给 yaml 错误加上是哪份文档没解析通的前缀。
- **仍为 WARN，不升 FAIL**（论证）：示例文件不被任何进程直接读取，按它部署的是运维复制出的副本；副本里非法的 `total_timeout` 由 viper `GetDuration` 读成 0，
  App 兜底 30s（`app/app.go:313-316`），这种兜底会不会被平台 SIGKILL 已由 FAIL 分支判定——`configuredShutdownTotal` / `configTotalTimeout`
  （`shutdown_budget.go:136-181`）把读不懂的 total 同样按 30s 计入“三份配置最大 total + 5s ≤ 模板宽限期”。升 FAIL 只会让 CI 因一份示例的笔误失败，
  而部署层面的危险已有 FAIL 覆盖。dev 配置的处理不变：YAML 解析失败交给 config 检查、非法时长为 FAIL（`deploy/dev` 直接运行它）。
- 未改：FAIL 判定与文案、宽限期公式、`Set it to` 的取值（RR-77 范围）、非正时长（如 `0s`）仍按“覆盖不了”判定。
