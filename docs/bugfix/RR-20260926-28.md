# RR-20260926-28：Durability 0 未知结果由 finalizer 写持久拒绝收敛

问题：[原始复审](../bug/RR-20260926-28.md)（复现见 [REPRO-2026-09-26-03](../bug/REPRO-2026-09-26-03.md) §4）。日期 2026-09-26。
实施基线：main `87d9499`。状态：代码已修复，适用本地验证通过，已本地提交，未推送/发布。

## 根因（基线行号）

- `remoteentity/transaction_manager.go:429-437`（`ApplyRemoteCommits`）：后端返回非确定拒绝的错误一律记为 Indeterminate 并包装
  `ErrRemotePersistenceIndeterminate`（RR-20260926-20 的修复，正确）；`batch.go:460-463` 于是不回滚，`batch.go:534-541` 的 Close 把 gate、
  ownership 读锁、写额度转交 finalizer。
- `remoteentity/transaction_manager.go:237-262`（`processDeferredRemoteClose`）只在 Applied / Committed / Rejected 收尾，其余一律“隔离 + 退避重试”。
- `remoteentity/mongo_committer.go:206-207`（`CommitStatus`）对不存在的事务返回 Unknown。Durability 1/2 有 WAL，投影最终会写出 Applied
  或持久拒绝；Durability 0 没有 WAL，事务若根本没到达 Mongo（发出前 ctx 过期、断网、StartSession 失败），没有任何路径能让它变确定，
  finalizer 永远重试，写额度逐笔泄漏，实体永久隔离。

## 修复与取舍

1. **持久拒绝**：新增 `MongoCommitter.RejectUnresolvedRemoteCommits`（`mongo_committer.go:463`），与
   `RejectRemoteCommitsInTransaction` 同机制——以相同事务 `_id` 和 digest 插入 Rejected 记录。唯一 `_id` 在“拒绝”与“迟到提交”之间裁决：
   插入成功后，迟到的 Mongo 事务插入同一 `_id` 时冲突而整体中止，`CommitRemoteBatch` 读到记录也只返回 `ErrRemoteRejected`；插入撞键
   （`fmongo.ErrDuplicateKey`）说明事务已存在，重新读取并按真实状态返回（Applied/Committed 发布确认，不回滚；digest 不同按拒绝错误报出）。
   不覆盖已有记录。`Backend` 转发该能力（`backend.go`），存储不支持时返回 `ErrRemoteAtomicBatchUnsupported`。
2. **只对 Durability 0 生效**：`deferredRemoteClose` 记录 `durability`（`batch.go:536` 起由 Close 传入）。finalizer 回源得到 Unknown 且
   durability==0 时调用 `rejectUnresolvedMemoryTransaction`（`transaction_manager.go:338`）；Durability 1/2 的 Unknown 仍交给 WAL 投影收敛，
   finalizer 不能抢先拒绝已经 durable 的 WAL 记录。回源出错、后端不支持、写拒绝出错都视为仍无结论：保持隔离、gate、fence、写额度并退避重试，
   不在无持久结论时释放。拒绝使用的提交内容由 `finalizedRemoteCommits` 按批次实体顺序生成，与提交时的 digest 一致（`commitsLocked` 共用它）。
3. **拿到结论后的收尾**：Rejected 分支改为 `settleRejectedRemoteEntries`（`transaction_manager.go:389`；首版 `9a4ef81` 的
   “解冻”设计已撤回，见文末“复核更正”）：
   - 回滚经 `entity.RunLocal` 的本地执行路径，在每个实体自己的本地锁内调用 `RollbackRemoteCommit`（沿用 RR-20260925-09 的 panic 解锁）。
     finalizer 不是 Nest 快 worker，也拿不到已结束消息的快池续行，`finalizeCtx` 未注入执行器时 RunLocal 就地执行；它与快池 handler 经 Guard
     取得的是同一把实体锁，互斥成立，但**不是**投递到快池执行（见“未验证项与边界”）。回滚后清除定稿标记，释放时按 BaseVersion 解锁（与 Abort
     一致），重试也不会重复回滚。
   - **批次内实体保持隔离直到重新加载**：生成实体的 `RollbackRemoteCommit` 是 no-op，被拒绝事务的内存修改仍在实例里，下一次提交按整份 DAO
     编码（`codegen/internal/dao/template_dao.go:580-585` 的 `MarshalPersist` 忽略 mask；`remoteentity/mongo_payload.go:35-36` 以 ReplaceOne
     写整文档），会把被拒绝的修改一并 CAS 进 Mongo。框架无法证明内存等于权威，所以拒绝后一律 `quarantineEntries`（已隔离的保持，未隔离的补隔离），
     下一写者在 `batch.go:256-265` 立即得到 `ErrRemoteFenced`；实体被业务卸载、从权威重新加载后才能再写。隔离失败时不释放，交回重试路径。
   - Applied 分支仍先发布再释放；Committed 分支仍对账后释放（`acknowledgeRemoteCommit` 解除隔离）；tracker 由持久结论更新为 Rejected/Committed。
4. 不伪造提交：拒绝写入成功才回滚；撞键读回已提交才发布；两者都不成立时不收尾。

放弃的方案：直接在 finalizer 里把 Unknown 当未提交回滚（服务端可能仍有在途提交，违反“未知≠未提交”）；复用
`RejectRemoteCommitsInTransaction`（它对已有非拒绝记录返回 `ErrRemoteRejected`、插入撞键返回裸错误，语义含混，只能等下一轮回源，
故另加返回真实状态的入口）；给 Rejected 记录设置 `expires_at`（DataEngine 的拒绝记录也不过期，保持同一机制，见边界）。

## 兼容性变化

- 新增公开方法 `MongoCommitter.RejectUnresolvedRemoteCommits`、`Backend.RejectUnresolvedRemoteCommits`；持久格式不变（同一事务集合、同一文档结构）。
- Durability 0 且事务从未到达 Mongo：修前 gate/锁/写额度被永久占用，同实体下一写者在 gate 上等到超时；修后在 finalizer 下一轮
  （`FinalizeRetryInterval`，默认 500ms 起）写入 Rejected、回滚、释放，实体保持隔离，下一写者立即得到 `ErrRemoteFenced`，重新加载后可写。
  调用方拿到的仍是可 `errors.Is(ErrRemotePersistenceIndeterminate)` 的错误（不变）。原复审验收里的“实体可写”按数据安全改为“重新加载后可写”。
- **行为变化（全部持久级别的 finalizer Rejected 分支）**：修前 finalizer 第一次回源就读到 Rejected（实体此前未被隔离）时，回滚后直接释放、
  实体仍可写，生成实体会把被拒绝的修改随下一次写入写进 Mongo（`TestRejectedAsyncWriteIsNotCarriedByNextWrite` 在 `87d9499` 上即红）；
  修后该分支同样隔离实体。既有用例 `TestDurableLeaseRejectionReleasesDeferredWriteGate` 相应改为断言 gate/额度释放且下一写者立即被
  `ErrRemoteFenced` 拒绝。
- 新增指标 `remote_entity.unresolved_reject_error_total`、`remote_entity.unresolved_resolved_total{state}`（低基数）。

## 未验证项与边界

- **真实 Mongo 上的裁决时序未验证**：非事务插入与在途事务写同一 `_id` 的互斥（在途事务已插入时拒绝插入等待其结束后撞键；拒绝先插入时
  事务写冲突中止）依据 MongoDB 文档化语义，本轮只在 mongotest 上验证了顺序化结果；集成用例没有构造“服务端在途提交”。
- finalizer 回滚不是投递到 Nest 快池执行：Remote Manager 没有可在消息结束后使用的快池执行器，沿用既有 Rejected 分支在实体本地锁内
  就地回滚。若要严格“回滚归快池”，需要 Nest 为 Remote 提供独立于消息生命周期的快池执行入口，属另行设计。
- 生成实体的 `RollbackRemoteCommit` 是 no-op，内存不会回到拒绝前；本修复靠“隔离到重新加载”挡住被拒绝修改的写出，而不是恢复内存。
  实体何时被卸载重载由业务/EntityManager 生命周期决定，框架没有主动丢弃内存实例并从权威重载的入口；需要自动恢复写入时应另行设计该入口。
  隔离期间本地读取仍会看到被拒绝的内存值。
- 拒绝记录不设 `expires_at`，与 DataEngine 的拒绝记录一致，不会被 TTL 清理；只在未知结果时产生。
- 关停时（`StopFinalizer`）仍按既有逻辑隔离并释放未收尾项，不在关停期间写拒绝。
- 未做性能复测；finalizer 只在未知结果路径多一次 Mongo 插入。

## 复核更正（2026-09-26）

协调方复核指出：首版提交 `9a4ef81` 在 Rejected 收尾时把本事务造成的 Quarantined 退到 Recovering 并作废 marker，让下一写者经
`beginWrite` 复核后解冻。复核属实，这会写出被拒绝的数据：`beginWrite` 只比较版本（`batch.go:219`：`EntityVersion() != expectedVersion`
才重载），拒绝后本地版本与权威都停在 BaseVersion，不会重载；Recovering 分支（`batch.go:240-255`）直接解冻；而生成实体 rollback 是 no-op、
下一次提交按整份 DAO ReplaceOne（见上文“修复与取舍”第 3 条），被拒绝的修改随之进入 Mongo。修前 Quarantined 恰好挡住了这一点。
