# RR-20261006-04 修复：文件 outbox 打开时清理崩溃遗留的临时文件（O6）

[问题](../bug/RR-20261006-04.md)。收尾第 3 批 A6（分支 `cb3`）。已修复、声明场景验证，未发版。

## 决策

- **采用**：`NewFileOutboxStoreWithOptions` 扫描目录时（原本就在数 `.packet`）删除确认是本 outbox 生成的临时文件，有删除时目录 fsync。判别 `isFileOutboxTemporary`：`DirEntry.Type().IsRegular()`（不跟随符号链接、不碰目录），名字恰为 `outbox-` + 非空十进制数 + `.tmp`——与 `PutRecord` 用的 `os.CreateTemp(dir, "outbox-*.tmp")` 一致（Go 1.27 `os/tempfile.go` `nextRandom` 是 `uint32` 的十进制）。模式抽成常量 `fileOutboxTemporaryPattern`，`PutRecord` 与判别共用。删除失败（ErrNotExist 除外）让打开失败，与本 store 对目录异常的 fail-closed 风格一致；崩溃遗留的文件没有进程持有，Windows 上也能删除。
- **只在打开时清理，不在 `LoadRecords` 里清理**：打开是启动装载点，目录归一个 store 独占时此刻没有在途写入；`LoadRecords` 可在运行中被调用，虽有 mutex，但把清理放在一处更好推理。
- **目录独占**：`FileOutboxStore` 注释与 `docs/skill/production-readiness.md` 写明同一目录不能有两个在写的 store（另一个 store 的在途临时文件会被删掉，它的替换失败并返回错误，不会静默损坏）。
- unix（`file_replace_unix.go`）与 windows（`file_replace_windows.go`）只在替换与目录 fsync 上不同；清理在共用的 `file_outbox.go`，windows 上 `syncDirectory` 是 no-op（MoveFileEx WRITE_THROUGH 已是屏障），删除不需要额外屏障。
