## 实证（修前）

沿用 [RR-20260928-05](RR-20260928-05.md) 的演练手法，不调用 systemctl、不写任何系统目录、不连任何外部服务：

- 脚本：v1 用 RR-20260928-05 之前的 install.sh（`c5857a5` 生成器生成，`WorkingDirectory=$APP_ROOT`），v2 用基线（或修后）的 install.sh / rollback.sh；演练副本里把 `UNIT_PATH=/etc/systemd/system/...` 临时改成 `${UNIT_PATH:-...}`（**未提交**），副本里若还有未改到的 `/etc/systemd` 就中止。

- 运维状态：v1 安装前在 `$APP_ROOT/configs/data` 放好数据表（主记录说的“为绕过 RR-05 手工放过数据”的部署）；起不来的 v2 用一个直接 `exit 1` 的二进制代替。

## 根因

`codegen/internal/roost/render_deploy.go`（基线行号）：install.sh `:141` 直接覆盖 `$UNIT_PATH`，`:197-198` 切 `current` 后 `daemon-reload`；readiness 失败时 `:207` 只把 `current` 切回上一个 release 再 restart，unit 仍是新版本写的。rollback.sh `:364` / `:381` 也只切 `current`。unit 的形态随生成器变化（RR-20260928-05 把 `WorkingDirectory` 从 `$APP_ROOT` 改成 `$APP_ROOT/current`），只切 `current` 等于让旧 release 在一份不是为它写的 unit 下运行。

## 决策：unit 随 release 一起回退（不采用“补齐 configs/data”或“切换前拒绝”）

每个 release 的 unit 记在 `$APP_ROOT/units/<version>.service`；install.sh 与 rollback.sh 共用两个函数（`renderShellUnitRecord`）：

- `record_unit <当前 release>`：覆盖 unit 之前，当前 release 还没有记录时，把 `$UNIT_PATH` 现在的内容记给它。这是本版之前安装的 release 唯一能得到记录的时机（第一次用新 install.sh 升级、或第一次用新 rollback.sh 回退时）。
- `use_unit <release>`：把该 release 的记录装到 `$UNIT_PATH` 并 `daemon-reload`；没有记录时保留现有 unit 并打印 `no unit recorded for release <v>; keeping <unit>`（即修前行为）。
- install.sh：`record_unit "$PREVIOUS"` → 新 unit 写进 `units/$VERSION.service` → 切 `current` → `use_unit "$RELEASE_ROOT"` → restart；失败时切回 `$PREVIOUS` 并 `use_unit "$PREVIOUS" || true` 再 restart。首次安装失败仍是停服。
- rollback.sh：`record_unit "$PREVIOUS"` → 切到目标 → `use_unit "$TARGET"` → restart；目标 readiness 失败时切回并 `use_unit "$PREVIOUS" || true`。

理由：

- **回滚的语义是回到安装前的状态**。install.sh 改了两样东西——unit 与 `current`——回滚只退一样，就不是原状态。unit 里除了 `WorkingDirectory`，还有按该版本 Mod 算出的 `TimeoutStopSec`（`shutdown.total_timeout` + 5s）、运行用户等，它们本来就属于生成这个 release 的那一版生成器；与 RR-20260928-05 “数据与二进制同版本、随 release 回退”是同一个道理。
- **不补齐 `configs/data`**：旧 release 按约定不可变；从新 release 拷数据会让旧二进制读新版本的表（RR-20260927-34 / RR-05 排除过的情形）；运维放在 `$APP_ROOT/configs/data` 的那份，恢复旧 unit（`WorkingDirectory=$APP_ROOT`）后自然就被读到，不需要再拷。
- **不在切换前拒绝**：拒绝的是所有从旧 release 出发的升级，包括会成功的那些；主记录建议的变通（用新 install.sh 以新版本名重装当前版本）本身也是一次“上一个 release 没有 configs/data”的升级，同样会被拒绝，只能再加一个逃生开关。回退 unit 则让这类升级照常进行，失败时回到原状。
- **记录放在 `$APP_ROOT/units/`，不放进 release**：新 release 可以带自己的 unit，但本版之前的 release 只能在外面补记录，而旧 release 不可写；一个位置统一处理两种情况。文件 root 所有、0644，服务在 `ProtectSystem=strict` 下只读。

没有做：本版之前安装、而且在第一次新脚本升级 / 回退时不是 `current` 的更早 release 拿不到 unit 记录（当时正在用的 unit 只记给当时的 `current`，不猜测更早版本用的是什么），回退到它们时沿用当前 unit 并打印提示，与修前相同。已经在基线脚本下失败过一次自动回滚的部署，`$UNIT_PATH` 已是新 unit，之后记录的也是新 unit，需要按 RR-20260928-05 修复记录里的手工步骤恢复。

## 文件与行为

- `codegen/internal/roost/render_deploy.go`：`renderShellUnitRecord`（`record_unit` / `use_unit`）接进 `renderShellInstall` 与 `renderShellRollback`；install.sh 的 unit 写到 `$APP_ROOT/units/$VERSION.service` 再经 `use_unit` 安装，`PREVIOUS` 在写 unit 之前求出；rollback.sh 新增 `UNIT_PATH`；生成的 `deploy/shell/README.md` 说明 unit 记录与回退。
- `codegen/internal/roost/shell_rollback_unit_promises_test.go`：`TestShellRollbackRunsThePreviousReleaseUnderItsOwnUnit`，真的执行生成的 install.sh / rollback.sh（configdata 工程），PATH 替身同上（`systemctl` 装载 / 按装载的 unit 起一个按工作目录找 `configs/data/_manifest.json` 的假二进制，`healthcheck.sh` 看它的就绪文件）。起点是 RR-05 之前的布局（v1 只有二进制与配置、`WorkingDirectory=$APP_ROOT`、运维数据在 `$APP_ROOT/configs/data`）；断言：起不来的 v2 自动回滚后 v1 在 `$APP_ROOT` 下就绪且没有 “rollback also failed readiness”；v3 正常安装在 `releases/v3` 下就绪；`rollback.sh v1` 回到 `$APP_ROOT`、`rollback.sh v3` 回到 `releases/v3`。副本里 `UNIT_PATH` 改到临时目录，改不到（仍含 `/etc/systemd`）就 `Fatal`；Windows 或缺 `sh` / `sha256sum` / `install` / `readlink` 时跳过。
- 使用说明：`docs/DEPLOYMENT.md` §4、`codegen/docs/PROJECT_GENERATOR.zh-CN.md` 部署入口表；[RR-20260928-05 修复记录](RR-20260928-05.md)兼容性一节追加后续说明。

## 兼容性

- install.sh / rollback.sh 是 codegen 受控文件，`roost project sync` 即更新（基线生成器建的 game-demo 工程 sync 后只更新 `deploy/shell/{install.sh,rollback.sh,README.md}` 三个文件，与新生成工程逐字相同）。service 配置不变。
- 新增目录 `$APP_ROOT/units/`；`/etc/systemd/system/<instance>.service` 仍是 systemd 读取的位置，内容由 `use_unit` 从记录装入。手工改过 `$UNIT_PATH` 的部署：下一次安装 / 回退会用记录覆盖它（修前 install.sh 本来就每次重写 unit），手工改动应放进 drop-in（`<instance>.service.d/`），drop-in 不受影响。
- 第一次用新脚本升级 RR-05 之前安装的实例时，旧 unit 被记给当时的 `current`；升级失败或之后 `rollback.sh` 回到它，都回到旧 unit，行为与升级前相同（包括运维放在 `$APP_ROOT/configs/data` 的数据表；没放过的，旧 release 修前本来就起不来）。

## 未验证项 / 风险

- 没有真 systemd：`daemon-reload` 的装载语义、`WorkingDirectory` 跟随链接由替身近似；`install -o/-g` 属主、GNU `mv -T` 由替身代替；未在 Linux 上跑（macOS 演练，生成器回归在 Linux CI 上会用原生 GNU 工具）。
- 没有用 game-demo 的 game 服务做这次演练（它到 readiness 需要其余 9 个服务与 Mongo / NATS / Redis）；unit 记录与回退逻辑与服务无关，game-demo 生成的两个脚本与最小工程的这部分逐字相同。
