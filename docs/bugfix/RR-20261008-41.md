# RR-20261008-41 修复记录

问题：[Remote 缓存验收依赖 1ns 真实时钟必然前进，误判合法 L1 命中](../bug/RR-20261008-41.md)。基线d30c3f02；仅修复测试夹具与验收条件，不改生产代码，不移动v1.23.1。

## 根因与处置

正式 SnapshotClient 在 testing/synctest 中验证期限内、期限边界及期限之后的 v1/v2；并发 v1～v60 用已有 b2Clock 显式跨过最后确认时间再验证收敛。

修前仅将原正式SnapshotClient用例放入synctest冻结时间，没有修改读写路径或原断言，确定复现v2后读v1。修后明确断言期限内和等于期限时仍是v1，超过1ns后必须是v2。并发用例仍要求L2及两个节点全部为v60；未删写者、读者、删除@30或乱序路径，没有提高超时/容量。

## 方向判断

这次并非生产逻辑重复失效，而是验收方混淆了业务陈旧上限与墙钟精度；延续已有B2可控时钟设计，用当前Go的synctest覆盖正式装配，不给生产新增测试专用入口。

## 红绿和限制

修前原文见问题记录。目标场景macOS `go test -race ./remoteentity ./sync/lockstep -run <3个相关用例> -count=30`通过；相邻4包race三轮通过。完整macOS/Linux结果统一回填[本轮收口](../review/FOLLOWUP-MAC-LINUX-2026-10-08.md)。这不把一次旧日志的所有潜在根因都推定为相同原因；当前声明契约须在明确时间/停机边界下通过，不靠平台性能偶然性。
