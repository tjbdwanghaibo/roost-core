# RR-20261006-34 修复：停止循环跳过同一轮里被待停止上限删掉的记录

问题：[RR-20261006-34](../bug/RR-20261006-34.md)。基线 `443d08f6`，分支 `skpart`，与衍生物分区存放（[方案](../feature/REFACTOR-2026-10-07-skill-spawn-partition.md)）同一提交，未发版。

## 根因

`Shutdown` / `RemoveProgram` 的循环先取 ID 列表、再逐个取回记录，但循环体里的停止请求会经待停止上限删掉列表里后面的记录；取回后没有判空。

## 修法

两处循环按 ID 取回（分区后为 `runtime.spawns.get(id)`）后判空，为空就跳过：上限删除时 Runtime 已计数、写 Error 日志，声明不再负责停它（`MaxStopPendingSpawns` 的既有契约），与 `retrySpawnStopsLocked` 的处理一致。

| 方案 | 结论 |
| --- | --- |
| ① 取回后判空、跳过（采用） | 与上限删除的既有语义一致：被删的记录 Runtime 不再负责 |
| ② 同一轮停止里暂停上限删除，结束后再收缩 | 未采用：上限是内存约束，`Shutdown` 一轮可能新增任意多条待停止记录；多一个“暂停”状态，重试路径也要同样处理 |
| ③ 把被删的记录也再停一次 | 未采用：它已经不在表里，再停的结果没有地方记；宿主正拒绝停止，这一次大概率同样失败 |

## 文件与行为

- `skill/spawn_owned.go`：`RemoveProgram`、`Shutdown` 的循环取回后 `if spawn == nil { continue }`。
- `skill/runtime_spawn_stop_sweep_promises_test.go`：`Shutdown` / `RemoveProgram` 两个子用例，只用公开 API；断言入口返回宿主的错误、前一个衍生物进待停止、后一个已被上限删掉、之后 8 个 tick 内重试把前一个停掉（`cancelled`）。
- 行为：之前 panic 的场景现在照常返回宿主的错误；其余不变。

无格式、API 变化。

## 后续：结构性修复（维护者第十三轮“待停止上限”选 B，2026-10-07）

上限不再删记录：最早的待停止记录挪进第五个分区“已放弃”（status `abandoned`），删记录只剩三个登记点（Advance 末尾清理已放弃分区、随 cast 回收已停止的记录、启动失败且已停的记录），源码守卫核对。`Shutdown` / `RemoveProgram` 循环取回的是那条已放弃的记录，停止请求是空操作；修后去掉两处判空（变异，未提交）相关用例仍全部通过。本记录加的判空保留作双重保险。本用例只把“后一个被删掉”的断言改成“后一个已放弃”。详见[分区方案 §11](../feature/REFACTOR-2026-10-07-skill-spawn-partition.md#11-待停止上限改为已放弃分区维护者第十三轮待停止上限选-b2026-10-07)。
