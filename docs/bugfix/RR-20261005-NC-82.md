# NC-82 修复：RateLimiter 每主体 key 上限，满表陌生 key O(1) 拒绝

[问题](../bug/RR-20261005-NC-82.md) · [证据](evidence/noncore-bugfix-20261005-n02/README.md)。已修复、声明场景验证，未发版。维护者 2026-10-05 指示按“每主体上限 + 满表扫描限流”修复（N02 合并前复核）。

## 决策与实现

`security/ratelimit.go`：

1. **每主体上限**：`RateLimitConfig.MaxKeysPerOwner`，`<=0` 取 `DefaultMaxKeysPerOwner = 256`，超过 `MaxKeys` 时按 `MaxKeys` 计。`RateLimiter` 增加 `owners map[int64]int`，新 key 建立时 +1、闲置清扫删除时 -1（归零删除条目），与 key 表在同一把锁下同步。新 key 先过主体上限再过共享表上限：主体超限只拒绝它**尚未建立**的新 key（计 `OwnerCapacityRejected`），它已有的 key 照常限速，其他主体不受影响。
2. **满表拒绝 O(1)**：删除“表满时在全局锁内再做一次完整 idle 扫描”的紧急路径。满表时陌生 key 直接拒绝（计 `CapacityRejected`）；闲置 key 只由已有的周期清扫回收，周期清扫本来就是每 `SweepInterval` 至多一次。“紧急扫描限频到每 SweepInterval 一次”与周期清扫共用同一节流后两者等价，所以直接删掉，代码更短。
3. `RateLimitStats` 增加 `MaxKeysPerOwner`、`OwnerCapacityRejected`；`gateway.RateLimit` 注释写明 MessageID 由客户端决定、与“拒绝未注册 MessageID”中间件的组合方式。

### 默认值 256 的依据

- `gateway.RateLimit` 的 key 是 `{PlayerID, MessageID}`，合法玩家在 IdleTTL 内的 key 数不超过它用到的请求协议数。game-demo 模板 `demo/protocol/def` 共 29 个请求 MessageID（10000～10024、10100～10103）；协议生成器只要求 ID 唯一（`codegen/internal/protocol/parse.go:400`），不限范围，协议号本身给不出上界。256 约为 demo 的 9 倍，给大型游戏留足协议余量，合法流量不会碰到。
- 默认表 `MaxKeys = 100000`：单主体最多占 0.256%，要占满默认表需要至少 ⌈100000/256⌉ = 391 个同时活跃、各自用满上限的已认证主体——这已是容量本身不足（看 `CapacityRejected` 调大 `MaxKeys`），不再是单点滥用。
- 选 2 的幂只是便于记忆；没有更细的业务数据，接入方协议数超过 256 时显式调大。

### “限流前先校验 MessageID 已注册”的评估

| 方案 | 正确性 | 契约 | 改动面 | 调用方 |
| --- | --- | --- | --- | --- |
| A 每主体上限（采用） | 限流器自己保证“一个主体耗不尽共享表”，与 key 来源无关；`security.RateLimiter` 直接使用（Action 非 MessageID）同样受保护 | 只收紧新 key 准入，已有 key 行为不变 | `ratelimit.go` 一处，无新依赖 | 无需改；协议多于 256 的游戏调大 |
| B 限流前拒绝未注册 MessageID | 合法 key 数被注册协议数天然限定，更贴近根因；但只保护经过注册表的那一条链，且依赖每个组装方都放对顺序 | `gateway` 是传输中立库，没有协议注册表（注册表在生成工程 `render_access.go`），要么新增回调 API，要么由应用自己在 Chain 里放校验中间件 | 新 API + 无使用方 | 每个组装方都要接 |
| A+B | 互补：B 让合法 key 数 = 协议数，A 兜住 B 漏接或非 MessageID 的用法 | — | — | — |

结论：A 是限流器层面的必要修复，必须在库内做；B 更贴近“为什么会有海量 key”的根因，但属于应用组装（生成 access 的 `ProtocolRegistry.Dispatch` 已对未知 MessageID 拒绝，且生成 access 不用 `gateway.RateLimit`，O6），仓内没有使用方，不新增 API，只在 `gateway.RateLimit` 注释里写明组合方式。

## 行为变化（兼容性）

- 单主体新 key 超过 256（或配置值）时被拒绝：此前只要共享表有空位就接受。`AllowN` 返回 false、`gateway.RateLimit` 返回 `ErrRateLimited`，与其他限流拒绝同一错误；用 `Stats().OwnerCapacityRejected` 区分。
- 满表时刚闲置的 key 最多晚一个 `SweepInterval`（默认 1 分钟，Normalize 保证 ≤ IdleTTL）才腾出名额：此前满表会立即扫描回收。要更快回收就调小 `SweepInterval`（代价是每个间隔一次 O(Keys) 扫描）。
- `RateLimitConfig`/`RateLimitStats` 只新增字段，零值即默认，已有字面量不需要改。仓内没有装配方（O6），没有需要迁移的调用方。
