# NC-51 修复：sweep 对已确认 Keys 执行与 Opening 相同的键合法 / 归属边界

[问题](../bug/RR-20261005-NC-51.md) · [证据](evidence/noncore-bugfix-20261005-revn06/README.md)。已修复、声明场景验证，未发版。

## 决策与实现

`kit/service/global/activity/service.go` 抽出 `windowKeyProblem(key, groupID)`（`Key.Validate` + `GroupID == groupID`），Opening 循环与 `openingIntentProblem` 改用它（行为不变），已确认 Keys 循环在任何 `Activities` 读写之前调用它：坏条目跳过、**保留**在 Keys（不剪、不移入 Delivering、不读不写别的组的活动），每 tick 计 `sweep.window_key_malformed`，日志与 Opening 一样只在出现 / 消失时各写一次（`malformedConfirmed` 按所属窗口分组，与 `malformedOpening` 分开，同一个键可能同时在两处）。

没有自动清理坏条目：本包从不写出它们，删除依据（“记录不在了”）对一个不该在这里的键不成立，与 RR-20261001-09 残余对 Opening 的决定一致。键约束自 v1.1（`cab72dfc`）起不变，不存在合法的旧格式键会被新校验挡住。已经混进 Delivering 的跨组键不处理（需运维）；`RetireDelivered` 对“不在该窗口”也返回 true 只记观察。

## 验证与边界

`confirmed_key_ownership_promises_test.go`：跨组确认键——修前 group-a 的 sweep 结算了 group-b 的活动，修后只结算本组、group-b 活动仍 collecting、无派发、不进 group-a Delivering、条目保留、计数 1，group-b 自己的 sweep 随后恰好结算一次；非法确认键——修前被剪掉，修后两 tick 均保留、计数 1→2，本组活动照常完成。`./kit/service/global/activity` `-race -count=3` 与既有 RR-09 / NC-42 回归全绿。真实 Redis / Cluster 未跑（纯窗口逻辑）。
