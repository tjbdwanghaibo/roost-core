# RR-20260930-09 · Tablegen JSON 退役与所有权

来源：[第三轮问题](../bug/REVIEW-2026-09-30-codegen-03.md#rr-20260930-09--tablegen-元数据清空后旧-json-留存)。修前最后一个 meta 删除后旧 JSON 留存。基线 Core `da56c998`。

`tablegen` 把 `_manifest.json` 升至 v2，`tables` 记录自身输出文件名和 SHA-256。每轮先解析所有当前 CSV，再对旧清单中的孤儿核对哈希；未改动才删除，手写且未登记的 JSON 保留，已改动的旧输出报错要求人工处理。JSON 文件名限制在输出目录直接子文件，避免退役清单越界。无 meta 时仍执行数据对账；`roost` 在 CSV 目录为空但 manifest 存在时不再跳过 config-data。新项目脚手架直接写 v2 空 manifest。

旧 v1 manifest 没有文件归属记录：若目录有当前 meta 未认领的 JSON，本轮明确失败并要求人工确认，不能自动判断是旧生成物还是手工数据。此前 v1 工程需先在 meta 尚齐全时运行一次生成以升级 manifest；已删 meta 的遗留 JSON 要由维护者核对并清理，再重新生成。此为兼容/恢复边界，未自动迁移生产数据。

正式 `TestConvertCSVToJSONRetiresOwnedDataAndPreservesManualData`、`TestConvertCSVToJSONRefusesEditedOrLegacyUnownedRetirement`、`TestStagedProjectCommitAndCheckSeeTableJSONRetirement` 与定向 race 通过。隔离外部工程实测：生成 `monster.json` → 删最后 schema/CSV → `roost generate --check` 报 `configs/data/monster.json` 漂移 → `roost generate` 删除 → `--check` 通过，`go test ./...` 通过。未发版；旧策划表/线上数据的业务迁移另行决定。
