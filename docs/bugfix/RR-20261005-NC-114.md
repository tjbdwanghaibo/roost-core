# NC-114 / NC-115 修复：skillsync 三条下发路径共用同一可见性规则

[NC-114 问题](../bug/RR-20261005-NC-114.md) · [NC-115 问题](../bug/RR-20261005-NC-115.md) · [本轮](../review/REVIEW-2026-10-05-n09-batch2.md)。已修复、声明场景验证，未发版。

## 根因

可见性在快照（`FilterStateSnapshot`）、增量（`FilterStateMutation` / `FilterPresentation`）、presentation reset 三处各写一套：reset 完全没有过滤（`coordinator.go:320-334, 454-455`）；ability 快照按空 handle、增量按具体 handle 问 `FieldVisible`（`visibility.go:122-136` 与 `:351-352`）；cast / process remove 不带归属实体（`runtime_mutation.go:475, 587`），persistent remove 不看 `Binding`，过滤器推出实体 0 后放行。

## 决策

- **reset 复用 `FilterPresentation`**：`Coordinator.presentationReset` 是 reset 的唯一构造点，游标过期的 Flush 与 Recover 都调用它；每条 `ActivePresentation` 还原成 Runtime 为它发出的增量事件形状（`activePresentationEvent`：Source = 施法者 / owner，PrimaryTarget = Anchor.Target，process 记为 `process_update`），交给 observer 的策略；不可见整条去掉（计 `Filtered`），可见的取回过滤后的 Anchor；策略报错 fail-closed（计 `VisibilityFailures`）。未采用“在 `VisibilityPolicy` 接口上加 `FilterPresentationReset`”：会破坏所有自定义策略的编译，而且同一条规则又要写第二遍。
- **ability 快照按 handle**：快照逐个 ability 问 `FieldVisible(observer, abilities, <handle>)`，与增量共用 `abilityHandleReference`。
- **remove 带实体**：`diffCastStates` 的 cast remove 带 `Caster`，`diffProcessStates` 的 process remove 带 `Owner`（增量写点路径与全量 diff 共用这两个函数，`stateMutationVerifyIncremental` 影子校验覆盖）；persistent remove 按自身 `Binding` 判断，与 upsert / 快照一样要求 owner 与 subject 都可见。

## 文件与行为

- `skill/skillsync/coordinator.go`：`presentationReset`、`activePresentationEvent`；两处 reset 改走它。
- `skill/skillsync/visibility.go`：ability 快照按 handle；persistent remove 按 Binding；`abilityHandleReference`。
- `skill/runtime_mutation.go`：cast / process remove 带归属实体。

## 兼容性

- wire：`StateMutation` 的 cast / process remove 多出 `caster` / `owner` 字段（已有 `omitempty` 字段，只追加）；`ApplyStateMutation` 不读它们，旧客户端不受影响。Applier 的 `decodeStrict` 认识这两个字段（同一结构体），新旧版本互通。
- 行为收紧：observer 的可见性在 upsert 与 remove 之间变化时，remove 按 remove 当时的可见性判断；“先可见后不可见”的实体，其 remove 不再下发，客户端保留旧条目直到下一份 full（[本轮 O12](../review/REVIEW-2026-10-05-n09-batch2.md)）。按 handle 写 `FieldVisible` 的策略，快照里不再出现被隐藏的 ability。
- presentation reset 可能因策略报错而失败（之前不调用策略、不会失败），与 state 快照的 fail-closed 一致。

## 未验证 / 风险

- reset 的 process 条目只经 `EntityVisibilityPolicy` 的源码推导与通用断言（Anchor 坐标为 nil）覆盖，本批 fixture 只有 cast 视觉；没有接 kit syncstream / NATS 端到端。
- 自定义 `VisibilityPolicy` 若依赖 `PresentationEvent.Sequence` 等字段区分事件，reset 里的还原事件取 `LatestPresentationSequence`，与真实增量序号不同。

## 补测（2026-10-06，分支 `sktest2`）

上面“未验证 / 风险”第一条（reset 的 process 条目只经推导覆盖）补了专门用例 `TestPresentationResetProcessEntryMatchesItsIncrementalEvent`（`skill/skillsync/presentation_reset_process_promises_test.go`）：带 area 视觉的召唤进程，分“仍归施法”与“已移交”两种，比对 reset 交给 `FilterPresentation` 的事件与 Runtime 增量逐字段一致，并在四种策略下比对 reset 与过滤后增量的去留和 Anchor。

结果：“已移交”一次通过；“仍归施法”**红**——reset 把 lifecycle 实体当 `PrimaryTarget`，增量里是施法目标，按 `PrimaryTarget` 判定的策略在 reset 里放出了增量里挡住的表现。登记并修复为 [RR-20261006-22](RR-20261006-22.md)。默认 `EntityVisibilityPolicy` 的结论修前修后一致。
