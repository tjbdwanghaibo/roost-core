# RR-20260915-07:忽略 WAL 半条尾记录后续写污染日志

**仓库 / 位置**:roost-core `syncstream/file_journal.go`,`Load` / `replayWAL` / `flushBatch`。
**修复单元**:U-0211(C5)。**定位文档**:TROUBLESHOOTING T-105。

## 问题

WAL 末尾有一条未换行的半条 JSON(中断写入)。`replayWAL` 正确地忽略它并成功恢复;但字节还在磁盘上,`flushBatch`
用 `O_APPEND` 续写——半条 + 新完整记录同处一行,下一次启动 `decode WAL: invalid character '{' after object key:value pair`,
整个 History 起不来。

## 根因

"忽略未提交的尾部"只做了读的一半,没有把文件恢复到最后一条完整记录的边界(C5:半尾被静默跳过,后续写当它不存在)。

## 方案选择

- **恢复后立即 Checkpoint 到新 generation。** 审查的对照证明可行,但每次带半尾的恢复都多一次 checkpoint,
  且在第一次 Append 之前不做的话窗口仍在。
- **记住最后完整记录的偏移,首次续写前截断(采用)。** `replayWAL` 返回 valid 字节数;`Load` 若 `valid < size` 则记
  `truncateTo`;`flushBatch` 首次打开 WAL 句柄时 `Truncate(truncateTo)` + fsync,再追加。journal 独占该文件,截断安全;
  `Truncate` 作用于 fd,不受 O_APPEND 影响。完整行的非法 JSON 仍然拒绝——只有"读到 EOF 仍无换行"才算半尾。
  Checkpoint 成功后 `truncateTo` 归 -1(新 generation)。

## 改动

`file_journal.go`:`truncateTo` 字段;`replayWAL` / `loadGeneration` 返回 valid 长度;`Load` 两条路径记录;`flushBatch` 截断。

## 证明

`syncstream/wal_tail_truncate_promises_test.go`:clean / partial_tail / partial_then_checkpoint 三种恢复后追加再恢复,
序号 2 都能读回;完整一行的 `{not json}` 仍拒绝加载。
修前红:`acknowledged sequence 2 cannot recover: syncstream: decode WAL: invalid character '{' after object key:value pair`。

## 未做 / 边界

- 真实临时文件,没有内核断电 / 磁盘控制器行为。
