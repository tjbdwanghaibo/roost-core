# RR-20260930-16 修复：`appendModConfigSections` 按文件原有行尾追加 Mod 段

问题：[RR-20260930-16](../bug/RR-20260930-16.md)（REMAINING §3 N23，维护者 2026-09-30 拍板）。日期 2026-09-30。基线 main `4784ef82`，worktree `.claude/worktrees/agent-af9baa8dcead1162b`，分支 `worktree-agent-af9baa8dcead1162b`。
状态：**已修复**（本地提交，未推送 / 未发版）。codebase-memory 图谱 ready，但索引的是主检出路径，本轮以当前源码与实跑为准。

## 根因

见问题记录。要点：`codegen/internal/roost/render.go` `appendModConfigSections` 对 `configs/service/config.<svc>.yaml` 与 `config.<svc>.prod.example.yaml` 直接把目录里的 LF 段追加到 `string(raw)` 后写回，CRLF 文件从此两种行尾混用；Secret 示例在 RR-20260928-13 已按原行尾写回，这两份文件没跟上。

## 决策

- 读文件后先 `lfText(raw)` 规范成 LF 并记住是否 CRLF，`appendMissingConfigBlocks` 照旧在 LF 文本上定位与追加，写回时 `restoreLineEndings(body, crlf)`。这正是同一函数里 Secret 示例与 `refreshGeneratedShutdownConfigs`、`ensurePlayerTCPConfig` 的做法，行为口径一致：含 `\r\n` 的文件写回后统一为 CRLF（本来混用的文件也被统一，与 RR-20260928-13 相同），LF 文件与空文件保持 LF。
- 没有采用“把目录里的段按文件行尾转换后再追加”：那要给 `appendMissingConfigBlocks` 加行尾参数，而它的定位（`strings.HasPrefix(body, key+":")` / `"\n"+key+":"`）本来就假定 LF 文本，规范化一次更简单也更不容易漏。

## 文件与行为

- `codegen/internal/roost/render.go` `appendModConfigSections`：见上，注释写明编号与原因。
- `codegen/internal/roost/config_section_line_endings_promises_test.go`：`TestAddedConfigSectionsFollowTheFilesLineEndings`，三个子用例——CRLF 工程 `add mod redis` 后两份文件都有 `\r\nredis:\r\n` 且整份文件没有裸 LF 行（`bareLineFeed`）；LF 工程不出现 `\r`；开发配置清空后追加的段仍是 LF。

## 兼容性

只影响 `roost add mod` / `add saga` 对 CRLF 工程的写回。LF 工程逐字节不变（既有 `TestAddedConfigSectionsReachTheKubernetesSecretExample`、`TestCRLFKubernetesSecretExampleGetsTheSameEditsAsLF` 照常通过）。不改生成文件形状，不需要重生成 fixture。
