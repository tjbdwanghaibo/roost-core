## 根因（基线行号，`demo/internal/service/game/playerowner.go.tmpl`）

- `:606` 归还在选中的锁里置 `handingBack = true`；`:626` 撤离、`:636` 等投影之后，`:641` **无条件** `owners.Release(ctx, playerID)`。
- `:874` `Claim` 不看 `handingBack`，只用 `Admit` 判断连续性；`:875` `store.Claim` 在 Redis 里还是本进程的 → `mine=true`；`:906` `confirmClaim` → `:692` `confirmLocked` 把 **`handingBack` 清成 false**。
- 结果：竞争者擦掉了归还的标记，归还不回头看就释放——`Claim` 回答“是你的”，共享表无主。两种交错见问题记录。

## 决策

**采用：归还与认领在同一玩家上互斥（复审推荐的修法 A，加一个登记计数）。**

- `Claim` 开头 `enterClaim`：锁内若该玩家 `handingBack`，取 `handBackDone`、解锁、等它（或调用方 ctx）；否则在同一临界区 `claiming[playerID]++`，`Claim` 返回前 `leaveClaim`。
- 归还选人时（同一把锁）跳过 `claiming > 0` 的玩家，置 `handingBack` 并新建 `handBackDone`。于是对每个玩家：要么 `Claim` 看见归还并等，要么归还看见 `Claim` 并跳过。
- `handingBack` 只由新的 `finishHandBack` 清除（取代 `cancelHandBack`），`confirmLocked` 不再碰它——标记属于设它的那次归还。
- 归还在 `store.Release` 前锁内复核 `local[playerID]` 仍是本轮标记的那个状态且仍在归还（防御第二道：别的路径——例如公开的 `Release`——若已结束这把租约，就不再释放）；
  通过后**状态保持标记**直到 `store.Release` 返回，才删本地状态、close `handBackDone`。这样“本地已删、Redis 未删”的间隙里到来的 `Claim` 也会等，而不会读到即将被删的认领。
- 等过归还的 `Claim` 一律 `continuous = false`：归还开始撤离了，撤离可能超时后仍在后台跑；加入它（已结束则是一次空调用）再确认，登录不会落到正在被销毁的副本上。

**为什么不只是“Release 前复核”**：复审已验证不够——复核与 `store.Release` 之间仍可插入 `store.Claim`（Release 先于确认那种交错）。
**为什么用登记计数而不是让 `Claim` 只碰一下 `lastUsed`**：碰 `lastUsed` 只让归还在 `HandBackIdle`（20s）内不选它，`Claim` 若慢于此（撤离等待 + Redis）仍会重叠；
还有一条后台 `Owns` → `Claim`（本地状态在、Redis 键已过期、`Admit` 拒绝所以不碰 `lastUsed`）与刷新循环的归还并发的交错，计数把它也关掉了。
**未采用**：
- CARRYOVER A7（`Admit` 配对 `Done` 的在途计数，归还不再用 `lastUsed` 近似）——更彻底，但是写路径契约变更，留在 feature 线；
- CARRYOVER A6 / OPEN-ITEMS C24（跨进程移交协议）——同上；
- 登录到来时**打断**归还（取消其 ctx、立即放弃）：登录更快，但撤离不可取消（A8），被打断的归还照样留下一个在后台销毁的副本，`Claim` 还是要加入它；收益只是少等一段，换来归还逻辑多一个取消源。登录等待已受 `login_timeout` 约束，超时后客户端重试即可。

## 锁与等待顺序

- `owners.mu` 从不在等待时持有：等 `handBackDone`、等撤离、等投影、Redis 往返都在锁外。
- 归还从不等待 `Claim`；`Claim` 只等归还 → 等待图无环。
- 归还跑在刷新循环 goroutine 上，并在 `handBackIdle` 返回前结束它标记的每一个玩家（未处理的由 defer 一律 `finishHandBack(…, false)`）；同一 goroutine 上 `renew` 的重取 `Claim`
  因此永远看不到进行中的归还，不会自己等自己。
- 等待上界：选中该玩家的那一轮归还结束（本提交时是整轮；RR-20260921-04 之后是 `handBackPassBudget` 加该轮的释放往返）或调用方 ctx 结束，先到为准。
- 快池：`Claim` 的调用方是登录（连接读循环 goroutine，RR-20260926-36 记录）、后台 `Owns`（saga 步骤消费的 `Admit` 谓词，JetStream 回调 goroutine，`saga/command_consumer.go:274/353`）
  与刷新循环本身；都不在 Nest 快 worker 上，且原本就有 Redis 往返与撤离等待。`Owns` 只在 Redis 不再答本进程时才走到 `Claim`，归还期间那只剩最后一次释放往返。未新增快池等待入口。
