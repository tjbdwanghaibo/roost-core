# RR-20260928-02 修复：Guard 的撤销记录以（EntityManager, ID）为键

问题：[RR-20260928-02](../bug/RR-20260928-02.md)（OPEN-ITEMS B43）。日期 2026-09-28；基线 `9568140`；worktree 分支 `fix-r9-b15`（叠在 RR-20260928-01 之后）。
codebase-memory 图谱停在 09-26，已过期，未使用；以源码为准。

## 根因

- `entity/manager_factory.go:94`（基线）RR-21 分支 `guard.revokedInThisGuard(value.ID())` 只按 ID 查；
- `entity/entity_guard.go:90` `revokedCreated []int64`、`:521` `slices.Contains(e.revokedCreated, id)`；`manager_factory.go:165` 登记时只记 `id`。
- 而 `removing` 是每个 `EntityManager` 自己的（`m.removing[id]`）。同一 handler 在 Manager A 上撤销 X 后，在 Manager B 上撞上 B 自己的 `removing[X]`
  （别的持有者 Destroy 收尾中）时，按 ID 命中 A 的撤销记录，误走 RR-21 的“本 handler 自己撤销、确定失败”分支（`ErrEntityRemoved`），
  而不是 RR-81 的暂时冲突（`ErrCreatedEntityLockConflict`）。

## 决策

- 按修复约束：`revokedCreated` 改为 `[]revokedEntity{manager *EntityManager, id int64}`，`revokeCreated` 登记 `(m, id)`，`CreateInScope` 以 `(m, value.ID())`
  查。RR-21 分支只在撤销发生在同一个 Manager 时命中；其余情形原样落到 RR-81。
- 仍是线性 `slices.Contains`：一个 handler 内的撤销数很小，与原实现相同；结构体两字段可比较，直接用 `==` 语义。
- 未采用：按 `value.Base().owningManager()` 判断——新实例在 `TryAdd` 失败时尚未归属任何 Manager，调用方 `m` 才是撞上 `removing` 的那个。

### Guard `eMap` 按 ID 记的既有模糊地带（不扩大，未改）

`EntityGuard.eMap` 以 ID（`GUId`）为键记当前持有的实例（`holding`，`entity/entity_guard.go:320`）。同一 Guard 先持有 A 上的 X、再给 B 上同 ID 的 X 取锁时，
两者锁不同（各自 Manager 的 LockManager），按 RR-20260926-67 的机制被当作“同 ID 换了实例”：B 的 X 进 `eMap`，A 的 X 连同它的锁转入 `superseded`，
Guard 释放时一并解锁。锁序判断（`maxLockedGroup` / `mayLockEntity`）同样按 `eMap` 里的条目。这一处本批**没有改**：本修复只改撤销记录的键，
不读也不写 `eMap`，所以既有模糊地带既未扩大也未收窄；跨 Manager 同 ID 在一个 handler 里共存的锁账本语义如需收紧，另行登记。

## 文件与行为

- `entity/entity_guard.go`：`revokedCreated []revokedEntity`、`type revokedEntity`、`revokedInThisGuard(manager, id)`，注释写明键与原因。
- `entity/manager_factory.go`：`revokeCreated` 登记 `revokedEntity{manager: m, id: id}`；`CreateInScope` 以 `(m, value.ID())` 查，RR-21 注释补“同一个 Manager”。
- 回归：`nest/created_entity_self_revoke_promises_test.go` `TestCreateInOtherManagerAfterSameIDRevokeKeepsRemovalWindowConflict`（由探针 `probes-r15/zz_b43_probe_test.go`
  改写）：Manager B 上 X 在别的持有者 Destroy 收尾窗口里（`openDestroyWindow`），handler 在 A 上新建 X 后被嵌套独立事务回滚撤销，再在 B 上新建 X；
  对照组不在 A 上撤销。两组都要求 `ErrCreatedEntityLockConflict`、不带 `ErrEntityRemoved`、文案不含“revoked earlier in this handler”。

## 兼容性

未导出结构变化，无 API 变化。同一 Manager 上的 RR-21 行为不变；只有“撤销在别的 Manager 上”的情形从 `ErrEntityRemoved` 变回 RR-81 的冲突（可回滚事务会整条回滚重排，
不能回滚的 handler 不重排，与 RR-81 一致）。
