# RR-20260915-06:流清理后重建复用旧 ACK 身份

**仓库 / 位置**:roost-core `syncstream/syncstream.go`(`appendLocked` / `Import` / 快照),`lifecycle_journal.go`(`RotateEpoch`),
`file_journal.go`(`replayHistoryMutation`)。
**修复单元**:U-0215(C8)。**定位文档**:TROUBLESHOOTING T-109。

## 问题

同 observer/stream 在 epoch 7 发布 sequence 1;DeleteStream / DeleteObserver / SweepIdle 删掉全部序号状态却保留全局 epoch;
再发布不同的新快照,又是 epoch 7 / sequence 1。旧连接的 Resync(AfterSequence=1) 得到"无需发送",旧 ACK(7,1) 返回 nil;
`PruneAcknowledged` 时新快照被裁掉(Retained=0)。RotateEpoch 对照正确。

## 根因

ACK / Resync 只携带 (epoch, sequence),服务端分不出新旧消费者;身份的高水位随数据一起被清理了(C8:清理路径与
编号路径对"这个身份用过哪些序号"没有共同记忆)。

## 方案选择

- **按身份保留墓碑(删除时记 latest)。** 语义最贴切,但 `Observer` 含 Session,身份在生产里持续更替,墓碑数在一个
  epoch 内无界;按条数淘汰就把保证变成尽力而为(U-0165 的教训),按时间又要新的元数据。
- **每次局部删除都 RotateEpoch。** 会作废其他所有流,审查明确不建议。
- **epoch 内的序号地板(采用)。** `sequenceFloor` = 本 epoch 内任何流已分配的最大序号;新建(含重建)的流从
  `floor+1` 开始。O(1) 状态,保证无条件:同一身份重建后序号必然高于它以前的所有序号,旧 ACK 只能确认更旧的、
  Resync(AfterSequence=旧) 会拿到新包。RotateEpoch 归零。持久化:`HistorySnapshot.SequenceFloor`(omitempty,老快照为 0
  时从流的 Latest 推导),WAL 重放跟着 Append 抬高;重放时新流的第一条记录允许任意起始序号(之后仍须逐一连续)。
  **代价**:新建流的首序号不再固定为 1,且与其他流的活跃度有关(observer B 的首序号高于 A 已用到的)。

  这个代价比我第一版记录里写的大——当时我写"核对过消费方,skillsync 不受影响",**是错的**,`skill/skillsync` 的测试
  立刻红了(`packet sequence gap: current=0 base=1 sequence=2`)。实际连带改了三处:

  1. `appendLocked`:新建流的**第一条包是链的起点**,`BaseSequence` 必须是 0,不能是 `state.latest`(=floor)——
     否则它指向一条这条流从来没有过的包。这是我第一版实现里真正的错误。
  2. `Import` 的首包规则:delta 首包原来只接受 `base+1 == seq`(前面的被裁掉),现在还接受 `base == 0`(链起点,
     序号可以从 floor+1 开始)。与 `Resync` 对首包的判据一致。
  3. `skill/skillsync/applier.go`:无游标的流原来要求首包 `base == 0 && seq == 1`,现在只要求 `base == 0`——
     **链的起点由 base 判定,不是由绝对序号 1 判定**。这是更正确的判据(它检查的本来就是链连续性),但确实是
     一处下游语义变更。其测试里写死的 `gap.Sequence = 3 / BaseSequence = 2` 也改成相对于已应用包来构造。

  另外核对过 `syncstream/publisher.go`:Sequence 映射成 Version,允许间隙,不受影响。老测试
  `TestObserverStreamsAreIsolated` 编码的是被本 RR 推翻的旧契约("各 observer 首序号都为 1"),改为断言每流内部连续、
  彼此独立推进。

## 改动

`syncstream.go`:`sequenceFloor`;`appendLocked` 新流起点与抬高;`HistorySnapshot.SequenceFloor`;`exportStreams` / `Import` 读写。
`lifecycle_journal.go`:`RotateEpoch` 归零。`file_journal.go`:重放抬高、新流首条放宽、RotateEpoch 归零。

## 证明

`syncstream/history_identity_promises_test.go`:三种清理后重建的序号大于旧的、旧 ACK 不裁新包、Resync 拿到新包;
RotateEpoch 对照;重建的流经 journal 重放能恢复到同一 latest。
修前红:`old identity silently swallowed new packet: … fresh={… Sequence:1 …} status={… Retained:0 Pruned:1}`。

## 未做 / 边界

- 序号在 observer 之间"可见"(B 能从自己的首序号推知 A 大约发过多少包)——是选择 O(1) 无条件保证换来的信息侧信道,
  比原来的"新内容被当作已消费"轻得多,但要说明。
- 没有引入逐流 generation;ACK / Resync 报文不变。
- **仓库外的消费方若假设"流的首个包序号为 1",会被这次变更打到**。判据应改为"`BaseSequence == 0` 即链起点"。
  这一条已写进 CHANGELOG 的行为变化与 T-109。
- `skill/skillsync` 包内有先于本轮存在的 gofmt import 顺序问题(`coordinator.go` 等我没碰的文件也在 `gofmt -l` 里),
  本轮没有顺手改,以免把无关改动混进来。
