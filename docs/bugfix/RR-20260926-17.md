# RR-20260926-17：关闭排空外部在途调用

问题：[原始复审](../bug/RR-20260926-17.md)。日期 2026-09-26。
实施基线：main `381efc9` 加上一轮 RR-03～09 的未提交修复；原报告基线 `aaada47` 保留。
状态：代码已修复，适用本地验证通过，尚未提交/发布。完整证据和限制见[本轮汇总](../review/REVIEW-2026-09-26-release-fixes.md)。

## 修复与依据

复用 internal/operation.Lifetime 管理 Projector、Committer、WAL 的准入和停止。Close 先拒绝新调用，等待所有已准入的外部 Flush/Replay/Commit；超时保留所有权。WAL 目录锁在旧 Replay/Ack 退出后才交出，旧实例不能再 Ack。

涉及：`internal/operation/lifetime.go`、`dataengine/engine/projector.go`、`projector_replay.go`、`nestwal/committer.go`、`wal.go`。

## 验证

TestCloseRetainsDirectoryUntilExternalReplayReturns（修前失败）；TestProjectorCloseWaitsForExternalProjection；TestCommitterCloseWaitsForExternalFlush（race ×5）。命令、负对照范围与环境见汇总；没有把全部测试绿色当成生产故障已穷尽。

## 兼容与边界

关闭超时不表示资源已释放；调用方应等待并再次 Close。新增包只承担三个模块共用的生命周期基建。

关闭停止准入后，重复 Shutdown 直接等待既有 Close，保留幂等停机；新增 OpenRuntime 重复 Shutdown 回归通过。

### (1) OnFatal 里同步 Close 自等

根因：`isFatalProjection` 在 ReplayPass/Flush 仍持有 operation 时同步回调 `OnFatal`（`projector.go:368-369`，基线行号）；后台循环路径更糟，
回调运行在 `run` goroutine 里，Close 还要等 `done`。回调里同步 `Close` 必然等到自己的截止时间。

两种方案里选了“移出持有 operation 的路径”，具体为**异步投递**（`projector.go` `isFatalProjection`，与 `nestwal.Options.OnFatal` 同一做法：独立 goroutine、吞掉 panic）：

- fatal 先于回调可见：`fatalOnce` 内先写 `fatalErr`、再唤醒全部待投影等待方（RR-10 补修），最后才 `go onFatal(err)`；回调开始前 Commit/Enqueue/CommitSystem
  已在 WAL 前以 fatal 拒绝，Flush 返回 fatal，等待方拿到 fatal。
- 回调里允许同步 `Close` / `Shutdown`：触发 fatal 的 ReplayPass/Flush 退出后 drained，后台循环在 fatal 后退出、`done` 关闭。
- 未采用：“在 operation End 之后同步调用”——Flush 内嵌 ReplayPass（两层 operation），后台循环还要先关 `done`，需要一套“最外层出口负责通知”的状态，
  比异步复杂且仍然容易在某个出口漏掉；“文档约束 + Close 检测重入返回错误”——Lifetime 不知道调用栈归属，检测重入要给每个调用带身份，而且只是把自等换成报错，
  回调仍不能完成它的本职（fence 并停机）。
- 代价：kit 的 `Mod.onFatal`（Nest fence + RuntimeFailure）比 Flush 返回稍晚几微秒；这段时间的新事务已被 Projector 在 WAL 前拒绝并由 Nest 回滚，不产生持久副作用。

回归：`projection_lifetime_test.go` TestProjectorOnFatalMayCloseProjector（external_flush：ManualReplay + 外部 Flush 触发 fatal；background_loop：后台循环触发）。
回调内先断言准入已被 fatal 拒绝，再以 1s 截止 Close，要求返回 nil，之后 ReplayPass 返回 `ErrRuntimeStopped`。
`remote_conflict_test.go` 的“只通知一次”断言改为等待异步通知。

```text
修前：GOWORK=off go test -count=1 ./dataengine/engine -run TestProjectorOnFatalMayCloseProjector -v
    projection_lifetime_test.go:217: Close inside OnFatal=context deadline exceeded
    projection_lifetime_test.go:217: Close inside OnFatal=context deadline exceeded
--- FAIL: TestProjectorOnFatalMayCloseProjector (2.04s)
    --- FAIL: .../external_flush (1.03s)
    --- FAIL: .../background_loop (1.01s)
修后：GOWORK=off go test -race -count=3 ./dataengine/engine -run 'TestRemote.*Conflict|TestProjectorOnFatal|TestProjectorFatal'   # ok
```

### (2) 真正的负对照替代 TestCommitterCloseWaitsForExternalFlush

旧测试用已取消的 ctx 调 Close：修复前 Close 在 `done` 与 `ctx.Done()` 间随机选，两条路都返回 Canceled，WAL 也没被关，所以修前即绿。
重写（同名，`nestwal/close_replay_test.go`）：外部 Flush 卡在 apply 内时用**活 ctx** 调 Close，要求 Close 在放行前不返回、之后的回放被拒（`ErrClosed`）；
放行后 Close 返回 nil、WAL 已关闭；**以新拥有者身份重开同一目录，已应用的记录不得再次出现**（checkpoint 未丢）。

负对照（修后代码临时去掉 `Committer.Close` 对 `operations.Stop()` 返回的 drained 等待）：

```text
GOWORK=off go test -count=10 ./nestwal -run TestCommitterCloseWaitsForExternalFlush -v
    close_replay_test.go:161: new owner replays 1 record(s) the closed committer already applied: checkpoint was lost   # 10/10
```

（缺陷版本里 WAL.Close 自己会等 Replay 回调返回，所以 Close 看起来“等了”；但 Flush 随后的 ack 撞上已关闭的 WAL，checkpoint 丢失，这正是 RR-17 的后果。）
修后 `GOWORK=off go test -race -count=10 ./nestwal -run TestCommitterCloseWaitsForExternalFlush` → ok；`-race -count=3 ./nestwal` → ok。
