# RR-20261001-02：`sameSendIntent` 逐字段比较，nil 与空切片视为相同

问题：[RR-20261001-02](../bug/RR-20261001-02.md)。日期 2026-10-01。基线 `2308e37f`（main）。状态：已修复，本地验证通过（含真实 Redis 变体），未发版。

## 根因

`service/mail/send_intent.go:7`（`2308e37f`）：

```go
func sameSendIntent(a, b Envelope) bool { return reflect.DeepEqual(a, b) }
```

`replaySend`（`service/mail/service.go:289-308`）在 RR-20260929-16 的同 RequestID 恢复里先用 `record.Intent.clone()` 重建信封、`Envelopes.Create`，再 `Get` 回读并用 `sameSendIntent(stored, envelope)` 确认“没有人在保留的 id 下换了信封”。Intent 侧的 `Recipients` / `Attachment` 在没有值时总是 nil：`Envelope.clone()`（`types.go:351-356`）用 `append([]T(nil), …)` 保持 nil，`SentRecord` JSON 往返 `omitempty` 也保持 nil。`reflect.DeepEqual` 把 nil 切片与 `[]T{}` 判为不同，于是只要 `EnvelopeStore.Get` 把缺失字段还原成空切片（文档库解码、自定义存储常见做法），恢复就返回 `ErrConflict: reserved envelope differs or is missing`；信封此时已经存在，之后每次重试都在同一处失败，这条发送既完不成也不能换 RequestID 重发（ledger 已占）。内置 Redis 存储两侧都走 JSON，nil 对 nil，不触发；触发面是 `store.go` 鼓励的自定义 `EnvelopeStore`。

## 决策与未采用方案

- 采用：`sameSendIntent` 改成逐字段比较——字符串 / 整数 / `Audience` 用 `==`，`Recipients` 用 `slices.Equal`，`Attachment` 用 `bytes.Equal`（两者都把 nil 与空视为相等）。ID、Audience、Scope、Subject、Body、SendRequestID、CreatedAtUnix、ExpiresAtUnix 全部保留严格比较，“在保留的 id 下替换正文 / 期限 / 收件人”仍然 `ErrConflict`。
- 未采用“只比 ID / 只比 ID + 期限”：那会让恢复路径接受被替换的正文或附件，放宽 RR-16 的承诺。
- 未采用“比较前把两侧都规范化（nil → 空）再 DeepEqual”：等价但多一次拷贝，而且新字段加进 Envelope 时同样需要有人记得改规范化函数，没有比逐字段更安全。
- 未采用在 `clone()` / JSON 解码侧把 nil 规范成空切片：这会改 `Send` 返回值与持久格式的形状（`omitempty` 不再省略），影响面超出本条。
- 同包 `reflect.DeepEqual` 排查：`service/mail` 与 `kit/service/mail` 非测试代码只有这一处；测试里的 `get_consistency_promises_test.go:44` 比较的是同一存储同一路径的两次读（Get vs GetMany），两侧都是 nil 对 nil，不是本条的问题。
- 新字段保护：`TestSameSendIntentFieldwise` 用 `reflect.TypeOf(Envelope{}).NumField() == 10` 钉住字段数，`Envelope` 加字段时会红，提醒同时扩比较函数与差异表。

## 文件与行为

- `service/mail/send_intent.go`：去掉 `reflect`，逐字段比较；注释写明为什么不用 DeepEqual。
- `service/mail/rr_20261001_02_test.go`（新）：
  - `TestSameRequestRecoveryToleratesEmptyVsNilSlices`：`reviewEnvelopeOnceFailure`（首次 Create 失败）外包一层 `nilToEmptyEnvelopes`（Get 把 nil `Attachment` / `Recipients` 还原成空切片）；direct 无附件、broadcast 无收件人两个子用例，断言第二次同 RequestID Send 成功、第三次返回同一 ID。
  - `TestSameRequestRecoveryStillRejectsSubstitutedEnvelope`：回读时分别换 Body / ExpiresAtUnix / Attachment / Recipients / Scope，断言恢复仍是 `ErrConflict`（负对照，修前修后都过）。
  - `TestSameSendIntentFieldwise`：clone 相同、nil 与空相同、十个字段逐个改动都判不同、字段数钉 10。
- 行为变化只有一处：同 RequestID 恢复时，存储回读出的空切片与 Intent 的 nil 切片视为同一信封。其他路径不变。

## 兼容性

- 无 API / 持久格式 / 键空间变化。内置 Redis `EnvelopeStore` 行为不变（两侧本来就 nil 对 nil）。
- 自定义 `EnvelopeStore` 此前在这条路径上会卡死的发送，升级后下一次同 RequestID 重试即可完成；不需要迁移。
- 比较语义严格程度：除 nil / 空切片等价外与 DeepEqual 相同。
