# NC-117 修复：提交前失败的 cast 与其他终态 cast 同样有界保留

[问题](../bug/RR-20261005-NC-117.md) · [本轮](../review/REVIEW-2026-10-05-n09-batch2.md)。已修复、声明场景验证，未发版。

## 根因

`trackCompletedCastLocked`（`skill/runtime_retention.go:20-32`）只收 finished 与“已提交的 failed”，提交前失败的 cast 永不进完成队列；checkpoint 恢复（`runtime_checkpoint.go:862`）却把所有 finished / failed 当作完成并按上限判 corrupt（`:1023`）。排除“未提交的 failed”看上去是为了 `startLocked` 删除并复用 ID 的失败启动，但其余提交前失败（commit 付费不足、NC-111 修复后 Cancel / Release 回调失败）并不删除。

## 决策

- 完成队列收所有终态（finished / failed），与恢复规则一致，按 `CompletedCastLimit` 回收；
- `startLocked` 删除失败启动、复用 ID 时，用新的 `forgetCompletedCastLocked` 撤掉刚登记的条目，避免队列里留下指向被复用 ID 的旧条目。

未采用“恢复时也排除未提交的 failed”：两边一致了，但无界保留仍在。代价：失败启动登记时若队列已满，会先淘汰一条更老的可回收终态 cast，再被撤掉，可检查的历史少一条（不影响正确性）。

## 文件与行为

`skill/runtime_retention.go`（`trackCompletedCastLocked`、`forgetCompletedCastLocked`）、`skill/runtime.go`（`startLocked` 失败删除处）。提交前失败的 cast 超过上限后被回收，之后 `InspectCast` 查不到它（与已完成的 cast 一致）；回收产生 `cast_remove` mutation。

## 兼容性

checkpoint 格式不变。旧版本写出的、含大量未提交 failed cast 的 checkpoint：未超上限的照常恢复（恢复本来就把它们当作完成）；已超上限的在旧版本同样恢复不了，修复不自动迁移这类 checkpoint。
