# RR-20260920-09：租约失而复得之后用的还是旧副本（U-0268）

- 等级：P1
- 仓库 / 位置：roost-codegen `demo/internal/service/game/playerowner.go.tmpl`、`service.go.tmpl`
- 审查记录：[REVIEW-2026-09-20-03](../bug/REVIEW-2026-09-20-03.md) · 复现附录 [REPRO-2026-09-20-03](../bug/REPRO-2026-09-20-03.md)
- 缺陷类：C8（快慢路径不对称：租约有终点，实体没有）

## 问题

`refreshLoop` 发现租约不再是自己的、随后又重新取得时，只打一条 Warn 就继续服务；登录路径同理。
而这中间另一个进程完全可能合法地拥有过这个玩家并写过文档——`Owns` 对无主玩家就地取得所有权就是设计，
`fence` 断开连接的目的也正是"让玩家重连到那时的 owner"。

## 根因

三件各自成立的事实：

1. **常驻实体永不重新加载**：`entity/manager_access.go:88` 命中常驻实例直接返回；`EntityManager` 只有显式
   `Destroy`，没有淘汰入口；生成工程里 Player 从不 Destroy，`PlayerOwners.Release` 一个调用方都没有。
2. **复得被当成良性**：`renew` 的 `case mine:` 只打日志；`enter_game.go` 的 `Claim` 成功后直接
   `GetOrCreate`，拿回的就是那份旧实体。
3. **两种历史不可分**：键不存在既可能是没人拿过，也可能是别人拿过、写过、租约也到期了。
   `playerroute.Route{SID, Token}` 的 Token 按 RR-20260920-03 的修法标识**进程**、进程内固定，没有世代号。

## 方案选择

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 租约值加单调世代号（每次 Claim `INCR`） | 能精确回答"中间有没有别人持有过"，但要多一个永不过期的计数器键，且 Lua 与 Store 都要改 | 未采用：**不需要知道有没有人用过那段间隔，知道有间隔就够了** |
| 复得时强制回源比对文档版本 | 要在 demo 层重新实现一遍版本比对 | 未采用 |
| **有间断就扔掉副本** | 只在失败/间断路径上多做事，happy path 逐字不变 | **采用** |

判据用的是**已经存在的那一个**：`Admit`。它只在 Redis 确认过、且减掉 guard 之后仍然有效的窗口里放行，
所以"`Admit` 此刻会拒绝"与"这次认领跨过了一个间断"是同一句话——无论间断来自 fence、失效、重启，
还是这个玩家本来就不在这里（那种情况下扔副本是一次找不到东西的空调用）。

实现时被自己的测试打回过一次：第一版只看 `Admit`，而测试里键是被删掉的、本地窗口还没到期，
于是 `continuous` 为真、副本没扔。**Redis 说"这把租约不是你的"就是权威答复，本地时钟看起来还没到期不作数。**
因此加了 `leaseState.interrupted`：`renew` 在决定之前先打这个标记，`Admit` 见到它直接拒绝，`confirm` 清掉它。
这条同时让 Admit 更严格了——键被运维误删、Redis failover 之后，窗口内的写入也会被拒绝。

## 改动

- `leaseState` 加 `interrupted`；`Admit` 拒绝被打断的租约；`renew` 在重新认领前 `interrupt(...)`。
- `Claim`：认领前先问"是否连续持有"，认领成功且不连续时**先扔副本再 confirm**；扔不掉就不 confirm
  并返回错误——租约在 Redis 里是我们的，但没人刷新它，30 秒后自己消失，与"进程持有着它死掉"是同一个结局。
- `fence`：断开连接的同时扔副本（不等待，跑在自己的 goroutine 上——刷新循环后面还排着别的玩家的续租）。
- 新增 `residentEvictor` 缝与 demo 的实现 `playerEvictor`：先 `Scene.Leave`（退订、退休、注销 room subject），
  再用**只查常驻、不加载**的 `manager.GetWithCategory` 找到实体并 `Destroy(..., deletePersisted=false)`。
  不删任何持久化数据：文档才是权威，下一次加载读的就是它。
- `service.go`：在发布 owners **之前**装好 evictor，这样不存在"登录比装配早"的窗口。

## 证明

新测试（生成工程 `internal/service/game/playerowner_test.go`）：

- `TestALeaseThatWasInterruptedDropsTheResidentCopy`
- `TestAClaimWhoseCopyCannotBeDroppedIsNotTakenIntoService`
- `TestAnUninterruptedLeaseKeepsItsPlayer`（happy path 不受影响）
- `TestFencingAlsoDropsTheCopy`

修前（第一版实现、缝已在）：

```text
--- FAIL: TestALeaseThatWasInterruptedDropsTheResidentCopy
    playerowner_test.go: the copy from before the gap was kept: dropped=[]
```

变异验证：把 `continuous := owners.Admit(playerID) == nil` 改成 `true`，上面两条同时红
（"the copy from before the gap was kept" / "the player was taken into service although the stale copy is still resident"）。
修后生成工程 `go test ./... -race` 全绿，codegen 仓全绿。

**行为变化**：没有装 evictor 的 `PlayerOwners` 现在**任何**认领都会被拒绝（错误信息直说缺什么）。
这是故意的 fail-closed：装配漏了就要响。`ownersUnderTest` 相应地默认装一个。
原来编码"复得是良性的"那条老测试（`TestALapsedLeaseNobodyElseTookIsRetakenInsteadOfFenced`，U-0259）
改成断言新不变量而不是删掉：它现在装 evictor，仍然要求不 fence、仍然要求重新取得。

## 未做 / 边界

- **没有端到端实测**：把"复得之后第一次写"跑成一条真实的 `fatal projection version conflict` 需要两个进程 +
  真 Redis + 数倍于 `Lease=30s` 的时间窗口。本单元是确定性单测 + 变异验证。
- **扔副本会等实体上的事务**：`EntityManager.Destroy` 要拿实体锁。因此给了 5 秒预算（`evictBudget`），
  `Claim` 路径同步等、`fence` 路径异步。极端情况下刷新循环会被一次认领阻塞最多 5 秒，
  小于 `RefreshInterval=10s`，不会连累别人的租约。
- **世代号仍然没有**：本修复用"有没有间断"代替"中间有没有人写过"，代价是偶尔多扔一次其实没人碰过的副本
  （下一次访问冷加载，正确但慢一点）。要精确区分需要世代号，记在这里备查。
