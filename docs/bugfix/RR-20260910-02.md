# RR-20260910-02:已领取邮件被淘汰后,重复投递重新生成发奖 token

**仓库 / 位置**:roost-kit `service/mail/mailbox.go`(`deliver`、`evict`)、
`service/mail/service.go`(`Deliver`、`ReserveClaim`、`CommitClaim`)、`service/mail/types.go`。
**修复单元**:U-0165(C8)。**定位文档**:TROUBLESHOOTING T-59。

## 问题

1. 投递有附件、仍在有效期内的邮件 A,`ReserveClaim` 得到 token-1,`CommitClaim` 成功。
2. 继续投递使邮箱超过 `MaxMailboxEntries`;A 是终态,**整条 Entry 连同领取身份被删除**。
3. 腾出可淘汰容量后,异步 fanout 的重复消息再次对 A 调 `Deliver`。
4. A 被重新建立为未读且没有 token,`ReserveClaim` 成功返回**同一个附件**和 token-2。

发奖服务若按契约只以 `Claim.Token` 去重,就会再发一次。

## 根因

`evict` 认为终态条目可以整条丢掉,`deliver` 认为"条目不在就是从未投递",两条路径对同一状态的
判据不同(C8)。更根本的是:**展示保留与领取身份保留被绑在同一个上限上**。Entry 带主题、状态、
时间戳,`MaxMailboxEntries` 约束它是为了让邮箱可读;而"这封邮件已经领过"必须活得比 Entry 长。

`CommitClaim` 自己的注释早就写明了这个不变量 —— "the token … stays the delivery key for this
mail forever, so a late duplicate delivery attempt still dedupes" —— 而淘汰把它删了。

## 方案选择

- **禁止淘汰 Claimed。** 不够:玩家把已领取的邮件删掉后状态变 `StatusDeleted`,又变成可淘汰,
  同一个洞从另一条路打开。而且已领取条目永不淘汰会让邮箱被它们占满,`full()` 开始拒收新邮件,
  把罕见的重复发奖风险换成硬性停摆。
- **token 由 (playerID, mailID) 稳定派生。** 发奖侧按 token 去重就只付一次,但邮件仍然会重新
  变成未读、重新可领,产品语义上仍然错;而且 token 从随机凭证变成可推导值。
- **把两种保留分开(采用)**:淘汰终态条目时,若它带着 claim token,留下一条极小的墓碑
  `SettledClaim{Token, SettledAtUnix}`;墓碑有自己的上限 `MaxSettledClaims`,按时间最旧先挤掉。
  `deliver` 遇到墓碑就当"已投递且已终结",不重建未读条目;`ReserveClaim` 遇到墓碑答
  `ErrAlreadyClaimed`;`CommitClaim` 带原 token 的迟到重试仍然幂等成功。

**墓碑键在 token 而不在 Status**:被领取后又被玩家删除的邮件,淘汰时状态是 `StatusDeleted`,
按状态判会漏掉它。

**上限为什么可以是计数**:`ReserveClaim` 本来就拒绝过期信封,所以复活的邮件只在信封仍然有效
时才可能被重领 —— 墓碑只需要活得比信封长。残余风险因此很窄:一封信封仍未过期、又被
`MaxSettledClaims` 条更新的"已领取且已淘汰"邮件挤出去的邮件。

## 改动

- `mailbox.go`:`Mailbox` 加 `SettledClaims map[string]SettledClaim`,`init` 建表;`evict` 删除
  带 token 的条目时写墓碑,末尾调新增的 `evictSettledClaims` 给墓碑自己收界;`deliver` 命中
  墓碑时返回一个终态的合成 Entry 且 `added=false`。
- `service.go`:`Deliver` 的容量前置对墓碑不要求腾位置(不插入就不需要空间);`ReserveClaim` 的
  "条目不存在"分支命中墓碑时计 `refused:reserve_claim:already_claimed` 并返回
  `ErrAlreadyClaimed`;`CommitClaim` 的同一分支命中墓碑时按 token 是否相符,分别答重放成功或
  `ErrClaimTokenWrong`(同样不说正确的 token 是什么)。
- `types.go`:`MaxSettledClaims = 200`,与 `MaxMailboxEntries` 同量级,注释写明为什么是独立上限。

## 证明

`service/mail/claim_identity_promises_test.go` 四条,全部用公开 Service 与真实 MemoryStore,
不直接改邮箱内部状态:

- `TestEvictionKeepsTheClaimIdentityOfAClaimedMail`:领取并提交 → 填满淘汰 → 先断言那条 Entry
  确实被淘汰(否则测试证明不了任何事)→ 腾位置后重投 → 断言重投仍然幂等不报错、`ReserveClaim`
  返回 `ErrAlreadyClaimed`、邮件没有变回未读。
- `TestEvictionStillForgetsAMailThatWasNeverClaimed`:从未领取过的邮件被淘汰后重投,仍然应该
  重新显示为未读 —— 这正是保留上限的用途,不能一起改掉。
- `TestCommitClaimReplaysAfterTheEntryWasEvicted`:淘汰之后带原 token 的迟到提交仍然答重放,
  换个 token 仍然 `ErrClaimTokenWrong`。
- `TestSettledClaimsAreBounded`:墓碑超过上限时按最旧先删,最新的保留。

修前红,失败输出正是报告里的那句:

```text
claimed mail resurrected with a new delivery key: first="token-1" replay="token-2"
```

修后 `go test ./service/mail -race` 绿,kit 全仓构建与测试绿。

## 未做 / 边界

- **没有连接真实资产服务。** 证明的是"不再铸出第二个 token、不再重新可领",没有声称此前一定
  发生过真实资产重复。
- **上限是计数而不是信封有效期。** 按有效期保留需要墓碑知道信封何时过期,而 `evict` 是
  `Mailbox` 上的方法,拿不到信封存储。上文说明了为什么计数上限在这里是够的,以及残余风险的形状。
- **`Mailbox` 多了一个 JSON 字段。** 带 `omitempty`,旧的存量值解码后 `SettledClaims` 为 nil,
  `init` 会建表,所以没有迁移动作;但一次发布之后回退旧版本会忽略这个字段,回退期间淘汰掉的
  已领取邮件会重新可领。
- **产品语义没有改。** "已终结的邮件不再复活"是本次确立的行为;要不要让玩家重新看到那封邮件
  (例如以只读形式)是产品决定,这里选择的是不显示。
