# RR-20260930-03：`cache.AtomicLocalStore` 时钟记录随存活键数有界

问题主记录：[docs/bug/RR-20260930-03.md](../bug/RR-20260930-03.md)。基线 `f6566d4e`（main），修复提交 `c0d8826f`，分支 `fix-r14-cache`。状态：**已修复，未发版**；C01 24 小时长稳尚未重跑。

图谱说明：codebase-memory 图谱已过期（generation 09-26），行号与结论来自源码。

## 根因（基线行号）

`cache/atomic_local.go:190` `SetWithTTL` 每次写入（含覆盖已有键）都向 `shard.order` 追加 `{key, generation}`。旧记录只在 `evictLocked` 结尾压缩（`:276-278`，条件 `hand > 1024 && hand*2 > len(order)`），而 `hand` 只在条目数或字节数超限、需要淘汰时前进（`:254-266`）。`Delete`（`:205-214`）和过期删除（`expire`，`:232-238`）也不回收记录。键集合远低于上限的缓存永不淘汰，`hand` 始终为 0，`order` 随写入次数线性增长。Remote 快照 L1（`entity/remote_snapshot.go:231`）就是这种情况。

## 修复

`cache/atomic_local.go` 新增 `(*atomicLocalShard).compactOrderLocked`。当 `len(order) - hand > 2 × entries + atomicLocalOrderSlack(1024)` 时，就地过滤 `order[hand:]`：只保留 generation 等于 `items[key].generation` 的记录，`clear` 尾部（底层数组不再引用已删除的键），然后把 `hand` 置 0。

- 调用点：`SetWithTTL` 在 `evictLocked` 之后调用；`Delete` 实际删除后调用；`expire` 删除后调用。这三处是全部写入口。`Set` 走 `SetWithTTL`，本类型没有 CAS 或其他条件写。`ReadThroughStore` / `LayeredStore` 回填也经 `Set` / `Delete` 进入。
- 所有权：`order` / `hand` 只在分片写锁下修改。压缩不在 `evictLocked` 的淘汰循环里执行，因为循环正按 `hand` 遍历 `order`。既有的淘汰后压缩保留不动。
- 不变式：每个存活键在 `order[hand:]` 中恰有一条当前记录（淘汰指针走过的当前记录都已被淘汰；覆盖写产生新记录并追加在末尾）。因此过滤后 `len(order) == entries`，并且剩余记录的相对顺序不变。淘汰顺序（覆盖写 = 重新插入）不变，Stale / Conflict / Superseded 准入规则不变。
- 读路径：`Get` 仍只取读锁。过期删除本来就在 `expire` 的写锁内，这里只是在同一把锁内多一次阈值判断。没有采用“只在新键时追加记录”，因为那会改变淘汰语义，回归中的变异检查也证明它会失败。
- 上界与成本：未淘汰部分不超过 `2e + 1024`；加上既有压缩对 `hand` 前缀的限制（`max(1024, len/2)`），`len(order) ≤ 4e + 2048`。触发线随存活键数线性增长，过滤成本摊销 O(1)：每次覆盖写约多 1 次 map 查找。

兼容性：没有 API、配置或持久格式变化。有长期内存上界，但覆盖写多了少量 CPU（见基准）。
