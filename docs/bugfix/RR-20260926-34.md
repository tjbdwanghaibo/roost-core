# RR-20260926-34 修复：投影事务内身份裁决改为“先快照读、后插入”，伪 Mongo 忠实中止事务，驱动错误链保留

问题：[RR-20260926-34](../bug/RR-20260926-34.md)（探针见 [REPRO-2026-09-26-04 §2](../bug/REPRO-2026-09-26-04.md)）。
日期 2026-09-26；实施基线 main `49f20ee`。状态：已修复、本地验证通过，已本地提交，未推送/未发布。

## 根因

`dataengine/engine/mongo_store.go`（基线）`stageReceipt` / `stageEffect` / `insertTransactionMarker` 都在 `Project` 的
`session.WithTransaction` 回调内先 `InsertOne`，撞唯一键后在**同一事务**里 `FindOne` 读回裁决。真实 Mongo 在事务内任一写错误后
立即中止事务，之后的读返回 `NoSuchTransaction`（251，带 `TransientTransactionError`），`errors.Join` 后驱动仍识别该标签，重跑回调，
每次都同样撞键，直到 `transaction_timeout`：相同回执得不到“成功”，漂移得不到 fatal 身份冲突，只剩非 fatal 超时，WAL 头部卡住。

单测没有发现，因为 `mongo/mongotest` 撞键后不中止事务，事务内读照常返回文档；另外 `mongo/driver/collection.go` 的 `wrapError`
把驱动错误换成裸 `fmongo.ErrDuplicateKey`，驱动错误链（WriteException、错误码、标签）丢失。

## 决策（按维护者批准的修复约束）

- 采用约束中的第一种做法：**事务内先快照读再插入**。
  - `stageReceipt`：快照里已有同 ID 回执时，digest 与 payload 都相同即幂等成功（允许来自另一事务，语义同前），任一不同即
    `ErrReceiptIdentity`（fatal）；没有才插入。
  - `stageEffect`：已有同 ID effect 时，同一事务且同 topic 即幂等成功；其余即 `ErrTransactionIdentity`（fatal）；没有才插入。
  - `insertTransactionMarker`：回调开头的 `checkTransaction` 已在同一快照确认 marker 不存在，删去撞键后的事务内读回。
  - 并发事务插入同一回执 / effect / marker 时，服务端以 WriteConflict（transient）中止本事务，驱动重跑回调，下一次快照读看到
    对方已提交的文档，按上面的规则裁决。真实 Mongo 的 8 路并发同记录回归证明这一点。
  - 快照读未命中却撞键不属于正常路径（快照隔离下对方提交在快照之后应得到 WriteConflict）。此时事务已被中止，不再读回：返回
    包裹原错误（`%w`）的**非 fatal** 错误整笔回滚，投影器重试时由新事务的快照读重新裁决。不吞 Transient 标签，也不把它升级成 fatal。
- `wrapError`：撞键返回 `fmt.Errorf("%w: %w", fmongo.ErrDuplicateKey, err)`，`errors.Is(err, fmongo.ErrDuplicateKey)` 仍成立，
  `errors.As` 仍可取回 `mongo.WriteException` / `mongo.ServerError` / `mongo.LabeledError`。`ErrNoDocuments` 仍映射为裸
  `fmongo.ErrNotFound`（没有服务端状态可保留，也保持 `==` 比较的兼容）。
- 伪 Mongo 忠实化（`mongo/mongotest`）：`WithTransaction` 为每次尝试在回调 ctx 里放入事务状态；事务内写方法返回错误（`ErrNotFound`
  除外，它不是服务端错误）即中止事务，之后该事务的所有读写返回 `ErrNoSuchTransaction`（带 `TransientTransactionError` 标签，
  `HasErrorLabel` 与驱动 `mongo.LabeledError` 同形）；回调返回带该标签的错误时重跑（上限 16 次或 ctx 结束，真实驱动是 120s），
  回调吞掉写错误返回 nil 时提交被拒并重跑；撞键错误也做成“带标签、不含 Transient”的错误，和驱动一样按错误链中**第一个**带标签的
  错误判定是否重试。事务外的语句行为不变。
- 语义保持：同一 saga start 在两个事务各发一次（effect ID 为内容哈希，`saga/nest.go`）仍是 fatal `ErrTransactionIdentity`，
  回归显式断言。

未采用：撞键立即返回哨兵、在 `Project` 事务外重读裁决。它要在事务外重建与事务内相同的裁决（marker、回执、effect 各一套），
并处理“事务外读到的是否就是撞上的那份”这类竞态；先读后插只改三个函数，裁决仍在同一快照内完成。

## 兼容性

- 公开 API 无破坏。`wrapError` 返回的撞键错误文本由 `mongo: duplicate key` 变为 `mongo: duplicate key: <驱动原文>`；全仓无
  `== fmongo.ErrDuplicateKey` 或按文本比较的用法（已检索 `*.go` 与模板）。
- 驱动按错误链里第一个带标签的错误决定是否重试：撞键 WriteException 现在出现在链上，若调用方把撞键错误 `errors.Join` 在一个
  transient 错误**之前**返回，驱动不会重试（以前因为撞键是裸哨兵会重试）。本仓只有本次删掉的两处这样拼接。
- 伪 Mongo 行为收紧：事务内写错误后继续使用同一事务的测试会看到 `ErrNoSuchTransaction`。全仓 `go test ./...` 在收紧后（实现未改时）
  只有本 RR 改写 / 新增的三项身份用例红，其余全绿（当时另有根包 `TestFaultMatrixScriptNamesEveryFullEnvironmentSuite` 红，原因是
  集成回归一度放在 `dataengine/engine`，不在故障矩阵脚本包清单内；已移到 `kit/dataengine`，与伪 Mongo 无关）。
- `ErrReceiptIdentity` / `ErrTransactionIdentity` 的错误文本附加了 ID，`errors.Is` 不变。

## 对抗性自查

- **多 DAO 原子性**：`Project` 仍是一个 `WithTransaction`；身份裁决在同一回调内先于插入完成，fatal 或非 fatal 错误都让整笔回滚
  （DAO、Remote 持久写、回执、outbox、marker 一起）。真实 Mongo 回归断言 B/C 的 DAO 未落库。
- **事务 marker 幂等重放**：回调开头 `checkTransaction` 不变；已提交记录重放由 marker 吸收，不重复 staging（真实与伪 Mongo 回归都覆盖）。
  删去的 marker 撞键读回原本只是在“快照未命中后又撞键”时生效，而这在快照隔离下是 WriteConflict；并发 8 路回归 marker=1。
- **receipt/effect 至少一次与去重**：相同回执跨事务仍成功（不覆盖已存回执，与修前设计一致）；同一记录内重复的回执 / effect
  现在由事务内“读自己的写”裁决（修前是撞键后读回，真实 Mongo 下同样会卡死）。outbox 投递后文档被删除，之后复用同一 effect ID
  不再被识别为身份冲突——这是修前即存在的窗口限制，本次未改变，已写入 `stageEffect` 注释。
- **fatal 分类**：`isFatalProjection` 未改；`ErrReceiptIdentity` / `ErrTransactionIdentity` 以 `%w` 包裹，fatal 计数回归为 1。
  新的“快照后出现”错误只包裹 `ErrDuplicateKey`，非 fatal；conflict 路径（`applyPut` 事务内撞键 → `ErrProjectionConflict`）未改。
- **Remote 投影**：`mongo_projection.go` 未改。Remote 持久写（`ApplyRemoteCommitsInTransaction`）先于回执 / effect，身份冲突时随事务
  回滚且不发布；相同回执现在成功后照常 `ApplyRemoteCommits` 发布。lease-fence 跳过路径的 marker 仍在同一事务内写入。
  `remoteentity.MongoCommitter` 的事务内路径本就是先读后写，伪 Mongo 收紧后其测试全绿。
- **伪 Mongo 收紧后的其他调用方**（逐个判定，均不属缺陷）：`nestwal/effect_inbox.go`、`saga/command_consumer.go`、`saga/mongo_store.go`
  `Apply`、`remoteentity/mongo_committer.go` 都是事务内先读后写、写错误立即返回；`dataengine/engine/mongo_projection.go` `ProjectBatch`
  在 BulkWrite 错误时立即返回；`mongo_load.go` 只读。`saga/dataengine_step_inbox.go` `reserveInTransaction` 在事务内
  `_ = inbox.markCompleted(...)` 吞掉写错误：真实服务端会拒绝提交并由驱动重跑，唯一可达的写错误是 WriteConflict（transient，重跑即可），
  判为不是问题；若将来 `markCompleted` 出现确定性失败会重跑到超时，记于此供 review 参考。全仓 `go test ./...` 无新红。

## 后续验证（2026-09-27）

来源：[OPEN-ITEMS-2026-09-27](../review/OPEN-ITEMS-2026-09-27.md) B15（`stageEffect`“快照读没命中却撞键”的非 fatal 分支没有用例）。基线 `d4234c9`；图谱过期（09-26），以当前源码为准。

- 结论：**无缺陷**。已收为回归 `dataengine/engine/stage_effect_race_test.go`（`TestStageEffectDuplicateAfterSnapshotMissIsRetryable`）：
  伪 Mongo 包一层 outbox 集合，在投影事务的 `FindOne` 未命中之后、`InsertOne` 之前绕过事务写入同 `_id` 文档。断言 `Project` 返回
  `errors.Is(fmongo.ErrDuplicateKey)`、不带 `ErrTransactionIdentity` / `ErrProjectionConflict` / `ErrReceiptIdentity`（投影器 `isFatalProjection` 的三个判据），
  整笔回滚（mutation、transaction marker 都不可见）；把并发写者按已提交放回后重试：同一事务身份幂等成功（mutation 落库、outbox 仍 1 条），
  不同事务得到 `ErrTransactionIdentity`（由重试时的快照读裁决）。
- 负对照（只改实现、跑完用备份恢复）：把该分支改成包 `ErrTransactionIdentity` 后两个子用例都红：
  `... transaction identity conflict: effect effect-a appeared after the snapshot read: mongo: duplicate key: a duplicate after a snapshot miss must not be classified as fatal`。
- 命令：`GOWORK=off go test -race -count=50 -run TestStageEffectDuplicateAfterSnapshotMissIsRetryable ./dataengine/engine/` → `ok`。
- 边界：伪 Mongo 的回滚是全局快照恢复，会一并抹掉注入的“并发”文档，用例在重试前手工放回；真实 Mongo 快照隔离下这一形态表现为 WriteConflict（本记录“未验证项”第 2 条不变）。
  `stageReceipt` 的同形分支未单独构造。
