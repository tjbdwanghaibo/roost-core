# RR-20261004-09 修复：RefHMap 注册表 guard 改为“覆盖检查”，同布局并发不再误报；LayeredStore.Delete 远端失败也丢 L1

问题：[RR-20261004-09](../bug/RR-20261004-09.md)（来源 [NC-30 复审 §4 D1](../review/REVIEW-2026-10-04-nc30-audit.md)；引入它的是 B 线 [NC-30](RR-20261004-NC-30.md) `7fbdc735`，随 v1.19.1 发布）。
日期 2026-10-04；实施基线 main `d638f312`（v1.19.1 = `d3e69336` 之后）。状态：已修复，本地验证通过（含真实 Redis），已提交，未推送、未发版。

## 根因（基线行号）

- `cache/ref_hmap.go:49`（Set 的 `refHMapWriteScript`）与 `:79`（Delete 的 `refHMapDeleteScript`）：`(HGET root.__keys or "") ~= ARGV` 逐字节比较 Lua 执行时的注册表与调用方 `registeredKeys` 读到的快照，不等就返回 0，`refHMapWriteResult` 报 `ErrRefHMapRegistryChanged`。
  NC-30 要防的是“清理清单漏了键”——调用方读完注册表后，另一个布局登记了本次 KEYS 之外的 hash，按旧清单 DEL 会把它变成无 TTL、再也找不到的孤儿。字节不同并不等于漏键：同布局并发时注册表会出现（并发首次创建）、消失（并发删除、整条到期）或被同内容重写，而本次 KEYS（旧注册表 ∪ `plan.keys()`，或 fallback `plan.keys()`）仍覆盖当前注册表的每个键。
- `cache/layered.go:151-154`：`remote.Delete` 返回错误时直接 `return err`，不删 L1、不清 L1 到期。上面的误报让并发删除的输家拿到错误，Redis 里记录已被删掉，本进程 L1 在 TTL 窗口内继续返回它；远端真的拒绝或网络失败时也一样留着 L1。

## 决策

1. **guard 改为覆盖检查**（`refHMapRegistryGuardLua`，Set / Delete 两个脚本共用的 Lua 片段）：当前注册表与快照字节相等时直接放行（快路径，相等必然覆盖）；否则逐条解析当前注册表（按 `\n` 分、去空白，与 `parseRefHMapRegistry` 一致），只要有一个键不在本次 KEYS 里就返回 0。
   - 真正的 schema 竞争（旧布局写者按 fallback 清单清理，新布局在它读完后登记了 child）仍拒绝：child 不在旧写者的 KEYS 里。
   - 保留 NC-30 的其余承诺：DEL 前在同一 Lua 内确认注册表；root 固定为 KEYS[1]（`registeredKeys` 不变）；Eval 错误原样透传、非 0/1 回复报错（`refHMapWriteResult` 不变）。
   - 脚本只 `HGET KEYS[1]`，注册表内容只当字符串比对，不按其内容访问任何键——没有引入未声明键访问，Cluster 同槽性质与 NC-30 / RR-03 相同。
   - 快照参数（ARGV[3] / ARGV[1]）保留：Go 侧调用、参数布局、包内替身都不用改参数位置。
2. **`LayeredStore.Delete`**：远端删除返回错误时也删 L1、清 L1 到期，再返回远端错误（L1 也失败时 `errors.Join` 两者；只有远端失败时原样返回，不包一层，`errors.Is` / 等值比较都保持）。丢缓存总是安全的：远端没删成时下一次 Get 读回权威值。Get / Set 的回填规则（RR-20261004-02）不动。
   - 顺带：L1 删除失败时也清 L1 到期（之前直接返回、到期保留）。到期清掉后 Get 不再信任 L1，读远端，只会更保守。

### 未采用的方案

1. **Go 侧收到 `ErrRefHMapRegistryChanged` 后自动重读注册表重试**：同布局情形重试一次就会成功，但把“明确拒绝”和重试策略混在一起；NC-30 已定下“不自动重试或补偿”，真正的 schema 竞争重试时还要重新决定业务意图。而且多一次往返，误报本身没有消失。
2. **只在注册表变空（记录被删 / 到期）时放行**：覆盖不了并发首次创建（"" → 同布局注册表）和同布局重写，5 种情形里只修 3 种。
3. **比较“键集合相等”而不是“包含于 KEYS”**：Set 的 KEYS 是旧注册表 ∪ 本布局，并发首次创建时当前注册表是本布局的子集但不等于 KEYS 的集合；集合相等仍会误报。覆盖（⊆ KEYS）正是 DEL 不漏键的充要条件。
4. **去掉 guard，回到 NC-30 之前**：真正的 schema 竞争会重新留下孤儿 child（NC-30 的 12 条回归会红）。
5. **`LayeredStore.Delete` 按错误种类决定是否保留 L1**（像 `ReadThroughStore` 对 `FatalRemoteError` 保留 L1，NC-13）：Layered 没有 fatal 分类的配置，生成的 CachedDAO 直接用它；保留 L1 的唯一后果是可能返回被删的值，丢 L1 的唯一后果是多一次远端读。按约束选后者，`ReadThroughStore` 的 NC-13 规则不动。

## 兼容性

- **行为放宽（回到 NC-30 之前）**：同布局并发首次创建、并发删除、Set 与 Delete 交错、Set 读完注册表后记录到期、注册表被同布局重写，v1.19.1 返回 `ErrRefHMapRegistryChanged`，修后成功（last-writer，与 NC-30 之前一致）。依赖这些情形报错的调用方应改为依赖业务版本 / Stale，guard 从来不是值 CAS。
- **仍拒绝**：Lua 执行时注册表包含本次 KEYS 之外的键（另一布局发布了新 hash，或 Patch 按新布局登记了路径）——NC-30 的 12 条回归全部保留。
- **LayeredStore.Delete**：远端失败时 L1 不再保留；返回的错误不变（只有 L1 也失败时才是 `errors.Join`）。生成的 CachedDAO 的 Delete 失败后，本进程下一次 Get 走远端。
- **存储格式、键、Go API、Eval 参数布局都不变**；旧进程（v1.19.1）与新进程混跑时，旧进程仍会对同布局并发误报，新进程不会。脚本文本变长（共用片段约 20 行），仍是 EVAL 一次往返；字节不等时多一次注册表解析（键数 = 布局 hash 数），没有跑基准。

## 未验证 / 风险

- 没有起 Redis Cluster / HA 实测；脚本访问的键与 NC-30 相同（只 `HGET KEYS[1]`），同槽论证见 RR-03 记录。
- 没有跑基准；字节不等时脚本多一次注册表解析。
- 复审的 6 个探针（`audit-nc30-probes/`）没有原样复跑，它们的场景已全部收进新回归（同一 hook、同一插入点）。
