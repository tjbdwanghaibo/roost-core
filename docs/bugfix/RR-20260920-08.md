# RR-20260920-08：`OpTimeout` 不覆盖排队（U-0266，C8）

> 2026-09-24 补充：本记录原修复覆盖单实体写闸排队。后续确认冷 wrapper 构造的权威读取脱离调用方 context，多实体还会重开预算，已有较长 deadline 也会放大预算；已由 [RR-20260924-23](RR-20260924-23.md) 修复。下文保留历史证据；当前契约是整批**准入**共享上界，不包含业务执行、提交发布与失败清理的全部耗时。

## 问题

`remoteentity/batch.go:103-124` 的 `beginWrite` 先在每实体一格的写闸上 `select`，
**只看调用方的 ctx**；拿到闸之后才 `context.WithTimeout(ctx, cfg.OpTimeout)`。

于是配置成 3 秒的 `op_timeout` 与一次 **79 秒** 的 dispatch 可以同时为真：同一个实体上排队的 N 个写者，
最后一个要等前面 N-1 个各自跑完，而这段排队没有任何上界（调用方没有 deadline 时是**无限**等待）。

## 根因

C8：同一个判据在两条路径上不一致。同包的加锁路径 `ownership.go:251-262` **先**
`m.ownershipContext(parent)`（即 `WithTimeout(parent, OpTimeout)`）**再**去等同一个写闸——
它是对的。写路径把顺序反了过来。

所以这不是"两种合理设计的取舍"，而是一处遗漏：包内已经存在正确的形状。

## 方案选择

- **采用**：把 deadline 移到 `select` 之前，让排队与后续操作共用同一个预算。契约随之写死：
  **`OpTimeout` 是一次远端写的总预算，包含本地排队**。
- 放弃 **给排队单独一个超时**：两个预算意味着总上界是两者之和，问题只是变小没有消失。
- 放弃 **加大写闸容量**：闸是每实体的写串行化，放宽它就是放弃串行化。
- 排队超时返回的是 `context.DeadlineExceeded`，调用方可以据此退避重试；没有引入新的错误类型，
  因为调用方对"预算用完"和"操作超时"应该做同一件事。

## 改动

`remoteentity/batch.go`：`ctx`/`cancel` 的构造移到 `gateStarted` 之前，`select` 的第二个分支从
`parent.Done()` 改成 `ctx.Done()`，并加 `remote_entity_write_gate_timeout_total` 计数器
——排队超时此前没有任何可观测信号。

## 证明

`remoteentity/write_budget_promises_test.go`：

- `TestAQueuedWriterIsBoundedByTheOperationBudget`：闸被别人占住、调用方无 deadline。修前红：

  ```text
  a queued writer did not return within 600ms of an operation budget of 150ms; nothing bounds the wait
  ```

  （第一版写成在测试 goroutine 上直接调用，结果是**测试挂住**——那其实是最纯粹的红，
  但挂住的测试比失败的测试说的少，所以改成带上界的 select。）
- `TestConcurrentWritersEachReturnWithinTheBudget`：8 个并发写者各自都要在预算内回来。
- `TestACallerDeadlineShorterThanTheBudgetStillWins`：调用方自带 100ms 时以它为准——预算是上界不是下界。
  这条**修前就是绿的**，留着是为了钉住修复没有把它弄坏。

`./remoteentity` 全包 `-race` 绿，core 全量绿。

## 未做 / 边界

- **只改了写路径**。包里其它等待（`ensureMarker`、`ClaimOwnership` 的内部重试）本来就在 ctx 之下，
  没有逐一核对它们各自的重试次数与预算是否自洽。
- **没有改变公平性**：写闸仍然是一格 channel，没有排队顺序保证。预算到期的写者直接失败，
  不会"插队"，但也不保证先到先得。真要公平队列是另一件事。
- 79 秒那次实跑的**外层**现象（重启窗口内 `found_guild` 失败）由这条解释，但第十八批记录里
  那条"重启后要等前任的锁租约"仍然成立：租约到期前拿不到分布式锁，现在会在预算内以可重试的
  `guild_busy` 返回，而不是堆在闸上。
