# RR-20260927-15：同一 fence 下拒绝 StateVersion 回退

问题：[RR-20260927-15](../bug/RR-20260927-15.md)（OPEN-ITEMS C32）。日期 2026-09-27。基线 `d4234c9`，分支 `fix-r7-de`。
状态：已修复，本地验证通过，本地提交，未推送 / 发布。codebase-memory 图谱过期（09-26），定位以当前源码与 `git grep` 为准。

## 决策

在 `RemoteEntityBase.SetRemoteVersionVector` 的 CAS 循环里加一条：`version.LockFence == current.LockFence && version.StateVersion < current.StateVersion`
时返回 `ErrRemoteVersionConflict`，不写入。`acknowledgeRemoteCommit` 既有的“Set 失败后再次核对 `remoteReceiptObsolete`”于是生效：迟到重放判为过期、返回 nil、
向量不变。

- 为什么放在 setter：它是版本向量唯一的受检写入口（`SetEntityVersion` 是另一条非受检入口，不在本条范围），既有的 stale fence 拒绝也在这里；
  只在重放路径补判定挡不住“判定之后、写入之前”的并发推进（本 RR 的触发形态）。
- 为什么是 `ErrRemoteVersionConflict` 而不是 `ErrRemoteFenced`：fence 没有过期，是状态版本落后；调用方现有的 `errors.Is(ErrRemoteVersionConflict)` 语义（版本冲突）贴切。
- 对正式装配无影响：`GrantWrite` 每次写递增 fence，旧向量先被 `ErrRemoteFenced` 拒绝。

核对其余调用方（`git grep SetRemoteVersionVector`，生产代码 4 处）：`remoteentity/batch.go:310` 准备写入时写 `{EntityVersion(), 当前或新 fence}`，
`EntityVersion()` 就是当前向量的 StateVersion，同 fence 时相等；marked / durable 路径用新 fence。`remoteentity/ownership.go:379` 只改 marker / route、StateVersion 不变。
`entity/entity_factory.go:314` 对新建实体写恢复向量（初始 fence 0、版本 0）。codegen / kit / demo 无直接调用。

未采用：在 `acknowledgeRemoteCommit` 里加锁把“判定 + 写入”做成原子——需要实体锁或新锁，重放路径按 RR-63 约定不持实体锁；setter 的 CAS 已经给出原子比较。

## 兼容性

- 公开 API 签名不变。行为收紧：对同一 fence 写入更小 StateVersion 的调用现在得到 `ErrRemoteVersionConflict`（此前被静默接受）。
  框架内唯一可能走到这一分支的是已提交事务的迟到重放，按过期处理成功返回。自定义代码若依赖“同 fence 下可以把版本写小”，需要改用新 fence。
