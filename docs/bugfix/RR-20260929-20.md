# RR-20260929-20：Mail 取消按预约代次校验

状态：已实施，Memory/真实 Redis、local/bus 回归通过；未发版。[原问题](../bug/REVIEW-2026-09-29-services-03.md#rr-20260929-20) · [本批验证与升级](SERVICE-BUGFIX-2026-09-29-03.md)。

稳定 Token 表示同一奖励，重租约时保持正确；旧 CancelClaim 仅按 Token 清 Deadline，无法区分旧 A 与新 B。

现在 `CancelClaim(ctx, playerID, mailID, token, attempts int32)` 要求正代次，在 Mailbox CAS 内同时匹配 Token 和 ClaimAttempts。旧 A 取消返回 false、不清 B 的 Deadline；当前 B 能取消，重复取消为 no-op。CommitClaim 继续按稳定 Token 确认真实发奖，不把迟到真实确认错误拒绝。ReserveClaim 对负数/MaxInt32 计数拒绝，保留证明，防止代次回绕重用。

更新了正式 Mail 接口、生成的 request/handler/client/capability、split 接入样例与 fake、game claim_mail 模板、已有 RPC/Redis 测试。由 go:generate 生成，未手改 transport。

正式新增回归：旧取消保护新预约，local/bus 传递 Attempts，当前/重复取消，缺 attempts 的旧 JSON 拒绝，稳定 Token 及迟到 Commit，计数异常不修改存储。Memory 和真实 Redis 的原触发通过。

**升级是 Go API 变更**：所有取消调用传 `claim.Attempts`。旧 JSON 缺字段会得到 CodeRequestInvalid，不能降级到 token-only。先更新全部 mail owner 的校验，再升级调用者；过渡期间旧取消会被拒绝，允许租约到期恢复。新客户端连接旧 owner 仍不安全，因为旧 owner 忽略 attempts。已有生成工程的业务 controller 不一定自动重写，需要补同一参数并重新生成/编译。

存量正 ClaimAttempts 继续使用；稳定 Token 不换。负数或耗尽的异常记录应对账处置，不重置一个仍有在途请求的计数。未做真实发奖/网络集群滚动演练；本修复证明租约控制隔离，不宣称外部 exactly-once 发奖。
