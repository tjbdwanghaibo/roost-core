# RR-20261006-23 修复：只有运行中的进程钉住 cast，已停的记录随 cast 一起回收

问题：[RR-20261006-23](../bug/RR-20261006-23.md)。基线 `37338490`，分支 `sktest2`，未发版。与 [RR-20261006-21](RR-20261006-21.md) 同根因、同一批提交。
读代码：codebase-memory 共享 generation 停在 09-30，以当前源码为准；进程记录的删除点与 `castEvictableLocked` 的调用方用 `rg` 穷举（`pruneCompletedCastsLocked` 一处）。

## 根因

`castEvictableLocked`（基线 `skill/runtime_retention.go:75-90`）把 cast 名下任何进程记录都当作引用，而 `runtime.processes` 里的记录在进程停止后从不删除。U-0028 加的守卫本意是“进程还在用这个 cast 时不回收”，判据写成了“有记录”。

## 方案取舍

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| ① 只看运行中的进程，回收 cast 时连它已停的记录一起删（采用） | `castEvictableLocked` 改用 `castHasRunningProcessLocked`；`pruneCompletedCastsLocked` 删 cast 前 `forgetCastProcessesLocked` | 采用。已停记录的寿命与它的 cast 相同，受 `CompletedCastLimit` 约束；移交后仍在运行的进程照旧钉住 cast，进程结束后下一次回收时放行 |
| ② 进程停止时立即删记录 | `stopProcess` 里删 | 未采用：同一提交里 state mutation 只会看到 remove、看不到停止状态；`InspectCast` 期间也读不到它起过的进程 |
| ③ 单独给进程记录一个上限 | 新选项 | 未采用：多一个配置项，cast 仍被钉住，checkpoint 校验仍会失败 |

## 兼容性

API、checkpoint 格式与 wire 不变。行为差异：起过进程的 cast 在进程结束后按 `CompletedCastLimit` 回收，回收时它已停进程的记录一并删除（state mutation 发出对应的 `process_remove`，与 cast 被回收时的 `cast_remove` 同一笔）。旧版本留下的 checkpoint 若已超过上限，本来就恢复不了，修复不改变这一点；未超过的照常恢复，之后按新规则回收。

## 回归（`GOWORK=off`）

- 红（基线实现，文本见问题记录）。
- 绿：`TestCastsWhoseProcessesEndedStayWithinTheCompletedCastLimit`——9 次召唤施法后保留 4 个 cast（上限 3 + 移交后仍在运行的 1 个）、记录不超过 4 条、checkpoint 恢复成功；长进程结束、再完成一次施法后被钉住的 cast 也被回收。
- 守卫能红（变异，不提交）：把 `castEvictableLocked` 的最后一行改成 `return true`（不再看运行中的进程）→ `runtime_process_retention_promises_test.go:63: cast 1 was evicted while its handed-off summon still runs`。原守卫 `TestReferencedCompletedCastsSurviveTheRetentionBound`（U-0028，pending 任务钉住 cast）不变通过。
- 本批（RR-21 / -22 / -23 与 SKILL-1 / SKILL-3 补测）：`gofmt -l skill` 空；`go vet ./skill/...` 通过；`go test -race -count=3 ./skill/...` 5 包通过（skill 包全部用例在 `stateMutationVerifyIncremental` 影子校验下运行）；根包 `go test -count=1 .`（含 `TestExamplesRun`）通过；`go build ./... && go vet ./...` 通过。
