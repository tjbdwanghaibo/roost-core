## 根因（基线 `815ac535` 模板行号）

`demo/internal/service/game/playerowner.go.tmpl`：

- `:482-585` `renew`：`:483` `owners.store.Refresh(ctx, owners.snapshot())`，`:979-987` `snapshot()` 返回 `local` 里的**全部**玩家；default 分支 `:504` `interrupt`（`interrupted=true`）→ `:505` `Claim`。
- `:842-883` `Claim`：`:865` `continuous` 为假 → `:866` `dropResident`；失败时 `:867-875` 只打 Error、不 `confirmClaim`、返回包着 `errStaleCopyKept` 的错误。注释说“nothing refreshes it, and it lapses on its own”——对登录路径（`local` 里本来没有他）成立，对刷新循环**不成立**：`local[playerID]` 还在，只是 `interrupted`。
- 下一轮 `renew`：`snapshot()` 仍含他 → `Refresh`（`CompareAndExpire` 自己的 token，而重新认领刚把自己的 token 放回去）→ `Held` → `:654` `confirmRenewal` → `:676-690` `confirmLocked`：`:682` `validUntil` 延长、`:684` `interrupted=false`。
- `:769-806` `Admit`：`:785` 的 `interrupted` 检查已被清掉、窗口也被延长 → 放行。而此刻副本的清除还在后台跑（或已失败），实体仍常驻——RR-20260920-09“有间断就不能再用内存里那份副本”的契约被续租绕过。RR-20260930-23 之后玩家的连接已被关掉，但重连登录之前任何后台消费者（`Owns` → `Admitted`）都能被放行到 stale 副本上。

## 决策：`Claim` 扔副本失败后忘掉该玩家的本地租约状态（`abandon`）

两种候选：(a) 删掉 `local[playerID]`；(b) 给 `leaseState` 加“待销毁”标记，`snapshot` / `confirmLocked` / `Admit` / `handBackIdle` 各自绕开它。采用 (a)：

- **与已有的结局一致**：登录路径的同一结局本来就是“`local` 里没有他、租约在 Redis 里自己过期”，`Claim` 的注释和 `TestAClaimWhoseCopyCannotBeDroppedIsNotTakenIntoService` / `TestAClaimWaitsAtMostTheBudgetForABusyEntity` 已经把“nothing refreshes it, so it lapses”写成承诺；(a) 让刷新循环的那条路径也落到同一个结局，不新增状态。
- **一个动作覆盖全部出口**：没有本地状态，`snapshot()` 不含他 → `Refresh` 不续 → `confirmRenewal` 不会被调到；`Admit` 以“无状态”拒绝；`handBackIdle` 也不会去碰一个在 `local` 里不存在的玩家（它本来就只遍历 `local`）。(b) 要在四处各加一个分支，漏一处就是同类缺陷。
- **不释放 Redis 里的认领**：清除还在后台跑，这个进程此刻确实还持有一份副本（只是拒绝服务它）；让租约自然过期，和“进程持有着它死掉”一样把下一个 owner 挡在外面同样长。
- **删除有条件**：`abandon` 只在该状态此刻仍会被 `Admit` 拒绝时删（`refusalLocked`，Admit 的判断抽出来、不带 `lastUsed` 副作用）。登录路径的 `Claim` 与刷新循环的 `Claim` 可能并发：两者都加入同一个在途 eviction，若另一次先等到清除完成并 `confirmClaim`，那份租约是在服务中的、副本已经没了，不能被这次迟到的失败删掉。
- **恢复点写明**：只有一个——之后的 `Claim`（重连登录的 `enter_game`，或后台消费者 `Owns` 见无主 / 自己 SID 但本地无确认时的认领）：`continuous` 为假 → `store.Claim`（租约若还没过期返回自己 SID，过期则 SetNX 重取）→ `dropResident` 加入在途的 eviction 或新跑一次（已无常驻副本时是一次找不到东西的空调用）→ 成功才 `confirmClaim`。清除本身完成（`runEviction`）不自动恢复任何东西：没有人在服务这个玩家，租约照旧过期。

未采用 (c)“`confirmLocked` 只在 `used`（认领）时清 `interrupted`，续租不清”：能挡住 `Admit`，但续租仍延长 Redis 里的租约——玩家被钉在这个进程上直到有人重新登录，而这个进程手里是一份不能用的副本；与已写明的“让它过期”相反。

## 未验证项 / 风险

- 只有模板单测（evictor 替身）；没有在真实环境构造“实体被长事务占住 > 5s 且续租恰在此时中断”的演练。
- `abandon` 的条件删除关闭的是“并发的另一次认领已确认”这一种交错；仍有一条更窄的、修前就存在的交错没有回归：登录路径的 `Claim` 因本地窗口耗尽（续租连续 Err、Redis 里键已过期）而 `continuous` 为假，`store.Claim` SetNX 重取后 `dropResident` 超时，而刷新循环恰好在这两步之间 `Refresh` 到刚放回去的 token、`confirmRenewal` 延长了窗口——此时 `abandon` 看到状态可服务而不删。token 按进程固定（RR-20260920-03），`Refresh` 分不出“续的是重取前还是重取后的键”，要关死它需要租约带世代号（RR-20260920-09 当时未采用的方案）。
- `handBackIdle` 的 `dropResident` 超时后 `cancelHandBack` 让租约回到服务、而后台 eviction 仍会把实体销毁（RR-20260920-12 接受的“清除继续”）——与本条同族但不同路径，未改。
