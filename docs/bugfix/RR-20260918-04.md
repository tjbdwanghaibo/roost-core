# RR-20260918-04：副本领取账本清理之后，旧的成功 Run 能再领一次

- 单元：U-0237 · 缺陷类 C4（跨包契约不一致）· 等级 P1
- 仓库：roost-codegen `demo/`（game-demo 模板，作用于生成的工程）
- 排障行：T-131 · 关联 U-0226 / RR-20260917-08（同一条奖励路径的上一轮修复）

## 问题

U-0226 给清关奖励加了 run id 账本，让重放不再重复发奖；账本按时间清理，保留期 4 小时。那条保留期的论证是：

> 重放只能经 `session.Finish` 到达奖励路径，而 run 的存储 TTL（`session.run_ttl`，生成配置里 30 分钟）一到
> Finish 就答 ErrRunMissing，所以保留得比这个 TTL 长就不可能忘早了。

**这句话是错的**，审查第二轮把它打回了。`RedisConfig` 明写只有 Requests 带 TTL，Runs / Claims **没有存储 TTL**；
`run_ttl` 管的是 run 能保持**开启**多久，不是它在存储里活多久。一个 succeeded 的 run 永远是 succeeded，
`Finish` 会一直返回那个终态。于是：

1. Run A 成功，事务记下 A 并发 100 经验。
2. 四小时后玩家领另一个 Run B。`ClaimDungeonRun(B)` 在写入口清掉了 A 的记录，再给 B 发 100。
3. 再发一次 `FinishDungeon(A)`。session 仍答 succeeded，账本里已经没有 A，事务再发 100。

两次合法清关应付 200，实际 300。前置条件不能省：光重放 A 自己不会清掉 A（`claimed` 判断先返回），
要另一次领取来触发清理。

## 根因

一句话：**"记录可以忘了"和"这次领取还能不能通过"是两个不同的判据，而且中间有缝。** 清理用的是账本自己的
保留期，准入用的是"账本里有没有"——没有任何一条规则说"被忘掉的 run 不会再来"。上一轮我用另一个服务的存储
行为去补这条缝，而那个行为根本不存在。

更一般地：**用别的服务忘不忘来给自己的账本收界，是把自己的正确性押在别人的存储策略上。** 就算 session 真的
有 TTL，改一次配置也会静默地把这条链打断。

## 方案选择

- **（选中）给奖励一个自己的截止时间，并让它与保留期是同一个数。** 账本存的值改成 run 的**结算时刻**
  （`run.FinishedAtUnix`，session 服务盖的章），准入与清理共用一个谓词 `dungeon.ClaimWindowClosed(resolvedAt, now)`。
  于是：

  ```
  记录被清掉  ⟺  now - resolvedAt > ClaimWindowSeconds  ⟺  该 run 的领取被拒
  ```

  "被清掉"蕴含"被拒"，与调用到达顺序无关，也不依赖任何别的服务的存储。
- 单纯把 4 小时调大：窗口还是会到，问题原样保留，只是更难复现。审查点名不接受。
- 把 `claimed` 判断挪到清理之前：挡不住"另一次领取先清理、重放后到"的顺序。
- 给 versioned Run 加 TTL：改的是别人的服务，而且把正确性继续押在存储策略上。
- 永不遗忘（持久身份）：只有在业务承诺无限期补领时才需要，那样账本无界，得配一个可证明安全的压缩水位——
  demo 不承诺无限期，所以选有界窗口，并把"承诺无限期就得换这条路"写进注释。

## 改动

roost-codegen `demo/`：

- `game/dungeon/dungeon.go`：`ClaimRetentionSeconds` → `ClaimWindowSeconds`（仍是 4h，含义变了），
  `ClaimExpired(claimedAt, …)` → `ClaimWindowClosed(resolvedAtUnix, nowUnix)`；注释写清旧论证错在哪、
  新不变量为什么成立、时间戳不可证明（≤0）时为什么拒而不是发。
- `game/handler/claim_dungeon.go`：handler 多一个 `resolvedAtUnix` 参数，**在付款的同一个事务里**做准入检查；
  过窗口返回 `ErrDungeonClaimWindow`（新 errcode `dungeon_claim_window` 100012），不是静默的零。
- `game/entities/player/profile_component.go`：`ClaimDungeonRun(runID, resolvedAtUnix, nowUnix)`，
  存结算时刻、按同一谓词清理。
- `game/controllers/player/finish_dungeon.go`：`resolvedAt := run.FinishedAtUnix`（为 0 时退到 `StartedAtUnix`），
  传给事务；不是 `time.Now()`，也不是请求里的任何东西。过窗口时打 Warn 日志（玩家、run、结算时刻）。
- `db/def/player.go`、`demo/README.md`：账本的值与规则重新描述。
- 步骤表 `internal/roost/demo.go` 加两个新文件；`internal/roost/demo_test.go` 的断言跟着改，
  并新增两条（handler 必须调 `ClaimWindowClosed`；端点必须从 `run.FinishedAtUnix` 取锚点）。

**旧数据**：v1.15.10 及以前写下的记录存的是领取时刻，而领取时刻 ≥ 结算时刻，按新读法只会**晚**过期、
不会早过期——没有哪条旧记录会因此重新开始发钱。不需要迁移。

## 证明

随工程生成 `game/handler/claim_dungeon_test.go`（真实 Nest 引擎、真实生成的 Player/World 实体、
记录型 committer，不需要 Mongo）：

- `TestDungeonClearIsPaidOnce`：一次发放、重放不发。
- `TestAPrunedRunIsRefusedInsteadOfPaidAgain`：正是审查复现的那个顺序——领 A、窗口之后领 B（B 的领取清掉 A 的记录，
  测试先断言记录确实没了）、再重放 A。断言重放被拒，且 World 计数器上两次合法清关一共付出 200。

修前红（把生成工程里的准入检查摘掉、账本改回记领取时刻）：

```
--- FAIL: TestAPrunedRunIsRefusedInsteadOfPaidAgain
    claim_dungeon_test.go:137: replaying a run whose record was pruned was accepted; it pays a third time
```

与审查报告的"期望 200、实际 300"是同一件事。另外 `game/dungeon/dungeon_test.go` 把谓词的边界
（等于窗口 / 超一秒 / 0 / 负数）与"窗口必须长于 run 自己的寿命"钉成表测试。

修后：生成工程 `go build ./...`、`go vet ./...` 干净，六个测试包全绿，`project doctor` 31 项 OK / 0 FAIL；
codegen `go vet ./... && go test ./... -count=1` 全绿。

## 未做 / 边界

- **邮件那条账本的论证与这条不同，本轮核对过：成立。** `rewards.ClaimRetentionSeconds`（31 天）依赖的是
  `mail.send_ttl`（720h）——而那是一条**真实存在**的 Redis key TTL（`service/mail/server_run.go` 明写
  "envelopes expire by Redis key ttl"），信封没了就拿不到预留，也就没有发放路径。这和 session 的区别正是
  "论证依赖的那条 TTL 存不存在"。不过它仍然是"押在别的服务的存储策略上"这一类论证，改成与本条同形
  （账本存邮件自己的发送时刻、准入与清理同一谓词）会更结实——这是个契约选择，已写进 `docs/bug/WANTED.md`
  交 review 判，本轮没有顺手改。
- **首次未领取但窗口已过**的玩家会拿到 `dungeon_claim_window` 拒绝 + 一条 Warn 日志，补发是运营口径；
  demo 没有做自动补偿。窗口取 4h 是 demo 的取值，真实游戏要按"客户端断线重连 + 人工重试"的最坏时长定。
- 没有验：重启恢复后的账本读取、并发领取与清理交错、跨进程同时领取同一个 run（Nest 的实体锁串行化了
  同一个 Player，但没有专门的测试）。审查列的验收清单里这几项留着。
- 机器人脚本只覆盖即时重放（`finish_dungeon_replay`）；过窗口的重放需要 4 小时，实跑里没有对应场景。
