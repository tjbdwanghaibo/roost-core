# RR-20260920-05：读不回来的订单不能永久占住重试页（U-0262，C5）

## 问题

`PendingOrders` 每次返回索引里最老的一批（默认 128 个）due id。对不可解码的记录，
`AttemptDelivery` 返回解码错误；`server_run.go` 只有 `ErrOrderInvalid` 分支会退休索引条目，
普通 error 仅记录日志。于是坏成员的 score 原封不动、也不离开索引，下一 tick 枚举到的还是同一批。

128 个 score 更小的坏成员 + 1 个健康成员，就是一个稳定状态：健康的那个**永远进不了**
`AttemptDelivery`。它是一笔已付款、待发货的订单。

## 根因

C5：错误被吞成一条日志，而**这条错误是可判定的终局**——字节解不开的记录会永远以同样的方式
失败。循环把它当普通失败对待（记日志、下一条），于是它每一轮都回到队头。

这和 U-0256（RR-20260919-07）是同一个形状的第二次出现：那次是"索引里的订单不存在"，
这次是"订单存在但读不回来"。两者的正确处置**不同**，这是本条的核心判断。

## 方案选择

| 情形 | 处置 | 为什么 |
| --- | --- | --- |
| 索引条目没有对应订单（U-0256） | **退休**该条目 | 没有任何东西要发货，删掉是安全的 |
| 订单存在但解不开（本条） | **推后**该条目 | 它是一条需要人看的真记录；退休等于把它藏起来 |

- 放弃 **也退休**：那会把一笔可能已付款的订单从唯一的恢复入口里抹掉。
- 放弃 **对所有错误都推后**：一次 Redis 抖动会影响**所有**订单，把健康订单一起推后 15 分钟。
  所以必须能区分"读不回来"和"基础设施出问题"——core 为此加了 `versionstore.ErrMalformedRecord`。
- 放弃 **在 kit 里按错误文本判断**：文本不是契约。

## 改动

- **roost-core v1.15.16**：`versionstore.ErrMalformedRecord`。四条解码失败路径（无分隔符 /
  版本非数字 / 版本为零 / 载荷解不开）都带上它，codec 自己的错误保留为 cause；传输错误不带。
- **roost-core v1.15.17**：`versionstore.IndexDefer` / `IndexDeferIn`——把已有索引条目挪到后面，
  不碰值（值正是读不出来的那个东西）。`ZADD XX` 语义：**defer 一个不存在的条目不会凭空造出来**，
  因为索引是"存在的记录"的视图，defer 一个不存在的条目说明调用方已经和索引分叉了。
- **roost-kit**：`PendingDeferrer` 接口 + `RedisOrders.DeferPending`；`server_run` 在
  `ErrMalformedRecord` 分支推后 `PoisonedRetryDelay`（15 分钟）并记 error 级日志。
  重试循环的一趟抽成 `Service.retryPendingOnce`，这样一趟可以被直接驱动。

15 分钟这个数：长到不再挤占页面，短到部署方修好记录（codec 回滚、人工修复）之后不必重启就能重试。

## 证明

kit `service/platform/poison_pending_promises_test.go`：
`TestAnUndecodableOrderStopsBlockingThePage` —— 128 个更老的坏成员 + 1 个健康成员，跑一趟，
断言健康成员出现在下一页里。索引替身带真实 score 并实现 defer，所以"最老优先"和"推后会生效"
在测试里都有意义。

**变异验证**：把 defer 调用短路掉（`&& false`），立刻红：

```text
after a pass over 128 unreadable orders the page is still
[poison-000000.000 poison-000001.000 poison-000002.000]; the healthy order is never read
```

core 侧：`versionstore/malformed_promises_test.go` 四条解码失败路径 + 一条反面（传输错误不得被
归成 malformed）+ `IndexDefer` 的真 Redis 用例（挪动已有条目、不创建不存在的条目）。

## 未做 / 边界

- **没有"毒药订单"的专门运维面**。被推后的条目仍然在索引里，`PendingOrders` 在 15 分钟后会再看到它，
  日志是 error 级；但没有一个"列出所有反复解码失败的订单"的入口。要做的话应该配一个计数器
  （按 order_id 的连续 malformed 次数）和一条 GM 查询，这需要先定"多少次算毒药"。
- **推后是固定 15 分钟，不是指数退避**。索引条目上没有地方记尝试次数（值读不出来），
  加一个就要在索引之外再存一份状态；固定值够用且可预测。
- 一次 Redis 抖动期间，如果恰好有记录真的解不开，它也会被推后 15 分钟——这是有意的取舍：
  分类依据是错误**类型**而不是当时的环境。
