# RR-20260913-03:Remote payload 的身份未与信封绑定

**仓库 / 位置**:roost-core `remoteentity/syncer.go`,`SnapshotReplicaStore.ApplyReplica`。
**修复单元**:U-0179(C2)。**定位文档**:TROUBLESHOOTING T-73。

## 问题

通用 Replicator 会校验外层 SyncMsg 与 `mirror.Envelope` 的 key / version。但 Remote 自己这第三层
—— `wire.Key`、`wire.Update.Key`、`Update.StateVersion` —— 谁都没有和它们交叉校验过。

审查把一条合法的 scope=1 消息的 payload 里 `Update.Key.Scope` 改成 2,外面两层 key/version 一字
不动,消息照样通过,**实际写进了 scope=2 的缓存并返回 nil**:用于路由和排序的身份,和实际被修改
的视图不是同一个。

## 根因

分层校验各管一层,没有人负责"这三层说的是同一件事"。

## 方案选择

- **让 Replicator 泛化地比较 payload。** 它不认识 Remote 的 wire 结构,做不到。
- **在 Remote 的接收入口交叉校验(采用)**:写入之前要求 key 合法、外层 key 等于按完整 key 算出的
  replica key、payload key 等于 wire key、外层 version 等于 payload 的 StateVersion。delete 分支
  只校验前两条 —— 它的版本语义由删除水位负责(见未做一节)。

这是**协议完整性**,不是授权。谁可以往这个内部 topic 发消息,仍然由传输与服务身份边界决定;
校验 hash 不等于鉴权。

## 改动

`remoteentity/syncer.go`:新增 `validateSnapshotWireIdentity(env, wire)`,`ApplyReplica` 在解码之后
立即调用,任何一项不符就返回错误、不落任何写。

## 证明

`remoteentity/snapshot_payload_identity_promises_test.go`:先断言一条正常消息能应用;再四种畸形 ——
payload key 与 wire key 不符、wire key 与信封 key 不符、payload 版本与信封版本不符、delete 指向
另一个 key —— 每种都必须报错,并且断言**那个外来 scope 的缓存前后没有变化**(只报错却已经写进去
就没有意义)。

修前红:

```text
a message whose payload identity contradicts its envelope was applied
```

修后 remoteentity 含 `-race` 全绿。

## 未做 / 边界

- **delete 分支只校验 key,没有校验版本。** 因为删除本身还缺版本屏障,那是 RR-20260913-01,
  没有修;在那之前给 delete 加版本校验会把一个尚未定义的语义写死。
- Interest payload 的同类约束没有做。审查建议"另审 Interest payload 对应约束",与
  RR-20260913-02 的订阅代际是同一块地方,一起做更合适。
- U-0045 的外层校验没有改动,这里是新增的一层,不重新打开那个单元。
