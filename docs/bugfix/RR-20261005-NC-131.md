# RR-20261005-NC-131：表满时 Stats 先清理过期兴趣，健康检查不再被过期条目钉在 Fail

2026-10-05，基线 `a80be80c`（审查 `173738a0`）。**已修复、声明场景验证，未发版。** [问题](../bug/RR-20261005-NC-131.md) · [本轮](../review/REVIEW-2026-10-05-n05-revn05.md) · [证据](evidence/noncore-bugfix-20261005-n05/README.md)。

## 根因

本机兴趣表的过期条目只在“新建兴趣且表满”或“每 1024 次续租”时清理（`remoteentity/transaction_manager.go:832-855`）；`Manager.Stats` 直接取 map 长度，Remote Mod 健康检查拿它与 `snapshot_interest_keys` 比较。读满之后不再有读取，过期条目永远在，健康永远 Fail。

## 修法

`Manager.Stats`（`remoteentity/assembly.go`）在表已满（`len >= localInterestCapacity`）时先调用既有的 `pruneLocalInterestsLocked` 再计数。清理同时撤销本机注册表里自己的 lease，与续租路径的清理完全相同；不新增状态。只在表满时扫描，平时 Stats 不做全表遍历。锁顺序与续租路径一致（`localInterestMu` → 注册表锁）。

没采用：每次 Stats 全表清理——表未满时健康不受影响，没有必要每次检查都扫 65536 项；后台定时清理——多一个 goroutine 与停机责任，只为一个计数。

## 验证

- 修前红：`Stats().LocalInterests = 4 after every interest expired, want 0` / `health ... = fail (capacity exhausted ...)`。
- 修后：`TestExpiredLocalInterestsDoNotKeepHealthFailing` 通过（含“表满且全部有效时仍 Fail”的对照）；`remoteentity` / `kit/remoteentity` `-race -count=3` 通过。

## 兼容与未验证

健康结论只在表满时变化（过期条目不再计入）；`local_interests` 在表未满时仍可能含少量未清理的过期条目（只出现在 OK 消息里）。owner 侧注册表（`remoteInterestRegistry`）的容量不进健康检查，见审查 O4。
