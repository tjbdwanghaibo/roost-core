# RR-20261006-20 修复：TaskPool 先计提交再入队，读统计先读结束数再读 total

问题：[RR-20261006-20](../bug/RR-20261006-20.md)（N13 O9 后半，维护者决定 NONCORE-46 选 A）。基线 `a3002263`，分支 `tpstat`，未发版。
读代码：改动只在 `goroutine/task_pool.go` 一个文件，codebase-memory 共享 generation 停在 09-30，以当前源码为准直接阅读；调用方用 `rg 'GetStats\(\)|NewTaskPool'` 穷举（仓内无非测试调用方）。

## 根因

计数顺序和读取顺序都没对齐“结束 ⇒ 已提交”：`Submit`（基线 `goroutine/task_pool.go:114-117`）入队后才加 total；`GetStats`（`:154`）先读 total 后读结束数。

## 方案取舍

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| ① 调整顺序（采用） | `Submit` 先 `totalTasks.Add(1)` 再入队，入队被拒（队列满 / 已关闭）时 `Add(-1)` 撤回；`GetStats` 先读 `completedTasks` / `failedTasks`，后读 `totalTasks` | 采用。热路径不加锁：提交多一次失败时才有的原子减，完成路径不变。正确性：任务的 `total+1` 先于入队，入队先于执行，执行先于 `completed/failed+1`；读方先读到某个结束计数、再读 total，读到的每个结束任务的 `total+1` 都已可见（Go 原子操作顺序一致），所以 `completed + failed ≤ total` |
| ② 一把锁包住计数与读取 | 提交、完成、读统计都取同一把 `statsMu` | 未采用。每个任务的提交与完成都去抢同一把锁，只为一个零调用方的统计接口；worker 之间本来互不争用 |
| ③ 只改读顺序或只改写顺序 | — | 不够：两个窗口独立，红测试各钉一个，缺一个就有一条仍红 |

代价：被拒绝的提交在“先加、后撤回”之间会让 total 短暂多算一个。这个方向不破坏 `completed + failed ≤ total`，只是 total 可能瞬时偏大；`GetStats` 注释写明三个计数不是同一时刻的快照，只保证这条关系。

零调用方 API（`TaskPool` 整组）按 C8 决定保留，不删。

## 兼容性

公开 API 不变。行为差异只在统计读数：不再出现结束数大于提交数；被拒绝的提交仍不计入 total（撤回之后）。

## 回归（`GOWORK=off`）

- 红（修前，失败文本见 [bug 记录](../bug/RR-20261006-20.md)“复现”）：`TestTaskPoolStatsCountSubmitBeforeTheTaskCanFinish`（写侧窗口）、`TestTaskPoolStatsReadFinishedBeforeSubmitted`（读侧窗口）都读到 `total 0, completed 1`。
- 绿：
  - `TestTaskPoolStatsCountSubmitBeforeTheTaskCanFinish`：提交 goroutine 停在任务进 channel 之后，任务在 worker 上执行完，另一方读统计——`completed + failed ≤ total`；Submit 返回后为 1 / 1 / 0。
  - `TestTaskPoolStatsReadFinishedBeforeSubmitted`：读方停在读完结束数之后，期间另一 goroutine 提交并等任务执行完——读数仍满足关系。
  - `TestTaskPoolRejectedSubmitIsNotCounted`：队列满被拒的提交撤回计数，两个受理一个拒绝时 total = 2（修前也通过，钉住撤回）。
