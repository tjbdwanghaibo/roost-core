# RR-20260920-04：租约丢了必须停止本地写入（U-0259，C5）

## 问题

RR-20260920-03 把每一次对 Redis 的改动变成了原子操作，但"一名写者"仍然不成立：

- `PlayerOwners.refreshLoop` 把 `Refresh` 的**所有结果和错误都丢掉**，`local` 集合原样不变；
- Player 实体不会卸载，也不会停止接收 handler。

于是网络故障或 GC 暂停超过 30 秒之后，B 进程可以合法地 `Claim` 同一个玩家，而 A 仍然持有
resident Player、按本地实体锁继续写。两份实体各有独立版本视图，终点是 projection conflict
或重复的业务效果。

## 根因

**持有一把租约，和知道自己还持有它，是两件事。** 旧代码只表达了前者：`local` 里有这个 id
就当作"我的"，而那个集合只在 Claim 时增长，从不因为续租失败而收缩。C5（静默吞错）——
`Refresh` 的返回值当时甚至没有返回值可吞。

## 方案选择

- **采用**：`Refresh` 逐 player 返回结果（RR-03 已铺好），本地记 `validUntil = 最近一次被 Redis
  确认的时刻 + Lease`；所有写入路径问 `Admit`，它只在 `validUntil - AdmissionGuard` 之前放行。
  时间驱动而不是 tick 驱动——续租线程卡住时，准入照样会自己走到头。
- **采用**：准入检查放在**访问边界**（生成的 `access.player` Mod 的中间件），而不是逐个 endpoint。
  一个可选 capability（`access.player.write_gate`）没有发布时，整条链路的行为与以前完全一致。
- 放弃 **每个动作查一次 Redis**：一次 RTT 换不来更真的答案（读完的下一微秒它就可能过期），
  却要付在每个请求上。
- 放弃 **只记日志 / 加长 Lease / 重试续租**：都不排除双写，审查已经点名。
- **未采用但更强**：把 owner generation 带进持久化 CAS，或者直接用 remote-managed 的 versioned lock。
  那要改实体与提交路径，见"未做"。

## 改动

- **roost-codegen** `internal/roost/render_access.go`：`access.player` 增加**可选**的
  `WriteGate` capability 与一条中间件。中间件在协议注册之前挂上，所以覆盖每一个 endpoint
  （包括以后新增的）；gate 惰性解析并缓存，因为发布它的服务比这个 Mod 起得晚。
  gate 拿到 `messageID`，是因为只有 gate 的主人知道哪些消息必须在"还没有所有权"时就能跑——
  登录就是取得所有权的那条消息。
- **roost-codegen** `internal/roost/render_player_tcp.go`：`Runtime.CloseSessions(playerID, reason)`。
  走的是网络错误那条关闭路径，所以 scene / chat presence / 所有权清理照常触发。
- **roost-codegen** `demo/internal/service/game/playerowner.go.tmpl`：
  - `leaseState{validUntil, lost}`、`Admit` / `Admitted` / `AdmitMessage`、`AdmissionGuard = 5s`；
  - `renew()` 消费逐 player 结果：**确认**→ 续期；**读不出来**→ 不放弃也不延长（UNKNOWN ≠ 失去），
    准入自己收口；**明确不是我们的**→ 先原子地 `Claim` 一次再决定（见下），失败才 fence；
  - `fence()`：丢掉本地租约 + 关闭该玩家的连接；**不** release Redis 里的键——那把键要么已经是
    别人的（删掉就是删别人的），要么状态未知，让它自然过期才是安全的；
  - `Owns` / `OwnedHere` 先走 `Admitted`，保证后台消费者与端点用的是同一条规则。
- `service.go.tmpl`：把 owners 同时注册到 `accessplayer.WriteGateCapability`，并在 transport 起来后
  `owners.Fence(runtime)`。

### 一个实跑改出来的决定：先重取，再围栏

第一版对"不是我们的"一律 fence。实跑（删掉全部租约键、只有一个进程）发现这会把 16 个玩家全部踢掉，
而当时**根本没有别人接手**——只是我们的续租断了。改成先 `Claim` 一次：SetNX 是原子的，所以
"没人拿着吗"和"那就拿回来"是同一个动作；拿回来就继续服务，拿不到才说明真的易主，这时才 fence。
同样的实跑改后：`retaken=16, fenced=0`。

## 证明

生成工程 `internal/service/game/playerowner_test.go`：

- `TestALostLeaseFencesThePlayer`：租约被别的进程持有 → `Admit` 拒绝 + 连接被关 + **不** release；
- `TestALapsedLeaseNobodyElseTookIsRetakenInsteadOfFenced`：只是过期没人接手 → 重取、不踢人；
- `TestAnUnknownRenewalRunsAdmissionOutInsteadOfPretending`：续租报错时不放弃租约、也不延长期限，
  过了 guard band 之后准入自己拒绝，且**不**断开连接（不确定不等于失去）；
- `TestAdmissionStopsOneGuardBandBeforeTheDeadline`：边界两侧各断言一次；
- `TestASidMatchWithoutAConfirmedLeaseIsNotOwnership`：Redis 里 sid 对得上但本进程没有确认过的租约
  （前一次化身留下的），不算所有权；
- `TestTheWriteGateExemptsLoginAndRefusesEverythingElse`：登录放行，其余按 `Admit`。

**变异验证**：把 `renew` 改回"跑一次 Refresh、忽略全部结果"（旧行为），
`TestALostLeaseFencesThePlayer` 立刻变红。

**实跑**：单进程 16 机器人在线时删掉全部租约键 → 日志 `lease had lapsed and was retaken` 16 次、
`fenced` 0 次；两个进程各跑两轮机器人场景 → `success=2 failure=0`，两边 `fenced` 都是 0（不误伤）。

## 未做 / 边界

- **租约"提前消失"不在保护范围内**。这套保证的前提是：一把租约只会因为**到期**而结束。
  实跑里我手工 `DEL` 掉在线玩家的租约键，B 立刻合法 Claim 并开始写，而 A 要到下一次续租
  （最多一个 `RefreshInterval`）才知道——当场复现了 `fatal projection version conflict`。
  这不是本修复的漏洞，而是它的**前提被破坏**（Redis 丢键 / 被 flush / 被人为删除）。
  真正能扛住这一类的是"owner generation 进入持久化 CAS"，即上面未采用的更强方案。
- **在途事务**只靠 `AdmissionGuard = 5s` 保护：准入在确认期限前 5 秒停止，所以耗时短于 5 秒的事务
  不会跨过截止时刻。比这更慢的事务不在保护范围内。
- **实体仍然不会卸载**。被 fence 的玩家只是不再被服务；它的 Player 对象还在内存里，直到进程结束。
- 关闭连接的那一步在实跑里没有直接观测到（机器人在下一次续租之前就自己跑完退出了），
  由单测断言覆盖。
