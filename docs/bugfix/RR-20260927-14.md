# RR-20260927-14 修复：卸载后重载积压指标与真实最坏延迟

问题：[RR-20260927-14](../bug/RR-20260927-14.md)（OPEN-ITEMS C14）。日期 2026-09-27；基线 `d4234c9`；worktree 分支 `fix-r7-ent`（叠在 RR-20260927-13 之后）。
codebase-memory 图谱停在 09-26，已过期，未使用；以源码为准。

## 真实上界（按 `entity/unload_resync.go` `resync` 循环推出）

- 每个实体最多 `Attempts` 次 `reloadOnce`，每次是一次共享冷加载（`ManagerAccess.Get`，受 `T_load` = 框架加载上限约束，默认 `DefaultEntityLoadTimeout` 30s）；
  第 k 次失败（k < Attempts）后退避 `min(RetryMin·2^(k-1), RetryMax)`。
  `T_entity = Attempts × T_load + Σ_{k=1}^{Attempts-1} min(RetryMin·2^(k-1), RetryMax)`。
- `jobs` 按实体去重，风暴中最多 `QueueCapacity` 个排队（超出立即 remove）加 `Workers` 个处理中；FIFO 下最后一个被接纳的实体最迟在
  `ceil((QueueCapacity+Workers)/Workers) × T_entity` 后得出结论（重载成功或 remove）。
- 默认值：退避和 `0.1+0.2+0.4+0.8 = 1.5s`，`T_entity = 5×30s + 1.5s = 151.5s`，上界 `1025 × 151.5s ≈ 43.1 小时`（与 audit2 的估计一致）；
  加载快速失败时 `1025 × 1.5s ≈ 25.6 分钟`——bf-59 的“分钟级”只对这种情形成立。
- 假设与另计：风暴后没有新的卸载（处理中再被卸载的实体会再排一轮）；发布经 `RunLocal` 回快池的排队等待不在 `T_load` 内。
- 收紧示例（配置键见 RR-20260927-13）：`workers 8, attempts 3, queue_capacity 256, entity_load_timeout 5s` → `T_entity = 15.3s`，`33 × 15.3s ≈ 8.4 分钟`。

## 决策

- 默认值不变（清单推荐）。
- **指标**：gauge `entity.unload_resync.backlog` = `len(jobs)`（排队、处理中与“再来一轮”），无标签（一个服务一个 `ManagerAccess`，一条序列），在 `jobs` 变化的三处
  （登记、处理结束、停止）于 `r.mu` 内更新；停止时 `clear(jobs)` 并归零——被丢弃的排队不会再重载，不应继续显示为积压。处理中的 worker 结束时照常 `delete`
  （空操作）。只加积压 gauge，没有把累计计数也转成指标（它们已有 `UnloadResyncStats`，清单只要求积压）。
- **Stats**：`UnloadResyncStats.Backlog`（此刻值，非累计），在 `r.mu` 下读 `len(jobs)`，与 gauge 一致，便于测试与自建装配。
- entity 首次 import `metrics`（core 层内依赖，`metrics` 只依赖标准库；`dependency_boundary_test` 通过）。
