# RR-20261006-12 修复：派发取锁只用 Guard 作用域里的 Guard，取锁与重试不再归还 Guard

问题：[RR-20261006-12](../bug/RR-20261006-12.md)（来源 [WANTED W-2026-10-06-01](../bug/WANTED.md)）。基线 `87d8d91e`，分支 `fixn`，未发版。
读代码：codebase-memory 共享 generation 停在 09-30，本修复涉及的 `nest/group_lock.go`、`nest/nest_dispatch.go`、`nest/group_transition.go`、`entity/entity_guard.go` 以当前源码为准直接阅读，调用方用 `rg` 穷举（含测试）。

## 根因

`releaseDispatchLocks`（基线 `nest/nest_dispatch.go:480`）把两件事混在一起：有作用域时“放本次取得的实体锁”，没有作用域时“把整个 Guard 归还池”。`lockDispatchEntitiesForHandlerWithStore`（基线 `nest/group_lock.go:235`）的组迁移重试在两轮之间调用一次释放、下一轮继续用同一个 Guard，于是无作用域时 Guard 在仍被使用时就进了池，最后再被调用方归还一次。

## 两种修法的取舍

| 修法 | 做法 | 结论 |
| --- | --- | --- |
| ① 调用方持有并归还，重试不归还 | `releaseDispatchLocks` 只放 `acquired`；无作用域时由取得 Guard 的调用方（`dispatchLoadedEntities` / `groupTransitionDispatch`）结束时 `EntityGuardRelease` | 未采用。Guard 上挂的不只是本次取得的实体锁：handler 里新建实体的锁、被同 ID 新实例取代的旧实例（superseded）、解锁后回调、撤销新建的收尾，都只能由完整的 Guard 释放收尾。无作用域时调用方等于要自己再写一遍作用域；而且 handler 里 `CurrentGuardScope()` 为 nil，`Cast` 返回 `ErrCastNoContext`、`ReleaseCast` 不生效，与快池派发的语义不一致。保留这条分支只是给一个不存在的生产调用方留了一条更难用对的路 |
| ② 禁止无作用域调用（采用） | 派发取锁只用当前 goroutine 作用域里的 Guard；没有作用域、或传入的 Guard 不是作用域的那一个，取锁前返回 `errDispatchWithoutGuardScope`，不取任何锁；释放只放本次取得的实体锁，Guard 只由作用域结束时归还一次 | 采用。Guard 的所有权只有一种：作用域。生产入口全在作用域里（证明见下），检查只把已有前提变成入口处的显式条件；删掉了归还 Guard 的分支，取锁代码再也碰不到池 |

报错而不是 panic：入口本来就返回 error，调用方（只有测试会走到）拿到可 `errors.Is` 的明确错误；`runNestLogic` 的 recover 也会把 panic 变成错误，panic 没有额外收益。错误未导出——这是 nest 内部函数的前置条件，不是业务可以处理的情况。

## 生产路径都有作用域（按当前源码穷举）

- `dispatchScopeGuard` 的调用方：`dispatchLoadedEntities`、`groupTransitionDispatch`、`lockDispatchEntitiesForHandlerWithStore`（检查传入的 Guard）。
- `dispatchLoadedEntities` ← `singleDispatch`、`dispatchMany`（← `multiDispatch` / `multiGroupDispatch`）；这些与 `groupTransitionDispatch` 的非测试调用方只有 `runNestLogic` 的 `switch`（`nest/nest_dispatch.go:219-230`），而 `runNestLogic` 在 `switch` 之前 `entity.NewGuardScope("nest:"+msg.Name)`（`:204`）。
- `runNestLogic` 的调用方：快池派发（`nest/nest_dispatch.go:187`）与快续行（`nest/remote_dispatch.go:62`）。
- `broadcastDispatch` 每个目标自建作用域、直接 `scope.Guard().RequireEntity`，不经这几个函数。
- 改后 nest 非测试代码里不再有 `entity.EntityGuardRelease` 调用；`entity.GetEntityGuard()` 只剩 `cast.go`（先检查了 `CurrentGuardScope() != nil`）。

## 兼容性

只改 nest 未导出函数。生产行为不变（入口全在作用域里）。直接调用 nest 内部派发函数而不建作用域的测试会拿到 `errDispatchWithoutGuardScope`，需要像 `runNestLogic` 一样先 `entity.WithGuardScope`。

## 回归（`GOWORK=off`）

- 红（修前，失败文本见 [bug 记录](../bug/RR-20261006-12.md)“复现”）：`TestDispatchLockingWithoutGuardScopeNeverReturnsCallerGuardToPool` 报 Guard 被归还 2 次；`TestDispatchEntriesRequireGuardScope` 报无作用域的 `singleDispatch` 成功执行。
- 绿：
  - `TestDispatchLockingWithoutGuardScopeNeverReturnsCallerGuardToPool`：无作用域 + 组迁移重试形状（A2 用例形状，锁组 0 → 9105 由 Mutex 钩子在第一次 Lock 后改，确定触发）——取锁返回 `errDispatchWithoutGuardScope`，归还次数 0，实体锁与组作用域都没留下；调用方自己归还一次后计数为 1。
  - `TestDispatchLockingGroupRetryInScopeKeepsGuardUntilScopeEnds`：作用域里同样触发重试——重试进入新锁组（9106），`releaseLocks` 只放实体锁、Guard 不归还，作用域结束时归还正好 1 次。修前也通过（作用域路径本来正确），钉住重试路径不碰 Guard。
  - `TestDispatchEntriesRequireGuardScope`：无作用域的 `singleDispatch`、`groupTransitionDispatch` 返回 `errDispatchWithoutGuardScope`，handler 不执行、实体锁不残留；同样的调用放进作用域照常执行。

- `go run ./cmd/glsvet ./nest ./entity ./dataengine/engine ./sync/entitysync` 与 `go run ./cmd/glsvet -tests ./nest`：无输出，退出 0。
