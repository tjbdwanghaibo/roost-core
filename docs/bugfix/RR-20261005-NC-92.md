# NC-92 修复：被 JetStream 请求流截获的轻量 RPC 不再执行，调用方得到可识别错误

[问题](../bug/RR-20261005-NC-92.md) · [证据](evidence/noncore-bugfix-20261005-n03/README.md) · [本轮](../review/REVIEW-2026-10-05-noncore-n03.md)。已修复、声明场景验证（含真实 NATS），未发版。

## 根因

JetStream RPC 的请求流收 `<prefix>.rpc.>`（`bus/jetstream_rpc.go:131`），覆盖轻量 RPC 的主题。轻量 core request 被流存下：broker 用 PubAck 回 reply inbox，调用方当 RPC 响应解码失败（`bus/rpc_error.go:49-51`）；JetStream 消费者随后把这条没有 `DeadlineAt` / `ReplySubject` 的轻量信封交给 handler，无期限执行、回包静默跳过（`bus/jetstream_rpc.go:389, 466-467, 479-481`）。

## 修法

- 服务端：`onJetStreamRPCRequest` 解码后拒绝没有 `ReplySubject` 的请求——`callJetStreamRPC` 总会设置它，缺失只可能是被截获的轻量调用；告警、计 `no_reply_subject`，返回 nil（ACK，不重投、不执行）。
- 调用端：`decodeRPCResponse` / `decodeRPCResponseBytes` 在解码失败或版本不符时识别 JetStream PubAck（总是 JSON，与 Bus codec 无关），返回 `bus.ErrRPCCapturedByJetStream`（含流名与序号）。真正的坏信封仍报原来的版本错误。
- README §14 ④ 补一句：目标在 JetStream 模式时轻量调用会被截获，两端 `nats.rpc.transport` 必须一致。

未采用：让请求流避开轻量主题（改 JetStream 主题布局）——要改流的 subjects 与 consumer filter，已有部署的流需迁移；本条只消除“报错却执行”。也没有在调用端自动改走 `CallReliable`：静默换传输会改变调用语义（至少一次 vs 至多一次）。

## 兼容与边界

- 新导出 `bus.ErrRPCCapturedByJetStream`；新请求指标结果 `no_reply_subject`。
- 旧版本服务端仍会执行被截获的请求；错误文本据此写成“新版服务端拒绝执行，旧版可能稍后执行”。滚动升级期间不要依赖这条错误判断“未执行”。
- 两端都轻量、都 JetStream 的既有往返不变（`TestJetStreamRPC*`、`TestRPCBudget*`、`TestDecodeRPCResponseRefusesEveryMalformedEnvelope` 通过）。

## 验证

- 修前红（包内，先只加哨兵变量）：`business ran 1 times for a request no caller can receive the answer of`；`lightweight call answered by a JetStream PubAck = bus: unsupported rpc response version 0, want ErrRPCCapturedByJetStream`（同步与异步各一）。
- 修前红（真实 NATS，实现回基线、保留哨兵）：`Call = bus: unsupported rpc response version 0`、`CallTo = ...`、`captured lightweight requests: handler runs=2 ack_pending=0, want 0 / 0`。
- 修后绿：包内两例；真实 NATS 两种调用都得到 `ErrRPCCapturedByJetStream (stream RR_NC92_REQ_..., seq N)`，服务端告警拒绝，handler runs=0，两个 consumer ack_pending=0。
- `GOWORK=off go test -race -count=3 ./bus/ ./kit/nats/ ./servicerpc/` 通过。
- 未验证：第三方直接向 `<prefix>.rpc.>` 发布无 reply 的 JetStream 消息的用法（仓内没有）现在会被拒绝。
