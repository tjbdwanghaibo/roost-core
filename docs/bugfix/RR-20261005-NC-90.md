# NC-90 修复：Bus 停止把在途 JetStream RPC handler 纳入排空，回包不随 Bus 停止取消

[问题](../bug/RR-20261005-NC-90.md) · [证据](evidence/noncore-bugfix-20261005-n03/README.md) · [本轮](../review/REVIEW-2026-10-05-noncore-n03.md)。已修复、声明场景验证（含真实 NATS），未发版。

## 根因

1. JetStream RPC handler 在 nats.go consume 回调 goroutine 里同步执行（`nats/driver/jetstream.go:74-77`），不在 Bus pool 里；基线 `stopResources`（`bus/bus.go:412-427`）只排空 pool，对 JetStream 订阅调用 `Stop()` 后就返回。nats.go 的 `ConsumeContext.Stop` 不等在途回调，`Closed()` 在订阅失效后立即关闭，都不能用来等。
2. 回包用 `processCtx` 发布（`bus/jetstream_rpc.go:452`），而 `processCtx` 派生自 Bus 运行期 context，停止第一步就取消（`bus/bus.go:345-348`）。在停止预算内完成的 handler 也必然丢回包。

## 修法

- `jetStreamRPC` 增加请求 handler 自己的准入与在途计数（`beginHandler` / `endHandler` / `closeHandlerAdmission`），`onJetStreamRPCRequest` 入口先取得准入；停止关准入后到达的投递返回 `errJetStreamRPCStopping`（driver NAK，交给同服务其他实例），不进入业务。
- 停止顺序（`stopResources` 注释）：先关 JetStream 请求准入并停请求消费者 → 退订 core 订阅 → 排空 pool → 等 JetStream 在途 handler 归零 → 停响应消费者并关闭 pending。等待超预算返回 ctx 错误、保留责任；`awaitStop` 重试时依次再等 pool 与 JetStream handler，之后才停响应消费者、置终态。NatsMod 不用改：它已经在 Bus 返回 ctx 错误时保留 bus / asm。
- 回包改由 `publishJetStreamRPCReply` 发布：预算是调用方期限（请求没带期限时为 AckWait），与 Bus 生命周期脱钩。
- handler 因 Bus 停止被取消而返回错误时（`processCtx.Err()` 是 `Canceled`，期限到达是 `DeadlineExceeded`），不回“已取消”的失败包，返回错误让 broker 重投——保持修前对这类请求的重投行为（修前是回包发布失败“碰巧”导致 NAK）。
- 响应消费者推迟到排空之后再停：排空中的 handler 发起的嵌套 `CallReliable` 还能收到回答。修前 pool 超预算保留时响应消费者已经停了。

未采用：

- 把 JetStream handler 投进 pool、以 pool 为唯一排空点——会改变 JetStream 消费的顺序与背压语义（池满要 NAK），超出本条范围；在方向判断里作为候选。
- 停止时不取消 handler 的 ctx——会让不看期限的 handler 拖住停机，与轻量路径“停止取消业务 ctx”的既有语义不一致。
- 用 nats.go 的 `ConsumeContext.Closed()` 等待——如上，订阅失效后它立即关闭，不能证明回调已退出。

## 兼容与边界

- `Bus.StopWithContext` / `Stop` 现在会等在途 JetStream handler：不看 ctx 的 handler 会让停止返回 ctx 错误（由 NatsMod 保留并可重试），而不是假装完成。handler 内用无界 ctx 停自己的 Bus 会等待自身，与 pool handler 的既有限制相同（已写进注释）。
- 新增请求指标结果 `interrupted`（低基数）。
- 订阅缓冲里尚未回调的消息仍在 AckWait 后重投；投递次数已到 MaxDeliver 时被停止中断的请求会被 Term，与修前相同。
- Start 失败的清理（`detachLocked`）同样会关掉 JetStream 请求准入；修前它已停掉全部 JetStream 订阅，失败后重试 Start 也不会重建它们，本条没有改变这一点。

## 验证

- 修前红（`bus`，`GOWORK=off go test -count=1 -run 'TestJetStreamStop|TestJetStreamDeliveryAfterStop' ./bus/`）：

  ```
  stop with a JetStream handler still running = <nil>, want the budget's ctx error
  handler that finished within the stop returned bus: publish jetstream rpc response roost.rpc_resp.2001.req-slow: context canceled: the delivery is NAKed and redelivered
  the response of a handler that finished within the stop was never published
  a delivery that arrived after the stop was acknowledged
  business ran 1 times for a delivery after the stop
  ```

  `TestJetStreamStopHandsInterruptedRequestBackToBroker` 修前修后都通过（行为保持的控制）。
- 修前红（真实 NATS，实现文件 `git stash` 回基线，`-tags integration -run TestRealJetStreamStopWaitsForInFlightHandler ./kit/nats/`）：`budgeted stop with the handler in flight: err=<nil> bus_retained=false asm_retained=false`。
- 修后绿：上面三条包内用例；真实 NATS `budgeted stop ... err=context deadline exceeded bus_retained=true asm_retained=true` → `retry stop ... err=<nil> asm_retained=false` → 调用方拿到回包，`request consumer: delivered=1 ack_floor=1 ack_pending=0 redelivered=0 runs=1`。
- `GOWORK=off go test -race -count=3 ./bus/ ./kit/nats/ ./nats/... ./servicerpc/` 通过；组合验证见本轮记录的验证节。
- 未验证：多节点 NATS 集群节点故障时的停止；长时间停机重试。
