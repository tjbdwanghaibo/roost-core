# NC-100：Redis 驱动在回复丢失后自动重放 Lua 脚本，versionstore.Update 一次调用把 mutate 写两次并返回成功

2026-10-05，基线 `be7bcc18`（含 NC-52 修复）。**P1**（数据损坏：同一个 mutate 被静默应用两次，调用方拿到成功）。状态：**已复现（真实 Redis + toxiproxy、包内 RESP 替身），未修复**。[本轮](../review/REVIEW-2026-10-05-n04-revn04.md) · [证据](../bugfix/evidence/noncore-bugfix-20261005-revn04/)。

## 触发、预期与实际

- 触发：`RedisStore.Update` 的 compare-and-set 脚本已在 Redis 执行，回复在网络上丢失且连接断开（EOF / 部分回复），或无 ctx 截止时读超时（`ReadTimeout` 3s）。驱动 `fredis.DefaultConfig` 的 `MaxRetries: 3`（`redis/config.go:30`）经 `redis/driver/client.go` 原样交给 go-redis。
- 预期：一次 Update 至多写一次；回复丢失是结果未知，原样交给调用方。
- 实际：go-redis `processWithRetry` 对 `io.EOF` / `ErrUnexpectedEOF` / 带超时标记的读超时 `shouldRetry` 为真（go-redis v9.22.0 `error.go:84-119`、`redis.go:1214`），**换连接重发同一条 EVAL**。脚本第二次执行时 `GET` 读到的是本次 Update 刚写入的信封，`current ~= ARGV[1]`，返回 `{0, current}`；`versionstore/redis_store.go:367-381` 把它当作“输给了别人”，退避、重读（读到的是自己的写）、再次调用 mutate 并 CAS 成功，返回 v3。

```text
# 真实 Redis 8.10.1（隔离 17379）+ 本用例自建 toxiproxy 代理（limit_data 1 字节，downstream）
lost_reply_integration_test.go:154: one Update wrote its mutation 2 times: stored [hello msg-1 msg-1] / v3
  (update returned [hello msg-1 msg-1] / v3 applied=true err=<nil>, mutate ran 2 times)

# 包内 RESP 替身（第一次 EVAL 计数后断开不回复），生产构造 NewRedisClient、MaxRetries 3
script_no_retry_promises_test.go:153: one eval call executed the script 2 times on the server (reply=1 err=<nil>); want exactly once
script_no_retry_promises_test.go:153: one evalsha call executed the script 2 times on the server (reply=1 err=<nil>); want exactly once
```

对照：同一真实 Redis 用例把 `MaxRetries` 设为 -1 时，Update 返回 `EOF`、Redis 中 `[hello msg-1] / v2`——一次写入，结果未知被正确交还（探针已删，结论写入正式回归）。

## 根因

`redis/driver/client.go:325-331`（基线）`Eval` / `EvalSha` 直接用 `c.rdb.Eval(...)`，没有关闭驱动对该命令的自动重放；`EvalBatchDurable` 的 pipeline 同样可被整体重发（`redis.go:1628-1660`，`cmdsContainNoRetry` 为假）。框架自己的设计已经写明不应重放结果不确定的写：集群恢复 hook “不重放结果不确定的写命令”（`redis/driver/cluster_recovery.go:12-14`），App 单实例锁的 Redis 客户端专门设 `MaxRetries = -1`（`kit/redis/singleton.go:39-41,71`），但 RedisMod 的主客户端（所有 Service、cache、remoteentity 共用）没有。

与 NC-52 无因果：修 NC-52 之前 `raw = result.Current` 同样是自己刚写的信封，结果相同。

## 影响

- `versionstore.RedisStore.Update`：chat / account / activity / mail / session / platform / directory / match / global 的全部写都经过它。带请求 ID 去重环的写（chat `RequestID`、rank 的 request ring 等）第二次 mutate 会识别出自己，影响被吸收；不带幂等键的 mutate（计数累加、无 RequestID 的追加、rank `requestID==""` 的累加提交）会静默重复。
- 其他走 `IRedis.Eval` 的脚本（cache RefHMap、rank swap、remoteentity marker / snapshot L2 / versioned lock）在同一触发下也会被重放；它们各自对“丢回复”的处理（例如 RR-20261004-01 的 token 认领）是按“调用方看到错误”设计的，驱动重放绕过了这层设计。本轮只对 versionstore 做了行为复现，其他脚本的重放后果未逐一证明。
- 触发需要“脚本执行后、回复到达前”断连或 3s 读超时；网络抖动、Redis 主从切换、代理重启都可能出现，频率低但后果是静默数据错误，故定 P1。

## 验收覆盖点

一次 Eval / EvalSha（含 EvalBatchDurable）至多执行一次；回复丢失时返回错误；普通读写命令保留驱动重试；versionstore 在真实 Redis 上回复丢失时 Redis 中至多一次写入、调用方拿到错误。没做：Redis Cluster 下 MOVED/ASK 与 NoRetry 的组合（本机无 Cluster）；go-redis 对非脚本写命令（`RPush` / `SetNX` / `Incr`）的同类重放见本轮运行记录观察项。
