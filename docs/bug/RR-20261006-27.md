# RR-20261006-27：loadtest 的分位数是桶上界，两个 sid 时 p95 报 16.384s、全部成功仍退出码 1；失败说明不点名阈值

2026-10-06，基线 main `0db819b0`。P3（门禁误判：生成工程的 loadtest 既是压测也是 demo 的回归测试，两个 game 同机跑时机器人全部成功、退出码却是 1；门禁的实际值比任何一个样本都大，阈值失去意义）。来源：[真实进程演练](../bugfix/REAL-PROCESS-DRILLS-2026-10-06.md)第 1 项的“观察”（10-05 与 10-06 两次演练都出现，当时没有处理）。状态：已复现；已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261006-27.md)。

## 触发与差异

10-06 演练步骤 6a：sid 1000 / 1001 各 10 个机器人同时跑。机器人 C 的原始输出（`rpd2/logs/loadtest-C.log`）：

```
robot loadtest: run done … state=failed stop_reason=threshold started=10 success=10 failure=0 canceled=0 elapsed=9.635844208s
  "thresholds": [ {"metric": "error_rate", "max": 0, "actual": 0, "violated": false},
                  {"metric": "p95", "max": 16, "actual": 16.384, "violated": true} ],
  "quantiles_ms": { "p50": 9557, "p90": 15018, "p95": 16384, "p99": 16384 }
loadtest: run robot-demo-20261006-222401-001 ended failed (threshold)
```

整次运行 9.636s 结束，10 个机器人的场景耗时都不超过它，p90 / p95 / p99 却是 15.0 / 16.4 / 16.4s。

1. **p95 为什么落在 16.384s：统计口径的估计错误，不是真实延迟，也不是排队时间。** 场景耗时从 `runner.runOnce` 开始计（`robot/runner/runner.go:407`，建机器人上下文、连接、登录、整个场景），不含等待开窗或排队，都落在运行窗口内。错在估计：`metrics` 直方图的桶从 1ms 起翻倍（`metrics/metrics.go:27`，17 个桶，最大上界 65.536s），`histogram.quantile`（`metrics/metrics.go:102-126`）在命中的桶里按 `[下界, 上界]` 线性插值。排名落在某桶的最后一个样本时，估计就是桶的上界；10 个样本时 p95 的排名是 `int(0.95×10+0.5)=10`，即“最慢样本所在桶的上界”。两个 sid 时最慢的机器人超过 8.192s，落进 `(8.192s, 16.384s]`，p95 = 16.384s，最多是真实值的两倍。另一头，排名落进溢出（> 65.536s）时返回最大桶上界 65.536s，比每个溢出样本都小——阈值大于 65.536s 时更慢的运行会被判通过。
2. **rc=1 怎么判出来的：阈值判定本身按设计执行（`actual > max` 即违反，`robot/loadtest/manager.go:563`），但输入的 actual 是错的。** 缺省 `-max-p95 16` 的说明写着“健康运行落在 8s 桶，所以上限取下一个桶”——下一个桶的上界是 16.384，比 16 大，这个“取下一个桶”的意图本身就不成立：只要最慢的机器人超过 8.192s，判定必然失败。
3. **输出没说清。** 退出前最后一行只有 `ended failed (threshold)`，不说哪条阈值、实际值多少、按多少样本算；要翻上面的 JSON，而 JSON 里的 16.384 也看不出只是桶上界。
