## RR-20260915-01 · P2 · 满容量替换受 delta 操作顺序影响而被拒

状态：未修复。位置：`statesync/delta.go:167`、`:203` 在每次对象/组件操作后检查存量上限；生成顺序来自 `diffObjects:29`、`diffComponents:63` 的有序合并。

触发：MaxObjects=1，旧快照只有 ID=2，新快照只有 ID=1；双方经 NewSnapshot 校验均合法。BuildDelta 先 Create(1) 再 Remove(2)，EncodeFrame/DecodeFrame 均接受。ApplyDelta 在第一步暂存两个对象时立即 ErrObjectLimit，没有机会执行删除。组件同理：MaxComponentsPerObject=1，从 TypeID=2 换到 TypeID=1，先 Set 后 Remove，ErrComponentLimit。

期望：合法前后快照经框架 BuildDelta → EncodeFrame → DecodeFrame → ApplyDelta 应能还原目标，替换成功与 ID 大小无关。实际两个较小 ID 替换失败；改为 ID/TypeID=3（先删后加）均成功。组件 schema 变化和同 Ref 的 archetype 变化两个对照也成功。测试只需串行，不涉及网络失败或旧 RR 的触发。

影响：对象容量已满时兴趣集进出、组件容量已满时投影替换，可能生成客户端无法应用的合法增量；是否失败取决于标识排序。全量恢复可能绕开，但本轮未证明具体客户端会自动恢复。不是所有增删都失败。

建议（未实施）：区分最终存量上限和单帧操作/临时资源上限。可预计算并验证最终集合后应用，或在保证协议语义的前提下规范删除先行；不能简单取消所有边界检查，也不能只修对象层而遗漏组件层。对于外部输入的重复键和冲突操作，应明确拒绝/覆盖契约，避免无条件重排序改变含义。

证据：六个独立叶子，两失败四通过，0.523s；完整编解码回环，均使用相同 Limits。[复现](REPRO-2026-09-15.md) · [运行](../review/REVIEW-2026-09-15.md)。
