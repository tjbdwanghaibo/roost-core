# RR-20260930-17：生成工程的 CI 只跑 `docker compose config --quiet`，“语法合法、语义错”的部署物抓不到

日期：2026-09-30。基线：main `4784ef82`。来源：[REMAINING-2026-09-28](../review/REMAINING-2026-09-28.md) §3 N24，维护者 2026-09-30 拍板“加结构检查（不在 CI 里 `compose up`）：对 `docker compose config` 的输出断言关键字段，写成生成工程自带的脚本或 go test”；原始观察在 [RR-20260927-33 修复记录 §未验证项 / 风险](../bugfix/RR-20260927-33.md)。
等级 **P3**：生成工程的门禁缺口。RR-20260927-33 那种 tmpfs 按逗号拆成四条挂载的错误在每个消费者的 CI 里都是绿的，直到 `compose up`。状态：已修复（本地提交，未推送 / 未发版），见 [修复记录](../bugfix/RR-20260930-17.md)。

图谱说明：codebase-memory 图谱 `Users-whb-roost-roost-core` 状态 ready，索引的是主检出路径，行号与结论以当前源码为准。

## 触发条件 / 预期 / 实际

生成器把生产 compose 的某个值写成语法合法但语义错的形状（历史实例：`render_cicd.go` 的 `tmpfs: [/tmp:rw,noexec,nosuid,size=64m]`，YAML flow 序列按逗号分成四项）。

预期：生成工程的 CI 红。

实际：生成的 `.github/workflows/ci.yml`（`render.go` `renderCI`，基线 `:996`）与 `Makefile` `compose-check`（`:864`）只跑 `docker compose config --quiet`，四项都是合法字符串，通过；`docker compose up` 才报 `invalid mount path: 'noexec' mount path must be absolute`。生成器自己的回归（`compose_tmpfs_promises_test.go`）按 YAML 结构断言，但那只在生成器仓库跑，消费者工程里没有对应门禁。

修前的“红”是对新检查的要求（本条是补门禁，不是改行为）：把模板里 tmpfs 那段临时改坏时，新检查要在生成工程里红。基线 `4784ef82` + 新生成器，`render_cicd.go:455` 临时改回 `tmpfs: [/tmp:rw,noexec,nosuid,size=64m]` 后重新生成 game-demo，在生成工程里执行：

```text
$ ROOST_COMPOSE_CHECK=1 GOWORK=off go test -count=1 ./deploy/docker/
--- FAIL: TestProductionComposeResolvesToTheShapeTheDeploymentReliesOn (0.18s)
    --- FAIL: TestProductionComposeResolvesToTheShapeTheDeploymentReliesOn/global (0.00s)
        compose_check_test.go:86: tmpfs resolved to 4 mounts ["/tmp:rw" "noexec" "nosuid" "size=64m"], want exactly one (an unquoted flow sequence splits at the commas, RR-20260927-33)
    …（game / gate 等全部 10 个 Service 同样一条）
FAIL
FAIL	example.com/planet/deploy/docker	0.663s
```

还原模板后同一检查绿（见修复记录）。生成器仓库里的 `TestGeneratedComposeShapeCheckCatchesTheTmpfsShapeComposeUpRefuses` 把这一红一绿固定下来（用 docker 真跑生成出来的检查）。

## 根因（基线行号）

- `codegen/internal/roost/render.go:996`（CI）与 `:864`（Makefile `compose-check`）：只有 `docker compose config --quiet`。它只校验语法与变量插值，不看解析出来的结构。
- `docker compose config` 本身能把结构暴露出来（RR-33 记录里就是用它看到四条 `- /tmp:rw`、`- noexec`…），只是没有人对它的输出断言。

## 修复约束（维护者拍板）

1. 生成工程的 CI 里加一步，对 `docker compose config` 的输出断言关键字段；至少覆盖 RR-20260927-33 修的 tmpfs，以及该记录里点名的其他语义项（`security_opt`、`cap_drop`、`healthcheck.test`、config bind、命名卷）。
2. 断言写成生成工程自带的脚本或 go test，让模板错误在生成工程 CI 里红；不在 CI 里 `compose up`。
3. 不给生成工程引入新依赖（标准库即可），本地没有 docker 的开发者 `go test ./...` 不被挡住。
