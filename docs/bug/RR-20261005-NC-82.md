# NC-82：RateLimiter 全局 key 表可被单个已认证主体占满，满表后每次陌生 key 都在全局锁内全表扫描

2026-10-05，基线 `50e9a4e8`。P3（`gateway.RateLimit` / `security.RateLimiter` 是公开库 API，仓内正式链路与生成工程当前**没有**装配它们）。状态：已复现，**未修复，需维护者选择语义**。[本轮](../review/REVIEW-2026-10-05-noncore-n02.md) · [证据](../bugfix/evidence/noncore-bugfix-20261005-n02/observation-gateway-ratelimit.txt)。

## 触发与影响

`gateway.RateLimit`（`gateway/middleware.go:38`）以 `{PlayerID, MessageID}` 为 key，MessageID 是客户端可控的 uint32，在协议注册表拒绝未知 ID 之前就进入限流器。`RateLimiter.AllowN`（`security/ratelimit.go:105`）的 key 表全局共享、`MaxKeys` 默认 100000；表满时新 key 一律拒绝（`:132`），并且每次拒绝前都在全局互斥锁内做一次完整 idle 扫描（`:126`）。

- 一个已认证玩家依次发送 1000 个不同 MessageID（`MaxKeys=1000`）后，另一个从未超速的玩家首个请求得到 `ErrRateLimited`，`Stats={Keys:1000 CapacityRejected:1}`。表项 IdleTTL（默认 10 分钟）内持续拒绝所有新玩家/新动作。
- 满表后每个陌生 key 的成本（本机 Apple M 系、`-benchtime 200x`）：MaxKeys=1000 约 20µs/次，100000 约 0.52ms/次，且持锁，其他所有 Allow 调用排在它后面。约 2000 次/秒的陌生 key 即可让限流器串行饱和。

现注释只承诺“key 基数不能无界增长内存”，这一条成立；但限流中间件的用途（按玩家限速）被一个主体变成了对全体的拒绝，且拒绝路径本身成为放大器。

## 为什么未修

修法需要业务语义选择，不应由 review 擅定：

1. 每个 OwnerID 的 key 上限（例如默认 64/256，超出只拒绝该主体自己的新动作）：需要额外计数状态与默认值，影响合法的大量动作 ID 场景；
2. 中间件只按 PlayerID 限流、或要求调用方先校验 MessageID 再进限流（改变 key 语义/装配顺序）；
3. 满表拒绝路径的紧急扫描限频（例如每 SweepInterval 至多一次）：消除 O(N) 放大，但刚过期的 key 最多晚一个间隔才能腾出空位。

建议 1+3：3 无争议、可单独先做；1 需维护者定默认值。仓内无使用方，排期不急，接入前必须先定。
