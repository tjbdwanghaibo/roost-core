# NC-130：共享 L2 以 CAS 拒绝更旧的快照后，本机 L1 仍装下它，读取停在比 L2 更旧的版本

2026-10-05，基线 `a80be80c`。**P3**（读取陈旧，最长一个 L1 TTL，默认 30s；不改权威数据，写入仍经 Mongo 校验）。状态：已复现，未修复。[本轮](../review/REVIEW-2026-10-05-n05-revn05.md) · [证据](../review/evidence/noncore-review-20261005-n05/README.md)。

## 触发与差异

某节点对 key 的 L1 是冷的，这时有一份比共享 L2 更旧的快照要写进来：

- 迟到的复制消息（owner 已把 v2 写进 L2，v1 的消息才到）；迁移接管后旧 owner 的消息晚于新 owner 写入 L2；JetStream 游标落后或新 sid 重放历史；
- 权威加载读到 v1 的同时 owner 提交了 v2 并写进 L2；
- 重启后的 outbox 恢复重新发布一笔旧提交。

预期：`RemoteSnapshotCache.Publish` 自己的约定（`entity/remote_snapshot.go:472-480`）——“输给更新的快照是预期结果，存下的值至少和这一份一样新”；`cache.Store` 约定被判 stale 的 Set 返回 `ErrStaleWrite`（`cache/store.go:12-22`，RR-20261004-NC-15）。

实际：`remoteSnapshotL2Store.Set`（`remoteentity/snapshot_l2.go:196-198`）CAS 落败时返回 nil；`cache.ReadThroughStore.Set`（`cache/read_through.go:235-258`）先写 L2、再无条件写 L1，于是 L1 装下 v1 而 L2 是 v2。之后该节点 Cached 与 Monotonic（minVersion ≤ v1）读取都命中 L1 返回 v1，直到 L1 TTL 或下一条更新消息；迁移场景下读到旧 route epoch，`nest/remote_access.go` 对带新 RouteEpoch 的必需访问报 `ErrRemoteSnapshotIdentity`。权威加载路径更直接：读取返回 v1，L2 早已是 v2。

## 复现

`remoteentity/snapshot_l2_stale_backfill_promises_test.go`（共用一个 Redis 替身，CAS 规则与脚本逐条一致）：

```
consistency 2 read version=1 route=1 payload="v1" after a late replica; L2 holds version=2 route=1 — L1 was pinned below the shared layer
consistency 2 read version=5 route=1 payload="v1" after a late replica; L2 holds version=6 route=2 — L1 was pinned below the shared layer
monotonic read returned version=1 payload="v1"; L2 already held version 2
older write = <nil>, want cache.ErrStaleWrite (cache.Store contract)
```

对照（修复前即通过）：L2 断网时迟到消息照常降级装进 L1；同一份快照重复发布被接受。

## 影响

只影响读取：节点在 L1 TTL 内交出比共享层旧的快照；权威写入不受影响。迁移后的必需远程访问在这段时间内失败。

## 验收覆盖点

- L2 CAS 落败（更新版本 / 更新 epoch）时 L1 不装旧值，读取交出 L2 的版本；权威加载输给 L2 时返回 L2 的较新快照。
- `remoteSnapshotL2Store.Set` 对被拒的旧写返回 `cache.ErrStaleWrite`，L2 内容不变。
- L2 不可达仍降级为只写 L1；同版本重复发布照常；之后更新的消息照常生效。

本轮没做：Redis Cluster 上的脚本、真实多节点时序。
