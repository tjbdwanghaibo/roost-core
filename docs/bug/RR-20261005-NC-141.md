# NC-141：Tick 期间取消 / 改期一个同样到期的定时器，它仍按旧期限触发

2026-10-05，基线 `23f82dbccfd5171373470ab942f33177ed4f4eed`。P2（潜伏：仓内唯一调用方 World 的 handler 不取消、不改期别的定时器；定级低是因为没有触发路径，不是因为后果轻——被取消的业务定时器照样执行）。状态：已复现、已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261005-NC-141.md)。[本轮](../review/REVIEW-2026-10-05-n11.md)。

## 触发与差异

`timer/scheduler.go:131`（RemoveTimer）、`:154`（ChangeTimer）在 `s.running` 时一律把操作推迟到 Tick 结束并立即返回 true。若目标是“本次 Tick 也到期、还在堆里”的定时器：

- RemoveTimer：目标照样在本次 Tick 被弹出触发，推迟的删除之后找不到节点；
- ChangeTimer：目标先按旧期限触发（一次性定时器随即被删），推迟的改期找不到节点，新期限也丢了；持久化钩子先收到 Delete，最终状态里没有这个定时器。

两个调用都返回 true。预期：返回 true 之后它不再按旧期限触发；改期后按新期限触发一次。

同文件 `TestDeferredOperationsDuringTickKeepTheirMeaning` 四个邻近分支（取消自己、同 handler 新建再取消、Tick 内新建不在本次触发、改自己的期限）在基线上通过，是修复的不变量。[证据](../bugfix/evidence/noncore-bugfix-20261005-revn11/red-nc141-nc147-timer.txt)。

## 约束

只改“目标仍在堆里”的情形：取消立即出堆；改期立即出堆、推迟到 Tick 结束再按新期限入堆（不在本次 Tick 触发，避免两个 handler 互相改期形成循环）。目标不在堆里（正在触发的自己、本 Tick 新建尚未入堆）保持推迟语义。
