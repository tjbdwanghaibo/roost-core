# RR-20260926-67：handler 内先 Destroy 再新建同 ID，新实例在未加锁状态下发布

日期：2026-09-27。基线：本地 main `7706419`（RR-48～63 合并后，未推送）。来源：第二轮修复后独立审计。等级 P3（修前即有）。状态：已复现，未修复。
（最终状态见文末修复节：**已修复，随 v1.17.1 发布**，详见[修复记录](../bugfix/RR-20260926-67.md)。上面的“状态”是登记时的原值，保留不改。——2026-09-27 回写，OPEN-ITEMS A13②）

`entity/entity_manager.go:268` Destroy 在 handler 中途 ReleaseLock；新实例拿到新 mutex，`entity/entity_guard.go:251` 见 eMap 仍记旧实例直接返回“已持有”。复现：[REPRO-2026-09-26-06](REPRO-2026-09-26-06.md) §3：strict 与 memory 均 `sameMutex=false freshLockableByOtherGoroutineMidHandler=true`。

修复约束：Guard 以实例（而非仅 ID）判断是否已持有；同 ID 新实例在 handler 内按 RR-48 规则取锁并纳入提交边界；Destroy 后同 ID 重建的回滚语义保持。

## 修复（2026-09-27）

状态：**已修复，未发布**（本地提交，未推送）。按修复约束实现：`EntityGuard` 以实例判断是否已持有（同一实例，或同 ID 且共用已持有的 mutex）；
同 ID 换了锁的新实例不算已持有、按锁序只 try-lock（新锁无人持有即成功），取得后新实例进 `eMap`，旧实例及其仍被持有的锁移入 `superseded`、
Guard 释放时一并解锁；锁序检查与 Cast / 派发的“已持有则跳过加锁”改按实例（新导出 `GuardedEntity`）。新实例经 `CreateInScope` 纳入提交边界，
回滚时撤销发布，旧实例的销毁不回滚（与修前相同）。修前红：§3 P-D 改写的回归 strict / memory 均“新实例 handler 中途可被其他 goroutine 加锁”；
新增的 Destroy 后别处重建再 Cast 用例修前拿到未加锁的新实例。详见[修复记录](../bugfix/RR-20260926-67.md)。
