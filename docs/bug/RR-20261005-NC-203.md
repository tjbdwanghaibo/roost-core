# RR-20261005-NC-203：remote-acceptance.lock 只有持锁者自己看，其他入口在别人持锁时照常注入故障、停节点，reset 连锁一起删

日期 2026-10-05。基线 main `8597046c`。等级 **P3**。状态：已复现，未修复；已修复、声明场景验证，未发版（见文末）。来源：N15（接力清单线索）。

## 触发与实际

`scripts/test-remote-matrix.sh:6-8` 与 `scripts/perf/remote.sh:11-13` 用 `mkdir $ROOST_DATAENGINE_IT_ROOT/remote-acceptance.lock` 互斥（REMOTE-ACCEPTANCE §“共用测试集群的容量和故障测试必须串行”）。但同一环境上会改动服务的其他入口都不看这把锁。临时根上放一个锁目录后：

```
dataengine-env.sh fault nats-all   exit=0
dataengine-env.sh down             exit=0
scripts/remote-fault.sh nats-all   exit=0
dataengine-env.sh reset            exit=0  [roost-it] removing …/roost-dataengine-it
RESULT: lock dir (and root) REMOVED by reset while held
```

（[脚本](../review/evidence/noncore-review-20261005-n15/lock_red.sh) · [输出](../review/evidence/noncore-review-20261005-n15/nc203-red.txt)。没有任何节点进程，只验证入口是否拒绝。）矩阵或 C01 运行期间，另一会话执行这些命令（或 `up` / `heal` 把矩阵故意停掉的主节点拉起、`/reset` 掉矩阵注入的毒、`test` 跑整套故障用例）都会让验收结果失真，`reset` 还会删掉对方的数据和锁本身。

## 根因

锁是持锁者单方面的约定：`kit/scripts/integration/dataengine-env.sh` 的 up / down / reset / test / fault / heal 与 `scripts/remote-fault.sh` 都没有检查它，持锁者也没有办法让自己的子进程（矩阵调用的 heal、remote-fault）通过检查。

## 影响与定级

验收 / 长稳结果失真或环境被删；不影响生产。定 P3。

## 验收

锁被别人持有时，会改动环境的入口以 2 拒绝并说明；持锁者（矩阵、remote.sh）及其子进程照常执行；status 只读不受限；`test` 自己运行期间也持有该锁。

## 修复（2026-10-05）

已修复、声明场景验证，未发版。[修复记录](../bugfix/RR-20261005-NC-203.md)。以上原始现象与修前红保留不改。
