# RR-20261006-01：Remote 实体删除已提交到权威，确认却报“身份不符”，删除的发布（L2 墓碑 + 推送）整段被跳过

日期：2026-10-06。基线：v1.21.0 之后的 `7d837dab`。来源：[Mirror 第 6 步本机替代](../feature/MIRROR-STEP-6-LOCAL-2026-10-06.md) S4 场景（私有依赖进程上的两进程样例）。等级 **P2**。状态：**已修复、声明场景验证，未发版**（[修复记录](../bugfix/RR-20261006-01.md)）。

## 现象

生成工程 `testdata/remoteflow` 的 Managed `Guild`，在它自己的 strict handler 里 `access.Destroy(ctx, guild, DestroyReasonCommon, true)`（删除随事务走 `deferEntityDelete`，正式的 Remote 删除路径）：

- 调用方拿到 `nest: finish remote write batch: remote entity persistence outcome is indeterminate: Guild: remote acknowledgement identity mismatch`；
- Mongo 里公会的数据文档与 `_remote_entity_snapshots` 文档已删除（删除确实提交了）；
- 共享 L2 里仍是删除前的 v3（没有墓碑），只读方（`RemoteMirrorMod`，陈旧上限 3s）在删除 8 秒后仍读到 v3：陈旧上限到期时重新确认只会从 L2 读回 v3，直到 L2 TTL（缺省 5 分钟）过期才回源 Mongo 得到“不存在”。同进程别的 Manager 缓存同理。

探针原文（私有环境，`scripts/mirror-local.sh` 起的进程，修前）：

```text
PROBE delete: [DELETEERR ... nest: finish remote write batch: remote entity persistence outcome is indeterminate: Guild: remote acknowledgement identity mismatch]
PROBE reader after 8s: [3]
PROBE ...:remote_entity:snapshot:0:238:4611686018525734841:1447779876:0: "... version\n3 ..."
PROBE mongo:            （两个集合都已空）
```

## 根因

- 删除随事务走 `deferEntityDelete`：准入之后实例就从内存删掉，实体管理器清空它（`EntityBase.doClear`，`entity/entity_base.go`，ID 归零）。strict / pipelined 的 Remote 提交与确认在投影器里稍后才到。
- `remoteentity.Manager.acknowledgeRemoteCommit`（`remoteentity/transaction_manager.go`）从登记（`remoteEntityWrapper.attachedEntity()`）拿实例，登记里还挂着这个被清空的实例（`detachEntity` 只在持久拒绝的重载路径调用），把删除提交交给它的 `AcknowledgeRemoteCommit`。
- 生成代码按身份核对（`codegen/internal/entity/gen.go` 模板：`commit.EntityID != e.GUId()` → `remote acknowledgement identity mismatch`），返回错误。
- `afterRemoteCommit` 在确认处返回，`publishCommitted`（L1 / L2 带版本删除 + 推送删除）不执行；投影器 / 批次把事务记为结果未知，`MarkRemoteCommitPublished` 也不执行。

包内既有用例的 `testRemoteEntity.AcknowledgeRemoteCommit` 不核对身份，所以 `TestRemoteWriteBatchUsesExplicitDeleteIntentBeforeEntityRemoval` 等删除用例没有暴露它；生成工程此前没有成功删除 Remote 实体的端到端用例。

## 影响

- 删除 Managed Remote 实体（strict，实测；pipelined 带 Remote 批次时走同一 strict 路径，未单独实测）的调用方拿到“结果未知”，而权威已删除；按“结果未知不得当作未提交”的契约，业务只能去查询。
- B2 的防复活前提（共享 L2 墓碑）在这条路径上从未建立：L2 TTL 内所有读者（Mirror 只读方、别的 Manager）都会把已删除的实体当作存在。
- 确认到达时实例还没被清空（身份相符）的路径不受影响；Durability 0（`ApplyRemoteCommits` 在批次 Commit 里同步确认）与清空的先后本轮没有在生成链路上核对，单元回归按“先清空再确认”的顺序覆盖。

## 修复约束

确认只负责推进内存实例；实例已不是这个实体（被同一事务删除后清空，或被回收）时没有可推进的内存状态，应视为确认完成、照常发布，并把它从登记上摘掉。不改生成代码的身份核对（它防的是把别的实体的回执用到自己身上），不改提交 / 发布 / 回执的顺序与格式。
