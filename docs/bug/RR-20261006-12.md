# RR-20261006-12：nest 派发取锁在没有 Guard 作用域时把调用方的 Guard 放回池，组迁移重试使同一 Guard 两次归还

2026-10-06，基线 `87d8d91e`。P3（按当前源码生产不可达：派发入口都在 `runNestLogic` 的作用域里；一旦有无作用域调用方碰上组迁移重试，会污染全进程的 Guard 池，症状出现在别的请求上）。来源：[WANTED W-2026-10-06-01](WANTED.md)（收尾第 4 批 A2 查 `-shuffle` 失败时发现，[A2 证据](../bugfix/CLOSING-BATCH-4-2026-10-06.md) §A2）。维护者 2026-10-06 要求交 review 前不留 WANTED（roost-bugfix §7），转 RR。状态：已复现；已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261006-12.md)。

## 机制

- `nest/nest_dispatch.go:480`（基线）`releaseDispatchLocks`：`entity.CurrentGuardScope() == nil` 时调用 `entity.EntityGuardRelease(guard)`——释放 Guard 上的全部实体锁、跑解锁后回调、`clean()` 并 `guardPool.Put(guard)`；有作用域时只放本次取得的实体。
- `nest/group_lock.go:235`（基线）`lockDispatchEntitiesForHandlerWithStore`：取锁后校验锁组快照，锁组在取锁期间变了就 `releaseLocks()` 再 `continue`，下一轮**仍用同一个 `guard`**。
- 没有作用域时：第一次 `releaseLocks()` 已把 Guard 放回池，重试又用它取锁，成功后调用方 `releaseLocks()` 再放一次——`sync.Pool` 里同一个指针两份。之后两个 `NewGuardScope` 可能取到同一个 Guard，两个快 worker 互相解对方的实体锁（`unlock of unowned mutex`）。
- `groupTransitionDispatch`（`nest/group_transition.go:154`）同样用 `entity.GetEntityGuard()` + `releaseDispatchLocks`，无作用域时也会把 Guard 整个归还。

“释放本次取得的实体锁”与“归还 Guard”混在同一个函数里，所有权不清：Guard 是调用方（或作用域）的，取锁代码却会归还它。

## 触发 / 预期 / 实际

- 触发：当前 goroutine 没有 Guard 作用域，`guard := entity.GetEntityGuard()` 后调用 `lockDispatchEntitiesForHandler`，第一次取锁后实体的锁组变了（0 → 9105）。
- 预期：取锁代码不归还调用方的 Guard；Guard 只由它的所有者归还一次。
- 实际：调用内部归还一次（重试前），调用方 `releaseLocks()` 再归还一次，共两次。

## 复现

修前红（`GOWORK=off go test ./nest -run 'TestDispatchLocking|TestDispatchEntriesRequireGuardScope' -count=1 -v`，`nest/dispatch_guard_scope_promises_test.go`；锁组在第一次 `Lock` 成功后由测试 Mutex 钩子改掉，确定触发重试，不靠 sleep）：


计数方式：Guard 每被归还池一次（`EntityGuardRelease` → `releaseEntities`），挂在它上面的解锁后回调就跑一次，归还时清空；测试在调用前、调用方释放前各挂一个回调。

历史复现（A2）：基线上把 `nest/group_lock_test.go` 换回 `8a292a5a` 版本，`-test.run '^(TestLockDispatchEntitiesForHandlerRetriesEpochChangeWhileWaiting|TestSymmetricCrossCreatePairsResolveWithinRequeueBudget)$' -test.shuffle=1` 约 4/5 失败。

## 生产可达性

按基线源码不可达：`lockDispatchEntitiesForHandlerWithStore` / `releaseDispatchLocks` 的生产调用方只有 `dispatchLoadedEntities`（← `singleDispatch` / `dispatchMany` ← `runNestLogic`）与 `groupTransitionDispatch`（← `runNestLogic`）；`runNestLogic`（`nest/nest_dispatch.go:204`）在分派前 `entity.NewGuardScope`，快池派发与 `remote_dispatch.go` 的快续行都经它。可达的只有直接调用内部函数的测试（A2）。修复把这个前提变成取锁入口的显式检查，见修复记录。
