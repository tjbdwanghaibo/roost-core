## RR-20260917-08 — P1：FinishDungeon 重放及非成功终态仍发奖励

**状态：未修复；新增 demo 功能问题。** Codegen `demo/game/controllers/player/finish_dungeon.go.tmpl:32`、`:49`、`:56`；Core `service/session/service.go:541`、`:556`。

处理器注释假定已结束的 run 会返回 ErrRunTerminal，因此调用成功就代表本次首次结算。实际 Session.finish 对已有终态执行 releasePending 并返回原 run，没有错误。这是 Session 的幂等完成/资源释放语义。处理器随后只看请求中的 Success，不检查返回状态，也没有把 RunID 作为奖励事务的去重键。

触发：同一玩家对同一 run 重复发送 Success=true；或先失败，再发送成功；或 run 过期后重试两次成功请求。期望仅权威成功 run 获得一次奖励；实际分别发出两次奖励命令、对 failed 发一次、对 expired 发一次。后两者响应同时包含 `State:failed/expired` 和 `ExpGranted:100`。正常成功及错误 owner 两个对照通过。

证据：实际 CLI 生成的 Controller、实际 Core Session 内存存储和实际生成的 AddExp sender；仅 Nest.Client.RequestMulti 被记录型替身替代。5 个独立叶子，2 通过、3 失败。它证明重复奖励命令被派发，未运行真实 Nest 存储或线上 TCP。源码中的调用参数仅有实体、World 和经验值，没有 RunID 去重身份。按此模板接入游戏会允许玩家反复触发经验及升级链，因此优先 P1；不是声称线上已遭利用。

实施方向：

1. 以返回的权威 run.State 判断可奖励条件，业务胜负还需由服务端验证。
2. 在 Player/World 奖励事务内，以 RunID（必要时包含奖励类型/版本）原子记录领取结果并发奖；重复请求返回原结果。
3. 保留 Session.Finish 的幂等释放语义，支持“完成已持久化、奖励未提交”后的补偿重试。控制器先查再写或只返回首次完成标记不能同时解决并发重复与崩溃漏奖。
4. 回归覆盖顺序/并发重复、failed/expired/cancelled、错误 owner、奖励提交后响应丢失、完成后奖励前崩溃。

## RR-20260917-05 — P2：嵌套 DAO 的第二层变更不通知父级

**状态：未修复；Wanted-02 转入。** Codegen `internal/dao/template_nested.go`；当前 golden `internal/dao/testdata/golden/gen_equip_info_nested.go:102`、`:165` 和 `gen_gem_info_nested.go:104`。

EquipInfo 的 gems map 在 SetGems、setGemsRawMap/BSON 恢复时没有把 GemInfo.SetNotify 接到父级 Mark。业务通过 GetGems 取得现有 child 后 SetLevel，child 变更了，但父级未标脏，DAO 顶层无法通过该链捕获持久化 patch。

使用当前 golden 生成物，分别构造 raw 恢复、公开 setter、BSON round-trip 三种入口；变更 child 后父级通知均为 0（期望 1）。直接修改父对象的对照通知为 1。4 叶子中 1 过、3 失败。这里独立验证的是两层 map 引用及通知，不把结果冒充真实 Mongo 提交/回滚端到端测试。

U-0224 的 BSON 表示修复有效：原三项运行时测试均通过；本项是另一个 dirty 传播契约缺口，不否定原修复。实施应统一绑定 setter、解码和恢复入口；继续检查 nested struct、slice、map 的递归链，以及替换/删除时解除旧 child 通知与同一 child 被多父级共享的所有权。最终用真实生成 DAO 验证变更进入事务 patch、提交恢复、回滚及同步标脏。

## RR-20260917-06 — P2：attribute Feature 没有提供可使用的运行时契约

**状态：未修复；Wanted-03 转入。** Codegen `internal/attribute/gen.go:17`、`:169`、`:177`，`internal/roost/render.go:138` 附近 attribute 脚手架；参考 `docs/CODEGEN_REFERENCE.zh-CN.md` §11。

生成物使用本包的 AttrID、AttrValue、AttributeMeta、AttributeProfile、Snapshot、Container、Selector；脚手架仅产生 `package attribute`。参考文档说明“所在包需提供”，但没有给 feature 消费者一份可直接实现/导入的权威契约。空 feature 本身可编译，真正写 profile 并生成后才暴露断口。

复现已手动提供 `dirtyMask uint64`，排除草稿遗漏该字段的干扰；实际 attribute CLI 成功，生成包编译失败，报 undefined AttrID/AttributeMeta/AttributeProfile 等。这里确认的是 feature 交付不完整，不把有意要求应用提供类型的独立生成器一概判错，也不声称穷尽查明三仓不存在任何同名类型。

建议先定义框架公共属性运行时和接口，倾向放 Core；Codegen 负责项目 profile、公式和类型访问器，Kit 只装配。尤其不能仅为 Snapshot/Container 加跨包 type alias：现有生成器会给这两个类型生成方法，Go 不允许给外包类型别名定义新方法。需要改为本地 wrapper 或生成包级访问函数，并把 dirtyMask 约定显式化。验收至少覆盖真实脚手架、一个/多个 profile、公式、快照、选择器与生成后编译运行。

## RR-20260917-07 — P2：默认 Saga Assembly 没有接收原生 Nest 完成效果

**状态：未修复；Wanted-04 转入。** Core `saga/assembly.go:106` 附近 Start 订阅，`saga/nest.go` NewCompletionEffect；关联 `saga/jetstream.go`、`saga/nest_starts.go`。

原生 Nest 步骤用 NewCompletionEffect 产生 `saga.result.<id>`，经 Data Engine outbox 的效果前缀成为 `ROOST_EFFECTS / roost.effect.saga.result.<id>`。Assembly.Start 实际只注册普通完成 `ROOST_SAGA / roost.saga.result.>` 和 Nest 启动 `ROOST_EFFECTS / roost.effect.saga.start`，原生完成不匹配任何默认消费者。

测试实际调用 Assemble/Start，以 mongotest 与记录订阅配置的 JetStream 替身核对由真实 NewCompletionEffect 导出的主题。普通完成、启动两个对照通过，原生完成失败；3 叶子 2 过、1 失败。**未搭建真实 broker，也未执行 inbox→outbox→Engine 完整投递**；缺订阅为直接证据，等待/重试不收敛是该接线缺口的后果推断。用户手工补消费者可绕过，不扩大为所有 Saga 都不能完成。新增 gift demo 使用 SubscribeMongoStep，不属于此原生路径。

复用现有完成解析与 Engine.Complete 管道，为 effect stream/prefix 增加明确持久消费者；配置、启动失败清理、健康检查、Drain/Stop 均纳入 Assembly 的资源所有权。补真实 outbox 发布、结果重复、重启重放、坏消息、启动部分失败测试。不要改全局 effect prefix，也不要在 Nest 事务外另发一次非原子的完成消息替代 outbox。

## RR-20260917-09 — P3：battle demo 的启动宽限期没有触发开帧

**状态：未修复；范围仅新增 demo 适配。** Codegen `demo/internal/service/game/battle.go.tmpl:56` 的宽限期约定，以及 `:220`、`:229`、`:235`。

注释约定等待首次输入、最多宽限 2 秒后开始；实现只有收到 command 才把 started 设为 true，ticker 在 false 时始终跳过。battleStartGrace 仅参与最终超时计算，没有独立事件开启帧序列。无人输入时会一直不开帧，最终超时退出。

实际生成的 battleManager.run + Core lockstep.Room：等待 grace+200ms，无输入 NextFrame 仍为 1（0 帧）；有效输入对照推进了 45 帧。2 叶子 1 过、1 失败。读取状态前等待 run 完全退出；传输适配未接 TCP，输入对照发送报错，因此只证明开帧状态机，不证明客户端收帧。

落实独立宽限计时器并开启 started，或明确改为必须输入才开帧并同步协议/注释；建议保留已声明的超时开局语义。另明确绝对最长生命周期与 idle timeout 是否不同，验证无人输入、延迟输入和停止期间 timer 清理。该问题不等于 Core lockstep.Room 有相同缺陷。
