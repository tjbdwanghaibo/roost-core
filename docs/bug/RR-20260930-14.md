# RR-20260930-14：广播 handler 里 Destroy 后同 ID 重建，`broadcastDispatch` 按 ID 释放，一把锁跨后续广播目标持有

日期：2026-09-30。基线：`4784ef82`。来源：REMAINING §3 N28（RR-20260927-26 §未验证项），维护者 2026-09-30 拍板“做”。等级 **P3**：广播目标之间锁边界不干净——Destroy 后同 ID 重建时旧实例（已销毁）的锁持有到整轮广播结束，等它的访问者（按 Cast 顺序 Touch 后等锁）被拖到广播结束才能看到“已销毁”；不丢数据、不死锁（广播自身不等这把锁）。状态：已复现；2026-09-30 已修复，未发版，见文末“修复”。

## 触发

1. 广播消息（`DispatchBroadcast`）目标 `[X, Y, …]`。
2. X 的 handler 里 `Destroy(X)` 再 `Create` 同 ID 的 X（新实例、新锁；旧实例被广播自己 `Touch` 着，ID 不清零）。
3. 目标 X 的 handler 结束，广播继续执行 Y 及之后的目标。

## 预期

一个目标结束时它取得的全部锁（声明实例、Destroy 后重建的新实例、Cast 取得的实体）都已释放；后续目标执行期间别的 goroutine 能锁到旧 X（看到已销毁退出）与新 X。

## 实际

`broadcastDispatch` 整轮共用 runNestLogic 的 Guard，目标结束按 ID `ReleaseEntity(e.GUId())`：eMap 里 X 当前登记的是新实例，于是放掉新实例的锁，`restoreSuperseded` 把旧实例放回 eMap，旧锁持有到整轮广播结束（`defer entity.EntityGuardRelease(guard)` 在作用域内是空操作，实际由 runNestLogic 的作用域结束释放）。回归 `nest/broadcast_release_per_target_promises_test.go` 在基线上（memory / state_strict 两个子用例相同）：

## 根因

`nest/nest_dispatch.go:483-484`（基线）`guard := entity.GetEntityGuard(); defer entity.EntityGuardRelease(guard)`——广播在 runNestLogic 的 `nest:<name>` 作用域内运行，取到的是这把跨全部目标的 Guard；`:537` 目标结束 `guard.ReleaseEntity(e.GUId())` 按 ID 释放，`entity/entity_guard.go` `ReleaseEntity` 释放的是 ID 当前登记的实例并把 superseded 的旧实例放回 eMap（RR-20260926-67 的形状）。只把这一处改成按实例释放（`ReleaseEntityInstance`）会变成新实例的锁留到整轮结束——两种都有一把锁跨后续目标持有，根因是广播目标之间没有自己的锁边界。

## 修复约束

1. 每个广播目标在自己的 Guard 作用域里取锁、执行、释放：目标结束释放它取得的全部锁与 post-release 回调，与单目标派发的边界一致；目标自身的实例按实例释放。
2. 不改广播“每目标一个事务、锁内提交、无提前释放”的语义；不支持 Remote 批次的规则（`ErrRemoteBroadcastUnsupported`）不变。
3. 回归：Destroy 后同 ID 重建，下一个目标 handler 里旧 X 与新 X 都可被别的 goroutine 锁到，广播后新 X 是已发布实例、两把锁空闲；补 Remote 实体 `ReleaseCast` 的回归（RR-20260927-26 §未验证项）。
