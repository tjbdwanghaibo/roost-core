## RR-20260914-02 · P2 · 开活动与 sweep 交错丢失窗口索引

状态：未修复。位置：Kit `service/global/activity/service.go:212`（先 admitToWindow）、`:224`（Create）、`:572`（不存在就 prune）、`:675`（按 key 删除）。

触发顺序：

1. OpenActivity 将 key 加入 Windows，尚未调用 Activities.Create。
2. AdvanceExpired 读到这个 key，Activities.Get 返回不存在，于是从窗口删除。
3. Create 成功，OpenActivity 正常返回；第一个 game 的 NotifyPhase 使活动进入 collecting。
4. 宽限期过去，后续 sweep 因窗口里没有 key，不再访问该活动。

预期：成功打开并收到首个通知的活动，在其余 game 沉默时仍能按宽限期完成。实际：`status=collecting window=[]`，扫描返回无工作；没有自动恢复入口被本轮流程触发。玩家可能持续等待跨服聚合结果，必须依赖额外通知或人工恢复。

证据：`TestReviewOpenSweepInterleave` 用 Store.Create 包装器在实际创建前同步执行一次真实 AdvanceExpired；这是两个独立操作可出现的合法顺序，未伪造 Store 返回、未改业务函数。正常开活动/到期对照通过。单 key CAS 保证窗口自己的更新一致，却不能保证窗口与活动记录的跨 key 生命周期。

建议：复用现有 versionstore CAS，把窗口条目做成带身份的 opening/active 生命周期，或提供能恢复的创建意图。清理必须验证其观察到的那一代仍可清理。仅在 Create 后再 add 一次不足以证明正确：sweep 可能早先已收集 prune 候选、在二次 add 之后才执行删除。若使用多 key 原子操作，还需明确 Redis Cluster slot 约束；本轮未给出已验证实现。

验收应包含本交错、延迟 prune 落在 Create/补写之后、Create 失败/进程退出、并发重试和窗口容量回收。

## RR-20260914-03 · P2 · 派发扫描依赖本轮新完成列表，重试任务失去入口

状态：未修复。位置：Kit `service/global/activity/server_run.go:92`；`service.go:618-626`（完成后移出窗口并仅返回本次 completed），`:669`（通知完成后 settleCompletion 移除窗口）。

Server.sweepGroup 只对 AdvanceExpired 本次返回的 `advanced` 调用 DueDispatches/AttemptDispatch。活动完成后就从聚合窗口删除，下一轮不会重新出现在 advanced；由 NotifyPhase 直接完成的活动及 heal 的旧完成活动，也不会进入本次 completed 返回列表。

`TestReviewDispatchAcrossSweeps` 连续执行两轮 sweep，中间推进注入时钟一分钟，超过退避：

| 完成路径 | 两轮后 game 1 Attempts | 状态 |
| --- | --- | --- |
| grace 到期由首轮完成 | 1，预期 2 | pending 且 due=true |
| 最后一个 notify 收齐 | 0，预期 2 | pending 且 due=true |
| 首次派发 Create 失败，下轮 heal 成功 | 0，预期 2 | pending 且 due=true |

三个子例失败；显式调用 DueDispatches → AttemptDispatch 两次及 ACK 排除对照通过。这说明派发状态机原语可工作，但内置循环无法持续重新发现待发记录。应用若另有自建扫描器可能绕过此问题，本报告不声称所有接入方式都不能派发。

建议：复用 versionstore 的 CAS 建立独立、持久、有界的待派发索引，在 ensureDispatches 和索引之间设计可恢复交接。该索引保留至 ACK/终止状态，与活动聚合窗口独立；到期重试、heal、管理端 reopen 都应重新进入调度。不能只把同一活动永久留在聚合窗口，否则会消耗 MaxPendingActivities 的开活动容量。分批扫描需有游标/公平性，避免前 64 条重复占位。

另有接入观察：sweepGroup 当前丢弃 AttemptDispatch 返回的 payload；本轮没有网络发送/接收 ACK 的端到端证明。修复调度时应同时明确投递适配器的责任，不能把 Attempts 计数当作已送达。
