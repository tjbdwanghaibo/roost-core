# RR-20261006-20：TaskPool 统计瞬间读到“结束数大于提交数”（completed + failed > total）

2026-10-06，基线 `a3002263`。P4（统计口径，`goroutine.TaskPool` 仓内零调用方，不影响任务执行）。来源：[N13 review](../review/REVIEW-2026-10-05-n13.md) §4 O9 后半；[revleft](../review/REVIEW-2026-10-06-revleft.md) §4 O9 曾以“没有确定性红测试、零调用方”不改。维护者决定 NONCORE-46 选 A（修），零调用方 API 按 C8 保留。状态：已复现；已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261006-20.md)。

## 机制

两个独立的窗口，任一都能让一次 `GetStats` 读到 `completed + failed > total`：

- 写侧：`goroutine/task_pool.go:114`（基线）`Submit` 先 `submitTask` 把任务送进 worker channel，`:117` 才 `totalTasks.Add(1)`。两步之间 worker 已取走任务、执行完并 `completedTasks.Add(1)`（`executeTask`）。
- 读侧：`:154` `GetStats` 先读 `totalTasks`、再读 `completedTasks` / `failedTasks`。两次读之间有任务提交并结束，后读的结束数包含先读的 total 没算到的任务。

## 触发 / 预期 / 实际

- 触发：一个 goroutine 提交并完成任务，另一个 goroutine 读统计，读落在上面任一窗口里。
- 预期：任何一次读到的 `completed + failed ≤ total`。
- 实际：读到 `total 0, completed 1`。

修前红是在基线计数顺序上只加了两个测试缝（缝本身不改顺序）跑出来的。

## 可达性

`TaskPool` / `GetStats` 在仓内（core、kit、codegen 模板、demo）没有非测试调用方（`rg 'GetStats\(\)'` 只有定义本身）；仓外使用者读统计时会看到这个瞬时不一致。
