## RR-20260912-01 · P2 · Shutdown 等锁时忽略截止时间

**状态：未修复。** 位置：`nestwal/committer.go:235` Flush、`:242` flushMu.Lock、`:319` Shutdown、`:380` replayMu.Lock。

**触发：** 后台 replayPass 正在 ApplyMutations，持有 replayMu；随后调用带短截止时间的 Committer.Shutdown。投影器等待下游，但正确监听传入的 context。

**期望：** 截止时间到后 Shutdown 返回 context 错误，保留可收尾的状态；不应无界等待其他 replay 的锁。

**实际：** Shutdown 先同步调用 Flush，再调用 Close。Flush 进入 replayPass 时阻塞于无 context 的 mutex.Lock；后台 replay 使用的是 committer 自身 context，只有后面的 Close 才 cancel。调用者的截止时间无法中断该等锁过程。并发 Flush 还可能先堵在 flushMu；此分支为源码分析，本轮直接验证 replayMu。

**实测：** 使用真实临时 WAL 文件、Enqueue/ticket 和后台 committer；applier 同时监听 release 与自身 context.Done。20ms 的 Shutdown context 到期后再观察 50ms 仍无返回，释放 applier 后才退出：

```text
Shutdown stayed blocked behind background replay after its context expired;
returned only after releasing applier
```

**影响：** 慢后端可使停机调用超过其预算；不能把向 Shutdown 传 timeout 当作可靠的返回时限。不是“不遵守 context 的 applier”构造：applier 遵守的是后台传入的 committer context，而 Shutdown 尚未执行 Close 去取消它。

**建议：** 让等待 Flush/replay 所有权的过程可被调用者取消，或用后台停止状态机配合可取消等待。区分优雅排空与停止重试，不通过并发关闭仍在使用的 WAL 强行绕过锁。添加后台 replay 忙碌、多个 Flush、超时后再次停止的回归。

## RR-20260912-02 · P2 · Sync 未等待已接受的异步记录

**状态：未修复。** 位置：`nestwal/wal.go:566` Sync、`:718` collectBatch、`:976` syncActive。

**触发：** WAL.Enqueue 已成功返回 ticket，但 writer 尚在收集批次或记录仍在 appendCh，此时调用 Sync。

**期望：** 按 Sync 注释的契约，返回成功前将调用时已接受的异步记录推进到持久化边界；做不到时按 context 返回错误。

**实际：** Sync 只检查 context/terminal，再同步当前 active 文件。它没有向 writer 排入屏障，也没有捕获并等待已准入 LSN。尚未物理写入的数据不在本次 fsync 的范围内，因此可以成功返回而 ticket 未完成。

```text
Sync returned nil before admitted ticket resolved:
admitted=1 appended=0 durable_lsn=0 ticket_lsn=1
```

**实测方法：** 合法配置 BatchDelay=time.Hour 扩大收集窗口，Enqueue 后立即 Sync，Sync 带 30ms context。测试并不等待一小时；清理时 Close 打断批次等待并正常写入。正向对照在同配置下调用 Close，ticket 与 durable watermark 均正确完成。默认短 BatchDelay 也存在这一窗口，未测其生产出现频率。

**影响：** 依赖 Sync(nil error) 作为“之前已接收写入全部持久化”的调用者会过早推进自己的状态。等待具体 ticket 的正常 Pipelined 请求路径仍有正确的确认门槛；没有证明所有 Nest 请求都过早成功，也没有实际制造数据丢失。

**建议：** 明确捕获准入边界，等待 writer 完成对应批次及 fsync；可采用有序屏障或 LSN 水位等待，兼顾取消、关闭和 terminal 错误。仅直接 fsync 文件无法覆盖仍在内存队列中的记录。
