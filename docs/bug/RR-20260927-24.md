# RR-20260927-24：strict 等 Remote 确认到截止时回复只带 `ErrRemoteCommitTimeout`，不带 RR-37 承诺的 `ErrRemotePersistenceIndeterminate`

日期：2026-09-27。基线：本地 main `4c7424c`。来源：[OPEN-ITEMS-2026-09-27](../review/OPEN-ITEMS-2026-09-27.md) B23（批次 5 在真实 Nest + 正式 Remote Manager 上核对四种“结果未知”场景）。等级 **P4**。引入：RR-20260926-37。状态：已修复（[修复记录](../bugfix/RR-20260927-24.md)，分支 `fix-r7-rr24`，基线 `23c1201`），本地提交，未推送。

`remoteentity/transaction_tracking.go:178` `waitRemoteTransaction` 的 `ctx.Done()` 分支返回 `errors.Join(entity.ErrRemoteCommitTimeout, ctx.Err())`，状态为 `RemoteCommitUnknown`；
其余三种结果未知（Durability 0 回复丢失 / 从未到达，strict 投影器报告未知）都带 `entity.ErrRemotePersistenceIndeterminate`。RR-37 修复记录与 USER_GUIDE §4 判别表第 2 行承诺“Remote 结果未知 → `ErrRemotePersistenceIndeterminate`”，
按这个哨兵判“可能已提交、不得重试”的调用方在 strict 截止场景漏判。批次 5 已把判别表第 2 行补上 `ErrRemoteCommitTimeout`（`14272fd`，文档对齐现状），代码未改。

修复约束：截止分支在保留 `ErrRemoteCommitTimeout` 与 `ctx.Err()` 的同时 Join `ErrRemotePersistenceIndeterminate`（只增加 `errors.Is` 命中，不删除已有哨兵，非破坏）；
`nest/nest.go` `ErrLockTimeout` 等 godoc 里“可能已提交”哨兵清单补上 `ErrRemoteCommitTimeout`；`remoteentity/reply_sentinel_table_test.go` 改为断言四种场景都满足 `ErrRemotePersistenceIndeterminate`；判别表第 2 行说明两者关系。
