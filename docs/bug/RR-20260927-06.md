# RR-20260927-06：嵌套独立事务结果未知 fence 引擎之后，外层 handler 自己的事务仍交给 committer 并被真实 WAL 接受

日期：2026-09-27。基线：`d4234c9`（main，v1.17.1 之后的文档提交）。来源：[OPEN-ITEMS-2026-09-27](../review/OPEN-ITEMS-2026-09-27.md) **B03 → C07**
（[bug-76 §复核残留](RR-20260926-76.md)、[bf-76 §未验证项 / 风险](../bugfix/RR-20260926-76.md)、[audit4](../review/REVIEW-2026-09-27-audit4.md) 探针 C）。
等级 **P3**：需要 handler 内嵌套独立事务且 DAO `AcceptMutation` 失败。引入：修前即有（RR-76 只 fence，不拦截外层）。状态：已复现，已修复（见下）。

## 现象

外层 undo_strict / state_strict / undo_pipelined handler 里调 `RunIsolatedTransaction`，嵌套事务的 committer 是真实 `nestwal.Committer`：
WAL 追加并落盘成功，随后 DAO 的 `AcceptMutation` 返回错误。`acceptPersistence`（`nest/persist_change.go:312-327`，`:322` 把错误 Join 成
`ErrCommitIndeterminate`）让嵌套事务结果未知，RR-76 在返回业务之前 fence 引擎（`FenceError()` 满足 `ErrNestFenced`）。业务吞掉这个错误、
继续改声明实体并 `MarkPersist`，外层自己的事务照常交给同一个 committer：WAL `Admitted` 从 1 变成 2，回复 `ok`。
fence 之后引擎仍在写 WAL，而 fence 的含义是“停写、从 WAL 恢复”。

真实 WAL 只在物理写 / fsync 结果未知时进入 terminal（`nestwal/wal.go:340-342` 追加前检查 terminal）；`acceptPersistence` 这一来源下
WAL 健康，会接受外层记录。bf-76 “真实 WAL 已 terminal、会拒绝”的说法只对 fsync 来源成立。

前提断言（嵌套事务 WAL 追加成功且结果未知、handler 内已 fence、WAL 未 terminal）都通过，失败的是“fence 之后外层不再交给 committer”。

## 根因（`d4234c9` 源码；codebase-memory 图谱停在 09-26，已过期，以下全部来自源码）

- `nest/execution.go:271-286` `commitDurable`：嵌套事务结果未知时只 `markNestedTransactionCommitted` + `fenceEngine` + `abandon`（RR-65 / 76）。
- 外层 handler 返回后，`runTransaction`（`nest/execution.go:228-231`）照常进入 `commitDurable` / `commitPipelined`；`durableCommit`
  （`nest/rollback.go:576-611`）与 `pipelinedEnqueue`（`:674-698`）在调用 `committer.Commit` / `Enqueue` 之前不看引擎是否已 fence。
  派发入口（`nest/nest_dispatch.go:141`、`:208`）只在 handler 开始前检查 fence。

## 修复约束（清单 §H C07 推荐，维护者 2026-09-27 决定按推荐执行）

B03 证实后：fence 之后，外层自己的提交在交给 committer 之前返回 `ErrNestFenced`；检查点不阻塞快池。RR-76（返回业务之前 fence）与
RR-84（收尾阶段的独立事务不认领消息）的语义不回退。
