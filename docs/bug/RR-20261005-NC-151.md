# NC-151：phase 的 `on.recast` / `on.timeout` 与 `timeout_ticks` 能编译、运行时从不执行；`timeout_ticks > 0` 让编译器放过 enter fallthrough，tap 技能每次施法 ErrProgramInvariant

2026-10-05，基线 `45d4bc1c`。P2（编译器宣称的静态证明与 Runtime 不一致：作者写的事件流被静默丢弃，或通过启动期 CompileAll 的技能每次施法都以“不可变 Program 不变量失败”终止）。状态：已复现、已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261005-NC-151.md)。[本轮](../review/REVIEW-2026-10-05-n09-batch3.md)。

## 触发与差异

`skill/README.md:247` 写明“每个 phase 的 `on` 支持 `enter`/`recast`/`cancel`/`direction_changed`/`target_changed`/`timeout`/`release`/`pulse`”。编译链全部接受这些事件：`parse.go:268-295` 解码、`compile_normalize.go:266` 归一化、`lower.go:316-322` 为每个事件生成 root。

Runtime 只在这些地方按事件名取 root（`phaseRootOperation` 的全部调用方）：`executor.go:30`（enter）、`runtime_cast_window.go:249`（cancel）、`runtime_cast_window.go:138, 373`（release）、`runtime_cast_policy.go:50`（pulse）、`runtime_input.go:19, 60`（`direction_changed` / `target_changed`，`InputPort` 只有这两个值，`program_input.go:10-13`）。**`recast` 与 `timeout` 没有任何派发点。**

`timeout_ticks` 同样只被编译器读：`phaseTimeoutTask`（`scheduler.go:42-49`）在 live 代码里从未构造，只在 checkpoint 恢复时由 `runtime_checkpoint.go:1133` 生成；`executeScheduledTask` 的 switch（`scheduler.go:435-468`）没有它的分支，恢复出来也只会落到 `default: ErrProgramInvariant`。`git log -S 'phaseTimeoutTask{'` 显示自 `5ccbe7fc`（08-10）起就是这样。

而编译器把 `timeout_ticks` 当作 enter fallthrough 的合法出口：`compile_lifetime.go:13`

```go
if phase.timeoutTicks == 0 && fact.CanFallthrough && !policySuspend {
	context.addDiagnostic(DiagnosticLifecycleFallthrough, …, "phase enter flow may fall through without a timeout")
}
```

于是 enter 不以 finish / goto 结束、`timeout_ticks > 0` 的 tap 技能编译通过；运行时 `executeCast` 走 `flowContinue → beginPolicyWait`（`executor.go:50-51`），tap 不是 charge / toggle / hold，`runtime_cast_policy.go:6-7` 返回 `ErrProgramInvariant`。

## 复现（探针，基线代码）

phase `timeout_ticks: 3`，enter 是一次 damage（不 finish），`on.timeout` 是 damage + finish：

```
diags=[]
skill: immutable program invariant failed      // runtime.Activate 返回
```

`skill/testdata/recast_combo.json`（“Declares a bounded recast branch for a combo skill”）的 recast 分支在 acceptance 里从未执行；acceptance 只断言 cast 以 enter 的 finish 结束。

## 影响

- 写了 `on.recast` / `on.timeout` 的技能：编译、启动期 CompileAll（game-demo `service.go.tmpl` 的 fail-fast）都通过，运行时这些分支永远不跑。
- 依赖 `timeout_ticks` 结束 phase 的技能：编译通过，运行时每次施法失败（`CastFailed`，enter 里已执行的效果已经提交）。
- 不依赖 fallthrough 的 `timeout_ticks > 0`（`area_heal.json` 5、`dynamic_numeric.json` 4 等）没有任何作用，作者以为的“phase 上限”不存在。

## 验收覆盖点

编译期：`on.recast` / `on.timeout` 被拒绝并定位到事件路径；enter fallthrough 不再被 `timeout_ticks` 豁免；非零 `timeout_ticks` 至少给出诊断。运行期：原探针形状不再能编译出 Program。既有 fixture（除 recast_combo）与 game-demo / `roost add skill` 生成的定义仍然编译通过。

## 实施方向（约束与候选）

A. 在 Runtime 实现 phase 计时（进入 phase 时排 `phaseTimeoutTask`，到期执行 `on.timeout` 或结束），并定义 recast 的触发入口——需要维护者定语义（计时期间 enter 仍挂起时谁取消、recast 与 toggle 二次激活的关系、checkpoint 形状）。
B. 编译期 fail-closed：拒绝 Runtime 不派发的事件，fallthrough 不再以 `timeout_ticks` 豁免，非零 `timeout_ticks` 给出诊断。保持现有 Runtime 不变，等维护者决定是否做 A。
