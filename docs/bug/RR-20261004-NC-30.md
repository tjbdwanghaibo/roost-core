# RR-20261004-NC-30：RefHMap 清理旧 registry 时遗留并发 schema 的子 hash

日期：2026-10-04；源码基线 `e7027a65c8a3b7649837a61c50a29d999ba32636`；P2。初始状态：真实 Redis 已确认、未修复。当前状态见末尾修复追加。

## 触发、期望与实际

同一 Prefix/Name/业务 key 的两个合法布局：旧布局只有 ID/Version，新布局增加 Child.Score。A 的 Set 或 Delete 已通过 HGet 读取旧 `__keys`；在它进入写操作前，B 全量 Set 发布新布局和子 hash。然后 A 使用旧清单完成，并返回 nil。

最后的全量 Set 应清理它替换掉的已登记子 hash，Delete 应清理被它删除记录的已登记键；否则应明确拒绝此次清理。实际旧实现删除 root 并失去新 child 的登记，子 hash 还在。配置 TTL=0 时它永久存留，随后正常 Delete 也找不到它。有限 TTL 下残余持续到该子 hash 到期。本项不把所有 last-writer 覆盖登记成 bug。

真实 Redis 8.8.0，在 HGet 已得到服务端旧值后同步调用另一个 store.Set，事件顺序可控，不用 sleep。修前两个反例均为：

```text
registry race was not refused before writes: err=<nil> child_remaining_after_delete=1 probe=<nil>
```

四个控制为顺序 Set/Delete 清理、同布局已有记录的 last-writer、registry 读取 WRONGTYPE 拒绝。首次实测及修前 Git overlay 复跑均 6 叶子，2 fail/4 pass；不是编译、超时或 race harness 失败。[原始证据及复跑](../bugfix/evidence/noncore-bugfix-20261004-10/README.md)。

## 根因和方案

修前 `cache/ref_hmap.go:339` writeHashes 先 registeredKeys（349），再 Eval（365）；Lua 删除的 KEYS 是过去读到的清单。Delete（192）同样先读，再以 Pipeline.Del/Del 删除。脚本虽独占执行，但没有把清单读取与执行时的 root registry 对照。

优先复用已有 root 的 `__keys`、同槽 KEYS 和 Eval：读取原始 registry，一并传入脚本；在任何 DEL 前读取 root registry 并逐字比较，变化就返回未应用的明确冲突。Set/Delete 共用裁决方式。无需动态发现未声明 Redis 键、增加锁服务或自动重试；它保护清理清单，不升级成值/version CAS。
