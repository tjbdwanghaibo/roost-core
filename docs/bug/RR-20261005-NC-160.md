# NC-160：failurelog 把脚本的“结果未知”当成“没执行”，非原子降级再执行一次——死信追加两次、多删同值记录、清空时删掉新到的死信

2026-10-05，基线 `45d4bc1c`。**P2**（运维数据被静默改写：DLQ 重复 / 多删 / 丢新条目，调用方拿到成功）。状态：**已复现（包内替身 + 真实 Redis 与生产驱动），未修复**。[本轮](../review/REVIEW-2026-10-05-n12-revn12.md) · [证据](../review/evidence/noncore-review-20261005-n12/)。

## 触发、预期与实际

- 触发：`RedisList.AppendRaw` / `DeleteRaw` / `Purge` 的 Lua 脚本已在 Redis 执行，回复丢失（连接 EOF、读超时、ctx 到期）。生产唯一使用方是 bus 的可靠消息死信（`bus/reliable.go:93`，`RedisReliableStore.DeadLetter` / `PurgeDeadLetters` / `DeleteDeadLetters`）。
- 预期：一次调用至多执行一次；结果未知原样交给调用方（与 cache RefHMap 的 [NC-21](../bugfix/RR-20261004-NC-21.md)、驱动脚本不重放的 [NC-100](RR-20261005-NC-100.md) 同一契约）。
- 实际：`failurelog/failurelog.go:108`、`:193`、`:274`（基线）的 `tryXxxWithScript` 对 **任何** Eval 错误返回“没走脚本”，调用方随即走为“适配器没有 Lua”准备的非原子降级：

| 操作 | 降级 | 已执行脚本后再降级的结果 |
| --- | --- | --- |
| AppendRaw | `RPUSH` + `LTRIM` + `EXPIRE`（`:112`） | 同一条死信出现两次，返回成功 |
| DeleteRaw | `LREM` 每个值 N 次（`:197` → `:307`） | 多删一条同值记录（重复死信的另一份） |
| Purge | `LLEN` + `DEL`（`:277-287`） | 脚本清空之后、降级之前写进来的新死信被一起删掉，返回的条数也不对 |

```text
# 真实 Redis（隔离环境）+ 生产驱动 redis/driver（MaxRetries 3）经本地代理，代理吞掉第一条 EVAL 的回复并断开
unknown_result_integration_test.go:151: AppendRaw err=<nil>; real list now holds 2 entries
unknown_result_integration_test.go:153: one AppendRaw stored 2 copies in real Redis [{"msg_id":"m-1",...} {"msg_id":"m-1",...}] (err=<nil>); want 1

# 包内替身（脚本按语义执行后返回传输错误）
append: one AppendRaw whose script ran but whose reply was lost stored 2 entries [dead-letter dead-letter] (err=<nil>)
delete: deleting one copy whose script ran but whose reply was lost left [] (err=<nil>); want one copy kept
purge:  Purge whose script ran but whose reply was lost left [] (err=<nil>); the dead letter written after the purge must survive
```

## 根因

降级路径的入口条件写成了“脚本出错”，而不是“适配器没有 Lua”。生产驱动的 Eval 永远不会返回 `(nil, nil)`（脚本回复为空时驱动报 `redis.Nil` 错误），所以在生产里降级只会在“结果未知”时触发——恰好是唯一不该降级的时刻。NC-100 关闭了驱动对脚本的重放之后，这条路径成了确定的第二次执行。注释（`:220-223`）还写着沿用 `cache.refhmap.write_degraded_total` 的约定，而那个降级与指标已由 NC-21 删除。

N04 观察 3 提到的“`RPush` 在 go-redis 默认重试下可能重复追加”：生产里 `RPush` 只在上述降级里被调用，所以重复追加的实际入口是本条；驱动对 `RPUSH` 自身的重放是同一路径上的第二层放大。

## 影响

DLQ 是运维排查与人工重投的依据：重复条目让 `ListDeadLetters` 计数虚高，人工 requeue 时同一消息两次发布（同一 `requeueMsgID`，在 inbox TTL 内被去重，过期后会真的执行两次）；`DeleteDeadLetters` 多删一份；`PurgeDeadLetters` 删掉清空之后才到的死信，静默丢失。触发需要脚本执行后丢回复，频率低。定 P2。

## 验收覆盖点

三种操作在“脚本已执行、回复丢失”时都至多执行一次并把错误交给调用方（`errors.Is` 保留原因）；适配器真没有 Lua（替身 `(nil, nil)`）时降级行为不变；真实 Redis + 生产驱动的同一场景。没做：Redis Cluster；`DeadLetter` 报错后 bus 侧（inbox 停在 processing）的端到端重投。
