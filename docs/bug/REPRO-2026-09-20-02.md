## 1. RR-20260920-06：被拒绝的 subscribe 永不重试

### 1.1 源码判定（不需要跑）

```
game/scene/runtime/interest.go:252   hold.subscribed = true        // 在 room.Subscribe 之前
internal/service/game/scene.go:336   slog.Warn("scene: subscribe") // 失败只记日志
game/scene/runtime/interest.go:262   if band == hold.band { return _, false }   // 不再发出
```

三行合起来：pair 被标成已订阅、房间侧其实没有、而唯一的重发条件是 band 变化。
`Scene.applyChanges` 的注释"the next tick that touches it tries again"与第三行直接矛盾。

### 1.2 拒绝确实会发生（不是假想）

`roost-core/entitysync/subscription.go:224-237` 在快照的 `CommitLSN` 未 durable 时返回
`ErrDurabilityDeferred` 并回滚订阅；`room.Subscribe` 另有 `ErrRoomSubjectRetiring` /
`ErrRoomSubscriberLimit` / `ErrRoomSubjectLimit` 三条拒绝路径。

16 机器人实跑的服务端日志里这条 Warn 真实出现过（一次 8 条、一次 2 条）：

```text
"msg":"scene: subscribe","observer":103062532,"subject":103063556,
"err":"entitysync: envelope admission failed\nroom: room frame admission failed\n…"
```

### 1.3 业务层症状（与之一致，未逐 pair 对上）

`go run ./cmd/loadtest -count 16`，每轮 2~6 个客户端稳定失败：

```text
scene_expect: after 40s ... "pos_x" never arrived;
own fields=[_id attr_base attr_final exp items level] own_updates=6 other_updates=104
```

`own_updates>0` 说明该客户端收到过自己 subject 的更新，`other_updates≈100` 说明会话与通道正常。
把断言超时从 10s 改到 40s 结果不变（不是慢，是丢）。

**本轮没有做的**：把某一次被拒的 pair 与某一个缺字段的客户端逐一对上，需要 pair 级日志。
登记依据是 1.1 的代码本身。

## 2. RR-20260920-07：`SmallSafeMap` 被写成空文档

临时用例（放进 `roost-core/safemap`，跑完即删）：

```go
m := &SmallSafeMap[string, int64]{}
m.SetRawMap(map[string]int64{"a": 1, "b": 2})
raw, _ := bson.Marshal(bson.M{"m": m})
var back bson.M
_ = bson.Unmarshal(raw, &back)
t.Logf("encoded as: %#v", back["m"])
```

```text
SmallSafeMap encoded as: bson.D{}
round trip lost the contents: &safemap.SmallSafeMap[string,int64]{…, entries:[]Entry[string,int64](nil)}
```

判据在驱动里：`go.mongodb.org/mongo-driver/v2@v2.6.0/bson/marshal.go:40` 要的是
`MarshalBSONValue() (byte, []byte, error)`，而 `bson/types.go:19` 是 `type Type byte`（定义类型）。

全仓扫描同类实现：

```bash
grep -rn "MarshalBSONValue\|UnmarshalBSONValue" --include='*.go' roost-core roost-kit roost-codegen | grep -v _test
```

只有 `safemap/small.go` 一处签名错误；`entity/remote_snapshot_codec.go` 的 `RemoteChecksum` 是正确签名
（它就是踩过这个坑之后改对的）。

## 3. RR-20260920-08：`OpTimeout` 不覆盖排队

### 3.1 源码判定

`roost-core/remoteentity/batch.go:103-124`：`select` 等 `w.writeGate` 只看 `parent.Done()`；
`context.WithTimeout(ctx, OpTimeout)` 在拿到闸**之后**才加，而且只在 parent 没有 deadline 时才加。

### 3.2 实跑

配置 `remote_entity.lock_ttl=15s`、`op_timeout=3s`。单进程跑一轮机器人（建了公会）→
`run.sh stop game` → `run.sh start game` → 立刻再跑一轮，客户端对 `found_guild` 做 20 次重试
（每次前等 1 秒）。服务端：

```text
slow dispatch  handler=handlerFoundGuild  cost_ms=79031
```

79 秒既不是 15 秒的租约，也不是 3 秒的超时；把重试去掉则是单次 3 秒失败。
冷启动（库全空、无前任进程）时同一个 handler 稳定 ~200ms，所以这段等待只在"同一实体上有人排队"时出现。

### 3.3 环境注意

复现 3.2 时**必须同时清空 `remote_entity` 控制库**，只 drop `game` 会留下上一轮的事务/标记记录，
第一次 `found_guild` 会因此走进另一条等待，看起来像同一个现象但不是。本轮在这上面浪费过一次。
