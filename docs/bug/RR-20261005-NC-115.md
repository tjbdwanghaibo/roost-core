# NC-115：state 可见性的快照与增量口径不一致——ability 按 handle 只在增量生效，三类 remove 对不可见实体放行

2026-10-05，基线 `855c2a38236f4efc9575fa9ba84bf8bf4100daf3`。P2（可见性泄漏：按 handle 隐藏的 ability 经快照完整下发；不可见实体的 cast / process 结束时机与 persistent state 绑定的实体 ID 经 remove 下发；仓内没有 skillsync 正式调用方）。状态：已复现，未修复。[本轮](../review/REVIEW-2026-10-05-n09-batch2.md)。

## 触发与差异

`EntityVisibilityPolicy` 用两套手写规则分别过滤快照与增量（`skill/skillsync/visibility.go`）：

1. **ability handle**：增量按具体 handle 问 `FieldVisible(observer, abilities, "<handle>")`（`mutationVisibilityField`，`visibility.go:351-352`），快照对整组只问一次 `FieldVisible(observer, abilities, "")`（`visibility.go:122-136`）。按 handle 隐藏某个 ability 的策略，增量里它被拒绝，快照里它被完整发送（反过来写的策略则快照全隐藏、增量照发）。
2. **cast / process remove 不带归属实体**：`diffCastStates` / `diffProcessStates` 生成的 remove 只有 `CastID` / `ProcessID`（`skill/runtime_mutation.go:475`、`587`）；`FilterStateMutation` 从 `Caster` → `Owner` → `Cast.Caster` → `Process.Owner` 推实体（`visibility.go:229-241`），remove 一律得到 0，`visible(0)` 返回 true，放行。对应的 upsert 带完整快照，按施法者 / owner 被过滤。
3. **persistent remove 不看 Binding**：remove 的 `Persistent` 为 nil，实体同样推成 0；upsert 要求 `Binding.Owner` 与 `Binding.Subject` 都可见（`visibility.go:239-240, 285-288`），remove 却连同 `Binding{Owner, Subject}` 原样下发。

预期：同一份状态经快照或增量下发，observer 看到的集合相同；不可见实体的数据（包括其状态何时结束、绑定到谁）不下发。

## 影响

按 ability handle 做视野 / 信息隐藏的策略在重连或游标过期后失效；不可见实体的 cast / process 何时结束、persistent state 绑定的实体 ID 持续外泄。与 NC-114 同类：三条下发路径（快照、增量、reset）各自手写过滤规则。

## 验收覆盖点

快照与增量对 ability 使用相同的 handle 键；cast / process remove 携带与 upsert 相同的归属实体（只追加 JSON 字段，客户端 reducer 不依赖它们），过滤器按它判断；persistent remove 按 `Binding` 判断。增量 baseline 影子校验（`stateMutationVerifyIncremental`）覆盖新字段。本轮没有处理“observer 可见性中途变化时如何重发快照”，那是业务接入的契约（见本轮观察）。
