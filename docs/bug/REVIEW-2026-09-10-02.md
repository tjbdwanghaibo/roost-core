# 2026-09-10 第二轮问题

## RR-20260910-02（P2）：已领取邮件被淘汰后，重复投递重新生成发奖 token

状态：未修复。Kit 基线 `c4e7cef1029fb6326fa88b84c622f059bc62c0c4`。

位置：`service/mail/mailbox.go:146–170` 的 evict 删除整个终态 Entry；`mailbox.go:121–136` 的 deliver 在 Entry 不存在时新建未读状态；`service.go:716–724` 的 ReserveClaim 在 ClaimToken 为空时生成新 token。入口是 `Service.Deliver`（service.go:321）。

### 触发与结果

1. 向玩家投递有附件、仍在有效期内的邮件 A，ReserveClaim 得到 token-1，CommitClaim 成功。
2. 持续投递其他邮件，使邮箱超过 MaxMailboxEntries（当前为 200）；A 是可淘汰终态，整个 Entry 连同领取身份被删除。
3. 另一条普通邮件被删除，腾出可淘汰容量；广播重试/延迟重复投递再次对 A 调用 Deliver。
4. A 被重新建立为未读且没有 token，ReserveClaim 成功返回同一附件和 token-2。

独立测试使用真实 Service、MemoryStore 和既有 fake envelope 存储，未直接修改邮箱内部状态。通过公开 Deliver 填充邮箱，检查原 Entry 确已被淘汰，然后重投。实际失败：

`claimed mail resurrected with new delivery key: first="token-1" replay="token-2"`

### 契约与影响

Deliver 是供本地 fanout 实现调用的公开幂等步骤；Mail RPC 刻意不暴露它。本问题不依赖未认证客户端能够直接调用 Deliver。正常成功 Send 的发送账本会避免再次 fanout，但异步 fanout 的重复消息、部分失败后的再次投递属于该步骤需要处理的场景。

期望是同一玩家/邮件的投递与领取身份在允许重投的有效窗口内不变，或者已终结邮件被拒绝恢复。实际容量淘汰将“历史不可见”变成“领取身份遗忘”。奖励服务如果依契约只以 Claim.Token 去重，就可能再次发放；本轮未连接实际资产服务，证明的是新 token 和同一附件重新可领，未声称已经发生真实资产重复。

### 建议方向

将展示条目保留策略与投递/领取去重身份分开。可考虑保留终态 tombstone 到信封有效期及可接受重投窗口结束，或以稳定且安全的业务身份派生 token，并明确删除后是否允许恢复。仅禁止淘汰 Claimed 不足以覆盖 Delete 后丢失同一领取记录的路径；仅稳定 token 也需说明状态复活的产品语义。修改应覆盖容量淘汰、延迟重投、已删除记录、旧 Commit 重试及实际资产回执。
