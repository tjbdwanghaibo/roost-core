# NC-180：BucketHolder 持桶读锁调用遍历回调，回调改同一容器即自锁

2026-10-05，基线 `f6245613441d16aafec33870166a4ec14f1ca15b`。P2（潜伏：仓内唯一正式遍历方 `kit/statslog` 的回调只读计数，没有触发路径；定级低是因为没有触发路径，不是因为后果轻——触发后同桶所有查找与全进程 Add / Destroy 永久卡住）。状态：已复现，未修复。[本轮](../review/REVIEW-2026-10-05-n13.md)。

## 触发与差异

`container/bucket.go:122-130` 的 `Bucket.Range` 在 `RLock` 内逐个调用回调；`RangeAll` / `RangeWithCursor*` / `RangeByCursor` 都走它。回调里对同一桶的 `Del` / `Add` 要写锁，`Get` 未命中也升级为写锁（`bucket.go:89-92`，与 `buildIF` 无关），当场自锁。回调里读同一桶的已有键是递归 `RLock`，此时只要有一个写者排队（任何并发的 Add / Del / 未命中 Get）也会卡住。

`entity.EntityManager.Range` / `RangeByCategory` / `CountByCategory`（`entity/entity_manager.go:332-358`）与公开的 `ManagerAccess.Range`（`entity/manager_access.go:607-611`）直接包装 `RangeAll`，文档只写了“Return false from fn to stop early”，没有回调限制。业务写“遍历并卸载空闲玩家”——回调里 `Destroy`——时，`Destroy` 先拿实体锁和 `addMu`，再 `m.entities.Get(id)`（已有键，递归读锁可过）、`m.entities.Del`（写锁，等 Range 自己的读锁）永远等下去；此后 `TryAdd` / `Destroy` 全部卡在 `addMu` 上。

预期：遍历回调可以读写同一个容器，不卡住（与 `safemap.ShardedSafeMap.Range` 的“脱锁回调可安全改 map”、`EntityManager.RangeGroupEntities` 先取切片一致）。

## 复现

`container/bucket_range_promises_test.go` 的 `TestBucketRangeCallbackMayChangeTheHolder`（删当前键 / 加键 / 查不存在的键三叶）与 `entity/entity_manager_range_promises_test.go` 的 `destroy inside Range` 叶，有界等待 2s：

```
entity_manager_range_promises_test.go:37: Range did not return: Destroy inside the callback waits for the bucket lock Range holds
```

## 约束

修在 `container`，不改 entity / nest 生产代码。回调看到的是读锁内取的桶快照：回调期间并发删除的实体仍可能交给回调——调用方本来就要在拿到实体锁后复核 `IsRemoved`（`lock_manager.go:34-40` 的同一约定）。快照的分配按桶大小计，Range 不在请求热路径上（唯一正式调用方是周期统计）。
