## RR-20260920-01：Remote snapshot checksum 超出 BSON int64

### 结论修正

W-2026-09-19-01 把 `12630717602282170696 overflows int64` 推断成负 `stateVersion` 转 `uint64`。当前及该候选所述基线的 `remoteentity/batch.go` 都会把负版本归零，`RemoteEntityBase.SetEntityVersion` 也有相同保护；这条推断不成立。

问题仍然成立，直接触发项是 `remoteentity/mongo_committer.go:216-219`：snapshot 的 `Checksum uint64` 原样放入 BSON。用错误里的同一个数执行：

```go
bson.Marshal(bson.M{"checksum": uint64(12630717602282170696)})
```

Mongo Go driver 稳定返回同一条 `overflows int64`。checksum 是完整 64 位散列，高位为 1 是正常值，不是异常版本；因此约一半的散列空间不能写入当前 BSON 形状。提交的版本、epoch、fence 也都是 `uint64` 并直接进入 BSON，但它们是单调计数并参与数值比较，修复策略不能与 checksum 简单共用。

### 影响与实施方向

远程事务在投影阶段失败后，包含该 snapshot 的 WAL 记录会在启动恢复时再次执行同一个确定性失败。影响不止一次请求失败，还可能形成启动毒丸。

建议按字段语义定编码：

1. checksum 不做数值查询，编码成固定 8 字节 binary，读回时兼容历史 BSON int64；
2. version/epoch/fence 要保持 Mongo 比较顺序，若业务上限就是 `MaxInt64`，在进入 WAL 前显式校验并转换；若必须保留完整 uint64，选 Decimal128 或可排序编码，并提供迁移；
3. 在 durable admission 前执行同一套可编码性校验，避免把确定无法投影的记录先写进 WAL；
4. 恢复遇到历史毒丸时应报告 transaction/entity/snapshot key 并进入可操作的隔离流程，不能静默跳过权威提交。

验收应覆盖 checksum 的 `MaxInt64`、`MaxInt64+1`、`MaxUint64`，版本/fence 上限，旧数字文档兼容，以及 WAL 重启恢复。

## RR-20260920-02：latest-only datagram 丢掉不可重建的增量

链路已经闭合：

```text
RoomBroadcaster.flushStateBatch
  → SubscriptionCoordinator.DistributeBatch
  → RoomEnvelopeSink.AdmitEnvelopes
  → RoomTransportSink.AdmitRoomFrames
  → AsyncTransport.AdmitBatch
```

`RoomTransportSink` 把 snapshot/leave 走 reliable，把普通 delta 走 datagram。`AsyncTransport.AdmitBatch` 以 stream 为 key 保存 `queue.latest`；同 stream 已有待发帧时直接替换，并递增 `DatagramFramesDropped`。现有 `TestAsyncTransportKeepsLatestCompleteFrame` 正面验证了“1 正在发送，2 被 3 覆盖，只发送 1 和 3”。

问题在跨层契约：frame 2 与 frame 3 都是相对实体 dirty mask 的增量，frame 3 不是 frame 2 的超集。frame 2 入队成功后，`DistributeBatch` 已提交 prepared batch、清除 dirty，并推进订阅 content version / session sequence；传输层随后覆盖 frame 2 不会把它的 `pos_x` 合并进 frame 3，也没有 ACK、缺口补发或周期全量。玩家停止变化后，该字段永久缺失。这与 W-2026-09-20-01 的 16 客户端实跑现象完全一致。

### 实施方向

最小正确方案是普通 room delta 暂时走已有 reliable queue，让队列上限和 slow-consumer eviction 明确表达背压。若要保留 datagram 性能，则 latest-only 的值必须是**自包含的最新状态**或可安全合并的累积 delta，不能是一次性 dirty 增量。

完整方案可复用现有工具：以 `statesync` 的 ACK baseline 生成增量；客户端用 `SessionSequence` 检测缺口并请求全量；服务端在 ACK 前不丢弃构造下一帧所需的状态。验收必须用阻塞 transport 固定交错：frame 1 正在发，frame 2 只含 `pos_x`，frame 3 只含 `equipment`，最终客户端必须同时得到两项，或明确触发 resync。还要覆盖分片、sequence wrap、慢消费者剔除和 ACK/重连。

## RR-20260920-03：玩家租约的检查与修改不是一个原子操作

Codegen `demo/game/playerroute/playerroute.go.tmpl` 的三个路径都有同一竞态：

- `Claim` 发现现 owner 是自己后，另发 `EXPIRE`；
- `Refresh` 对每个 id 执行 `GET`，确认 SID 后另发 `EXPIRE`；
- `Release` 执行 `GET`，确认 SID 后另发 `DEL`。

在 `GET` 返回旧 SID 后、第二条命令执行前，租约可以过期并被另一进程取得。旧进程随后会给新 owner 续期，或直接删除新 owner 的 key。独立 fake keyspace 固定这个交错，两个安全断言都稳定失败。

实现应把 value 从单一 SID 升级为 `{sid, process-incarnation/token}`，使用 Core 已有 `redis.ScriptRunner` / Lua 做 compare-and-expire、compare-and-delete。相同 SID 的进程重启也必须换 token，否则旧实例和新实例无法区分。Claim 的“已经是我”分支也要比较 token，不能只比较 SID。验收覆盖过期后重领、同 SID 重启、旧 release、旧 refresh、Redis 回复丢失和并发 Claim。

## RR-20260920-04：租约丢失没有阻断本地写入

即使 RR-03 的 Redis 操作改成原子，当前 owner 层仍不能保证“一名写者”。`PlayerOwners.refreshLoop` 忽略 `Refresh` 的所有错误和失主结果，`local` 集合不变；Player 实体也不会卸载或停止接收 Nest handler。网络故障或 GC 暂停超过 30 秒后，B 可以合法 Claim；A 仍持有 resident Player，并按本地实体锁继续写。两份实体各有独立版本视图，最终落到 projection conflict 或重复业务效果。

不必为每个动作增加一次 Redis RTT。可让续租返回逐 player 的结果，在本地保存 token 与 `validUntil`；只有最近一次被 Redis 确认的租约仍有效时才允许新事务进入。续租失败接近截止时间时进入 fail-closed，停止该实体的新 handler，等待在途事务结束后卸载或停止服务。更强的方案是把 owner generation/fence 带入持久化 CAS，或直接采用 remote-managed 的 versioned lock。仅记录日志、延长 Lease 或重试刷新都不能排除双写。

验收至少覆盖 Redis 中断超过 Lease、进程长暂停、同 SID 双实例、续租回复丢失、在途事务越过截止时刻，以及恢复后由新 owner 独占写入。

## RR-20260920-05：不可解码 pending 记录会永久占据批次

RR-20260919-07 的“索引指向不存在记录”原触发已修：Server 遇到 `ErrOrderInvalid` 会 `RetirePending`。但不可解码记录走另一条路径：`RedisOrders.PendingOrders` 只从 ZSet 返回 id，`AttemptDelivery` 的 `Orders.Update` 解码错误直接返回普通 error，Server 只记日志，不移动或隔离成员。

生产 `RetryBatch=128`，因此一条坏记录只消耗一个槽，不会像旧实现那样丢掉整页；但最老的 128 个不可解码成员会在每个 tick 占满整页，后面的健康付费订单永久不可见。把一条坏记录直接从 pending 删除也不安全，因为记录仍代表一笔未履约付款。

建议增加 durable quarantine：原子地把成员从 due index 移到 poison index，保留原 order value、错误摘要、首次/最近失败时间与重试次数并告警；管理员修复后可重新入 pending。枚举也应支持有界 overscan，避免少量 poison 长期降低吞吐。验收覆盖第 1/128/129 个坏项、整页 poison、隔离写失败、修复重入与多实例竞争。
