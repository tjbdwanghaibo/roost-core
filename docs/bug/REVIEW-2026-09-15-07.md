## RR-20260915-06 · P2 · 流清理后重建复用旧 ACK 身份

位置：syncstream/lifecycle_journal.go 的 DeleteStream:120、DeleteObserver:136、SweepIdle:163；syncstream/syncstream.go 的 Append:140、AcknowledgeEpoch:200、Resync:300。

触发：同 observer/stream 在 epoch 7 发布旧快照 sequence 1；删除流、删除 observer 或经过 IdleTTL 清理；同 observer/stream 再发布不同的新快照。三种入口均删除全部序号状态，却保留 History 的全局 epoch，因此新包仍是 epoch 7、sequence 1。

期望：旧连接的 Resync/ACK 不能将不同的新内容视为已消费。实际：旧 AfterSequence=1 得到 FullRequired=false、Packets 为空；旧 epoch 7/sequence 1 的 ACK 返回 nil。配置 PruneAcknowledged=true 时，新快照被裁掉，Retained=0、Pending=0。无需并发即可复现。RotateEpoch(8) 对照正确拒绝旧 ACK 并要求全量。

影响限定：需要复用完整的 Observer/Stream 身份；若宿主总是更换 Observer.Session/Scope 或同步旋转 epoch，可避开。IdleTTL 自动清理仍容易在相同身份恢复使用时触发。即使不启用裁剪，Resync 的“无需发送”判断也会误认新内容已消费。

建议：将数据保留期限与身份高水位分离，清理 payload 时保留序号或墓碑；或引入明确的逐流 generation，并贯穿 Packet/ACK/Resync/journal。已有 RotateEpoch 能作为显式全局失效工具，但会清空其他流，不应未经设计直接在每次局部删除时调用。若选择由宿主更换身份，必须使清理 API 和 IdleTTL 契约显式可执行。方案未实施。

## RR-20260915-07 · P2 · 忽略 WAL 半条尾记录后续写污染日志

位置：syncstream/file_journal.go 的 Load:77、replayWAL:151、flushBatch:233。replayWAL 遇未换行尾部直接成功，flushBatch 后续使用 O_APPEND，未将文件恢复到最后完整记录边界。

复现：真实 FileHistoryJournal 成功记录 sequence 1 并关闭；向临时 WAL 追加未换行的半条 JSON，模拟中断写入；重新打开并 Load 成功；Append sequence 2 返回成功，关闭；再次打开失败：`syncstream: decode WAL: invalid character '{' after object key:value pair`。干净 WAL 对照通过；半尾恢复后先调用 History.Checkpoint 再追加的对照通过。

期望：接受恢复后，可以持续写入并在下一次启动重放所有成功记录。实际：已忽略的半条尾部仍在磁盘，新完整记录直接拼在其后并 fsync；第二次恢复无法读取这一行，导致整个 History 启动失败。此测试使用真实临时文件，未模拟内核断电/磁盘控制器行为。

建议：恢复时记录最后完整记录偏移，在独占 journal 所有权下安全截断未提交尾部并同步，再允许追加；或将已恢复快照发布到新 checkpoint/WAL generation 后再开放写入。应继续拒绝完整行的非法 JSON，不能把任意损坏都当半尾截掉。使用现有 checkpoint 轮转可作为实现方向，本轮不修改代码。
