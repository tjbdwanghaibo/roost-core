# NC-92：JetStream 部署里的轻量 RPC 被请求流截获——调用方得到协议错误，请求却在之后被无期限执行

2026-10-05，基线 `be7bcc18`（N03 源码与 `7922e428` 相同）。**P2**（调用方看到“失败”，服务端实际执行了，调用方据此重试就是重复副作用；触发需要调用端与服务端的 `nats.rpc.transport` 不一致，或业务直接调用 `IBus.Call`）。状态：已复现（真实 NATS），未修复。[本轮](../review/REVIEW-2026-10-05-noncore-n03.md) · [证据](../review/evidence/noncore-review-20261005-n03/README.md)。

## 触发与差异

服务端 `nats.rpc.transport=jetstream`；调用端用轻量传输（`IBus.Call` / `CallTo`，或 ServiceRPC 客户端的配置没开 jetstream）调用同一方法。

- JetStream RPC 打开时，Bus 建的请求流收 `<prefix>.rpc.>`（`bus/jetstream_rpc.go:131`）；轻量调用的主题 `<prefix>.rpc.<type>.<method>` / `<prefix>.rpc.<type>.<sid>.<method>` 正落在这个范围里。服务端在 JetStream 模式下只订阅 JetStream 消费者，不订阅 core 主题（`TestHandleRpcRegistersOnlyJetStreamTransportWhenEnabled`）。
- core NATS 的 request 落进流后，JetStream 用 PubAck（`{"stream":...,"seq":N}`）回复 reply inbox。调用端把 PubAck 当 RPC 响应解码：`decodeRPCResponse` 报 `bus: unsupported rpc response version 0`（`bus/rpc_error.go:49-51`）。
- 同一条请求随后被 JetStream 消费者投递给 `onJetStreamRPCRequest`：轻量信封没有 `DeadlineAt`，过期检查（`bus/jetstream_rpc.go:389`）不生效，`processCtx` 没有期限（`:466-467`）；没有 `ReplySubject`，回包被静默跳过（`:479-481`），消息 ACK。业务 handler 被执行，调用方永远不知道。

预期：两端传输不一致时，要么请求被明确拒绝且不执行，要么调用方得到“已被接收、结果未知”的可识别错误；不能“报告失败、实际执行”。

## 复现（真实 NATS）

`TestRevn03ProbeLightweightCallIntoJetStreamSubjects`（两端都开 jetstream，调用端直接用 `Bus.Call` / `CallTo`）：

```
lightweight Call: err=bus: unsupported rpc response version 0 resp=map[]; handler runs afterwards=1 handler_had_deadline=false
lightweight CallTo: err=bus: unsupported rpc response version 0; handler runs afterwards=2
```

`TestRevn03ProbeDiscoveredCallDeadline` 里 ServiceRPC 用 `TransportLightweight` 调同一个 JetStream 服务，结果相同（`err=bus: unsupported rpc response version 0`）。

## 影响

- 配置漂移（某个进程的配置漏了 `nats.rpc.transport`）时，所有调用“失败”但副作用照常发生；调用方的重试 / 补偿逻辑据此重复执行。
- 被执行的请求没有调用方期限，handler 拿到的是无期限的 Bus 生命周期 ctx。

## 验收覆盖点

- 服务端：没有 `ReplySubject` 的 JetStream RPC 请求（只有被截获的轻量请求会这样）不进入业务，ACK 并计数 / 告警。
- 调用端：轻量调用收到 JetStream PubAck 时返回可识别的错误（`errors.Is` 可判定），说明请求被 JetStream 流接收、目标使用 JetStream 传输，而不是笼统的 version 0。
- 两端一致（都轻量 / 都 jetstream）的既有往返不变。

本轮没做：没有审查第三方直接向 `<prefix>.rpc.>` 发布 JetStream 消息的用法（仓内没有）。
