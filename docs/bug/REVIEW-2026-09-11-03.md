## RR-20260911-05 · P3 · 拒绝投递仍修改 MemoryStore 邮箱

**状态：未修复。** 这是 U-0171 新拒绝分支的相邻问题，不否定 U-0170 的读取副本修复，也不将原墓碑提前遗忘问题重新打开。

**位置：** Kit `service/mail/service.go:336` 的 Update 回调，`:348` 插入、`:356` 淘汰先于 `:358` 的容量拒绝；Core `versionstore/memory_store.go:45` 直接传入含 map 的 current.Value。Mailbox 的 `clone` 位于 `service/mail/mailbox.go:302`，Deliver 回调未在修改前调用它。

**触发：** 使用框架自带 MemoryStore。通过公开 Send、ReserveClaim、CommitClaim、Delete、Deliver 达到 200 条未过期领取墓碑；再投递一封需淘汰已领取 Entry、产生第 201 条墓碑的邮件。没有直接修改存储 map 来制造容量。

**期望：** Deliver 返回 ErrClaimHistoryFull 时本次投递不生效，原条目、墓碑、计数、版本保持一致且不变。

**实际：** Update 获得的是 Mailbox 结构体浅拷贝，Entries/SettledClaims map 仍指向存储对象。回调先修改 map，再返回 `save=false,error`；MemoryStore 不保存新结构体，但 map 修改已经发生，Unread 等值字段和 Version 则维持旧值。

```text
refused delivery changed mailbox: inserted=true settled=200->201
version=1202->1202 unread_field=199 actual_unread=200
```

**影响：** 本地调试/测试环境中，“拒绝”与实际保存状态矛盾，邮箱计数失真，墓碑数量越过预期上限。此例是串行逻辑失败，race detector 没有报告数据竞争。MemoryStore 明确限定为测试与单进程调试，因此列 P3，不声称 Redis 生产实例也发生相同对象共享。

**证据：** 新增 `TestReviewClaimHistoryRefusalIsAtomic` 在 race 下失败；相同 API 序列仅将 Update 传给回调的对象改为 clone 的临时对照通过。该对照只存在于 overlay 测试，不是源码修复，也不是真实 Redis 测试。原 Mail 包 race 测试通过，现有成功/拒绝断言未覆盖拒绝后的完整状态。

**建议方向：** 先明确 Store/Mutate 的可变对象所有权契约；Mail 在独立副本上计算候选状态，容量检查通过后才返回保存，或让存储提供明确的快照隔离能力。加上拒绝后比较 Entries、SettledClaims、Unread、Evicted、Version 的回归；仅检查错误码不足以证明原子拒绝。不要依赖给 scalar 字段赋旧值来回滚共享 map。
