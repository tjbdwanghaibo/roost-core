# RR-20261006-11：兴趣表满时 release 不留撤销水位，迟到的旧续租复活已撤销的租约

2026-10-06，基线 `87d8d91e`。P3（资源与流量：被撤销的 key 在 owner 处继续有推送、占着 consumer 的配额和节点容量，最长到那条续租自己的到期时刻，即一个 `snapshot_interest_ttl`；推送的内容仍经 L2 版本准入，不会交出错误的值）。来源：v1.23.0 发版文档 [REM-4](../release/v1.23.0/impl-saga-drv-dao-rem.md#rem-4) 的不一致说明“表满放不下撤销水位：只撤销，不留水位（推断）”，维护者要求本轮闭环（“这次不能有 wanted”）。状态：已复现；已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261006-11.md)。

## 机制

`remoteentity/interest.go` `release`（基线 `:218`～`:237`）：带代际的 release 本应在兴趣表里留一个撤销水位（`released` 条目，存活 `snapshot_interest_ttl`），挡住撤销之前发出、之后才到的续租（Mirror 第 4 步，`interestLease` 注释的承诺）。但当被撤销的条目不存在、表又已满（`!exists && r.total >= r.maxSubs`）时，代码只调 `removeLocked`（空操作）就返回，不留水位。

条目不存在而 release 先到，正是水位要防的情形：续租还在路上（线上重排），或续租曾在这个节点因表满 / 配额被拒、复制 handler 返回错误后等待重投。之后表里只要空出一格（别的租约到期被清、别的 consumer 撤销），迟到的旧续租走“新租约”分支，`!exists && total < maxSubs`，建起一条 consumer 已经撤销的租约。

## 触发与差异

`remoteInterestLimits{PerConsumer: 4, Total: 2}`：两条 filler 租约占满表；consumer 7 对 key C 的 release（代际 21）先到；filler 的 A 被清掉空出一格；consumer 7 对 C 的续租（代际 20，撤销之前发出）迟到。预期：不复活，`interested(C) == false`。实际：`interested(C) == true`，consumer 7 记着一条租约。

## 后果判断

- 推送的内容不会被“误当成有效”：consumer 收到的复制消息照常经 `RemoteSnapshotCache.ApplyReplica` → `admitLocked`（L2 版本 CAS）准入，旧代际的租约只决定 owner 发不发，不决定缓存收不收。
- 真实代价是资源：owner 继续给已撤销的 key 推送；复活的租约计入 consumer 的 O4 配额与每节点条目数，表本来就满，可能挤掉这个 consumer 别的 key 的新续租（`consumer_quota` / `registry_full`）。上界是那条续租自己的 `ExpiresAt`（发出时刻 + `snapshot_interest_ttl`）。

## 修复

[修复记录](../bugfix/RR-20261006-11.md)：表满放不下水位时改记每个 consumer 一个的溢出水位（代际上限 + key 指纹位图），不占表容量，同样存活 `snapshot_interest_ttl`。

## 后续（2026-10-06，分支 `fixr2`）

修复记录原列的两条未验证项已实测：溢出水位到期（兴趣表时钟注入缝，到期前挡、到期后清、每个 consumer 至多一个），兴趣 handler 出错时 JetStream 结算为 Ack（真实 NATS，与设计一致）。见[修复记录](../bugfix/RR-20261006-11.md) §5。
