## P2 RR-20260914-01：Close 尚未排空时，Sync 把关闭标志当作持久化完成

Core `50859c59124aeb15593ef6bf2475a5e4715a7e2d`，未修复。位置：[wal.go](../../nestwal/wal.go):618 的 `if closed { return nil }`；Close 在 748 行先设置 closed，再由 writer 异步排空。关联 RR-20260912-02，但本项是新增屏障中关闭分支的错误假设，旧普通 Sync 触发修复仍有效。

确定性交错：Enqueue 已返回 ticket；writer 收完该批、尚未 processBatch 时暂停；另一 goroutine 发起 Close，closed=true 但 doneCh 未关闭；此时调用 Sync。实际 `err=<nil> admitted=1 appended=0 durable=0 ticket=1`，ticket 仍未完成。期望 Sync 等待该记录持久化/关闭完成，或在截止时返回错误，不能提前报告成功。

复现使用真实临时 WAL 文件，仅通过 Go overlay 在 collectBatch 与 processBatch 之间插入调度屏障；没有更改写入、fsync、Close 或 Sync 的判断逻辑。该暂停模拟合法的 goroutine 调度延迟，不是篡改 closed 或伪造持久化水位。未修改仓库生产文件。

对照一：相同 writer 暂停但不调用 Close，Sync 正确返回 DeadlineExceeded。对照二：等 Close 真正完成后调用 Sync，成功且 ticket 已完成。两项对照通过；只有“关闭进行中”失败。真实文件未遭断电，本轮证明的是成功承诺早于实际持久化，不声称已实测宕机丢数据。

建议把停止准入与排空完成分开：closed 只能表示拒绝新写；关闭中的 Sync 必须按 ctx 等待 doneCh，并传播关闭/终止错误后再确认目标 LSN。不要以固定等待时间补丁替代状态同步；保持完全关闭后 Sync 的既有幂等行为。

## 已知设计边界的真实 Redis 补证：跨实例 L2 删除水位

两个独立 RemoteSnapshotCache（独立 L1）共享同一真实 Redis L2：A 删除 v2 并留本地墓碑；A Publish v1 被挡住；B 没有墓碑，Publish v1 成功写回 Redis。随后 A.Get 仍被本地墓碑挡住，但 L2 已再次存有 v1。

该行为已在 RR-20260913-01 bugfix 的边界中披露，本轮不重复新建 RR；将它登记为[未收敛协议 OQ-01](../review/OPEN-QUESTIONS.md)。测试 PASS 是因为断言当前边界确实存在，不是“删除防复活验收通过”。两个缓存实例在同进程，Redis 真实；不冒称多机 broker 集成已完成。这个结果不足以批准 Mirror 的全局删除语义。
