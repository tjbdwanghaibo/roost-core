## RR-20260919-07：坏记录仍能占满 pending 页

RR-20260919-05 的修复把单订单读取错误改成 `continue`，解决了“一个错误使整页返回失败”。但 `demo/internal/service/platform/pending_index.go.tmpl:126-157` 仍先执行：

```go
entries, err := client.ZRangeWithScores(ctx, key, 0, int64(limit-1))
```

之后才逐项读取订单并跳过坏项。若 `limit=1`，ZSet 最老成员长期不可读，当前调用每次只看到它；健康的第二个成员永远进不了过滤循环。现有回归使用大于样本数的 limit，因而没有覆盖分页边界。

这仍会阻断付费订单恢复，等级保持 P1，但它是 RR-05 原触发修好后的新分页根因，单列编号。实现时应区分“扫描预算”和“返回上限”：在有界扫描预算内分段读取，坏项不占返回槽位；达到预算后停止并记录游标/坏项。不能无界扫描整个集合。若通过推迟坏项 score 隔离，还需保留重试退避和人工修复入口，避免把损坏记录永久隐藏。

验收至少覆盖 `limit=1`、首/中/尾坏项、连续多页坏项、未到期分界、并发退休，以及扫描预算耗尽后下一轮能继续前进。

## RR-20260919-08：loader panic 永久污染实体 flight

`entity/manager_access.go:115-138` 在调用 `loader.LoadEntity` 后才删除 map 项并关闭 `done`；`dataengine/engine/entity_repository.go:70-89` 对 `loadAggregate` 重复了同一模式。两处都没有 `defer`。因此 loader、store、builder、反序列化或初始化中的 panic 会绕过删除与 `close(done)`。

Nest 顶层会恢复 handler panic，进程可能继续运行，但该 fullID 的 flight 仍留在 map。后续请求会等待一个永远不会关闭的 channel，最终只得到自己的 context deadline；重试不会再次进入 loader。图谱入向链显示这条路径覆盖 `ManagerAccess.Get`、Nest single/multi/broadcast、guard scope 和 remote entity load。

建议两层都使用统一的 flight 完成器，在 `defer` 中保证“写入稳定结果 → 删除当前 flight → close(done)”恰好一次。panic 契约需要明确：可以把 panic 转成带堆栈的稳定错误共享给 leader/waiter；若保留 leader re-panic，也必须先完成 flight，并给 waiter 一个确定错误。不要只在 Nest 外层 recover，因为 repository 还能被其他入口直接调用。

验收应覆盖 leader panic、多个 waiter、panic 后重试、取消 waiter、不同行为的两个 fullID，以及 repository 内层 panic。首个 caller 的 context 当前同时作为共享 load 的执行 context，这会让 leader 取消影响所有 waiter；它是相邻设计风险，修复时应一并明确但本轮未另立 RR。

## RR-20260919-09：缺失实体的 nil 契约在 Nest 分派处断裂

生产 `ManagerAccess.Get` 在 manager 未命中且没有 loader，或 loader 合法返回 nil 时，会返回 `(nil,nil)`。`nest/nest_dispatch.go:689-695` 的 single path 和 `:964-970` 的 broadcast path 在只检查 `err` 后直接调用 `e.Touch()`。

single 请求因此返回顶层 panic recovery 生成的 runtime nil pointer 错误，而不是 `ErrEntityNotFound`。broadcast 的逐实体 recovery 位于 `Touch` 之后，一项缺失会逃到整次 `NestDispatch` 的外层 recovery，后面的有效实体也不再执行。multi/multiGroup 已使用 `e != nil && e.Touch()`，说明同包内已有正确边界。

修复应在 single/broadcast 显式处理 `e == nil`；single 返回 `ErrEntityNotFound`，broadcast 跳过当前 id 并继续。测试必须使用真实 `ManagerAccess`，因为现有 mock getter 会对缺失直接返回 error，掩盖生产契约。还应决定 `Getter.Get` 是否统一要求缺失返回 `ErrEntityNotFound`；在统一前，所有消费者都必须容忍 `(nil,nil)`。

## RR-20260919-10：activity dispatch 没有形成真正的交付闭环

Kit `service/global/activity/server_run.go:81-140` 从持久 `DeliveringActivities` 找到 due dispatch，随后调用 `AttemptDispatch`。该方法只用 CAS 增加 `Attempts`、设置下一退避时间并返回 payload；`trace_path` 的生产入向调用只有 `sweepGroup → run → Serve`，链上没有 RPC、bus 或其他传输。默认五次后它会进入 `DispatchExhausted`，即使游戏服从未收到 payload。

Codegen `demo/internal/service/game/activity.go.tmpl:355-376` 是拉取端，但每次只构造“上一窗口”和“当前窗口”两个 activity ID，再调用 `LookupDispatch`。离线超过一个窗口后，旧 pending dispatch 不会再被查询；Kit 的枚举能力没有通过 Coordinator RPC 暴露给游戏服。两边组合会把仍持久存在的奖励义务推进 exhausted，或让旧窗口永久不可见。

建议优先复用现有组件形成拉取式闭环：

1. 在 dispatch 创建时维护按 `gameSID` 的有界 pending 索引，复用现有 Store/CAS 与 `DeliveringActivities` 的持久索引模式。
2. 通过现有 servicerpc 生成器暴露 `DueDispatchesForGame(gameSID, cursor, limit)` 与“领取一次尝试”的方法；游戏真正拿到 payload 时才消耗 attempt。
3. 游戏 runner 按游标/limit 排空 owed dispatch，不再从本地时钟猜两个 activity ID；仍按 mail → 本地持久记录 → `AckDispatch(token)` 的次序处理。
4. Kit sweep 继续负责 `AdvanceExpired`、创建缺失 dispatch、退休终态记录和监控，不再在没有交付者时消耗 attempt。
5. 保留 `ReopenDispatch` 作为人工恢复，并增加 pending age、attempt、exhausted 与游标滞后指标。

验收应覆盖离线多个窗口、服务重启、分页、领取回复丢失、settle 前/后崩溃、ACK 丢失、并发 runner 和人工 reopen；不能只断言 Attempts 递增。
