## RR-20260908-01：Session 忽略幂等账本 Create 竞争失败

**P2，已复现，未修复。** kit [service/session/service.go](../../../cube-kit/service/session/service.go)
第 311–321 行。core [versionstore/versionstore.go](../../versionstore/versionstore.go) 的 Create
契约明确表示：第二个返回值决定是否插入，键已存在时是 `false, nil`。

**触发：** 两个不同 owner 并发使用同一个 RequestID，初始 `Requests.Get` 均读到不存在。
它们各自创建 run 并取得不同 owner 的 claim，再竞争同一个 ledger 键。

**实际：** 落败者得到 `created=false, err=nil`，Enter 丢弃 created，继续计 accepted 并
返回成功。账本只保存胜者，落败 owner 重试同一请求会因 owner 不匹配被拒绝。
第一次成功回复承诺了不存在的幂等结果。owner claim 不能串行化全局 RequestID 的竞争。
公开 [session_rpc.go](../../../cube-kit/service/session/session_rpc.go) 也声明 Enter 按 RequestID 幂等。

**复现：** 真实 `versionstore.MemoryStore` 外仅给前两次 Get 加屏障，让两次读在写入前
完成；Create 使用真实原子实现，两个 Enter 都成功，只有一个 ledger，落败者重试失败。
测试全文和命令见[复现附录](REPRO-2026-09-08.md)。

```text
FAIL TestReviewEnterLedgerCollisionMustNotSucceed
both owners succeeded (runs run-1, run-2), ledger owner=1;
losing owner's retry=session: request is invalid: request "same-request" belongs to owner 1
```

**建议：** 处理 created=false，读取并核对已有 ledger，区分合法重放与竞争冲突；同时
处理本次创建但尚未交付的 run/claim，不能只补报错或无版本删除。改变 RequestID 的
命名空间属于独立 API/数据迁移决定。本轮未进行真实 Redis 并发验证。

## RR-20260908-02：ReadThrough 取消等待不归还名额

**P2，已复现，未修复。** core [cache/read_through.go](../../cache/read_through.go) 第 91–105 行。

**触发：** 首个 loader 尚未完成，跟随请求因取消/超时离开。加入等待执行 `call.waiters++`，
取消分支直接返回，没有减回。当前源码的 waiter 名额只随整个 call 被删除而消失。

**实际：** `MaxWaitersPerKey` 限制的是本次 load 的累计入场次数；即使没有活跃跟随者，
后续请求仍可能收到 `ErrLoadWaitersExceeded`。默认上限 256，设置为 1 即可最小复现。
慢后端叠加短超时/重试会错误拒绝健康请求，影响持续到首个 load 完成，不是永久故障。

```text
FAIL TestReviewCanceledWaiterReleasesCapacity
no live waiters, but replacement rejected: cache: load waiter limit exceeded
```

**建议：** 用相同同步策略在等待结束/取消路径归还当前 call 的名额，避免与新一轮 load
混淆。测试控制 loader 的开始/结束和跟随者取消，证明容量可复用且真实满额仍拒绝。
累计统计 `Coalesced` 与当前等待者数量必须区分。本轮证明公开 API 场景，不主张所有
调用方都受影响。

## RR-20260908-03：单行 import 包拆分产生非法 Go 语法

**P2，已复现，未修复。** codegen
[internal/roost/consolidate.go](../../../cube-codegen/internal/roost/consolidate.go) 第 330–334 行。
公开入口：`roost project upgrade --consolidate`。

**触发：** 旧业务文件只有一个不带括号的 import，且同时使用保留在 kit 和迁移到 core 的符号：

```go
package consumer
import "github.com/tjbdwanghaibo/roost-kit/redis"
var _ = redis.NewRedisMod
var _ = redis.NewClient
```

**实际：** 迁移映射将 NewRedisMod 留在 kit，将 NewClient 移到 core/redis/driver，需要
新增 import。实现无条件把新 ImportSpec 文本插在第一个之后，假定存在 `import (...)`。
合法单行输入产生裸露的 `coreredis "…"`，format.Source 报错，升级失败。已有混合导入
测试使用括号块，未覆盖这一形态。

```text
FAIL TestReviewConsolidateSingleImportSplit
rewritten source does not format: 3:2: expected declaration, found coreredis
```

失败文件在 format 报错后不落盘；这不证明整项目原子性，遍历到它之前其他文件可能
已经被处理。本轮未把项目级回滚问题作为额外确认发现。

**建议：** 按 AST 导入声明合并/构造，或把单行声明转为括号块再插入；覆盖单行/括号块、
kit/core 混用、contract 分流及 dry-run，生成消费者应进一步编译，不能只匹配字符串。
