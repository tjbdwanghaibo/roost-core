# NC-230：ops 端口 bind 失败时 OpsMod.Start 仍返回 nil，进程在没有探针端点的情况下继续运行

2026-10-06，基线 `c8ecbabb`。**P3**。状态：已复现，已修复（见文末）。[本轮](../review/REVIEW-2026-10-06-n01b.md) · [证据](../bugfix/evidence/noncore-bugfix-20261006-n01b/README.md)。来源：N01 留项“Ops bind”（10-04 第二批已观察到“启动 bind 失败未验”）。

## 触发与差异

`kit/ops/ops_mod.go` `Start`（基线 :122-147）在 `ops.enabled` 时把 `server.ListenAndServe()` 放进 goroutine，bind 失败只记 `slog.Error("ops: http server failed")`，`Start` 已经返回 nil。

- 预期：`Start` 返回 nil 表示 `/healthz`、`/readyz`、`/metrics`、`/admin/*` 已在 `ops.addr` 上监听；端口被占用时启动失败，按启动失败路径收尾（停已启动的 Mod、释放单实例锁、非零退出）。
- 实际：进程照常启动、服务业务，但没有任何探针 / 运维端点。

## 影响

- 同机部署（shell、dev-run 的第二实例、两个服务误配同一 ops 端口）：健康检查探到的是**占着端口的另一个进程**，可能把这个实例判成健康。生成的 dev-run 脚本已经为同一类假绿加了“端口上已有应答就拒绝启动”的绕行（`codegen/internal/roost/render_dev_run.go:284-291`），说明这种误判真实发生过。
- k8s：startupProbe 要等满 `failureThreshold × periodSeconds` 才重启，这段时间进程持有单实例锁、在没有 readiness 的情况下运行。
- [APP-SINGLETON-LOCK](../feature/APP-SINGLETON-LOCK-2026-10-05.md) §4 表中“P2 的 ops bind 会先失败但不会让 P2 退出”的描述以此为前提。

## 复现

`kit/ops/listen_promises_test.go` `TestOpsStartFailsWhenTheAddressIsTaken`（先占用一个端口，再以它为 `ops.addr` 走正式 Init / Provide / Start）。修前：

```

```
