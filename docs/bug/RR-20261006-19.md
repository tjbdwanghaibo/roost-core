# RR-20261006-19：可靠 RPC 的 `method` 标签没有上界（`bus_rpc_pending{method}` 等）

2026-10-06，基线 `ac913a60`。P3（指标基数与内存：每个新 method 字符串多一组序列、调用方 `pendingByMethod` 多一条，永不删除；
达到每指标上限 2048 之后连真实方法的新序列也被丢掉）。来源：[REVIEW-2026-10-05-n12-revn12](../review/REVIEW-2026-10-05-n12-revn12.md) O3（`bus_rpc_pending{method}`、
`bus_rpc_consumer_delivery{method}`），[第十二轮 kit 批](../feature/DECISIONS-R12-KIT-2026-10-06.md) §2“受 2048 上限约束、拥有者需要时直接调用”，
v1.23.0 发版文档 OPS-2；维护者第十三轮“不留 WANTED”。状态：已复现；已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261006-19.md)。

## 机制与生命周期

- 调用方（`bus/jetstream_rpc.go` `callJetStreamRPC`）：`bus_rpc_pending{method}`、`bus_rpc_call_total{method,result}` 的 method 是 `CallReliable` /
  `CallToReliable` 的任意字符串参数；`pendingByMethod` 每个新值存一个计数器。
- 被调方（`onJetStreamRPCRequest`）：`bus_rpc_request_total{method,result}`、`bus_rpc_consumer_delivery{method}` 的 method 取自请求 envelope 的 `MsgName`，
  由对端决定，不是本进程注册的方法。
- method **没有注销概念**：`HandleRpc` 只注册，Bus 没有撤销单个方法的入口；调用方也不知道对端有哪些方法。所以这些序列不能“在注销时删除”，
  修前也没有自己的上界——第十二轮记录写的“受 2048 上限约束”是注册表的兜底，它丢弃的是之后的任何序列，包括真实方法的。

## 复现

`bus/rpc_method_label_bound_promises_test.go`（修前用一个临时测试文件提供新常量，跑完删除）：调用方 300 个不同方法、被调方收到 300 个命名未注册方法的请求：

```text
--- FAIL: TestCallerRPCMethodLabelsAreBounded (0.01s)
    rpc_method_label_bound_promises_test.go:63: bus_rpc_pending has 300 method labels after 300 distinct methods; the bound is 257
--- FAIL: TestServedRPCMethodLabelsAreTheRegisteredMethods (0.01s)
    rpc_method_label_bound_promises_test.go:116: bus_rpc_request_total has 301 method labels (e.g. "forged.M119") after 300 requests naming unregistered methods; want only map[_unregistered:true mail.List:true]
```

## 修复

[修复记录](../bugfix/RR-20261006-19.md)：被调方只用注册过的方法作标签（其余 `_unregistered`），调用方每个 Bus 至多 256 个方法标签（其余 `_other`）。
