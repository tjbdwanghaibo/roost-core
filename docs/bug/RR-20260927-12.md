# RR-20260927-12：撤销 handler 内新建的实体仍以 DestroyReasonCommon 调用销毁回调，业务无法区分“撤销新建”与普通删除

日期：2026-09-27。基线：`d4234c9`。来源：[OPEN-ITEMS-2026-09-27](../review/OPEN-ITEMS-2026-09-27.md) C27（[bf-35](../bugfix/RR-20260926-35.md) “兼容性与新导出 API”、
[bf-30](../bugfix/RR-20260926-30.md) §3）。等级 P4（语义不一致，业务在 `OnDestroy` 里做不可逆动作时才有后果）。状态：已复现，已修复。
codebase-memory 图谱停在 09-26，已过期；以源码为准。

## 现象与根因

`entity/manager_factory.go:175-176`（`revokeCreated` 的 post-release）调用 `DestroyAll(DestroyReasonCommon)` / `OnDestroy(DestroyReasonCommon)`。
`DestroyReasonCommon`（0）也是业务 `Destroy` 最常用的原因；RR-30 / 39 的仅内存卸载已改用专门的 `DestroyReasonMemoryUnload`（`entity/entity_kind.go:48`，255）。
被撤销的新建实体从未进入已提交的持久化记录、从未成为权威，业务的 `OnDestroy` 却看到与业务删除相同的原因。bf-35 当时没有新增原因值，理由是“业务包会给原因值
起领域别名，新增数值可能冲突”；RR-39 之后框架已从高位（255）往下分配自己的原因，这一顾虑有了约定。

## 修复约束（清单 §H 推荐，维护者 2026-09-27 决定按推荐执行）

新增 `DestroyReasonCreateRevoked`，撤销新建实体时使用（新增枚举值，非破坏）；核对所有按 reason 分支的代码，包括生成器模板与 demo。

生产代码 / 模板 / demo（核对表见修复记录）。详见[修复记录](../bugfix/RR-20260927-12.md)。
