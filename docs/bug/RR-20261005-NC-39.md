# RR-20261005-NC-39：Saga 启动幂等身份跟随运行状态变化

2026-10-05；P2；审查基线 main `cb11be90`；**已复现、已修复，声明场景已验证，未发版**。来源：N06 接续 review，不是重复登记 NC-38。

## 触发、预期与实际

同一 `StartRequest` 首次创建成功后，步骤完成用 `Completion.Data` 更新业务数据，或终态失败经 `Resume` 修改/清除截止时间。之后 WAL 原启动 effect 重投，或调用方重试 `StartSaga`。

预期：原始意图返回这笔 Saga 的当前进度；同业务键的不同原始意图返回 `ErrIdentityConflict`，两者都不重置状态。

实际：原请求返回 identity conflict；把新启动请求的 Data/DeadlineAt 改成当前运行值却成功。8 个反例覆盖内存/正式 MongoStore 两来源，各含步骤推进、全部完成、Resume 改期限与清期限。Mongo 路径每次换 Store/Engine 并重读，原信封经过 `handleNestStart`。

修前文本：`original start redelivery rejected after progress: saga: idempotency identity conflict`；`runtime state accepted as a new start intent after progress: <nil>`。完整红文本与旧源码 overlay 在[证据](../bugfix/evidence/noncore-bugfix-20261005-16/README.md)。不是编译失败或超时红。

## 根因与影响

基线 `saga/engine.go:185` 的 `StartSaga` 在重复键分支比较 `existing.Data`、`existing.DeadlineAt`；同文件 `applyCompletion` 和 `Resume` 正常修改这些字段。不可变启动身份和可变业务状态混在一起。此前 `TestStartSagaRejectsBusinessKeyWithDifferentIntent` 只在推进前比较，截止精度回归也没有 Resume 后重投，因而漏检。

原启动消息可能持续 NAK、占用消费者额度并最终进入终止/死信；错误的不同请求被当成已有结果。不会因此新建第二笔 Saga，但破坏启动幂等和冲突判断承诺。

## 修复与边界

新增持久 `Record.StartDigest` / BSON `start_digest,omitempty`，固定规范化原始字段的 SHA-256；显式 ID 单独判断。步骤、恢复与完整 Replace 原样保存摘要。[修复/兼容](../bugfix/RR-20261005-NC-39.md)。

旧缺摘要记录仍可读取/运行；只有未推进的初始记录可按旧值接受重复，已推进者明确冲突，不从当前状态伪造原始身份。不自动补历史数据或改生产回执。真实 Mongo/混跑旧 writer 的升级演练未验收。
