基线：Core `41d49b982b0ec2c1b6c73bf6bfd8e4f8af15c54b`、Kit `48301507d06343f0de788de38f8a670f45adcf49`、Codegen `242b4384d4d96ad616b4197396c55972835cd741`。本轮只审查与写文档，未修代码。[交接验收与运行](../review/REVIEW-2026-09-16-05.md)。

## RR-20260916-06：最后一个 manager 启动期间 Stop，成功启动的对象未清理

**P2，Core，未修复；Kit ManagerMod 同样受影响。** 位置：[manager/engine.go](../../manager/engine.go):113 Start、:136 stopRequested、:160 started 追加、:182 stopStarted。Kit manager/manager_mod.go:74 转发 Start。

一次可控交错：

1. Engine 只有一个管理器；其 Start 已进入，但被 channel 阻塞。
2. 并发调用 Engine.Stop；Stop 置 stopping=true，并取走当前为空的 started，返回。
3. 放开管理器 Start，让它成功返回；Engine 将它追加到 started，循环结束直接返回 nil。
4. Start/Stop 均结束，管理器 starts=1、stops=0，资源仍在运行。若再补一次 Stop 才会被清理，但调用者正常的一次关闭流程并无此补偿义务。

期望：启动期间的停止请求必须与成功启动对象交接；不能让停止请求已生效后 Start 仍报告整体成功且漏清理。独立 race 复现 last 失败，has_next_control 通过：后面还有一个管理器时，下一次循环顶部的检查恰好完成补偿。根因就是回收依赖“还有下一轮循环”。

影响：最后一个（包括唯一一个）管理器的 goroutine、连接、监听或其他生命周期资源可在关闭后遗留。不是数据竞争检测能捕捉的问题，是合法锁操作之间的业务时序缺口。

建议：明确 starting/running/stopping/stopped 状态与启动中对象的归属。每个 Start 成功返回后，在同一状态锁下完成接纳/停止判定，保证停止路径或启动路径中恰好一个负责清理；包括循环尾部。不要简单持有引擎锁调用用户 Start/Stop（可重入且可能阻塞）。说明 Stop 是否等待在途启动、如何处理 context 超时、回滚错误，以及成功 Start 之后停止的错误归属。修复验收必须检查清理次数**等于 1**，并覆盖单个、最后一个、中间一个和停止错误。

现有 engine_test.go:309 的并发测试只检查“次数不大于 1”，并额外调用 Stop；:391 的关停测试在慢管理器后安排第三个对象。两种测试都可能漏掉本边界。M-09 是原样迁移，旧 Kit 527eecd 的同一逻辑也有缺口；本轮不将其称为迁移新引入的回归。

## RR-20260916-07：第一个 manager 启动期间仍接受 Register，新增对象永久未启动

**P2，Core，未修复；Kit 转发继承该行为。** 位置：[manager/engine.go](../../manager/engine.go):56 Register、:59 started != nil、:113 Start、:117 pending 快照、:160 首次写入 started。

Start 已复制 pending 并进入第一个管理器的慢 Start，此时 started 仍为 nil。Register 只用 started != nil 判定启动是否开始，因而返回 nil，把新管理器加入 managers。pending 已经固定，晚加入者不会启动；随后 Stop 只清理 started，它也不会停止。独立测试：err=nil、late.starts=0、late.stops=0、Managers 长度为 2。

期望：按现有 ErrRegisterAfterStart 契约，在开始启动时就关闭注册，返回该 sentinel；若要支持动态加入则必须设计另一套接纳与补启动协议。不能成功接纳却永久漏启动。业务依赖通过 Manager(name) 看见该对象时，可能使用未初始化的资源。

建议：在 Start 获取 pending 的同一临界区标记 starting；Register 按显式状态拒绝，不能借“是否已有一个成功启动者”代替生命周期状态。定义启动校验失败后能否重新配置，补空 manager 集合、第一次启动阻塞、首次启动失败、启动完成和停止后的注册边界。可与 RR-06 同一状态机改造，但两项用不同回归测试验收。

## 独立复现（完整 manager overlay 测试）

以下文件放在仓库外，再通过 go test -overlay 映射到 core/manager/review_lifecycle_test.go：

```go
package manager

import (
	"context"
	"errors"
	"github.com/spf13/viper"
	"github.com/tjbdwanghaibo/roost-core/app"
	"sync/atomic"
	"testing"
	"time"
)

type reviewManager struct {
	name             string
	entered, release chan struct{}
	starts, stops    atomic.Int32
}

func (m *reviewManager) Name() string { return m.name }
func (m *reviewManager) Start(*app.Registry) error {
	m.starts.Add(1)
	if m.entered != nil {
		close(m.entered)
		<-m.release
	}
	return nil
}
func (m *reviewManager) Stop() { m.stops.Add(1) }
func reviewWait(t *testing.T, c <-chan struct{}) {
	t.Helper()
	select {
	case <-c:
	case <-time.After(3 * time.Second):
		t.Fatal("timeout")
	}
}

func TestReviewManagerStopDuringStart(t *testing.T) {
	for _, another := range []bool{false, true} {
		name := "last"
		if another {
			name = "has_next_control"
		}
		t.Run(name, func(t *testing.T) {
			m := &reviewManager{name: "slow", entered: make(chan struct{}), release: make(chan struct{})}
			defer func() {
				select {
				case <-m.release:
				default:
					close(m.release)
				}
			}()
			ms := []app.IManager{m}
			if another {
				ms = append(ms, &reviewManager{name: "next"})
			}
			e := NewEngine(ms...)
			if err := e.Provide(app.NewRegistry(viper.New())); err != nil {
				t.Fatal(err)
			}
			done := make(chan struct{})
			var startErr error
			go func() { startErr = e.Start(); close(done) }()
			reviewWait(t, m.entered)
			stopDone := make(chan struct{})
			go func() { _ = e.Stop(context.Background()); close(stopDone) }()
			// Ensure Stop has recorded the request before allowing Start to return.
			deadline := time.Now().Add(3 * time.Second)
			for !e.stopRequested() {
				if time.Now().After(deadline) {
					t.Fatal("Stop not entered")
				}
				time.Sleep(time.Millisecond)
			}
			close(m.release)
			reviewWait(t, done)
			reviewWait(t, stopDone)
			if m.stops.Load() != 1 || startErr == nil {
				t.Fatalf("shutdown lost: starts=%d stops=%d startErr=%v", m.starts.Load(), m.stops.Load(), startErr)
			}
		})
	}
}

func TestReviewManagerRegisterDuringFirstStart(t *testing.T) {
	m := &reviewManager{name: "slow", entered: make(chan struct{}), release: make(chan struct{})}
	defer func() {
		select {
		case <-m.release:
		default:
			close(m.release)
		}
	}()
	e := NewEngine(m)
	if err := e.Provide(app.NewRegistry(viper.New())); err != nil {
		t.Fatal(err)
	}
	done := make(chan struct{})
	go func() { _ = e.Start(); close(done) }()
	reviewWait(t, m.entered)
	late := &reviewManager{name: "late"}
	err := e.Register(late)
	close(m.release)
	reviewWait(t, done)
	_ = e.Stop(context.Background())
	if !errors.Is(err, ErrRegisterAfterStart) {
		t.Fatalf("late registration accepted: err=%v starts=%d stops=%d registered=%d", err, late.starts.Load(), late.stops.Load(), len(e.Managers()))
	}
}
```

本轮实际命令：`go test -race -count=1 -overlay <review.json> ./manager -run TestReviewManager -v`。三个叶子 1 通过、2 失败；channel 控制交错，超时仅防止测试悬挂。测试使用停止状态轮询来同步进入点，没有修改被测实现。测试结束时不额外调用一次 Stop 掩盖 RR-06。它不启动真实后台资源，仅使用原子计数模拟生命周期。
