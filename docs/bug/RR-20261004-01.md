## 触发条件、预期与实际

- 触发：`beginWrite` → `rMu.Lock` → `TryLock` 的取锁脚本 `versionedTryLockLua` 已在 Redis 执行（owner 已是本次 token、fence 计数器已递增），但客户端没拿到回复：ctx 截止（`remote_entity.request_timeout` 很短或 Redis 慢）、连接断开、或脚本还在路上、稍后才落地。
- 预期：下一次 `TryLock` 以 Redis 为准——owner 是本锁对象自己没拿到回复的那一代，就重新取得（新 token、新 fence、新代际）；被别人持有走 NotAcquired；空闲正常取得。
- 实际：`TryLock` 用一枚新 token 争锁，Lua 只认 `owner == false` 或 RR-21 的 `releaseUnknownToken`，于是 `{0,0,0}` → `ErrVersionedLockNotAcquired`；`Lock` 的重试预算（默认 5 次退避）远等不到 TTL，这个实体的每次写都回 `remote_entity: shared lock <id>: versioned lock not acquired`，直到 LockTTL 过期。

## 根因（基线 `17ae93be` 行号）

- `remoteentity/versioned_lock.go:120-125` `TryLock`：`token := generateToken()` → `Eval(versionedTryLockLua, …, token, ttlMs, l.releaseUnknownToken)`，`err != nil` 直接 `return`；这次 token 不留在任何地方，脚本是否已执行无从核对。
- `:45` / `:302-310`：唯一能让 Lua 认出"自己的旧代"的 `releaseUnknownToken` 只由 `releaseOutcomeUnknown`（释放无答复，RR-20260930-21）写入；取锁无答复没有对应路径。
- `remoteentity/versioned_lock_lua.go:11`：取得条件只有 `owner == false or (ARGV[3] ~= "" and owner == ARGV[3])`，单个精确 token。
- 后果链：`remoteentity/batch.go:165-167` `beginWrite` 的 `rMu.Lock` 失败即拒绝这次写；`Lock`（`versioned_lock.go:171-210`）对 NotAcquired 按"别人持有"退避重试，预算用完返回；锁对象随 wrapper 常驻，LockTTL（缺省 24h）内无人续期也无人释放这枚租约。

## 修复约束

- 不伪造持有：没拿到答复的那一代不能当成本地已持有（不登记续期、不发许可）；只能让下一次 `TryLock` 交 Lua 由 Redis 判定。
- 不放宽 fence / 版本：重新取得是新一代，新 token、新 fence（authority 模式下仍由 `GrantWrite` 发 Mongo 许可），版本缓存不补写。
- 续期代际按 [RR-20260926-43](../bugfix/RR-20260926-43.md)；旧代迟到回复（含迟到落地的取锁脚本）不得破坏新代状态（[RR-20260924-20](RR-20260924-20.md)）。
- 与 RR-20260930-21 共用同一条"以 Redis 为准"的 Lua 判定，不另起机制；释放未知之后再有取锁未知时，两者都要能取回。

## 触发与实证

`TryLock` 在 `versioned_lock.go:120` 生成 token，`:122–124` Eval 出错直接返回，直到成功路径 `:160` 才保存 token。真实 Lua 已 HSET owner/PEXPIRE，但客户端返回 DeadlineExceeded 时，本地 acquired=false、没有记住本次 token；下一次生成新 token，ARGV[3] 只有旧 releaseUnknownToken，服务端拒绝 NotAcquired。Close 因 acquired=false 也不清理这个 owner。

隔离 Redis 8.8.0、TTL=24h，Lua 真执行后注入回复丢失。先断言 errors.Is(DeadlineExceeded)、本地未持有、真实 owner 非空、TTL>23h，再立即重取；实际：

> healthy Redis cannot reconcile our applied acquisition before TTL: versioned lock not acquired

`applied_reply_lost` 和 `reclaim_reply_lost` 两个叶子失败；healthy/not_applied 两个控制通过，race 无诊断，退出1是行为断言。相同问题既发生于首次取锁，也发生于 RR-20260930-21 的释放未知回收脚本已换成新 token、但这次回复又丢失。独占实例与临时键已清理。不是 toxiproxy 真实弱网，也没有复现全部生成实体/authority/三资源压测。

## 影响与边界

锁对象自占的 lease 可阻止同实体随后写入，预算短于剩余 TTL 时持续 NotAcquired，长 TTL 放大可用性损失；没有证据证明这条路径造成 stale writer 越权或数据损坏。它与 RR-20260930-21 的“释放未知仍 acquired=true”是不同出口，不撤销该修复。本轮不改生产 Remote，不修这个新 RR。

## 实施方向与验收

优先复用 transaction-free 锁状态、随机 token、既有 owner/fence Lua 和 authority 许可；取锁出错保持“未获业务写许可”，保留尚需裁决的 attempt 身份，由 Redis 原子判断 owner，不无条件 DEL、不放宽 fence/版本校验、不直接把错误当成功。

不能仅把本次失败 token 覆盖 `releaseUnknownToken`：回收旧 S 时，新的 T 命令可能未执行（owner仍S）或已执行（owner是T），两者都需有界保留/裁决；下一次未知再发新 token 会继续扩大候选集合。可评估固定 pending attempt 的幂等脚本重问与完成后新代际切换，避免无界 token 列表；方案需与 authority GrantWrite 的未知结果/清理及 async touch 代际对齐，不在 review 文档假装已经实现。

验收至少覆盖首次/回收取锁的执行前错误、执行后丢回复、连续多次未知、明确别人持有、旧 owner 到期、解析失败、authority 不先准入、Close/重开对象边界、新 token/fence 与晚到续租隔离。当前只证明两个执行后反例和两个控制；没有承诺上述矩阵完成。
