# NC-83：生成的 player TCP 停机超时后丢掉 server 所有权，重试 Stop 在连接仍运行时报告成功；会话关闭订阅者阻塞时 StopWithContext 不受 ctx 约束

2026-10-05，基线 `50e9a4e8`。P2（生成工程 `internal/access/player/tcp/server_gen.go`，生成器 `codegen/internal/roost/render_player_tcp.go`）。状态：已复现、已修复（生成器）、声明场景验证，未发版；已生成工程需重新生成。[修复](../bugfix/RR-20261005-NC-83.md) · [本轮](../review/REVIEW-2026-10-05-noncore-n02.md)。

## 触发与影响

不配合 context 的认证回调（或 Dispatch handler）占住一个连接 goroutine 时：

1. `Server.Stop(ctx)`（基线生成器 `render_player_tcp.go:644`）首次调用把 listener 置空、关闭连接，等待超时返回 `context deadline exceeded`；
2. 第二次 `Stop` 看到 `listener == nil` 直接返回 `nil`，此时认证回调仍在运行（`authenticator_inside_after_second=1`）；
3. `Mod.StopWithContext`（`:376`）在 `Stop` 出错后照样 `mod.server = nil`，重试同样立即成功（`server kept = false`）；
4. `stopLifecycle`（`:522`）无条件 `<-lifecycleDone`：某个 `OnSessionClosed` 订阅者阻塞时，传入 100ms ctx 的 `StopWithContext` 1 秒后仍未返回。

App 的 `stopModSafely` 自己受 ctx 约束，单次停机不会因此卡死，也会按超时保留依赖；但“超时后用新 context 重试直到真实排空”这一既定停机契约（Ops 同类问题 RR-20261004-NC-04 已修）在 TCP 接入层不成立：直接调用方、测试或人工重试会把仍在运行的连接当作已关闭，进而释放其依赖。

## 根因

Stop 把“发起关闭”和“已经排空”合在同一个 listener 指针状态里；所有权在结果未知时就被释放。lifecycle 等待没有接收调用方预算。
