# 09-15 第六轮：Downstream 生命周期迁移

## RR-20260915-05 · P2 · SetDownstream 未迁移慢消费者回调

状态：新发现，未修复。Core `b58e2806da5f0912f0a96f1b0e4f92b4b93d9b4f`。Verify 图谱定位、精确 snippet、当前源码和临时 overlay。

位置：`room/room_broadcast.go:513` RoomBroadcaster.SetDownstream 只替换 envelopeSink.downstream；创建时在 428–435 行向原 sink 注册 handleSlowConsumer，关闭时使用保存的 unregisterSlowConsumer。`room/room_transport_sink.go:433` runNextCallback 根据自身 handlers 查找 room 回调。

复现：创建真实 RoomTransportSink A 和 B；NewRoomBroadcaster 使用 A，尚无 subject/subscriber 时 SetDownstream(B) 成功。随后注册主体和订阅，B 的 transport 对可靠快照返回该 session 的 ErrReliableBackpressure；默认策略成功剔除 session，B 的 OnSlowConsumer 已完成，但 room.Subscribers 仍保留原订阅。另一个断言确认 A.handlers 仍有一个该 room 回调。直接使用创建时 sink 的对照能清理订阅。

期望：替换后的 sink 具有同样的 room 生命周期处理能力，原 sink 不再拥有该 room 的回调。实际：新 sink 没有 room handler，旧 sink 的 handler 一直保留到 room.Close。当前复现刻意在第一次订阅之前替换，排除了传输基线热迁移这个额外前提。

影响：默认慢消费者剔除不释放 room membership、subscriber 配额和相关序号状态；旧 sink 还保留对 room 的引用及潜在旧事件入口。新 sink 的应用层 OnSlowConsumer 回调可以另行清理，但默认自动处理链失效。没有验证旧事件误删新订阅，后者仅保留为下一轮风险。

建议：把 downstream 更换与生命周期注册当作一次交接。检查新 sink 能力并注册处理器，注册失败保留原 sink/原处理器；成功后更新 downstream 和 unregister 所有权，再解除旧注册。同实例重复设置应避免重复注册；旧在途回调可考虑 generation 校验。仍需单独定义已有传输基线迁移或限制，此问题即使没有既有基线也能触发。仅提供方案，未修改源码。

与 RR-20260915-04 根因不同：本项不需要“剔除后剩余批次失败”，新 sink 正常派发且已完成回调；缺的是构造后更换时的 room 注册。旧 RR 本轮不验收。
