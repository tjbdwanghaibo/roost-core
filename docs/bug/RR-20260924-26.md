# RR-20260924-26：未复制 Redis 锁写丢失后，已确认 fence 被复用

2026-09-24，基线 967bc69 加当前 Remote 优化工作树；P1，生产 HA 准入未通过。**历史失败已复现；2026-09-25 根因修复与针对性回归通过，见文末**。范围是允许自动副本晋升的 Redis Cluster，不能用单节点长稳或“副本已追平后再杀主”的绿色结果替代此项。方案见 [修复设计与当前边界](../bugfix/RR-20260924-26.md)。

## 真实复现

```sh
ROOST_REMOTE_CLUSTER_IT=1 GOWORK=off go test -race -tags=integration \
  ./remoteentity -run '^TestRealRemoteRedisClusterUnreplicatedFence$' -count=1 -timeout=120s -v
```

独立 3 主 3 从 Redis Cluster，全部 AOF always。等待初始复制完成，然后：

1. 暂停目标槽位的唯一 replica，并由主节点关闭该 replica 的复制连接，确保接下来的写不能被副本接收。
2. 正式 Remote versioned lock 在主节点获取锁成功，调用方收到 **fence=1**。
3. 强杀主节点，恢复 replica，让集群正常选主。
4. 同一实体再次获取锁，返回 **fence=1**，而不是大于已确认值。

实测失败信息：`PRODUCTION_GATE_FAILED: acknowledged fence 1 reused after unreplicated primary failure: new fence=1`。测试主体 12.90s，原始日志 `/tmp/remote-cluster-unreplicated.log`。只操作夹具自己的进程和数据。

## 根因与影响界限

`versionedTryLockLua` 的 fence 使用 Redis 非过期 INCR key，但“非过期”不等于跨异步复制故障持久。主节点本地 AOF 持久化并不能让尚未收到写的副本拥有该值。路由刷新、延长租约、增加重试、hash tag 都不能解决这个问题。

Mongo 提交还校验 ExpectedVersion/epoch，并不据此推导本测试已发生重复落库或业务数据损坏；本条实际证明的是已确认的 lock fence 不再跨该故障单调，旧 owner fencing 的前提不成立。测试只覆盖 lock fence，ownership marker 在同一存储上的回退风险尚未单独穷尽验证。


## 2026-09-25 修复进展

正式 Assembly 现在使用 Mongo 多数派持久化所有权与写许可，Redis 只协调竞争。共享和 owner-routed 写均先取得许可，提交事务原子匹配最新许可、所有权代际与版本；同一文档的写冲突覆盖授予和提交的竞争。不支持的 meta 拒绝自动接管。用户确认未部署后，已删除未发布的迁移入口及弱校验分支；当前 MongoCommitter 默认强制许可，见 [RR-20260925-02](../bugfix/RR-20260925-02.md)。

同一真实六节点故障保持原失效条件：Redis 计数器仍是 **1 → 1**，持久化许可是 **1 → 2**；测试额外断言旧业务提交失败、新业务提交成功，已通过（race，13.66 秒测试主体）。原始反例未删除，也没有把 Redis 回退当成 fencing 通过。三种持久化策略的正式生成业务链通过。完整范围、后续压测和未验证项目见 [修复记录](../bugfix/RR-20260924-26.md)。
