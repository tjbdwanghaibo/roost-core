## RR-20260911-03 · P2 · finalizer 停止后仍接受晚到的 Close

- 位置：`remoteentity/transaction_manager.go:139`、`:148`、`:292`；`remoteentity/batch.go:455`。
- 触发：停止前已取得的 RemoteWriteBatch 进入 Indeterminate；StopFinalizer 成功返回后才执行 Close。无需在停机后创建新 batch。
- 期望：Close 同步释放资源，或将所有权交给仍会完成清理的消费者；停止完成后不能再次成功交接到已退出的队列。
- 实际：deferRemoteClose 的 select 同时面对可写的缓冲队列与已关闭的 finalizeCtx.Done，仍可能选择入队并返回 nil。最终 drain 只等待 finalizer workers/retryWG，未排除外部 batch.Close 的后续发送；finalizeOnce 又阻止重启。Close 已设置 closed 并清空自身 entries，重复 Close 不会补清理。
- 影响：遗留 writeGate、ownership 读锁、wrapper 引用及 finalize slot。若 entry 持有分布式锁，也会遗漏该路径的 unlock；这一后端影响为源码推断，未连接真实 Redis 验证。进程内 Manager 留存或关闭顺序交错时尤其值得处理。
- 证据：64 个停止前创建的 batch，Stop 后依次 Close 均返回 nil，但实测遗留 queue=29、slots=29。测试随后手动清理仅用于避免测试自身泄漏，不属于修复。select 的随机选择使具体数量不固定。
- 边界：没有证明默认应用装配的正常停机顺序必然触发；先排空所有 batch 再停止 finalizer 可避开此交错，但底层生命周期契约缺少交接保护。
- 建议：在停止与所有外部发送者之间建立同一准入/交接屏障，确保每个 entries/slot 恰好有一个清理者；仅在 select 前检查一次 ctx 不能消除并发窗口。

## RR-20260911-04 · P2 · Nest 丢弃已接受的延迟同步请求而不回复

- 位置：`nest/dispatcher.go:173`，尤其 `:202`；`nest/client.go:255`；`nest/nest.go:353`。
- 触发：合法已注册 handler 的 Request 使用 SendOptionWithDelay，消息已进入延迟队列但尚未到期，此时 Shutdown。
- 期望：已接受请求最终得到执行结果，或收到明确的停止错误；不能仅回收消息而留下等待者。
- 实际：OnDestroyWithContext 取走延迟队列后直接 recycleMsg，没有向 RetChan 发送终态；Shutdown 返回成功，Request 仍等待自己的 context 或同步超时。这里不是永久无界等待：waitResult 有超时分支，但调用方失去及时且准确的停止结果。
- 影响：停机期间额外保留请求等待与上游连接，错误语义退化为取消/超时。group_transition.go:375 的重新排队也保留 RetChan，因此可能涉及内部延迟重试；本轮只动态验证显式延迟请求，内部重排为源码推断。
- 证据：等待 delayedCount>0 后执行 Shutdown，成功返回后 50ms 仍未收到回复，取消请求才退出。已注册有效 handler 的独立 race 复现失败；没有 race detector 数据竞争报告，这是生命周期逻辑缺陷。
- 建议：队列回收前统一完成同步请求的停止回复，保证与到期分派互斥并且最多回复一次；增加显式延迟和内部重排请求的停机回归。
