# RR-20261004-09：RefHMap 注册表 guard 逐字节比较，无 schema 变化的并发首次创建 / 并发删除也误报 `ErrRefHMapRegistryChanged`；经 Layered 时 L1 还留着已被删除的值

日期：2026-10-04。基线：v1.19.1（`d3e69336`）。来源：[NC-30 复审 §4 D1](../review/REVIEW-2026-10-04-nc30-audit.md)。等级 **P2**（RR-20261004-NC-30 引入、已随 v1.19.1 发布的回归）。状态：已确认，未修复。

## 现象

真实 Redis 上 5 种无 schema 变化的情形，v1.19.1 返回 `ErrRefHMapRegistryChanged`，回退 NC-30 后都成功：同一新 key 两写者同时首次创建、两个 Delete 并发、Set 与 Delete 并发、Set 读完注册表后记录整条到期、经 `LayeredStore` 的首次创建。经过 `LayeredStore` 时更严重：`remote.Delete` 失败直接返回、不删 L1（`cache/layered.go:151-154`），Redis 里记录已被并发删除，本进程 L1 在 TTL 窗口内仍返回被删的值（探针：`A.Get still held=true`）。

## 根因

`cache/ref_hmap.go:49` 与 `:79`（`7fbdc735`）的 Set / Delete Lua 在 DEL 前把 root 上的 `__keys` 与调用方读到的注册表**逐字节**比较；注册表的出现 / 消失 / 重写本身（不改变布局）也会让比较失败。

## 修复约束

- guard 改为“当前注册表里的键都在本次 KEYS 里就放行”（Lua 内检查，不访问未声明键）；真正的 schema 竞争（注册表含本次布局之外的键）仍拒绝。复审在临时 worktree 试过该方案（`audit-nc30` scratchpad 的 `candidate-coverage-guard.diff`）：NC-30 12 条、RR-20261004-03 回归、6 个探针、整个 `./cache/...` 全绿。
- `LayeredStore.Delete`：远端删除失败时同样删除 L1（丢缓存总是安全的），再返回错误。
- 回归：5 种情形 + Layered L1 残留，真实 Redis；保留 NC-30 与 RR-03 的回归。
