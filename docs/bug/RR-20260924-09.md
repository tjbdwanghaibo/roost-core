# RR-20260924-09：DataEngine 等待投影与停机所有权时忽略截止时间

日期：2026-09-24。等级：P2。基线：`967bc69` 加已有 Sync/Nest 工作树，Go 1.27.0 / darwin arm64。状态：已复现、修复并验证，未提交、未发布；[修复记录](../bugfix/RR-20260924-09.md)。

## 触发与影响

Projector 正在调用较慢的 ProjectionStore 时，另一个 ReplayPass、Flush 或 Shutdown 进入等待；或者 Runtime.Shutdown 正等待 Outbox 退出，此时又有带截止时间的并发 Shutdown。

预期：等待者能返回自己的 context 错误，仍由当前持有者完成操作；未成功投影的数据保留 WAL，不允许为了及时返回而提前 ack 或关闭其他调用正在使用的资源。

实际：`Projector.flushMu`、`Projector.replayMu` 和 `Runtime.shutdownMu` 是普通 `sync.Mutex`，锁内包含存储、WAL 或 worker 退出等待。调用方 context 不能取消 Lock。后台投影使用 Projector 自己的 context，Shutdown 在 Flush 返回之后才执行 Close/cancel，因此即使后端响应 context，也不能解除这条等待链。

影响包括主动 Flush、启动恢复屏障及有超时预算的停机。已经修复的 nestwal.Committer 可取消等待不覆盖独立的 dataengine/engine.Projector 实现。本问题不是 WAL 数据丢失复现。

## 确定性复现

测试文件：[shutdown_deadline_test.go](../../dataengine/engine/shutdown_deadline_test.go)。用通道确认投影或 Outbox 已进入阻塞点，再发起带 20ms 截止时间的调用；1s 仅为测试失败上限，不靠 sleep 创建竞争。

```sh
GOCACHE=/tmp/roost-nest-go-cache GOWORK=off go test ./dataengine/engine \
  -run 'TestProjectorWaitsRespectDeadline|TestProjectorShutdownDeadlineBehindBackgroundProjection|TestRuntimeConcurrentShutdownHonorsDeadline' \
  -count=1 -timeout=30s
```

修前实际输出：三个测试的五个场景全部失败，均为 `operation remained blocked after its deadline`：

1. ReplayPass 等待另一轮 ReplayPass；
2. Flush 等待 ReplayPass；
3. Flush 等待另一轮 Flush；
4. Shutdown 等待真实后台投影；
5. Assembly → Runtime 的第二次 Shutdown 等待第一次 Shutdown。

前四项使用临时目录内真实文件 WAL，存储为可控替身；第五项使用真实 OutboxWorker 和可控 Claim。没有使用真实 Mongo/NATS 或物理断电实验。

首次编写测试时 Outbox 替身对重复 Claim 关闭同一通道，发生测试自身 panic；替身改成 sync.Once 后重新运行，以上五项均以超时断言失败，修前证据以此次完整复跑为准。

## 根因位置

- [projector.go](../../dataengine/engine/projector.go)：Flush 和 ReplayPass 的串行所有权等待。
- [runtime.go](../../dataengine/engine/runtime.go)：Shutdown 的串行所有权等待。
- [assembly.go](../../dataengine/engine/assembly.go)：正确保留未完成 Runtime，但无法替内部 Mutex 提供可取消等待。
