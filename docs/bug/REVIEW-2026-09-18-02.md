## RR-20260918-04 — P1：副本领取记录清理后，旧成功 Run 可再次发奖

**状态：新确认，未修复。** 关联 RR-20260917-08 / U-0226，但原来的即时重放、失败/过期副本路径已经修复。本项根因是新领取账本的保留期与 Session 实际重放寿命不一致。

位置：Codegen `demo/game/dungeon/dungeon.go.tmpl:26–45`、`demo/game/entities/player/profile_component.go.tmpl:104–120`、`demo/game/controllers/player/finish_dungeon.go.tmpl:65` 起；Core `service/session/service.go:556–561`、`service/session/redis_store.go:39–62`；Kit `service/session/session_mod.go:83–91`。

修复说明假设 `session.run_ttl=30m` 会使 Run 从存储消失，因此领取记录留 4 小时就安全。实际 `RedisConfig` 明确规定 Runs/Claims **没有存储 TTL**，只有 Requests 带 TTL；Kit 把 run_ttl 传给 Service 的运行期限。已成功 Run 在 Finish 的 Terminal 分支直接返回原成功终态，早于开放 Run 的超时判定。Sweep 处理结束与资源释放，也不能作为成功 Run 在 4 小时内删除的保证。

触发顺序：

1. Run A 成功，真实 Player+World Nest 事务记录领取身份并发 100 经验。
2. 超过 4 小时后领取另一个新 Run B。`ClaimDungeonRun(B)` 删除 A 的旧领取记录，再给 B 发 100 经验。
3. 再请求 FinishDungeon(A)。Session 仍返回 succeeded，账本却已无 A，事务再次给 A 发 100。

独立复现使用当前 CLI 生成的 Controller、sender、真实 Nest Engine、Player/World 实体和 DAO；Core Session 用 MemoryStore 与可控时间，committer 只返回接受成功（无真实 Redis/Mongo/WAL）。A 的首次领取时间通过 handler 的现有 nowUnix 参数建模，B 及 A 的重放走真实 Controller。期望两次合法奖励总计 200，实际 **300**；最后响应 `State:succeeded ExpGranted:100 LevelsGained:1`。Redis 无 TTL 的生产装配由源码补证，不宣称已运行 Redis 重启测试。

影响：保留原成功 RunID 的玩家，在新领取触发清理后可再次得到旧 Run 奖励。重复请求同一旧 Run 本身不会清理它，因为 claimed 查询先返回；需要另一次领取触发旧记录清理。不能把这个前置条件漏掉。

建议优先继续复用现有 Nest 与 DAO：先明确权威的领奖截止时间/重放拒绝规则，再清理去重记录。截止应基于可信的 Run 创建/结束时间，在所有可达领奖入口强制检查，并与保留期使用同一契约；既有数据也必须覆盖。若业务承诺无限期重试领奖，就不能仅按时间忘记已领取身份，应保留持久身份或使用可证明安全的压缩水位。单纯延长 4 小时、把 claimed 查询挪位置、给 versioned Run 随意加 TTL，均没有解决契约问题。

验收至少补：保留期内重试、边界等于/超过期限、领取 B 后重放 A、重启恢复、并发领取与清理、旧版本账本迁移。过期拒奖方案还须说明首次未领取但已过窗口的玩家如何处理，不把重复发奖变成静默漏奖。

## RR-20260918-03 — P2：nested DAO 替换与回滚未恢复通知归属

**状态：新确认，未修复。** 关联 RR-20260917-05 / U-0232；原 raw-map、setter、BSON 恢复后的深层通知 4 个场景已通过。本项检查新增绑定逻辑在替换/撤销后的归属。

位置：Codegen `internal/dao/template_nested.go:197–260`，尤其 `:200` 的 undo、`:219/:239` 的旧 child 解绑、`:229/:247/:256` 的新 child 绑定；当前生成例子 `internal/dao/testdata/golden/gen_equip_info_nested.go:172–201`。Core `nest/rollback.go:141–174`、`:341–375`、`:639`、`:907–921` 与 `dataengine/hook.go:6–15`。

map/slice setter 正常替换会解绑旧 child、绑定新 child；undo 闭包仅把字段值设回 old，没有撤销/恢复 callback。Nest 按逆序执行已登记闭包，RollbackUndo 的 DAO capture 仅恢复 tracker，不会自动遍历修复嵌套 hook。结果是字段身份恢复了，但运行时关系没恢复。

| 当前生成类型 | 正常替换后旧 child 不应通知 | 新 child 应通知 | 回滚后恢复的旧 child 应通知 | 回滚丢弃的新 child 不应通知 |
| --- | --- | --- | --- | --- |
| map[int32]*GemInfo | 通过 | 通过 | 失败：0 次，期望 1 | 失败：1 次，期望 0 |
| []*Child | 通过 | 通过 | 失败：0 次，期望 1 | 失败：1 次，期望 0 |
| *Child | 失败：旧引用未解绑，仍通知 | 通过 | 通过 | 失败：新引用未解绑，仍通知 |

单指针即使没有回滚也不解绑旧值，和 map/slice 分支不一致。上述独立场景不共享 child 给两个父对象，不依赖“多父对象共享是否支持”的未定义行为。

进一步把真实 HeroDao → EquipInfo → GemInfo 连上，在 `RunIsolatedTransaction` 中替换后返回错误，再在下一次成功事务修改恢复的 GemInfo.Level。对照产生 1 条 commit；回滚后实际 **Level=9、commit 数为 0**。不是仅多打一次 dirty：后续真实状态修改可以静默漏出持久化链。committer 为记录型替身，无 Mongo 崩溃验证。

建议生成内部“不标 dirty、不登记 undo”的绑定/解绑/恢复辅助函数。正常替换与撤销均应使“可达 child 集合”和通知所属父对象一致；undo 恢复最初值之前清理当前 children，再重绑恢复值。不要在 undo 中直接调用公开 setter：此时 tx 已是 rolledBack，会再次登记 undo/MarkPersist 而失败。处理同一 child 重叠、nil、多次替换、重复指针及 callback 身份，不通过全量序列化掩盖引用语义。顶层 DAO Init/替换/删除与 BSON 就地恢复也应纳入下一步一致性检查，本轮没有把它们判为全覆盖。

验收：本轮 map/slice/pointer 12 场景全部应绿；真实 DAO 后续提交对照 2 场景应绿；补失败、panic、确定性拒绝提交、多次写入回滚、restore 后继续写、并发入口持有 entity 锁的测试。不同失败模式不能仅由一个 handler-return-error 场景推断。
