# RR-20261006-10：驱动与 Mod 的 Close 口径不一致（重复 Close、并发 Close、Close 之后的调用）

2026-10-06，基线 `ba13cb05`。P3（停机重试与工具 / 集成测试的“已经关了”判断随驱动和部署形态变化；并发停止有数据竞争，现有 App 路径走不到）。来源：[WANTED W-2026-10-06-02](WANTED.md)（收尾第 1 批实测登记），维护者要求同类行为统一。状态：已复现；已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261006-10.md)。

## 机制

全仓的 Close / Stop 有三种口径，没有一处约定：

| 口径 | 对象（基线源码） |
| --- | --- |
| 重复 Close 返回 nil | mongo `Client.Close`（NC-260）、redis Cluster、redis `IPubSub`、kit `RedisMod` / `MongoMod` |
| 粘滞返回第一次的结果 | etcd `Client.Close`（`etcd/driver/client.go:177`，`sync.Once` + `closeErr`）、kit 单实例锁 `singletonStore.Close`（`kit/redis/singleton.go:144`） |
| 每次报错 | redis 单机 `Client.Close`（`redis/driver/client.go:473`，直接透传 go-redis，第二次返回 `redis: client is closed`）、nats `Assembly.Close`（`nats/driver/assembly.go:66`，第一次排空失败后每次都再排空已关闭的连接、每次都返回 `ErrClosedUndrained`） |

并发与关闭之后：

1. 并发 Close：redis 单机与 mongo 的后到者不等第一个释放完就返回（单机拿到 `ErrClosed`，mongo 从驱动拿到 `ErrClientDisconnected` 按已关闭返回 nil）；nats 的后到者与第一个同时排空，失败就硬关连接。
2. kit `RedisMod` / `MongoMod` / `NatsMod` 的 `StopWithContext` 读写 `m.asm` / `m.client` / `m.bus` 不加锁（`kit/redis/redis_mod.go:116/120`、`kit/mongo/mongo_mod.go:117/129`、`kit/nats/nats_mod.go:183/197`），并发调用是数据竞争，可能 Close 两次。App 每次停机对每个 Mod 只串行调一次，现有路径走不到。
3. Close 之后的调用：etcd 的 Get / Put / Txn / Grant / Revoke 等不快速失败——clientv3 的重试拦截器把“连接正在关闭”（`codes.Canceled`）当可重试错误一直重试，阻塞到调用方截止时间，没有截止时间就一直阻塞；nats `Client.Publish` 空等 3 × 20ms 重试，返回的错误不能 `errors.Is` 到 `fnats.ErrClosed`（`Request` 能）；redis `DistLock` 在客户端关闭后 Acquire 一次就把锁记成结果未知，之后一直返回 `ErrDistLockStateUncertain`，而 `ErrClosed` 按 `IsDefinitelyNotExecuted` 的分类是“确定没执行”。

## 触发与差异

预期（统一口径）：重复 Close 幂等返回 nil，第一次的错误只报一次；并发 Close 的后到者等第一个做完；Close 之后的其他调用返回已关闭错误。实际见下方修前红文本。
