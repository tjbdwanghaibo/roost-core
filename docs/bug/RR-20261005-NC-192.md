# NC-192：生产配置校验要求的一组开关没有任何代码读取——校验通过不代表限流、登录鉴权、WAL 持久生效

2026-10-05，基线 `f6245613`。**P2**（可观测性 / 误导：运维为了通过生产校验写下 `player_protocol.rate_limit.enabled: true` 等开关，以为相应保护已开启，实际没有任何组件读取它们；同时一份正确的生成工程打开 `env: production` 后起不来）。状态：已确认（源码 + 探针），未修复——修法需要维护者定（见“待定”）；**维护者选方案 1（决定 C1，2026-10-05），已修复、声明场景验证，未发版**（见文末）。[本轮](../review/REVIEW-2026-10-05-n14.md) · [证据](../review/evidence/noncore-review-20261005-n14/README.md)。

## 触发与差异

配置里 `env` / `app.env` / `environment` 为 `prod` / `production` 时，`validateProductionServiceConfig`（`app/config_validation.go:66-140`）按服务名追加要求。逐键查非测试 Go 与模板的读取方（[nc192-probe.txt](../review/evidence/noncore-review-20261005-n14/nc192-probe.txt)）：

| 服务 | 要求 | 读取方 |
| --- | --- | --- |
| game | `player.login_auth_required=true`、非 dev 的 `player.login_secret` | 无。生成的接入用 `auth.go` 的演示凭据（`codegen/internal/roost/help.go` 说明“上线前必须换成真实校验”），不读这两个键 |
| game | `player_protocol.rate_limit.enabled=true` | 无（只有 `app/app.go:121` 的 `SetDefault`）。生成的 player TCP 接入不用 `gateway.RateLimit`，仓内没有按请求限流的装配方（N02 观察 O6、NC-82 记录） |
| game / instance | `save_load.wal.enabled`、`save_load.wal.required`、`save_load.wal.mode=durable` | 无。当前 WAL 由 DataEngine 的 `dataengine.*` 配置决定 |
| game / instance | `instance.client_mode`、`instance.state_store_required` | 无 |
| account | `account.redis_required=true`、非 dev 的 `account.ops_token` | 无（`account.session_secret` 有读取方，要求成立） |
| global / match_group | `global.redis_required` / `match_group.redis_required` | 无 |

这些键来自开源初版（`e38264f7`）的服务形态；之后接入、持久化与服务实现都换了，校验没有跟着换。

- 预期：生产校验要求的每个开关都对应一个真实生效的保护；通过校验意味着保护已开启。
- 实际：上表的开关写什么都不改变运行行为；写下它们只是为了让校验放行。

## 复现（探针，未提交）

`project new -template game-demo` 生成的每份 `*.prod.example.yaml` 追加 `env: production`（并放开 `ops.allow_public_addr`）后跑 `ValidateServiceConfig`：

```
game: config: production game requires player.login_auth_required=true
      config: production requires non-dev player.login_secret
      config: production game requires player_protocol.rate_limit.enabled=true
      config: production game requires save_load.wal.enabled=true
      config: production game requires save_load.wal.required=true
      config: production game requires save_load.wal.mode=durable
account: config: production requires non-dev account.ops_token
         config: production account requires account.redis_required=true
global: config: production global requires global.redis_required=true
```

补上这些键之后校验通过，运行行为与不补完全相同。生成配置本身不写 `env`，所以默认部署不会走到这段校验；文档里也没有说明 `env: production` 的作用（`rg` 无结果）。

## 影响

- 误导：校验报错的措辞（“production game requires player_protocol.rate_limit.enabled=true”）让人以为框架有按请求限流、登录鉴权开关与 WAL 持久开关，补上即开启。生成的游戏服实际没有按请求限流，演示凭据也不会因为 `login_auth_required` 而失效。
- 可用性：按校验指引打开 `env: production` 的部署必须写入九个无效键才能启动。

## 待定（需要维护者选择）

1. **删去无效要求**，保留有读取方的（ops 暴露、`account.session_secret`、platform 密钥、admin_gateway、Redis 地址），并在 USER_GUIDE 写明 `env: production` 校验什么、不校验什么。代价：失去“提醒生产要有限流 / 真实鉴权”的形式化入口。
2. **换成当前真实生效的键**：WAL 持久性改查 DataEngine 的 `dataengine.*`；鉴权改查生成接入的真实开关（目前没有，需要先有）；限流先在生成接入里装配 `gateway.RateLimit`（或 `player_agent` 中间件）并给出配置，再由校验要求它。代价：限流 / 鉴权是功能工作（N02 / N08 范围）。
3. 维持现状只改措辞（说明这些键仅为部署声明）。不推荐：误导仍在。

## 验收覆盖点（按选定方案）

- 生产校验每个要求都能指到一个读取它的组件，`rg` 无读取方的要求为零。
- 生成工程的生产示例 + `env: production` 通过校验时，相应保护实际生效（限流 / 鉴权需要真实请求验证）。

## 修复（2026-10-05，维护者决定 C1：方案 1）

已修复、声明场景验证，未发版。[修复记录](../bugfix/RR-20261005-NC-192.md)。生产校验只保留有读取方的要求（ops 端点暴露、`account.session_secret`、`platform.session_secret` / `payment_secret`、admin_gateway 令牌、依赖 Redis 的服务的 `redis.addr`），上表九组无读取方的要求删除；`docs/USER_GUIDE.md` §10“`env: production` 校验什么”写明范围。以上原始现象保留不改。
