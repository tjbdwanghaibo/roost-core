## RR-20260918-01 — P2：sync=true 实体生成物与 Core 配置不兼容

**状态：未修复；Wanted-05 的生成入口缺口。** Codegen `internal/entity/gen.go:357` 附近生成 EntitySyncBuilderParam，`:362` 生成 FlushPolicy，`:367` 生成 SubjectPackerFactory；Core `entity/subject_sync.go:143` 的当前配置仅有 Enabled、Topic、PackerFactory。

真实 CLI 生成一个最小实体（EntityBase + ComponentManager + DaoManager，不含业务 DAO 或组件），在独立消费模块中直接编译当前 Core：

| 标签 | 生成 | 消费编译 |
| --- | --- | --- |
| sync=false | 成功 | 通过 |
| sync=true | 成功 | unknown field FlushPolicy；undefined entity.SyncFlushOnEntityRelease |
| sync=true subjectPacker=NewPacker | 成功 | 上述错误 + unknown field SubjectPackerFactory |

NewPacker 明确返回当前 entity.SubjectSyncPacker，排除了业务工厂签名错误。生成器自身 `go test -count=1 ./internal/entity` 通过，因此文本测试未捕获消费 API 漂移。这个问题在进入 RoomManager 之前就阻止正常构建，不是缺一个 Kit Mod。当前不含 sync=true 的 demo 能构建，不能替代这个 feature 的验收。

实施建议：以 Core 已统一的 PackerFactory 契约收敛模板和文档；移除过时 FlushPolicy 常量/字段。明确 syncPacker 与 subjectPacker 的兼容策略：迁移为同一入口、弃用并报可操作错误，或提供经过定义的适配；不要同时产生两个不存在/冲突的字段。增加真实消费模块测试，至少包含不带 packer、带当前 packer、旧标签迁移及 sync=false 对照。还应验证通过 BuildEntity 初始化时实际建立 Sync 状态，不能只修到编译通过。

## RR-20260918-02 — P2：RoomBroadcaster 隐藏的 coordinator 无法接入持久化水位

**状态：未修复；限于 pipelined commit 部署。** Core `room/room_broadcast.go:423` 配置、`:451` 构造内部 SubscriptionCoordinator，`:695` 订阅、`:968`/`:986` 批量准备/分发、`:1076` 单实体 flush；`room/room_manager.go:25` 的配置同样没有 durable watermark。对照 `entitysync/subscription.go:490` SetDurableWatermark。

EntityBase 的 LastCommitLSN 契约要求尚未达到 committer durable 水位的内容不外发。独立 coordinator 已提供 SetDurableWatermark，但 RoomBroadcaster 自行创建且私有持有 coordinator，RoomManager/Broadcaster 的公共配置和方法没有转交该来源，内部也没有调用安装。因此通过这条默认房间链不能使用已有的 pipelined 外发屏障。

独立消费测试通过公开 API 创建当前生成实体（sync=false，手动 EnableSync 是绕过 RR-01 的隔离方式）、RoomManager、RoomTransportSink，再连接记录型 AtomicBatchTransport。实体标记 LastCommitLSN=10，把部署 durable 水位建模为 9：首次订阅快照、FlushSubject 增量、FlushDirty 批量三条路径都已向 transport 准入 1 帧。房间层没有可设置水位的入口，所以测试没有伪称向它配置了 9。

对照使用同一个生成实体与真实 SubscriptionCoordinator，实际安装返回 9 的水位函数：三条对应路径均阻止投递并保留 dirty；水位升至 10 后各投递一次。三失败/三通过。**这是受控水位模型和真实编码/准入调用，不是真实 WAL group-commit、断电或网络到达测试。** 若部署使用同步持久提交或没有 pipelined committer，这个条件不成立；不把没有显式安装屏障的普通 coordinator 视为自身 bug。

与旧 RR-20260915-03 的关系：旧项是 coordinator 已配置水位时具体分支漏检查，本项是上层封装没有安装/配置现有能力，根因与实施位置不同。本轮对照仅用于定位新装配缺口，不更新旧问题的验收状态。

实施建议：RoomManagerConfig/RoomBroadcasterConfig 接受水位来源（复用现有 committer.DurableLSN 能力）；在房间可订阅、可启动 worker 之前安装到内部 coordinator。无需新建平行 coordinator，也不建议公开其可变裸指针。同步持久模式可显式无 gate；pipelined 装配遗漏时应拒绝启动或有明确校验。保留当前 coordinator 的延迟/dirty/批量原子语义，新增 snapshot/profile、单体/batch、并发提交、水位推进与重启的真实装配测试。
