# RR-20261006-15：同一步骤的尝试跨 Resume 累积超过 4096 后，这一步永远 Reserve 不了

2026-10-06，基线 `b549e4df`。P2（可达的活性故障：一个反复失败、被多次 Resume 的步骤，修好原因后再 Resume 也执行不了，直到旧 claim 过了 `receiptTTL`，缺省 30 天；
不丢数据、不重复执行）。来源：v1.23.0 发版文档 [impl-saga-drv-dao-rem.md](../release/v1.23.0/impl-saga-drv-dao-rem.md) SAGA-2 review 检查点
“`maxOperationAttempts` 4096 在多次 Resume 后可以被超过”（读源码推断），维护者 2026-10-06 要求本轮闭环。状态：已复现；已修复、声明场景验证，未发版。
[修复](../bugfix/RR-20261006-15.md)。

## 机制

- 步骤收件箱（原生 `DataEngineStepInbox` 与 Mongo `MongoCommandInbox` 共用 `saga/step_operation_inbox.go`）每次尝试写一份 claim，`expires_at = now + receiptTTL`。
  同一操作实例（saga + 方向 + 步骤，`Command.IdempotencyKey`）在 Resume 之后不变，新一生的 CommandID 是 `<key>:rN:<attempt>`，claim 继续累积在同一个 `operation_key` 下。
- 每生最多 `MaxAttempts ≤ 1000` 次尝试（`Definition.Validate`），**Resume 次数不设上限**（`Engine.Resume` 只要求记录是 Failed / ManualRequired）。
  第 0 步正向重试用尽 → Failed → Resume → 又一生 1000 次……五生就超过 4096；`MaxAttempts` 小时需要的 Resume 更多，但没有上限。
- `resolveOtherAttempts` → `operationClaims` 按 `{namespace, operation_key}` 取**全部** claim，`Limit 4097`，超过 4096 返回
  `ErrConflict: operation <key> has more than 4096 attempts`（`saga/step_operation_inbox.go:308-318`，修前）。
  其中绝大部分是判定时直接跳过的：可重试失败（`settled` 且非成功非拒绝）、被接替的（`superseded`）、旧一生的拒绝。

## 越界之后会怎样

- **拒绝，不溢出、不无界增长**：检查在写自己的 claim 之前，守卫让同一操作的 Reserve 串行，所以 claim 数停在 4097，之后每次 Reserve 都在写 claim 前失败。
- 消费者（`command_consumer.go:339-345`）把这个错误当可重试错误 nak；过了命令截止后走 `ErrCommandExpired` 分支 ack。协调器每次尝试超时、用尽重试后进入
  补偿或 Failed；再 Resume 也一样。直到旧 claim 按 TTL 过期，这一步执行不了。
- 只读的 `operationSuccess`（不执行的投递 ack 前重发成功）用同一个 `Limit 4097` 截断而不报错。修前它实际看不到截断：Reserve 的门让 claim 数最多 4097 = Limit。
  收窄扫描后这个上界不再成立，所以一并改为与 Reserve 同一查询、超过上限报错（见修复记录）。

## 修复

[修复记录](../bugfix/RR-20261006-15.md)：claim 标记 completed 时写 `outcome`；按操作的查询只取有影响的 claim（pending、任何一生的成功、本生的拒绝、没有 outcome 的旧 claim），
它们的数量是与尝试次数、Resume 次数无关的小常数，4096 改为只在数据异常时触发的上限。
