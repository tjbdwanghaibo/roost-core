## RR-20260922-01：自己 subject 的一组字段永不到达，而且它不是 RR-20260920-06

### 现象

wave 1（进程刚起、16 机器人 → sid 1000，同时 8 机器人 → sid 1001）：

```text
robot=1  player=900001  scene_expect: after 10s the client knows 16 subjects (want 2) and 56 frames; "pos_x" never arrived
robot=9  player=900009  ... 16 subjects ... 63 frames; "pos_x" never arrived
robot=4  player=900004  ... 16 subjects ... 59 frames; "pos_x" never arrived
```

3/16，与 `RR-20260920-02.md` 末尾记的"修后 3/16 失败、`own_updates=6~7`、缺 `pos_x`"一模一样。
probe C（sid 1001 侧 8 人，同一时刻 sid 1000 在重启后承压）：

```text
robot=1 ... knows 8 subjects and 23 frames; "equipment" never arrived
robot=2 ... knows 8 subjects and 24 frames; "pos_x" never arrived
robot=6 ... knows 8 subjects and 25 frames; "equipment" never arrived
```

所以丢的不只是位置那一组——`equipment` 也会丢。

### 为什么它一定是缺陷，且不是 RR-06

1. **U-0267 在位**：生成工程的 `internal/service/game/scene.go` 与 `game/scene/runtime/interest.go` 都带 RR-20260920-06 标记。
2. **全程没有一条 `scene: subscribe` WARN**——RR-06 的机制是"subscribe 被房间拒绝且永不重试"，那条 Warn 是它的
   必然伴随物；两个进程的日志里 WARN 只有 `slow dispatch`。
3. **机器人侧的两种解释都排除了**：
   - watcher 是**合并**不是替换（`cmd/loadtest/main.go` consume：`for key, value := range document { known[key] = value }`），
     所以字段不会"到过又被抹掉"；
   - `move` 到 (501,500) 相对出生点 (500,500) 是**真实变化**：`map_component.go.tmpl:105` 的 `from == to` 短路不会命中
     （`Place` 只在出生点被怪占住时才挪人，且环序先给 (499,499)），`:117-119` `SetPosX/SetPosY` + `PublishSyncDirty`
     一定执行，服务端 `handlerMovePlayer result=ok`。
4. 客户端"知道 16 个 subject、收到 56~63 帧"，会话与通道活着；同一批帧送到了别人。

于是结论只能是：**一次已提交的字段变化，没有送到它自己的订阅者，而其他订阅者收到了**。这正是 W-2026-09-20-02
原文的判断（候选 (b)："该订阅者的 baseline 在没收到那一帧的情况下被推进了"）。09-20 第三轮把它分流到 RR-06，
RR-06 是在查它时**顺带发现**的另一条真缺陷，但不是它。

### 根因——本轮没有定到行

这一条我诚实地写"未定位"。已经排掉的：LOD 筛字段（packer 忽略 profile，上一轮已排）、订阅被拒（本轮零 Warn）、
机器人合并/no-op move（本节 3）。剩下的候选仍是 W-02 的 (b)，落点在 `roost-core/entitysync` 的 prepared batch /
content version 与 `room.flushStateBatch` 的按订阅者分发之间。

**触发条件有了新信息**：warm 进程单独跑 16 人两次全绿（probe A、probe B），只有**进程刚起的头 16 个登录**
（wave 1）与**另一进程重启承压时**（probe C 的 1001 侧）出现。即：不是人多本身，是"首批帧 / 高延迟"下的次序问题。

### 一个必须排除的干扰项（给修的那一半）

机器人在 `enter_game` **之后**才 `scene_watch`（`demo.yaml.tmpl:18/24`），而 robot session 对没有 handler 的 push
是**静默丢弃**（`robot/session/session.go:285` 只在有 handler 时投递，无缓冲；`robot/robot.go:150` 的 capture
只能装在会话建立后）。`Scene.Join` 在 `enter_game` 应答前就同步 `applyChanges(ctx, Interest().Tick())`
（`scene.go.tmpl:297`）——首帧快照与客户端装 watch 之间**天然有窗口**。这解释不了 `move` 的增量为什么没到
（它发生在 watch 之后），所以不是本条的根因；但它让 `scene_expect` 对"首帧带的字段"的断言带有随机性。
修的那一半做判别实验时先把 `scene_watch` 挪到 `enter_game` 之前，或在 `scene_expect` 前再 `move` 一次，
把这个噪声去掉，再看剩下的红。

### 影响

P1：复制状态**静默少发货**，客户端对自己的位置 / 装备永久错误，40 秒不收敛（W-02 原记录）。

### 验收覆盖点

- W-02 草稿的 core 侧用例：一个房间 16 个 subject 各自订阅自己，先全量再同 tick 各改一字段并 flush，
  断言每个观察者收到**自己那个** subject 的改动；然后加 LOD band；然后在首帧未确认前叠加第二次改动。
- 端到端：进程冷起后的头 16 个登录，`scene_expect` 16/16；`scene_watch` 前置后再跑一轮，两个结果都要记。
- 把 `RR-20260920-06.md` 末尾"16 观察者用例未做"改成指向本条。

## RR-20260922-02：故障矩阵没有家了

### 现象

```text
ok   github.com/tjbdwanghaibo/roost-core/kit/dataengine  61.583s
?    github.com/tjbdwanghaibo/roost-core/kit/saga         [no test files]
?    github.com/tjbdwanghaibo/roost-core/kit/remoteentity [no test files]
ok   github.com/tjbdwanghaibo/roost-core/kit/nats         1.808s
[roost-it] roost-core checkout not found at /Users/whb/roost/roost-core/kit/../roost-core; core redis fault suites NOT run
```

### 根因

`kit/scripts/integration/dataengine-env.sh`：

- `:120` `go test -tags=integration ./dataengine ./saga ./remoteentity ./nats`——`kit/saga`、`kit/remoteentity`
  如今只剩 `mod.go` / `remote_entity_mod.go`，它们的集成测试早在 09-08 那轮随实现下沉到 core；两个格子是空的，脚本却报绿。
- `:130` `core_dir="${ROOST_CORE_DIR:-$repo_root/../roost-core}"`——`repo_root` 现在是 `roost-core/kit`，
  `../roost-core` 指向不存在的 `roost-core/roost-core`；`:139` 的"NOT run"是**唯一**的提示，退出码仍是 0。
- `.github/workflows/` 里**没有任何一个** workflow 调用这个脚本（`grep dataengine-env` 只命中 `ci.yml:34` 的一句注释）。
  合仓前它在 roost-kit 自己的 nightly 里；subtree 搬进来时 kit 的 `.github/` 没有跟进来。

### 为什么它一定是缺陷

CARRYOVER B1 的原话是"搬迁只移动代码不改行为，所以预期无差异——但没有证据"。本轮跑完的结论是：
**跑得到的部分是绿的**（13 个 `Real*` + 4 个 `Toxic*` 格子，见 REPRO），**但脚本自己不知道它少跑了六个套件**，
而且它在 CI 里已经不存在。一个"报绿但漏跑"的矩阵比没有矩阵更坏。

### 验收覆盖点

- 包列表以"有 `//go:build integration` 的测试文件"为准（本轮 grep：`kit/dataengine`×4、`kit/service/integration`×2、
  `kit/nats`×2、`service/mail`、`redis/driver`、`mongo/driver`、`kit/service/rank`、`etcd/driver`）；空格子应当是错误。
- `core_dir` 改成 `$repo_root/..`，或者干脆合成一段（现在是同一个仓）。
- 给它一个 workflow（nightly），并让 `ROOST_IT_TOXIPROXY=1`。

### B3：所有权三条（RR-09/10/11）两进程实跑

sid 1000 与 1001 同时服务各自的机器人，共享 Mongo / Redis / JetStream durable：

- **跨进程步骤正确让位**：1000 的 saga 消费者拿到 1001 玩家（100001–100008）的步骤，逐条
  `gift saga: step left to the player's owner … owner_sid=1001`，无一处越权写。
- **空闲归还真实发生**：两进程共 40 条 `player owners: idle lease handed back`，按 ≤8 条 / 次刷新分批
  （10:35:39 ×8、:46 ×8、:56 ×7、10:36:46 ×1 …）——**这就是 RR-20260921-04 说的 `handBackBudget` 在真实日志里的样子**，
  本轮因为撤离都很快所以无害。
- **零** `fenced`、**零** `lease lost`、**零** `renewal failed`、**零** `fatal projection version conflict`、
  **零** `enter_game: player is owned by another process`。
- 1000 重启后，1001 归还过的玩家的步骤由新进程接手：`gift saga: ran a step handed over by another process` ×20+。

没做的：RR-20260921-03 的窄窗口（归还进行中登录）无法用机器人对准，仍只有单测探针。

## 5. 观察（不登记）

- **冷进程 + 16 机器人：16/16 红，但服务端零 ERROR。** 1000 重启后立刻承接 1001 交来的 20 多个步骤，随后自己的
  机器人 7 个 `found_guild: guild is busy`（单个 Guild 实体，16 人争锁，`handlerFoundGuild` 0.8–1.4s）、
  9 个 `gift saga still waiting (step 0)`。都是机器人固定轮询预算在冷进程上耗尽；warm 进程同一脚本全绿。
  值得留意的一点：**交接来的别人的步骤排在自己的步骤前面**（同一条 durable）。是否算缺陷要看 saga 的公平性契约，本轮不判。
- p95 阈值：三次 16 人跑 p95 = 15.7–16.4s，卡在 `-max-p95 16` 上下；本机三节点 JetStream + 副本集 + 24 机器人的开销，不是回归。
- 生成配置的 `ROOST_EFFECTS` / `ROOST_SAGA` 各预留 8 GiB，itest 节点 `max_file_store` 4 GiB → `no suitable peers for placement,
  insufficient storage`，进程起不来。环境事实，改成 512 MiB 即可；已记进个人记忆。
