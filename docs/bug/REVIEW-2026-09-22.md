## RR-20260922-01：自己 subject 的一组字段永不到达，而且它不是 RR-20260920-06

### 现象

wave 1（进程刚起、16 机器人 → sid 1000，同时 8 机器人 → sid 1001）：

```text
robot=1  player=900001  scene_expect: after 10s the client knows 16 subjects (want 2) and 56 frames; "pos_x" never arrived
robot=9  player=900009  ... 16 subjects ... 63 frames; "pos_x" never arrived
robot=4  player=900004  ... 16 subjects ... 59 frames; "pos_x" never arrived
```

3/16，与 `RR-20260920-02.md` 末尾记的"修后 3/16 失败、`own_updates=6~7`、缺 `pos_x`"一模一样。
probe C（sid 1001 侧 8 人，同一时刻 sid 1000 在重启后承压）：

```text
robot=1 ... knows 8 subjects and 23 frames; "equipment" never arrived
robot=2 ... knows 8 subjects and 24 frames; "pos_x" never arrived
robot=6 ... knows 8 subjects and 25 frames; "equipment" never arrived
```

所以丢的不只是位置那一组——`equipment` 也会丢。

### 为什么它一定是缺陷，且不是 RR-06

1. **U-0267 在位**：生成工程的 `internal/service/game/scene.go` 与 `game/scene/runtime/interest.go` 都带 RR-20260920-06 标记。
2. **全程没有一条 `scene: subscribe` WARN**——RR-06 的机制是"subscribe 被房间拒绝且永不重试"，那条 Warn 是它的
   必然伴随物；两个进程的日志里 WARN 只有 `slow dispatch`。
3. **机器人侧的两种解释都排除了**：
   - watcher 是**合并**不是替换（`cmd/loadtest/main.go` consume：`for key, value := range document { known[key] = value }`），
     所以字段不会"到过又被抹掉"；
   - `move` 到 (501,500) 相对出生点 (500,500) 是**真实变化**：`map_component.go.tmpl:105` 的 `from == to` 短路不会命中
     （`Place` 只在出生点被怪占住时才挪人，且环序先给 (499,499)），`:117-119` `SetPosX/SetPosY` + `PublishSyncDirty`
     一定执行，服务端 `handlerMovePlayer result=ok`。
4. 客户端"知道 16 个 subject、收到 56~63 帧"，会话与通道活着；同一批帧送到了别人。

于是结论只能是：**一次已提交的字段变化，没有送到它自己的订阅者，而其他订阅者收到了**。这正是 W-2026-09-20-02
原文的判断（候选 (b)："该订阅者的 baseline 在没收到那一帧的情况下被推进了"）。09-20 第三轮把它分流到 RR-06，
RR-06 是在查它时**顺带发现**的另一条真缺陷，但不是它。

### 追加（2026-09-22，wire 级证据把根因收窄到"字段位丢失"）

给机器人加了一条探针：把它收到的**自己 subject** 的每一帧 wire 更新都打出来（`full/version/base/mask/fields`）。
干净世界、16 机器人一轮，4/16 失败，且**失败的 4 个恰好是从未收到过任何带 `pos_x` 帧的那 4 个**
（按真实 player id 对齐，不是巧合）：

```text
player=100015 own_updates=7 last=[ver=8 base=7 mask=0x712  fields=[_id attr_base attr_final equipment items level]]
player=100017 own_updates=7 last=[ver=8 base=7 mask=0x4712 fields=[… equipment guild_id level]]
player=100022 own_updates=7 last=[ver=8 base=7 mask=0x4712 fields=[… equipment guild_id level]]
player=100021 own_updates=8 last=[ver=9 base=8 mask=0x4000 fields=[_id guild_id]]        ← 收到了 ver 9，但只有 guild_id，没有 pos_x
邻居 100016     last=[ver=9 base=8 mask=0x30   fields=[_id items pos_x]]                    ← 同样 ver 9，是 pos_x
```

三件事把根因从"某个订阅者被漏发"收窄到"**累积的字段位在一次 flush 里丢了**"：

1. **通道是活的**：这些客户端各自收到 56–61 帧总量（别的 subject 一直在到），只有**自己 subject** 的
   `pos_x` 没来——排除"会话/连接问题"。
2. **不是 RR-06**：全程零 `scene: subscribe` 拒绝（U-0267 的重试机制的必然伴随物），且失败的是自己订阅自己
   （`SourceSelf`，band 恒 0，从不 reband，不会进 `Subscribe` 的 Pending 窗口）——排除"订阅被拒不重试"。
3. **100021 是决定性的一帧**：它**收到了 ver 9**，但 mask 只有 `0x4000`(guild_id)——它的建会（guild）改动到了，
   而紧随其后的 move 的 `pos_x` 位**没有出现在任何一版里**。版本号照常前进，字段位却少了。

**与"慢事务"强相关**：这 4 个都是建了公会的玩家，服务端对应 `handlerFoundGuild` 的 `slow dispatch`
（0.8–1.4s）。即：一次慢事务提交之后，紧接着的 move 的 dirty 位在"标脏 → Prepare 捕获 mask → Commit 按
generation 清 mask"这条流水线里丢了——`room` 有 50ms 周期 flush，所以**不是**"flush 没被触发"
（那样周期 flush 会兜住），而是 flush 真的跑了、版本真的前进了，delta 里却少了那次 move 的位。

**为什么仍然判"未定位、不硬修"**：把它坐实到行需要一条 core 层的红——在 `SubjectSyncState` 上并发
`MarkDirty` 与在飞的 `Prepare`/`Commit`（`entity/subject_sync.go` 的 `dirtyGeneration` / `dirtyMask` 清除逻辑，
以及 `room.flushDirty` 对 `r.dirty` 的取用与删除时机 `room_broadcast.go:737-743`）之间造出"版本进、位丢"。
本轮时间用在把现象钉死到"字段位丢失"这一层；红测试与定行留给修的那一半。这**不是**赶工能可靠拿下的
P1，按 skill §0 的约定不硬修。探针跑完即删，未改一行实现。


### 追加（2026-09-22 晚，用户要求"直接修"——但根因仍未定到行，如实记录已排除的机制）

1. **机器人帧解复用不会吞掉 push**（曾疑）。`demo/loadtest/playertcp/conn.go.tmpl:143` 明确按 flags 字节区分：

### 追加（2026-09-22 下午，判别 H1/H2：**H2，且根因定到行**——断线玩家撤不掉订阅，毒死整批 flush）

探针改成打印**每个观察者收到的每个 subject 的每一帧**（`FRAME t obs subj ver base mask fields`）与 move 应答时刻（`MOVE t player x y`），
冷进程 16 人再跑一轮（expB，超时 40s）：6/16 红，自视角没见 `pos_x` 的 subject 恰好 6 个。观察者 × subject 矩阵
（原始见 [REPRO §7](REPRO-2026-09-22.md#7-h1h2-判别观察者--subject-矩阵2026-09-22-下午)）：

```text
subject 100005（失败者）: 观察者 100001/100002/100003 收到 v9(带 pos_x)，其余 13 个观察者（含它自己）停在 v8
subject 100007（失败者）: 同样只有 100001–100003 收到 v11(pos_x)，其余 13 个停在 v10
所有 16 个观察者收到任何帧的最后时刻：100001–100003 = 15:16:16.712；其余 13 个 = 15:16:15.748–15.756
```

即 **15:16:15.75 这一刻，13 个会话的下发同时停了，只有 id 最小的 3 个还在收**。6 个失败者正是 move 落在这之后的 6 个
（MOVE 15.731–16.414），move 落在之前的都过了。**H2 成立**：版本产生了、送到了别人，只是"别人"只剩 3 个。
幸存者还收到**重复帧**（同一 `(subj, ver)` 各 21 次，间隔 ~200ms）——失败的批次一直在重试，每次都在同一处再失败。

机制（三段代码，一条链）：

1. **room 把一次 flush 的全部帧按 subscriber id 升序排成一批**（`room_broadcast.go:320 lessRoomFrameGroupKey`），
   一次 `AdmitRoomFrames` 交给 sink。生成工程的 `sceneLane.AdmitBatch`（`internal/service/game/scene.go:107-131`，
   codegen 模板）**逐个** `PushPlayer`，第一个失败就 `dropAsync` 并 `return err`；`SlowConsumerPolicy` 是
   `FailBatch`，于是整批判失败——**但排在前面的已经推出去了，不回滚；排在后面的一个都没推**。这就是"前 3 个收到、后 13 个没有"。
   coordinator 收到 admit 错误后 `batch.AbortWithError`（脏位保留）→ room 下一 tick 重试 → 前 3 个再收一遍（重复帧）→ 又在同一处失败。
2. **失败的那一次 push 是给一个已经断线的玩家**：`server_gen.go:826 pushPlayer` 对无会话的玩家返回 `ErrSessionNotFound`
   （**不计任何指标**，所以 `/metrics` 里没有 push 错误）。100004 是最早通过 `scene_expect` 的机器人，跑完脚本后
   `runner.go:403 defer rb.Close()` 断线，时刻正是 15.75；它的 id 恰好排在 100001–100003 之后。
3. **断线玩家撤不掉自己作为观察者的订阅**——这是 core 的缺陷，定到 `entitysync/subscription.go:300-312`：
   `SubscriptionCoordinator.Unsubscribe` 先把订阅置为 Closing，然后**必须**把一条 `EnvelopeLeave` 经同一个 sink
   投递给被撤订阅的观察者，投递失败就 `restoreActive` 并返回 `ErrEnvelopeAdmission`（`TestSubscriptionUnsubscribeFailureRestoresActive`
   把这当成约定）。对一个会话已不存在的观察者，投递**永远**失败，订阅**永远** Active，room 于是**每次 flush 都为死会话生成帧**，
   第 1 段的批次就永远在它那里断掉。`RetireSubject` 同理要向它自己的自订阅投 Leave，也失败；`UnregisterSubject` 因
   `ErrRoomSubjectHasSubscribers` 拒绝。RR-20260918-06 加的会话关闭钩子（`scene.go:159 watchSessions → Leave`）确实被调用了，
   但 `Leave` 的每一步都要向已死会话投递，所以钩子在这条路上**等于没有**。room / coordinator 都没有"不投递、直接遗忘一个不可达观察者"的入口；
   sink 的 `ReleaseSession` 没有任何调用者；所有失败只进 `slog.Debug` 与没人读的 `flushFailures` / `failedBatches` 计数——游戏日志 WARN/ERROR 全程为零。

运行时证据（expC，开 `log.level: debug` 再冷跑一轮，原始见 [REPRO §8](REPRO-2026-09-22.md#8-debug-日志坐实-leave-链路2026-09-22-下午)）：
15:27:00.444 第一对机器人（100007、100016）断线，随即 `scene: unsubscribe` **失败 196 次**，错误链
`entitysync: envelope admission failed → room: room frame admission failed → scene: push to player 100016: player tcp: session not found`；
16 个 subject 全部 `scene: subject not retired` + `scene: subject not unregistered`；00.43 之后只有 100001–100006（排在 100007 之前）
还在收帧，各收到 4 帧重复。这一轮 16/16 绿，只因为所有 move 都在 00.444 之前送达或首帧 v1 已带 `pos_x`。

**为什么此前的现象都说得通**：

- "冷进程才红、warm 全绿"：是"最后一个 move 送达"与"第一个机器人跑完断线"之间的竞赛。冷进程慢事务把中间步骤拉长，先完成者断线时后来者还没 move。
- "与 `handlerFoundGuild` 慢事务相关"：慢事务只是拉开机器人之间的进度差，不在链路上。
- "自己 subject 的字段没到"：`scene_expect` 只断言自己 subject，所以只看见自己的；其实被阻断的会话**什么帧都收不到**，
  probe C 丢 `equipment` 也是同一件事。W-02 原记录"40s 仍缺失"是真丢，不是迟到。
- 昨晚白盒用例证明的"脏位在流水线里不丢"是对的——丢的不在 entity / room 的脏位，在 sink 之后。

**定性**：两处缺陷，一条链。

- core（P1）：`Unsubscribe` / `RetireSubject` 把"通知观察者"当成"撤掉订阅"的前置条件，对不可达观察者没有退路，
  且失败不可见。修法方向：给 coordinator / room 一个**不投递的遗忘路径**（如 `EvictSubscriber(subscriber)`：直接删订阅、释放 budget、
  `envelopeSink.ReleaseSubscriber`），由会话关闭钩子调用，或在 `Unsubscribe` 收到 sink 的"会话不存在"类永久错误时走这条路；
  `flushFailures` / `failedBatches` 连续增长应有限频 WARN。
- codegen 模板 `sceneLane.AdmitBatch`（P2）：一个死会话不该饿死其后所有人。至少把死会话的错误收集后跳过继续推，或按 `AdmissionError{Session}`
  报给 sink 让 Evict 策略生效（现在 Evict 只认 `ErrReliableBackpressure`）。`pushPlayer` 的 `ErrSessionNotFound` 也该计指标。
- 验收：core 层红——一个 subject 两个观察者，sink 对观察者 B 永久拒绝，flush 后观察者 A 必须收到且 B 的订阅必须被清掉；
  端到端——16 机器人里让最早完成者立即断线，其余人的后续 delta 必须照到。

本轮**未修**：用户要求的是判别 H1/H2。探针与 debug 配置跑完已从 scratch 工程还原，仓库未改一行实现。

### 一个必须排除的干扰项（给修的那一半）

机器人在 `enter_game` **之后**才 `scene_watch`（`demo.yaml.tmpl:18/24`），而 robot session 对没有 handler 的 push
是**静默丢弃**（`robot/session/session.go:285` 只在有 handler 时投递，无缓冲；`robot/robot.go:150` 的 capture
只能装在会话建立后）。`Scene.Join` 在 `enter_game` 应答前就同步 `applyChanges(ctx, Interest().Tick())`
（`scene.go.tmpl:297`）——首帧快照与客户端装 watch 之间**天然有窗口**。这解释不了 `move` 的增量为什么没到
（它发生在 watch 之后），所以不是本条的根因；但它让 `scene_expect` 对"首帧带的字段"的断言带有随机性。
修的那一半做判别实验时先把 `scene_watch` 挪到 `enter_game` 之前，或在 `scene_expect` 前再 `move` 一次，
把这个噪声去掉，再看剩下的红。
