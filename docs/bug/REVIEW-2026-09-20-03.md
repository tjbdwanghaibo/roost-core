## RR-20260920-09：失而复得的租约配的是一份没人刷新过的实体

### 现象

两个进程轮换之后，某个玩家的写入开始出现版本冲突。按 `playerroute` 包注释，这条路的终点是
`fatal projection version conflict`——一个进程直接死掉。

### 根因

三件各自成立的事实合起来就是缺陷：

1. **常驻实体永不重新加载。** `entity/manager_access.go:83-90`：

   ```go
   if value := access.manager.GetWithCategory(meta.FullID, category); value != nil {
       return value, nil          // 命中常驻实例，不回源
   }
   ```

   `EntityManager` 没有任何淘汰入口（只有显式 `Destroy`），而生成工程里 Player **从不被 Destroy**
   （`grep Destroy internal/ game/` 只命中 spawner 的怪物）。`PlayerOwners.Release` 同样**一个调用方都没有**。

2. **租约可以失而复得，而复得被当成良性。** 生成工程 `internal/service/game/playerowner.go:212-223`：

   ```go
   mine, err := owners.Claim(ctx, result.PlayerID)
   case mine:
       slog.Warn("player owners: lease had lapsed and was retaken")   // 然后照常准入
   ```

   登录路径是同一件事的另一个入口：`enter_game.go:45-57` 的 `Claim` 成功后直接
   `Players().GetOrCreate(...)`，拿回的就是上面那份常驻实体。

3. **"中间没人写过"是没有证据的推断。** 键不存在有两种历史：没人拿过；**别人拿过、写过、租约也到期了**。
   `playerroute.Route` 只有 `{SID, Token}`，而 `Token` 按 RR-20260920-03 的修法**标识进程**、进程内固定，
   没有任何随每次 Claim 递增的世代号。两种历史在表上完全同形——探针里两条历史的终局逐字相同。

而失效期间另一个进程**确实会**写：`Owns` 对无主玩家答 true 并就地 Claim（这是设计），
`fence` 的注释也明说断开是为了"让玩家重连到那时的 owner"。所以"A 让位 → B 接管并写 → B 重启 → 玩家回到 A"
不是异常交错，而是把设计好的故障转移走了两趟。

### 影响

A 在失效期间的内存副本落后于文档。复得之后 A 继续从这份副本推进版本：轻则丢更新，重则版本冲突，
按本仓已有的实测结论是进程死亡。**准入门（U-0259）不覆盖这条**——它管的是"我现在还持有租约吗"，
而这里 A 确实持有；错的是它手里那份实体。

### 实施方向

要点是"失去过租约"必须使那份实体作废，而不是等到"现在还持有吗"。可选的方向：

1. 租约值加**单调世代号**（每次 Claim `INCR`），本地记住最近一次被确认的世代；复得时世代不连续就等于
   中间有人持有过。这是让两种历史可分的最小信息量。
2. 只要观察到一次"这把租约不是我的"，就把该玩家的实体一并卸载（fence 的语义从"停止服务"扩展到"扔掉副本"），
   复得时自然冷加载。注意这要求 Player 有一条真正的卸载路径——今天没有。
3. 退一步的兜底：复得时不复用常驻实体，强制回源比对文档版本，不一致就拒绝服务该玩家并告警。

验收至少覆盖：失效—他人写—复得后本进程的第一次写；失效—无人接管—复得（必须仍然是良性的，不能退化成
每次抖动都踢人）；登录入口与刷新循环两条复得路径；以及世代号或卸载路径在同 sid 重启后的行为。

## RR-20260920-10：后台工作会把离线玩家永久钉在一个进程上

### 现象

某个玩家在 B 进程反复登录失败，返回 `player_elsewhere`，owner_sid 指向 A；A 没有这个玩家的连接，
也没有任何人在玩他。等多久都不恢复。

### 根因

`playerowner.go:365-380` 的 `Owns`：无人持有时**就地 Claim 并答 true**——这是对的，离线玩家的邮件、
saga 步骤、已付款订单不能因为没人在线就永远不做。问题在于这把租约之后再也回不去：

- `Release` 没有调用方；
- Player 实体永不 Destroy，所以"所有权随实体结束"这条永远不触发；
- `refreshLoop` 对 `local` 里的每个 id 无条件续租，**不区分**这个 id 是在线会话还是一次后台工作带进来的。

于是一次给离线玩家的赠礼步骤，就让 A 永久成为这个玩家的 owner。而登录侧是 fail-closed 的
（`enter_game.go:52-57`，这是 U-0259 的正确部分）：落在 B 的登录按名拒绝。两条都对，合起来是一个
除非 A 重启否则不会结束的锁定。

### 影响与定级

玩家被锁在一个进程上，能否进游戏取决于网关把他分到哪里；N 个进程就是 1/N。没有数据损坏，
所以按本仓评级规则是 P2——**定级低是因为它不毁数据，不是因为后果轻**：这是一个付费玩家进不来的
故障，而且不会自愈。

### 实施方向

分歧点是"为了做一次后台工作而取得的所有权"应该有寿命。可选：

1. 后台取得的租约标记成**一次性**：工作完成就 `Release`（此时实体仍常驻——所以这一条必须和
   RR-20260920-09 的卸载路径一起定，否则等于把 U-0259 记录里说过的"放走常驻实体"重新引入）。
2. 给 `local` 分两类：有会话的持续续租，没有会话的只续到工作结束，之后让它自然到期。
3. 登录侧加一条移交协议（owner 收到"有人要登录"后卸载并 Release），代价是要有跨进程请求。

验收至少覆盖：后台步骤取得所有权后玩家在另一进程登录；同一玩家连续多次后台工作；owner 进程重启后的恢复；
以及"放走常驻实体"不得因此重新发生（这是 U-0259 明确排除过的方向）。

## 其他审查结论

- **`PlayerOwners.Claim` 的注释与代码不符**（安全方向）。注释写"登录路径放行并记日志，因为为一把陈旧租约
  拒绝登录比两个进程短暂分歧更糟"，而 `enter_game.go` 是 fail-closed 的按名拒绝。代码是对的，注释停在了
  U-0259 之前的设计上——它正好在解释本轮两条 RR 的那段逻辑旁边，建议随修复一起更正。不登记 RR。
- saga 的 `Admit` 缝**通过**：拒绝发生在 `inbox.Reserve` 之前（`saga/command_consumer.go:352-359`），
  不留认领；`MaxDeliver` 默认 25000，所以"弹给非 owner"不会耗尽投递预算变成丢步骤。
- U-0261 的 `validateRemoteCommitEncodable` **通过**：五个 commit 计数器、每个 mutation、每个 snapshot 的四个
  计数器都校验了，checksum 因为改存 8 字节 binary 而被**有意**排除且注释写明。审查上一轮建议的
  "在 durable admission 之前也校验一次"没有实现，但现在唯一能触发拒绝的输入是超过 `MaxInt64` 的单调计数器，
  没有触发路径，不登记。
- U-0267（兴趣系统重试队列）**通过**：队列上界落在写入口，`held` 里不存在或已被本 tick 重新订阅的条目在排空时
  被过滤；`Leave` 期间排队的 pair 不会产生虚假 unsubscribe。配套检查了"部分 Enter 留下幽灵 subject 导致无限重试"
  这条担心——`spatial.InterestManager` 的 `AddSubject` 与 `AddObserver` 校验逐条相同（`spatial/interest.go:209-264`），
  前者成功后者不可能失败，构造不出这个状态，不登记。
- 第十八批 Guild 的 `JoinGuild` **通过**：两处写在一个事务里；`Join` 对已是成员答成功而不是报错，与端点会被重试
  的事实一致；`handlerJoinGuild` 对"玩家 GuildID 为 0 但已在 roster 里"的残留状态是自愈的。
