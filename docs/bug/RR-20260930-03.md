# RR-20260930-03：`cache.AtomicLocalStore` 覆盖写无限追加时钟记录，Remote 快照 L1 缓存随写入次数线性增长（C01 堆涨到 4.7GB）

日期：2026-09-30。基线：`f46db3e`。来源：REMAINING C01（24 小时长稳）与其调查。等级 **P2**：长跑进程内存无上限增长、最终 OOM，不影响数据正确性。引入：`74e6d971`（V2.0，2026-08-22，v1.10.0 起所有版本都有；v1.17.1 同速增长，非本轮回归）。状态：已复现；2026-09-30 已修复（`c0d8826f`），未发版，见文末“修复”。

## 现象

C01：正式 kit Backend 装配、80 TPS strict、1000 会话、10000 实体、写许可 256，24 小时 6909969 笔。堆每小时最低值从 81MB 单调升到 2529MB（结束 4.7GB），约 366B / 请求，与 completed 线性相关；goroutine、`remote.Transactions`（< 65536 且早已饱和）、Wrappers、WALUnacked、metrics 序列数均平稳。

## 根因

`cache/atomic_local.go:190` `SetWithTTL` 每次写（含覆盖已有键）都 `shard.order = append(shard.order, atomicLocalOrder{key, generation})`；压缩旧记录只在 `evictLocked`（`:276-278`，`hand > 1024 && hand*2 > len(order)`），而 `hand` 只在需要淘汰（条目数或字节数超限，`:255-266`）时前进；`Delete` / 过期删除（`:210-235`）也不清理 order。
Remote 快照 L1 缓存（`entity/remote_snapshot.go:231`：65536 条目、256MB、64 分片 → 每分片 1024 条、4MB）在该装配里只有约 20000 个活跃键（每分片约 312），永不淘汰，`hand` 恒为 0，order 按“快照写入次数 × 40B”增长（发送方 `MongoStore.Project → RemoteSnapshotCache.Publish` 与接收方 NATS `ApplyUpdate` 各一份）。

红测试（调查员，10 个键覆盖写 10 万次，`live=10 order=100000 hand=0`）：

```go
package cache

import (
	"context"
	"testing"
)

// C01 调查红测试（未提交）：键集合远低于 MaxEntries/MaxBytes 时，同一批键反复覆盖写，
// 时钟记录 shard.order 应随存活键数有界，而不是随写入次数线性增长。
func TestC01AtomicLocalOrderBoundedUnderOverwrite(t *testing.T) {
	cfg := atomicTestConfig()
	cfg.MaxEntries = 1024
	cfg.MaxBytes = 1 << 20
	store := NewAtomicLocalStore(cfg)
	ctx := context.Background()
	const keys, rounds = 10, 10000
	for version := int64(1); version <= rounds; version++ {
		for key := range keys {
			if err := store.Set(ctx, atomicTestValue{Key: key, Version: version, Size: 1}); err != nil {
				t.Fatal(err)
			}
		}
	}
	shard := &store.shards[0]
	shard.mu.RLock()
	order, items, hand := len(shard.order), len(shard.items), shard.hand
	shard.mu.RUnlock()
	t.Logf("writes=%d live=%d order=%d hand=%d", keys*rounds, items, order, hand)
	if order > 4*keys+1024 {
		t.Fatalf("clock order grew with overwrites: live=%d order=%d (writes=%d)", items, order, keys*rounds)
	}
}
```

## 修复约束

1. `len(shard.order)` 必须随存活键数有界（例如不超过存活键数的常数倍加一个常量）：在 `SetWithTTL` 与 `Delete` / 过期之后，当 `len(order) - hand` 超过 `2 × entries + 常量`（如 1024）时就地过滤 `order[hand:]`，只保留 generation 等于 `items[key].generation` 的记录并把 `hand` 置 0；摊销 O(1)。
2. 不改变 Stale / Conflict / Superseded 的准入规则，不改变淘汰选择顺序（覆盖写 = 重新插入的时钟语义保持），不给读路径加独占锁；不采用“只在新键时 append”（会改变淘汰语义）。
3. 回归：覆盖写有界（上面红测试）；Delete / 过期交替写有界；压缩后淘汰顺序不变（A、B、C 写入、A 反复覆盖、超限时先淘汰 B）；`cache` 包与 `entity` / `remoteentity` 相关 race。
4. 修复后同参数跑 ≥ 60 分钟 heap profile，确认 `:190` 不再增长、堆平稳，再重跑 C01。

## 修复（2026-09-30）

修复提交 `c0d8826f`（分支 `fix-r14-cache`，基线 `f6566d4e`），详见[修复记录](../bugfix/RR-20260930-03.md)。按修复约束第 1、2 条实施：`SetWithTTL`（`evictLocked` 之后）、`Delete`、过期删除之后，当 `len(order) - hand > 2 × entries + 1024` 时就地只保留当前 generation 的记录并把 `hand` 置 0；不在淘汰循环内压缩，读路径不新增独占锁，淘汰顺序与准入规则不变。

- 回归 `cache/atomic_local_order_bounded_promises_test.go`：覆盖写、Delete 交替、过期交替有界，压缩后淘汰顺序不变（A、B、C，A 反复覆盖，先淘汰 B）；在 `f6566d4e` 上 4 项因“order 无界”失败（`live=10 order=100000 hand=0` 等），修后 `-race -count=50` 通过。
- 覆盖写基准：+15.9% sec/op（67→78ns），80→0 B/op。
- 65 分钟同参数 heap profile（`artifacts/perf/remote/c01x-heap-65m-c0d8826f-fix`，本地）：order 追加行 10m / 30m / 60m / 结束均为 10.80MB（修前 `:190` 15.68 → 59.99 → 103.89MB），inuse 总量 104.41 → 107.97 → 106.21MB（修前 119.97 → 169.30 → 210.95MB）；0 错误，全量核验通过。
