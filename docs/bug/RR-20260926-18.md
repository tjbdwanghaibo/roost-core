# RR-20260926-18：`nestwal.OpenRuntime` 打开的 WAL 在 `CommitterOptions.CloseWAL` 为零值时不被 `Runtime.Shutdown` 回收，目录锁与 writer goroutine 泄漏

日期：2026-09-26。基线：main `aaada47`。等级 P2（公开 API 缺陷；仓库内无调用方）。
状态：已复现（探针，已删除），源码已核对，未修复。来源：上线前复审（DataEngine 生命周期）。

## 触发条件

`nestwal.OpenRuntime(walOpts, applier, pub, nestwal.CommitterOptions{...})` 未显式设置 `CloseWAL: true`。`NewCommitter` 会给其他零值字段补默认值，唯独 bool 型 `CloseWAL` 保持 false。

## 预期 vs 实际

预期：Runtime 打开并拥有 WAL，Shutdown 成功即回收它。dataengine 侧同类问题已在 RR-20260924-11 修成“Runtime 拥有 WAL，与 CloseWAL 无关”。

实际：`nestwal/runtime.go:54-59` 只调 `Committer.Shutdown`；`nestwal/committer.go:318` 仅在 `c.opts.CloseWAL` 为 true 时关 WAL。Shutdown 返回 nil，目录仍被锁住。

## 复现

```text
GOWORK=off go test -race ./nestwal -run TestZZProbeOpenRuntimeShutdownReleasesWAL -count=1     （审查 agent 探针，已删除）
Runtime.Shutdown returned nil but the WAL it opened is still locked: nestwal: directory is already locked
```

## 实施方向（约束）

- 由 Runtime 负责关闭它自己打开的 WAL（与 RR-20260924-11 的 dataengine 修法一致），不依赖调用方记得设置 bool。

## 验收覆盖点

- `OpenRuntime` 零值 `CommitterOptions`：Shutdown 后同目录可再次 Open。
- 外部传入 WAL（非 Runtime 打开）时的所有权语义不变。
