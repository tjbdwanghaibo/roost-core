## RR-20260921-01：贡献的窗口没有回传，断言只能靠猜

### 现象

`framework-compat` 的 demo 格偶发失败（2026-09-20 12:15:01 UTC 一次）：

```text
robot action activity_standing: window race-1789906500 counted score=0 progress=0
for one dungeon clear (and its replay), want 1/1
```

`1789906500` 是 12:15:00 UTC，且被 `WindowSeconds = 300` 整除——机器人在上一个窗口
（`race-1789906200`，12:10:00–12:15:00）清的本，在新窗口里读的榜。

### 根因

三处，缺一不可：

1. **`Contribute` 知道自己写进了哪个窗口，然后把它扔掉。**
   `demo/internal/service/game/activity.go.tmpl:310` 现算 `activityID := gameactivity.ID(time.Now().Unix())`，
   拿着它调 `ApplyProgress` 并写 board，最后只返回 `Participant`——**`Participant` 里没有窗口 id**。
2. **端点连那个返回值也不要。** `demo/game/controllers/player/finish_dungeon.go.tmpl:132`：

   ```go
   } else if _, err := runner.Contribute(context.Context(), context.PlayerID, run.ID); err != nil {
   ```

   `FinishDungeonResponse` 只带 `State` 与 `Outcome`（`:70`），所以**没有任何客户端能知道自己那一点落在哪个窗口**。
3. **`Standing` 另算一次窗口。** `activity.go.tmpl:331` 同样 `gameactivity.ID(time.Now().Unix())`。
   两次调用之间没有任何东西把读锚定到写。

于是 `demo/cmd/loadtest/main.go.tmpl:445-460` 的断言只能这样写：拿到 `resp.ActivityID`、
**存进 blackboard**、然后对 `resp.Score` 下一个精确等于 1 的判断——却从不比较这个 id 与自己贡献时的那个。
跨过边界时它必然红，而错误信息把原因说成"计数不对"，指向的是计数逻辑，不是窗口换了。

### 为什么这是缺陷而不是"窗口本来就会滚"

窗口会滚是对的，`ApplyProgress` 对已完成的窗口也**明确拒绝**（`kit/service/global/activity/service.go:987`），
这些都没问题。缺陷在于**信息在一条没人接的返回值里断掉了**：写侧知道窗口 id，读侧知道窗口 id，
中间没有任何一环把两者对上。结果有两个：

- **CI 门禁失去意义**：它按一个自己没有钉住的前提断言，失败时指向错误的地方。这类抖动的代价不是"偶尔重跑"，
  而是下一次真的计数错误会被当成"又是那个窗口问题"。
- **客户端无法解释**：玩家 12:14:59 清本、12:15:01 打开排行榜看到 0。数据没丢（它在上一个窗口里，
  照常结算），但界面没有任何依据说明这一点。

### 实施方向

要定的是"贡献之后，调用方凭什么知道它落在哪儿"。可选：

1. `Contribute` 返回窗口 id（或把它并进 `Participant`），`FinishDungeonResponse` 带上它；
   机器人先记下这个 id，`activity_standing` 只在 id 相同时断言精确计数，不同则断言"上一个窗口有那一点"。
2. `Standing` 接受一个可选的窗口 id 参数，客户端查自己那一个。
3. 只改机器人：把 `finish_dungeon` 与 `activity_standing` 之间的时间钉在窗口内（例如贡献后立即读，
   并在边界附近跳过断言）。**这条最省事但最弱**——它让门禁绕开问题而不是覆盖它。

验收至少覆盖：贡献与读取在同一窗口（精确计数）；贡献在 N、读取在 N+1（必须能分辨出来，而不是报计数错）；
窗口未开时贡献被拒（现状是 `ErrMissing` 后只记日志，这条是**有意**的，见
`finish_dungeon.go.tmpl:126-129` 的注释，不要在这次一并改掉）。

## RR-20260921-02：demo-publish 从未发布过任何东西

### 现象

`gh run list --workflow demo-publish --limit 30` 在合仓前后都是 **0 次成功**。最后一步固定失败：

```text
! [remote rejected] demo-generated -> demo-generated
  (refusing to allow a GitHub App to create or update workflow
   `.github/workflows/ci.yml` without `workflows` permission)
```

### 根因

`.github/workflows/demo-publish.yml` 把 `roost project new` 生成的整棵树推到 `demo-generated` 分支，
而生成工程**自带一份 `.github/workflows/`**（`roost new` 的产物包含 CI）。GitHub 不允许 Actions 的
`GITHUB_TOKEN` 创建或修改 workflow 文件，于是推送被远端拒绝——与合仓无关，这条从一开始就是这样。

三仓合一仓（P5）修好了它前面的所有步骤（生成、编译、测试、`generate --check`、`id check` 现在都通过），
恰恰因此才暴露出后面这段一直是坏的：在那之前它总是更早地失败。

### 影响

`demo-generated` 分支上的内容是旧的或根本不存在，而 README 与 GENERATED.md 都把它当成"可克隆可阅读的
最新 demo"。没有任何人收到过信号——一条从未成功过的流水线，和一条从未存在过的流水线，在日志之外没有区别。

### 实施方向

要定的是"发布出去的 demo 要不要带它自己的 CI"：

1. 发布时剔除 `.github/workflows/`，在 GENERATED.md 里说明去哪看 CI——最省事，但读者少看到一块东西；
2. 换成带 `workflow` scope 的 PAT——内容完整，代价是多一个需要轮换的密钥；
3. 推到另一个仓库而不是本仓分支——同样要凭据，但把生成物与框架仓分开，README 的说法也更准。

这是产品决定不是技术决定，所以这里只列不选。无论选哪个，验收都要包含"**流水线成功一次**"这个从未被满足过的条件。
