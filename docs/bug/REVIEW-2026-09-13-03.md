## RR-20260913-10 / P3：快照 Lua 将 uint64 版本转为浮点，丢失排序精度

位置：[remoteentity/snapshot_l2.go](../../remoteentity/snapshot_l2.go):16–26 的 tonumber 与 HSET。实际 Redis 8.8.0 执行源码中的原始 Lua：

- 先写 9007199254740993，再写同字节的 9007199254740992，实际接受旧值，wire 中版本回退到 9007199254740992。
- 先写 9007199254740992，再写不同字节的 9007199254740993，实际被当成“同版本内容冲突”拒绝。

这是 Go 的 uint64 契约与 Lua 数值比较域不一致，两个表现同一根因，不拆编号。普通 1～32 并发发布正确保留 32 的对照通过。Marker/Route 同样使用 tonumber，存在同类精度风险，但本轮这两种数值未分别复现。

优先级 P3：触发值极大，正常从低位递增的业务不应把它当作近期主要故障；不能只因“跨语言数值”将它升为常见 P2。合法 API 没有限定在精确整数域内，迁移/导入的大值仍可能触发。

建议：明确并校验支持的计数域，或用精确十进制比较/编码实现 uint64 全域；比较后写回原始字符串，不能经过浮点归一化。真实 Lua 必须保留两条边界测试，现有 uint64 Redis 替身无法暴露该差异。

## RR-20260913-11 / P3：所有权 epoch 拼接成科学计数法并持久化坏记录

位置：[remoteentity/marker.go](../../remoteentity/marker.go):25–34 的 EnterShared Lua 以 `.. ((tonumber(currentFence) or 0)+1)` 拼接；:185–198 的 parseMarkerLease 只接受十进制 uint64。

预置格式合法的 lease `local:1001:100000000000000:1`，执行实际 EnterSharedExpected。Redis 写入 `shared:1001:1e+14:1`，然后 Go 解析失败；再次 GetOwnership 也失败。错误发生在 Redis 已写坏记录之后，不是安全地拒绝输入。

这是低频大计数边界，按 P3。预置仅为避免执行 10^14 次状态转换，输入在声明的 uint64 域内。LeaveShared/Transfer 也有数值拼接，列为同类待扩展，不声称本轮逐条复现。普通 claim→shared→local→transfer 与旧 CAS 拒绝均通过。

建议：保证线格式始终是精确十进制，先验证输出可表示范围再持久化；不要仅在 Go 返回解析错误，因为那时共享记录已改变。与 RR-10 协同确定 epoch 计数域，但此项的格式损坏与快照排序精度是不同根因/路径。
