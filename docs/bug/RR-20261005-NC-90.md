# NC-90：Bus 停止不等在途的 JetStream RPC handler，回包注定丢失、连接在 handler 底下被关闭

2026-10-05，基线 `be7bcc18`（N03 源码与 `7922e428` 相同）。**P2**（停止时在途的可靠 RPC：Stop 报告已排空而业务仍在跑，结果必然丢失并在 AckWait 后重投，产生重复执行）。状态：已复现（真实 NATS），未修复。[本轮](../review/REVIEW-2026-10-05-noncore-n03.md) · [证据](../review/evidence/noncore-review-20261005-n03/README.md)。

## 触发与差异

`nats.rpc.transport=jetstream` 的服务，一个 `HandleRpc` handler 正在执行时进程停机（`NatsMod.StopWithContext` → `Bus.StopWithContext` → `Assembly.Close`）。

- 承诺：`Bus.StopWithContext` 注释写“stops the worker pool and waits for it to drain within ctx. A ctx error only means this caller stopped waiting”；NatsMod 在 Bus 返回 ctx 错误时保留 bus / asm，因为“handler 仍在运行、连接仍在使用”（`kit/nats/nats_mod.go:160-166`）。也就是：停止返回 nil 代表 handler 已退出，连接可以关。
- 实际：JetStream RPC handler 不在 Bus 的 pool 里，而是在 nats.go 的 consume 回调 goroutine 里同步执行（`nats/driver/jetstream.go:74-77`）。停止只对它们调用 `sub.Stop()`（`bus/jetstream_rpc.go:243-247`），而 `pullSubscription.Stop` 只关闭 `done`（nats.go v1.53.1 `jetstream/pull.go:768`），不等在途回调；`Closed()` 在订阅已失效时立刻关闭（`pull.go:803-816`），也不能拿来等。于是 Bus 在 pool 排空后立即返回 nil，NatsMod 接着 drain 并关闭连接——JS 消费订阅已经退订，`Conn.Drain` 不再等它。

还有第二层：handler 的 `processCtx` 派生自 Bus 运行期 context（`bus/jetstream_rpc.go:464-476`），停止第一步就取消它（`bus/bus.go:345-348`）；回包用同一个 ctx 发布（`bus/jetstream_rpc.go:452`）。所以**即使 handler 在停止预算内正常完成，回包也必然以 `context canceled` 失败**，消息被 NAK / 未确认，AckWait 后重投给同服务的其他实例再执行一次。

## 复现（真实 NATS，隔离环境 15222～15224，独有前缀 / 流名，用后删除）

`TestRevn03ProbeJetStreamHandlerInFlightAtStop`：两个 NatsMod（sid 9301 服务端、9302 调用端），服务端 handler 进入后阻塞；调用端 `CallReliable`（8s）；handler 进入后对服务端 `StopWithContext(2s)`。

```
stop returned err=<nil> after 50.301084ms; handler still running=1
WARN nats jetstream: settling delivery failed; broker will redeliver after ack wait op=nak ... err="nats: connection closed"
handler ctx err when released: context canceled
caller result: nats: request timeout; handler runs=1
StopWithContext returned nil while the JetStream handler was still running
--- FAIL: TestRevn03ProbeJetStreamHandlerInFlightAtStop
```

Stop 50ms 就返回 nil，handler 仍在运行；放行后回包与 settle 都失败（连接已关），调用方等满 8s 超时。原始输出见[证据](../review/evidence/noncore-review-20261005-n03/probe-nats-baseline.txt)。

## 影响

- 每次滚动重启 / 正常停机，所有在途的 JetStream RPC 都变成“业务可能已执行、调用方超时、AckWait（默认 10s）后在其他实例重做”。对非幂等 handler 是重复副作用；对调用方是一次本可避免的超时。
- Stop 报告完成后业务代码仍在运行，依赖的 Mod（Redis / Mongo 等，NatsMod 的依赖在它之后停）可能已经关闭——违反“关闭排空的唯一收尾责任”。
- 轻量 RPC 不受影响：它的 handler 在 pool 里被排空，`Reply` 不带 ctx，回包能发出去。

## 验收覆盖点

- 停止期间在途 handler 未退出时，`StopWithContext` 只能返回 ctx 错误并保留责任；重试继续等同一批 handler，退出后才返回 nil、才关连接。
- handler 在停止预算内完成时，回包送达调用方、消息 ACK，不重投。
- 尊重 ctx 而因停止中断的 handler 不回“已取消”的失败包，消息交还 broker 重投（保持修前对这类请求的重投行为）。
- 停止开始后才到达的投递不进入业务，交还 broker；不在本实例反复 NAK 消耗投递次数。

本轮没做：JetStream 订阅缓冲里尚未回调的消息仍在 AckWait 后重投（不是本条承诺）；跨机器 / 集群节点故障。
