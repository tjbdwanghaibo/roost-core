# RR-20260926-20：Memory 持久级别（Durability 0）直接提交遇到“结果未知”时按失败回滚，并立即释放权限，不再负责恢复

日期：2026-09-26。基线：main `aaada47`。等级 P2（内存与已提交的 Mongo 状态分叉；已应用的 outbox 要等重启才发布）。
状态：已复现（探针，已删除），源码已核对，未修复。来源：上线前复审（Remote 持久权威）。

## 触发条件

DurabilityMemory 的 handler 写 Remote 实体（`nest/rollback.go:670-675` 允许，走 `remoteentity/batch.go:447-448` 同步提交），`CommitRemoteBatch` 返回裸错误，
例如 `session.WithTransaction` 在 commitTransaction 出现 UnknownTransactionCommitResult 后一直重试到超时（`remoteentity/mongo_committer.go:105-113` 原样返回），而服务端其实已提交。

## 预期 vs 实际

预期：未知结果 ≠ 未提交（roost-coding）：应标记 indeterminate，交给按状态驱动的 finalizer 恢复。

实际：`remoteentity/batch.go:456-463` 只在错误属于 `ErrRemotePersistenceIndeterminate` 或 Durability==2 时标 indeterminate；Durability 0 遇到其他错误直接
`rollbackRemoteEntries` 并隔离；Close 立即释放 gate 与锁，不排入 finalizer；调用方拿到普通错误而非 `ErrCommitIndeterminate`。
Mongo 中的 Applied outbox 只能等进程重启后由 `RecoverOutbox` 发布。这与 `transaction_manager.go:429` 中 tracker 把同一错误记为 Indeterminate 的做法不一致。

## 复现

审查 agent 探针（后端先真实提交，再返回 `context.DeadlineExceeded`；已删除，源码未保留）：

```text
memory commit err=context deadline exceeded indeterminate=false rolledBack(dirty)=true
stats after close={... ActiveTransactions:0 WritesInFlight:0 ...}
mongo state=2(Applied) pending applied outbox=1
```

复审方已按源码核对 `batch.go:456-463`。

## 实施方向（约束）

- 只有能判定“确定未提交”的错误才回滚；其余按不确定处理，保留 gate 交给 finalizer 回源，调用方得到可 `errors.Is` 的不确定错误。

## 验收覆盖点

- Durability 0 + 后端已提交后返回超时：不回滚，状态最终为 Committed，outbox 在本进程内发布，调用方得到不确定错误。
- 明确的 CAS 冲突 / 拒绝仍回滚（在快池持锁执行）。
