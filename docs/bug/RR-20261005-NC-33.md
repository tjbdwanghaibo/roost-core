# RR-20261005-NC-33：缓存副本信封与业务对象身份脱节

2026-10-05，P2；发现基线 `b2232db528de9947a2cf1cccaed79e7a9e29d2dc`。

## 承诺、反例与根因

配置了 `ReplicaConfig.KeyOf` / `VersionOf` 的接收端，应只将与信封相同身份的对象交给 Store。通用 Replicator 已检查 SyncMsg 与 Envelope，却无法理解第三层业务 payload。

[cache/mirror.go](../../cache/mirror.go) 的 `replicaStore.ApplyReplica` 原先反序列化后直接 Set。真实 Replicator 两个反例：信封 key7/version3 携带 ID8/version3，键8被写成 bad；携带 ID7/version4，键7被写成 version4，之后合法 version3 还被 Store 判为 stale。均返回成功。原始[红日志](../bugfix/evidence/noncore-bugfix-20261005-13/red.txt)保留，不依赖 panic 或超时证明缺陷。

这会破坏路由/去重域与实际更新对象的一致性，是内部协议完整性缺陷，不是发布权限绕过证明。与 RR-20260913-03 的 SnapshotReplicaStore 是不同适配器，不能从该历史修复推导通用缓存也已绑定。

## 状态追加
