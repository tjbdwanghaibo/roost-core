# RR-20261001-05：activity `applyProgress` 在 ledger 条目被 TTL 删除后永不回收 `PendingRequestIDs`，32 个孤儿后该参与者每个新请求永久 `ErrConflict`

日期：2026-10-01。基线：main `24d15652`。来源：[B 线 service 修复独立复审（后半）§3](../review/REVIEW-2026-10-01-bline-audit-service-2.md)（RR-20260929-02 修法引入）。等级 **P2**：CAS 成功、mark 失败、客户端没在 `ReservationTTL` 内重放的请求成为孤儿；累计 32 个后该参与者的每个新请求永久返回 `ErrConflict: pending progress confirmations are full`，ledger 恢复也无用，只有原客户端用同 requestID 重放才能释放一个名额，且没有 admin 对账入口。状态：已确认，未修复。

## 根因（到行）

`kit/service/global/activity/service.go:1072-1080` `applyProgress` 只把 ledger `found && Applied` 的 pending 当已确认并回收；ledger 条目被 TTL 删除（`!found`）时既不回收也不报错，`PendingRequestIDs` 只增不减。复审探针在 main 上实证（Memory ledger 手动 Delete 模拟 TTL），输出见复审报告。

## 修复约束

- `!found` 的 pending 视为已越过重试地平线，可回收（ledger TTL ≥ ReservationTTL 时客户端已不可能合法重放）；或改错误分类让调用方能区分“满了”与“冲突”；并补 owner-only 对账入口。写明选择理由。
- 回归：Memory + 真实 Redis（TTL 过期后回收），32 个孤儿后新请求仍能进入。

## 修复（2026-10-01）

状态改为**已修复**（Memory + 隔离真实 Redis 验证，已提交，未推送、未发版）。记录：[docs/bugfix/RR-20261001-05.md](../bugfix/RR-20261001-05.md)。

- `applyProgress` 的确认扫描把 `!found`（ledger 条目被 TTL 删除）的 pending 也回收：pending 只在条目 Create 之后才加入，条目消失即越过 `ReservationTTL` 这条客户端重试地平线，ledger 自己也已把重放当新请求；回收计入指标 `apply_progress.proof_expired`。接线不变量：ledger 存储 TTL ≥ `ReservationTTL`（正式装配两处同值；`New` 无法校验，写在 `Config.Ledger` 注释）。
- 满窗改报 `ErrProgressBacklog`（新码 `CodeProgressBacklog` 620119），不再是 `versionstore.ErrConflict`；调用方可区分“背压（≤ 一个 TTL）”与“CAS 争用（立即重试）”。
- 新 owner-only 入口 `Admin.ReconcileProgress(key, participantID, note)`：对每个 pending id 补上缺的 ledger mark 再释放证明（participant 写早已落地，补 mark 是完成第二步，不是断言）；备注必填，记在 `Participant.AdminNote / AdminActionAtUnix`。
- 修前红：`participant permanently refused after ledger expiry: versionstore: version conflict: pending progress confirmations are full`（Memory 与真实 Redis 3s TTL 真等过期都红）；修后 `./kit/service/global/...` race 两后端、`./kit/service/integration/` 真实 Redis 全绿。T-180。
