## RR-20260919-01：顶层 nested 指针没有完成所有权交接

### 现象

为当前 Codegen 生成一个只有 `Child *Child` 的 DAO，执行 `old → new`：

| 场景 | 期望 | 实际 |
| --- | --- | --- |
| 提交后修改 old | 0 条提交 | **1 条提交** |
| 提交后修改 new | 1 条提交 | 1 条提交 |
| 回滚后修改 old | 1 条提交 | 1 条提交 |
| 回滚后修改 new | 0 条提交 | **1 条提交** |

模板 `internal/dao/template_dao.go:206-235` 的 Kind 3 setter 在赋值后给新对象 `SetNotify`，undo 也会重新绑定 old，
但两条路径都没有先给离开的对象 `SetNotify(nil)`。因此提交后的 old、回滚后的 new 都继续把修改报告给 DAO。

### 影响

这是 RR-20260918-10 同一所有权不变量在另一个模板分支上的遗漏，但修复位置和触发形状不同：RR-10 修的是顶层 map/slice，
本项是顶层 nested pointer。游离对象仍能生成真实 `CommitRecord`，可把已不在内存对象图中的内容写回字段，属于数据正确性问题。

### 实施方向

生成 `bind<Child>` / `unbind<Child>`，让普通 setter 与 undo 都按“解绑当前 → 替换 → 绑定新当前”执行；`Init` 复用同一 helper。
验收至少保留上述四叶子，并增加 nil、同事务多次替换、提交拒绝和 panic 回滚。解绑最好校验预期对象，避免误解绑后来已经接管字段的对象。

## RR-20260919-02：map 中的 nested 别名只持久化最后一个 key

### 现象

把同一个 `*EquipInfo` 依次放到 `equips.1` 与 `equips.2`，随后修改它。内存中两个 key 指向同一新值，持久化补丁却只有：

```text
map[equips.2:true]
```

模板 `bind<field>Value` 每次都执行 `val.SetNotify(func() { markKeyDirty(key, val) })`。nested 的通知是单槽，第二次绑定覆盖第一次，
所以数据库只更新最后绑定的 key。进程重载后两个副本不再相等。

### 影响与契约选择

RR-20260918-10 的 bugfix 把 alias 写成未定义边界，但公开 setter 没有拒绝它，也没有类型或文档让调用者知道 DAO 图必须是树。
“接受输入后静默少写一个副本”不能继续作为未定义行为。

建议明确选择**唯一父所有权**：一个可变 nested 对象同一时刻只属于一个字段 / key / index。为 nested 生成物增加 owner token，
`bind(owner, notify)` 在已有不同 owner 时明确失败，`unbind(owner)` 只释放自己的绑定。只扫描当前 map 能通过本次复现，但抓不到跨字段、跨 DAO 的别名；
把通知改成多订阅则意味着一个对象可被多个聚合根共同持久化，回滚、锁和提交顺序都会复杂很多，不建议作为默认模型。

验收应覆盖同 map 两 key、跨字段、跨 DAO、解绑后重新绑定，以及失败前没有产生部分 mutation。

## RR-20260919-03：会话关闭订阅者 panic 能终止进程

`internal/roost/render_player_tcp.go:418-425` 复制订阅者后直接调用 `fn(event)`，没有逐订阅者 recovery。独立用例直接调用生成物的
`deliverClosed`，panic 原样逃出：

```text
session-close subscriber panic escaped lifecycle dispatcher: review subscriber panic
```

生产路径由 `dispatchClosed` 的独立 goroutine 调用它；Go 中该 panic 若无人恢复会终止整个进程。Core 的 bus、Nest、configdata、room、etcd
等回调边界已经采用逐回调隔离，因此这里也应逐订阅者 recover、计 `player_tcp_session_closed_callback_panics_total`、记录订阅者/事件身份，
并继续执行其余订阅者。验收必须证明“panic 不逃逸、同批健康订阅者仍执行、后续事件仍能派发、停机排空仍完成”。

## RR-20260919-04：订单与待办索引不是一个原子事实

Kit `service/platform.Service.HandleCallback` 先用 `Orders.Create` 持久化订单，再进入 `AttemptDelivery`；batch15 的索引却只在
Codegen `internal/service/platform.grantDeliverer.Deliver` 内调用 `pendingIndex.track`。两者之间至少有以下窗口：

1. `Create` 成功后进程退出，deliverer 尚未运行；
2. `Create` 成功、订单已消耗一次 attempt，但 `ZADD pending` 失败；
3. 调用方已经按“付款已记录”确认 provider，不再重发 callback。

第二种窗口已用最新生成工程复现：订单仍是持久的 `reserved`，grant 没写，索引恢复后 `PendingOrders(128)` 返回空列表。后台循环唯一输入就是该列表，
因此它无法自行恢复这笔订单。源码注释把 provider 重发当兜底，但服务契约同时允许调用方在订单已记录时确认接收，二者不能共同构成恢复保证。

建议把“创建订单 + 加入待办集合”收敛到同一个 Redis Lua/CAS 写。Core 已有 `redis.ScriptRunner`、`CompareAndSet` 与 durable eval 能力，
Kit 可为 platform 提供带二级索引的 Redis OrderStore，而不是让部署侧 deliverer 在订单创建后补写索引。若暂时保留通用 `OrderStore`，至少新增
`Pending.Track` 并在 `Create` 后、首次 attempt 前调用；这只能缩小窗口，不能作为最终原子方案。验收需注入 create 后退出、ZADD 失败和回复丢失，
并证明仅靠后台循环最终进入 delivered/exhausted。

## RR-20260919-05：一条坏订单阻塞整页健康订单

`pendingIndex.PendingOrders` 按 score 读取一页，然后逐条调用 `Order` 判终态；其中任一读取报错便立即 `return nil, err`。Server 收到错误后跳过本 tick，
下个 tick 仍从同一个最老成员开始。一条损坏 envelope、单键读取错误或长期不可解码记录会让同页其余健康订单永远没有机会进入 `AttemptDelivery`，
与实现宣称的“失败订单不能饿死后面的订单”相冲突；现有公平性测试只覆盖 score 后移，没有覆盖读取失败。

独立复现把 `broken` 放在 score 1、`healthy` 放在 score 2，只有前者 `Order` 返回错误；结果整页返回空，healthy 持续留在集合中且从未被尝试。
建议先解析本地 capability 失败这类全局错误；逐订单错误则保留该成员、记录 order_id 并继续构造其余候选。更通用的接口方案是让
`PendingOrders` 返回“部分 ids + error”，并让 Kit Server 在记录错误后仍处理非空部分。验收应覆盖首/中/尾坏项、多个坏项、退休失败和批次上限。

## RR-20260919-06：付费 grant 会在尚未履约时过期删除

batch15 用固定 `ClaimRetentionSeconds = 30 天` 同时决定 Player 去重账本保留期和 grant 准入。玩家付款后若 30 天未登录，或者背包长期无法接收，
`handlerGrantPurchase` 返回 `purchase_expired`；`PurchaseDrain` 随后仍执行 `HDEL`。此时平台订单早已在“grant 写入 Redis”后标为 delivered，
既不会再投递，唯一 grant 也被删除，玩家永久收不到已付款物品。现有测试把“过期拒绝”当成功契约，恰好稳定证明了这一行为。

对于付费资产，去重记录的可清理时间不能早于“业务履约已确认”。短期正确方案是取消未领取 grant 的固定过期和 PurchaseClaims 清理，接受账本增长；
完整方案是在现有平台永久订单上增加 game 侧幂等确认状态：Nest 事务提交物品与 claim id，随后幂等 RPC 把订单推进到 fulfilled，再删 grant；只有经过
审计/归档证明不会再出现 grant 后，Player 账本才可压缩。不能仅把 30 天改大，因为当前 grant 没有更早的权威终止时刻。

`fctx.RuntimeConfig()` 当前真正承载的是 configdata 发布的活动快照和 Nest 请求捕获值；进程启动配置已有 `Registry.Config()`。
