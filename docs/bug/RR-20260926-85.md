# RR-20260926-85：RR-79 的延迟释放通知删掉会话重开后新做、随即被 RR-59 撤销的 Direct 绑定

日期：2026-09-27。基线：本地 main `8d06d80`（RR-73～80 合并后，未推送）。来源：第四轮修复后独立审计（[REVIEW-2026-09-27-audit4](../review/REVIEW-2026-09-27-audit4.md)）。等级 **P4**：Direct 无生产调用方。引入：RR-20260926-79 修复（`b95c895` 上不复现）。状态：已复现，未修复。
（最终状态见文末修复节：**已修复，随 v1.17.1 发布**，详见[修复记录](../bugfix/RR-20260926-85.md)。上面的“状态”是登记时的原值，保留不改。——2026-09-27 回写，OPEN-ITEMS A13②）

同一 Flush 周期内 `CloseSession(7)` → `OpenSession(7)` → `Bind(7,8)` → 实体 8 被 RR-59 撤销。下一次政策阶段交付 7 的释放通知时，`sync/entitysync/policy/direct.go:93` 用 `Holds` 确认，
而 `sync/entitysync/subscriptions.go:309` 的 `Holds` 在 subject 退役时返回假，于是删除绑定并 `Unsubscribe`；`Unsubscribe` 返回“未登记”时 Manager 又删掉 RR-70 为这对 pair 保留的撤销记录。
实体 8 重载后 7 不再恢复订阅，违反 RR-79 约束“RR-70 恢复语义不变”。复现：[REPRO-2026-09-26-08](REPRO-2026-09-26-08.md) §2。

修复约束：释放通知只能删除“通知所指那次会话生命期”内的绑定——重开后新建的绑定（包括随后被 RR-59 撤销、处于待重新提交状态的）必须保留，其 RR-70 撤销记录不得被删除；
判定不能只看 `Holds` 的当前值（退役中的 subject 返回假）。RR-78/79 回归不回退，锁序不变。

## 修复（2026-09-27）

状态：**已修复，未发布**（本地提交，未推送）。

释放通知改为携带释放时刻的戳（`ReleasedSubscription.Stamp`）：会话关闭在删除会话的同一把 `m.mu` 内取，业务注销在退役 subject 的同一把
`subj.mu` 内取；订阅在确认生命期与登记的临界区内取同一时钟的戳（新导出 `SubscriptionSource.SubscribeStamped`）。`Direct` 的绑定记着最近一次
成功订阅（`Bind` 或重新提交）的戳，释放通知只删除戳更早的绑定，不再看 `Holds`；重开会话 / 重新登记后新做的绑定戳更晚，即使随后被 RR-59 撤销
也保留，它的 RR-70 撤销记录随之保留，实体重新登记后照常恢复。
