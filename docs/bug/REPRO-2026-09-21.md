## 1. RR-20260921-01：窗口边界的算术对得上

CI 原文（`framework-compat` / `source-head, demo`，2026-09-20 12:15:01 UTC）：

```text
2026-09-20T12:15:01.996Z WARN robot runner: scenario failed robot=2 player=900002 scenario=demo
  err="robot action activity_standing: window race-1789906500 counted score=0 progress=0
       for one dungeon clear (and its replay), want 1/1"
```

窗口算术（`WindowStart(n) = n - n%300`）：

```text
1789906500 → 2026-09-20 12:15:00 UTC | 1789906500 % 300 = 0
报错时刻 12:15:01 → 落在窗口 1789906500，上一个窗口是 1789906200（12:10:00–12:15:00）
```

也就是说：清本发生在 `race-1789906200`，读榜发生在 `race-1789906500`。同一条流水线在
11:07 与 13:20 的两次运行都通过——**它只在跨过整 300 秒时失败**，与负载、并发、机器都无关。

### 源码判定（三行，缺一不可）

```text
demo/internal/service/game/activity.go.tmpl:310   activityID := gameactivity.ID(time.Now().Unix())   // 写侧现算
demo/game/controllers/player/finish_dungeon.go.tmpl:132   } else if _, err := runner.Contribute(…)     // 返回值被丢掉
demo/internal/service/game/activity.go.tmpl:331   activityID := gameactivity.ID(time.Now().Unix())   // 读侧另算一次
```

`FinishDungeonResponse` 的字段是 `State` 与 `Outcome`（`finish_dungeon.go.tmpl:70`），不含窗口；
`svcactivity.Participant` 里也没有窗口 id。所以这条信息在两次调用之间**没有通路**，不是"忘了传"。

对照：`ApplyProgress` 对已完成窗口是**明确拒绝**的（`kit/service/global/activity/service.go:987`，
`ErrStatus`），窗口不存在时返回 `ErrMissing`（`:984`）。服务端语义清楚，问题不在那里。

**本轮没有做的**：没有构造"贡献落在 N、读取落在 N+1"的确定性单测——那需要把 `time.Now` 做成可注入的时钟，
而 `ActivityRunner` 现在直接调 `time.Now()`。这是实施侧修的时候顺带要加的缝，不是复现的前提：
上面的算术与三行源码已经完全确定这条路径。
