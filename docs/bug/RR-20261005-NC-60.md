# NC-60：attribute.Container.Snapshot 在锁外复制，与 Apply / ClearDirty 竞争

2026-10-05，基线 `50e9a4e853641f348c879b85c282af9c5813f656`。P2（并发读者拿到撕裂快照，-race 报数据竞争；当前仓内没有跨 goroutine 读属性的调用方，定级不是因为后果轻）。状态：已复现、已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261005-NC-60.md) · [本轮](../review/REVIEW-2026-10-05-noncore-n07.md)。

## 触发与差异

`Container` 文档写明“safe for concurrent use”，`Snapshot` 注释承诺“The copy is taken under the container's lock, so a snapshot never catches a profile mid-write from this container's own mutators”。基线 `attribute/container.go:103-114`：

```go
c.mu.RLock()
profile, ok := c.layers[selector.key()]
c.mu.RUnlock()
...
return Snapshot{Selector: selector, Profile: profile.CloneProfile()}
```

读锁在 `CloneProfile` 之前就释放了。另一个 goroutine 的 `Apply`（`:133-144`，写锁内 `LoadValues`）或 `ClearDirty` 可以在复制进行中改写同一个 profile：快照读到一半新一半旧的值（例如 HP 已改、派生 Power 未重算），-race 下是数据竞争。

## 复现

`attribute/container_snapshot_promises_test.go` 用钩子让 `CloneProfile` 停在中途，再发起 `Apply`，有界等待（100ms）它是否进入 `LoadValues`：

```
container_snapshot_promises_test.go:59: Apply entered LoadValues while Snapshot was still copying the same profile: the copy is not taken under the container lock
--- FAIL: TestSnapshotCopiesUnderTheContainerLock
```

`-race` 同一用例报 3 处 `WARNING: DATA RACE`。原文见[证据](../bugfix/evidence/noncore-bugfix-20261005-n07/README.md)。

## 影响与范围

只影响把 `Snapshot` / 生成的 `<Name>In` 交给第二个 goroutine，同时由容器方法（`Apply` / `ClearDirty`）写入的用法。经 `Live` 拿到 profile 后直接写入不在承诺内（注释写明由属主自己的锁串行）。game-demo 模板只在实体锁内读写，本轮没有找到仓内跨 goroutine 触发路径。

本轮没做：没有审第三方 profile 的 `CloneProfile` 在锁内回调容器的可能（会自锁死；生成的实现是 `cp := *p`，不回调）。
