# RR-20261005-NC-70：Ctrl-C / SIGTERM / SIGHUP 打断 go 命令窗口后，`.roost-deps-*` / `.roost-generate-*` 暂存树（整份工程副本）留在工程父目录

日期 2026-10-05。基线 main `50e9a4e853641f348c879b85c282af9c5813f656`（含 cb11be90 的重发信号补修）。等级 **P3**。状态：已复现（正式 CLI 与正式入口回归），未修复。来源：N08 codegen 非核心 review（[本轮](../review/REVIEW-2026-10-05-n08-codegen.md)）。

## 触发

1. `roost project deps`、`project sync`、`project upgrade`、`project new`（都经 `UpdateFrameworkDependencies` → `.roost-deps-*`）或 `roost generate`（`GenerateTransactional` → `TidyProjectDependencies` → `.roost-generate-*`）正在暂存树里跑 `go get` / `go mod tidy`。这是这些命令里最长的窗口：首次下载模块、慢代理时常是数十秒到数分钟。
2. 用户按 Ctrl-C，或 supervisor 发 SIGTERM / SIGHUP。

## 预期

RR-20261004-13 / cb11be90 定下的语义不变：roost 杀掉 go 的整棵进程树，然后照旧死于该信号。同时，命令自己的暂存树不应残留——这些暂存树只是“在旁边准备、成功才提交”的中间产物；暂存树残留在工程旁边已按缺陷处理过（[RR-20261004-12](RR-20261004-12.md)，Windows 上 `.roost-sync-*` 删不掉）。

## 实际

暂存树每次都留在工程父目录，下次运行不会清理，用户文档也没提。它是一整份工程副本（`copyProject` 只跳过 `.git` / `bin` / `dist` / `log` / `.testcache` / `.roost-*`），含 `configs/`、`deploy/` 等应用自有文件；工程是 monorepo 的子目录时，父目录是 Git 工作区，残留就是一棵未跟踪的重复工程树（`git add -A` 会把它连同其中的本地配置一起加进去）。

正式 CLI（替身 `go` 记录工作目录后长睡，在它运行时向 roost 发 SIGINT；脚本与原始输出见[证据](../review/evidence/noncore-review-20261005-n08/README.md)）：

```
== deps (SIGINT)
fake go cwd: .roost-deps-1211074997
roost exit status: 130
siblings of project:
.roost-deps-1211074997
...
== generate (SIGINT)        → .roost-generate-1252251067 残留
== sync (SIGINT)            → .roost-deps-4276096581 残留
== upgrade (SIGINT)         → .roost-deps-4091517380 残留
== new (SIGINT)             → .roost-deps-2667098078 残留
```

五条命令 exit 130（死于 SIGINT）、替身 go 子树都已不在——cb11be90 的承诺成立；只有暂存树残留。SIGTERM 下 `generate` 同样残留（exit 143）。残留树 2.9M，与 game-demo 工程本身同大。作为对照，`go get` 超时（5 分钟）走普通错误路径时 `defer os.RemoveAll(stage)` 生效、无残留。

正式入口回归 `TestInterruptedCommandRemovesItsStagingTree`（新增，`//go:build unix`）修前红：

```
interrupt_stage_promises_test.go:134: interrupted roost deps left its staging tree .roost-deps-2619724946 beside the project
interrupt_stage_promises_test.go:134: interrupted roost generate left its staging tree .roost-generate-1887797228 beside the project
```

同一用例的其余断言（死于 SIGINT、go 孙进程消失、工程 `go.mod` 未变、之后用可用的 go 重跑成功）修前即通过，红只落在暂存树残留上。

## 根因

- `codegen/internal/roost/dependencies.go:39-43` 与 `codegen/internal/roost/generate.go:224-228`：暂存树只由 `defer os.RemoveAll(stage)` 收尾。
- `codegen/internal/roost/command_tree.go:66-77`：`runCommandTree` 接住中断、杀树、`signal.Stop` 后 `self.Signal(sig)` 重发并等默认动作生效。进程死于信号，任何 defer 都不会运行。
- RR-20261004-13 修复记录“未采用的方案 3”比较过“转为返回错误、走回滚删暂存目录”，为保持“死于信号”的语义放弃了它，但没有在重发前补上暂存树清理，也没有把残留写进使用说明。拦截信号的位置（`runCommandTree`）不知道暂存树，持有暂存树的调用方又没有机会运行——这是本缺陷的确切缺口。

## 影响与定级

不损坏工程本身（提交只发生在 go 命令成功之后；sync / upgrade 的模板提交在 deps 之前完成、与超时失败时相同），所以定 P3。代价是磁盘、目录噪声，以及工程副本（含本地配置）留在工程目录树之外、monorepo 下进入父仓库未跟踪文件。

## 范围与未做

- 只覆盖“roost 正在等 go 命令时被中断”的窗口，这是这几条命令里唯一的长窗口。生成器（进程内）、`copyProject`、提交阶段被中断时没有信号处理，进程按 Go 默认动作直接退出，暂存树同样会留下；这些窗口是毫秒到秒级，本轮未改，单列为残余。
- `doctor` 的 go 命令在真实工程里跑，没有暂存树；`generate --check` 的临时副本在系统临时目录且不跑 go 命令，不在本条范围。
- Windows 未实跑：Windows 上 `treeInterruptSignals` 为空，`runCommandTree` 不接管信号（控制台 Ctrl-C 直达整棵树），本条修复不改变 Windows 行为。
