## RR-20260911-01 · P2 · 墓碑计数淘汰早于信封过期，再次生成领取 token

状态：未修复；关联 RR-20260910-02 / U-0165，原短序列修复有效，本条记录墓碑层的另一触发条件。作者已在 bugfix 中披露该残余风险，本轮将它独立复现并纳入问题索引。

- 位置：Kit `service/mail/mailbox.go:227` 的 evictSettledClaims，特别是 246 行删除；上限见 `service/mail/types.go:197`。ReserveClaim 的过期检查在 `service/mail/service.go:663` 附近。
- 条件：A 已领取并提交、Entry 被淘汰而留下墓碑；信封仍有效时，又有 MaxSettledClaims=200 条较新的已领取邮件被淘汰。A 的墓碑成为最旧项，被计数上限挤掉；之后 A 重投。
- 期望：只要同一附件仍可能被重新请求，已经结算的领取身份必须保留，或由另一个可靠机制阻止重新发放新身份。
- 实际：A 不在 Entries/SettledClaims，Deliver 当作首次投递；ReserveClaim 只确认信封仍有效，重新返回同一附件和新 token。按 token 去重的发奖端无法把它与第一次识别为同一次发奖。
- 独立验证：只通过 Service 的 Send/Deliver/ReserveClaim/CommitClaim/Delete 构造记录，使用真实 MemoryStore 和既有测试信封存储，不手改 map。A 有效期一周；测试时钟仅推进 400 秒，墓碑确实消失后重投，输出 `old=token-1 new=token-202 elapsed=400s`，race 测试失败。墓碑尚在时先断言 ErrAlreadyClaimed，确认旧修复确实生效。
- 影响与限制：确认重复领取身份，未连接资产服务、未声称已发生真实奖励重复；无需信封过期或服务重启。计数上限不能保证时间期限，不能由“过期邮件会拒绝领取”推出未过期邮件安全。
- 建议方向：明确幂等保留期限，使结算身份覆盖信封可领取/重投窗口；容量不足时采用可解释的拒绝、持久化或稳定身份策略。单纯增大 200 只能推迟触发。需要同时定义过期清理与迟到 Commit 重试的语义。

## RR-20260911-02 · P3 · Mailbox.clone 未复制新增 SettledClaims map

状态：未修复；U-0165 增加字段后遗漏读取副本的所有权边界。

- 位置：Kit `service/mail/mailbox.go:264`；对外读取 `service/mail/service.go:923`；Core `versionstore/memory_store.go:27` 的 Get 按值返回泛型对象。
- 条件：使用框架提供的 MemoryStore，邮件已留下墓碑。调用 Service.Mailbox 取得状态，修改返回对象的 SettledClaims map。
- 期望：Mailbox 方法经 clone 返回可独立使用的状态；修改该副本不应绕过 Store.Update 改变保存的领取记录。
- 实际：clone 只复制 Entries，`out := m` 使 SettledClaims 继续共享底层 map。`delete(snapshot.SettledClaims, mailID)` 后再次调用 Mailbox，存储内墓碑已消失。
- 验证：先通过正常领取/淘汰建立墓碑，再只修改公开读取接口返回值；独立测试失败：`mutating returned mailbox deleted stored settled claim`。
- 影响与限制：目前确认于进程内 MemoryStore，影响本地调试及使用引用型存储的读取隔离；源码明确 MemoryStore 不是多副本生产权威库，因此按 P3 记录，不宣称 Redis 解码对象共享或远程玩家可直接篡改。并发使用存在共享可变 map 风险，但本轮未靠并发 race 报告作证。
- 建议方向：clone 复制所有可变集合，包括 SettledClaims；测试同时覆盖修改返回副本与后续服务更新对已返回快照的影响。
