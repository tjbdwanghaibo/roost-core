# NC-183：TaskPool Submit 与 Shutdown 并发 panic “send on closed channel”

2026-10-05，基线 `f6245613441d16aafec33870166a4ec14f1ca15b`。P3（`goroutine.TaskPool` 仓内零调用方；公开 API，后果是调用方 goroutine 被 panic 带走）。状态：已复现、已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261005-NC-183.md)。[本轮](../review/REVIEW-2026-10-05-n13.md)。

## 触发与差异

`goroutine/task_pool.go:180-196`：`submitTask` 先 `w.closed.Load()`，再 `select { case w.taskChan <- task: … default: … }`；`close()` 先 CAS `closed` 再 `close(w.taskChan)`。两步之间没有互斥，Submit 读到未关闭后、发送之前 Shutdown 关闭 channel，向已关闭 channel 发送即 panic（`select` 的 `default` 不挡这个）。`TaskPool.Submit` 外层的 `running` 检查（:103）同样只是快照。

预期：并发时 Submit 要么受理（任务随后被 worker 排空执行），要么返回错误。

## 复现

`goroutine/task_pool_shutdown_promises_test.go` 的 `TestSubmitRacingShutdownNeverPanics`（2000 轮，4 个提交方，至少受理一次后 Shutdown），连跑三次：

```
task_pool_shutdown_promises_test.go:56: Submit panicked 60 times while Shutdown ran; first: send on closed channel
```

## 约束

沿用 `worker.Worker` 的做法（`worker/worker.go:89-112` 的 `closeMu`：读锁内检查并入队，Close 拿写锁），让“受理”蕴含“被排空”。
