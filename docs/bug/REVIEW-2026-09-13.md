## RR-20260913-01 / P2：快照删除丢失版本约束

位置：[remoteentity/syncer.go](../../remoteentity/syncer.go):100–103；`DeleteRemoteSnapshot` 在第 68 行发送 version，但接收侧直接 `cache.Delete(key)`，不比较 `env.Version`，也不保留删除水位。[entity/remote_snapshot.go](../../entity/remote_snapshot.go):389 的 Delete 是缓存失效原语。

两个实际失败场景，同一根因：

1. 发出 delete v2，再发出 full v3；先交付 v3，后交付 delete v2。期望保留 v3，实际 `found=false`。
2. 发出 full v1，再发出 delete v2；先交付 delete，后交付 full v1。期望保持已删，实际 `found=true version=1`。

测试使用真实发布 API 生成消息，记录后重排投递，经过完整 Replicator 解码与 SnapshotReplicaStore。正常 v1/v2 乱序 upsert 能保留 v2、按序 delete 能删除的对照通过。这将[上轮原语观察](REVIEW-2026-09-12-02.md)推进为已存在 Remote 复制路径的确认问题，不是把未实现 Mirror 再报一次。

影响：迟到消息、旧 outbox 重发或历史流恢复遇到较新本地快照时，可丢失热缓存或提供已删除的旧视图；不宣称已经证明权威数据库丢数据。NATS/JetStream wrapper 没有额外版本过滤，顺序测试证明协议对这些输入不安全；本轮没有实测真实 broker 发生乱序的概率。

建议：协议层将删除与 upsert 放在同一 key/代际/版本比较与 apply 边界中；保留 tombstone 或权威水位，覆盖 L1/L2、淘汰/重连与同 ID 重建。不能仅把 Get(version) 和 Delete 分成两个无锁步骤。删除水位生命周期需要与可重放窗口或重新同步代际协调。

## RR-20260913-02 / P2：旧兴趣释放取消新订阅

位置：[remoteentity/interest.go](../../remoteentity/interest.go):153–154、85；[transaction_manager.go](../../remoteentity/transaction_manager.go):589 的 Release 发布时间戳，但接收端仅按 key/SID 无条件删除，没有订阅代际比较。

步骤：真实 `RenewRemoteSnapshotInterest → ReleaseRemoteSnapshotInterest → RenewRemoteSnapshotInterest` 生成三条消息；接收新 renewal 后，迟到的旧 release 删除当前兴趣。测试失败 `old release canceled the newer renewal`，按序 renew/release 对照通过。接收表与发布表的状态操作均是真实实现。

影响：[syncer.go](../../remoteentity/syncer.go):35 的兴趣过滤可能静默跳过本应发送的快照更新。下一次成功续租/权威回填可能恢复，并非永久丢失；但本地仍认为新兴趣有效，读时续租还会合并请求，不能假设下一次读马上修好。默认兴趣 TTL 与缓存 TTL 都是 30 秒，具体陈旧时间取决于读模式、续租时点及网络，不能笼统保证固定时长。

建议：renew/release 使用可比较且不可复用的订阅 generation/序号；只释放匹配代际。现有 ExpiresAt 是过期时刻，不宜简单当成订阅版本：合法 release 的发布时间通常早于它撤销的 lease 到期时刻。需要证明 release→renew、renew→release、重放、进程重启 SID 复用等交错。

## RR-20260913-03 / P2：Remote payload 身份未与信封绑定

位置：[remoteentity/syncer.go](../../remoteentity/syncer.go):96–103。通用 Replicator 校验外部 SyncMsg 与 mirror.Envelope 的 key/version，但 Remote 第三层 `wire.Key`、`wire.Update.Key` 和 `Update.StateVersion` 没有与它们交叉校验。

复现：真实生成 scope=1 的 full 消息，只将 payload 的 `wire.Update.Key.Scope` 改成 2，保留 `wire.Key`、两层 envelope key/version。消息通过 Replicator，实际向 scope=2 缓存写入，返回 nil。期望拒绝且两个 scope 不应被此畸形消息修改；实际 `foreignCached=true`。

影响：有缺陷的发布者或能写该内部 topic 的来源，可以使路由/顺序身份与实际写入的视图不一致。这是协议完整性问题；本轮不证明未认证外部攻击者能发布，也不声称 hash/CRC 自身就是授权机制。

建议：写入前校验 wire.Key == Update.Key、完整 key 有效、outer key == 按完整 key 计算的 replica key、outer version == Update.StateVersion（含数值域）；delete 分支明确 op/version/key 规则，另审 Interest payload 对应约束。权限仍应由传输/服务身份边界负责。U-0045 的外层校验保持有效，这里是新增一层未绑定，不重新打开 U-0045。

## RR-20260913-04 / P2：快照加载取消后泄漏等待名额

位置：[entity/remote_snapshot.go](../../entity/remote_snapshot.go):282–292，`loadMonotonic` 跟随者 `call.waiters++` 后，ctx 取消直接返回，不减回。

复现：MaxWaiters=1，权威 loader 用屏障保持未完成；一个跟随者进入同 key/minVersion 的合并加载后取消并退出。没有活跃跟随者时，再来健康请求仍立即收到 `ErrRemoteOverloaded`，而不是占用空闲名额等待。测试使用锁内观察确认跟随者已加入，然后取消；没有靠随机 sleep 争取竞态。

影响：慢权威后端叠加超时重试时，可把累计历史等待人数当成当前并发人数，直到本次 load 完成前拒绝后续读。默认上限 256 会推迟触发，不消除问题。Manager 外围 fallback 如何影响业务最终返回及放大请求，尚未额外集成实测。

建议：取消路径在 loadMu 下核对相同 call 实例并归还名额，覆盖完成/取消竞态，不能扣到同 key 的新一代 call。已修复的 [RR-20260908-02 / U-0155](../bugfix/RR-20260908-02.md) 位于 `cache.ReadThroughStore`；本项为 entity 自建合并层的独立遗漏，不否定旧修复。
