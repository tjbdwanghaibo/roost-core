## RR-20260917-01：合法 Queue 的键碰撞，导致跨队列读取和成组

**P2，Core，未修复。** [service/match/types.go](../../service/match/types.go):159 Validate、:176 Key；[queue_store.go](../../service/match/queue_store.go):331 Candidates、:359 Commit；[redis_store.go](../../service/match/redis_store.go) 将 Queue.Key 原样作为逻辑存储键。

以下两组 Queue 均通过 Validate：

| Mode | GroupSize | Partition | Key |
| --- | --- | --- | --- |
| a:2 | 3 | x | a:2:3:x |
| a | 2 | 3:x | a:2:3:x |

Mode/Partition 未限制冒号，Key 用冒号拼接三字段，映射不是一一对应。两个池实际访问同一个 queueState；Candidates 不核对 Ticket.Queue，Commit 也只按共享状态中的 ticket ID、等待状态和主体去重校验。

独立场景：分别在两队列入队一位玩家，第二队列 Candidates 返回两张票；用第二队列 GroupSize=2 提交两票成功，其中一票来自三人队列。正常不同 Partition 隔离、同队列提交两个对照通过。新五场景中三失败、二通过。问题不只是路由亲和性碰撞，而是存储身份合并；Redis 包装使用同一 Key，源码可推导同样风险，但本轮没有连接真实 Redis 复现。

影响：合法配置组合下不同模式/分区混池，票据查询、主体占位、幂等请求账本及比赛提交共用状态。不宣称 demo 的固定 duel/default 配置已触发，也不把 Mode/Partition 视为必然由不可信客户端自由输入。

实施建议：定义无歧义的规范键（长度前缀、结构化编码或对各自由字段独立转义），存储键和 RPC affinity 使用同一权威表示。短期拒绝保留分隔符也可，但必须明确兼容性与既有配置。旧存储键不能直接静默换名，否则已有票/比赛不可达；制定版本化键迁移。Commit 追加 Ticket.Queue 与请求 Queue 一致性检查作为防御，不能只靠它修复读取和占位污染。验收上述碰撞、空 Partition、Unicode/分隔符及持久化迁移。

## RR-20260917-02：ScoreWindow 的整数溢出导致窗口判定错误

**P2，Core，未修复。** [service/match/grouping.go](../../service/match/grouping.go):54 Group、:68 窗口增长、:75 距离、:85 排序、:95 absInt64。Subject.Validate 没有分数范围限制，Score 的语义由调用方决定。

| 合法输入边界 | 期望 | 实际 |
| --- | --- | --- |
| 分数 0 与 MinInt64，窗口 10 | 不成组 | abs(MinInt64) 仍为负数，成组且排序可把远端放到锚点前 |
| MaxInt64 与 MinInt64，窗口 10 | 不成组 | 相减回绕为小距离，成组 |
| InitialWindow=MaxInt64-5，增长 10，等待 1 秒，MaxWindow=100；分差 5 | 受上限约束后可成组 | 加法先溢出为负，随后 cap 比较失效，不成组 |
| InitialWindow=10，增长 MaxInt64/2+1，等待 2 秒，MaxWindow=100；分差 5 | 可成组 | 乘法先溢出，不成组 |

九项算术场景五通过、四失败；通过项含普通近/远分数、负分近邻、MaxInt64 附近小差值及正常 cap。没有依赖非法负窗口或无效 Queue。常规游戏分数区间通常不会达到此极值；当前 API 未限定区间，因此通用实现不能默默把溢出当作合法距离。demo 使用 FirstCome，不直接受此策略问题影响。

实施建议：先明确非负窗口/增长配置合同，对不支持范围显式拒绝；支持完整 int64 分数时用无溢出的非负距离表示，筛选与排序必须一致。不能先做有符号减法再转 uint64，也不能仅把 abs 改成浮点而损失大整数精度。增长用有上限的饱和计算或乘加前溢出检查，先判断是否已达到 cap，别让回绕参与比较。补等待时间差的边界与时钟回拨语义。

## RR-20260917-03：内存匹配 Store 泄露可变切片，返回结果可改写存储状态

**P3，Core，未修复；本轮确认范围为 NewMemoryStore / 内存 versionstore。** [queue_store.go](../../service/match/queue_store.go):54 clone、:225 入队 Subject、:305 Ticket、:331 Candidates、:426 保存 Match 并赋 result、:437 Match；[store.go](../../service/match/store.go) 的 NewMemoryStore；[versionstore/memory_store.go](../../versionstore/memory_store.go) 按值存取泛型对象，未深复制引用字段。

七个独立场景均失败：

- 修改 Enqueue 的输入 Payload、其返回 Ticket.Payload、Ticket 查询的 Payload、Candidates 的 Payload，之后查询存储得到 Xld 而非 old。
- 修改 Commit 返回 Match.Members[0].ID 或 Match 查询返回的 Members，之后读到成员 999。
- 修改 Match 返回的 TicketIDs，之后存储读到 forged。

未再次调用任何变更方法；同一切片穿过输入/输出边界。queueState.clone 复制 map 和 Waiting，但 Ticket.Subject.Payload、Match.Members、Match.TicketIDs 仍是浅复制。泛型 versionstore 无法自动猜测 T 的所有权规则；类型化 match.Store 对外返回对象时需承担这层隔离，不能让外部用户通过隐藏 queueState 的引用绕过更新语义。

影响：单进程工具/测试中修改返回结果即可污染存储，且行为与序列化后端不一致；并发修改还可能形成数据竞争，但本轮只做顺序证明，未声称 race 检测报错。按内存实现用途定为 P3，不扩大为 Redis 已落库对象可被同进程切片直接篡改。

实施建议：在输入/返回边界深复制可变字段，明确内部只读对象所有权；需覆盖 Enqueue、Cancel、Ticket、Candidates、Commit、Match。只复制最外层切片仍不足，Members 中的 Payload 也需要处理。可提供 cloneTicket/cloneMatch/cloneSubject 等类型化工具复用，避免修改通用 versionstore 合同造成全框架隐性成本。配对算法若要重排候选，应只修改自己拥有的工作副本。

## 观察项：终态历史保留使队列空了但聚合状态仍增长

独立完成 128 场两人比赛，将时钟推进一年再 Sweep：Waiting=0，Tickets=256，Matches=128，Requests=256。当前 Config 的 TicketTTL 是等待超时，不是终态记录保留周期；Sweep 解决等待票过期，不清理历史。

这是容量/长期运行设计待定项，本轮不另立 RR，也不声称 128 场已经造成性能故障。单一 queueState 的每次 clone/CAS/Redis JSON 编解码成本随历史数据增长；MaxQueueLength 只约束等待列表，不能视为完整状态大小上限。需定义比赛查询、幂等重放和归档各自保留期限，再设计受限清理；不能为减内存直接删除 Requests，导致旧重试重新入队。未做真实 Redis 大状态压测。

## demo 新范围结果

九项读候选/策略/提交错误场景通过；2、4、5 张票的三项成组场景通过，即使 Nest 计数和 TCP 推送不可用，已提交比赛仍可通过 Ticket→Match 找回，奇数余票仍等待。符合当前“通知是捷径，票据是查询依据”的契约；不把统计或推送失败记为自动丢比赛。

这不证明真实网络通知成功，也没有覆盖 HandlePollMatch 的网络端到端执行。详细边界和新场景计数见运行记录。
