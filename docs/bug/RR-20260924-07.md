# RR-20260924-07：pipelined 释放异常跳过完成或丢失回复

- 日期 / 基线：2026-09-24，`967bc69` 加 Nest N1～N4 已完成工作树。
- 范围 / 等级：Nest pipelined 的 inline、完成池、队列满降级路径；P1。
- 状态：修前已复现、已修复；未提交、未发布。[修复记录](../bugfix/RR-20260924-07.md)。

## 触发、预期与实际

业务成功 Enqueue，EntityManager release hook 抛出 panic。即使实体和组锁已由 defer 清理，这笔交易已准入，仍须等待 WAL 结果：成功则完成回调和 TransactionReleased，失败不确定则 abandon/fence，最终回复一次并保留释放错误。

原实现的三个结果不同：

| 路径 | 实际错误 |
| --- | --- |
| inline | release panic 直接展开栈，跳过 ticket 等待、AfterCommit 与 TransactionReleased |
| queued | RR-05 解锁屏障虽能开放，但完成任务不知道释放失败，回复业务成功 |
| saturated | 已把回复标为 deferred，但 panic 跳过本 worker 的 complete，外层也不再回复 |

根因在 [execution.go](../../nest/execution.go) 的 `commitPipelined` 与 [pipelined_completion.go](../../nest/pipelined_completion.go) 的完成交接。`sync.OnceFunc` 还会在 dispatch 的兜底 defer 再次重放同一个 panic，不能只在提前释放处恢复一次。

## 确定性复现

[completion_release_panic_test.go](../../nest/completion_release_panic_test.go) 走生产 NestDispatch、Guard、EntityManager release hook。饱和用例在尚未启动的完成队列中占满唯一槽位，保证 submit 同步失败；无需 sleep 或靠运行速度制造满队列。

```sh
GOCACHE=/tmp/roost-nest-go-cache GOWORK=off go test ./nest \
  -run '^TestPipelinedReleasePanicStillCompletesAndReplies$' -count=1 -timeout=20s
```

Go 1.27.0 / darwin arm64，修前实际输出：

```text
inline: AfterCommit calls=0, want 1
inline: TransactionReleased was skipped
queued: reply=committed, want release failure after durable completion
saturated: accepted transaction lost its reply
saturated: AfterCommit calls=0, want 1
saturated: TransactionReleased was skipped
```

这与 RR-05 的“完成早于解锁”是不同缺口：只有解锁屏障仍不能保证释放异常后的完成责任与回复责任。
