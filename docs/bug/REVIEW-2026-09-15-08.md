## RR-20260915-08 · P2 · Import/Restore 绕过绑定 journal 的持久化替换

位置：syncstream/syncstream.go:482 Import 完整校验后仅替换 streams/epoch，573 Restore 调用 Import；lifecycle_journal.go:49 NewHistoryWithJournal 将 journal 保留给后续 Append/ACK。

触发：真实 FileHistoryJournal 先保存 epoch 7/sequence 1 的 old。对同一个已绑定 journal 的 History Import 或 Restore 一个新快照，再 Append sequence 2，所有调用均成功，关闭后重启。

实际：新快照若仍用 epoch 7，重启后的第一包又变成 old，而运行时已替换为 replacement；若新快照改用 epoch 8，后续 WAL 混入不同 epoch，重启返回 ErrInvalidSnapshot。Import/Restore 两入口、同/新 epoch 共四个场景失败。替换后显式 History.Checkpoint 再追加的两个对照通过。

期望：持久化 History 的成功替换不能使后续成功写入失去一致恢复基础；要么同步发布替换快照，要么拒绝绑定 journal 时的该调用并明确安全接口。没有任何并发或半条 WAL，本项与 RR-20260915-07 不同。

建议：使用现有 HistoryJournal.Checkpoint，在互斥保护下持久化验证后的候选快照后再发布内存；失败则保持旧状态，并处理 checkpoint 已发布但返回错误的歧义。构造时的加载可用独立内部导入路径，避免恢复过程再次写 journal。也可选择拒绝持久化实例的公开 Import/Restore，提供明确的持久化替换 API。简单调用 Import 后再 Checkpoint 存在中断窗口，只是本轮成功路径对照，不是原子修复。

## RR-20260915-09 · P2 · Recover 将过期捕获提交为更新的 Full

位置：syncstream/syncstream.go:275 Recover 在锁外调用 provider，返回后不比较开始时的 epoch/stream generation/latest，直接 Append；Append:140 按当前状态赋予 epoch 和新序号。

受控触发：provider 已捕获 old，通过 channel 暂停返回；另一调用在同流 Append 新 Full(new)，再放行 provider。Recover 返回 epoch 7/sequence 2 的 Full(old)。若暂停期间先 RotateEpoch(8) 再发布 new，旧捕获被标成 epoch 8/sequence 2。两个场景失败；无变化、provider 报错、可直接 replay 不调用 provider 三个对照通过。

影响：接收者按更高序号应用 Full 时可以回退到旧内容；旧代快照可能污染新代。测试不依赖数据竞争，捕获与修改顺序由 channel 明确控制，未模拟实际客户端。若宿主串行化整个业务快照捕获、History 追加和 Recover 返回区间可避开；现有接口和“锁外调用 provider”注释没有保证这种跨步骤原子性。

建议：在调用 provider 前记录 epoch 与目标流的修改代数/序号，返回后在相同互斥边界验证再提交；失效则返回明确可重试结果或有界重捕获。删除重建还需结合不复用的 generation，不能只比较 latest。不要简单持 History 锁执行任意 provider，可能反向取锁或重入 History。框架只保证 History 边界，业务若变更而不关联追加仍需宿主协调。
