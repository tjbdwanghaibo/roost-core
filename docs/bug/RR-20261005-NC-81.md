# NC-81：Engine recover 把响应开始后的 panic 改写成“完整”的 2xx，并吞掉 http.ErrAbortHandler

2026-10-05，基线 `50e9a4e8`。P3（公开 `httpserver.Engine` 上的任意 handler；框架自带的 Webroute/Ops 出口在 NC-80 修复后不再在写头后 panic）。状态：已复现、已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261005-NC-81.md) · [本轮](../review/REVIEW-2026-10-05-noncore-n02.md)。

## 触发与影响

`recoverMiddleware`（基线 `httpserver/server.go:278`）对任何 panic 都调用 `JSON(w, 500, ...)`：

- handler 已写状态/部分响应体或 Flush 后 panic：`WriteHeader(500)` 无效，错误 JSON 拼在已发出的部分后面，HTTP/1.1 分块正常结束。客户端读到 `status=200 body="{\"items\":[1,2{\"error\":...}\n"`、`readErr=<nil>`，无法察觉响应被截断。net/http 的约定是 handler panic 时中止响应，客户端看到传输失败。
- `panic(http.ErrAbortHandler)`（标准库约定的“中止且不打印堆栈”信号，如 `httputil.ReverseProxy` 拷贝失败）被记录完整堆栈并回答 500 JSON。

修前 overlay 与旧产品正式回归：3 种“已开始”形状与 ErrAbortHandler 共 4 红，响应前 panic、1xx 后 panic、Hijack/Flush/ResponseController 控制通过。

## 根因

recover 中间件没有记录响应是否已经开始，把“能否改写为 500”当成恒真。
