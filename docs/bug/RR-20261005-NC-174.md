# NC-174：remoteentity Assembly.Stop 停复制只退订，不等已进入 ApplyReplica 的 handler

2026-10-05，基线 `origin/main` `25bb0d66`。**P3**。来源：[NC-83 修复记录](../bugfix/RR-20261005-NC-83.md#仓内其他同形停机实现只读核对未修)。范围：只涉及 replicator 的停机生命周期，不涉及 owner / grant / fence（核心线 K3）。状态：已修复（[记录](../bugfix/RR-20261005-NC-174.md)），未发版。

## 触发与差异

`remoteentity/assemble.go:198` `Assembly.Stop`：finalizer 在 ctx 内停完后 `stopReplicators()`，即 `sync/syncbus/mirror` `Replicator.Stop()`——只调 `unsub()`、置 `started=false`。ISyncBus 的退订不保证在途回调已返回（JetStream fanout 甚至可能在退订后用旧快照调到这个 handler）。`SnapshotReplicaStore.ApplyReplica` 会写快照缓存，遇到 gap / epoch / schema 不一致还会 `LoadAuthoritative`（经 backend 读权威）；`InterestReplicaStore` 写兴趣表。

Stop 返回 nil 后 App 继续停 remoteentity 的依赖（Redis、SyncBus，之后 NATS / Mongo），在途 handler 仍在跑。

设计文档早已写明需要的顺序（`docs/review/IMPLEMENTATION-REMOTE-POLICY-MIRROR.md`：“解绑消息入口，等待已准入 apply/fetch 退出，再释放缓存与依赖……Replicator.Stop 仅解绑订阅，不能假设它已等待所有 handler”），Assembly 没有做“等待”这一步。

## 正式调用方与触发路径

- kit `RemoteEntityMod.StopWithContext` → `Assembly.Stop(ctx)`；App 一次停机即触发（不需要重试）：停机时有一条快照 / 兴趣复制消息正在 apply。
- 后果：停机报告完成后 handler 仍在访问 Manager 与（可能）Redis / Mongo；依赖关闭后它以错误结束。窗口在进程退出前，没有观察到持久数据被破坏。

## 复现

`remoteentity/assembly_replica_drain_promises_test.go`：测试持有兴趣表的锁，让投递卡在 `renewIfNeeded`；在 Stop 等待时取消它的 ctx。修前：`Stop reported success while a replica handler was still applying`。
