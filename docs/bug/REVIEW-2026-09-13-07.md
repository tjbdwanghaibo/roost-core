## P2 RR-20260913-01：部分修复，L2 路径仍越过删除水位

原两个 Replicator 删除乱序复现均通过，说明直接 Publish 的墓碑有效。但 [DeleteAtVersion](../../entity/remote_snapshot.go)（520–536 行）只比较 L1，墓碑检查仅在 Publish（404 行），[ReadThrough.loadOne](../../cache/read_through.go)（137–159 行）不经过这道检查。

1. L2 有 v1，Get 捕获 v1 后暂停；DeleteAtVersion(v2) 成功并删除 L2，墓碑 TTL 一分钟；释放原 Get，v1 被重新写入 L1。实测 `returned=true cached=true`。删除之后完成的回填复活了旧值，完全发生在墓碑有效期内，不属于极晚重放的声明边界。
2. L1 空、L2 已存 v3，收到旧删除 v2。实测 L2 `found=false version=0`。较新共享缓存被旧删除清掉；这里证明缓存值丢失，不声称权威数据库被删。

建议所有 L1 写入路径共享删除水位准入；L2 删除需原子比较内容版本/权威代际并保留必要水位，而非仅在本机 Get 后无条件 Delete。TTL 与 broker 重放窗口的关系仍需真实协议证明，不能从缓存 TTL 推导出来。

## P2 RR-20260913-05：部分修复，预检查后竞争仍吞掉冲突

[Publish](../../entity/remote_snapshot.go)（425–447 行）新增 cold L1 的 L2.Get 预检查，但 [ReadThrough.Set](../../cache/read_through.go)（192–202 行）仍在 IgnoreRemoteError 下吞掉实际 Set 的语义冲突。

确定性交错：B 发布先读到 L2 miss 后暂停；另一发布者在 L2 写入同版本 A；放行 B，L2.Set 正确拒绝 B，但上层返回成功并写入 L1。实测 `err=<nil> L1="B" L2="A"`。原根因仍是把一致性错误当可用性故障；沿用 RR-05，不重复新建编号。

建议实际远端写入返回时分类错误，语义冲突必须阻止 L1 接纳；提前 Get 只能优化发现，不能作为并发正确性屏障。保留网络故障允许降级的既有契约。

## 观察：RR-20260913-02 原场景通过，重启代际承诺未通过
