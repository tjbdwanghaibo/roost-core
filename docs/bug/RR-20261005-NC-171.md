# NC-171：Nest Mod 卸载后重载的停止超时即丢失句柄，重试在重载 worker 仍可能运行时关闭 entitysync

2026-10-05，基线 `origin/main` `25bb0d66`。**P3**（形状确认；正式路径的触发窗口很窄，见下）。来源：[NC-83 修复记录](../bugfix/RR-20261005-NC-83.md#仓内其他同形停机实现只读核对未修)。状态：已修复（[记录](../bugfix/RR-20261005-NC-171.md)），未发版。

## 触发与差异

`kit/nest/nest_mod.go:246` `stopUnloadResync`：`err := m.stopResync(ctx); m.stopResync = nil`——等重载 worker 退出超时也清空句柄。`StopWithContext`（`:280`）注释写明“等 worker 退出超时也继续停 Nest”。

- 第一次停止：`entity.unloadResync.stop`（自身符合三步：幂等发起、ctx 内等 `wg`、可重试）超时返回 ctx 错误，句柄被清空；`engine.Shutdown(ctx)` 用同一个过期 ctx，通常也返回 ctx 错误，于是这一次没有走到 entitysync。
- 用新 ctx 重试：`stopUnloadResync` 看到 nil 句柄直接返回 nil，不再等 worker；`engine.Shutdown` 等到 Nest 排空后，`entitySync.Stop / Drain / Close` 关闭了重载 worker 的 Rebind / Retract 目标，返回 nil。停机报告成功，worker 实际可能还在运行。
- 成功停完后再调用一次 `StopWithContext`，`entitySync` 已关闭，返回 `entitysync: manager is closed`（修前测试里看到；不是重试正确性的一部分，但一并按“排空后再调用返回 nil”处理）。

## 正式调用方与触发路径

- 正式调用方是 App 的 Mod 停机（一次调用、不重试），所以“重试报成功”只在直接调用方出现。
- 正式 `ManagerAccess` 接线下，`stop` 取消 worker 的 ctx 后，worker 在 `ManagerAccess.Get`（共享加载，等待方按自己的 ctx 离开）和退避定时器上都会立即离开；只剩 `SubjectAwaitsReload` / `Rebind` / `RetractUnloadedSubject` 这些持 entitysync 锁的短步骤。要让等待超时，需要停机预算在这几步里耗尽，或 entitysync 的 subject 锁被长时间占用。真实环境的触发窗口很窄；即使发生，关闭后的 entitysync 对这些调用返回 `ErrSubjectNotRegistered` / false，没有观察到内存破坏。
- 复现用 `unloadResyncConfigurer` 接口注入一个受 channel 控制的停止句柄（kit 的正式接线点），确定性地让第一次等待超时。

## 复现

`kit/nest/unload_resync_stop_retry_promises_test.go`。修前：

```
retry Stop reported success while the unload resync worker was still running (stop handle calls=1)
entity sync was closed while the unload resync worker that targets it was still running
Stop after the resync drained = entitysync: manager is closed
```
