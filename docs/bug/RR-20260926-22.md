# RR-20260926-22：demo 模板公会持久发号器的 upsert 过滤条件含范围谓词，首次并发建公会时 duplicate key，导致 CI generated-consumer 间歇性失败

日期：2026-09-26。基线：main `aaada47`。等级 P2（demo 模板 / 生成物缺陷；玩家收到一次 server error，重试即成功，不重复发号不损数据；CI 间歇红）。
引入：`646ce63`（持久化发号替换进程内 `RuntimeIDs().Next()`）。状态：已复现（Mongo 最小探针 + 生成工程端到端），未修复。框架 core/kit 无缺陷。

## 现象

framework-compat `generated-consumer (source-head, demo)` 在 8ce21a5、aaada47 失败（646ce63、a22c5a5 通过），机器人 6 个失败 2 个：
`found_guild: response code 1: server error`；`poll_match: ticket still waiting`。服务日志：

```text
"msg":"found_guild failed","player_id":100002,"stage":"mint","err":"guild id allocator: reserve: mongo: duplicate key"
```

`poll_match` 是连带结果：robot 1 在 found_guild 失败退出，只剩 5 人进 2 人一组的 duel 队列，余 1 人等不到对手。

## 根因（代码）

`demo/game/controllers/player/guild_ids.go.tmpl:23-26`：

```go
controller.guildIDs.FindOneAndUpdate(ctx,
    bson.M{"_id": "guild", "next": bson.M{"$lt": int64(entity.StaticUniqueIDBase - 1)}},
    bson.M{"$inc": bson.M{"next": int64(1)}}, &counter,
    fmongo.FindOneAndUpdateOption{Upsert: true, ReturnAfter: true})
```

计数文档不存在时，并发 upsert 都匹配不到而各自 insert，后到者 E11000。Mongo 只在过滤条件全为唯一键等值时才服务端自动重试 upsert 的 duplicate key，
此处多了 `next: {$lt: …}` 范围条件，不重试。计数达到上限后也会每次报 duplicate key 而不是“号段耗尽”。调用处 `guild.go.tmpl:84-87`，集合绑定 `controller.go.tmpl:230`（写死库名 `"game"`）。

## 复现

- Mongo 最小探针（本地 roost-it，Mongo 8.0.28）：6 goroutine 同时对空集合执行模板原样调用，30 轮 29 轮出错共 119 次 duplicate key；过滤只留 `{_id:"guild"}` 时 30 轮 0 错。
- 生成工程端到端（head，只做 connect/enter_game/found_guild，`-count 40`）：3 轮 2 轮复现，日志与 CI 一致；`358c89f` 同场景 3/3 绿。
- 完整 demo `-count 5`（奇数人数）稳定得到 `poll_match: ticket still waiting`，证实连带关系。

## 实施方向（约束）

- 发号 upsert 的过滤只用唯一键等值（号段上限在返回后检查，已有），或对 duplicate key 有界重试 / 预建计数文档。
- 库名不写死；为并发首次发号补模板测试。

## 验收覆盖点

- 空集合 N 并发发号 0 错、号唯一递增；达到上限报“号段耗尽”。
- framework-compat source-head demo lane 稳定通过（多次）。
