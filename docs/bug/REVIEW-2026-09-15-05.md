# 09-15 第五轮：Room 传输剔除通知

## RR-20260915-04 · P2 · 已剔除连接的通知在剩余批次失败后丢失

状态：新发现，未修复。Core `4537a6d6c236956d45a07cb7675879ad576456ec`。证据为 Verify 图谱定位、当前源码补证和临时 overlay；旧问题不复核。

位置：`room/room_transport_sink.go:324` 的 admitWithSlowConsumerPolicy，尤其普通错误出口 `return nil, err`；调用方 `AdmitRoomFrames:216` 在错误时直接返回，成功出口才执行 `dispatchSlowConsumers:400`。room 消费通知的入口为 `room/room_broadcast.go:439` handleSlowConsumer。

触发：一个房间同主体有 session 1、2 两名订阅者。整批可靠快照准入遇到 session 1 的 ErrReliableBackpressure，默认 SlowConsumerEvict 删除其传输基线、标记 deadSessions、调用 RemoveSession，并积累通知。筛除 session 1 后重试剩余 session 2，此时 transport 返回另一个错误，例如临时失败或 context.Canceled。

期望：剩余批次仍可报错并保留 dirty，但已经发生的连接剔除必须通知 room 清理订阅与配额。实际：第二次失败返回 nil events，已产生的通知被丢弃；调用方也只在全流程成功时派发。随后正常重试时 deadSessions 路由被直接跳过，无法重新生成原通知，room 却提交 dirty、推进帧号。

独立复现使用真实 RoomBroadcaster → RoomEnvelopeSink → RoomTransportSink，只替换 AtomicBatchTransport 以稳定注入两阶段错误。普通错误、取消错误两种场景均失败；剔除后剩余批次立即成功的对照通过。失败场景重试成功后：sink DeadSessions=1、EvictedRoomSessions=1、CallbackPending=0；room ActiveSubscribers=2、SessionSequences=2、PendingSubjects=0。等待 300ms 后旧订阅仍存在。代码路径显示事件根本未入队，不只是回调调度慢。

影响：room 保留失效订阅和占用名额，仍为不会送达的连接做 profile/信封工作；上层自定义剔除通知也丢失。真实应用如果另有断连订阅清理，可能缓解，但当前默认 room 回调链无法自行收敛。没有声称对所有网络适配器都必现。

建议：将已发生的剔除副作用与剩余批次准入结果分别交接。保留累计 events，错误返回也必须在释放 room locks 后派发；仅修改 helper 返回值还不够，调用方的提前返回也须处理。继续使用已有 pendingCallbacks/worker，不新增通知系统。失败批次的 plans/dirty 仍不得提交；同时明确重复事件去重和 Close 期间丢弃策略。此为建议，未修改实现。
