## RR-20260911-06 · P2 · AfterCommit panic 遗漏回复和释放通知

**状态：未修复。** 与 RR-20260911-04 延迟队列停机遗漏回复不同：本项发生在事务已经持久化后的 completion worker。

**位置：** `nest/pipelined_completion.go:234` 的 tx.Commit 在回复之前执行；`nest/rollback.go:417` 起逐个执行 commits 回调，没有逐项异常隔离。`rollback.go:722` 将 TransactionReleased 追加到业务回调之后；`worker/worker.go:76` 的 SafeFunc 只在最外层恢复并记录 panic。

**触发：** 开启 PipelinedAsyncCompletion，合法持久化 handler 注册一个会 panic 的 AfterCommit 回调；ticket 已成功确认。completion worker 调用 tx.Commit 时回调 panic。

**期望：** 持久化事实保持不回滚；框架必须完成释放通知，并向等待者给出明确结果或可诊断的完成异常。业务回调异常不能静默取消框架收尾义务。

**实际：** Commit 先将事务标记 committed，随后执行回调。panic 越过后续回调（包括 TransactionReleased）和 retChan 发送；worker 的 SafeFunc 记录日志后继续工作。completionOrder 的 defer 仍释放排序节点，所以不是同实体链永久卡住；但本次调用只能等待自己的取消/超时。Shutdown 排空 worker 后返回 nil，未报告这些遗漏。

**实测：** 真实 Nest Request、实体、RecordUndo/MarkPersist/AfterCommit 路径；可控 committer 返回成功 ticket，release notifier 仅增加计数。race 测试失败：

```text
ERROR SafeFunc panic err="review hook panic"
durable completion lost obligations: missing_reply=true release_count=0 durable_lsn=1 value=1
```

Shutdown 已成功；再等 30ms 没有回复，取消 Request 后才退出。value=1 与 durable_lsn=1 证明不能把此异常当作可回滚的准入失败。没有检测到数据竞争；这是异常控制流遗漏。

**影响：** 客户端看见取消/超时而事务已成功，业务重试需要幂等；释放通知丢失还可能让 projector 保留该事务的 held 状态。后者依据 nestwal.Committer.Enqueue/TransactionReleased/isHeld/replayPass，以及 dataengine Projector 的 admit/release 源码，未用真实 WAL/数据库做端到端验证。不要将其写成已证明数据丢失。

**相邻风险（源码推断）：** completion pool 饱和时 pump.run 直接调用 complete；该 goroutine 没有 worker.SafeFunc 的恢复边界，同类 panic 可能逃逸并导致进程退出。本轮未制造饱和后进程崩溃，不将推断混入实测结果。

**建议：** 将必需释放通知与业务回调分开保证执行；在 completion 统一边界处理 panic，确保正常 worker 与饱和回退具有一致语义。回复明确区分“已持久化但收尾失败”，不得回滚已确认数据。仅恢复 panic 并打日志仍会丢回复/释放；应验证回调异常、释放恰好一次和请求终态。
