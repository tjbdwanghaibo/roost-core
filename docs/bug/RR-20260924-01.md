# RR-20260924-01：pipelined 的准入回调在 Entity 解锁后运行

- 日期 / 基线：2026-09-24，core `967bc69` 加工作树；等级 P1。
- 范围：Nest pipelined 提交、DataEngine Entity 删除等 AfterAdmission 消费者。
- 状态：已复现、已修复并验证，未发布；[修复记录](../bugfix/RR-20260924-01.md)。

## 触发与预期

handler 登记 `RollbackTx.AfterAdmission` 并以 DurabilityPipelined 提交。接口承诺回调在准入之后、Entity 锁释放之前执行，适用于锁保护的生命周期变更。

实际 `invokeWithTransaction` 在 Enqueue 后写入 LSN，随后 releaseLocks；准入回调却只放在后续 `tx.Commit` 中运行。inline 模式等 ticket 后调用，async 模式由完成池调用，两者都可能已无原 Entity 锁。

DataEngine 的 `Runtime.deferEntityDelete` 将内存删除登记为 AfterAdmission，因而已接纳的删除在提前解锁时尚未反映到生命周期，后继业务有机会访问该实体；完成池也不具备原 guard 上下文。新建锁内同步捕获若复用该接口，也会捕获到错误时点。

## 可重复证据

新增 [admission_boundary_test.go](../../nest/admission_boundary_test.go)，用可控 ticket 在 release 回调中确认持久化，不靠 sleep 安排顺序：

```sh
GOWORK=off go test ./nest -run TestPipelinedAdmission -count=1
```

修前 inline 与 async 均输出：`admission at release=0 total=1 locked=false LSN=1; want 1/1/true/1`。回调 panic 场景的顺序为 `[release admission commit]`，预期 `[admission release commit]`。

根因路径：`nest/rollback.go: invokeWithTransaction → releaseLocks → tx.Commit`；`RollbackTx.Commit` 才消费 afterAdmission；`dataengine/engine/entity_delete.go: deferEntityDelete` 是实际消费端。Strict 不提前放锁，本问题不是所有模式一律发生。
