# RR-20260926-03：Slow 消息快阶段继承慢阶段 local executor，RunLocal 在快池内投递快续行并同步等待，快池饥饿死锁

日期：2026-09-26。基线：main `a22c5a5`。等级 P2（整池不可用 + 停机排不空；无数据损坏）。
状态：已复现，未修复。机制自 RR-20260925-07 双池实现即存在，不是 a22c5a5 引入。

## 触发条件

消息走慢池（`SendOptionSlow()`、Cost 或 Remote），其 handler 在快阶段直接或间接调用 `entity.RunLocal(ctx, fn)`，
ctx 取自 fctx 的 Base。生产中可达的间接路径：handler 绕过 `msg.getter`，用 Base 调 `ManagerAccess.Get`
（`kit/nest/nest_mod.go:117` 以 `entity.runtime` 暴露）或生成的 lifecycle `Get/GetOrCreate`
（`codegen/internal/roost/add_workflow.go:132` → `:95`）访问冷实体 → `entity/manager_access.go:97` 因 ctx 无
`LoadedEntitiesOnly` 不拦截 → `:103` → `:165` loader → `dataengine/engine/entity_repository.go:52` → `:106` → `:133`（Store I/O）→
`:189 entity.RunLocal`。

## 预期 vs 实际

预期：快阶段已经在快 worker 上，需要本地步骤时就地执行；roost-coding 规定快池内不得阻塞等待，
“投递到快池并同步等待”只属于慢 worker。普通快消息正是就地执行。

实际：快 worker 把 fn 作为新的快续行投进自己所在的快池，并阻塞等待它：

```text
慢 worker S：dispatchRemoteLogic → 快续行 A（handler）入快池，<-A.done
快 worker F：执行 A（持 Guard）→ RunLocal → dispatchFastContinuation → 快续行 B 入快池，<-B.done
B：等空闲快 worker；F 被 A 占着 → A 等 B、B 等 F、F 被 A 占
```

快池 1 worker 必然卡死；N 个 worker 时 N 个并发此类请求即全池卡死，之后无关的普通快请求也无法执行。
卡住期间 Guard 不释放，父慢 job 不完成，`pending > 0`，`Shutdown` 超时。

## 根因（代码）

1. 慢阶段把执行器注入 Base：`nest/nest_dispatch.go:32-40`（`msg.localExecutor` → `dispatchFastContinuation`）、
   `nest/nest_dispatch.go:116-119`（`current.Base = entity.WithLocalExecutor(current.Base, msg.localExecutor)`）。
2. 快续行原样继承：`nest/remote_dispatch.go:64` 捕获 `fctx.CaptureSnapshot()`（`fctx/context.go:222` 快照含 Base），
   `nest/remote_dispatch.go:35` 在快 worker 上用该快照建上下文，`:54` 进入 `runNestLogic`。
3. `entity/local_executor.go:26-27`：`RunLocal` 只看 ctx 里有没有执行器，不判断是否已在快池。
4. `nest/dispatch_queue.go:173-179`：`continueFast` 的前提是“只供占有一个慢 worker 的已准入请求调用”，
   快 worker 调用违反了这个前提；续行仍需真正空闲的快 worker（`:181-187`）。
5. `WithLocalExecutor` 的注释只禁止“fn 内再次调用该执行器”，没有覆盖“快阶段带着慢阶段 ctx 再调用”。
6. 放大因素：快阶段禁冷加载只包装 `msg.getter`（`nest/nest_dispatch.go:147-149`、`nest/slow_load.go`），
   Base 本身没有 `LoadedEntitiesOnly`，所以上面的冷加载路径能在快 worker 上做 Store I/O 后再撞上本死锁。

## 复现

探针源码与输出摘录见 [REPRO-2026-09-26](REPRO-2026-09-26.md) §1（Go 1.27.0，darwin/arm64，三个用例分进程跑）：

- 快池 1 / 慢池 2，Slow handler 内 `RunLocal`：请求 1s 后 `nest: sync canceled`，fn 未执行；
  `Slow.Running=1`、`ContinuationRunning=1`；`Shutdown(500ms) = context deadline exceeded`。
- 快池 2，两个并发此类请求：随后的无关普通快请求也超时、未执行（`plainRan=0`，`Fast.Ready=1`、`WaitingForWorker=1`、`OldestWaiting≈800ms`）。
- 真实 `entity.ManagerAccess` + 按 `entity_repository.go:189` 形态调用 `RunLocal` 的 loader：handler ctx 实测 `LoadedEntitiesOnly=false`，
  `loads=2`、冷实体未创建、Shutdown 超时；同样代码在普通快消息里完成（对照组），但冷加载发生在快 worker 上。
- 堆栈：快 worker 停在 `local_executor.go:27` → `nest_dispatch.go:37` → `remote_dispatch.go:73`；慢 worker 停在 `remote_dispatch.go:60`。

限制：没有用真实 `EntityRepository`（`dataengine/engine` 依赖 nest，nest 包内测试不能导入）；死锁只取决于 `:189` 这一次 `RunLocal` 调用，探针原样复制了该形态。
正常 Slow 用法（handler 只经 `msg.getter` / `CastMulti`）不触发：冷目标在 `manager_access.go:97` 返回 `ErrColdLoadInLogic`。

## 实施方向（约束）

- 慢阶段的执行器不得随快照进入快阶段；快阶段的本地步骤就地执行。
- 快阶段所有实体访问入口（不只 `msg.getter`）都要带禁冷加载约束，否则“就地执行”只是把死锁换成快 worker 上的阻塞 I/O。
- 与 [RR-20260926-06](RR-20260926-06.md)（快池内框架等待入口 fail-fast/panic）一起设计。

## 验收覆盖点

- 快池 1 worker：Slow handler 内 `RunLocal` 不再投递续行（就地执行或按 RR-06 panic），请求在超时前返回，Shutdown 正常排空。
- 快池 N worker、N 个并发此类请求：无关普通请求仍能执行。
- Slow handler 经 Base 调 `ManagerAccess.Get`/lifecycle 访问冷实体：返回 `ErrColdLoadInLogic`（或 RR-06 的 panic 错误），loader 调用 0 次。
- 慢阶段原有 `RunLocal`（冷加载发布、Remote 回滚/Abort）行为不变。
