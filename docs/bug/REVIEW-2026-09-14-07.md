## RR-20260914-11 · P2 · ForceFull 被请求之前发送的 ACK 取消

位置：`statesync/session.go:55`（控制报文 ACK）、`:102`（直接 Acknowledge）无条件清除 forceFull；`:107` ForceFull 只更新本地 generation。外部入口 `statesync/replicator.go:217`。

触发：发布 tick 1，PrepareLatest/Commit；ACK 尚未到达时调用 ForceFull。随后 tick 1 ACK 通过 Acknowledge 或 HandleControl 到达，ackTick 从 0 变 1，并清除 forceFull。发布 tick 2 后 BuildLatest 返回 FrameDelta（kind=2、base=1），不是要求的全量。

期望：请求全量之后，在属于该恢复请求的全量发送完成之前，旧发送 ACK 不能取消恢复意图。实际：两个入口独立失败。若 ForceFull 用于清除客户端基线丢失或运输切换后的状态不确定性，下一次发送可能继续依赖旧基线，恢复承诺落空；本轮仅验证直接调用场景，不声称真实运输切换已复现。

对照：先 ACK 再 ForceFull，正常全量；ControlResync(sequence=2) 后旧 ACK(sequence=1) 被拒，保持全量。因此不把有序客户端 resync 也笼统描述成失败。问题独立于 RR-10：没有同 tick 投影修改。

建议（未实现）：将 ACK 水位推进与 forceFull 恢复意图解耦，复用 generation/PreparedFrame 提交凭证，只有属于当前恢复代际的全量发送成功才释放相应意图。避免单纯抑制 ACK 水位或清空全部历史来掩盖时序问题；补查并发 ForceFull/Commit 的先后。

## RR-20260914-12 · P3 · 单片重组绕过 MaxFrameBytes

位置：`statesync/datagram.go:213` ChunkCount==1 直接返回成功，绕过同文件 `:254` 多片累积大小检查。

触发：接收端配置 MaxFrameBytes=256、MaxDatagramBytes=1200。发送端按自身默认限制构造 400 字节载荷；单片报文长度 442，CRC/头合法。PushFor 返回 done=true、400 字节、nil；相同载荷按 maxDatagram=300 分为两片，则 ErrFrameTooLarge。两条路径应遵守相同帧大小限制。

影响限定：仅在配置 MaxFrameBytes 小于单片可容纳载荷时触发，默认限制不触发这个关系。载荷仍受 MaxDatagramBytes 限制，不是无限内存增长。后续 `statesync/codec.go:63` DecodeFrame 另查总长度；继续使用相同 Limits 解码会拒绝。因此本项是重组 API 的限制契约不一致，不能声称越过完整客户端解码链。专项使用不透明字节验证运输重组边界，未声称它是合法业务帧。

建议（未实现）：在单片成功返回前统一总长度准入；保留无需 inflight 表的快路径，并保证多片/单片错误语义一致。补小限制、恰好等于上限及超限对照。
