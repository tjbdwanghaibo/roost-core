# RR-20261005-01：game-demo activity 的 `activity.game_sids` 含重复 sid 或候选超过 `Live` 单次上限时，启动照常成功，此后每个窗口都开不出来，只有每 5 秒一条 Warn

日期：2026-10-05。基线：main `50e9a4e8`。等级 **P2**（可用性：活动静默停摆，不损坏数据）。
来源：N01 / N06-S4 审查（[运行记录](../review/REVIEW-2026-10-05-n01s4.md)），审查点“game-demo / activity 使用 App.Live 的实际调用（candidates）”。
状态：已复现，未修复（审查时）。**更正（2026-10-05）：已修复，见[修复记录](../bugfix/RR-20261005-01.md)。**

## 触发

生成的 game-demo，game 服务配置（`configs/service/config.<game>.yaml`）：

1. `activity.game_sids` 里同一个 sid 出现两次（例如本服 1300，配置 `[1302, 1301, 1302]`），并且 1302 的进程持有单实例锁；或
2. 本服加上配置的 sid 共超过 `app.SingletonLiveMaxSIDs`（200）个。

## 预期

`activity.game_sids` 是启动时就确定的候选集。一份注定让每个窗口都开不出来的候选集，应当在启动时按配置键名报错（与同一函数里 `activity.key_prefix` 为空、`server_type` 为空时的 fail-closed 一致），而不是让进程正常服务、活动永远不开。

## 实际

启动成功；之后 `runActivity` 每 5 秒一次 `openCurrentWindow`：

- 情形 1：`candidateSIDs`（`demo/internal/service/game/activity.go.tmpl:157-166`）只跳过本服与非正数，不去重，`expectedGameSIDs`（`:276-289`）把 `Live` 的结果原样作为 expected；`Live` 按入参顺序逐个返回活着的 sid（`app/singleton.go:580-586`），重复项原样保留。协调器 `validateExpectedGames` 拒绝带重复项的 expected 集合（`kit/service/global/activity/types.go:899-923`，“Duplicates are refused rather than de-duplicated”），`openCurrentWindow` 只记 `activity: window not opened`（`activity.go.tmpl:247-250`）后返回。只要重复的 sid 活着，每一拍都如此。
- 情形 2：`Live` 对超过 200 个 sid 的请求直接报错（`app/singleton.go:563-565`），`openCurrentWindow` 记 `activity: live games unavailable; window not opened`（`activity.go.tmpl:240-244`）后返回，每一拍都如此。

```go
// demo/internal/service/game/activity.go.tmpl:157（基线 50e9a4e8）
func candidateSIDs(configured []int, own int32) []int32 {
	out := []int32{own}
	for _, sid := range configured {
		if int32(sid) == own || sid <= 0 {
			continue
		}
		out = append(out, int32(sid))
	}
	return out
}
```

这不是第 3 笔（`f051e24a`）引入的回归：改用 `Live` 之前，`LiveGames` 同样不去重、候选超过 `MaxPageSize` 同样报错（`git show 40d89ac6^:kit/service/global/service.go` 的 `LiveGames`）。改用 `Live` 之后这条路径仍是 activity 开窗的唯一入口，所以照样登记。

## 影响

活动功能在这份配置下永久不开窗；进程健康、就绪探针全绿，只有 Warn 日志。重复项是手写配置的常见笔误；生成值是 `[1000]`，默认不触发。

## 验收覆盖点

- 重复 sid、候选超过 `app.SingletonLiveMaxSIDs`：`startActivity` 在其他能力查找与 `Bind` 之前报错，错误含 `activity.game_sids`。
- 本服 sid、非正数照旧跳过，不算错误；`expectedGameSIDs` / `Live` 既有三条用例不变。
- 只改生成模板，生成工程 `go build ./... && go vet ./...`、`go test -race` 通过。

实施方向（约束与候选，不是命令）：在启动时拒绝而不是静默去重，与协调器“重复项拒绝、不改写调用方的集合”一致；候选上限取 `Live` 的单次上限。活着的 sid 超过协调器 `MaxExpectedGames`（64）但候选不超过 200 的情形在启动时无法判定，不在本条，见运行记录观察项。

## 本轮没做 / 没验

- 没有在真实进程上复现（drill5 / drill6 都是 `[1000]` 或两 sid 不重复）。
- 没有覆盖“候选 ≤ 200 但同时活着的 > 64”（运行期才知道，需维护者决定是否支持一个活动组超过 64 个 game 服）。
