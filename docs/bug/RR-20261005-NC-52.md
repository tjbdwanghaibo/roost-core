# NC-52：versionstore RedisStore.Update 退避后用退避前的值重试，竞争写落在退避窗口里时每次重试必输，伪 ErrConflict

2026-10-05，基线 `50e9a4e8`。P2（可用性：所有 Redis 后端的 Service——chat、account、activity、mail、session、platform、directory、match、global——在同键并发下返回可重试的 ErrConflict 远多于必要）。状态：已复现、已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261005-NC-52.md) · [本轮](../review/REVIEW-2026-10-05-n06-revn06.md)。

`versionstore/redis_store.go:369-382`（基线）：

```go
// Lost the race. CompareAndSet hands back what is stored now, so the
// retry re-applies mutate to fresh state without another round trip.
s.backoff(attempt)
raw = result.Current
```

CompareAndSet 带回的是“输掉那一刻”的值，随后 `backoff` 睡 (0, 2ms<<attempt]。退避的目的（`versionstore.go:124-130` 注释：让同键写者错开、不要一起耗尽预算）就是让赢家先写；赢家或其他写者只要在这段睡眠里写了一次，下一次 CAS 期望的就是旧字节，必输。稳定竞争下 8 次预算全花在不可能通过的比较上，调用方拿到 `versionstore: version conflict ... after 8 attempts`。同仓 `kit/service/rank/redis_store.go:195` 的循环写明“Back off with jitter before re-reading”，是正确形状；versionstore 自己的循环不是。

确定性复现（fake Redis，竞争者在每个退避窗口写一次）：

```text
retry_freshness_promises_test.go:57: Update after 8 attempts (8 backoffs, 9 competitor writes) failed: versionstore: version conflict: nc52:k after 8 attempts
retry_freshness_promises_test.go:109: mutate saw found=[true true false]; want present then absent (deleted during the backoff)
```

真实隔离 Redis（本机，`-race`，20 次 Update/写者，值为逐次增长的字符串切片）：修前三轮 6 写者 0～2/120、8 写者 3～5/160 次 ErrConflict；同机改为退避后重读，两轮均 0/120、0/160（探针跑完即删，不提交；小样本，只证明方向，不是容量数字）。chat 组合控制（两副本 × 3 写者并发 Append + 周期 Prune，见 [S2 记录](../review/REVIEW-2026-10-05-n06-revn06.md)）修前 `-race -count=3` 连续多轮全部因 `append k-200-0: versionstore: version conflict ... after 8 attempts` 失败，修后 9/9 通过。

影响：世界频道等单键热点在常规并发下出现伪冲突，用户请求失败需重试；冲突率指标被放大，掩盖真实热点。不丢数据、不重复写（CAS 语义正确）。没做：未做吞吐 / 延迟前后对照；MemoryStore 是锁实现，无此问题；Cluster 未跑。
