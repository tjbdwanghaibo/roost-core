# RR-20261006-36：`PatchSyncer.Stop` / `ReplicaSyncer.Stop` / `syncstream` 退订返回时回调仍可能在跑

2026-10-07，基线 `66d72a33`（main）。P3（三处都是公开 API，仓内没有生产调用方：`syncbus.PatchSyncer`、`cache.ReplicaSyncer` 只在测试里用，`syncstream.Subscribe*` 只在 skill 集成测试里用；接入方按“停止返回即可释放依赖”使用时，`Apply` / `Store` / handler 会在被释放的依赖上运行）。来源：A3 ②（维护者第十三轮要求本版完成，[方案](../feature/A3-2-SYNCBUS-DRAINING-UNSUBSCRIBE-2026-10-07.md)）实施中穷举 `ISyncBus` 订阅方时发现。状态：已复现；已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261006-36.md)。

## 机制

旧 `ISubscriber.Subscribe` 返回的退订函数只发起退订，不等在途回调（普通 NATS 只发 UNSUB；JetStream fanout 只从 map 删 handler，consume 回调可能正拿着旧快照调用它）。`mirror.Replicator` 为此自带一层准入门（NC-174），而另外三个订阅方没有：

- `syncbus.PatchSyncer.Stop()`（基线 `sync/syncbus/patch_syncer.go:55`）：调 `unsub()` 后直接返回；
- `cache.ReplicaSyncer.Stop()`（基线 `cache/mirror.go:40`）：调 `Replicator.Stop()`（只发起，不等）而不是 `StopWithContext`；
- `syncstream.SubscribeWithOptions` 返回的退订函数（基线 `syncstream/publisher.go:290`）：`unsub()` 后清空重组表，不等在途 handler。

## 触发 / 预期 / 实际

- 触发：`Apply` / `Store.Set` 卡在屏障上时调用停止。
- 预期：停止在回调返回前不报告完成（三步停机）。
- 实际：停止立即返回，回调仍在跑。

## 复现

基线代码上临时加的屏障用例（`GOWORK=off go test -count=1 -run TestOld ./sync/syncbus ./cache`）：

```text
--- FAIL: TestOldPatchSyncerStopReturnsWhileApplyRuns (0.00s)
    old_stop_red_test.go:25: PatchSyncer.Stop returned while Apply was still running
FAIL	github.com/tjbdwanghaibo/roost-core/sync/syncbus	0.455s
--- FAIL: TestOldReplicaSyncerStopReturnsWhileStoreRuns (0.00s)
    old_stop_red_test.go:41: ReplicaSyncer.Stop returned while the Store write was still running
FAIL	github.com/tjbdwanghaibo/roost-core/cache	1.084s
```

传输层同一根因（JetStream / 普通 NATS 的退订函数在回调返回前就返回，fake 与真实 nats-server 都红）的修前文本见方案 §9。

## 根因与方向

同一不变量（“停止返回 = 回调已静止”）由每个订阅方各自补，补漏了三处——这正是 A3 的来由。修复不在三处各加准入门，而是随 A3 ② 把排空下沉到传输层：`Subscription.Unsubscribe(ctx)` 本身等在途回调，三处改为等它。
