## RR-20260921-03：归还进行中被重新 Claim

`internal/service/game/zprobe_handback_test.go`（临时）：

```go
// probeEvictor 只在被 arm 之后阻塞，这样铺垫用的那次 Claim 能正常通过，
// 被按住的只有归还流程里的那次撤离。
type probeEvictor struct {
	mu      sync.Mutex
	armed   bool
	entered chan struct{}
	release chan struct{}
	once    sync.Once
}

func (b *probeEvictor) arm() { b.mu.Lock(); b.armed = true; b.mu.Unlock() }

func (b *probeEvictor) EvictPlayer(_ context.Context, _ int64) error {
	b.mu.Lock()
	armed := b.armed
	b.mu.Unlock()
	if !armed {
		return nil
	}
	b.once.Do(func() { close(b.entered) })
	<-b.release
	return nil
}

func TestProbeReclaimDuringHandBack(t *testing.T) {
	table := newFakeLeaseTable(1000)
	fencer := &fakeFencer{}
	var clockMu sync.Mutex
	clock := time.Unix(1_700_000_000, 0)
	now := func() time.Time { clockMu.Lock(); defer clockMu.Unlock(); return clock }
	advance := func(d time.Duration) { clockMu.Lock(); clock = clock.Add(d); clockMu.Unlock() }

	owners := newPlayerOwners(table, fencer, now)
	evictor := &probeEvictor{entered: make(chan struct{}), release: make(chan struct{})}
	owners.Evict(evictor)
	ctx := context.Background()

	// 一个后台消费者为了一件事取走了租约。
	if mine, err := owners.Claim(ctx, 42); err != nil || !mine {
		t.Fatalf("setup claim = %v, %v", mine, err)
	}
	evictor.arm()
	// 那件事早就做完了，租约现在是空闲的。
	advance(HandBackIdle + time.Second)

	var renewDone sync.WaitGroup
	renewDone.Add(1)
	go func() { defer renewDone.Done(); owners.renew(ctx) }()

	select {
	case <-evictor.entered: // 归还已经进到撤离里，ActiveSessions 那道检查已经过了
	case <-time.After(5 * time.Second):
		t.Fatal("the hand-back never reached the eviction")
	}

	// 玩家在这个窗口里登录到本进程。
	var mine bool
	var claimErr error
	var loginDone sync.WaitGroup
	loginDone.Add(1)
	go func() { defer loginDone.Done(); mine, claimErr = owners.Claim(ctx, 42) }()

	time.Sleep(50 * time.Millisecond)
	close(evictor.release)
	loginDone.Wait()
	renewDone.Wait()

	t.Logf("mine=%v err=%v admitted=%v redis_owner=%v released=%v",
		mine, claimErr, owners.Admitted(42), table.owner[42], table.released)
	if !mine {
		t.Logf("login refused — no split")
		return
	}
	// enter_game 从这里继续：它会把 Player 实体装载进本进程。
	// 所以本进程必须确实还持有这把租约。
	if owner := table.owner[42]; owner != 1000 {
		t.Fatalf("Claim told the login it owns player 42, but the shared table says owner=%d: "+
			"enter_game now loads the Player entity here with no claim behind it", owner)
	}
	if !owners.Admitted(42) {
		t.Fatalf("Claim told the login it owns player 42, but every write path refuses them")
	}
}
```

原始输出，`go test ./internal/service/game/ -run TestProbeReclaimDuringHandBack -race -count=5`：

```text
=== RUN   TestProbeReclaimDuringHandBack
2026/09/21 18:01:47 INFO player owners: idle lease handed back player_id=42
    zprobe_handback_test.go:78: mine=true err=<nil> admitted=true redis_owner=0 released=[42]
    zprobe_handback_test.go:85: Claim told the login it owns player 42, but the shared table says
        owner=0: enter_game now loads the Player entity here with no claim behind it
--- FAIL: TestProbeReclaimDuringHandBack (0.05s)
```

第五次运行落到另一支交错，同样红：

```text
    zprobe_handback_test.go:78: mine=true err=<nil> admitted=false redis_owner=0 released=[42]
    zprobe_handback_test.go:85: Claim told the login it owns player 42, but the shared table says owner=0 …
```

两种交错的区别只是 `confirmClaim` 与 `Release` 谁先拿到锁：

- `admitted=true`（`Release` 先、`confirmClaim` 后）：本地状态被重建，进程认为自己拥有 42 并放行写；
  Redis 无主。**这一支最坏。**
- `admitted=false`（`confirmClaim` 先、`Release` 后）：两边都被删干净，登录成功但每条消息被拒。

`-race` 没有报告数据竞争——这不是内存竞态，是两个操作对同一个决定的次序竞态。

### 顺带排除的一条

同一个窗口里走 `Owns`（后台消费者的入口）**不会**出问题：`Admit` 因 `handingBack` 拒绝，
`store.Owner` 返回本进程 SID 而非 0，于是落到 `Claim` 之外的最后一支 `return false, nil`
（`playerowner.go.tmpl:788`）。危险的入口只有绕开 `Admit` 的 `Claim`，也就是登录。

## RR-20260921-04：一次归还批次占住刷新循环多久

`internal/service/game/zprobe_budget_test.go`（临时）。把 `evictWait` 缩小 100 倍让探针跑得快，
再按同样倍数换算回出厂常量：

```go
type slowEvictor struct {
	mu    sync.Mutex
	armed bool
	delay time.Duration
}

func (s *slowEvictor) EvictPlayer(_ context.Context, _ int64) error {
	s.mu.Lock()
	armed, delay := s.armed, s.delay
	s.mu.Unlock()
	if !armed {
		return nil
	}
	time.Sleep(delay) // 实体锁被一个事务占着
	return nil
}

func TestProbeHandBackPassHoldsTheRefreshLoop(t *testing.T) {
	// …同样的 table / fencer / 可推进时钟…
	scale := time.Duration(100)
	owners.evictWait = evictBudget / scale
	evictor := &slowEvictor{delay: time.Hour}
	owners.Evict(evictor)

	// 二十把空闲租约——多于一个批次的预算。
	for id := int64(1); id <= 20; id++ {
		if mine, err := owners.Claim(ctx, id); err != nil || !mine {
			t.Fatalf("setup claim %d = %v, %v", id, mine, err)
		}
	}
	evictor.arm()
	advance(HandBackIdle + time.Second)

	start := time.Now()
	owners.renew(ctx)
	elapsed := time.Since(start)

	real := elapsed * scale
	if real >= playerroute.Lease {
		t.Fatalf("one hand-back pass can hold the refresh loop for %s, which is >= the lease (%s): "+
			"every OTHER player's lease this process holds expires while it is busy giving 8 of them back",
			real.Round(time.Second), playerroute.Lease)
	}
}
```

原始输出：

```text
=== RUN   TestProbeHandBackPassHoldsTheRefreshLoop
2026/09/21 18:03:52 WARN player owners: idle lease kept because its player could not be dropped
    player_id=11 err="player owners: dropping player 11 is taking longer than 50ms; it continues in the background"
… （8 条，playerID 因 map 遍历顺序而不同）
    zprobe_budget_test.go:64: one renew pass took 407.902792ms; per-eviction wait 50ms;
        observed multiple = 8.2
    zprobe_budget_test.go:68: at the shipped evictBudget=5s that is 41s of refresh loop held,
        against Lease=30s / RefreshInterval=10s
    zprobe_budget_test.go:71: one hand-back pass can hold the refresh loop for 41s, which is >= the
        lease (30s): every OTHER player's lease this process holds expires while it is busy giving 8 of them back
--- FAIL: TestProbeHandBackPassHoldsTheRefreshLoop (0.41s)
```

实测倍数 8.2 而不是 8.0：8 次撤离等待，加上 20 把租约的 `Refresh` 与选取开销。
缩放只影响 `evictWait`，`handBackBudget` 没有动，所以换算是线性的。

**这一条其实不需要探针**：`handBackBudget`(8) × `evictBudget`(5s) = 40s > `Lease`(30s) 是算术。
探针的价值只在于证明这三个常量确实在同一条串行路径上相乘。
