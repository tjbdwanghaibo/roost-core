# RR-20260921-03：game-demo 归还租约的过程中被重新 `Claim`，登录方拿到“是你的”，共享表里却已无人拥有该玩家

日期：2026-09-21（登记）、2026-10-04（核实）。等级 **P1**。状态：已修复（本地提交，未推送、未发版）。
来源：[REVIEW-2026-09-21-02](REVIEW-2026-09-21-02.md) §RR-20260921-03 与 [REPRO-2026-09-21-02](REPRO-2026-09-21-02.md)（09-21 第二轮审查，当时只登记在 [README](README.md) 表行与聚合报告里，没有单独主记录）；
现状核实：[REVIEW-2026-10-04-open-triage](../review/REVIEW-2026-10-04-open-triage.md) §1.1 / §2.1（v1.19.1 上 60/60 红，窗口比登记时更宽）。本文件是 10-04 修复时补建的主记录，问题描述摘自这两份报告。

## 位置、现象与根因（v1.19.1 = `d3e69336`，`demo/internal/service/game/playerowner.go.tmpl`）

- `handBackIdle:592-643`：`:606` 在选中玩家的那把锁里置 `handingBack = true`；`:622` 只在撤离**之前**看一次 `ActiveSessions`；`:626` `dropResident`；
  `:636` 等投影落库（RR-20260926-31 新增）；`:641` **无条件** `owners.Release(ctx, playerID)`——不再确认 `handingBack` 仍是自己设的那一个。
- `Claim:859-908`：`:874` `continuous := owners.Admit(playerID) == nil` 只把 `Admit` 当“是否连续持有”的探针，`handingBack` 让它为 false，但这只触发“跨间断扔副本”；
  `:875` `store.Claim` 此时 Redis 键仍是本进程的（同 token 走 `CompareAndExpire` 返回 ours），`mine=true`；`:906` `confirmClaim` → `confirmLocked:692` **`state.handingBack = false`**。
- `Release:934-944` 删本地状态 + `store.Release`（`CompareAndDelete` 同 token → 删除成功）。

设置标记的一方再也没有回头看它，而与它竞争的那个操作亲手清掉了标记。两种结局（探针均确定性复现）：

- 确认先于 Release：`mine=true admitted=false redis_owner_held=false`——登录成功、本地无租约，之后每条消息被 `AdmitMessage` 拒，Redis 无主。
- Release 先于确认：`mine=true admitted=true redis_owner_held=false`——本进程放行写入而共享表无主，另一进程可合法 Claim 并装载第二份 → `fatal projection version conflict`。

唯一入口是登录（`enter_game.go.tmpl:61-76`，`mine=true` 即 `GetOrCreate` 装载）；后台 `Owns` 在该窗口里 Redis 仍答本进程，走 `route.SID == self` 分支返回 false。
窗口：在 `:622` 之后完成 auth 的登录，到 `:641`——`dropResident`（≤ `evictBudget` 5s）+ 投影等待（≤ `projectionWait` 5s）。

## 修复约束（复审验证过的）

- 只在 `Release` 前锁内复核 `handingBack` **不够**：复核与 `store.Release` 之间仍可插入 `store.Claim`，即第二种交错。
- 推荐：`Claim` 在 `store.Claim` 之前发现该玩家正在归还就等这次归还结束（有界、受调用方 ctx 约束）再决定；归还在 `Release` 前锁内复核，被打断就不 Release；
  归还放弃之后 `handingBack` 回 false；登录等待受 `login_timeout` 约束、超时给明确错误。
- 不在快池阻塞（`Claim` 的调用路径：登录在连接读循环 goroutine，后台 `Owns` 在 saga 消费 goroutine）。

## 修复（2026-10-04）

状态：**已修复**（本地提交，未推送、未发版）。记录：[docs/bugfix/RR-20260921-03.md](../bugfix/RR-20260921-03.md)。

- `Claim` 先经 `enterClaim`：锁内看到该玩家正在归还就在锁外等 `leaseState.handBackDone`（或调用方 ctx 结束，返回包着 `ctx.Err()` 的错误，登录路径据此回 `login_timeout`），
  否则在**同一临界区**登记 `claiming[playerID]++`，返回前 `leaveClaim` 撤销；归还选人时跳过 `claiming > 0` 的玩家。两边各自在一把锁里做决定，同一玩家上二者互斥。
- 归还的 `handingBack` 只由 `finishHandBack` 清除（`confirmLocked` 不再碰它）；`Release` 前锁内复核状态仍是本轮标记的那一个；状态在 `store.Release` 期间保持标记，
  释放完才删本地状态并 close `handBackDone`，所以释放途中到来的 `Claim` 也会等。等过归还的 `Claim` 一律按“跨间断”处理（加入仍在跑的撤离）。
- 回归 `TestAClaimDuringAHandBackNeverEndsWithAnUnownedPlayer`（两种交错 + 归还放弃 + 调用方 ctx 结束）：修前在基线模板生成工程上两种交错 20/20 红
  （`mine=true … admitted=false redis_owner_held=false released=[77]` / `admitted=true redis_owner_held=false released=[77]`），修后绿。
