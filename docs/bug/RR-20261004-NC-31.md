## 触发、期望与实际

注册的 `DAOStep.Apply` 返回 `nil` 错误，但输出为坏 BSON、不同 `_id`，或 BSON 语法正确而字段与目标生成 DAO 类型不符。Repository 冷加载旧 schema 时触发普通 DAO 迁移。

期望：在 `CommitSystem` / WAL 准入前验证转换结果能被目标 DAO 加载、身份一致；无效迁移报告明确错误，原持久文档不变。迁移器可能存在实现错误，但框架已有目标解码契约，不能到写回以后才使用它。

实际三个具名反例：

| 输出 | 本轮结果 | 后果 |
| --- | --- | --- |
| `score` 是 string，目标为 int64 | CommitSystem调用1次，MongoStore投影1次；schema从1到3、version从7到8；随后RestorePersisted报类型错误 | 旧可迁移记录已经被替换。新的Manager/Repository再次冷加载仍失败；文档已是目标schema，不会再次迁移 |
| 非法 BSON字节且非空 | CommitSystem调用1次；unacked=1、projection=0；投影持续`invalid document length`，调用方最后只得到context deadline | 错误内容已准入真实文件WAL，取消等待不撤销它；不是成功前的同步拒绝 |
| BSON中的 `_id` 改成另一实体 | CommitSystem调用1次；unacked=1、projection=0；投影持续`invalid document key`，最后context deadline | 持久文档尚未被改，但已留下不可投影的WAL记录 |

两个超时是单场景自带1秒预算后的结果，反例断言是 **已发生CommitSystem及持久副作用**，不是用整包timeout充当红。没有数据删除、跳过坏WAL或自动补偿。

## 根因与位置

- [migration_runner.go](../../dataengine/engine/migration_runner.go) L60 调`migrator.Migrate`后只检查返回error，随后直接生成全量mutation并[提交](../../dataengine/engine/migration_runner.go) L75。没有目标解码、身份校验。
- [entity_repository.go](../../dataengine/engine/entity_repository.go) L227 先调用Runner持久迁移，成功后整聚合重读；[RestorePersisted](../../dataengine/engine/entity_repository.go) L246在持久提交之后才执行。因此“实体未发布”不代表原记录未污染。
- [生成模板](../../codegen/internal/dao/template_dao.go) L765已有目标类型解码能力；直接RestorePersisted对坏BSON/坏字段类型会在恢复tracker前报错，但普通Repository路径没有在提交前复用。
- [ValidateMutation](../../dataengine/validate.go) L66对普通Put检查非空payload/版本/形状，不解析目标BSON。[MongoStore.applyPut](../../dataengine/engine/mongo_store.go) L149才查BSON及ID；它能拒绝前两种结构错误，不能验证生成业务字段类型。
- [Projector.ReplayPass](../../dataengine/engine/projector_replay.go) L153遇投影错误不推进失败记录；连续前缀因此受阻是源码推断。本轮单条真实WAL反例已观察重试与unacked，未执行多条积压、重启、真实Mongo/HA矩阵。

## 实施方向（本轮未实施）

优先复用`entity.PersistedDaoLoader.RestorePersisted`与生成DAO自身的Unmarshal，不新增并行BSON模型、反射加载器或直接写库入口。

1. 在Runner调用CommitSystem之前验证目标payload：以目标schema调用hydration/解码，避免再次跑migration；确认DAO.Id与doc.Key.ID一致。解码只作用于尚未发布的候选DAO，失败不触碰持久状态；是否需要额外候选对象按调用方所有权明确，不能改已加载业务对象。
2. 手写DAO缺该能力时给明确unsupported或独立验证契约，不能静默绕过检查。数据库scope、version/schema元数据与现有Put归一化保持；不要求迁移步骤自己改`_version`。
3. 验证通过后仍走原SystemCommit→WaitProjection→整聚合重读，保留真实CAS及Remote信封拒绝规则；不要用内存转换替代持久确认。
4. 将本轮3个反例改成正式回归：无效输出不调用CommitSystem、原文档/版本不变；保留正常升级、取消后晚投影/重载及较新schema拒绝。另补真实Mongo、多DAO、CAS被并发写淘汰和进程重启。

已进入WAL的坏结果不是“自动跳过即可”：修复只防新准入，已有坏记录须具名备份与恢复方案，不据此获准删除生产数据。
