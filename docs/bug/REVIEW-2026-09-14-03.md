## RR-20260914-04 · P2 · 已入帧输入的迟到重传再次入帧

状态：未修复。位置：`lockstep/sequencer.go:164`、`:208`。

SubmitInput 在原帧号小于 next 时先改成 next，只在目标帧 pending map 内去重；Advance 随后删除已切帧 map，没有保存原始 (player, frame) 的处理身份。输入已进入帧 1，同一输入在切帧后重传又进入帧 2；首次迟到进入帧 2 的输入重传后又进入帧 3。

`TestReviewInputReplayAfterCut` 两个子例失败：`same original input executed in frames 1 and 2` / `frames 2 and 3`。executed 指被纳入帧，未运行模拟。一次性开火/技能操作可能被执行两次；所有客户端仍可能一致地收到这些帧，不应称为必然客户端分歧。

预期：重传幂等，同时保留第一次迟到输入折入下一帧的策略。建议在选择执行帧前验证原始输入身份，复用 Sequencer 增加每玩家有界已见窗口或确认水位，并明确乱序/重放期限。只存最大已见帧号会误丢尚未收到的低帧号。验收须覆盖按时、首次迟到、跨 tick 重传、乱序及显式输入覆盖迟到占位。

## RR-20260914-05 · P2 · 每 tick 补一帧不能追上持续推进的帧头

状态：未修复。位置：`lockstep/room.go:153-159`、`:295`、`:416`。

CatchupBatchFrames=1 被接受；每 Tick 先产生一帧再补至多一帧，积压变化为 +1-1=0。先生成五帧，从帧 1 追赶，二十轮成功发送后仍 `next=21 head=25 reliable_pages=20`，CatchingUp 不结束，实时 datagram 被跳过。batch=2 对照收敛。

预期：接受的配置在正常链路下能有限时间回到 live，或创建时拒绝不收敛配置。此处不是丢帧，客户端可持续收到固定落后的历史；问题是不能兑现追帧完成并切回 live 的契约。建议保证净补帧速度大于产帧速度，例如拒绝/归一化 1，或解耦追帧泵与 Tick。增大超时不能改变此速率关系。

## RR-20260914-06 · P3 · 座位 -1 与旁观者标记碰撞

状态：未修复。位置：`lockstep/sequencer.go:102`、`lockstep/room.go:125`、`:231`。

NewRoom 接受 Players={-1}，Attach(-1,101) 后 AttachSpectator(101) 仍成功。`TestReviewSpectatorSentinel` 报 `same session accepted as seat -1 and spectator: <nil>`，同一 session 同时位于 seats/spectators，违反互斥契约。

由源码可推得 broadcastOrder 列出两次、DetachSpectator 可清除共享 ownership/catchup 状态；本轮直接测试的是双重绑定。建议 Room 拒绝保留值，或用显式接收者种类代替占用 PlayerID 的哨兵；统一配置与 wire 对负座位的契约。

## RR-20260914-07 · P3 · 接受的房间生成自身解码器拒绝的帧

状态：未修复。位置：`lockstep/room.go:148`、`lockstep/sequencer.go:102`、`lockstep/wire.go:135`。

257 个玩家、MaxInputBytes=1、RedundancyDepth=1、MaxDatagramBytes=8192 被接受。所有玩家提交一字节后 Tick 成功，DecodeBroadcast 却报 `lockstep: frame encoding corrupt: input count 257`。配置只检查字节预算，没有统一解码上限 MaxFrameInputs=256。

预期：合法配置与输入生成可解码的数据。该触发需要超过 256 座位和自定义 datagram 上限，故列 P3。建议构造时校验协议条数上限；若支持更大规模，应统一升级/拆分协议，不能只放大 datagram 配置。
