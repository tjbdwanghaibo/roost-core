# RR-20260927-01：RR-80 的两个写失败用例在 Windows 上注入不生效，CI windows-compatibility 为红

日期：2026-09-27。基线：main `d4234c9`（v1.17.1 之后的文档提交）。来源：[OPEN-ITEMS-2026-09-27](../review/OPEN-ITEMS-2026-09-27.md) A01。等级 **P4**（测试 / CI，不影响生成物）。
引入：RR-20260926-80 修复（`520855b`）新增的用例。状态：已修复（见下）。

## 现象

`ffcf902` / tag v1.17.1 的 `ci / windows-compatibility`（run `36306850323`，tag 的 `36306851665` 相同）失败：

```text
shutdown_budget_promises_test.go:319: sync succeeded although configs/service is read-only
shutdown_budget_promises_test.go:341: sync succeeded although internal/bootstrap is read-only
```

## 根因（`d4234c9` 行号）

`codegen/internal/roost/shutdown_budget_promises_test.go:291-300` 的 `readOnlyDir` 用 `os.Chmod(dir, 0o555)` 让目录不可写，
`:317` / `:339` 的两个用例（`TestSyncWritesNothingWhenTheShutdownRefreshCannotBeWritten`、`TestSyncRollsTheShutdownRefreshBackWithTheTemplates`）
靠它让 `writeAtomic` 失败。Windows 上 `os.Chmod` 只按 `0o200` 位切换文件的只读属性，对目录不生效；目录照常可建临时文件、可改名，
`SyncProject` 成功，用例在 `:319` / `:341` 失败。被测代码（sync 的提交与回滚）没有问题，是故障注入在 Windows 上没有发生。

本地（darwin）把 `readOnlyDir` 的 `Chmod` 改成不改变权限（模拟 Windows 上的效果）后，两条用例在同样两行以同样文本失败，确认是这一机制。

## 修复约束（清单推荐）

改用在 Windows 上同样生效的写失败注入（优先），或在 Windows 上 `t.Skip` 并写明原因；看 windows job 转绿。

## 修复

见[修复记录](../bugfix/RR-20260927-01.md)：Windows 上改为持有目录里每个文件的句柄（Go 在 Windows 打开文件不带 `FILE_SHARE_DELETE`，替换 / 挪走这样的文件会被拒绝），
Unix 上沿用去掉目录写权限。
