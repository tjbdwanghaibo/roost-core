# RR-20261005-NC-201：redis-cluster-suites.sh 继承 ROOST_DATAENGINE_IT / REDIS_ADDR，把全环境故障套件跑到共享隔离环境上

日期 2026-10-05。基线 main `8597046c`。等级 **P3**。状态：已复现，未修复；已修复、声明场景验证，未发版（见文末）。来源：N15。

## 触发与实际

`kit/scripts/integration/redis-cluster-suites.sh:15-17` 的注释承诺：同包里以 `REDIS_ADDR` / `ROOST_DATAENGINE_IT` 准入的用例“在这里照常 skip”。但脚本不清理这两个变量，在 source 过隔离环境 env.sh（导出 `ROOST_DATAENGINE_IT=1`）的 shell 里执行时，替身 go 收到：

```
stub go test -tags=integration -count=1 -p 1 ./kit/redis ./kit/service/mail ./redis/driver ./remoteentity ./service/mail
ROOST_DATAENGINE_IT=1
REDIS_ADDR=127.0.0.1:1
```

（[脚本](../review/evidence/noncore-review-20261005-n15/cluster_red.sh) · [输出](../review/evidence/noncore-review-20261005-n15/nc201-red.txt)。）没有 `-run` 限制，`./redis/driver` 的 toxic 用例会 `/reset` 共享 toxiproxy，`./remoteentity` 的进程杀死 / 分区用例会改动共享 Mongo / Redis——正是共同要求里“跑 integration 一律加 -run”要防的情形（N03 约 1s 事故）。

## 根因

脚本只 `export GOWORK=off`，没有 `unset` 注释里说会 skip 的准入变量；准入完全靠调用者的环境。

## 影响与定级

审查 / 修复者按文档在本机跑 Cluster 套件时，会对共享隔离环境注入故障、干扰并行会话，结果也混入非 Cluster 用例。测试设施问题，定 P3。

## 验收

脚本内 go test 看不到 `ROOST_DATAENGINE_IT` / `REDIS_ADDR`，Cluster 准入变量照常传入。

## 修复（2026-10-05）

已修复、声明场景验证，未发版。[修复记录](../bugfix/RR-20261005-NC-201.md)。以上原始现象与修前红保留不改。
