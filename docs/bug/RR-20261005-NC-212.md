# NC-212：CompileEnvironment 只查 catalog handle 唯一、不查 key 唯一；同一个 key 在一次编译里被解析成两个条目

2026-10-05，基线 `c10cc9ac`。P3（需要业务提供带重复 key 的 catalog 才触发；触发后编译器对同一个名字用两套策略，能编译出 Host 不接受的绑定）。状态：已复现；已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261005-NC-212.md)。[本轮](../review/REVIEW-2026-10-05-n09-batch4.md)。

## 触发与差异

`validateCompileEnvironment` 的 `validateCatalogHandles`（`compile_authority.go:113-125`、`checkHandles :192-201`）只要求 handle 非零且唯一。key 只有 temporal（`:311-317`）和 process property 查了唯一。

编译器按 key 查 catalog 的写法不一致：

- `compile_capability.go:12-29` 建 authority 表，后出现的条目覆盖前面的（last wins）；`compile_owned_entity.go:9-12` 的 template 表也是 last wins；
- `unitTemplateEntry`（`compile_owned_entity.go:71-78`，typecheck 用它取参数 / 覆盖策略）、`compile_typecheck.go:30` 等用循环取第一个（first wins）。

## 复现

默认环境追加第二个 `deployable.trap`（handle 2，带 int 参数 `power`），owned_trap 的 spawn 绑定 `"parameter_bindings":{"power":true}`：

- 单条目且带 `power:int` 时：`TYPE_MISMATCH …parameter_bindings.power value has type 3, expected 2`；
- 重复 key：`validateCompileEnvironment` 零诊断，编译零诊断，spawn 的 template handle 是 2、绑定是 bool——typecheck 看的是第一个条目（没有 `power`，跳过类型检查），capability 校验看的是第二个条目（有 `power`，通过）。

正式回归（修前）：`TestCompileEnvironmentRejectsDuplicateCatalogKeys`：`missing error CATALOG_DUPLICATE_HANDLE at $.gameplay.unit_templates[1].key in []skill.Diagnostic{}`。

## 影响

catalog 由业务生成，重复 key 通常是数据错误。目前它不被拒绝，编译器对同一个名字前后用不同条目，编出的 Program 被 Host 按 handle 2 的策略执行，类型检查形同虚设。

## 验收覆盖点

attributes / resources / statuses / unit_templates / collision / damage_types / elements / tags / shared_states 各自 key 非空且唯一，重复时在 `…[i].key` 报错；默认环境不受影响。
