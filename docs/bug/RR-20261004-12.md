# RR-20261004-12：生成器运行期间 `runGenerators` 用 `os.Chdir` 把整个进程移进被生成的工程，并发启动的子进程继承 `.roost-sync-*` 暂存树为工作目录（Windows 上暂存目录因此删不掉）

日期：2026-10-04。基线：main `9bf20e28`（v1.19.2 之后）。来源：[W-2026-10-04-05](WANTED.md)（windows-compatibility 上 demo 模板测试两次 `TempDir RemoveAll cleanup` 失败）。等级 **P3**。状态：已确认，已修复（见下）。

## 触发

1. 同一进程里，一个 goroutine 正在跑 `SyncProject`（或 `NewProject` / `Generate` / `GenerateTransactional` / `Generate -check`），处于生成器窗口：`runGenerators` 已 `os.Chdir(<暂存树或工程根>)`、尚未切回。
2. 另一个 goroutine 在这段窗口里启动子进程且不设 `exec.Cmd.Dir`（库调用方自己的命令、本仓 `cli.go` 的 `go env`、`framework_release.go` 的 `go mod download`；测试里是并行用例 `TestGeneratedComposeShapeCheckCatchesTheTmpfsShapeComposeUpRefuses` 的 `docker compose version`）。

## 预期

生成器只读写传给它的工程；进程的工作目录不随之移动，别的 goroutine 启动的子进程与相对路径解析不受影响。`generatorWorkingDirectory` 的注释承诺的正是“库调用方并发时互不影响”。

## 实际

子进程继承暂存树为工作目录。macOS / Linux 允许删除别的进程的工作目录，所以只是“子进程跑错了目录”；**Windows 上进程的当前目录句柄不带 `FILE_SHARE_DELETE`，目录在该进程存活期间删不掉**：`SyncProject` 的 `defer os.RemoveAll(stage)`（错误被忽略）失败，`.roost-sync-*` 残留在工程旁边。CI 失败文本（run 37205724165，windows-compatibility）：

```
--- FAIL: TestDemoTemplateFollowsTheGameServiceName (60.22s)
    testing.go:1617: TempDir RemoveAll cleanup: unlinkat C:\Users\RUNNER~1\AppData\Local\Temp\TestDemoTemplateFollowsTheGameServiceName642858298\001\.roost-sync-3468441803: The process cannot access the file because it is being used by another process.
```

报错落在暂存目录**本身**（不是其中某个文件），错误码是 `ERROR_SHARING_VIOLATION`——正是“目录被某进程以无删除共享方式打开 / 作为当前目录”的形态；`testing` 已对该错误码重试 2 秒（`testing_windows.go` `isWindowsRetryable`），仍失败。

macOS 上的修前红（见 [修复记录](../bugfix/RR-20261004-12.md)）：

```
--- FAIL: TestGeneratorsDoNotMoveTheProcessIntoTheTreeTheyGenerate (0.01s)
    the process working directory was the generated tree while generators ran: /private/var/folders/…/TestGeneratorsDoNotMoveTheProcessIntoTheTreeTheyGenerate3562826371/001
    a child started without Dir while generators ran inherited the generated tree as its working directory (go env GOMOD = /private/var/folders/…/001/go.mod)
--- FAIL: TestSyncProjectStagesNeverBecomeAChildsWorkingDirectory (1.38s)
    9 children started without Dir ran inside a staging tree, e.g. /private/var/folders/…/001/.roost-sync-4089255759/go.mod
```

探针：5 次 `SyncProject` 期间另一 goroutine 连续启动 4919 个不设 Dir 的 `pwd`，72 个落在 5 个不同的 `.roost-sync-*` 里。

## 根因（基线 `9bf20e28` 行号）

- `codegen/internal/roost/generate.go:329-344`：`runGenerators` 持 `generatorWorkingDirectory` 锁，`os.Getwd` → `os.Chdir(root)` → 跑生成器 → `os.Chdir(old)`。锁只串行化生成器之间，挡不住同进程其他 goroutine 观察到进程级工作目录；第 30-33 行注释把它说成库调用方并发的保护。
- 生成器参数全是相对路径（`generate.go:67-147`：`./game`、`./service`、`dao.DefaultDefDir`、`registry.Run(".")`、`projectRPCDirs(".")` 等），依赖这次 chdir。
- `codegen/internal/roost/project.go:181-185, 212`：`SyncProject` 在工程旁边建 `.roost-sync-*`，`Generate(stage)` 把进程移进去；`defer os.RemoveAll(stage)` 的错误被丢弃，所以 Windows 上的删除失败不报告、暂存树静默残留。`NewProject`（`.roost-project-*`，`project.go:94-110`）、`GenerateTransactional`（`.roost-generate-*`）、`checkGenerated`（系统临时目录）同理。

## 修复约束

- 生成器拿工程根下的路径，`runGenerators` 不再改进程工作目录；生成物逐字节不变（servicerpc 的头注释记录 `-dir` 原文、孤儿识别按头注释匹配，必须仍是 `./internal/rpc/<name>`）。
- 不改测试清理方式、不跳过 Windows。

## 修复（2026-10-04）

**状态：已修复（worktree，本地验证通过，已提交，未推送、未发版）。** 记录：[docs/bugfix/RR-20261004-12.md](../bugfix/RR-20261004-12.md)。`generator.Run` 改为 `func(root string, w io.Writer) error`，各生成器参数用 `under(root, …)` 组成绝对路径；`servicerpc` 新增 `RunIn(base, args, w)`，相对 `-dir` / `-out` 按 base 解析、头注释仍记原文；`runGenerators` 去掉 chdir，锁改名 `generatorRuns`、只做串行化。

**未证明的部分**：CI 两次失败需要占用一直持续到用例结束后 2 秒以上；本包并行阶段在 Windows 上唯一不设 Dir 的子进程 `docker compose version` 是短命的，所以本修复消除的是进程内唯一能让暂存树成为某进程工作目录的路径，不能证明它就是那两次失败的全部原因。修复后 windows-compatibility 若仍以同样文本失败，占用者只能来自进程外（Defender / 索引），那时测试侧的有界重试才有依据。
