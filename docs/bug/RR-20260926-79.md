# RR-20260926-79：Direct 政策的绑定表只在 Unbind 时清理

日期：2026-09-27。基线：本地 main `736bdb2`（RR-64～72 合并后，未推送）。来源：第三轮修复后独立审计（[REVIEW-2026-09-27-audit3](../review/REVIEW-2026-09-27-audit3.md)）。等级 **P4**。引入：RR-20260926-70 修复。状态：已复现，未修复。

会话关闭或业务 `Unregister` 时 Manager 丢掉订阅，但 `sync/entitysync/policy/direct.go:53` 的 `Direct.bound` 表项不删，内存随历史绑定数单调增长
（`manager live subscriptions=0, Direct.bound entries=1000`）。未发现过期绑定被错误恢复。Direct 目前不在生产代码使用。复现：[REPRO-2026-09-26-07](REPRO-2026-09-26-07.md) §2。

修复约束：会话关闭 / subject 注销（非 RR-59 撤销）时删除相关绑定，上界落在“活跃绑定数”；RR-59 撤销后的恢复语义（RR-70）不变。

## 修复（2026-09-27）

状态：**已修复，未发布**（本地提交，未推送）。按上方修复约束实现，见[修复记录](../bugfix/RR-20260926-79.md)。

机制：Manager 在本来就逐条丢掉订阅的两处——`dropSession`（`CloseSession` 与传输失败关闭会话）和 `Unregister`——于同一把 `subj.mu` 内记下带
`Released` 回调的来源（新增 `Manager.NewSubscriptionSourceWithHooks` / `SubscriptionSourceHooks` / `ReleasedSubscription`），连同 RR-59 撤销后尚待
重新提交的该会话 / 该 subject 的记录，排队到下一次 Flush 的政策阶段交付（先于重新提交），不在调用方路径上回调、不起 goroutine。`policy.Direct`
收到后以新增的 `SubscriptionSource.Holds` 确认本来源确实不再持有（通知途中重新 Bind 的保留）再删除绑定，并 `Unsubscribe` 释放 Manager 为它留的
撤销记录。RR-59 撤销不算释放，RR-70 的恢复语义与记录不变。

修前红（`62fdbe6` + RR-78 的实现 + 本次回归）：`Direct keeps 1000 bindings with no manager subscription behind them (bound=1000 live=0)`、
`the binding of a closed session outlived it while its subject was away: bound=1`；另以临时探针确认旧实现在实体重新登记后把已关闭会话的绑定重新提交到
同 ID 重开的新连接（`bound=1 reopened session 7 holds 8=true`）。
