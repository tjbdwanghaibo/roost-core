## RR-20260909-02：Session 冲突清理可能误删重新取得的 claim

**P2，已复现，未修复。** Kit `79d40dee4df8c4c6d637ef531466aad32b6252b7`，Core `df76988f059de8827f20026f4f718fd61ae057ce`。

**位置：** Kit `service/session/service.go:339` 先 discard run 再 releaseClaimIfCurrent；新增 helper `:364–365` 将旧 claim 直接传给 Store.Delete。Core `versionstore/memory_store.go:63` 重建键时版本回到 1，`:78–81` 仅比较版本后删除。

**触发顺序：**

1. 两个不同 owner 同一 RequestID 竞争。账本 Update 正确决定胜者，落败请求 A 开始清理。
2. A 已删掉自己从未交付的 run，尚未执行 releaseClaimIfCurrent，旧 claim 仍在。
3. 同一 owner 的新请求 B 使用另一个 RequestID 进入。resolveClaim 看到旧 run 不存在，正常释放孤立 claim，再创建新 run 与新 claim；B 成功返回。
4. 新 claim 的版本也是 1。A 恢复执行，用旧 claim 的版本 1 调 Delete，新 claim 被误删。
5. 请求 C 随后进入，因 owner 已无 claim 而再次成功。B 与 C 的 run 在存储中均为 open，破坏“每个 owner 一个 live run”。

**根因：** 版本号只能区分一次键生命周期内的修改。删键后重建版本重置，会出现旧版本与新版本数值相同的 ABA。`releaseClaimIfCurrent` 注释中“被别人替换一定导致版本不匹配”的前提不成立；即使传入完整 Versioned，当前 Delete 也不比较旧值的 RunID。

**独立证明：** 在真实 MemoryStore 外仅包装 Runs.Delete：实际删除完成后、返回前，让同 owner 新请求通过真实 Enter 执行完整重入。账本竞争使用本次修复新增的 barrierLedger。没有伪造 claim 的删除或重建结果，没有修改框架代码。普通运行和 `-race` 均在同一业务断言失败，race 运行没有报告数据竞争：

```text
FAIL TestReviewCollisionCleanupPreservesReacquiredClaim
successful replacement run-3 lost claim; third Enter=(run-4,<nil>); stored states=(open,open)
```

完整外部测试及命令见[复现附录](REPRO-2026-09-09-02.md)。

**影响：** 成功返回的 run 失去 owner 的 claim 索引，后续进入绕过唯一 live run 限制；按 owner 查询/清理可能只看见后一个 run。没有实测资源泄漏数量或真实游戏后果。

**Redis 边界：** 本轮行为复现使用 MemoryStore。另读 `versionstore/redis_store.go`：Delete 重新读取当前值，只比较 expect.Version，之后 CAS 使用的是重新读取的 raw；这不能证明旧 claim 的身份。因此从源码推断该身份前提也不能依赖 Redis 自动补齐，但本轮没有连接真实 Redis 重放此交错，不将其写成已实测。

**建议方向：** 清理必须原子校验不可复用的 claim 身份/代际，或者让版本跨删除重建保持单调。仅在 Delete 前增加一次 RunID Get 检查仍有检查到删除之间的竞争窗口；仅调换两个清理操作也需要重新证明失败与重入语义。修复前先保留本测试，并增加后端契约的“旧 token 不得删除重建值”验证。不要在本轮顺带扩大到所有 Store 调用者都受影响的结论。

## 2026-09-29：正常 Finish 的 ABA 新触发

**原 Enter 撞键清理顺序已修；正常 Finish 仍有同根因残留，P2。** 当前单仓 Core `e10dd3f18d2da985f969cbc54cb19a87f1f287af`。本轮没有重新验收原旧触发，历史“已修复”限定为 U-0158 的原清理路径。

位置：`service/session/service.go:426–445` 的 releaseClaim 分开 Get/RunID 校验和版本 Delete；`finish:570` 调 resolve 先将 A 置终态再清理 claim。`versionstore/redis_store.go:355` Create 重建为 v1，`:392` Delete 只先检查版本，再用重新读取的当前 raw 做 CAS。

独立测试仅暂停第一次 Claims.Delete 的调用入口，不伪造删除结果：

1. A 正常 Finish 已终态，读到自己的 v1 claim；删除执行前暂停。
2. B 用相同 owner、新 RequestID 正常 Enter，resolveClaim 识别 A 终态，清掉旧 claim，创建 B 的新 v1 claim并成功返回。
3. A 恢复删除，版本相同导致 B 的 claim 被删；C 再 Enter 成功，B、C 都 live。

本轮**真实 Redis**和 race 运行失败：`TestReviewTerminalFinishCannotDeleteReacquiredClaim: b=run-2 c=run-3 both live`，无 Go race 报告。区别于原修复：撞键落败 run 在释放 claim 前保持 live 可以保护那条路径；正常 Finish 的 run 已终态，这个前提不成立。Get 前比 RunID 不能代替删除时的原子身份约束。

保留本编号，不给同根因新增 RR。优先使用不可复用身份/代际的原子条件删除，或跨删除重建单调版本；实现时同步明确 MemoryStore/RedisStore 的契约。没有扩大为所有服务一定遭遇 ABA，也没有实测资源泄漏数量。
