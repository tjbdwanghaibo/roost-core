# RR-20260926-48：事务内新建实体的锁持有到事务结束且为无超时阻塞锁——交叉创建两个 ID 使两个快 worker 永久死锁；memory 模式 handler 内 Create 不加锁

日期：2026-09-26。基线：本地 main `2330d57`（RR-30、33～47 修复合并后，未推送）。来源：修复合并后独立审计。等级 **P2**（活性：快池永久死锁，Guard 与声明实体不释放）。引入：RR-20260926-35 复核补修。状态：已复现，未修复。

- H1 `Create(X)` 再 `Create(Y)`，H2 `Create(Y)` 再 `Create(X)`：两 worker 永久阻塞于 `entity/entity_guard.go:242` 的 `mu.Lock()`（`entity/manager_factory.go:23` → CreateInScope → `:66` RequireEntity），不做 Cast 的锁序检查（`CheckContainAllLock`）也不 try-lock。
  复现：[REPRO-2026-09-26-05](REPRO-2026-09-26-05.md) §1：`after 2s only 0/3 requests returned … Fast:{Running:2 … OldestWaiting:2.000098459s}` FAIL；49f20ee 同探针 PASS。推断：先 Create X 再 Cast 更高锁组亦可成环。
- memory 模式（`nest/execution.go:121` 快路径不绑定 capturer）handler 内 Create 创建后立即解锁，handler 随后修改未加锁实体：`another goroutine could lock the new entity mid-handler=true`（§1b，基线同样）。

修复约束（维护者 2026-09-26 批准）：事务内（及任何 Nest handler 内）新建实体的加锁遵循与 Cast 相同的锁序规则并使用 try-lock；冲突时整条消息回滚后按锁超时类可重试错误重新准入（不得在快 worker 上无界阻塞，不得在 handler 执行一半迁移）；memory 模式 handler 内 Create 同样在 Guard scope 内持锁至 handler 结束；RR-35 的提交边界与撤销发布语义保持。

## 修复（2026-09-26）
