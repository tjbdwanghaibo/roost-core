# NC-62：attribute 生成器接受框架无法表示的声明（float 静默截断、超 64 位 / AttrID 范围）

2026-10-05，基线 `50e9a4e853641f348c879b85c282af9c5813f656`。P3（float 字段的值经 GetAttr / ExportValues 静默丢失；需要用户声明非整数属性，模板自带 profile 不触发）。状态：已复现、已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261005-NC-62.md) · [本轮](../review/REVIEW-2026-10-05-noncore-n07.md)。

## 触发与差异

`attribute.AttrValue` 是 int64，“One type for the wire and for bulk transfer is what lets the framework move attributes it knows nothing about”；脏位是 uint64 的一位，`AttrID` 是 uint16。生成器 `codegen/internal/attribute/parse.go:128-197`（`buildProfile`）只检查字段数不超过 `max`，不检查：

1. 字段类型能否装进 AttrValue。`float64` 字段照样生成 `AttrValue(c.Rate)`，0.15 截成 0；`ExportValues` 判断的是原字段 `!= 0`，于是把 `{id: 0}` 写进稀疏表（还违反“零值不进表”），导出 / 持久化 / 重放后值为 0。
2. `max` 是否超过 64：第 65 个字段生成 `AttrMaskX uint64 = 1 << 64`，生成成功、编译失败。
3. `index + max - 1` 是否超过 uint16：生成的 `AttrID` 常量溢出，同样到编译期才失败。

## 复现

临时模块里用当前生成器 + 运行时文件：

```
rate=0.15 GetAttr=0 export=map[1:0] reload=0
vet: combat/gen_wide_attribute.go:139:23: cannot use 1 << 64 (untyped int constant 18446744073709551616) as uint64 value in constant declaration (overflows)
```

新增 `TestParseDirRejectsAttributesTheWireCannotCarry` 修前 6 叶子全部 `accepted a profile the framework cannot represent`。原文见[证据](../bugfix/evidence/noncore-bugfix-20261005-n07/README.md)。

整数窄类型（int32 等）由生成 setter 转换是文档写明的行为，不在本条；`SetAttr` 对超范围值按 Go 转换回绕也保持原样，只在记录里列为观察。具名类型（`type Rate float64`）语法上看不出底层类型，修复后仍按原样信任，写在修复记录的限制里。
