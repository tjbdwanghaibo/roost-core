# RR-20260928-14：`codegen/internal/roost` 包测试在 Windows CI 超过 10 分钟默认超时

日期：2026-09-28。基线：`3a58811`（已推送）。来源：推送后 CI（run 36358695147，windows-compatibility）。等级 **P3**（门禁失效：Windows job 无法给出结论，RR-20260927-01 的 Windows 修复因此也未得到验证）。引入：本轮大量新增“生成完整工程 / 实跑生成脚本”的回归。状态：已修复（本地，`fix-r11-b22`，未推送；Windows 上待 CI 实跑确认），见下。

`.github/workflows/ci.yml` windows-compatibility 的 `go test ./...` 使用默认 10 分钟包超时（job `timeout-minutes: 20`），日志：`panic: test timed out after 10m0s` / `FAIL github.com/tjbdwanghaibo/roost-core/codegen/internal/roost 600.145s`。macOS 上该包 `-race -count=1` 约 365～524s。

修复约束：先用 `go test -json` 在本机测出各用例耗时并列出前 20；优先把测试本身变快且不削弱断言——共享只读的生成工程（按参数缓存，只读用例复用、会改文件的用例复制一份）、安全的 `t.Parallel`、避免重复编译 CLI；
若仍超出 Windows 预算，再在 CI 为该包给出显式 `-timeout`（并相应调整 job `timeout-minutes`），理由与实测耗时写进记录；不得删用例、不得用 `-short` 跳过 Windows 专属路径（RR-20260927-01 的用例必须在 Windows job 里跑到）；Linux / macOS job 同样受益并核对未超时。

## 修复

见[修复记录](../bugfix/RR-20260928-14.md)。只改测试：同参数的生成工程只真实 `NewProject` 一次，各用例拿私有副本；副本与新鲜生成逐字节、逐权限位相同，由新用例 `TestProjectFixtureCopiesMatchAFreshNewProject` 每次实跑证明。另外给 47 个慢用例加了 `t.Parallel`。本机非 race 从 265s 降到 73s（`-parallel 1` 下 102s），`-race` 降到 116s。按 Windows 慢 2～3 倍估算仍低于 10 分钟，所以 CI 不加 `-timeout`。RR-20260927-01 的两条 Windows 用例照常在 Windows job 里跑。
