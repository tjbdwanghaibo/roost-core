# RR-20260927-11：handler 内新建实体的事务捕获失败被业务吞掉后，事务照常提交

日期：2026-09-27。基线：`d4234c9`。来源：[OPEN-ITEMS-2026-09-27](../review/OPEN-ITEMS-2026-09-27.md) C26（[bf-35](../bugfix/RR-20260926-35.md) “未验证项 / 风险”）。
等级 P3（需要 DAO / 实体的回滚捕获或参与者登记失败，且业务吞掉 `Create` 的错误）。状态：已复现，已修复。
codebase-memory 图谱停在 09-26，已过期；以源码为准。

## 现象与根因

`entity/manager_factory.go:101-106`：`CreateInScope` 调 `capturer.CaptureCreatedEntity` 失败时撤销发布、把错误交给业务。Nest 的实现
`nest/rollback.go` `(*RollbackTx).CaptureCreatedEntity` 只把 `CaptureEntities` 的错误原样返回，事务上不留任何记号；`invokeWithTransaction`
（`nest/execution.go:206-216`）只看 handler 的返回值与 `createLockBusy`。业务吞掉错误、返回成功时事务照常准入提交：捕获失败之前可能已经
`RegisterCommitParticipant`（实体 / DAO 的提交参与者在快照之前登记），本事务的其他修改带着“新建失败”的结果持久化。

同一个函数里新建锁冲突（RR-20260926-48）已有“记在事务上、handler 结束时强制失败”的处理（`createLockBusy`）；动态 Cast 的捕获失败
（`nest/cast.go:189`）同样只把错误返回业务，没有事务级记号（见修复记录“核对”）。

## 修复约束（清单 §H 推荐，维护者 2026-09-27 决定按推荐执行）

与 Cast 捕获失败同类处理：`CreateInScope` 捕获失败标记事务必须失败（业务吞错也回滚）。

## 修复（2026-09-27）

状态：**已修复，未发布**（worktree 分支 `fix-r7-ent` 本地提交）。`RollbackTx` 记下第一次新建捕获失败（`createCaptureFailed`），
`invokeWithTransaction` 在 handler 结束时与 `createLockBusy` 同处把它并入错误并整条回滚；不重排。详见[修复记录](../bugfix/RR-20260927-11.md)。
