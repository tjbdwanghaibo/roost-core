# RR-20261006-37：motion `enabled_slots` 只在定义写了 steering / offsets 时才查，Runtime 却每步都发这两种步骤

2026-10-07，基线 `dac4f38c`（main）。P3（需要业务环境关掉 steering 或 offsets 槽位才触发；默认环境开着全部槽位，仓内没有关掉槽位的环境）。来源：B3 ③（维护者第十三轮要求本版完成，[方案](../feature/B3-3-HOST-CAPABILITY-TABLE-2026-10-07.md)）实施中，守卫 `TestRuntimeAsksHostOnlyForCompiledRequirements` 第一次运行时发现。状态：已复现；已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261006-37.md)。

## 触发 / 预期 / 实际

- 触发：环境的 `Motion.EnabledSlots` 不含 `steering`（或 `offsets`），表示 Host 不接受这种 motion 步骤；技能定义的运动衍生物不写 steering（或 offsets）。
- 预期：Host 不接受的步骤不会在运行期发给它——要么编译期拒绝，要么 Runtime 不发。
- 实际：编译通过（`compile_motion.go` 只在 `motion.steering != nil` / `len(motion.offsets) > 0` 时查槽位）；Runtime 的 `stepSpawnMotion`（`spawn_motion.go`）对每个运动衍生物每步都发 `SteeringMotionStep`（交出解析后的方向）与 `OffsetsMotionStep`（交出加完偏移的位置），不论定义写没写。Host 拒绝时施法失败，费用已扣。

## 复现（基线代码上的临时用例）

```text
enabled_slots without steering, definition without steering: compile errors=false; Activate err=host: steering motion is not supported; cast status=failed; caster mana after=90 (was 100)
```

## 根因

编译器与 Runtime 对“哪些 motion 步骤会发给 Host”各有一份理解：槽位检查按定义里写了什么，Runtime 按固定的步骤流水线。这正是 B3 ③ 要消除的“三处各自维护集合”。
