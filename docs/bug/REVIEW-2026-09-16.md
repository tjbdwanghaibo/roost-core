# 09-16：Journal 不确定结果

## RR-20260916-01 · P2 · 写入/发布结果不确定后继续使用旧内存状态

新发现，未修复。Core `b4bf09e8ec627c06c781c015f3082be6e9ab978e`。用户声明没有修复，旧问题不验收。

位置：syncstream/file_journal.go:233 flushBatch 在 Write 后调用 Sync，错误返回没有隔离后续 Record；Checkpoint:261 在 durableReplace 返回成功后才更新 generation。Linux 的 file_durability_unix.go:20 先 Rename，再同步目录，因此存在文件已发布但函数报错的阶段。History.Append（syncstream.go:140）在 Record 报错时保持旧 latest。

两条受控复现均使用真实临时文件，并通过测试 overlay 注入错误返回，不是实际硬件故障测试：

1. 先保存 sequence 1；下一条 sequence 2 完整写入并同步，注入同步结果错误，使 History 仍保留 latest 1。直接重试 Append 又成功写入 sequence 2。重启因同一 WAL 出现两个 sequence 2 返回 ErrInvalidSnapshot。
2. 保存 sequence 1 后，checkpoint 实际发布新 generation，再注入发布同步错误。对象仍保存旧 generation；随后 Append sequence 2 返回成功，却落在旧 WAL。重启选最新 checkpoint/WAL 对，仅恢复 sequence 1，成功追加的 sequence 2 消失。

期望：不确定副作用必须先恢复一致的写入起点，或拒绝后续写入；不能把错误都解释为无副作用。实际：两条失败路径都允许后续调用成功，随后重启失败或遗漏成功写入。正常写入、正常 checkpoint、错误后关闭并重新 Load 两个对照均通过；明确写入前或发布前返回错误的两个对照也能安全重试。

证据限制：注入在真实操作成功后返回错误，代表“副作用已完成但调用方收到错误”的一种允许故障状态；没有证明某型号磁盘实际产生该结果，也未执行 Linux 断电。Linux Rename 后目录同步的源码顺序直接支持第二种歧义。Windows 下测试验证上层错误处理状态机，不声称实际 MoveFileExW 错误必然意味着已发布。

建议：区分确定拒绝和结果不确定，后者进入故障状态、拒绝继续写，要求关闭/重载或显式恢复；如支持原地恢复，应按可确认的 WAL 末端及已发布 generation 重建 History，不能仅重置错误位。不要无条件截断成功完整记录，也不要用仍可能过期的内存快照强制覆盖已发布快照。本轮仅提供方向，未修复。

与旧半尾、Import/Restore 问题不同：本项不需要半条记录或外部快照导入，根因是错误返回未阻止继续使用落后的写入状态。
