## RR-20260914-09 · P2 · 回调失败后丢失已释放但未应用的帧

状态：未修复。位置：`robot/lockstep.go:92`、`:104`、`:115`，尤其 apply 中 Simulate、SubmitInput、ReportHash 的提前返回。

HandleBroadcast/HandleFrames 先让 Assembler 一次释放整个连续批次，再交给 apply。Assembler 的 next 此时已经越过整个批次。apply 中途出错时没有保存尚未处理的帧，也没有将 Bot 标记为不可继续；再次投递原批次被当作重复丢弃，后续新帧照常返回成功。

触发：发送帧 1、2 的同一个编码包，在处理帧 1 时让一个回调只失败一次。第一次 HandleBroadcast 正确返回错误；恢复后重传同包，再输入帧 3，两个调用都成功，但模拟漏帧：

| 注入位置 | 实际模拟成功序列 | Assembler Next |
| --- | --- | --- |
| Sink.SubmitInput | [1,3] | 4 |
| Sink.ReportHash | [1,3] | 4 |
| Simulate（在修改模拟状态前拒绝） | [3] | 4 |

`TestReviewBotFailureResume` 三个子例失败，`TestReviewBotHappyPath` 正常同包重传对照通过，总 0.956s。测试允许两种安全行为：恢复帧，或者明确拒绝继续使用已失败实例；当前两者都没有。不是第一次错误被吞掉，而是第一次错误之后成功返回的处理已缺失权威帧。

影响：机器人/客户端若在暂时错误后继续处理消息，模拟状态与权威输入序列不一致，hash/负载测试结果失真。若宿主始终在第一次错误后销毁 Bot，可避开后续跳帧；当前类本身未执行该隔离，也未在上述 API 声明错误后实例不可用。本轮没有验证真实游戏客户端，影响范围明确为这个框架消费者及复用它的接入。

## 根因与修复方向（未实现）

接收游标不能当作应用游标。Assembler 正确地记录“已交给消费者”，但 Bot 未记录“已应用到模拟”。重传无法补救，因为去重边界已经前移。hasher.Fold 还在 Simulate 之前执行，模拟失败时 hash 也已经前移。

可选最小安全方案：对无法恢复的 Simulate 失败进入显式 terminal，之后拒绝处理并要求重建/快照恢复；不得假装能够回滚有副作用的模拟。

若需要恢复：保留未应用的已释放帧，分开处理模拟完成与出站通知。输入发送/hash 上报失败应保留发送任务或明确失败契约，不能丢掉批次尾部，也不能重跑已成功模拟造成重复副作用。复用现有 Assembler 与 Bot 状态，不另造帧协议。

验收应覆盖三个错误点、同批尾帧、重传和新帧、模拟部分副作用、不重复模拟与 hash 连续性。不要只把错误忽略或重置 Assembler 到批次开头。
