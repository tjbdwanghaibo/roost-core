## RR-20260921-03：归还到一半被重新 Claim，claim 没了，实体还在

### 现象

一个空闲租约正在被归还（`handBackIdle`），在它撤离实体的那段时间里同一个玩家登录到本进程。
`Claim` 返回 `mine=true`，`enter_game` 据此继续往下走并把 Player 实体装载进来——而共享表里
这个玩家已经**没有主人**。

探针（`-race`，两种交错各跑到过）：

```text
mine=true err=<nil> admitted=true  redis_owner=0 released=[42]
mine=true err=<nil> admitted=false redis_owner=0 released=[42]
```

`admitted=true` 那一支是更坏的：本进程认为自己拥有 42 并放行写事务，而 Redis 说 42 无主——
另一个进程现在可以合法地 Claim 它并装载**第二份副本**。这正是整个 `playerowner.go` 存在的理由
（文件头："two copies means two version counters over one document"，结局是
`fatal projection version conflict` 加一个死进程）。

### 根因

`demo/internal/service/game/playerowner.go.tmpl`，三行凑成的：

1. **`handBackIdle:491`** 在锁内把 `state.handingBack = true` 并把 playerID 收进 `idle`，
   注释写得很清楚："Marked while the lock that chose it is still held, so no admission can slip
   between the choice and the stop."

2. **`Claim:701`** 不看 `handingBack`。它只把 `Admit` 当作"是否连续持有"的探针：

   ```go
   continuous := owners.Admit(playerID) == nil
   route, err := owners.store.Claim(ctx, playerID)
   ```

   此刻 Redis 里的 claim **还没被释放**（释放在 `:511`，撤离之后），所以 `store.Claim` 返回本进程的
   SID，`mine = true`。随后 `confirmClaim:547` → `confirmLocked:553` 把 **`state.handingBack = false`** 抹掉。

3. **`handBackIdle:506-511`** 拿到 `dropResident` 成功之后，**不再检查任何东西**，直接：

   ```go
   owners.Release(ctx, playerID)
   ```

   `Release:744` 删本地状态 + 删 Redis 的 claim。

于是那个"归还进行中"的标记，被与它竞争的那个操作亲手清掉了，而设置标记的那一方再也没有回头
看过它。`ActiveSessions > 0` 那道检查（`:502`）拦不住：它在撤离**之前**问，而窗口在撤离**期间**。

### 为什么它一定是缺陷

不需要谈概率。`Claim` 的契约是"返回 true 表示本进程拿到了所有权"，`enter_game.go.tmpl:45` 正是
据此决定装载实体的。探针证明在这个交错下 `Claim` 返回 true 而共享表里 owner=0——**返回值是假的**。
这与 RR-20260920-11 是同一族：那一条是"归还把正在跑的步骤脚下抽空"，这一条是"归还把刚建立的
所有权抽空"。上一轮用 `handingBack` 堵住了 `Admit` 这条入口，但 `Claim` 从来不走 `Admit`。

### 影响

P1。两种结局，都由交错决定，都坏：

- `admitted=true`：本进程带着"我拥有"继续写，Redis 无主 → 另一进程可 Claim 并装载第二份 →
  两个版本计数器写同一个文档 → `fatal projection version conflict`，进程死。
- `admitted=false`：玩家登录成功了，但之后每条消息都被 `AdmitMessage` 按名拒绝，本进程又不会
  再续租（本地状态已删），要等 `Lease` 30 秒自然消解。

触发窗口 = 一次 `dropResident` 的时长，上界 `evictBudget` = 5 秒。需要玩家在这 5 秒内连上来。
注意会话是在 **auth 时**就登记到 `playerSessions` 的（`codegen/internal/roost/render_player_tcp.go:691`，
早于 `enter_game`），所以更早连上的连接会被 `:502` 的 `ActiveSessions` 拦掉——真正危险的是
在 `ActiveSessions` 检查**之后**才完成 auth 的那一个。

### 实施方向（是修的那一半的判断，这里只说约束）

设置了标记的一方必须在动手之前再看一眼这个标记还是不是自己设的。`dropResident` 返回之后、
`Release` 之前，在锁内确认 `state.handingBack` 仍为 true；被清掉就说明有人重新取得了这把租约，
放弃这次归还。`CARRYOVER` 的 **A7（在途工作没有计数）** 是同一个洞的另一种解法：如果 `Admit` 有
配对的 `Done`，"归还"就不必用 `lastUsed` 近似，也就不会有这个窗口。本轮把 A7 的证据补齐了。

### 验收覆盖点

- 归还进行中的一次 `Claim`：要么 `Claim` 返回 false（归还赢），要么归还放弃且 Redis claim 保留
  （Claim 赢）。不允许出现 `mine=true` 且 `owner=0`。
- 两种交错都要覆盖（本地确认先行 / 释放先行），探针里两种都自然出现过。
- 归还放弃之后 `handingBack` 必须回到 false，否则这把租约永远不被 `Admit` 放行。

## RR-20260921-04：一次归还批次能把刷新循环占住 40 秒，超过租约本身

### 现象

`handBackIdle` 串行归还至多 `handBackBudget` = 8 个玩家，每个最多等 `evictBudget` = 5 秒。
它跑在 `refreshLoop` 的那条 goroutine 上，`renew` 的末尾。探针（按 100 倍缩放后换算回出厂常量）：

```text
one renew pass took 407.902792ms; per-eviction wait 50ms; observed multiple = 8.2
at the shipped evictBudget=5s that is 41s of refresh loop held, against Lease=30s / RefreshInterval=10s
```

### 根因

`playerowner.go.tmpl:268` 的 `handBackBudget` 注释说明它存在的理由：

> bounds how many players one refresh pass gives back. Each hand-back evicts an entity, which can
> wait on a transaction, and this runs on the loop that also renews everybody else's lease.

作者知道这个风险，并用"个数"给它收界。但代价的单位是**时间**，而 8 × 5s = 40s 已经越过
`Lease` = 30s（`demo/game/playerroute/playerroute.go.tmpl:46`）。循环被占住期间没有任何续租发出，
本进程持有的**其余每一把**租约都会在 Redis 里过期。

这正是 U-0272 / RR-20260920-12 要消灭的那个失败模式——"one busy entity could cost this process the
leases of everybody else"。U-0272 把**单次等待**限住了，但没有人检查这个界在批次上相乘之后还成不成立。

### 为什么它一定是缺陷

算术层面就能判定，不依赖复现：一个声称"保护刷新循环"的界，其最坏取值大于被保护对象的寿命。
探针只是把这句话跑了一遍。

### 影响

P2，但后果重：越过 30 秒之后所有其余租约在 Redis 里消失，下一轮 `renew` 会对每一个走
"lease lost" 分支——能重新 Claim 的重新 Claim（每个再带一次 `dropResident`，进一步拖长），
抢不回的走 `fence`，玩家被批量断线。

**定级 P2 是因为触发条件苛刻**（需要同时有 8 个空闲玩家的撤离各自慢到 5 秒），不是因为后果轻。
空闲的判据是"无连接且 `HandBackIdle`(20s) 无人使用"，而 `Admit` 在准入时就盖了 `lastUsed`——
一个准入后跑了 20 秒以上仍未结束的后台步骤，其玩家正好同时满足"空闲"和"实体锁被占住"。

### 实施方向

界要用时间表示，不是用个数：整个 `handBackIdle` 一次的总预算应当明显小于
`Lease − RefreshInterval`，或者干脆让归还不占刷新循环的 goroutine（撤离本来就已经在
自己的 goroutine 上跑了，等待方才是问题）。与 **A8（`Destroy` 不可取消）** 直接相关：
只要撤离不可取消，任何"等待它"的地方都要自己算清相乘之后的界。

### 验收覆盖点

- 一次 `renew` 的总时长上界，在所有撤离都吃满预算时，仍小于 `Lease − RefreshInterval`。
- 归还被预算截断时，没归还成的那些要保留租约（现行 `cancelHandBack` 已经是对的，别改坏）。
- 断言写成常量之间的关系，不要写死 40 或 30——常量一改这条就该自己重新判定。

## RR-20260921-05：本仓的生成物没有任何 CI 步骤校验（CARRYOVER A12 升级）

### 现象

本仓有 13 处 `//go:generate`（`kit/service/*` 七处、`service/*` 三处、`codegen/internal/roost` 一处等），
产物是**提交进仓库**的 `*_gen.go`。`.github/workflows/` 里唯一的 `generate --check`
（`framework-compat.yml:147`、`demo-publish.yml:55`）跑的都是**生成工程**那棵树，不是本仓。

这不是假设：合仓以来本仓的生成物一直不是规范形态（import 顺序），是 09-21 手动重生成才发现的
（`c74edcd`）。

### 根因

守卫缺失。`ci.yml` 的步骤只有分片测试、Redis 集成、race、`replace` 检查、模块路径、tag 校验——
没有一步跑 `go generate` 再比对工作树。

### 为什么它一定是缺陷

生成器和它的产物都在同一个仓里、同一个 CI 里，两者可以独立漂移而没有任何东西会红。
已经漂移过一次，并且是靠人偶然发现的。

### 影响

P2。产物漂移不会让当前代码跑错（它只是不规范或过期），但"生成器改了、产物没跟上"这类漂移
会在下一次有人重生成时变成一大片无关 diff，把真正的改动淹掉——这也是 U-0270 那一族（清单与
tag 漂移）的同一个教训。

### 实施方向

`ci.yml` 加一步：`go generate ./...` 后 `git diff --exit-code`。**现在加是绿的**——本轮实跑过
`GOWORK=off GOFLAGS=-mod=mod go generate ./kit/... ./service/... ./codegen/...`，工作树无变化。

### 验收覆盖点

- 故意改脏一个 `*_gen.go`，CI 必须红。
- 该步骤不能依赖网络（生成器已在仓内，`go run ./codegen/cmd/servicerpc` 即可）。
