# RR-20261006-05：global `Bind` 结果未知后用同样参数重试，被报成 `ErrConflict "already bound"`

2026-10-06，基线 `8a292a5a`。P3（误报冲突，不写错数据；调用方无法区分“绑的就是自己”和“被别人绑了”）。来源：收尾盘点 A7（A2 驱动契约实施时留作观察的 “global Bind 的误报”，见 DECISIONS-PENDING 第二轮 A2 行）。状态：已复现；已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261006-05.md)。

## 机制

`kit/service/global/service.go` `Bind` 用 `versionstore.Store.Create`（insert-only）写首个绑定。`!created` 时直接返回 `ErrConflict: game %d is already bound`，不看已存的是什么（`Create` 没建成时按契约返回零值，要看必须再 `Get`）。A2 之后 Redis 写命令不经驱动重放，写已落库、回复丢失时调用方拿到结果未知并重试同一个 `Bind`，第二次 `Create` 输给的正是自己第一次的写。

## 触发与差异

`Create` 落库后把回复换成传输错误，再用同样的 `(gameSID, group, globalSID)` 重试：预期返回已存的绑定；实际 `ErrConflict`。

## 复现

`TestBindRetriedAfterUnknownOutcomeReturnsTheSameBinding`（`kit/service/global/bind_retry_promises_test.go`）修前：

```
--- FAIL: TestBindRetriedAfterUnknownOutcomeReturnsTheSameBinding (0.00s)
    bind_retry_promises_test.go:47: retrying the same bind after an unknown outcome: global: conflict: game 7 is already bound, want the stored binding
```

## 修复

[修复记录](../bugfix/RR-20261006-05.md)：`!created` 时读回已存绑定，group 与 globalSID 都一致按幂等成功（计重放），不一致才报冲突。
