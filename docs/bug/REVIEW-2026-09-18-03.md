## RR-20260918-05：邮件账本的去重寿命短于合法信封寿命

**位置**：Codegen `demo/game/rewards/rewards.go.tmpl`、`demo/game/entities/player/bag_component.go.tmpl:111-121`、`demo/game/handler/claim_mail_reward.go.tmpl:26-35`；Kit `service/mail/mail_mod.go:62`。

`ClaimMailReward` 先按领取时刻删除超过 31 天的记录，再插入当前 mail ID。Kit 对 `mail.send_ttl` 只做正数校验，没有 `<=31d` 的跨层不变量。把一个已领取 mail 的账本时刻放到保留期之前、仍让邮件信封可领取，再调用真实生成 handler，结果 `Claimed=true` 且背包数量从 2 增到 3。该触发只需要受支持的配置 `send_ttl > 31d`，不依赖并发。

资产去重身份的寿命必须覆盖权威请求身份的整个可接受期。建议把账本清理改为使用信封 `SentAt/ExpiresAt` 或服务给出的不可再领取水位；Controller 将权威时间锚传给 Nest handler。若选择配置约束，也必须在启动时跨层拒绝 `send_ttl >= claim retention`，但该方案会继续把资产正确性绑定到另一个服务的存储策略。

## RR-20260918-06：连接关闭不驱动在线状态清理

**位置**：Codegen `internal/roost/render_player_tcp.go:348,528,592`；demo `internal/service/game/scene.go.tmpl:420`。

生成的 Runtime 只公开 push 与 `ActiveSessions`。Server 在连接退出时执行 `unregisterSession`，却没有通知消费者。scene 只在新 Join 时扫 `ActiveSessions`，或在向旧成员 push 失败时懒清理。独立运行中先加入一个成员，再令其活动会话数降到 0，并等待两个复制周期；成员数仍是 1。没有新 Join/Push 时状态不会收敛。

建议生成一个异步、多订阅者的会话生命周期源：关闭路径只把 `{PlayerID, SessionID}` 投递到有界队列，单独 worker 调用订阅者；注册返回 unsubscribe，Runtime.Close 负责停机和排空策略。scene、chat presence 订阅同一个源。不要在 socket 清理栈上同步执行任意业务回调。

## RR-20260918-07：syncTopic 的语法歧义被静默接受

**位置**：Codegen `internal/entity/gen.go:225-253`，fixture `internal/entity/testdata/player.go`。

`syncTopicExpr` 只把包含点号的导出标识符认作常量表达式，其余输入全部 quote。独立包内测试得到 `syncTopicExpr("SyncTopicPlayer") == "\"SyncTopicPlayer\""`；生成器自己的 fixture 也锁定了该行为。标记看起来像合法 Go 常量，生成成功却订阅错误 topic，故不能降为文档提示。

建议消除歧义：字面量要求显式引号，合法 Go 表达式按 parser 校验后原样生成；为了兼容也可先拒绝“首字母大写、无引号、无包名”的值，并迁移内置 fixture。必须增加同包常量、限定常量、显式字符串、非法表达式四类生成/编译测试。

## RR-20260918-08：单观察者 AOI block 数无上界

**位置**：Core `spatial/interest.go:37-76,279-302`。

`InterestConfig.validate` 校验半径和 band，BlockIndex 限制整图格数；`resubscribe` 对 LeaveRadius 形成的矩形遍历全部 block。Bounds `10000×10000`、BlockSize `10`、EnterRadius `900`、LeaveRadius `1000` 能成功构造并添加观察者，实际登记 40,401 个 block。每个观察者的内存和移动差分成本因此可由一项合法配置放大到接近整图。

建议在 `InterestConfig` 增加 `MaxObserverBlocks`，构造时用饱和整数计算最坏窗口 block 数并拒绝超限；默认值可与已有 AOI 1024 格经验一致，但应成为明确配置。运行指标同时暴露实际 block 数分布，便于发现接近上限的配置。

## RR-20260918-09：多进程怪物实体 ID 碰撞

**位置**：Codegen `demo/internal/service/game/spawner.go.tmpl:45,54,146`。

每个 spawner 都从常量 `monsterUniqueIDBase` 开始本地自增。独立创建两个 spawner，第一次 mint 均得到 900001。demo 的 Room subject、spatial subject 和 Nest/Entity 寻址都把完整 entity ID 当全局身份；多副本部署时碰撞会让不同实体共用订阅、路由和状态槽。

建议优先复用框架已有的服务实例身份：给运行期 ID 分配明确的 bit/段布局，由稳定、唯一的 sid 派生 shard 前缀，低位使用本地原子序列，并在启动时验证 sid 可编码、序列不会溢出。若现有 entity ID 布局不能安全容纳，应复用现有 Redis 原子发号器按段租赁，而不是每只怪跨网络 INCR。生成 demo 必须增加两个不同 sid 不撞、同 sid 重启不复用仍存活 ID、边界溢出拒绝三类测试。

## RR-20260918-10：顶层 DAO map 的 nested 值所有权没有转移

**位置**：Codegen `internal/dao/template_dao.go:251-269`，golden `internal/dao/testdata/golden/gen_hero_dao.go:398-418`。

`SetEquips(key,new)` 给 new 安装闭包，却没有对同 key 的 old 调 `SetNotify(nil)`。Rollback undo 把 old 放回并调用 `Init()`，但没有解除已丢弃 new 的闭包。4 个真实生成 DAO 场景结果：提交替换后 old 仍产生一笔 commit（应为 0）；new 正常产生一笔；回滚后 old 正常产生一笔；回滚后 new 仍产生一笔（应为 0）。闭包捕获游离值和 key，后续 mutation 可能把旧值写到当前 key，属于持久化数据错误，不只是多余 dirty。

修复应把“值进入/离开容器”和“通知绑定/解绑”作为同一个所有权操作。普通替换先解绑旧值再绑定新值；undo 执行时先解绑当前值，再恢复并绑定旧值。`Del`、raw hydrate、`Init`、同 key 多次替换与 nil 值应复用统一 helper。验收除 4 个所有权场景外，还应解码 CommitRecord 确认游离对象不能生成 stale patch，并覆盖 panic、提交拒绝与多次写回滚。
