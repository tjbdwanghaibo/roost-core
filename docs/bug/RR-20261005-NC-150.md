## 触发与差异

`skill.Parse` 先用 `rejectDuplicateKeysWithLimits` 扫一遍重复键，再用 `decodeStrictSingle` 解码：

- 重复键按**字节**比较（`skill/parse_duplicate.go:80-84`，`seen[key]`），`"id"` 与 `"ID"` 是两个键；
- `decodeStrictSingle`（`skill/parse.go:176-190`）用 `DisallowUnknownFields`，但 `encoding/json` 把对象键与结构体字段按**大小写不敏感**匹配，`"ID"`、`"Cooldown_Ticks"` 都不算未知字段；同一字段出现两次时后者覆盖前者。

文档承诺：`skill/README.md:153`“严格 wire 解析（未知字段、重复键、尾随数据都会被拒绝）”，`skill/README.md:230`“wire 层是封闭的（未知字段即解析错误）”，`docs/skill/skill-testing-guide.md:10`“拒绝重复键、未知字段和尾随数据”。

实际（探针，基线代码）：

```
upperID:   accepted id="skill.planet.other"     // {"id":"skill.planet.fireball","ID":"skill.planet.other",…}
upperOnly: accepted                              // "Cooldown_Ticks": 0 当作 cooldown_ticks
nestedDup: accepted                              // {"flow":"finish","reason":"done","Reason":"other"}
```

三者都能 `Compile` 通过、无诊断。嵌套层同样：所有 wire 结构体都经 `decodeStrictSingle`，各 `decode*` 的 header 预读用的是 `json.Unmarshal`（`wire_flow.go:74` 等），同样大小写不敏感。

## 影响

- 审核 / 生成工具（大小写敏感的 JSON 实现、人工 review）看到的是第一个 `id` / `costs`，Runtime 用的是后一个：例如 `"costs":[…], "Costs":[]` 让审核看到消耗、运行时零消耗。
- 非规范大小写的键被当成合法字段，wire 不再是封闭集合，生成器偏离 schema 时不会在边界失败。
