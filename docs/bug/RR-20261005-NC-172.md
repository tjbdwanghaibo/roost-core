# NC-172：JetStream 同步总线 Stop 不等在途 handler，SyncBusMod 随即释放总线、NatsMod 在 handler 底下关连接

2026-10-05，基线 `origin/main` `25bb0d66`。**P3**。来源：[NC-83 修复记录](../bugfix/RR-20261005-NC-83.md#仓内其他同形停机实现只读核对未修)。状态：已修复（[记录](../bugfix/RR-20261005-NC-172.md)），未发版。

## 触发与差异

`sync/syncbus/driver/jetstream.go:269` `jetStreamSyncBus.Stop` 取走全部订阅后逐个 `sub.Stop()` 就返回；nats.go v1.53.1 `ConsumeContext.Stop` 只关闭 `done`，不等在途 consume 回调（NC-90 已核对同一行为）。总线没有 `StopWithContext`，`kit/syncbus/mod.go:224` `SyncBusMod.StopWithContext` 走 `Stop()` 分支后置 `m.bus = nil`、返回 nil。

App 按依赖逆序：SyncBusMod 返回 nil → NatsMod `StopWithContext` drain 并关闭连接。JetStream 消费订阅已经退订，`Conn.Drain` 不再等它。在途 handler 返回后 ack 在已关闭的连接上失败，消息留在 ack_pending、AckWait 后重投。

## 正式调用方与触发路径

- 正式调用方 App 一次停机即触发（不需要重试）：`syncbus.transport=jetstream`，停机时某个本地订阅者的 handler 正在执行。
- 仓内正式订阅者只有 remoteentity 的两个 replicator（NC-174 另行修复其自身的排空）；`ModSyncBus` 是公开 capability，业务代码可以直接订阅。
- 后果：Stop 报告完成而 handler 仍在运行；它的 ack 必然失败、消息重投（at-least-once 仍成立，但每次停机都会制造一次重投）。

## 复现

- 包内（`sync/syncbus/driver/jetstream_stop_drain_promises_test.go`，修前唯一入口 `Stop()`）：`Stop returned while a handler was still running on the subscription`。
- 真实 nats-server（私有进程，`-tags integration -run TestRealJetStreamSyncBusStopDrainsAnInFlightHandler ./kit/syncbus/`，修前驱动）：

  ```
  budgeted stop with the handler in flight: err=<nil> bus_retained=false nats_closed=true
  retry stop: err=<nil>; consumer ack_pending=1 ack_floor=0 consumers=1
  ```
