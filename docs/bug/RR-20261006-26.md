# RR-20261006-26：nats 排空被硬关后，驱动的 Connected() 约 5s 内仍报 true

2026-10-06，基线 main `37338490`。P4（`Assembly.Close` 已返回终态的 `ErrClosedUndrained`——连接已硬关、不再拥有任何资源——之后 `Assembly.Connected()` / `Client.Connected()` 在最长约 5s 内为 true；之后的调用不受影响，仍返回 `fnats.ErrClosed`）。来源：[真实进程演练](../bugfix/REAL-PROCESS-DRILLS-2026-10-06.md)第 4 项，`kit/nats` `TestRealNatsModUndrainedCloseIsReportedOnce` 在 `-race -count=3` 循环里偶发红（2/150）。状态：已复现；已修复、声明场景验证，未发版。[修复](../bugfix/RR-20261006-26.md)。

## 机制

`Client.DrainWithContext`（`nats/driver/client.go:154-178`）调 `conn.Drain()` 启动 nats.go 的排空协程，ctx 到期时 `conn.Close()` 硬关。nats.go v1.53.1 的 `drainConnection`（`nats.go:6202`）在等订阅数归零的循环里每 10ms 轮询；硬关清空了订阅，它随即跳出循环，**不检查连接已关闭**就 `changeConnStatus(DRAINING_PUBS)`，再 `FlushTimeout(5s)`（连接已关，PONG 不会来），最后再 `Close()` 一次。这段时间 `IsConnected()`（`status == CONNECTED || isDraining()`）为 true，`IsClosed()` 为 false，`ClosedHandler` 也会第二次触发。驱动的 `Connected()`（`:192`）直接返回 `conn.IsConnected()`。

- 预期：Close / 硬关之后 `Connected()` 一直为 false（Assembly 的注释与 NatsMod 的处理都把 `ErrClosedUndrained` 当“连接已关闭”的终态）。
- 实际：硬关后约 10ms 起、最长约 5s 内为 true。之后的调用照常拿到 `ErrConnectionDraining`，驱动映射为 `fnats.ErrClosed`，所以只影响 `Connected()` 的读者（健康检查；NatsMod 在 Stop 后已把 `asm` 置空，健康检查读不到它）。

## 复现

`kit/nats/close_contract_real_promises_test.go` `TestRealNatsModUndrainedCloseIsReportedOnce`（`-tags integration`，真实 NATS），断言由“Stop 返回那一刻 `Connected()` 为 false”改为“之后 300ms 内一直为 false”。修前 `-count=20` 全部红：

```
--- FAIL: TestRealNatsModUndrainedCloseIsReportedOnce (0.21s)
    close_contract_real_promises_test.go:221: first Stop = nats: connection closed before drain finished: context deadline exceeded
    close_contract_real_promises_test.go:229: Assembly.Connected() = true after the undrained close returned (DEBUG status=DRAINING_PUBS closed=false draining=true); the connection was closed hard
```

（`DEBUG` 部分来自查明根因时的临时输出，不在提交的用例里。）首次偶发时的原断言见[摘录](../bugfix/evidence/real-process-drills/2026-10-06/rr26-red.txt)。没有单元级红：nats/driver 的单元用例只有不可达地址，排空走不到这条路径（需要真实服务端上的订阅）。
