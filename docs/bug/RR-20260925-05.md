# RR-20260925-05：Remote 串行投影放大 Nest 请求排队和确认超时

2026-09-25；P1，Remote / DataEngine / Nest 跨模块容量问题。基线为当前工作树；完整源码 hash 和环境随性能产物保存。

## 触发与影响

1000 业务 worker、10000 Entity、每事务 2 Entity × 2 DAO，strict。20 TPS 的 30 分钟记录出现 4 个错误，首错 `nest: sync timeout`；提高到 50 TPS 后稳定放大为大量超时。错误并不是客户端 Sync 的同步超时。业务请求超时后，已进入 WAL 的事务仍可能继续落库，不能直接把超时当成回滚成功。

修前 50 TPS 产物 `artifacts/perf/remote/timeout-baseline-50-20260925/`：60 秒输入 3000 笔，含请求等待 65.008 秒，143 成功、2857 错误、0 丢弃；成功完成 2.200 TPS。首批保存的错误样本请求耗时均约 5000ms，投影积压同步增长。Go 测试和外层脚本均失败，没有全量验证标记。成功完成 TPS 不等同于后台持久化吞吐。

## 根因链路

1. `dataengine/engine/projection_plan.go` 将每个 Remote WAL 记录分成独立段；`projector_replay.go` 对这些段逐笔调用 `MongoStore.Project`。
2. `MongoStore.Project` 完成本笔 Mongo 原子事务，随后等待 `Manager.ApplyRemoteCommits` 的快照发布与发布标记，之后才能投影下一笔。实体彼此独立也共享一条串行服务队列。
3. Nest strict 请求在释放 Entity 锁后仍等待 Remote 确认；确认变慢占用 dispatch worker，使后续请求在 worker 队列积压。
4. `nest/client.go` 的 `waitResult` 使用默认 5 秒总回复等待。队列和确认的总时间超出这个预算时返回 `ErrNestTimeout`。

阶段计量（50 TPS 修前、remote_update）：queue 平均 3587.28ms / 最大 4982.10ms；remote_confirm 平均 1268.71ms / 最大 4975.18ms；durable_commit 平均 14.79ms / 最大 37.45ms；handler 平均不足 0.01ms。不同阶段计数并不完全相同，不能把均值简单相加当作单笔请求时长。原 30 分钟异常时段堆栈还显示投影线程在 Mongo CommitTransaction 网络等待。综合证据支持串行投影 → 确认等待 → worker 排队 → 回复超时，而非业务计算或 Sync 发包阻塞。

历史 30 分钟只存首错且没有每笔阶段信息，因此不能事后指定那四笔各自卡在 Mongo 的哪条命令；本轮保存逐请求错误样本和阶段数据补足可复现链路。

## 可控复现

`TestRemoteProjectionIndependentEntityCompletesWhileFirstBlocked` 控制第一笔 Remote Project 不返回，要求不同实体的第二笔完成。只禁用并行投影路径的构建 overlay 在 5 秒内稳定失败 `timed out waiting for independent entity confirmation before first returns`；启用路径通过。没有通过放宽超时、降低 durability 或丢弃 WAL 规避问题。

## 状态

已定位、修复并验证。五包 race/vet、21/21 故障矩阵通过；30 分钟 60 TPS 实跑 108000 成功、0 错误/丢弃，实际 59.997 TPS，p99=845ms，最终 Mongo/NATS/回滚/outbox 全量校验通过。没有延长默认超时，未部署。完整证据见 [实施报告](../feature/REFACTOR-2026-09-25-remote-throughput.md) 和[修复说明](../bugfix/RR-20260925-05.md)。
