# RR-20260926-69：entitysync forget 先删表后清通知器，同一 state 快速重新登记后失去脏通知器，后续变化不再同步

日期：2026-09-27。基线：本地 main `7706419`（RR-48～63 合并后，未推送）。来源：第二轮修复后独立审计。等级 P3（修前即有窗口；RR-55 的重试专门撞进该窗口）。状态：放大窗口后复现（3000 轮中直接登记 3 次全部丢失），未修复。

`sync/entitysync/manager.go` forget `:523` 删表、`:540` 才对旧 subject 的 state `SetDirtyNotifier(nil)` / `DiscardFrozenSync`；RegisterAfterRetirement `:391`、`:394` 见不在表或 forgotten 即 Register(state) 装上新通知器，随后 forget 把它清掉。后果：`queued=false err=nil`，之后 MarkDirty 不进 pending，观察者收不到后续变化。复现：[REPRO-2026-09-26-06](REPRO-2026-09-26-06.md) §5。

修复约束：通知器清除在删表前或 m.mu 内完成，或“比对后再清”（只清属于被 forget 的 subject 的通知器），或 forget 完成前不走直接 Register；回归用确定性顺序控制（不靠 sleep）。

## 修复（2026-09-27）

已修复，按上方修复约束实现，见[修复记录](../bugfix/RR-20260926-69.md)：`forget(subj)` 先核对表里仍是同一个 subject，在删表之前、同一把 `m.mu` 内清除旧 subject 的脏通知器并丢弃冻结内容，再删表；表里已是同 ID 的新 subject 时不动。回归 `TestRegistrationInTheForgetWindowKeepsItsDirtyNotifier` 用测试缝 `forgetUnlinked` 让 `RegisterAfterRetirement` 确定性落在离表窗口：修前红（`MarkDirty does not schedule it`），修后登记保留通知器、后续变化正常同步；REPRO §5 探针 3000 轮 lost-notifier=0。已本地提交，未推送/发布。
