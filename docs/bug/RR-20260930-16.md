# RR-20260930-16：`add mod` / `add saga` 给 CRLF 的服务配置追加 Mod 段时用 LF，一份文件行尾混用

日期：2026-09-30。基线：main `4784ef82`。来源：[REMAINING-2026-09-28](../review/REMAINING-2026-09-28.md) §3 N23，维护者 2026-09-30 拍板“追加时沿用文件原有行尾”；原始观察在 [RR-20260928-13 修复记录 §未验证 / 风险](../bugfix/RR-20260928-13.md)。
等级 **P4**：生成器对 Windows `core.autocrlf=true` 检出的工程写出行尾混用的文件；YAML 解析不受影响。状态：已修复（本地提交，未推送 / 未发版），见 [修复记录](../bugfix/RR-20260930-16.md)。

LF 工程与空文件两个子用例修前修后都通过（它们守的是不误改）。

## 根因（基线行号）

`codegen/internal/roost/render.go:589` `appendModConfigSections`：对开发配置与生产示例直接 `appendMissingConfigBlocks(string(raw), …)` 后 `writeAtomic(path, []byte(body))`（`:612-618`）。`appendMissingConfigBlocks`（`:641`）追加的是目录里的 LF 文本（`modCatalog[name].Config`），不看文件原有行尾。同一函数下面的 Secret 示例经 `editKubernetesSecretExampleConfig` 已按 `lfText` / `restoreLineEndings` 处理（RR-20260928-13），只剩这两份文件。

调用方：`add.go:78`（`add mod`）、`add.go:241`（`add saga`）。

## 修复约束

1. 追加时沿用文件原有行尾：含 `\r\n` 的文件按 CRLF 追加；LF 文件与空文件保持 LF。
2. 复用 `render_deploy.go` 既有的 `lfText` / `restoreLineEndings`，不另写一套；LF 工程逐字节不变。
3. 回归断言整份文件行尾一致（`bareLineFeed`），并覆盖 LF 与空文件。
