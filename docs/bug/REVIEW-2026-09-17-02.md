## RR-20260917-04：platform 后台订单重试没有可用的候选入口

**P2，Kit，本轮基线未修复。** `service/platform/server_run.go:34` run、`:51` 遍历 retryOrders、`:81` 固定返回 nil；`platform_mod.go:30/46` Mod/NewMod；`platform_rpc_assembly_gen.go:89` Server；`service.go:395` AttemptDelivery。

已验证的支付回调记录订单，第一次发货临时失败；随后渠道不再回调，部署依赖 Server 后台重试。订单有剩余次数，退避已到期，发货服务已恢复。期望有可接入的候选来源，由 owner 循环继续尝试；实际 run 每 30 秒执行，但 retryOrders 固定返回 nil。该私有方法不可从外包覆盖，Server/Mod/Config 没有候选注入入口，“由部署提供订单列表”的注释没有实现。

独立 overlay 使用当前包内存 fixture：首次 callback 模拟一次发货失败，将业务时钟推进一分钟，运行未修改的 Server.run 和真实 30 秒 ticker，32 秒后取消。结果 `grants=0, State=reserved, Attempts=1, NextAttemptAtUnix=1700000005`，业务 Now 已为 1700000060。手动 AttemptDelivery、再次提交同一签名 callback 两个对照均成功发货一次。三场景两过一失败；不是订单尚未到期或发货服务仍失败。

没有外部主动重试的部署中，一次可恢复故障可长期挂起。外部自建重试和渠道重新回调仍能恢复，不声称所有订单都会丢失。未连接支付渠道/真实 Redis，直接测试 owner 循环，未经过 bus/Server.Init。

实施建议：

1. 复用 versionstore 与 activity 的持久 Delivering 索引/退休模式，提供有界、可报错的 PendingOrders 能力，不每 tick 全量扫描 Redis。
2. 若业务提供 pending 索引，提供显式 collaborator，经 Mod 传至 Service；要求重启续接和分页。关闭后台恢复必须显式说明，不能用空回调掩盖缺失。
3. 订单和索引必须有恢复协议；记录订单后尽力加入索引仍有崩溃窗口。参考 activity 的先登记、确认和对账，或一起持久提交。内存 ID 列表不承担恢复保证。
4. Kit 保留 ticker/context/日志及装配；Core 保留 due 判定、次数上限和状态推进。不要为了重试擅自扩大跨进程管理员权限。
5. 验收无渠道回调恢复、重启恢复、索引写失败、分页公平性、终态退休、取消与来源错误。外部发货结果不确定时的幂等另需定义，接通 timer 不等于端到端恰好一次。

## RR-20260917-01 升级限制

沿用原 RR，不重复编号：原报告已要求旧键迁移。U-0221 解决同版本键单射，但“旧共享键下的票本就不属于任何一方”“含冒号的部署之前就是碰撞状态”不能作为放弃迁移的依据。可构造碰撞不等于实际部署了冲突配置；Ticket 仍保存 Queue，单个合法队列也可能使用冒号。

按旧 `%s:%d:%s` 规则预置未改变的 queueState，再用新 Store 读取，五场景四失败一对照通过：

| 历史/新请求 | 结果 |
| --- | --- |
| 历史 Mode=a:b，同队列升级后查询 | 旧 a:b:2: → 新 a%3Ab:2:，旧票不可达 |
| 历史 Mode=a%3Ab，同队列升级后查询 | 新键 a%253Ab:2:，旧票不可达 |
| 历史 Mode=a%3Ab，新请求 Mode=a:b，同主体/请求 ID | 新键命中另一队列旧键，Enqueue 重放 foreign Ticket |
| 同上，Ticket 查询 | 返回 foreign Ticket，未核对 Ticket.Queue |
| 普通 duel 历史键 | 原票可查询，对照通过 |

这是存储升级模拟，未连接真实 Redis；Redis 使用同一 Key/JSON，可推导风险，但非真实迁移演练。Candidates/Commit 的新归属检查不覆盖所有读写入口。

实施前补齐全部含 `%`/`:` 字段的清单、跨代键冲突预检、旧节点停用策略、备份和迁移验证。采用显式版本化存储空间或离线搬迁至隔离目标，避免逐键改名覆盖未搬旧数据。保留票、比赛、幂等账本关系；无法自动分流的状态隔离报告。“清空等待队列”不等于终态与账本迁移完成。
