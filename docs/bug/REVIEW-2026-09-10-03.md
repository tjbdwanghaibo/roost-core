## RR-20260910-03 · P2 · 完成事务的等待者可能因缓存淘汰而崩溃

- 位置：Core `remoteentity/transaction_manager.go:768`；容量淘汰见 650～683，终态通知见 697～726。
- 条件：FlushRemoteTransaction 已取得 tracker.done 并等待；事务完成关闭 done；等待者重新取得 txMu 前，另一事务准入因容量压力淘汰刚完成的记录。
- 期望：已有等待者返回这笔事务的终态；缓存淘汰只影响后续历史查询。
- 实际：唤醒后重新执行 `m.remote.txs[id].status.Clone()`，条目已被删除，发生 nil pointer panic。该行处于 txMu 临界区，后面的 Unlock 没有执行；调用方即使 recover，后续事务跟踪仍可能被这把锁阻塞。
- 验证：TransactionTrackLimit=1，利用 Context.Done 的测试屏障固定“取得 done 后、读取终态前”的调度窗口；通过真实 complete/track 路径触发淘汰，没有直接删除 map。race 模式下 `TestReviewTransactionWaitSurvivesEviction` 失败，输出 `invalid memory address or nil pointer dereference`。这是生命周期竞态，race detector 不一定报告数据竞争。
- 影响：有并发提交及容量/过期清理的等待路径；并非宣称每次提交都会崩溃。TTL 删除存在同类源码窗口，本轮实测的是容量淘汰。
- 建议：让等待者保有可读取终态的 tracker 生命周期，或让淘汰遵守活动等待者引用。仅在唤醒后检查 nil 并返回“未知”，仍会丢掉本应返回的完成结果。

## RR-20260910-05 · P2 · category 引用业务包常量时生成物遗漏 import

- 位置：Codegen `internal/entity/parse.go:370`，尤其 378～381；输出引用见 `internal/entity/gen.go:336`。本次 M-05 新增场景。
- 条件：合法标记 `category=view.EntityCategoryPlayer`，view 仅在 category 表达式使用；EntityKind 与字段不需要该包。源文件已合法导入 view，并用 `var _ = view.EntityCategoryPlayer` 保证源文件自身可编译。
- 期望：生成文件导入 view。Go 的 import 作用域是单个文件，源文件导入不能替代生成文件导入。
- 实际：collectEntityImports 收集 EntityKind、SyncTopic、packer、component、dao，却没有收集 Category。生成成功，消费者 `go test ./...` 失败：`player_gen_wire.go:25:14: undefined: view`。
- 验证：临时模块通过真实 parseDir/generate 产出接线后编译；同一最小实体改用 `entity.EntityCategoryPlayer` 的对照消费者通过。现有 category 测试接受 view 表达式，但生成测试只覆盖 core entity 常量。
- 影响：采用业务分类常量包的项目升级后生成产物不能编译；不是所有 category 标记均失败。
- 建议：把 Category 纳入 import 收集，并覆盖自定义别名和真实消费者编译，不只检查生成文本。

## RR-20260910-06 · P2 · 注册聚合新增 entity 导入与业务包别名冲突

- 位置：Codegen `internal/registry/gen.go:212`；模板固定 core entity 导入见同文件 import 块。本次 M-05 新增场景。
- 条件：某个注册函数来自包路径 `example.com/alias/entity`。importAliases 只预留 registry/sync/fmt/err，将业务包分配为 entity。
- 期望：业务别名避开模板固定导入名。
- 实际：生成物同时导入 core/entity 和 `entity "example.com/alias/entity"`，消费者编译失败：`entity redeclared in this block`、`undefined: entity.RegisterEntity`。
- 验证：使用真实 registry.Generate，输入一个 Registration，业务包只提供无参 RegisterEntity；Generate 成功，真实临时消费者失败。没有替换模板或手写错误产物。
- 影响：业务注册包 basename 为 entity 的合法布局；现有常见 player/component 布局测试不能证明这一边界。
- 建议：所有固定导入与动态别名统一分配/预留，加入 basename 碰撞的消费者编译测试。

## RR-20260910-04 · P3 · Checkpoint 恢复改变完成历史的淘汰顺序

- 位置：Core `skill/runtime_checkpoint.go:557`、`:827`；`runtime_retention.go:30` 起的完成顺序与淘汰逻辑。
- 条件：早创建的慢技能后完成，晚创建的快技能先完成；CompletedCastLimit=2。保存/恢复后再完成第三个技能触发淘汰。
- 期望：恢复前后的同一后续输入保留相同的已完成 Cast 查询记录。
- 实际：运行时按完成顺序追加 completedCastOrder；Checkpoint 按 ID 排序序列化 Casts，Restore 又按这个顺序重建 completedCastOrder。恢复丢失完成先后关系。
- 验证：两个独立 MemoryHost 执行相同前史，其中一个 checkpoint/restore；后续均运行同一快技能。race 测试失败：原运行时 `slow=true fast=false`，恢复后 `slow=false fast=true`（InspectCast 是否存在）。不存在两个继续运行的 Runtime 共享同一个 Host 的干扰。
- 影响限于本轮证明的历史保留/诊断查询差异；未证明伤害、奖励或随机结果不同，不升级为战斗确定性故障。
- 建议：快照显式保存并校验完成历史顺序，或定义恢复一致的淘汰策略；测试应让创建顺序与完成顺序交错。
