# RR-20260926-16：async 持久级别下 checkpoint 可先于 WAL 段 fsync 落盘，断电后 WAL 以 “acknowledgement is beyond recovered WAL end” 拒绝打开

日期：2026-09-26。基线：main `aaada47`。等级 P2（节点断电 / 内核崩溃后无法启动，需人工处理；数据本身不丢）。
状态：已复现（探针 + 模拟断电，已删除），源码已核对，未修复。来源：上线前复审（DataEngine 持久化）。

## 触发条件

handler 使用 `DurabilityAsync`，随后发生断电或内核崩溃（进程崩溃不触发：页缓存仍在）。持续 async 负载下任意时刻基本都有一个“超前”的 checkpoint。
strict / pipelined 不受影响（fsync 前记录一直 held）。

## 预期 vs 实际

预期：checkpoint 只覆盖已 fsync 的 WAL 位置；断电后恢复到最后一个 fsync 点并继续。

实际：
- async Append 只等写入、不等 fsync（`nestwal/wal.go:321`，`requireSync` 仅 strict），释放后投影循环立即被唤醒。
- `Replay` 读到的上限是已写入的 `w.offset`，不是已 fsync 的位置（`wal.go:510-543`）；`Ack` 越界检查同样用 `w.offset`（`wal.go:481-486`）。
- `storeCheckpoint` 对 checkpoint 文件与目录 fsync（`nestwal/checkpoint.go:73-99`），而段文件要等 10ms group commit 才刷盘。
- 断电后段尾丢失、启动时被截断，已落盘的 checkpoint 位于恢复出的 WAL 末尾之后：`openActive` 返回 `ErrCorrupt "acknowledgement is beyond recovered WAL end"`（`wal.go:1046-1050`），
  Assembly.Start 失败。丢掉的 WAL 尾部已投影进 Mongo，数据不丢，但节点起不来。

## 复现

审查 agent 探针 `TestZZProbeAsyncCheckpointBeforeSegmentFsync`（已删除，源码未保留）：`GroupCommitInterval=1h`，提交一条 async 记录并释放、等 ack；
按“fsync 过的文件保留、未 fsync 的段回到长度 0”复制目录再 Open：

```text
wal stats after ack: syncs=0 acknowledged=1 segment=1 offset=176 projected=1
reopen after simulated power loss: err=nestwal: corrupt log
    acknowledgement is beyond recovered WAL end
```

断电为模拟；“checkpoint 先于段 fsync”是实测（`syncs=0` 时 `acknowledged=1`）。复审方已按源码核对 `wal.go:321,481-486,1046-1050`。

## 实施方向（约束）

- checkpoint / ack 不能越过已 fsync 的位置（或写 checkpoint 前先确保覆盖范围已 fsync）；不降低 strict/pipelined 语义。
- 恢复时不能自动删除或跳过记录来“修复”；如需容忍超前 checkpoint，必须能证明对应记录已投影（持久身份）。

## 验收覆盖点

- 上述模拟断电：重开成功，未投影记录不丢，已投影记录幂等。
- async 吞吐同口径对照（性能纪律），strict/pipelined 行为不变。
