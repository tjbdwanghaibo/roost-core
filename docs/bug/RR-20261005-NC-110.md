# NC-110：启动失败的 cast 被删除并复用 ID，却留下已排程的任务——下一个 cast 执行旧任务，checkpoint 无法恢复

2026-10-05，基线 `be7bcc1853020d9f744360d78831abd0ddf990a3`。P2（被拒绝的施法在之后落地伤害、另一 cast 的流程被打乱、checkpoint 恢复判为 corrupt；需要 charge 模式且 enter 流程在排程等待之后失败，仓内没有正式 Runtime 调用方，定级不是因为后果轻）。状态：已复现，未修复。[本轮](../review/REVIEW-2026-10-05-n09-batch1.md)。

## 触发与差异

`skill/runtime.go:433-443`：`prepareCast` 失败且 cast 未提交时，`startLocked` 标 failed、`stopProcesses`、`markAbilityCastFinished`，然后 `delete(runtime.casts, cast.id)` 并 `runtime.nextCastID--`——这个 ID 会分给下一个 cast。它没有撤销这个 cast 已经排程的任务和帧。

charge 模式在提交之前就执行 enter 流程（`runtime_cast_window.go:33-37`，`prepareCast` 直接 `executeCast`）。enter 里 `parallel` 的一支是 `wait`（`executor.go:113-124` 先排程该分支），另一支失败（例如 `resource spend` 余额不足，`executeResource` 直接返回错误），`Start` 返回 `(0, ErrInsufficientResource)`，调用方得到“施法没有发生”。但 `flowContinuationTask{CastID: 1, PhaseToken: 1}` 还在调度器里。

下一次 `Start` 拿到同一个 ID 1，新 cast 的 `phaseToken` 也从 1 开始；`executeScheduledTask`（`scheduler.go:416-431`）只按 (CastID, PhaseToken) 和帧是否存在判断，于是旧程序的操作索引在新 cast 上执行。

预期：失败启动不留下任何排程工作；ID 复用只在没有残留时安全。

## 复现

`skill/runtime_cast_terminal_promises_test.go`（基线代码上）：

```
--- FAIL: TestFailedStartLeavesNoScheduledWorkForTheReusedCastID
    runtime_cast_terminal_promises_test.go:46: failed start left 1 scheduled tasks and 1 frames for cast 1
    runtime_cast_terminal_promises_test.go:60: health at tick 3 = 60: the rejected cast's wait landed on the reused id (second cast is due at tick 4)
--- FAIL: TestCheckpointAfterFailedStartRestores
    runtime_cast_terminal_promises_test.go:84: restore after a failed start: skill: runtime checkpoint is corrupt
```

探针继续推进到 tick 4 时 `Advance` 返回 `skill: immutable program invariant failed`（新 cast 的流程已被旧任务改乱）。

## 影响

被拒绝的施法照样造成伤害；同一 Runtime 上的其他施法者的 cast 被打乱并让 `Advance` 出错；失败启动之后的任何 checkpoint 都恢复不了（重启恢复链断）。MemoryHost 与任何 Host 都受影响，与 Nest 无关。

## 本轮没做

没有穷举所有“提交前执行并可能失败”的路径（owned 进程 / spawn 在 charge enter 中失败后的宿主侧残留未验证）。
