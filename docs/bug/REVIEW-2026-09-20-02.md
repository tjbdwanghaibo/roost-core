## RR-20260920-06：被拒绝的 subscribe 永不重试（→ 订阅者永久看不到那个 subject）

### 先排除一个候选

W-2026-09-20-02 给了两个候选根因，其中"LOD profile 把这组字段筛掉了"**不成立**。
生成工程的 `game/entities/player/sync_packer.go` 两个方法都**忽略 profile**：

```go
func (packer playerSyncPacker) PackSubjectSnapshot(entity.SyncProfile) (…) { return packer.pack(dataengine.AllFields) }
func (packer playerSyncPacker) PackSubjectDelta(_ entity.SyncProfile, mask uint64) (…) { return packer.pack(mask) }
```

profile 不参与取字段，band 再低也不会少发字段。这条候选到此为止。

### 真正的缺陷

链路是：`InterestSystem.apply` 产出订阅变更 → `Scene.applyChanges` 调 `room.Subscribe` →
`SubscriptionCoordinator.Subscribe` 捕获快照并可能**拒绝**。

`roost-core/entitysync/subscription.go:224-237` 明确会拒绝：快照的 `CommitLSN` 还没durable 时返回
`ErrDurabilityDeferred`（RR-20260915-03 的耐久闸）。`room.Subscribe` 还会因
`ErrRoomSubjectRetiring`、`ErrRoomSubscriberLimit`、`ErrRoomSubjectLimit` 或下游传输错误而失败。

生成工程 `internal/service/game/scene.go:336-338` 对这些失败只记一条 `slog.Warn` 就丢弃，注释写着
"the pair stays claimed in the interest system, so the next tick that touches it tries again"。
**这句话是假的。** `game/scene/runtime/interest.go:252-258`：

```go
if !hold.subscribed {
    hold.subscribed = true     // 在调用 room 之前就乐观置位
    …
    return change{Subscribe: true}, true
}
return s.rebandLocked(key, hold)
```

而 `rebandLocked`（:262-269）在 `band == hold.band` 时返回 `false`——**不产生任何变更**。
于是：pair 已被标成 subscribed，房间那边其实没有订阅，重发只会在 band 变化时发生；
两个站着不动、同在 band 0 的玩家永远不会 reband。**这个订阅者从此永久收不到那个 subject。**

### 影响

- 与负载相关：耐久闸的拒绝随 WAL 落盘延迟出现，房间的 subject/subscriber 上限随在场人数出现——
  两者都在人多时才发生，这解释了"4 个、8 个机器人不复现，16 个每轮复现"。
- 永久：没有任何重试路径，40 秒后仍然缺失（Wanted 里已实测）。
- 静默：客户端看到的是"某个 subject 的状态停在某一刻"，服务端只有一条 Warn。

Wanted 观察到的具体形态（自己的 subject 收到了更新却始终不带位置那一组字段）与这条**一致但未完全证明**：
要把"哪一次 subscribe 被拒"和"缺哪一组字段"对上，需要一次带 pair 级日志的复现，本轮没有做。
登记这条的依据是上面那段代码本身：**承诺重试而实际不会重试**，这与症状是否完全对应无关。

### 实施方向

1. `hold.subscribed` 必须表示"房间确认过"，不是"我们发过"。让 `applyChanges` 把结果回写给兴趣系统
   （成功才置位），或者让兴趣系统保留"待确认"态。
2. 失败要有重试路径，并且**与 band 变化解耦**：一个待确认的 pair 应该在下一个 tick 被重新发出。
3. 区分可重试与终局：`ErrDurabilityDeferred`、传输背压是可重试的；`ErrRoomSubjectLimit` 说明容量不足，
   应该有指标和告警，而不是每 tick 重试一次。
4. 顺手把那句不成立的注释改掉——它现在是误导。

验收至少覆盖：subscribe 第一次被拒后下一 tick 会重试；重试成功后该订阅者收到**全量**快照（而不是只收后续 delta）；
band 不变也能重试；容量类拒绝不进入无限重试；以及 16 个观察者同场景时没有 pair 停在"已标记未订阅"。

## RR-20260920-07：`SmallSafeMap` 的 BSON 自定义编码从未生效

`roost-core/safemap/small.go:121-133` 实现的是

```go
func (m *SmallSafeMap[K, V]) MarshalBSONValue() (bson.Type, []byte, error)
func (m *SmallSafeMap[K, V]) UnmarshalBSONValue(t bson.Type, data []byte) error
```

而驱动（`go.mongodb.org/mongo-driver/v2@v2.6.0`）的接口是

```go
type ValueMarshaler interface { MarshalBSONValue() (typ byte, data []byte, err error) }
type ValueUnmarshaler interface { UnmarshalBSONValue(typ byte, data []byte) error }
```

`bson.Type` 是 `type Type byte`——**定义类型，不是别名**，所以签名不匹配、接口未被实现、方法被静默忽略。
类型退回默认结构体编码器，而它的字段（`mu`、`entries`）都是未导出的，结果是**空文档**。

独立复现（REPRO §2）稳定得到 `bson.D{}` 与一次丢光内容的往返。

**影响**：目前是潜伏的——codegen 的 DAO 生成器把每一个 map 字段都生成成 `*fmap.SmallSafeMap`
（`internal/dao/gen.go:356`），但生成的 DAO 自己拼 patch、走 `daoMapDocs` 转换，不把整个 map 交给 bson。
只要有人把它直接放进一个要写 Mongo 的结构体或快照载荷，内容就会静默变成 `{}`。定级 P2 是因为当前无触发路径，
而不是因为后果轻。

**实施方向**：改成驱动的签名，并加 `var _ bson.ValueMarshaler = (*SmallSafeMap[string, int64])(nil)`
与对应的 Unmarshaler 断言，让这类错误在编译期红。全仓扫描确认同类实现只有这一处
（`entity.RemoteChecksum` 已是正确签名）。验收覆盖：空 map、非空 map、往返相等、以及类型断言存在。

## RR-20260920-08：`OpTimeout` 不约束每实体写闸的排队

`roost-core/remoteentity/batch.go:103-124`：

```go
func (w *remoteEntityWrapper) beginWrite(parent context.Context) (*remoteWriteEntry, error) {
	select {
	case w.writeGate <- struct{}{}:      // 每实体一格的写闸
	case <-parent.Done():                // 只受调用方 ctx 约束
		return nil, parent.Err()
	}
	…
	ctx := parent
	if _, ok := ctx.Deadline(); !ok {
		ctx, cancel = context.WithTimeout(ctx, w.mgr.cfg.OpTimeout)   // 排队之后才加
	}
```

`OpTimeout` 是在**拿到闸之后**才套上去的，所以它约束的是"拿到闸以后那一段"，不是一次远端写的整体。
同一个实体上排队的 N 个写者，最后一个要等前面 N-1 个各自跑完；配置成 3 秒的 `op_timeout` 与一次
79 秒的 dispatch 因此可以同时为真（Wanted 的实测）。

**影响**：可用性与延迟，没有数据损坏。但它把一个可配置的上界变成了没有上界——在"同一个实体被并发写"
这种远端托管实体最典型的场景下，压力越大越糟。定级 P2；若某个部署把远端实体放在玩家高频路径上，
它的表现会接近 P1。

**实施方向**：先定契约——**`OpTimeout` 是一次远端操作的总预算，包含本地排队**。然后把 deadline 移到
`beginWrite` 的最前面（进 select 之前），让排队和后续操作共用同一个 deadline；排队超时要返回一个
**可重试**的错误（调用方能据此退避），而不是和"提交失败"同一个形状。

验收覆盖：单个写者的正常路径不变；N 个并发写者时每一个都在 `OpTimeout` 内返回（成功或可重试拒绝）；
总耗时不随 N 线性增长；调用方自带更短 deadline 时以更短的为准。
