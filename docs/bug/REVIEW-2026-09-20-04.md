## RR-20260920-11：重新取得的租约会在下一轮被当成空闲还掉

### 现象

一个给离线玩家的后台步骤被 `Owns` 放行、开始执行；同一秒之后的刷新轮把这个玩家的实体卸载、
租约归还。另一个进程于是可以立刻认领并加载同一个玩家——两份副本、两个版本计数器，
正是这张表存在的理由本身。

### 根因

`playerowner.go` 的 `confirm`（生成工程 `:442-458`）：

```go
state.validUntil = owners.now().Add(playerroute.Lease)
state.lost = false
state.interrupted = false
if state.lastUsed.IsZero() {        // ← 只在第一次盖章
    state.lastUsed = owners.now()
}
```

`confirm` 服务于两个完全不同的事件：**续租确认**（不能算使用，否则永远没有空闲租约）
与**一次新的认领**（必须算使用，工作正要开始）。U-0269 把两者混成一个函数，用 `IsZero` 当补丁，
于是第二种事件不盖章。

只有在 `Admit` **拒绝**的那条路上才会暴露：`Owns` 先问 `Admitted`，通过就顺手盖章（`Admit` 里
"Admitting is using" 那一行），所以窗口内的一切都正常；而窗口过期后的 `Owns` 走
`store.Owner` → `Claim` → `confirm`，`lastUsed` 停在上一次工作的时刻。紧接着
`handBackIdle` 用 `now - lastUsed >= HandBackIdle` 判空闲，条件成立。

### 影响

范围恰好是 U-0269 想服务的那类玩家：**离线、由后台工作驱动**（赠礼、邮件、已付款发货）。
这类玩家没有会话，所以 `ActiveSessions` 为 0 的那一半条件天然成立。
后果比原来的 RR-20260920-10 更重：不是拿不到所有权，而是**在自己正在写的时候把所有权让出去**。

### 实施方向

把两个事件分开。最小改法是让"新的认领"显式盖一次章（`Claim` 成功后 `markUsed`），
`confirm` 只管租约期限与两个标志位；或者给 `confirm` 一个参数说明它是哪一种事件。
无论哪种，判据要能回答"这把租约上一次**被使用**是什么时候"，而续租不是使用。

另外值得一并定清楚：归还是一次**自愿**释放，它现在不等在途工作，只用 `lastUsed` 的空闲期做代理。
`Admit` 有 `AdmissionGuard` 这条"已经放行的工作必须能做完"的保证，归还路径没有对应物。
即使 `lastUsed` 修对了，"刚放行 19 秒的工作 + 一次归还"仍然缺一个屏障。

验收至少覆盖：窗口过期后的 `Owns` 重新取得 → 下一轮不得归还；连续两次刷新都空闲 → 应当归还；
在线玩家永不归还；以及归还与刚放行的事务之间的竞争。

## RR-20260920-12：撤离的预算不覆盖它要等的那件事

### 根因

`dropResident` 给 `EvictPlayer` 套了 `context.WithTimeout(ctx, evictBudget)`，注释也写着
"一次撤离最多 5 秒"。但 `EntityManager.Destroy`（`roost-core/entity/entity_manager.go:189-207`）
只在**入口**看一次 `ctx.Err()`，随后 `mu.Lock()` 等实体锁——那把锁不接受 ctx：

```go
if err := ctx.Err(); err != nil { return err }
if !e.Touch() { return ErrEntityRemoved }
mu := e.GetMutex()
mu.Lock()          // ← 没有 deadline，等到事务结束为止
```

这与今天上午修掉的 RR-20260920-08 是同一个形状（`OpTimeout` 在拿到写闸之后才生效），
只是这次出现在 demo 侧，并且是本人当天引入的。

### 影响

`Claim` 路径是同步的，而 `renew` 会调它。于是一个事务很长的实体可以把**整个刷新轮**钉住，
它后面所有玩家的续租都在排队；`Lease=30s`、`RefreshInterval=10s`，阻塞超过 20 秒就开始有别的玩家
的租约真的失效——一个忙实体换来一片失主。登录路径（`EnterGame` → `Claim` → 撤离）同样会被钉住，
但那只影响这一个玩家。

### 实施方向

三条路，选哪条要先定"撤离失败"的语义：

1. 让撤离可取消——需要 core 的 `Destroy` 支持带 ctx 的等待（改动最大，收益最通用）;
2. 把 `Claim` 路径的撤离也挪出刷新循环（异步 + 不确认），代价是"认领成功但尚未安全"的中间态要有人表达;
3. 先用一次非阻塞尝试（实体锁可得才撤离，否则判失败重试），把等待彻底移出这条路径。

无论哪条，`evictBudget` 这个名字与注释现在是**不成立的承诺**，要跟着结论一起改。

验收至少覆盖：实体上有长事务时的 `Claim` 耗时上界；同一轮里其他玩家的续租不被推迟；
以及撤离失败时租约状态仍然是 fail-closed 的。

## 其他审查结论

- **U-0267（兴趣系统重试队列）本轮复审通过**。重试队列的上界仍落在写入口；
  新增的 `playerEvictor` 会对每一次跨间断的认领调用 `Scene.Leave`，包括每一次普通登录——
  `Leave` 首行按 `members` 判在场并直接返回，不产生虚假 unsubscribe，也不会给重试队列留下条目。
- **U-0268 的主路径通过**：`interrupted` 标志让"Redis 说过不是你的"成为权威判据，
  `Claim` 跨间断先扔副本再 confirm，扔不掉不接管。本轮两条问题都出在它旁边的两处细节
  （`lastUsed` 的盖章时机、撤离的等待预算），不动摇这条不变量。
- `fence` 为每个失主玩家起一个 goroutine 做撤离，数量上界是本进程的玩家数。本轮判为可接受，
  不登记；但如果将来撤离改成可取消，这里应当一并改成有界的工作池。
