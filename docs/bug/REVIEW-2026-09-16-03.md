# 09-16 第三轮：真实 JetStream 的本地订阅扇出

用户声明没有修复，本轮跳过所有旧 RR 的修复核验。Core `21e0a6c02468123635c67b61581b6847e765733c`，只记录问题，不修改生产实现。独立 NATS server v2.11.9、Windows 回环网络、单节点文件存储，35 个新增场景中 32 通过、3 失败，三个失败归为同一个新问题。

## RR-20260916-03 — P2：同一总线的同 topic 订阅竞争同一消费者，广播变为分摊

状态：新发现，未修复。Verify 图谱定位 + 当前源码 + 真实 broker 复现。

位置：`room/jetstream_syncbus.go:147–193,247–255`，`nats/driver/jetstream.go:62–82`。业务影响链路：`syncstream/publisher.go:248–294,297–351`。

触发：同一 JetStreamSyncBus 实例对同一 topic 注册两个本地 handler。Stream、Prefix 和 LocalSid 全部相同，无需跨租户、改配置、断网或并发 Stop。两个 Subscribe 均成功。

期望：注册到同一主题的本地消费者分别得到消息；普通 NATS 适配使用普通 Subscribe，具有这一行为。实际：每次 Subscribe 都以相同 topic/SID 生成同一个持久消费者名，再独立调用 Consume。真实服务端把消息分摊到两个 Consume 实例，适配层没有本地 handler 列表进行广播。

### 可重复证据

| 场景 | 期望 | 实际 |
| --- | --- | --- |
| 同一 JetStream bus 两个 handler，发布 12 条不同 ID 的消息 | 两边各 12 条 | 两边各 6 条，失败 |
| 普通 NATS bus 同样注册两个 handler | 两边各 12 条 | 通过 |
| 两个 JetStream bus 使用不同 SID | 各自 12 条 | 通过，持久消费者身份不同 |
| 两个 syncstream.Subscribe，共用 JetStream bus，identity 分片 | 两边各重组出一个 Packet | 51 个分片发布确认成功，两边均 0 个 Packet，失败 |
| 同上，gzip 分片 | 两边各一个 Packet | 18 个分片发布确认成功，两边均 0 个 Packet，失败 |

分片断言前轮询真实 ConsumerInfo，确认 NumPending=0、NumAckPending=0 且 Delivered.Consumer 不少于已发布分片数。不是只等待固定时间推测未收到。两个本地 reassembler 各持有不同部分；包装 handler 返回 nil 后分片被 ACK，未完整组装也不会自行补齐。分配比例不是协议保证，6/6 是本次实际输出。

影响：切换 NATS → JetStream 后，本地多个同主题同步器漏更新；分片流甚至可能所有订阅者都无法重组。使用 SubscribeForObserver 在本地为同一 topic 注册多个 observer 过滤器时，还存在消息被错误的过滤器消费并 ACK 的风险；这一 observer 组合是源码推断，本轮未另写专项。不能由 broker 接受/ACK 数正常推导业务应用成功。

这与上轮 RR-20260916-02 不同：上轮是不同 Prefix 的配置身份冲突；本问题在同一个 bus、相同完整 subject 内即可触发。仅把 Prefix 加入 durable 散列不能修复本地广播缺失。旧问题本轮未复核。

### 建议实施方向

优先复用现有 IJetStream、订阅对象及同步原语，在 JetStreamSyncBus 内按 topic 维护一个底层订阅和本地 handler 注册表：第一位订阅者创建消费者，后续订阅者只注册本地 handler；单个 unsubscribe 只移除自身，最后一位离开才停底层订阅。保留现有稳定消费者身份和重启游标。

回调调用前在锁内复制 handler 列表，锁外逐个调用，避免慢 handler 阻塞注册/取消。每个 handler 的消息所有权、panic 隔离、取消交错和错误记录必须有明确契约，避免一个 handler 阻断其余处理。初始化失败与并发第一次订阅也要由同一注册状态管理，不要重复创建底层 Consume。

若业务实际需要队列分工，应提供显式队列语义，不能让相同 ISubscriber 调用随 transport 悄悄改变含义。给每次 Subscribe 随机生成 durable 名虽然能避免竞争，但会产生消费者积累、历史重放与游标迁移问题，不建议作为直接修复。

验收至少覆盖：同主题两 handler 都收到、取消其中一个后另一个继续、最后一个取消释放底层资源、失败创建后重试、并发注册、各 handler 数据隔离、identity/gzip 分片均可重组。完整独立代码见 [复现文档](REPRO-2026-09-16-03.md)。

## 契约观察，不另立 bug

真实 broker 进程重启后，活跃消费者和离线 durable 恢复场景都再次收到一条旧消息，随后收到新消息。测试初稿错误地要求恢复后第一条必为新消息，已改为容忍重复并验证继续前进；这是至少一次交付边界，未记为框架缺陷。

成功发布后人为丢弃返回确认，再由 BufferedPublisher 重试，真实接收端收到两次同一业务 Packet。Publisher 每次发布生成新的 delivery ID，因此不能将 broker 的 ID 去重当作业务幂等。本轮注入发生在真实确认之后，未模拟 TCP 半开或精确丢 ACK。

Apply 返回错误时，SyncBus 按既有契约记录并返回 nil；在 400ms 观察窗口内没有再次调用。结合包装源码，不能依赖底层 NAK 自动重试这个业务错误；该窗口本身不证明永久不会重复交付。已关闭 NATS Client 的 Drain 返回 connection closed 也仅记录 API 行为，不列缺陷。
