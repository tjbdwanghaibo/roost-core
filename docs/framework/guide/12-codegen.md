# 12 代码生成与工程（说明）

> 配套实现文档：[impl/12-codegen.md](../impl/12-codegen.md)（文件地图、主流程与状态机、不变量与守卫测试、review 检查点、源码疑点）。
> 源码基准：tag `v1.23.0`（`28912cd6`），文中 `path:line` 都按这个 tag。生成代码的行号是**生成器模板源码**的行号（例如 `codegen/internal/roost/render.go` 里 Go 字符串的行号），不是生成出来的文件的行号。
> 本篇按维护者要求不派子 agent，全部结论按 tag 源码直接读取；部分行为用 `-skip-deps` 生成的探针工程（`project new` 与 `-template game-demo` 各一次）核对过，文中注明“实测”。

## 速览

- **这一块是什么**：`roost` 命令行（`codegen/cmd/roost`）加十几个生成器，把一份清单 `roost.yaml` 和源码里的 `//roost:` 标记变成一个可编译、可部署的游戏服工程；再加上两套模板（`-template game` / `game-demo`）、机器人压测框架 `robot/`、以及仓库自己的发布与验收脚本、根包门禁。
- **最重要的保证**：`project new / sync / upgrade / deps` 与 `generate` 都在工程旁边的**暂存树**里完成全部工作，最后一次性提交；中途失败、被 Ctrl-C 或检测到并发修改，工程目录保持原样（只有已经开始的提交会做完）。生成器只改写带 `Code generated by roost-codegen` 头的文件或明确归 codegen 所有的部署目录，业务文件只创建一次、之后不碰。
- **最容易踩的坑**：① 标记的**键名拼错**在 `//roost:nest`、`//roost:dao`、`//roost:redisdao`、`//roost:rpc`、`//roost:attribute` 上会被静默忽略并回落到缺省值（例如 `durabilty=strict` 得到 async），只有 `//roost:entity`、`//roost:mirror`、`//roost:web`、`//roost:register` 拒绝未知键（§7.2 G1，本次核对实测）。② `roost.yaml` 的 `versions.codegen` 写成 `v1.15.x` 会让生成的 Makefile 里每个 `$(ROOST)` 目标都失败，写成 `v1.16`～`v1.22` 会用旧生成器处理新工程（§7.2 G2，实测）。③ `.github/`、`deploy/dev|shell|docker|k8s/` 下的文件归 codegen 所有，手改会被下一次 `sync` 覆盖；要改部署形状，改生成器或改 `roost.yaml`。④ 工程放在某个 git 仓库的子目录里时，`roost generate --changed` 什么生成器都不跑（只跑 registry），并报告成功（§7.2 G3）。

## 1. 定位与边界

**负责**

- 把 `roost.yaml`（工程清单）渲染成工程骨架：`main.go`、`internal/bootstrap/generated.go`、每个服务的配置、Makefile、GitHub Actions、shell / systemd / Docker / Kubernetes 部署物、本地开发编排、面向新人的文档。
- 把源码标记（`//roost:entity`、`//roost:dao`、`//roost:nest`、`//roost:rpc`……）变成生成代码，并把全部静态注册汇总成一个 `registry.RegisterAll()`。
- 业务脚手架（`roost add …`）：创建一次、之后归业务的文件，以及需要同时改清单的操作（加服务、加 Mod、加接入层、加 saga、加 rpc）。
- 工程体检（`project doctor` / `next`）、ID 分配（`id next/check`）、配置快速检查（`config check`）、框架升级与导入改写（`project upgrade [--consolidate]`、`project deps`）。
- 两个模板：`game`（业务服 + 9 个托管框架服务）与 `game-demo`（在 `game` 上加一条完整可运行的业务链路）。
- 机器人 / 压测框架 `robot/`，以及仓库的发布、验收脚本与根包门禁。

**不负责**

- 生成代码在运行期的语义（Nest 事务、DAO 持久化、Sync、Saga……）：那是各自分区的内容，本篇只说“生成了什么、从哪里生成”。
- 业务数据配置的规则与热更（07）；`StarterYAML` 的配置段内容（来自 kit 各 Mod 自己的声明，07）。
- 生成工程的运维（指标、告警、admin，11）。
- **类型检查**：生成器做语法级 AST 解析，不加载类型信息（`codegen/README.md` “语法级 AST 解析，不做类型检查”）；类型错误由生成之后的 `go build` / `go vet` 报出。

→ [实现文档](../impl/12-codegen.md)对应：§1 包与文件地图。

## 2. 核心概念与术语

| 术语 | 含义 | 定义位置 |
| --- | --- | --- |

| 业务所有（application-owned） | 只在不存在时创建一次的文件：`go.mod`、`main.go`、`internal/service/<svc>/service.go`、配置 YAML、`collaborators.go`、`auth.go`、`.gitignore`、`README.md`、`configs/schema/doc.go`…… | `render.go:28`～`:211` 里 `owned=false` 的项 |
| 生成产物 | 生成器写出的文件，靠文件内容里的 `Code generated` 字样（或 `configs/data/*.json`、`docs/generated/`、protocol 产物）识别；`generate --check` 只比较这些 | `codegen/internal/roost/generate.go:555`、`:566` |
| 暂存树 | 工程旁边的 `.roost-sync-*` / `.roost-generate-*` / `.roost-deps-*` / `.roost-project-*` 目录：先把工程复制进去，在里面渲染、生成、`go mod tidy`，再把变化提交回工程 | `project.go:203`、`generate.go:233`、`dependencies.go:41`、`project.go:104` |
| 标记（marker） | 源码注释 `//roost:<kind> key=value …`。旧前缀 `//cube:` 本版仍接受，`generate` 每次运行列出仍用旧前缀的文件 | `codegen/internal/marker/marker.go:18`、`generate.go:417` |

| 运行期守卫 | `codegen/scripts/*-runtime.sh`：把生成器的 golden / 脚手架输出编译进**已发布的最低 core**真跑一遍，弥补生成器单测只比文本 | `codegen/scripts/core-pin.sh:1`、`.github/workflows/ci.yml:72`～`:81` |

## 3. 设计原因

| 决定 | 原因 | 出处 |
| --- | --- | --- |
| 一切写操作走暂存树 + 一次提交 | 生成器本是一次性命令，直接在工程里跑，失败到一半会留下一半新一半旧的生成物；并发编辑（IDE、另一个 roost）会被覆盖。暂存树里跑完、核对“业务输入没被别人改过”、再按文件做乐观并发检查提交，失败按逆序回滚 | `project.go:190`～`:274`、`generate.go:210`～`:297`；RR-20260930-CG-14 |
| 信号由 `Main` 统一接管（维护者决定 B6） | 早先在 `go` 子进程那一层捕获并重新抛出信号，进程死在调用栈中间，暂存树残留、`go.mod` 不回滚（RR-20261004-12/13、RR-20261005-NC-70）。现在第一次信号只取消 ctx，命令走普通错误路径回滚、删暂存树，然后进程按原信号退出；第二次信号立即退出 | `codegen/internal/roost/interrupt.go:20`～`:99` |
| go 子命令作为独立进程组运行 | `go` 会再起 compile / link / git，只杀 `go` 会留下孤儿占着暂存树（Windows 上删不掉）、并让带缓冲输出的 `Wait` 不返回 | `codegen/internal/roost/command_tree.go:15`～`:42`（RR-20261004-13） |
| 一个模块、一个版本（三仓合一仓 P3 / P5） | kit 与生成器都在 roost-core 里；`go.mod` 只 require `roost-core`，`project deps` 只 `go get roost-core@<策略>` | `render.go:247`、`dependencies.go:143`～`:150` |
| 生成器下限按“产物真能编译”逐版抬高 | 下限不是猜的：每次生成物开始调用新 API，就把 `minimumVersions.Core` 抬到第一个带它的版本，`minimum` lane 恰好在这个版本上生成并编译 | `manifest.go:22`～`:85` |
| 静态注册在 `app.New` 之前、由生成的聚合完成 | 在某个 Mod 的 Start 里注册实体 builder，对在 Provide 里解析实体的 Mod 已经太晚；放在 `app.New` 之前从构造上消除顺序问题，所以没有“注册 Mod” | `codegen/internal/registry/parse.go:1`～`:10` |
| 标记解析集中在 `marker` 包 | `//cube:` → `//roost:` 改名后要同时接受两种前缀并提示迁移，规则只写一处 | `marker/marker.go:1`～`:7`（protocol 生成器例外，见 [实现 §11](../impl/12-codegen.md)） |
| 停机预算按服务实际注册的 Mod 计算 | 一个值不可能同时适合 23 个 Mod 的 game 进程和 6 个 Mod 的框架服务进程；生成器按 bootstrap 实际注册的 Mod 数与声明预算算 `shutdown.total_timeout`，部署宽限期 = max(它, 配置里实际写的最大值) + 5s | `codegen/internal/roost/shutdown_budget.go:15`～`:36`、`:126`（RR-20260926-66 / -80） |
| game-demo 存成真文件（`demo/*.tmpl`）而不是 Go 字符串 | 体量大、要被人照着改，真文件能读、能 diff、能整段 review；`.tmpl` 后缀让它们不参与 codegen 自身编译；正确性靠 CI 生成工程再编译、再跑机器人 | `demo/README.md` 开头；`codegen/internal/roost/demo.go:57` |
| 运行期守卫钉在已发布的最低 core | 守卫证明的承诺是“生成器写出的工程在它声明的最低版本上能编译能跑”；钉到发布清单的 `release:` 会让每个发版提交下载一个还不存在的 tag | `codegen/scripts/core-pin.sh:5`～`:13` |
| 根包门禁把“CI 跑了它”写进普通 `go test` | 合仓后 `go:generate` 产物没人重新生成、四个运行期守卫没人调用，都是“守卫在仓里，CI 不跑”；把 workflow 内容当测试对象，删掉那一步会在本地 `go test` 里红 | `ci_generated_code_test.go:13`～`:20`（RR-20260921-05） |

## 4. 怎么用

### 4.1 安装与命令总表

### 4.2 新建工程与模板

```bash
roost project new planet -module github.com/me/planet                     # 最小工程：一个 game 服务
roost project new planet -module github.com/me/planet -template game      # + 9 个托管框架服务
roost project new planet -module github.com/me/planet \
  -mods configdata,mongo,nats,dataengine,nest -template game-demo          # + 一条完整业务链路（CI 的 demo 场景同款）
```

| 模板 | 清单变化 | 额外写入 |
| --- | --- | --- |
| （无） | `DefaultManifest`：服务 `game`；共享 Mod `lock,ops,statslog`；服务 Mod `configdata,etcd,redis,mongo,nats,syncbus,remote_entity,dataengine,nest,manager`；feature `protocol,config,entity,nest,event,dao,errcode`；ID 号段 protocol 组 `game` 10000–19999、entity 1–255、component 2000–2999、errcode 100000–199999 | — |
| `game` | 把 catalog 里**全部 9 个**框架服务（account、activity、chat、global、mail、match、platform、rank、session）各加成一个托管服务，并写进第一个服务的 `uses`；第一个服务确保有 `nest` | Player / World 实体与生命周期、`game/lifecycle/world_singleton.go`、确保 World 存在的 game Service |

校验规则（`manifest.go:303`～`:494`，全部错误一次报出）：

- 名字都是 `^[a-z][a-z0-9_]*$`；module 路径逐段检查，拒绝 `..`、反斜杠、引号等注入（`manifest.go:507`）。
- Mod 必须在 catalog 里（13 个：`lock ops statslog configdata etcd redis mongo nats syncbus remote_entity dataengine manager nest saga`，`catalog.go:45`）；依赖自动补齐（`syncbus→nats`、`remote_entity→redis,mongo,syncbus`、`dataengine→mongo,nats`、`saga→mongo,nats`），`nest` / `saga` 自动带上 `dataengine`（`catalog.go:102`）。旧名 `sync` / `room` 读作 `syncbus`（`manifest.go:256`）。
- 服务不得重复共享 Mod；`manager` 不能放进 `shared_mods`。
- `access` 只支持 `player`，传输只支持 `tcp`；`access.player` 要求 `protocol` feature 且目标服务有 `nest`、不能是托管框架服务。
- `rpcs` 只能被一个服务拥有、托管框架服务不能拥有或使用 rpc；有 rpc 必须开 `rpc` feature；有 `sagas` 必须有服务带 `saga` Mod。
- `versions.*`：`latest` 或语义版本（预发布后缀按前缀判断），主版本必须是 1，且 ≥ 下限（core `v1.23.0`、kit `v1.14.8`、codegen `v1.15.0`，`manifest.go:86`）。kit / codegen 已不再是独立模块，见 §7.2 G2。
- `cicd` 目前只接受 GitHub + GHCR，环境必须含 staging / production，部署目标必须含 shell / docker / k8s。
- `ids` 不得超过框架编码上限（entity 255、component 65535、protocol 2^32−1）。

`//roost:register` 的阶段顺序是语义的：`pre → kind → config → component → entity → protocol → nest → route → post`（kind 必须先于 entity，config 必须先于读配置表的注册），同阶段按 `order`、再按 import 路径 + 函数名，输出确定。标记只能打在**导出的包级函数**上，无参数，返回空或单个 `error`；未知选项、缺 `phase`、同一函数标两次都报错（`codegen/internal/registry/parse.go:147`～`:235`）。`RegisterAll` 跑完全部注册后再做一次 `entity.ValidateEntityRegistry()`（`gen.go:130`）。

### 4.7 同步、升级、依赖

**`shutdown_budget`**（`shutdown_budget.go:126`～`:151`）：

```
total_timeout = 声明预算之和 + 3s × 未声明预算的 Mod 数 + 5s（Service.Shutdown）+ 3s（开启单实例锁时的 Release）
宽限期        = max(total_timeout, 三件套里实际写的最大 total_timeout) + 5s
```

声明预算的只有 dataengine（30s）与生成的玩家 TCP Mod（10s）。实测：game 23 个 Mod → `40s + 3s×21 + 5s + 3s = 111s`，k8s 宽限 116s；mail 6 个 Mod → `0 + 3s×6 + 5s = 23s`，宽限 28s。这个数写进三件套的 `shutdown:` 段（带摘要行）和每一种部署模板。只计生成器认识的 Mod：手工装的 Mod（例如 `RemoteMirrorMod`）要自己加进 `total_timeout` 再 `sync`。`deploy/k8s/README.md` 里的公式文字漏了单实例锁的 3s（**已登记 F01-4**）。

### 4.9 机器人与压测

- 框架在 `robot/`，与协议无关：transport（线格式）→ session（多路复用）→ `Context`（一个机器人）→ action / scenario（行为树）→ runner（调度：`pool` / `looping` / `arrival-rate`，`robot/runner/runner.go:35`）→ loadtest（单活跃运行的控制面：profile、历史、admin 命令、SLO 阈值、报告，`robot/loadtest/manager.go:1`）。业务只提供编解码、拨号器、消息号和场景 YAML。
- game-demo 的 `cmd/loadtest` 只做三件事：注册本工程的消息、加载 `loadtest/scenarios/*.yaml`、把 flag 变成 `loadtest.Profile`；`loadtest/playertcp` 是生成的玩家 TCP 帧（16 字节大端头、握手、严格递增序号）的客户端适配，常量要与 `server_gen.go` 同步。
- 用法：`make loadtest LOADTEST_COUNT=20`（= `go run ./cmd/loadtest -endpoint 127.0.0.1:7000 -count 20 …`）。机器人走真实凭据（account `Login` → `CreateRole` → `SelectRole` → 握手），环境准备时先 `go run ./cmd/accountctl -redis … upsert-server -sid 1000`。`-count` 给偶数（duel 两人一组），不要超过 `player_access.tcp.max_connections_per_ip`（默认 128）。任何一步返回非零 code 或 `error_rate` / `p95` 超阈值，进程非零退出并打印 JSON 报告。详见 `demo/README.md` “机器人压测 = 回归测试”。
- CI 的 demo 场景正是这一套：`run.sh start` 起 10 个进程，`go run ./cmd/loadtest -count 6`（`.github/workflows/framework-compat.yml:207`～`:236`）。
- lockstep 机器人（`robot/lockstep.go`）的追帧缺陷属 04 分区（**已登记 F04-9**）。

### 7.2 已知限制与本次核对发现的问题

已登记、本篇不重复调研的生成器问题：**F01-4**（部署说明公式漏单实例锁 3s）、**F01-7**（`demo/README.md` 说 codegen 有独立 go.mod）、**F02-4 / F03-9**（`//roost:nest` 不接受 `durability=pipelined`）、**F04-10～F04-12**（玩家 TCP panic / WriteGate 断连无栈、`shutdown_timeout: 0s` doctor 误判、`dispatch_timeout` 写成显式值）、**F05-6**（entity 错误文本列出 `mirror_cache`）、**F07 F1 / F5 / F6**（tablegen `json` 标签、`key=`、单例多行）、**F09-R1 / R3 / R4**（生成客户端 affinity 不生效、JetStream 传输不兼容、servicerpc 校验漏洞）、**F09-N15**（match wire 字段 `ticket_i_ds`）。
