# Nest 消息热路径优化设计

本文说明 Nest 如何减少每条消息的框架开销。**状态：本轮六项局部优化已实施；目标视图缓存与指标预绑定明确延期，未引入相应缓存。最终选择与证据见第 8 节及 [性能报告](../performance/NEST-HOT-PATH-20261013.md)。**

评估日期：2026-10-13。源码基线：`fd13e178`。此前 `58d27e7a` 已完成 Msg 字段整理与客户端目标存储优化，不属于本次待实施内容，详情见 [Nest 三池与 Await](NEST-AWAIT.md)。

## 1. 目标与范围

Nest 在执行业务前，需要确认消息涉及哪些实体、建立先后关系、准备实体、取得执行权限，并安装事务与观测上下文。即使 Handler 什么也不做，这些步骤仍有成本。“热路径”指每条消息都会经过、调用特别频繁的代码。

本方案优先减少重复计算和临时内存分配，保持现有短业务池、长业务池与 I/O 池的职责，以及多实体顺序、Guard、事务、Remote、Await 和关闭排空契约。不会通过减少持久保证、删除并发检查或改变业务顺序获得性能收益。

现有包结构保持不变：

```text
framework/nest/          消息、目标解析、调度、业务执行和上下文
infra/observe/metrics/  公共指标实现（第二批确有需要时修改）
docs/framework/         现行设计与实施状态
```

不新增调度层，不迁移公开符号。业务 API、网络协议、WAL 与持久格式、代码生成接口均计划保持不变，预期不要求重新生成业务工程。Nest 继续依赖公共观测包，观测包不能反向依赖 Nest。若实施发现必须改变这些边界，应先更新本设计。

## 3. 第一批：目标解析复用与分组预分配

### 当前重复工作

[客户端入口](../../framework/nest/client.go)先标准化目标；[调度队列](../../framework/nest/dispatch_queue.go)的 `dispatchIDs` 为多目标展开、排序、去重；[I/O 准备](../../framework/nest/io_load.go)再次取得调度目标，并按路径标准化；[业务执行](../../framework/nest/nest_dispatch.go)的 `dispatchMany` 也会标准化目标。

[CastMulti](../../framework/nest/cast.go)每次重新生成当前消息的声明目标集合，再逐个检查待访问目标是否在声明内。同一 Handler 多次 Cast 时，这部分准备可能重复。

### 目标设计

一次准入形成消息自有、只读的目标信息，供后续阶段复用，但必须保留两种不同视图：

| 视图 | 用途 | 必须保留的内容 |
| --- | --- | --- |
| 业务目标 | 向 Handler 传递实体和分组 | 原始顺序、重复项、组边界 |
| 调度目标 | 建立 tail 依赖、检查声明范围 | 标准化后的去重集合，可排序 |

例如业务目标 `[A, B, A]` 的调度集合可以是 `[A, B]`，但不能因此把 Handler 的第三个参数删除。分组同理：`[[A, B], [A]]` 不能失去第二组。

实施时先沿用现有 job 拥有目标存储的约束，确定 Msg、job 与续行间如何共享只读视图，再决定最少的内部字段。不能同时在两处保存可变缓存。调用方传入的切片必须先隔离，消息准入后不得因调用方修改切片而改变目标。

公开入口、直接构造 Msg 的路径都要验证；内部执行函数只有在明确取得已准备视图时才能跳过重复标准化，其他路径继续校验。非法 ID 不能因缓存变成有效输入，也不能无意改变错误返回阶段。

内部续行复用既有准入资格；Await 恢复属于新的消息准入，不能继承旧 tail。克隆、失败准入、重入队和对象复用都要明确视图是否重建、何时失效；不能仅按 Msg 指针做全局缓存。

`CastMulti` 复用只读声明集合。小集合保留简单线性检查，较大有序集合可对照二分查找；不预设新增 map 必然更快。声明检查与 Guard 权限检查仍分别存在。

独立的低风险改动是：`multiGroupDispatch` 展开各组前累加总长度，一次分配容量。不能假设任意外部 Msg 的各组共享连续数组，也不能为了复用存储让一个组的 append 覆盖另一个组。

## 4. 第二批：指标和上下文

### 固定指标避免重复编码

[metricKey](../../infra/observe/metrics/metrics.go)当前根据名称和标签生成字符串。对于 Handler、阶段等固定组合，可研究注册时预绑定指标句柄，让逐条消息的更新不再重复构造相同 key。

先核对公共观测包已有接口，优先复用，不为 Nest 另造指标系统。句柄必须遵守原有标签编码、series 上限、并发更新、重置和生命周期。动态 Handler 或动态标签不能形成无界缓存；重新注册、禁用指标、热更与重置后不能继续更新失效对象。若公共包修改范围过大，本批可独立推迟，不阻塞第一批。

### 同一执行阶段减少重复上下文安装

[pushCurrentNestDispatchMsg](../../framework/nest/group_transition.go)通过 goroutine ID 和 `sync.Map` 保存当前消息，并在退出时恢复旧值。后续应结合 `ensureNestContext`、Guard scope 的调用位置，确认同一消息嵌套时哪些注册可以省略。

“消息指针相同”本身不足以证明上下文相同。必须同时核对执行池身份、Guard、事务、快照和慢执行器的有效范围；不同嵌套消息仍要完整恢复前一层。返回、panic、Remote 续行和池间切换均不能泄漏上下文。优先去除已证明重复的安装，不移除用于业务池阻塞检查和实体访问保护的状态。

## 5. 第三批：临时存储和依赖边

### 多实体临时存储

业务实体列表、加锁列表、Touch 清理列表及[分组快照](../../framework/nest/group_lock.go)有不同职责。可以研究一次申请底层存储并切成互不重叠的区间，或针对常见的 1～4 实体使用小容量存储，但要以逃逸分析和 benchmem 判断实际收益。

分组快照承担并发状态检查，不能删掉。业务可变列表不能与解锁、释放引用使用的列表混用。跨 Remote、异步提交或续行的存储在实际终态前不能归还或覆盖；worker 返回也不一定代表消息完成。本方案不预先引入全局对象池。

### 重复前驱边去重

若消息 P、N 都声明 A、B，当前可以在 P 到 N 之间登记两条依赖边，同时让 N 的前驱计数加二。完成时对应减二，逻辑自洽，**这不是已确认的 bug**。

候选优化是每个不同前驱只登记一次，从而减少共享队列锁内的 append 和完成遍历。必须同时修改计数和边登记；只改一边会造成提前执行或永远不就绪。优先比较少量前驱的线性去重与原实现，不默认每次创建 map。没有收益则保留原实现。

本方案保留 `waiting` 与 `continuations`。内部续行不能当成普通新消息排到自己的 tail 后。是否更换共享锁，需要另采集 CPU、mutex/block profile；本次内存采样不能支持“锁已是瓶颈”或“应该改无锁队列”的结论。

## 6. 验证与验收

每批单独提交、单独对照，避免多个变化互相掩盖。实施前补齐缺少的测试或基准，本文列出的矩阵不是已经运行通过的结果。

| 范围 | 必须覆盖 |
| --- | --- |
| 目标解析 | 单实体、双实体、四实体、多组、重复 ID、乱序 ID、空目标、非法 ID；输入切片隔离和组 append 隔离 |
| 顺序与权限 | 同 ID 串行、独立 ID 并行、多个 ID 共享同一前驱、跨长短业务池；Cast 声明和 Guard 检查 |
| 生命周期 | 准入失败、取消、超时后的晚完成、panic、克隆、Remote 续行、Await 恢复、关闭排空 |
| 上下文 | 同消息嵌套、不同消息嵌套、异常恢复、池间切换；业务池禁止等待仍有效 |
| 指标 | 开启/关闭、并发更新、series 饱和、标签转义、注册变化、重置与释放 |

性能对照至少包含空 Handler 和 100μs Handler，单/双/多目标，单 worker 与多 worker，同 ID 热点与独立实体，以及分组 1/8/32 组。同步 Request 和异步 Dispatch 分开测量，不能把 Request 的回复 channel、计时器开销当成所有消息的共同成本。100μs 必须明确是 CPU 工作还是等待，不能用 sleep 冒充 CPU 业务。

同机、同 Go、同参数对照；正式时间测量不带 race/profile。每组建议至少五次独立测量，保存全部样本，用 benchstat 等方式比较，不挑最好一次。记录 ns/op、B/op、allocs/op；并发压力另外记录成功完成吞吐、失败/拒绝数、排队及端到端 p99/max、积压和最终排空。

验收首先要求行为正确；目标场景还应有可重复的分配减少或性能收益，常见单实体和单组场景不得出现未经说明和接受的稳定退化。此前分组存储优化曾有单组退化，因此必须保留这一对照，不以多组收益代替单组结果。没有可重复收益或显著增加复杂度的改动应撤回。

本地按影响运行 Nest 定向测试、编译和静态检查；并发改动在支持环境运行 race，指标改动补观测包验证。涉及真实实体管理、Remote 或事务生命周期时，增加正式链路回归，不能仅靠 Mock Getter。无需等待 GitHub CI，但未运行的检查必须明确记录。

## 7. 实施顺序、回退与完成条件

1. 第一批：分组容量预分配、目标视图生命周期和重复解析消除，分别留性能对照。
2. 第二批：根据新的 profile 判断指标与上下文的剩余占比，再分别实施。
3. 第三批：多实体临时存储、重复前驱边去重，各自证明收益再保留。

各批的最终选择、验证命令、完整结果和未验证边界见第 8 节。第一批保留分组预分配，第二批保留上下文局部优化，第三批保留临时存储与前驱边优化；目标视图复用与指标预绑定延期。

无公开格式变化时，回退以撤销对应批次提交为主，不需要数据迁移。不用生产配置开关长期维护两套内部状态机；对照实现可留在基准中。若出现顺序、Guard、释放责任或上下文隔离退化，优先回退，不能用扩大队列、增加 worker 或放宽测试掩盖。

完成意味着：所有保留改动有行为回归和同口径收益证据，无收益候选已撤回或明确延期，当前文档与最终实现一致。完成本方案不等于完成生产容量、跨机 HA 或长期运行验收。

第二批保留两项局部改动：`ensureNestContext` 直接传 Snapshot option，避免临时可增长切片导致闭包逃逸；`pushCurrentNestDispatchMsg` 遇到同 goroutine 的同消息只省登记，不省 fctx、Guard 或事务作用域。新增同消息/不同消息嵌套与 panic 恢复回归，既有 Context、Await、Remote 和阻塞约束用例通过 5 轮。见 [分配采样](../performance/benchmarks/nest-hot-path-20261013/alloc-profile.txt) 与 [上下文样本](../performance/benchmarks/nest-hot-path-20261013/context.txt)。

指标预绑定明确延期：新采样仍显示指标编码分配，但公共 Registry 目前无绑定句柄接口，Reset、series 限额及动态标签需要一并设计。不能为本轮 Nest 优化另建全局句柄缓存。目标视图缓存（包括慢准备、Cast 复用）也暂不引入：现有直接 Msg、Clone、重排、广播和续行的校验阶段不同，`normalizeFullIDs` 本次只占约 1.42% 分配字节；先保留显式校验，不用跳过校验换取收益。这两项是候选延期，不能表述为已完成缓存复用。

第三批临时存储保留两项：锁列表与 Touch 列表一次分配、切成容量不重叠的区间；分组快照在取锁调用栈内用 4 项数组，大集合按需扩容，重试重新采集，不进入 release 闭包、不引入对象池。Group/Multi/Touch/Release/Cast 回归重复 5 轮通过。四实体异步热点样本在上下文批次基础上减少 192 B/op、2 allocs/op，见 [临时存储样本](../performance/benchmarks/nest-hot-path-20261013/storage.txt)。
