# reward：服务端奖励组，只抽清单，不发货

宝箱、副本或订单都可以调用同一个奖励组。输入是服务端选定的组 ID，输出是按物品号升序、同物品合并后的 `[]reward.Item`。`reward` 不知道玩家是谁，不扣箱、不改余额，也不负责发货。它不是抽卡或掠夺系统。

## 能力

安装 `roost module add reward`。不依赖 `bag`、`wallet`、`gacha` 或 `unlock`；只给工程接入配置数据（`configdata`）。没有客户端协议、Player 组件、DAO 字段或远端服务。

```go
// import "<工程 Go module>/game/modules/reward"
items, err := reward.Roll(groupID)
if err != nil {
    return err // 没有可以发放的部分结果
}
// items[i].ItemID 和 items[i].Count 都是 int64。调用方决定保存、展示还是入账。
```

### 怎么配一组奖励

在 `configs/table/reward_group.csv` 定义组，在 `reward_entry.csv` 里写组内各项，然后 `roost generate`。组和行的 `id` 各自唯一；`group_id` 指向组，`item_id` 是奖励物品号，`count` 是命中本条时给的数量。组的 `draws` **只**管加权池，不放大固定项或独立概率项。

| 行 `kind` | 抽法 | 配置要求 |
|---|---|---|
| `fixed` | 每次解析都给一次 | `chance_bp=0, weight=0` |
| `chance` | 每行各自独立判断；可全中或全不中 | `chance_bp` 为万分率 `0..10000`，`weight=0`；如 2500 表示 25% |
| `weighted` | 每次按该条权重占池中剩余总权重的比例选一条 | `weight>0, chance_bp=0` |

组没有 `weighted` 行时 `draws=0`；有加权项时配 `1..64` 次。`replacement=true` 是有放回，下次仍可中同一行；`false` 是无放回，抽数不得多于池中行数。**不放回按配置行，不按物品号**：若两条各给同一种道具，两条都可以命中，最后数量相加。单组最多 256 行；空组不是合法空奖。合法组的独立概率项全未命中可以得到空清单，调用方应以 `err` 而非清单长度区分成功与失败。

安装自带三个可替换的样例：第 1 组固定给物品 `1001 × 2`，另有 25% 的机会给 `1002 × 1`；第 2 组加权有放回抽两次；第 3 组加权无放回抽两行，其中两行同为物品 1004。样例中的 ID 不是业务常量。

## 能力边界

- 一组在消耗随机数之前完整校验。权重总和以及**每种物品能达到的最大合计数量**都必须能放入 `int64`：两种不同物品各自数量很大，并不因为合起来超过上限而拒绝。任何抽取错误均不返回半份清单。
- `Roll` 读一次当前配置快照，组定义与条目来自同一版本。请求内遵循已固定的快照；在请求外按本次调用的快照抽。生产随机数由服务端产生，客户端不能指定种子或抽取结果。
- 返回的是**物品号和数量的方案**。`reward` 不依赖道具表，不判断物品是否下架、是否超堆叠或背包是否已满；真正入账时由资产模块在业务事务里校验。错误应原样返回，不能忽略一条失败后只发剩下的。
- 无保底、免费次数、定价、扣货币、付费概率公示或抽取回执；这些不属于本模块。这里只处理平面奖励组，不递归引用其他组，不解释负数量或拿其他玩家的资源。
- **相同组号不是幂等键。** `Roll` 两次是两次独立抽取，不能把组号或种子当成已抽结果。需要重试稳定的业务应保存具体物品清单，而不是只保存组号后按最新配置重抽。

## 复用方式

- **订单／副本结算单**：由服务端规则选组，第一次创建订单或结算单时抽取，在同一事务保存具体清单。展示、补领和重试都读这份清单；后续改权重不改已经承诺的奖励。
- **开箱业务**：先按本次操作的业务键查已提交回执；命中直接返回原清单。首次操作在同一 Player 事务里检查并扣箱、抽清单、逐项入包、保存回执；任何一步失败整笔回滚。成功提交前不向玩家确认结果。以上是宿主用法，安装 `reward` 不会自动生成开箱协议。
- **已有 gacha**：既有抽卡、保底和收费继续走 `gacha`，本模块不会接管或改变其随机数与回执。

## 联动

无强制业务依赖，也不自动拦截其他模块。服务端直接调用 `game/modules/reward`，订单持久化、背包发货或邮件投递由各业务实现；跨事务投递需由业务持久保存清单和可重放的投递凭据。

## 验证范围

`roost module verify reward` 在实际安装的 `./game/modules/reward` 包运行 `^TestReward` 场景；`codegen/internal/roost` 的 `TestModuleRewardStandaloneAndCustomTable` 另在独立新工程替换两张 CSV、重新生成，用外部包导入公开 API 读取结果。这里验证抽取行为与业务分工示例，不等于测试了一个生产开箱服务或真实资产入账。
