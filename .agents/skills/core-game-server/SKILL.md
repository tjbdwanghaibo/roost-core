# Core 框架学习与游戏服实践

## 角色与目标

同时承担资深游戏服务器技术专家、结对导师和准备使用 core 开发目标游戏的开发者角色：不仅判断框架内部是否正确，还要实际回答“我要做这类游戏，怎样接入、哪里难用、缺什么能力、出了故障怎么恢复”。帮助用户理解 core 的设计契约、正确实现业务，并在实际使用中找出学习的问题和框架的问题。不要只复述文档，也不要默认框架设计或用户理解一定正确。解释设计的适用条件、代价和可验证的边界。

主仓库是 `roost-core`；`ssr` 仅供部分代码学习、业务场景和工程经验对照。不要为阅读 ssr 安装完整服务、索取企业凭据或启动它的基础设施。不要直接移植其旧 API、并发模型或隐含运行假设到 core。

用户只要求保存或更新此 skill 时，完成 skill 本身即可，不自动启动全面审计或业务改造。

## 游戏类型参数

调用格式为 `$core-game-server game_type="游戏类型"`，也接受 `$core-game-server SLG` 或“用这个 skill review MMO 框架接入”这样的自然语言。参数是任务指令约定，不依赖额外 CLI 或参数解析程序。

示例：

```text
$core-game-server game_type="SLG"
$core-game-server game_type="MMORPG" review 玩家跨地图与断线重连
$core-game-server game_type="MOBA"
$core-game-server game_type="卡牌RPG" 实践抽卡养成、回合战斗与关卡奖励
$core-game-server game_type="合成/超休闲" 实践棋盘、离线存档冲突与服务器奖励
$core-game-server game_type="放置/模拟经营" 实践多工坊、离线收益、倍率切换与跨天奖励
$core-game-server game_type="自走棋/多人回合竞技"
$core-game-server game_type="塔防/合作PvE"
$core-game-server game_type="多人合作生存/撤离"
$core-game-server game_type="回合制卡牌" 实践战斗结算与奖励发放
$core-game-server game_type="开放世界生存 + 即时战斗"
```

- `game_type` 支持自定义类型或混合类型；沿用会话中最近明确的类型，用户修改后更新。未提供且无法从上下文推断时先采用通用游戏服视角继续，不把类型偏好作为开工前提，也不要默认为 ssr 的 SLG 类型。
- 开始时简要说明目标类型、本轮业务切片和重点风险。类型只能提供场景假设，不能据此编造玩家规模、tick 频率、一致性要求或部署拓扑；这些要求从用户、仓库和实际证据确定，未知项标明。
- 所有学习例子、调用链、最小消费者和 review 优先级围绕该类型组织。既检查通用资产与并发正确性，也检查目标游戏能否用正式接口实现关键玩法，避免只完成抽象代码风格检查。

| 目标类型 | 优先场景与 review 重点 |
| --- | --- |
| SLG / 策略 | 优先跨服、视野、活动：跨服联盟／国战权威与补偿、战争迷雾／侦察／联盟共享视野、赛季窗口／贡献／结算补发；再展开行军、资源、战斗与长期恢复 |
| MMORPG / 开放世界 | 优先跨服、视野、活动：Player 静态 sid 下的跨服协作、同屏／副本／队伍／隐身可见性、世界 Boss／限时副本／活动奖励；再展开交易、战斗与容量 |
| FPS / MOBA / 动作竞技 | 权威状态、输入准入与顺序、tick 预算、同步延迟、重连追帧、确定性与反作弊边界；区分状态同步和帧同步的适用条件，不预设框架提供回滚或延迟补偿 |
| 回合制 / 卡牌 / 自走棋 | 回合推进、指令幂等、超时托管、随机性与回放、结算和奖励恰好一次、配置版本固定 |
| 合成 / 超休闲 | 棋盘操作权威、生产器与随机身份、离线命令批次、跨设备代际与存档冲突、服务器目标判定、广告证明与永久到账回执；不信任客户端余额或成功分数 |
| 放置 / 经营 / 养成 | 多生产队列与投入预扣／退款、固定离线窗口、倍率分段／整数余数、产出缓冲／仓库容量、跨天活动、收益和资产账本、长时间离线后的恢复 |
| 塔防 / 合作 PvE | 共同资源与建造格竞争、塔所有权、阻路验证、波次和服务器伤害、基地胜负、断线托管、活动波次恢复及团队奖励 |
| 生存 / 撤离 | 付费准入与局内身份、共享采集、制作预扣／容量预留、死亡转移／拾取竞争、撤离中断／清单封存、永久兑付与活动局恢复 |
| 自定义 / 混合类型 | 先提取核心循环、交互对象、实时性和资产模型，再组合相关检查方向；明确哪些是假设 |

review 每个重要结论都要关联该类型的具体玩法后果，并区分“现有接口可实现”“需要业务补齐”“框架缺口”“已有能力但尚未验证”。提出 feature 时给出实际接入场景、最小 API/配置需求和验收用例；不能因其他同类游戏常见某功能就认定 core 必须内建。

## 开始工作

1. 确认仓库位置、当前 HEAD、工作区已有改动及适用 `AGENTS.md`。不要重置、自动更新代码或覆盖用户文件。云任务使用现有隔离 checkout，不主动创建 worktree。
2. 阅读当前 `docs/maintenance/README.md`、`docs/framework/README.md`、`docs/maintenance/KNOWN-LIMITS.md`，按需查阅当前发布说明和 `CHANGELOG.md`。历史已修复问题不能作为当前缺陷；文档与实现不一致时记录差异并验证。
3. 遵循 AGENTS.md 的代码索引流程。索引工具不可用、过期或覆盖不足时，明确限制，读取当前源码并用 `rg` 补证；不能据不完整搜索声称“没有实现”或“只有这一处”。
4. 根据 `go.mod` 确认工具链。若存在 `/workspace/.cloud-setup/activate.sh`，先 source；否则使用仓库声明的环境，不把旧会话安装状态当作保证。
5. 优先围绕用户当前目标和 `game_type` 工作。没有具体目标时，从 `docs/GETTING-STARTED.md`、`codegen/README.md`、`demo/README.md` 和 `demo/WALKTHROUGH.md` 入手，选择目标类型的代表性业务切片；类型未指定时采用“登录后的玩家请求 → 修改背包 → 持久化 → 同步客户端”。逐步展开，避免一次通读所有模块。

## 学习与实践循环

每轮围绕一个可检验的问题推进：业务目标 → 当前理解和疑问 → 相关契约 → 源码调用链 → 最小实践 → 实际结果 → 修正理解与记录问题。

- 先用游戏场景说明输入、输出、状态归属和失败结果，再映射到具体类型、函数和配置。用图或少量代码解释关键时序，不堆砌包名。
- 引用当前源码位置，至少追到关键状态变更或失败分支；不要凭类型名推断行为。对于跨模块路径，说明入口、调度、锁、持久化、同步和退出时的先后关系。
- 优先使用正式生成器、Sender 和公开接口。涉及模板或生成器时，在仓库外或忽略目录生成独立消费者，编译并实际调用；不要手改生成文件来掩盖问题。
- 学习产物以能工作的最小业务切片为准。仅写伪代码时明确说明；不要把编译通过等同于运行行为正确。
- 学习或 review 中发现已确认的问题时，本 skill 已获授权在固定分支 `fix/core-game-server-review` 完成修复、相关回归、必要的现行文档更新、提交和推送，不必再询问是否开始修复。用户明确要求只读或不修改时遵守该限制；涉及重大产品决策或不兼容契约变更时，先完成调查并明确待定方向。

自走棋／多人回合竞技的现行入口是 `docs/framework/AUTO-CHESS-INTEGRATION.md`，正式消费者为 `scripts/test-auto-chess-generated.sh`。默认八席共享卡池，World Match 管理全部局内事实，Player 静态归属只接永久奖励。按“成局名单与配置固定 → 商店预占池／购买／出售／合星守恒 → 上阵与等级／锁店 → 准备屏障／服务器期限 → 冻结编队与确定性战斗 → 轮空／淘汰／收入／有界终局 → 八人原子领奖”实践。接管 Epoch 来自可信会话入口，旧连接不能写，新连接查询旧 Seq 原回执；视图不得暴露对手商店、备用席、种子或账本。

`ROOST_AUTO_CHESS_REAL=1` 与隔离 Mongo 门变量执行八人冻结战斗 strict WAL 未投影时 SIGKILL；实体 Create 只创建内存实例，参与冷恢复的玩家必须先经正式事务建档。先核对完整冷事实，再启动真实计时驱动循环补一个阶段并按下一期限继续，领奖后第三进程重试全部命令与八人奖励。离线不快进整局，账本满不淘汰旧身份。共享池／配对／轮空／利息／托管规则属于业务；八个逻辑玩家不等于真实客户端网络、跨 sid 或容量验收。长期对局归档必须与永久奖励防重共同设计，跨 sid 使用 Remote／Saga，不把本地 MultiSync 当分布式事务。

塔防／合作 PvE 的现行入口是 `docs/framework/TOWER-DEFENSE-INTEGRATION.md`，正式消费者为 `scripts/test-tower-defense-generated.sh`。默认四人、5×5 地图、三波敌人。World Room 持有共同金币、塔所有权、路线、怪物、基地和波次，Player 静态持有永久奖励。按“正式玩家建档／固定名单配置 → 同格竞争／扣费／阻路 BFS 同事务 → 所有者升级／出售及期望等级 → 全员准备或超时托管 → 服务器攻击／移动／基地扣血 → 胜败与团队领奖”实践；不得把客户端命中或胜者作为授权来源。

`ROOST_TOWER_DEFENSE_REAL=1` 与隔离 Mongo 门变量在活动波次已经推进一步、strict WAL 未投影时 SIGKILL；先比较完整冷事实，驱动循环补一步后持续续战，第三进程重试全部建造／准备和团队领奖。默认离线暂停而非按停机秒数追伤害；一波步数有上限，战斗阶段不允许改变路线。阻路、伤害、共享资金权限、托管、分奖属于业务。实际客户端／鉴权、补位、动态导航、完整技能 Host、跨 sid／HA、自动派奖／归档与容量另行验收，不把四个逻辑玩家等同真实网络规模。

多人合作生存／撤离的现行入口是 `docs/framework/SURVIVAL-EXTRACTION-INTEGRATION.md`，正式消费者为 `scripts/test-survival-extraction-generated.sh`。默认四人同局、四个相邻区域；World Raid 持有局内物资与状态，Player 静态持有永久资产。按“正式建档／固定名单配置 → 入场费与 Joined 同事务 → 位置／采集／全局物资守恒 → 制作预扣与在途容量预留 → 环境伤害／药剂 → 死亡退料入包／拾取竞争 → 可中断撤离／不可变清单 → 原子永久兑付”实践。重复入场不重新收费或复活，客户端不能提供物资清单、时间、伤害、撤离成功或奖励。

`ROOST_SURVIVAL_EXTRACTION_REAL=1` 与隔离 Mongo 门变量，在制作与撤离同时在途、strict WAL 未投影时 SIGKILL；恢复后先比较完整冷事实，再启动驱动有界完成事件，第三进程重试准入、全部命令和清单兑付。明确默认时间规则：已到期且完成时间早于 Raid End 的安全区撤离先完成；硬结束不延长；环境伤害离线只补一次。制作在途仍保留原料容量，死亡时未完成制作退料入掉落包。以上属于业务选择，不扩张框架保证；真实客户端、射击／物理／AOI、局外逐件装备、自动结算／归档、跨 sid／HA 与容量另行验收。

用户询问已有玩法文档时，核对 `docs/framework/README.md` 与 `docs/maintenance/DOCUMENTS.md` 中的入口、实际文件和可执行脚本，回答已写类型与未验收范围；新增类型同时维护两处目录，避免文档存在但维护清单漏项或重复。

## 必须理解并检查的契约

### SLG／MMORPG 的长期学习重点

用户明确要求这两类重点学习“跨服、视野、活动”。后续继续 SLG 或 MMO 时优先深化这三条线，不以增加更多游戏类型或重复基础经济回归替代专题学习。优先级是持续偏好，用户指定其他任务时按当轮任务执行。

- **跨服**：先画 Player／联盟／战场／活动的权威归属和 sid 路由，分别实践 Remote owner／lease／fence、Mirror 只读、Saga 正向／补偿／重复投递／结果未知查询、原服永久资产到账。沿用 Player 静态 sid，不默认实施动态迁移。赠礼通过不等于跨服战场完成，本地多实体事务不等于跨服原子事务。
- **视野**：先定义谁可以看到哪些字段，再接 AOI 空间候选、关系来源、Profile 白名单与 Sync 发布。SLG 重点迷雾／侦察／联盟共享／多块被观察；MMO 重点同屏密集／副本隔离／队伍关系／隐身权限。检查撤销一个来源但其他来源仍在、最后一个来源撤销、提交前不可见、失败回滚、切图与重连 Full、慢客户端和扇出。AOI 候选及关系来源不是安全授权，攻击／采集还需服务端独立校验。
- **活动**：按活动组／实例／窗口定义身份和业务时钟，学习本服持久期限、协调器 expected 集合、阶段通知／宽限聚合、贡献幂等与乱序累计值、结算投递／确认、原服邮件／资产到账和恢复／人工补发。不开活动就靠协调器本机时钟自动结算、用当前窗口重报旧贡献、把投递确认等同玩家已领奖，均不得作为默认接法。明确 demo 尽力贡献失败不自动补报的已接受取舍；需要可靠贡献时先实现业务持久意图，不悄悄修改公共保证。

每次选一条具体链路，产出“玩法输入 → 状态拥有者 → 正式接口与源码 → 提交／可见性／失败顺序 → 可执行场景 → 证据与缺口”，维护在 SLG／MMORPG 现行手册。建议主线为 SLG 跨服联盟活动、MMO 跨服世界 Boss；先完成各自独立模块验证，再连接跨服、视野和活动，不能把三个各自通过的测试当作联合链路已通过。

main 的 test-slg-generated.sh 已整合基础联盟消费者；下面的独立脚本承担 TCP／空间深化验收，两份夹具的证据须分别记录。SLG 联盟活动主线先运行 `scripts/test-slg-alliance.sh`（显式隔离 Redis / NATS），学习 `scripts/testdata/slg-alliance` 的“成员权限与贡献意图同 CAS → 已提交关系视野 → 窗口固定的贡献补报 → 冻结并清空待报意图 → 两服阶段聚合 → 原服奖励义务持久回执 → ACK”。此入口直接消费正式生成的 Activity RPC；协调器为子进程，两个静态 sid 客户端在父进程。按 SLG 手册区分已验收与后续：Interest 来源归并不等于空间迷雾或客户端协议；业务 Redis CAS 不等于 Remote owner/fence；原服收到奖励义务不等于 Player 已到账；正常重启不等于 SIGKILL／断电。超出贡献服务去重期限的未确认意图停止自动补报、交业务对账，不能换身份重加。Player 金币到账由下面的生成消费者扩展继续验证；Remote 联盟实体由下面的可选模式继续验证；邮件附件、空间授权交集与跨服撤权传播仍逐项接入，保留这些区别。

联盟活动的实际 Player 到账用 `scripts/test-slg-alliance-player.sh`：显式 Redis/NATS/Mongo，CLI 生成 Player DAO/Sender，同一活动链 ACK 后从原服持久义务继续发金币；每个静态 sid 独立 WAL 与测试子进程，建档、空间移动与到账的 strict 记录未投影后 SIGKILL，恢复先比较完整钱包，再重读义务／并发重试，第三进程再次验证。金币与永久回执同一 Player 事务；错服／改金额拒绝，账本满后拒新身份。此项补齐实际资产证据，但不升级 ACK 为玩家已领奖，不证明 Remote 权威、Saga、邮件附件、常驻调度与长期归档、完整网关服务或跨机故障。Remote 联盟实体已有下一段扩展；之后优先接空间授权交集与跨服视野传播，继续维护各运行模式的证据边界。

`ROOST_SLG_REMOTE=1 bash scripts/test-slg-alliance-player.sh` 把联盟事实换成 CLI 生成的 Managed Remote 实体，生成 Sender 执行业务条件写，Mongo 权威 / Redis 锁与 L2 / 两个 Runtime 的独立 WAL 按正式装配接线。先比较完整冷事实，再继续同一活动、原服义务与 Player 崩溃恢复。显式 owner 2000→2001 要检查 marker / route 上升、旧 Runtime 活着仍被拒；Claim 后检查 Shared，不无条件重复 EnterShared。业务 CAS 版本不是 Remote fence，未知提交不当作冲突盲重算。两 Runtime 位于同一父进程，不声称跨机 HA、Mirror 推送或 lease 中途过期已测。

尤其检查重复发奖、超卖、道具丢失、旧 fence 写入、跨玩家越权、同步提前可见、断线重连状态错误等游戏业务后果。不要用盲目重试、吞错、删除 WAL、关闭断言或降低验证强度绕过失败。

## 主动发现问题，但先分类再下结论

对学习中遇到的疑点，区分以下类别；证据不足时标为待验证假设。

- **学习理解问题**：概念混淆、缺少前置知识、错误心智模型。给出原理解、正确契约、一个反例及验证方式，不归责用户。
- **文档或可用性问题**：入口缺失、示例过期、命名误导、配置缺少校验、错误信息难以定位。指出具体障碍及最小改善建议。
- **业务接入误用**：违反已明确的公开契约。说明正确接入方法，同时检查框架是否应更早拒绝误用。
- **框架实现问题**：合法调用下违背承诺、丢失或重复状态、并发竞态、恢复错误等。必须提供源码证据及最小复现；不能仅凭偏好的架构认定缺陷。
- **环境或验证问题**：工具链、权限、网络、依赖服务、测试夹具或不稳定测试。与产品行为缺陷分开；单次失败或复跑通过都不足以确认根因。
- **设计取舍或已知限制**：说明当前保证范围、业务影响和可选方案，不擅自改写项目已明确接受的决策。

问题记录至少包含：类别、状态、基线提交、业务触发条件、期望与实际结果、源码/日志证据、复现命令、影响范围、临时规避及建议修复。严重程度依据玩家资产、可用性、恢复成本和触发概率判断；推测与确认分开。

先检查当前已知限制和现行记录，合并重复问题。用户要求落盘时优先更新相关现行设计/维护文档，遵循仓库规范；不要每轮生成新的交接或审计报告。没有复现的问题不得写成已确认缺陷。

## 验证与修复

- 按影响范围选择最小但有意义的检查。一般改动运行相关包测试和所需构建；涉及并发时补相关 race 回归，涉及生成器时编译并运行生成消费者。
- 框架修复先建立能在修前失败的回归，再修复、复测并更新相关契约文档；不顺带扩大重构范围。
- 跨模块或框架整体就绪验证使用 `GOWORK=off go build ./...`、`GOWORK=off go vet ./...`、`GOWORK=off go test ./...`，按机器资源限制并行度；不要把全仓检查机械用于每次纯文档任务。
- 真实服务验证使用隔离资源和唯一命名空间，按相关集成说明启动，并做代表性功能请求。不能把 PID、端口、仅编译、零测试或跳过视为功能通过；不使用生产玩家数据做故障注入。
- 记录执行命令、退出状态、通过/失败/跳过/未运行的区别。偶发失败保留首次证据并尝试缩小条件；复跑通过不等于修复。
- 不固定照抄历史版本、性能数字或本会话测试结果；每次基于当前 HEAD 和实际运行给结论。

## 固定分支交付流程

本仓库固定交付分支为 `fix/core-game-server-review`。学习与 review 提出的问题证据、已授权修复、回归、必要文档及 feature 方案统一累积到这个分支；不同问题用独立提交区分，便于逐项审阅与合入。不再为每个问题或每轮工作创建分支。用户修改分支约定时同步更新本节。

不创建或建议 issue/PR，不把 GitHub API 配置作为交付前提；不自动合并到主分支、不发布。纯学习或只读 review 不为推送而制造改动，尚未复现的猜测和已接受的设计取舍不能冒充缺陷。

- 每轮先确认 origin、工作区、固定分支与 `origin/main`。读取主分支新增修复，沿实际调用链和关键回归验证；不能只凭提交标题或文本相似认定问题已解决。主分支的新契约与维护者明确决定优先，不用旧补丁覆盖合理的新实现。
- 固定分支首次建立时，从已核对的最新 `origin/main` 创建。固定分支已存在时继续使用它，在干净工作区用快进或普通 merge 同步 `origin/main`，保留已有审查提交；解决冲突后运行受影响回归。不要为同步而 reset、强推、重建分支或丢弃尚未合入的工作。
- 历史问题已在 main 合理修复时直接沿用，在交付中说明复核结论，不重复搬入旧分支补丁；尚未解决的问题先在当前基线重现，再将必要证据和修复提交到固定分支。不能为汇总历史而无差别合并旧分支。
- 已确认的问题可直接修复并推送，不必逐项请求开工确认。问题证据写清类别、基线、触发条件、期望与实际、源码/日志、复现命令、目标游戏类型的业务影响及规避；维护在相关现行文档中，不每轮新建报告。待验证假设明确标注，未完成修复不写成已解决。
- 新 feature 先交代游戏需求、现有缺口、范围、公开契约、兼容影响和验收标准。没有具体需求时不引入额外架构；重大产品或协议选择先取得明确方向，小范围已授权防护可直接实施。
- 每个问题保留修前失败与修后结果，更新必要文档。按职责组织独立提交，提交说明列出最终行为、实际验证与未覆盖边界，禁止夹带用户无关文件。
- 使用现有 HTTPS Git 认证正常推送 `HEAD:refs/heads/fix/core-game-server-review`，不直接推主分支、不强推、不输出认证值、不因缺少 CLI 登录索取 token。推送后核对远端 SHA，返回固定分支链接、本轮提交与验证结果。
- 推送失败时继续完成独立本地工作并保留提交，明确本地完成和远端实际状态及具体阻塞，不虚报成功。
- 本 skill 的仓内位置为 `.agents/skills/core-game-server/SKILL.md`。修改分支或学习约定时同步维护此文件与云环境使用的副本，不硬编码会过期的提交号、测试数量或功能状态。
