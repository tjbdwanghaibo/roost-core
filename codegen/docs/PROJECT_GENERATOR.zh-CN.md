# Roost 项目生成器使用说明

本文写工程生成：`roost project` 的创建 / 同步 / 升级、`roost.yaml`、Mod 装配、ID、生成工程的配置、构建、部署生成物与文档。各生成器的标记、参数与拒绝规则见[命令与标记参考](CODEGEN_REFERENCE.zh-CN.md)，入口与快速上手见 [README](../README.md)，生成器的实现与不变量见 [Codegen 实现与维护](../../docs/framework/impl/12-codegen.md)。

## 1. 目标

roost-codegen 用一份 roost.yaml 管理项目结构、Service、Wiring Mod、代码生成、基础配置、本地依赖和 CI。业务层只实现 Service、Controller、Entity 等业务逻辑，不负责重复的 App 装配、Mod 生命周期和生成命令维护。

生成器遵循以下边界：

- 带有 Code generated by roost-codegen 的文件由 project sync 管理。
- Service、配置、main.go 等业务可编辑文件只在缺失时创建。
- 新项目先写入同级临时目录，全部生成成功后才原子改名。
- 单个文件使用临时文件、Flush 和 Rename 更新。
- 不生成 .gitkeep；需要保留包时生成有效 doc.go。

## 2. 安装和运行

推荐直接跟随最新 codegen，不需要把 codegen 加进业务 module：

    go run github.com/tjbdwanghaibo/roost-core/codegen/cmd/roost@latest help

也可以安装本地命令：

    go install github.com/tjbdwanghaibo/roost-core/codegen/cmd/roost@latest
    roost help

框架只有 roost-core 一个模块（wiring、skill、框架服务与生成器都是其中的包），`roost.yaml` 只有 `versions.core` 一个版本策略，新项目默认为 `latest`。Go module 的 `require` 不接受 `latest` 查询值，因此 `project new/sync/deps` 会联网解析最新 release，并把本次解析出的具体版本和校验和写入 `go.mod/go.sum`：策略留在 `roost.yaml`，一次 CI / 发布过程使用同一份可复现依赖图。普通 PR CI 只验证已提交的依赖图；每周 `dependency-update.yml` 才解析 latest、跑完整测试并创建升级 PR。

内置帮助（`roost help <能力>`、`roost <command> --help`）的专题清单见[参考 §0](CODEGEN_REFERENCE.zh-CN.md#0-内置帮助系统)。

生成项目 Makefile 的更新指令：

```bash
make project-upgrade # 使用 @latest codegen 升级工程模板
make deps-update  # 只解析 roost-core 一个框架模块
make roost-up     # GOWORK=off go get -u ./...，然后 GOWORK=off go mod tidy
make codegen-up   # go install github.com/tjbdwanghaibo/roost-core/codegen/cmd/roost@latest
```

`project-upgrade` 使用最新生成器更新全部受控工程模板，并把 `versions.core` 设为 `latest`。`roost-up` 更新完整项目依赖图，适合主动升级窗口；更新后必须检查 `go.mod/go.sum` 并执行 `make ci`。`codegen-up` 更新 GOPATH/GOBIN 中安装的 CLI，不修改业务 module。

### 纯新手第一次使用

默认项目启用的基础设施较完整。第一次只想理解目录和生成流程时，建议显式选择
`configdata`，避免一开始就要求 MongoDB、Redis、NATS 和 etcd：

    roost project new hello_roost \
      -module example.com/hello_roost \
      -mods configdata \
      -features protocol,config,entity,nest,dao,errcode
    cd hello_roost
    make deps-update
    roost project next

新项目随附的使用文档见 [§18](#18-生成项目里的文档)，先读 `docs/QUICKSTART.zh-CN.md`。

初学者最容易混淆的是：Service 是进程入口，Mod 是运行时基础设施，Feature 是生成期开关，
带生成标识的文件不能手改。生成器负责重复接线，不会生成完整玩法和权限规则。

### Windows 安装与 PATH

在 roost-core 仓库的 `codegen/` 目录下（脚本按当前目录 `go install ./cmd/roost`）可以运行可重复执行的安装脚本。脚本读取当前
`GOBIN`/`GOPATH`，保留它们和现有用户 PATH，只追加 `go install` 实际使用的
Go bin 目录：

    powershell -ExecutionPolicy Bypass -File .\scripts\install-windows.ps1

手工配置的等价步骤如下：

    $goBin = (go env GOBIN).Trim()
    if (-not $goBin) {
        $goPath = ((go env GOPATH).Trim() -split [IO.Path]::PathSeparator)[0]
        $goBin = Join-Path $goPath "bin"
    }
    $userPath = [Environment]::GetEnvironmentVariable("Path", "User")
    $entries = @($userPath -split ";" | Where-Object { -not [string]::IsNullOrWhiteSpace($_) })
    if (-not ($entries | Where-Object { $_.Trim().TrimEnd("\") -ieq $goBin.TrimEnd("\") })) {
        [Environment]::SetEnvironmentVariable("Path", (($entries + $goBin) -join ";"), "User")
    }

例如当前 `GOPATH` 为 `D:\Program Files\Go\bin` 且 `GOBIN` 为空时，需要加入
PATH 的目录就是 `D:\Program Files\Go\bin\bin`。关闭并重新打开 PowerShell 后执行：

    go install github.com/tjbdwanghaibo/roost-core/codegen/cmd/roost@latest
    Get-Command roost
    roost help

如果安装成功但找不到命令，先检查：

    go env GOBIN GOPATH
    $goBin = go env GOBIN
    if (-not $goBin) { $goBin = Join-Path (go env GOPATH) "bin" }
    Get-ChildItem $goBin -Filter roost.exe
    $env:Path -split ";"

用户 PATH 修改后，已经打开的 PowerShell 不会自动刷新。可以重新打开终端，或只在当前窗口临时执行：

    $goBin = (go env GOBIN).Trim()
    if (-not $goBin) { $goBin = Join-Path (((go env GOPATH).Trim() -split [IO.Path]::PathSeparator)[0]) "bin" }
    $env:Path += ";$goBin"

## 3. 创建项目

最小命令（module 必填，避免误用框架作者的仓库命名空间）：

    roost project new planet -module github.com/your-account/planet

指定 module、服务和能力：

    roost project new planet \
      -module github.com/acme/planet \
      -services game,gate \
      -mods configdata,etcd,redis,mongo,nats,syncbus,remote_entity \
      -features protocol,config,entity,nest,dao,errcode \
      -out D:/work/planet

features 与 mods 的合法取值见第 4 节"features 完整清单"与第 5 节的 Mod 表。

默认无需传版本参数，生成项目会跟随最新版本。若要提高某个模块的最低版本，可传明确版本；它不得低于 codegen 的兼容下限：

    roost project new planet \
      -module github.com/acme/planet \
      -roost-core-version v1.25.0

生成器随 roost-core 发布，Makefile 按 `versions.core` 运行它；没有单独的 codegen 版本。

默认生成：

    planet/
      roost.yaml
      main.go
      Makefile
      Dockerfile
      internal/bootstrap/generated.go
      internal/service/game/service.go      # package game
      configs/service/
      configs/schema/
      configs/generated/
      configs/data/
      protocol/def/
      game/
      db/def/
      deploy/dev/docker-compose.yaml
      .github/workflows/ci.yml

`internal/service/<name>/` 的 Go 包名按 Go 惯例小写：服务名去掉 `_` / `-` 后全小写（`world_boss` → `worldboss`），
是 Go 关键字时加后缀 `service`。已有工程沿用目录里现有的包名（以业务文件 service.go / managers.go /
collaborators.go 为准），生成器重写 `framework_clients_gen.go` 时跟随它，不改写业务文件；早先生成的
`package Game` 工程因此保持大写、仍可编译，想改成小写时手工改该目录全部文件的 package 子句即可。

## 4. roost.yaml

新项目内的 `docs/ROOST_YAML.zh-CN.md` 是随 codegen 版本生成的字段级权威说明。
下面给出仓库级总览；未知字段会在严格 YAML 解码阶段直接报错。

示例：

    schema: 1
    project:
      name: planet
      module: github.com/acme/planet
    versions:
      core: latest
    shared_mods:
      - lock
      - ops
      - statslog
    services:
      game:
        mods:
          - configdata
          - etcd
          - redis
          - mongo
          - nats
          - syncbus
          - remote_entity
      gate:
        mods:
          - etcd
    features:
      - protocol
      - config
      - entity
      - nest
      - dao
      - errcode

顶层和嵌套字段：

| 字段 | 是否必需 | 含义与约束 |
| --- | --- | --- |
| `schema` | 是 | roost.yaml 格式版本；当前必须为 `1` |
| `project.name` | 是 | 应用名；小写字母开头，只允许小写字母、数字和下划线 |
| `project.module` | 是 | 生成代码使用的 Go module import path |
| `versions.core` | 是 | roost-core 的 `latest` 策略或明确最低版本 |
| `versions.kit` / `versions.skill` / `versions.service` / `versions.codegen` | 否 | 已退役、不再解码：写了会在加载时（普通加载与 `roost project upgrade` 一致）报 `versions.<key> (...) is retired and no longer read`，需手工删掉；wiring、skill、框架服务与生成器都跟随 `versions.core` |
| `shared_mods` | 否 | 进程级共享 Mod；每个 Service 不得重复声明 |
| `services` | 是 | Service 名到配置的 map；至少一个 Service |
| `services.<name>.mods` | 否 | 该 Service 装配的 Wiring Mod，依赖会自动展开 |
| `access.player.service` | 否 | 玩家协议接入层所属 Service；用 add access 创建 |
| `access.player.transports` | 否 | 显式启用的客户端传输；当前支持 tcp，用 add transport 创建 |
| `access.player.self_sync` | 否 | 默认 false。true 时每个在线玩家经 Entity Sync 收到自己的 Player 状态（视图 `self`）：bootstrap 改用 `NewModWithEntitySync` 并装 `wiring/selfsync`，TCP Mod 加 `WithSelfSync`，缺失时创建一次 `protocol/def/self_sync.go`。需要 tcp 传输与 entity feature；Player 标记缺省按 `sync=true`；没写 `subjectPacker=` 时生成 `game/entities/player/player_sync_packer_gen.go`（视图 `self` 包含 DAO 全部 sync 字段，标了 sync 的字段默认全部对玩家本人可见；写了 `subjectPacker=` 时用业务的 packer、删掉生成的那份），`project sync` / `generate` / `doctor` 检查并给出改法，DAO 没有 sync 字段时 doctor 警告。见 [PLAYER-ACCESS §7](../../docs/framework/PLAYER-ACCESS.md#7-玩家看自己的状态self_sync) |
| `services.<name>.rpcs` / `uses_rpcs` | 否 | 本工程跨进程服务的拥有者 / 调用方；用 `roost add rpc` 创建，见 §6 |
| `services.<name>.port_block` | 是（生成器写） | 端口块号 0～99、各服务不同，一经分配不再改变；开发配置的按服务端口由它派生（ops `9100+N`、`etcd.advertise_addr` `9000+N`），见 §5“端口块”。手改加服务时不写，`roost project sync` 分配 |
| `features` | 否 | 生成目录、生成器和 bootstrap 接线的项目级开关 |
| `sagas` | 否 | `roost add saga` 已生成的 Saga 名称；不要只手工添加 |
| `ids` | 否 | protocol/entity/component/errcode 的编号空间 |
| `ids.<kind>.min/max` | 视类型 | 普通编号空间的闭区间，必须 `min > 0` 且 `max >= min` |
| `ids.protocol.groups.<name>.min/max` | 否 | Protocol 按业务组划分的独立闭区间 |

底层编码上限会 fail-fast：EntityKind 为 1..255，ComponentType 最大 65535，Protocol 消息 ID
最大 4294967295。不要沿用旧脚手架曾给出的 Entity 1000..1999 区间；它无法转换为 core 的 uint8 EntityKind。

`versions.*: latest` 保存在 roost.yaml 中作为持续更新策略；Go 不允许在 require 中写
`latest`，所以 go.mod/go.sum 保存一次解析出的具体版本。`features` 与 `mods` 是两个维度：
前者决定生成什么，后者决定服务运行时启动什么。

修改清单后执行 `make sync` 与 `make doctor`（sync 的暂存与提交语义见 [§13](#13-doctordiff-和升级)）。

**已退役的写法**（项目未上线，生成器不读取、不迁移，加载或生成时点名拒绝并给出手工改法）：

| 旧写法 | 现在 |
| --- | --- |
| `versions.kit / skill / service / codegen` | 删除这些行，只留 `versions.core` |
| mod 名 `sync` / `room` | `syncbus` |
| feature `replication-quic / -kcp / -udp` | `nettransport-quic / -kcp / -udp` |
| feature `event`（实体事件链与 eventgen 已删除） | 从 `features` 删除；同时删掉工程里遗留的 `framework/event/`、`*_event_gen.go` 与 `DealEventXxx` / `SubEvent` 调用 |
| 源码标记 `//cube:` | `//roost:`（`roost generate` 在运行任何生成器之前失败并列出文件） |
| cfggen meta 的 `objects:` | `globals:` |
| tablegen v1 `_manifest.json` | 删除 v1 manifest 与旧生成器留下、meta 已不存在的 JSON，再生成（见[参考 §9.1](CODEGEN_REFERENCE.zh-CN.md#91-_manifestjson-与-json-退役)） |

旧格式的 `shutdown:` 块、旧部署模板的宽限期写法与 `deploy/k8s/` 顶层旧 base 文件按应用文件对待，sync 不改写也不删除，请人工删除或按当前模板重新生成。合仓前的工程（仍 require roost-skill / roost-service / roost-kit / roost-codegen 或 import 旧包路径）没有自动迁移工具。

### features 完整清单

features 是项目级**代码生成开关**，与 mods 是两个维度：features 决定"生成哪些目录骨架、`make generate` 跑哪些生成器、bootstrap 里接什么线"（编译期形态）；mods 决定"进程运行时装配哪些 Wiring Mod"。未知 feature 在加载 roost.yaml 时直接报错。

| feature | 脚手架目录 | 驱动的生成器 / bootstrap 接线 |
| --- | --- | --- |
| `protocol` ✦ | `protocol/def/` | protocol 生成器（消息注册、bind、handlers、robot-protocol） |
| `config` ✦ | `configs/schema/`、`configs/table_template/`、`configs/generated/`、`configs/data/`（含 `_manifest.json`） | tablegen 三连：`config-template`（meta → CSV 模板）、`config-data`（CSV → JSON）、`config-go`（meta → struct + 注册 + 类型化访问器）；与 `configdata` mod 同时存在时 bootstrap 自动调 `RegisterGeneratedConfigData` |
| `entity` ✦ | `game/entities/` | entity 生成器（`-dir ./game`） |
| `nest` ✦ | `game/handler/`、`game/bootstrap/register.go` | nest 生成器；bootstrap 里插入 `gamebootstrap.RegisterNestHandlers()` |
| `dao` ✦ | `db/def/`、`db/` | dao 生成器 |
| `errcode` ✦ | — | errcode 扫描器，产出 `docs/generated/errcode.csv` |
| `attribute` | `game/gameplay/attribute/` | attribute 生成器 |
| `webroute` | `service/web/` | webroute 生成器（`-dir ./service`） |
| `rpc` | `internal/rpc/<name>/` | 由 `roost add rpc` **自动追加**；servicerpc 生成两半（见 §6） |
| `saga` | — | 无独立生成器——由 `make new-saga`（`roost add saga`）**自动追加**的标记；saga 骨架由 add 命令生成，bootstrap 聚合各 `Definitions()`。要求至少一个 Service 挂 `saga` mod |
| `nettransport-quic` / `nettransport-kcp` / `nettransport-udp` | `internal/transport/generated.go` | 生成 `NewQUIC()` / `NewKCP()` / `NewUDP()`（AsyncTransport 组装）与 `NewSyncTransport`（把 AsyncTransport 包成 Entity Sync 传输，见第 16 节）；三者可并选 |

✦ = `roost project new` 不传 `-features` 时的默认六项：`protocol, config, entity, nest, dao, errcode`。

这些 feature 都由 roost-core 提供，版本门槛即 `versions.core` 的兼容下限（当前 v1.25.0）；低于下限的明确版本在 manifest 校验阶段被拒绝。

## 5. Wiring Mod 自动装配

支持的 Mod（`->` 后为自动补齐的依赖，声明时无需手写）：

| mod | 自动依赖 | 说明 |
| --- | --- | --- |
| `lock` | — | 进程内实体锁管理 |
| `ops` | — | health、ready、metrics 和 admin HTTP |
| `statslog` | — | 运行时、Entity 和 Nest 周期统计 |
| `configdata` | — | 不可变配置快照加载和热更（与 `config` feature 配合成完整配置管线）；自带运维命令 `configdata.reload` / `configdata.rollback` / `configdata.status`（经 ops `/admin/execute`） |
| `etcd` | — | 注册发现、watch、选主和本地镜像 |
| `redis` | — | Redis、pipeline、pub/sub（单实例锁后端 `kitredis.SingletonStore` 与之共用 `redis.*` 配置） |
| `mongo` | — | Mongo client、collection、session 和索引策略 |
| `nats` | — | NATS、JetStream、RPC 和 Bus |
| `syncbus` | `nats` | NATS 或 JetStream 同步 Bus（运行期缺省前缀 `roost.sync`；生成配置写 `<project>.sync`） |
| `remote_entity` | `redis`、`mongo`、`syncbus` | 跨服实体所有权、原子事务、快照分发与版本锁 |
| `dataengine` | `mongo`、`nats` | Nest transaction WAL、Mongo projection、聚合加载/migration、effect outbox |
| `manager` | — | 本服务的内存单例 manager 生命周期 |
| `nest` | `dataengine`（自动补齐） | 实例级 Nest 引擎装配 |
| `saga` | `mongo`、`nats`，并自动补齐 `dataengine` | saga 引擎与 Data Engine start effect |

默认值：`shared_mods = lock, ops, statslog`；`roost project new` 不传 `-mods` 时每个 Service 默认 `configdata, etcd, redis, mongo, nats, syncbus, remote_entity, dataengine, nest, manager`（即除 `saga` 外全量）。约束：Service 的 mods 不得与 shared_mods 重复（校验期拒绝）；依赖由生成器拓扑展开并检测环，未知 Mod 报 `unknown wiring mod`。

**共享资源的名字按工程名派生**（新用户试用第四轮登记项 1）：生成配置里决定“与谁共享”的键不再是所有工程共用的固定值，两个工程共用一套开发用 Mongo / NATS / etcd 时不撞库撞流。以工程 `planet` 为例：

| 键 | 生成值 | 运行期缺省（不写这个键时） |
| --- | --- | --- |
| `nats.prefix` | `planet` | `roost` |
| `syncbus.prefix`（流名由它推出） | `planet.sync`（流 `PLANET_SYNC`） | `roost.sync` |
| `dataengine.database` | `planet` | `game` |
| `dataengine.databases`（DAO 逻辑库 → 物理库，D9 修订版 A） | `{main: planet}`：骨架 DAO 写逻辑库 `db=main`，物理库按工程名派生 | `{}`：没有映射的逻辑库物理名就是逻辑名本身 |
| `dataengine.effects.subject_prefix` / `stream` | `planet.effect` / `PLANET_EFFECTS` | `roost.effect` / `ROOST_EFFECTS` |
| `saga.database` | `planet_saga` | `saga` |
| `saga.subject_prefix` / `stream` | `planet.saga` / `PLANET_SAGA` | `roost.saga` / `ROOST_SAGA` |
| `saga.start_effect_prefix` / `start_effect_stream` | 不写：取 `dataengine.effects.subject_prefix` / `stream`（效果流只配一处） | 同左 |
| `remote_entity.mongo.database` | `planet_remote` | `remote_entity` |
| `etcd.service_prefix` | `/planet/services/` | etcd 包的缺省 |

规则写在各 Wiring Mod 配置声明的 `example` 里（`{project}` 工程名、`{PROJECT}` 大写、`{project_db}` 库名：系统库 `admin` / `local` / `config` 加 `_data`、截到 52 字节），新建与之后 `roost add mod` / `add saga` / `add access` 追加的段同一规则（`codegen/internal/roost/catalog.go` 的 `projectNameVars`）。只影响生成器写出的配置，Mod 的运行期缺省值不变；同一工程的所有服务按同一工程名得到同一组值。已有工程的配置归业务、不改写：旧工程仍是 `roost` / `game` / `ROOST_*`，而此后追加的段会写新名字，与已有段不一致时手工统一（升级说明见 CHANGELOG）。

**按服务区分的端口：端口块**（维护者 2026-10-19 决定）。开发配置集的服务在同一台机器上一起运行（`deploy/dev/run.sh`），每个服务要有自己的 ops 端口与 `etcd.advertise_addr`。每个服务在 `roost.yaml` 里有一个端口块号 `services.<name>.port_block`（0～99），由生成器分配并写入，**一经分配不再改变**：

- 新建工程：按“业务服务在前、托管框架服务在后，各自按名字排序”依次分配 0、1、2……（game-demo：game 0，account 1，activity 2 … session 9）；
- 之后新增的服务（`add service`、命令或模板带进来的托管服务）取“当前最大块号 + 1”，几个同时新增时按上面的顺序；已有服务的块号与端口不受影响；
- 手改 `roost.yaml` 加服务时不写块号：其他命令报错并给出下一个空闲块号，`roost project sync` 自动分配并写回；
- 删除服务不回收块号；只有删掉的恰好是最大块号时，下一个新服务会拿到同一个号（删服务时一并删掉它的配置文件）。
- 块号重复或超出 0～99 时加载失败。

所有按服务区分的端口只从块号 N 派生（`codegen/internal/roost/port_blocks.go` 的 `portsFor`，规则只此一处），四段互不重叠：

| 端口 | 开发配置 | 生产示例 / k8s Secret 示例 |
| --- | --- | --- |
| `ops.addr` | `127.0.0.1:9100+N`（9100–9199） | `0.0.0.0:9100` |
| `etcd.advertise_addr`（写进服务注册、别的进程据此连接本服务；各服务必须不同） | `127.0.0.1:9000+N`（9000–9099；game-demo：game 9000、activity 9002、match 9006） | `CHANGE_ME:9000`（填这个容器自己的可达地址） |
| `deploy/dev/second-game.sh` 第二个 game 的 ops | `9200+N`（9200–9299） | — |
| 第二个 game 的 `etcd.advertise_addr` | `8900+N`（8900–8999） | — |

第二个 game 改用独立的两段端口：改用块号之前它用“第一个 + 10”，工程有 11 个以上服务时会撞上别的服务。玩家 TCP（7000，第二个 game 7001）与 web（8080）各只有一个服务持有，不按服务派生。新建工程、之后 `add mod` 追加的段、doctor `config-sections` 的补段提示都经 `localizeDevConfig` 写入本服务的端口。配置归应用、可以手改：`roost config check --all` 与 doctor `config-across-services` 在开发配置的 `ops.addr` / `etcd.advertise_addr` 端口与块号派生值不一致时给 WARN（不影响退出码；`run.sh` 与 `second-game.sh` 按块号走），端口冲突与 advertise 重复才是失败。

**按 sid 区分的本地状态：WAL 目录**（2026-10-20 修复）。开发配置不写 `dataengine.wal.dir`，运行期取工作目录下的 `data/wal/dataengine/<sid>`，同一工作目录、同一份配置用 `--sid` 起的几个进程各用各的目录（WAL 对目录加独占锁，共用目录的第二个进程启动时报 `nestwal: directory is already locked` 退出）。以前开发配置显式写了不带 sid 的 `data/wal/dataengine`，绕过了这条缺省；已有工程删掉这一行即可（目录里未投影的记录先排空，见 [PLAYER-MIGRATION](../../docs/framework/PLAYER-MIGRATION.md)）。生产示例与 k8s Secret 示例由 `productionizeConfig` 写 `dir: /var/lib/roost/wal`：生产每个实例一个容器 / Pod / systemd 单元，WAL 落在只挂给这个实例的持久卷上。`second-game.sh` 只在配置手写了 `…/wal/dataengine` 时把它改成 `…/wal/dataengine-<sid>`。

Core 会根据 DependsOn 排序生命周期。生成器负责补齐必需依赖，不复制 Wiring 内部的连接、重试、health 或 shutdown 逻辑。

增加 Service：

    roost add service chat -mods etcd,redis,mongo,nats

给已有 Service 增加 Mod：

    roost add mod syncbus -service chat

## 6. 日常业务脚手架

`roost add` 的全部种类、参数和例子见[参考 §3](CODEGEN_REFERENCE.zh-CN.md#3-业务骨架roost-add)；推荐顺序见 [README 第一条业务](../README.md#3-第一条业务)，每完成一步运行 `roost project next`。下面只写会改动工程装配的几类。

TCP 生成层的帧格式、鉴权、主动推送、配置硬上限和上线门禁见
[Player TCP 接入](PLAYER_ACCESS_TCP.zh-CN.md)。

Saga 命令会自动给目标 Service 添加 `saga`、`dataengine` 及其传递依赖，并生成
`saga/alliance_rally/definition.go`（类型、步骤、补偿 topic 常量、`Register`、`EmitStart` 和幂等
`Start` 入口）与 `saga/alliance_rally/steps.go`（步骤运行时）。业务 Nest handler 必须调用
`EmitStart`，使 Entity mutation 与 Saga 启动意图进入同一个 WAL record；`Start` 仅用于
durable consumer、管理和恢复路径。生成的 bootstrap 会把 manifest 中的
定义传给 Saga Mod；自定义装配时才需要调用 `Register`。

步骤消费者只有一种写法：`steps.go` 的 `RegisterSteps` 按主题常量把每一步登记到
`wiring/saga` 的 `Steps`（`-native` 列出的步骤用 `Steps.Native`，其余 `Steps.Mongo`），
`StartSteps(ctx, registry, deps)` 建 `Steps`（group 即 durable 前缀 `<service>-<saga>`，同一逻辑服务的
多个副本共享，不同 saga 不复用）并启动；服务 Init 里调用它、Shutdown 里 `Drain(ctx)`，生成器不改写
服务（doctor 的 `saga-steps:<saga>` 在没人启动时 WARN）。`-native` 的步骤各生成正向与补偿两个
Nest handler（参数 `saga.NativeStep`，事务内 `step.Complete`）；幂等键是 command 的
`IdempotencyKey`：原生步骤由收件箱保证至多一次生效，Mongo 步骤里事务外的调用要用它做幂等，不要以
投递次数或 `CommandID` 作为业务幂等键。`Subscribe<Step>` 辅助函数已不再生成（2026-10-18，D12 方向 B）；
按 sid 绑定实体的多进程部署要给原生步骤补 `WithAdmit` 准入（单进程原生步骤 saga 正向约 8/s、
全补偿约 5/s 以内 P50 在 1 秒内，P99 不稳定（2026-10-20 各 15 分钟实测 0.9～3.9 s），WAL 宜放快盘；
正向 10/s 仍全部正确但延迟升到秒级，正向 12/s、全补偿 7/s 起重试放大而崩溃，见 `roost help saga`）。

`roost add effect <topic> -consumer <service>` 生成 effect 的载荷、`Emit<Topic>` 辅助
（`game/effects`）与消费服务里的 `kitdataengine.SubscribeEffects` 骨架，不改 roost.yaml；
消费服务要有 dataengine Mod。

每个骨架还会生成 `Definitions()`。修改步骤顺序或补偿语义时递增 `Version`，把旧定义
保留在 `Definitions()` 中；bootstrap 会注册全部仍在运行的版本。通过
`Engine.List` 确认旧版本已无非终态记录后，才能删除旧定义。

生成配置把 coordinator/publisher 的 claim batch 分开，并限制 `max_ack_pending`、
Mongo 操作时间、NAK 指数退避和 stream 最大磁盘占用。生产集群应把 Saga 与 Nest
effect stream 的 `replicas` 调整为 3；`start_effect_durable` 在同一 NATS domain 内必须
按应用唯一、在同一应用的所有 coordinator 副本间保持一致。扩容优先增加固定 worker，
修改 batch/timeout 时必须满足生成器文档中的 lease 预算并重新压测。

protocol、entity、component 默认从 roost.yaml 的 ID 空间分配下一个空闲 ID，也可以使用 -id 显式指定。

## 13. Doctor、Diff 和升级

    roost project doctor                            # 含生成物新鲜度检查
    roost project doctor -strict=false              # 只检查结构、版本和配置
    roost project doctor -json                      # CI / 平台读取 JSON
    roost project doctor --workflow first-business  # 检查首条业务链并给出修复命令
    roost project next [--workflow player-tcp]      # 按真实进度只显示一个当前动作
    roost project diff                              # 预览 sync 将改写的模板与配置 shutdown: 块（不含生成器输出）
    roost project deps                              # 只重新解析框架依赖

**sync / deps / generate 的提交语义**：先把项目复制到同级临时目录，在其中完成模板渲染、全部生成器与 `GOWORK=off go mod tidy`；所有权冲突或任一步失败都不写回项目，不留下半生成工程。提交阶段逐文件原子替换，后续失败回滚已写内容；若开发者或另一生成器进程在提交窗口修改了目标文件或业务输入，命令拒绝覆盖并保留新内容。依赖解析只解析 roost-core 一个模块，只提交最终 `go.mod/go.sum`，不回写依赖命令对其他业务文件的改动；`roost generate` 只整理当前依赖、不升级框架，所以新增 DAO / Protocol 等 import 后不需要手工 `go get`。逐文件回滚不能替代进程强杀 / 磁盘故障验证。`make sync` 同步模板后自动执行同样的依赖解析，CI 在测试和构建镜像前运行 `make deps-update`。

**升级到当前工程模板**（旧 Makefile 尚无 `project-upgrade` 时）：

    go run github.com/tjbdwanghaibo/roost-core/codegen/cmd/roost@latest project upgrade --root . --dry-run -core latest
    go run github.com/tjbdwanghaibo/roost-core/codegen/cmd/roost@latest project upgrade --root . -core latest

之后直接用 `make project-upgrade`，它始终通过 `@latest` 运行。升级幂等，只覆盖带 `Code generated by roost-codegen` 标识的受控文件；自定义 Makefile 报冲突并保持原样，业务代码与业务配置保留。声明更高的最低版本用 `roost project upgrade -core vX.Y.Z`（不得低于生成器兼容下限）；`versions.core` 的明确版本是 Go MVS 下限而不是上限，其他直接依赖要求更高版本时最终解析结果更高。生成器（Makefile 里的 `$(ROOST)`）按 `versions.core` 运行，可用 `make generate CORE_VERSION=vX.Y.Z` 单次覆盖。

**配置声明检查**：每个服务配置里的框架段（ops、redis、dataengine、saga、框架服务的 key_prefix…）由 Wiring Mod 自己的配置声明生成——声明里标了 `example` 的键写入配置，键上方的注释来自声明的 `help`；生成的 player TCP 接入层与 RPC 客户端 Mod 也带声明，`add transport tcp` 补的键来自同一份声明。业务服务与 Mod 一样实现 `ConfigSchema()`，用 `app.SchemaOf` + `app.LoadConfig` 读自己的键。doctor 的相关检查：

- `config-schema:<service>`：工程能编译时 `go build` 一次进程，对每个服务运行 `<bin> <service> --print-config-schema` 读回全部声明（含业务声明），检查开发配置、生产示例与 k8s Secret 示例——值不合声明、框架段里没有任何声明的键为 FAIL，别的服务的键为 WARN，只属于业务的段里拼错的键为 FAIL。
- `config-sections:<service>`（只读，维护者 2026-10-17 决定）：按服务实际注册的 Mod（共享 Mod 加 `effectiveServiceMods`，与生成器同一份计算）找开发配置、生产示例与 k8s Secret 示例（`stringData` 的 `config.yaml`）里缺的顶层配置段——每个 Mod 的起始段、托管框架服务的段；带 DataEngine 的服务还有 `redis:` 与 `singleton:` 段，且 `singleton.enabled` 须为 `true`。缺段为 WARN（不让 doctor 失败），WARN 里给出可直接追加到该文件末尾的文本（生产示例与 Secret 已按生产改写：地址 `CHANGE_ME`、流副本 3；Secret 已缩进四格）。典型来源：在 `add` 命令之外手改 `roost.yaml` 加 Mod 后 `project sync`（sync 不追加配置段，行为不变），或修复前走过 `add access` / `add rpc` 的工程。业务有意删掉的段同样会报——不需要时忽略；想消掉提示又保持代码默认值，留一个空段（例如 `saga: {}`）。“有没有”只看行首的 `<key>:`，段里的值不比较。doctor 没有另外的豁免开关。
- `config-across-services`（维护者 2026-10-19 批准）：同一工程各服务之间——声明里带 `shared` 的共享资源名（`nats.prefix`、效果流名与主题前缀及 saga 的 start 效果流、saga 库 / 流 / 主题、Remote 库与 L2 前缀、`etcd.service_prefix`、`singleton.key_prefix`、业务时区 `time.business_timezone` / `time.business_day_start` 等）在开发配置集与生产示例里各自必须一致；开发配置集里带 `listen` 的监听地址（`ops.addr`、`web.addr`、`player_access.tcp.addr`，开关打开时）端口不得冲突，带 `unique` 的 `etcd.advertise_addr` 各服务不同。FAIL 并点名服务、键与取值。与 `roost config check --all` 同一个实现（`checkConfigAcrossServices`），不需要编译工程。
- `config-check:<service>`：用同一个编译好的进程对每个服务的开发配置运行 `<bin> <service> --check-config --config configs/service/config.<service>.yaml`（与进程启动前同一处检查）：除键的声明外，还有各 Mod 配置结构体的跨键规则与跨 Mod 一致性规则（`app.ModConfigCrossChecker`，例如同进程有 DataEngine 时显式写的 `saga.start_effect_stream` / `start_effect_prefix` 必须等于 `dataengine.effects.stream` / `subject_prefix`）。不通过为 FAIL，详情是进程的报错与可直接复跑的命令。生产示例与 Secret 示例带占位值，不在这里跑；发布前对真实生产配置运行同一条命令。工程编译不过时不报这一项。
- `remote-runtime`：工程里有 `remote=managed` 实体时，带 Nest 的服务全都没有 `remote_entity` Mod 为 FAIL（运行时每次写都会被拒），只有部分服务缺为 WARN，详情给出 `roost add mod remote_entity -service <service>`；`roost generate` 在跑生成器之前做同一检查（全缺时拒绝，部分缺时打印 WARN）。没有这类实体时不报这一项。
- `saga-steps:<saga>` / `effect-consumer:<service>/<func>`（只读，WARN 不让 doctor 失败）：`roost add saga` 生成的 `steps.go` 有 `StartSteps` / `RegisterSteps`，工程里却没有非测试文件导入该 saga 包并调用它（或调用处所在包没有 `Steps.Drain(ctx)`）时 WARN；`roost add effect` 生成的 `start<Topic>EffectConsumer` 在服务包里没有被调用时 WARN。生成器不改写服务的 Init / Shutdown，这两项提醒“生成了但没启动”——没启动时进程照常起来，步骤命令却等到超时、effect 堆在流里。文本判据（注释不算调用），只说明写了，不证明运行时一定走到；`steps.go` 里没有这两个函数（如 game-demo 手写接线）时不报。
- `skills:catalog`：工程有 `game/skills/catalog.go` 时运行 `go test ./game/skills/`（生成的 `catalog_test.go` 用 `CompileAll` 编译全部技能 JSON），写坏的定义为 FAIL 并带编译器原话；没有 `catalog_test.go` 为 WARN（下一次 `roost add skill` 补上）。工程编译不过时不报这一项。
- `config-reads`：扫工程源码，直接调 viper 读方法 / `app.Config*` 单键读取、或声明了却没有任何代码读的字段为 FAIL（与 app / wiring 的守卫同一份实现 `internal/configschema/guard.go`）。
- `time:logic_offset`：dev / prod example / k8s secret example 三套配置里各服务的业务时钟偏移是否一致。game-demo 的业务时间读 `app.BusinessClock(registry)`（带 `time.logic_offset`），租约、saga 截止、支付时间仍是系统时钟并标 `//glsvet:system-clock`；`cmd/glsvet` 对 `game` 目录下直接读 `time.Now` / `Since` / `Until` 打印 `hint:`，不计入失败。
- `shutdown:<service>`：见 [§17](#17-生产部署生成物)。

进程自己的 `--check-config` 检查真实生产配置的值（含业务 Mod 的声明、跨键与跨 Mod 规则），不报没有声明的键；`roost config check` 先按声明查键，通过后交给编译出的进程跑同一个 `--check-config`（跨键 / 跨 Mod 规则），与 doctor 的 `config-check:<service>` 结论相同；工程编译不过时明确提示跨 Mod 规则没查。框架配置声明在生成器里有一份快照（`codegen/internal/roost/kitconfig_gen.go`），维护方法见 [Codegen 实现与维护](../../docs/framework/impl/12-codegen.md)。

## 14. 生产检查清单

- Makefile 和 CI 默认使用最新 codegen；框架依赖先解析成具体版本，再进入同一次测试和发布构建。
- prod 配置无 localhost、CHANGE_ME 或开发 token。
- `time.business_timezone` / `time.business_day_start` 写成游戏运营的业务时区与每日重置时刻（生成值 UTC / 00:00，各服务相同）：业务日与每日重置按它算，不按容器的 `TZ`；生成的 `main.go` 内嵌 `time/tzdata`，见 [CODEGEN_REFERENCE §14](CODEGEN_REFERENCE.zh-CN.md#14-配置格式和生产门禁)。
- ops admin 默认关闭；开启时使用外部密钥管理。
- etcd advertise address 可被其他节点访问。
- NATS reliable 模式同时启用 Redis。
- QUIC 使用正式证书和固定 ALPN。
- UDP/KCP 接入层配置鉴权、密钥轮换、Cookie、限速和 DDoS 防护。
- 提交前执行 make ci。
- 部署前执行 race 测试和优雅停服演练。
- MongoDB 使用 replica set 或支持 transaction 的 sharded cluster；禁止 standalone。
- `/var/lib/roost/wal` 使用单写持久卷，并验证异常重启后 replay。
- JetStream effect 由 Data Engine Mongo outbox 持久化后发布；consumer receipt TTL 必须大于消息最大保留时间。
- Sync 慢消费者淘汰、断线 session 清理、100 Entity/20 Hz 和 Redis/Mongo/NATS 故障注入均通过 staging 门禁。

## 15. Module path 与发布依赖

生成的 `go.mod` 只 require 一个框架模块 `github.com/tjbdwanghaibo/roost-core`（wiring、skill、框架服务、生成器都是其中的包）。首次离线启动使用当前兼容下限作为合法 bootstrap：

    github.com/tjbdwanghaibo/roost-core v1.25.0

不生成 `replace`。在正常的 `project new/sync/deps` 路径中，上述版本会立即被当前最新 release 替换；具体版本留在 `go.mod/go.sum`，而“继续跟随最新”的策略留在 `roost.yaml`。生成的 `internal/frameworkdeps/generated.go` 通过稳定路径 `github.com/tjbdwanghaibo/roost-core/gameplay/skill` 的类型别名保留暂未被业务导入的 skill，因此 tidy 不会删掉它。若需要离线生成，bootstrap 下限仍可构建；恢复网络后执行 `make deps-update` 即可追到最新。

## 16. 帧同步 Transport 预设

在 features 中启用 nettransport-quic、nettransport-kcp 或 nettransport-udp 后，sync 会生成 internal/transport/generated.go：

- nettransport-quic：QUIC DATAGRAM + Reliable Stream，并包装 AsyncTransport。
- nettransport-kcp：KCP 可靠流 + OOB datagram，并包装 AsyncTransport。
- nettransport-udp：安全 UDP datagram + 外部 ReliableSender 组合。

生成的只是 Transport 装配入口。监听器、TLS、登录票据、会话密钥和 BindSession 仍属于网关接入层，不能用开发默认值代替生产安全配置。

## 17. 生产部署生成物

新项目同时生成三套部署入口：

| 路径 | 用途 | 关键默认值 |
| --- | --- | --- |
| `deploy/shell/` | Linux 物理机/VM | 静态二进制、systemd、非登录用户、只读系统、按服务生成的停机宽限期（`TimeoutStopSec` = 该服务 `shutdown.total_timeout` + 5s）、实例独占 WAL；`WorkingDirectory` 是当前 release，启用 configdata 的服务安装时把 `configs/data` 拷进 release（与镜像布局一致），release 里的 `log` 链接到 `LOG_ROOT`；每个 release 的 unit 记在 `$APP_ROOT/units/<version>.service`，自动回滚与 `rollback.sh` 连同 unit 一起回退；没有记录 unit 的旧 release 在动任何东西之前被拒绝，需停服务、删旧 `current` 与 `releases` 后全新安装，切换时先按正在用的 unit 停机再装入目标 unit 启动 |
| `Dockerfile`、`deploy/docker/` | 容器 | distroless nonroot（镜像不带 zoneinfo，不设 `TZ`：业务时区来自 `time.business_timezone`，生成的 `main.go` 内嵌 `time/tzdata`）、不包含环境配置与密钥（启用 configdata 时数据表 `configs/data` 随镜像放在 `/app/configs/data`，与相对的 `config_data.dir` 一致）、只读根文件系统运行示例（相对的 `stats_log.dir: log` 即 `/app/log` 挂可写卷：镜像里是属于 65532 的空目录，compose 每服务一个 `<app>-<service>-log` 命名卷，k8s 挂 `stats-log` emptyDir，systemd 链接到 `LOG_ROOT`）、版本 ldflags |
| `deploy/k8s/` | Kubernetes/Kustomize | Secret 挂载、探针、资源预算、PDB、安全上下文；Data Engine 使用 StatefulSet+RWO PVC |

停机时长按服务生成：每个服务的 `shutdown.total_timeout` = 声明停机预算之和（dataengine 的
`dataengine.shutdown_timeout`，生成值 30s；托管 player TCP 接入的服务另加生成的 TCP Mod 声明的 `player_access.tcp.shutdown_timeout`，生成值 10s）+ 3s × 其余 Mod 数（App 给未声明预算 Mod 的固定保底）+ 5s（Service.Shutdown 与之共用同一时限）+ 3s（生成配置打开 `singleton.enabled` 的服务，即带 dataengine 的服务：App 单实例锁在 Mod 停完后 Release，Mod 停机截止时间为此提前 3s），
Mod 数按该服务 bootstrap 实际注册的 Mod 计（共享 Mod、Wiring Mod、框架 ClientMod / owner Mod、rpc Mod、player access Mod）；
只有生成器 Manifest 已知的 Mod 计入：应用手写、在 bootstrap 里自行注册的 Mod 即使实现 `app.ModStopBudgetProvider.StopBudget`，其声明值也不进公式，`roost project doctor` 同样不检查它，
需要时手工调大该服务的 `shutdown.total_timeout` 与下面各处宽限期；
k8s `terminationGracePeriodSeconds`、compose `stop_grace_period`、systemd `TimeoutStopSec`、`deploy/dev/run.sh` / `second-game.sh` 的
`kill -9` 前等待均为 `max(公式值, 该服务配置里实际生效的 total_timeout) + 5s`（读 `config.<svc>.yaml`、`.prod.example.yaml` 与 k8s secret 示例，
缺键按 App 兜底 30s），即永远不低于配置 total + 5s。game-demo 新工程：缺省 Mod 集的 game 服务 26 个 Mod → 120s / 125s（`-mods configdata,mongo,nats,dataengine,nest` 时 25 个 → 117s / 122s；含合服启动自检 `svcaccount.NewServingGuardMod()`）；每个框架服务 6 个 Mod → 23s / 28s。
配置是应用自有的：`roost project sync`（含 `add mod` / `add saga` / `add access` 等）只在 `shutdown:` 段仍是生成器原样时随 Mod 变化改写它，
改过的段或旧版生成器写的段保持不动，宽限期跟随它们的值。配置段的改写在渲染模板之前、与模板同一次提交（同受回滚与并发输入检查保护），
增减 Mod 后一次 sync 即收敛、`roost project diff` 为空。`roost project doctor` 的 `shutdown:<service>`：磁盘上的部署模板宽限期低于配置
total + 5s 为 FAIL（未 sync 或手改模板，会被 SIGKILL）；三份配置逐份判定，任一份的 total 覆盖不了 Mod 保底即 WARN 并指明文件，
`Set it to` 的建议值按该份配置里实际的 `dataengine.shutdown_timeout` 计算（各份不同时逐文件给出），0 或负的时长按运行时的 30s 兜底判定；
示例配置解析失败或时长非法时 WARN 只指明文件与键，不附 `Set it to` 建议（dev 配置时长非法为 FAIL）；
OK / WARN 行显示磁盘上部署模板的实际宽限期；配置里 `singleton.enabled: true` 时所需合计另加 3s。

App 单实例锁（[方案](https://github.com/tjbdwanghaibo/roost-core/blob/9d955fb0df35f082dfc9be24c2f3a4524d437067/docs/feature/APP-SINGLETON-LOCK-2026-10-05.md) §6.3）：项目里有 `redis` Mod 或带 `dataengine` 的服务时，bootstrap 生成 `a.Singleton(kitredis.SingletonStore)`；带 `dataengine` 的服务配置写 `singleton.enabled: true`（`key_prefix: roost:<project>:singleton`、15s / 3s / 5s / 30s），没有 `redis:` 段时只补配置段（开发 compose 随之带 redis），其他服务写同一段的 `enabled: false`；`add mod` / `add saga` / `add access` 之后才带上 dataengine 的服务把未改过的 `enabled: false` 段翻成 `true`（改过的段保持并 WARN）。服务因 `add mod`、`add saga`、`add access`（带入 nest → dataengine / mongo / nats）、`add rpc`（拥有者带入 nats）多出的 Mod，配置段追加进该服务的 dev / prod 示例配置与 k8s Secret 示例，只追加文件里还没有的顶层段、已有的值不动；在这些命令之外手改 roost.yaml 再 `project sync` 不追加，`roost project doctor` 的 `config-sections:<service>` 以 WARN 列出缺的段与要追加的文本（[§13](#13-doctordiff-和升级)），不改文件。启用的服务部署侧的启动等待覆盖 `singleton.startup_wait`：k8s `startupProbe` 为 `startup_wait + 30s`（默认 60s），shell 的 `HEALTH_ATTEMPTS` 默认 `startup_wait + dataengine.startup_timeout` 次（60，其他服务 30），compose `start_period` 60s（其他服务 30s）。

新项目还会生成 `.github/workflows/ci.yml`、`dependency-update.yml`、`release.yml`、`deploy-shell.yml`、`deploy-docker.yml`、`deploy-k8s.yml` 和 `security.yml`。普通 CI 使用已经提交的 `go.mod/go.sum`，不会执行 `deps-update` 或 `go get -u`；追踪最新框架由独立依赖升级流水线完成并创建 PR。Release 构建一次不可变二进制包和 OCI 镜像，Shell 使用版本包，Docker 与 Kubernetes 使用同一个镜像 digest。

本地交付检查和三种部署入口：

```bash
make cicd-check
make release-check VERSION=v1.2.0
make deploy-shell SERVICE=game SID=1000 VERSION=v1.2.0 CONFIG=/etc/roost/game.yaml
make deploy-docker IMAGE=ghcr.io/example/planet@sha256:<digest> ENV_FILE=/etc/roost/planet.env
make deploy-k8s ENV=staging IMAGE=ghcr.io/example/planet@sha256:<digest>
```

Shell 和 Docker 生产部署默认使用带 `roost-shell`、`roost-docker` 标签的 self-hosted runner；Kubernetes 使用带 `roost-k8s` 标签且具有目标集群最小 RBAC 的 runner。请在仓库设置中创建 `staging` 和 `production` Environment，并为 production 配置审批。生产 Secret、SSH 凭据、kubeconfig 和配置文件不得写入 `roost.yaml` 或仓库。

生成器不会把 `secret.<service>.example.yaml` 加入 kustomization，也不会覆盖本地 Secret。部署前复制为 `.local.yaml`、替换所有 `CHANGE_ME`，单独 apply。生产镜像只构建一次，环境差异通过配置挂载解决。

```bash
sh deploy/shell/build.sh
sh -n deploy/shell/*.sh
docker build --build-arg VERSION=v1.0.0 -t planet:v1.0.0 .
kubectl apply -f deploy/k8s/secret.game.local.yaml
kubectl apply -k deploy/k8s
```

有 WAL 的工作负载固定单副本并使用独占 PVC。直接提高 replicas 会复用 SID，可能形成双 writer；扩容必须为新实例分配唯一 SID 和存储身份。升级、回退与故障处理见[维护手册](../../docs/maintenance/README.md)，WAL 目录与单写约束见 [Nest 事务与 WAL](../../docs/framework/NEST_TRANSACTION_WAL.md)。
